# 새 세션에서 교재 작성하기

이 문서는 현재 교재의 페이지 구조와 작성·검토 절차를 설명합니다. 새 세션은 루트 `AGENTS.md`, 이 문서, `.moai/context.md`의 진행표를 읽고 시작합니다. 과거 대화나 완성 HTML을 기억하고 있다고 가정하지 않습니다.

학생은 개발을 처음 시작한 사람일 수 있습니다. 짧은 설명을 읽고 Jupyter 셀을 실행한 뒤, 무엇이 달라졌는지 직접 확인하는 교재를 만듭니다. 기본 실습의 흐름은 **개념 설명 → 짧은 코드 → 실제 결과 → 결과를 읽는 방법**입니다.

## 새 챕터를 시작할 때

1. 커리큘럼의 해당 챕터와 앞뒤 학습 내용을 확인하고 절마다 답할 질문을 한 문장으로 적습니다. 이미 정해진 독자·문체·테마를 다시 질문하지 않습니다.
2. [템플릿 사용 안내](_template/README.md)에 따라 챕터와 절의 원본 파일을 만듭니다. 예전 챕터의 전체 본문·출력·기관명·검증 기록을 복제하지 않습니다.
3. 절마다 아래 두 형식 중 하나를 고릅니다. Context rot처럼 현상을 관찰하는 절에 실패·수정 형식을 강제로 넣지 않습니다.
4. 필요한 데이터와 설치 패키지를 준비하고 노트북을 먼저 실행합니다. 결과를 읽은 뒤 설명·도식·복습 문제를 작성합니다.
5. 코드와 설명을 대조한 기록을 챕터의 집필 점검표에 남기고, 작성자와 구분되는 검토자가 다시 읽습니다. 실행 성공만으로 이 검토를 대신하지 않습니다.

템플릿은 작성할 자리를 가진 초안입니다. `[[작성: …]]`를 채우고 실제 실행을 마치기 전에는 발행하지 않습니다. 초안에 과거 실행 번호·출력·검증 해시를 복사해 넣지 않습니다. 새 절을 추가할 때도 기존 파일을 덮어쓰지 않습니다.

## 페이지의 고정 구조

흰색 Jupyter 테마, 입력 번호, 분리된 출력, 셀별 복사, 전체 코드 복사, 노트북 다운로드를 사용합니다. 코드 셀 첫 줄 위에 불필요한 빈 줄을 넣지 않고 복사 버튼은 코드 영역 밖에 둡니다. 학생용 HTML에는 강사 노트·시간 배분·시연 지시를 넣지 않습니다.

| 순서 | 제목 | 작성할 내용 |
| --- | --- | --- |
| 1 | 학습 목표 | 실제 셀을 실행한 뒤 할 수 있는 일 2~4개 |
| 2 | 이 내용을 배우는 이유 | 학생이 마주할 문제와 이번 절에서 해결할 질문 |
| 3 | 앞에서 배운 내용 | 필요한 개념과 준비 방법. 이전 커널의 변수에 의존하지 않음 |
| 4 | 핵심 개념 | 비유·쉬운 정의·구체 예·도식과 읽는 법 |
| 5 | 실행 예제 | 준비 → 설명·코드·관찰 반복 → 값 하나 변경·비교 |
| 6 | 일부러 실패해 보기 / 실험 결과 해석 | 선택한 형식에 맞는 비교 또는 관찰 해석 |
| 7 | 주의할 점과 실무 메모 | 실제 한계, 비용, 버전·데이터 차이, 다음에 확인할 것 |
| 8 | 정리와 다음 절 | 실제로 확인한 내용과 다음 학습의 연결 |
| 9 | 복습 문제 | 이번 코드와 관찰로 답할 수 있는 문제 3~5개와 해설. 확장은 따로 표시 |
| 10 | 참고 자료 | 공식 자료 URL·확인 날짜·검증한 버전 |

페이지 제목과 목차는 같은 제목을 사용합니다. 그림의 축·색·점·화살표가 뜻하는 것을 설명하고, 실제 예제의 값 하나로 읽는 방법을 보여 줍니다. 미래에 구현할 단계는 “후속 단계”로 표시합니다. 예를 들어 HWPX 문자열 추출만 실행했다면 Document 변환까지 실행한 도식으로 표시하지 않습니다.

## Before/After형과 실험 해석형

### Before/After형: 같은 원인을 고쳐 비교합니다

기본 실행으로 정상 결과를 먼저 확인합니다. 이후 **Before 코드·실제 결과 → 원인 설명 → After 코드·실제 결과 → 무엇이 해결됐는지**를 보여 줍니다. 설명만 쓰거나 예정된 오류 메시지만 출력하지 않습니다.

질문·원문·정답 기준·모델은 유지하고, 원인에 해당하는 조건을 바꿉니다. 여러 조건을 바꿔야 한다면 각각의 역할과 비교의 한계를 적습니다. 새 정보가 필요하다면 어디서 확인했는지, 또는 실습을 위해 어떤 가정을 추가했는지 명시합니다. 출처나 시행일을 임의로 만들어 실제 자료를 복구했다고 설명하지 않습니다.

| 피할 예 | 이 주제에서 확인할 결과 |
| --- | --- |
| Select를 설명하며 `require_context([])`의 예외만 관찰 | 같은 질문에서 근거를 메시지에 넣지 않은 실제 답과 선택한 근거를 넣은 실제 답 |
| 규정 충돌을 설명하며 “시행일:” 문자열 유무만 검사 | 서로 맞지 않는 두 규정에 대한 실제 답, 확인한 시행일로 규정을 선택한 뒤의 실제 답 |
| 청킹을 설명하며 잘못된 인자의 타입 오류만 관찰 | 같은 원문에서 청크 경계에 잘린 단어·조건과 설정을 고친 뒤 남은 본문 |
| 출처 누락을 고치며 `page=1`을 새로 대입 | 실제 문서에서 가져온 쪽 번호가 검색·생성 과정에 유지되는지 확인 |
| 캐시 파일 수가 같다는 이유로 API 호출 0회라고 단정 | 파일 수는 파일 수로 설명. 호출 수 주장은 별도 측정이 있을 때만 사용 |

`assert`는 관찰한 결과를 확인하는 보조 수단입니다. 개발자가 직접 만든 검사 함수가 예상대로 예외를 냈다는 사실은 환각·검색 실패·컨텍스트 문제의 증거가 아닙니다. 단, 타입 오류나 예외 처리 자체를 가르치는 절은 해당 오류를 직접 다룰 수 있습니다.

근거가 없어 “모른다”고 답하거나 충돌을 발견해 “확인이 필요하다”고 답하면 그 자체를 모델의 실패로 기록하지 않습니다. 정보가 빠진 프로그램, 아직 답을 정할 수 없는 자료 상태, 모델의 잘못된 답을 구분해서 설명합니다.

노트북의 꼬리 셀에는 설명 셀까지 `metadata.lesson_part="before"` 또는 `"after"`를 지정합니다. HTML 5번에는 `{{notebook:절|example}}`, 6번에는 `{{notebook:절|failure}}`를 한 번씩 넣습니다. PC에서는 좌우 비교, 모바일에서는 Before 다음 After 순서로 읽습니다.

### 실험 해석형: 관찰한 범위에서 결론을 냅니다

길이별 정답률, 청크 분할 기준, 색인 설정처럼 결과를 측정하는 절에 사용합니다. 노트북에 `metadata.lesson_format="experiment"`를 지정하고 Before/After 태그를 넣지 않습니다. 모든 실행 코드는 5번에 넣고 6번 “실험 결과 해석”에는 실제 관찰과 한계를 설명합니다.

Context rot 실험이라면 질문·정답 근거·모델 등을 유지하고 입력 길이에 따른 정답률을 측정합니다. 입력 토큰이 늘었다는 사실만으로 성능 저하를 확인했다고 쓰지 않습니다. 세 길이에서 모두 정답이었다면 그 조건에서는 저하를 관찰하지 못했다고 적습니다. 실패를 얻으려고 질문·정답·채점 기준을 중간에 바꾸지 않습니다.

청크 수가 적어진 것과 검색 품질이 좋아진 것은 다른 관찰입니다. 한 질문에서 나온 결과로 모델 전체의 우열을 단정하지 않습니다. 반복 횟수와 조건을 먼저 정하고 결과 원문을 읽어 판정합니다.

## 초보자가 복사해서 실행할 수 있는 코드

- 노트북 하나를 새 Python 3.12 커널에서 독립 실행합니다. 첫 셀부터 실행하면 설치·import·데이터·변수가 모두 준비되어야 합니다.
- 셀 하나에는 한 가지 학습 행동을 둡니다. 기본 3~15줄, 최대 25줄을 기준으로 나누고 필요한 설명을 생략해 줄 수만 줄이지 않습니다.
- 주요 변수의 의미, 인자의 단위, 반환값, 낯선 문법과 처리 이유를 한국어 주석으로 설명합니다. 코드 앞에서 실행 목적을, 뒤에서 관찰할 값을 짚습니다.
- 여러 줄 문서와 프롬프트는 삼중 큰따옴표와 실제 줄바꿈으로 작성합니다. `"\n".join(...)`처럼 구분자가 필요한 연산은 그대로 사용합니다.
- 기본 생성 코드는 LangChain의 `init_chat_model` → `invoke` → `AIMessage.text`, 임베딩은 `OpenAIEmbeddings`를 사용합니다. 직접 SDK 실습이 명시된 절은 그 예외를 설명합니다.
- `.env`를 현재 폴더부터 상위 폴더에서 찾고 키의 존재만 확인합니다. 비밀 값이나 전체 환경 변수를 출력하지 않습니다.
- 학생 코드에 프로젝트 전용 모듈, `sys.path` 변경, `__file__`, 개인 절대 경로를 요구하지 않습니다. 파일이 필요하면 제공 자료와 상대 경로를 안내합니다.
- 기본 실습은 완성 코드입니다. 과제용 빈칸·TODO는 요청된 별도 과제본에 둡니다. 공통 클래스·모듈·설정 시스템 구현은 그것이 학습 목표일 때만 기본 경로에 넣습니다.
- 개발 입문자가 이해하기 어려운 추상어는 구체적인 상황으로 풉니다. 필요한 기술 용어는 뜻과 예를 먼저 설명하고, 가능성·예외·적용 범위는 유지합니다.

## 코드와 교재가 같은 이야기를 하는지 확인하기

집필 점검표에는 다음 내용을 실제 셀·출력과 연결해 기록합니다. “통과”만 적지 않습니다.

| 확인 항목 | 기록할 내용 |
| --- | --- |
| 학습 질문 | 이 절에서 학생이 답할 질문 하나 |
| 입력과 비교 조건 | 같은 값, 바꿀 값, 질문·원문·정답 기준 |
| 실제 연산 | 호출하는 메서드나 실행하는 처리와 해당 셀 |
| 관찰 결과 | 원문·출처·조건·숫자 등 출력에서 확인한 구체 값 |
| Before/After 또는 실험 | 실패 원인·수정 이유 또는 비교 조건·반복 수·관찰/미관찰 |
| 해석 범위 | 결과가 보여 주는 것, 추가 측정 없이는 알 수 없는 것 |
| 본문과 그림 | 목표·정의·해설·캡션·복습이 실제 코드와 일치하는지 |
| 별도 검토 | 지적, 수정 위치, 다시 확인한 실행 결과 |

특히 “자료를 필터에 사용함”과 “모델에 전달함”과 “답에 표시함”을 구분합니다. 기관·주제·날짜로 자료를 선택하고 본문·ID만 전달했다면 날짜까지 답에 유지했다고 설명하지 않습니다. 단어 포함 검사만으로 조건 전체가 보존됐다고 하지 말고 실제 본문을 읽습니다.

## 실행·빌드·발행 순서

정본은 본문 `_src/*.html`과 `labs/.../notebooks/*.ipynb`입니다. 생성된 완성 HTML은 직접 수정하지 않습니다. 공통 화면은 `_notebook/theme.css`·`copy.js`, 실행 셀은 `_notebook/render.py`, 신규 챕터 골격은 `_template/`에서 관리합니다.

아래 경로 변수는 해당 챕터의 실제 상대 경로로 바꿉니다. 챕터 `pyproject.toml`·`uv.lock`에 검증할 패키지를 고정한 뒤 실행합니다. 노트북 설치 셀도 같은 버전을 사용합니다.

```bash
LAB_CHAPTER="labs/part3/ch11-evaluation"
TEXTBOOK_CHAPTER="textbook/part3/ch11-evaluation"
uv run --project "$LAB_CHAPTER" --with nbclient==0.11.0 --with ipykernel==7.3.0 --with pip --with python-dotenv==1.2.3 python textbook/_notebook/execute.py "$LAB_CHAPTER"/notebooks/*.ipynb
uv run --project "$LAB_CHAPTER" --with pillow python "$TEXTBOOK_CHAPTER/_build.py"
uv run --project "$LAB_CHAPTER" python textbook/_notebook/verify.py --chapter "$TEXTBOOK_CHAPTER"
node textbook/_notebook/visual.cjs "$TEXTBOOK_CHAPTER"
```

위 Ch11 경로는 명령 형식을 보여 주는 예입니다. Node 화면 검사는 Playwright와 Chromium이 있는 실행 환경에서 실행합니다. 새 챕터 생성 명령과 필요한 작성 파일은 템플릿 안내를 따릅니다.

코드를 수정하면 새 커널에서 다시 실행하고 출력·숫자 해설을 함께 갱신합니다. 문장만 고쳤다면 코드와 출력이 그대로인지 확인합니다. 실행기는 오류·미실행·실행 후 변경된 코드/출력을 거부합니다. 정적 검사와 별도로 주제 검토를 수행합니다.

발행 전에는 PC 1280px·모바일 390px에서 본문 16px 이상, 코드·캡션 14px 이상, 대비·잘림·가로 넘침·그림 경계·복사·다운로드 일치를 확인합니다. 원본 코드와 HTML에서 복사한 코드가 같아야 합니다.

새 챕터를 학생 시작 화면과 묶음에 넣을 때는 `_notebook/build_index.py`의 챕터 목록과 `_notebook/build_bundle.py`의 발행 목록·필요 데이터 목록을 등록하고 두 도구를 실행합니다. 이 등록은 현재 자동이 아닙니다. 공개할 자료만 명시하고 `.env`·정답 자료·개인 경로가 묶음에 들어가지 않았는지 확인합니다. 도구 안의 기존 챕터 예외를 새 챕터에 무조건 복제하지 않습니다. 직접 SDK를 배우는 Ch18처럼 검증 규칙의 예외가 필요한 절은 커리큘럼 근거와 해당 범위를 검증기에 명시하고, 다른 절의 검사를 약화하지 않습니다.
