05절까지 노트북에서 설정값을 직접 바꾸고 결과를 화면으로 확인했습니다. 몇 번은 기억할 수 있지만 Ch 12는 5일 동안 "가설 → 설정 변경 → 평가 실행 → 표에 한 줄"을 30번 이상 반복합니다. 커리큘럼은 이 절의 이유를 한 문장으로 적어 두었습니다. "이게 없으면 Chapter 12에서 5일 동안 실험을 세 번밖에 못 돌립니다."(커리큘럼 원문)

하네스가 하는 일은 세 가지뿐입니다. 설정을 한 곳에 모은다. 실행한다. 한 줄 기록한다. 지표는 아직 없습니다. Ch 11이 지표를 만들면 하네스의 빈칸에 들어옵니다. 순서가 중요합니다. 지표 없이 튜닝하면 "느낌으로 좋아졌다"가 되고, 하네스 없이 지표만 있으면 실험을 실행할 때마다 손으로 표를 채우게 됩니다.

4핵심 개념

비유 — 실험 노트

설정을 바꿀 때마다 한 줄이 쌓이는 실험 노트가 없으면, 5일이 지나도 무엇을 해 봤는지 모릅니다. 화학 실험실에서 시약의 양을 바꿔 가며 반응을 볼 때, 연구자는 매번 노트에 한 줄을 씁니다. 날짜, 조건, 결과. 노트가 없으면 "어제 그 조건이 무엇이었더라"를 찾는 데 하루가 걸립니다. 하네스는 그 노트를 자동으로 쓰는 장치입니다. 설정 다이얼을 돌리고(YAML) 실행하면(한 명령) 노트에 한 줄이 생깁니다(JSONL).

정의

실험 하네스 (experiment harness)
설정을 입력받아 파이프라인을 실행하고 결과를 정해진 형식으로 기록하는 실행기입니다. 기본 노트북은 이 역할을 셀 단위로 보여 주며, 전체 말뭉치 선택 확장은 실행기를 rag.py와 분리합니다.
설정 파일 (config.yaml)
전체 말뭉치 선택 확장에서 바꿀 수 있는 값을 모아 둔 파일입니다. 기본 노트북은 같은 구조를 파이썬 딕셔너리로 먼저 확인합니다.
실행 (run) · run_id
설정 하나로 질의셋을 한 번 실행하는 단위입니다. 기본 노트북은 name=k2인 한 행을 기록하고, 선택 확장은 시각과 이름을 합친 run_id로 요약과 상세 파일을 구분합니다.
설정 해시 (config hash) · 캐시
색인 결과를 좌우하는 설정(문서·청크·임베딩)만 골라 짧은 문자열로 만든 것입니다. 같은 해시면 색인을 다시 만들지 않고 저장된 것을 씁니다. k나 프롬프트를 바꾸어도 이미 만든 같은 색인을 재사용하면 문서 청크의 재임베딩 비용은 0입니다. 질문 임베딩과 생성 호출 비용은 별도로 발생합니다.
JSON Lines (JSONL)
한 줄에 JSON 객체 하나를 두는 파일 형식입니다. 줄을 덧붙이기만 하면 되고, 한 줄이 깨져도 나머지는 읽힙니다. queries.jsonl과 runs.jsonl이 이 형식입니다.

도식 — 루프

기본 노트북과 선택 확장

기본 노트북은 중첩 딕셔너리의 설정을 바꾸고, 색인 설정의 SHA-256 해시로 캐시 재사용 여부를 판단하며, 실행 결과를 JSONL 한 행에 추가한 뒤 다시 읽습니다. 전체 말뭉치 선택 확장은 이 값을 config.yaml에 모으고 corpus·split·embedding·retrieval·generation 설정을 한 명령으로 바꿀 수 있게 합니다.

설정 덮어쓰기와 해시

기본 노트북의 override()는 점으로 구분한 키의 값을 바꾸고, index_key()는 split과 embedding 설정을 해시합니다. 문서는 이 예제에서 고정되어 있습니다. 다음 설명은 문서 범위와 YAML 입력까지 관리하는 전체 말뭉치 선택 확장에 해당합니다.

load_config()의 마지막 줄이 요점입니다. --set split.chunk_size=1000에서 "1000"은 문자열로 들어오는데, yaml.safe_load("1000")이 정수 1000으로 바꿔 줍니다. "[easy]"는 리스트가 됩니다. 이 한 줄이 없으면 chunk_size="1000"이 스플리터에 들어가 오류가 납니다. index_key()는 설정 딕셔너리 중 색인에 영향을 주는 세 덩어리만 골라 해시합니다. retrieval.k나 generation.prompt는 넣지 않습니다. 그래서 k만 바꾼 실험은 캐시를 그대로 씁니다.

기록 한 행

기본 노트북의 한 행에는 설정 이름, 설정 해시, 캐시 적중 여부, 검색 문서 ID가 들어갑니다. 임시 JSONL 파일에 실제로 한 행을 추가하고 다시 읽습니다. 전체 말뭉치 선택 확장은 규모·토큰·비용을 더해 runs.jsonl에 저장하고 질문별 상세를 별도 파일로 남깁니다. 확장의 metrics는 아직 비어 있으며 Ch 11에서 채웁니다.

7주의할 점과 실무 메모

  • 비용 추정의 정확도. 생성 토큰은 응답 메타데이터에서 정확히 오지만, 임베딩 토큰은 OpenAIEmbeddings가 알려 주지 않아 글자 수 ÷ 1.2로 어림했습니다(02절 실측 498자 = 431개의 토큰). 이 추정치가 실제 청구액과 얼마나 다른지는 확인하지 않았습니다. 정확한 값이 필요하면 tiktoken으로 세어 넣으면 됩니다.
  • 요금은 바뀝니다. prices 칸의 값은 2026-09-07 확인값이며 확인 날짜를 주석에 적어 두었습니다. 요금표 URL을 함께 적어 두면 나중에 갱신할 때 어디를 볼지 압니다.
  • 지연 시간은 평균만으로 부족합니다. 전체 말뭉치 선택 확장은 latency_mean_s만 기록하지만 Ch 15는 p50/p95/p99를 요구합니다. 상세 파일에 질문별 지연을 추가하는 작업은 B트랙 과제입니다.
  • 동시 실행과 로그 경쟁. runs.jsonl에 덧붙이기("a" 모드)는 한 프로세스일 때 안전합니다. Ch 12에서 실험을 병렬로 실행하면 줄이 섞일 수 있습니다. 병렬 실행 시에는 실행마다 파일을 따로 쓰고 나중에 합칩니다.
  • .cache/와 runs/는 git에 넣지 않습니다. 색인 파일은 수 MB이고 실행 로그는 개인 실험 기록입니다. 프로젝트 .gitignore에 .cache/가 들어 있습니다. 다만 Ch 12의 실험 로그 30건은 중간 프로젝트 리포트의 근거이므로 Ch 12에서는 runs.jsonl만 따로 보관합니다.

8정리와 다음 절

  • 기본 노트북은 설정 덮어쓰기 → 색인 설정 해시 → 캐시 판단 → JSONL 한 행 기록의 순서로 하네스 원리를 확인합니다.
  • k만 바꾸면 색인 해시가 같아 기존 벡터스토어를 재사용하고, 청크 크기를 바꾸면 해시가 달라 새 색인이 필요합니다.
  • 기본 JSONL 행에는 설정 해시·캐시 적중 여부·검색 문서 ID가 있습니다. 전체 말뭉치 확장은 여기에 규모·비용을 더하고, Ch 11은 품질 지표를 추가합니다.

다음 학습과 이어지는 지점 — Ch 10의 현재 노트북은 원문 하나로 청킹 3종과 임베딩 2종을 비교합니다. 커리큘럼의 "문서 100건 × 3 청킹 × 2 임베딩"은 자료 확보 후 진행할 전체 말뭉치 확장 목표이며, 기존 하네스의 --set으로 조합을 바꿀 수 있습니다. Ch 11은 상세 파일의 gold_doc_id와 retrieved를 비교하는 Recall@k·Precision@k 함수를 만들어 metrics 칸에 넣습니다. Ch 12는 이 루프를 5일 동안 30번 이상 실행하고, 그 runs.jsonl이 중간 프로젝트 평가 리포트의 뼈대가 됩니다. Ch 15는 여기에 judge 점수와 p95 지연을 더합니다. 이 챕터는 여기서 마무리됩니다. 다음은 Ch 10 문서 처리입니다.

9복습 문제

문제 4개 · 해설 포함

1. 기본 노트북에서 retrieval.k를 1에서 2로 바꾸어도 색인을 다시 만들지 않는 이유는 무엇입니까?

index_key()가 split과 embedding만 해시하므로 retrieval.k가 바뀌어도 해시가 같습니다. 기본 노트북은 같은 해시 키의 메모리 벡터스토어를 재사용합니다.

2. 전체 말뭉치 선택 확장에서 청크 1,000과 k=8은 비용 구조가 어떻게 다릅니까?

청크 1000은 색인을 다시 만들어야 하고(임베딩 비용·시간) 이 실행에서는 청크 하나가 길어져 입력 토큰이 약 1.6배가 되었습니다. k=8은 색인은 그대로이고 입력 토큰만 약 1.8배가 되었습니다. 어느 쪽이 답을 더 잘 맞히는지는 지표가 있어야 알 수 있습니다.

3. 전체 말뭉치 선택 확장의 Q008에서 기준선은 E02 2쪽을 가져왔는데도 "찾을 수 없습니다"였습니다. 쪽 단위 로그만 보면 생성 실패로 보입니다. 실제 원인은 무엇이고, 어떻게 알 수 있었습니까?

검색 실패입니다. 가져온 것은 2쪽의 첫 청크(#9, 환영 인사)였고 급여일이 있는 청크(#10)는 5위였습니다. 로그에 chunk_id를 함께 적어야 드러납니다. 기록 단위는 검색 단위(청크)와 같아야 하고, 검색 지표(정답 청크가 k개 안에 있었나)와 생성 지표(답이 맞았나)를 나눠 기록해야 합니다.

4. 전체 말뭉치 선택 확장의 runs.jsonl 한 줄에 아직 없는 것과, 그것을 채우는 챕터를 쓰세요.

품질 지표(metrics: {})와 지연의 분포(p95 등)입니다. 검색·생성 지표는 Ch 11, judge 점수와 p50/p95/p99는 Ch 15가 채웁니다.

시연 순서 — ① 기준 설정에서 retrieval.k와 split.chunk_size를 각각 덮어쓰기 ② 세 설정의 해시를 나란히 출력 ③ 문서 두 건을 실제 임베딩해 해시 키로 캐시에 저장 ④ k=2가 같은 객체를 재사용하는지 확인 ⑤ 실행 기록을 JSONL에 추가하고 다시 읽기 ⑥ 청크 크기 변경의 해시 검사 실패를 보여 준 뒤 선택 확장의 빈 metrics로 Ch 11 예고.

예상 질문 — "지금 정답 문서 ID가 있으니 Recall을 바로 계산하면 안 되나요?" → 계산할 수 있으며 B트랙에서는 시도하되, 지표를 어떻게 나눠 측정할지(Recall@50 vs Precision@5)와 무엇을 맞다고 볼지가 Ch 11의 내용이므로 Ch 11에서 정식으로 다룬다고 답함. "YAML 대신 파이썬 딕셔너리로 하면요?" → 기본 노트북처럼 사용할 수 있으며, 실험이 늘어나면 설정 파일로 분리해 변경 이력을 관리할 수 있다고 답함. "MLflow 같은 도구를 쓰면요?" → 나중에 사용해도 되며, 그 도구의 역할을 이해하려고 짧은 셀로 설정 변경·캐시·기록의 관계를 먼저 확인한다고 답함.

학생이 막히는 지점 — 검색 설정과 색인 설정을 해시에서 구분하는 점, 해시 문자열 자체보다 같고 다름을 읽어야 한다는 점, "a" 모드가 기존 JSONL 뒤에 행을 추가한다는 점. 선택 확장에서는 상대 경로와 디스크 캐시 규칙을 추가로 확인합니다.

A/B 트랙 — A트랙은 기본 노트북의 덮어쓰기·해시·캐시·JSONL까지. B트랙은 선택 확장으로 넘어가 ① Pydantic 설정 스키마 ② 질문별 지연과 p95 ③ gold_doc_id in retrieved 비율을 세는 함수를 추가합니다(Ch 11 예행, 이름은 아직 Recall이라 부르지 않게 함).
