1학습 목표

  • 이 절을 마치면 한국어 검색용 임베딩 모델을 언어·길이·차원·입력 규칙·비용 기준으로 비교할 수 있습니다.
  • 이 절을 마치면 영어 종합 벤치마크 순위를 한국어 도메인 검색 품질로 해석하면 안 되는 이유를 설명할 수 있습니다.
  • 이 절을 마치면 텍스트와 모델 설정을 포함한 캐시 키를 만들고, 같은 입력의 두 번째 임베딩에서 캐시 적중을 확인할 수 있습니다.
  • 이 절을 마치면 인덱스 재구성과 벡터 재계산을 구분해 변경된 청크만 다시 임베딩하는 원칙을 적용할 수 있습니다.

2왜 지금 이것인가

05·06절에서 청크 경계를 여러 방식으로 만들었습니다. 다음 단계는 각 청크를 벡터로 바꾸는 일입니다. Ch 9에서는 첫 RAG를 완주하기 위해 text-embedding-3-small 하나를 임시로 사용했습니다. 이번 절에서는 모델 이름을 설정 한 줄로 취급하지 않고, 한국어 질문과 문서를 같은 검색 공간에 놓기 위해 어떤 입력 규칙과 기록이 필요한지 확인합니다.

임베딩 모델을 바꾸면 모든 벡터의 좌표계가 달라집니다. 같은 모델이라도 차원, 리비전, 문서·질의 접두사가 바뀌면 이전 벡터를 그대로 사용할 수 없습니다. 반면 스플리터 설정이 바뀌어도 결과 청크 가운데 텍스트가 정확히 같은 항목은 같은 모델 설정에서 벡터를 재사용할 수 있습니다. 이 차이를 알면 인덱스는 다시 구성하되 불필요한 API 호출은 줄일 수 있습니다.

이 절에서 언급하는 모델은 비교 후보입니다. 이 과정의 최종 모델은 [[미정: 임베딩 모델]]이며, Ch 11에서 한국어 질의셋의 검색 지표를 계산하기 전에는 확정하지 않습니다. 작은 모델과 큰 모델이라는 이름도 품질의 결론이 아닙니다. 차원·비용·입력 길이가 다른 두 기능 예제로 사용합니다.

3선수 지식 되짚기

  • Ch 5 임베딩 — 텍스트를 고정 길이 벡터로 바꾸고 코사인 유사도를 계산했습니다. 이번 절은 모델 선택과 입력 규칙, 재사용 가능 조건을 다룹니다.
  • Ch 9 build_index() — 청크를 임베딩해 벡터스토어에 저장했습니다. 당시 파일명에 모델을 넣은 이유를 캐시 키와 인덱스 매니페스트로 확장합니다.
  • 05·06절 청킹 — 청크 텍스트가 임베딩 함수의 입력입니다. 경계가 바뀌면 새 청크가 생기지만, 변경 뒤에도 텍스트가 같은 청크는 벡터 캐시를 재사용할 수 있습니다.

4핵심 개념

비유 — 같은 주소 체계와 보관함 표찰

서로 다른 도시의 지도 좌표를 한 표에 섞으면 거리를 비교할 수 없습니다. 청크는 A 모델로, 질문은 B 모델로 변환한 뒤 가까운 것을 찾는 일도 마찬가지입니다. 모델과 차원, 입력 규칙이 같아야 같은 주소 체계입니다. 한 번 계산한 좌표를 보관할 때는 어느 주소 체계로 만들었는지 표찰을 붙여야 합니다. 캐시 키가 그 표찰입니다.

정의

다국어 임베딩 (multilingual embedding)
여러 언어의 텍스트를 검색·분류 같은 작업에 사용할 수 있도록 벡터로 표현하는 모델입니다. 지원 언어 목록은 후보 조건이며 특정 한국어 업무 문서에서 높은 검색 품질을 보장하지 않습니다.
차원 (dimension)
임베딩 벡터에 들어 있는 숫자의 개수입니다. 차원이 커지면 저장 공간과 거리 계산량이 늘어날 수 있으며, 차원 수만으로 품질을 판단할 수 없습니다.
모델 리비전 (model revision)
같은 모델 이름 아래에서 사용한 정확한 코드·가중치 버전입니다. 로컬 오픈 모델은 커밋 SHA를 기록하고, API 모델은 공급자가 제공하는 고정 버전 식별자를 사용할 수 있는지 확인합니다.
입력 접두사 (input prefix)
모델 카드가 문서와 질의를 구분하기 위해 요구하는 앞부분입니다. 예를 들어 문서에는 passage: , 질의에는 query: 를 붙이는 모델이 있으며 생략하면 모델 카드가 설명한 검색 방식과 달라집니다.
벡터 캐시 (vector cache)
같은 정규화 텍스트와 같은 임베딩 설정으로 계산한 벡터를 다시 사용하기 위한 저장소입니다. 캐시 키가 입력과 설정을 빠짐없이 구분해야 잘못된 벡터 혼용을 막을 수 있습니다.
인덱스 매니페스트 (index manifest)
원문, 파서, 청킹 설정, 청크 ID와 벡터 캐시 키의 대응을 기록한 목록입니다. 인덱스를 어떻게 구성했는지 재현하고 변경 범위를 판단하는 근거가 됩니다.

모델 후보를 읽는 순서

첫째, 문서와 질문의 언어가 지원 범위에 있는지 봅니다. 둘째, 최대 입력 길이가 현재 청크의 토큰 길이를 수용하는지 확인합니다. 셋째, 문서와 질의에 서로 다른 접두사나 프롬프트가 필요한지 모델 카드를 읽습니다. 넷째, 차원과 실행 위치, 라이선스, API 단가를 기록합니다. 마지막으로 한국어 질의셋에서 검색 결과를 측정합니다. 앞의 네 조건은 실행 가능한 후보를 고르는 기준이고, 마지막 측정은 이 도메인에 맞는 후보를 판단하는 기준입니다.

OpenAI의 text-embedding-3-small과 text-embedding-3-large는 기본 차원이 각각 1,536과 3,072이며 dimensions 옵션으로 축소할 수 있습니다. 2026-09-08 확인 단가는 100만 토큰당 각각 미화 0.02달러와 0.13달러입니다. 이 값은 비용 예측에 쓰며 한국어 순위를 뜻하지 않습니다. 공급자가 제공하는 영문 또는 다국어 벤치 결과도 후보 선정 자료일 뿐, 우리 문서의 정답률이 아닙니다.

로컬 오픈 모델 후보로는 intfloat/multilingual-e5-large와 BAAI/bge-m3를 조사했습니다. 두 모델 카드 모두 다국어 지원과 1,024차원을 명시합니다. E5는 검색 입력에 passage: 와 query: 접두사를 요구하고 최대 길이가 512개의 토큰입니다. BGE-M3는 최대 8,192개의 토큰과 dense·sparse·multi-vector 기능을 설명하지만, 이 장의 비교 범위에서는 dense 벡터만 사용합니다. 이 두 모델도 최종 선택이 아니라 공개된 모델 카드와 고정 리비전을 가진 후속 비교 후보입니다.

영어 순위가 한국어 순위가 아닌 이유

MTEB는 모델·과제·언어별 평가를 모으는 평가 모음입니다. 종합 점수 한 줄에는 여러 언어와 분류·검색·군집화 같은 서로 다른 과제가 섞일 수 있습니다. 영어 검색 과제에서 높은 모델이 한국어 사내 규정의 조사·고유명사·표현 변형에서도 같은 순위를 유지한다는 보장은 없습니다. 리더보드를 사용할 때는 Korean retrieval 과제를 별도로 보고, 최종 결정은 이 과정의 한국어 질문과 정답 문서로 측정합니다.

캐시 키와 인덱스 매니페스트를 분리합니다

운영용 벡터 캐시 키에는 정규화된 청크 텍스트의 해시, 제공자, 모델, 리비전, 차원, 문서 입력 접두사와 전처리 버전을 포함합니다. 이 절의 작은 구현은 정확한 입력 텍스트, 제공자, 모델, 버전, 차원, 입력 접두사를 직렬화해 해시합니다. 전처리가 생기면 그 구현 리비전을 version에 반영하거나 별도 필드로 확장해야 합니다. 이 값이 모두 같으면 스플리터를 바꾼 뒤에도 텍스트가 같은 청크의 벡터를 재사용할 수 있습니다. 모델이나 리비전, 차원, 접두사가 다르면 같은 텍스트도 다시 임베딩합니다.

인덱스 매니페스트에는 원문 해시, 파서와 정규화 버전, 청킹 방식과 크기·오버랩, 청크 ID, 각 청크가 참조하는 벡터 캐시 키를 적습니다. 청킹 설정이 바뀌면 청크의 순서와 ID 대응이 달라지므로 인덱스는 다시 구성합니다. 그러나 새 인덱스를 구성한다는 말이 모든 벡터 API를 다시 호출한다는 뜻은 아닙니다. 새로 생기거나 텍스트가 바뀐 청크만 캐시 미스로 계산합니다.

두 번 실행해 적중과 미스를 분리하기

embed_with_cache()는 제공자·모델·버전·차원·접두사를 인자로 드러내고 EmbeddingCache에 전달합니다. 캐시는 키에 해당하는 JSON 파일이 있으면 벡터를 읽고, 없는 텍스트만 묶어 임베딩 함수에 전달합니다. 첫 실행의 미스 수와 두 번째 실행의 적중 수를 따로 반환하므로 캐시가 실제로 사용되었는지 로그로 확인할 수 있습니다. 비용 함수는 cl100k_base 토크나이저로 입력 토큰을 세고 확인한 단가를 곱한 추정값입니다. 다른 제공자나 모델에는 해당 토크나이저와 단가를 그대로 사용하지 않습니다.

7주의할 점과 실무 메모

  • 최종 모델은 미정입니다. 이 절의 small·large API 후보와 두 오픈 모델은 비교 틀을 보여 줍니다. 한국어 검색 지표와 운영 조건을 확인하기 전에는 하나를 정본으로 선언하지 않습니다.
  • 입력 규칙을 모델 카드에서 확인합니다. 문서와 질의 접두사, 최대 길이, 정규화 권고가 모델마다 다릅니다. 후보 이름만 바꾸고 같은 입력 함수를 쓰면 공정한 비교가 아닙니다.
  • 가격에는 확인일을 붙입니다. API 단가는 바뀔 수 있습니다. 로그에는 실제 입력 토큰 합계와 단가, 통화, 확인일을 함께 남깁니다.
  • 캐시에 원문을 저장하는 문제. 캐시 파일에 벡터만 저장해도 키 생성 과정에서 원문 해시를 사용합니다. 민감 문서라면 캐시 경로의 접근 권한과 보존 기간을 별도로 정합니다.

8정리와 다음 절

  • 임베딩 후보는 언어·입력 길이·차원·접두사·리비전·비용을 확인한 뒤 한국어 검색 질의셋으로 측정합니다.
  • 영어 또는 종합 벤치마크의 순위는 한국어 도메인 검색 순위를 보장하지 않습니다.
  • 벡터 캐시 키와 인덱스 매니페스트를 분리하면 인덱스를 다시 구성하면서도 정확히 같은 청크의 벡터를 재사용할 수 있습니다.

다음 학습과 이어지는 지점 — 다음 절은 세 청킹 설정과 두 임베딩 후보를 3×2 격자로 실행합니다. 캐시의 첫 번째·두 번째 실행 적중 수와 인덱싱 시간은 기록하지만, 검색 품질 지표는 Ch 11에서 채웁니다.

9복습 문제

문제 4개 · 해설 포함

1. 임베딩 벡터 캐시 키에 포함해야 하는 항목을 네 가지 이상 쓰세요.

운영용 키에는 정규화된 청크 텍스트 해시, 제공자, 모델, 리비전, 차원, 문서 또는 질의 입력 접두사, 전처리 버전을 포함합니다. 이 절의 구현은 정확한 텍스트와 제공자·모델·버전·차원·접두사를 사용합니다.

2. 영어 검색 벤치마크에서 1위인 모델을 한국어 사내 문서 검색의 최종 모델로 바로 선택하면 안 되는 이유는 무엇입니까?

언어와 과제, 문서 형식, 고유명사와 질문 분포가 다르기 때문입니다. 영어 순위는 후보 근거이며 한국어 retrieval 과제와 우리 질의셋의 Recall@k를 별도로 측정해야 합니다.

3. 청킹 설정을 바꾸면 인덱스는 다시 구성해야 합니다. 그런데 모든 청크를 재임베딩할 필요가 없는 경우를 설명하세요.

변경 전후에 정규화된 청크 텍스트가 정확히 같고 제공자·모델·리비전·차원·접두사·전처리도 같으면 기존 벡터 캐시를 사용할 수 있습니다. 새로 생기거나 내용이 바뀐 청크만 계산합니다.

4. E5 후보의 문서 접두사를 생략한 실행과 BGE-M3의 dense 모드 실행을 비교했습니다. 결과 해석 전에 확인할 조건을 쓰세요.

E5 모델 카드가 요구하는 passage: 와 query: 접두사를 적용해 다시 실행해야 합니다. 두 모델의 최대 길이, 잘린 입력, 고정 리비전, 정규화 방식, dense 벡터 사용 범위도 기록해야 공정하게 비교할 수 있습니다.

시간 배분(3h) — 강의 60분: 모델 후보 읽기(15) · 영어 벤치와 한국어 질의셋 구분(10) · 캐시 키(15) · 인덱스 매니페스트와 부분 재임베딩(20). 실습 120분: 캐시 첫 실행(20) · 두 번째 실행 적중 확인(20) · 키 요소 변경 실험(30) · 비용 추정(20) · 매니페스트 설계(30).

시연 순서 — ① 두 문장을 캐시가 없는 상태에서 실행 ② 같은 조건으로 다시 실행해 적중 수 확인 ③ 버전이나 전처리 설정 하나를 바꾸어 미스 발생 확인 ④ 청크 목록 하나만 변경하고 불변 텍스트의 키 비교 ⑤ 모델 카드에서 접두사·차원·최대 길이·리비전 찾기.

예상 질문 — “large가 항상 더 좋은가요?” → 이름과 차원만으로 한국어 검색 품질을 결론낼 수 없으며 자체 질의셋으로 측정합니다. “스플리터를 바꾸면 캐시를 전부 지워야 하나요?” → 인덱스는 재구성하지만 텍스트와 임베딩 조건이 같은 벡터는 재사용할 수 있습니다. “MTEB 1위면 충분하지 않나요?” → 해당 언어·검색 과제를 보고 우리 도메인 결과와 분리해야 합니다.

학생이 자주 막히는 지점 — 모델 이름만 기록하고 리비전·차원·접두사를 빠뜨리는 경우, 교육용 특징 벡터를 실제 임베딩 품질 결과로 해석하는 경우, 인덱스 파일과 벡터 캐시를 같은 것으로 생각하는 경우를 확인합니다.

A/B 트랙 — A트랙은 제공된 캐시 예제로 적중·미스와 비용 추정을 재현합니다. B트랙은 정규화 텍스트 해시와 전체 설정을 포함한 매니페스트를 JSON으로 만들고, 한 청크를 수정했을 때 재계산 대상만 출력합니다.
