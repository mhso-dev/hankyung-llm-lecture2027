1학습 목표

  • 데코레이터가 함수를 받아 새 함수를 반환하는 과정을 설명할 수 있습니다.
  • functools.wraps로 원래 함수의 이름·설명·서명을 유지할 수 있습니다.
  • contextmanager와 try/finally로 예외 발생 여부와 관계없이 자원을 정리할 수 있습니다.

2이 내용을 배우는 이유

여러 함수에서 호출 시각 기록, 권한 확인, 재시도 같은 공통 처리를 반복하면 핵심 기능보다 부가 코드가 많아집니다. 데코레이터는 공통 처리를 한곳에 정의하고 필요한 함수에 적용하게 합니다. 파일·연결·잠금처럼 사용 뒤 정리가 필요한 자원은 정상 처리뿐 아니라 예외 경로에서도 정리되어야 합니다. 컨텍스트 매니저는 시작과 정리 규칙을 묶어 with 문에서 재사용하게 합니다. 이 절은 A 경로 01~08절을 마친 학생이 선택하는 B 경로 확장 학습입니다. Ch 18에서는 API 호출의 기록과 재시도에, Ch 30에서는 서비스 자원의 수명 관리에 같은 구조가 이어집니다.

3앞에서 배운 내용

04절에서 함수가 인자를 받고 값을 반환하는 방법을 배웠습니다. 05절에서는 try, except, finally와 파일을 여는 with 문을 사용했습니다. 07절의 타입 힌트는 데코레이터의 입력 함수와 반환 함수가 같은 결과 자료형을 유지한다는 점을 표현할 때 사용합니다. 여기서는 파일을 다시 다루는 대신, 닫힘 상태를 눈으로 확인할 수 있는 작은 자원 객체를 사용합니다.

4핵심 개념

쉬운 예

건물 출입구에서 모든 방문자가 같은 절차를 거친다고 생각해 봅니다. 방문 목적은 사람마다 다르지만 입장 기록과 퇴장 기록은 공통입니다. 각 업무 함수 안에 기록 코드를 복사하면 수정할 곳이 늘어납니다. 데코레이터는 업무 함수를 감싸 호출 전후의 공통 절차를 담당합니다. 자원 정리는 대여 물품을 반납하는 절차와 비슷합니다. 업무 중 문제가 생겨도 반납 규칙은 사라지지 않습니다.

정의

데코레이터(decorator)는 함수를 입력으로 받아 기능을 덧붙인 함수를 반환하는 호출 가능한 객체입니다. @trace 문법은 아래에 정의된 함수를 trace에 전달하고 반환된 함수를 같은 이름에 연결합니다. 래퍼(wrapper)는 원래 함수를 감싸는 내부 함수입니다. *args와 **kwargs는 위치 인자와 키워드 인자를 그대로 전달합니다. 메타데이터(metadata)는 함수 이름, 설명, 서명처럼 함수를 설명하는 정보입니다. functools.wraps는 이 정보를 래퍼에 복사합니다.

컨텍스트 매니저(context manager)는 with 블록에 들어갈 때 준비하고 나올 때 정리하는 규칙을 가진 객체입니다. contextlib.contextmanager를 쓰면 제너레이터 함수 하나로 이 규칙을 작성할 수 있습니다. yield 앞은 준비 단계, yield 뒤는 종료 단계입니다. 종료 코드를 finally에 두면 블록 내부에서 예외가 발생해도 실행됩니다.

6일부러 실패해 보기

Before 코드는 자원을 만든 뒤 의도적으로 RuntimeError를 발생시킵니다. close()가 정상 처리 문장 뒤에 있으므로 해당 문장까지 실행되지 않습니다. 실제 출력의 닫힘: False는 정리가 누락되었음을 보여 줍니다. After 코드는 같은 오류를 with managed_resource() 안에서 발생시킵니다. 관리자의 finally가 먼저 정리 실행을 출력하고, 예외 처리 뒤 닫힘 상태는 True입니다. 이 결과는 예외가 없어졌다는 뜻이 아닙니다. 오류는 호출자가 처리하고, 컨텍스트 매니저는 자원 정리를 보장합니다.

7주의할 점과 실무 메모

  • wraps를 생략해도 작은 예제는 실행될 수 있지만 문서 생성기, 디버거, 의존성 주입 도구가 함수 정보를 잘못 읽을 수 있습니다.
  • 래퍼에서 예외를 무조건 잡아 숨기면 호출자가 실패를 알 수 없습니다. 기록 후 다시 발생시키거나 처리 책임을 명확히 정합니다.
  • contextmanager 함수는 yield를 정확히 한 번 수행해야 합니다. 준비 중 실패했다면 아직 얻지 못한 자원을 정리하려 하지 않도록 단계별 상태를 고려합니다.
  • 이 실습의 DemoResource는 정리 순서를 관찰하기 위한 모의 객체입니다. 데이터베이스 연결이나 네트워크 세션의 실제 종료 방식은 해당 라이브러리 문서를 확인합니다.

8정리와 다음 절

  • 데코레이터는 함수 호출 전후의 공통 처리를 재사용합니다.
  • wraps는 원래 함수의 이름·설명·서명을 유지합니다.
  • 컨텍스트 매니저의 finally는 정상 종료와 예외 종료 모두에서 자원을 정리합니다.

다음 학습과 이어지는 지점 — 10절에서는 함수 호출 경계에 들어온 데이터가 정해진 자료형과 범위를 만족하는지 Pydantic으로 확인합니다. Ch 18의 API 호출과 Ch 30의 서비스 자원 관리에서도 이 절의 호출 전후 처리 구조를 다시 사용합니다.

9복습 문제

1. wraps를 쓰는 주된 이유는 무엇인가요?

정답과 해설: 래퍼가 원래 함수의 이름, 문서 문자열, 서명 같은 정보를 유지하게 하기 위해서입니다. 실행 결과만 같다고 함수 정보까지 자동으로 보존되지는 않습니다.

2. contextmanager 함수에서 yield 앞뒤는 각각 무엇을 담당하나요?

정답과 해설: 앞부분은 자원 준비, 뒷부분은 종료 처리를 담당합니다. 종료 처리는 finally 안에 두어 예외 경로에서도 실행하게 합니다.

3. Before 예제에서 자원이 열린 채 남은 직접 원인은 무엇인가요?

정답과 해설: 예외가 resource.close()보다 먼저 발생하여 실행 흐름이 except로 옮겨졌기 때문입니다.

4. 데코레이터가 예외를 잡은 뒤 아무 일도 하지 않고 반환하면 어떤 문제가 생기나요?

정답과 해설: 호출자는 작업 실패를 알지 못하고 성공으로 오해할 수 있습니다. 예외 처리 책임에 따라 다시 발생시키거나 명시적인 실패 값을 반환해야 합니다.
