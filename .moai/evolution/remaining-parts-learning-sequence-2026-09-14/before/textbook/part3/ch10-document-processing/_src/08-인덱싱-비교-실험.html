1학습 목표

  • 이 절을 마치면 재귀·토큰·구조 기반 청킹으로 같은 원문을 세 가지 방식으로 나눌 수 있습니다.
  • 이 절을 마치면 세 가지 청킹과 두 임베딩 모델의 6개 조합에서 실제 색인과 검색을 실행할 수 있습니다.
  • 이 절을 마치면 각 조합의 청크 수·검색 결과 1위 청크의 ID·점수·본문을 같은 형식으로 기록할 수 있습니다.
  • 이 절을 마치면 기본 제공 자료와 실제 업무 문서 100건·상용 파서 선택 실습의 범위를 구분할 수 있습니다.

2이 내용을 배우는 이유

앞 절에서는 문서를 읽고 나누는 방법과 임베딩을 배웠습니다. 이번 절에서는 그 과정을 3가지 청킹 × 2가지 임베딩 모델의 실험으로 연결합니다. 짧은 배송·환불 원문과 질문 하나를 고정하고, 여섯 조합에서 실제 벡터 색인과 검색을 실행합니다.

여섯 결과가 나와도 바로 최종 설정을 고르지는 않습니다. 이번 기본 실습은 실행 구조와 청크 경계를 확인하는 작은 실험입니다. 수강생의 실제 업무 문서 100건, 정답 질문, 상용 파서 자격증명이 준비되어야 해당 업무 분야의 검색 품질과 파서 차이를 비교할 수 있습니다.

3앞에서 배운 내용

  • Ch 9 검색 결과 확인 — 생성 전에 검색된 본문과 출처를 확인했습니다. 이번 절에서는 답변을 생성하지 않고 검색 결과까지 관찰합니다.
  • 05절 문자·재귀·토큰 청킹 — 문자 경계와 토큰 수가 청크에 미치는 영향을 확인했습니다.
  • 06절 구조 기반 청킹 — 마크다운 제목 같은 문서 구조를 메타데이터와 청크 경계에 반영했습니다.
  • 07절 임베딩 — 텍스트를 벡터로 변환하고 차원을 확인했습니다. 이번 절은 두 모델을 같은 256차원으로 사용합니다.

4핵심 개념

비유 — 같은 재료로 조리 조건 바꾸기

같은 재료를 사용하면서 온도만 바꾸면 온도에 따른 차이를 관찰할 수 있습니다. 재료와 시간까지 한꺼번에 바꾸면 무엇이 결과에 영향을 주었는지 구분하기 어렵습니다. 검색 실험도 원문과 질문을 고정하고 한 조건씩 바꿉니다.

정의

실험 격자 (experiment grid)
여러 조건의 모든 조합을 빠짐없이 실행하는 표입니다. 이 절은 청킹 3종과 임베딩 모델 2종을 곱해 6개 조합을 만듭니다.
같게 유지할 조건 (controlled condition)
조합 사이의 차이를 읽기 위해 바꾸지 않는 값입니다. 이번 실습에서는 원문·질문·검색 결과 수·임베딩 벡터 차원을 유지합니다.
실험 기록 (experiment record)
어떤 설정에서 어떤 결과를 관찰했는지 함께 남긴 자료입니다. 이번 실습은 여섯 딕셔너리의 필드 이름을 같게 맞춥니다.
결과를 확인한 자료 범위 (evaluation scope)
결론을 내릴 때 실제로 사용한 문서와 질문의 수입니다. 이 절은 짧은 원문 하나와 질문 하나만 사용하므로 전체 검색 품질을 판단할 수 없습니다.

여섯 조합을 모두 실행합니다

청킹 방법text-embedding-3-smalltext-embedding-3-large이번 설정
재귀실행실행45자, 오버랩 8자
토큰실행실행25토큰, 오버랩 4토큰
구조 기반실행실행마크다운 1·2단계 제목

모든 실행에서 원문, 질문, 검색 결과 수 k=2, 벡터 길이 256을 유지합니다. 청킹 방법을 비교할 때는 같은 모델의 세 행을 보고, 임베딩 모델을 비교할 때는 같은 청킹 방법의 두 열을 봅니다. 두 모델의 기본 벡터 차원은 다르지만 이번에는 저장 크기 조건을 맞추기 위해 256차원으로 사용합니다.

숫자와 본문을 함께 읽습니다

InMemoryVectorStore에 문서를 추가하면 임베딩 모델이 문서를 벡터로 바꿉니다. similarity_search_with_score()는 질문으로 검색한 문서와 점수를 함께 반환합니다. 점수만 비교하지 말고, 본문에 제주 배송과 추가 기간을 설명하는 내용이 있는지 확인합니다.

출력의 청크 ID는 이번 실행에서 청크를 구분하는 이름입니다. recursive:02와 token:02의 끝 번호가 같아도 같은 원문 범위를 뜻하지 않습니다. 청킹 방법이 바뀌면 경계도 바뀌므로 본문을 함께 읽어야 합니다. 서로 다른 임베딩 모델의 점수 크기만으로 우열을 판단하지 않습니다.

원리 더 알아보기 — 비교할 두 실행 고르기

한 청킹 방법의 small·large 두 결과를 비교하면 청크 본문은 같고 모델만 다릅니다. 한 모델의 재귀·토큰·구조 기반 결과를 비교하면 모델은 같지만 청크의 크기 단위와 경계 규칙이 다릅니다. 숫자 하나의 효과를 측정하는 실험과 달리, 여기서는 세 전략의 실제 산출물을 함께 읽습니다.

기본 실습의 첫 부분은 짧은 원문 하나와 질문 하나로 실행 구조와 청크 경계를 확인합니다. 그 결과는 교육용 원문에만 해당하므로 Ch 11 평가 입력으로 직접 사용하지 않습니다. 이어지는 연결 실습은 Ch 11과 같은 18개 디지털 PDF와 Q001을 사용해 6개 설정의 검색 결과를 같은 JSONL 필드로 기록합니다.

5실행 예제

먼저 짧은 원문에서 재귀·토큰·구조 기반 청킹의 실제 청크를 출력합니다. 각 청크 집합에 두 임베딩 모델을 적용한 6개 결과로 청킹 경계를 관찰합니다. 다음에는 제공된 18개 디지털 PDF를 재귀·토큰·쪽 구조의 세 단위로 나누고 두 모델을 적용해 Ch 11의 Q001을 검색합니다. 이 6개 결과에는 설정과 함께 문서 ID·청크 ID·쪽·순위·점수를 기록합니다.

확인할 점 — 이번 실행의 청크 수는 재귀 7개, 토큰 10개, 구조 기반 3개입니다. 재귀 청킹과 구조 기반 청킹에서는 두 임베딩 모델 모두 제주와 이틀을 함께 담은 청크를 1위로 반환했습니다. 토큰 청킹의 두 모델은 두 단어가 나뉜 token:02를 1위로 반환했습니다. 이 결과는 질문 하나에서 관찰한 청크 경계이며 전체 품질 순위가 아닙니다.

6실험 결과 해석

짧은 원문에서 여섯 조합을 모두 실행했습니다. 재귀 청킹은 7개, 토큰 청킹은 10개, 구조 기반 청킹은 3개가 되었고, 토큰 청킹의 1위 청크에는 질문과 답의 단어가 함께 들어 있지 않았습니다. 이어서 실제 PDF 18개와 Q001로 6개 설정을 실행해 Ch 11이 읽을 JSONL을 만들었습니다. 두 실험은 문서와 질문이 다르므로 점수나 순위를 서로 직접 비교하지 않습니다. Q001 한 질문의 검색 지표도 전체 설정의 우열을 뜻하지 않습니다.

7주의할 점과 실무 메모

  • 비교할 행과 열을 구분합니다. 같은 모델의 세 행은 청킹 방법 차이를, 같은 청킹 방법의 두 열은 임베딩 모델 차이를 보여 줍니다.
  • API는 실제로 호출됩니다. 문서를 저장하거나 질문으로 검색할 때 임베딩 비용이 발생합니다. 이 노트북은 공급자의 토큰 사용량이나 청구 비용을 출력하지 않습니다.
  • 한 질문은 전체 평가를 대신하지 않습니다. 같은 1위 결과가 나왔다고 모델이 동등하다고 결론짓거나, 다른 결과가 나왔다고 한 모델이 우수하다고 결론짓지 않습니다.
  • 제공 자료는 업무 문서 100건이 아닙니다. 배포 묶음에는 교육용 디지털 PDF 18건과 기존 문서의 스캔 변형 3건이 있습니다. 정답 정보를 포함한 집필용 전체 질의셋 149개는 학생 배포에서 제외합니다. PDF와 질문 수를 합치거나 파일을 복제해 100건으로 세지 않습니다.
  • 상용 파서 비교는 선택 실습입니다. Upstage·LlamaParse 호출은 서비스 자격증명, 비용 확인, 문서 외부 전송 승인이 필요합니다. 기본 노트북은 상용 파서를 실행했다고 주장하지 않습니다.

8정리와 다음 절

  • 재귀·토큰·구조 기반 청킹과 두 임베딩 모델의 여섯 조합을 실제로 실행했습니다.
  • 각 조합의 청크 수·1위 청크 ID·점수·본문을 같은 필드로 기록했습니다.
  • 교육용 제공 자료와 업무 문서 100건·상용 파서 선택 실습을 구분하고, 작은 표본의 단어 검사를 전체 품질 평가로 표현하지 않았습니다.

다음 학습과 이어지는 지점 — Ch 11은 continuity-ch10-indexing.jsonl의 6개 설정을 읽고 Q001의 정답 문서 ID와 검색 결과를 비교합니다. 개발용 질문 하나의 결과는 연결 동작을 확인하는 범위이며, 설정을 선택하려면 개발용 질문 전체로 확장해야 합니다. Ch 12에서는 같은 말뭉치·질문·평가 단위를 유지한 결과끼리 검색 설정을 반복 비교합니다.

9복습 문제

문제 4개 · 해설 포함

1. 여섯 조합은 어떻게 만들어집니까?

재귀·토큰·구조 기반 청킹 3종과 small·large 임베딩 모델 2종을 곱해 만듭니다.

2. recursive:02와 token:02는 같은 내용입니까?

끝 번호만으로는 알 수 없습니다. 청킹 규칙이 다르므로 실제 본문을 확인해야 합니다.

3. 첫 검색 결과에 제주라는 단어가 있으면 배송 기간 질문에 답할 수 있다고 확정할 수 있습니까?

확정할 수 없습니다. 추가 기간을 설명하는 내용과 그 문맥까지 읽어야 합니다. 키워드 검사는 필요한 단서가 있는지 확인하는 보조 수단입니다.

4. 교육용 PDF 21건이 있으므로 업무 문서 100건 실습이 준비되었다고 볼 수 있습니까?

볼 수 없습니다. 스캔 변형 3건은 기존 원본의 별도 업무 문서가 아닙니다. 중복을 제외한 실제 업무 문서 100건과 정답 질문을 별도로 준비해야 합니다.
