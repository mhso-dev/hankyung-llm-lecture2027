1학습 목표

  • 이 절을 마치면 내려받은 실습 폴더에서 제공 PDF 경로를 찾고 Path 객체의 파일명·이름·확장자를 확인할 수 있습니다.
  • 이 절을 마치면 딕셔너리의 원본 값을 doc_id·source·page 등 공통 메타데이터로 바꿀 수 있습니다.
  • 이 절을 마치면 쪽 번호 하나를 바꾼 새 메타데이터를 만들고 원본과 결과를 비교할 수 있습니다.

2이 내용을 배우는 이유

Ch 9에서는 PDF 한 쪽을 Document 하나로 바꾸고 바로 청크로 나누었습니다. 이번에는 PDF 외에 DOCX, HTML, CSV, HWPX도 함께 다룹니다. 01절은 출처를 metadata 딕셔너리로 준비하고, 02~04절은 각 파일에서 본문·표·행을 읽어 확인합니다. 이 결과를 후속 단계에서 page_content와 metadata에 옮기면 같은 Document 구조로 처리할 수 있습니다. 01~04절의 기본 노트북 자체는 LangChain Document 목록을 만들거나 합치지 않습니다.

파일 내용을 읽는 도구인 파서를 비교하기 전에, 어떤 문서를 사용했는지부터 기록합니다. 문서 수·파일 형식·경로·doc_id가 없으면 파서를 바꾼 후 어느 문서의 내용이 빠졌는지 비교할 수 없습니다. doc_id는 같은 문서를 다시 처리해도 바뀌지 않는 값을 사용합니다. 이 절에서 먼저 파일과 메타데이터 개수를 확인한 뒤, 다음 절부터 형식별 파서로 실제 내용을 읽습니다.

labs/data/rag-corpus/에는 교육용으로 만든 가상 PDF 21건이 있습니다. 18건은 글자를 추출할 수 있고, 3건은 글자 층이 없는 스캔 PDF입니다. 기본 노트북은 제공 PDF 한 건의 경로와 메타데이터를 확인합니다. 수강생이 실제 업무에서 다룰 문서 100건은 아직 제공되지 않았으며, 자료가 준비되면 각 파일에 같은 메타데이터 항목을 붙여 확장합니다.

3앞에서 배운 내용

  • 문자열과 정수 — 따옴표로 감싼 값은 문자열이고, int()는 숫자 문자열을 정수로 바꿉니다.
  • 목록과 딕셔너리 — 목록은 여러 값을 순서대로, 딕셔너리는 키와 값을 한 쌍으로 저장합니다.
  • 파일 경로 — Path 객체로 폴더와 파일 경로를 연결하고 is_file()로 실제 파일을 확인합니다. 앞 장의 모듈이나 함수를 불러오지 않습니다.

4핵심 개념

비유 — 접수대에서 같은 칸을 가진 봉투로 옮기기

한 기관의 접수대에 종이 신청서, 이메일 인쇄물, 엑셀 목록이 함께 들어온다고 생각해 보세요. 담당자는 원본을 그대로 창고에 보관하고, 처리 부서에는 같은 모양의 봉투로 전달합니다. 봉투 앞면에는 접수 번호, 원본 종류, 접수 시각, 담당 부서를 적습니다. 처리 부서는 봉투 안의 본문을 읽으면 되고, 원본 형식에 따라 접수 방법이 달랐다는 사실까지 알 필요는 없습니다. 로더가 하는 일도 이와 같습니다. 파일별 파서는 다르지만, 청킹 단계에 넘기는 결과는 같은 Document 구조여야 합니다.

정의

문서 객체 (Document)
추출한 본문과 부가 정보를 한 단위로 묶은 객체입니다. LangChain의 Document는 page_content와 metadata를 가집니다. 이후 청킹·임베딩·검색은 원본 파일 대신 이 객체를 받습니다.
파서 (parser)
파일의 내부 구조를 해석하여 텍스트, 표, 이미지 위치 같은 내용을 추출하는 프로그램입니다. 같은 PDF라도 파서에 따라 읽기 순서와 표 표현이 달라질 수 있습니다.
메타데이터 (metadata)
본문을 설명하는 부가 정보입니다. 문서 ID, 원본 파일명, 쪽 번호, 형식, 수정 시각처럼 검색 필터와 출처 표기에 필요한 값을 담습니다.
출처 계보 (provenance)
검색된 청크가 어느 원본 파일의 몇 쪽에서 나왔는지 찾을 수 있게 남긴 기록입니다. 이를 출처 계보라고 부릅니다. source, parser, page를 함께 남기면 검색된 청크를 원본까지 거슬러 확인할 수 있습니다.

도식 — 파일이 달라도 본문과 출처를 담는 칸은 같습니다

모든 로더가 같은 이름의 메타데이터 항목을 만들도록 먼저 정합니다. 예를 들어 쪽 번호는 항상 page, 파일명은 항상 source에 저장합니다. doc_id가 같은 문서를 다시 처리할 때마다 바뀌면 이전 색인과 새 색인의 결과를 비교하기 어렵습니다. 파일명이 바뀔 수 있는 환경에서는 업무 시스템의 문서 번호를 사용하고, 그런 번호가 없으면 대소문자와 슬래시 표기를 한 방식으로 맞춘 상대 경로나, 파일 내용으로 계산한 해시를 조합합니다. 이 챕터의 교육용 가상 문서는 파일명 앞의 E01, M03, H06을 문서 ID로 사용합니다.

메타데이터는 세 부류로 나누어 생각할 수 있습니다. 첫째, 원본에서 직접 읽은 값입니다. 제목, 작성자, 수정 시각이 여기에 해당합니다. 둘째, 파일 시스템에서 얻은 값입니다. 상대 경로, 확장자, 파일 크기입니다. 셋째, 처리 과정이 만든 값입니다. 사용한 파서 이름, 처리 시각, OCR 적용 여부, 청크 번호입니다. 이 세 부류를 구분해 두면 잘못된 값의 책임 지점을 찾기 쉽습니다. 예를 들어 PDF 안의 제목과 파일명이 다르면 어느 값을 저장할지 팀의 규칙으로 정할 수 있습니다.

7주의할 점과 실무 메모

  • 문서를 구별하는 ID와 제목을 구분합니다. 제목은 사람이 읽기 위한 값이라 수정될 수 있습니다. doc_id는 제목이나 파일명이 바뀌어도 같은 문서라면 같은 값을 유지합니다.
  • 쪽 번호의 기준을 통일합니다. 일부 라이브러리는 첫 쪽을 0으로 반환합니다. 교재와 최종 출처 표시는 사람이 보는 쪽 번호인 1부터 시작하도록 변환합니다.
  • 원본을 보존합니다. 추출 텍스트만 남기면 파서 오류를 다시 확인할 수 없습니다. 추출한 텍스트에 원본 파일명과 쪽 번호를 함께 저장합니다.
  • 민감한 경로와 문서 속성을 걸러냅니다. 작성자 계정, 내부 서버 경로, 임시 폴더 이름은 검색 품질에 필요하지 않다면 배포용 메타데이터에서 제외합니다.
  • 재처리 조건을 기록합니다. 파일 수정 시각이나 내용 해시를 보관하면 바뀐 문서만 다시 파싱하고 임베딩할 수 있습니다. 캐싱과 재임베딩 비용은 이 챕터 후반 절에서 다룹니다.

8정리와 다음 절

  • Path의 name·stem·suffix 속성으로 실제 파일 경로에서 메타데이터 값을 얻습니다.
  • doc_id·source·page·file_type·parser를 딕셔너리의 공통 키로 저장합니다.
  • 딕셔너리를 펼쳐 새 값을 덮어쓰면 원본을 보존하면서 변경 전후를 비교할 수 있습니다.

다음 학습과 이어지는 지점 — 이 절의 입력 목록과 공통 메타데이터는 02~04절의 로더 결과에 같은 이름으로 저장할 항목입니다. Ch 11에서는 doc_id를 정답표와 비교합니다. file_type과 parser는 문서 처리 조건을 구분하는 기록으로 남지만, Ch 12의 기본 실습이 이 필드를 실패 유형별로 집계하지는 않습니다. 다음 02절에서는 같은 PDF를 서로 다른 방식으로 읽어 표의 행·열과 스캔본의 글자가 실제 추출 결과에서 빠지는지 확인합니다.

9복습 문제

문제 4개 · 해설 포함

1. [하] 여러 파일 형식의 로더가 같은 Document 구조를 반환해야 하는 이유는 무엇입니까?

청킹·임베딩·검색 단계가 원본 형식마다 별도 코드를 가질 필요 없이 page_content와 metadata라는 같은 두 항목만 처리하면 되기 때문입니다. 형식별 차이는 로더 안에서 흡수하고, 본문과 메타데이터 구조는 통일합니다.

2. [중] doc_id와 문서 제목을 같은 값으로 사용했을 때 생길 수 있는 문제를 설명하세요.

제목은 사람이 수정하거나 여러 문서에서 중복할 수 있습니다. 제목이 바뀌면 같은 문서를 새 문서로 인식하고, 제목이 중복되면 서로 다른 문서의 청크가 하나로 집계됩니다. 제목이 바뀌어도 유지되는 업무 문서 번호나 상대 경로·내용 해시 조합을 사용해야 합니다.

3. [중] source = Path("E02.pdf")일 때 source.name, source.stem, source.suffix는 각각 무엇입니까?

name은 E02.pdf, stem은 E02, suffix는 .pdf입니다.

4. [상] 파서를 교체한 뒤 검색 품질이 달라졌습니다. 나중에 같은 조건으로 다시 확인하려면 어떤 메타데이터가 필요합니까?

최소한 원본을 가리키는 doc_id와 source, 쪽 번호, 파일 형식, 파서 이름과 버전, 처리 시각 또는 사용한 설정을 구별하는 이름이 필요합니다. 이 정보로 같은 원본을 같은 조건에서 다시 처리하고 이전에 읽은 결과와 비교할 수 있습니다.
