1학습 목표

  • 이 절을 마치면 문장 하나와 문장 목록을 임베딩하고, 입력 개수·벡터 개수·벡터 길이를 확인할 수 있습니다.
  • 이 절을 마치면 영어 종합 벤치마크 순위를 실제로 사용할 한국어 문서의 검색 품질로 해석하면 안 되는 이유를 설명할 수 있습니다.
  • 이 절을 마치면 LangChain의 캐시를 설정하고, 같은 문서를 두 번 요청한 뒤 저장 파일 수와 반환 벡터를 비교할 수 있습니다.
  • 이 절을 마치면 차원이 다른 벡터를 섞은 오류를 확인하고 같은 설정의 벡터로 수정할 수 있습니다.

2이 내용을 배우는 이유

05·06절에서 청크 경계를 여러 방식으로 만들었습니다. 다음 단계는 각 청크를 벡터로 바꾸는 일입니다. Ch 9에서는 첫 RAG를 완주하기 위해 text-embedding-3-small 하나를 임시로 사용했습니다. 이번 절에서는 모델 이름을 설정 한 줄로 취급하지 않고, 한국어 질문과 문서를 같은 검색 공간에 놓기 위해 문서와 질문에 같은 모델·차원을 사용했는지 어떻게 기록할지 확인합니다.

임베딩 모델을 바꾸면 모든 벡터의 좌표계가 달라집니다. 같은 모델이라도 차원, 정확한 모델 버전, 문서·질문 앞에 붙이는 구분 문구가 바뀌면 이전 벡터를 그대로 사용할 수 없습니다. 반면 스플리터 설정이 바뀌어도 결과 청크 가운데 텍스트가 정확히 같은 항목은 같은 모델 설정에서 벡터를 재사용할 수 있습니다. 이 차이를 알면 인덱스는 다시 구성하되 불필요한 API 호출은 줄일 수 있습니다.

이 절에서 언급하는 모델은 비교 후보입니다. 이 과정의 최종 모델은 [[미정: 임베딩 모델]]이며, Ch 11에서 한국어 질의셋의 검색 지표를 계산하기 전에는 확정하지 않습니다. small·large라는 이름만으로 품질을 판단할 수 없습니다. 차원·비용·입력 길이가 다른 두 기능 예제로 사용합니다.

4핵심 개념

비유 — 같은 주소 체계와 보관함 표찰

서로 다른 도시의 지도 좌표를 한 표에 섞으면 거리를 비교할 수 없습니다. 청크는 A 모델로, 질문은 B 모델로 변환한 뒤 가까운 것을 찾는 일도 마찬가지입니다. 모델과 차원, 입력 규칙이 같아야 같은 주소 체계입니다. 한 번 계산한 좌표를 보관할 때는 어느 주소 체계로 만들었는지 표찰을 붙여야 합니다. 캐시 키가 그 표찰입니다.

정의

다국어 임베딩 (multilingual embedding)
여러 언어의 텍스트를 검색·분류 같은 작업에 사용할 수 있도록 벡터로 표현하는 모델입니다. 지원 언어 목록은 후보 조건이며 특정 한국어 업무 문서에서 높은 검색 품질을 보장하지 않습니다.
차원 (dimension)
임베딩 벡터에 들어 있는 숫자의 개수입니다. 차원이 커지면 저장 공간과 거리 계산량이 늘어날 수 있으며, 차원 수만으로 품질을 판단할 수 없습니다.
모델 버전 (model revision)
같은 모델 이름 아래에서 사용한 정확한 코드·가중치 버전입니다. 로컬 오픈 모델은 커밋 SHA를 기록하고, API 모델은 공급자가 제공하는 고정 버전 식별자를 사용할 수 있는지 확인합니다.
입력 접두사 (input prefix)
모델 카드가 문서와 질의를 구분하기 위해 요구하는 앞부분입니다. 예를 들어 문서에는 passage: , 질의에는 query: 를 붙이는 모델이 있으며 생략하면 모델 카드가 설명한 검색 방식과 달라집니다.
벡터 캐시 (vector cache)
같은 입력 문자열과 같은 임베딩 설정으로 계산한 벡터를 다시 사용하기 위한 저장소입니다. 이 노트북은 입력 문자열의 공백이나 줄바꿈을 자동으로 정리하지 않습니다. 전처리 방법을 추가한다면 그 이름과 버전도 캐시 키에 반영해야 다른 입력의 벡터가 섞이지 않습니다.
인덱스 구성 기록표 (index manifest)
원문, 파서, 청킹 설정, 청크 ID와 벡터 캐시 키의 대응을 기록한 목록입니다. 인덱스를 어떻게 구성했는지 재현하고 변경 범위를 판단하는 근거가 됩니다.
원리 더 알아보기 — 모델 후보와 평가 기준

모델 후보를 읽는 순서

첫째, 문서와 질문의 언어가 지원 범위에 있는지 봅니다. 둘째, 최대 입력 길이가 현재 청크의 토큰 길이를 수용하는지 확인합니다. 셋째, 문서와 질의에 서로 다른 접두사나 프롬프트가 필요한지 모델 카드를 읽습니다. 넷째, 차원과 실행 위치, 라이선스, API 단가를 기록합니다. 마지막으로 한국어 질의셋에서 검색 결과를 측정합니다. 앞의 네 조건은 실행 가능한 후보를 고르는 기준이고, 마지막 측정은 실제로 사용할 한국어 문서와 질문에 맞는 후보를 판단하는 기준입니다.

OpenAI의 text-embedding-3-small과 text-embedding-3-large는 기본 차원이 각각 1,536과 3,072이며 dimensions 옵션으로 축소할 수 있습니다. 2026-09-08 확인 단가는 100만 토큰당 각각 미화 0.02달러와 0.13달러입니다. 이 값은 비용 예측에 쓰며 한국어 순위를 뜻하지 않습니다. 공급자가 제공하는 영문 또는 다국어 벤치 결과도 후보 선정 자료일 뿐, 우리 문서의 정답률이 아닙니다.

로컬 오픈 모델 후보로는 intfloat/multilingual-e5-large와 BAAI/bge-m3를 조사했습니다. 두 모델 카드 모두 다국어 지원과 1,024차원을 명시합니다. E5는 검색 입력에 passage: 와 query: 접두사를 요구하고 최대 길이가 512개의 토큰입니다. BGE-M3는 한 텍스트를 표현하는 방법을 여러 가지 제공합니다. 이 장의 후속 비교에서는 텍스트 하나를 숫자 목록 하나로 바꾸는 dense 벡터만 사용합니다. 최대 입력 길이는 8,192개의 토큰입니다. 이 두 모델도 최종 선택이 아니라 공개된 모델 카드와 사용한 정확한 모델 버전을 기록할 수 있는 후속 비교 후보입니다.

영어 시험 점수가 한국어 업무 문서의 검색 결과를 보장하지 않는 이유

MTEB는 모델·과제·언어별 평가를 모으는 평가 모음입니다. 종합 점수 한 줄에는 여러 언어와 분류·검색·군집화 같은 서로 다른 과제가 섞일 수 있습니다. 영어 검색 과제에서 높은 모델이 한국어 사내 규정의 조사·고유명사·표현 변형에서도 같은 순위를 유지한다는 보장은 없습니다. 리더보드를 사용할 때는 Korean retrieval 과제를 별도로 보고, 최종 결정은 이 과정의 한국어 질문과 정답 문서로 측정합니다.

벡터 저장 이름과 인덱스 구성 기록표를 따로 관리합니다

기본 실습은 CacheBackedEmbeddings에 임베딩 모델과 LocalFileStore를 전달합니다. namespace는 저장 항목을 구분하는 이름이며, 이 예제에서는 모델 이름과 256차원 설정을 포함합니다. 라이브러리는 입력 텍스트로 키를 만들고 지정한 저장소에서 벡터를 찾습니다. 모델이나 차원을 바꾸면 이름도 바꿔 이전 설정의 벡터와 섞이지 않게 합니다. 전처리나 접두사를 추가하는 확장에서는 그 조건도 구분해야 합니다.

인덱스 구성 기록표에는 원문 해시, 사용한 파서와 공백·줄바꿈·문자 표기를 정리한 방법의 버전, 청킹 방식과 크기·오버랩, 청크 ID, 각 청크가 참조하는 벡터 캐시 키를 적습니다. 청킹 설정이 바뀌면 청크의 순서와 ID 대응이 달라지므로 인덱스는 다시 구성합니다. 그러나 새 인덱스를 구성한다는 말이 모든 벡터 API를 다시 호출한다는 뜻은 아닙니다. 새로 생기거나 텍스트가 바뀐 청크만 캐시 미스로 계산합니다.

같은 문서를 두 번 요청하기

처음에는 비어 있는 임시 폴더를 사용합니다. 문장 목록을 첫 번째로 요청하면 문서 벡터가 저장됩니다. 두 번째로 같은 목록을 요청한 뒤 파일 수와 벡터를 비교합니다. 파일 수가 유지되고 벡터가 같다는 출력만으로 외부 호출 횟수를 직접 측정했다고 표현하지 않습니다. 아래 차원 실습에서는 같은 캐시 이름이 실제로 오래된 벡터를 반환하는 현상을 따로 확인합니다.

7주의할 점과 실무 메모

  • 최종 모델은 미정입니다. 이 절의 small·large API 후보와 두 오픈 모델은 비교 틀을 보여 줍니다. 한국어 검색 지표와 운영 조건을 확인하기 전에는 하나를 정본으로 선언하지 않습니다.
  • 입력 규칙을 모델 카드에서 확인합니다. 문서와 질의 접두사, 최대 길이, 공백·줄바꿈·문자 표기를 정리하는 방법이 모델마다 다릅니다. 예를 들어 모델마다 요구하는 query:·passage: 표시가 다르면, 각 모델 설명서에 맞게 입력을 준비한 뒤 비교해야 합니다.
  • 가격에는 확인일을 붙입니다. API 단가는 바뀔 수 있습니다. 로그에는 실제 입력 토큰 합계와 단가, 통화, 확인일을 함께 남깁니다.
  • 캐시에 원문을 저장하는 문제. 캐시 파일에 벡터만 저장해도 키 생성 과정에서 원문 해시를 사용합니다. 민감 문서라면 캐시 경로의 접근 권한과 보존 기간을 별도로 정합니다.

8정리와 다음 절

  • 임베딩 후보는 언어·입력 길이·차원·접두사·정확한 모델 버전·비용을 확인한 뒤 정답 문서가 표시된 한국어 질문 모음으로 측정합니다.
  • 영어 또는 종합 벤치마크의 순위는 한국어 업무 문서 검색 순위를 보장하지 않습니다.
  • 벡터 캐시 키와 인덱스 구성 기록표를 분리하면 인덱스를 다시 구성하면서도 정확히 같은 청크의 벡터를 재사용할 수 있습니다.

다음 학습과 이어지는 지점 — 다음 절은 한 설정으로 검색을 끝까지 실행한 뒤 청크 크기만, 그다음 임베딩 모델만 바꿉니다. 검색 결과를 관찰하는 연습을 마친 뒤 Ch 11에서 정답 질의셋과 품질 지표를 배웁니다.

9복습 문제

문제 4개 · 해설 포함

1. 문장 세 개를 256차원으로 임베딩하면 벡터 개수와 각 벡터의 길이는 얼마입니까?

벡터는 세 개이고 각각 256개의 숫자를 담습니다. 입력 문장 수와 벡터 길이는 서로 다른 값입니다.

2. 캐시를 비교할 때 빈 임시 폴더부터 사용하는 이유는 무엇입니까?

이전 실습의 저장 파일이 남아 있으면 첫 요청부터 기존 벡터를 사용할 수 있습니다. 비어 있는 상태로 시작해야 저장 전후의 변화를 관찰할 수 있습니다.

3. 모델 이름은 같지만 차원을 바꿨습니다. namespace도 바꾸어야 하는 이유는 무엇입니까?

서로 다른 차원으로 만든 벡터를 구분하기 위해서입니다. 같은 입력이어도 차원 설정이 다르면 이전 벡터를 그대로 사용하면 안 됩니다.

4. 영어 벤치마크 순위가 높은 모델을 한국어 업무 문서에도 바로 선택할 수 있습니까?

언어와 문서, 질문의 표현과 길이, 자주 묻는 내용이 다르므로 바로 선택할 수 없습니다. 해당 한국어 질문과 정답 문서로 검색 품질을 측정해야 합니다.
