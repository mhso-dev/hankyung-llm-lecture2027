1학습 목표

  • 프롬프트 버전에 원문과 변경 이유를 함께 기록할 수 있습니다.
  • 모델과 과제를 고정하고 누적된 세 프롬프트 전략의 토큰·지연·단어 포함 표시를 비교할 수 있습니다.
  • 프롬프트, 실행 결과, 측정 조건을 JSON 파일로 저장하고 다시 읽어 확인할 수 있습니다.

2이 내용을 배우는 이유

프롬프트를 수정하다 보면 마지막 문장만 남고 어떤 문제를 고치려고 무엇을 바꿨는지 사라지기 쉽습니다. 이름을 v2라고 붙이는 것만으로는 버전이 보존되지 않습니다. 원문, 변경 이유, 모델, 입력, 실행 결과, 평가 기준을 함께 저장해야 다른 사람이 같은 조건을 다시 살필 수 있습니다. 기록이 없으면 출력 차이가 프롬프트 때문인지 모델 변경이나 다른 고객 문의 때문인지 구분하기 어렵습니다.

이번 절에서는 기준선, 형식·금지 조건 추가, 관련 예시 추가의 세 전략을 비교합니다. 세 번째 전략은 두 번째 조건을 유지한 채 관련 예시만 추가합니다. 이렇게 누적 조건을 분명히 해야 두 번째에서 세 번째로 바뀐 결과를 예시 추가와 연결해 해석할 수 있습니다. 마지막에는 메모리에 있던 사전을 prompt-ab-continuity.json 파일로 저장하고 실행 시각별 사본도 함께 남깁니다.

3앞에서 배운 내용

Ch 6에서는 usage_metadata에서 토큰·캐시 사용량을 읽고 time.perf_counter()로 호출 지연을 기록했습니다. 이 절의 노트북은 Ch 6의 provider-comparison-continuity.json을 직접 읽어 이전 실행의 출처와 공통 필드를 확인합니다. 현재 고객 문의는 Ch 6 질문과 다르므로 두 실행의 수치를 직접 비교하지 않고, 같은 측정 형식만 이어서 사용합니다. 이번 챕터에서는 과업 제약, 관련 예시, 공개 근거, 반복 표본, JSON 필드 진단을 차례로 확인했습니다. 이번 절은 새 프롬프트 기법을 추가하는 대신 앞에서 사용한 전략을 세 버전으로 묶습니다. 파일 저장에는 Ch 5에서 배운 pathlib.Path와 json.dumps(), json.loads()를 사용합니다.

4핵심 개념

버전과 변경 기록

프롬프트 버전(prompt version)은 특정 시점의 프롬프트 원문과 그 원문을 식별하는 이름입니다. 버전 이름은 v1-direct처럼 사람이 읽을 수 있지만, 이름만 저장해서는 실제 문장을 복구할 수 없습니다. 변경 기록(change log)은 이전 버전에서 무엇을 추가하거나 수정했는지와 그 이유를 적은 기록입니다. 이번 실습의 change_log는 v1을 기준선, v2를 형식·금지 조건 추가, v3를 v2 조건 유지·관련 예시 추가로 설명합니다.

기준선(baseline)은 이후 변경과 비교할 첫 조건입니다. 통제 변수(control variable)는 비교 중에 유지하는 값입니다. 여기서는 모델 openai:gpt-5.4-mini, 생성 상한 220토큰, system 메시지, 고객 문의, 단어 포함 검사 목록을 유지합니다. 실험 변수는 프롬프트 전략입니다. v1에서 v2로 갈 때는 출력 형식과 금지 조건을 함께 추가했으므로 두 요소 각각의 효과를 분리할 수 없습니다. v2와 v3의 차이는 관련 예시 추가 한 가지로 좁혀져 있습니다.

A/B 비교와 실행 기록

A/B 비교(A/B comparison)는 같은 대상 집합을 두 조건으로 나누어 결과를 비교하는 방법입니다. 이번 실습은 세 조건을 사용하므로 엄밀히는 A/B/n 비교에 가깝습니다. 각 버전을 한 번씩 실행하기 때문에 반복 변동을 평균내지 못하며, 결과표는 탐색용 실행 기록으로 읽어야 합니다. mention_count는 ‘교환’, ‘A-1042’, ‘사진’ 중 몇 단어가 나타났는지를 세며 품질 점수가 아닙니다. 원문이 규정을 지키는지와 근거 없는 약속을 추가했는지는 사람이 읽어야 합니다.

실행 아티팩트(run artifact)는 실행 조건과 결과를 나중에 다시 읽을 수 있도록 저장한 파일입니다. 이번 JSON에는 모델, 생성 상한, 고객 문의, 단어 목록, 세 프롬프트 원문, 변경 이유, 응답, 사용량, 지연, 캐시 토큰, 예상 비용, 가격 기준일과 100만 토큰당 단가가 들어갑니다. 모델 별칭은 이후 다른 스냅샷을 가리킬 수 있으므로 높은 재현성이 필요한 평가에서는 접근 가능한 고정 모델 ID와 실행 날짜도 추가해야 합니다.

도식 읽기

5실행 예제

versions 사전은 세 프롬프트 원문을 보존합니다. v2는 세 줄 형식과 규정 밖 약속 금지를 추가하고, v3는 이 두 조건을 그대로 둔 채 관련 예시를 추가합니다. 각 원문을 같은 모델과 system 메시지로 한 번씩 실행한 뒤, 입력·출력·캐시 토큰, 전체 호출 지연, 예상 비용, 단어 포함 개수를 표의 한 행으로 만듭니다. 마지막 셀은 모든 원문과 결과를 labs/part2/ch07-prompt-engineering/runs/prompt-ab-continuity.json에 저장하고 실행 시각별 사본 경로를 출력합니다.

6실험 결과 해석

세 응답은 모두 ‘교환’, ‘A-1042’, ‘사진’을 포함하여 mention_count가 3이었습니다. 입력 토큰은 v1 95, v2 118, v3 139토큰으로 늘었습니다. 지시와 예시가 추가되었기 때문입니다. 출력 토큰은 각각 113, 108, 71토큰이었고 전체 호출 지연은 1.560초, 1.165초, 0.870초였습니다. 캐시 입력은 세 행 모두 0토큰이었고 예상 비용은 각각 0.00057975달러, 0.0005745달러, 0.00042375달러였습니다. 입력이 긴 버전의 출력과 지연이 이번 실행에서 오히려 작았으므로, 입력 길이만으로 출력 길이나 지연 순서를 예측할 수 없음을 확인할 수 있습니다.

원문을 읽으면 세 버전 모두 교환 접수에 사진이 필요하다고 안내하고 주문번호를 포함합니다. v2와 v3는 세 줄 형식으로 응답했으며, v3는 관련 예시를 추가하면서 v2의 규정 밖 약속 금지 조건을 유지했습니다. 그러나 단어 포함 개수 3은 세 답의 업무 품질이 같다는 뜻이 아닙니다. 문장의 명확성, 정책 준수, 불필요한 약속은 별도의 루브릭으로 평가해야 합니다.

마지막 셀은 실행 날짜와 ID, Ch 6 기록의 경로·SHA-256 지문, 모델 설정, 세 프롬프트와 원문 응답, 공통 측정 필드를 prompt-ab-continuity.json과 실행별 사본에 저장합니다. mention_count는 품질 점수가 아니며, 생성 답변의 업무 품질은 human_review_required로 남겨 사람이 원문을 검토해야 합니다.

7주의할 점과 실무 메모

  • 한 버전에서 여러 요소를 동시에 바꾸면 어떤 요소가 결과 차이를 만들었는지 분리하기 어렵습니다. 변경 기록에 묶여 바뀐 조건을 그대로 적습니다.
  • 생성 응답은 실행할 때마다 달라질 수 있습니다. 버전마다 같은 반복 횟수를 정하고 실행 순서 효과도 확인합니다.
  • 프롬프트 파일과 실행 로그에는 API 키, Authorization 헤더, 공개할 수 없는 고객 원문을 저장하지 않습니다. 필요한 식별자는 비식별 입력 ID로 대체합니다.
  • 지연은 네트워크와 제공자 부하의 영향을 받습니다. 한 번의 수치로 프롬프트 전략의 속도를 일반화하지 않습니다.
  • LangSmith 같은 외부 저장소를 사용할 때는 데이터 보관 정책과 접근 권한을 확인합니다. 이번 기본 실습은 로컬 JSON 파일만 사용합니다.

8정리와 다음 절

  • 프롬프트 버전은 이름, 원문, 변경 이유를 함께 보존해야 합니다.
  • 비교에서는 모델·입력·평가 기준을 유지하고 바꾼 조건을 기록합니다.
  • 실행 아티팩트에 프롬프트와 결과를 함께 저장해야 이후 검토와 재실행이 가능합니다.

다음 학습과 이어지는 지점 — Ch 8에서는 프롬프트 한 문장보다 넓은 모델 맥락을 다룹니다. 06절이 이 실행 기록과 지문을 직접 읽은 뒤, 별도 질문으로 full·selected·compressed를 실행하고 같은 측정 필드를 남깁니다. 두 실험은 질문과 입력 단위가 다르므로 수치를 직접 비교하지 않습니다. Ch 11은 검색된 문서 순위를 평가하고, 생성 답변의 정확성·근거성 평가는 Ch 15에서 다룹니다.

9복습 문제

문제 1

v2-constraints라는 이름만 저장하면 버전 기록으로 부족한 이유는 무엇인가요?

해설 — 실제 프롬프트 원문과 변경 이유, 실행 조건이 없으면 어떤 문장을 실행했는지 복구하거나 결과 차이의 원인을 검토할 수 없습니다.

문제 2

v2와 v3 비교에서 유지한 조건과 추가한 조건은 무엇인가요?

해설 — 세 줄 형식과 규정 밖 약속 금지를 유지하고, 현재 문의와 관련된 예시를 추가했습니다.

문제 3

세 버전의 mention_count가 모두 3이면 품질이 같다고 판정할 수 있나요?

해설 — 판정할 수 없습니다. 단어 포함 검사는 문맥과 정책 준수, 근거 없는 약속을 확인하지 않으므로 원문과 별도 루브릭이 필요합니다.

문제 4

이번 JSON 기록에 재현성을 높이기 위해 추가할 항목 두 가지를 고르면 무엇인가요?

해설 — 실행 날짜, 고정 모델 스냅샷, 제공자 설정, 반복 번호, 입력 ID, 평가자 판정 가운데 목적에 맞는 항목을 추가할 수 있습니다.
