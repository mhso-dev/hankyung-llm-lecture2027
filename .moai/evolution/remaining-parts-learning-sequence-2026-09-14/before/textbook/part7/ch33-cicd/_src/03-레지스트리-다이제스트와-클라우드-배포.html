1학습 목표

  • 레지스트리·다이제스트와 클라우드 배포의 핵심 단계와 종료 조건을 설명할 수 있습니다.
  • 제공된 로컬 실습을 실행하고 성공과 실패를 종료 코드로 구분할 수 있습니다.
  • 실행 기록을 근거로 다음 배포 단계를 진행하거나 중단할 수 있습니다.

2이 내용을 배우는 이유

latest 같은 태그는 새 이미지를 가리키도록 이동할 수 있습니다. 태그만 배포 기록에 남기면 장애가 난 시점에 어떤 바이트를 실행했는지 확인하기 어렵습니다. 이 절에서는 같은 Dockerfile에서 v1과 v2 이미지를 실제로 빌드하고, 서로 다른 이미지 ID를 배포 기록에 고정합니다.

로컬 Docker 데몬은 이미지 빌드와 검사를 담당합니다. 레지스트리 push와 클라우드 반영에는 별도 자격 증명과 대상 환경이 필요하므로 실행하지 않으며, 어느 경계까지 확인했는지 출력과 확인 필요 항목으로 구분합니다.

Ch15의 evaluation-cases.json과 회귀 비교는 이전에 성공했던 답변 품질을 기준선으로 남기는 방법을 보여 주었습니다. Ch29의 에이전트 평가는 최종 답변뿐 아니라 도구 호출 수와 궤적도 확인해야 한다는 점을 다루었습니다. Ch32의 Docker 이미지는 실행 환경을 파일로 고정했습니다. 이 절에서는 그 결과를 자동 검사의 입력으로 사용하며, 원본 평가 자료를 다시 계산했다고 주장하지 않습니다. 공개 실습용 요약 자료의 출처 장과 필드 의미를 README에 기록합니다.

4핵심 개념

변경을 통과시키는 검사대

공항의 수하물은 접수, 보안 검사, 목적지 분류를 차례로 통과합니다. 한 단계가 실패하면 다음 운송 단계로 보내지 않습니다. CI/CD도 변경 하나를 테스트, 정적 검사, 빌드, 평가, 배포 검증의 순서로 처리합니다. 비유에서 검사대는 작업 단계에, 통과 표시는 종료 코드 0에 대응합니다.

정의

이미지 레지스트리(image registry)는 컨테이너 이미지를 저장하고 배포 환경에 전달하는 서비스입니다. 태그(tag)는 `v1`이나 `latest`처럼 사람이 읽기 좋은 이름이지만 같은 태그가 새 이미지로 이동할 수 있습니다. 다이제스트(digest)는 이미지 내용에서 계산한 식별자이므로 `sha256:...` 형식으로 정확한 내용을 가리킵니다. 클라우드 배포에서는 CI가 이미지를 빌드하고 레지스트리에 push한 뒤, 배포 시스템이 승인된 다이제스트를 pull하도록 구성할 수 있습니다. 이 연결에는 레지스트리 인증과 클라우드 권한이 필요하므로 실습에서는 로컬 파일의 SHA-256과 JSON 배포 이력으로 경계를 확인합니다.

앞 절에서 만든 wheel과 평가 보고서는 CI가 만든 결과물입니다. 이 절은 그 결과를 실행 환경과 묶은 OCI 이미지를 다룹니다. Docker의 이미지 ID는 로컬 이미지 구성을 식별하며, 레지스트리에 push한 뒤 받는 manifest digest와 적용 범위를 구분해야 합니다.

도식 읽기

도식의 화살표를 따라가며 현재 단계가 무엇을 입력으로 받고 무엇을 남기는지 확인합니다. 검사 결과가 실패이면 다음 단계 화살표를 따라가지 않습니다. 운영 환경에서는 승인, 비밀 정보, 네트워크 상태 같은 조건이 더해질 수 있습니다.

5실행 예제

같은 Dockerfile에 서로 다른 리비전 빌드 인자를 주어 v1과 v2 OCI 이미지를 실제로 빌드합니다. Docker가 계산한 이미지 ID가 달라지는지 확인하고 v1 식별자를 배포 기록에 저장합니다. 로컬 Docker 데몬까지 실행하며 레지스트리 전송과 클라우드 권한 사용은 수행하지 않습니다.

확인할 점 — 출력의 상태 이름, 실제 값, 기준값, 프로세스 종료 코드를 함께 읽습니다. 성공 메시지만 출력하는 코드는 검사로 사용할 수 없습니다. 실패 조건에서 0이 아닌 종료 코드가 나와야 GitHub Actions 같은 실행기가 작업을 실패로 표시합니다.

6실험 결과 해석

v1과 v2는 같은 태그 이름을 사용할 수 있지만 계산된 다이제스트는 서로 달랐습니다. 따라서 배포 기록에 태그만 남기면 당시의 정확한 내용을 나중에 식별하지 못할 수 있습니다. 다이제스트를 저장하면 롤백 때 이전 내용 식별자를 다시 선택할 수 있습니다. 로컬 이미지 ID 확인은 레지스트리에 push한 manifest digest, 서명, 다중 플랫폼 이미지 목록까지 검증하지 않습니다. 클라우드에서는 승인된 digest를 Deployment 매니페스트의 image 값에 기록하고 OIDC 기반 최소 권한으로 적용합니다.

7주의할 점과 실무 메모

  • 이미지 다이제스트와 이미지 서명은 역할이 다릅니다. 다이제스트는 내용 식별과 변경 탐지를 돕고, 서명 검증은 신뢰한 주체가 만든 이미지인지 확인하는 정책에 사용합니다.
  • 클라우드 자격 증명은 저장소 파일에 넣지 않고 OIDC 또는 비밀 저장소와 최소 권한을 사용합니다.
  • 배포 성공 뒤에도 readiness와 실제 요청 검증이 끝나기 전에는 새 버전이 정상이라고 판단하지 않습니다.

이번 출력의 sha256: 값은 로컬 이미지 ID입니다. 레지스트리 manifest digest, 이미지 서명, 다중 플랫폼 목록은 확인하지 않았습니다. 실제 클라우드 배포 전에는 push 결과의 digest와 배포 매니페스트의 image 값이 같은지 별도로 검사합니다.

8정리와 다음 절

  • 레지스트리는 배포할 이미지를 저장하고 전달합니다.
  • 태그는 이동할 수 있지만 다이제스트는 특정 내용을 식별합니다.
  • 이 실습은 로컬 배포 기록까지 확인했으며 실제 push와 클라우드 반영은 수행하지 않았습니다.

9복습 문제

태그와 다이제스트의 차이는 무엇인가요?

태그는 사람이 정한 이동 가능한 이름이고, 다이제스트는 이미지 내용에 대응하는 식별자입니다.

다이제스트만 확인하면 제작자를 신뢰할 수 있나요?

그렇지 않습니다. 제작자 신뢰에는 이미지 서명과 공급망 정책이 추가로 필요합니다.

실제 배포에 추가로 필요한 것은 무엇인가요?

레지스트리와 클라우드 권한, 배포 대상, readiness 검사, 네트워크 설정 등이 필요합니다.

배포 기록에 다이제스트를 남기는 이유는 무엇인가요?

정확히 어떤 내용을 배포했는지 추적하고 이전 내용을 다시 선택하기 위해서입니다.
