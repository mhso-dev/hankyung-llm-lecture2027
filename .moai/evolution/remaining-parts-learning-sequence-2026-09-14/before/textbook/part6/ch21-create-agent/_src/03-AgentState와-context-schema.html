1학습 목표

  • AgentState에 남길 값과 context로만 전달할 값을 나눌 수 있습니다.
  • ToolRuntime.context에서 권한 정보를 읽는 도구를 작성할 수 있습니다.
  • 실행 결과 상태에 context가 자동 저장되지 않는 이유를 설명할 수 있습니다.

2이 내용을 배우는 이유

실행 중 누적되는 상태와 호출 때 주입하는 컨텍스트를 어떻게 구분하는가?

사용자 식별자나 권한을 대화 메시지에 매번 붙이면 모델이 필요 없는 내부 값까지 읽습니다. 실행 상태와 호출 컨텍스트를 나누면 기록할 값과 도구에만 주입할 값을 구분할 수 있습니다.

3앞에서 배운 내용

MessagesState와 TypedDict 상태를 사용합니다. 필요한 자료와 객체는 노트북에서 다시 선언하므로 앞 노트북의 메모리 상태는 필요하지 않습니다.

4핵심 개념

정의와 구체 예

AgentState는 messages를 포함하는 TypedDict 기반 상태입니다. 구조화 출력을 구성했을 때에는 결과 상태에 structured_response가 추가됩니다. 사용자 필드를 추가한 SupportState는 request_tag를 실행 결과까지 유지합니다. context_schema는 실행 중 도구와 미들웨어가 읽을 컨텍스트의 형식을 선언합니다. ToolRuntime[UserContext]를 받은 도구는 runtime.context로 user_id와 access_level을 읽습니다.

context를 상태에 자동 보존하지 않는다고 해서 로그에도 남지 않는다는 뜻은 아닙니다. 추적 시스템과 도구 로그에 민감 정보가 기록되는지 별도로 점검해야 합니다.

7주의할 점과 실무 메모

  • context를 상태에 자동 보존하지 않는다고 해서 로그에도 남지 않는다는 뜻은 아닙니다. 추적 시스템과 도구 로그에 민감 정보가 기록되는지 별도로 점검해야 합니다.
  • 실제 모델 호출 비용은 절당 1달러 미만으로 예상하며, API 키 값은 출력하지 않습니다.
  • 재실행하면 모델 문장과 지연이 달라질 수 있으므로 저장된 원문 출력과 조건을 함께 읽습니다.

8정리와 다음 절

  • AgentState는 messages를 포함하는 TypedDict 기반 상태이며, 구조화 출력을 구성했을 때 structured_response가 결과 상태에 추가됩니다. SupportState의 request_tag는 실행 결과까지 유지됩니다. context_schema는 실행 중 도구와 미들웨어가 읽을 컨텍스트의 형식을 선언합니다.
  • request_tag=lesson-03은 최종 상태 키에 남았습니다. context로 전달한 student-7과 read-only는 도구 답에 나타났지만 결과 상태에 context 키가 자동으로 생기지 않았습니다. 이 차이를 두 assert로 확인했습니다.

9복습 문제

1. request_tag는 왜 AgentState에 두나요?

해설 — 실행 중 누적하고 최종 결과에서도 확인할 값이기 때문입니다.

2. access_level은 어디에서 읽나요?

해설 — 도구의 ToolRuntime.context에서 읽습니다.

3. 사용자 상태 스키마는 어떤 형식을 사용하나요?

해설 — TypedDict 기반 AgentState를 확장합니다.
