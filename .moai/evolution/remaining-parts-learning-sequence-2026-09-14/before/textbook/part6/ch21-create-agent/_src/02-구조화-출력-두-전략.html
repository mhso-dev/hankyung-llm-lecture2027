1학습 목표

  • ToolStrategy와 ProviderStrategy가 구조화 결과를 만드는 방식을 구분할 수 있습니다.
  • structured_response에서 Pydantic 스키마의 필드를 읽을 수 있습니다.
  • 메시지 수와 모델 호출 수가 같은 측정값이 아님을 설명할 수 있습니다.

2이 내용을 배우는 이유

ToolStrategy와 ProviderStrategy는 어디에서 스키마를 강제하고 결과를 어떤 키로 반환하는가?

자연어 답을 정규식으로 잘라 쓰면 필드가 빠지거나 형태가 바뀔 때 오류가 늦게 드러납니다. 에이전트 루프 안에서 스키마를 검증하면 후속 코드가 topic, answer, source 필드를 확정된 형식으로 받을 수 있습니다.

3앞에서 배운 내용

앞 절의 create_agent 호출을 사용합니다. 필요한 자료와 객체는 노트북에서 다시 선언하므로 앞 노트북의 메모리 상태는 필요하지 않습니다.

4핵심 개념

정의와 구체 예

ToolStrategy는 구조화 결과를 도구 호출 형식으로 만들고 LangChain이 스키마를 검증합니다. ProviderStrategy는 모델 제공자의 네이티브 구조화 출력 기능을 사용합니다. 두 방식 모두 최종 상태의 structured_response에 Pydantic 객체를 저장합니다. 스키마 유형을 직접 넘기면 모델 프로필에 따라 전략을 자동 선택할 수도 있습니다.

7주의할 점과 실무 메모

  • ProviderStrategy의 사용 가능 여부는 모델 프로필과 제공자 기능에 달려 있습니다. 도구와 구조화 출력을 동시에 쓸 때는 모델이 두 기능을 함께 지원하는지도 확인해야 합니다.
  • 실제 모델 호출 비용은 절당 1달러 미만으로 예상하며, API 키 값은 출력하지 않습니다.
  • 재실행하면 모델 문장과 지연이 달라질 수 있으므로 저장된 원문 출력과 조건을 함께 읽습니다.
