1학습 목표

  • TTFT와 total 비교의 핵심 구성 요소를 실제 출력에서 구분할 수 있습니다.
  • first_event, TTFT 근삿값, total의 측정 지점을 구분할 수 있습니다.
  • 별도 호출의 usage와 추정 비용을 시간 결과와 함께 해석할 수 있습니다.

2이 내용을 배우는 이유

스트리밍을 켰다는 사실만으로 응답 전체가 빨라지지는 않습니다. 사용자가 첫 변화를 본 시간, 클라이언트가 내용이 있는 첫 답변 조각을 받은 시간, 최종 결과가 끝난 시간을 따로 측정해야 합니다. 이 구분은 Ch30의 FastAPI 서버 전송 이벤트(SSE) 응답 설계에 그대로 이어집니다.

3앞에서 배운 내용

Ch23에서 체크포인터와 thread_id가 상태를 저장하는 방법을 배웠고, Ch24에서 interrupt와 재개 사건을 확인했습니다. 이번 챕터에서는 같은 실행을 사용자 화면과 운영 로그에 어떤 단위로 보여 줄지 다룹니다.

4핵심 개념

구체적인 상황

사용자는 화면에 첫 변화가 나타나면 시스템이 동작한다고 느끼지만, 그 변화가 실제 답변 내용인지 ‘시작됨’ 표시인지는 구분하기 어렵습니다. 세 시각을 같은 이름으로 기록하면 성능 보고서가 잘못됩니다.

정의

이 실습의 첫 토큰까지의 시간(Time To First Token, TTFT) 근삿값은 요청을 시작한 뒤 클라이언트가 내용이 있는 첫 모델 메시지 조각을 받을 때까지 걸린 시간입니다. 조각 하나가 토큰 하나와 같다는 뜻은 아니며 서버 내부의 첫 토큰 생성 시각도 아닙니다. first_event는 모드와 관계없이 첫 사건을 받은 시간이고 total은 마지막 사건까지 소비한 전체 시간입니다. custom의 시작 사건을 TTFT라고 부르면 모델이 아직 답을 만들기 전의 값을 첫 답변 내용으로 오해하게 됩니다.

5실행 예제

perf_counter()를 요청 직전에 시작하고 updates, messages, custom을 순서대로 각각 새로 실행합니다. 첫 yield를 first_event로, messages의 내용이 있는 첫 chunk를 TTFT 근삿값으로, 반복 종료를 total로 기록합니다. 세 실행은 같은 질문을 각각 별도로 모델에 요청하므로 answer 길이와 usage도 함께 기록합니다. rows의 ttft_s는 messages에서만 숫자가 됩니다.

설치 셀은 Python 3.12 환경에 LangChain 1.4.0, langchain-openai 1.6.0, LangGraph 1.2.11을 고정합니다. 입력·캐시 입력·출력 토큰 수와 공개 가격표를 사용해 각 호출의 추정 비용을 계산하며 키 값은 출력하지 않습니다.

확인할 점 — messages 행에만 ttft_s 값이 있는지, updates와 custom 행에는 비어 있는지 확인합니다. 마지막 합계는 세 API 호출의 비용을 더한 값입니다.

6실험 결과 해석

이번 실행에서 updates의 first_event와 total은 모두 2.622초였습니다. messages는 first_event 0.613초, 내용이 있는 첫 조각까지 0.620초, total 1.101초였습니다. custom은 시작 사건이 0.003초에 왔고 total은 1.431초였습니다. updates와 custom에는 내용이 있는 messages 조각이 없으므로 TTFT 근삿값을 기록하지 않았습니다.

세 모드는 순서대로 실행한 별도 API 호출입니다. 입력은 각 45토큰, 캐시 입력은 각 0토큰이었지만 출력은 91·84·111토큰, 답변 길이는 143·150·179자로 달랐습니다. 호출별 추정 비용은 각각 $0.00044325, $0.00041175, $0.00053325이며 세 호출의 합계는 $0.00138825입니다. 따라서 이 한 번의 실행으로 모드의 속도나 비용 우열을 단정할 수 없습니다.

7주의할 점과 실무 메모

  • 한 번의 측정만으로 모델이나 모드의 우열을 단정할 수 없습니다. 운영 환경에서는 워밍업 횟수, 반복 횟수, 입력 길이, 네트워크 구간, 백분위수를 함께 기록합니다. 비용은 스트리밍 여부보다 실제 입력·출력 토큰 수와 호출 횟수에 따라 달라집니다.
  • 비밀 키는 .env에서 읽고 존재 여부만 확인합니다. 노트북 출력, 예외 메시지, 배포 묶음에 키가 포함되지 않았는지 발행 전에 검사합니다.
  • 외부 모델 호출의 응답과 지연은 공급자 상태에 따라 달라집니다. 운영 기준은 반복 측정의 중앙값과 상위 백분위수로 정합니다.

8정리와 다음 절

  • first_event, TTFT 근삿값, total은 측정 지점이 다릅니다.
  • TTFT 근삿값은 messages의 내용이 있는 첫 조각을 기준으로 하며, 서버 내부의 첫 토큰 시각은 아닙니다.
  • 세 번의 별도 API 호출 결과는 출력 길이와 usage가 다르므로 모드의 성능 우열을 뜻하지 않습니다.

다음 학습과 이어지는 지점 — Ch30에서는 messages와 custom 사건을 FastAPI SSE로 브라우저에 전송하고 연결 종료와 재접속을 처리합니다.

9복습 문제

1. custom의 first_event 0.003초를 TTFT라고 부를 수 있나요?

해설 — 아닙니다. 그 사건은 노드가 보낸 시작 알림이며 모델 답변의 첫 내용 조각이 아닙니다.

2. messages의 first_event 0.613초와 TTFT 근삿값 0.620초가 다른 이유는 무엇인가요?

해설 — first_event는 받은 첫 사건을 기록하고, TTFT 근삿값은 내용이 있는 첫 조각이 도착할 때까지 기다려 기록하기 때문입니다.

3. 세 모드의 total 시간을 바로 비교할 수 없는 이유는 무엇인가요?

해설 — 세 모드는 순서대로 별도 API 호출로 실행했고 출력 토큰 수와 답변 길이도 달랐기 때문입니다.

4. 세 호출의 합계 비용 $0.00138825는 무엇을 더한 값인가요?

해설 — updates, messages, custom을 각각 실행한 세 호출의 추정 비용을 더한 값입니다. messages 한 호출만의 비용이 아닙니다.
