1학습 목표

  • 평가 요청을 OpenAI Batch API 입력 JSONL로 만들 수 있습니다.
  • 요청 식별자(custom_id) 중복·엔드포인트(endpoint)·요청 본문을 제출 전에 검증할 수 있습니다.
  • Batch 완료·할인과 로컬 입력 검증의 확인 범위를 구분할 수 있습니다.

2이 내용을 배우는 이유

회귀 스위트가 커지면 평가 요청을 한 건씩 기다리는 방식은 느리고 비용 관리도 어렵습니다. OpenAI Batch API는 비동기 작업을 24시간 완료 창으로 처리하며 공식 문서는 50% 할인을 안내합니다. 다만 제출과 완료 확인에는 시간이 걸리므로 수업 기본 경로는 JSONL 생성과 정적 검증까지 수행합니다.

3앞에서 배운 내용

앞 절의 회귀 사례에는 질문, 응답과 평가 모델 기준이 있습니다. Batch 한 행은 요청 식별자(custom_id), HTTP 메서드(method), 엔드포인트(endpoint), 요청 본문(body)을 포함합니다. 이 절은 /v1/responses용 요청을 만듭니다.

4핵심 개념

쉬운 예

택배 상자에 운송장 번호를 붙이듯 비동기 평가 요청에는 custom_id를 붙입니다. 나중에 결과가 다른 순서로 도착해도 이 ID로 원래 사례를 찾고 누락이나 중복을 확인할 수 있습니다.

정의

JSONL은 한 줄에 하나의 JSON 객체를 저장하는 형식입니다. 각 Batch 요청의 custom_id는 결과를 원래 사례와 연결하는 요청 식별자이며 파일 안에서 중복되면 안 됩니다. 메서드(method)는 POST, url은 선택한 엔드포인트(endpoint), 요청 본문(body)에는 모델과 입력을 둡니다. 업로드할 때 purpose는 batch이고 현재 완료 기한(completion window)은 24h입니다.

5실행 예제

노트북은 세 평가 사례를 batch-eval-input.jsonl로 만듭니다. 각 줄을 다시 읽어 JSON 구문, custom_id 유일성, POST, /v1/responses, 모델과 입력 존재를 검증합니다. 실제 파일 업로드·Batch 생성·완료 대기·청구 할인 확인은 수행하지 않습니다. 따라서 출력은 입력 파일이 유효하다는 증거이며 Batch가 완료되었다는 증거가 아닙니다.

6실험 결과 해석

세 사례를 /v1/responses용 JSONL 3행으로 만들고 JSON 구문, 요청 식별자 유일성, POST 메서드, 엔드포인트, 요청 본문 필드를 모두 통과했습니다. 이어서 만든 모의 결과에서는 누락 ID, 중복 ID와 알 수 없는 ID를 각각 검출했습니다. 실제 업로드·완료·50% 할인 청구는 확인하지 않았습니다.

7주의할 점과 실무 메모

  • Batch는 실시간 사용자 응답 경로에 사용하지 않고 오프라인 평가에 사용합니다.
  • 공식 50% 할인 정책과 실제 계정 청구액 확인은 구분합니다.
  • 입력 파일에 API 키나 개인정보를 넣지 않으며 업로드 전 별도 검사를 수행합니다.

8정리와 다음 절

  • Batch 요청은 요청 식별자(custom_id)로 원래 사례와 연결합니다.
  • JSONL 형식과 요청 식별자 문제를 업로드 전에 검사했습니다.
  • 입력 검증과 실제 제출·완료·할인 확인을 구분했습니다.
