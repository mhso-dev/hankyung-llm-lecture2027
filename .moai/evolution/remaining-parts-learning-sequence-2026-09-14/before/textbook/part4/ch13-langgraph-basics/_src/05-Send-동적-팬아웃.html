1학습 목표

  • Send가 목적지 노드와 그 노드에 전달할 상태를 함께 지정한다는 점을 설명할 수 있습니다.
  • 입력 개수에 따라 동적으로 늘어나는 맵(map) 단계를 구성할 수 있습니다.
  • 리듀서로 팬아웃 결과를 하나의 상태에 모을 수 있습니다.

2이 내용을 배우는 이유

검색 결과가 세 건이면 세 문서를 확인하고 다섯 건이면 다섯 문서를 확인해야 합니다. 문서 수만큼 노드를 미리 등록할 수는 없습니다. Send는 조건부 엣지에서 같은 노드를 서로 다른 입력으로 여러 번 호출해 동적인 맵-리듀스(map-reduce) 흐름을 만듭니다.

이번 절의 질문은 “검색된 문서 수가 실행할 때마다 달라도 각 문서를 같은 노드로 보내고 결과를 모을 수 있을까요?”입니다. 노트북 출력과 그래프 그림을 함께 읽어 답합니다.

3앞에서 배운 내용

Ch12에서는 여러 검색 후보를 RRF로 합친 뒤 재정렬했습니다. 이번 절은 세 개의 짧은 문서 조각을 입력으로 사용해 각 조각의 글자 수와 ID를 병렬 작업으로 계산합니다. 실제 검색은 7절에서 연결합니다.

각 노트북은 Python 3.12 새 커널에서 독립 실행되며 이전 절의 메모리나 개인 경로를 사용하지 않습니다.

4핵심 개념

쉬운 예

우체국이 편지 묶음을 주소별 배달원에게 나눠 주고 완료 보고를 다시 모으는 상황과 같습니다.

정의

팬아웃(fan out)은 한 흐름을 여러 작업으로 나누는 구조입니다. Send(node, arg)는 실행할 노드 이름과 그 실행에만 전달할 상태를 담습니다. 조건 함수가 Send 목록을 반환하면 항목 수만큼 노드 실행이 만들어집니다. 여러 실행이 같은 results 키를 갱신하므로 operator.add 리듀서가 결과 목록을 합칩니다.

코드에서 읽는 순서

dispatch는 documents 목록을 순회해 문서마다 Send 객체 하나를 만듭니다. 각 객체의 node에는 inspect_document를, arg에는 그 실행이 읽을 document를 넣습니다. 세 Send는 같은 함수를 호출하지만 서로 다른 작은 상태를 받습니다. 각 실행은 results에 딕셔너리 하나가 든 목록을 반환하고 operator.add가 이 목록들을 합칩니다. 마지막에 ID로 정렬하면 실행 완료 순서가 달라도 입력 문서와 결과를 안정적으로 대응할 수 있습니다.

5실행 예제

문서마다 Send를 만드는 dispatch와 길이를 검사하는 inspect_document를 정의합니다. 문서 세 건을 입력했을 때 결과가 세 건인지 확인한 뒤, 입력을 한 건으로 줄여 결과 수도 한 건이 되는지 비교합니다. 결과는 ID 순으로 정렬해 입력 문서와 대응합니다.

6실험 결과 해석

문서 세 건을 입력하면 inspect_document 노드가 세 번 실행되고 results에 세 딕셔너리가 모입니다. 문서 한 건으로 다시 실행하면 결과도 한 건입니다. 그래프의 노드 수는 바뀌지 않았지만 실행 작업 수가 입력 길이에 따라 달라졌습니다.

문서 세 건과 한 건을 넣은 실행에서 결과 개수가 각각 3과 1이었습니다. 등록한 그래프 구조는 같고 Send 목록 길이만 달라진 비교입니다.

이번 실행은 입력 문서 수에 따라 Send 작업과 결과 수가 달라지는지만 확인했습니다. 작업 시간과 동시 실행 정도를 측정하지 않았으므로 병렬 처리의 성능 향상을 판단할 수 없습니다.

7주의할 점과 실무 메모

  • Send에 전달하는 arg는 목적지 노드가 읽을 수 있는 키를 포함해야 합니다.
  • 결과를 ID로 정렬하면 병렬 실행 결과의 순서가 달라도 같은 항목끼리 비교할 수 있습니다.
  • 동시에 같은 키를 갱신할 때는 합칠 리듀서가 필요합니다.

8정리와 다음 절

  • 문서 3건은 Send 작업 3개와 결과 3건을 만들었습니다.
  • 문서 1건으로 바꾸면 같은 그래프에서 결과도 1건이 됐습니다.
  • results 리듀서가 각 작업의 목록을 하나로 합쳤습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 한 노드가 상태를 갱신하면서 다음 목적지까지 함께 반환하는 Command를 사용합니다.
