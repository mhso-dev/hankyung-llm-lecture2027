1학습 목표

  • StateGraph의 상태, 노드, 엣지를 코드에서 구분할 수 있습니다.
  • START와 END를 포함한 순차 그래프를 컴파일하고 실행할 수 있습니다.
  • 실행 흔적과 Mermaid 문자열을 읽어 실제 실행 순서를 확인할 수 있습니다.

2이 내용을 배우는 이유

Part 3에서 만든 RAG는 문서 읽기, 검색, 병합, 재정렬, 생성 함수를 차례로 호출했습니다. 단계가 두세 개일 때는 함수 나열도 읽을 수 있습니다. 조건에 따라 건너뛰거나 되돌아가는 단계가 생기면 호출 순서가 여러 곳에 흩어집니다. LangGraph는 상태와 실행 순서를 하나의 그래프로 선언해 이 문제를 다룹니다.

이번 절의 질문은 “파이썬 함수 나열을 상태 그래프로 옮기면 실행 순서를 어떻게 읽을 수 있을까요?”입니다. 노트북 출력과 그래프 그림을 함께 읽어 답합니다.

3앞에서 배운 내용

Ch12의 통합 실습은 질문을 받고 검색 결과와 출처를 만든 뒤 답변을 생성했습니다. 이번 절은 그 처리 단계에서 모델 호출을 제외하고, 질문 정리와 검색어 작성이라는 두 함수를 그래프에 배치합니다. 앞 노트북의 변수에는 의존하지 않습니다.

각 노트북은 Python 3.12 새 커널에서 독립 실행되며 이전 절의 메모리나 개인 경로를 사용하지 않습니다.

4핵심 개념

쉬운 예

지하철 노선도에서 역은 작업이고 선은 이동 순서입니다.

정의

LangGraph의 상태(State)는 그래프 실행 동안 노드들이 함께 읽고 갱신하는 데이터입니다. 노드(node)는 상태를 읽어 일부 값을 반환하는 함수이고, 엣지(edge)는 다음 노드를 정하는 연결입니다. StateGraph는 이 세 요소를 모아 실행 가능한 그래프를 만드는 빌더입니다. START는 입력이 들어오는 가상 시작점이고 END는 더 실행할 노드가 없음을 나타내는 가상 끝점입니다. compile()은 선언한 노드 이름과 연결을 확인하고 invoke()할 수 있는 실행 객체를 반환합니다.

코드에서 읽는 순서

코드는 상태 형식을 먼저 선언한 뒤 노드 함수를 정의합니다. 각 함수의 state 매개변수는 현재 상태를 읽고, 반환 딕셔너리는 다음 상태에 반영할 값만 담습니다. 이어서 add_node로 이름과 함수를 연결하고 add_edge로 START부터 END까지의 순서를 적습니다. compile() 뒤 invoke()에 입력 상태를 전달하면 엣지를 따라 노드가 실행됩니다. trace 값과 Mermaid의 화살표를 함께 보면 파이썬 함수 이름, 그래프 노드 이름, 실제 실행 순서를 하나씩 대응할 수 있습니다.

6실험 결과 해석

실행 결과의 trace에는 normalize와 make_query가 차례로 남습니다. Mermaid 출력에서도 START에서 normalize, make_query, END로 이어지는 화살표가 나타납니다. 노드를 등록한 순서가 실행 순서를 정하는 것이 아니라 add_edge로 선언한 연결이 실행 순서를 정합니다.

질문을 바꾼 두 실행에서 검색어는 달라졌지만 trace는 같은 두 노드를 기록했습니다. 고정 엣지가 입력 내용과 무관하게 같은 실행 순서를 만든 결과입니다.

이번 실행은 엣지로 고정한 두 노드의 순서만 확인했습니다. 노드가 늘어나거나 분기가 생긴 그래프의 실행 특성은 뒤 절에서 따로 확인합니다.

7주의할 점과 실무 메모

  • 노드는 전체 상태를 복사해 반환하지 않고 바꿀 키만 반환할 수 있습니다.
  • compile() 전의 객체는 설계도이며 compile() 결과가 실행 객체입니다.
  • 이 절의 그래프는 모델이 경로를 정하지 않습니다. 코드로 적은 고정 엣지가 경로를 정합니다.

8정리와 다음 절

  • 두 질문 모두 normalize와 make_query를 같은 순서로 실행했습니다.
  • 노드는 상태 갱신을 반환하고 엣지는 실행 순서를 정했습니다.
  • Mermaid에서 START부터 END까지의 고정 연결을 확인했습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 각 노드가 반환한 일부 값이 기존 상태에 어떻게 반영되는지 확인합니다.
