1학습 목표
비동기 Engine과 세션 팩터리의 역할을 설명할 수 있습니다.
동시 작업마다 별도 AsyncSession을 만들어 조회할 수 있습니다.
순차 실행과 동시 실행의 대기 시간 차이를 실제 출력으로 해석할 수 있습니다.
2이 내용을 배우는 이유
Ch30에서 FastAPI 요청 함수를 비동기로 작성했습니다. 요청 함수가 데이터베이스를 기다리는 동안 이벤트 루프까지 멈추면 다른 사용자의 요청을 처리하지 못합니다. 이 절에서는 비동기 드라이버와 세션을 사용해 같은 조회 세 건을 순차 실행과 동시 실행으로 비교합니다.
3앞에서 배운 내용
Ch2에서 `async`와 `await`가 대기 가능한 작업을 표현한다는 점을 배웠고, Ch30에서는 FastAPI 경로 함수를 비동기로 작성했습니다. Ch4에서 만든 관계형 표와 기본 SQL도 다시 사용합니다.
4핵심 개념
구체적인 상황
식당의 주문 담당자가 한 주문의 조리가 끝날 때까지 계산대 앞에 서 있으면 다음 손님을 받지 못합니다.
정의
주문표를 주방에 넘긴 뒤 다른 주문을 받으면 같은 시간에 더 많은 손님을 응대할 수 있습니다. 비동기 입력·출력(asynchronous I/O)은 데이터베이스 응답처럼 외부 작업을 기다리는 동안 이벤트 루프가 다른 작업을 진행하게 하는 방식입니다. `AsyncEngine`은 비동기 드라이버와 연결 풀을 관리하고, `AsyncSession`은 한 업무 작업에서 실행한 조회와 변경을 묶습니다. 하나의 세션은 변경 가능한 상태를 가지므로 여러 `asyncio` 작업이 공유하지 않습니다. 각 작업이 세션 팩터리에서 자기 세션을 받아야 합니다.
이 절의 새 용어 — AsyncEngine, AsyncSession, 비동기 I/O, 커넥션 풀
운영에서 경계를 정하는 방법
운영 코드에서는 엔진을 애플리케이션 시작 시 한 번 만들고 요청마다 다시 만들지 않습니다. 엔진은 접속 주소와 풀을 오래 유지하고, 세션은 요청이나 백그라운드 작업 한 건처럼 짧은 범위에서 생성합니다. FastAPI 의존성이라면 `yield` 앞에서 세션을 만들고 뒤에서 닫아 반환할 수 있습니다. 조회 결과를 모두 메모리에 옮긴 뒤 응답을 만드는지, 결과 스트림을 보내는 동안에도 연결을 점유하는지 구분해야 합니다. 후자는 느린 클라이언트 한 명이 연결을 오래 차지할 수 있습니다. 또한 비동기는 데이터베이스가 SQL을 더 빨리 계산하게 만들지 않습니다. 여러 독립 작업의 대기 시간을 겹칠 수 있게 합니다. CPU를 많이 쓰는 변환이나 하나의 트랜잭션 안에서 순서가 필요한 SQL은 `gather`로 묶는 대상이 아닙니다. 동시 실행을 늘리기 전에 작업이 서로 독립적인지, 풀에 충분한 연결이 있는지, PostgreSQL이 추가 부하를 감당하는지 차례로 확인합니다.
코드 읽기와 개념 경계
create_async_engine은 비동기 드라이버와 연결 풀을 묶은 Engine을 만들고, async_sessionmaker는 요청마다 사용할 AsyncSession 생성 규칙을 만듭니다. async with Session() as session은 세션의 사용 범위를 표시하며 await session.execute(...)에서 실제 데이터베이스 입출력이 발생합니다. scalar_one()은 결과가 정확히 한 값이어야 한다는 조건까지 확인해 문자열을 반환합니다.
asyncio.gather로 세 조회를 동시에 시작해도 하나의 AsyncSession을 공유하면 안 됩니다. 세션은 하나의 진행 중인 트랜잭션을 나타내는 변경 가능한 객체이기 때문입니다. 예제의 delayed_read가 호출마다 새 세션을 여는 이유가 여기에 있습니다. 출력의 순차·동시 시간 차이는 로컬 pg_sleep 조건에서 관찰한 값이며 실제 쿼리 성능의 일반적인 배수를 뜻하지 않습니다.
도식 읽기
푸른 요청 상자에서 시작해 붉은 세션 상자와 초록 연결 풀을 지나 보라색 PostgreSQL 응답으로 이동합니다. 색은 처리 단계를 구분하며 실패 여부를 뜻하지 않습니다.
5실행 예제
노트북은 전용 스키마와 세 행을 만든 뒤 세션 하나의 조회 결과를 확인합니다. 이어 각 작업이 자기 세션을 열도록 구성하고, 0.15초 대기 조회 세 건을 순차 실행과 동시 실행으로 비교합니다.
확인할 점 — 세 조회 결과가 같은지, 순차 시간과 동시 시간이 각각 얼마인지 확인합니다. 시간 차이는 독립된 대기와 세 개 연결이라는 실험 조건에서만 해석합니다.
6실험 결과 해석
실제 실행에서는 0.15초 대기 쿼리 세 건의 순차 실행 시간이 약 0.46초였고, 연결 세 개로 동시 실행한 시간은 약 0.20초였습니다. 운영 성능 전체를 뜻하지 않으며, 인위적인 대기와 로컬 네트워크에서 동시 대기의 차이만 보여 줍니다.
이 결과는 Docker의 독립 PostgreSQL 17.8 컨테이너와 작은 데이터에서 측정했습니다. 행 수, 네트워크, 디스크, 동시 요청 수가 달라지면 시간과 실행 계획도 달라집니다.
실제 서비스에서는 쿼리별 지연뿐 아니라 한 요청이 세션을 보유한 전체 시간도 측정합니다. 동시 실행 개수를 풀 크기보다 크게 바꿔 대기 구간이 생기는 지점을 찾고, 그 결과를 요청 제한 설정에 반영합니다.
7주의할 점과 실무 메모
비동기 함수 안에서 동기 데이터베이스 드라이버를 호출하면 이벤트 루프가 멈출 수 있습니다.
`AsyncSession` 하나를 여러 동시 작업이 공유하면 트랜잭션 상태가 섞일 수 있습니다.
애플리케이션 종료 시 `await engine.dispose()`로 풀의 유휴 연결을 정리합니다.
운영 전 확인 순서
배포 전에는 요청 수를 한 단계씩 늘리며 활성 세션 수와 풀 체크아웃 수를 기록합니다. 동기 드라이버가 섞이지 않았는지 실행 경로를 확인하고, 타임아웃 뒤 세션이 닫히는지도 시험합니다. 취소된 요청이 연결을 계속 점유한다면 동시 처리 수를 늘리기 전에 정리 경로를 고쳐야 합니다.
8정리와 다음 절
`AsyncEngine`은 비동기 드라이버와 연결 풀을 관리합니다.
동시 작업마다 별도 `AsyncSession`을 만들며 하나의 세션을 공유하지 않습니다.
대기 쿼리 세 건은 순차 약 0.46초, 동시 약 0.20초였습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 세션과 연결이 변경 작업을 어떤 단위로 확정하고 되돌리는지 확인합니다.
9복습 문제
1. `AsyncEngine`을 사용하는 주된 이유는 무엇인가요?
해설 — 데이터베이스 응답을 기다리는 동안 이벤트 루프가 다른 작업을 처리할 수 있게 하기 위해서입니다.
2. `AsyncSession`을 여러 동시 작업이 공유해도 되나요?
해설 — 안 됩니다. 세션은 한 논리 트랜잭션의 변경 가능한 상태를 가지므로 작업마다 별도 세션을 사용합니다.
3. 동시 실행 시간이 짧아진 결과가 모든 쿼리의 성능 향상을 보장하나요?
해설 — 보장하지 않습니다. 이 실험은 독립적인 대기 쿼리 세 건과 연결 세 개라는 조건에서만 동시 대기 효과를 확인했습니다.
4. 엔진을 마칠 때 호출한 메서드는 무엇인가요?
해설 — `await engine.dispose()`이며 풀의 유휴 연결을 정리합니다.

1학습 목표
커밋과 롤백이 결정되는 트랜잭션 블록의 경계를 설명할 수 있습니다.
출금과 입금을 서로 다른 트랜잭션에 둔 실패 결과를 재현할 수 있습니다.
두 변경을 한 트랜잭션에 묶어 모두 취소되는 결과를 확인할 수 있습니다.
2이 내용을 배우는 이유
에이전트 서비스는 메시지 저장, 사용량 차감, 작업 상태 갱신을 한 요청에서 함께 수행할 수 있습니다. 중간 단계만 데이터베이스에 남으면 다음 재개에서 사실과 다른 상태를 읽습니다. 이 절에서는 이체의 출금과 입금을 사용해 함께 확정하거나 함께 취소하는 경계를 확인합니다.
3앞에서 배운 내용
앞 절에서 작업마다 비동기 세션을 만들었습니다. Ch23에서는 중단 뒤 재개와 멱등성을 배웠습니다. 여기서는 재개가 읽을 데이터 자체를 서로 맞게 저장하는 방법을 다룹니다.
4핵심 개념
구체적인 상황
은행 창구에서 한 계좌의 돈만 줄이고 상대 계좌의 돈을 늘리지 않으면 장부 총액이 달라집니다.
정의
두 기록은 하나의 업무 단위로 처리해야 합니다. 트랜잭션(transaction)은 여러 SQL 문을 하나의 확정 단위로 묶습니다. 원자성(atomicity)은 그 안의 변경이 모두 반영되거나 모두 취소되는 성질입니다. `commit`은 변경을 확정하고 `rollback`은 아직 확정하지 않은 변경을 취소합니다. PostgreSQL의 기본 격리 수준인 READ COMMITTED에서는 각 문장이 시작될 때 이미 확정된 행을 봅니다. 더 강한 격리 수준은 동시 변경 이상을 줄이지만 충돌 재시도 가능성과 비용도 함께 고려해야 합니다.
이 절의 새 용어 — 트랜잭션, 원자성, commit, rollback, 격리 수준
운영에서 경계를 정하는 방법
트랜잭션 경계는 함수의 길이가 아니라 업무 규칙으로 정합니다. 주문 상태를 ‘결제 완료’로 바꾸는 일과 결제 이력을 추가하는 일이 함께 성립해야 한다면 같은 경계에 둡니다. 조회 결과를 화면에 표시하는 작업까지 트랜잭션에 포함해 연결을 오래 점유할 필요는 없습니다. 예외를 잡은 뒤 계속 세션을 사용하려면 먼저 롤백이 끝났는지도 확인합니다. 데이터베이스 제약 조건은 마지막 방어선입니다. 잔액이 음수가 될 수 없다면 CHECK 제약을 두고, 업무 한 건이 중복 저장되면 안 된다면 고유 키를 둡니다. 애플리케이션의 사전 검사만으로는 두 동시 요청이 같은 값을 보고 함께 통과할 수 있습니다. 격리 수준을 높일 때는 실패가 사라진다고 가정하지 않습니다. 충돌한 트랜잭션이 취소될 수 있으므로 재시도 횟수, 같은 업무 식별자, 사용자에게 보여 줄 결과를 함께 설계합니다.
코드 읽기와 개념 경계
트랜잭션은 여러 SQL 문을 하나의 성공 또는 실패 단위로 묶습니다. async with engine.begin() as conn 블록이 정상 종료되면 커밋하고, 예외로 빠져나오면 롤백합니다. Before는 출금 블록이 이미 정상 종료된 뒤 장애를 발생시켜 400과 500이 남습니다. After는 출금과 입금을 같은 블록에 두므로 중간 예외가 두 변경을 모두 되돌립니다.
원자성은 두 행이 동시에 바뀐다는 뜻이지, 업무 규칙의 정확성까지 자동으로 보장하지 않습니다. 잔액이 음수가 되지 않는 조건, 같은 요청의 중복 처리, 동시에 들어온 이체의 격리 수준은 별도 설계가 필요합니다. 따라서 총액 1000 확인은 이 예제의 핵심 불변식을 검사하지만 모든 금융 정합성을 증명하지는 않습니다.
도식 읽기
푸른 출금 뒤 붉은 트랜잭션 경계 안에서 초록색 오류를 만나면 보라색 전체 롤백으로 이동합니다. 화살표는 변경을 확정하기 전의 실행 순서입니다.
5실행 예제
노트북은 잔액 합계 1000에서 시작합니다. Before는 출금을 먼저 확정한 뒤 장애를 내어 총액 900을 관찰하고, After는 출금과 입금을 같은 `engine.begin()` 블록에 두어 예외 때 두 변경이 모두 취소되는지 확인합니다.
확인할 점 — Before의 두 잔액과 총액 900, After의 두 잔액과 총액 1000을 비교합니다. 출력된 RuntimeError는 장애 위치를 표시하고, 실제 롤백 결과는 이후 SELECT로 확인합니다.
6일부러 실패해 보기
Before에서는 출금 트랜잭션이 먼저 확정된 뒤 장애가 발생해 잔액이 400과 500, 총액이 900으로 남았습니다. After에서는 두 변경을 같은 `engine.begin()` 블록에 넣었습니다. 입금 전 예외가 블록 전체를 롤백해 두 잔액은 500과 500, 총액 1000을 유지했습니다.
이 결과는 Docker의 독립 PostgreSQL 17.8 컨테이너와 작은 데이터에서 측정했습니다. 행 수, 네트워크, 디스크, 동시 요청 수가 달라지면 시간과 실행 계획도 달라집니다.
동시 이체까지 검증하려면 두 작업이 같은 계좌를 갱신하도록 실행하고 잠금 대기와 최종 잔액을 확인합니다. 이번 절은 한 요청 내부의 중간 장애만 다루므로 동시 갱신의 격리 현상까지 일반화하지 않습니다.
7주의할 점과 실무 메모
트랜잭션을 오래 유지하면 잠금과 풀 연결 점유 시간이 늘어납니다.
외부 결제 API 호출은 데이터베이스 롤백으로 취소되지 않으므로 멱등성 키와 보상 작업이 필요합니다.
SERIALIZABLE에서 충돌로 취소된 트랜잭션은 같은 업무 키로 안전하게 재시도해야 합니다.
운영 전 확인 순서
장애 시험은 각 SQL 문 사이에서 예외가 난 경우를 나누어 실행합니다. 롤백 뒤 업무 합계와 행별 상태를 모두 조회하고, 같은 요청을 다시 보냈을 때 중복 행이 생기지 않는지도 확인합니다. 운영 로그에는 비밀 값 대신 업무 식별자와 트랜잭션 결과를 남깁니다.
8정리와 다음 절
트랜잭션은 함께 성립해야 하는 SQL 변경을 한 확정 단위로 묶습니다.
별도 커밋은 장애 뒤 총액 900을 남겼고 한 경계의 롤백은 총액 1000을 유지했습니다.
외부 API 부작용에는 데이터베이스 롤백과 별도의 멱등성 설계가 필요합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 트랜잭션을 사용하는 코드가 기대하는 표 구조를 버전별 마이그레이션으로 관리합니다.

1. 원자성은 어떤 상태를 보장하나요?
해설 — 한 트랜잭션 안의 변경이 전부 확정되거나 전부 취소되는 상태를 보장합니다.
2. Before의 총액이 900이 된 이유는 무엇인가요?
해설 — 출금이 별도 트랜잭션에서 먼저 커밋된 뒤 입금 전에 장애가 발생했기 때문입니다.
3. `engine.begin()` 블록에서 예외가 나면 어떻게 되나요?
해설 — 블록에서 시작한 아직 확정되지 않은 트랜잭션을 롤백합니다.
4. 외부 API 호출도 데이터베이스 롤백으로 취소되나요?
해설 — 취소되지 않습니다. 멱등성 키나 보상 작업을 별도로 설계해야 합니다.

1학습 목표
Alembic 리비전 파일이 스키마 변경 순서를 기록하는 방법을 설명할 수 있습니다.
`upgrade head`와 `downgrade base`로 표의 생성과 제거를 실행할 수 있습니다.
카탈로그 조회로 적용·제거·재적용 상태를 확인할 수 있습니다.
2이 내용을 배우는 이유
코드 배포에서 모델 필드를 추가해도 이미 운영 중인 데이터베이스 표는 자동으로 바뀌지 않습니다. 코드와 스키마 버전이 어긋나면 요청이 시작된 뒤에야 없는 열이나 표 오류가 나타납니다. 이 절에서는 변경 파일을 버전 기록으로 남기고 적용과 롤백을 실제 카탈로그 조회로 확인합니다.
3앞에서 배운 내용
Ch4에서 `CREATE TABLE`을 실행했고 앞 절에서는 트랜잭션 경계를 정했습니다. Alembic은 이 DDL 변경의 순서와 현재 적용 위치를 파일과 버전 표로 관리합니다.
4핵심 개념
구체적인 상황
건물 도면을 지우고 매번 새로 그리면 어느 공사에서 문제가 생겼는지 알기 어렵습니다.
정의
변경 도면에 번호를 붙이고 순서대로 적용하면 현재 상태와 되돌릴 지점을 확인할 수 있습니다. 마이그레이션(migration)은 데이터베이스 구조 변경을 순서가 있는 코드로 기록하는 작업입니다. 리비전(revision)은 한 변경의 식별자이며 `down_revision`은 바로 앞 변경을 가리킵니다. `upgrade()`는 앞으로 적용할 DDL을, `downgrade()`는 되돌릴 DDL을 작성합니다. 자동 생성은 모델과 데이터베이스의 차이를 초안으로 만들 뿐이므로, 데이터 손실 가능성과 제약 조건을 사람이 읽어야 합니다.
이 절의 새 용어 — 마이그레이션, revision, upgrade, downgrade
운영에서 경계를 정하는 방법
배포 순서는 새 코드와 이전 코드가 잠시 함께 실행될 수 있다는 전제에서 정합니다. 새 열을 바로 필수로 만들기보다 먼저 NULL을 허용해 추가하고, 새 코드가 값을 쓰게 한 뒤 기존 행을 채우고, 마지막 배포에서 제약을 강화하는 방식이 안전할 수 있습니다. 이를 확장과 축소 패턴이라고 부릅니다. 롤백 파일도 작성 가능하다는 사실과 운영에서 안전하게 실행 가능하다는 사실은 다릅니다. 열을 삭제한 뒤 downgrade로 같은 이름의 열을 다시 만들더라도 원래 행 값은 돌아오지 않습니다. 큰 표의 인덱스 생성은 오랜 잠금이나 많은 I/O를 만들 수 있으므로 PostgreSQL 버전과 `CREATE INDEX CONCURRENTLY` 사용 조건을 따로 검토합니다. CI에서는 빈 데이터베이스에 처음부터 head까지 적용하는 경로와, 현재 운영 리비전에서 다음 리비전으로 이동하는 경로를 모두 시험합니다. 배포 기록에는 적용한 리비전 ID와 실행 시간을 남겨 장애 시 코드 버전과 스키마 버전을 함께 찾을 수 있게 합니다.
코드 읽기와 개념 경계
Alembic 리비전은 데이터베이스 구조 변경을 순서가 있는 파일로 기록합니다. upgrade head는 현재 데이터베이스를 최신 리비전까지 올리고, downgrade base는 정의된 역방향 작업을 적용합니다. 노트북의 subprocess.run(..., check=True)는 명령이 실패하면 즉시 예외를 내며, 이어지는 to_regclass 조회가 실제 표의 생성과 제거를 확인합니다.
코드 롤백과 스키마 다운그레이드는 같은 일이 아닙니다. 애플리케이션만 이전 버전으로 돌려도 이미 삭제하거나 변환한 열은 돌아오지 않습니다. 데이터가 손실되는 변경은 역방향 SQL보다 먼저 확장-이행-축소 순서를 검토하고 백업 복구 시간을 측정해야 합니다. 이 실습은 교육용 표 하나의 가역성만 확인합니다.
도식 읽기
푸른 리비전 파일을 붉은 upgrade 명령이 적용하면 초록색 버전 표와 tickets 표가 생깁니다. 보라색 downgrade는 반대 방향 변경을 실행합니다.
5실행 예제
노트북은 Alembic 설정 폴더를 찾고 명령 실행 함수를 준비합니다. 빈 스키마에 `upgrade head`를 적용해 tickets 표를 확인하고, `downgrade base`로 제거한 뒤 다시 최신 리비전을 적용합니다.
확인할 점 — 마이그레이션 폴더 이름, 적용 뒤 표 이름, 다운그레이드 뒤 `None`, 재적용 뒤 복구된 표 이름을 순서대로 확인합니다. 이 절은 실행 시간을 출력하지 않습니다.
6일부러 실패해 보기
`upgrade head` 뒤에는 `ch31_migration.tickets`와 Alembic 버전 기록이 생성되었습니다. `downgrade base` 뒤 `to_regclass`는 NULL을 반환해 표가 제거됐음을 확인했습니다. 다시 `upgrade head`를 실행하자 같은 표가 복구되었습니다. 표를 되돌렸다는 사실만 확인했으며 운영 데이터가 안전하게 복원된다는 뜻은 아닙니다.
이 결과는 Docker의 독립 PostgreSQL 17.8 컨테이너와 작은 데이터에서 측정했습니다. 행 수, 네트워크, 디스크, 동시 요청 수가 달라지면 시간과 실행 계획도 달라집니다.
롤백 시간을 측정할 때는 DDL 실행 시간과 데이터 되채우기 시간을 나눕니다. 배포 제한 시간을 넘는 변경은 한 리비전에 모두 넣지 않고 호환 가능한 여러 단계로 나누어 각 단계의 중단 가능 지점을 기록합니다.
7주의할 점과 실무 메모
삭제 열이나 타입 축소는 롤백만으로 데이터를 복구하지 못할 수 있으므로 먼저 백업과 복원 연습이 필요합니다.
여러 애플리케이션 인스턴스가 시작할 때 동시에 마이그레이션을 실행하지 않도록 배포 단계에서 한 번 실행합니다.
자동 생성 결과에는 이름 없는 제약 조건과 데이터 변환 절차가 빠질 수 있어 파일을 검토해야 합니다.
운영 전 확인 순서
마이그레이션 검증에서는 빈 데이터베이스 적용, 현재 리비전에서 다음 리비전 적용, 한 단계 롤백을 구분합니다. 각 경로에서 Alembic 버전과 실제 열·제약·인덱스를 조회합니다. 시간 측정이 필요한 DDL은 운영과 비슷한 행 수의 복제 환경에서 실행합니다.
8정리와 다음 절
Alembic 리비전은 스키마 변경의 앞뒤 순서를 코드로 기록합니다.
upgrade, downgrade, 재적용을 `to_regclass`의 표 존재 여부로 확인했습니다.
되돌리는 DDL이 있어도 삭제한 운영 데이터가 자동으로 복원되지는 않습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 요청이 늘 때 마이그레이션된 데이터베이스 연결을 풀에서 어떻게 빌리고 반환하는지 확인합니다.

1학습 목표
연결 풀의 크기·초과 연결·대기 제한이 요청에 미치는 영향을 설명할 수 있습니다.
유일한 연결을 오래 점유해 두 번째 요청의 TimeoutError를 재현할 수 있습니다.
연결을 일찍 반환하고 대기 제한을 조정한 뒤 두 작업의 성공을 확인할 수 있습니다.
2이 내용을 배우는 이유
FastAPI가 동시에 많은 요청을 받아도 PostgreSQL이 허용하는 연결 수는 제한되어 있습니다. 요청마다 새 연결을 무제한으로 만들거나 반환을 늦추면 데이터베이스가 정상이어도 애플리케이션에서 대기 시간 초과가 발생합니다. 이 절에서는 크기 1인 풀을 의도적으로 고갈시키고 대기 제한과 연결 범위를 조정합니다.
3앞에서 배운 내용
첫 절에서 `AsyncEngine`이 연결 풀을 관리한다는 점을 확인했습니다. 앞 절까지 만든 트랜잭션과 마이그레이션도 결국 풀에서 빌린 연결로 실행됩니다.
4핵심 개념
구체적인 상황
도서관에 열람용 태블릿이 한 대뿐이면 한 사람이 반납할 때까지 다음 사람이 기다립니다.
정의
반납 시간이 없으면 대기열은 끝없이 늘어납니다. 커넥션 풀(connection pool)은 미리 열어 둔 데이터베이스 연결을 요청에 빌려주고 사용 뒤 다시 보관하는 구성 요소입니다. `pool_size`는 유지하는 연결 수, `max_overflow`는 순간적으로 추가할 연결 수, `pool_timeout`은 연결을 얻기 위해 기다릴 최대 초입니다. 이 값은 각각 크게 정하는 문제가 아닙니다. 애플리케이션 프로세스 수를 곱한 전체 연결 수가 PostgreSQL 한도와 운영 여유 안에 들어가야 합니다.
이 절의 새 용어 — 커넥션 풀, pool_size, max_overflow, pool_timeout
운영에서 경계를 정하는 방법
풀 설정은 프로세스 하나의 숫자만 보면 부족합니다. 예를 들어 웹 프로세스 네 개가 `pool_size=5`, `max_overflow=5`를 사용하면 순간 최대 연결은 40개가 될 수 있습니다. 여기에 작업 프로세스, 관리자 접속, 마이그레이션 연결을 더한 값이 PostgreSQL의 허용 범위 안에 있어야 합니다. 풀 고갈 지표는 오류 수만이 아닙니다. 연결 체크아웃 대기 시간, 체크아웃된 연결 수, 쿼리 시간, 트랜잭션 시간을 함께 관찰해야 원인이 느린 SQL인지 반환 누락인지 구분할 수 있습니다. `pool_pre_ping`은 오래된 연결을 사용하기 전에 상태를 확인하는 데 도움을 주지만 매번 추가 왕복이 생깁니다. `pool_recycle`은 일정 시간이 지난 연결을 교체하지만 실행 중인 쿼리를 빠르게 만들지는 않습니다. 요청 제한과 백프레셔도 필요합니다. 데이터베이스가 처리할 수 있는 수보다 많은 작업을 무제한으로 대기시키면 메모리와 사용자 대기 시간만 늘어납니다. 짧은 대기 뒤 명확한 오류를 반환하고 재시도 정책을 적용할지 업무 특성에 따라 결정합니다.
코드 읽기와 개념 경계
연결 풀은 열린 데이터베이스 연결을 재사용하고 동시에 빌릴 수 있는 수를 제한합니다. pool_size는 유지할 기본 연결 수, max_overflow는 일시적으로 더 만들 수 있는 수, pool_timeout은 연결을 얻기 위해 기다릴 최대 시간입니다. 연결을 빌린 async with 블록이 끝나면 실제 소켓을 없애기보다 풀에 반환합니다.
풀을 크게 하면 모든 문제가 해결되는 것이 아닙니다. 애플리케이션 인스턴스 수와 각 풀의 최대 연결을 곱한 값이 데이터베이스 허용치를 넘을 수 있습니다. 느린 쿼리나 커밋하지 않은 트랜잭션이 연결을 오래 점유하면 작은 트래픽에서도 고갈됩니다. 따라서 대기 시간, 사용 중 연결 수, 쿼리 시간을 함께 봐야 원인을 구분할 수 있습니다.
도식 읽기
푸른 동시 요청이 붉은 크기 1인 풀에 모이고 초록색 대기 제한을 지납니다. 보라색 마지막 상자는 연결 반환과 TimeoutError 두 결과가 갈리는 지점입니다.
5실행 예제
노트북은 연결 하나와 짧은 `pool_timeout`을 둔 엔진에서 첫 작업이 연결을 점유하게 합니다. 두 번째 작업의 제한 시간 초과를 관찰한 뒤, 짧은 쿼리와 충분한 대기 시간을 사용해 두 작업을 완료합니다.
확인할 점 — Before의 `TimeoutError`와 풀 상태, After의 두 결과와 전체 소요 시간을 확인합니다. 성공은 연결을 빌리고 반환한 이 실험 조건을 뜻하며 운영 연결 수의 적정값을 정하지 않습니다.
6일부러 실패해 보기
Before에서는 풀 크기 1, 추가 연결 0, 대기 제한 0.2초로 설정했습니다. 첫 쿼리가 0.6초 동안 연결을 점유하자 두 번째 쿼리는 `TimeoutError`를 냈습니다. After에서는 첫 작업을 0.25초로 줄이고 대기 제한을 1초로 늘렸습니다. 두 번째 작업은 첫 연결이 반환된 뒤 같은 풀 연결을 받아 1을 반환했습니다.
이 결과는 Docker의 독립 PostgreSQL 17.8 컨테이너와 작은 데이터에서 측정했습니다. 행 수, 네트워크, 디스크, 동시 요청 수가 달라지면 시간과 실행 계획도 달라집니다.
After가 성공한 이유는 풀 용량이 늘어서가 아니라 첫 연결이 제한 시간 안에 반환됐기 때문입니다. 요청 수가 계속 늘면 다시 대기하므로 실제 처리량과 허용 지연을 기준으로 풀과 작업 큐를 함께 조정합니다.
7주의할 점과 실무 메모
대기 제한만 늘리면 오류가 늦게 나타날 뿐 처리량 문제는 남을 수 있습니다.
세션과 결과 스트림을 요청 수명보다 오래 보관하지 말고 필요한 데이터만 읽은 뒤 연결을 반환합니다.
프로세스가 네 개면 프로세스별 풀 설정의 합계를 계산하고 관리자·마이그레이션용 연결 여유도 남깁니다.
운영 전 확인 순서
부하 시험은 평균 지연만 보지 않고 연결 대기 시간의 상위 백분위수와 시간 초과 수를 함께 기록합니다. 쿼리 종료 뒤 체크아웃 수가 원래 값으로 돌아오는지 확인합니다. 연결 누수가 의심되면 요청별 체크아웃과 체크인 이벤트를 짧은 기간 추적합니다.
8정리와 다음 절
풀 크기와 추가 연결 수는 모든 프로세스의 합계로 계산합니다.
유일한 연결이 대기 제한보다 오래 점유되자 `TimeoutError`가 발생했습니다.
연결 범위를 짧게 하고 대기 시간·쿼리 시간·체크아웃 수를 함께 관찰합니다.
다음 학습과 이어지는 지점 — 마지막 절에서는 같은 PostgreSQL 인스턴스에 벡터 표와 체크포인터 표가 있을 때 색인과 백업 범위를 확인합니다.

2이 내용을 배우는 이유
에이전트 서비스는 검색 문서와 실행 상태를 같은 PostgreSQL에 저장할 수 있습니다. 벡터 표만 백업하면 대화 재개 정보가 사라지고, 체크포인터 표만 백업하면 검색 결과를 다시 만들 시간과 원본이 필요합니다. 마지막 절에서는 두 표 집합이 함께 존재하는 구조와 HNSW 인덱스, 논리 백업의 포함 범위를 확인합니다.
3앞에서 배운 내용

4핵심 개념
구체적인 상황
한 창고에 상품과 배송 장부를 함께 보관하면 창고 주소는 하나지만 재고와 장부의 수명과 복구 우선순위는 다릅니다.
정의
PostgreSQL 스키마는 관련 표의 이름 공간을 나누며, 인덱스는 특정 표의 조회 경로를 추가합니다. HNSW(Hierarchical Navigable Small World)는 여러 층의 근접 그래프를 탐색하는 근사 최근접 이웃 인덱스입니다. 코사인 거리 쿼리에는 `vector_cosine_ops` 연산자 클래스를 맞춰야 합니다. 체크포인터는 그래프 실행 단계의 상태와 중간 쓰기를 저장합니다. 논리 백업(logical backup)은 `pg_dump`가 스키마와 행을 SQL 또는 아카이브 형식으로 추출하는 방식입니다. 백업 파일의 존재만으로 복구가 보장되지 않으므로 별도 데이터베이스에 복원하고 애플리케이션 조회까지 확인해야 합니다.
이 절의 새 용어 — HNSW, 연산자 클래스, 체크포인터, 논리 백업, 복원 연습
운영에서 경계를 정하는 방법
공존 설계에서는 같은 서버를 쓴다는 사실보다 소유권과 복구 순서를 문서로 남기는 일이 중요합니다. 애플리케이션 마이그레이션이 체크포인터 패키지가 만든 표를 변경하지 않게 스키마와 권한을 나눌 수 있습니다. 백업 범위에는 표뿐 아니라 확장, 함수, 인덱스, 시퀀스와 필요한 역할을 검토합니다. HNSW 인덱스는 원본 벡터 행에서 다시 만들 수 있으므로 복구 시간을 줄이기 위해 백업할지, 백업 크기를 줄이고 복원 뒤 재생성할지 선택할 수 있습니다. 선택은 데이터량과 허용 복구 시간에 달려 있습니다. 체크포인터는 오래된 스레드를 계속 보관하면 빠르게 늘 수 있으므로 제품의 보존 기간과 삭제 작업을 정합니다. `pg_dump`는 실행 시점의 서로 맞는 스냅샷을 만들지만, 지속 복제나 시점 복구 전체를 대신하지 않습니다. 정기 복원 훈련에서는 새 데이터베이스에 확장을 설치하고 덤프를 복원한 뒤 최근 스레드 재개, 문서 검색, 인덱스 존재와 권한을 애플리케이션 경로로 확인합니다.
코드 읽기와 개념 경계
pgvector 표의 임베딩은 의미 검색용 애플리케이션 데이터이고, LangGraph 체크포인터 표는 실행 상태를 이어가기 위한 운영 데이터입니다. 같은 PostgreSQL 스키마에 놓을 수 있어도 생성 주체와 복구 기준이 다릅니다. HNSW 인덱스는 근사 최근접 이웃 검색을 돕지만, 행이 세 개인 실습에서는 최적화기가 순차 스캔을 선택할 수 있습니다. 인덱스가 존재한다는 사실과 실제 계획에서 사용됐다는 사실을 구분합니다.
논리 백업에 두 종류의 표 정의가 들어갔다는 검사는 백업 범위를 확인합니다. 이것만으로 벡터 값, 체크포인트 행, 확장 설치, 복구 후 검색 결과까지 보장되지는 않습니다. 운영 검증은 새 데이터베이스에 복원한 뒤 행 수와 대표 벡터 검색, 스레드 재개를 실행해야 합니다.
도식 읽기
푸른 문서·HNSW와 붉은 체크포인터 표가 초록색 ch31_shared 스키마에 공존합니다. 보라색 pg_dump 상자는 이 스키마를 선택한 논리 백업입니다.
5실행 예제
노트북은 문서 세 건과 코사인 HNSW 인덱스를 만들고 대표 벡터 검색과 `EXPLAIN` 계획을 확인합니다. 이어 PostgresSaver 체크포인트를 저장하고, 전용 스키마의 논리 덤프를 별도 데이터베이스에 복원합니다.
확인할 점 — 가장 가까운 문서, Seq Scan 실행 계획, 체크포인트 결과값, 복원 뒤 문서·체크포인트 행 수와 HNSW 인덱스 이름을 확인합니다. 그래프 스레드 재개 자체는 이 노트북의 실행 범위가 아닙니다.
6실험 결과 해석
전용 `ch31_shared` 스키마에 문서 세 건과 코사인 HNSW 인덱스를 만들었습니다. `[0.9,0.1,0]`에 가장 가까운 문서는 ‘배송’이었습니다. 데이터가 세 행뿐이어서 실제 `EXPLAIN (ANALYZE, BUFFERS)`에서는 최적화기가 순차 스캔을 선택했습니다. 인덱스를 만들었다는 사실만으로 모든 쿼리가 그 인덱스를 사용하지 않음을 확인했습니다. PostgresSaver로 value 6을 12로 계산한 체크포인트를 실제 저장했습니다. 논리 덤프를 별도 `ch31_restore` 데이터베이스에 복원한 뒤 문서 3행, 1개 이상의 체크포인트 행, HNSW 인덱스를 다시 조회했습니다.
이 결과는 Docker의 독립 PostgreSQL 17.8 컨테이너와 작은 데이터에서 측정했습니다. 행 수, 네트워크, 디스크, 동시 요청 수가 달라지면 시간과 실행 계획도 달라집니다.
실행 계획의 Seq Scan은 HNSW 생성 실패가 아닙니다. 세 행에서는 전체를 읽고 정렬하는 비용이 작아 최적화기가 순차 스캔을 선택했습니다. 행 수와 통계를 운영 규모에 맞춘 뒤 같은 EXPLAIN을 반복해야 인덱스 선택과 버퍼 사용을 판단할 수 있습니다.
7주의할 점과 실무 메모
근사 인덱스는 정확 검색과 속도·재현율 특성이 다르므로 Ch11 평가셋으로 변경 전후를 측정합니다.
WAL과 정기 논리 백업은 목적이 다릅니다. 필요한 복구 시점과 허용 손실 시간을 먼저 정합니다.
백업에는 확장 설치 명령과 역할·권한이 환경에 따라 다르게 포함될 수 있으므로 깨끗한 복원 대상에서 연습합니다.

pgvector 표의 임베딩은 의미 검색용 애플리케이션 데이터이고, LangGraph 체크포인터 표는 실행 상태를 이어가기 위한 운영 데이터입니다. 같은 PostgreSQL 스키마에 놓을 수 있어도 생성 주체와 복구 기준이 다릅니다. HNSW 인덱스는 근사 최근접 이웃 검색을 돕지만, 행이 세 개인 실습에서는 최적화기가 순차 스캔을 선택할 수 있습니다. 인덱스가 존재한다는 사실과 실제 계획에서 사용됐다는 사실을 구분합니다.
## 실제 쿼리 계획
행이 세 개뿐인 표에서 최적화기가 HNSW보다 순차 스캔을 선택하는지 실행 계획을 읽습니다.
## 체크포인터 표 공존
공식 체크포인터 구현의 `setup()`으로 같은 스키마에 운영 표를 추가합니다.
## 논리 백업 확인
전용 스키마를 SQL 형식으로 덤프하고 두 종류의 표 정의가 모두 포함되는지 검사합니다.
### 백업을 새 데이터베이스에 복원하여 확인
이 셀은 Docker 컨테이너 안에서 `pg_dump`를 실행해 `ch31_shared`의 논리 백업을 문자열로 받습니다. `subprocess.run(..., check=True)`는 외부 명령이 실패하면 예외로 중단하며, `text=True`와 `capture_output=True`는 출력을 문자열로 수집하도록 지정합니다. 별도의 실습용 `ch31_restore` 데이터베이스를 다시 만든 뒤 백업을 복원하고 문서·체크포인트 행 수와 HNSW 인덱스 존재를 확인합니다. 이 검사는 모든 벡터 값의 일치나 스레드 재개까지 확인하지는 않습니다. 두 항목은 추가 복구 검사로 구분합니다.
