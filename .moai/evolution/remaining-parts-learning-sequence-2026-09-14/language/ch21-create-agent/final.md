1학습 목표
create_agent의 model·tools·system_prompt가 맡는 역할을 설명할 수 있습니다.

그래프 구조와 실제 메시지 경로가 보여 주는 범위를 구분할 수 있습니다.
2이 내용을 배우는 이유
create_agent의 세 인자가 Ch20의 모델·도구·지시를 어떻게 묶고, 반환 그래프가 어떤 루프를 실행하는가?
Ch20에서는 model 노드, tools_condition, ToolNode, tools→model 엣지를 직접 연결했습니다. create_agent를 사용하면 호출 한 줄로 같은 반복 구조를 얻지만, 문제가 생겼을 때 어느 단계에서 멈췄는지 읽으려면 내부 그래프를 알아야 합니다.
3앞에서 배운 내용
Ch20에서 직접 연결한 StateGraph와 ToolNode를 사용합니다. 필요한 자료와 객체는 노트북에서 다시 선언하므로 앞 노트북의 메모리 상태는 필요하지 않습니다.
4핵심 개념
정의와 구체 예
ReAct는 모델이 상황을 읽고 다음 행동을 정한 뒤 도구 결과를 다시 관찰하는 반복 방식입니다. create_agent의 model은 판단과 답변을 생성하고, tools는 모델이 선택할 수 있는 동작을 제공하며, system_prompt는 근거 사용과 종료 기준을 지시합니다. 반환값은 CompiledStateGraph이므로 invoke, stream, get_graph 같은 LangGraph 인터페이스를 그대로 사용합니다.
코드를 읽는 순서
@tool은 평범한 Python 함수를 모델이 선택할 수 있는 도구 명세로 바꿉니다. 함수 이름은 도구 이름이 되고, 매개변수의 타입 힌트는 입력 형식이 되며, 독스트링은 모델이 언제 이 도구를 골라야 하는지 판단하는 설명이 됩니다. lookup_policy(topic: str) -> str에서 모델은 topic 문자열을 만들고, 실행기는 함수를 호출하며, 반환 문자열은 ToolMessage로 대화 상태에 추가됩니다.
create_agent(model, tools, system_prompt=...)는 이 명세와 모델을 엮어 CompiledStateGraph를 반환합니다. 이 객체를 만드는 순간에는 질문을 처리하지 않습니다. invoke({"messages": ...})를 호출해야 루프가 시작되고, 모델이 도구 호출을 만들지 않을 때 끝납니다. 따라서 print(type(agent).__name__)은 그래프의 종류를, result["messages"]는 한 요청이 실제로 지나간 기록을 보여 줍니다.
도식 읽기
사용자 질문→model→도구 선택→ToolNode→model 또는 END 순서로 읽습니다. 마지막 model이 tool_calls를 만들면 초록 ToolNode로 이동하고, 만들지 않으면 END로 이동합니다.

확인할 점 — 실제 실행은 HumanMessage, 도구 호출이 든 AIMessage, 규정 원문 ToolMessage, 최종 AIMessage의 4개 메시지를 남겼습니다. lookup_policy의 topic은 대출이었고 답에는 14일이 포함됐습니다. get_graph().draw_mermaid_png()는 PNG 서명과 8,388바이트를 반환했습니다. 두 모델 호출의 합은 입력 379토큰, 출력 47토큰, 추정 0.000496달러였습니다.
다른 상황과 적용 경계
같은 구조를 주문 조회에 적용하면 lookup_policy 대신 lookup_order(order_id)를 등록할 수 있습니다. 달라지는 것은 도구의 입력과 반환 자료이고, 모델→도구→관찰→모델이라는 루프는 같습니다. 반대로 항상 한 번만 실행할 계산이라면 모델이 다음 행동을 고를 이유가 없으므로 일반 함수나 고정 그래프가 더 분명합니다.

4핵심 개념
정의와 구체 예
ToolStrategy는 구조화 결과를 도구 호출 형식으로 만들고 LangChain이 스키마를 검증합니다. ProviderStrategy는 모델 제공자의 네이티브 구조화 출력 기능을 사용합니다. 두 방식 모두 최종 상태의 structured_response에 Pydantic 객체를 저장합니다. 스키마 유형을 직접 넘기면 모델 프로필에 따라 전략을 자동 선택할 수도 있습니다.
코드를 읽는 순서
출력 스키마는 모델이 채워야 할 필드의 이름과 타입을 미리 정한 형식입니다. PolicyAnswer(BaseModel)은 topic, answer, source가 모두 문자열이어야 한다고 선언합니다. Field(description=...)의 설명은 사람만 읽는 주석이 아니라 모델에게 각 필드의 의미를 알려 주는 스키마 정보입니다. 에이전트 실행 뒤에는 자연어 메시지를 다시 자르는 대신 result["structured_response"]에서 검증된 PolicyAnswer 객체를 꺼냅니다.
response_format=ToolStrategy(PolicyAnswer)는 스키마를 가상의 도구 호출로 표현하고 LangChain이 결과를 검증하게 합니다. ProviderStrategy(PolicyAnswer)는 제공자 API의 구조화 출력 기능에 같은 스키마를 전달합니다. 둘 다 같은 객체를 반환하지만 강제하는 위치가 다릅니다. 스키마 클래스만 직접 넘기면 모델 프로필을 기준으로 전략을 고를 수 있지만, 이 실습은 차이를 관찰하려고 두 전략을 명시합니다.
도식 읽기
출력 스키마에서 두 갈래로 나뉜 뒤 structured_response에서 합쳐집니다. 초록 ToolStrategy는 도구 메시지를 거치고, 보라색 ProviderStrategy는 제공자 응답 형식을 사용합니다.

구조화 출력은 자연어 답을 표나 데이터베이스 행으로 넘길 때 유용합니다. 예를 들어 상담 분류라면 category, urgency, reason을 필드로 두고, urgency를 제한된 값으로 정의해 후속 분기 코드가 예상하지 못한 문자열을 받지 않게 할 수 있습니다. 사람에게 보여 줄 긴 설명만 필요하다면 별도 스키마가 오히려 수정 비용을 늘릴 수 있습니다.

## 출력 스키마와 두 에이전트
출력 스키마는 모델이 채워야 할 필드의 이름과 타입을 미리 정한 형식입니다. `PolicyAnswer(BaseModel)`은 `topic`, `answer`, `source`가 모두 문자열이어야 한다고 선언합니다. `Field(description=...)`의 설명은 사람만 읽는 주석이 아니라 모델에게 각 필드의 의미를 알려 주는 스키마 정보입니다. 에이전트 실행 뒤에는 자연어 메시지를 다시 자르는 대신 `result["structured_response"]`에서 검증된 `PolicyAnswer` 객체를 꺼냅니다.
`response_format=ToolStrategy(PolicyAnswer)`는 스키마를 가상의 도구 호출로 표현하고 LangChain이 결과를 검증하게 합니다. `ProviderStrategy(PolicyAnswer)`는 제공자 API의 구조화 출력 기능에 같은 스키마를 전달합니다. 둘 다 같은 객체를 반환하지만 강제하는 위치가 다릅니다. 스키마 클래스만 직접 넘기면 모델 프로필을 기준으로 전략을 고를 수 있지만, 이 실습은 차이를 관찰하려고 두 전략을 명시합니다.

## 메인 루프 메시지 확인
구조화 출력은 자연어 답을 표나 데이터베이스 행으로 넘길 때 유용합니다. 예를 들어 상담 분류라면 `category`, `urgency`, `reason`을 필드로 두고, `urgency`를 제한된 값으로 정의해 후속 분기 코드가 예상하지 못한 문자열을 받지 않게 할 수 있습니다. 사람에게 보여 줄 긴 설명만 필요하다면 별도 스키마가 오히려 수정 비용을 늘릴 수 있습니다.
메시지 수는 모델 호출 수와 같지 않습니다. ToolStrategy는 구조화 결과를 나타내는 도구 메시지를 남길 수 있으므로 전체 메시지가 더 많아도 모델을 한 번만 호출했을 수 있습니다. 이번 셀은 `AIMessage` 수와 전체 메시지 수를 따로 세어 이 경계를 확인합니다.

## 상태와 실행 컨텍스트 정의
상태(state)는 그래프 단계 사이에 남고 체크포인터가 저장할 수 있는 실행 데이터입니다. `SupportState(AgentState)`의 `request_tag`는 입력 상태에 들어가고 최종 결과에도 남습니다. 실행 컨텍스트(context)는 한 번의 호출 동안 노드와 도구가 참고하지만 상태 채널로 자동 저장되지 않는 의존 정보입니다. `UserContext`를 데이터 클래스로 선언한 이유는 `user_id`와 `access_level`이라는 입력 형식을 호출 전에 고정하기 위해서입니다.
`ToolRuntime[UserContext]`는 모델이 채우는 도구 인자가 아닙니다. LangChain 실행기가 `current_access`를 호출할 때 런타임 객체를 주입하고, 함수는 `runtime.context`에서 호출자가 건넨 컨텍스트를 읽습니다. `agent.invoke(state, context=UserContext(...))`에서 첫 번째 인자는 누적 상태이고 `context=`는 실행 의존 정보입니다. 두 값을 분리하면 모델에게 권한 값을 도구 인자로 생성하게 하지 않아도 됩니다.
## 컨텍스트를 전달해 실행
## 상태와 컨텍스트 구분
쇼핑 상담에서는 장바구니 항목과 대화 메시지를 상태에 두고, 데이터베이스 연결이나 현재 사용자의 권한 객체를 컨텍스트에 둘 수 있습니다. 같은 권한을 다음 날 다시 써야 한다면 컨텍스트만으로는 충분하지 않으며 별도 저장소에서 다시 읽거나 상태에 필요한 식별자를 남겨야 합니다.
이번 출력에서 `request_tag`가 남고 `context` 키가 없는 사실은 자동 저장 여부만 보여 줍니다. 도구가 컨텍스트 값을 답 문자열에 포함했기 때문에 `read-only`는 메시지에는 나타납니다. 이것을 컨텍스트 객체 전체가 상태에 저장됐다는 뜻으로 해석하면 안 됩니다.

이 노트북은 Python 3.12 새 커널에서 독립 실행합니다.
## 패키지 설치
## 환경 준비
## 로컬 문서와 검색 도구
리트리버(retriever)는 질문을 받아 관련 문서를 반환하는 검색 인터페이스입니다. 이것을 도구로 등록하면 검색 시점과 검색어를 모델이 선택합니다. `search_rules(query: str) -> str`에서 `query`는 모델이 만든 검색 문자열이고, 함수는 `DOCS`를 읽어 관련 문장을 줄바꿈 문자열로 반환합니다. `SEARCH_LOG.append(query)`는 검색 품질을 높이는 기능이 아니라 이번 실행에서 모델이 어떤 검색어를 선택했는지 관찰하는 기록입니다.
고정 RAG는 애플리케이션 코드가 매 질문마다 정해진 검색을 먼저 실행합니다. Agentic RAG는 모델이 검색할지, 어떤 말로 검색할지, 결과가 없을 때 다시 검색할지를 정합니다. `create_agent(..., [search_rules])`는 이 선택권을 제공하지만 검색 결과의 정확성까지 보장하지 않습니다. 도구의 설명과 반환 형식이 모호하면 모델이 적절한 검색어를 만들어도 근거를 잘못 읽을 수 있습니다.
## Agentic RAG 실행
## 검색 결과가 없는 질문
상품 지원 시스템에서는 주문 번호가 있는 질문만 주문 도구를 호출하고 일반 안내는 검색 없이 답하게 할 수 있습니다. 반면 모든 질문이 같은 사내 문서 한 묶음에서 답을 찾아야 한다면 고정 검색이 실행 횟수와 재현성을 관리하기 쉽습니다. 모델 선택이 필요한 경우와 애플리케이션 규칙으로 충분한 경우를 구분합니다.
검색 로그가 두 줄이면 재검색했다는 사실은 알 수 있지만 두 번째 검색어가 더 좋았다는 결론은 문서와 답을 함께 읽어야 합니다. 결과 없음 답변도 성공한 거부인지 검색어 실패인지 구분해야 하므로, 이 셀은 검색어와 최종 답을 함께 출력합니다.
