1학습 목표
pytest·Ruff·wheel 빌드가 서로 다른 결함을 찾는 이유를 설명할 수 있습니다.
별도 프로세스의 종료 코드로 단계의 성공과 실패를 판정할 수 있습니다.
검증한 wheel을 다음 배포 단계가 사용하는 산출물로 구분할 수 있습니다.
2이 내용을 배우는 이유
서비스 코드를 작성한 뒤에도 변경은 계속됩니다. 작은 수정이 기존 기능, 평가 점수, 이미지 내용, 운영 지표에 영향을 줄 수 있습니다. 사람이 매번 같은 명령을 기억해서 실행하면 확인 순서가 빠지거나 서로 다른 환경에서 다른 결과를 얻게 됩니다. 테스트·린트·빌드와 GitHub Actions는 변경을 일정한 순서로 확인하고, 기준을 만족한 결과만 다음 단계로 보내는 방법입니다.
이 장의 실습은 외부 저장소와 클라우드 계정 없이 로컬에서 실행됩니다. 학생은 명령의 출력과 프로세스 종료 코드를 직접 확인합니다. 실제 GitHub Actions와 클라우드 배포에서는 같은 명령을 원격 실행 환경과 배포 권한에 연결합니다. 로컬 성공은 원격 배포 성공을 보장하지 않으므로, 확인한 범위를 명확히 구분합니다.
3앞에서 배운 내용
Ch2에서 pytest와 패키징을, Ch3에서 PR 검토 흐름을, Ch32에서 Docker 이미지를 만들었습니다. 이 절은 이미 배운 검사를 사람이 기억해서 실행하는 대신, 같은 명령과 순서를 워크플로 파일에 기록하는 방법으로 연결합니다.
4핵심 개념
단계마다 다른 검사를 수행하는 생산선
제품 생산선에서 치수 검사, 표면 검사, 포장 검사는 서로 다른 결함을 찾습니다. 코드도 pytest가 동작을, Ruff가 정적 규칙을, wheel 빌드가 배포 파일 생성을 확인합니다. 어느 단계든 종료 코드가 0이 아니면 다음 단계로 보내지 않습니다.
정의
GitHub Actions의 워크플로(workflow)는 저장소의 이벤트에 반응해 하나 이상의 작업(job)을 실행하는 YAML 파일입니다. 각 작업은 실행기(runner)에서 단계(step)를 순서대로 수행합니다. 이 실습의 워크플로는 PR과 main 브랜치 push를 시작 조건으로 삼고, 테스트와 린트와 평가 회귀를 같은 Python 3.12 환경에서 실행합니다. 테스트는 관찰 가능한 동작을 확인하고, 린트는 실행 전에 찾을 수 있는 코드 문제를 검사하며, 빌드는 배포할 파일을 만듭니다. 세 검사는 목적이 다르므로 하나의 성공으로 다른 검사를 대신하지 않습니다.
연속 통합(Continuous Integration, CI)은 저장소 변경을 자주 합치면서 자동 검사로 오류를 이르게 찾는 방식입니다. 연속 전달 또는 연속 배포(Continuous Delivery/Deployment, CD)는 검사를 통과한 결과물을 배포 가능한 상태로 만들거나 실제 환경에 반영하는 과정입니다. 파이프라인(pipeline)은 이 단계와 의존 관계를 기록한 실행 순서입니다. 아티팩트(artifact)는 빌드가 만든 패키지, 이미지, 평가 보고서처럼 다음 단계가 사용하는 결과물입니다.
코드 읽기와 개념 경계
CI의 한 단계는 명령의 화면 문구보다 종료 코드로 성공과 실패를 판단합니다. pytest, Ruff, wheel 빌드는 각각 동작, 정적 규칙, 배포 산출물을 검사하며 서로 대신하지 않습니다. subprocess.run의 returncode가 0이면 성공이고 0이 아니면 실패입니다. 노트북은 일부러 실패하는 임시 테스트와 수정한 테스트를 같은 방식으로 실행해 이 계약을 확인합니다.
로컬에서 세 명령이 통과해도 CI 환경의 Python 버전, 잠금 파일, 운영체제가 다르면 결과가 달라질 수 있습니다. 워크플로에는 실행 환경과 설치 명령을 고정하고, 빌드한 wheel을 다음 배포 단계가 같은 산출물로 사용하도록 보관합니다. 테스트를 배포 때 다시 다른 소스에서 만들면 검증 대상과 배포 대상이 어긋납니다.
도식 읽기테스트 입력에서 pytest·Ruff·wheel 빌드를 차례로 지나 종료 코드로 진행 여부를 결정하는 순서입니다. 각 초록 상자는 앞 단계가 실제로 성공했을 때만 도달합니다.
세 검사의 결과를 한 문구로 합치지 않고 단계별 종료 코드와 산출물 이름을 남깁니다. 어느 단계에서 멈췄는지 알아야 수정할 파일과 다시 실행할 범위를 정할 수 있습니다.
5실행 예제
먼저 제공된 테스트 스위트와 Ruff 검사를 별도 프로세스로 실행합니다. 이어서 임시 폴더에 실패하는 테스트를 만들고 pytest의 실제 종료 코드를 관찰합니다. 같은 테스트의 기대값만 수정해 성공 종료 코드와 비교합니다. GitHub에 PR을 만들지는 않지만, `.github/workflows/ci.yml`에는 같은 명령이 들어 있습니다.
확인할 점 — pytest와 Ruff의 종료 코드 0, 생성된 wheel 한 개를 확인합니다. 임시 실패 테스트는 0이 아닌 코드를, 수정본은 0을 반환하는지 비교합니다.
6일부러 실패해 보기
실패 테스트는 `2 + 2 == 5`라는 잘못된 기대값 때문에 실제로 실패합니다. pytest는 실패 개수와 함께 종료 코드 1을 반환하고, CI 실행기는 이를 작업 실패로 처리할 수 있습니다. 수정본은 기대값을 4로 고정하며 종료 코드 0을 반환합니다. 이 비교는 테스트 실패를 출력 문자열로 흉내 내지 않고 별도 프로세스의 상태로 확인합니다.
7주의할 점과 실무 메모
Actions 버전 태그는 편리하지만 공급망 정책이 엄격한 저장소에서는 검토한 커밋 SHA로 고정합니다.
로컬에 설치된 도구와 원격 실행기의 버전이 다르면 결과가 달라질 수 있으므로 pyproject와 lock 파일을 함께 커밋합니다.
빌드 성공은 서비스의 답변 품질을 뜻하지 않습니다. 평가 회귀는 다음 절에서 별도 단계로 연결합니다.
자동화가 모든 위험을 판단하는 것은 아닙니다. 측정 기준이 빠져 있으면 파이프라인은 빠진 기준을 검사하지 못합니다. 외부 서비스 장애, 권한 오류, 실제 사용자 트래픽의 변화도 로컬 실습만으로 알 수 없습니다. 팀은 자동 검사가 판단할 항목과 사람이 승인할 항목을 배포 정책에 함께 기록해야 합니다.
8정리와 다음 절
CI는 변경마다 같은 검사를 같은 순서로 실행합니다.
프로세스 종료 코드가 자동화의 통과와 중단을 결정합니다.
테스트·린트·빌드는 서로 다른 문제를 확인합니다.
다음 학습과 이어지는 지점 — 이 장에서 만든 상태 검사와 중단 조건은 Ch38 Hooks에서 작업 전후에 자동으로 실행하는 검사의 원형이 됩니다. 최종 프로젝트에서는 실제 저장소 권한과 배포 환경을 연결한 뒤 같은 원칙으로 확장합니다.
9복습 문제
워크플로와 작업의 관계를 설명해 보세요.
워크플로는 이벤트와 전체 자동화 흐름을 정의하고, 작업은 한 실행기에서 수행할 단계의 묶음입니다.
린트가 통과하면 테스트를 생략해도 되나요?
생략할 수 없습니다. 린트는 정적 문제를 찾고 테스트는 실행 결과를 확인하므로 목적이 다릅니다.
실패를 CI가 인식하려면 무엇이 필요하나요?
검사 프로세스가 0이 아닌 종료 코드를 반환해야 합니다.
이 실습에서 실제 GitHub PR을 생성했나요?
생성하지 않았습니다. 로컬 실행과 워크플로 파일의 구조만 검증했습니다.

1학습 목표
승인된 평가 기준선과 현재 결과의 역할을 구분할 수 있습니다.
Groundedness와 추가 도구 호출 수를 독립 기준으로 판정할 수 있습니다.
허용 범위를 벗어난 결과를 0이 아닌 종료 코드로 CI에 전달할 수 있습니다.
2이 내용을 배우는 이유
단위 테스트가 모두 통과해도 에이전트의 답변에서 근거가 빠지거나 도구 호출이 늘 수 있습니다. 이런 변화는 함수 반환값만 검사하는 테스트로 찾기 어렵습니다. 이 절에서는 Ch15의 Groundedness와 Ch29의 궤적 기준을 후보 함수의 실제 출력에 적용해, 품질 저하가 생긴 변경을 종료 코드 1로 중단합니다.
실습은 네 평가 사례를 후보 함수에 다시 입력합니다. 정상 코드에서는 Groundedness 1.00과 추가 호출 0회를 확인하고, 임시 복사본의 답변과 궤적 코드를 손상했을 때 두 기준이 FAIL로 바뀌는지 비교합니다.
3앞에서 배운 내용
Ch15에서 근거성 평가와 기준선을, Ch29에서 최종 답뿐 아니라 도구 호출 궤적을 확인했습니다. 앞 절에서 CI가 종료 코드로 다음 단계 진행 여부를 결정한다는 점을 배웠습니다. 이 절은 두 평가 기준을 그 종료 코드에 연결합니다.
4핵심 개념
승인한 견본과 새 결과 비교
인쇄소는 새 인쇄물을 승인된 견본과 나란히 놓고 색과 위치를 각각 검사합니다. 평가 회귀도 승인된 기준선과 현재 결과를 비교하되, 답의 근거성과 도구 호출 효율을 한 점수로 섞지 않습니다.
정의
회귀(regression)는 새로운 변경 뒤에 이전에 만족하던 동작이나 품질 기준이 깨지는 현상입니다. 단위 테스트가 함수의 정해진 출력을 검사한다면 평가 회귀는 Groundedness, 궤적의 추가 도구 호출 수처럼 확률적 시스템의 품질과 비용을 검사합니다. 기준선(baseline)은 비교할 이전 결과이며, 허용치(tolerance)는 실행 변동을 고려해 받아들일 범위입니다. Ch15의 생성 품질과 Ch29의 궤적 효율을 한 점수로 합치면 원인을 찾기 어려우므로 두 검사를 분리해 표시하고, 모두 통과할 때만 전체 종료 코드 0을 반환합니다.
앞 절에서 CI의 작업과 종료 코드를 확인했습니다. 여기서는 테스트 단계 뒤에 evaluate_regression.py를 추가합니다. 스크립트는 커밋된 점수를 읽는 데 그치지 않고 run_candidate()를 실행해 답변과 도구 목록을 새로 계산합니다.
코드 읽기와 개념 경계
평가 회귀 검사는 현재 결과를 저장된 기준선과 비교해 배포 가능 여부를 종료 코드로 바꿉니다. 이 예제는 근거성 점수와 추가 도구 호출 수를 함께 검사합니다. 임시 복사본에서 답과 도구 호출을 악화시키면 평가 스크립트가 0이 아닌 코드를 반환하고, 원래 구현에서는 0을 반환합니다.
기준선은 영원한 정답이 아니라 승인된 비교점입니다. 질문 집합이나 평가 방식이 바뀌면 점수 변화가 모델 회귀인지 평가 변경인지 분리해야 합니다. 평균 점수만 보면 특정 중요 질문의 큰 하락이 가려질 수 있으므로 핵심 사례별 하한과 전체 집계를 함께 둡니다.
도식 읽기기준선과 현재 결과가 두 비교기로 들어가 Groundedness와 추가 호출 수를 각각 판정한 뒤 하나의 종료 코드로 합쳐지는 흐름입니다.
기준선 변경과 모델 변경이 동시에 일어나면 실패 원인을 구분하기 어렵습니다. 기준선은 별도 리뷰로 갱신하고, 같은 평가 입력에서 후보 변경만 비교합니다.
5실행 예제
공개 고정 자료에서 기준선과 현재 결과를 읽습니다. Groundedness는 기준선보다 0.02를 초과해 낮아지지 않아야 하고, 추가 도구 호출 수는 기준선 이하여야 합니다. 정상 자료로 성공을 확인한 뒤 임시 폴더에서 두 값을 나쁘게 바꾸어 실제 회귀 검사 프로세스가 실패하는지 확인합니다.
확인할 점 — 정상 자료의 두 PASS와 종료 코드 0을 확인합니다. 임시 실패 자료에서는 두 FAIL과 0이 아닌 종료 코드가 함께 나오는지 비교합니다.
6일부러 실패해 보기
실패 자료는 첫 사례의 필수 사실을 답변에서 제거하고 두 번째 사례의 실제 궤적에 불필요한 검색 호출 두 번을 추가합니다. 평가 함수가 원자료를 다시 채점하면 Groundedness와 추가 호출 수가 모두 기준을 벗어납니다. 두 항목은 각각 FAIL로 출력되고 프로세스는 종료 코드 1을 반환합니다. 수정 단계에서는 같은 평가 함수를 원래 네 사례에 실행해 종료 코드 0을 확인합니다. 네 사례의 고정 자료는 연결 방법을 배우기 위한 것이며 실제 모델 전체의 품질을 대표하지 않습니다.
7주의할 점과 실무 메모
확률적 평가에는 반복과 사람 라벨 점검이 필요합니다. 작은 점수 변동만으로 배포를 항상 중단하면 거짓 경보가 늘어날 수 있습니다.
평가 자료를 제품 코드와 함께 무심코 바꾸면 기준이 완화될 수 있습니다. 기준선 변경에는 리뷰와 변경 이유를 남깁니다.
비밀 정보나 실제 고객 대화는 공개 CI 로그와 아티팩트에 포함하지 않습니다.
네 사례가 통과했다는 결과는 네 사례에 포함되지 않은 질문의 품질을 설명하지 않습니다. 사례와 기준선을 바꾸는 PR에서는 제품 코드 변경과 분리해 검토하고, 기준을 낮춘 이유와 사람 검토 결과를 함께 남깁니다.
8정리와 다음 절
평가 회귀는 과거 성공 사례가 변경 뒤에도 유지되는지 확인합니다.
최종 답변 품질과 에이전트 궤적 효율은 분리해 표시합니다.
회귀 실패는 실제 비정상 종료 코드로 CI를 중단합니다.
다음 학습과 이어지는 지점 — 다음 절은 평가를 통과한 코드를 Docker 이미지로 만들고, 정확한 이미지 ID를 배포 기록에 남깁니다.
9복습 문제
기준선은 무엇인가요?
현재 변경과 비교할 이전의 승인된 평가 결과입니다.
Groundedness와 추가 호출 수를 왜 분리하나요?
하나는 답변의 근거 충실도이고 다른 하나는 실행 궤적의 효율이므로 실패 원인과 대응이 다릅니다.
허용치가 필요한 이유는 무엇인가요?
모델 평가가 실행마다 조금 달라질 수 있어 의미 없는 변동과 실제 저하를 구분하기 위해서입니다.
기준선 파일 변경 시 무엇을 확인해야 하나요?
평가 기준을 약화한 것인지, 승인된 개선 결과를 반영한 것인지 리뷰해야 합니다.

Ch32에서 Dockerfile로 이미지를 만들었고 앞 절에서 검사를 통과한 변경만 다음 단계로 보냈습니다. 이 절은 그 결과물을 어떤 식별자로 기록해야 이전 배포를 다시 선택할 수 있는지 다룹니다.
4핵심 개념
진열 이름과 창고 물품 번호
매장의 ‘신상품’ 표시는 다른 상품으로 옮겨 갈 수 있지만 창고 물품 번호는 특정 재고를 가리킵니다. Docker 태그는 이동 가능한 이름이고, 이 실습에서 확인하는 로컬 이미지 ID는 현재 Docker 데몬의 특정 이미지 구성을 식별합니다.
정의
이미지 레지스트리(image registry)는 컨테이너 이미지를 저장하고 배포 환경에 전달하는 서비스입니다. 태그(tag)는 v1이나 latest처럼 사람이 읽기 좋은 이름이며 새 이미지로 이동할 수 있습니다. 로컬 이미지 ID는 현재 Docker 데몬이 빌드한 이미지 구성을 식별합니다. 레지스트리 manifest digest는 push된 매니페스트의 내용을 식별하며, 다중 플랫폼 이미지에서는 목록과 플랫폼별 매니페스트의 적용 단위도 구분해야 합니다. 이 실습은 로컬 이미지 ID와 JSON 이력까지만 확인하고 레지스트리 digest는 생성하지 않습니다.
앞 절에서 만든 wheel과 평가 보고서는 CI가 만든 결과물입니다. 이 절은 그 결과를 실행 환경과 묶은 OCI 이미지를 다룹니다. Docker의 이미지 ID는 로컬 이미지 구성을 식별하며, 레지스트리에 push한 뒤 받는 manifest digest와 적용 범위를 구분해야 합니다.
코드 읽기와 개념 경계
이미지 태그는 이동 가능한 이름입니다. 노트북의 docker image inspect ... {{.Id}}는 레지스트리 digest가 아니라 로컬 이미지 ID를 반환합니다. 실습은 v1과 v2 이미지의 로컬 ID가 다른지 확인하고, 교육용 JSON의 digest 필드에 v1의 로컬 ID를 저장합니다. 필드 이름만 보고 레지스트리 매니페스트를 검증했다고 해석하지 않습니다.
특정 이미지 식별자를 기록해도 그 이미지가 안전하거나 올바르다는 보장은 아닙니다. 서명·취약점 검사·테스트 결과를 같은 산출물과 연결해야 합니다. 레지스트리 manifest digest는 실제 push 뒤 별도로 기록하며, 이번 로컬 실험에서는 관찰하지 않았습니다. 클라우드 배포 권한과 환경 승인은 이미지 생성 권한과 분리합니다.
도식 읽기같은 태그 설명 아래 v1·v2를 빌드하고 서로 다른 로컬 이미지 ID를 얻어 교육용 배포 기록에 저장하는 범위입니다. 레지스트리 push 단계는 도식의 미실행 경계로 읽습니다.
레지스트리에 push하면 manifest digest가 별도로 생기며 다중 플랫폼 목록에서는 적용 단위가 다시 달라질 수 있습니다. 이번 JSON의 `digest` 필드명은 교육용이지만 실제로 담긴 값은 로컬 이미지 ID입니다.
5실행 예제
같은 Dockerfile에 서로 다른 리비전 빌드 인자를 주어 v1과 v2 OCI 이미지를 실제로 빌드합니다. Docker가 계산한 이미지 ID가 달라지는지 확인하고 v1 식별자를 배포 기록에 저장합니다. 로컬 Docker 데몬까지 실행하며 레지스트리 전송과 클라우드 권한 사용은 수행하지 않습니다.
확인할 점 — v1과 v2의 로컬 이미지 ID가 다른지, 교육용 배포 JSON이 v1의 로컬 ID를 저장했는지 확인합니다. 레지스트리 manifest digest는 출력되지 않습니다.
6실험 결과 해석
v1과 v2는 같은 태그 이름을 사용할 수 있지만 로컬 Docker가 반환한 이미지 ID는 서로 달랐습니다. 따라서 배포 기록에 태그만 남기면 당시의 정확한 내용을 나중에 식별하지 못할 수 있습니다. 이 실습은 로컬 이미지 ID를 저장해 롤백에서 이전 로컬 결과를 다시 선택합니다. 로컬 이미지 ID 확인은 레지스트리에 push한 manifest digest, 서명, 다중 플랫폼 이미지 목록까지 검증하지 않습니다. 클라우드에서는 승인된 digest를 Deployment 매니페스트의 image 값에 기록하고 OIDC 기반 최소 권한으로 적용합니다.
7주의할 점과 실무 메모
이미지 다이제스트와 이미지 서명은 역할이 다릅니다. 다이제스트는 내용 식별과 변경 탐지를 돕고, 서명 검증은 신뢰한 주체가 만든 이미지인지 확인하는 정책에 사용합니다.
클라우드 자격 증명은 저장소 파일에 넣지 않고 OIDC 또는 비밀 저장소와 최소 권한을 사용합니다.
배포 성공 뒤에도 readiness와 실제 요청 검증이 끝나기 전에는 새 버전이 정상이라고 판단하지 않습니다.
이번 출력의 sha256: 값은 로컬 이미지 ID입니다. 레지스트리 manifest digest, 이미지 서명, 다중 플랫폼 목록은 확인하지 않았습니다. 실제 클라우드 배포 전에는 push 결과의 digest와 배포 매니페스트의 image 값이 같은지 별도로 검사합니다.

이 실습은 로컬 배포 기록까지 확인했으며 실제 push와 클라우드 반영은 수행하지 않았습니다.

1학습 목표

배포 명령의 성공은 사용자의 요청이 정상이라는 뜻이 아닙니다. 새 버전은 실행 중이어도 오류율과 지연이 함께 나빠질 수 있습니다. 이 절에서는 4분의 메트릭에서 오류율을 계산하고 이미 집계된 p95 지연을 읽어, 기준 위반이 두 구간 연속될 때만 FIRING으로 바꾸는 규칙을 실행합니다.

3앞에서 배운 내용
Ch29에서 운영 지표를 정의했고 Ch34에서 p95 계산을 더 자세히 다룹니다. 앞 절의 배포 식별자는 어떤 변경 뒤 지표가 달라졌는지 연결하는 기준이 됩니다. 이 절은 네 구간의 고정 자료로 지속 조건을 먼저 학습합니다.
4핵심 개념
한 번의 체온과 이어지는 발열
체온이 한 번 높게 측정된 경우와 여러 번 이어진 발열은 대응 기준이 다릅니다. 운영 경보도 한 구간의 임계값 초과와 일정 시간 계속된 이상을 구분해 순간 변동으로 인한 호출을 줄입니다.
정의
모니터링(monitoring)은 서비스의 요청 수, 오류, 지연, 자원 사용량 같은 상태를 지속해서 수집하고 해석하는 활동입니다. 메트릭(metric)은 시간에 따라 기록하는 수치입니다. p95 지연은 요청의 95%가 그 값 이내에 완료되었다는 뜻입니다. 경보 규칙(alerting rule)은 측정식과 임계값, 지속 시간을 조합해 사람이 확인할 상태를 만듭니다. 오류율 하나가 잠깐 높아졌다는 이유만으로 즉시 호출하면 잡음이 많아질 수 있으므로, 이 실습은 오류율과 p95 지연이 동시에 기준을 넘고 두 구간 이어질 때 FIRING으로 판정합니다.
앞 절은 배포 대상을 이미지 ID로 고정했습니다. 이제 대상이 실행된 뒤의 상태를 측정합니다. check_metrics.py는 분 번호로 행을 정렬하고, 두 조건을 동시에 만족한 연속 길이의 최댓값을 계산합니다.
코드 읽기와 개념 경계
오류율은 오류 수를 전체 요청 수로 나눈 비율이고, p95 지연은 요청 시간의 느린 쪽 경계를 나타냅니다. 예제는 각 분의 오류율을 계산하고 자료에 저장된 p95 지연을 읽은 뒤 error_rate > 0.05 and p95_ms > 800을 평가합니다. 한 조건만 넘은 1·2분은 경보가 아니고 두 조건이 함께 넘은 3·4분이 경보 구간입니다.
임계값을 한 번 넘었다고 바로 호출하면 일시적인 잡음에 반응할 수 있고, 너무 오래 기다리면 실제 장애 탐지가 늦어집니다. 지속 시간, 최소 요청 수, 복구 조건을 함께 정해야 합니다. 이 고정 자료의 5%와 800ms는 규칙 동작을 보여 주는 값이며 운영 서비스의 정상 기준은 실제 분포와 사용자 영향으로 정합니다.
도식 읽기1분부터 4분까지 오류율과 p95를 함께 비교합니다. 두 조건이 동시에 참인 구간이 3분과 4분에 이어질 때만 FIRING으로 이동합니다.
경보는 원인을 확정하지 않습니다. 지속 조건이 충족됐다는 사실을 조사 시작 신호로 보내며, 실제 원인은 로그·트레이스·최근 배포 기록과 함께 확인합니다.
5실행 예제
4분의 고정 메트릭을 읽고 각 분의 오류율을 계산합니다. p95 지연은 자료에 미리 집계된 값을 사용하며 원시 요청 시간으로 다시 계산하지 않습니다. 오류율 5% 초과와 p95 800ms 초과를 동시에 적용하며, 두 구간 이상 이어졌을 때 실제 검사 프로세스가 종료 코드 1을 반환하도록 합니다. 운영 경보 도구에서는 같은 조건을 PromQL 표현식과 `for` 지속 시간으로 옮길 수 있습니다.
확인할 점 — 각 분의 오류율·p95·조건 결과를 읽고 3·4분만 동시에 참인지 확인합니다. 검사 프로세스의 FIRING과 종료 코드 1은 이 지속 조건의 결과입니다.
6실험 결과 해석
1분과 2분은 두 조건을 동시에 넘지 않았습니다. 3분과 4분은 오류율과 p95 지연이 함께 기준을 넘었으므로 고정 규칙에서 FIRING이 되었습니다. 종료 코드 1은 배포 후 검증이나 로컬 시뮬레이션을 중단하는 데 사용할 수 있습니다. 실제 Prometheus 경보는 Alertmanager 같은 외부 구성 요소로 알림을 전달하며, 본 실습은 메시지를 외부로 전송하지 않습니다.
7주의할 점과 실무 메모
평균 지연은 일부 매우 느린 요청을 숨길 수 있으므로 p50, p95, p99를 목적에 맞게 함께 봅니다.
LLM 서비스에서는 HTTP 오류뿐 아니라 빈 답변, 도구 실패, 토큰 비용, 대화당 단계 수도 관찰해야 합니다.
경보 임계값은 제공된 예제 수치를 그대로 운영에 적용하지 않고 실제 정상 범위와 오류 예산을 근거로 정합니다.
이 실습의 5%와 800ms는 규칙 실행을 확인하기 위한 값입니다. 운영 임계값은 실제 정상 구간과 오류 예산으로 정합니다. Alertmanager 전송은 실행하지 않았으므로 FIRING 출력은 담당자에게 알림이 도착했다는 증거가 아닙니다.
8정리와 다음 절
메트릭은 시간에 따라 수집하는 수치이며 경보 규칙은 대응이 필요한 조건을 표현합니다.
여러 신호와 지속 시간을 조합하면 순간적인 잡음을 줄일 수 있습니다.
경보는 원인을 확정하지 않으며 조사와 대응을 시작할 근거를 제공합니다.
다음 학습과 이어지는 지점 — 다음 절은 FIRING 상태를 롤백 조건으로 사용하고, 이전 리비전의 HTTP health가 회복되는지 확인합니다.
9복습 문제

관찰한 요청의 95%가 해당 시간 이내에 완료되었다는 뜻입니다.
오류율 한 번 초과만으로 경보를 보내지 않는 이유는 무엇인가요?
순간적인 변동으로 인한 불필요한 호출을 줄이고 지속되는 문제를 구분하기 위해서입니다.
경보가 원인을 알려 주나요?
경보는 조건 충족을 알리며 원인은 로그와 트레이스, 변경 이력을 함께 조사해야 합니다.
LLM 서비스에서 추가로 볼 지표는 무엇인가요?
토큰과 비용, 도구 호출 실패, 단계 수, 근거 충실도 같은 지표가 있습니다.

4핵심 개념
이전 조리법으로 되돌린 뒤 다시 맛보기
새 조리법의 결과가 나쁘면 기록에서 이전 조리법을 선택할 수 있습니다. 그러나 종이의 번호만 바꿔서는 음식이 회복됐는지 알 수 없습니다. 롤백도 이전 배포를 활성화한 뒤 실제 요청을 보내 복구를 확인해야 합니다.
정의
롤백(rollback)은 문제가 있는 새 배포를 이전에 확인된 리비전으로 되돌리는 운영 절차입니다. 리비전(revision)은 배포 상태의 순서가 있는 버전 기록입니다. 롤백은 코드만 이전으로 바꾸는 작업으로 끝나지 않습니다. 데이터베이스 스키마, 메시지 형식, 캐시, 외부 API가 이전 버전과 호환되는지 확인해야 합니다. 복구 검증은 이전 다이제스트가 활성화되었는지, readiness가 정상인지, 오류와 지연이 회복되는지 확인합니다. 이 실습의 v1과 v2 식별자는 고정 문자열 stable-v1과 regressed-v2를 SHA-256으로 해시해 만든 모의 값입니다. 실제 Docker 이미지 ID나 레지스트리 다이제스트를 조회한 값이 아닙니다. 기록의 digest 필드에는 이 모의 값을 넣어 롤백 이력 형식과 상태 전환을 확인합니다. 운영에서는 앞 절에서 확인한 실제 이미지 식별자를 전달해야 합니다.
앞 절에서 가장 긴 위반 구간이 2로 계산되어 FIRING이 되었습니다. 이 절은 그 신호를 복구 판단에 사용합니다. 롤백 사건에는 출발 리비전, 목표 리비전, 이유, 활성 다이제스트를 함께 기록합니다.
코드 읽기와 개념 경계
롤백은 이전 다이제스트를 다시 활성화하는 변경이고, 복구 검증은 그 뒤 서비스가 기대 상태로 돌아왔는지 확인하는 별도 단계입니다. 예제는 v1과 v2 배포 사건을 기록하고 경보 프로세스의 실패를 확인한 뒤 rollback.py로 새 사건을 추가합니다. 마지막에는 활성 다이제스트와 HTTP 검사를 모두 확인합니다.
이전 이미지로 돌아갔다고 데이터베이스와 외부 작업까지 되돌아가는 것은 아닙니다. 스키마가 비호환이거나 이미 발송된 메시지가 있다면 코드 롤백만으로 복구되지 않습니다. 배포 전에는 이전 버전이 현재 데이터 구조를 읽을 수 있는지, 롤백 후 어떤 대표 요청으로 기능을 확인할지 정합니다.
도식 읽기v2의 경보와 HTTP 503에서 이전 v1 식별자를 선택하고, 새 롤백 사건을 남긴 뒤 HTTP 200을 확인하는 순서입니다. 기존 실패 기록은 삭제하지 않습니다.
활성 식별자 확인은 제어 상태를, HTTP 응답은 실행 상태를 보여 줍니다. 두 결과를 함께 확인해야 기록만 바뀌었거나 프로세스만 우연히 살아 있는 경우를 구분할 수 있습니다.

7주의할 점과 실무 메모
되돌릴 이미지가 레지스트리에서 삭제되지 않도록 보존 정책을 정합니다.
하위 호환되지 않는 데이터 마이그레이션은 애플리케이션 롤백만으로 복구되지 않을 수 있습니다. 확장 후 축소 방식이나 별도 데이터 복구 절차를 준비합니다.

롤백 뒤에는 배포 상태와 서비스 지표를 다시 검증합니다.
코드와 데이터의 호환성을 함께 설계해야 복구 절차가 작동합니다.

# 레지스트리·다이제스트와 클라우드 배포
태그와 다이제스트가 가리키는 배포 대상을 비교합니다.
### 이 준비 셀이 하는 일
첫 셀의 `Path` 탐색은 어느 상위 폴더에서 열어도 Ch33의 `pyproject.toml`을 기준으로 실습 폴더를 찾습니다. 뒤의 `subprocess.run(..., cwd=lab, capture_output=True)`은 명령을 별도 프로세스로 실행하고 화면 문구와 종료 코드를 함께 반환합니다. 이 보조 코드는 CI를 흉내 내는 공통 실행 경계이며, 각 절의 판정은 다음 셀에서 해당 명령의 실제 반환값을 읽어 결정합니다.
### 바로 다음 코드를 읽는 방법
이미지 태그는 이동 가능한 이름입니다. 노트북의 `docker image inspect ... {{.Id}}`는 레지스트리 manifest digest가 아니라 현재 Docker 데몬의 로컬 이미지 ID를 반환합니다. 실습은 v1과 v2 이미지의 로컬 ID가 다른지 확인하고, 교육용 JSON의 `digest` 필드에 v1의 로컬 ID를 저장합니다. 필드 이름만 보고 레지스트리 매니페스트를 검증했다고 해석하지 않습니다.
### 이 단계에서 구분할 범위
특정 이미지 식별자를 기록해도 그 이미지가 안전하거나 올바르다는 보장은 아닙니다. 서명·취약점 검사·테스트 결과를 같은 산출물과 연결해야 합니다. 레지스트리 manifest digest는 실제 push 뒤 별도로 기록하며, 이번 로컬 실험에서는 관찰하지 않았습니다. 클라우드 배포 권한과 환경 승인은 이미지 생성 권한과 분리합니다.
## 결과 해석
같은 latest 태그라는 설명만으로 실제 바이트를 식별할 수 없지만, 내용에서 계산한 다이제스트는 v1과 v2가 달랐습니다. 로컬 배포 기록은 다이제스트를 저장했습니다.

# 모니터링과 알림
오류율과 p95 지연이 함께 기준을 넘은 상태가 두 구간 이어지는지 확인합니다.
### 이 준비 셀이 하는 일
첫 셀의 `Path` 탐색은 어느 상위 폴더에서 열어도 Ch33의 `pyproject.toml`을 기준으로 실습 폴더를 찾습니다. 뒤의 `subprocess.run(..., cwd=lab, capture_output=True)`은 명령을 별도 프로세스로 실행하고 화면 문구와 종료 코드를 함께 반환합니다. 이 보조 코드는 CI를 흉내 내는 공통 실행 경계이며, 각 절의 판정은 다음 셀에서 해당 명령의 실제 반환값을 읽어 결정합니다.
### 바로 다음 코드를 읽는 방법
오류율은 오류 수를 전체 요청 수로 나눈 비율이고, p95 지연은 요청 시간의 느린 쪽 경계를 나타냅니다. 예제는 각 분의 오류율을 계산하고 자료에 저장된 p95 지연을 읽은 뒤 `error_rate > 0.05 and p95_ms > 800`을 평가합니다. 한 조건만 넘은 1·2분은 경보가 아니고 두 조건이 함께 넘은 3·4분이 경보 구간입니다.
### 이 단계에서 구분할 범위
임계값을 한 번 넘었다고 바로 호출하면 일시적인 잡음에 반응할 수 있고, 너무 오래 기다리면 실제 장애 탐지가 늦어집니다. 지속 시간, 최소 요청 수, 복구 조건을 함께 정해야 합니다. 이 고정 자료의 5%와 800ms는 규칙 동작을 보여 주는 값이며 운영 서비스의 정상 기준은 실제 분포와 사용자 영향으로 정합니다.
## 결과 해석
1·2분에는 두 조건을 동시에 만족하지 않았습니다. 3·4분에는 오류율 5% 초과와 p95 800ms 초과가 함께 관찰되어 경보 상태가 되었습니다. 이 고정 자료는 임계값 동작만 보여 주며 실제 서비스 정상 범위를 정하지 않습니다.

### 바로 다음 코드를 읽는 방법
롤백은 이전 모의 식별자를 다시 활성화하는 변경이고, 복구 검증은 그 뒤 서비스가 기대 상태로 돌아왔는지 확인하는 별도 단계입니다. 예제는 v1과 v2 배포 사건을 기록하고 경보 프로세스의 실패를 확인한 뒤 `rollback.py`로 새 사건을 추가합니다. 마지막에는 활성 모의 식별자와 HTTP 검사를 모두 확인합니다.
## 실패 재현
