1학습 목표
이 절을 마치면 코사인 유사도(cosine similarity)와 유클리드 거리(L2 distance)가 무엇을 비교하는지 설명할 수 있습니다.
모든 문서 벡터와 질문 벡터의 거리를 계산해 정확 검색 순위를 만들 수 있습니다.
같은 질문에서 거리 함수만 바꾸고 Recall@3 결과를 비교할 수 있습니다.
2이 내용을 배우는 이유
검색 속도를 높이는 HNSW를 평가하려면 먼저 비교 기준이 필요합니다. 정확 검색(exact search)은 질문 벡터를 모든 문서 벡터와 비교합니다. 문서가 많아지면 계산량이 커지지만 후보를 미리 줄이지 않으므로, 근사 검색이 놓친 문서를 확인하는 기준이 됩니다. 이 절에서는 작은 문서 12개를 모두 비교하고 02절에서 같은 결과를 pgvector HNSW와 대조합니다.
3앞에서 배운 내용
Ch 5에서 텍스트를 숫자 목록인 임베딩 벡터로 표현했습니다. Ch 9 학생용 노트북에서는 InMemoryVectorStore.similarity_search()로 질문과 가까운 Document 객체를 받았고, Ch 11은 그 결과의 doc_id가 정답 문서 ID에 포함되는지 측정했습니다. 이번 절은 검색 도구 내부에서 수행하는 거리 계산과 순위 생성을 직접 구현합니다.
4핵심 개념
지도에서 가까운 지점 찾기
두 장소의 좌표가 있으면 두 점 사이의 길이를 측정할 수 있습니다. 임베딩 공간도 각 텍스트를 좌표로 나타냅니다. 다만 수백 개 좌표축의 절대 위치를 비교할지, 원점에서 뻗는 방향을 비교할지에 따라 거리의 뜻이 달라집니다.유클리드 거리(L2 distance)두 벡터의 같은 위치에 있는 값을 뺀 뒤 제곱하여 합하고 제곱근을 구합니다. 값이 작을수록 가깝습니다.코사인 유사도(cosine similarity)두 벡터가 향하는 방향이 얼마나 비슷한지 -1에서 1 사이의 값으로 나타냅니다. 값이 클수록 비슷합니다.정확 검색(exact nearest-neighbor search)질문을 모든 문서와 비교하여 거리 순으로 정렬하는 검색입니다.정규화(normalization)벡터 길이를 1로 맞추는 처리입니다. 길이가 모두 1이면 코사인 순위와 L2 순위가 같아질 수 있습니다.기준선(baseline)설정을 바꾼 결과와 비교할 수 있도록 고정한 첫 실행 결과입니다.
문서 12개와 질문 벡터를 입력하면 모든 벡터의 거리를 계산하고 거리순으로 정렬합니다. 마지막 상자는 top-3 문서 ID와 Recall@3를 확인하는 단계입니다.
정확 검색은 문서 수가 N이고 벡터 차원이 D일 때 질문 하나마다 대략 N×D개의 값을 확인합니다. 12개 문서에서는 부담이 작지만 문서가 수백만 개라면 질문마다 전체를 비교하기 어렵습니다. 02절의 HNSW는 일부 후보를 빠르게 찾는 대신 정확 검색과 결과가 달라질 수 있습니다.
거리 계산의 입력과 방향
임베딩 함수는 문서와 질문을 같은 차원의 벡터로 반환합니다. 코사인 유사도는 방향이 비슷할수록 커지고, L2 거리는 좌표 사이의 직선거리가 가까울수록 작습니다. 따라서 두 순위는 정렬 방향이 반대입니다. 벡터를 단위 길이로 정규화하면 두 척도가 밀접해지지만, 일반 벡터에서 항상 같은 순위를 보장하지는 않습니다.
정확 검색은 질문 벡터와 모든 문서 벡터의 거리를 계산한 뒤 정렬합니다. 반환된 상위 3개는 현재 12개 문서를 모두 비교한 결과이므로 근사 인덱스의 후보 누락이 없습니다. 다만 임베딩이 질문의 의미를 잘 표현했는지까지 보장하지 않으며, 코드 번호 같은 정확한 문자열은 sparse 검색과 따로 비교해야 합니다.
5실행 예제
text-embedding-3-small을 256차원으로 사용해 문서 12개와 질문 8개를 변환합니다. 첫 질문에서 코사인 유사도와 L2 거리를 각각 계산하고, 모든 질문에서 정답 문서가 상위 3개 안에 포함되는지 확인합니다. 이번 입력의 API 비용 예상은 미화 0.01달러 미만입니다.
확인할 점 — 문서 배열의 모양은 (12, 256)이고 질문 배열은 (8, 256)입니다. 첫 문서 벡터의 L2 노름은 1.0001로 1에 가깝습니다. 첫 질문의 두 거리 함수는 같은 세 문서를 같은 순서로 반환했습니다.
6실험 결과 해석
코사인과 L2 모두 8개 질문 가운데 7개에서 정답 문서를 top-3에 포함했습니다. C02의 정답 LIB-002는 두 방식 모두 top-3에 없었습니다. 두 거리 함수의 점수 크기는 서로 다르지만 이 입력에서는 순위와 Recall@3가 같았습니다. 벡터가 거의 단위 길이였다는 관찰과 연결됩니다. 이 결과만으로 다른 임베딩 모델이나 전체 문서에서도 두 거리가 항상 같다고 결론 내릴 수 없습니다.
7주의할 점과 실무 메모
유사도는 클수록 가깝고 거리는 작을수록 가깝습니다. 정렬 방향을 바꾸면 검색 결과가 반대로 됩니다.
모델·차원·전처리가 다른 벡터를 같은 검색 공간에서 비교하지 않습니다.
Recall@3 7/8은 이 교육용 질문 8개에서 얻은 값입니다. Ch 11의 전체 질의셋과 R@50·P@5·nDCG@5를 대신하지 않습니다.
8정리와 다음 절
정확 검색은 모든 문서 벡터를 비교합니다.
거리 함수는 점수의 의미와 정렬 방향이 다릅니다.
이번 단위 길이 벡터에서는 코사인과 L2의 top-3가 같았습니다.
다음 학습과 이어지는 지점 — 02절에서는 같은 12개 벡터를 pgvector에 저장하고 HNSW 결과를 정확 검색과 비교합니다.
9복습 문제
문제 4개 · 해설 포함
1. 정확 검색이 근사 검색의 기준선이 되는 이유는 무엇입니까?
모든 문서를 비교하므로 근사 색인이 후보를 줄이는 과정에서 빠뜨린 문서를 확인할 수 있습니다. 틀렸다면 「이 내용을 배우는 이유」를 다시 읽습니다.
2. 코사인 유사도 0.8과 0.5 가운데 어느 문서가 더 가깝습니까?
0.8인 문서입니다. 유사도는 큰 값이 더 가깝습니다. 틀렸다면 「핵심 개념」의 정의를 다시 읽습니다.
3. L2 거리 배열을 코드로 정렬할 때 오름차순과 내림차순 중 무엇을 사용합니까?
오름차순을 사용합니다. 거리가 작은 문서부터 선택해야 합니다. 틀렸다면 실행 예제의 exact_rank()를 확인합니다.
4. 이번 실험에서 두 거리의 Recall@3가 같았으므로 항상 같은 결과라고 말할 수 있습니까?
말할 수 없습니다. 임베딩 모델과 벡터 길이 분포, 문서가 달라지면 순위가 달라질 수 있습니다. 틀렸다면 「실험 결과 해석」을 다시 읽습니다.

1학습 목표
pgvector의 vector와 halfvec의 차이를 설명할 수 있습니다.
코사인 거리 연산자에 맞는 연산자 클래스로 HNSW 인덱스를 만들 수 있습니다.
ef_search만 바꾸어 정확 검색과 HNSW 결과를 비교할 수 있습니다.
2이 내용을 배우는 이유
01절의 정확 검색은 문서 수에 비례해 비교 횟수가 늘어납니다. HNSW(Hierarchical Navigable Small World)는 가까운 이웃으로 연결된 그래프를 따라가며 일부 후보를 찾습니다. 검색 시간을 줄일 수 있지만 후보를 모두 확인하지 않으므로 정확 검색과 다른 결과가 나올 수 있습니다. 저장 타입·거리 연산자·인덱스 설정을 함께 기록해야 결과를 다시 만들 수 있습니다.
3앞에서 배운 내용
01절의 exact_rank()는 12개 문서를 모두 비교했습니다. Ch 10에서는 모델과 차원이 같아야 같은 공간에서 비교할 수 있음을 확인했습니다. 이번 절은 256차원 벡터를 PostgreSQL 17.10과 pgvector 0.8.2에 저장합니다.
4핵심 개념
여러 층의 길 안내판
큰 지역에서 목적지를 찾을 때 먼저 고속도로로 가까운 구역까지 이동한 뒤 작은 길로 들어갑니다. HNSW도 멀리 연결된 상위 계층에서 시작해 가까운 이웃이 촘촘한 아래 계층에서 후보를 고릅니다.pgvectorPostgreSQL에 벡터 타입, 거리 연산자, 근사 검색 인덱스를 추가하는 확장입니다.HNSW벡터를 여러 계층의 이웃 그래프로 연결하는 근사 최근접 이웃 인덱스입니다.vector단정밀도 부동소수점 값을 저장합니다. 공식 v0.8.6의 HNSW 인덱스 제한은 2,000차원입니다.halfvec반정밀도 값을 저장합니다. HNSW 인덱스 제한은 4,000차원입니다.ef_search검색할 때 고려하는 후보 목록의 크기입니다. 기본값은 40이며 높이면 더 많이 탐색하는 대신 시간이 늘 수 있습니다.연산자 클래스(operator class)인덱스가 어떤 거리를 기준으로 정렬할지 정합니다. 코사인 거리에는 vector_cosine_ops를 사용합니다.
왼쪽 정확 검색은 12개 문서를 모두 비교합니다. 오른쪽 HNSW는 상위 계층에서 시작해 연결선을 따라 후보를 좁힙니다. 일부 문서는 그래프 경로에 따라 이번 탐색에서 제외될 수 있습니다.
코사인 거리는 <=>, L2 거리는 <-> 연산자를 사용합니다. 질의의 ORDER BY 연산자와 인덱스의 연산자 클래스가 일치해야 합니다. 인덱스를 만들었다는 사실만으로 항상 선택되는 것은 아니므로 EXPLAIN으로 실행 계획도 확인합니다.
SQL 거리 연산과 HNSW 실행 시점
pgvector의 vector(256) 열은 차원이 고정된 벡터를 저장합니다. ORDER BY embedding <=> query LIMIT 3은 코사인 거리가 작은 행부터 세 건을 반환합니다. 인덱스가 없으면 정확 검색을 수행하고, HNSW 인덱스를 만든 뒤 같은 모양의 질의가 근사 검색 경로를 사용할 수 있습니다.
ef_search는 검색 중 살펴볼 동적 후보 목록의 크기입니다. 값을 늘리면 더 많은 후보를 살펴볼 수 있지만, 이 작은 자료에서 결과가 같았다는 사실만으로 모든 자료의 재현율이 같다고 결론 내릴 수 없습니다. 정확 검색 결과를 기준선으로 두고 근사 결과의 ID와 실행 계획을 함께 비교합니다.
5실행 예제
전용 컨테이너의 확장 버전을 조회하고 ch12_core_hnsw 표에 12개 벡터를 넣습니다. 정확 검색과 HNSW의 top-3를 비교하고 ef_search를 4와 40으로 실행합니다. 마지막에는 2,001차원 vector와 halfvec의 HNSW 인덱스 생성 결과를 확인합니다.
확인할 점 — 실제 확장 버전은 0.8.2입니다. 이 작은 표에서는 정확 검색과 HNSW가 LIB-004, LIB-001, LIB-003을 같은 순서로 반환했고 ef_search 변경도 순위를 바꾸지 않았습니다.
6실험 결과 해석
vector(2001) HNSW 인덱스는 “2,000 dimensions” 제한 오류를 반환했고 halfvec(2001)은 생성에 성공했습니다. 공식 최신 v0.8.6의 2,000/4,000차원 설명과 실습 컨테이너의 0.8.2에서 관찰한 결과가 일치한 사례입니다. 문서 12개는 속도 이점이나 ef_search에 따른 Recall 차이를 관찰하기에 부족합니다. 전체 질의셋과 큰 말뭉치에서 지연 시간과 Recall을 함께 측정해야 합니다.
7주의할 점과 실무 메모
공식 최신 안정판은 v0.8.6이지만 실습 컨테이너는 실행을 검증한 0.8.2-pg17입니다. 기능과 출력의 기준 버전을 섞지 않습니다.
halfvec는 차원 제한을 늘리지만 정밀도를 낮춥니다. 저장 크기와 Recall@50·nDCG@5를 함께 비교합니다.
Docker 포트는 127.0.0.1:55432에만 공개합니다. 실습 암호를 서비스에 사용하지 않습니다.
8정리와 다음 절
HNSW는 그래프를 따라 후보를 줄이는 근사 검색입니다.
타입·차원·거리 연산자·인덱스 연산자 클래스를 함께 맞춥니다.
현재 환경에서 vector 2,001차원 색인은 실패하고 halfvec는 성공했습니다.
다음 학습과 이어지는 지점 — 03절은 HNSW 결과에 메타데이터 필터를 적용했을 때 LIMIT보다 적게 반환되는 현상을 확인합니다.

1학습 목표
HNSW와 WHERE를 함께 사용할 때 post-filtering 순서를 설명할 수 있습니다.
필터 결과가 LIMIT보다 적은 현상을 실제 SQL로 재현할 수 있습니다.
hnsw.iterative_scan을 켜고 반환 개수와 순서를 다시 확인할 수 있습니다.
2이 내용을 배우는 이유
사용자별 문서, 날짜 범위, 공개 등급처럼 메타데이터 조건을 적용하면 검색 대상이 줄어듭니다. HNSW가 가까운 후보를 먼저 찾은 뒤 필터를 적용하면 초기 후보 중 조건에 맞는 문서가 부족할 수 있습니다. 데이터베이스에 조건을 만족하는 행이 있는데도 LIMIT 5보다 적게 반환될 수 있으므로, 빈 결과를 곧바로 “관련 문서가 없음”으로 해석하면 안 됩니다.
3앞에서 배운 내용
02절은 HNSW가 일부 후보를 탐색하고 ef_search가 후보 폭을 조절한다는 점을 확인했습니다. Ch 9에서 문서의 doc_id와 페이지를 메타데이터로 저장했습니다. 이번 절은 category='rare' 조건을 사용해 벡터 검색과 메타데이터 필터의 실행 순서를 살펴봅니다.
4핵심 개념
후보를 고른 뒤 조건 검사하기
지원자 5명을 먼저 고른 뒤 자격 조건을 확인하면, 조건을 통과한 사람이 5명보다 적을 수 있습니다. 조건을 통과할 때까지 다음 지원자를 더 확인해야 원하는 인원을 채울 수 있습니다. HNSW의 post-filtering과 iterative scan도 이 순서로 이해할 수 있습니다.메타데이터 필터(metadata filter)범주·날짜·권한처럼 벡터 밖의 열 값으로 행을 제한하는 조건입니다.post-filtering근사 인덱스가 찾은 후보에 SQL 필터를 나중에 적용하는 처리입니다.선택도(selectivity)전체 행 가운데 조건을 통과하는 비율입니다.iterative scan충분한 결과를 찾거나 상한에 도달할 때까지 근사 인덱스를 더 탐색하는 기능입니다.strict_order반환 결과의 정확한 거리 순서를 유지하는 모드입니다.
위 흐름은 초기 후보에 rare 필터를 적용해 0개가 남는 Before입니다. 아래 흐름은 같은 필터를 유지하고 탐색을 이어가 결과 5개를 채우는 After입니다.
pgvector 0.8.0부터 iterative scan을 사용할 수 있습니다. strict_order는 거리 순서를 유지하고, relaxed_order는 순서가 조금 달라질 수 있습니다. PostgreSQL 17에서 relaxed 결과를 정확히 다시 정렬하려면 공식 문서의 materialized CTE와 distance + 0 방식을 확인합니다.
필터가 적용되는 순서 읽기
근사 인덱스 질의는 가까운 후보를 먼저 탐색한 뒤 WHERE category='rare' 조건을 적용할 수 있습니다. 초기 후보 대부분이 common이면 LIMIT 5를 요청해도 rare 행이 다섯 건보다 적게 남을 수 있습니다. 이는 rare 데이터가 없다는 뜻이 아니라 탐색한 후보 안에서 필터를 통과한 행이 부족한 상태입니다.
SET LOCAL hnsw.iterative_scan = strict_order는 현재 트랜잭션의 뒤따르는 질의가 필요한 행을 얻거나 탐색 한도에 이를 때까지 인덱스를 더 살펴보게 합니다. strict는 거리 순서를 유지하고 relaxed는 순서가 조금 달라질 수 있는 대신 재현율을 높일 수 있습니다. 반복 탐색도 무한하지 않으므로 반환 개수와 설정을 로그에 함께 남깁니다.
5실행 예제
질문 벡터에 가까운 common 범주의 벡터 3,000개와 조금 더 먼 rare 범주의 벡터 12개를 8차원으로 만듭니다. HNSW 인덱스를 만들고 ef_search=5, category='rare', LIMIT 5를 고정합니다. 합성 데이터는 실행 순서를 분명하게 보기 위한 것이며 실제 임베딩 품질을 나타내지 않습니다.
확인할 점 — 표에는 rare 행이 12개 존재합니다. 데이터가 없는 상황과 필터 적용 뒤 초기 후보가 남지 않은 상황을 구분합니다.
6실패 확인
Before는 iterative scan을 끈 상태에서 0개를 반환했습니다. After는 데이터·질문·필터·LIMIT·ef_search를 그대로 두고 strict_order만 켰으며 5개를 거리 순으로 반환했습니다. 원인은 rare 데이터 부족이 아니라 초기 HNSW 후보 뒤에 필터가 적용된 것입니다. 반복 탐색은 초기 후보 이후까지 탐색을 이어 이 문제를 해결하지만 지연 시간이 늘 수 있습니다.
7주의할 점과 실무 메모
iterative scan을 켰다고 항상 LIMIT을 채우는 것은 아닙니다. 조건 일치 행 수와 최대 탐색 상한을 함께 확인합니다.
선택도가 매우 낮으면 필터 열의 B-tree 인덱스, 부분 HNSW 인덱스, 파티션을 비교합니다.
반환 개수와 지연 시간, Recall@50, Precision@5, nDCG@5를 같은 실험 행에 남깁니다.
8정리와 다음 절
근사 인덱스 필터는 초기 후보 뒤에 적용될 수 있습니다.
필터 결과가 k보다 적다고 관련 문서가 없다고 단정하지 않습니다.
iterative scan은 더 탐색하여 결과를 보충할 수 있습니다.
다음 학습과 이어지는 지점 — 04절은 벡터 거리와 다른 신호인 한국어 낱말 빈도로 sparse 검색을 만듭니다.
9복습 문제
문제 4개 · 해설 포함
1. LIMIT 5인데 HNSW 필터 결과가 2개일 수 있는 이유는 무엇입니까?
초기 근사 후보에 필터를 적용한 뒤 통과한 행이 2개뿐일 수 있기 때문입니다. 틀렸다면 post-filtering을 다시 읽습니다.
2. strict_order는 무엇을 보존합니까?
반환 결과의 정확한 거리 순서를 보존합니다. 틀렸다면 모드 설명을 확인합니다.
3. Before와 After에서 바꾼 설정은 무엇입니까?
hnsw.iterative_scan만 off에서 strict_order로 바꿨습니다. 틀렸다면 「실패 확인」을 다시 읽습니다.
4. 반환 개수가 늘면 검색 설정이 최종적으로 좋아졌다고 말할 수 있습니까?
말할 수 없습니다. 지연 시간과 정답 문서의 순위 지표를 함께 측정해야 합니다. 틀렸다면 「주의할 점과 실무 메모」를 확인합니다.

textbook/part3/ch12-retrieval-tuning/_src/04-한국어-Kiwi와-BM25.html

1학습 목표
공백 분리와 형태소 분석의 한국어 처리 차이를 설명할 수 있습니다.
문서와 질문에 같은 Kiwi 토큰 정책을 적용할 수 있습니다.
BM25 점수로 문서 순위를 만들고 Recall@3를 계산할 수 있습니다.
2이 내용을 배우는 이유
dense 검색은 뜻이 비슷한 표현을 찾는 데 유용하지만 ISBN, 제품 코드, 조항 이름처럼 정확한 낱말이 중요한 질문도 있습니다. sparse 검색은 질문과 문서에 같은 낱말이 나타나는지와 말뭉치에서 그 낱말이 얼마나 드문지를 사용합니다. 한국어는 조사와 어미가 낱말 뒤에 붙으므로 공백만 나누면 도서를과 도서를 다른 문자열로 처리합니다. 형태소 분석으로 검색에 사용할 기본 단위를 먼저 정해야 합니다.
3앞에서 배운 내용
Ch 5에서 토큰은 모델이 텍스트를 처리하는 단위임을 배웠습니다. Ch 10에서는 한국어 문장 경계를 보존하며 청크를 만들었습니다. 01~03절은 임베딩 벡터 거리만 사용했습니다. 이번 절은 같은 문서에 낱말 빈도 기반 점수를 추가합니다.
Ch5의 모델 입력 토큰과 이번 절의 BM25 검색 토큰은 용도와 분할 규칙이 다릅니다. 이번 절은 Kiwi가 반환한 형태소의 Token.form을 검색 토큰으로 사용하고 품사에 따라 일부를 제외합니다. 따라서 이 토큰 수를 Ch5의 GPT-2·KLUE 토큰 수나 Ch10의 cl100k_base 토큰 수와 직접 비교하지 않습니다.
4핵심 개념
서로 다른 꼬리가 붙은 낱말 찾기
색인에 예약자가가 있고 질문에는 예약자는이 있으면 공백 분리는 둘을 다른 항목으로 봅니다. Kiwi는 둘에서 명사 예약자와 조사를 분리할 수 있습니다. 검색 정책이 내용을 나타내는 형태소를 남기면 같은 개념을 연결할 수 있습니다.형태소(morpheme)뜻이나 문법 기능을 가진 가장 작은 말의 단위입니다.형태소 분석기(morphological analyzer)문장을 형태소와 품사로 나누는 프로그램입니다.Kiwi한국어 문장을 분석해 Token.form과 품사 태그를 반환하는 도구입니다.sparse 검색대부분 값이 0인 낱말별 특징을 사용해 질문과 문서가 공유하는 표현을 찾는 검색입니다.BM25질문 낱말이 문서에 나타나는 횟수, 말뭉치에서 드문 정도, 문서 길이를 함께 반영하는 순위 함수입니다.품사 필터분석 결과 가운데 검색에 사용할 품사만 남기는 규칙입니다.
원문과 질문은 같은 Kiwi 정책을 통과합니다. 형태소 배열이 BM25의 입력이며, BM25는 각 문서 점수를 계산해 높은 순서로 문서 ID를 반환합니다.
수업 코드는 명사·동사·형용사·부사·숫자·외국어를 남깁니다. 이것은 모든 한국어 검색에 맞는 표준이 아니라 비교할 수 있도록 명시한 한 설정입니다. 문서와 질문에 서로 다른 정책을 적용하면 같은 낱말도 일치하지 않으므로 두 입력의 전처리 함수를 공유합니다.
형태소 목록이 BM25 점수가 되는 과정
Kiwi.tokenize(text)는 형태소 토큰 객체 목록을 반환하고 이 절서는 token.form만 골라 검색어 목록으로 사용합니다. 이 토큰은 언어 모델 입력 토큰과 목적과 경계가 다릅니다. 문서와 질문에 같은 분석 함수를 적용한 뒤 BM25Okapi(corpus_tokens)가 문서별 통계를 준비하고 get_scores(query_tokens)가 점수 배열을 반환합니다.
BM25는 질문에 나타난 단어가 문서에 얼마나 드물고 적절한 빈도로 등장하는지 반영합니다. ISBN·제품 코드처럼 표기가 정확한 질문에 강할 수 있지만, “연장”과 “기간을 늘리다”처럼 표현이 달라지면 공통 토큰이 부족합니다. Kiwi가 모든 복합명사를 원하는 방식으로 나눈다고 가정하지 말고 실제 토큰 출력을 먼저 확인합니다.
5실행 예제
예약자가 없으면 일반 도서를 연장할 수 있습니다.를 공백과 Kiwi로 나눕니다. Kiwi는 예약, 없, 일반, 도서, 연장, 수, 있을 남겼습니다. 12개 문서를 BM25에 넣고 ISBN 질문의 순위를 확인한 뒤 8개 질문의 Recall@3를 계산합니다.
확인할 점 — ISBN 질문에서 LIB-003이 BM25 6.292점으로 1위였습니다. C02 질문은 공백 분리에서 정답이 top-3에 없었지만 Kiwi에서는 LIB-002가 1위였습니다.
6실험 결과 해석
Kiwi+BM25는 교육용 질문 8개 모두에서 정답 문서를 top-3에 포함했습니다. 형태소 분석이 C02의 늦게와 문서의 연체를 같은 말로 바꾼 것은 아닙니다. 질문과 문서가 공유한 다른 내용어가 순위에 기여했습니다. 한 질문의 점수를 보고 특정 형태소 하나가 원인이라고 단정하지 않고, 토큰 배열과 전체 점수를 함께 읽습니다. 문서 12개에서 얻은 8/8은 전체 질의셋의 성능 주장이 아닙니다.
7주의할 점과 실무 메모
rank_bm25는 토큰화와 정리를 수행하지 않습니다. 문서와 질문을 코드에서 직접 준비합니다.
명사만 남기면 부정이나 행동을 나타내는 정보가 사라질 수 있습니다. 질의셋에서 품사 정책별 결과를 비교합니다.
PostgreSQL ts_rank는 전문 검색 순위 함수이지만 BM25 구현과 같다고 설명하지 않습니다.
8정리와 다음 절
한국어 sparse 검색은 공백 분리보다 형태소 단위가 유용할 수 있습니다.
문서와 질문에 같은 Kiwi 정책을 적용합니다.
BM25는 낱말 빈도·희귀도·문서 길이를 함께 사용합니다.
다음 학습과 이어지는 지점 — 05절에서는 같은 질문에서 dense와 sparse의 성공·실패를 나란히 비교합니다.

dense와 sparse 검색이 사용하는 신호를 구분할 수 있습니다.

검색기별 성공 여부가 다른 질문을 찾아 원문과 토큰을 확인할 수 있습니다.
2이 내용을 배우는 이유
검색기는 질문마다 다른 이유로 성공합니다. dense 검색은 표현이 달라도 가까운 의미를 찾을 수 있고, sparse 검색은 ISBN이나 고유명사처럼 정확한 표현을 강하게 반영할 수 있습니다. 어느 한쪽이 항상 우수하다고 단정하기보다 같은 질문 모음에서 두 순위와 실패 사례를 확인해야 06절에서 결합할 근거가 생깁니다.
3앞에서 배운 내용
01절의 dense 검색은 OpenAI 임베딩과 코사인 유사도를 사용했습니다. 04절의 sparse 검색은 Kiwi 형태소와 BM25를 사용했습니다. 두 검색기 모두 같은 core-documents.json과 core-queries.json을 읽고 문서 ID 순위를 반환합니다.
4핵심 개념
뜻으로 찾는 색인과 낱말로 찾는 색인
“책을 빌리는 기간”과 문서의 “도서 대출 기간”은 낱말이 일부 다르지만 뜻이 가깝습니다. 반면 ISBN은 글자가 정확히 일치하는지 여부 자체가 중요한 단서입니다. dense와 sparse는 이 두 종류의 신호를 서로 다른 방식으로 사용합니다.dense 검색모든 차원에 연속적인 숫자가 들어 있는 임베딩 벡터의 거리를 사용합니다.sparse 검색말뭉치의 낱말별 특징처럼 대부분 값이 0인 표현을 사용합니다.의미 변형(semantic variation)뜻은 비슷하지만 표면에 나타난 낱말이 다른 질문입니다.어휘 일치(lexical match)질문과 문서에 같은 낱말이나 코드가 나타나는 관계입니다.
같은 질문이 두 갈래로 나뉩니다. dense는 벡터 거리 순위, sparse는 Kiwi+BM25 순위를 만듭니다. 아래 비교표에서 정답 문서 포함 여부가 다른 질문을 확인합니다.
공정한 비교를 위해 질문, 문서, 정답 문서 ID, top-k를 고정합니다. dense에는 질문 벡터를 넣고 sparse에는 형태소 목록을 넣습니다. 이러한 입력 차이는 각 검색기의 원리에서 생깁니다. 출력 점수의 척도가 다르므로 코사인 점수와 BM25 점수의 숫자 크기를 직접 비교하지 않습니다.
두 검색기가 같은 입력을 보는 방식
dense 검색은 문서와 질문을 연속된 실수 벡터로 바꾸어 의미적 거리를 계산합니다. sparse 검색은 형태소별 값 대부분이 0인 표현을 사용하고 BM25로 정확한 단어 겹침을 계산합니다. 같은 문서 12개와 같은 k=3을 사용해야 표현 방식의 차이를 비교할 수 있습니다.
의미를 바꾸어 말한 질문에서 dense가 정답을 찾고 정확한 ISBN에서 sparse가 앞설 수 있지만, 이것은 각 방식의 경향을 보여 주는 사례입니다. 어느 하나가 모든 질문에 우월하다는 결론은 8개 질문으로 확정할 수 없습니다. 두 결과가 서로 다른 정답을 보완한다면 다음 절의 결합 검색을 시도할 근거가 됩니다.
5실행 예제
의미 변형으로 표시한 C01과 정확한 표기가 포함된 C03을 먼저 확인합니다. 이어서 8개 질문에서 각 검색기의 top-3와 정답 포함 여부를 같은 행에 기록합니다. OpenAI 임베딩 입력의 예상 비용은 미화 0.01달러 미만입니다.
확인할 점 — C01과 C03은 두 검색기 모두 정답을 top-3에 포함했습니다. C02만 dense는 정답을 놓치고 sparse는 포함하여 성공 여부가 달랐습니다.
6실험 결과 해석
dense Recall@3는 7/8, sparse Recall@3는 8/8이었습니다. 이 작은 자료에서는 sparse가 dense보다 한 질문에서 정답 문서를 더 top-3에 포함했지만, “sparse가 dense보다 우수하다”는 일반 결론은 낼 수 없습니다. C02의 두 순위와 원문을 읽어 이 자료에서 어떤 표현이 작용했는지 확인하고, Ch 11의 30개 질문과 큰 말뭉치에서는 Recall@50이 포화될 수 있으므로 P@5·nDCG@5·반환 개수도 함께 확인합니다.
7주의할 점과 실무 메모
두 검색기의 점수 범위가 다르므로 원점수를 그대로 더하지 않습니다.
검색기 비교 중에 청킹·임베딩 차원·토큰 정책·k를 함께 바꾸지 않습니다.
평균값만 보지 말고 한쪽만 성공한 질문과 양쪽이 모두 실패한 질문을 읽습니다.
8정리와 다음 절
dense는 임베딩 거리, sparse는 낱말 빈도 기반 점수를 사용합니다.
같은 조건에서 문서 ID 순위와 정답 포함 여부를 비교합니다.
이번 입력에서는 C02의 성공 여부가 달랐습니다.
다음 학습과 이어지는 지점 — 06절은 서로 다른 점수 척도를 직접 더하지 않고 두 순위를 RRF로 합칩니다.

textbook/part3/ch12-retrieval-tuning/_src/06-RRF-하이브리드-검색.html

1학습 목표
상호 순위 융합(Reciprocal Rank Fusion, RRF)의 계산식을 설명할 수 있습니다.
1부터 시작하는 두 순위를 직접 구현한 함수로 합칠 수 있습니다.
가중치 하나만 바꾸고 Recall@3와 개별 질문 순위를 비교할 수 있습니다.
2이 내용을 배우는 이유
05절의 dense와 sparse는 서로 다른 질문에서 강점을 보였습니다. 두 결과의 원점수는 척도가 달라 그대로 더하기 어렵습니다. RRF는 점수 대신 문서가 각 검색기에서 몇 위인지 나타내는 순위를 사용합니다. 두 목록에서 모두 앞쪽에 있는 문서에 두 항의 점수를 더하므로, 서로 다른 검색 신호를 짧은 함수로 결합할 수 있습니다.
3앞에서 배운 내용
dense는 코사인 유사도 순위, sparse는 BM25 순위를 반환했습니다. 두 함수의 공통 출력은 순서가 있는 doc_id 목록입니다. RRF는 이 공통 형식만 사용하므로 각 점수의 최소·최대 범위를 맞추는 정규화가 필요하지 않습니다.
4핵심 개념
두 추천 목록에서 반복해서 앞에 나온 항목
서로 다른 두 사람이 책을 추천했다고 가정합니다. 두 목록에서 모두 앞쪽에 있는 책은 한 목록에서만 뒤쪽에 있는 책보다 높은 결합 점수를 받습니다. RRF는 각 순위를 분모에 넣어 상위 순위의 기여를 크게 계산합니다.상호 순위 융합(RRF)여러 검색 결과의 순위를 역수 형태로 변환해 같은 문서의 값을 더하는 결합 방법입니다.rank constant상위 순위 사이의 점수 차이를 완화하는 분모의 상수입니다. 기본 실험은 60을 사용합니다.가중치(weight)특정 검색기 순위의 기여를 늘리거나 줄이는 계수입니다.후보 창(candidate window)각 검색기에서 RRF 계산에 넣는 상위 문서 수입니다.하이브리드 검색(hybrid search)dense와 sparse처럼 다른 검색 신호를 결합하는 검색입니다.
RRF(d) = Σ weight / (rank_constant + rank(d))로 계산합니다. 순위는 1부터 시작합니다. 한 검색 결과에 문서가 없으면 그 검색기의 항은 더하지 않습니다.왼쪽의 dense 순위와 sparse 순위가 가운데 RRF 함수로 들어갑니다. 같은 문서 ID의 두 항을 더한 뒤 오른쪽 결합 순위를 만듭니다.
기본값은 두 가중치 1.0, rank constant 60, 후보 창 6입니다. 가중치를 바꿀 때 후보 창과 상수를 유지합니다. 최종 top-3만 저장하면 왜 순위가 바뀌었는지 확인하기 어려우므로 입력 순위와 문서별 RRF 점수도 로그에 남깁니다.
서로 다른 점수를 순위로 합치기
dense의 거리와 BM25의 원점수는 범위와 방향이 달라 그대로 더할 수 없습니다. RRF는 각 목록에서 문서가 나타난 순위 r를 받아 weight / (c + r)을 더합니다. 함수의 입력은 문서 ID 순위 목록들과 가중치이고, 반환값은 결합 점수로 다시 정렬한 문서 목록입니다.
두 검색기 모두 상위에 둔 문서는 두 항을 받아 올라가고, 한 목록에만 있는 문서도 한 항을 받습니다. sparse 가중치를 높이는 것은 BM25 원점수를 키우는 동작이 아니라 sparse 순위의 기여를 키우는 정책입니다. c와 가중치는 개발 질문으로 선택하고 시험 질문을 본 뒤 다시 맞추지 않습니다.
5실행 예제
C03에서 dense와 sparse의 상위 6개를 가져오고 15줄의 rrf()로 합칩니다. LIB-003은 두 검색기에서 모두 1위이므로 0.03279점을 받아 결합 1위가 됩니다. 이어서 sparse 가중치만 1.0에서 1.5로 바꾸고 전체 8개 질문의 Recall@3를 계산합니다.
확인할 점 — 동일 가중치 순위는 LIB-003, ACC-002, LIB-004입니다. sparse 가중치를 1.5로 높이면 LIB-003, LIB-004, ACC-003으로 바뀝니다.
6실험 결과 해석
dense Recall@3는 7/8, sparse는 8/8, 동일 가중치 RRF는 7/8이었습니다. RRF가 이번 작은 자료에서 Recall@3를 개선하지 못했습니다. 결합 방법을 사용했다는 사실이 자동 개선을 뜻하지 않습니다. sparse 단독이 이미 모든 정답을 top-3에 포함했고, 두 목록을 결합하면서 dense의 다른 후보가 앞쪽으로 이동했습니다. Ch 11의 30개 질문에서는 Recall@50이 포화될 수 있으므로 P@5·nDCG@5와 질문별 순위를 함께 비교합니다.
7주의할 점과 실무 메모
순위는 1부터 시작합니다. 0부터 넣으면 공식 식과 다른 점수가 됩니다.
가중치·rank constant·후보 창을 한 번에 바꾸지 않습니다.
한 검색기가 정답을 후보 창에 넣지 못하면 그 검색기의 RRF 항은 정답에 기여하지 못합니다.
8정리와 다음 절
RRF는 서로 다른 원점수 대신 순위를 사용합니다.
같은 문서의 검색기별 역순위 점수를 더합니다.
이번 입력에서는 RRF의 Recall@3 개선을 관찰하지 못했습니다.
다음 학습과 이어지는 지점 — 07절은 하이브리드 검색이 만든 후보 안에서 질문과 문서를 함께 읽는 cross-encoder로 순서를 다시 정합니다.

문제 4개 · 해설 포함
1. RRF가 코사인과 BM25 원점수를 직접 더하지 않는 이유는 무엇입니까?
두 점수의 계산 방식과 척도가 다르기 때문입니다. RRF는 공통된 순위를 사용합니다. 틀렸다면 「이 내용을 배우는 이유」를 다시 읽습니다.
2. 한 문서가 dense 1위와 sparse 1위이면 몇 개의 항을 더합니까?
두 개의 항을 더합니다. 틀렸다면 RRF 식을 확인합니다.
3. sparse 가중치만 높이는 실험에서 유지할 설정을 두 개 적어 보세요.
rank constant와 후보 창을 유지합니다. 질문·문서·정답도 같아야 합니다. 틀렸다면 핵심 개념의 마지막 문단을 확인합니다.

4핵심 개념
쉬운 예
도서관에서 책을 찾을 때 먼저 검색대가 관련 서가를 좁히고, 그 안에서 제목과 목차를 자세히 읽어 우선순위를 정한다고 생각해 봅니다. 첫 단계가 서가를 빠뜨리면 다음 단계는 그 책을 검토할 수 없습니다. 반대로 후보를 지나치게 많이 가져오면 자세히 읽는 시간이 늘어납니다.
정의
질문과 각 후보 본문을 함께 읽어 관련성 점수를 계산하는 교차 인코더입니다. 1차 후보 목록은 리랭커가 볼 수 있는 범위입니다. 질문과 후보 본문을 한 쌍으로 입력해 점수를 계산하고, 그 점수의 내림차순으로 같은 후보를 다시 정렬합니다.
도식 읽기
도식은 위에서 아래로 질문, 1차 후보 8개, CrossEncoder 점수, 상위 5개 순서로 읽습니다. 초록은 입력·문서·후보, 파랑은 직접 구현한 선택·설정, 보라는 모델 점수·질문 재작성, 노랑은 측정 결과·로그를 뜻합니다. 화살표는 데이터 전달 방향입니다.
후보 생성과 쌍 점수화를 구분하기
1차 검색은 질문과 문서를 따로 표현해 많은 문서에서 후보를 빠르게 고릅니다. CrossEncoder.predict([(question, passage), ...])는 질문과 후보 본문을 한 쌍으로 함께 입력해 후보마다 관련성 로짓을 반환합니다. 코드가 점수가 큰 순서로 기존 후보를 다시 정렬하며, 새 문서를 추가하지는 않습니다.
리랭커 로짓은 모델에 따라 0~1 확률이 아닐 수 있으므로 절대값보다 같은 질문 안의 순서를 읽습니다. 정답 문서가 1차 후보에 없으면 CrossEncoder는 평가할 수 없습니다. 고객 문의처럼 어휘가 비슷한 규정 후보를 정밀하게 가르는 데 도움을 줄 수 있지만 후보 재현율을 먼저 확인해야 합니다.
5실행 예제
노트북은 Python 3.12 새 커널에서 실행합니다. 먼저 부모 문서 수, 자식 청크 수, 질문 수를 출력해 입력 범위를 확인합니다. 다음 셀은 가장 작은 문항 하나에서 중간 결과를 보여 줍니다. 마지막 셀은 조건을 바꾸거나 평가 범위를 넓힙니다. 출력의 문서 ID, 점수, 실행 시간 또는 로그 수를 본문 설명과 대조합니다.
확인할 점 — 코드가 실제 검색 또는 모델 추론을 수행하는지, 정답 문서 ID를 결과 뒤에 새로 붙이지 않는지, 비교할 때 질문과 원문이 유지되는지 확인합니다.
6실험 결과 해석
Q001에서 8개 후보를 만든 뒤 bge-reranker-v2-m3가 계산한 점수로 상위 순서를 다시 정렬했습니다. 후보를 2개로 줄인 실행에서는 입력 목록의 부모 ID만 확인했습니다. 이 결과는 리랭커가 새 문서를 검색하지 않는다는 경계를 보여 줍니다.
한 번의 출력은 이 데이터와 실행 환경에서 관찰한 결과입니다. 다른 도메인, 더 긴 문서, 다른 언어 비율에서는 순서와 시간이 달라질 수 있습니다. 설정을 채택하기 전에는 실제 서비스 질문을 같은 형식으로 추가해 다시 계산해야 합니다.
7주의할 점과 실무 메모
이번 절의 중간 결과를 확인한 뒤 다음 단계로 전달합니다. 검색 후보, 선택 결과, 부모 원문, 재작성 질문, 로그 행은 서로 다른 데이터입니다.
실행 시간은 CPU, GPU, 배치 크기, 입력 길이, 모델 캐시에 따라 달라집니다. 장치와 패키지 버전을 로그에 함께 남깁니다.
로컬 CrossEncoder 추론은 API 비용이 없지만 첫 실행에서 모델 가중치를 내려받을 시간과 저장 공간이 필요합니다.
공개 PDF 6건과 30문항은 학습용 기준선입니다. 실제 서비스의 문서 분포와 질문 유형을 대신하지 않습니다.

후보 수를 늘려 지표가 좋아지면 정답이 작은 후보 밖에 있었을 가능성이 있고, 같은 후보에서 모델별 순위가 다르면 점수화 차이를 조사합니다. 모델별 전체 추론 시간은 후보 수별 실행 시간이 아니며 장치·캐시 상태에도 영향을 받습니다. 품질과 시간을 하나의 원인으로 섞어 해석하지 않습니다.

4핵심 개념
쉬운 예
도서관에서 책을 찾을 때 먼저 검색대가 관련 서가를 좁히고, 그 안에서 제목과 목차를 자세히 읽어 우선순위를 정한다고 생각해 봅니다. 첫 단계가 서가를 빠뜨리면 다음 단계는 그 책을 검토할 수 없습니다. 반대로 후보를 지나치게 많이 가져오면 자세히 읽는 시간이 늘어납니다.
정의
대명사와 생략된 대상을 대화 맥락으로 보충해 독립 검색 질문을 만드는 처리입니다. 입력은 대화 맥락과 후속 질문이고 출력은 독립 검색 질문입니다. 재작성문은 검색 입력으로 추가하며 원문 질문과 원문 검색 순위도 별도로 보존합니다.
도식 읽기
도식은 위에서 아래로 대화 맥락, 후속 질문, 모델 재작성, 원문·재작성·RRF 결과 순서로 읽습니다. 초록은 입력·문서·후보, 파랑은 직접 구현한 선택·설정, 보라는 모델 점수·질문 재작성, 노랑은 측정 결과·로그를 뜻합니다. 화살표는 데이터 전달 방향입니다.
이 절의 gpt-4.1-mini는 대화에서 생략된 대상을 보충하는 질문 재작성 예제에 사용합니다. Ch6·Ch9의 gpt-5.4-mini 답변 생성과는 입력·출력 과제가 다릅니다. 같은 재작성 모델을 고정하고 원문과 재작성문의 검색 결과만 비교하며, 두 모델의 답변 품질을 비교하는 실험으로 해석하지 않습니다.
재작성 모델의 입력과 출력 경계
후속 질문 “그 경우 기간은?”만 검색하면 대상 기관과 업무가 빠집니다. 재작성 프롬프트는 대화 기록과 현재 질문을 입력으로 받고, 문서 검색에 독립적으로 사용할 한 문장을 반환하도록 요청합니다. model.invoke()를 호출할 때 생성이 실행되며 반환 문자열을 검색 함수의 새 질문으로 사용합니다.
재작성은 빠진 대상을 보충할 수 있지만 원문의 조건을 삭제하거나 없는 조건을 넣을 수도 있습니다. 그래서 원문 검색 결과를 버리지 않고 원문·재작성문 순위를 RRF로 합칩니다. 이미 기관명과 대상이 분명한 질문은 재작성 이득이 없을 수 있으므로 모든 질문에 자동 적용하기 전에 원문 대비 변화를 기록합니다.
5실행 예제
노트북은 Python 3.12 새 커널에서 실행합니다. 먼저 부모 문서 수, 자식 청크 수, 질문 수를 출력해 입력 범위를 확인합니다. 다음 셀은 가장 작은 문항 하나에서 중간 결과를 보여 줍니다. 마지막 셀은 조건을 바꾸거나 평가 범위를 넓힙니다. 출력의 문서 ID, 점수, 실행 시간 또는 로그 수를 본문 설명과 대조합니다.
확인할 점 — 코드가 실제 검색 또는 모델 추론을 수행하는지, 정답 문서 ID를 결과 뒤에 새로 붙이지 않는지, 비교할 때 질문과 원문이 유지되는지 확인합니다.
6실험 결과 해석
실제 채팅 모델이 ‘그곳’을 ‘미르시립도서관’으로 보충한 독립 질문을 반환했습니다. 원문 검색, 재작성문 검색, 두 순위의 RRF 결합을 따로 출력해 원문을 보존했습니다. API 출력은 모델 버전과 시점에 따라 달라질 수 있습니다. 이미 대상을 포함한 개발용 Q001에는 재작성을 적용하지 않습니다.
한 번의 출력은 이 데이터와 실행 환경에서 관찰한 결과입니다. 다른 도메인, 더 긴 문서, 다른 언어 비율에서는 순서와 시간이 달라질 수 있습니다. 설정을 채택하기 전에는 실제 서비스 질문을 같은 형식으로 추가해 다시 계산해야 합니다.
7주의할 점과 실무 메모
이번 절의 중간 결과를 확인한 뒤 다음 단계로 전달합니다. 검색 후보, 선택 결과, 부모 원문, 재작성 질문, 로그 행은 서로 다른 데이터입니다.
실행 시간은 CPU, GPU, 배치 크기, 입력 길이, 모델 캐시에 따라 달라집니다. 장치와 패키지 버전을 로그에 함께 남깁니다.

앞 도식은 TF-IDF와 MMR의 36개 개발 설정과 선택 설정의 시험 평가를 보여 줍니다. 다음 도식은 제공 PDF 로딩, dense와 Kiwi BM25 검색, RRF, CrossEncoder, 쪽 본문과 출처 선택, 답변 생성을 연결한 별도의 개발 질문 1건 스모크 실행입니다. 두 실행은 검색 구성·질문 수·평가 단위가 달라 수치를 직접 비교하지 않습니다. 통합 실행은 단계가 연결되는지만 확인하며, 답변 품질은 Ch15에서 평가합니다.
통합 실행의 임베딩은 Ch10·Ch12 앞 실습과 같은 text-embedding-3-small의 256차원으로 고정합니다. 답변 생성에는 Ch6·Ch9와 같은 gpt-5.4-mini를 사용합니다. 통합 로그의 settings.dimensions는 실제 임베딩 배열에서 읽은 차원이고 settings.chat은 답변 모델입니다. 모델을 맞추더라도 문서·청킹·질문이 다른 앞 예제와 답변 품질을 직접 비교하지 않습니다.
설정 선택과 최종 확인을 분리하기
36개 행은 문자 분석기·n-gram·보고 순위·MMR λ의 조합입니다. 평가 함수는 설정 한 개와 개발 질문을 입력받아 질문별 순위와 평균 지표를 반환하고, 로그는 설정과 결과를 한 행에 저장합니다. 개발 nDCG@5로 설정을 선택한 뒤 시험 질문은 한 번만 실행해야 시험 결과가 선택 과정에 섞이지 않습니다.
마지막 통합 RAG 스모크 실행은 PDF 읽기부터 dense·BM25·RRF·리랭킹·생성까지 연결되는지 확인합니다. 이는 앞의 36개 TF-IDF 설정과 검색기·질문 수·평가 단위가 다르므로 같은 표에서 우열을 비교하지 않습니다. 연결 성공, 검색 지표, 생성 답의 사실성은 서로 다른 검증 결과로 기록합니다.
5실행 예제
노트북은 Python 3.12 새 커널에서 실행합니다. 먼저 부모 문서 수, 자식 청크 수, 질문 수를 출력해 입력 범위를 확인합니다. 다음 셀은 가장 작은 문항 하나에서 중간 결과를 보여 줍니다. 마지막 셀은 조건을 바꾸거나 평가 범위를 넓힙니다. 출력의 문서 ID, 점수, 실행 시간 또는 로그 수를 본문 설명과 대조합니다.
확인할 점 — 코드가 실제 검색 또는 모델 추론을 수행하는지, 정답 문서 ID를 결과 뒤에 새로 붙이지 않는지, 비교할 때 질문과 원문이 유지되는지 확인합니다.
6실험 결과 해석
문자 분석기 2종, n-gram 범위 3종, 보고 순위 2종, λ 3종을 조합해 36개 개발 설정을 실행했습니다. 각 질문에서 상위 50개 청크를 후보로 만든 뒤 parent_id 중복을 제거하고 문서 순위를 평가했습니다. 따라서 이 절의 chunk-candidate-unique-parent-macro-v1은 Ch11의 고유 문서 후보 정책과 단위가 다르며 두 수치를 직접 비교하지 않습니다. 개발 nDCG@5는 0.9754, 선택 설정의 시험 nDCG@5는 0.9508이었습니다. 별도 통합 실행은 개발 문항 Q002를 사용해 PDF 6건 35쪽을 읽고 dense·Kiwi BM25·RRF·CrossEncoder를 거친 뒤 검색된 쪽 본문으로 답변과 출처를 생성했습니다. 이 실행은 처리 단계의 입력과 반환 형식만 확인한 것으로, 검색 지표나 생성 답변 품질은 평가하지 않았습니다.

이번 절의 중간 결과를 확인한 뒤 다음 단계로 전달합니다. 검색 후보, 선택 결과, 부모 원문, 재작성 질문, 로그 행은 서로 다른 데이터입니다.

TF-IDF+MMR 개발 로그 36개에서 설정을 고르고 시험 문항은 한 번 평가했습니다.

# RRF 하이브리드 검색
이 노트북은 빈 Python 3.12 커널에서 순서대로 실행합니다.
## 실행 환경 준비
05절과 같은 두 검색기의 순위를 상호 순위 융합(reciprocal rank fusion, RRF)으로 합칩니다. API 예상 비용은 미화 0.01달러 미만입니다.
### 서로 다른 점수를 순위로 합치기
dense 거리와 BM25 원점수는 그대로 더할 수 없어 RRF는 각 목록의 순위 `r`를 `weight / (c + r)`로 바꿔 더합니다. 두 목록 모두 상위에 둔 문서는 두 항을 받습니다. sparse 가중치를 높이는 것은 BM25 원점수가 아니라 sparse 순위의 기여를 키우는 정책입니다.
## 기본 실행
RRF는 서로 다른 원점수를 더하지 않고 각 검색기의 순위만 사용합니다.
## 중간 결과 관찰
한쪽에만 있는 문서도 점수를 받고, 두 순위 모두에서 상위에 있는 문서는 두 항을 더합니다.
## 값 하나를 바꿔 비교
나머지 설정은 유지하고 sparse 가중치만 1.0에서 1.5로 바꿉니다.
## 반복 실험과 결과 해석
8개 질문에서 dense, sparse, 동일 가중치 RRF의 Recall@3를 비교합니다.

### 후보 생성과 쌍 점수화를 구분하기
`CrossEncoder.predict([(question, passage), ...])`는 질문과 각 후보 본문을 함께 입력해 관련성 로짓을 반환합니다. 코드는 큰 점수 순으로 기존 후보를 다시 정렬하며 새 문서를 추가하지 않습니다. 로짓은 0~1 확률이 아닐 수 있으므로 같은 질문 안의 순서를 읽고, 정답이 1차 후보에 있는지 먼저 확인합니다.
## 작은 성공 예제
개발용 Q001 한 문항에서 상위 8개 청크를 만들고 순서를 확인합니다.
## 실제 CrossEncoder 추론

## 후보 밖 문서는 회복되는가?
후보 수를 2개로 줄여 정답 문서가 빠지면 리랭커가 추가할 수 없는지 확인합니다.

# MMR로 관련성과 다양성을 함께 고려해 선택하기
이 노트북은 공개 PDF 6건과 Ch11의 30문항을 사용합니다. 첫 셀부터 순서대로 실행합니다.
## 입력 준비
최대 주변 관련성(Maximal Marginal Relevance, MMR)을 수식 그대로 직접 구현합니다.
### 관련성과 중복 억제를 한 단계씩 계산하기
MMR은 질문 관련성에서 이미 고른 문서와의 최대 유사도를 뺀 점수로 다음 후보를 선택합니다. `lambda_mult`가 1에 가까우면 관련성, 0에 가까우면 기존 선택과의 차이를 더 크게 봅니다. 다양성이 높다는 사실은 정답 관련성을 뜻하지 않으므로 두 점수를 함께 확인합니다.
## MMR 함수
λ가 1에 가까우면 질문 관련성을, 0에 가까우면 이미 고른 청크와의 차이를 더 크게 봅니다.
## λ 값 비교
같은 질문과 같은 후보 행렬에서 λ만 바꿉니다.
## 관련성 점수도 함께 읽기
다양성이 커져도 질문과 무관한 결과가 선택될 수 있으므로 점수를 확인합니다.
