1학습 목표
add_messages 리듀서와 trace를 가진 AgentState에 모델 노드와 ToolNode를 등록할 수 있습니다.
tools_condition이 도구 실행과 종료를 고르는 기준을 설명할 수 있습니다.
실제 모델 호출의 AIMessage, ToolMessage, 최종 AIMessage를 순서대로 읽을 수 있습니다.
2이 내용을 배우는 이유
Ch18에서는 OpenAI SDK를 직접 호출하고 코드로 단계·분기·병렬 실행과 종료를 연결했습니다. Ch19에서는 @tool과 bind_tools로 모델이 읽을 도구 설명과 인자 형식을 만들고, 모델 응답의 tool_calls를 해석해 도구 함수를 호출했습니다. 이제 그 요소를 Ch13의 StateGraph에 넣습니다. 모델이 도구를 요청하면 ToolNode가 실행하고, 요청하지 않으면 종료하는 연결이 처음 완성됩니다. 이 구조를 직접 조립해야 다음 Ch21의 create_agent가 감추는 반복 구조를 읽을 수 있습니다.
3앞에서 배운 내용
Ch13에서 StateGraph, MessagesState와 add_messages 리듀서, 조건부 엣지를 배웠습니다. Ch17에서는 모델·도구·반복·정지 조건이 에이전트의 구성 요소라는 사실과 자율성의 비용을 확인했습니다. Ch19에서는 주문 조회 함수에 @tool을 붙이고 model.bind_tools(tools)가 도구 스키마를 모델 요청에 포함시키는 과정을 배웠습니다. 이번 노트북은 앞 노트북의 변수에 의존하지 않고 작은 읽기 전용 규정 자료를 다시 선언합니다.
4핵심 개념
구체적인 상황
도서관 상담 직원이 질문에 바로 답할지, 규정 담당자에게 조회를 요청할지 정하는 상황을 떠올려 봅니다.
정의와 메시지 흐름
모델 노드는 질문을 읽고 바로 답하거나 도구 호출 요청을 작성합니다. tools_condition은 마지막 AIMessage에 tool_calls가 있는지만 확인하는 분기 함수입니다. 요청이 있으면 tools 노드로 이동하고, 없으면 END로 이동합니다. ToolNode는 요청 이름과 인자를 확인해 실제 도구를 실행하고 그 결과를 ToolMessage로 추가합니다. 도구 결과를 읽은 모델이 최종 답을 만들면 tool_calls가 사라지고 그래프가 끝납니다. 이때 직접 정의한 AgentState의 messages 필드에 붙인 add_messages 리듀서가 HumanMessage, AIMessage, ToolMessage를 실행 순서대로 보존합니다. trace 필드는 실행한 노드 이름을 별도로 누적합니다.
도식 읽기
model이 작성한 호출 요청의 유무로 분기합니다. ToolNode 실행 결과는 model에 전달되고, 호출 요청이 없는 응답은 END로 이동합니다.
코드를 읽기 전에
이 절은 MessagesState를 직접 사용하지 않고 AgentState를 정의합니다. AgentState.messages에 add_messages 리듀서를 붙여 새 메시지를 기존 목록에 합치고, 별도의 trace 목록에는 실행한 노드 이름을 기록합니다. StateGraph(AgentState)에 모델 노드와 ToolNode를 등록하고 tools_condition을 조건부 엣지로 연결합니다. 그래프를 compile()한 뒤 invoke()해야 노드 실행이 시작됩니다. 그래프를 그리는 코드만으로 모델이나 도구가 실행되지는 않습니다.
모델 노드는 마지막 메시지를 읽어 답 또는 tool_calls가 든 AIMessage를 반환합니다. 조건 함수는 마지막 AIMessage의 호출 요청 유무만 보고 tools 또는 종료로 보냅니다. ToolNode가 결과 ToolMessage를 추가하면 다시 모델 노드로 돌아갑니다.
다른 상황과 개념 경계
배송 규정 질문은 모델이 바로 답할 수도 있고 최신 규정을 조회할 수도 있습니다. 한 번의 조회 뒤에도 정보가 부족하면 모델이 다른 도구를 요청해 루프가 이어질 수 있습니다. tools_condition은 답이 사실인지 판정하지 않고 호출 요청의 존재만 확인하므로, 품질 검사와 실행 상한은 별도로 설계해야 합니다.
5실행 예제
먼저 gpt-5.4-mini에 lookup_policy를 bind_tools로 연결합니다. call_model은 모델 응답을 messages에 추가하고 모델 호출만 trace에 기록합니다. 그 다음 StateGraph에 model과 ToolNode를 등록하고 tools_condition을 조건부 엣지로 연결합니다. 대출 기간 질문과 인사 질문을 각각 실행해 ToolMessage 생성 여부를 비교합니다.
확인할 점 — 대출 기간 질문의 trace에는 모델 호출 두 번이 나타나고, 그 사이의 ToolNode 실행은 메시지 목록의 ToolMessage로 확인합니다. 메시지 종류는 HumanMessage, AIMessage, ToolMessage, AIMessage 순서입니다. 첫 AIMessage의 tool_calls에는 lookup_policy와 topic 인자가 있고, ToolMessage에는 로컬 규정 문자열이 있습니다. 반면 인사 질문은 도구를 호출할 이유가 없으므로 model 노드를 한 번 실행한 뒤 끝날 수 있습니다. 모델 출력은 실행 시점에 달라질 수 있으므로 정확한 문장보다 메시지 종류, 호출 이름, 도구 결과 포함 여부를 확인합니다.
6실험 결과 해석
대출 질문은 HumanMessage, 도구 호출이 있는 AIMessage, '일반 도서는 1인 5권까지 14일'이라는 ToolMessage, 최종 AIMessage 순서로 끝났습니다. 모델 trace는 두 번 기록됐고 ToolNode 실행은 가운데 ToolMessage로 확인했습니다. 두 모델 호출은 입력 370토큰, 출력 50토큰이었고 추정 비용은 0.000503달러, 전체 지연은 1.963초였습니다. 인사 질문에는 ToolMessage가 없었습니다.
두 질문을 한 번씩 실행한 구조 확인입니다. 다른 질문에서도 같은 도구 선택이 일어나는지, 응답 품질이 유지되는지는 더 많은 고정 질문으로 따로 측정해야 합니다.
7주의할 점과 실무 메모
tools_condition은 질문의 키워드를 직접 검사하지 않습니다. 마지막 AIMessage의 tool_calls 유무만 봅니다.
ToolNode는 모델이 아닙니다. 이미 만들어진 도구 호출 요청을 실행하는 그래프 노드입니다.
이번 자료의 도구는 로컬 딕셔너리를 읽기만 합니다. 쓰기 도구에는 별도의 권한 확인과 중복 실행 방지가 필요합니다.
가격 계산은 2026-09-10 공개 단가인 입력 100만 토큰당 0.75달러, 출력 100만 토큰당 4.50달러를 사용합니다. 실제 청구액은 계정의 캐시·배치 조건에 따라 달라질 수 있습니다.
8정리와 다음 절
tools_condition은 마지막 AIMessage의 tool_calls 유무로 ToolNode 또는 END를 선택합니다.
ToolNode의 실행 여부는 요청 AIMessage와 결과 ToolMessage의 연결로 확인합니다.
도구가 필요 없는 질문은 model 한 번 뒤에 종료될 수 있습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 ToolNode가 실행한 도구에서 오류가 발생했을 때 예외를 숨기지 않고 ToolMessage로 어떻게 전달할지 확인합니다.
9복습 문제
1. tools_condition이 확인하는 값은 무엇인가요?
해설 — 마지막 AIMessage의 tool_calls 유무를 확인합니다.
2. ToolNode가 메시지 상태에 추가하는 대표 메시지는 무엇인가요?
해설 — 도구 실행 결과와 tool_call_id를 담은 ToolMessage입니다.
3. tools 노드 뒤에 model 노드로 돌아가는 엣지가 필요한 이유는 무엇인가요?
해설 — 모델이 도구 결과를 읽고 최종 답을 만들거나 다음 도구 호출을 정해야 하기 때문입니다.
4. 이번 실행의 성공을 최종 답 문장 일치로 판정하지 않는 이유는 무엇인가요?
해설 — 모델 표현은 실행할 때마다 달라질 수 있고, 이번 학습 목표는 메시지 흐름과 도구 실행이기 때문입니다.

1학습 목표
ToolMessage의 tool_call_id가 요청과 결과를 연결하는 방식을 설명할 수 있습니다.
handle_tool_errors=False와 사용자 정의 오류 처리 함수를 비교할 수 있습니다.
도구가 실패한 뒤 모델이 오류 내용을 읽고 안전한 답을 만들게 할 수 있습니다.
2이 내용을 배우는 이유
모델은 도구 인자를 잘못 만들 수 있고, 도구가 지원하지 않는 값을 요청할 수도 있습니다. 예외가 그래프 밖으로 바로 전파되면 실행이 중단되어 모델은 무엇이 잘못됐는지 알지 못합니다. 모든 오류를 성공 결과처럼 바꾸는 것도 문제입니다. 오류 종류와 다음 행동을 담은 ToolMessage를 남기면 모델이 재시도하거나 제한을 설명할 근거를 얻고, 개발자는 같은 메시지 기록에서 원인을 추적할 수 있습니다.
3앞에서 배운 내용
앞 절에서 첫 AIMessage의 tool_calls에 이름·인자·id가 들어 있고 ToolNode가 결과 ToolMessage를 추가하는 것을 확인했습니다. Ch19에서는 지원 범위를 도구 docstring과 Pydantic 스키마에 적었습니다. 이번에는 스키마를 통과한 문자열이더라도 로컬 자료에 없는 주제라면 ValueError가 발생하는 사례를 사용합니다.
4핵심 개념
구체적인 상황
택배 송장 번호가 발송 요청과 배송 결과를 연결하듯 tool_call_id는 하나의 도구 요청과 결과를 연결합니다.
정의와 메시지 흐름
ToolMessage는 content에 도구 결과나 처리된 오류를 담고 tool_call_id에 원래 요청 id를 넣습니다. ToolNode의 handle_tool_errors=False는 도구 예외를 호출자에게 그대로 전파합니다. 반면 특정 예외를 받는 오류 처리 함수는 학생이 이해할 수 있는 오류 문자열을 반환하고 ToolNode가 이를 ToolMessage로 만듭니다. 오류가 메시지가 되었다고 해서 성공한 것은 아니며, 모델에게 다음 판단 자료가 생겼다는 뜻입니다.
도식 읽기
ToolNode가 도구를 실행하다 ValueError를 만나면 사용자 정의 오류 처리 함수가 오류 내용을 ToolMessage로 바꿉니다. 모델은 이 메시지를 읽고 사용자에게 결과를 설명합니다.
코드를 읽기 전에
도구 함수가 ValueError를 일으키면 기본 실행은 예외로 중단될 수 있습니다. handle_tool_errors=False인 ToolNode는 이 예외를 밖으로 전파해 실패 위치를 그대로 보여 줍니다. 오류 처리 함수를 지정한 ToolNode는 허용한 예외를 문자열로 바꾸고, 원래 요청 ID를 가진 ToolMessage에 담아 상태에 추가합니다.
ToolMessage가 생겼다는 사실은 도구가 성공했다는 뜻이 아닙니다. content를 읽어 정상 결과와 처리된 오류를 구분해야 하며, 모델은 그 메시지를 다음 입력으로 받아 사용자 설명이나 다른 행동을 선택합니다.
다른 상황과 개념 경계
재고 ID가 없다는 업무 오류는 ‘존재하지 않음’ 메시지로 바꾸어 모델이 다른 ID를 묻게 할 수 있습니다. 인증 실패나 데이터베이스 손상처럼 복구 정책이 다른 오류까지 같은 문장으로 바꾸면 운영 진단이 어려워집니다. 처리할 예외 유형, 사용자에게 공개할 내용, 기록할 원인을 나누어 설계합니다.
5실행 예제
topic='주차'인 하나의 AIMessage를 고정해 두 그래프에 넣습니다. Before의 ToolNode에는 handle_tool_errors=False를 사용합니다. After에는 ValueError만 처리하는 handle_policy_error를 연결합니다. 마지막에는 실제 gpt-5.4-mini가 오류 ToolMessage를 포함한 대화를 읽도록 호출합니다.
확인할 점 — Before에서는 lookup_policy(topic='주차') 호출이 ValueError로 끝나고 ToolMessage가 만들어지지 않습니다. After에서는 같은 호출 id와 같은 인자를 유지한 채 handle_policy_error가 오류를 설명하는 ToolMessage를 반환합니다. 이어서 실제 모델이 이 메시지 기록을 읽으면 지원하지 않는 규정이라고 설명해야 합니다. 비교의 원인은 ToolNode의 오류 처리 설정 하나이며 질문과 도구는 같습니다.
6일부러 실패해 보기
Before는 'ValueError: 지원하지 않는 주제: 주차'를 발생시키고 실행을 중단했습니다. After는 tool_call_id가 call_bad_1인 ToolMessage에 허용 주제 세 가지를 담았습니다. 후속 모델은 주차 규정을 확인할 수 없다고 답했습니다. 후속 호출은 입력 73토큰, 출력 97토큰, 추정 비용 0.00049125달러, 지연 1.356초였습니다.
잘못된 호출은 비교 조건을 고정하려고 코드에서 직접 만들었습니다. 모델이 이런 호출을 얼마나 자주 만드는지 보여 주는 실험은 아니며, 그 비율은 별도 평가셋에서 측정해야 합니다.
7주의할 점과 실무 메모
handle_tool_errors=True처럼 모든 예외를 같은 방식으로 처리하면 네트워크 장애와 잘못된 인자를 구분하기 어렵습니다.
오류 메시지에는 비밀 값, 내부 경로, 전체 스택 추적을 넣지 않습니다. 운영 로그에는 원인을 보존하되 모델 입력은 필요한 정보로 제한합니다.
쓰기 도구가 일부 동작한 뒤 실패했다면 단순 재시도는 중복 변경을 만들 수 있습니다. Ch24의 내구 실행에서 멱등성을 다시 다룹니다.
8정리와 다음 절
tool_call_id는 하나의 요청과 하나의 도구 결과를 연결합니다.
좁은 오류 처리 함수는 ValueError를 모델이 읽을 ToolMessage로 바꿉니다.
오류 메시지로 바뀌어도 도구 실행이 성공한 것은 아닙니다.
다음 학습과 이어지는 지점 — 다음 절에서는 오류 처리와 별개로, 모델이 계속 도구를 요청해 그래프가 끝나지 않는 상황을 recursion_limit과 명시적 종료 조건으로 다룹니다.
9복습 문제
1. tool_call_id는 왜 필요한가요?
해설 — 여러 도구 요청 중 어떤 요청에 대한 결과인지 정확히 연결하기 위해 필요합니다.
2. 오류를 ToolMessage로 바꾸면 도구 실행이 성공한 것인가요?

상태에 누적한 실행 횟수를 기준으로 END로 이동하는 명시적 종료 조건을 구현할 수 있습니다.
2이 내용을 배우는 이유
모델이 도구를 선택하는 루프에는 실행 횟수 변동이 생깁니다. 정상 질문도 두세 번 도구를 호출할 수 있지만, 잘못된 프롬프트나 서로 맞지 않는 도구 결과 때문에 같은 요청을 반복할 수도 있습니다. 비용과 지연이 계속 늘어나지 않게 실행 한도를 두고, 정상 경로에는 업무 의미가 드러나는 종료 조건을 넣어야 합니다. 실행 한도는 마지막 안전장치이고 종료 조건은 정상 동작을 설명하는 규칙입니다.
3앞에서 배운 내용
Ch17에서 정지 조건 없는 자율성은 비용과 예측 불가능성을 키운다고 배웠습니다. 앞 절의 ToolNode 루프는 모델 응답에 tool_calls가 없으면 tools_condition이 END를 선택했습니다. 이번 실험은 모델 출력이 실행할 때마다 달라지는 현상과 구분하기 위해, 항상 같은 순환을 만드는 로컬 그래프로 recursion_limit의 경계를 재현합니다.
4핵심 개념
구체적인 상황
건물의 비상 차단기와 정상 종료 버튼은 역할이 다릅니다.
정의와 메시지 흐름
recursion_limit은 그래프가 지정한 super-step 수를 넘으면 GraphRecursionError를 발생시키는 비상 차단기입니다. super-step은 한 번에 실행 가능한 노드 묶음이 진행되는 단위입니다. 명시적 종료 조건은 상태의 attempts나 remaining 같은 값을 읽어 END를 선택하는 정상 종료 버튼입니다. 한도 값을 무조건 크게 올리면 순환 원인을 감출 수 있으므로 먼저 엣지와 조건 함수를 확인해야 합니다.
도식 읽기
tick 실행 뒤 종료 조건을 검사합니다. count가 3보다 작으면 tick을 반복하고, 3이면 END로 이동합니다. recursion_limit은 그래프 전체 실행의 단계 수를 제한하며 END 뒤에 실행하는 노드가 아닙니다.
코드를 읽기 전에
recursion_limit은 함수 재귀 깊이가 아니라 한 그래프 실행에서 허용할 최대 super-step 수를 제한하는 실행 설정입니다. 모델과 도구가 계속 서로를 호출해 한도를 넘으면 GraphRecursionError가 발생합니다. 이 예외를 잡는 코드는 강제 중단을 관찰하는 방법이며, 중간 결과가 충분하거나 정상 완료됐다는 뜻은 아닙니다.
명시적 종료 예제는 상태에 시도 횟수나 완료 여부를 두고 조건부 엣지가 END를 선택하게 합니다. 한도는 모든 경로의 마지막 안전장치이고, 업무 완료 조건은 그래프가 정상적으로 끝나는 규칙입니다.
다른 상황과 개념 경계
검색 결과가 없을 때 같은 검색어를 반복하는 그래프는 단계 한도로 멈출 수 있지만 사용자에게 유용한 결과는 남기지 못합니다. ‘서로 다른 검색어를 세 번 사용했는데 근거 없음’을 사람 확인 상태로 보내면 종료 이유와 다음 행동이 분명해집니다. 실행 한도와 업무 종료 상태를 함께 기록해야 실패율을 올바르게 셀 수 있습니다.
5실행 예제
모델 호출 없이 count를 하나씩 늘리며 실행할 때마다 같은 결과를 내는 로컬 그래프를 만듭니다. 종료 엣지가 없는 그래프를 recursion_limit=4로 실행해 경계 오류를 확인합니다. 이어서 stop_or_continue가 count 3에서 END를 반환하도록 조건부 엣지를 추가하고 같은 시작 상태와 같은 실행 한도로 다시 실행합니다.
확인할 점 — Before 그래프는 tick 노드에서 count를 늘린 뒤 다시 tick으로만 이동합니다. recursion_limit=4에서 GraphRecursionError가 실제로 발생합니다. 이 그래프는 모델 판단을 흉내 내지 않고 경계 동작만 분리해 확인합니다. After 그래프는 tick 뒤 stop_or_continue가 count 3에서 END를 반환합니다. 같은 시작 상태에서도 예외 없이 count 3과 trace 세 항목을 반환합니다.
6일부러 실패해 보기
종료 조건이 없는 그래프는 'Recursion limit of 4 reached'라는 GraphRecursionError를 실제로 발생시켰습니다. 종료 조건을 추가한 그래프는 예외 없이 count 3을 반환했고 trace에는 tick:1, tick:2, tick:3이 남았습니다. 이 결과는 모델의 반복 성향이 아니라 LangGraph 실행 한도의 동작을 분리해 보여 줍니다.
이 절은 모델을 호출하지 않는 결정적 경계 실험입니다. 실제 모델 루프가 몇 단계에서 끝나는지나 적절한 운영 한도는 질문과 도구별 실행 기록으로 정해야 합니다.
7주의할 점과 실무 메모
recursion_limit은 configurable 안에 넣지 않고 invoke의 설정 딕셔너리 최상위 키로 전달합니다.
한도를 늘리기 전에 반복이 예상된 정상 경로인지, 종료 엣지가 빠진 순환인지 구분합니다.
예외가 발생하면 최종 상태가 정상적으로 반환되지 않습니다. 중간 결과 보존이 필요하면 체크포인터와 별도 오류 처리를 설계해야 합니다.
실제 모델 루프에는 총 호출 횟수, 도구별 횟수, 비용 상한 같은 업무 기준도 함께 둡니다.
8정리와 다음 절
recursion_limit은 한 실행의 최대 super-step 수를 제한합니다.
GraphRecursionError는 허용된 super-step 안에 종료 조건에 도달하지 못했다는 신호입니다.
정상 경로에는 상태로 설명할 수 있는 명시적 END 조건을 둡니다.
다음 학습과 이어지는 지점 — 마지막 절에서는 코드가 고정한 if 분기와 모델이 고른 도구 분기를 같은 질문·자료·모델로 실행해 토큰, 지연, 결과 변동을 비교합니다.

fixed 경로의 키워드 규칙은 세 질문에 맞춰 작성한 기준선입니다. 새로운 표현이 들어오면 규칙을 확장하거나 실패 사례로 기록해야 합니다.

# recursion_limit과 명시적 종료
그래프의 반복이 끝나지 않을 때 실행 한도와 상태 기반 종료 조건은 각각 어떤 역할을 할까요?
## 실행 환경 준비
Python 3.12 새 커널에서 첫 셀부터 순서대로 실행합니다. API 키 값은 출력하지 않습니다.
## 패키지 준비
고정한 LangGraph 버전을 확인하고 그래프 구성 요소를 불러옵니다.
## 코드를 읽기 전에
`recursion_limit`은 함수 재귀 깊이가 아니라 한 그래프 실행에서 허용할 최대 super-step 수를 제한하는 실행 설정입니다. 모델과 도구가 계속 서로를 호출해 한도를 넘으면 `GraphRecursionError`가 발생합니다. 이 예외를 잡는 코드는 강제 중단을 관찰하는 방법이며, 중간 결과가 충분하거나 정상 완료됐다는 뜻은 아닙니다.
명시적 종료 예제는 상태에 시도 횟수나 완료 여부를 두고 조건부 엣지가 `END`를 선택하게 합니다. 한도는 모든 경로의 마지막 안전장치이고, 업무 완료 조건은 그래프가 정상적으로 끝나는 규칙입니다.
## Before: 종료 없는 순환 그래프
count를 늘린 뒤 다시 같은 노드로 이동하는 종료 없는 그래프를 만듭니다.
## Before: 실제 한도 초과 확인
recursion_limit=4로 실행해 GraphRecursionError가 발생하는지 확인합니다.
## After: 상태 기반 종료 조건 추가
count가 3에 도달하면 END를 반환하는 stop_or_continue 조건을 추가합니다.
## After: 정상 종료와 실행 흔적 확인
같은 실행 한도에서 count 값 3과 세 번의 tick 기록을 반환하는지 확인합니다.
## 다른 상황에 적용하기
검색 결과가 없을 때 같은 검색어를 반복하는 그래프는 단계 한도로 멈출 수 있지만 사용자에게 유용한 결과는 남기지 못합니다. ‘서로 다른 검색어를 세 번 사용했는데 근거 없음’을 사람 확인 상태로 보내면 종료 이유와 다음 행동이 분명해집니다. 실행 한도와 업무 종료 상태를 함께 기록해야 실패율을 올바르게 셀 수 있습니다.

‘환불 규정’처럼 키워드와 처리 경로가 안정적인 요청은 고정 분기가 예측 가능할 수 있습니다. 같은 문장에 배송·회원 등 여러 의도가 섞이면 모델 선택이 더 유연할 수 있지만 잘못된 도구 선택도 측정해야 합니다. 비교할 때는 정답률, 불필요한 호출, 미호출, 지연, 출력 변동을 같은 평가셋에서 함께 기록합니다.
