하네스가 프레임워크 위에서 어떤 문제를 해결하는지 분류합니다.

이 실험이 확인한 범위를 설명할 수 있습니다.
2이 내용을 배우는 이유
Ch 6에서 그린 계층 지도에서는 하네스를 모델 호출 바깥의 실행 틀로만 표시했습니다. 이제 설치된 패키지의 조립 코드를 읽어 그 틀이 실제로 무엇을 더하는지 확인합니다. 기능을 일곱 이름으로 외우는 것이 목적이 아니라, 파일이 사라졌는지·위임 도구가 없는지·요약이 동작하지 않는지에 따라 확인할 위치를 찾는 것이 목적입니다.
3앞에서 배운 내용
Ch 21의 create_agent는 모델과 도구의 반복을 만들었습니다. Ch 23의 체크포인터는 실행 상태를 이어 주었고 Ch 24는 사람 승인을, Ch 26은 위임 구조를 다뤘습니다. DeepAgents는 이 기능을 대체하지 않고 LangChain과 LangGraph 위에서 긴 작업에 자주 필요한 구성을 묶습니다.
노트북은 앞 절 변수에 의존하지 않으며 Python 3.12, deepagents==0.7.0, langchain==1.4.0을 설치하고 상위 폴더의 .env를 찾습니다.
4핵심 개념
정의와 구체적인 상황
DeepAgents 0.7.0의 생성 함수와 미들웨어 조립 코드를 기준으로 이 장에서는 일곱 기능을 파일시스템, 서브에이전트, 컨텍스트 요약, 스킬, 장기 메모리, 파일 권한과 사람 승인, 비동기 서브에이전트로 분류합니다. 이는 현재 공개 API를 배우기 위한 분류입니다. 과거 글의 ‘4대 요소’와 숫자만 비교하지 말고 설치한 버전에서 실제로 조립되는 기능을 확인해야 합니다.
코드 읽기와 비교 경계
하네스(harness)는 모델 하나를 뜻하지 않습니다. 모델 호출 주위에 도구, 파일 저장, 위임, 요약, 권한 같은 반복 기능을 조립해 긴 작업을 실행하는 틀입니다. 이 셀은 inspect.getsource(create_deep_agent)로 설치된 0.7.0의 생성 함수 소스를 문자열로 읽고, 각 기능을 조립하는 이름이 실제로 들어 있는지 확인합니다. in source 결과가 True라는 것은 생성 경로에 관련 코드가 존재한다는 뜻이며, 모든 실행에서 그 기능이 활성화되었다는 뜻은 아닙니다.
프레임워크와 하네스의 차이는 추상화 수준입니다. LangGraph는 상태와 노드의 실행 순서를 구성하고, LangChain의 에이전트는 모델과 도구 반복을 구성합니다. Deep Agents 하네스는 그 위에 장기 작업에서 반복되는 파일·서브에이전트·컨텍스트 관리 기능을 미리 조립합니다. 짧은 한 번의 도구 호출에는 하네스의 추가 표면이 필요하지 않을 수 있습니다. 기능 수를 비교할 때는 기본 활성 기능과 인자를 전달해야 생기는 선택 기능을 구분해야 합니다.
도식 읽기
색이 쓰인 곳에서 파란색은 학생 코드와 실행 흐름, 보라색은 모델의 판단, 초록색은 도구와 데이터, 노란색은 측정값, 빨간색은 실패 또는 권한 경계를 뜻합니다. LangChain create_agent에서 시작해 DeepAgents 하네스를 거쳐 7개 기능과 긴 작업 실행으로 내려갑니다. 세 번째 상자의 7개 기능은 모두 항상 활성화된다는 뜻이 아닙니다. skills·memory·permissions·async subagents는 인자를 전달할 때 추가됩니다.
5실행 예제
설치된 create_deep_agent 소스에서 일곱 미들웨어 이름을 찾습니다. 출력의 True는 해당 조립 경로가 소스에 존재한다는 뜻입니다. 이어서 True의 개수를 세고 7인지 검증합니다.
확인할 점 일곱 항목이 모두 True인지와 합계가 7인지 확인합니다. 이 출력은 기능의 조립 경로를 확인한 결과이며, 각 기능의 실행 품질을 평가한 결과는 아닙니다.
6실험 결과 해석
실행 결과에서 파일시스템·서브에이전트·컨텍스트 요약·스킬·장기 메모리·권한과 사람 승인·비동기 서브에이전트가 모두 True였고 합계는 7이었습니다. 이 실험은 코드 경로의 존재를 확인합니다. 실제 도구 선택과 저장 결과는 뒤 절에서 별도로 실행합니다.
7주의할 점과 실무 메모
소스 문자열 검색은 조립 경로의 존재만 보여 줍니다. 실제 도구 선택과 산출물은 기능별 실행으로 확인합니다.
이 장은 설치된 deepagents==0.7.0 소스와 릴리스 노트를 기준으로 읽습니다.

2이 내용을 배우는 이유
함수 시그니처만 읽으면 tools 인자가 있다는 사실은 알 수 있지만 모델이 도구를 선택하고 결과를 다시 읽는지는 알 수 없습니다. 이 절은 Chapter 27이라는 고정 입력을 course_lookup에 전달하고 HumanMessage → AIMessage → ToolMessage → AIMessage 순서를 실제로 확인합니다.
3앞에서 배운 내용

4핵심 개념
정의와 구체적인 상황
create_deep_agent는 LangChain의 create_agent 위에 파일시스템과 위임, 요약 미들웨어를 조립합니다. 기본 파일 도구는 ls, read_file, write_file, edit_file, delete, glob, grep입니다. execute는 실행을 지원하는 샌드박스 백엔드가 있을 때만 실제 명령을 수행합니다. 0.7에서는 write_file이 기존 파일 전체를 교체할 수 있으므로 권한 규칙이 중요합니다.
코드 읽기와 비교 경계
create_deep_agent(model=..., tools=[...])는 설정을 저장하는 객체가 아니라 호출 가능한 CompiledStateGraph를 반환합니다. tools에는 업무 도구를 전달하고, 파일 도구와 위임 도구는 하네스의 미들웨어가 조건에 따라 더합니다. agent.invoke({'messages': [...]})를 호출해야 실제 모델과 도구 반복이 시작됩니다. 반환 딕셔너리의 messages에는 사용자 메시지, 도구 호출을 요청한 AI 메시지, 도구 결과, 최종 AI 메시지가 순서대로 남습니다.
기본 도구가 보인다고 해서 모든 경로에 접근할 수 있는 것은 아닙니다. 파일 도구의 실제 범위는 연결한 backend와 permissions가 정합니다. course_lookup 같은 업무 도구는 모델이 필요하다고 판단할 때 호출하지만, 필수 호출을 보장해야 한다면 시스템 지침만 의존하지 말고 궤적 검사나 명시적 그래프 경로를 추가합니다. 이 예제는 도구 호출과 ToolMessage 존재를 확인하며, 답변의 사실 정확성은 반환한 고정 수업 자료 범위에서만 판단할 수 있습니다.
도식 읽기
색이 쓰인 곳에서 파란색은 학생 코드와 실행 흐름, 보라색은 모델의 판단, 초록색은 도구와 데이터, 노란색은 측정값, 빨간색은 실패 또는 권한 경계를 뜻합니다. create_deep_agent가 백엔드·미들웨어를 조립하고 파일·위임 도구를 더한 뒤 CompiledStateGraph를 반환하는 순서입니다. 실행 출력의 model과 tools 노드는 마지막 상자에 포함된 내부 실행 노드입니다.

0.7.0부터 TodoListMiddleware와 write_todos는 기본 구성에서 빠졌습니다. 계획이 필요한 애플리케이션만 middleware=[TodoListMiddleware()]로 추가합니다. 작성된 기본 시스템 프롬프트도 비어 있으며, 파일 도구와 위임 도구의 스키마와 겹치던 설명이 줄었습니다. 릴리스 PR의 65% 감소는 gpt-5.5에 ‘hello’를 보낸 첫 턴에서 5,395토큰과 1,895토큰을 비교한 값입니다. 전체 작업의 총 토큰이나 모든 모델의 절감률로 일반화할 수 없습니다.
코드 읽기와 비교 경계
TodoListMiddleware()는 모델에게 write_todos 도구와 그 사용 지침을 추가합니다. 이를 middleware=[...]로 전달하는 것은 모든 요청에 계획을 강제한다는 뜻이 아니라, 모델이 할 일 목록을 기록할 수 있는 기능을 선택적으로 연결하는 것입니다. write_todos 호출은 계획 내용을 상태에 남기고 후속 단계가 이를 읽게 합니다. 두 할 일을 요청한 예제에서 도구 호출과 저장된 todo 상태를 함께 확인해야 ‘계획 기능이 연결되었다’고 말할 수 있습니다.
시스템 프롬프트 길이와 작업 품질은 같은 측정값이 아닙니다. 기본 지침을 줄이면 첫 호출 입력은 작아질 수 있지만, 업무에 필요한 제약까지 빠지면 재시도나 잘못된 도구 사용이 늘 수 있습니다. 반대로 모든 짧은 질문에 todo 작성을 요구하면 계획 도구 호출 자체가 불필요한 단계가 됩니다. 플래닝은 여러 산출물, 선후 관계, 중간 검증이 있는 작업에 적용하고, 한 단계 조회에는 직접 도구 호출을 우선합니다.

completed는 모델이 todo를 완료 상태로 기록한 값입니다. 버전 정보나 설명 산출물의 정확성은 따로 검증합니다.

두 방법은 손실 위험도 다릅니다. 요약은 원문에 있던 조건이나 예외를 생략할 수 있으므로 중요한 수치와 출처를 별도로 유지해야 합니다. 오프로딩은 원문을 보존하지만 모델이 다시 읽지 않은 부분은 현재 판단에 사용되지 않습니다. 이번 출력에서 ToolMessage에 파일 경로가 남고 실제 파일이 존재하는지는 오프로딩을 확인하지만, 오래된 대화가 정확히 요약되는지는 확인하지 않습니다. 장기 대화 요약은 별도의 반복 실행과 사실 보존 평가가 필요합니다.
도식 읽기
색이 쓰인 곳에서 파란색은 학생 코드와 실행 흐름, 보라색은 모델의 판단, 초록색은 도구와 데이터, 노란색은 측정값, 빨간색은 실패 또는 권한 경계를 뜻합니다. 긴 대화·큰 도구 결과에서 요약 또는 오프로딩으로 갈라진 뒤 요약 메시지·파일 경로가 다음 모델 호출에 전달됩니다. 이 실습은 큰 도구 결과의 오프로딩 경로만 실행하며 오래된 대화 요약 임계점은 별도 장기 실행이 필요합니다.

### 코드 읽기와 비교 경계
하네스(harness)는 모델 하나를 뜻하지 않습니다. 모델 호출 주위에 도구, 파일 저장, 위임, 요약, 권한 같은 반복 기능을 조립해 긴 작업을 실행하는 틀입니다. 이 셀은 `inspect.getsource(create_deep_agent)`로 설치된 0.7.0의 생성 함수 소스를 문자열로 읽고, 각 기능을 조립하는 이름이 실제로 들어 있는지 확인합니다. `in source` 결과가 `True`라는 것은 생성 경로에 관련 코드가 존재한다는 뜻이며, 모든 실행에서 그 기능이 활성화되었다는 뜻은 아닙니다.

### 코드 읽기와 비교 경계
`create_deep_agent(model=..., tools=[...])`는 설정을 저장하는 객체가 아니라 호출 가능한 `CompiledStateGraph`를 반환합니다. `tools`에는 업무 도구를 전달하고, 파일 도구와 위임 도구는 하네스의 미들웨어가 조건에 따라 더합니다. `agent.invoke({'messages': [...]})`를 호출해야 실제 모델과 도구 반복이 시작됩니다. 반환 딕셔너리의 `messages`에는 사용자 메시지, 도구 호출을 요청한 AI 메시지, 도구 결과, 최종 AI 메시지가 순서대로 남습니다.
기본 도구가 보인다고 해서 모든 경로에 접근할 수 있는 것은 아닙니다. 파일 도구의 실제 범위는 연결한 backend와 permissions가 정합니다. `course_lookup` 같은 업무 도구는 모델이 필요하다고 판단할 때 호출하지만, 필수 호출을 보장해야 한다면 시스템 지침만 의존하지 말고 궤적 검사나 명시적 그래프 경로를 추가합니다. 이 예제는 도구 호출과 `ToolMessage` 존재를 확인하며, 답변의 사실 정확성은 반환한 고정 수업 자료 범위에서만 판단할 수 있습니다.

# 플래닝과 시스템 프롬프트
0.7에서 플래닝과 기본 프롬프트가 어떻게 달라졌는지 측정 범위와 함께 확인합니다.
## 설치
고정된 패키지를 현재 커널에 설치합니다.
## 실행 환경 준비
상위 폴더의 .env를 찾아 키 값은 출력하지 않고 버전만 확인합니다.
## 단계 1
0.7에서 opt-in인 TodoListMiddleware를 에이전트에 추가합니다.
### 코드 읽기와 비교 경계
`TodoListMiddleware()`는 모델에게 `write_todos` 도구와 그 사용 지침을 추가합니다. 이를 `middleware=[...]`로 전달하는 것은 모든 요청에 계획을 강제한다는 뜻이 아니라, 모델이 할 일 목록을 기록할 수 있는 기능을 선택적으로 연결하는 것입니다. `write_todos` 호출은 계획 내용을 상태에 남기고 후속 단계가 이를 읽게 합니다. 두 할 일을 요청한 예제에서 도구 호출과 저장된 todo 상태를 함께 확인해야 ‘계획 기능이 연결되었다’고 말할 수 있습니다.
시스템 프롬프트 길이와 작업 품질은 같은 측정값이 아닙니다. 기본 지침을 줄이면 첫 호출 입력은 작아질 수 있지만, 업무에 필요한 제약까지 빠지면 재시도나 잘못된 도구 사용이 늘 수 있습니다. 반대로 모든 짧은 질문에 todo 작성을 요구하면 계획 도구 호출 자체가 불필요한 단계가 됩니다. 플래닝은 여러 산출물, 선후 관계, 중간 검증이 있는 작업에 적용하고, 한 단계 조회에는 직접 도구 호출을 우선합니다.
`todos` 상태의 `completed`는 모델이 해당 항목을 완료로 기록했다는 뜻입니다. 버전 확인 결과나 설명 산출물을 실제로 검증했다는 증거가 아니므로, 산출물을 따로 검사해야 합니다.

감소율은 현재 실행의 사용량이 아니라 릴리스 PR에 적힌 5,395와 1,895를 재계산한 값입니다. 예제의 todo 상태와 서로 다른 근거입니다.

요약과 큰 도구 결과 오프로딩이 컨텍스트 크기를 다루는 위치를 구분합니다.

### 코드 읽기와 비교 경계
오프로딩(offloading)은 큰 도구 결과의 원문을 파일로 옮기고 `ToolMessage`에는 미리보기와 경로만 남기는 처리입니다. 이 예제의 `FilesystemMiddleware` 한도는 도구 결과가 어느 크기에서 파일로 이동하는지 정합니다. 모델은 경로를 보고 필요할 때 파일 도구로 일부를 다시 읽습니다. 요약은 여러 메시지의 뜻을 짧게 다시 쓰는 처리이고, 오프로딩은 원문을 다른 저장 위치에 보존한다는 점이 다릅니다.

# 통합 실행과 운영 한계

권한 규칙은 모델에게 부탁하는 문장이 아니라 도구 실행 직전에 판정되는 실행 경계여야 합니다. 이 예제는 허용된 보고서 경로와 차단된 `/blocked.txt` 경로를 각각 요청하고, 도구 결과에서 성공과 `permission denied`를 확인합니다. 모델이 차단 파일을 쓰려고 시도했다는 사실과 파일이 실제로 만들어졌다는 사실은 다릅니다. 거부 결과가 메시지에 남아도 최종 답변이 성공처럼 말할 수 있으므로 파일 존재와 도구 결과를 함께 검사합니다.
정지 조건도 권한과 같은 방식으로 관찰 가능해야 합니다. ‘보고서 작성 완료’는 지정 경로의 파일, 필수 항목, 검증 결과가 모두 있을 때 판정합니다. 최대 반복 수는 무한 실행을 막는 경계일 뿐 업무 완료를 증명하지 않습니다. 이 실습은 사용량을 집계하지 않습니다. 종료 판정을 위해 허용된 파일 본문, 거부 ToolMessage, 차단 파일의 부재를 서로 다른 검사로 남깁니다.
