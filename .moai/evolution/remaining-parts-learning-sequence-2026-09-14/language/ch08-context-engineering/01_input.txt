1학습 목표
이 절을 마치면 모델이 이번 답을 만들 때 실제로 읽는 자료가 무엇인지 설명할 수 있습니다.
이 절을 마치면 컨텍스트 윈도 최대 한도와 수업에서 정한 토큰 예산을 구분할 수 있습니다.
이 절을 마치면 입력 예산에서 출력 예약분과 여유분을 먼저 제외해야 하는 이유를 계산 절차로 설명할 수 있습니다.
이 절을 마치면 로컬 추정값과 API가 반환한 실제 사용량을 구분하여 기록할 수 있습니다.
2이 내용을 배우는 이유
Ch 6에서는 언어 모델에 메시지를 보내고 답을 받는 기본 호출을 배웠고, Ch 7에서는 지시와 예시를 배치하여 프롬프트를 구성했습니다. 이제 자료를 더 많이 넣으면 답이 언제나 좋아지는지 살펴볼 차례입니다. 모델이 한 번에 참고할 수 있는 범위에는 한도가 있습니다. 질문, 지시, 대화 기록, 문서, 도구 결과, 그리고 모델이 작성할 답까지 모두 같은 한도 안에서 자리를 사용합니다.
컨텍스트 엔지니어링은 모델에게 어떤 자료를 얼마나 보낼지 정하는 일입니다. 질문에 필요하다는 이유만으로 자료를 계속 추가할 수는 없습니다. 답에 필요한 자료를 정해진 토큰 수 안에 배치해야 합니다. 이 절에서는 먼저 토큰 예산표를 만듭니다. 다음 절에서는 긴 자료를 저장하고 필요한 부분을 선택하며, 03절에서는 내용을 줄이거나 업무별로 나눕니다. Ch 9에서는 이 장의 선택(Select)을 검색 코드로 확장합니다.
아직 에이전트를 만들지는 않습니다. 이 장의 흐름과 선택 기준은 모두 사람이 코드에 고정합니다. 어떤 자료를 포함할지 모델이 스스로 판단하고 도구를 호출하는 단계는 Ch 20부터 다룹니다.
3앞에서 배운 내용
Ch 6에서는 시스템 역할과 사용자 역할을 구분한 메시지 목록을 모델에 전달했습니다. 이 절에서는 특정 함수 이름을 가정하지 않고, 모델 호출에는 역할이 붙은 메시지가 입력된다는 개념만 사용합니다. Ch 7에서는 지시, 예시, 출력 형식을 프롬프트 안에 배치했습니다. 그 요소들도 모두 입력 공간을 차지합니다.
Ch 6에서 작성한 호출 코드의 메시지 목록을 열어 역할이 어떻게 나뉘었는지 확인합니다. 이어서 Ch 7에서 추가한 지시·질문·예시·출력 형식의 순서를 표시합니다. 이 요소들이 01절의 예산표에서 각각 입력 공간을 사용하는 대상입니다.
4핵심 개념
비유 — 작업 전에 책상 자리를 나눕니다
넓이가 정해진 책상에서 자료를 검토한다고 생각해 봅시다. 책상 전체가 모델의 최대 작업 공간입니다. 업무 지시서, 질문지, 참고 문서, 이전 대화 기록이 책상 위에 놓입니다. 마지막에는 답안지를 펼칠 자리도 남아 있어야 합니다. 자료로 책상을 가득 채우면 답안지를 놓을 공간이 부족해집니다. 따라서 자료를 올리기 전에 답안지 자리와 예상하지 못한 추가 자료를 위한 자리를 먼저 확보합니다.
{{img:01-책상-예산|많은 자료가 쌓인 책상과 필요한 자료만 놓은 책상을 비교한 그림}}
왼쪽 책상은 입력 자료가 답안 작성 공간까지 차지한 상태이고, 오른쪽 책상은 지시·질문·근거와 답안 공간을 나누어 둔 상태입니다.보는 순서 — ① 책상 전체 범위 → ② 입력 자료 영역 → ③ 비워 둔 답안 영역.
정의
컨텍스트 (context)
모델이 현재 답을 만들 때 참고하도록 전달된 정보 전체입니다. 시스템 지시, 사용자 질문, 대화 기록, 예시, 문서와 도구 결과가 포함될 수 있습니다. 외부 파일에 존재하지만 호출 메시지에 실리지 않은 내용은 현재 컨텍스트가 아닙니다.
컨텍스트 윈도 (context window)
한 번의 모델 호출에서 처리할 수 있는 입력과 출력의 전체 범위입니다. 모델마다 최대 한도가 다를 수 있으며, 같은 모델도 사용하는 API와 설정에 따라 적용 조건을 확인해야 합니다.
토큰 (token)
모델이 텍스트를 처리하는 단위입니다. 토큰은 글자나 단어와 일치하지 않습니다. 같은 글자 수라도 언어, 숫자, 공백, 기호의 구성에 따라 토큰 수가 달라질 수 있습니다.
토큰 예산 (token budget)
이번 작업에서 사용할 수 있도록 사람이 정한 토큰 상한입니다. 모델이 허용하는 최대 한도와 별개이며, 비용·지연 시간·답의 안정성을 고려하여 더 작은 값으로 정할 수 있습니다.
출력 예약분 (output reservation)
모델이 답을 생성할 공간으로 미리 남겨 두는 토큰 수입니다. 추론 과정에 별도 토큰이 사용되는 모델이나 설정에서는 문서에 명시된 계산 방식에 따라 해당 사용분도 함께 고려합니다.
여유분 (safety margin)
토큰 추정 오차, 추가 지시, 도구 결과처럼 실행 중 늘어날 수 있는 내용을 수용하려고 비워 두는 공간입니다.
사용량 메타데이터 (usage metadata)
LangChain 응답 객체의 AIMessage.usage_metadata에 붙는 사용량 정보입니다. 입력, 출력, 전체 토큰 수가 들어갑니다. 모델 제공자가 이 정보를 보내지 않았다면 0토큰을 썼다는 뜻이 아니므로, 값이 없는 상태로 실행 기록을 완료하지 않습니다.
예산은 최대 한도보다 작게 정합니다
모델 최대 한도는 기술적으로 허용되는 범위이고, 수업 예산은 이번 실습에서 지킬 운영 기준입니다. 최대 한도가 크더라도 모든 호출에 그만큼의 입력을 사용할 이유는 없습니다. 긴 입력은 비용과 처리 시간을 늘리고, 서로 관련이 적은 자료가 함께 들어가면 모델이 필요한 근거를 찾기 어려워질 수 있습니다. 수업 예산은 실습 결과를 비교하기 위한 공통 조건이기도 합니다.
입력에 사용할 수 있는 범위는 다음 순서로 정합니다. 먼저 이번 호출의 전체 예산을 정합니다. 그다음 원하는 답의 길이를 고려하여 출력 예약분을 제외합니다. 이 장의 노트북은 init_chat_model()의 max_tokens=300으로 생성 상한을 설정합니다. 모델 제공자가 추론 토큰을 별도로 집계하는지는 반환된 메타데이터와 공식 문서에서 확인합니다. 마지막으로 추정 오차와 실행 중 추가되는 메시지를 위한 여유분을 제외합니다. 남은 범위 안에서 시스템 지시, 질문, 대화 기록, 참고 문서를 배분합니다.

문자 수와 토큰 수는 같은 값이 아닙니다
문자 수는 편집기에서 세기 쉽지만 모델의 처리 단위는 토큰입니다. 따라서 “문서가 2,000자이므로 2,000토큰이다”라고 계산할 수 없습니다. 한국어 조사와 어미, 영문 약어, 숫자, 코드 기호가 섞이면 분할 결과가 달라집니다. Ch 5에서 확인한 텍스트 분할 규칙은 모델마다 다를 수 있으므로 다른 모델의 계산기를 그대로 적용해서도 안 됩니다.
실습에서는 두 값을 따로 기록합니다. 호출 전에는 해당 모델에 맞는 로컬 계산 도구로 추정 토큰 수를 구합니다. 호출 후에는 API 응답의 실제 사용량을 저장합니다. 두 값이 다르다고 계산 오류라고 단정할 수는 없습니다. 로컬 도구는 시스템·사용자 역할 표시처럼 API가 메시지에 덧붙이는 형식과 서비스 내부 처리를 모두 똑같이 계산하지 못할 수 있습니다. 호출 전 예산 검사에는 넉넉하게 계산한 추정값을 사용하고, 비용과 실행 기록에는 API가 반환한 실제 값을 사용합니다.
도식 — 한도 안에서 자리를 먼저 확보합니다
전체 예산에서 출력 예약분과 여유분을 먼저 확보한 뒤, 남은 공간에 지시·질문·대화 기록·근거를 배치합니다. 최대 한도와 수업 예산은 서로 다른 경계입니다.
입력 예산 계산과 실제 호출 설정
input_budget(total, output_reserve, safety_margin)는 세 정수를 받아 입력에 배정할 토큰 수 하나를 반환하는 Python 함수입니다. 여기서 total=4096은 실습에서 정한 전체 배정량입니다. 사용 모델의 실제 최대 컨텍스트를 조회한 값이 아닙니다. return은 계산값을 호출한 위치로 반환하고, 음수이면 raise ValueError가 잘못된 배정을 알립니다.
출력 예약량을 300에서 600으로 늘리는 비교는 입력에 남는 공간이 300만큼 줄어드는 산술 관계를 확인합니다. 이 함수의 인자를 바꿔도 앞에서 만든 모델 객체의 max_tokens=300은 바뀌지 않습니다. 모델 출력 상한까지 바꾸어 실험하려면 모델 설정도 별도로 변경해야 합니다.
한 줄 분류 라벨을 받는 과제와 세 문단 설명을 받는 과제는 필요한 출력 공간이 다릅니다. 같은 전체 배정량에서 설명에 공간을 더 주면 입력 자료를 더 선별해야 합니다. 반대로 출력 공간을 너무 작게 정하면 중요한 단서가 입력에 있어도 답이 완성되기 전에 잘릴 수 있습니다. 실제 요청을 설계할 때는 필요한 답의 형태를 먼저 정하고 입력과 출력 배정을 함께 확인합니다.
5실행 예제
출력 공간을 먼저 예약하고 입력 길이를 로컬에서 추정한 뒤, 같은 입력을 실제 API에 전달합니다. 노트북의 짧은 셀을 위에서부터 실행하면서 로컬 추정값과 응답의 실제 사용량을 비교합니다.
확인할 점 — 실습 파일은 labs/part2/ch08-context-engineering/notebooks/01-컨텍스트와-토큰-예산.ipynb입니다. 새 커널에서 설명과 코드를 번갈아 읽으며 기본 예산, 로컬 추정값, 실제 사용량 순서로 확인합니다. 마지막 비교에서는 출력 예약분만 300에서 600으로 바꿉니다.
6일부러 실패해 보기
왼쪽에서는 수업에서 정한 작업 예산이 너무 작아 준비한 500토큰 입력의 허용량을 계산하지 못합니다. 오른쪽에서는 모델의 최대 한도는 바꾸지 않고 작업 예산만 4,096토큰으로 고칩니다. 출력 예약분과 여유분을 빼고 남은 3,668토큰 안에 같은 입력이 들어가는지 확인합니다.
7주의할 점과 실무 메모
최대 한도를 운영 목표로 사용하지 않습니다. 모델이 받을 수 있는 최대량과 서비스가 매 호출에 사용하도록 허용할 양은 다릅니다. 팀에서는 비용과 지연 시간 기준을 포함한 별도의 예산을 정합니다.
출력 제한을 나타내는 코드 인자의 뜻을 확인합니다. 사용하는 모델과 API 버전에 따라 출력 토큰과 추론 토큰을 세는 방식이 다를 수 있습니다. 수업 코드에 고정된 SDK 버전의 공식 문서를 기준으로 해석합니다.
사용량 정보가 언제 제공되는지 확인합니다. 일반 응답과 스트리밍 응답은 사용량 정보의 위치나 제공 조건이 다를 수 있습니다. 값이 없을 때 0으로 기록하면 실제 사용량이 없었다는 잘못된 뜻이 됩니다.
한국어와 코드를 각각 측정합니다. 같은 문자 수라는 이유로 같은 토큰 수를 가정하지 않습니다. 실제 서비스 자료의 언어와 형식을 반영한 표본으로 예산을 검증합니다.
민감한 원문은 사용량 기록에 포함하지 않습니다. 운영 로그에는 토큰 수와 문서 식별자 등 필요한 정보만 남기고, 개인 정보나 비밀 값이 포함된 메시지 원문은 별도 정책에 따릅니다.
8정리와 다음 절
컨텍스트는 현재 호출에서 모델에 전달된 정보이며, 외부에 존재하기만 하는 자료는 포함되지 않습니다.
토큰 예산은 모델 최대 한도와 별도로 정하고, 출력 예약분과 여유분을 먼저 확보합니다.
문자 수, 로컬 추정 토큰, API 실제 사용량은 서로 다른 값으로 기록합니다.
다음 학습과 이어지는 지점 — 02절에서는 예산을 넘는 전체 자료를 외부 저장소에 Write하고, 질문에 필요한 항목만 Select하여 현재 호출의 컨텍스트에 넣습니다. Ch 9에서는 이 선택을 검색으로 자동화합니다.
9복습 문제
문제 4개 · 해설 포함
[하] 1. 외부 JSON 파일에 저장되어 있지만 호출 메시지에 포함되지 않은 문서는 현재 컨텍스트입니까?
정답과 해설 — 아닙니다. 현재 컨텍스트는 모델이 이번 답을 만들 때 받도록 전달된 정보입니다. 파일은 저장된 자료이며, 읽어서 메시지에 포함해야 컨텍스트가 됩니다. 틀렸다면 이 절의 핵심 개념 ‘정의’를 다시 봅니다.
[중] 2. 전체 예산에서 입력 가용분을 정하는 순서를 설명하세요.
정답과 해설 — 전체 수업 예산을 정한 뒤 출력 예약분을 제외하고, 추정 오차와 추가 메시지를 위한 여유분을 제외합니다. 남은 범위를 지시·질문·기록·문서에 배분합니다. 틀렸다면 이 절의 핵심 개념 ‘예산은 최대 한도보다 작게 정합니다’를 다시 봅니다.
[중] 3. 로컬 토큰 추정값과 API 실제 사용량을 따로 기록해야 하는 이유를 쓰세요.
정답과 해설 — 로컬 계산기는 시스템·사용자 역할 표시처럼 API가 메시지에 덧붙이는 형식과 서비스 내부 처리를 모두 똑같이 계산하지 못할 수 있습니다. 추정값은 호출 전 예산 검사에, API 값은 실행 뒤 사용량 기록에 사용합니다. 틀렸다면 이 절의 핵심 개념 ‘문자 수와 토큰 수는 같은 값이 아닙니다’를 다시 봅니다.
[상] 4. 모델 최대 한도가 충분히 큰데도 팀이 더 작은 수업 예산을 정해야 하는 이유를 세 가지 제시하세요.
정답과 해설 — 비용과 지연 시간을 관리하고, 관련성이 낮은 자료가 함께 들어오는 것을 줄이며, 실습 결과를 같은 조건에서 비교하기 위해서입니다. 답에는 최대 한도와 운영 예산의 역할이 다르다는 설명이 포함되어야 합니다. 틀렸다면 ‘이 내용을 배우는 이유’와 이 절의 핵심 개념 ‘예산은 최대 한도보다 작게 정합니다’를 다시 봅니다.

1학습 목표
이 절을 마치면 Write와 Select가 컨텍스트 윈도 밖과 안을 어떻게 연결하는지 설명할 수 있습니다.
이 절을 마치면 결정과 문서 조각을 외부 JSON 파일에 저장하고, 다시 읽어 메시지에 포함해야 하는 이유를 설명할 수 있습니다.
이 절을 마치면 질문에서 정한 기관·주제·날짜를 조건문으로 비교하여 필요한 자료를 선택할 수 있습니다.
이 절을 마치면 기관·주제·날짜로 자료를 선택하고, 답에 표시된 출처 식별자로 원문을 찾을 수 있습니다.
2이 내용을 배우는 이유
01절에서 컨텍스트에 사용할 수 있는 입력 가용분을 계산했습니다. 실제 업무 자료는 그 범위보다 길 수 있습니다. 모든 회의 기록과 규정을 매번 메시지에 복사하면 예산을 빠르게 사용하고, 현재 질문과 관련이 적은 문장이 답에 영향을 줄 수 있습니다. 긴 자료는 호출 밖에 보관하고, 이번 질문에 필요한 항목만 읽어 오는 절차가 필요합니다.
LangChain 팀은 컨텍스트를 다루는 여러 사례를 Write·Select·Compress·Isolate라는 네 이름으로 정리했습니다. 이 이름들은 업계가 공통으로 정한 공식 절차가 아니며, API가 이 순서대로 실행하도록 요구하지도 않습니다. 이 절에서는 그중 자료를 파일에 저장하는 Write와 필요한 자료를 골라 메시지에 넣는 Select를 다룹니다. 나머지 두 방법은 03절에서 살펴봅니다.
선택은 사람이 정한 조건문과 데이터로 수행합니다. 모델이 어떤 문서를 사용할지 판단하지 않으며, 임베딩이나 벡터스토어도 사용하지 않습니다. Ch 9에서는 사람이 정한 선택 기준의 일부를 검색으로 자동화합니다. 따라서 이 절의 기록 형식과 출처 식별자는 다음 챕터의 검색 결과를 이해하는 기초가 됩니다.
3앞에서 배운 내용
01절에서 외부 파일은 그 자체로 현재 컨텍스트가 아니라고 배웠습니다. 파일의 내용을 읽고 호출 메시지에 포함해야 모델이 참고할 수 있습니다. 또한 입력 가용분 안에서 지시, 질문, 근거를 배분했습니다. 이 절에서는 근거 전체를 넣지 않고 필요한 항목만 선택합니다.
Ch 6에서 작성한 모델 호출 코드에서 사용자 메시지를 만드는 위치를 찾습니다. Ch 7에서 지시와 근거를 나누어 배치한 방식을 다시 확인합니다. Select의 결과는 그 메시지의 근거 영역에 추가되며, 선택하지 않은 기록은 포함하지 않습니다.
4핵심 개념
비유 — 자료 보관함과 열람대
자료실에는 여러 기관의 규정과 회의 기록이 보관되어 있습니다. 질문을 처리할 때 모든 서류를 열람대에 펼치지 않습니다. 먼저 자료 목록에서 기관, 문서 종류, 적용 날짜를 확인합니다. 질문과 맞는 자료를 고른 뒤 그 문서만 열람대에 놓습니다. 보관함에 기록하는 일이 Write이고, 열람대에 놓을 자료를 고르는 일이 Select입니다. 모델은 열람대에 놓인 내용만 현재 답의 근거로 사용할 수 있습니다.
정의
Write (외부 기록)
나중에 사용할 결정, 문서 조각, 중간 결과를 현재 컨텍스트 윈도 밖의 변수나 파일에 저장하는 전략입니다. 이 절에서는 사람이 읽을 수 있는 JSON 파일을 사용합니다.
외부 저장소 (external store)
현재 모델 호출과 분리되어 정보를 보관하는 위치입니다. 파일, 데이터베이스, 객체 저장소 등이 될 수 있습니다. 저장되었다는 사실만으로 모델의 입력이나 학습 데이터가 되지는 않습니다.
Select (선택)
외부 기록 가운데 이번 질문에 필요한 항목을 골라 현재 호출 메시지로 가져오는 전략입니다. 이 절에서는 사람이 작성한 명시적 조건으로 선택합니다.
메타데이터 (metadata)
본문 옆에 항목별로 적어 두는 설명 정보입니다. 표의 열처럼 문서 식별자, 기관, 문서 종류, 적용 시작일, 상태를 따로 저장합니다. 프로그램은 이 항목을 비교하여 필요한 문서를 고릅니다.
출처 식별자 (source ID)
선택한 근거가 어느 기록에서 왔는지 추적하는 고유 값입니다. 답을 검토하거나 원문을 다시 열 때 사용합니다.
적용 조건 (applicability condition)
기록이 유효한 기관, 업무, 대상, 날짜, 버전의 범위입니다. 자료를 고를 때 이 조건을 확인하지 않으면 다른 기관이나 시점의 규정을 잘못 사용할 수 있습니다.
Write는 모델의 학습이나 자동 기억이 아닙니다
프로그램이 JSON 파일을 저장하면 다음 실행에서도 데이터를 다시 읽을 수 있습니다. 그러나 모델은 그 파일의 위치와 내용을 자동으로 알지 못합니다. 파일을 저장해도 모델 자체가 새 내용을 학습하는 것은 아니며, 제품 전체에서 자동으로 기억하는 기능이 생기지도 않습니다. 다음 호출에서 쓰려면 프로그램이 파일을 열고, 필요한 항목을 고른 뒤, 그 내용을 메시지에 넣어야 합니다.
이 구분은 디버깅에 필요합니다. 저장 파일에 올바른 값이 있는데 답이 틀렸다면 세 지점을 차례로 봅니다. 파일을 제대로 읽었는지, 올바른 항목을 선택했는지, 선택한 내용이 실제 메시지에 포함되었는지 확인합니다. “저장했으니 모델이 기억해야 한다”는 가정으로는 어느 단계가 빠졌는지 찾을 수 없습니다.
기록은 본문과 조건을 함께 보존합니다
Write 단계에서 문장만 저장하면 Select 단계가 판단할 정보가 부족합니다. 예를 들어 “매주 월요일에 운영하지 않는다”는 문장에는 어느 기관의 어느 시설인지, 언제부터 적용되는지, 현재 유효한지 나타나지 않습니다. 예를 들어 JSON 항목에 본문과 함께 출처 식별자, 기관, 문서 종류, 적용 날짜, 상태를 둘 수 있습니다. 이번 실습에서는 ID·기관·주제·적용일·본문을 기록합니다. 실제 필드 구성은 필요한 정보에 맞추되, 선택에 필요한 조건을 본문에서 분리하여 명시적으로 저장한다는 원칙을 지킵니다.
필드 역할선택에서 확인하는 내용이 정보를 기록하는 이유
출처 식별자어느 기록인가?원문 확인과 오류 추적
기관·대상질문의 대상과 같은가?다른 기관의 정보가 섞이는 것을 방지
문서 종류규정, 안내, 회의 기록 중 무엇인가?근거의 성격을 구분
적용 날짜·상태질문의 시점에 유효한가?폐기된 규정이나 아직 시행되지 않은 규정을 잘못 사용하는 일을 방지
본문질문에 답하는 사실이 있는가?답의 직접 근거
Select는 질문과 메타데이터를 함께 봅니다
이 절에서는 질문에 필요한 기관·주제·기준 날짜를 사람이 코드에 적습니다. 조건문은 기관과 주제가 맞고, 적용 시작일이 기준 날짜보다 늦지 않은 기록을 고릅니다. 출력된 ID와 본문을 읽어 대출·주차 기록이 선택되고 휴관 기록은 빠졌는지 확인합니다. 같은 규정의 여러 버전 중 최신 것을 고르거나 적용 종료일을 확인하는 기능은 이번 코드에 포함하지 않습니다.
이번 실습에서는 기관·주제·날짜를 자료 선택에 사용합니다. 선택을 마친 뒤에는 본문과 출처 식별자를 메시지에 넣고, 모델에게 답에도 그 식별자를 표시하도록 요청합니다. 답의 [E01-p3]를 저장된 기록의 ID와 비교하면 어떤 자료를 사용했는지 확인할 수 있습니다. 기관과 날짜를 답에 표시하는 기능은 이번 코드에 포함하지 않습니다.
점진적으로 필요한 내용만 엽니다
자료가 많을 때는 처음부터 모든 본문을 읽지 않아도 됩니다. 첫 단계에서는 식별자, 제목, 기관, 적용 날짜처럼 짧은 목록을 봅니다. 두 번째 단계에서 질문과 맞는 항목을 고릅니다. 세 번째 단계에서 선택한 항목의 본문만 읽습니다. 이를 점진적 공개(progressive disclosure)라고 합니다. 처음에는 얕은 정보를 보고, 필요한 경우에만 상세 내용을 여는 방식입니다.
점진적 공개가 언제나 더 빠르거나 더 적은 토큰을 보장하지는 않습니다. 목록의 메타데이터가 부정확하거나 선택 조건이 부족하면 필요한 문서를 놓칠 수 있습니다. 이 절에서는 사람이 후보와 원문을 확인하여 이 한계를 관찰합니다. Ch 9에서 검색이 선택을 자동화한 뒤에도 출처와 조건을 검토해야 하는 이유가 여기에 있습니다.
도식 — 저장된 자료가 현재 메시지로 들어오는 경로
Write는 결정과 문서 조각을 외부 JSON에 보존합니다. Select는 질문과 메타데이터를 비교해 항목을 고르고, 선택한 본문과 출처 식별자를 현재 메시지에 넣습니다.
파일의 기록이 질문의 근거가 되는 과정
json.dumps(records)는 Python 목록을 저장 가능한 JSON 문자열로 변환합니다. write_text()가 그 문자열을 파일에 쓰고, read_text()가 다시 문자열로 읽습니다. json.loads()가 목록으로 복원한 뒤에야 각 기록의 키를 이용해 조건을 검사합니다. 저장, 읽기, 선택, 메시지 조립은 각각 별도 단계입니다.
선택 코드에서 topics는 필요한 주제를 모은 집합입니다. row["topic"] in criteria["topics"]는 한 기록의 주제가 그 집합에 있는지 검사합니다. 기관 일치, 주제 포함, 적용 시작일 조건을 and로 연결하므로 세 조건이 모두 참인 기록만 선택됩니다. selected_ids에는 중복 없는 식별자를 모으고, 두 번째 반복문은 원래 기록 순서대로 본문을 가져옵니다.
같은 상품의 2025년 설명서와 2026년 설명서를 함께 저장한 상황을 생각해 봅니다. 두 설명서의 적용 시작일이 질문 날짜보다 빠르면 이번 조건은 둘 다 선택할 수 있습니다. 가장 최근 버전 하나를 고르는 규칙은 별도로 필요합니다. 기관과 주제가 맞는다는 사실만으로 최신 문서를 선택했다고 결론 내리지 않는 이유입니다.
5실행 예제
effective_date는 날짜 필터를 관찰하기 위한 합성 메타데이터이며, PDF의 발행일이나 실제 규정 시행일을 뜻하지 않습니다.
짧은 기록 세 개를 JSON으로 저장하고 다시 읽습니다. 그다음 질문에서 정한 기관·주제·날짜와 각 기록의 같은 항목을 비교하여 필요한 문서 ID를 고릅니다. 선택 결과만 실제 API 입력에 포함되므로 Write와 Select의 차이를 한 셀씩 확인할 수 있습니다.
확인할 점 — 실습 파일은 labs/part2/ch08-context-engineering/notebooks/02-Write와-Select.ipynb입니다. 저장할 목록, 출력된 임시 파일 이름, 다시 읽은 목록, 선택 결과를 차례로 확인합니다. 기본 선택에서 주차 ID 한 개를 제외했을 때 기록 수와 주제가 어떻게 달라지는지 비교합니다.
6일부러 실패해 보기
Before에서는 파일을 저장해 놓고도 근거를 메시지에 넣지 않습니다. After에서는 앞에서 선택한 대출·주차 기록을 넣습니다. 질문과 답변 규칙을 같게 두고 실제 모델의 답을 비교합니다. 근거가 없어 답하지 못하는 것은 이 실습에서 모델이 잘못한 일이 아닙니다. 자료를 저장하고도 호출에 전달하지 않은 프로그램의 누락을 관찰합니다.
7주의할 점과 실무 메모
JSON 저장은 보안 저장을 뜻하지 않습니다. 개인 정보와 비밀 값은 평문 예제 파일에 넣지 않습니다. 실제 서비스에서는 접근 권한, 암호화, 보존 기간을 별도로 설계합니다.
저장과 컨텍스트 포함을 구분합니다. 파일에 있는 데이터는 프로그램이 읽어 메시지로 전달하기 전까지 현재 모델 호출의 입력이 아닙니다.
출처 식별자를 변형하지 않습니다. 요약이나 답을 만들 때도 원래 식별자를 유지해야 원문을 다시 확인할 수 있습니다.
날짜 형식을 맞춘 뒤 비교합니다. 이 실습의 날짜는 모두 YYYY-MM-DD 형식이므로 문자열 순서와 날짜 순서가 같습니다. 이 합성 필드에서 effective_date <= as_of는 실습용 적용 시작일 당일부터 자료를 선택합니다. 서로 다른 날짜 형식을 받는 프로그램에서는 먼저 날짜 값으로 변환해야 합니다. 종료일이나 이전 버전의 폐기 여부를 판단하는 규칙은 추가로 작성해야 합니다.
Select의 누락 가능성을 기록합니다. 사람이 정한 규칙이 모든 표현을 포괄하지 못할 수 있습니다. 후보가 없으면 근거 없이 답을 만들기보다 선택 실패로 처리합니다.
8정리와 다음 절
Write는 정보를 컨텍스트 윈도 밖에 저장하며, 저장 자체는 모델 학습이나 자동 기억이 아닙니다.
Select는 질문과 메타데이터를 비교하여 필요한 기록을 고르고 현재 메시지로 가져옵니다.
기관·주제·날짜는 선택 조건으로 사용하고, 본문과 출처 식별자는 모델에 전달하여 답의 근거를 확인합니다.
다음 학습과 이어지는 지점 — 03절에서는 선택한 기록이나 긴 대화가 여전히 예산보다 클 때 Compress로 줄이고, 서로 다른 업무 자료는 Isolate로 분리합니다. Ch 9에서는 이 절의 사람 선택을 검색이 수행하며, 출처 식별자와 메타데이터가 검색 결과를 검토하는 기준으로 이어집니다.
9복습 문제
문제 4개 · 해설 포함
[하] 1. JSON 파일에 기록한 사실을 모델이 다음 호출에서 사용하려면 반드시 어떤 단계가 필요합니까?
정답과 해설 — 프로그램이 파일을 읽고, 필요한 항목을 선택하여, 그 내용을 호출 메시지에 포함해야 합니다. 틀렸다면 이 절의 핵심 개념 ‘Write는 모델의 학습이나 자동 기억이 아닙니다’를 다시 봅니다.
[중] 2. 본문과 함께 출처 식별자와 적용 날짜를 저장해야 하는 이유를 각각 설명하세요.
정답과 해설 — 출처 식별자는 답의 근거가 된 원문을 다시 찾아 오류를 추적하게 합니다. 적용 날짜는 질문 시점에 유효한 기록인지 판단하게 합니다. 틀렸다면 이 절의 핵심 개념 ‘기록은 본문과 조건을 함께 보존합니다’를 다시 봅니다.
[중] 3. 문서 본문 전체를 처음부터 읽는 방식과 점진적 공개 방식의 차이를 세 단계로 설명하세요.
정답과 해설 — 점진적 공개는 먼저 식별자와 메타데이터 목록을 보고, 질문과 맞는 항목을 고른 뒤, 선택한 본문만 읽습니다. 모든 본문을 처음부터 현재 메시지에 넣지 않습니다. 틀렸다면 이 절의 핵심 개념 ‘점진적으로 필요한 내용만 엽니다’를 다시 봅니다.
[상·확장] 4. 같은 기관의 이전 규정과 현재 규정이 있을 때, 안전한 Select 규칙과 답의 출력 형식을 설계하세요.
정답과 해설 — 질문의 기준 날짜를 확인하고, 기관이 같으며 그 날짜에 유효한 기록을 선택합니다. 선택한 본문과 함께 출처 식별자·적용 기간을 메시지에 넣고, 답에는 사용한 출처 식별자를 표시합니다. 기준 날짜가 없으면 임의로 고르지 않고 추가 조건이 필요함을 표시합니다. 틀렸다면 이 절의 핵심 개념 ‘Select는 질문과 메타데이터를 함께 봅니다’를 다시 봅니다.

1학습 목표
이 절을 마치면 Compress는 한 기록을 줄이고 Isolate는 업무별로 자료를 나누는 방법임을 설명할 수 있습니다.
이 절을 마치면 긴 기록을 줄일 때 결정·예외·날짜·기관·출처를 보존하는 수동 압축 규칙을 적용할 수 있습니다.
이 절을 마치면 서로 다른 업무에 필요한 자료만 독립 메시지로 구성하고, 분리 전후를 비교할 수 있습니다.
이 절을 마치면 텍스트 태그에 의한 구분과 보안 격리를 구별하고, 고정 함수 분리가 에이전트가 아닌 이유를 설명할 수 있습니다.
2이 내용을 배우는 이유
02절에서는 긴 자료를 외부 JSON 파일에 기록하고, 질문에 필요한 항목을 선택하여 현재 메시지로 가져왔습니다. 선택한 기록도 여전히 길 수 있습니다. 여러 번 이어진 대화에는 이미 끝난 논의와 반복된 설명이 남습니다. 또한 한 프로그램이 고객 문의와 코드 검토처럼 서로 다른 업무를 처리하면 각 업무의 자료가 한 메시지에 섞일 수 있습니다.
압축(Compress)은 현재 질문에 필요한 사실을 남기고 반복 표현을 줄입니다. 분리(Isolate)는 대출 문의와 휴관 문의처럼 서로 다른 업무의 자료를 나누어, 각 호출에 필요한 묶음만 전달합니다. 두 방법 모두 입력을 줄일 수 있지만 하는 일은 다릅니다. Compress는 한 기록을 짧게 만들고, Isolate는 한 업무의 자료가 다른 업무 메시지에 섞이지 않게 합니다.
이 절에서는 사람이 보존할 항목을 먼저 정한 뒤 요약을 쓰고 원문과 대조합니다. 업무 분리도 사람이 작성한 함수와 메시지 목록으로 수행합니다. 모델이 할 일을 나누거나 다른 모델을 호출하지 않으므로 에이전트나 다중 에이전트 구조가 아닙니다. 모델이 다음 행동을 판단하고 도구를 호출하는 구조는 Ch 20 이후에 배웁니다.
3앞에서 배운 내용
01절에서는 전체 예산에서 출력 예약분과 여유분을 제외하여 입력 가용분을 정했습니다. 02절에서는 외부 기록의 메타데이터를 보고 필요한 항목만 메시지에 포함했습니다. 이 절은 Select 이후에도 자료가 길거나, 서로 다른 업무 자료가 한 묶음에 남아 있는 경우를 다룹니다.
Ch 6에서 되짚을 내용은 하나의 모델 호출이 명시적으로 전달된 메시지를 처리한다는 사실입니다. Ch 7에서 되짚을 내용은 지시와 근거의 경계를 읽을 수 있게 메시지를 구성했다는 점입니다. 이 절에서는 같은 원리를 업무별 메시지에 각각 적용합니다.
4핵심 개념
비유 — 회의록 요약과 업무별 서류철
긴 회의록을 다음 회의에 그대로 가져가면 결정 사항을 찾는 데 시간이 걸립니다. 결정, 예외, 적용 날짜, 담당 기관, 원문 위치를 한 장에 정리하면 필요한 사실을 빠르게 확인할 수 있습니다. 이것이 Compress에 해당합니다. 한편 인사 문의와 시스템 장애 보고서를 같은 서류철에 넣으면 관련 없는 정보가 판단에 영향을 줄 수 있습니다. 업무별 서류철을 만들고 각 업무에 필요한 문서만 넣는 것이 Isolate에 해당합니다.
정의
Compress (압축)
현재 과업에 필요한 사실을 유지하면서 긴 대화나 문서의 표현을 줄이는 전략입니다. 요약은 원문의 모든 정보를 보존하지 않으므로 원문과 대조할 수 있어야 합니다.
수동 압축 (manual compression)
사람이 보존 항목과 삭제 기준을 먼저 정하고 그 규칙에 따라 요약을 만드는 방식입니다. 이 절에서는 모델에게 자동 요약을 맡기지 않습니다.
정보 손실 (information loss)
압축 과정에서 원문의 사실, 조건, 예외, 관계가 사라지거나 의미가 바뀌는 현상입니다. 짧아진 문장이 자연스럽더라도 중요한 조건이 없어졌다면 잘못된 압축입니다.
Isolate (분리)
서로 다른 작업이나 자료 묶음이 영향을 주지 않도록 컨텍스트를 나누는 전략입니다. 이 절에서는 업무별로 독립된 메시지 목록을 구성합니다.
독립 메시지 (independent message set)
대출 문의라면 대출 지시·질문·근거만 넣는 식으로, 한 업무의 자료만 담아 따로 만든 메시지 목록입니다. 다른 업무의 기록이 필요하면 프로그램 코드가 그 기록을 골라 추가해야 합니다.
경계 (boundary)
어느 자료를 어느 업무 메시지에 넣을지 정하는 규칙입니다. 텍스트 구분선은 사람이 읽기 좋게 나눌 뿐입니다. 사용 권한을 검사하거나 데이터 접근을 막지는 못합니다.
압축에서 반드시 보존할 항목을 먼저 정합니다
압축을 “짧게 다시 쓰기”로만 이해하면 중요한 조건이 사라집니다. 먼저 보존 항목을 정한 뒤 각 항목이 요약에 남았는지 검사해야 합니다. 이 절에서는 결정, 예외, 날짜, 기관, 출처 식별자를 최소 보존 항목으로 사용합니다. 과업에 따라 금액, 단위, 승인자, 버전이 추가될 수 있습니다.
보존 항목삭제될 때 생기는 문제검사 질문
결정무엇을 해야 하는지 알 수 없음최종 결정이 분명한가?
예외일반 규칙을 모든 경우에 잘못 적용규칙이 적용되지 않는 조건이 남았는가?
날짜이전 값과 현재 값을 구분하지 못함결정일과 적용일이 구분되는가?
기관·대상다른 조직이나 대상에 잘못 적용누구에게 적용되는지 분명한가?
출처 식별자원문을 다시 찾아 검증할 수 없음각 핵심 사실을 원문과 연결할 수 있는가?
압축본에는 수동으로 압축한 기록임을 명시합니다. 이 표시는 압축본이 원문과 동일한 문서가 아니며, 누락 가능성을 검토해야 한다는 신호가 됩니다. 원문 식별자도 함께 보존합니다. 중요한 판단을 내릴 때는 압축본만 읽고 끝내지 않고 해당 출처의 원문을 다시 확인할 수 있어야 합니다.
압축 품질은 길이가 아니라 의미 보존으로 확인합니다
압축률이 높다고 좋은 결과가 되는 것은 아닙니다. 핵심 결정 한 줄만 남기고 예외와 적용 날짜를 삭제하면 문장은 짧지만 잘못된 행동을 유도합니다. 반대로 반복 표현을 제거하고 같은 뜻의 문장을 합치면서 조건과 출처를 유지했다면 길이가 조금 길어도 목적에 맞는 압축입니다.
검토는 원문과 압축본을 나란히 놓고 수행합니다. 압축본의 각 주장에 대응하는 원문 위치를 찾습니다. 원문에는 있으나 압축본에서 빠진 예외와 날짜를 찾습니다. 압축본에 원문보다 강한 표현이 추가되지 않았는지도 확인합니다. 예를 들어 “검토를 권장한다”를 “반드시 승인한다”로 바꾸면 요약이 아니라 의미 변경입니다.
Isolate는 업무마다 필요한 자료만 전달합니다
한 프로그램이 두 업무를 순서대로 처리한다고 가정합니다. 고객 문의 메시지에는 고객 정책과 문의 내용이 필요합니다. 코드 검토 메시지에는 코드, 검토 기준, 변경 요구가 필요합니다. 두 자료 묶음을 하나의 긴 메시지에 함께 넣으면 모델은 관련 없는 기관명이나 지시를 답에 반영할 수 있습니다.
Isolate에서는 업무별 입력을 처음부터 별도로 구성합니다. 고객 문의 함수는 고객 문의 자료만 받아 메시지를 만들고, 코드 검토 함수는 코드 검토 자료만 받아 다른 메시지를 만듭니다. 두 함수의 호출 순서는 프로그램에 고정되어 있습니다. 함수가 독립되어 있어도 모델이 실행 순서나 도구 사용을 결정하지 않으므로 에이전트라고 부르지 않습니다.
텍스트 태그는 보안 격리가 아닙니다
메시지 안에 <customer>와 <code_review> 같은 태그를 붙이면 제목표처럼 자료의 종류를 표시할 수 있습니다. 그러나 두 자료는 여전히 같은 호출 입력에 들어가므로 모델이 모두 읽을 수 있습니다. 태그는 한쪽 자료를 읽지 못하게 막는 장치가 아닙니다. 민감한 자료를 보호하려면 프로그램이 사용 권한을 검사하고, 자료를 별도 저장소와 별도 호출로 나누며, 로그에 남길 항목도 제한해야 합니다. 이런 실제 접근 제한을 보안 격리라고 합니다.
따라서 이 절에서 “분리했다”는 말은 독립된 메시지 목록을 구성했다는 뜻입니다. 같은 메시지에 태그만 붙인 상태를 보안 격리라고 설명하지 않습니다. 태그를 사용하더라도 프로그램이 각 업무에 필요하지 않은 자료를 호출 전에 제외해야 합니다.
도식 — 줄이는 일과 나누는 일
Compress는 한 자료 묶음에서 결정·예외·날짜·기관·출처를 남기고 반복 표현을 줄입니다. Isolate는 도서관 대출 질문과 휴관 질문의 메시지를 각각 구성하여 필요한 자료만 전달합니다.
요약할 내용을 고르는 판단과 문자열 조립
이 실습의 compress(record)는 긴 원문을 읽어 요약을 생성하는 함수가 아닙니다. 사람이 미리 고른 사실·조건·예외·출처를 담은 딕셔너리를 받아 네 항목을 한 문자열로 연결합니다. loan_original에서 무엇을 남길지는 loan 딕셔너리를 작성한 사람이 결정했습니다. 함수 이름에 압축이라는 말이 있어도 모델 요약 호출이 추가되는 것은 아닙니다.
set(required) - record.keys()는 필요한 키 중 입력에 없는 키를 구합니다. 빈 집합이면 네 키가 있다는 뜻입니다. 값이 빈 문자열인지, 원문을 정확히 옮겼는지까지 검사하지는 않습니다. 아래에서는 문자열 길이와 특정 조건의 포함 여부를 함께 보지만, 의미가 보존되었는지는 원문과 네 항목을 대조해서 확인합니다.
회의 기록의 “금요일 배포, 단 검토가 완료된 경우”를 “금요일 배포”로 줄이면 조건부 계획을 확정 일정처럼 바꾸게 됩니다. 도서관 연장 규정에서 예약 조건을 지우는 문제와 같은 원리입니다. 업무별 입력 목록을 나누어도 요약 자체의 오류는 남을 수 있으므로, 자료 분리와 의미 보존을 각각 확인해야 합니다.
5실행 예제
반복 설명이 있는 원문에서 사실·조건·예외·출처를 남긴 한 줄 기록을 만들고, 두 문자열의 길이를 비교합니다. 이어서 대출 근거와 휴관 근거를 함께 놓아 분리 전 상태를 확인합니다. 그다음 대출과 휴관 근거를 별도 메시지로 구성하고, 서로의 출처가 섞이지 않았는지 검사한 뒤 두 메시지를 각각 실제 API에 전달합니다.
확인할 점 — 실습 파일은 labs/part2/ch08-context-engineering/notebooks/03-Compress와-Isolate.ipynb입니다. 원본의 네 필드, 혼합 근거, 대출·휴관 메시지 두 묶음, 실제 응답을 순서대로 확인합니다. 기본 압축과 condition 값 하나를 바꾼 압축도 비교합니다.
6일부러 실패해 보기
왼쪽에서는 같은 원문을 줄이면서 “예약이 없으면”이라는 조건을 빼고, 조건이 실제로 사라졌음을 출력합니다. 오른쪽에서는 원문의 연장 문장을 다시 사용하여 조건을 포함한 요약을 만들고, 해당 문구가 보존되었는지 확인합니다.
7주의할 점과 실무 메모
압축본을 원문으로 취급하지 않습니다. 수동 압축 표시, 생성 날짜, 원문 출처 식별자를 함께 남깁니다.
수치와 단위를 함께 보존합니다. 금액, 기간, 비율을 남기면서 단위를 삭제하면 의미가 달라질 수 있습니다.
날짜의 역할을 구분합니다. 문서 작성일, 결정일, 적용 시작일, 종료일은 서로 다른 값입니다. 압축 과정에서 하나의 ‘날짜’로 합치지 않습니다.
태그를 접근 제어로 사용하지 않습니다. 같은 호출에 포함된 정보는 모델 입력에 전달됩니다. 민감한 정보는 애플리케이션에서 호출 전에 제외합니다.
분리된 함수가 자동으로 에이전트가 되지는 않습니다. 사람이 정한 순서대로 고정 함수가 실행되고 모델이 흐름을 바꾸지 않는다면 일반 프로그램 흐름입니다.
압축과 선택의 순서는 자료에 따라 정합니다. 오래된 대화 기록을 먼저 압축한 뒤 필요한 결정을 선택할 수 있고, 여러 문서 중 필요한 문서를 먼저 선택한 뒤 그 문서만 압축할 수도 있습니다. 어느 순서를 사용했는지 실행 기록에 남깁니다.
8정리와 다음 절
Compress는 표현을 줄이되 결정·예외·날짜·기관·출처를 보존하며, 압축본임을 명시합니다.
Isolate는 서로 다른 업무마다 독립 메시지를 구성하여 필요한 자료만 전달합니다.
텍스트 태그는 보안 격리가 아니며, 고정 함수의 분리는 에이전트 판단을 뜻하지 않습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 컨텍스트가 잘못된 정보, 과도한 자료, 관련 없는 자료, 서로 맞지 않는 정보 때문에 답에 어떤 문제가 생기는지 비교합니다. Ch 9에서는 Select를 자동 검색으로 확장하지만, 검색 결과가 길면 Compress가 필요하고 서로 다른 질문을 처리할 때는 Isolate로 자료 묶음을 나눕니다.
9복습 문제
문제 4개 · 해설 포함
[하] 1. Compress와 Isolate의 목적을 각각 한 문장으로 쓰세요.
정답과 해설 — Compress는 한 자료 묶음에서 과업에 필요한 사실을 남기며 표현을 줄입니다. Isolate는 서로 다른 작업의 자료 묶음을 나누어 각 호출에 필요한 자료만 전달합니다. 틀렸다면 이 절의 핵심 개념 ‘정의’를 다시 봅니다.
[중] 2. 규정 요약에서 결정만 남기고 예외와 적용 날짜를 삭제했을 때 생길 수 있는 오류를 설명하세요.
정답과 해설 — 일반 규칙을 예외 대상에 잘못 적용하거나, 이전 결정을 현재 규정으로 잘못 사용할 수 있습니다. 압축 전 보존 항목을 정하고 원문과 대조해야 합니다. 틀렸다면 이 절의 핵심 개념 ‘압축에서 반드시 보존할 항목을 먼저 정합니다’를 다시 봅니다.
[중] 3. 한 메시지 안에서 두 자료를 텍스트 태그로 나누었는데도 보안 격리라고 할 수 없는 이유는 무엇입니까?
정답과 해설 — 두 자료가 같은 호출 입력에 포함되어 모델에 함께 전달되기 때문입니다. 태그는 구조를 표시하지만 접근 권한을 강제하지 않습니다. 틀렸다면 이 절의 핵심 개념 ‘텍스트 태그는 보안 격리가 아닙니다’를 다시 봅니다.
[상] 4. 도서관 대출 질문과 휴관 질문을 처리하는 고정 프로그램을 설계할 때, 분리 규칙과 에이전트가 아닌 이유를 함께 설명하세요.
정답과 해설 — 대출 질문 호출에는 대출 규정·질문·해당 출처만 넣고, 휴관 질문 호출에는 휴관 안내·질문·해당 출처만 넣습니다. 두 메시지 목록을 분리하고 호출 전에 허용 자료를 검사합니다. 실행 순서와 자료 선택을 사람이 코드에 고정하며 모델이 흐름이나 도구 사용을 결정하지 않으므로 에이전트가 아닙니다. 틀렸다면 이 절의 핵심 개념 ‘Isolate는 업무마다 필요한 자료만 전달합니다’를 다시 봅니다.

1학습 목표
이 절을 마치면 잘못된 정보, 무관한 정보, 비슷한 대상, 서로 맞지 않는 규정이 답에 어떤 오류를 만들 수 있는지 설명할 수 있습니다.
이 절을 마치면 하나의 오답에 두 가지 이상의 문제가 함께 나타날 수 있음을 사례에서 확인할 수 있습니다.
이 절을 마치면 실패를 유도하는 입력을 구성한 일과 실제 출력에서 실패를 확인한 일을 구분하여 기록할 수 있습니다.
이 절을 마치면 오답만 보고 원인을 단정하지 않고, 어떤 입력에서 어떤 답이 나왔는지 표로 기록할 수 있습니다.
2이 내용을 배우는 이유
앞 절에서는 컨텍스트를 구성하는 원칙을 배웠습니다. 필요한 정보를 외부 파일에 기록하고(Write), 현재 질문에 맞는 정보를 고르고(Select), 긴 내용을 줄이고(Compress), 서로 다른 작업을 분리합니다(Isolate). 이제 반대 방향에서 살펴볼 차례입니다. 어떤 정보를 넣었을 때 답이 틀리는지 살펴보면, 앞에서 배운 네 방법을 언제 쓸지 판단할 수 있습니다.
Poisoning, Distraction, Confusion, Clash는 업계가 공통으로 정한 공식 오류 이름이 아닙니다. LangChain 팀이 Drew Breunig의 글을 인용하여 여러 실패 사례를 설명할 때 소개한 이름입니다. 네 이름 중 하나만 골라야 하는 것도 아닙니다. 예를 들어 긴 회의록 때문에 중요한 문장을 놓치면서, 이름이 비슷한 다른 기관의 규정까지 답에 섞일 수 있습니다. 이때는 Distraction과 Confusion을 함께 기록합니다. 다만 이름을 붙였다고 해서 모델이 왜 그런 답을 했는지까지 알 수 있는 것은 아닙니다. 입력과 실제 답을 함께 살펴봐야 합니다.
이 구분은 다음 학습의 준비이기도 합니다. Ch 9에서는 Select를 검색으로 자동화합니다. 검색이 관련 없는 문서를 가져오면 Distraction이나 Confusion이 나타날 수 있습니다. Ch 19에서는 모델이 읽는 도구 설명이 서로 비슷할 때 Confusion을 다시 다룹니다. 지금은 에이전트와 검색을 사용하지 않고, 고정된 파이썬 코드로 기준 입력과 네 실패 조건을 구성하여 결과를 비교합니다.
3앞에서 배운 내용
Write — 다음 호출에 쓸 결정과 사실을 외부 파일에 기록합니다. 잘못된 정보까지 기록하면 이후 호출에서 반복 사용될 수 있습니다.
Select — 현재 질문과 관련된 문서 조각만 고릅니다. 관련 없는 조각이나 다른 기관의 문서를 고르면 답의 근거가 흐려집니다.
Compress — 긴 내용을 줄이면서 결정, 수치, 출처를 남깁니다. 요약 과정에서 조건이 빠지면 원문과 다른 주장처럼 사용될 수 있습니다.
Isolate — 목적이 다른 자료 묶음을 분리합니다. 고객 문의 자료와 내부 코드 검토 자료를 한 입력에 섞지 않는 것이 이 장의 범위입니다.
앞 절에서 사용한 컨텍스트 조립 방식도 다시 사용합니다. 시스템 지시, 질문, 선택한 문서 조각을 일정한 순서로 문자열에 배치합니다. 달라지는 것은 문서 조각의 구성뿐입니다. 모델, 질문, 시스템 지시는 고정해야 어느 입력 차이가 결과에 영향을 주었는지 비교할 수 있습니다.
4핵심 개념
비유 — 여러 사람이 함께 쓰는 인수인계 노트
고객지원팀이 한 권의 인수인계 노트를 사용한다고 가정합니다. 첫 담당자가 휴관일을 잘못 적으면 다음 담당자도 그 기록을 사실로 사용합니다. 이것이 Poisoning과 닮았습니다. 질문과 무관한 회의 기록이 수십 쪽 붙어 있으면 필요한 한 줄을 찾기 어려워집니다. 이것은 Distraction에 해당합니다. 이름이 비슷한 두 기관의 안내문이 섞이면 다른 기관의 규정을 현재 기관의 규정으로 잘못 적용할 수 있습니다. 이것은 Confusion입니다. 같은 기관의 구 규정과 신 규정이 날짜 표시 없이 함께 있으면 어느 문장을 따라야 할지 판단하기 어렵습니다. 이것은 Clash입니다.
인수인계 노트의 사례처럼 한 사례에 여러 문제가 겹칠 수 있습니다. 잘못 저장된 정보가 다른 기관의 문서에서 왔다면 Poisoning과 Confusion을 함께 확인합니다. 오래된 규정을 잘못 요약해 다음 호출에서 다시 썼다면 Poisoning과 Clash를 함께 확인합니다. 아래 표에서는 이름 하나를 고르지 말고, 해당하는 질문을 모두 확인합니다.
정의
컨텍스트 오염 (context poisoning)
이전 답이나 저장한 메모에 틀린 내용이 들어 있고, 그 내용을 다음 질문에 다시 넣어 사실처럼 사용하는 문제입니다. 공격자가 정보를 바꾼 경우에만 쓰는 말이 아닙니다. 모델이 지어낸 내용, 사람이 잘못 입력한 값, 오래된 요약도 원인이 될 수 있습니다.
컨텍스트 산만화 (context distraction)
현재 질문과 관계없는 내용이 많이 들어가서 모델이 중요한 지시나 근거를 놓치는 문제입니다. 문장 자체가 모두 사실이어도 이번 질문에 필요하지 않으면 답을 방해할 수 있습니다.
컨텍스트 혼동 (context confusion)
이름이나 설명이 비슷한 두 대상이 함께 들어가서, 모델이 다른 대상을 고르거나 두 대상의 내용을 섞는 문제입니다. 예를 들어 미르시립도서관 질문에 미르시립자료관 규정이 섞일 수 있습니다.
컨텍스트 충돌 (context clash)
입력 안에 서로 맞지 않는 지시나 사실이 있는데, 어느 출처가 최신인지 또는 무엇을 먼저 따라야 하는지 표시되지 않은 문제입니다. 예를 들어 같은 휴관일이 월요일과 화요일로 함께 적혀 있는 경우입니다.
출력에서 확인한 증거 (observational evidence)
모델의 실제 답에서 잘못된 요일, 다른 기관명, 서로 맞지 않는 문장처럼 직접 확인한 내용입니다. 실패가 나도록 입력을 만들었다는 사실만으로는 모델이 실제로 실패했다고 말할 수 없습니다.
도식 — 입력에서 진단까지
같은 질문에 서로 다른 컨텍스트를 제공한 뒤 실제 답에서 어떤 문제가 생겼는지 확인합니다. 한 답에 여러 문제가 겹칠 수 있으므로 해당하는 질문을 모두 확인합니다.보는 순서 — ① 왼쪽의 네 입력 변화 → ② 오른쪽의 진단 기록 → ③ 출력과 입력을 함께 확인하는 질문.

문제 이름입력에서 확인할 것출력에서 확인할 것먼저 할 일
Poisoning이전 출력이나 메모의 잘못된 주장이 다시 들어갔는가같은 잘못이 후속 답에서 사실처럼 반복되는가어디에서 가져왔는지와 사실을 확인했는지 따로 적습니다.
Distraction질문과 무관한 긴 내용이 추가되었는가핵심 근거를 놓치거나 무관한 내용을 길게 답하는가현재 과제에 필요한 조각만 선택합니다.
Confusion이름이나 설명이 비슷한 다른 대상이 함께 있는가기관명, 제품명, 규정을 다른 대상과 섞는가기관 ID와 출처를 적고 서로 다른 기관의 자료를 나눕니다.
Clash서로 다른 지시나 사실이 함께 있는가한쪽을 임의로 고르거나 모순된 내용을 동시에 답하는가시점, 출처, 우선순위 규칙을 추가합니다.
Distraction과 Confusion의 차이는 정보량만으로 결정되지 않습니다. 무관한 회의록이 길어서 핵심 문장을 찾기 어려워졌다면 Distraction을 의심합니다. 다른 기관의 규정이 짧더라도 현재 기관의 규정처럼 답에 사용되었다면 Confusion을 확인합니다. Clash도 단순히 숫자가 두 개 있다는 뜻이 아닙니다. 서로 다른 조건에 적용되는 두 값이라면 충돌이 아닐 수 있습니다. 적용 조건이 같은데 값이 다르거나, 우선순위가 필요한데 표시가 없을 때 충돌로 진단합니다.
비교 조건 이름과 실제 실패를 구분하기
conditions의 키인 poisoning이나 clash는 개발자가 입력에 붙인 이름입니다. conditions.items()로 이름과 내용을 하나씩 읽어 같은 질문에 넣고, 반환된 AIMessage를 results[name]에 저장합니다. 딕셔너리의 키가 오류 진단 결과를 자동으로 만드는 것은 아닙니다. 실제 답이 잘못된 문장을 사용했는지 별도로 읽어야 합니다.
예를 들어 배송 안내에 “일반 배송은 3일, 도서 지역은 5일”이 있으면 숫자가 달라도 적용 지역이 달라 충돌하지 않습니다. 같은 지역·같은 배송 조건에 3일과 5일이 동시에 적혀 있고 시행일도 없다면 충돌 여부를 확인해야 합니다. 값의 차이를 발견한 뒤 대상과 조건이 같은지 확인하는 순서가 중요합니다.
뒤의 날짜 선택은 모든 규정에 통용되는 해결책이 아닙니다. 같은 업무의 새 규정이 이전 규정을 대체한다는 실습 가정 아래, 기준일 전에 시행된 후보에서 가장 늦은 날짜를 고릅니다. max(eligible, key=effective_date)에서 key는 비교할 값을 꺼내는 함수입니다. 후보가 비어 있으면 max()가 값을 고를 수 없으므로 실제 서비스에서는 후보 없음도 별도로 처리해야 합니다.
5실행 예제
기준 입력을 유지하면서 잘못된 메모, 무관한 정보, 비슷한 기관의 규정, 서로 맞지 않는 규정을 하나씩 추가합니다. 다섯 조건을 같은 질문으로 실제 호출하고, 조건별 입력 토큰과 응답 원문을 비교합니다. 실패가 발생할 것이라고 미리 단정하지 않고 출력에서 관찰한 요일과 추가 확인 표현을 기록합니다.
확인할 점 — 실습 파일은 labs/part2/ch08-context-engineering/notebooks/04-네-가지-실패-모드.ipynb입니다. 기준 근거를 먼저 실행한 뒤 혼동 요소 한 가지씩 추가한 입력과 실제 응답을 비교합니다. API 응답은 실행마다 달라질 수 있으므로 출력 원문을 직접 읽습니다.
6일부러 실패해 보기
Before에서는 월요일 하루만 휴관한다는 규정과 화요일 하루만 휴관한다는 규정을 같은 질문과 함께 모델에 전달합니다. 시행일이 없어 확인이 필요하다는 답이 나오면, 모델이 잘못 선택한 것은 아니지만 현재 자료로 답을 확정할 수는 없습니다. After에서는 시행일을 확인했다는 실습 상황을 추가합니다. 같은 업무의 새 규정이 이전 규정을 대체한다고 가정하고 최신 규정을 선택한 뒤, 같은 질문으로 다시 호출합니다. 날짜를 임의로 추측하여 충돌을 해결하는 방법으로 이해하지 않도록 주의합니다.
7주의할 점과 실무 메모
네 이름만으로 모든 오답을 설명하지 않습니다. 이 이름들은 팀에서 문제를 확인할 때 쓰는 질문에 가깝습니다. 검색이 잘못된 문서를 가져왔는지, 지시가 부족했는지, 모델이 해당 내용을 학습하지 않았는지, 최신 자료가 빠졌는지도 따로 확인합니다.
Poisoning은 공격만을 뜻하지 않습니다. 사람이 잘못 입력한 수치, 오래된 회의 요약, 모델이 만든 환각을 검증 없이 저장한 경우도 포함합니다. 보안 공격은 Ch 16에서 별도로 다룹니다.
한 번 정확히 답했다고 같은 문제가 다시 생기지 않는다고 결론 내리지 않습니다. 모델이 이번 한 번은 문제 문장의 영향을 받지 않았을 수 있습니다. 같은 조건을 반복하거나 입력 순서와 질문을 바꾸어 다시 확인하고, 실제로 확인한 범위까지만 기록합니다.
Confusion과 Clash는 출처 메타데이터로 줄일 수 있습니다. 기관 ID, 문서 버전, 시행일, 적용 대상을 입력에 표시하면 구분에 도움이 됩니다. 표시했다고 해서 모델이 언제나 올바르게 따른다는 보장은 없습니다.
프롬프트에는 개인정보나 비공개 기록을 넣지 않습니다. 수업에서는 수업을 위해 만든 가상 기관 자료만 사용합니다. 실제 고객 문의나 내부 회의록을 복사하지 않습니다.
8정리와 다음 절
Poisoning은 잘못된 정보의 재사용, Distraction은 무관한 정보의 집중 방해, Confusion은 비슷한 대상의 구분 실패, Clash는 서로 맞지 않는 지시나 사실의 처리 문제를 살펴보는 이름입니다.
네 이름은 공식 오류 코드가 아니며, 한 답에 여러 문제가 함께 나타날 수 있습니다.
실패가 나도록 문제 문장을 넣은 사실과 모델 답에서 실제 오류를 확인한 사실을 따로 기록해야 합니다.
다음 학습과 이어지는 지점 — 다음 05절에서는 입력이 길어질 때 성능이 달라지는 context rot를 같은 질문과 모델을 유지한 채 입력 길이만 바꾸어 살펴봅니다. Ch 9에서는 Select가 검색으로 자동화되면서 Distraction과 Confusion이 검색 결과의 품질 문제로 다시 나타납니다. Ch 19에서는 서로 비슷한 도구 설명이 Confusion을 일으킬 수 있는 조건을 다루고, 이 절의 진단표를 도구 선택 기록에 적용합니다.
9복습 문제
문제 4개 · 해설 포함
[하] 1. 이전 호출에서 만들어진 잘못된 휴관일을 메모에 저장하고 다음 답변에 다시 사용했습니다. 우선 확인할 실패 양상과 그 이유를 쓰세요.
정답·해설 — Context Poisoning을 우선 확인합니다. 잘못된 정보가 다음 호출의 입력에 남아 사실처럼 다시 쓰였기 때문입니다. 공격자가 개입하지 않아도 이 문제가 생길 수 있습니다. Confusion이라고 답했다면 서로 비슷한 두 대상을 잘못 구분한 일도 있었는지 따로 확인합니다.
[중] 2. 질문과 무관한 긴 회의록과 이름이 비슷한 다른 기관의 안내문을 함께 넣었더니 다른 기관의 규정이 답에 포함되었습니다. 가능한 진단 두 가지를 설명하세요.
정답·해설 — 질문과 관계없는 긴 회의록 때문에 핵심 근거를 놓쳤다면 Distraction입니다. 다른 기관의 규정을 현재 기관의 규정으로 사용했다면 Confusion입니다. 두 일이 함께 나타났으므로 두 이름을 모두 기록할 수 있습니다.
[중] 3. 구 규정과 신 규정을 함께 넣었지만 모델이 시행일 확인을 요청했습니다. “Clash 실패가 발생했다”고 기록하면 왜 부정확합니까?
정답·해설 — 서로 맞지 않는 두 규정을 입력에 넣었지만, 모델은 하나를 임의로 고르지 않고 시행일을 물었습니다. 따라서 “서로 맞지 않는 규정을 입력했지만, 모델 답에서는 잘못된 선택을 확인하지 못함”이라고 기록해야 합니다. 문제를 일으키려 넣은 문장과 실제 답에서 확인한 오류를 구분합니다.
[상] 4. 한 답변이 다른 기관의 오래된 규정을 현재 기관의 최신 규정으로 인용했습니다. Poisoning, Confusion, Clash를 각각 적용할 수 있는 조건을 구분하여 쓰고, 추가로 확인할 로그를 제안하세요.
정답·해설 — 오래된 규정을 이전 메모에서 다시 가져왔다면 Poisoning입니다. 이름이 비슷한 다른 기관을 잘못 골랐다면 Confusion입니다. 최신 규정과 오래된 규정이 함께 있는데 적용 순서를 잘못 정했다면 Clash입니다. 어떤 경우인지 확인하려면 입력에 들어간 문서 ID·버전·시행일, 메모를 만든 시점, 답이 인용한 문장을 남겨야 합니다.

성능 저하가 관찰되었는지 실행 결과에 근거해 설명하고, 이 작은 실험의 한계를 말할 수 있습니다.
2이 내용을 배우는 이유
04절에서는 입력에 포함된 정보가 답을 어떻게 바꾸는지 살펴보았습니다. 이번 절의 질문은 하나입니다. 같은 정답 근거를 넣었을 때, 입력이 길어지면 모델이 그 근거를 덜 정확하게 활용할까요? 이를 확인하려면 입력 토큰 수와 답의 정확성을 함께 비교해야 합니다. 토큰 수만 출력해서는 성능이 낮아졌는지 알 수 없습니다.
입력이 길어지면 모델이 그 안에서 필요한 문장을 찾고 답에 적용하는 능력이 낮아질 수 있습니다. 이 현상을 컨텍스트 로트(context rot)라고 부릅니다. 입력을 조금 늘리기만 하면 모든 질문에서 오답이 생긴다는 뜻은 아닙니다. 이 실습은 성능 저하가 일어났다고 미리 가정하지 않습니다. 길이에 따라 정답 확인 결과가 달라지는지 실제 답으로 확인합니다.
아래 코드는 하나의 휴관일 질문을 세 길이에서 반복합니다. 결과가 낮아지면 답 원문에서 어떤 오류가 생겼는지 확인합니다. 결과가 같으면 이번 조건에서는 저하를 관찰하지 못했다고 설명합니다. 두 경우 모두 실험의 결과이며, 관찰하지 않은 현상을 재현했다고 쓰지 않습니다.
3앞에서 배운 내용
컨텍스트와 토큰 — 모델은 지시문과 자료, 질문을 입력으로 받습니다. 글자 수와 토큰 수는 다르며, 실제 입력 토큰은 호출 결과의 usage_metadata에서 확인합니다.
LangChain 모델 호출 — 앞 절에서 준비한 방식과 같은 init_chat_model()과 invoke()를 사용합니다. 응답 본문은 AIMessage.text에서 읽습니다.
반복문과 딕셔너리 — 조건별 입력을 딕셔너리에 담고 반복문으로 호출합니다. 각 실행의 답과 토큰 수를 목록에 보관합니다.
4핵심 개념
입력의 양과 정답을 활용하는 성능
긴 회의록 가운데 “정기 휴관일은 월요일”이라는 문장이 있다고 생각해 봅니다. 회의록이 길어져도 그 문장은 그대로입니다. 모델이 계속 월요일이라고 답한다면, 자료가 늘었어도 이 문제의 정답은 유지한 것입니다. 긴 조건에서 화요일이라고 답하거나 필요한 정보를 찾지 못한다면, 그 실행에서는 정답 활용에 실패한 것입니다.
이 예에서는 입력 길이만 바꾸고, 모델이 정답을 맞혔는지 확인합니다. 입력이 길어서 비용이 늘어난 일, 질문을 잘못 입력한 일, 파이썬 코드가 오류로 멈춘 일은 정답 성능 저하와 다른 문제입니다. 이번 실습은 입력 길이와 정답 확인 결과만 비교합니다.
컨텍스트 로트 (context rot)입력이 길어질 때 모델이 필요한 정보를 찾아 적용하는 성능이 낮아지는 현상입니다. 모델·과제·자료 구성에 따라 관찰 여부와 정도가 달라질 수 있습니다.
통제 조건 (controlled condition)입력 길이의 영향만 비교하려고 바꾸지 않고 그대로 두는 항목입니다. 질문, 근거 문장, 모델, 지시문, 출력 상한, 근거를 자료 가운데에 두는 규칙을 같게 유지합니다.
반복 실행 (repeated run)같은 입력을 다시 호출하는 것입니다. 한 번의 우연한 응답을 전체 경향으로 해석하지 않도록 각 길이를 세 번 실행합니다. 세 번은 통계적 결론을 내리기에 충분한 표본을 뜻하지 않습니다.
정답 확인 기준코드는 답에 ‘월요일’과 출처 ‘E01 p.2’가 모두 들어 있는지 확인합니다. 이 검사는 두 문자열의 포함 여부만 판단하므로 답의 뜻까지 이해하지는 못합니다. 예를 들어 ‘월요일이 아닙니다’에도 ‘월요일’이 들어 있습니다. 따라서 자동 검사 결과와 답 원문을 함께 읽습니다.
도식 — 같은 문제에서 입력 길이만 늘려 비교하기
아래 세 상자는 모델에 보낼 입력 세 개입니다. 각 입력의 가운데에는 동일한 휴관일 근거가 있습니다. 짧은 입력에는 주변 문장을 넣지 않고, 중간 입력에는 근거 앞뒤로 같은 문장을 각각 120번, 긴 입력에는 각각 1,200번 넣습니다. 여기서 숫자는 문장 반복 수이며 토큰 수가 아닙니다.
파란 상자는 서로 다른 입력 길이, 노란 상자는 같은 기준으로 결과를 기록하는 과정입니다. 세 입력을 각각 세 번 호출하므로 총 아홉 개의 답을 확인합니다.보는 순서 — ① 위쪽 세 입력의 차이 → ② 같은 호출·기록 과정 → ③ 길이별 정답 확인 결과 비교.
‘가운데’는 정답 문장을 입력 자료의 앞뒤 주변 문장 사이에 둔다는 뜻입니다. 원본 PDF의 페이지 번호를 뜻하지 않습니다. 입력이 늘어나면 근거 앞의 문자 수는 늘지만, 자료 가운데에 둔다는 배치 규칙은 같습니다. 이번 실습에서 근거를 앞·가운데·뒤로 이동하는 별도 위치 실험은 하지 않습니다.
실행 전에 무엇을 고정하고 바꾸는지 확인합니다
역할이번 실습의 값
고정할 질문미르시립도서관의 정기 휴관일과 출처
고정할 근거[E01 p.2] 정기 휴관일은 매주 월요일입니다.
고정할 호출 조건같은 모델·지시문·출력 상한, 자료 가운데의 근거
바꿀 값근거 앞뒤에 붙이는 무관한 문장의 반복 수: 각 0·120·1,200회
관찰할 결과각 호출의 입력 토큰, 실제 답, 핵심어·출처 포함 여부와 답의 의미
반복 관찰을 다른 과제에 적용하기
각 길이의 호출을 세 번 실행하므로 records에는 아홉 개의 딕셔너리가 쌓입니다. rows는 그중 길이 이름이 같은 행만 골라 만든 목록입니다. sum(record["keyword_pass"] for record in rows)는 Python에서 참을 1, 거짓을 0으로 더하는 성질을 이용해 문자열 기준을 통과한 행 수를 셉니다. 답 전체의 의미를 채점한 점수와 구분합니다.
같은 방법을 회의록에서 담당자를 찾는 과제에 적용하려면 담당자 이름이 적힌 근거와 질문을 고정하고 주변 기록의 양을 바꿀 수 있습니다. 반면 두 부서의 일정 차이를 계산하는 과제는 여러 근거를 연결해야 합니다. 지금의 한 문장 찾기 결과만으로 그 과제도 같은 성능을 보인다고 예상할 수는 없습니다.
추가 실험에서는 먼저 주변 문장의 종류만 바꾸거나, 길이를 유지한 채 근거 위치만 바꾸는 식으로 비교합니다. 길이·위치·질문 난이도를 동시에 변경하면 어느 차이가 결과에 영향을 주었는지 구분하기 어렵습니다. 아래 저장 출력은 동일 문장의 반복과 가운데 근거만 시험한 결과이며, 이 추가 설계를 실제 실행한 결과는 아닙니다.
5실행 예제
준비 셀부터 순서대로 실행합니다. 먼저 입력 세 개를 만들고 질문과 근거가 보존되었는지 확인합니다. 이어서 같은 세 조건을 세 차례 호출합니다. 기록에서 입력 토큰과 정답 확인 결과를 함께 읽는 것이 이 코드의 목적입니다.
확인할 점 — 마지막 출력의 각 행에서 입력 토큰과 기준 충족 횟수를 함께 봅니다. 토큰 수가 증가했는지 확인한 다음, 기준 충족 횟수도 달라졌는지 확인합니다. 기준 충족 횟수만 보지 말고 앞에 출력된 아홉 개의 답도 읽습니다.
6실험 결과 해석
아래 표는 2026-09-09에 gpt-5.4-mini로 실행한 노트북의 실제 결과입니다. 각 조건의 세 호출에서 입력 토큰 수가 같아 한 값으로 표시했습니다.
입력 길이입력 토큰 수핵심어·출처 자동 확인답 원문 확인
short643 / 3세 답 모두 월요일과 E01 p.2를 올바르게 제시
medium2,2243 / 3세 답 모두 월요일과 E01 p.2를 올바르게 제시
long21,6643 / 3세 답 모두 월요일과 E01 p.2를 올바르게 제시
이번 실행에서는 성능 저하를 관찰하지 못했습니다. 입력 토큰은 늘었지만, 아홉 개의 답 모두 휴관일과 출처를 올바르게 답했습니다. 따라서 이 결과를 context rot의 발생 사례로 제시할 수 없습니다. 이 노트북은 같은 과제에서 입력 길이와 정답 활용 성능을 함께 측정하고 결과를 해석하는 실습입니다.
긴 입력에서 기준 충족 횟수가 줄었다면 해당 답을 먼저 읽습니다. 요일을 틀렸는지, 근거를 찾지 못했는지, 출처 형식만 달라졌는지를 구분합니다. 출처 표기 한 번이 빠진 것을 곧바로 모든 정보 활용 능력의 저하로 해석하지 않습니다. 같은 문제가 더 많은 반복과 다른 질문에서도 나타나는지 추가 측정해야 합니다.
세 길이의 결과가 같다면 “이번 모델, 질문, 자료 구성, 입력 길이 범위에서는 이 기준으로 저하를 관찰하지 못했다”고 정리합니다. “입력 토큰이 늘었으므로 context rot가 발생했다”거나 “이번에 모두 맞았으므로 context rot는 없다”는 결론은 모두 실행 결과를 넘어섭니다.
7주의할 점과 실무 메모
작은 실험의 범위를 지킵니다. 정답 문장이 하나이고 주변 문장은 같은 문장의 반복입니다. 실제 긴 문서에서 여러 근거를 연결하는 과제의 난이도를 대표하지 않습니다.
자동 검사와 의미 판단을 구분합니다. ‘월요일이 아닙니다’에도 ‘월요일’이 들어 있습니다. 자동 확인을 통과한 답도 원문을 읽어야 합니다. 이 문자열 검사를 완전한 정확도 지표로 사용하지 않습니다.
반복 세 번으로 성능 순위를 만들지 않습니다. 응답은 실행마다 달라질 수 있습니다. 여러 질문과 충분한 반복을 사용한 평가는 Ch 11·15에서 다룹니다.
입력이 길어지면 호출량도 늘어납니다. 전체 실습을 다시 실행하면 아홉 번의 API 호출이 추가됩니다. 길이를 더 늘리기 전에 입력 토큰과 모델의 한도를 확인합니다.
같은 위치 규칙을 유지합니다. 이번 결과는 자료 가운데에 근거를 둔 조건의 결과입니다. 다른 위치에서도 같을 것이라고 가정하지 않습니다.
8정리와 다음 절
context rot를 살펴보려면 입력 토큰 증가와 정답 활용 성능의 변화를 함께 확인해야 합니다.
같은 질문과 근거에서 주변 문장의 양만 바꾸고, 세 길이를 각각 세 번 호출했습니다.
관찰된 답과 확인 기준으로 결론을 제한합니다. 저하가 나오지 않았다면 미관찰 결과로 기록합니다.
다음 학습과 이어지는 지점 — 06절에서는 필요한 자료만 전달하는 설계를 비교합니다. 이번 결과에서 성능 저하가 나왔는지와 별개로, 각 설계가 필요한 근거를 보존하면서 입력량을 어떻게 바꾸는지 살펴봅니다. 여러 질문을 사용하는 평가와 더 정교한 채점은 Ch 11·15에서 이어집니다.
9복습 문제
문제 4개 · 해설 포함
1. 입력 토큰 수가 늘었다는 출력만으로 context rot를 관찰했다고 말할 수 없는 이유는 무엇입니까?
입력의 양만 확인했기 때문입니다. 같은 과제에서 필요한 정보를 활용하는 성능이 낮아졌는지 답도 확인해야 합니다.
2. 이번 실습에서 바꾼 값 하나와 고정한 조건 세 가지를 쓰세요.
근거 앞뒤에 넣는 주변 문장의 반복 수를 바꿨습니다. 질문·정답 근거·모델을 고정했고, 지시문·출력 상한·근거를 가운데에 두는 규칙도 유지했습니다.
3. 긴 입력의 답이 ‘월요일이 아닙니다. [E01 p.2]’라면 자동 검사는 어떻게 판단하며, 사람은 무엇을 확인해야 합니까?
두 문자열이 있으므로 자동 검사는 통과합니다. 사람은 근거와 답의 의미를 비교하여 요일을 부정한 잘못된 답임을 확인해야 합니다.
4. 모든 길이에서 세 번 모두 올바르게 답했다면 어떤 결론을 쓸 수 있습니까?
이번 모델·질문·자료 구성·길이 범위에서는 저하를 관찰하지 못했다고 쓸 수 있습니다. 모든 긴 문서에서 성능이 유지된다는 결론은 내릴 수 없습니다.

이 절을 마치면 문서 목록을 먼저 보고, 질문에 필요한 문서의 본문만 읽는 절차를 설명할 수 있습니다.
이 절을 마치면 전체 입력, 선택 입력, 압축 입력을 같은 과제로 비교하고 토큰 절약과 근거 보존을 함께 평가할 수 있습니다.
이 절을 마치면 모델과 프롬프트를 고정하고, 압축을 위한 추가 호출 비용을 본 답변 비용과 구분해 기록할 수 있습니다.
이 절을 마치면 학생이 문서 ID를 직접 고르는 이 절의 코드와 Ch 9에서 검색 코드가 문서를 고르는 방식의 차이를 설명할 수 있습니다.
2이 내용을 배우는 이유
05절에서는 길이를 달리한 세 조건의 답을 관찰했고, 이번 실행에서는 성능 저하를 확인하지 못했습니다. 이 결과를 모든 긴 문서의 과제로 확대할 수는 없습니다. 처음부터 모든 문서 본문을 보낼 필요도 없습니다. 먼저 문서 ID와 한 줄 설명만 보여 주고, 질문에 필요한 문서를 고른 뒤 그 본문을 읽을 수 있습니다. 이처럼 정보를 한꺼번에 주지 않고 필요한 단계에서 자세히 보여 주는 방식을 단계적 공개라고 합니다.
단계적 공개는 화면 설계에서 오랫동안 사용한 개념이지만, 컨텍스트 엔지니어링에서는 모델이 처음부터 모든 세부 내용을 받지 않도록 하는 입력 설계로 적용할 수 있습니다. Anthropic의 Agent Skills 설명은 스킬 이름과 설명, 본문, 연결 파일을 단계별로 여는 사례를 제시합니다. 컨텍스트 엔지니어링 글도 파일 경로와 링크 같은 가벼운 식별자를 유지하고 필요한 자료를 실행 시점에 불러오는 방식을 권합니다.
이 절에서는 에이전트를 만들지 않습니다. 모델이 어떤 문서를 읽을지 판단하거나 도구를 호출하지도 않습니다. 학생이 질문과 문서 ID의 대응을 코드에 적고, 고정된 파이썬 반복문가 목록을 보여 준 뒤 지정된 본문 하나를 읽습니다. Ch 9에서는 사람이 정한 대응을 검색이 자동화합니다. 두 단계의 경계를 분명히 알아야 “선택”과 “에이전트 판단”을 같은 것으로 오해하지 않습니다.
3앞에서 배운 내용
Ch 7의 마지막 노트북은 프롬프트 원문, 변경 이유, 응답, 토큰·캐시·지연·예상 비용을 prompt-ab-continuity.json에 저장했습니다. 이 절은 그 파일과 SHA-256 지문을 직접 읽어 실행 기록의 출처를 확인한 뒤 같은 측정 필드와 가격 기준일·100만 토큰당 단가를 컨텍스트 설계 비교에 사용합니다. Ch 7은 고객 지원 질문이고 이 절은 도서관 질문이므로 두 실행의 수치를 직접 비교하지 않습니다.
Write — 현재 호출에 넣지 않은 자세한 본문을 파일이나 변수에 보관합니다. 단계적 공개는 기록을 삭제하지 않고 처음 입력에서 제외합니다.
Select — 현재 질문과 관련된 기록만 컨텍스트 안으로 가져옵니다. 이 절에서는 학생이 지정한 문서 ID를 반복문에서 비교합니다.
Compress — 원문 전체 대신 짧은 요약을 사용할 수 있습니다. 다만 조건, 예외, 출처가 사라질 수 있으므로 원문 보존 여부를 따로 평가합니다.
Context rot 실험 — 입력 길이만 바꾸고, 같은 질문·모델을 사용했으며 근거는 항상 자료 가운데에 두었습니다. 각 길이를 세 번씩 실행했습니다. 이 절도 무엇을 고정하고 바꿨는지 같은 방식으로 기록합니다.
4핵심 개념
비유 — 도서관의 목록과 서가
도서관에서 질문 하나에 답하려고 모든 책을 책상에 쌓지 않습니다. 먼저 목록에서 여러 책의 제목, 주제, 청구기호를 짧게 확인합니다. 필요한 책을 정한 다음 서가에서 그 책을 가져와 자세한 본문을 읽습니다. 단계적 공개는 여러 문서의 짧은 목록과 선택한 한 문서의 자세한 본문을 나눕니다.
목록만으로 최종 답을 만들 수는 없습니다. 목록은 어느 본문을 읽을지 결정하는 데 필요한 최소 정보입니다. 본문을 읽은 뒤에는 답의 근거가 되는 문장이 입력에 있어야 합니다. 따라서 단계적 공개의 성공 기준은 토큰 감소 하나가 아닙니다. 필요한 근거를 보존하면서 불필요한 내용을 줄였는가를 함께 봐야 합니다.
정의
단계적 공개 (progressive disclosure)
처음에는 문서 ID와 한 줄 설명만 보여 주고, 질문에 필요한 문서를 고른 뒤 그 문서의 자세한 본문을 보여 주는 방식입니다.
요약 목록 (summary catalog)
문서 ID, 제목, 한 줄 설명을 모은 목록입니다. 본문 선택을 돕지만 최종 답의 근거를 대신하지 않습니다.
전체 입력 (full context)
후보 문서의 본문을 모두 한 번에 프롬프트에 포함하는 설계입니다. 선택 과정은 없지만 무관한 정보와 입력 토큰이 늘 수 있습니다.
선택 입력 (selected context)
현재 질문에 필요하다고 지정한 원문 본문만 프롬프트에 포함하는 설계입니다. 이 절에서는 사람이 정한 ID와 고정 코드로 만듭니다.
압축 입력 (compressed context)
원문 대신 짧게 줄인 내용을 프롬프트에 포함하는 설계입니다. 토큰을 줄일 수 있지만 예외 조건과 출처가 손실될 수 있고, 모델로 압축하면 별도 호출 비용이 생깁니다.
도식 — 목록에서 필요한 본문으로
처음에는 문서 ID·제목·한 줄 설명만 보고, 질문에 해당하는 ID를 정한 뒤 그 본문만 읽습니다. 이 절에서는 학생이 ID를 코드에 적고 반복문이 해당 문서를 찾습니다. 모델은 문서를 고르지 않습니다.보는 순서 — ① 왼쪽의 짧은 문서 목록 → ② 가운데의 질문과 지정된 문서 ID → ③ 오른쪽의 선택된 원문과 답변.
세 입력 설계 비교
설계프롬프트에 들어가는 내용기대되는 이점확인할 위험
full후보 문서 전체 본문선택 과정에서 정답 문서를 제외할 위험이 적습니다.무관한 정보, Confusion, 입력 토큰 증가가 생길 수 있습니다.
selected질문에 대응하는 원문 본문원문 근거를 유지하면서 입력을 줄일 수 있습니다.선택 규칙이 틀리면 필요한 문서를 처음부터 제외합니다.
compressed원문을 줄인 요약더 적은 토큰으로 핵심 사실을 제공할 수 있습니다.조건, 예외, 출처, 수치의 관계가 손실될 수 있습니다.
세 설계의 우열은 미리 정하지 않습니다. 질문이 여러 문서의 관계를 물으면 full이 필요한 근거를 더 잘 보존할 수 있습니다. 질문별 선택 규칙이 정확하면 selected가 적은 입력으로 같은 답을 만들 수 있습니다. 압축문이 질문에 필요한 예외까지 보존하면 compressed도 유효할 수 있습니다. 반대로 압축이 핵심 조건을 삭제하면 가장 짧지만 가장 부정확한 입력이 됩니다.
고정 코드로 구현하는 세 단계
실행 순서는 세 단계입니다. 첫째, 문서 ID와 제목만 있는 짧은 목록을 만듭니다. 둘째, 학생이 필요한 ID E01-p3을 코드에 적습니다. 셋째, 같은 ID를 가진 원문 하나를 가져옵니다. 모델은 마지막에 완성된 자료와 질문을 받아 답만 만듭니다. 어떤 문서를 고를지 학생 코드에 이미 정해져 있으므로 모델이 다음 행동을 결정하는 에이전트가 아닙니다.
E01-p3은 Ch 9의 doc_id=E01, page=3과 같은 출처 위치를 가리킵니다. 이 구조는 Ch 9의 Select와 직접 이어집니다. Ch 9에서는 문서가 많아져 사람이 ID를 지정하기 어려워지므로 질문과 가까운 문서 조각을 검색합니다. 검색이 선택을 자동화하지만, 어떤 문서를 몇 개 가져오고 어떤 순서로 프롬프트에 넣을지는 여전히 학생이 코드로 정합니다. 질문이 휴관일이면 Ch 9가 같은 E01에서 2쪽을 선택할 수 있으므로 3쪽과 다른 결과는 출처 불일치가 아닙니다. 모델이 검색 도구를 선택하고 호출하는 단계는 Ch 20 이후입니다.
문서 목록을 읽는 사람과 답을 만드는 모델
이 코드의 catalog는 문서별 ID와 제목만 복사한 목록입니다. selected_id는 사람이 대출 규정의 ID로 지정하고, 반복문이 일치하는 첫 문서를 찾아 selected에 보관합니다. break는 찾은 뒤 반복을 중단합니다. 이 선택 과정에는 모델 호출이 없으며, 모델은 나중에 완성된 입력을 받아 답을 생성합니다.
온라인 상품의 호환성을 묻는 상황에서는 상품 목록으로 후보를 고른 뒤 상세 규격을 읽을 수 있습니다. 그러나 “이 상품과 이전 모델의 차이”를 묻는다면 두 모델의 상세 규격이 필요합니다. 선택 입력이 항상 문서 하나여야 하는 것은 아닙니다. 질문이 요구하는 근거 수에 맞춰 선택 범위를 정합니다.
문자 수 비교의 selected["text"]에는 본문만 있지만 실제 호출용 selected_context에는 출처 ID도 붙습니다. 따라서 본문 길이 출력과 API가 보고한 입력 토큰을 같은 대상으로 해석하지 않습니다. 출력 검사의 “연장 예외” 항목도 실제로는 “연장”이라는 문자열의 포함 여부만 봅니다. 예약이 없는 경우라는 조건과 1회·7일 제한은 답 원문에서 별도로 확인해야 합니다.
5실행 예제
먼저 짧은 문서 목록을 확인하고 대출 규정의 식별자를 선택합니다. 전체·선택·압축 입력을 같은 질문과 지시로 각각 실제 API에 전달하여 입력·출력·캐시 토큰, 지연, 예상 비용, 답변 원문, 대출 조건·연장 예외·출처의 보존 여부를 비교합니다. 압축문은 사람이 미리 작성했으므로 별도의 압축 모델 호출 비용은 포함되지 않습니다. 결과는 context-design-continuity.json과 실행 시각별 사본에 저장합니다.
2026-09-09 새 커널 실행에서 full·selected·compressed의 입력 토큰은 각각 110·86·82토큰, 출력 토큰은 169·155·118토큰이었습니다. 캐시 입력은 모두 0토큰이었고 지연은 1,376.7·1,411.3·1,450.1밀리초, 예상 비용은 0.000843·0.000762·0.0005925달러였습니다. 세 답 모두 문자열 확인 세 항목을 통과했지만, 이 검사는 생성 답변 품질 점수가 아니므로 원문을 함께 읽습니다.
확인할 점 — 실습 파일은 labs/part2/ch08-context-engineering/notebooks/06-단계적-공개와-설계-비교.ipynb입니다. 전체 문서, 제목 목록, 선택한 원문, 압축문의 실제 호출 결과를 단계별로 확인합니다. 마지막 비교에서는 목록에 공개할 항목 수를 1에서 2로 바꿉니다.
6일부러 실패해 보기
왼쪽에서는 대출 질문에 주차 문서 E01-p5를 선택하고 실제 모델 답을 확인합니다. 오른쪽에서는 질문과 지시를 그대로 두고 선택 문서만 대출 규정 E01-p3으로 고칩니다. 다시 호출한 답에 대출 권수·기간·연장 조건이 나타나는지 비교합니다.
7주의할 점과 실무 메모
단계적 공개가 언제나 빠르거나 저렴한 것은 아닙니다. 목록 확인, 본문 읽기, 압축 생성이 추가 단계가 되며 잘못된 선택은 재호출을 유발합니다. 사용 패턴과 재사용 횟수를 함께 봅니다.
요약은 원문을 완전히 보존하지 않습니다. 수치, 부정 표현, 적용 기간, 예외, 출처를 우선 확인합니다. 중요한 결정에는 원문 링크나 문서 ID를 남깁니다.
모델과 프롬프트를 고정합니다. 세 설계를 비교하면서 답변 모델이나 지시를 바꾸면 입력 설계의 영향을 구분할 수 없습니다.
선택 규칙을 숨기지 않습니다. 이 절에서는 질문과 문서 ID의 대응을 코드에 명시합니다. Ch 9의 검색과 비교할 수 있도록 어떤 ID를 왜 선택했는지 기록합니다.
에이전트라는 표현을 사용하지 않습니다. 함수 호출 순서와 문서 ID가 코드에 고정되어 있고 모델이 흐름을 바꾸지 않습니다. 에이전트는 Ch 20 ToolNode부터 다룹니다.
한국어 문서의 조건 표현을 보존합니다. “이상”, “미만”, “다만”, “부칙”, “시행일”을 압축 과정에서 삭제하면 적용 범위가 달라질 수 있습니다.
8정리와 다음 절
단계적 공개는 요약 목록에서 시작해 현재 요청에 필요한 본문만 읽는 입력 설계입니다.
full, selected, compressed는 입력 토큰뿐 아니라 정답 근거와 예외 조건의 보존 여부를 함께 비교해야 합니다.
이 절의 선택은 학생이 지정한 문서 ID와 고정 코드가 수행하며, 모델이 도구나 흐름을 결정하지 않습니다.
다음 학습과 이어지는 지점 — Ch 9에서는 Select를 검색으로 자동화하여 문서가 많을 때 필요한 조각을 가져옵니다. Ch 11에서는 정답 문서 ID와 검색 지표로 선택 결과를 평가합니다. 생성된 답의 내용·근거·출처 형식을 자동 평가하는 방법은 Ch 15에서 다룹니다. Ch 19에서는 비슷한 도구 설명이 선택에 주는 Confusion을 다시 확인합니다. Ch 22에서는 Compress와 Isolate를 장기 실행 흐름에 적용하며, 요약의 근거 보존과 작업별 컨텍스트 분리를 다룹니다.

## 1. API 연결 준비
아래 셀은 현재 작업 폴더에서 상위 폴더로 올라가며 `.env`를 찾습니다. 키 값은 화면에 출력하지 않습니다.

## 2. 출력 공간을 먼저 예약합니다

### 세 값을 넣어 반환값을 확인합니다
전체 한도 `4096`에서 출력 예약분 `300`과 안전 여유 `128`을 뺍니다. 반환된 숫자는 `available`에 저장됩니다.

토크나이저는 문장을 모델이 세는 작은 단위인 토큰으로 나누어, 호출 전에 입력 크기를 추정합니다. 실제 호출 뒤에는 응답 객체의 `AIMessage.usage_metadata`에서 제공자가 센 토큰 수를 확인합니다.

### 모델에 전달할 메시지를 만듭니다
`system`에는 답변 규칙을, `user`에는 앞에서 만든 질문을 넣습니다. 셀을 실행한 뒤 역할 순서를 확인합니다.
### 모델을 한 번 호출합니다

### 답과 실제 토큰 수를 관찰합니다

## 5. 출력 예약분 한 값만 바꿔 비교합니다
전체 한도와 안전 여유는 유지하고 출력 예약분만 `300`에서 `600`으로 늘립니다. 입력 예산이 얼마나 줄어드는지 확인합니다.

예제 데이터는 코드 안에 직접 적습니다. `effective_date`는 날짜 필터를 관찰하기 위한 합성 메타데이터이며, PDF의 발행일이나 실제 규정 시행일을 뜻하지 않습니다. 저장 파일은 운영체제의 임시 폴더에 만들기 때문에 노트북을 어느 폴더에서 열어도 실행할 수 있습니다.

## 5. 선택 ID 한 개를 줄여 비교합니다

## 2. 사실·조건·예외·출처를 보존합니다
길이만 줄이면 중요한 예외를 잃을 수 있습니다. 네 필드를 모두 확인한 뒤 한 줄로 압축합니다.
`compress(record)`의 입력은 사람이 이미 골라 적은 네 항목의 딕셔너리이고 반환값은 이를 연결한 문자열입니다. 원문을 자동 요약하거나 모델을 호출하는 함수가 아닙니다. `set(required) - record.keys()`는 빠진 키를 찾으며, 각 값의 진실성이나 원문과의 일치까지 검사하지 않습니다.
회의 기록에서 “검토가 완료되면 금요일 배포”를 “금요일 배포”로 줄이면 적용 조건이 사라집니다. 아래 대출 규정도 같은 관점으로 원문과 조건을 비교합니다. 이후 서로 다른 메시지 목록을 만드는 작업은 입력 자료를 나누는 것으로, 운영체제의 접근 권한이나 보안 격리를 설정하지 않습니다.
### 압축할 원본을 준비합니다
긴 원문을 읽고 답에 필요한 사실·조건·예외·출처를 짧은 사전에 옮깁니다. 다음 셀에서 원문과 압축 결과의 길이를 비교합니다.
### 함수의 반환값을 관찰합니다
`compressed`에는 네 필드가 정해진 순서로 연결됩니다. 원문보다 짧으면서 조건이 남았는지 확인합니다.
## 3. 서로 다른 주제의 근거를 함께 놓아 봅니다
대출 규정 옆에 휴관 규정을 추가합니다. 먼저 두 주제가 섞인 문자열을 출력해 분리 전 상태를 관찰합니다.
## 4. 질문별 메시지를 두 묶음으로 분리합니다
대출 질문에는 대출 근거만, 휴관 질문에는 휴관 근거만 넣습니다. 각 메시지의 사용자 내용을 출력해 출처가 섞이지 않았는지 확인합니다.
`loan_messages`와 `closure_messages`는 서로 다른 입력 목록입니다. 각각 필요한 규정만 포함한 뒤 별도로 호출합니다. 뒤의 `assert`는 특정 출처 ID가 다른 입력에 없는지 확인할 뿐, 모든 정보 유출 가능성을 검사하지 않습니다.
### 분리 결과를 코드로 확인합니다
대출 메시지에는 휴관 출처가 없고, 휴관 메시지에는 대출 출처가 없어야 합니다.
### 분리한 두 메시지를 각각 실행합니다
두 호출의 답변을 주제 이름과 함께 출력합니다. 답변 문구는 실행마다 달라질 수 있습니다.

원본을 복사한 뒤 `condition` 값만 더 구체적으로 바꿉니다. 두 압축 문자열에서 달라진 부분을 확인합니다.
## 정리

# 04. 네 가지 실패 모드
네 이름은 잘못된 정보, 무관한 정보, 비슷한 대상, 서로 충돌하는 규정이 입력에 들어간 문제를 살펴볼 때 씁니다. 한 사례에 여러 문제가 함께 나타날 수 있습니다. 문제 문장을 넣은 사실과 모델 답에서 실제 오류를 확인한 사실은 따로 기록합니다.
## 실행 환경 준비
실습 파일은 `labs/part2/ch08-context-engineering/notebooks/04-네-가지-실패-모드.ipynb`입니다. 새 커널에서 시작해 첫 코드 셀로 패키지 버전을 맞춘 뒤, 설명과 코드를 위에서부터 순서대로 실행합니다. `.env`는 현재 작업 폴더의 상위 경로에서도 찾습니다.
## 1. API 연결 준비
### 모델 객체를 만듭니다
`.env` 확인이 끝난 뒤 모델 이름과 출력 제한을 지정합니다. 이 셀은 아직 API에 질문을 보내지 않습니다.
## 2. 다섯 가지 입력 조건을 만듭니다
기준 입력을 유지하면서 잘못된 메모, 무관한 정보, 비슷한 기관, 상충 규정을 하나씩 추가합니다.
### 기준 입력에 문제 문장을 하나씩 추가합니다
각 조건은 정상 입력인 `clean`을 그대로 두고, 잘못된 메모·무관한 문장·비슷한 기관·상충 규정 중 하나만 더합니다. 조건 이름과 실제로 추가한 문장을 함께 읽습니다.
## 3. 같은 질문으로 다섯 조건을 실행합니다
어떤 실패가 나타날지 미리 정하지 않습니다. 조건 이름, 실제 입력 토큰, 응답 원문을 나란히 기록합니다.

### 같은 질문으로 실제 답을 읽습니다
임의의 오류를 내는 검사 대신 모델이 두 규정을 어떻게 설명하는지 확인합니다. 확인이 필요하다고 답했다면 잘못된 규정을 고른 실패는 관찰되지 않은 것입니다. 다만 현재 자료만으로 질문에 확정 답변을 할 수는 없습니다.
## 수정: 확인한 시행일로 적용할 규정을 고릅니다
이 연습에서는 기관에 확인한 결과 기존 규정의 시행일은 2025-01-01, 대체 규정의 시행일은 2026-01-01이라고 가정합니다. 날짜는 실습용으로 정한 값이며 실제 기관의 규정이 아닙니다. 두 규정의 본문은 그대로 두고, 같은 업무의 새 규정이 이전 규정을 대체한다는 조건에서 기준일까지 시행된 가장 최근 규정을 선택합니다.
`eligible`은 기준일 전에 시행된 후보 목록입니다. `max(eligible, key=effective_date)`는 각 후보를 `effective_date()`에 넘겨 얻은 날짜 문자열을 비교합니다. 함수 이름을 넘기므로 비교할 때마다 필요한 후보의 날짜를 읽습니다. 후보가 비어 있거나 서로 다른 날짜 형식이 섞인 경우는 이 예제의 입력에 없으며 실제 처리에서는 별도 분기가 필요합니다.
### 선택한 규정으로 같은 질문에 다시 답합니다
새 규정을 고른 결과를 근거로 넣습니다. 질문·모델·답변 규칙은 Before와 같습니다. 실제 답이 화요일과 선택한 출처를 사용하는지 확인합니다. 이는 시행일을 확인하고 선택한 효과이며, 모델 자체의 성능이 높아졌다는 뜻은 아닙니다.

# 05. 입력 길이에 따라 정답을 활용하는 성능이 달라질까요?
같은 질문·정답 근거·모델을 사용하고, 근거 앞뒤의 무관한 문장 수만 늘립니다. 세 길이를 각각 세 번 호출하여 답과 입력 토큰, 정답 확인 결과를 기록합니다. 성능 저하가 나오는지는 실행 후 판단합니다. 토큰 수가 늘었다는 사실만으로 context rot가 나타났다고 결론 내리지 않습니다.
## 1. 실행 환경 준비
Python 3.12 커널에서 아래 셀을 순서대로 실행합니다. 프로젝트 폴더 또는 상위 폴더의 `.env`에 OPENAI_API_KEY를 둡니다. 이 실습은 생성 API를 총 아홉 번 호출합니다.
## 2. 모든 조건에서 같은 문제를 사용합니다
답에 필요한 정보는 아래 근거 문장 하나에 있습니다. 모델은 휴관일과 출처를 답해야 합니다. 근거 문장과 질문을 바꾸면 문제 자체가 달라지므로 두 값을 고정합니다.
## 3. 근거를 가운데에 두고 주변 문장 수만 바꿉니다
0·120·1,200은 근거의 각 앞뒤에 붙일 문장의 반복 수입니다. 토큰 수가 아닙니다. 실제 입력 토큰 수는 모델 호출 후 확인합니다. 근거를 입력 자료 가운데에 두는 배치 규칙은 세 조건에서 같습니다.
## 4. 비교 전에 입력 조건을 확인합니다
모든 입력에 질문과 정답 근거가 한 번씩 들어 있어야 합니다. 주변 문장에 정답을 추가하거나 근거 문장을 삭제하지 않았는지 확인합니다. 이 검사는 성능 점수가 아니라 실험에 사용할 입력의 확인입니다.
## 5. 각 길이를 세 번 실행하고 실제 답을 읽습니다
짧음·중간·김 순서의 비교를 세 차례 반복합니다. `record`는 한 번 실행한 길이, 반복 번호, 답, 토큰 수를 담는 딕셔너리입니다. `records`는 아홉 개의 `record`를 차례로 모은 목록입니다. 응답의 `input_tokens`는 모델 제공자가 센 입력 토큰 수입니다. 아홉 번의 호출이 끝날 때까지 출력되는 답을 확인합니다.
## 6. 모든 답에 같은 확인 기준을 적용합니다
월요일과 출처가 모두 포함되었는지 확인합니다. 이 문자열 검사만으로 답 전체의 정확성을 보장할 수는 없습니다. 위 답 원문에서 ‘월요일이 아니다’처럼 뜻이 반대인 표현, 다른 기관의 답, 근거 밖 설명이 있는지도 읽어야 합니다.
## 7. 입력 토큰과 정답 확인 결과를 나란히 비교합니다
각 길이에서 조건을 충족한 응답 수를 셉니다. 점수가 낮아졌다면 먼저 실제 답을 다시 읽습니다. 점수가 같다면 이번 과제와 입력 범위에서는 이 기준으로 성능 저하를 관찰하지 못한 것입니다.
`rows`는 현재 길이 조건과 이름이 같은 기록만 고르는 목록 표현식입니다. `sum()`은 참을 1, 거짓을 0으로 더하여 문자열 기준 충족 횟수를 셉니다. 이번에는 길이마다 기록이 세 개이므로 분모가 3입니다. 이 값은 답 전체의 사실성을 자동 채점한 점수가 아닙니다.
회의록 담당자 찾기에도 같은 비교 방법을 적용할 수 있습니다. 여러 문서의 일정을 연결하는 과제는 필요한 추론이 달라 별도 실험이 필요합니다. 추가 실험에서 근거 위치와 길이를 동시에 바꾸면 원인을 구분하기 어려우므로 하나씩 변경합니다. 여기의 저장 출력에는 그런 추가 실험이 포함되어 있지 않습니다.
## 결과 해석
입력 토큰 증가와 정답 확인 결과를 함께 읽습니다. 모든 길이에서 정답을 유지할 수도 있습니다. 그런 결과를 성능 저하가 발생한 것처럼 표현하지 않습니다. 짧은 근거 한 문장과 반복된 주변 문장만 사용하는 작은 실험이므로, 긴 실제 문서의 모든 과제로 결론을 확대하지 않습니다. 더 복잡한 과제와 여러 질문을 사용하는 평가는 Ch 11·15에서 다룹니다.

## 2. 목록과 원문을 분리합니다
목록에는 여러 문서의 ID와 제목만 넣어 선택을 돕습니다. 답에 필요한 근거는 선택한 문서의 원문에서 가져옵니다.
### 먼저 제목 목록만 공개합니다
원문 전체를 읽기 전에 ID와 제목만 복사합니다. 반복문에서 만든 `item`을 `catalog`에 하나씩 추가합니다.
## 3. 필요한 ID의 원문만 공개합니다
이 예제에서는 학생이 `E01-p3`을 직접 선택합니다.
`selected_id`는 사람이 정한 값입니다. 반복문은 각 문서의 ID와 비교하고 일치하면 문서 딕셔너리를 `selected`에 저장한 뒤 `break`로 중단합니다. `selected is None`은 끝까지 찾지 못했는지 확인합니다. 이 단계에서 모델은 문서를 선택하지 않습니다.
상품 두 모델의 호환성 차이를 비교한다면 두 상세 규격이 모두 필요합니다. 선택 입력의 문서 수는 항상 하나로 고정하지 않고 질문의 근거 범위에 맞춰 정합니다. 아래에서는 대출 규정 한 문서로 답할 수 있는 질문을 사용합니다.
### 세 가지 공개 방식의 길이를 비교합니다
전체 원문, 선택한 원문, 사람이 작성한 압축문을 같은 문자 수 기준으로 비교합니다.
## 4. 세 설계를 같은 조건으로 실행합니다
전체 원문, 선택 원문, 압축문을 이름별로 준비합니다. 선택 원문에도 같은 출처 ID를 붙여 세 입력의 표기 조건을 맞춥니다.
### 같은 질문과 지시로 세 번 호출합니다
압축문은 앞에서 사람이 작성한 값이므로 별도의 압축 모델 호출 비용은 없습니다. 여기서 측정하는 사용량은 세 답변 호출의 입력 토큰입니다.
### 실제 출력과 입력 토큰을 관찰합니다
설계 이름 아래에 입력 토큰과 답변 원문을 함께 출력합니다. 세 응답의 표현은 실행마다 달라질 수 있습니다.
### 필요한 정보가 보존됐는지 비교합니다
토큰 수가 작아도 대출 조건, 연장 예외, 출처가 빠지면 충분한 답이 아닙니다. 자동 검사는 문자열 존재 여부만 보여 주므로 답변 원문도 함께 읽습니다.
아래 딕셔너리의 “연장 예외”는 실제로 “연장” 문자열이 있는지만 검사합니다. 예약이 없다는 조건과 1회·7일 제한을 모두 확인하는 검사가 아니므로 답 원문에서 별도로 읽습니다. “출처”도 `E01` 포함만 보므로 페이지가 정확한지까지 자동 판정하지 않습니다.
### 실행 기록을 보존합니다
Ch 7과 같이 비교 조건과 원문, 사용량, 지연, 예상 비용, 자동 확인을 정본과 실행별 사본에 저장합니다.
## 5. 목록 공개 수 한 값만 바꿉니다
전체 문서와 선택 결과는 그대로 두고 목록에서 보여 줄 항목 수만 `1`에서 `2`로 바꿉니다.
## 정리
목록, 선택, 원문 읽기를 순서대로 수행합니다. 토큰 감소와 필요한 조건의 보존 여부를 함께 비교합니다.
## 실패 재현: 질문과 다른 문서를 선택합니다
대출 질문에 주차 문서를 선택하면 입력은 짧아져도 필요한 대출 근거가 사라집니다.
### 주차 문서를 모델에 전달해 답을 확인합니다
질문과 지시는 그대로 두고 선택한 문서만 `E01-p5`로 바꿉니다. 모델이 대출 조건의 근거를 받지 못한 상태에서 어떤 답을 하는지 읽습니다.
## 수정: 대출 규정 문서를 선택합니다
질문과 지시는 유지하고 대출 규정 `E01-p3`을 선택합니다. 같은 모델의 답에 대출 권수·기간·연장 조건이 나타나는지 확인합니다.
