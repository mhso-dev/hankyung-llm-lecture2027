1학습 목표
일곱 가지 stream mode의 핵심 구성 요소를 실제 출력에서 구분할 수 있습니다.
그래프 실행에서 필요한 사건과 관찰값을 구분할 수 있습니다.
한 그래프에서 관찰한 사건 수의 적용 범위를 설명할 수 있습니다.
2이 내용을 배우는 이유
한 번에 최종 답만 반환하면 사용자는 실행이 멈췄는지 판단하기 어렵습니다. LangGraph는 한 실행에서 생긴 사건을 일곱 방식으로 관찰하게 합니다. 이번 절에서는 상태 전체, 변경분, 메시지 조각, 사용자 정의 진행률, 체크포인트, 태스크, 디버그 사건의 크기와 용도를 실제 출력으로 구분합니다.
3앞에서 배운 내용
Ch23에서 체크포인터와 thread_id가 상태를 저장하는 방법을 배웠고, Ch24에서 interrupt와 재개 사건을 확인했습니다. 이번 챕터에서는 같은 실행을 사용자 화면과 운영 로그에 어떤 단위로 보여 줄지 다룹니다.
4핵심 개념
구체적인 상황
고객 문의 그래프의 prepare와 write 노드는 같은 상태를 처리하지만, 운영 화면은 진행률만 필요하고 디버거는 태스크와 체크포인트가 필요합니다. 하나의 실행에서 소비자마다 필요한 관찰 범위가 다릅니다.
정의
스트림 모드(stream mode)는 실행 중 어떤 종류의 사건을 소비자에게 내보낼지 정하는 옵션입니다. values는 각 단계 뒤의 전체 상태, updates는 노드가 바꾼 값, messages는 모델 메시지 조각과 메타데이터, custom은 노드가 직접 보낸 자료를 반환합니다. checkpoints는 저장된 상태 스냅숏, tasks는 태스크 시작·종료·오류, debug는 체크포인트와 태스크를 포함한 자세한 실행 정보를 제공합니다. checkpoints와 tasks는 체크포인터가 있어야 사건이 생깁니다.
코드 읽기와 비교 경계
graph.stream(input, config, stream_mode=...)는 그래프를 실행하면서 사건을 하나씩 반환하는 반복 가능한 객체를 만듭니다. input은 처음 상태, config는 thread_id 같은 실행 설정, stream_mode는 관찰할 사건의 종류입니다. list(...)로 감싸면 스트리밍 중간에 처리하지 않고 실행이 끝난 뒤 모든 사건을 한꺼번에 모읍니다. 따라서 이 셀의 list는 모드별 자료형과 사건 수를 비교하기 위한 선택이며, 사용자 화면에 즉시 표시하는 구현에서는 for 반복문 안에서 사건을 바로 처리합니다.
values와 updates의 차이는 같은 상태를 얼마나 크게 복사하는가에 있습니다. 주문 상태에 고객 정보, 검색 결과, 답변이 모두 있다면 values는 매 단계 전체를 보내고 updates는 이번 노드가 바꾼 필드만 보냅니다. 반면 custom은 상태 변경과 관계없이 개발자가 정의한 진행 사건입니다. 같은 실행을 재생하거나 복구하려면 checkpoints, 화면의 진행 표시에는 updates나 custom, 모델 답변의 점진적 표시에는 messages가 맞습니다. 모드 선택은 사건 수가 적은 항목을 고르는 문제가 아니라 소비자가 알아야 할 사실을 고르는 문제입니다.
도식 읽기
일곱 가지 stream mode의 실행 흐름. 위에서 아래로 사건 또는 제어권이 이동합니다. 파란 상자는 실행 단계, 초록 상자는 전달되는 자료, 노란 상자는 측정값 또는 종료 판정을 나타냅니다. 화살표는 노트북에서 실제로 진행되는 호출이나 사건의 방향입니다.
5실행 예제
StateGraph에 InMemorySaver를 연결한 뒤 values부터 debug까지 같은 입력을 일곱 번 실행합니다. counts 딕셔너리에 사건 수를 모으고 messages가 0개, custom이 2개인지 검사합니다. 마지막 셀에서는 updates와 custom을 동시에 구독하여 (mode, data) 튜플을 확인합니다.
설치 셀은 Python 3.12 환경에 LangChain 1.4.0, langchain-openai 1.6.0, LangGraph 1.2.11을 고정합니다. 이 절의 그래프는 모델을 호출하지 않으므로 API 키와 API 비용이 필요하지 않습니다.
확인할 점 — counts에서 values 3개, updates 2개, custom 2개를 확인합니다. 마지막 출력에서는 updates와 custom 앞에 붙은 mode 이름을 확인합니다.
6실험 결과 해석
로컬 그래프에는 모델 호출이 없으므로 messages 사건은 0개였습니다. values 3개, updates 2개, custom 2개, checkpoints 4개, tasks 4개, debug 8개가 실제로 출력되었습니다. custom은 두 노드가 각각 한 번 보낸 두 사건입니다. 사건 수는 그래프의 노드 수, 체크포인터, custom writer의 호출 횟수에 따라 달라집니다. 따라서 이 수치를 다른 그래프에도 적용할 수 있는 고정된 규격으로 보아서는 안 됩니다.
이 실험은 두 노드와 InMemorySaver로 만든 한 그래프에서 관찰한 결과입니다. 다른 그래프에서는 사건 수가 달라질 수 있습니다. 그래프 구성을 비교하려면 같은 입력으로 여러 번 실행하고 필요한 사건만 소비하는지 함께 확인합니다.
7주의할 점과 실무 메모
여러 모드를 리스트로 넘기면 기본 v1 형식에서는 (mode, data) 튜플을 받습니다. 이 절의 마지막 셀이 바로 그 형식을 출력합니다. 최신 문서의 version='v2'는 type·ns·data 필드를 가진 통일된 형식을 제공하지만, 기준 버전의 기본값은 v1이므로 코드에서 선택한 형식을 밝혀 둡니다.
checkpoints와 tasks는 체크포인터가 있어야 관찰할 수 있습니다. 이 노트북은 InMemorySaver를 연결했으므로 두 모드에서 사건 수를 셀 수 있습니다.
이 절은 로컬 그래프만 실행합니다. 다음 두 절처럼 외부 모델을 호출하는 노트북에서는 .env에서 읽은 키 값이 출력과 배포 묶음에 들어가지 않았는지 확인합니다.
8정리와 다음 절
일곱 모드는 같은 실행을 서로 다른 단위로 보여 줍니다. 체크포인터가 필요한 모드와 모델 호출이 필요한 모드를 입력 조건과 함께 해석합니다.
이 노트북에서는 노드 두 개와 체크포인터 하나가 만든 사건 수를 확인했습니다.
사건 수가 달라지는 그래프를 비교할 때는 노드와 체크포인터 구성을 함께 기록합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 messages·updates·custom을 한 실행에서 함께 구독하고 화면 문구를 각 사건의 의미에 맞춰 나눕니다.
9복습 문제
1. 왜 messages 사건이 0개였나요?
해설 — prepare와 write 노드가 모델을 호출하지 않았기 때문입니다. messages는 그래프 안의 모델 호출에서 생깁니다.
2. checkpoints와 tasks를 관찰하려면 왜 InMemorySaver가 필요한가요?
해설 — 두 모드는 저장된 상태와 태스크 실행 정보를 바탕으로 사건을 만듭니다. 체크포인터를 연결하지 않으면 이 정보를 저장할 수 없습니다.
3. updates와 custom을 함께 구독할 때 출력이 (mode, data) 튜플인 이유는 무엇인가요?
해설 — 어느 모드에서 온 자료인지 구분해야 하기 때문입니다. mode가 사건의 종류를, data가 그 사건의 내용을 나타냅니다.
4. custom 사건이 2개인 까닭은 무엇인가요?
해설 — prepare와 write 노드가 각각 stream writer로 한 번씩 진행 자료를 보냈기 때문입니다.

1학습 목표
토큰과 중간 진행 스트리밍의 핵심 구성 요소를 실제 출력에서 구분할 수 있습니다.
messages 사건 수와 내용이 있는 조각 수를 구분할 수 있습니다.
messages·updates·custom을 화면 문구에 맞게 선택할 수 있습니다.
2이 내용을 배우는 이유
답변 토큰과 업무 진행률은 서로 다른 사실입니다. 토큰은 모델이 생성한 글의 일부이고, 중간 단계는 그래프 노드가 끝났다는 신호이며, custom 사건은 개발자가 정한 업무 진행 상황입니다. 화면에서 세 신호를 섞으면 ‘30% 완료’라는 표시가 실제보다 앞설 수 있습니다.
3앞에서 배운 내용
Ch23에서 체크포인터와 thread_id가 상태를 저장하는 방법을 배웠고, Ch24에서 interrupt와 재개 사건을 확인했습니다. 이번 챕터에서는 같은 실행을 사용자 화면과 운영 로그에 어떤 단위로 보여 줄지 다룹니다.
4핵심 개념
구체적인 상황
배송 안내 화면에서 글자가 나타나는 동안 ‘모델 호출 30%’와 ‘완료 100%’를 함께 표시하려고 합니다. 토큰 조각, 노드 완료, 업무 진행률은 발생 원인과 갱신 시점이 다릅니다.
정의
토큰 스트리밍(token streaming)은 messages 모드로 모델의 메시지 조각을 순서대로 받는 방식입니다. 중간 단계 스트리밍은 updates로 노드가 반환한 변경분을 받습니다. custom 모드는 get_stream_writer()로 ‘문서 2/5 처리’처럼 도메인에 맞는 값을 보냅니다. 도구 호출 진행 상황은 도구 내부에서 custom 사건을 보내야 실제 처리 단계를 나타낼 수 있습니다.
코드 읽기와 비교 경계
get_stream_writer()는 현재 실행에 연결된 기록 함수를 반환합니다. 노드 안에서 writer({...})를 호출하는 순간 custom 사건이 발생하지만, 그 딕셔너리가 그래프 상태에 자동으로 저장되지는 않습니다. 노드가 마지막에 반환한 {'answer': ...}는 상태 변경분이 되어 updates에서 관찰됩니다. messages의 data는 (message_chunk, metadata) 튜플이므로 첫 값에서 답변 조각을 읽고 두 번째 값에서 어느 노드와 모델 호출에서 생긴 조각인지 확인합니다.
세 신호는 화면에서도 서로 다른 문장으로 표현해야 합니다. messages는 실제 답변 일부이므로 채팅 말풍선에 이어 붙일 수 있습니다. updates는 노드가 끝났다는 사실이므로 단계 목록을 갱신하는 데 알맞습니다. custom의 30과 100은 코드가 정한 값이므로 파일 개수나 처리 건수 같은 계산 근거가 없으면 정확한 진행률로 약속할 수 없습니다. 예를 들어 검색 도구가 재시도 중이라면 토큰이 잠시 없어도 작업은 진행될 수 있고, 답변 토큰이 나오기 시작해도 전체 업무가 끝났다는 뜻은 아닙니다.
도식 읽기
토큰과 중간 진행 스트리밍의 실행 흐름. 위에서 아래로 사건 또는 제어권이 이동합니다. 보라 상자는 모델이 답변을 생성하는 단계, 초록 상자는 전달되는 자료, 노란 상자는 측정값 또는 종료 판정을 나타냅니다. 화살표는 노트북에서 실제로 진행되는 호출이나 사건의 방향입니다.
5실행 예제
answer 노드는 모델 호출 앞뒤에 get_stream_writer()로 30과 100을 보냅니다. 같은 실행에서 messages·updates·custom을 구독하고 seen 딕셔너리로 사건 수를 셉니다. 내용이 있는 messages 조각만 preview에 모은 뒤, 이어 붙인 문자열이 answer 상태의 최종 답변과 같은지 검사합니다.
설치 셀은 Python 3.12 환경에 LangChain 1.4.0, langchain-openai 1.6.0, LangGraph 1.2.11을 고정합니다. 예상 API 비용은 1달러 미만이며 키 값은 출력하지 않습니다.
확인할 점 — seen의 messages와 preview의 내용 조각 수를 따로 확인합니다. 마지막 True는 이어 붙인 preview와 answer 상태의 최종 답변이 같다는 뜻입니다.
6실험 결과 해석
실제 출력에서 messages 사건은 88개였고, 그중 내용이 있는 조각은 84개였습니다. updates는 answer 노드가 끝난 뒤의 변경분 1개, custom은 30과 100 진행 사건 2개로 나타났습니다. 내용 조각을 이어 붙인 문자열은 answer 상태의 최종 답변과 같았습니다. 사건 수와 내용 조각 수는 같은 값이 아닐 수 있으므로 각각의 의미를 구분해 기록합니다.
이 실험은 한 질문과 한 실행 환경의 결과입니다. 메시지 조각 수와 답변 내용은 모델 실행마다 달라질 수 있습니다. 진행률은 개발자가 정의한 값이므로 실제 작업량과 일치하도록 계산 근거를 함께 설계해야 합니다.
7주의할 점과 실무 메모
custom 진행률은 모델 토큰 수에서 자동으로 계산되지 않습니다. 예를 들어 파일 5개 중 2개를 처리했다면 2/5처럼 실제 완료 수를 바탕으로 값을 정합니다. messages의 metadata로 노드 이름과 호출을 필터링할 수 있습니다.
비밀 키는 .env에서 읽고 존재 여부만 확인합니다. 노트북 출력, 예외 메시지, 배포 묶음에 키가 포함되지 않았는지 발행 전에 검사합니다.
외부 모델 호출의 응답과 지연은 공급자 상태에 따라 달라집니다. 운영 기준을 정할 때는 같은 입력을 반복 실행하고 중앙값과 상위 백분위수를 기록합니다.
8정리와 다음 절
messages는 답변 조각, updates는 answer 상태 변경, custom은 개발자가 정의한 진행 사건입니다. 사용자 문구도 이 세 의미에 맞춰 나눕니다.
messages 사건 수와 내용 조각 수는 다를 수 있으므로 같은 열에 기록하지 않습니다.
내용 조각을 이어 붙인 값과 최종 answer를 비교하면 누락 여부를 확인할 수 있습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 같은 에이전트를 세 모드로 각각 실행해 first_event, TTFT, total을 구분해 측정합니다.

1. custom의 30과 100은 누가 정한 값인가요?

정의
이 실습의 첫 토큰까지의 시간(Time To First Token, TTFT) 근삿값은 요청을 시작한 뒤 클라이언트가 내용이 있는 첫 모델 메시지 조각을 받을 때까지 걸린 시간입니다. 조각 하나가 토큰 하나와 같다는 뜻은 아니며 서버 내부의 첫 토큰 생성 시각도 아닙니다. first_event는 모드와 관계없이 첫 사건을 받은 시간이고 total은 마지막 사건까지 소비한 전체 시간입니다. custom의 시작 사건을 TTFT라고 부르면 모델이 아직 답을 만들기 전의 값을 첫 답변 내용으로 오해하게 됩니다.
코드 읽기와 비교 경계
perf_counter()는 시스템 시계가 수정되어도 경과 시간 측정에 사용할 수 있는 단조 증가 시계를 읽습니다. measure()는 스트림을 만들기 직전에 시작 시각을 기록하고, 첫 yield에서 first_event, messages의 내용 있는 첫 조각에서 ttft_s, 반복문이 끝난 뒤 total_s를 계산합니다. 함수가 반환하는 딕셔너리의 None은 측정 실패가 아니라 해당 모드에는 답변 조각이라는 관찰 대상이 없었다는 표시입니다.
세 모드의 시간을 공정하게 비교하려면 한 모델 호출에서 여러 모드를 동시에 구독하거나, 실행 순서를 섞어 충분히 반복해야 합니다. 현재 코드는 모드마다 새 모델 요청을 보내므로 네트워크 상태와 생성된 답변 길이도 함께 달라집니다. custom의 첫 사건이 매우 빨리 도착해도 그것은 ‘작업 시작’을 일찍 알린 결과이며 모델의 첫 답변이 빨라졌다는 뜻이 아닙니다. 반대로 messages의 total이 짧게 나온 한 번의 결과도 스트리밍이 전체 계산 시간을 줄였다는 증거가 되지 않습니다.

`perf_counter()`는 시스템 시계가 수정되어도 경과 시간 측정에 사용할 수 있는 단조 증가 시계를 읽습니다. `measure()`는 스트림을 만들기 직전에 시작 시각을 기록하고, 첫 `yield`에서 `first_event`, `messages`의 내용 있는 첫 조각에서 `ttft_s`, 반복문이 끝난 뒤 `total_s`를 계산합니다. 함수가 반환하는 딕셔너리의 `None`은 측정 실패가 아니라 해당 모드에는 답변 조각이라는 관찰 대상이 없었다는 표시입니다.
세 모드의 시간을 공정하게 비교하려면 한 모델 호출에서 여러 모드를 동시에 구독하거나, 실행 순서를 섞어 충분히 반복해야 합니다. 현재 코드는 모드마다 새 모델 요청을 보내므로 네트워크 상태와 생성된 답변 길이도 함께 달라집니다. `custom`의 첫 사건이 매우 빨리 도착해도 그것은 ‘작업 시작’을 일찍 알린 결과이며 모델의 첫 답변이 빨라졌다는 뜻이 아닙니다. 반대로 `messages`의 `total`이 짧게 나온 한 번의 결과도 스트리밍이 전체 계산 시간을 줄였다는 증거가 되지 않습니다.
## 세 번의 독립 실행 준비
같은 질문을 updates, messages, custom 순서로 한 번씩 실행합니다. 호출마다 답변 길이와 서버 상태가 달라질 수 있으므로 모드가 속도 차이의 원인이라고 판단하지 않습니다.
## 실제 사용량과 답변 보관
공급자가 반환한 입력·출력 토큰과 캐시 입력 토큰을 사용합니다. 비용은 일반 입력 100만 개당 0.75달러, 캐시 입력 0.075달러, 출력 4.50달러 기준의 추정치입니다. 최종 청구액은 계정의 사용 내역에서 확인합니다.
## 지표를 구분해 해석
messages에서 내용이 있는 첫 조각까지의 시간을 TTFT 근삿값으로 사용합니다. 조각 하나와 모델 토큰 하나는 일대일 관계가 아니며, 이 값은 서버 내부의 토큰 생성 시각이 아닙니다.
