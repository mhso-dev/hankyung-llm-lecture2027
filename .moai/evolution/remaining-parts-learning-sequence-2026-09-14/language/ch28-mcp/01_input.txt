1학습 목표
초기화와 capability 협상의 순서를 설명할 수 있습니다.
도구·리소스·프롬프트의 책임을 구분할 수 있습니다.
FastMCP 클라이언트로 세 종류를 발견하고 실제 결과를 읽을 수 있습니다.
2이 내용을 배우는 이유
Ch19에서는 Python 함수를 모델이 읽을 도구 스키마로 바꾸었습니다. 그 함수는 같은 프로그램 안에 있었습니다. Ch28에서는 기능을 별도 프로세스나 원격 서비스로 옮기고 여러 클라이언트가 같은 방식으로 발견하도록 만드는 MCP(Model Context Protocol)를 배웁니다. 먼저 프로토콜이 무엇을 주고받는지 알아야 서버 코드, 전송 방식, 모델 토큰을 서로 다른 층으로 구분할 수 있습니다.
3앞에서 배운 내용
Ch6에서 모델·프레임워크·하네스 계층을 구분했고, Ch19에서 도구 이름·설명·입력 스키마가 모델 선택에 영향을 준다는 사실을 확인했습니다. Ch27에서는 파일시스템과 하위 작업 기능을 미리 조립한 하네스를 사용했습니다. MCP는 이러한 기능을 클라이언트와 서버 사이의 표준 메시지로 제공하지만, 모델의 판단이나 업무 권한을 자동으로 해결하지는 않습니다.
4핵심 개념
쉬운 예
호텔 안내 데스크를 떠올려 봅니다. 손님이 요청할 수 있는 서비스 목록은 도구(tools), 읽을 수 있는 안내서는 리소스(resources), 직원에게 건넬 수 있는 작성 양식은 프롬프트(prompts)에 해당합니다. MCP에서 도구는 서버가 실행하는 호출 가능한 기능입니다. 리소스는 URI로 식별하는 읽을 자료입니다. 프롬프트는 사용자가 명시적으로 선택해 가져오는 재사용 메시지 틀입니다. 연결이 시작되면 클라이언트와 서버는 initialize 요청과 응답으로 프로토콜 버전과 capability를 교환합니다. 서버가 resources capability를 알리지 않았다면 클라이언트는 resources/list를 사용할 수 있다고 가정해서는 안 됩니다. 협상은 기능 존재를 확인하는 절차이고, 호출 권한을 부여하는 인증 절차와는 다릅니다.
정의와 경계
MCP는 클라이언트와 서버가 JSON-RPC 2.0 메시지로 기능과 데이터를 교환하는 응용 계층 프로토콜입니다. 클라이언트는 호스트 애플리케이션 안에서 서버 연결을 관리하고, 서버는 한정된 기능을 공개합니다. 초기화 요청에는 클라이언트가 지원하는 프로토콜 버전과 capability가 들어가며 서버 응답에도 선택한 버전과 서버 capability가 들어갑니다. 이 왕복이 끝난 뒤 initialized 알림을 보내면 정상 동작 단계로 넘어갑니다. tools/list는 호출 가능한 도구 정의, resources/list는 고정 URI 자료, prompts/list는 재사용 프롬프트 정의를 반환합니다. 목록 조회와 실제 사용은 각각 tools/call, resources/read, prompts/get으로 분리됩니다.
코드 읽기와 비교 경계
초기화 협상은 연결 직후 한 번의 요청과 응답으로 시작합니다. 클라이언트는 지원하는 프로토콜 버전과 기능을 보내고, 서버는 선택한 버전과 자신이 제공하는 capability를 반환합니다. 이어서 클라이언트가 initialized 알림을 보내면 도구 목록 같은 정상 요청을 시작합니다. capability는 ‘이 종류의 요청을 이해한다’는 선언이며, 특정 사용자가 그 도구를 호출해도 된다는 권한 판정은 아닙니다.
도구·리소스·프롬프트는 모델에 전달되는 방식도 다릅니다. 도구는 모델이 실행을 요청할 수 있는 이름·설명·입력 스키마를 가집니다. 리소스는 URI로 읽는 데이터이고, 프롬프트는 사용자가 선택하거나 클라이언트가 가져오는 메시지 틀입니다. 같은 도서관 서버라도 ‘대출 가능 여부 계산’은 도구, ‘운영 규정 원문’은 리소스, ‘문의 답변 작성 틀’은 프롬프트가 됩니다. 기능을 어느 범주로 공개할지는 변경 가능성, 실행 부작용, 선택 주체를 기준으로 정합니다.
도식 읽기
색이 쓰인 곳에서 파란색은 학생 코드와 실행 흐름, 보라색은 모델의 판단, 초록색은 도구와 데이터, 노란색은 측정값, 빨간색은 실패 또는 권한 경계를 뜻합니다.
5실행 예제
노트북은 다른 절의 변수에 의존하지 않습니다. 첫 셀에서 고정 버전을 확인한 뒤 각 단계의 실제 반환값과 검사식을 함께 실행합니다.
확인할 점 — 실험은 같은 FastMCP 서버를 메모리 안에서 연결합니다. 네트워크와 하위 프로세스의 변동을 제거하고 발견 결과에 집중합니다. list_tools, list_resources, list_prompts는 각각 한 항목을 반환합니다. lookup_policy 도구 호출은 대출 규정 문자열을 반환하고 policy://handbook 리소스는 세 규정을 담습니다. explain_policy 프롬프트는 입력한 주제를 포함하는 사용자 메시지를 반환합니다. 세 목록의 개수가 같다는 사실보다 결과의 역할과 호출 방법이 다르다는 점을 확인합니다.
6실험 결과 해석
세 목록과 세 사용 요청이 모두 성공한 결과는 이 서버가 도구·리소스·프롬프트를 각각 제공한다는 사실을 보여 줍니다. lookup_policy는 실행 결과를, policy://handbook은 URI로 읽은 자료를, explain_policy는 사용자 메시지 틀을 반환했습니다. 이 메모리 연결 실험은 발견과 사용 메서드의 차이를 확인하는 범위입니다. stdio 전송과 원격 연결의 동작은 다음 절에서 따로 확인합니다.
7주의할 점과 실무 메모
MCP의 JSON-RPC 메시지와 모델에게 전달되는 프롬프트는 같은 데이터가 아닙니다. 서버 발견 결과 중 모델에 도구 정의로 넣은 내용만 모델 입력 토큰에 포함됩니다.
서버가 capability를 알렸다는 사실은 해당 사용자가 모든 기능을 호출할 수 있다는 뜻이 아닙니다. 인증 뒤에도 도구별 권한 확인이 필요합니다.
커리큘럼의 MCP 2026-07은 개강 기준 목표 버전입니다. 2026-09-11 공식 사이트에서 확인한 최신 발행 스펙은 2025-11-25이므로 본문은 확인 가능한 스펙을 기준으로 작성했습니다.
8정리와 다음 절
MCP의 발견·전송·모델 호출은 서로 다른 층이므로 각 층의 값을 따로 측정합니다.
서버 기능은 클라이언트가 발견할 수 있어도 인증과 인가를 통과한 범위에서만 실행합니다.
실습 결과는 고정 버전과 로컬 읽기 전용 서버의 범위에서 해석합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 한 파일에 도구·리소스·프롬프트를 등록하고 stdio로 실행되는 FastMCP 서버를 완성합니다.
9복습 문제
문제 1
도구와 리소스의 가장 큰 차이는 무엇인가요?
해설 — 도구는 서버가 실행하는 기능이고, 리소스는 URI로 읽는 자료입니다.
문제 2
프롬프트는 언제 사용되나요?
해설 — 클라이언트 사용자가 이름과 인자를 지정해 재사용 메시지 틀을 가져올 때 사용됩니다.
문제 3
capability 협상으로 확인할 수 없는 것은 무엇인가요?
해설 — 사용자의 실제 호출 권한은 별도의 인증·인가 검사로 확인해야 합니다.
문제 4
도구 목록 개수와 모델 입력 토큰을 같은 수치로 볼 수 있나요?
해설 — 아닙니다. 목록 개수는 프로토콜 발견 결과이고 입력 토큰은 모델에 직렬화해 전달한 내용의 토큰화 결과입니다.

1학습 목표
FastMCP 인스턴스에 도구·리소스·프롬프트를 등록할 수 있습니다.
등록하지 않은 함수와 @mcp.tool 함수를 발견 결과로 비교할 수 있습니다.
독립 실행 가능한 course_server.py를 stdio 서버로 제공할 수 있습니다.
2이 내용을 배우는 이유
프로토콜 구조를 알아도 서버가 기능을 공개하지 않으면 클라이언트는 아무것도 발견하지 못합니다. FastMCP는 Python 함수의 타입 힌트와 docstring에서 입력 스키마와 설명을 만들고, 장식자(decorator)로 구성 요소 종류를 등록합니다. 이 절에서 만든 서버 파일은 다음 세 절에서 그대로 실행하므로 학생이 복사할 기준 파일이 됩니다.
3앞에서 배운 내용
앞 절에서 list_tools, list_resources, list_prompts와 실제 호출 방법을 확인했습니다. Ch4에서 함수와 타입 힌트를, Ch19에서 @tool 장식자와 입력 스키마를 배웠습니다. FastMCP의 @mcp.tool은 LangChain의 @tool과 이름이 비슷하지만 서로 다른 등록소에 함수를 넣습니다.
4핵심 개념
쉬운 예
게시판에 종이를 붙이지 않으면 방문자는 종이가 있다는 사실을 알 수 없습니다. Python 함수도 FastMCP 인스턴스에 등록해야 MCP 발견 요청에 나타납니다. @mcp.tool은 실행 가능한 기능, @mcp.resource(URI)는 읽을 자료, @mcp.prompt는 재사용 메시지를 등록합니다. 함수 이름은 기본 구성 요소 이름이 되고 docstring은 설명이 됩니다. 인자의 타입 힌트는 JSON Schema 입력 정의를 만듭니다. 서버 파일 마지막의 if __name__ == '__main__' 블록은 파일을 직접 실행할 때 stdio 전송을 시작합니다. 이 블록이 있어야 다른 클라이언트가 파일을 하위 프로세스로 실행할 수 있습니다.
정의와 경계
FastMCP는 MCP 서버와 클라이언트를 Python으로 구현하는 프레임워크입니다. FastMCP 인스턴스는 등록된 구성 요소와 서버 설정을 보관합니다. @mcp.tool이 붙은 함수는 이름, 설명, 입력 스키마와 실행 함수를 가진 도구가 됩니다. @mcp.resource에는 클라이언트가 요청할 URI를 지정하고, @mcp.prompt 함수에는 프롬프트 인자를 타입으로 선언합니다. course_server.py는 외부 API나 사용자 파일을 읽지 않고 모듈 안의 공개 규정 딕셔너리만 반환합니다. 이 제한 덕분에 서버 제작과 프로토콜 호출을 외부 상태 변경 없이 반복할 수 있습니다.
코드 읽기와 비교 경계
FastMCP('course')는 등록 정보를 보관하는 서버 객체를 만듭니다. 일반 함수는 Python 코드 안에 존재할 뿐 클라이언트가 발견할 수 없습니다. @mcp.tool을 붙이면 함수 이름, docstring, 타입 힌트가 각각 도구 이름, 설명, JSON Schema로 변환되어 list_tools() 결과에 나타납니다. 데코레이터가 붙는 시점은 서버 실행 시점이 아니라 모듈을 읽어 함수 정의를 실행하는 시점입니다.
도구 설명은 사람용 주석만이 아니라 모델의 선택 입력입니다. ‘조회합니다’처럼 범위가 넓은 설명보다 어떤 자료를 어떤 인자로 조회하고 무엇을 반환하는지 적어야 합니다. 리소스는 읽을 URI, 프롬프트는 재사용 메시지라는 다른 발견 경로를 가지므로 실행 가능한 계산을 리소스로 위장하지 않습니다. Before에서 함수가 목록에 없고 After에서 등록된 도구가 나타나는 차이는 Python 함수의 존재와 MCP 공개 표면이 별개임을 보여 줍니다.
도식 읽기
색이 쓰인 곳에서 파란색은 학생 코드와 실행 흐름, 보라색은 모델의 판단, 초록색은 도구와 데이터, 노란색은 측정값, 빨간색은 실패 또는 권한 경계를 뜻합니다.
5실행 예제

확인할 점 — Before에서는 lookup_policy와 이름이 같은 일반 함수를 만들지만 @mcp.tool을 붙이지 않습니다. list_tools 결과는 빈 목록이고 call_tool은 UnknownToolError를 발생시킵니다. 7주의할 점과 실무 메모
도구 docstring은 모델이 어떤 기능을 언제 호출할지 판단하는 자료가 됩니다. 내부 구현 설명보다 입력 범위와 반환 내용을 구체적으로 적습니다.
도구는 읽기 전용으로 만들었습니다. 파일 삭제·메일 발송·결제처럼 되돌리기 어려운 동작에는 승인, 중복 방지, 감사 로그를 추가해야 합니다.
stdio 서버에서 일반 print를 표준 출력에 쓰면 프로토콜 메시지를 손상할 수 있습니다. 진단 로그는 표준 오류나 FastMCP 로깅 기능으로 보냅니다.
학생 배포 파일은 course_server.py, 다섯 개 노트북, pyproject.toml, uv.lock입니다. .env와 실행 환경의 비밀 값은 배포 목록에 포함하지 않습니다.
8정리와 다음 절
MCP의 발견·전송·모델 호출은 서로 다른 층이므로 각 층의 값을 따로 측정합니다.
서버 기능은 클라이언트가 발견할 수 있어도 인증과 인가를 통과한 범위에서만 실행합니다.
실습 결과는 고정 버전과 로컬 읽기 전용 서버의 범위에서 해석합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 완성한 course_server.py를 실제 하위 프로세스로 실행하고 stdio와 원격 HTTP의 신뢰 경계를 비교합니다.

하위 프로세스 환경 변수와 원격 인증 정보를 최소 범위로 구성할 수 있습니다.
2이 내용을 배우는 이유
같은 도구 목록을 제공해도 서버가 어디에서 실행되는지에 따라 위험이 달라집니다. stdio에서는 클라이언트가 로컬 하위 프로세스를 만들고 표준 입력과 출력으로 통신합니다. 원격 서버에서는 이미 실행 중인 HTTP 서비스에 연결합니다. 코드를 그대로 옮기기 전에 누가 서버를 시작하고 어떤 비밀과 파일에 접근할 수 있는지 선을 그어야 합니다.

4핵심 개념
쉬운 예
stdio는 같은 컴퓨터 안의 전용 통로입니다. 클라이언트가 서버 프로세스의 시작과 종료를 관리하며 네트워크 포트를 열지 않습니다. 그러나 하위 프로세스는 전달받은 환경 변수와 운영체제 권한으로 로컬 파일에 접근할 수 있습니다. Streamable HTTP는 네트워크 주소의 서비스에 연결하며 여러 클라이언트가 사용할 수 있습니다. 서버는 요청의 Origin을 검증해야 합니다. 로컬 실행은 127.0.0.1에 바인딩하고, 공개 서비스에는 통신 보호와 인증·사용자별 인가를 설계합니다. MCP 공식 스펙은 HTTP 전송의 OAuth 절차를 stdio에 그대로 적용하지 않으며, stdio 구현은 필요한 자격 정보를 환경에서 읽을 수 있습니다. HTTP에서는 Authorization 헤더나 OAuth 흐름을 쓸 수 있지만, 헤더가 있다는 사실만으로 모든 도구를 허용해서는 안 됩니다.
정의와 경계
전송(transport)은 JSON-RPC 메시지를 어느 통로로 옮길지 정합니다. stdio 전송은 줄바꿈으로 구분한 메시지를 하위 프로세스의 표준 입력과 출력에서 교환합니다. Streamable HTTP 전송은 하나의 MCP 엔드포인트에 HTTP POST와 선택적인 GET을 사용합니다. 전송 선택은 도구의 업무 의미를 바꾸지 않지만 연결 수명, 자격 정보 위치, 접근 가능한 사용자의 범위를 바꿉니다. 인증은 요청 주체를 확인하는 과정이고 인가는 확인된 주체가 특정 도구를 호출할 수 있는지 판정하는 과정입니다. 최소 권한은 서버 프로세스와 사용자에게 필요한 자원과 동작만 허용하는 원칙입니다.
코드 읽기와 비교 경계
stdio 연결에서는 클라이언트가 서버 명령을 하위 프로세스로 시작하고 표준 입력·출력으로 JSON-RPC 메시지를 교환합니다. env에 넘긴 사전은 그 프로세스가 볼 수 있는 환경 변수를 정합니다. 부모 프로세스의 전체 환경을 복사하면 API 키처럼 서버에 필요하지 않은 값도 함께 전달될 수 있습니다. 필요한 변수만 새 사전에 넣는 After 코드는 서버 기능은 유지하면서 노출 범위를 줄입니다.
Streamable HTTP에서는 서버가 별도 주소에서 실행되므로 프로세스 환경 대신 네트워크 요청의 인증 정보와 서버 측 인가가 중요합니다. TLS는 전송 중 내용을 보호하고 인증은 요청 주체를 확인하지만, 어떤 사용자가 어떤 도구를 실행할 수 있는지는 인가 규칙이 정합니다. stdio가 로컬이라는 이유로 안전하다고 단정할 수도 없습니다. 하위 프로세스는 전달받은 운영체제 권한으로 파일과 네트워크에 접근할 수 있으므로 실행 파일, 환경, 작업 폴더를 함께 제한해야 합니다.
도식 읽기
색이 쓰인 곳에서 파란색은 학생 코드와 실행 흐름, 보라색은 모델의 판단, 초록색은 도구와 데이터, 노란색은 측정값, 빨간색은 실패 또는 권한 경계를 뜻합니다.

1학습 목표
langchain.mcp의 MCPAdapter를 올바른 대상 형식으로 열 수 있습니다.
MCP 도구를 LangChain BaseTool로 발견하고 직접 호출할 수 있습니다.
직접 작성한 LangChain 도구와 MCP 어댑터 도구의 경계를 설명할 수 있습니다.
2이 내용을 배우는 이유
서버 호출이 성공해도 기존 LangChain 에이전트가 그 도구를 바로 읽는 것은 아닙니다. 어댑터(adapter)는 MCP의 도구 설명과 호출 방식을 LangChain BaseTool 인터페이스로 바꿉니다. 이 변환을 확인하면 Ch19의 bind_tools 코드와 MCP 서버를 같은 모델 인터페이스에서 다룰 수 있습니다.
3앞에서 배운 내용
Ch19에서 @tool로 만든 BaseTool의 name, description, args_schema를 모델에 연결했습니다. 앞 절에서는 course_server.py를 stdio로 호출했습니다. 이번에는 같은 서버를 MCPAdapter에 넘기고 반환된 도구의 이름·설명·입력 스키마·호출 결과를 읽습니다.
4핵심 개념
쉬운 예
서로 다른 규격의 플러그를 연결하는 변환기를 생각해 봅니다. MCPAdapter는 FastMCP 클라이언트 연결과 프로토콜 협상을 담당하고, list_tools 결과를 LangChain BaseTool 목록으로 바꿉니다. LangChain 1.4.0에서는 from langchain.mcp import MCPAdapter가 공식 문서의 현재 경로이며 beta 경고가 발생합니다. 과거 외부 패키지인 langchain-mcp-adapters의 MultiServerMCPClient 예제가 많이 남아 있지만, 1.4.0 공식 문서는 새 네임스페이스로의 이동을 안내합니다. 커리큘럼의 langchain.mcp 표기는 확인 결과 유효합니다. 다만 모듈 이름만 적는 것으로 충분하지 않고 MCPAdapter 클래스를 사용해야 합니다.
정의와 경계
어댑터는 한 인터페이스의 값을 다른 인터페이스에서 사용할 수 있도록 변환하는 객체입니다. MCPAdapter는 URL, Path, FastMCP 인스턴스 같은 대상을 받고 연결 방법을 정합니다. Path 대상은 stdio 하위 프로세스, http 또는 https URL은 Streamable HTTP, FastMCP 인스턴스는 메모리 연결을 사용합니다. list_tools는 MCP 도구의 이름·설명·입력 스키마와 원격 호출 함수를 LangChain BaseTool로 감쌉니다. 반환 도구는 invoke나 ainvoke로 호출할 수 있고 bind_tools에도 전달할 수 있습니다. 연결 수명과 도구 캐시 정책은 어댑터가 관리하지만 업무 권한 판정은 서버나 호출 전 인터셉터에서 별도로 구현해야 합니다.
코드 읽기와 비교 경계
async with MCPAdapter(server_path) as adapter는 연결을 열고 블록을 벗어날 때 정리합니다. await adapter.list_tools()는 서버의 MCP 도구 정의를 가져와 LangChain BaseTool 객체 목록으로 변환합니다. 변환된 도구의 .name과 .args_schema는 모델 선택에 쓰이고, .ainvoke({...})를 호출하면 어댑터가 인자를 MCP 요청으로 보내 서버 결과를 다시 LangChain 결과 형식으로 반환합니다. await는 원격 또는 하위 프로세스 응답을 기다리는 동안 다른 비동기 작업이 실행될 수 있게 합니다.
직접 @tool로 만든 도구와 MCP 도구는 에이전트에서 비슷한 인터페이스를 가지지만 소유 경계가 다릅니다. 직접 도구는 같은 애플리케이션 코드와 배포 주기를 따르고, MCP 도구는 별도 서버가 목록·스키마·실행을 제공합니다. 어댑터가 형식을 맞춰도 서버 권한, 연결 실패, 버전 협상, 결과 신뢰성까지 해결하지는 않습니다. 예제의 두 도구가 같은 운영 시간을 반환한다는 사실은 인터페이스 호환을 보여 주며 두 구현의 장애 특성이 같다는 뜻은 아닙니다.
도식 읽기
색이 쓰인 곳에서 파란색은 학생 코드와 실행 흐름, 보라색은 모델의 판단, 초록색은 도구와 데이터, 노란색은 측정값, 빨간색은 실패 또는 권한 경계를 뜻합니다.
5실행 예제
노트북은 다른 절의 변수에 의존하지 않습니다. 첫 셀에서 고정 버전을 확인한 뒤 각 단계의 실제 반환값과 검사식을 함께 실행합니다.
확인할 점 — 실험은 Path 객체로 서버 파일을 지정합니다. MCPAdapter는 이 파일을 stdio 하위 프로세스로 시작하고 list_tools에서 lookup_policy 하나를 반환합니다. 도구의 args_schema는 topic 문자열을 요구하며 ainvoke에 운영을 전달하면 운영 시간이 반환됩니다. 직접 작성한 LangChain @tool과 비교하면 호출 측 인터페이스는 name과 invoke로 비슷하지만, MCP 도구 실행은 프로토콜을 거쳐 별도 서버로 전달됩니다. 어댑터가 변환한다고 해서 서버 코드를 클라이언트 프로세스 안에서 직접 호출하는 것은 아닙니다.
6실험 결과 해석
list_tools가 lookup_policy 하나를 반환하고, 변환된 도구의 args_schema가 topic을 필수 항목으로 표시했습니다. ainvoke 결과에 운영 시간이 들어 있으므로 도구 호출이 서버까지 전달된 사실도 확인할 수 있습니다. 직접 작성한 @tool과 MCP 도구는 모두 name과 args_schema를 제공하지만, 후자는 어댑터와 전송 계층을 거쳐 실행됩니다. 이 비교는 호출 측 인터페이스의 공통점을 보여 줄 뿐, 두 도구의 내부 구현이나 지연 시간이 같다는 뜻은 아닙니다.
7주의할 점과 실무 메모
langchain.mcp는 1.4.0에서 beta입니다. 경고를 숨기기보다 기준 버전과 변경 가능성을 참고 자료에 기록합니다.
MCPAdapter의 문자열 대상은 http 또는 https URL이어야 합니다. 로컬 스크립트는 Path 객체로 넘겨 의도를 분명히 합니다.
도구 목록은 연결 시점에 발견한 결과입니다. 서버 구성 요소가 바뀌면 캐시 정책과 재발견 시점을 정해야 합니다.
모델이 도구를 자동 선택하게 하는 호출은 다음 절에서 수행합니다. 이 절은 어댑터 변환과 실제 도구 호출만 분리해 확인합니다.
8정리와 다음 절
MCP의 발견·전송·모델 호출은 서로 다른 층이므로 각 층의 값을 따로 측정합니다.
서버 기능은 클라이언트가 발견할 수 있어도 인증과 인가를 통과한 범위에서만 실행합니다.
실습 결과는 고정 버전과 로컬 읽기 전용 서버의 범위에서 해석합니다.
다음 학습과 이어지는 지점 — 마지막 절에서는 직접 도구 한 개, MCP 도구 한 개, MCP 도구 다섯 개를 같은 첫 질문에 연결해 모델 입력 토큰을 측정합니다.

1학습 목표
직접 도구와 MCP 도구를 같은 질문과 모델 조건에서 비교할 수 있습니다.
도구 정의 개수·직렬화 크기·모델 입력 토큰을 서로 다른 측정값으로 기록할 수 있습니다.
첫 호출 usage_metadata로 비용을 계산하고 결과의 적용 범위를 설명할 수 있습니다.
2이 내용을 배우는 이유
MCP는 기능을 연결하는 비용을 없애지 않습니다. 모델이 어떤 도구를 고를지 판단하려면 이름·설명·입력 스키마를 첫 호출에 받아야 합니다. Ch19에서 도구 개수가 늘면 선택 정보가 커진다는 사실을 배웠습니다. 이제 직접 도구와 MCP 어댑터 도구를 같은 모델에 연결해 프로토콜 도입 자체와 도구 정의 수 증가를 분리합니다.
3앞에서 배운 내용
Ch19에서 bind_tools가 도구 설명을 모델 요청에 포함시키고 usage_metadata가 입력·출력 토큰을 제공한다는 사실을 확인했습니다. 앞 절에서 MCPAdapter가 MCP 도구를 BaseTool로 변환했습니다. 이번 실험은 도구 실행 뒤의 두 번째 호출이 아니라, 도구를 고르는 첫 모델 호출만 측정합니다.
4핵심 개념
쉬운 예
메뉴판의 음식 수와 종이 무게는 관련이 있지만 같은 값은 아닙니다. 도구 정의 수는 항목 개수입니다. JSON Schema 직렬화 문자의 수는 클라이언트가 가진 정의의 대략적인 크기입니다. input_tokens는 모델 제공자가 실제 요청을 토큰화하고 보고한 값입니다. MCP JSON-RPC 전송 바이트는 클라이언트와 서버 사이 통신량이며 usage_metadata에 포함되지 않습니다. 따라서 MCP 연결 전후 토큰을 말할 때는 모델에 전달한 도구 정의가 무엇인지 함께 기록해야 합니다. 직접 도구 한 개와 MCP 도구 한 개 비교는 어댑터 변환 차이를, MCP 도구 한 개와 다섯 개 비교는 목록 규모 차이를 보여 줍니다.
정의와 경계
첫 호출 입력 토큰은 사용자 메시지와 시스템 지침, 모델에 전달된 도구 정의 등 첫 모델 요청에 포함된 입력을 제공자가 토큰화한 수치입니다. 이번 실험에서는 대화 이력과 도구 결과가 아직 없으므로 도구 정의 규모의 차이를 읽기 좋습니다. schema_chars는 동일한 Python JSON 직렬화 방식으로 이름·설명·스키마를 문자열로 바꾼 문자 수입니다. 이 값은 토큰 수의 대체물이 아니며 설명 길이를 대조하는 보조 측정입니다. 직접 도구와 MCP 도구가 같은 158 입력 토큰을 기록하면 MCP라는 이유만으로 모델 입력이 늘었다고 말할 수 없습니다. MCP 도구 다섯 개가 316 토큰을 기록한 결과는 이 실행에서 정의 수와 내용이 늘어 입력이 커졌다는 증거입니다.
코드 읽기와 비교 경계
bind_tools(tools, tool_choice='required')는 선택 가능한 도구 정의를 첫 모델 요청에 포함하고 모델이 반드시 하나의 도구 호출을 만들도록 합니다. 이때 도구가 실행되는 것은 아닙니다. 반환한 첫 AIMessage의 tool_calls에는 선택한 이름과 인자가 있고, usage_metadata['input_tokens']에는 공급자가 보고한 전체 입력 토큰이 있습니다. schema_chars는 도구 이름·설명·스키마를 같은 JSON 방식으로 직렬화한 문자 수라서 정의 규모를 읽는 보조값입니다.
도구 수와 입력 토큰의 관계를 분리해서 읽어야 합니다. 직접 도구 한 개와 MCP 도구 한 개는 연결 방식이 다르지만 모델에 보이는 변환 결과가 비슷할 수 있습니다. MCP 한 개와 다섯 개 비교에서는 개수뿐 아니라 각 이름과 설명의 내용도 함께 바뀝니다. 따라서 이번 결과는 ‘이 정의 묶음에서 다섯 개 조건의 입력이 더 컸다’는 관찰입니다. 자주 쓰지 않는 도구를 상황에 따라 필터링하면 선택 오류와 입력 규모를 함께 줄일 수 있지만, 권한이 없는 도구를 숨기는 일은 서버의 인가 검사를 대신하지 않습니다.
도식 읽기
색이 쓰인 곳에서 파란색은 학생 코드와 실행 흐름, 보라색은 모델의 판단, 초록색은 도구와 데이터, 노란색은 측정값, 빨간색은 실패 또는 권한 경계를 뜻합니다.
5실행 예제
노트북은 다른 절의 변수에 의존하지 않습니다. 첫 셀에서 고정 버전을 확인한 뒤 각 단계의 실제 반환값과 검사식을 함께 실행합니다.
확인할 점 — 세 조건은 같은 gpt-5.4-mini 모델, 같은 질문, tool_choice='required', reasoning_effort='none'을 사용합니다. A는 직접 @tool 한 개, B는 같은 역할의 MCP 도구 한 개, C는 읽기 전용 MCP 도구 다섯 개입니다. 각 호출에서 input_tokens, output_tokens와 첫 AIMessage의 tool_calls를 출력합니다. 실행된 수치는 노트북 출력과 verification.md에 기록합니다. 한 번의 작은 질문이므로 토큰 증가 방향을 관찰할 수 있지만 모든 모델과 제공자의 직렬화 방식에 일반화할 수는 없습니다.
6실험 결과 해석
같은 gpt-5.4-mini 모델에서 직접 도구 한 개와 MCP 도구 한 개는 같은 input_tokens를 기록했습니다. MCP 도구 다섯 개 조건에서는 입력 토큰이 늘었습니다. 따라서 이 작은 조건에서는 MCP 연결 자체보다 다섯 도구의 이름·설명·스키마가 함께 늘어난 쪽에서 입력 토큰 차이가 나타났습니다. 첫 도구 선택 결과도 조건마다 같지 않을 수 있습니다. 이 값은 한 번의 실행 결과이며, 다른 모델·도구 정의·제공자 직렬화 방식에는 그대로 적용할 수 없습니다.
7주의할 점과 실무 메모
MCP 연결 초기화·목록 조회의 JSON-RPC 바이트를 모델 입력 토큰으로 부르지 않습니다. 이 실습은 OpenAI가 보고한 모델 호출 usage_metadata를 측정합니다.
직접 도구 한 개와 MCP 도구 한 개는 이름과 변환된 스키마 표현이 완전히 같지 않으므로 결과 차이를 MCP 하나의 원인으로 단정하지 않습니다. MCP 한 개와 다섯 개 조건도 도구 수와 각 정의 내용이 함께 바뀝니다.
도구가 많다고 항상 선형으로 같은 토큰 수가 늘지는 않습니다. 이름·설명·스키마 길이와 제공자 직렬화가 함께 영향을 줍니다.
비용은 2026-09-11에 이 교재가 사용하는 기존 gpt-5.4-mini 단가 가정으로 추정하며 모든 조건 합계가 1달러 미만인지 확인합니다. 실제 청구는 계정 조건에 따라 달라질 수 있습니다.
권한이 없는 도구는 모델에게 보이지 않게 서버나 클라이언트에서 필터링하면 보안 범위와 도구 정의 입력을 함께 줄일 수 있습니다. 단, 토큰 절감을 권한 검사의 대체 수단으로 사용해서는 안 됩니다.

서버 기능은 클라이언트가 발견할 수 있어도 인증과 인가를 통과한 범위에서만 실행합니다.
실습 결과는 고정 버전과 로컬 읽기 전용 서버의 범위에서 해석합니다.
다음 학습과 이어지는 지점 — Ch29에서는 최종 답만 보지 않고 도구 선택과 호출 순서를 포함한 실행 궤적을 평가합니다. Ch37에서는 MCP 도구 정의가 계기판의 컨텍스트 지표를 어떻게 악화시키는지 다시 측정합니다.

## MCPAdapter로 stdio 도구 발견
MCPAdapter로 stdio 도구 발견에 필요한 값과 결과를 확인합니다.
### 코드 읽기와 비교 경계
`async with MCPAdapter(server_path) as adapter`는 연결을 열고 블록을 벗어날 때 정리합니다. `await adapter.list_tools()`는 서버의 MCP 도구 정의를 가져와 LangChain `BaseTool` 객체 목록으로 변환합니다. 변환된 도구의 `.name`과 `.args_schema`는 모델 선택에 쓰이고, `.ainvoke({...})`를 호출하면 어댑터가 인자를 MCP 요청으로 보내 서버 결과를 다시 LangChain 결과 형식으로 반환합니다. `await`는 원격 또는 하위 프로세스 응답을 기다리는 동안 다른 비동기 작업이 실행될 수 있게 합니다.
직접 `@tool`로 만든 도구와 MCP 도구는 에이전트에서 비슷한 인터페이스를 가지지만 소유 경계가 다릅니다. 직접 도구는 같은 애플리케이션 코드와 배포 주기를 따르고, MCP 도구는 별도 서버가 목록·스키마·실행을 제공합니다. 어댑터가 형식을 맞춰도 서버 권한, 연결 실패, 버전 협상, 결과 신뢰성까지 해결하지는 않습니다. 예제의 두 도구가 같은 운영 시간을 반환한다는 사실은 인터페이스 호환을 보여 주며 두 구현의 장애 특성이 같다는 뜻은 아닙니다.

### 코드 읽기와 비교 경계
`bind_tools(tools, tool_choice='required')`는 선택 가능한 도구 정의를 첫 모델 요청에 포함하고 모델이 반드시 하나의 도구 호출을 만들도록 합니다. 이때 도구가 실행되는 것은 아닙니다. 반환한 첫 `AIMessage`의 `tool_calls`에는 선택한 이름과 인자가 있고, `usage_metadata['input_tokens']`에는 공급자가 보고한 전체 입력 토큰이 있습니다. `schema_chars`는 도구 이름·설명·스키마를 같은 JSON 방식으로 직렬화한 문자 수라서 정의 규모를 읽는 보조값입니다.
도구 수와 입력 토큰의 관계를 분리해서 읽어야 합니다. 직접 도구 한 개와 MCP 도구 한 개는 연결 방식이 다르지만 모델에 보이는 변환 결과가 비슷할 수 있습니다. MCP 한 개와 다섯 개 비교에서는 개수뿐 아니라 각 이름과 설명의 내용도 함께 바뀝니다. 따라서 이번 결과는 ‘이 정의 묶음에서 다섯 개 조건의 입력이 더 컸다’는 관찰입니다. 자주 쓰지 않는 도구를 상황에 따라 필터링하면 선택 오류와 입력 규모를 함께 줄일 수 있지만, 권한이 없는 도구를 숨기는 일은 서버의 인가 검사를 대신하지 않습니다.
