1학습 목표
체크포인터와 thread_id가 각각 맡는 역할을 설명할 수 있습니다.
같은 thread_id의 누적 결과와 다른 thread_id의 격리 결과를 읽을 수 있습니다.
메모리 체크포인터를 운영 재개 저장소로 쓰기 어려운 이유를 설명할 수 있습니다.
2이 내용을 배우는 이유
에이전트가 여러 차례 호출되는 동안 같은 사용자의 상태를 이어 가고 다른 사용자의 상태는 섞지 않아야 합니다.
이 절에서는 customer-a가 3 뒤에 4를 더해 7이 되는지, customer-b의 4가 독립적으로 시작하는지를 같은 그래프에서 확인합니다. 저장 시점과 외부 부작용의 중복 문제는 뒤 절에서 다룹니다.
3앞에서 배운 내용
Ch13의 StateGraph는 한 번의 invoke 안에서 State를 노드 사이에 전달했습니다. Ch20의 도구 반복도 같은 실행 안에서 메시지를 누적했습니다. 이번 절에서는 실행이 끝난 뒤에도 값을 찾을 수 있도록 compile(checkpointer=memory)를 사용하고, config의 configurable.thread_id가 어느 기록을 읽을지 지정합니다.
4핵심 개념
구체적인 상황
상담 시스템에서 customer-a가 앞서 입력한 3에 이어 4를 보내면 합계는 7이어야 합니다. 같은 시각 customer-b가 4를 보내도 customer-a의 3이 섞이면 안 됩니다. 체크포인트는 계산 결과를 남기고 스레드는 두 고객의 기록 경계를 만듭니다.
정의
체크포인터(checkpointer)는 그래프 단계가 끝날 때 상태 스냅샷을 저장합니다. 스레드(thread)는 관련 체크포인트를 묶는 논리적 실행 단위이며 thread_id가 그 묶음을 찾는 키가 됩니다.
StateSnapshot의 values는 그 시점의 채널 값이고 next는 다음에 실행할 노드 이름입니다. 실행을 마친 스냅샷에서 next가 빈 튜플이면 이어서 실행할 노드가 없다는 뜻입니다. get_state_history()는 입력, 노드 실행, 종료 뒤에 만들어진 스냅샷을 최신순으로 반환합니다.
코드를 읽는 순서
체크포인터(checkpointer)는 그래프의 단계별 상태 스냅샷을 저장하고, 스레드(thread)는 관련 체크포인트를 묶는 식별자입니다. builder.compile(checkpointer=memory)에서 저장 기능을 그래프에 연결하지만 이때 상태가 생기지는 않습니다. invoke(..., {"configurable": {"thread_id": ...}})가 실행될 때 해당 스레드에 체크포인트가 기록됩니다.
InMemorySaver는 현재 Python 프로세스의 메모리에만 저장합니다. get_state(config)는 선택한 스레드의 최신 StateSnapshot을, get_state_history(config)는 단계별 기록을 최신순으로 반환합니다. 상태의 events가 누적되는 방식은 상태 스키마와 노드가 반환하는 값에 달려 있으며, 체크포인터가 모든 리스트를 자동으로 합치는 것은 아닙니다.
도식 읽기
도식의 ‘입력 + thread_id’에서 시작해 ‘체크포인트 저장’을 거칩니다. customer-a는 ‘같은 스레드 재개’로 이동하고 customer-b는 ‘다른 스레드 격리’로 이동합니다. 노트북의 total 7과 total 4가 두 경로의 결과입니다.
5실행 예제
첫 셀은 total과 events를 가진 State와 add 노드를 정의하고 InMemorySaver를 붙입니다. customer-a 설정으로 3을 실행한 뒤 같은 설정에 4를 입력합니다. 마지막 셀은 입력 4를 유지한 채 thread_id만 customer-b로 바꾸어 누적값과 기록 수를 비교합니다.
확인할 점 — 같은 thread_id의 두 실행은 total 7로 이어졌고 다른 thread_id는 total 4에서 독립적으로 시작했습니다.
다른 상황과 적용 경계
같은 고객의 이어지는 대화에는 같은 thread_id를 사용하고, 독립된 상담이나 테스트에는 새 ID를 사용합니다. 사용자 ID를 그대로 스레드 ID로 쓰면 동시에 열린 두 상담이 섞일 수 있으므로 대화 단위를 구분하는 식별자가 필요합니다.
체크포인터는 그래프 상태를 저장하고 Store는 여러 스레드가 공유할 사용자 선호 같은 데이터를 저장합니다. 이번 customer-a와 customer-b 비교는 스레드 격리를 보여 주며, 프로세스 종료 뒤 복구는 증명하지 않습니다. 그 경계는 파일 또는 데이터베이스 기반 저장기를 사용하는 다음 절에서 다룹니다.
6실험 결과 해석
customer-a의 첫 결과는 3, 두 번째 결과는 7이며 저장된 최신 values의 total도 7입니다. customer-b는 4에서 시작합니다. 기록 수가 각각 6과 3인 것은 customer-a가 두 번, customer-b가 한 번 실행됐기 때문입니다. 기록 수 자체를 대화 턴 수로 해석하지 않습니다.
같은 thread_id의 두 실행은 total 7로 이어졌고 다른 thread_id는 total 4에서 독립적으로 시작했습니다.
7주의할 점과 실무 메모
InMemorySaver의 내용은 Python 프로세스가 끝나면 사라집니다.
thread_id를 사용자 입력에서 그대로 받기보다 인증된 사용자와 대화 식별자에서 서버가 생성합니다.
체크포인트 상태에는 비밀 키와 불필요한 개인정보를 넣지 않습니다.
8정리와 다음 절
같은 thread_id는 최신 체크포인트의 total을 이어 받아 7을 만들었습니다.
다른 thread_id는 customer-a의 값을 읽지 않아 total 4에서 시작했습니다.
InMemorySaver는 프로세스 종료 뒤 상태가 남지 않으므로 다음 절의 PostgreSQL 저장소와 용도가 다릅니다.
다음 학습과 이어지는 지점 — 다음 절에서는 메모리 대신 PostgreSQL에 체크포인트 표를 만듭니다.
9복습 문제
1. customer-a의 두 번째 total이 7인 이유는 무엇인가요?
해설 — 같은 thread_id의 최신 체크포인트 total 3을 읽고 새 입력 4를 더했기 때문입니다.
2. customer-b의 total이 4인 결과가 보여 주는 것은 무엇인가요?
해설 — 다른 thread_id는 customer-a의 저장 상태를 읽지 않는다는 것을 보여 줍니다.
3. StateSnapshot.next가 빈 튜플이라는 뜻은 무엇인가요?
해설 — 현재 실행에서 이어서 실행할 노드가 없다는 뜻입니다.
4. InMemorySaver를 운영 재개 저장소로 쓰기 어려운 이유는 무엇인가요?
해설 — 프로세스가 종료되면 메모리의 체크포인트도 사라지기 때문입니다.

1학습 목표
PostgresSaver.setup()이 준비하는 저장 표의 역할을 설명할 수 있습니다.
setup 전 UndefinedTable과 setup 뒤 value 12를 서로 다른 근거로 읽을 수 있습니다.
스키마 준비를 일반 그래프 요청과 분리해야 하는 이유를 설명할 수 있습니다.
2이 내용을 배우는 이유
운영 프로세스가 종료되어도 상태를 남기려면 별도 데이터베이스가 필요합니다. Ch4에서 배운 스키마와 표 조회를 체크포인터 준비에 적용합니다.
이 실습은 빈 ch23_lab 스키마에서 setup 전 오류와 setup 뒤의 표 목록을 비교합니다. 그래프가 value를 6에서 12로 계산한 사실과 체크포인트 표가 만들어진 사실을 따로 확인합니다.
3앞에서 배운 내용
Ch4에서 PostgreSQL 스키마와 information_schema.tables를 조회했습니다. 앞 절에서는 같은 thread_id가 메모리 체크포인트를 찾는 과정을 확인했습니다. 이번 절은 그 저장 위치를 ch23_lab 스키마로 옮기고, Ch4의 표 조회로 실제 생성 결과를 확인합니다.
4핵심 개념
구체적인 상황
서버가 재시작된 뒤에도 주문 처리 위치를 찾으려면 체크포인트가 애플리케이션 메모리 밖에 있어야 합니다. PostgreSQL은 여러 프로세스가 같은 저장소를 사용할 수 있지만, PostgresSaver가 사용할 표를 먼저 준비해야 합니다.
정의
PostgresSaver는 PostgreSQL에 체크포인트와 중간 쓰기를 저장하는 구현입니다. 최초 한 번 setup()을 호출해야 필요한 표와 마이그레이션 기록이 생성됩니다.
PostgresSaver.from_conn_string()은 autocommit과 dict_row를 갖춘 연결을 준비합니다. setup()은 checkpoint_migrations, checkpoints, checkpoint_blobs, checkpoint_writes 표를 생성하거나 필요한 마이그레이션을 적용합니다. 새 배포 환경에서 한 번 실행하고 일반 요청마다 반복하지 않습니다.
코드를 읽는 순서
PostgresSaver는 체크포인트와 pending write를 PostgreSQL 표에 저장하는 구현입니다. 데이터베이스 URI는 연결 위치를, search_path는 이 실습이 사용할 스키마를 정합니다. PostgresSaver(conn)은 이미 열린 연결을 사용하며, setup()은 필요한 표와 마이그레이션을 준비합니다. 저장기를 만든 것과 저장 구조를 준비한 것은 서로 다른 단계입니다.
Before는 새 스키마에서 setup() 없이 그래프를 실행해 실제 데이터베이스 오류를 확인합니다. After는 같은 연결에서 setup()을 먼저 호출한 뒤 체크포인터를 붙여 실행합니다. checkpoints는 상태 스냅샷을, checkpoint_writes는 단계 안의 쓰기를 저장하는 핵심 표입니다. 표가 존재한다는 사실과 운영 권한·백업·성능이 준비됐다는 사실은 구분해야 합니다.
도식 읽기
‘PostgreSQL 연결’ 다음의 ‘PostgresSaver.setup’ 상자가 준비 단계입니다. 그 결과 ‘체크포인트 표’가 생겨야 ‘그래프 실행 저장’이 성공합니다. Before의 UndefinedTable은 두 번째 상자를 건너뛴 경로이고, After의 네 표 목록은 정상 경로입니다.
5실행 예제
로컬 postgres:17 컨테이너의 ch23_lab 스키마를 비우고 value를 두 배로 만드는 그래프를 정의합니다. Before는 setup 없이 thread_id before를 실행해 실제 UndefinedTable을 수집합니다. After는 setup을 호출한 뒤 thread_id after를 실행하고 information_schema에서 표 이름을 읽습니다.
확인할 점 — setup 전에는 UndefinedTable이 발생했고 setup 뒤에는 value 12와 checkpoints, checkpoint_writes 표를 확인했습니다.
다른 상황과 적용 경계
개발자의 로컬 실험은 SQLite로 충분할 수 있지만 여러 서버가 같은 실행을 재개해야 하면 공유 데이터베이스가 필요합니다. 운영에서는 애플리케이션 시작 때마다 무제한으로 스키마 권한을 주기보다 배포 마이그레이션과 실행 계정의 권한을 분리합니다.
연결 문자열에는 비밀번호가 포함될 수 있으므로 로그나 노트북 출력에 원문을 남기지 않습니다. 이 실습은 로컬 PostgreSQL의 별도 스키마에서 표 생성과 값 12 저장을 확인합니다. 장애 조치, 연결 풀, 동시 실행 성능은 별도 운영 검증이 필요합니다.
6일부러 실패해 보기
Before의 오류는 학생이 만든 검사 함수가 아니라 PostgreSQL이 존재하지 않는 checkpoints 관계를 조회하며 반환한 오류입니다. After의 value는 6에서 12가 됐고 checkpoints와 checkpoint_writes가 모두 확인됐습니다. 계산 성공과 저장 스키마 준비를 서로 다른 출력으로 검증한 셈입니다.
setup 전에는 UndefinedTable이 발생했고 setup 뒤에는 value 12와 checkpoints, checkpoint_writes 표를 확인했습니다.
7주의할 점과 실무 메모
실습 URI의 postgres/postgres 계정은 로컬 컨테이너 전용이며 운영 자격 증명으로 사용하지 않습니다.
수동 psycopg 연결을 넘길 때는 autocommit=True와 row_factory=dict_row 요구를 공식 README에서 다시 확인합니다.
setup을 명시적 트랜잭션 안에서 호출하지 않습니다. 일부 마이그레이션은 CREATE INDEX CONCURRENTLY를 사용합니다.
8정리와 다음 절
setup 전에는 checkpoints 표가 없어 PostgreSQL이 UndefinedTable을 반환했습니다.
setup 뒤에는 checkpoints와 checkpoint_writes를 포함한 저장 표와 value 12를 확인했습니다.
setup은 배포 준비 단계이며, 일반 요청마다 실행하는 그래프 동작이 아닙니다.
다음 학습과 이어지는 지점 — 다음 절에서는 연결과 그래프 객체를 새로 만들어도 같은 스레드를 이어 갑니다.
9복습 문제
1. setup 전 실행에서 발생한 데이터베이스 오류는 무엇인가요?
해설 — checkpoints 표가 없어서 PostgreSQL의 UndefinedTable이 발생했습니다.
2. checkpoint_writes 표는 어떤 정보를 저장하나요?
해설 — 완전한 다음 체크포인트 전의 중간 쓰기와 pending writes를 저장합니다.
3. information_schema.tables를 조회한 이유는 무엇인가요?
해설 — setup이 실제 PostgreSQL 스키마에 표를 만들었는지 확인하기 위해서입니다.
4. setup을 일반 요청마다 호출하지 않는 이유는 무엇인가요?
해설 — 배포 준비 단계의 스키마 마이그레이션이며 매 요청의 그래프 실행과 역할이 다르기 때문입니다.

앞 절에서 PostgresSaver가 프로세스 밖의 데이터베이스에 체크포인트를 남기는 구조를 확인했습니다. 이번 절은 설치 부담을 줄이기 위해 SQLiteSaver를 사용하지만, 첫 연결을 닫고 새 연결과 새 그래프 객체를 만드는 방식으로 프로세스 경계를 모사합니다.
4핵심 개념
구체적인 상황
사용자가 질문 1을 보낸 요청과 질문 2를 보낸 요청은 서로 다른 웹 요청에서 처리될 수 있습니다. 두 번째 요청의 코드가 첫 번째 graph 변수를 참조하지 않아도 저장 파일과 thread_id가 같으면 앞선 턴을 불러올 수 있어야 합니다.
정의
재개(resume)는 같은 thread_id의 최신 체크포인트를 읽고 새 입력을 기존 상태에 합쳐 다음 실행을 시작하는 동작입니다. 저장소 연결과 그래프 객체가 달라져도 thread_id와 체크포인트가 같으면 상태를 찾을 수 있습니다.
turns 채널에는 operator.add 리듀서를 지정합니다. 새 입력 목록과 노드가 반환한 목록을 기존 목록 뒤에 더하므로 질문과 답변 순서가 보존됩니다. 리듀서가 없으면 새 turns 값이 이전 목록을 덮어씁니다. 첫 번째 연결을 닫는 것은 graph_first라는 Python 객체를 더 이상 사용할 수 없게 만드는 과정입니다. 두 번째 연결은 SQLite 파일에 저장된 채널 값과 다음 노드 정보만으로 실행을 구성합니다.
코드를 읽는 순서
SqliteSaver는 체크포인트를 SQLite 파일에 저장하므로 Python 그래프 객체를 새로 만들어도 같은 파일과 thread_id를 사용하면 상태를 읽을 수 있습니다. sqlite3.connect(..., check_same_thread=False)는 파일 연결을 만들고, SqliteSaver(conn)은 그 연결을 체크포인터 인터페이스로 감쌉니다. 연결의 생명주기와 그래프 객체의 생명주기를 구분합니다.
상태의 turns에는 Annotated[list[str], operator.add] 리듀서가 붙어 있습니다. 노드가 새 턴 목록을 반환하면 기존 목록을 덮어쓰지 않고 이어 붙입니다. 두 번째 프로그램 객체에서 invoke({"turns": ["질문 2"]}, 같은 config)를 호출하면 저장된 이전 턴을 먼저 불러온 뒤 새 입력과 노드 출력을 합칩니다.

웹 서버가 재시작된 뒤 사용자가 같은 상담을 이어 가는 상황에 이 패턴을 적용할 수 있습니다. 새 상담을 시작하려면 SQLite 파일을 지우는 대신 새 thread_id를 사용해야 기존 기록과 새 기록의 경계가 분명합니다.

2이 내용을 배우는 이유
체크포인트를 자주 동기 저장하면 복구 범위가 작아지지만 다음 노드가 기다리는 시간이 늘어날 수 있습니다. 저장 시점을 선택하려면 세 모드의 차이를 실제 중단에서 확인해야 합니다.
이 실습은 second 노드에 들어간 즉시 자식 프로세스를 종료합니다. 이 종료 시점에서는 exit가 first를 다시 실행했고, async와 sync는 first 결과를 읽어 second만 다시 실행했습니다.
3앞에서 배운 내용
앞 절은 정상 종료한 두 프로세스 사이의 재개를 확인했습니다. 이제 정상 종료라는 조건을 없앱니다. SQLiteSaver와 같은 thread_id는 유지하고, 두 번째 노드에 들어간 자식 프로세스를 운영체제 수준에서 종료해 durability 인자만 비교합니다.
4핵심 개념
구체적인 상황
first 노드가 분류를 마치고 second 노드가 긴 외부 처리를 시작한 순간 서버가 종료됐다고 가정합니다. 복구 뒤 first를 다시 실행해야 하는지, second부터 시작할 수 있는지는 first 결과가 종료 전에 저장됐는지에 달려 있습니다.
정의
내구성(durability) 모드는 체크포인트 저장 완료와 다음 노드 실행의 관계를 정합니다. sync는 저장 완료 뒤 다음 단계로 가고, async는 다음 단계와 저장을 겹쳐 실행하며, exit는 실행이 끝날 때 저장합니다.
sync는 first 체크포인트 저장이 완료된 뒤 second를 시작합니다. async는 저장과 second 실행을 겹치므로 지연을 줄일 수 있지만 매우 이른 종료에서는 저장 완료 여부가 달라질 수 있습니다. exit는 그래프가 끝날 때만 저장하므로 중간 종료에서 완료된 노드 결과가 남지 않습니다.
코드를 읽는 순서
내구 실행 모드는 완료된 단계의 체크포인트를 저장 호출과 어느 시점에 맞출지 정합니다. sync는 다음 단계로 진행하기 전에 저장 완료를 기다리고, async는 저장을 진행하면서 다음 작업을 이어 가며, exit는 실행이 끝날 때 상태를 기록합니다. 저장 시점이 다르면 갑작스러운 프로세스 종료 직전에 디스크에 남은 범위가 달라질 수 있습니다.
kill_and_resume(mode)는 같은 그래프와 입력을 자식 프로세스에서 실행하고, 두 번째 노드 진입을 알리는 ready 파일이 생기면 프로세스를 종료합니다. read_saved는 SQLite에서 최신 channel_values를 읽고, 같은 모드 이름을 thread_id로 사용해 새 프로세스로 재개합니다. ready 파일은 체크포인트 저장 완료 신호가 아니라 노드 진입 신호입니다.
도식 읽기
‘노드 1 완료’에서 세 경로로 갈라집니다. sync 상자는 저장 뒤 이동, async 상자는 저장과 이동의 겹침, exit 상자는 종료 시 저장을 뜻합니다. 실제 calls에서 exit만 first가 두 번 나타나며 두 체크포인트 모드는 second만 다시 실행합니다.

2이 내용을 배우는 이유
병렬 처리 하나가 실패했다고 이미 성공한 느린 작업까지 반복하면 비용과 부작용이 늘어납니다. 같은 단계의 부분 성공을 보존하는 단위가 필요합니다.
실습에서는 good과 flaky를 같은 superstep에서 시작합니다. 첫 실행 뒤 good은 한 번, flaky는 한 번 기록되며, 실패 원인을 없애고 재개하면 flaky만 한 번 더 실행되는지를 확인합니다.
3앞에서 배운 내용
앞 절에서는 순차 노드의 경계에서 저장 모드를 비교했습니다. 이번 절은 START에서 good과 flaky가 동시에 시작하는 같은 superstep을 사용합니다. 하나가 성공하고 하나가 실패한 부분 완료 상태가 재개에 어떤 영향을 주는지 살펴봅니다.
4핵심 개념
구체적인 상황
같은 단계에서 문서 저장은 성공했지만 알림 전송은 일시 오류로 실패했다고 가정합니다. 전체 단계를 반복하면 문서 저장이 두 번 실행될 수 있습니다. 성공한 작업의 반환값을 중간 쓰기로 보존하면 실패한 알림만 다시 시도할 수 있습니다.
정의
pending writes는 체크포인트 단계가 완전히 끝나기 전에 성공한 작업의 중간 쓰기입니다. 재개할 때 런타임은 이 결과를 사용해 성공한 노드를 건너뛰고 실패한 노드만 다시 실행할 수 있습니다.
checkpoint_writes 계열의 pending writes는 superstep이 완전히 끝나기 전에 각 task가 반환한 쓰기를 보존합니다. StateSnapshot.tasks에는 성공한 good의 result와 실패한 flaky의 error가 함께 나타납니다. 재개 입력으로 None을 전달하면 새 실행을 시작하지 않고 이 미완료 단계에서 이어 갑니다.
코드를 읽는 순서
LangGraph의 한 superstep에서는 여러 노드가 병렬로 실행될 수 있습니다. good과 flaky는 START에서 동시에 갈라지는 같은 단계의 노드입니다. results에는 리스트를 합치는 리듀서를 붙여 두 노드의 성공 결과가 하나의 상태 채널에 모이게 합니다. flaky가 오류를 내더라도 good이 이미 반환한 쓰기는 pending write로 체크포인터에 남을 수 있습니다.
첫 실행 뒤 snapshot.tasks에는 각 작업의 결과나 오류가 기록됩니다. graph.invoke(None, config)는 새 입력을 넣지 않고 실패한 단계에서 재개합니다. 저장된 good의 결과를 재사용하고 실패한 flaky만 다시 실행하므로 호출 로그에서 good은 한 번, flaky는 두 번 나타납니다.
도식 읽기
도식의 첫 상자에서 good과 flaky가 같은 단계로 실행됩니다. good은 ‘pending write’에 도달하고 flaky는 실패합니다. 마지막 ‘재개: flaky만 재실행’ 경로는 calls after resume의 good 1회, flaky 2회와 대응합니다.
5실행 예제
trace_path는 실제 함수 호출 이름을 한 줄씩 기록합니다. allow_path가 없을 때 flaky는 RuntimeError를 냅니다. 오류를 받은 뒤 snapshot.tasks를 읽고, allow_path를 만든 다음 graph.invoke(None, config)으로 같은 superstep을 재개합니다.
확인할 점 — 첫 실행에서 good과 flaky가 한 번씩 실행됐고 재개 뒤 good은 총 1회, flaky는 총 2회였습니다. 최종 상태에는 두 결과가 모두 포함됐습니다.
다른 상황과 적용 경계
문서 세 개를 병렬 분석하다 하나만 실패한 경우 성공한 두 분석을 다시 호출하지 않는 데 같은 원리를 사용할 수 있습니다. 다만 노드가 체크포인터 밖의 파일이나 외부 API에 먼저 쓴 결과까지 pending write가 관리하지는 않습니다. 외부 부작용에는 다음 절의 멱등성 설계가 필요합니다.
superstep 전체가 데이터베이스 트랜잭션처럼 모두 취소된다고 설명하면 이번 출력과 맞지 않습니다. 성공한 노드의 상태 쓰기는 보존되고 실패한 작업만 다시 실행될 수 있습니다. 실제 실행 순서는 병렬 스케줄링에 따라 달라질 수 있으므로 로그의 순서보다 호출 횟수와 최종 결과를 봅니다.
6실험 결과 해석
첫 호출 로그는 good, flaky이며 tasks에는 good의 한 결과와 flaky의 오류가 보입니다. 재개 뒤 로그에는 flaky만 한 번 추가됩니다. 최종 results에 good-result와 flaky-result가 모두 있으므로 성공한 중간 쓰기는 보존되고 실패한 task만 다시 실행됐습니다.
첫 실행에서 good과 flaky가 한 번씩 실행됐고 재개 뒤 good은 총 1회, flaky는 총 2회였습니다. 최종 상태에는 두 결과가 모두 포함됐습니다.
7주의할 점과 실무 메모
pending writes는 같은 superstep에서 런타임이 받은 상태 쓰기를 보존하며 외부 시스템의 부작용을 되돌리지 않습니다.
병렬 노드가 같은 키를 쓰면 리듀서 또는 충돌 처리 규칙이 필요합니다.
실패 원인이 계속 남아 있으면 재개도 다시 실패하므로 재시도 한도와 운영 알림을 둡니다.
8정리와 다음 절
good의 성공 result와 flaky의 오류가 같은 상태 기록에 남았습니다.
재개 뒤 good은 총 한 번, flaky는 총 두 번 실행돼 부분 성공이 보존됐습니다.
pending writes는 런타임 상태의 기능이므로 외부 쓰기 중복은 다음 절의 멱등 키로 다룹니다.
다음 학습과 이어지는 지점 — 다음 절에서는 노드 자체가 다시 시작될 때 외부 쓰기의 중복을 막습니다.
9복습 문제
1. 재개 뒤 good이 다시 실행되지 않은 증거는 무엇인가요?
해설 — trace에서 good은 전체 1회이고 flaky만 2회입니다.
2. StateSnapshot.tasks에서 확인한 두 항목의 차이는 무엇인가요?
해설 — good에는 result가 있고 flaky에는 RuntimeError가 있습니다.
3. invoke(None, config)의 None은 무엇을 뜻하나요?
해설 — 새 입력을 추가하지 않고 저장된 미완료 실행에서 이어 간다는 뜻입니다.
4. pending writes가 외부 결제 중복까지 막아 주나요?
해설 — 막아 주지 않습니다. 외부 쓰기는 별도의 멱등 키가 필요합니다.

노드 재시작이 외부 쓰기를 중복할 수 있는 실행 경로를 설명할 수 있습니다.

운영 환경에서 원자적 고유 제약이 필요한 이유를 설명할 수 있습니다.
2이 내용을 배우는 이유
체크포인트는 노드 안의 각 코드 줄 뒤에 저장되지 않습니다. 외부 쓰기 뒤 상태 반환 전에 프로세스가 끝나면 같은 노드가 다시 시작됩니다.
이 실습은 order-2306을 파일에 쓴 직후 자식 프로세스를 종료합니다. 같은 SQLite 상태로 재개했을 때 단순 추가는 두 줄을 남기고, operation_id를 확인한 경로는 한 줄만 남기는지를 확인합니다.
3앞에서 배운 내용
앞 절의 good 노드는 상태 반환까지 마쳐 pending write가 생겼습니다. 이번 절은 외부 파일에 주문 번호를 쓴 뒤 상태를 반환하기 전에 프로세스를 종료합니다. 체크포인트가 다음 노드 경계로 이동하지 못했으므로 같은 charge 노드가 처음부터 다시 시작됩니다.
4핵심 개념
구체적인 상황
결제 요청이 외부 서비스에는 반영됐지만 응답을 상태에 저장하기 전에 서버가 종료될 수 있습니다. 재개한 charge가 같은 요청을 다시 보내면 이중 결제가 됩니다. 호출마다 바뀌지 않는 주문 작업 키로 이미 처리했는지 확인해야 합니다.
정의
멱등성(idempotency)은 같은 작업을 여러 번 요청해도 외부 결과가 한 번 적용된 것과 같게 유지되는 성질입니다. operation_id를 이미 처리한 키로 기록하면 재시작한 노드가 중복 쓰기를 건너뛸 수 있습니다.
operation_id는 비즈니스 작업 한 건을 식별합니다. naive 전략은 호출할 때마다 로그에 추가합니다. idempotent 전략은 같은 operation_id가 이미 있으면 추가하지 않습니다. 이 실습의 파일 검사는 실제 운영에서 데이터베이스의 고유 키나 결제 API의 idempotency key에 대응합니다.
코드를 읽는 순서
멱등성(idempotency)은 같은 연산 요청을 여러 번 받아도 외부 결과가 한 번 처리한 것과 같게 유지되는 성질입니다. 체크포인터는 노드 시작과 완료 사이에 프로세스가 종료되면 그 노드를 다시 실행할 수 있습니다. 파일 쓰기는 이미 끝났지만 노드 완료 체크포인트가 없으면 재개 시 같은 주문 번호를 다시 쓸 수 있습니다.
interrupt_then_resume(strategy)는 자식 프로세스가 외부 쓰기를 마친 직후 종료 신호 파일을 만들게 하고, 부모가 그 프로세스를 강제로 종료한 뒤 같은 SQLite와 전략으로 재개합니다. operation_id="order-2306"은 논리적 작업을 식별합니다. idempotent 전략은 이미 처리한 ID인지 검사해 두 번째 쓰기를 건너뜁니다.
도식 읽기
‘외부 쓰기’ 다음 ‘상태 반환 전 종료’가 장애 지점입니다. 재개는 ‘노드 처음부터 재시작’으로 이동합니다. 마지막 ‘operation_id로 중복 차단’ 상자가 After의 한 줄 로그를 설명합니다.

다른 상황과 적용 경계
결제나 이메일 API가 멱등 키를 지원하면 호출자가 작업 ID를 보내고 서버가 이전 결과를 재사용하게 할 수 있습니다. 로컬에서 먼저 조회한 뒤 쓰는 방식은 두 프로세스가 동시에 통과할 수 있으므로 운영 저장소에서는 고유 제약이나 원자적 삽입을 사용해야 합니다.
재시도는 실패한 호출을 다시 시도하는 정책이고 멱등성은 반복 호출이 중복 효과를 만들지 않게 하는 성질입니다. 재시도 횟수를 1로 줄여도 종료 시점의 불확실성은 남습니다. 이번 로그 한 줄은 실습 worker의 중복 차단을 확인하며 외부 서비스 전체의 멱등성을 보장하지 않습니다.

7주의할 점과 실무 메모
확인과 쓰기를 별도 연산으로 구현하면 동시 요청 사이에 경쟁 조건이 생길 수 있으므로 운영에서는 원자적 고유 제약을 사용합니다.

멱등 처리가 어려운 작업은 interrupt 승인과 보상 작업을 함께 설계합니다.

상태 반환 전 종료된 charge 노드는 재개할 때 처음부터 실행됐습니다.

## After: operation_id로 중복 쓰기 차단
