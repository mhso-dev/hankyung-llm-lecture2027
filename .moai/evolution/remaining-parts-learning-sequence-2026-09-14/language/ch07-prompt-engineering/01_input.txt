1학습 목표
system·developer·user 메시지의 책임을 구분할 수 있습니다.
공통 정책, 과업 제약, 개별 입력을 역할별로 배치할 수 있습니다.
두 응답의 원문과 토큰·지연 시간을 같은 기준으로 비교할 수 있습니다.
2이 내용을 배우는 이유
Ch 6에서는 문자열이나 메시지 목록을 모델에 전달하여 첫 응답을 받았습니다. 이제 같은 호출 코드 위에서 지시를 어디에 놓을지 결정합니다. 고객 지원 정책, 답변 형식, 실제 고객 문의를 한 문장에 모두 넣어도 모델은 답할 수 있습니다. 그러나 정책이 바뀌거나 문의가 여러 건으로 늘어나면 어느 부분이 공통 규칙이고 어느 부분이 이번 입력인지 확인하기 어렵습니다. 메시지 역할을 나누면 프롬프트를 읽는 사람이 각 지시의 책임과 변경 범위를 빠르게 찾을 수 있습니다.
역할 분리는 지시를 강하게 만드는 주문이 아닙니다. 서로 맞지 않는 지시는 제공자와 모델의 역할 규칙에 따라 처리되며, 출력은 여전히 실행마다 달라질 수 있습니다. 이 절에서는 역할을 나누면 항상 품질이 오른다고 가정하지 않습니다. 같은 문구를 한 사용자 메시지에 합친 조건과 역할별로 나눈 조건을 실행하여 실제 차이를 확인합니다.
3앞에서 배운 내용
Ch 6의 init_chat_model("openai:gpt-5.4-mini"), invoke(), AIMessage.text, AIMessage.usage_metadata를 사용합니다. 프로젝트 루트의 .env에서 API 키를 읽되 키 값은 출력하지 않습니다. 노트북은 독립 실행되므로 이전 커널의 변수에 의존하지 않습니다.
4핵심 개념
한 문서의 세 칸으로 생각합니다
고객 지원 업무에는 세 종류의 내용이 있습니다. 모든 문의에 적용되는 담당자의 역할, 이번 업무에서 지켜야 할 답변 길이와 금지 사항, 고객마다 달라지는 주문번호와 문의입니다. 세 내용을 한 단락에 붙이면 다음 고객을 처리할 때 무엇을 교체해야 하는지 찾기 어렵습니다. 메시지 역할은 이 세 종류를 구분하는 표지와 같습니다.
정의시스템 메시지 (system message)대화 전체에서 유지할 모델의 역할이나 공통 행동 원칙을 담습니다.개발자 메시지 (developer message)OpenAI API에서 개발자의 지시를 표현하는 역할입니다. 사용자 입력보다 우선하여 따라야 하는 지시로 정의되지만, 다른 제공자에 같은 규칙을 적용할 수는 없습니다.사용자 메시지 (user message)질문, 자료, 주문번호처럼 사례마다 달라지는 입력을 담습니다. LangChain에서는 human으로도 표현합니다.메시지 우선순위서로 맞지 않는 지시가 있을 때 어떤 역할의 지시를 먼저 적용하는지 정한 API 규칙입니다.이식성 (portability)같은 프롬프트 구조를 다른 제공자에서도 적은 수정으로 사용할 수 있는 성질입니다.제약 (constraint)답변 길이, 포함할 필드, 금지할 약속처럼 결과가 지켜야 할 조건입니다.
도식 — 역할과 변경 범위초록 상자 세 개는 모델에 전달할 system·developer·user 입력입니다. 보라 상자는 모델 호출, 노란 상자는 응답 원문과 사용량 측정입니다. 세 화살표는 역할별 메시지가 한 호출에 모이는 방향을 나타냅니다.
도식의 위아래 위치를 모든 제공자의 절대 우선순위로 읽으면 안 됩니다. 이 절의 developer 예제는 OpenAI 모델로 실행합니다. 다른 제공자로 바꾸려면 해당 통합이 이 역할을 지원하는지 확인합니다. 세 제공자를 같은 코드로 비교할 때는 공통 정책을 system, 개별 과제를 human에 두는 구성이 더 이식하기 쉽습니다.
역할을 나누면 수정 지점이 드러납니다
사용자 메시지 하나에 담당자 역할, 금지 사항, 출력 형식, 고객 문의를 모두 쓰면 네 종류의 내용이 섞입니다. 역할을 나눈 구성에서는 담당자의 정체성은 system에, 금지 사항과 형식은 developer에, 고객 원문은 user에 둡니다. 다음 문의에서는 user만 교체할 수 있습니다. 회사의 형식이 바뀌면 developer를 찾으면 됩니다. 이 구분은 유지보수와 검토에 도움이 되지만 좋은 응답을 자동으로 보장하지는 않습니다.
같은 문구를 유지해야 비교가 됩니다
첫 조건에 “고객 지원 담당자로 답하세요”만 쓰고 둘째 조건에 금지 사항과 형식을 추가하면 역할뿐 아니라 지시 내용도 달라집니다. 그러면 차이가 역할 때문인지 추가 문구 때문인지 구분할 수 없습니다. 실습은 role_text와 constraint_text를 먼저 정의합니다. 사용자 메시지 하나 조건에는 두 문자열을 연결하고, 역할 분리 조건에는 같은 두 문자열을 system과 developer에 각각 넣습니다. 질문과 모델도 고정합니다.
지시의 내용과 지시가 놓인 역할을 따로 비교하기
실습의 run(messages)는 이 노트북이 정의한 보조 함수입니다. 메시지 목록을 받아 그 안에서 model.invoke()를 한 번 실행하고, 응답 텍스트·사용량·경과 시간을 딕셔너리로 반환합니다. run()을 정의한 셀은 요청을 보내지 않지만 flat = run(...)과 layered = run(...)은 각각 실제 요청을 보냅니다. 이 구분을 먼저 해야 아래 비교가 두 호출의 결과임을 알 수 있습니다.
예를 들어 한 안내에서는 “한 문장으로 답하세요”를 user에 넣고 다른 안내에서는 같은 문장을 developer에 넣을 수 있습니다. 문장 내용은 같고 역할만 달라집니다. 반면 두 번째 안내에 “주문번호도 포함하세요”를 새로 더했다면 역할과 요구 내용이 함께 바뀝니다. 현재 실습은 역할 문구와 제약 문구를 변수로 보관하여 두 조건이 같은 글자를 사용하는지 코드에서 대조합니다.
역할 분리는 어떤 내용을 교체할지 찾는 데도 쓰입니다. 번역 규칙을 유지하며 번역 대상만 바꾸거나, 상담 정책을 유지하며 고객 문의만 바꿀 수 있습니다. 이 설계상의 이점과 모델 답변의 품질 변화는 별도입니다. 두 응답이 모두 올바르면 이번 입력에서는 역할 배치에 따른 품질 차이를 관찰하지 못했다고 해석합니다.
5실행 예제
동일한 텀블러 파손 문의를 두 번 실행합니다. 첫 조건은 같은 역할 문구와 제약 문구를 사용자 메시지에 합칩니다. 둘째 조건은 system과 developer로 나눕니다. 각 응답에서 원문, 입력·출력·전체 토큰, 지연 시간을 출력합니다.
확인할 점 — 두 원문에서 교환 분류, 주문번호 A-1042, 파손 사진 요청의 뜻이 모두 유지되는지 읽습니다. 단어 포함 표시는 검토 위치를 찾는 보조 자료이며 품질 점수가 아닙니다.
6실험 결과 해석
최종 실행에서 두 조건 모두 세 내용을 올바른 뜻으로 포함했습니다. 역할 분리 조건이 품질을 높였거나 낮췄다는 실패는 관찰하지 못했습니다. 토큰과 지연 수치는 노트북에 저장된 새 실행 출력으로 확인해야 하며, 한 번의 지연 차이로 더 빠른 방식을 고르지 않습니다.
입력 토큰에는 메시지 역할을 나타내는 형식도 반영될 수 있습니다. 모델 제공자가 내부적으로 메시지를 직렬화하는 방식은 로컬 문자열 길이와 일치하지 않을 수 있습니다. 여러 입력에서 역할 효과를 비교하려면 같은 문구를 유지하고 반복 횟수와 판정 기준을 먼저 정해야 합니다. 이 실험의 확실한 결과는 역할별 변경 위치가 코드에서 분명해졌다는 점입니다.
7주의할 점과 실무 메모
역할 지원을 제공자 문서에서 확인합니다. OpenAI developer 역할을 다른 제공자도 같은 뜻으로 처리한다고 가정하지 않습니다.
비밀 값은 메시지에 넣지 않습니다. system 메시지는 비밀 저장소가 아닙니다.
충돌하는 지시를 별도로 시험합니다. 역할을 나눴다는 사실만으로 정책 준수를 단정하지 않습니다.
한 번에 한 조건을 바꿉니다. 역할, 모델, 질문, 예시를 동시에 바꾸면 원인을 분리할 수 없습니다.
업무 분기를 프롬프트에 계속 추가하지 않습니다. 유형별 if-else는 Ch 13의 그래프 조건 분기에서 다룹니다.
8정리와 다음 절
메시지 역할은 공통 정책, 과업 제약, 개별 입력의 변경 범위를 구분합니다.
developer는 제공자별 역할 규칙을 확인해야 합니다.
역할 효과를 비교할 때는 지시 문구와 입력을 고정합니다.
다음 학습과 이어지는 지점 — 02절에서는 페르소나와 실제 과업·출력 제약을 구분합니다.

정답과 해설 — user 또는 human 메시지에 둡니다. 개별 입력과 공통 정책을 분리하기 위해서입니다.
[중] 2. developer 역할의 이식성을 확인해야 하는 이유는 무엇입니까?
정답과 해설 — 역할 이름과 우선순위는 제공자별 API 규칙이기 때문입니다.
[중] 3. ‘사진’ 포함만으로 규정 준수를 판정할 수 없는 문장을 쓰세요.

[상] 4. 역할 비교에서 같은 문구를 유지해야 하는 이유는 무엇입니까?

1학습 목표
페르소나와 과업 지시의 차이를 설명할 수 있습니다.
목표·입력·제약·출력 형식을 프롬프트에 구체적으로 적을 수 있습니다.
응답 길이와 원문을 함께 읽어 제약의 효과를 판단할 수 있습니다.
2이 내용을 배우는 이유
“친절한 상담원처럼 답하세요”는 답변의 말투와 관점을 알려 줍니다. 그러나 무엇을 분류하고 어떤 정보를 포함하며 무엇을 약속하지 말아야 하는지는 알려 주지 않습니다. 실제 업무에서는 친절한 문장보다 주문번호, 다음 행동, 회사 규정이 빠지지 않는 것이 먼저입니다. 페르소나는 도움이 될 수 있지만 과업 명세를 대신하지 못합니다.
이 절에서는 같은 상담원 페르소나를 유지한 채 과업·금지 조건·출력 형식을 추가합니다. 첫 응답이 이미 충분할 수도 있습니다. 실패를 만들려고 질문이나 규정을 바꾸지 않고, 두 원문이 고정된 요구를 어떻게 표현했는지 정직하게 비교합니다.
3앞에서 배운 내용
01절에서 공통 역할을 system, 개별 고객 문의를 user에 두었습니다. 이 절도 같은 텀블러 파손 문의와 gpt-5.4-mini를 사용합니다. 교환, 주문번호 A-1042, 파손 사진이라는 세 단어 포함 여부는 정독 보조 표시로만 사용합니다. 실제 품질은 부정 표현과 문장 뜻을 포함하여 원문을 읽고 판단합니다.
4핵심 개념
직함과 업무 요청서를 구분합니다
새 상담원에게 “당신은 친절한 상담원입니다”라고만 말하면 태도는 알 수 있지만 처리 절차는 알 수 없습니다. 업무 요청서에는 파손 상품을 교환으로 분류하고, 주문번호와 사진을 확인하며, 규정 밖 보상을 약속하지 말라는 내용이 필요합니다. 프롬프트도 같은 방식으로 성격 설명과 수행 조건을 나누어 작성합니다.
정의페르소나 (persona)모델이 답할 때 취할 역할, 관점, 말투를 설명한 것입니다. 전문성의 범위를 좁히는 데 도움을 주지만 사실 정확성이나 절차 준수를 보장하지 않습니다.과업 (task)입력을 받아 어떤 결과를 만들어야 하는지 구체적으로 적은 일입니다.성공 기준 (success criteria)결과가 목적을 충족했다고 판단할 수 있는 관찰 가능한 조건입니다.부정 제약 (negative constraint)규정에 없는 보상 약속처럼 결과에 포함하면 안 되는 행동을 적은 조건입니다.출력 형식 (output format)세 줄, 필드 이름, JSON처럼 결과를 배열하는 모양입니다.
도식 — 페르소나를 과업 명세로 둘러쌉니다초록 상자는 고정 고객 입력입니다. 파란 상자는 작성자가 정하는 페르소나·과업·제약, 보라 상자는 모델, 노란 상자는 원문 평가입니다. 페르소나만 지정할 때와 과업·제약까지 지정할 때 어떤 정보가 추가되는지 읽습니다.
좋은 제약은 확인할 수 있습니다
“좋게 답하세요”는 사람마다 판단이 달라집니다. “분류, 다음 행동, 고객 문장을 세 줄로 작성하세요”는 결과에서 바로 확인할 수 있습니다. “절대로 실수하지 마세요”도 실행 가능한 행동을 알려 주지 않습니다. 대신 “규정에 없는 환불이나 보상을 약속하지 마세요”처럼 금지 대상을 적습니다. 제약이 많아질수록 좋아지는 것도 아닙니다. 서로 겹치거나 충돌하는 문장이 늘면 어떤 규칙을 적용해야 하는지 불분명해집니다.
목표와 형식의 역할이 다릅니다
출력 형식은 결과를 읽고 파싱하기 쉽게 하지만 답의 내용을 채워 주지는 않습니다. 세 줄을 요구해도 어떤 정보를 넣을지 말하지 않으면 중요한 주문번호가 빠질 수 있습니다. 반대로 필수 정보를 모두 적어도 형식이 없으면 긴 상담 문장이 나올 수 있습니다. 목표, 필수 정보, 금지 사항, 형식은 서로 다른 질문에 답합니다. 프롬프트 검토 때 네 항목을 따로 읽어야 합니다.
페르소나를 행동으로 바꾸어 읽는 연습
“친절한 상담원”이라는 페르소나는 말투나 관점을 정하는 단서입니다. “교환 접수에 필요한 사진을 요청하세요”는 입력에서 수행할 행동입니다. “분류·다음 행동·고객 문장의 세 줄”은 출력 배치입니다. 같은 프롬프트에 함께 쓸 수 있지만 각각 무엇을 바꾸는지 나누어 읽으면 결과를 고칠 때 수정 지점을 찾을 수 있습니다.
다른 상황으로 회의록 작성을 생각해 봅니다. “숙련된 비서”만 지정하면 어떤 회의를 어떻게 정리할지는 남아 있습니다. 결정 사항, 담당자, 기한을 추출하되 언급되지 않은 기한은 미정으로 표시하도록 지시하면 확인할 항목과 누락 처리 방식이 정해집니다. 비서라는 역할과 달리 이 조건들은 원문 회의록에서 항목별로 대조할 수 있습니다. 이는 적용 원리를 설명하는 사례이며 아래 모델 실행은 고객 문의로 진행합니다.
금지 조건에도 수행 가능한 다음 행동이 필요합니다. “주문번호를 추측하지 마세요”와 함께 “없으면 주문번호 확인을 요청하세요”를 적으면 정보가 부족할 때의 응답이 구체화됩니다. 모든 상황에 답을 만들어 내도록 요구하면 부족한 정보와 완료된 처리를 구분하기 어렵습니다. 현재 과제에는 주문번호가 있으므로 실제 결과에서 그 값을 정확히 유지했는지 확인합니다.
5실행 예제
첫 조건에는 “친절한 고객 상담원”이라는 페르소나만 둡니다. 둘째 조건은 같은 페르소나를 유지하고 세 줄 형식과 규정 밖 약속 금지를 추가합니다. 고객 문의와 모델은 같습니다. 결과 원문, 글자 수, 토큰, 지연 시간을 출력합니다.
확인할 점 — 최종 실행에서 첫 응답은 220자, 제약을 추가한 응답은 176자였습니다. 두 원문 모두 교환, A-1042, 사진을 올바른 뜻으로 포함했습니다. 제약 조건은 실패를 고친 것이 아니라 이미 충족한 내용을 더 일정한 세 줄 구조로 표현하게 했습니다.
6실험 결과 해석
조건글자 수전체 토큰지연정독 결과
페르소나2202211.287초세 필수 내용 포함
과업·제약1762431.235초세 필수 내용과 세 줄 구조 포함
입력 지시가 길어져 전체 토큰은 늘었지만 출력 글자 수는 줄었습니다. 전체 토큰은 입력과 출력의 합이므로 짧은 답이 항상 더 적은 전체 토큰을 뜻하지 않습니다. 두 조건 모두 과업을 충족했으므로 페르소나 조건의 실패를 재현했다고 표시하지 않습니다. 이 표본은 구체적인 출력 형식이 결과의 배열을 더 예측하기 쉽게 만들었다는 정도만 보여 줍니다.
지연 시간은 약 0.05초 달랐지만 한 번의 실행으로 속도 차이를 일반화할 수 없습니다. 반복 측정에서는 프롬프트 외에 모델, 생성 상한, 입력을 고정하고 중앙값이나 분포를 봅니다. 또한 고객에게 실제로 보낼 문장이라면 회사 정책 담당자가 문구를 검토해야 합니다.
7주의할 점과 실무 메모
전문가 페르소나는 실제 자격이나 사실 검증을 만들지 않습니다.
금지 제약만 나열하지 말고 원하는 행동도 함께 적습니다.
“항상”, “절대” 같은 표현은 실제 예외가 없는지 확인합니다.
길이 제한이 필수 정보와 충돌하면 필수 정보를 우선하도록 기준을 적습니다.
개인정보가 든 고객 원문을 프롬프트 실험 로그에 그대로 남기지 않습니다. 수업은 합성 문의를 사용합니다.
8정리와 다음 절
페르소나는 역할과 말투를 정하며 과업 명세를 대신하지 않습니다.
확인 가능한 목표·필수 정보·금지 사항·출력 형식을 구분합니다.
프롬프트 효과는 원문과 사용량을 함께 읽어 판단합니다.

1학습 목표
Zero-shot과 Few-shot 프롬프트의 차이를 설명할 수 있습니다.
현재 과제를 대표하는 입출력 예시를 고를 수 있습니다.
예시의 관련성과 입력 토큰 증가를 함께 평가할 수 있습니다.
2이 내용을 배우는 이유
출력 형식을 문장으로 길게 설명해도 모델이 작성자의 의도를 다르게 해석할 수 있습니다. 이때 완성된 입출력 한 쌍은 규칙을 구체적인 모양으로 보여 줍니다. 고객 문의와 기대 답안을 함께 주면 필드 순서, 문장 길이, 필요한 정보가 결과에 어떻게 나타나야 하는지 확인할 수 있습니다.
예시는 많다고 좋은 것이 아닙니다. 현재 문의와 관련 없는 예시는 입력 토큰을 사용하고 잘못된 분류 경계를 암시할 수 있습니다. 또한 예시에 있던 주문번호나 표현을 새 사례에 그대로 복사할 위험도 있습니다. 예시 선택은 장식이 아니라 실패 사례와 평가 기준을 근거로 하는 설계 결정입니다.
3앞에서 배운 내용
02절에서 과업과 출력 형식을 말로 지정했습니다. 이 절에서는 같은 세 필드 형식을 유지하고 예시의 존재와 관련성만 비교합니다. 모델, 텀블러 문의, 교환 규정, 확인 기준은 바꾸지 않습니다. 실행 결과는 매번 달라질 수 있으므로 노트북에 저장된 원문을 기준으로 해석합니다.
4핵심 개념
완성본 한 장을 함께 보여 줍니다
처음 작성하는 신청서에서 설명문만 읽는 것보다 올바르게 작성된 견본 한 장을 보면 칸의 의미를 빨리 이해할 수 있습니다. Few-shot 예시는 모델에게도 입력과 기대 출력의 대응을 보여 줍니다. 다만 견본이 다른 업무의 양식이면 오히려 혼동을 줄 수 있습니다.
정의Zero-shot 프롬프트현재 과업의 입출력 예시 없이 지시와 질문만 주는 방식입니다.Few-shot 프롬프트소수의 예시 입력과 예시 출력을 함께 제공하여 원하는 행동을 보여 주는 방식입니다.예시 선택 (example selection)평가하려는 입력의 형식, 주제, 경계 사례를 대표하는 예시를 고르는 과정입니다.관련성 (relevance)예시가 현재 과제의 판단 기준과 출력 형태를 얼마나 직접 보여 주는지 나타냅니다.경계 사례 (edge case)두 분류가 헷갈리거나 일부 정보가 빠져 일반 규칙만으로 처리하기 어려운 입력입니다.데이터 누출 (data leakage)평가 답안이나 평가 대상 자체가 예시에 섞여 결과가 실제 능력보다 좋아 보이는 문제입니다.
도식 — 예시는 선택을 거쳐 프롬프트에 들어갑니다초록 예시 후보 가운데 현재 파손 교환 과제와 판단 기준이 맞는 예시를 선택합니다. 선택된 예시는 파란 현재 질문과 함께 보라 모델 호출로 이동하고, 노란 측정 상자에서 필수 내용과 토큰을 확인합니다.
형식과 판단 근거를 함께 대표해야 합니다
뉴스레터 글꼴 설정 예시는 “분류/다음 행동/고객 문장”이라는 표면 형식은 보여 줍니다. 그러나 파손 상품의 사진과 주문번호 확인이라는 판단 근거는 보여 주지 못합니다. 셔츠 단추 파손 예시는 상품 하자, 교환, 사진 확인이라는 현재 과제의 구조를 공유합니다. 좋은 예시는 단어가 비슷한 문장이 아니라 어떤 근거로 어떤 출력을 내야 하는지 보여 주는 사례입니다.
예시를 평가 답안으로 만들지 않습니다
현재 평가 문의의 주문번호 A-1042와 정답 문장을 예시에 그대로 넣으면 모델은 과업을 해결하지 않고 복사할 수 있습니다. 실습의 관련 예시는 다른 상품과 다른 주문번호 B-203을 사용합니다. 공통 판단은 유지하되 개별 값은 다르게 둡니다. 예시 집합을 변경하면 버전 또는 식별자를 남겨 어떤 결과가 어떤 예시에서 나왔는지 추적합니다.
동적 선택은 뒤 단계입니다
LangChain은 많은 예시 중 관련 항목을 선택하는 구성도 제공합니다. 그러나 처음부터 선택기를 숨기면 왜 그 예시가 들어왔는지 알기 어렵습니다. 이 절에서는 작은 고정 예시를 직접 읽고 비교합니다. Ch 9에서 검색을 배우면 관련 자료를 고르는 과정과 연결할 수 있습니다.
예시의 입력과 답에서 각각 무엇을 배우는가
Few-shot의 한 예시는 요청 문장 하나가 아니라 입력과 원하는 출력의 대응입니다. 파손된 셔츠 문의는 어떤 사실을 확인할지 보여 주고, 예시 답은 그 사실을 교환 분류와 사진 요청으로 어떻게 연결할지 보여 줍니다. relevant_example + "
" + TASK는 예시와 현재 문의 사이에 빈 줄을 넣어 하나의 문자열을 만들며, 모델의 가중치를 다시 학습하는 코드는 아닙니다.
감정 분류로 옮기면 “배송은 빨랐지만 제품이 깨졌습니다”처럼 판단이 갈리는 문장이 경계 사례가 됩니다. 긍정 단어가 포함되어도 전체 평가를 부정으로 볼지, 혼합으로 둘지를 예시와 기준에서 일치시켜야 합니다. 쉬운 긍정 예시만 여러 개 넣는 것보다 실제로 혼동하는 판단을 드러내는 예시가 학습 목적에 맞습니다. 단, 효과는 별도 입력에서 확인해야 합니다.
예시는 그대로 복사할 부분과 바꿔야 할 부분을 함께 가집니다. 출력 필드 순서는 재사용할 수 있지만 B-203이라는 주문번호는 현재 A-1042로 바뀌어야 합니다. 관련 예시를 선택했다는 사실만으로 이 구분이 보장되지는 않습니다. 아래 원문에서 예시 주문번호가 섞였는지, 현재 주문번호가 누락됐는지, 필요한 행동이 유지됐는지를 각각 읽습니다.
5실행 예제
Zero-shot, 관련 예시 한 개, 형식만 비슷한 관련 없는 예시 한 개를 비교합니다. 세 조건 모두 현재 질문과 시스템 형식 지시는 같습니다. 예시 조건만 입력 토큰이 늘어납니다. 각 원문에서 새 주문번호가 유지되는지 반드시 읽습니다.
확인할 점 — Zero-shot 응답은 A-1042를 포함했습니다. 관련 예시는 교환과 사진을 언급했지만 A-1042를 쓰지 않았고, 관련 없는 예시는 세 항목을 모두 언급했습니다. 이번 표본에서는 예시 추가가 세 확인 항목을 더 잘 보존하지 못했습니다.

예시 속 이름·주문번호가 새 답에 복사되는지 확인합니다.

관련 예시도 현재 입력의 필수 값을 생략하게 만들 수 있으므로 원문을 읽습니다.
예시 추가에는 토큰 비용과 데이터 누출 위험이 따릅니다.

1학습 목표
ChatPromptTemplate으로 메시지 틀을 만들 수 있습니다.
MessagesPlaceholder에 선택적 대화 기록을 삽입할 수 있습니다.
템플릿 변수와 완성된 메시지를 구분하여 검사할 수 있습니다.
2이 내용을 배우는 이유
문자열을 더하여 프롬프트를 만들면 변수의 경계와 메시지 역할을 놓치기 쉽습니다. 질문이 바뀔 때마다 system 문구까지 복사하면 수정본이 여러 곳에 생깁니다. ChatPromptTemplate은 변하지 않는 메시지 구조와 실행할 때 채울 값을 구분합니다. 같은 형식을 여러 문의에 재사용하면서도 실제 모델에 전달된 메시지 목록을 확인할 수 있습니다.
대화형 서비스에는 과거 메시지가 있을 때도 있고 첫 요청처럼 없을 때도 있습니다. MessagesPlaceholder는 이미 만들어진 메시지 목록을 지정한 위치에 삽입합니다. 다만 기록을 많이 넣으면 비용과 혼동이 늘 수 있습니다. 이 절에서는 작은 기록 한 턴만 사용하여 구조를 확인하고, 길이 예산과 선택은 Ch 8에서 다룹니다.
3앞에서 배운 내용
01절에서 system과 user 메시지의 책임을 구분했고, 03절에서는 예시 입출력 쌍을 메시지에 추가했습니다. 이제 그 구조를 재사용 가능한 틀로 표현합니다. 모델 호출, AIMessage.text, 사용량 기록은 같습니다. 노트북은 기록 없음과 한 턴 있음의 두 조건을 실행합니다.
4핵심 개념
양식과 작성값을 나눕니다
신청서 양식에는 “이름”, “연락처”, “요청 내용”이라는 칸이 있고 사람마다 다른 값을 채웁니다. 프롬프트 템플릿도 고정 문장 속 {format_rule}과 {question} 자리에 실행값을 넣습니다. 양식 자체를 수정하지 않아도 여러 질문을 같은 구조로 처리할 수 있습니다.
정의프롬프트 템플릿 (prompt template)고정 메시지와 나중에 채울 변수를 함께 정의한 재사용 가능한 틀입니다.ChatPromptTemplate여러 역할의 채팅 메시지를 순서대로 구성하고 변수 값을 받아 완성된 프롬프트 값을 만드는 LangChain 클래스입니다.템플릿 변수{question}처럼 실행할 때 실제 값으로 바뀌는 자리입니다.MessagesPlaceholder문자열 한 개가 아니라 메시지 객체 목록을 템플릿의 지정 위치에 삽입합니다.optional=True해당 메시지 목록이 없어도 템플릿을 완성할 수 있게 하는 설정입니다.n_messages목록 뒤쪽에서 포함할 최근 메시지 수를 제한하는 선택 인자입니다.
도식 — 틀에 값을 넣고 메시지 목록을 확인합니다파란 템플릿에 초록 질문과 대화 기록을 넣으면 역할이 보존된 메시지 목록이 만들어집니다. 보라 모델은 완성된 목록만 받으며, 노란 측정 단계에서 메시지 수와 응답 원문을 확인합니다.
문자열 변수와 메시지 목록은 다릅니다
{question}에는 텍스트가 들어갑니다. 반면 history에는 ("human", "..."), ("ai", "...")처럼 역할을 가진 메시지 목록이 들어갑니다. 과거 대화를 하나의 긴 문자열로 합치면 누가 어떤 말을 했는지 경계가 사라질 수 있습니다. MessagesPlaceholder는 역할과 순서를 유지한 채 목록을 삽입합니다.
템플릿의 invoke와 모델의 invoke는 다른 단계입니다
ChatPromptTemplate.from_messages(...)는 메시지의 틀을 만드는 클래스 메서드입니다. ("human", "{question}")에는 현재 질문 대신 변수 자리만 들어 있습니다. 일반 문자열의 {question}을 템플릿이 읽고, 이후 base_values["question"]의 값으로 채웁니다. Python f 문자열처럼 정의 즉시 치환되는 코드와 구분합니다.
prompt.invoke(base_values)는 빈칸을 채워 ChatPromptValue를 만듭니다. 여기서 invoke를 호출해도 모델 서버에 질문하지 않습니다. 이어 붙인 .to_messages()가 이를 역할 있는 메시지 객체 목록으로 바꿉니다. 실제 모델 요청은 그 목록을 run(first_messages)에 넘겼을 때 함수 안의 model.invoke()에서 발생합니다. 같은 메서드 이름이라도 점 앞의 객체가 무엇인지 확인해야 합니다.
예를 들어 번역 템플릿의 언어와 원문은 문자열 변수이고, 이전 번역 요청과 답의 쌍은 메시지 목록입니다. MessagesPlaceholder("history", optional=True)는 그 목록이 들어갈 위치를 정합니다. 이 객체가 과거 대화를 저장하거나 찾아 주는 것은 아닙니다. 현재 코드가 history 값을 넘긴 경우에만 해당 메시지가 목록에 삽입됩니다. n_messages는 메시지 개수 기준이므로 대화 한 턴과 메시지 하나를 같게 세지 않습니다.
선택적 기록과 필수 기록을 구분합니다
기본 MessagesPlaceholder("history")는 값을 요구합니다. 첫 요청에는 기록이 없으므로 변수를 넘기지 않으면 템플릿 완성 단계에서 오류가 날 수 있습니다. optional=True를 사용하면 기록이 없는 경우 빈 목록처럼 처리할 수 있습니다. 이 설정은 과거 대화를 임의로 무시한다는 뜻이 아니라, 기록이 없어도 정상인 입력 형태를 명시한 것입니다.
완성된 메시지를 먼저 봅니다
템플릿 코드가 의도대로 보여도 변수 값에 중괄호가 남거나 메시지 순서가 바뀔 수 있습니다. 모델을 호출하기 전에 prompt.invoke(values).to_messages()를 출력하면 각 메시지의 역할과 내용을 확인할 수 있습니다. 디버깅에서는 템플릿 원문, 입력값, 완성 메시지, 모델 응답을 서로 다른 단계로 보존합니다.
최근 메시지만 자를 때 잃는 정보가 있습니다
n_messages로 최근 몇 개만 남길 수 있지만 오래된 정책이나 고객의 중요한 요구도 함께 사라질 수 있습니다. 단순히 메시지 수가 줄었다는 사실은 품질 개선을 뜻하지 않습니다. 무엇을 보존할지 정하고 원문과 대조해야 합니다. 이 문제는 Ch 8의 Select와 Compress에서 더 자세히 다룹니다.
5실행 예제
템플릿은 system 지시, 선택적 history, 현재 human 질문 순서입니다. 첫 실행은 history를 넘기지 않아 메시지 두 개를 만듭니다. 둘째 실행은 고객의 “세 줄 이내” 요청과 이전 답을 추가하여 메시지 네 개를 만듭니다. 현재 고객 문의와 평가 기준은 같습니다.
확인할 점 — 첫 메시지 목록은 system과 human 두 개, 기록을 추가한 목록은 네 개입니다. 두 응답 모두 교환, A-1042, 사진을 올바른 뜻으로 포함했습니다. 기록이 있는 응답은 세 줄 구조를 따랐습니다.

두 조건 모두 과업을 충족했으므로 기록 없음 조건을 실패로 부르지 않습니다. 기록을 추가하면 언제나 더 좋은 답이 나온다는 결과도 아닙니다. 실제 서비스에서는 기록이 현재 질문과 관련 있는지, 이전의 민감 정보가 포함되는지, 오래된 제약이 현재 정책과 맞는지 추가로 확인해야 합니다.
7주의할 점과 실무 메모
optional=True는 기록이 없어도 정상인 경우에만 사용합니다.
placeholder에는 문자열이 아니라 역할이 있는 메시지 목록을 전달합니다.
변수 이름이 템플릿과 입력 딕셔너리에서 일치하는지 확인합니다.
모델 호출 전에 to_messages()로 역할과 순서를 검사합니다.
대화 기록을 무제한으로 넣지 말고 개인정보와 오래된 지시를 검토합니다.
8정리와 다음 절
ChatPromptTemplate은 고정 구조와 실행값을 분리합니다.
MessagesPlaceholder는 메시지의 역할과 순서를 유지합니다.
기록 제한은 토큰 수뿐 아니라 잃는 정보까지 평가해야 합니다.
다음 학습과 이어지는 지점 — 05절에서는 세부 내부 추론을 요구하지 않고 최종 답과 확인 가능한 짧은 근거를 요청하는 경계를 배웁니다.

[상] 4. n_messages로 기록을 줄일 때 확인할 위험을 쓰세요.
정답과 해설 — 오래된 정책이나 필수 고객 요구가 함께 제거될 수 있으므로 보존 항목을 정하고 원문과 대조해야 합니다.

1학습 목표
사고의 연쇄와 ReAct가 제안된 배경과 두 기법의 적용 범위를 설명할 수 있습니다.
모델의 비공개 내부 추론과 사용자가 확인할 수 있는 짧은 근거를 구분할 수 있습니다.
같은 과제에서 최종 답 요청과 짧은 근거 요청의 출력·토큰·지연을 비교할 수 있습니다.
2이 내용을 배우는 이유
복잡한 문제를 모델에 맡길 때 “생각하는 과정을 모두 보여 달라”고 쓰면 답이 더 믿을 만해 보일 수 있습니다. 그러나 길게 생성된 설명은 모델이 실제로 계산한 내부 상태의 완전한 기록이 아니며, 설명이 자연스럽다는 이유만으로 결론이 맞다고 판정할 수도 없습니다. 고객 지원처럼 근거가 입력에 이미 있는 과제에서는 주문번호, 파손 상태, 필요한 사진처럼 사용자가 다시 확인할 수 있는 사실을 짧게 제시하는 편이 검토에 도움이 됩니다. 이번 절에서는 내부 추론 전문을 요구하지 않고도 결론과 공개 가능한 근거를 함께 받는 방법을 익힙니다.
ReAct는 이후 도구 사용 에이전트를 이해하는 데 필요한 개념입니다. 다만 이 시점에는 모델이 도구를 선택하거나 결과를 받아 반복하는 프로그램을 만들지 않습니다. Ch 20에서 ToolNode와 에이전트 실행 흐름을 배울 때 현재의 개념 경계를 다시 확인합니다.
3앞에서 배운 내용
Ch 6에서는 init_chat_model()로 모델을 준비하고 model.invoke(messages)로 한 번의 요청을 보냈습니다. AIMessage.text에서 공개된 답을 읽고 usage_metadata에서 입력·출력 토큰을 확인했습니다. 이번 챕터의 앞 절에서는 system 메시지에 공통 역할을, user 메시지에 현재 과제와 출력 조건을 두었습니다. 이번 실습도 같은 호출 함수를 사용하며, user 메시지의 요청 방식만 바꿉니다.
4핵심 개념
사고의 연쇄와 공개 근거
사고의 연쇄(Chain of Thought, CoT)는 중간 단계를 언어로 생성하도록 유도해 복합 추론 과제를 풀려는 프롬프트 전략으로 알려졌습니다. 이 기법의 효과는 모델과 과제에 따라 달라집니다. 공개된 OpenAI 모델 지침도 GPT-5 계열에는 상세한 단계 지시를 늘리는 방식보다 목표, 성공 기준, 제약, 출력 형식을 먼저 분명히 하도록 안내합니다. 따라서 “CoT를 쓰면 정확도가 높아진다”를 전제로 삼지 않고, 고정된 평가 자료에서 실제 결과를 측정해야 합니다.
공개 근거(brief evidence)는 답을 검토하는 사람이 입력에서 다시 찾을 수 있도록 사실이나 판단 기준을 짧게 적은 문장입니다. 예를 들어 “파손된 뚜껑이며 교환 접수에 사진이 필요함”은 주어진 문의와 규정에서 확인할 수 있습니다. 공개 근거는 모델의 비공개 내부 추론을 복원한 기록이 아닙니다. 근거 문장이 입력과 맞는지 사람이 대조할 수 있다는 점이 핵심입니다.
ReAct가 다루는 범위
ReAct는 추론(reasoning)과 행동(acting)을 결합한 접근입니다. 일반적인 실행 흐름에서는 모델이 현재 관찰을 바탕으로 다음 행동을 정하고, 도구가 반환한 관찰을 다시 받아 다음 단계를 정합니다. 이러한 반복에는 도구 권한, 종료 조건, 오류 처리, 상태 관리가 필요합니다. 이번 절의 노트북은 도구를 정의하지 않으며 모델 호출도 각 조건마다 한 번씩만 수행합니다. 따라서 짧은 근거가 포함된 응답을 ReAct 실행이라고 부르지 않습니다. 여기에서는 “관찰할 사실과 다음 행동을 구분한다”는 개념만 준비합니다.
도식 읽기왼쪽의 고객 문의와 규정이 한 번의 모델 호출로 전달되고, 오른쪽에는 공개 가능한 결론과 짧은 근거가 놓입니다. 점선 경계 밖의 도구 선택과 관찰 반복은 Ch 20에서 구현할 범위입니다.화살표가 모델 호출 뒤 다시 입력으로 돌아가지 않는지 확인합니다. 이번 실습은 반복 루프가 없습니다.
설명 문장과 실제 행동의 차이
“주문 상태를 확인하겠습니다”라는 생성 문장이 출력되어도 주문 데이터베이스를 조회한 것은 아닙니다. 실제 조회라면 Python 프로그램이 조회 함수를 실행하고 그 결과를 받아야 합니다. ReAct의 행동은 이런 실행 단계와 관찰 결과를 포함합니다. 이번 코드의 direct와 evidence는 모두 한 번 호출한 응답을 담은 딕셔너리이며 도구 실행 기록이 없습니다.
다른 상황으로 영수증 검토를 생각해 봅니다. 모델이 “수량 2, 단가 3,000원”이라는 원문 항목을 짧게 제시하면 검토자는 원문에서 그 값을 찾을 수 있습니다. 합계가 맞는지 확인하려면 실제 계산 결과와도 대조해야 합니다. 읽기 좋은 설명을 생성한 것, 원문 근거가 맞는 것, 계산이 맞는 것은 각기 확인할 대상입니다. 이는 개념 비교를 위한 사례이며 이번 실습에서 계산 도구를 실행하지 않습니다.
고객 문의에서도 사진 요청의 근거는 제공된 회사 규정에서 찾아야 합니다. 문장이 자연스럽다는 이유로 규정을 확인했다고 보지 않습니다. 아래에서는 같은 문의의 최종 답과 짧은 공개 근거를 비교하고, 근거 문장의 각 사실을 입력과 대응시킵니다. 비공개 내부 추론을 읽어 모델이 실제로 어떤 계산을 했는지 판정하는 실험은 아닙니다.
5실행 예제
노트북은 깨진 텀블러 뚜껑 교환 문의를 두 조건으로 실행합니다. 첫 조건은 분류, 다음 행동, 고객 문장으로 이루어진 최종 답만 요청합니다. 둘째 조건은 내부 판단 과정을 공개하지 말라는 제약과 함께 입력에서 확인한 근거 한 줄을 추가하도록 요청합니다. 모델, 문의, 규정, 생성 상한, 포함 여부를 살펴볼 세 단어는 그대로 유지합니다. run()은 응답 원문, 사용량, 전체 호출 지연을 하나의 사전으로 반환합니다.
확인할 점 — 두 응답에서 ‘교환’, ‘A-1042’, ‘사진’이 실제로 나타나는지 확인한 뒤 원문을 읽습니다. 단어 포함 표시는 세 문자열의 포함 여부만 보여 주며, 문장 전체가 정확한지 판정하는 점수는 아닙니다.
6실험 결과 해석
실행된 두 응답은 모두 ‘교환’, ‘A-1042’, ‘사진’을 포함했습니다. 최종 답만 요청한 조건은 입력 115토큰, 출력 87토큰, 전체 202토큰을 사용했고 응답 길이는 139자였습니다. 짧은 근거를 요청한 조건은 입력 134토큰, 출력 150토큰, 전체 284토큰을 사용했고 응답 길이는 251자였습니다. 실행 시점의 전체 호출 지연은 각각 1.187초와 1.393초였습니다. 둘째 조건은 요청 문구와 출력이 더 길었으며, 이번 한 번의 실행에서는 지연도 더 길었습니다.
둘째 응답에는 분류, 근거, 다음 행동, 고객 문장이 각각 나타났습니다. 근거 문장은 입력의 파손 사실과 사진 규정을 짧게 다시 확인했습니다. 두 응답 모두 이번에 확인한 세 단어를 포함했지만, 단어 포함만으로 어느 조건의 품질이 높다고 결론 내릴 수는 없습니다. 호출도 조건마다 한 번뿐이어서 지연 차이를 프롬프트 전략의 고정된 특성으로 일반화하지 않습니다. 이번 실험은 비공개 내부 추론을 수집하지 않았으며 ReAct의 도구 실행도 관찰하지 않았습니다.
7주의할 점과 실무 메모
모델이 작성한 근거 문장이 자연스러워도 입력이나 공식 자료에서 다시 확인해야 합니다. 공개 근거는 사실 확인 절차를 대신하지 않습니다.
상세한 단계별 풀이 지시는 입력·출력 토큰과 지연을 늘릴 수 있습니다. 정확도 개선 여부는 대표 평가 자료와 미리 정한 채점 기준으로 확인합니다.
고객 개인정보, 내부 정책, 비공개 판단 기준을 근거 문장에 그대로 노출하지 않습니다. 사용자에게 공개해도 되는 사실의 범위를 먼저 정합니다.
도구 호출이 필요한 과제는 권한과 실패 처리를 함께 설계해야 합니다. 이번 절의 한 번 호출 예제를 도구 사용 에이전트로 확장하지 않습니다.
8정리와 다음 절
사고의 연쇄는 모델과 과제에 따라 측정해야 하는 프롬프트 전략입니다.
짧은 공개 근거는 입력에서 다시 확인할 사실을 제시하며 내부 추론 전문과 구분됩니다.
이번 실습은 조건마다 모델을 한 번 호출했으며 ReAct의 도구 반복 흐름을 구현하지 않았습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 한 응답의 설명을 길게 받는 대신 같은 질문을 독립적으로 여러 번 실행하고, 공개된 최종 분류만 모아 표본 합의를 계산합니다.
9복습 문제
문제 1
짧은 공개 근거를 모델의 내부 추론 기록으로 취급하면 안 되는 이유는 무엇인가요?
해설 — 공개 근거는 사용자가 검토하도록 생성된 문장입니다. 모델 내부 상태의 완전한 기록이 아니므로 입력 사실과 별도로 대조해야 합니다.
문제 2
이번 실험이 ReAct 실행이 아닌 근거를 코드에서 어떻게 찾을 수 있나요?
해설 — 도구 정의와 도구 호출 결과를 다시 모델에 전달하는 반복이 없습니다. 각 조건은 정해진 메시지로 invoke()를 한 번 수행합니다.
문제 3
두 조건에 세 단어가 모두 포함되었다는 사실만으로 답의 품질이 같다고 할 수 있나요?
해설 — 할 수 없습니다. 단어 포함 검사는 문맥, 사실성, 불필요한 약속을 판정하지 않으므로 응답 원문을 평가 기준에 따라 읽어야 합니다.
문제 4
상세한 단계 지시를 도입하기 전에 무엇을 고정하고 측정해야 하나요?
해설 — 모델, 과제, 입력 자료, 생성 설정, 평가 기준을 고정하고 정답률이나 기준 충족 여부, 토큰, 지연을 반복 측정해야 합니다.

1학습 목표
자기 일관성의 목적을 독립 표본과 최종 답 집계의 관점에서 설명할 수 있습니다.
허용 라벨을 검사하고 유효하지 않은 응답과 동률을 명시적으로 처리할 수 있습니다.
표본 합의와 개별 응답의 내용 완전성을 구분해 평가할 수 있습니다.
2이 내용을 배우는 이유
생성 모델은 같은 질문에도 실행할 때마다 표현이나 결론이 달라질 수 있습니다. 한 번의 답만 저장하면 그 답이 반복해서 나타나는 경향인지 우연히 나온 표본인지 알기 어렵습니다. 자기 일관성(Self-Consistency)은 같은 조건에서 여러 최종 답을 얻고 집계하여, 한 번의 생성에 의존하는 정도를 줄이는 전략입니다. 그러나 여러 답이 같은 라벨에 모였다고 해서 그 라벨이 사실이라는 보장은 없습니다. 같은 잘못된 전제나 빠진 자료를 모든 호출이 공유하면 같은 오답에 합의할 수도 있습니다.
이번 절에서는 고객 문의의 최종 분류를 세 번 받아 공개된 첫 줄의 라벨만 집계합니다. 내부 추론을 저장하지 않으며 외부 사실 확인을 다수결로 대체하지 않습니다. 또한 라벨 합의와 주문번호·사진 같은 필수 내용의 포함 여부를 별도로 확인합니다.
3앞에서 배운 내용
앞 절에서는 같은 고객 문의에 대해 최종 답만 요청한 조건과 짧은 공개 근거를 요청한 조건을 비교했습니다. 두 조건 모두 run()이 응답 원문, usage_metadata, 전체 호출 지연을 반환했습니다. 이번 절은 한 가지 메시지 조건을 고정한 뒤 run(messages)를 세 번 호출합니다. Ch 2의 02~03절에서 배운 반복문·자료구조와 문자열 메서드를 사용하므로 새로운 프레임워크 기능은 추가하지 않습니다.
4핵심 개념
독립 표본과 합의
표본(sample)은 같은 실험 조건에서 얻은 응답 한 건입니다. 이번에는 앞 호출의 답을 다음 호출 메시지에 넣지 않고 같은 모델·프롬프트·질문·생성 설정으로 각각 호출합니다. 응답을 서로 전달하지 않는 구조이며, 이것만으로 표본의 통계적 독립성을 확인한 것은 아닙니다. 표본 수(sample count)는 호출 횟수이며 이번 실습에서는 3입니다. 합의(consensus)는 유효한 최종 라벨의 빈도를 집계한 결과입니다. 세 표본 중 두 개가 ‘교환’이고 하나가 ‘배송’이면 ‘교환’이 엄격 과반을 얻습니다.
유효성 검사(validation)는 첫 줄이 미리 허용한 라벨 중 하나인지 확인하는 단계입니다. 설명이 길어도 첫 줄 형식이 맞지 않으면 집계 대상에서 제외하거나 형식 오류로 기록해야 합니다. 이번 코드의 엄격 과반(strict majority)은 전체 시도 수의 절반보다 많은 유효 표를 얻은 상태입니다. 형식 오류 응답도 전체 시도 수에는 포함합니다. 가장 큰 빈도가 같으면 동률이며, 유효 표본이 없으면 집계 불가입니다. 코드가 동률에서 임의의 첫 라벨을 고르면 실행 순서가 결론에 영향을 주므로 동률 분기를 명시해야 합니다.
합의가 답의 품질을 보장하지 않는 이유
분류 라벨과 응답 내용은 서로 다른 평가 대상입니다. 세 응답이 모두 ‘교환’이라고 써도 한 응답이 주문번호를 빠뜨리거나, 규정에 없는 보상을 약속할 수 있습니다. 그러므로 집계 뒤에는 각 원문을 다시 읽고 필수 사실, 금지 조건, 근거의 정확성을 검사합니다. 다수결은 유효성 검사나 사실 확인을 대신하지 않습니다. 표본 수를 늘리면 호출 비용과 전체 대기 시간도 함께 늘어나므로, 평가 자료에서 얻는 개선과 비용을 함께 측정해야 합니다.
도식 읽기고정된 메시지가 독립 호출 세 개로 나뉘고, 각 최종 답에서 허용 라벨을 검사한 뒤 빈도를 집계합니다. 유효 표본 없음, 동률, 엄격 과반은 서로 다른 결과로 표시됩니다.합의 라벨로 이어지는 화살표와 개별 원문 검토로 이어지는 화살표가 분리되어 있는지 확인합니다.
합의의 분모를 정하고 경계 사례를 계산하기
이 실습은 여러 최종 응답의 라벨 합의를 읽는 축소 예제입니다. 여러 추론 경로를 표집하고 정답을 집계하는 Self-Consistency 연구의 전체 절차를 재현하지는 않습니다. 앞 응답을 다음 입력에 넣지 않는 별도 호출을 사용하지만, 같은 모델과 지시의 오류가 여러 응답에 함께 나타날 수 있으므로 통계적으로 완전히 독립된 판단을 얻었다고 단정하지 않습니다.
코드는 엄격 과반의 분모를 전체 시도 수인 len(samples)로 정합니다. 세 응답 중 형식 오류가 두 건이고 나머지 한 건이 교환이라면 유효 응답 안에서는 교환이 100%여도 전체 세 건의 과반은 아닙니다. count > len(samples) // 2에서 세 건의 절반을 내린 값은 1이므로 교환 표가 2개 이상이어야 합의가 됩니다. 유효 표본만 분모로 쓰는 다른 정책과 구분합니다.
가정한 라벨이 교환·교환·배송이면 교환으로 합의하고, 교환·배송·환불이면 합의 없음입니다. 교환·형식 오류·형식 오류도 합의 없음입니다. 이 계산 예들은 집계 규칙을 읽는 연습이며 실제 저장 출력의 세 표본은 모두 교환입니다. 실제 표본에서 관찰하지 않은 분기를 관찰한 것처럼 기록하지 않습니다.
5실행 예제
system 메시지는 첫 줄에 ‘배송’, ‘교환’, ‘환불’ 중 하나를 LABEL: 형식으로 쓰고 둘째 줄부터 확인 근거를 적도록 요구합니다. 리스트 컴프리헨션은 같은 메시지로 세 번 호출하며 앞 응답을 다음 입력에 추가하지 않습니다. 이어지는 셀은 첫 줄에서 라벨을 추출하고 허용 집합과 대조합니다. 마지막 셀은 표본 수, 전원 일치 여부, 필수 단어 포함 표시, 전체 토큰, 호출 지연 합계를 출력합니다.
확인할 점 — 다수결 결과를 읽기 전에 세 원문의 첫 줄이 형식에 맞는지 확인합니다. 그다음 ‘교환’ 합의와 ‘A-1042’, ‘사진’의 포함 여부가 같은 평가인지 구분해서 읽습니다.
6실험 결과 해석
실행된 세 표본의 유효 라벨은 모두 ‘교환’이었고 빈도는 {'교환': 3}으로 집계되었습니다. 엄격 과반 기준에 따라 합의 결과도 ‘교환’이며, 이번 세 표본에서는 전원 일치가 관찰되었습니다. 세 호출의 전체 토큰 합계는 614토큰이고 지연 합계는 3.467초였습니다. 개별 호출의 전체 토큰은 250, 184, 180토큰으로 달랐습니다. 같은 라벨을 반환해도 설명 길이와 표현이 달라 사용량이 달라질 수 있음을 보여 줍니다.
내용 검사는 합의와 다른 결과를 보여 줍니다. 세 응답 모두 ‘교환’과 ‘사진’을 포함했지만 둘째와 셋째 응답에는 주문번호 ‘A-1042’가 없었습니다. 첫 응답에는 세 단어가 모두 포함되었습니다. 따라서 “분류 라벨은 세 표본이 일치했다”와 “모든 응답이 필요한 세 내용을 포함했다”를 구분해 기록해야 합니다. 세 번의 일치는 이 고객 문의와 현재 모델 실행에서 관찰한 결과이며, 다른 질문의 정답이나 모델 전체의 안정성을 보장하지 않습니다.
7주의할 점과 실무 메모
표본 합의 전에 허용 라벨과 정확한 추출 규칙을 정합니다. 형식 오류를 가장 가까운 라벨로 자동 보정하면 모델의 형식 준수 실패가 기록에서 사라집니다.
동률은 승자를 임의로 정하지 않고 ‘동률’로 반환합니다. 유효 라벨이 하나도 없으면 ‘집계 불가’로 기록하고 원문을 검토합니다.
모델 별칭은 시간이 지나며 다른 스냅샷을 가리킬 수 있습니다. 재현성이 필요한 평가는 접근 가능한 고정 모델 ID와 생성 설정을 함께 기록합니다.
호출을 N번 수행하면 대체로 비용과 전체 처리량도 늘어납니다. 품질 기준의 개선이 추가 비용을 정당화하는지 평가 자료에서 확인합니다.
다수결은 외부 사실 확인, 정책 유효성 검사, 개인정보 검사를 대신하지 않습니다.
8정리와 다음 절
자기 일관성은 같은 조건의 독립 호출에서 공개된 최종 답을 모아 집계합니다.
유효하지 않은 라벨, 동률, 집계 불가를 명시적으로 구분해야 합니다.
라벨 합의와 응답 내용의 완전성은 별도의 평가 기준으로 확인합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 자유로운 문장 대신 JSON 객체를 요청하고, 파싱 성공과 요구한 필드의 존재를 각각 진단합니다.
9복습 문제
문제 1
세 표본이 같은 라벨을 반환하면 그 라벨이 정답이라고 보장할 수 있나요?
해설 — 보장할 수 없습니다. 모든 호출이 같은 잘못된 정보나 빠진 자료를 공유하면 같은 오답에 합의할 수 있으므로 외부 기준으로 확인해야 합니다.
문제 2
형식 오류 응답을 유효 라벨 집계와 분리해야 하는 이유는 무엇인가요?
해설 — 임의 보정은 출력 형식 실패를 숨기고 빈도를 바꿀 수 있습니다. 원문과 오류 수를 보존해야 프롬프트를 수정할 근거가 남습니다.
문제 3
이번 결과에서 전원 일치가 참인데도 내용 완전성이 부족한 근거는 무엇인가요?
해설 — 세 라벨은 모두 ‘교환’이지만 둘째와 셋째 응답에는 주문번호 ‘A-1042’가 없습니다. 라벨 일치와 필수 내용 포함은 다른 검사입니다.
문제 4
두 라벨이 같은 최대 빈도를 얻으면 어떻게 기록해야 하나요?
해설 — 임의의 승자를 선택하지 않고 ‘합의 없음’으로 기록합니다. 표본을 추가할지는 비용과 평가 규칙에 따라 별도로 결정합니다.

1학습 목표
JSON 파싱 성공과 필요한 필드 충족을 서로 다른 검사로 설명할 수 있습니다.
같은 과제에서 출력 지시의 구체성만 바꾼 세 프롬프트를 비교할 수 있습니다.
응답 원문을 보존하면서 json.loads()와 필드 존재 검사를 수행할 수 있습니다.
2이 내용을 배우는 이유
모델이 “JSON으로 답하라”는 요청을 따르면 프로그램이 바로 사용할 수 있을 것처럼 보입니다. 그러나 올바른 JSON 문법으로 작성되었다는 사실과 프로그램이 기대한 필드 이름·자료형·허용값을 지켰다는 사실은 다릅니다. 예를 들어 {"분류": "교환"}은 문법상 올바른 JSON이지만 프로그램이 category를 읽으면 키를 찾지 못합니다. 다음 행동이 문자열이어야 하는데 목록으로 생성되어도 파싱 자체는 성공할 수 있습니다.
이번 절은 프롬프트 문장만으로 구조를 요청했을 때 무엇을 진단해야 하는지 보여 줍니다. Ch 6에서 배운 Pydantic 기반 구조화 출력은 스키마와 모델 호출을 직접 연결하는 방법입니다. 여기서는 그 기능을 대체하려 하지 않고, 프롬프트 지시와 문자열 파싱만 사용한 경로의 한계를 관찰합니다.
3앞에서 배운 내용
Ch 6의 ‘구조화 출력과 검증’ 절에서는 Pydantic 모델로 필드 이름, 타입, 허용 범위를 선언하고 with_structured_output(..., include_raw=True)의 raw, parsed, parsing_error를 확인했습니다. 이번 챕터에서는 역할별 메시지, 과업 제약, 관련 예시가 출력에 미치는 영향을 비교했습니다. 이번 실습은 모델과 고객 문의를 고정하고 JSON을 요구하는 user 메시지의 구체성만 세 단계로 바꿉니다.
4핵심 개념
파싱, 필드, 자료형
파싱(parsing)은 문자열을 프로그램이 다룰 수 있는 자료 구조로 읽는 과정입니다. Python의 json.loads()는 JSON 문자열을 사전이나 목록 같은 객체로 변환합니다. JSON 문법이 깨져 있으면 JSONDecodeError가 발생합니다. 파싱 성공은 중괄호, 따옴표, 쉼표 같은 문법을 읽을 수 있었다는 뜻입니다.
필드(field)는 객체 안에서 값을 찾는 이름입니다. 이번 프로그램은 category, next_action, customer_message 세 필드를 요구합니다. 필드 존재 검사(field presence check)는 각 이름이 파싱된 객체에 있는지 확인합니다. 스키마(schema)는 필요한 필드, 자료형, 허용값 같은 구조 규칙을 모아 둔 정의입니다. 실습의 schema 프롬프트는 세 필드와 category의 허용값, 모든 필드가 문자열이라는 조건을 자연어로 적습니다. 자연어 스키마는 설명일 뿐이므로 Python 검증 코드가 자동으로 생기지는 않습니다.
세 단계 진단
brief는 JSON이라는 형식만 요구합니다. fields는 세 필드 이름을 추가합니다. schema는 코드 울타리나 부가 설명을 금지하고 필드 이름, 허용 분류, 문자열 자료형을 지정합니다. 비교할 때는 첫째로 원문이 JSON 문법인지, 둘째로 세 필드가 있는지, 셋째로 각 값의 자료형과 내용이 요구 조건에 맞는지 확인합니다. 이번 코드가 자동 검사하는 범위는 첫째와 둘째입니다. 셋째는 원문 정독으로 확인하며, 운영 코드에서는 Pydantic 같은 검증기를 사용해야 합니다.
구문 오류(syntax error)는 JSON 문법을 읽지 못한 상태입니다. 구조 오류는 파싱되었지만 필요한 필드나 자료형이 맞지 않는 상태입니다. 내용 오류는 구조가 맞아도 분류나 고객 안내가 업무 규정과 맞지 않는 상태입니다. 오류 층을 나누면 프롬프트를 고칠지, 스키마 검증을 추가할지, 업무 자료를 보완할지 결정할 수 있습니다.
도식 읽기세 프롬프트가 각각 응답 원문을 만들고, 모든 원문이 먼저 json.loads()를 거친 뒤 필드 존재 검사로 이어집니다. 파싱 성공과 필드 충족은 서로 다른 판정 상자로 표시됩니다.파싱 성공 화살표가 곧바로 ‘업무에 사용 가능’으로 이어지지 않는지 확인합니다.
JSON을 읽는 것과 필요한 필드를 검증하는 것
json.loads(result["text"])는 모델 응답인 문자열을 Python 값으로 읽습니다. JSON에는 객체뿐 아니라 목록, 문자열, 숫자도 있으므로 파싱이 성공했다고 딕셔너리가 만들어졌다고 가정하면 안 됩니다. 아래 저장 원문은 객체였지만 실제 프로그램에서는 먼저 기대한 자료형인지 검사해야 합니다. 자연어로 JSON을 요청하는 방식과 Ch 6의 구조화 출력 호출도 같은 기능으로 취급하지 않습니다.
진단 코드의 f in parsed는 현재 객체에 필요한 키가 있는지를 확인합니다. 예를 들어 category 키의 값이 빈 문자열이어도 키는 존재합니다. 값이 “알 수 없음”이어도 허용 라벨 검사 없이 키 존재 결과만 참이 됩니다. 따라서 파싱 성공, 객체 여부, 필드 존재, 값의 타입, 허용 범위, 업무 사실은 차례로 다른 질문입니다.
일정 추출에 적용하면 “일시”와 “장소”가 담긴 JSON이 문법상 유효해도 프로그램이 요구한 starts_at과 location 키는 없을 수 있습니다. 키를 맞춰도 날짜 형식이나 장소의 실제 존재는 아직 확인하지 않았습니다. 이런 사례를 층별로 나누어 보면 프롬프트를 더 구체화할 부분과 코드로 검증할 부분을 구별할 수 있습니다.
5실행 예제
prompts 사전은 같은 고객 문의를 세 가지 JSON 지시와 결합합니다. 사전 컴프리헨션은 같은 system 메시지로 각 조건을 한 번씩 호출합니다. 진단 셀은 응답 원문에 json.loads()를 실제 적용하고, 성공한 객체에서 세 영문 필드가 존재하는지 확인합니다. 예외가 발생하면 오류 유형을 기록하며 예상 오류 문구를 임의로 만들지 않습니다. 마지막 셀은 진단 결과와 사용량, 지연, 응답 원문을 함께 출력합니다.
확인할 점 — 세 조건이 모두 파싱되었는지 먼저 확인한 뒤, brief의 실제 키와 자료형을 읽습니다. 파싱 성공과 요구 필드 충족이 다른 결과임을 출력에서 찾습니다.
6실험 결과 해석
이번 실행에서는 brief, fields, schema 세 응답 모두 json.loads()로 파싱되었습니다. 따라서 이 세 표본에서는 JSON 구문 오류를 관찰하지 못했습니다. 그러나 brief 응답은 ‘분류’, ‘필요한 다음 행동’, ‘고객에게 보낼 한 문장’이라는 한국어 키를 사용했습니다. 프로그램이 요구한 category, next_action, customer_message는 모두 없었습니다. 또한 ‘필요한 다음 행동’ 값은 문자열이 아니라 두 항목의 목록이었습니다.
fields와 schema 응답은 요구한 세 영문 필드를 모두 포함했습니다. schema 응답의 category는 허용값 중 하나인 ‘교환’이었고 세 값도 문자열로 보였습니다. 입력 토큰은 지시가 구체해지면서 98, 110, 137토큰으로 늘었습니다. 전체 토큰은 각각 244, 199, 243토큰이어서 입력이 길어진 순서와 같지 않았습니다. 출력 길이도 함께 달라졌기 때문입니다.
세 번의 성공은 자연어 스키마가 항상 지켜진다는 증거가 아닙니다. 호출은 조건마다 한 번뿐이며 자동 진단 코드도 필드의 존재까지만 검사합니다. 허용값, 자료형, 추가 필드, 빈 문자열, 업무 내용의 정확성을 강제하려면 명시적인 스키마 검증이 필요합니다. 구조가 맞아도 파손 사진이 필요한 규정을 잘못 설명할 수 있으므로 내용 평가는 별도로 수행합니다.
7주의할 점과 실무 메모
응답을 정규식으로 잘라 JSON처럼 보이는 부분만 파싱하면 앞뒤의 오류나 지시 위반이 사라질 수 있습니다. 진단 단계에서는 원문 전체를 보존합니다.
필드가 있다는 사실만 검사하면 값의 자료형과 허용 범위를 놓칩니다. 운영 경로에서는 Pydantic 스키마로 필드 설명과 제약을 선언합니다.
파싱 실패 원문에 고객 개인정보가 포함될 수 있습니다. 로그 저장 범위와 마스킹 규칙을 먼저 정합니다.
모델별 구조화 출력 지원 방식이 다를 수 있습니다. LangChain 공통 인터페이스를 사용해도 제공자 문서와 고정 환경에서 실제 지원 범위를 확인합니다.
재시도로 우연히 성공한 결과만 남기지 않습니다. 첫 실패 원문과 재시도 횟수, 추가 비용을 함께 기록해야 원인을 진단할 수 있습니다.
8정리와 다음 절
JSON 파싱 성공은 문법을 읽었다는 뜻이며 필요한 필드와 자료형을 보장하지 않습니다.
출력 지시에 필드와 허용값을 적으면 이번 표본에서는 구조가 더 구체적으로 나타났습니다.
프로그램에서 사용할 값은 명시적인 스키마와 내용 평가로 다시 확인해야 합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 프롬프트 문구와 변경 이유를 버전별 아티팩트로 저장하고, 동일한 평가 조건으로 세 버전을 비교합니다.
9복습 문제
문제 1
brief 응답은 파싱에 성공했는데 왜 프로그램의 요구를 충족하지 못했나요?
해설 — JSON 문법은 맞았지만 프로그램이 찾는 세 영문 필드가 없었고 다음 행동의 자료형도 목록이었습니다.
문제 2
필드 존재 검사만으로 category가 허용값인지 확인할 수 있나요?
해설 — 확인할 수 없습니다. 필드가 존재하는지와 값이 ‘배송’, ‘교환’, ‘환불’ 중 하나인지는 별도의 검사입니다.
문제 3
세 응답이 모두 파싱된 결과를 다른 질문에도 일반화하면 안 되는 이유는 무엇인가요?
해설 — 각 조건을 한 번만 호출했고 입력과 생성 결과가 바뀌면 코드 울타리, 부가 설명, 잘못된 자료형이 나타날 수 있기 때문입니다.
문제 4
구조 검증을 통과한 응답에도 내용 평가가 필요한 이유는 무엇인가요?
해설 — 필드와 자료형이 맞아도 분류가 틀리거나 업무 규정에 없는 안내를 생성할 수 있기 때문입니다.

1학습 목표
프롬프트 버전에 원문과 변경 이유를 함께 기록할 수 있습니다.
모델과 과제를 고정하고 누적된 세 프롬프트 전략의 토큰·지연·단어 포함 표시를 비교할 수 있습니다.
프롬프트, 실행 결과, 측정 조건을 JSON 파일로 저장하고 다시 읽어 확인할 수 있습니다.
2이 내용을 배우는 이유
프롬프트를 수정하다 보면 마지막 문장만 남고 어떤 문제를 고치려고 무엇을 바꿨는지 사라지기 쉽습니다. 이름을 v2라고 붙이는 것만으로는 버전이 보존되지 않습니다. 원문, 변경 이유, 모델, 입력, 실행 결과, 평가 기준을 함께 저장해야 다른 사람이 같은 조건을 다시 살필 수 있습니다. 기록이 없으면 출력 차이가 프롬프트 때문인지 모델 변경이나 다른 고객 문의 때문인지 구분하기 어렵습니다.
이번 절에서는 기준선, 형식·금지 조건 추가, 관련 예시 추가의 세 전략을 비교합니다. 세 번째 전략은 두 번째 조건을 유지한 채 관련 예시만 추가합니다. 이렇게 누적 조건을 분명히 해야 두 번째에서 세 번째로 바뀐 결과를 예시 추가와 연결해 해석할 수 있습니다. 마지막에는 메모리에 있던 사전을 prompt-ab-continuity.json 파일로 저장하고 실행 시각별 사본도 함께 남깁니다.
3앞에서 배운 내용
Ch 6에서는 usage_metadata에서 토큰·캐시 사용량을 읽고 time.perf_counter()로 호출 지연을 기록했습니다. 이 절의 노트북은 Ch 6의 provider-comparison-continuity.json을 직접 읽어 이전 실행의 출처와 공통 필드를 확인합니다. 현재 고객 문의는 Ch 6 질문과 다르므로 두 실행의 수치를 직접 비교하지 않고, 같은 측정 형식만 이어서 사용합니다. 이번 챕터에서는 과업 제약, 관련 예시, 공개 근거, 반복 표본, JSON 필드 진단을 차례로 확인했습니다. 이번 절은 새 프롬프트 기법을 추가하는 대신 앞에서 사용한 전략을 세 버전으로 묶습니다. 파일 저장에는 Ch 2의 05절에서 배운 경로·파일 처리와 Ch 4의 05절에서 다룬 json.dumps()·json.loads()를 사용합니다.
4핵심 개념
버전과 변경 기록
프롬프트 버전(prompt version)은 특정 시점의 프롬프트 원문과 그 원문을 식별하는 이름입니다. 버전 이름은 v1-direct처럼 사람이 읽을 수 있지만, 이름만 저장해서는 실제 문장을 복구할 수 없습니다. 변경 기록(change log)은 이전 버전에서 무엇을 추가하거나 수정했는지와 그 이유를 적은 기록입니다. 이번 실습의 change_log는 v1을 기준선, v2를 형식·금지 조건 추가, v3를 v2 조건 유지·관련 예시 추가로 설명합니다.
기준선(baseline)은 이후 변경과 비교할 첫 조건입니다. 통제 변수(control variable)는 비교 중에 유지하는 값입니다. 여기서는 모델 openai:gpt-5.4-mini, 생성 상한 220토큰, system 메시지, 고객 문의, 단어 포함 검사 목록을 유지합니다. 실험 변수는 프롬프트 전략입니다. v1에서 v2로 갈 때는 출력 형식과 금지 조건을 함께 추가했으므로 두 요소 각각의 효과를 분리할 수 없습니다. v2와 v3의 차이는 관련 예시 추가 한 가지로 좁혀져 있습니다.
A/B 비교와 실행 기록
A/B 비교(A/B comparison)는 같은 대상 집합을 두 조건으로 나누어 결과를 비교하는 방법입니다. 이번 실습은 세 조건을 사용하므로 엄밀히는 A/B/n 비교에 가깝습니다. 각 버전을 한 번씩 실행하기 때문에 반복 변동을 평균내지 못하며, 결과표는 탐색용 실행 기록으로 읽어야 합니다. mention_count는 ‘교환’, ‘A-1042’, ‘사진’ 중 몇 단어가 나타났는지를 세며 품질 점수가 아닙니다. 원문이 규정을 지키는지와 근거 없는 약속을 추가했는지는 사람이 읽어야 합니다.
실행 아티팩트(run artifact)는 실행 조건과 결과를 나중에 다시 읽을 수 있도록 저장한 파일입니다. 이번 JSON에는 모델, 생성 상한, 고객 문의, 단어 목록, 세 프롬프트 원문, 변경 이유, 응답, 사용량, 지연, 캐시 토큰, 예상 비용, 가격 기준일과 100만 토큰당 단가가 들어갑니다. 모델 별칭은 이후 다른 스냅샷을 가리킬 수 있으므로 높은 재현성이 필요한 평가에서는 접근 가능한 고정 모델 ID와 실행 날짜도 추가해야 합니다.
도식 읽기프롬프트 원문과 변경 기록이 세 버전을 만들고, 고정된 모델·입력으로 실행한 결과가 비교표와 JSON 파일에 함께 저장됩니다. 파일을 다시 읽는 화살표는 이름만 붙인 상태와 영구 기록을 구분합니다.각 결과 행에서 프롬프트 원문과 모델·입력 조건까지 거슬러 올라갈 수 있는지 확인합니다.
파일의 이름과 내용의 지문을 함께 남기기
run_id는 한 실행을 구분하는 이름이고 SHA-256은 파일 바이트에서 계산한 고정 길이의 지문입니다. 코드의 read_bytes()로 파일을 읽고 sha256(...).hexdigest()로 16진수 문자열을 얻습니다. 같은 파일 이름의 내용이 바뀌면 지문으로 차이를 확인할 수 있습니다. 지문이 있다고 원자료의 내용이 정확하거나 신뢰할 수 있는 출처라고 보증되지는 않습니다.
가령 v2라는 이름을 그대로 둔 채 출력 형식만 바꾸면 결과를 나중에 해석할 때 어느 문장을 사용했는지 모호해집니다. 그래서 버전 이름 외에 실제 프롬프트 원문, 바꾼 이유, 모델과 입력, 응답을 같은 기록에 넣습니다. 이전 파일을 읽는 준비 셀은 새 실험의 성능을 계산하는 셀이 아니라 그 실험이 어떤 선수 자료를 사용했는지 확인하는 셀입니다.
이 방식은 번역 지침의 존댓말 규칙이나 정보 추출의 누락값 규칙을 비교할 때도 적용할 수 있습니다. 한 번의 실험에서 말투와 누락 처리 규칙을 함께 바꾸면 차이를 두 원인으로 분리하기 어렵습니다. 현재 v1→v2는 형식과 금지 조건을 함께 바꾸고 v2→v3는 예시 추가를 비교하므로, 각 행을 한 가지 순수 효과로 해석하지 않습니다.
5실행 예제
versions 사전은 세 프롬프트 원문을 보존합니다. v2는 세 줄 형식과 규정 밖 약속 금지를 추가하고, v3는 이 두 조건을 그대로 둔 채 관련 예시를 추가합니다. 각 원문을 같은 모델과 system 메시지로 한 번씩 실행한 뒤, 입력·출력·캐시 토큰, 전체 호출 지연, 예상 비용, 단어 포함 개수를 표의 한 행으로 만듭니다. 마지막 셀은 모든 원문과 결과를 labs/part2/ch07-prompt-engineering/runs/prompt-ab-continuity.json에 저장하고 실행 시각별 사본 경로를 출력합니다.
확인할 점 — 세 버전의 mention_count가 같더라도 출력 형식과 안내 문장을 원문에서 비교합니다. 마지막 출력에서 Ch 6 기록 ID와 지문, 새 JSON 정본과 실행 시각별 사본 경로가 나타나는지 확인합니다.
6실험 결과 해석
세 응답은 모두 ‘교환’, ‘A-1042’, ‘사진’을 포함하여 mention_count가 3이었습니다. 입력 토큰은 v1 95, v2 118, v3 139토큰으로 늘었습니다. 지시와 예시가 추가되었기 때문입니다. 출력 토큰은 각각 113, 108, 71토큰이었고 전체 호출 지연은 1.560초, 1.165초, 0.870초였습니다. 캐시 입력은 세 행 모두 0토큰이었고 예상 비용은 각각 0.00057975달러, 0.0005745달러, 0.00042375달러였습니다. 입력이 긴 버전의 출력과 지연이 이번 실행에서 오히려 작았으므로, 입력 길이만으로 출력 길이나 지연 순서를 예측할 수 없음을 확인할 수 있습니다.
원문을 읽으면 세 버전 모두 교환 접수에 사진이 필요하다고 안내하고 주문번호를 포함합니다. v2와 v3는 세 줄 형식으로 응답했으며, v3는 관련 예시를 추가하면서 v2의 규정 밖 약속 금지 조건을 유지했습니다. 그러나 단어 포함 개수 3은 세 답의 업무 품질이 같다는 뜻이 아닙니다. 문장의 명확성, 정책 준수, 불필요한 약속은 별도의 루브릭으로 평가해야 합니다.
마지막 셀은 실행 날짜와 ID, Ch 6 기록의 경로·SHA-256 지문, 모델 설정, 세 프롬프트와 원문 응답, 공통 측정 필드를 prompt-ab-continuity.json과 실행별 사본에 저장합니다. mention_count는 품질 점수가 아니며, 생성 답변의 업무 품질은 human_review_required로 남겨 사람이 원문을 검토해야 합니다.
7주의할 점과 실무 메모
한 버전에서 여러 요소를 동시에 바꾸면 어떤 요소가 결과 차이를 만들었는지 분리하기 어렵습니다. 변경 기록에 묶여 바뀐 조건을 그대로 적습니다.
생성 응답은 실행할 때마다 달라질 수 있습니다. 버전마다 같은 반복 횟수를 정하고 실행 순서 효과도 확인합니다.
프롬프트 파일과 실행 로그에는 API 키, Authorization 헤더, 공개할 수 없는 고객 원문을 저장하지 않습니다. 필요한 식별자는 비식별 입력 ID로 대체합니다.
지연은 네트워크와 제공자 부하의 영향을 받습니다. 한 번의 수치로 프롬프트 전략의 속도를 일반화하지 않습니다.
LangSmith 같은 외부 저장소를 사용할 때는 데이터 보관 정책과 접근 권한을 확인합니다. 이번 기본 실습은 로컬 JSON 파일만 사용합니다.
8정리와 다음 절
프롬프트 버전은 이름, 원문, 변경 이유를 함께 보존해야 합니다.
비교에서는 모델·입력·평가 기준을 유지하고 바꾼 조건을 기록합니다.
실행 아티팩트에 프롬프트와 결과를 함께 저장해야 이후 검토와 재실행이 가능합니다.
다음 학습과 이어지는 지점 — Ch 8에서는 프롬프트 한 문장보다 넓은 모델 맥락을 다룹니다. 06절이 이 실행 기록과 지문을 직접 읽은 뒤, 별도 질문으로 full·selected·compressed를 실행하고 같은 측정 필드를 남깁니다. 두 실험은 질문과 입력 단위가 다르므로 수치를 직접 비교하지 않습니다. Ch 11은 검색된 문서 순위를 평가하고, 생성 답변의 정확성·근거성 평가는 Ch 15에서 다룹니다.

v2-constraints라는 이름만 저장하면 버전 기록으로 부족한 이유는 무엇인가요?
해설 — 실제 프롬프트 원문과 변경 이유, 실행 조건이 없으면 어떤 문장을 실행했는지 복구하거나 결과 차이의 원인을 검토할 수 없습니다.

Few-shot은 예시 입력과 예시 답의 대응을 현재 요청에 함께 넣는 방식입니다. `relevant_example`과 `irrelevant_example`은 준비된 문자열이며 현재 질문 `TASK` 앞에 연결됩니다. 별도의 모델 훈련은 수행하지 않습니다. 고정된 작은 예시를 직접 고르는 방식이며 자동 예시 선택기는 사용하지 않습니다.
감정 분류에서는 칭찬과 불만이 함께 있는 문장이 경계 예시가 될 수 있습니다. 상담에서는 상품명보다 파손 사실과 사진 확인이라는 판단 구조가 관련성을 결정합니다. 예시 수뿐 아니라 어떤 구분을 보여 주는지를 확인합니다.
예시의 B-203은 현재 문의의 주문번호가 아닙니다. 현재 A-1042를 그대로 유지하면서 예시의 분류 방식만 적용했는지 원문을 읽습니다. 아래 단어 포함 표시는 형식·사실·규정 준수 전체의 점수가 아닙니다.

# ChatPromptTemplate과 MessagesPlaceholder
메시지 틀과 선택적 대화 기록을 사용하면 같은 프롬프트 구조를 어떻게 재사용할 수 있을까요?

## 고정 과제
모든 절에서 같은 고객 문의와 확인 단어를 사용합니다.
## 측정 함수
단어 포함 표시는 원문 정독을 돕는 표시이며 품질 점수가 아닙니다.
`run(messages)`는 이 노트북에서 작성하는 보조 함수입니다. 역할·내용 목록을 받아 `model.invoke()`를 한 번 실행하고, 답 문자열·사용량·경과 초를 담은 딕셔너리를 반환합니다. `def` 셀은 함수를 정의할 뿐이며 뒤에서 `run(...)`을 호출할 때 모델 요청이 시작됩니다. `mention_flags(text)`는 지정 단어가 문자열에 있는지 표시한 딕셔너리를 반환합니다. 답의 뜻을 판단하는 모델 호출은 포함하지 않습니다.
## 메시지 템플릿 만들기
`MessagesPlaceholder(optional=True)`는 기록이 없는 첫 요청도 같은 틀로 처리합니다.
`from_messages()`는 고정 메시지와 빈칸으로 템플릿을 만드는 클래스 메서드입니다. `{format_rule}`와 `{question}`은 실행 때 값으로 채울 변수 자리입니다. `base_values`가 같은 이름의 키로 값을 제공합니다. 여기서는 문자열 앞에 `f`가 없으므로 Python이 미리 값을 채우는 방식이 아닙니다.
`prompt.invoke(base_values)`는 완성한 `ChatPromptValue`를 만들고 `.to_messages()`가 역할 있는 메시지 객체 목록으로 바꿉니다. 이 단계는 모델을 호출하지 않습니다. 다음 `run(first_messages)`의 내부에서 `model.invoke()`를 실행할 때 요청이 발생합니다.
`MessagesPlaceholder("history", optional=True)`는 과거 메시지 목록을 삽입할 자리입니다. 기억을 저장하는 기능이 아니며 값이 없으면 빈 목록으로 처리합니다. 다음 셀은 human 질문과 ai 답이라는 메시지 두 개로 한 턴을 추가합니다. `{**base_values, "history": ...}`는 기존 딕셔너리 항목을 펼친 새 딕셔너리에 history를 추가하는 Python 표기입니다.

`run_id`는 실행을 구분하는 이름이고 SHA-256은 파일 내용을 바이트로 읽어 계산한 지문입니다. `read_text()`는 텍스트를, `read_bytes()`는 바이트를 읽습니다. `hexdigest()`는 계산된 지문을 16진수 문자열로 표현합니다. 이 값은 내용 변경을 비교하는 데 쓰며 사실 정확성을 평가하는 점수는 아닙니다.
`next((path for path in ... if ...), None)`는 조건에 맞는 첫 경로를 찾고 없으면 `None`을 반환합니다. `[Path.cwd(), *Path.cwd().parents]`에서 별표는 상위 경로들을 목록 안에 펼칩니다. 현재 폴더부터 상위 폴더를 찾는 준비 코드이며 모델 입력을 만드는 단계와 구분합니다.
`required <= ch06_record.keys()`는 필요한 키 집합이 저장 기록의 키에 모두 포함되는지 검사합니다. 이어지는 기록은 같은 필드 형식을 참고하지만 고객 문의와 Ch 6의 질문이 다르므로 두 실행 수치를 성능 변화로 비교하지 않습니다.
## 버전과 변경 이유 기록
버전마다 바꾼 조건을 한 가지 전략으로 설명합니다.
## 세 전략 실행
모델, 질문, 생성 상한과 평가 기준을 고정합니다.
## 토큰·지연·자동 확인 결과
단어 포함 수 동점도 결과입니다. 한 번의 실행으로 전략 전체의 우열을 확정하지 않습니다.

프롬프트 원문, 고정 조건, 원문 응답을 상대 경로의 JSON 파일에 함께 저장합니다.
