1학습 목표
이 절을 마치면 내려받은 실습 폴더에서 제공 PDF 경로를 찾고 Path 객체의 파일명·이름·확장자를 확인할 수 있습니다.
이 절을 마치면 딕셔너리의 원본 값을 doc_id·source·page 등 공통 메타데이터로 바꿀 수 있습니다.
이 절을 마치면 쪽 번호 하나를 바꾼 새 메타데이터를 만들고 원본과 결과를 비교할 수 있습니다.
2이 내용을 배우는 이유
Ch 9에서는 PDF 한 쪽을 Document 하나로 바꾸고 바로 청크로 나누었습니다. 이번에는 PDF 외에 DOCX, HTML, CSV, HWPX도 함께 다룹니다. 01절은 출처를 metadata 딕셔너리로 준비하고, 02~04절은 각 파일에서 본문·표·행을 읽어 확인합니다. 이 결과를 후속 단계에서 page_content와 metadata에 옮기면 같은 Document 구조로 처리할 수 있습니다. 01~04절의 기본 노트북 자체는 LangChain Document 목록을 만들거나 합치지 않습니다.
파일 내용을 읽는 도구인 파서를 비교하기 전에, 어떤 문서를 사용했는지부터 기록합니다. 문서 수·파일 형식·경로·doc_id가 없으면 파서를 바꾼 후 어느 문서의 내용이 빠졌는지 비교할 수 없습니다. doc_id는 같은 문서를 다시 처리해도 바뀌지 않는 값을 사용합니다. 이 절에서 먼저 파일과 메타데이터 개수를 확인한 뒤, 다음 절부터 형식별 파서로 실제 내용을 읽습니다.
labs/data/rag-corpus/에는 교육용으로 만든 가상 PDF 21건이 있습니다. 18건은 글자를 추출할 수 있고, 3건은 글자 층이 없는 스캔 PDF입니다. 기본 노트북은 제공 PDF 한 건의 경로와 메타데이터를 확인합니다. 수강생이 실제 업무에서 다룰 문서 100건은 아직 제공되지 않았으며, 자료가 준비되면 각 파일에 같은 메타데이터 항목을 붙여 확장합니다.
3앞에서 배운 내용
문자열과 정수 — 따옴표로 감싼 값은 문자열이고, int()는 숫자 문자열을 정수로 바꿉니다.
목록과 딕셔너리 — 목록은 여러 값을 순서대로, 딕셔너리는 키와 값을 한 쌍으로 저장합니다.
파일 경로 — Path 객체로 폴더와 파일 경로를 연결하고 is_file()로 실제 파일을 확인합니다. 앞 장의 모듈이나 함수를 불러오지 않습니다.
4핵심 개념
비유 — 접수대에서 같은 칸을 가진 봉투로 옮기기
한 기관의 접수대에 종이 신청서, 이메일 인쇄물, 엑셀 목록이 함께 들어온다고 생각해 보세요. 담당자는 원본을 그대로 창고에 보관하고, 처리 부서에는 같은 모양의 봉투로 전달합니다. 봉투 앞면에는 접수 번호, 원본 종류, 접수 시각, 담당 부서를 적습니다. 처리 부서는 봉투 안의 본문을 읽으면 되고, 원본 형식에 따라 접수 방법이 달랐다는 사실까지 알 필요는 없습니다. 로더가 하는 일도 이와 같습니다. 파일별 파서는 다르지만, 청킹 단계에 넘기는 결과는 같은 Document 구조여야 합니다.
정의
문서 객체 (Document)
추출한 본문과 부가 정보를 한 단위로 묶은 객체입니다. LangChain의 Document는 page_content와 metadata를 가집니다. 이후 청킹·임베딩·검색은 원본 파일 대신 이 객체를 받습니다.
파서 (parser)
파일의 내부 구조를 해석하여 텍스트, 표, 이미지 위치 같은 내용을 추출하는 프로그램입니다. 같은 PDF라도 파서에 따라 읽기 순서와 표 표현이 달라질 수 있습니다.
메타데이터 (metadata)
본문을 설명하는 부가 정보입니다. 문서 ID, 원본 파일명, 쪽 번호, 형식, 수정 시각처럼 검색 필터와 출처 표기에 필요한 값을 담습니다.
출처 계보 (provenance)
검색된 청크가 어느 원본 파일의 몇 쪽에서 나왔는지 찾을 수 있게 남긴 기록입니다. 이를 출처 계보라고 부릅니다. source, parser, page를 함께 남기면 검색된 청크를 원본까지 거슬러 확인할 수 있습니다.
도식 — 파일이 달라도 본문과 출처를 담는 칸은 같습니다
01절은 출처 메타데이터를 준비하고, 02~04절은 파일별 본문·표·행을 읽습니다. 도식 오른쪽의 두 칸은 이 결과를 후속 단계에서 Document로 옮길 때 사용할 자리입니다.
모든 로더가 같은 이름의 메타데이터 항목을 만들도록 먼저 정합니다. 예를 들어 쪽 번호는 항상 page, 파일명은 항상 source에 저장합니다. doc_id가 같은 문서를 다시 처리할 때마다 바뀌면 이전 색인과 새 색인의 결과를 비교하기 어렵습니다. 파일명이 바뀔 수 있는 환경에서는 업무 시스템의 문서 번호를 사용하고, 그런 번호가 없으면 대소문자와 슬래시 표기를 한 방식으로 맞춘 상대 경로나, 파일 내용으로 계산한 해시를 조합합니다. 이 챕터의 교육용 가상 문서는 파일명 앞의 E01, M03, H06을 문서 ID로 사용합니다.
메타데이터는 세 부류로 나누어 생각할 수 있습니다. 첫째, 원본에서 직접 읽은 값입니다. 제목, 작성자, 수정 시각이 여기에 해당합니다. 둘째, 파일 시스템에서 얻은 값입니다. 상대 경로, 확장자, 파일 크기입니다. 셋째, 처리 과정이 만든 값입니다. 사용한 파서 이름, 처리 시각, OCR 적용 여부, 청크 번호입니다. 이 세 부류를 구분해 두면 잘못된 값의 책임 지점을 찾기 쉽습니다. 예를 들어 PDF 안의 제목과 파일명이 다르면 어느 값을 저장할지 팀의 규칙으로 정할 수 있습니다.
필드예시사용 지점주의할 점
doc_idM03Ch 11 정답 문서 비교재처리해도 바뀌지 않아야 합니다.
sourceM03.pdf출처 표시와 오류 조사이 실습은 파일명만 저장합니다. 같은 파일명이 여러 폴더에 있다면 상대 경로도 별도 항목으로 저장합니다.
page4쪽 단위 출처 표기0부터 시작하는지 1부터 시작하는지 고정합니다.
file_typepdf형식별 실패 집계확장자만 믿지 않고 실제 처리 결과와 함께 봅니다.
parserpypdf다른 도구로 읽은 결과와 비교나중에 같은 도구로 다시 읽을 수 있게 버전도 적어 둡니다.
경로 정보와 문서 메타데이터를 구분하기
Path 객체는 파일 자체가 아니라 파일 위치를 표현합니다. source.name은 확장자를 포함한 이름, stem은 확장자를 뺀 이름, suffix는 확장자를 반환합니다. 점 뒤에 괄호가 없는 것은 저장된 속성을 읽는 표기이며, is_file()처럼 괄호가 있으면 검사를 실행하는 메서드 호출입니다.
Document(page_content=본문, metadata=사전)는 검색할 텍스트와 출처 정보를 한 객체로 묶습니다. 메타데이터는 모델이 자동으로 이해하는 본문이 아니라 검색·필터·출처 표시에서 코드가 사용하는 값입니다. 같은 내용의 개정판이 들어올 수 있는 규정 문서라면 파일명뿐 아니라 문서 ID와 시행일을 별도 키로 저장해야 어느 판본에서 나온 청크인지 구분할 수 있습니다.
5실행 예제
내려받은 실습 폴더 안에서 노트북을 열고 위에서 아래로 실행합니다. 별도 패키지나 API 키는 필요하지 않습니다. 먼저 Python 버전과 제공된 E02.pdf 위치를 확인하고, Path 객체의 속성을 관찰합니다. 이어서 메타데이터 딕셔너리를 만든 뒤 쪽 번호를 2에서 3으로 바꾸어 원본과 새 결과를 비교합니다. 이번 절은 metadata 딕셔너리까지만 만들며, 본문인 page_content와 실제 Document 객체는 02~04절의 파일 로딩 결과를 바탕으로 후속 단계에서 구성합니다.
6일부러 실패해 보기
Python은 목록 위치를 0부터 세지만, 사람이 보는 PDF 쪽 번호는 1부터 셉니다. Before 셀은 두 번째 쪽의 위치값 1을 출처에 그대로 저장해 실제 2쪽을 1쪽으로 잘못 표시합니다. After 셀은 위치값에 1을 더해 선택한 쪽과 출처 표시를 모두 2쪽으로 맞춥니다.
7주의할 점과 실무 메모
문서를 구별하는 ID와 제목을 구분합니다. 제목은 사람이 읽기 위한 값이라 수정될 수 있습니다. doc_id는 제목이나 파일명이 바뀌어도 같은 문서라면 같은 값을 유지합니다.
쪽 번호의 기준을 통일합니다. 일부 라이브러리는 첫 쪽을 0으로 반환합니다. 교재와 최종 출처 표시는 사람이 보는 쪽 번호인 1부터 시작하도록 변환합니다.
원본을 보존합니다. 추출 텍스트만 남기면 파서 오류를 다시 확인할 수 없습니다. 추출한 텍스트에 원본 파일명과 쪽 번호를 함께 저장합니다.
민감한 경로와 문서 속성을 걸러냅니다. 작성자 계정, 내부 서버 경로, 임시 폴더 이름은 검색 품질에 필요하지 않다면 배포용 메타데이터에서 제외합니다.
재처리 조건을 기록합니다. 파일 수정 시각이나 내용 해시를 보관하면 바뀐 문서만 다시 파싱하고 임베딩할 수 있습니다. 캐싱과 재임베딩 비용은 이 챕터 후반 절에서 다룹니다.
8정리와 다음 절
Path의 name·stem·suffix 속성으로 실제 파일 경로에서 메타데이터 값을 얻습니다.
doc_id·source·page·file_type·parser를 딕셔너리의 공통 키로 저장합니다.
딕셔너리를 펼쳐 새 값을 덮어쓰면 원본을 보존하면서 변경 전후를 비교할 수 있습니다.
다음 학습과 이어지는 지점 — 이 절의 입력 목록과 공통 메타데이터는 02~04절의 로더 결과에 같은 이름으로 저장할 항목입니다. Ch 11에서는 doc_id를 정답표와 비교합니다. file_type과 parser는 문서 처리 조건을 구분하는 기록으로 남지만, Ch 12의 기본 실습이 이 필드를 실패 유형별로 집계하지는 않습니다. 다음 02절에서는 같은 PDF를 서로 다른 방식으로 읽어 표의 행·열과 스캔본의 글자가 실제 추출 결과에서 빠지는지 확인합니다.
9복습 문제
문제 4개 · 해설 포함
1. [하] 여러 파일 형식의 로더가 같은 Document 구조를 반환해야 하는 이유는 무엇입니까?
청킹·임베딩·검색 단계가 원본 형식마다 별도 코드를 가질 필요 없이 page_content와 metadata라는 같은 두 항목만 처리하면 되기 때문입니다. 형식별 차이는 로더 안에서 흡수하고, 본문과 메타데이터 구조는 통일합니다.
2. [중] doc_id와 문서 제목을 같은 값으로 사용했을 때 생길 수 있는 문제를 설명하세요.
제목은 사람이 수정하거나 여러 문서에서 중복할 수 있습니다. 제목이 바뀌면 같은 문서를 새 문서로 인식하고, 제목이 중복되면 서로 다른 문서의 청크가 하나로 집계됩니다. 제목이 바뀌어도 유지되는 업무 문서 번호나 상대 경로·내용 해시 조합을 사용해야 합니다.
3. [중] source = Path("E02.pdf")일 때 source.name, source.stem, source.suffix는 각각 무엇입니까?
name은 E02.pdf, stem은 E02, suffix는 .pdf입니다.
4. [상] 파서를 교체한 뒤 검색 품질이 달라졌습니다. 나중에 같은 조건으로 다시 확인하려면 어떤 메타데이터가 필요합니까?
최소한 원본을 가리키는 doc_id와 source, 쪽 번호, 파일 형식, 파서 이름과 버전, 처리 시각 또는 사용한 설정을 구별하는 이름이 필요합니다. 이 정보로 같은 원본을 같은 조건에서 다시 처리하고 이전에 읽은 결과와 비교할 수 있습니다.

1학습 목표
이 절을 마치면 디지털 PDF와 스캔 PDF의 차이를 설명하고, 텍스트 추출과 OCR 적용 조건을 구분할 수 있습니다.
이 절을 마치면 제공된 PDF를 PdfReader로 열고 쪽 객체·본문 길이·본문 앞부분을 확인할 수 있습니다.
이 절을 마치면 같은 쪽의 기본 텍스트와 레이아웃 텍스트, 표 목록을 비교하고 선택한 쪽을 바꿀 수 있습니다.
2이 내용을 배우는 이유
Ch 9에서는 pypdf의 기본 텍스트 추출로 PDF 기반 RAG 흐름을 확인했습니다. 이번 노트북은 앞 장의 함수를 가져오지 않고 제공된 PDF를 직접 엽니다. 중간 난이도 문서의 표와 어려운 문서의 두 단 레이아웃에서는 글자가 추출되어도 의미가 보존되지 않을 수 있습니다. 스캔 변형본 세 건은 이미지 안에 글자가 있으므로 추출 결과가 비어 있습니다. 파일을 열 수 있다는 사실과 검색에 사용할 수 있는 본문을 얻었다는 사실을 구분해야 합니다.
PDF는 화면이나 인쇄 결과를 정확히 배치하기 위한 형식입니다. 일부 PDF는 태그나 구조 정보를 가질 수 있지만, 일반적인 텍스트 추출이 문단·표·머리말이라는 의미 구조를 항상 복원할 수 있는 것은 아닙니다. 글자가 쪽의 절대 좌표에 놓여 있으면 추출기는 어느 글자가 같은 행과 열인지 추정해야 합니다. 따라서 파서의 성공 여부를 “문자열이 반환되었다” 하나로 판정해서는 안 됩니다. 원본에서 중요했던 구조가 검색 가능한 표현으로 남았는지 확인해야 합니다.
3앞에서 배운 내용
목록 위치 — Python 목록은 0부터 시작하므로 pages[1]은 두 번째 쪽 객체입니다.
문자열 길이 — len()은 추출한 문자열의 글자 수를 반환하며, text[:120]은 앞부분을 확인합니다.
01절 경로 확인 — 상위 폴더를 순서대로 살펴 제공된 파일을 찾고, 파일이 없으면 파싱 전에 중단합니다. 앞 장의 로더 함수는 사용하지 않습니다.
4핵심 개념
비유 — 좌석 배치도와 참석자 명단
회의장 좌석 배치도에는 사람 이름이 공간에 놓여 있습니다. 글자를 위에서 아래로만 읽으면 왼쪽 열과 오른쪽 열의 이름이 섞일 수 있습니다. 표도 같습니다. 사람은 선과 간격을 보고 같은 행을 알아보지만, 텍스트 추출기는 좌표를 읽기 순서로 바꾸는 규칙이 필요합니다. OCR은 사진 속 이름표를 문자로 바꾸는 일입니다. 문자로 바꾼 뒤에도 어느 좌석에 해당하는지 정리하는 작업은 별도로 남습니다.
정의
텍스트 레이어 (text layer)PDF 안에서 선택·검색할 수 있는 문자 정보입니다. 스캔 PDF는 페이지 이미지밖에 없어 텍스트 레이어가 없을 수 있습니다.
레이아웃 (layout)글자·문단·열·표가 쪽 위에 배치된 공간 관계입니다. 문자열 추출 과정에서 이 관계의 일부가 사라질 수 있습니다.
읽기 순서 (reading order)사람이 문서 내용을 따라가는 순서입니다. 두 단 문서에서는 왼쪽 단을 끝까지 읽은 뒤 오른쪽 단으로 가야 하지만, 좌표 해석에 따라 줄별로 섞일 수 있습니다.
표 추출 (table extraction)표의 셀 경계와 행·열 관계를 찾아 구조화된 값으로 복원하는 처리입니다. 일반 텍스트 추출과 별도의 검출 전략이 필요할 수 있습니다.
광학 문자 인식 (optical character recognition, OCR)페이지 이미지의 글자 모양을 문자로 인식하는 처리입니다. OCR은 오탈자를 만들 수 있으며 표 구조를 자동으로 보장하지 않습니다.
셀 텍스트만 나열하면 머리글과 행의 대응이 사라집니다. 각 행에 머리글을 포함하여 직렬화하면 검색된 조각만으로도 값의 의미를 읽을 수 있습니다.
이번 실습은 pypdf의 기본 텍스트와 pdfplumber에서 layout=True로 얻은 레이아웃 텍스트·표 목록을 같은 쪽에서 비교합니다. 서로 다른 두 라이브러리의 결과를 비교하므로, 한 라이브러리에서 옵션 하나만 바꾼 효과를 측정하는 실험은 아닙니다. 두 반환값이 존재한다는 사실만으로 읽기 순서나 표의 행·열 관계가 정확하다고 확정할 수도 없습니다. PyMuPDF의 Page.find_tables()처럼 선이나 텍스트 위치로 표 후보를 찾는 기능은 다음 비교 단계의 후보이며, 검출 전략과 허용오차에 따라 결과가 달라집니다.
OCR 적용 여부는 파일 단위보다 쪽 단위로 결정하는 편이 안전합니다. 디지털 PDF 전체를 이미지로 바꿔 OCR하면 원래 PDF에 있던 글꼴·인코딩 정보가 사라지고, 비슷한 문자를 잘못 인식할 수 있습니다. 처리 시간도 늘어납니다. 먼저 추출 문자열 길이, 한글 비율, 대체 문자 수를 기록하고, 값이 낮은 쪽을 사람 검토 대상으로 표시합니다. OCR을 적용한 쪽에는 ocr_used=true와 사용한 엔진·언어 설정을 메타데이터에 남깁니다.
검사확인하는 문제자동 판정의 한계
추출 글자 수빈 스캔 쪽, 지나치게 짧은 결과표지처럼 실제로 짧은 쪽도 있습니다.
한글 비율글꼴 인코딩 오류, OCR 언어 설정 오류영문 사양표에는 낮은 값이 정상일 수 있습니다.
표 머리글과 값의 인접성행·열 관계 손실문자열 규칙만으로 병합 셀을 확정하기 어렵습니다.
원본 쪽 대조누락·순서·표 구조사람 검토가 필요하지만 대표 쪽에 한정할 수 있습니다.
텍스트 추출과 OCR의 경계
PdfReader(path)는 PDF 구조를 읽는 객체를 만들고, 실제 쪽 텍스트는 reader.pages[n].extract_text()를 호출할 때 문자열 또는 None으로 반환됩니다. pdfplumber.open(path)는 글자 위치와 표 후보를 함께 다룰 수 있으며 extract_table()은 찾은 표를 행 목록으로 반환합니다. 두 라이브러리의 반환값은 원래 페이지 모양을 그대로 보존한 화면이 아닙니다.
스캔 PDF에서 빈 문자열이 나온 것은 파일이 비었다는 뜻이 아니라 검색 가능한 텍스트 층이 없을 수 있다는 신호입니다. OCR은 페이지 이미지를 글자로 인식하는 별도 처리이며 이 노트북은 수행하지 않습니다. 디지털 영수증의 표는 좌표 기반 추출을 먼저 시도할 수 있지만, 촬영한 영수증은 OCR과 표 구조 복원이 모두 필요합니다.
5실행 예제
첫 셀에서 pypdf와 pdfplumber를 설치합니다. API 키는 필요하지 않습니다. 제공된 디지털 PDF와 스캔 PDF의 위치·크기를 먼저 확인한 뒤, PDF 객체, 선택한 쪽, 본문 길이와 앞부분을 차례대로 관찰합니다. 같은 쪽을 pdfplumber로 읽어 레이아웃 문자열과 표 목록을 비교하고, 마지막으로 선택값을 2쪽에서 1쪽으로 바꾸어 글자 수 차이를 확인합니다.
6일부러 실패해 보기
Before 셀은 스캔 PDF의 모든 쪽에서 텍스트가 바로 추출된다고 가정해 실패합니다. After 셀은 각 쪽의 문자열 길이를 검사해 OCR 후보 번호만 반환합니다. 이 실습은 OCR 엔진을 설치하거나 실행하지 않으며, 후보 분류 결과를 OCR 성공으로 해석하지 않습니다.
7주의할 점과 실무 메모
PDF는 의미 구조를 항상 보장하지 않습니다. 태그가 있는 PDF도 있지만, 일반 텍스트 추출이 표·문단 구조를 안정적으로 복원한다고 전제하지 않습니다.
OCR 엔진은 별도 의존성입니다. PyMuPDF의 통합 OCR도 Tesseract 설치가 필요합니다. 설치·언어 데이터·버전을 실행 환경에 기록합니다.
메모리를 확인합니다. 압축된 콘텐츠 스트림이 매우 크게 풀리는 PDF가 있으므로 파일 크기만으로 처리 비용을 판단하지 않습니다.
라이선스를 확인합니다. PyMuPDF/MuPDF는 AGPL 또는 상용 라이선스 체계입니다. 교육 실습과 제품 배포의 조건을 별도로 검토합니다.
상용 API 가격은 확인일과 함께 적습니다. Upstage의 Parse only 가격은 2026-09-08 기준 페이지당 미화 0.01달러로 표시되지만 변경될 수 있습니다. LlamaParse는 티어와 파서 버전을 실행 기록에 고정합니다.
8정리와 다음 절
디지털 PDF의 문자 추출, 표 구조 복원, 스캔 이미지 OCR은 서로 다른 문제입니다.
pypdf 기본 텍스트와 pdfplumber의 layout=True 레이아웃 텍스트·표 목록을 비교합니다. 두 라이브러리가 다르므로 옵션 하나의 단독 효과 비교가 아니며, 어느 쪽도 원본 구조의 정확성을 자동으로 보장하지 않습니다.
텍스트 품질을 쪽 단위로 검사하고 필요한 쪽만 OCR 후보로 보내며, 표와 읽기 순서는 원본과 대조합니다.
다음 학습과 이어지는 지점 — 이 실습에서 확인한 쪽 번호·본문 길이·표 개수·OCR 후보는 문서 처리 결과를 설명하는 메타데이터가 됩니다. 이번 실행은 S01의 5쪽을 후보로 분류하며 OCR은 실행하지 않습니다. 다음 03절에서는 DOCX·HTML·CSV 객체가 보존하는 구조를 직접 확인합니다.
9복습 문제
문제 4개 · 해설 포함
1. [하] 텍스트 추출과 OCR의 차이는 무엇입니까?
텍스트 추출은 PDF에 이미 저장된 문자 정보를 읽습니다. OCR은 페이지 이미지의 글자 모양을 새 문자로 인식합니다.
2. [중] PDF에서 모든 숫자가 추출되었는데도 표 질의에 답하지 못하는 이유는 무엇입니까?
숫자와 행·열 머리글의 관계가 사라질 수 있기 때문입니다. 표 질의에는 값 자체뿐 아니라 그 값이 어떤 조건과 항목에 해당하는지 필요합니다.
3. [중] pages[page_number - 1]처럼 1을 빼는 이유는 무엇입니까?
사람이 보는 쪽 번호는 1부터 시작하지만 Python 목록 위치는 0부터 시작하기 때문입니다. 2쪽은 목록 위치 1에 있습니다.
4. [상] 두 단 PDF의 읽기 순서가 잘못된 상태에서 청크 크기만 조정하면 해결되지 않는 이유는 무엇입니까?
청킹은 입력 문자열의 순서를 신뢰합니다. 파서가 서로 다른 단의 문장을 이미 섞었다면 청크 크기를 바꾸어도 잘못 연결된 문장 관계가 남으므로 파서나 레이아웃 처리 단계에서 고쳐야 합니다.

1학습 목표
이 절을 마치면 DOCX의 문단·표, HTML의 제목·본문, CSV의 머리글·행을 서로 다른 처리 단위로 설명할 수 있습니다.
이 절을 마치면 제공된 DOCX의 문단 객체, HTML의 태그 객체, CSV의 행 딕셔너리를 만들고 값을 확인할 수 있습니다.
이 절을 마치면 같은 CSV 행에서 선택하는 열을 바꾸어 결과를 비교하고, 필요한 열을 읽기 전에 CSV 첫 줄에 그 열 이름이 있는지 확인할 수 있습니다.
2이 내용을 배우는 이유
PDF에서는 문단과 표를 추정해야 했습니다. DOCX, HTML, CSV는 작성 도구가 구조를 비교적 분명하게 저장합니다. DOCX에는 문단과 표 객체가 있고, HTML에는 제목과 본문 요소가 있으며, CSV에는 열 머리글과 행이 있습니다. 이 구조를 모두 평문 한 덩어리로 바꾸면 파서가 제공한 정보를 스스로 버리는 셈입니다. 로더 단계에서 구조를 보존해야 뒤의 구조 기반 청킹이 제목, 표, 행 경계를 사용할 수 있습니다.
모든 형식을 Document로 바꾸더라도 내용을 똑같은 크기로 잘라야 하는 것은 아닙니다. 형식마다 의미 있는 최소 단위가 다릅니다. 이번 기본 실습은 공통 객체로 변환하기 전에 DOCX 문단, HTML 제목·본문, CSV 열·행을 각각 확인합니다. 반환 구조를 이해한 뒤에야 본문과 메타데이터로 옮길 범위를 정할 수 있습니다.

반복문과 조건문 — for로 항목을 하나씩 확인하고 if로 빈 문단이나 불필요한 태그를 제외합니다.
01절 딕셔너리 — 키로 값을 선택하는 방법을 사용합니다. 이 노트북은 앞 장의 로더나 청킹 함수를 가져오지 않습니다.
4핵심 개념
비유 — 서랍의 칸막이를 유지하기
서류함의 칸막이에는 계약서, 영수증, 고객 명단이 구분되어 있습니다. 모든 종이를 꺼내 한 줄로 이어 붙이면 글자는 남지만 분류 기준이 사라집니다. DOCX의 문단과 표, HTML의 제목 계층, CSV의 행도 같은 역할을 합니다. 기본 실습은 제공 파일에서 문단·제목·본문·열·행을 따로 출력합니다. 이후 구조 기반 청킹에서는 필요한 경우 단위 종류와 위치 필드를 더합니다.
정의
문단 (paragraph)DOCX에서 문장과 서식을 담는 기본 블록입니다. 빈 문단과 제목 문단도 있으므로 텍스트만 보고 역할을 확정하지 않습니다.
문서 객체 모델 (Document Object Model, DOM)HTML 요소를 부모와 자식 관계의 트리로 표현한 구조입니다. 제목 아래의 본문과 목록을 같은 구역으로 묶는 근거가 됩니다.
본문 선택자 (content selector)HTML에서 실제 문서 내용이 들어 있는 요소를 고르는 규칙입니다. 내비게이션·광고·바닥글을 제외하고 main이나 지정된 article을 선택합니다.
CSV 방언 (CSV dialect)구분자, 따옴표, 이스케이프 방식처럼 CSV 생산자마다 달라지는 형식 규칙의 묶음입니다.
형식 보존 단위 (typed unit)본문과 함께 paragraph, table, section, row 같은 종류를 기록한 처리 단위입니다.
DOCX 문단, HTML 제목·본문, CSV 머리글을 포함한 행은 서로 다른 객체로 읽힙니다. 기본 실습은 각 객체와 값을 직접 관찰하고, 공통 Document 변환은 이후 확장 단계에서 수행합니다.
기본 실습은 DOCX의 비어 있지 않은 문단, HTML의 h1과 p, CSV의 열 이름과 행을 읽습니다. 세 형식의 반환 객체가 다르다는 사실을 출력에서 먼저 확인합니다.
원리 더 알아보기
DOCX는 python-docx로 문단과 표를 별도 객체로 읽을 수 있습니다. 표까지 확장할 때는 iter_inner_content()로 문서 순서를 따르고, 표 제목과 열 이름을 각 처리 단위에 남길 수 있습니다. 표를 행별 Document로 나누거나 table_index 메타데이터를 붙이는 처리는 기본 실습에 포함하지 않습니다.
HTML은 script와 style을 제거한 뒤 선택한 태그를 읽습니다. 운영 사이트에서는 main이나 article 선택자를 추가해 메뉴와 바닥글을 제외합니다. CSV는 열 이름과 값을 결합해야 각 값의 의미를 보존할 수 있습니다. 인코딩, 구분자, 헤더 유무는 자동 추정 결과만 믿지 않고 파일을 읽는 조건으로 적어 둡니다. 예를 들어 UTF-8, 쉼표 구분, 첫 줄을 열 이름으로 사용한다고 기록합니다.
형식별 구조를 먼저 읽기
docx.Document(path)는 Word 문서를 열어 문단 객체 목록을 제공하고, paragraph.text가 각 문단의 문자열입니다. BeautifulSoup(html, "html.parser")는 태그 트리를 만들며 select_one("main")은 CSS 선택자에 맞는 첫 요소를 반환합니다. csv.DictReader는 첫 행을 열 이름으로 사용해 이후 행을 사전으로 반환합니다.
세 로더는 모두 텍스트를 얻지만 보존하는 구조가 다릅니다. DOCX는 문단 순서, HTML은 태그 계층, CSV는 열 이름이 의미의 단서입니다. 상품 표를 하나의 긴 문자열로 합치면 행과 열의 관계가 사라지므로 행별 Document와 상품 ID 메타데이터가 적합합니다. 반면 기사 HTML은 메뉴를 제외하고 main 본문을 하나의 문서로 추출할 수 있습니다.
5실행 예제
첫 셀에서 DOCX와 HTML 패키지를 설치하고 Ch10의 fixtures 폴더에서 세 파일을 확인합니다. API 키는 필요하지 않습니다. 이후 DOCX 문단, HTML 제목·문단, CSV 열 이름·행을 별도 셀에서 파싱하고 각 객체의 자료형과 반환값을 관찰합니다. 같은 CSV 행에서 선택 열을 상품에서 보관으로 바꾸어 값의 차이도 확인합니다.
6일부러 실패해 보기
Before 셀은 CSV 행에서 값만 꺼내 상품과 보관이라는 열 이름이 사라진 결과를 확인합니다. After 셀은 DictReader가 만든 딕셔너리를 유지해 첫 행의 상품과 보관 방법을 이름으로 읽고, 쿠키의 보관 방법: 실온처럼 관계가 드러나는 문장으로 출력합니다.
7주의할 점과 실무 메모
구조를 보존하되 거대한 단위로 만들지 않습니다. 문서 전체 표가 지나치게 크면 행 묶음으로 나누고 표 제목과 머리글을 각 단위에 반복합니다.
빈 문단과 숨김 요소를 검사합니다. 화면에 보이지 않는 텍스트나 변경 내용이 추출될 수 있으므로 업무 규칙에 맞는 포함 범위를 정합니다.
인코딩 오류를 조용히 대체하지 않습니다. 잘못 읽은 CSV를 대체 문자로 저장하면 원본 손실을 찾기 어렵습니다. 후보 인코딩과 실패를 로그에 남깁니다.
HTML 파서를 고정합니다. 잘못된 HTML에서 파서별 DOM이 달라질 수 있으므로 라이브러리와 파서 이름을 함께 기록합니다.
개인정보 열을 구분합니다. CSV의 주민번호·연락처처럼 검색에 불필요한 열은 로더에서 제외하거나 권한이 있는 사람만 읽을 수 있는 저장 위치로 분리합니다.

docx.paragraphs는 Document()가 반환한 docx 객체의 DOCX 문단 목록이며, BeautifulSoup.find_all()은 선택한 HTML 태그를 반환합니다.
csv.DictReader는 첫 줄을 열 이름으로 사용하고 각 데이터 행을 딕셔너리로 반환합니다.
CSV 열을 읽기 전에 실제 열 이름 집합을 검증하면 열 이름 오타와 CSV 첫 줄의 변경을 구체적인 오류로 확인할 수 있습니다.

1학습 목표
이 절을 마치면 HWP와 HWPX가 내부 구조와 처리 방법에서 어떻게 다른지 설명할 수 있습니다.
이 절을 마치면 제공된 HWPX의 ZIP 항목을 확인하고 본문 section XML만 선택해 텍스트를 추출할 수 있습니다.
이 절을 마치면 전체 XML과 본문 XML의 선택 결과를 비교하고, 레거시 HWP를 미지원 경로로 안전하게 분기할 수 있습니다.
2이 내용을 배우는 이유
한국의 공공기관과 기업 문서 저장소에는 HWP와 HWPX가 함께 있습니다. PDF만 처리하는 RAG는 결재문, 공고문, 회의 자료의 일부를 놓칠 수 있습니다. 그러나 두 확장자를 같은 방식으로 읽을 수 있다고 생각하면 구현 범위를 잘못 잡게 됩니다. HWP는 전용 구조를 해석해야 하는 네이티브 형식이고, HWPX는 본문과 설정을 담은 여러 XML 파일을 ZIP 방식으로 한 파일에 묶은 개방형 형식입니다. 이번 절은 모든 HWP·HWPX 문서를 완벽하게 파싱한다고 약속하는 대신, 파일 내부가 ZIP인지 먼저 확인하고, HWP와 HWPX를 서로 다른 읽기 방법으로 보내는 과정을 다룹니다.
기본 문서 묶음은 PDF이므로 Ch10 실습 폴더에 HWPX 구조 관찰용 최소 표식과 레거시 HWP 형식 분기용 표식을 별도로 제공합니다. 이 파일로 ZIP/XML 읽기와 미지원 분기를 검증할 수 있지만 실제 업무 문서의 표·각주·이미지나 한컴오피스 호환성을 주장하지 않습니다. 수강생이 실제 업무에서 다룰 문서 100건도 아직 저장소에 없으므로 HWP/HWPX 비율이나 처리 성공률을 제시하지 않습니다.
3앞에서 배운 내용
파일과 폴더 — Path로 제공 파일을 찾고 파일이 실제로 있는지 확인합니다.
반복문과 문자열 조건 — ZIP 항목을 하나씩 살펴보고 startswith()와 endswith()로 필요한 이름을 고릅니다.
XML 요소 — 요소 객체는 태그와 텍스트를 가지며 iter()로 자식 요소까지 순회합니다. 앞 절의 로더 함수는 사용하지 않습니다.
4핵심 개념
비유 — 잠긴 서류함과 라벨이 붙은 상자
HWP를 규격에 맞는 열쇠와 해석표가 필요한 서류함이라고 생각해 보세요. HWPX는 여러 XML 문서를 라벨이 붙은 상자에 나누어 담고, 그 상자를 ZIP으로 묶은 형태에 가깝습니다. HWPX는 상자를 열어 항목을 확인하기가 더 수월하지만, 라벨을 읽었다고 문단·표·각주가 저절로 완성되는 것은 아닙니다. 어떤 XML이 본문이고 요소의 순서가 무엇인지 해석해야 합니다.
정의
HWP 네이티브 형식 (HWP native format)한컴 한글의 전용 문서 형식입니다. 내부 레코드와 구조를 이해하는 전용 도구 또는 변환 경로가 필요하며, 범용 ZIP/XML 처리만으로 읽을 수 없습니다.
HWPX한글 문서의 XML 파일 구조를 정한 OWPML을 따르며, 국가표준 KS X 6101에 등록된 개방형 파일 형식입니다. 여러 XML과 자원을 ZIP 컨테이너에 담습니다.
개방형 워드프로세서 마크업 언어 (Open Word-Processor Markup Language, OWPML)HWPX 문서의 구조와 내용을 XML로 표현하는 규격입니다. 본문, 설정, 메타데이터가 여러 항목으로 나뉠 수 있습니다.
ZIP 컨테이너 (ZIP container)여러 XML·이미지·설정 파일을 ZIP 압축 폴더처럼 하나의 문서 파일 안에 묶는 저장 방식입니다. 확장자가 .hwpx여도 내부 항목과 필수 파일을 검사해야 합니다.
HWP는 전용 바이너리 해석기나 변환 도구를 거치고, HWPX는 ZIP 안의 XML을 검사합니다. 본문 추출을 마친 결과는 후속 단계에서 Document와 출처 메타데이터로 옮길 수 있습니다. 이번 실습은 HWP의 미지원 상태와 HWPX에서 읽은 문자열까지만 확인하며, Document를 만들지는 않습니다.
HWPX 처리의 첫 단계는 파일을 열어 항목 목록을 확인하는 것입니다. 그다음 본문 XML을 문서 순서대로 읽고, 텍스트 노드와 문단 경계를 추출합니다. 파일 안의 모든 XML 텍스트를 합치면 스타일 이름, 설정값, 메타데이터가 본문에 섞일 수 있습니다. 본문 항목을 명시적으로 선택하고, 문단 번호나 구역 파일명을 section에 남깁니다. 표와 병합 셀은 별도의 구조 해석이 필요하므로 기본 텍스트 로더가 어느 요소를 지원하는지 문서화합니다.
HWP에는 세 가지 현실적인 경로가 있습니다. 첫째, 신뢰할 수 있는 환경에서 HWPX나 PDF로 변환한 뒤 변환 산출물을 처리합니다. 둘째, 한컴이 제공하는 도구나 SDK를 사용합니다. 셋째, 회사의 보안 규칙상 외부 전송이 허용되면 상용 문서 파서에 전달합니다. 어느 경로든 원본과 변환본의 관계, 변환 도구 버전, 실패 파일을 기록합니다. 변환에 성공했다는 사실이 표·각주·변경 내용까지 보존되었다는 뜻은 아니므로 대표 문서를 원본과 대조합니다.

컨테이너와 본문 형식을 나누어 읽기
zipfile.is_zipfile(path)는 파일이 ZIP 컨테이너인지 확인하고, ZipFile(path)를 with 블록에서 열면 블록이 끝날 때 파일이 닫힙니다. HWPX 내부의 XML 바이트를 ElementTree.fromstring()에 넣으면 요소 트리가 반환됩니다. 태그 앞의 네임스페이스는 서로 다른 XML 어휘의 같은 태그 이름을 구분합니다.
ZIP을 열 수 있다는 사실과 HWPX 본문을 올바르게 복원했다는 사실은 다릅니다. 본문은 여러 섹션 XML에 나뉠 수 있고 표·각주·그림 순서도 별도 규칙이 필요합니다. 레거시 HWP는 ZIP/XML 형식이 아니므로 같은 코드로 읽을 수 없습니다. 이 절의 최소 표식 파일 성공은 실제 기관 문서 전체의 호환성을 보장하지 않습니다.
5실행 예제
별도 패키지와 API 키 없이 Python 표준 라이브러리만 사용합니다. Ch10의 fixtures 폴더에서 두 표식 파일을 확인하고, HWPX가 ZIP인지 검사한 뒤 내부 항목 목록을 관찰합니다. 모든 XML에서 본문 section XML로 선택 조건을 좁히고, XML 요소 객체와 추출 본문을 차례대로 출력합니다. 이 최소 파일은 코드 경로 확인용이며 실제 한컴오피스 호환성을 증명하지 않습니다.
6일부러 실패해 보기
Before 셀은 레거시 HWP 표식 파일을 ZIP으로 열어 BadZipFile을 포착합니다. After 셀은 같은 원인을 해결하기 위해 앞 8바이트와 ZIP 구조를 먼저 확인합니다. 표식 HWP는 미지원으로 분류하고 HWPX만 ZIP/XML 경로로 읽습니다. 파일 앞부분의 OLE 표식 하나만으로 일반 파일을 HWP라고 확정하지 않습니다.
7주의할 점과 실무 메모
HWP와 HWPX를 같은 형식으로 취급하지 않습니다. 확장자별 처리 경로와 실패 메시지를 분리합니다.
HWPX도 완전한 평문 형식은 아닙니다. ZIP 안의 여러 XML, 이미지, 표, 각주 관계를 해석해야 합니다.
변환본의 출처를 남깁니다. 원본 HWP의 ID, 변환 파일 경로, 변환 도구와 시각을 기록해야 갱신과 오류 조사가 가능합니다.
외부 서비스에 보내도 되는 문서인지 먼저 확인합니다. 계약서·인사 문서·개인정보가 든 HWP를 상용 API에 보내기 전에 회사 승인을 받고, 외부 서비스가 파일을 얼마나 오래 보관하는지 확인합니다.
호환성 표는 실제 샘플로 만듭니다. 문단, 표, 병합 셀, 각주, 이미지, 암호화 문서를 각각 검사하고 성공·부분 성공·실패로 구분합니다.
8정리와 다음 절
제공된 HWPX는 ZIP 항목 목록에서 Contents/section*.xml을 선택하고 t 요소의 텍스트를 추출합니다.
전체 XML과 본문 section XML은 범위가 다르므로 선택 조건과 결과 개수를 함께 확인합니다.
레거시 HWP 표식은 전용 파서가 필요한 미지원 경로로 분류하며 본문 추출 성공을 주장하지 않습니다.
다음 학습과 이어지는 지점 — 이번 실습에서 얻은 section 이름과 추출 본문은 다음 청킹 절의 입력 후보가 됩니다. 이 출력은 본문 XML을 골라 문자열을 얻었는지 확인하는 파싱 점검 결과이며, 검색 결과를 정답 문서 ID와 비교하는 Ch 11 평가보다 앞선 준비 단계입니다. 현재 Ch 11은 PDF 말뭉치의 검색 결과를 평가하므로 HWPX 형식·파서별 실패율은 포함하지 않습니다. 이를 측정하려면 대표 HWPX별 기대 문단·표와 파싱 상태를 담은 별도 평가 데이터와 로그가 필요합니다.
9복습 문제
문제 4개 · 해설 포함
1. [하] HWP와 HWPX의 내부 구조 차이를 한 문장으로 설명하세요.
HWP는 전용 구조를 해석해야 하는 네이티브 형식이고, HWPX는 OWPML 기반 XML과 자원을 ZIP 컨테이너에 담은 개방형 형식입니다.
2. [중] HWPX 안의 모든 XML 텍스트를 합치면 어떤 문제가 생깁니까?
설정·메타데이터가 본문에 섞이고 구역 순서가 어긋날 수 있으며, 표·각주 관계도 잃을 수 있습니다. 본문 항목과 필요한 요소를 명시해야 합니다.
3. [중] HWP를 HWPX로 변환한 뒤에도 원본 대조가 필요한 이유는 무엇입니까?
변환 성공은 문단·표·병합 셀·각주·이미지가 모두 보존되었다는 보장이 아닙니다. 검색에 필요한 구조와 값이 남았는지 대표 문서로 확인해야 합니다.
4. [중] name.startswith("Contents/section")와 name.endswith(".xml")을 함께 확인하는 이유는 무엇입니까?
설정 XML이나 이미지 같은 다른 ZIP 항목을 제외하고 본문 section XML 이름만 선택하기 위해서입니다.

1학습 목표
이 절을 마치면 문자 수, 구분자 우선순위, 토큰 수를 기준으로 같은 문서를 세 가지 방식으로 나눌 수 있습니다.
이 절을 마치면 재귀 청킹에서 오버랩이 설정한 최댓값만큼 항상 생기지 않는 이유를 설명할 수 있습니다.
이 절을 마치면 각 청크의 본문과 문자 수 또는 토큰 수를 출력해 분할 결과를 확인할 수 있습니다.
이 절을 마치면 다른 조건을 고정하고 chunk_size 하나만 바꾸어 결과를 비교할 수 있습니다.
2이 내용을 배우는 이유
앞 절까지는 PDF·DOCX·HTML·CSV·HWPX에서 텍스트를 꺼내고, 표와 이미지가 손실되는 지점을 확인했습니다. 파싱한 결과는 아직 문서 전체이거나 쪽 단위입니다. 검색 시스템은 이 긴 텍스트를 그대로 다루지 않습니다. 질문과 직접 관련 있는 범위를 찾을 수 있도록 더 작은 단위인 청크로 나눕니다. 같은 파싱 결과라도 어디에서 끊는지에 따라 검색 결과가 달라지므로, 청킹은 파일을 읽은 다음 가장 먼저 비교할 설정입니다.
긴 컨텍스트 모델을 보고 청크도 크게 만들면 된다고 생각하기 쉽습니다. 그러나 큰 청크는 주변 문맥을 더 보존하는 대신 질문과 무관한 문장도 함께 가져옵니다. 입력 토큰과 임베딩 시간도 늘어날 수 있습니다. 작은 청크는 질문에 맞는 문장을 정밀하게 찾기 쉽지만 설명과 조건이 서로 갈라질 수 있습니다. 이 절의 목표는 한 가지 크기를 정답으로 고르는 것이 아닙니다. 같은 문서를 세 방식으로 나누고, 각 방식이 무엇을 보존하고 무엇을 잃는지 실행 결과로 확인하는 것입니다.

01~04절 파싱 결과 — 청킹의 입력은 파서가 반환한 텍스트와 메타데이터입니다. 파싱 단계에서 사라진 표의 행과 이미지 속 글자는 청킹으로 복구할 수 없습니다.
4핵심 개념
비유 — 원고를 여러 크기의 카드로 나누기
긴 업무 규정을 카드에 나누어 적는다고 생각합니다. 문자 청킹은 카드 한 장에 글자를 일정 수만큼 적고 다음 카드로 넘어갑니다. 재귀 청킹은 먼저 문단을 통째로 넣어 보고, 카드에 들어가지 않으면 문장과 띄어쓰기 순서로 더 잘게 나눕니다. 토큰 청킹은 글자 수 대신 모델이 세는 조각 수를 카드의 한도로 씁니다. 세 방법 모두 카드를 만들지만 경계를 고르는 기준이 다릅니다.
정의
문자 청킹 (character chunking)
하나의 구분자로 텍스트를 나누고, 문자 길이를 계산하며 조각을 합치는 방식입니다. chunk_size는 목표 크기이며 구분자보다 긴 조각이 있으면 결과가 이 값을 넘을 수 있으므로 실제 길이를 확인해야 합니다.
재귀 청킹 (recursive chunking)
문단 구분, 줄바꿈, 문장 부호, 띄어쓰기처럼 큰 경계부터 차례로 시도하고, 조각이 너무 길 때만 더 작은 경계로 내려가는 방식입니다. 경계 후보의 우선순위가 결과를 좌우합니다.
토큰 청킹 (token chunking)
특정 토크나이저가 계산한 토큰 수를 기준으로 청크 한도를 맞추는 방식입니다. 모델 입력 한도와 비용을 직접 관리하기 좋지만, 토크나이저가 바뀌면 같은 텍스트의 경계도 달라질 수 있습니다.
구분자 우선순위 (separator priority)
재귀 청킹에서 어느 경계를 먼저 보존할지 정한 순서입니다. 일반적으로 문단, 줄, 문장, 띄어쓰기, 문자 순으로 내려가지만 한국어 문서의 목록·표·조문 형식에 맞게 조정해야 합니다.
세 방식에서 경계가 결정되는 순서
같은 입력이라도 문자 수, 구분자 우선순위, 토큰 수 가운데 무엇을 기준으로 삼는지에 따라 청크 경계와 개수가 달라집니다.
오버랩 설정값은 실제 중복 길이의 최댓값입니다
chunk_overlap=50을 지정하면 인접한 모든 청크가 정확히 50자를 공유한다고 해석하기 쉽습니다. 재귀 청킹에서는 그렇지 않습니다. 스플리터가 문단이나 문장 같은 큰 단위를 결합해 청크를 만들 때, 이전 조각 가운데 설정 한도 안에 들어오는 부분만 다음 청크에 남깁니다. 앞선 분할 조각의 크기가 이미 오버랩 한도를 넘거나 결합 조건과 맞지 않으면 실제 중복은 50자보다 작거나 0자가 될 수 있습니다. 따라서 설정값은 중복 길이의 최댓값으로 읽고, 실제 인접 청크의 접두부와 접미부를 비교해 확인해야 합니다.
오버랩을 크게 만들면 경계 근처의 문맥이 보존될 가능성이 커집니다. 동시에 같은 문장이 여러 번 임베딩되고 검색 결과에도 중복 청크가 들어올 수 있습니다. 비용과 검색 다양성에 영향을 주므로 오버랩 비율도 실험 설정에 기록합니다.
한 단계씩 결과를 확인합니다
노트북은 CharacterTextSplitter, RecursiveCharacterTextSplitter, 토큰 길이를 사용하는 재귀 스플리터를 차례로 생성합니다. 각 단계에서 split_text()를 호출한 직후 청크 본문과 길이를 출력합니다. 재귀 방식에서는 다른 조건을 유지하고 chunk_size만 35에서 50으로 바꾸어 청크 수와 본문의 변화를 확인합니다.
스플리터 객체와 실제 분할 시점
CharacterTextSplitter(...) 같은 생성자는 분할 규칙을 담은 객체를 만들 뿐 아직 원문을 나누지 않습니다. split_text(text)를 호출할 때 문자열을 입력받아 청크 문자열 목록을 반환합니다. chunk_size는 목표 길이이고, 선택한 구분자로 더 나눌 수 없는 긴 조각은 이를 넘을 수 있으므로 실제 출력 길이를 확인해야 합니다.
문자 스플리터는 한 종류의 경계만 사용합니다. 재귀 스플리터는 단락·줄·공백·문자처럼 큰 경계부터 차례로 시도하고, 토큰 스플리터는 모델 토크나이저가 센 단위를 기준으로 나눕니다. 배송 안내처럼 문단 구조가 분명하면 재귀 방식이 읽기 좋은 경계를 보존할 수 있고, 입력 한도를 엄격히 관리해야 하면 토큰 수를 별도로 확인해야 합니다. 같은 숫자의 chunk_size라도 문자와 토큰은 같은 길이가 아닙니다.
5실행 예제
다음 노트북은 배송·환불 규정 하나를 세 가지 방식으로 나눕니다. 먼저 문자 스플리터의 결과를 확인하고, 재귀 스플리터를 실행한 뒤 chunk_size 하나만 바꿉니다. 마지막에는 같은 원문을 토큰 기준으로 나누고 각 청크의 토큰 수를 출력합니다. 준비 셀부터 순서대로 실행하면 앞에서 만든 변수를 다음 셀이 그대로 사용합니다.
6일부러 실패해 보기
“배송 시작 시점과 제주 추가 기간”에 답하려면 결제 시점과 제주 배송 근거가 함께 필요합니다. Before 셀은 35자 설정에서 두 근거가 서로 다른 청크에 놓인 결과를 확인합니다. After 셀은 같은 재귀 방식과 5자 오버랩을 유지하면서 목표 크기를 50자로 늘려 두 배송 문장이 한 청크에 들어오는지 검증합니다.
7주의할 점과 실무 메모
유니코드 경계. 파이썬의 문자열 길이, 화면에 보이는 글자 수, 토크나이저의 토큰 수는 서로 다를 수 있습니다. 결합 문자, 이모지, 특수 공백이 섞인 입력은 특히 별도 사례로 검사합니다.
토크나이저 고정. 토큰 청킹에 사용한 토크나이저 이름과 버전을 설정에 남깁니다. 임베딩 모델과 생성 모델이 서로 다른 토크나이저를 쓸 수 있으므로 어느 모델의 한도를 관리하는지도 명시합니다.
큰 청크의 장단점. 청크를 크게 만들면 한 조각에 더 많은 문맥을 담을 수 있습니다. 동시에 관련 없는 내용이 함께 검색되거나 입력 토큰이 늘어날 수 있으므로, 큰 청크가 모든 종류의 문서와 질문에서 더 정확하다고 가정하지 않습니다. 문서 구조, 질문 길이, 검색 k, 비용을 함께 측정해야 합니다.
메타데이터 유지. 청크를 만들 때 doc_id, 쪽, 원래 요소 유형을 복사합니다. 문자열 목록만 반환하면 검색 결과가 어느 파일과 위치에서 왔는지 추적할 수 없습니다.
8정리와 다음 절
문자 청킹은 문자 수, 재귀 청킹은 구분자 우선순위, 토큰 청킹은 토크나이저가 계산한 수를 기준으로 경계를 정합니다.
재귀 청킹의 오버랩은 실제 중복을 항상 보장하지 않는 최댓값이므로 결과 청크에서 측정해야 합니다.
큰 청크와 작은 청크는 실제로 사용할 문서와 질문으로 검색 결과와 비용을 측정해 비교합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 Markdown 제목을 메타데이터로 보존하고, 문장 사이의 의미 변화로 경계를 정하는 방법을 실행합니다. 08절에서는 먼저 하나의 청킹·임베딩 조합을 끝까지 실행한 뒤 청킹과 모델을 한 번에 하나씩 바꿉니다.
9복습 문제
문제 4개 · 해설 포함
1. 문자 청킹과 토큰 청킹의 기준 차이를 한 문장으로 설명하세요.
문자 청킹은 파이썬 문자열의 문자 수를 기준으로 하고, 토큰 청킹은 지정한 토크나이저가 만든 토큰 수를 기준으로 합니다.
2. 재귀 청킹에서 chunk_overlap=50인데 실제 중복이 50자보다 작았습니다. 구현 오류라고 단정할 수 있습니까?
단정할 수 없습니다. 재귀 스플리터는 분할된 단위를 결합하며 이전 단위 가운데 한도 안에 들어오는 부분만 유지합니다. 설정값은 최댓값이고 실제 중복은 경계와 분할 단위에 따라 작아질 수 있으므로 청크를 직접 비교해야 합니다.
3. 한국어 500자와 영어 500자가 같은 토큰 수라고 가정하면 안 되는 이유는 무엇입니까?
토크나이저는 문자를 그대로 하나씩 세지 않고 학습된 어휘 단위로 나눕니다. 언어, 숫자, 특수문자, 이모지 구성에 따라 한 문자에 대응하는 토큰 수가 달라집니다.
4. 긴 컨텍스트 모델을 사용하므로 청크 크기를 두 배로 늘리자는 제안을 검토할 때 함께 기록해야 할 항목을 세 가지 이상 쓰세요.
청크 수와 길이별 개수(예: 100자 이하가 몇 개인지), 질문당 검색되는 총 토큰, 임베딩 시간과 비용, 정답 근거가 검색 범위에 포함되는지, 중복 청크 비율을 기록합니다. Ch 11 전에는 품질 지표가 비어 있으므로 비용이 낮거나 청크 수가 적다는 이유만으로 승자를 정하지 않습니다.

반대로 제목이 없거나 작성 형식이 일정하지 않은 문서도 있습니다. 회의록 한 문단 안에서 예산 이야기에서 일정 이야기로 주제가 바뀔 수 있습니다. 구조 방식은 작성자가 넣은 제목 표시(#, ##)가 바뀌는 위치에서 나눕니다. 시맨틱 방식은 이 표시 대신 인접한 문장 임베딩 사이의 거리가 큰 위치에서 나눕니다. 입력 문서에 믿을 만한 제목 표시가 있는지 확인한 뒤 방법을 고릅니다.

4핵심 개념
비유 — 목차를 따를지, 대화 주제의 변화를 들을지
잘 편집된 보고서는 목차와 소제목이 방의 문패처럼 붙어 있습니다. 문패가 바뀔 때 새 청크를 시작하면 작성자가 의도한 구역을 따를 수 있습니다. 형식이 없는 회의 대화에는 문패가 없습니다. 이때는 인접한 발언의 내용이 얼마나 달라졌는지를 보고 주제가 바뀐 지점을 찾습니다. 구조 기반 청킹은 문패를 읽고, 시맨틱 청킹은 내용의 변화를 비교합니다.
정의
구조 기반 청킹 (structure-aware chunking)
제목·문단·목록·표·쪽을 보고 문서를 나누고, 각 조각이 어디에 속하는지 함께 남기는 방식입니다. 예를 들어 “배송” 제목 아래의 문단을 함께 묶고 제목도 저장합니다.
시맨틱 청킹 (semantic chunking)
문장이나 문장 묶음의 임베딩을 비교해 의미 변화가 큰 지점에서 청크를 나누는 방식입니다. 어떤 임베딩 모델을 쓰는지, 거리가 얼마나 커야 나눌지에 따라 결과가 달라집니다.
의미 경계 (semantic boundary)
앞뒤 텍스트의 주제가 충분히 달라졌다고 판단해 새 청크를 시작하는 위치입니다. 정답으로 주어진 경계가 아니라 계산 기준으로 선택한 후보입니다.
중단점 (breakpoint)
문장 묶음 사이의 의미 거리가 기준보다 커서 새 청크를 시작하는 위치입니다. 백분위수(percentile)는 값을 작은 순서로 정렬했을 때 일정 비율이 그 값보다 작거나 같은 위치를 나타냅니다. 예를 들어 95번째 백분위수는 거리값의 95%가 그 기준값보다 작거나 같은 지점입니다. 문장이 적거나 같은 거리값이 많으면 예상한 청크 수와 다를 수 있으므로 실제 거리와 결과 본문을 함께 봅니다.
제목 경계 (header boundary)
Markdown의 #처럼 제목임을 명시한 위치입니다. 제목을 청크 본문 앞에 남기면 뒤따르는 문단이 어느 주제에 속하는지 확인할 수 있습니다.
두 방식은 어디에서 문서를 나눌까요?
구조 기반 방식은 제목·문단·표 표시를 보고 나눕니다. 시맨틱 방식은 이웃한 문장 묶음의 임베딩 거리를 계산해, 거리가 큰 곳에서 나눕니다.
MarkdownHeaderTextSplitter로 제목 계층을 보존합니다
노트북은 #을 section, ##를 topic이라는 메타데이터 이름에 연결합니다. split_text()가 반환한 각 Document에서 metadata와 page_content를 함께 출력하면 제목 계층과 본문의 대응을 확인할 수 있습니다.
이 실습은 Markdown 제목 표시가 있는 텍스트를 입력으로 사용합니다. PDF의 글꼴 크기나 화면 배치를 분석해 제목을 찾는 기능은 포함하지 않습니다. PDF에서 제목 구조를 사용하려면 파싱 단계에서 제목을 찾아 Markdown 표시나 별도 메타데이터로 보존해야 합니다.
SemanticChunker를 기본 설정부터 실행합니다
SemanticChunker는 문장 묶음의 임베딩 거리를 계산하고 큰 변화가 나타난 위치를 경계로 선택합니다. 기본값 95는 계산된 거리의 약 상위 5%에 해당하는 큰 변화를 경계 후보로 고르는 뜻입니다. 노트북은 먼저 기본값을 실행한 뒤, 원문과 임베딩 모델을 유지하고 breakpoint_threshold_amount만 50으로 낮춥니다. 50으로 낮추면 중앙값보다 큰 거리도 후보가 되어 경계가 늘 수 있으므로 청크 수와 본문을 함께 비교합니다.
이 예제의 기본 문장 분리 정규식은 .?! 뒤에 공백이 있는 위치를 사용합니다. 모든 한국어 문서의 문장 경계를 처리하는 범용 분리기는 아닙니다. 목록, 조문, 표 셀, 줄바꿈 중심의 문서에서는 별도의 문장 분리 규칙을 검토해야 합니다.
원리 더 알아보기: 거리값을 정렬해 경계를 고르는 백분위수
시맨틱 스플리터는 인접한 문장 묶음 사이의 거리를 계산합니다. 95번째 백분위수 기준값은 거리값의 95%가 그 값보다 작거나 같게 되는 지점입니다. 따라서 그보다 큰 약 상위 5%의 거리만 경계 후보가 됩니다. 50번째 백분위수 기준값은 중앙값이므로 그보다 큰 거리도 후보가 됩니다. 표본이 작거나 같은 값이 반복되면 정확히 5%나 50%의 경계가 생긴다는 뜻은 아닙니다. 거리 계산을 직접 구현하는 코드는 기본 실습에서 제외합니다. 먼저 라이브러리의 입력, 설정, 반환값을 확인한 뒤 필요할 때 공식 구현을 읽습니다.
구조 경계와 의미 변화 경계
MarkdownHeaderTextSplitter(headers_to_split_on=...)는 제목 기호와 메타데이터 이름의 규칙을 만들고, split_text(markdown_text)를 호출할 때 제목 계층을 읽어 Document 목록을 반환합니다. 제목 문자열은 본문에서 빠질 수 있어도 섹션과 주제 값은 메타데이터에 남습니다.
SemanticChunker(embeddings, breakpoint_threshold_amount=...)는 문장 임베딩 사이의 변화량을 계산하므로 split_text() 호출 때 임베딩 API가 실행됩니다. 백분위수 기준을 높이면 관찰된 변화 중 더 큰 값만 경계가 되는 경향이 있지만, 결과 청크 수는 원문의 문장 분포에 달려 있습니다. 제목이 신뢰할 만한 매뉴얼은 구조 청킹이 설명 가능하고, 제목 없이 화제가 바뀌는 인터뷰 기록은 의미 경계가 후보가 될 수 있습니다.
5실행 예제
다음 노트북은 먼저 MarkdownHeaderTextSplitter를 만들고 제목 메타데이터와 본문을 확인합니다. 이어서 같은 한국어 원문에 SemanticChunker의 기본 95번째 백분위수와 50번째 백분위수를 차례로 적용합니다. 준비 셀부터 순서대로 실행하면 구조 결과, 기본 시맨틱 결과, 설정 변경 결과를 단계별로 볼 수 있습니다.
6실험 결과 해석
95번째, 50번째, 0번째 백분위수에서 청크 수가 어떻게 달라지는지 비교합니다. 기준값이 낮아질수록 이 예제에서는 경계 후보가 늘지만, 청크가 많거나 적다는 사실만으로 더 좋은 설정이라고 판단하지 않습니다. 실제 질문 여러 개로 검색 결과를 측정해야 선택할 수 있습니다.
7주의할 점과 실무 메모
파일을 읽을 때 제목과 본문을 구분해야 합니다. PDF에서 제목과 본문을 구분하지 못했다면 구조 기반 청킹도 그 차이를 알 수 없습니다. 02절의 PDF 파서 비교 결과와 함께 판단합니다.
임베딩 모델이 바뀌면 나누는 위치도 달라집니다. 임베딩 모델이 바뀌면 거리값의 크기와 경계로 선택되는 위치가 바뀝니다. 모델 이름, 버전, 기준값을 캐시 키와 실험 설정에 포함합니다.
한국어 문장 분리. 마침표만으로 나누면 목록, 조문, 괄호, 표 셀을 잘못 처리할 수 있습니다. 문장 분리기의 이름과 규칙을 기록하고 원문 위치를 유지합니다.
실험용 패키지의 상태. SemanticChunker가 포함된 langchain-experimental==0.4.2는 보관된 패키지입니다. 이 절은 고정된 버전의 기능을 학습하는 예제이며, 새 서비스의 장기 지원 선택을 권장하는 근거로 사용하지 않습니다.
8정리와 다음 절
MarkdownHeaderTextSplitter는 Markdown 제목 계층을 각 문서의 메타데이터로 보존합니다.
SemanticChunker는 문장 묶음의 임베딩 거리와 백분위수 임계값으로 경계 후보를 정합니다.
구조 방식은 제목 표시가 있는 입력이 필요하고, 시맨틱 방식은 임베딩 모델과 거리 기준이 필요하므로, 청크 수만으로 우열을 판단할 수 없습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 문장 하나의 임베딩 벡터부터 관찰하고, 여러 문장의 벡터를 만든 뒤 LangChain의 캐시를 적용합니다. 08절에서는 하나의 청킹·임베딩 조합을 끝까지 실행하고 조건을 한 번에 하나씩 바꿉니다.
9복습 문제
문제 4개 · 해설 포함
1. 구조 기반 청킹이 사용해야 하는 입력 정보 두 가지를 쓰세요.
#과 ## 같은 제목 표시와 각 제목에 대응하는 본문이 필요합니다. 스플리터는 제목 텍스트와 수준을 Document.metadata에 저장합니다.
2. 시맨틱 청킹의 중단점은 무엇을 뜻합니까?
새 청크를 시작하는 위치입니다. 앞뒤 문장 묶음의 임베딩 거리를 계산하고, 그 거리가 정해 둔 기준보다 크면 이 위치에서 나눕니다. 사람이 정답으로 표시해 둔 위치와 반드시 일치하지는 않습니다.
3. 제목 글꼴만 큰 PDF를 평문으로 파싱한 뒤 구조 기반 청킹을 실행했습니다. 제목이 시작되는 위치를 찾기 어려운 원인과 개선 순서를 설명하세요.
평문 파서가 글꼴과 제목 유형을 버렸으므로 청킹 함수가 사용할 구조 정보가 없습니다. 먼저 레이아웃이나 제목을 보존하는 파서를 선택하고, 제목을 Markdown 표시나 별도 필드로 변환한 뒤 제목 표시를 읽을 수 있는 청킹 방식을 사용해야 합니다.
4. 시맨틱 방식이 구조 방식보다 청크 수가 적게 나왔습니다. 이 결과만으로 시맨틱 방식이 우수하다고 할 수 없는 이유는 무엇입니까?
청크 수는 저장 규모의 관찰값일 뿐 검색 품질을 나타내지 않습니다. 제목·표 구조 보존 여부, 정답 근거의 포함 여부, 임베딩 호출 시간과 비용을 함께 기록하고 Ch 11의 검색 지표로 비교해야 합니다.

임베딩 모델을 바꾸면 모든 벡터의 좌표계가 달라집니다. 같은 모델이라도 차원, 정확한 모델 버전, 문서·질문 앞에 붙이는 구분 문구가 바뀌면 이전 벡터를 그대로 사용할 수 없습니다. 반면 스플리터 설정이 바뀌어도 결과 청크 가운데 텍스트가 정확히 같은 항목은 같은 모델 설정에서 벡터를 재사용할 수 있습니다. 이 차이를 알면 인덱스는 다시 구성하되 불필요한 API 호출은 줄일 수 있습니다.
이 절에서 언급하는 모델은 비교 후보입니다. 이 과정의 최종 모델은 [[미정: 임베딩 모델]]이며, Ch 11에서 한국어 질의셋의 검색 지표를 계산하기 전에는 확정하지 않습니다. small·large라는 이름만으로 품질을 판단할 수 없습니다. 차원·비용·입력 길이가 다른 두 기능 예제로 사용합니다.

4핵심 개념
비유 — 같은 주소 체계와 보관함 표찰
서로 다른 도시의 지도 좌표를 한 표에 섞으면 거리를 비교할 수 없습니다. 청크는 A 모델로, 질문은 B 모델로 변환한 뒤 가까운 것을 찾는 일도 마찬가지입니다. 모델과 차원, 입력 규칙이 같아야 같은 주소 체계입니다. 한 번 계산한 좌표를 보관할 때는 어느 주소 체계로 만들었는지 표찰을 붙여야 합니다. 캐시 키가 그 표찰입니다.
정의
다국어 임베딩 (multilingual embedding)
여러 언어의 텍스트를 검색·분류 같은 작업에 사용할 수 있도록 벡터로 표현하는 모델입니다. 지원 언어 목록은 후보 조건이며 특정 한국어 업무 문서에서 높은 검색 품질을 보장하지 않습니다.
차원 (dimension)
임베딩 벡터에 들어 있는 숫자의 개수입니다. 차원이 커지면 저장 공간과 거리 계산량이 늘어날 수 있으며, 차원 수만으로 품질을 판단할 수 없습니다.
모델 버전 (model revision)
같은 모델 이름 아래에서 사용한 정확한 코드·가중치 버전입니다. 로컬 오픈 모델은 커밋 SHA를 기록하고, API 모델은 공급자가 제공하는 고정 버전 식별자를 사용할 수 있는지 확인합니다.
입력 접두사 (input prefix)
모델 카드가 문서와 질의를 구분하기 위해 요구하는 앞부분입니다. 예를 들어 문서에는 passage: , 질의에는 query: 를 붙이는 모델이 있으며 생략하면 모델 카드가 설명한 검색 방식과 달라집니다.
벡터 캐시 (vector cache)
같은 입력 문자열과 같은 임베딩 설정으로 계산한 벡터를 다시 사용하기 위한 저장소입니다. 이 노트북은 입력 문자열의 공백이나 줄바꿈을 자동으로 정리하지 않습니다. 전처리 방법을 추가한다면 그 이름과 버전도 캐시 키에 반영해야 다른 입력의 벡터가 섞이지 않습니다.
인덱스 구성 기록표 (index manifest)
원문, 파서, 청킹 설정, 청크 ID와 벡터 캐시 키의 대응을 기록한 목록입니다. 인덱스를 어떻게 구성했는지 재현하고 변경 범위를 판단하는 근거가 됩니다.
원리 더 알아보기 — 모델 후보와 평가 기준
모델 후보를 읽는 순서
첫째, 문서와 질문의 언어가 지원 범위에 있는지 봅니다. 둘째, 최대 입력 길이가 현재 청크의 토큰 길이를 수용하는지 확인합니다. 셋째, 문서와 질의에 서로 다른 접두사나 프롬프트가 필요한지 모델 카드를 읽습니다. 넷째, 차원과 실행 위치, 라이선스, API 단가를 기록합니다. 마지막으로 한국어 질의셋에서 검색 결과를 측정합니다. 앞의 네 조건은 실행 가능한 후보를 고르는 기준이고, 마지막 측정은 실제로 사용할 한국어 문서와 질문에 맞는 후보를 판단하는 기준입니다.
OpenAI의 text-embedding-3-small과 text-embedding-3-large는 기본 차원이 각각 1,536과 3,072이며 dimensions 옵션으로 축소할 수 있습니다. 2026-09-08 확인 단가는 100만 토큰당 각각 미화 0.02달러와 0.13달러입니다. 이 값은 비용 예측에 쓰며 한국어 순위를 뜻하지 않습니다. 공급자가 제공하는 영문 또는 다국어 벤치 결과도 후보 선정 자료일 뿐, 우리 문서의 정답률이 아닙니다.
로컬 오픈 모델 후보로는 intfloat/multilingual-e5-large와 BAAI/bge-m3를 조사했습니다. 두 모델 카드 모두 다국어 지원과 1,024차원을 명시합니다. E5는 검색 입력에 passage: 와 query:  접두사를 요구하고 최대 길이가 512개의 토큰입니다. BGE-M3는 한 텍스트를 표현하는 방법을 여러 가지 제공합니다. 이 장의 후속 비교에서는 텍스트 하나를 숫자 목록 하나로 바꾸는 dense 벡터만 사용합니다. 최대 입력 길이는 8,192개의 토큰입니다. 이 두 모델도 최종 선택이 아니라 공개된 모델 카드와 사용한 정확한 모델 버전을 기록할 수 있는 후속 비교 후보입니다.
영어 시험 점수가 한국어 업무 문서의 검색 결과를 보장하지 않는 이유
MTEB는 모델·과제·언어별 평가를 모으는 평가 모음입니다. 종합 점수 한 줄에는 여러 언어와 분류·검색·군집화 같은 서로 다른 과제가 섞일 수 있습니다. 영어 검색 과제에서 높은 모델이 한국어 사내 규정의 조사·고유명사·표현 변형에서도 같은 순위를 유지한다는 보장은 없습니다. 리더보드를 사용할 때는 Korean retrieval 과제를 별도로 보고, 최종 결정은 이 과정의 한국어 질문과 정답 문서로 측정합니다.
벡터 저장 이름과 인덱스 구성 기록표를 따로 관리합니다
이 도식은 캐시에 저장할 때 구분해야 할 입력과 설정을 보여줍니다. 실습에서는 모델 이름과 차원을 namespace에 넣습니다. 라이브러리가 이 설정을 자동으로 구분해 주는 것은 아니므로, 차원을 바꿀 때 이름을 그대로 쓰면 이전 벡터가 반환됩니다. 전처리를 추가한다면 그 방법과 버전도 구분해야 합니다.
기본 실습은 CacheBackedEmbeddings에 임베딩 모델과 LocalFileStore를 전달합니다. namespace는 저장 항목을 구분하는 이름이며, 이 예제에서는 모델 이름과 256차원 설정을 포함합니다. 라이브러리는 입력 텍스트로 키를 만들고 지정한 저장소에서 벡터를 찾습니다. 모델이나 차원을 바꾸면 이름도 바꿔 이전 설정의 벡터와 섞이지 않게 합니다. 전처리나 접두사를 추가하는 확장에서는 그 조건도 구분해야 합니다.
인덱스 구성 기록표에는 원문 해시, 사용한 파서와 공백·줄바꿈·문자 표기를 정리한 방법의 버전, 청킹 방식과 크기·오버랩, 청크 ID, 각 청크가 참조하는 벡터 캐시 키를 적습니다. 청킹 설정이 바뀌면 청크의 순서와 ID 대응이 달라지므로 인덱스는 다시 구성합니다. 그러나 새 인덱스를 구성한다는 말이 모든 벡터 API를 다시 호출한다는 뜻은 아닙니다. 새로 생기거나 텍스트가 바뀐 청크만 캐시 미스로 계산합니다.
같은 문서를 두 번 요청하기
처음에는 비어 있는 임시 폴더를 사용합니다. 문장 목록을 첫 번째로 요청하면 문서 벡터가 저장됩니다. 두 번째로 같은 목록을 요청한 뒤 파일 수와 벡터를 비교합니다. 파일 수가 유지되고 벡터가 같다는 출력만으로 외부 호출 횟수를 직접 측정했다고 표현하지 않습니다. 아래 차원 실습에서는 같은 캐시 이름이 실제로 오래된 벡터를 반환하는 현상을 따로 확인합니다.
임베딩 호출과 캐시 조회 순서
embed_documents([문장, ...])는 문자열 목록을 입력받아 같은 순서의 벡터 목록을 반환합니다. 대괄호의 [0]은 첫 문장의 벡터를 고르는 표기입니다. CacheBackedEmbeddings.from_bytes_store(embeddings, store, namespace=...)는 원래 임베딩 객체 앞에 캐시 조회 단계를 덧붙인 새 객체를 반환합니다.
첫 요청은 입력 텍스트와 네임스페이스로 키를 만들고, 값이 없으면 원래 임베딩을 호출한 뒤 벡터를 저장합니다. 같은 키의 다음 요청은 파일에서 벡터를 읽습니다. 파일 수가 늘지 않았다는 관찰만으로 외부 호출이 0회였다고 단정할 수는 없으며, 호출 횟수는 별도 계측이 필요합니다. 모델이나 차원이 바뀌면 같은 문장도 호환되지 않으므로 네임스페이스를 분리해야 합니다.
5실행 예제
먼저 문장 하나를 임베딩하고 앞의 다섯 값과 벡터 길이를 확인합니다. 다음에는 문장 목록의 개수와 반환된 벡터 개수를 비교합니다. 같은 문장과 모델에서 차원만 256에서 128로 바꾸어 반환 벡터의 길이도 확인합니다. 마지막으로 같은 문서를 두 번 요청해 캐시 파일 수와 반환값을 관찰합니다. 임시 폴더는 이번 실행을 위한 것이므로 다시 시작하면 새 캐시로 비교합니다.
확인할 점 — 문장 목록을 기본 설정으로 변환하면 문장 수와 벡터 수는 같고 각 벡터의 길이는 256입니다. 같은 입력을 두 번 요청하면 반환 벡터는 같고 캐시 파일 수는 유지됩니다. 이 두 출력은 외부 호출 횟수의 직접 측정값이 아닙니다.
6일부러 실패해 보기
Before 셀은 128차원 모델에 256차원 캐시와 같은 namespace를 잘못 연결해 오래된 256차원 벡터가 반환되는 문제를 확인합니다. After 셀은 차원을 구분하는 새 namespace를 사용해 128차원 벡터를 새로 계산하고 저장합니다.
7주의할 점과 실무 메모
최종 모델은 미정입니다. 이 절의 small·large API 후보와 두 오픈 모델은 비교 틀을 보여 줍니다. 한국어 검색 지표와 운영 조건을 확인하기 전에는 하나를 정본으로 선언하지 않습니다.
입력 규칙을 모델 카드에서 확인합니다. 문서와 질의 접두사, 최대 길이, 공백·줄바꿈·문자 표기를 정리하는 방법이 모델마다 다릅니다. 예를 들어 모델마다 요구하는 query:·passage: 표시가 다르면, 각 모델 설명서에 맞게 입력을 준비한 뒤 비교해야 합니다.
가격에는 확인일을 붙입니다. API 단가는 바뀔 수 있습니다. 로그에는 실제 입력 토큰 합계와 단가, 통화, 확인일을 함께 남깁니다.
캐시에 원문을 저장하는 문제. 캐시 파일에 벡터만 저장해도 키 생성 과정에서 원문 해시를 사용합니다. 민감 문서라면 캐시 경로의 접근 권한과 보존 기간을 별도로 정합니다.
8정리와 다음 절
임베딩 후보는 언어·입력 길이·차원·접두사·정확한 모델 버전·비용을 확인한 뒤 정답 문서가 표시된 한국어 질문 모음으로 측정합니다.
영어 또는 종합 벤치마크의 순위는 한국어 업무 문서 검색 순위를 보장하지 않습니다.
벡터 캐시 키와 인덱스 구성 기록표를 분리하면 인덱스를 다시 구성하면서도 정확히 같은 청크의 벡터를 재사용할 수 있습니다.
다음 학습과 이어지는 지점 — 다음 절은 한 설정으로 검색을 끝까지 실행한 뒤 청크 크기만, 그다음 임베딩 모델만 바꿉니다. 검색 결과를 관찰하는 연습을 마친 뒤 Ch 11에서 정답 질의셋과 품질 지표를 배웁니다.
9복습 문제
문제 4개 · 해설 포함
1. 문장 세 개를 256차원으로 임베딩하면 벡터 개수와 각 벡터의 길이는 얼마입니까?
벡터는 세 개이고 각각 256개의 숫자를 담습니다. 입력 문장 수와 벡터 길이는 서로 다른 값입니다.
2. 캐시를 비교할 때 빈 임시 폴더부터 사용하는 이유는 무엇입니까?
이전 실습의 저장 파일이 남아 있으면 첫 요청부터 기존 벡터를 사용할 수 있습니다. 비어 있는 상태로 시작해야 저장 전후의 변화를 관찰할 수 있습니다.
3. 모델 이름은 같지만 차원을 바꿨습니다. namespace도 바꾸어야 하는 이유는 무엇입니까?
서로 다른 차원으로 만든 벡터를 구분하기 위해서입니다. 같은 입력이어도 차원 설정이 다르면 이전 벡터를 그대로 사용하면 안 됩니다.
4. 영어 벤치마크 순위가 높은 모델을 한국어 업무 문서에도 바로 선택할 수 있습니까?
언어와 문서, 질문의 표현과 길이, 자주 묻는 내용이 다르므로 바로 선택할 수 없습니다. 해당 한국어 질문과 정답 문서로 검색 품질을 측정해야 합니다.

1학습 목표
이 절을 마치면 재귀·토큰·구조 기반 청킹으로 같은 원문을 세 가지 방식으로 나눌 수 있습니다.
이 절을 마치면 세 가지 청킹과 두 임베딩 모델의 6개 조합에서 실제 색인과 검색을 실행할 수 있습니다.
이 절을 마치면 각 조합의 청크 수·검색 결과 1위 청크의 ID·점수·본문을 같은 형식으로 기록할 수 있습니다.
이 절을 마치면 기본 제공 자료와 실제 업무 문서 100건·상용 파서 선택 실습의 범위를 구분할 수 있습니다.
2이 내용을 배우는 이유
앞 절에서는 문서를 읽고 나누는 방법과 임베딩을 배웠습니다. 이번 절에서는 그 과정을 3가지 청킹 × 2가지 임베딩 모델의 실험으로 연결합니다. 짧은 배송·환불 원문과 질문 하나를 고정하고, 여섯 조합에서 실제 벡터 색인과 검색을 실행합니다.
여섯 결과가 나와도 바로 최종 설정을 고르지는 않습니다. 이번 기본 실습은 실행 구조와 청크 경계를 확인하는 작은 실험입니다. 수강생의 실제 업무 문서 100건, 정답 질문, 상용 파서 자격증명이 준비되어야 해당 업무 분야의 검색 품질과 파서 차이를 비교할 수 있습니다.

4핵심 개념
비유 — 같은 재료로 조리 조건 바꾸기
같은 재료를 사용하면서 온도만 바꾸면 온도에 따른 차이를 관찰할 수 있습니다. 재료와 시간까지 한꺼번에 바꾸면 무엇이 결과에 영향을 주었는지 구분하기 어렵습니다. 검색 실험도 원문과 질문을 고정하고 한 조건씩 바꿉니다.
정의
실험 격자 (experiment grid)여러 조건의 모든 조합을 빠짐없이 실행하는 표입니다. 이 절은 청킹 3종과 임베딩 모델 2종을 곱해 6개 조합을 만듭니다.
같게 유지할 조건 (controlled condition)조합 사이의 차이를 읽기 위해 바꾸지 않는 값입니다. 이번 실습에서는 원문·질문·검색 결과 수·임베딩 벡터 차원을 유지합니다.
실험 기록 (experiment record)어떤 설정에서 어떤 결과를 관찰했는지 함께 남긴 자료입니다. 이번 실습은 여섯 딕셔너리의 필드 이름을 같게 맞춥니다.
결과를 확인한 자료 범위 (evaluation scope)결론을 내릴 때 실제로 사용한 문서와 질문의 수입니다. 이 절은 짧은 원문 하나와 질문 하나만 사용하므로 전체 검색 품질을 판단할 수 없습니다.
여섯 조합을 모두 실행합니다
청킹 방법text-embedding-3-smalltext-embedding-3-large이번 설정
재귀실행실행45자, 오버랩 8자
토큰실행실행25토큰, 오버랩 4토큰
구조 기반실행실행마크다운 1·2단계 제목
모든 실행에서 원문, 질문, 검색 결과 수 k=2, 벡터 길이 256을 유지합니다. 청킹 방법을 비교할 때는 같은 모델의 세 행을 보고, 임베딩 모델을 비교할 때는 같은 청킹 방법의 두 열을 봅니다. 두 모델의 기본 벡터 차원은 다르지만 이번에는 저장 크기 조건을 맞추기 위해 256차원으로 사용합니다.
숫자와 본문을 함께 읽습니다
InMemoryVectorStore에 문서를 추가하면 임베딩 모델이 문서를 벡터로 바꿉니다. similarity_search_with_score()는 질문으로 검색한 문서와 점수를 함께 반환합니다. 점수만 비교하지 말고, 본문에 제주 배송과 추가 기간을 설명하는 내용이 있는지 확인합니다.
출력의 청크 ID는 이번 실행에서 청크를 구분하는 이름입니다. recursive:02와 token:02의 끝 번호가 같아도 같은 원문 범위를 뜻하지 않습니다. 청킹 방법이 바뀌면 경계도 바뀌므로 본문을 함께 읽어야 합니다. 서로 다른 임베딩 모델의 점수 크기만으로 우열을 판단하지 않습니다.
원리 더 알아보기 — 비교할 두 실행 고르기
같은 원문과 질문을 둔 채, 먼저 청크 크기만 바꾼 뒤 같은 크기의 청크에서 모델만 바꾸어 비교합니다.
한 청킹 방법의 small·large 두 결과를 비교하면 청크 본문은 같고 모델만 다릅니다. 한 모델의 재귀·토큰·구조 기반 결과를 비교하면 모델은 같지만 청크의 크기 단위와 경계 규칙이 다릅니다. 숫자 하나의 효과를 측정하는 실험과 달리, 여기서는 세 전략의 실제 산출물을 함께 읽습니다.
기본 실습의 첫 부분은 짧은 원문 하나와 질문 하나로 실행 구조와 청크 경계를 확인합니다. 그 결과는 교육용 원문에만 해당하므로 Ch 11 평가 입력으로 직접 사용하지 않습니다. 이어지는 연결 실습은 Ch 11과 같은 18개 디지털 PDF와 Q001을 사용해 6개 설정의 검색 결과를 같은 JSONL 필드로 기록합니다.
여섯 조합을 공정하게 비교하기
이 실험의 독립 변수는 청킹 방법 세 가지와 임베딩 모델 두 가지이고, 원문·질문·정답 문서·검색 개수는 고정합니다. 각 조합은 splitter(text)로 청크를 만든 뒤 같은 검색 함수에 전달하며, 반환된 순위와 정답 포함 여부를 같은 열에 기록합니다. 조합 하나의 실행이 끝날 때만 그 행의 관찰값이 완성됩니다.
청크 수가 적거나 실행 시간이 짧다는 이유만으로 검색 품질이 좋다고 결론 내릴 수 없습니다. 정답 청크가 상위에 왔는지와 경계가 필요한 문장을 보존했는지를 함께 읽어야 합니다. 짧은 교육용 원문 한 건에서 나온 순위는 방법 전체의 우열이 아니라 이후 문서 집합에서 검증할 가설입니다. Ch 11은 질문 수를 늘리고 지표를 고정해 이 비교를 반복할 수 있게 만듭니다.
5실행 예제
먼저 짧은 원문에서 재귀·토큰·구조 기반 청킹의 실제 청크를 출력합니다. 각 청크 집합에 두 임베딩 모델을 적용한 6개 결과로 청킹 경계를 관찰합니다. 다음에는 제공된 18개 디지털 PDF를 재귀·토큰·쪽 구조의 세 단위로 나누고 두 모델을 적용해 Ch 11의 Q001을 검색합니다. 이 6개 결과에는 설정과 함께 문서 ID·청크 ID·쪽·순위·점수를 기록합니다.
확인할 점 — 이번 실행의 청크 수는 재귀 7개, 토큰 10개, 구조 기반 3개입니다. 재귀 청킹과 구조 기반 청킹에서는 두 임베딩 모델 모두 제주와 이틀을 함께 담은 청크를 1위로 반환했습니다. 토큰 청킹의 두 모델은 두 단어가 나뉜 token:02를 1위로 반환했습니다. 이 결과는 질문 하나에서 관찰한 청크 경계이며 전체 품질 순위가 아닙니다.
6실험 결과 해석
짧은 원문에서 여섯 조합을 모두 실행했습니다. 재귀 청킹은 7개, 토큰 청킹은 10개, 구조 기반 청킹은 3개가 되었고, 토큰 청킹의 1위 청크에는 질문과 답의 단어가 함께 들어 있지 않았습니다. 이어서 실제 PDF 18개와 Q001로 6개 설정을 실행해 Ch 11이 읽을 JSONL을 만들었습니다. 두 실험은 문서와 질문이 다르므로 점수나 순위를 서로 직접 비교하지 않습니다. Q001 한 질문의 검색 지표도 전체 설정의 우열을 뜻하지 않습니다.
7주의할 점과 실무 메모
비교할 행과 열을 구분합니다. 같은 모델의 세 행은 청킹 방법 차이를, 같은 청킹 방법의 두 열은 임베딩 모델 차이를 보여 줍니다.
API는 실제로 호출됩니다. 문서를 저장하거나 질문으로 검색할 때 임베딩 비용이 발생합니다. 이 노트북은 공급자의 토큰 사용량이나 청구 비용을 출력하지 않습니다.
한 질문은 전체 평가를 대신하지 않습니다. 같은 1위 결과가 나왔다고 모델이 동등하다고 결론짓거나, 다른 결과가 나왔다고 한 모델이 우수하다고 결론짓지 않습니다.
제공 자료는 업무 문서 100건이 아닙니다. 배포 묶음에는 교육용 디지털 PDF 18건과 기존 문서의 스캔 변형 3건이 있습니다. 정답 정보를 포함한 집필용 전체 질의셋 149개는 학생 배포에서 제외합니다. PDF와 질문 수를 합치거나 파일을 복제해 100건으로 세지 않습니다.
상용 파서 비교는 선택 실습입니다. Upstage·LlamaParse 호출은 서비스 자격증명, 비용 확인, 문서 외부 전송 승인이 필요합니다. 기본 노트북은 상용 파서를 실행했다고 주장하지 않습니다.
8정리와 다음 절
재귀·토큰·구조 기반 청킹과 두 임베딩 모델의 여섯 조합을 실제로 실행했습니다.
각 조합의 청크 수·1위 청크 ID·점수·본문을 같은 필드로 기록했습니다.
교육용 제공 자료와 업무 문서 100건·상용 파서 선택 실습을 구분하고, 작은 표본의 단어 검사를 전체 품질 평가로 표현하지 않았습니다.
다음 학습과 이어지는 지점 — Ch 11은 continuity-ch10-indexing.jsonl의 6개 설정을 읽고 Q001의 정답 문서 ID와 검색 결과를 비교합니다. 개발용 질문 하나의 결과는 연결 동작을 확인하는 범위이며, 설정을 선택하려면 개발용 질문 전체로 확장해야 합니다. Ch 12에서는 같은 말뭉치·질문·평가 단위를 유지한 결과끼리 검색 설정을 반복 비교합니다.

문서와 메타데이터 준비
개념 문서 본문과 출처 정보는 함께 이동해야 합니다. 먼저 실행 위치와 실제 문서 경로를 확인한 뒤 파일명, 확장자, 쪽 번호를 메타데이터로 정리합니다.
경로 정보와 문서 메타데이터를 구분하기
Path는 파일 위치를 표현합니다. name·stem·suffix는 저장된 속성을 읽고, is_file()처럼 괄호가 있으면 검사를 실행합니다. Document(page_content=본문, metadata=사전)는 검색할 텍스트와 출처를 묶습니다.
메타데이터는 모델이 자동으로 읽는 본문이 아닙니다. 코드가 검색 필터와 출처 표시에 사용하므로, 개정판 문서라면 파일명 외에 문서 ID와 시행일도 별도 키로 저장합니다.
노트북 실행 위치 확인
이 노트북은 내려받은 실습 폴더 안의 어느 위치에서 실행해도 됩니다. Path.cwd()는 현재 실행 폴더를 나타내며, 아래 셀은 상위 폴더를 차례로 확인해 제공된 PDF를 찾습니다.
경로 객체의 값 관찰
name은 파일명 전체, stem은 확장자를 뺀 이름, suffix는 점을 포함한 확장자입니다. 속성은 객체가 가진 값을 읽는 이름입니다.
공통 메타데이터 만들기
딕셔너리는 이름표인 키와 값의 쌍을 저장합니다. 파일을 읽는 도구가 문자열로 제공한 쪽 번호는 정수로, 쉼표가 든 태그 문자열은 문자열 목록으로 바꿉니다.
값 하나를 바꾸어 비교
같은 문서에서 선택한 쪽만 2쪽에서 3쪽으로 바꿉니다. {**metadata, "page": 3}은 원본 딕셔너리를 수정하지 않고 새 딕셔너리를 만듭니다.
실패 확인
Before 원인 Python 목록의 두 번째 항목은 위치 1로 고릅니다. 이 위치값을 그대로 출처 쪽 번호에 쓰면 실제 2쪽을 1쪽이라고 표시합니다.
After 수정 0부터 센 위치에 1을 더해 사람이 보는 쪽 번호로 바꿉니다. 같은 두 번째 쪽이 출처에도 2쪽으로 기록되는지 확인합니다.

PDF 실습 준비
개념 디지털 PDF는 텍스트 층을 가질 수 있지만 읽기 순서와 표 구조는 별도로 확인해야 합니다. 스캔 PDF는 이미지이므로 텍스트 추출 결과가 비어 있을 수 있습니다.
텍스트 추출과 OCR의 경계
PdfReader(path)가 PDF 객체를 만들고 pages[n].extract_text()가 한 쪽의 문자열을 반환합니다. pdfplumber.open()은 글자 위치와 표 후보를 다루며 extract_table()은 행 목록을 반환합니다.
스캔 PDF에서 빈 문자열이 나와도 파일이 비었다는 뜻은 아닙니다. OCR은 페이지 이미지를 글자로 인식하는 별도 처리이며 이 노트북은 수행하지 않습니다.
실행 위치와 데이터 폴더 확인
프로젝트 루트의 labs/data/rag-corpus를 찾습니다. 일반 PDF와 스캔 PDF가 모두 있는지 확인한 다음 PDF 파일 구조를 읽어 텍스트와 표를 추출합니다. 이 절에는 API 키가 필요하지 않습니다.
PDF 객체 열기

기본 텍스트 관찰
목록 위치는 0부터 시작하므로 pages[1]은 두 번째 쪽입니다. extract_text()가 값을 반환하지 않으면 or ""로 빈 문자열을 사용합니다.
레이아웃과 표 결과 비교
pdfplumber로 같은 쪽을 읽습니다. 레이아웃 문자열과 표 목록은 서로 다른 반환값이므로 길이와 표 개수를 각각 확인합니다.
선택한 쪽을 바꾸어 비교

실패 확인

After 수정 텍스트 길이가 20자 미만인 쪽을 OCR 후보로 분류합니다. 이 코드는 OCR을 실행하거나 인식 성공을 주장하지 않습니다.

DOCX·HTML·CSV 실습 준비
개념 DOCX는 문단, HTML은 태그, CSV는 행과 열을 보존합니다. 형식별 객체를 먼저 만든 뒤 각 구조에서 필요한 값을 꺼냅니다.
형식별 구조를 먼저 읽기
docx.Document()는 문단 객체 목록, BeautifulSoup()는 태그 트리, csv.DictReader는 열 이름을 키로 가진 행 사전을 제공합니다. 호출마다 반환 구조가 다르므로 바로 한 문자열로 합치기 전에 보존할 관계를 정합니다.
상품 CSV는 행별 Document와 상품 ID가 적합하고, 기사 HTML은 메뉴를 제외한 main 본문이 적합합니다. 이름이 같은 docx.Document와 LangChain Document는 서로 다른 클래스입니다.
실행 위치와 제공 파일 확인
이 노트북은 Ch10의 fixtures 폴더에 있는 작은 DOCX·HTML·CSV 파일을 사용합니다. 세 파일을 찾지 못하면 내용을 읽기 전에 중단합니다. API 키는 필요하지 않습니다.
DOCX 객체와 문단 관찰
Document 객체의 paragraphs 속성은 문단 객체 목록입니다. 각 문단의 text 속성에서 실제 문자열을 읽습니다.
HTML 태그와 본문 관찰
BeautifulSoup 객체는 HTML 태그 구조를 탐색합니다. style처럼 화면 표시를 설정하는 태그를 제거한 뒤 제목과 문단 텍스트만 확인합니다.
CSV 행과 열 관찰
DictReader는 첫 줄을 열 이름으로 사용하고 이후 각 행을 딕셔너리로 반환합니다. 따라서 rows[0]["상품"]처럼 첫 행의 특정 열을 읽을 수 있습니다.
선택값 하나를 바꾸어 비교
같은 첫 번째 CSV 행에서 선택하는 열만 상품에서 보관으로 바꿉니다. 행 객체는 같지만 열 이름에 따라 반환되는 값이 달라집니다.
실패 확인
Before 원인 CSV 행에서 값만 꺼내면 상품과 보관이라는 열 이름이 사라집니다. 그러면 각 값이 무엇을 뜻하는지 이름으로 확인할 수 없습니다.

HWP와 HWPX 실습 준비
개념 HWPX는 ZIP 압축 폴더처럼 여러 XML 파일을 한 문서 파일 안에 담습니다. 이 실습은 제공된 최소 HWPX의 내부 XML을 확인하며, 레거시 HWP 본문 추출이나 한컴오피스 호환성을 검증하지 않습니다.
컨테이너와 본문 형식을 나누어 읽기
is_zipfile()은 ZIP 컨테이너인지 확인하고, ZipFile을 with로 열면 블록 뒤 파일이 닫힙니다. XML 바이트를 ElementTree.fromstring()에 넣으면 요소 트리가 반환됩니다.
ZIP을 열었다고 본문 순서·표·각주까지 복원된 것은 아닙니다. 레거시 HWP는 ZIP/XML이 아니므로 같은 코드로 읽을 수 없고, 최소 표식 파일의 성공은 실제 문서 전체 호환성을 보장하지 않습니다.
실행 위치와 제공 파일 확인
Ch10의 fixtures 폴더에서 HWPX 표식 파일과 레거시 HWP 표식 파일을 찾습니다. 두 파일은 내부가 ZIP인지 확인한 뒤 읽는 방법을 나누는 연습용이며 실제 업무 문서를 대신하지 않습니다.
ZIP 방식으로 묶인 내부 파일 관찰
is_zipfile()은 파일이 ZIP 구조인지 확인합니다. namelist()는 압축 안에 들어 있는 파일 이름 목록을 반환합니다.
본문 XML만 선택
전체 ZIP 항목에서 Contents/section으로 시작하고 .xml로 끝나는 항목만 고릅니다. 필터 조건을 바꾸면 선택 결과가 달라집니다.
XML 객체와 본문 값 관찰
ET.fromstring()은 XML 바이트를 요소 객체로 바꿉니다. 각 태그의 로컬 이름이 t인 요소만 골라 텍스트를 합칩니다.
선택 조건을 바꾸어 비교
같은 ZIP 목록에서 선택 조건만 바꿉니다. 모든 XML을 선택한 결과와 본문 section XML만 선택한 결과의 개수를 비교합니다.
실패 확인
Before 원인 레거시 HWP는 HWPX와 같은 ZIP 형식이 아닙니다. 확장자만 보고 ZIP으로 열면 BadZipFile이 발생합니다.
After 수정 파일 앞부분과 ZIP 구조를 먼저 확인합니다. 레거시 HWP 표식은 미지원으로 분류하고, HWPX만 ZIP/XML 경로에서 읽습니다.

labs/part3/ch10-document-processing/notebooks/05-문자-재귀-토큰-청킹.ipynb

문자, 재귀, 토큰 청킹
하나의 짧은 배송·환불 규정을 세 가지 방법으로 나눕니다. 텍스트를 조각으로 나누는 각 스플리터 객체를 만든 직후 결과 본문과 길이를 확인합니다.
스플리터 객체와 실제 분할 시점
스플리터 생성자는 규칙 객체만 만들고 split_text(text)를 호출할 때 문자열을 나누어 청크 목록을 반환합니다. chunk_size는 목표 길이이며 경계가 없으면 실제 청크가 이를 넘을 수 있습니다.
문자 방식은 한 경계, 재귀 방식은 큰 경계부터 여러 경계, 토큰 방식은 토크나이저 단위를 사용합니다. 같은 chunk_size 숫자라도 문자 수와 토큰 수는 같지 않습니다.
1단계: 문자 기준으로 나누기
CharacterTextSplitter는 지정한 구분자를 기준으로 조각을 만든 뒤, chunk_size를 목표 크기로 삼아 조각을 합칩니다. 구분자가 없는 긴 조각은 이 크기를 넘을 수 있으므로 실제 길이를 확인합니다.
2단계: 재귀 방식으로 나누기
재귀 스플리터는 먼저 빈 줄에서 나누고, 조각이 여전히 길면 문장 끝, 그다음 공백 순서로 나눌 위치를 찾습니다. 빈 줄처럼 큰 단위의 경계에서 나눌 수 없을 때 다음 경계를 사용합니다.
3단계: 조건 하나만 바꾸기
재귀 방식은 그대로 두고 chunk_size만 35에서 50으로 바꿉니다. 청크 수와 본문이 어떻게 달라지는지 확인합니다.
4단계: 토큰 기준으로 나누기
토큰 스플리터는 모델 입력 한도를 다룰 때 사용합니다. 한국어 한 글자와 한 토큰은 같은 단위가 아니므로 토큰 수를 직접 확인합니다.
실패 확인
Before 원인 “배송 시작 시점과 제주 추가 기간”에 답하려면 결제 다음 날과 제주 지역은 이틀이라는 근거가 함께 필요합니다. 35자 설정에서는 두 근거가 서로 다른 청크에 놓입니다.
After 수정 앞의 3단계에서 이미 실행한 50자 결과를 다시 사용합니다. 같은 재귀 방식과 5자 오버랩을 유지한 결과에서 두 배송 문장이 한 청크에 들어와 질문에 필요한 근거를 함께 읽을 수 있는지 확인합니다.

labs/part3/ch10-document-processing/notebooks/06-구조와-시맨틱-청킹.ipynb

구조 청킹과 시맨틱 청킹
먼저 Markdown 제목을 메타데이터로 보존합니다. 그다음 LangChain의 시맨틱 스플리터를 기본 설정으로 실행하고, 문장 사이 거리 중 어느 정도로 큰 값을 경계로 삼을지 정하는 백분위수 하나만 바꿉니다.
구조 경계와 의미 변화 경계
MarkdownHeaderTextSplitter는 제목 규칙을 만들고 split_text()가 제목 계층을 메타데이터로 가진 Document를 반환합니다. SemanticChunker는 같은 호출에서 문장 임베딩을 실행해 의미 변화량이 큰 곳을 경계로 사용합니다.
제목이 신뢰할 만한 매뉴얼은 구조 청킹이 설명 가능하고, 제목 없이 화제가 바뀌는 인터뷰는 의미 경계가 후보가 됩니다. 백분위수를 높였을 때의 청크 수는 원문 분포에 따라 달라집니다.
1단계: Markdown 제목 구조 보존하기
제목 기호와 메타데이터 이름을 연결합니다. 결과의 metadata와 page_content를 함께 확인합니다.
2단계: 시맨틱 청킹 기본 설정 실행하기
아래 문장은 마침표 뒤에 공백이 있습니다. 이 예제의 기본 문장 분리 정규식은 .?! 뒤의 공백을 경계로 사용합니다.
이 절은 유지보수가 종료된 langchain-experimental 0.4.2의 SemanticChunker로 원리를 학습합니다. 해당 버전에 한정한 실습이며 새 운영 시스템의 기본 선택을 권장하는 예제가 아닙니다.
3단계: 임계값 하나만 바꾸기
모델과 원문은 그대로 두고 백분위수를 95번째에서 50번째로 낮춥니다. 95번째 백분위수는 거리값을 작은 순서로 놓았을 때 약 상위 5%의 큰 거리만 후보로 삼고, 50번째 백분위수는 중앙값보다 큰 거리도 후보로 삼는 설정입니다. 표본이 작거나 같은 값이 있으면 경계 비율이 정확히 5%나 50%가 되지는 않습니다. 실제 청크 수와 본문을 비교합니다.
4단계: 기준값을 더 낮추어 변화 폭 확인하기
백분위수를 0번째로 낮추면 가장 작은 거리보다 큰 위치도 경계 후보가 됩니다. 청크 수와 본문을 출력해 50번째 백분위수 결과와 비교합니다.
5단계: 세 기준값의 결과 비교하기
청크 수가 적거나 많다는 사실만으로 품질을 판단하지 않습니다. 각 기준값이 만든 청크 수를 나란히 놓고, 실제 질문에 맞는 값은 여러 질문의 검색 결과로 평가해야 한다고 해석합니다.

labs/part3/ch10-document-processing/notebooks/07-한국어-임베딩과-캐시.ipynb

한국어 임베딩과 캐시
문장 하나의 벡터를 먼저 관찰하고, 여러 문장을 한 번에 변환합니다. 마지막에는 LangChain의 캐시 기능으로 첫 요청의 벡터를 파일에 저장하고, 같은 문서를 다시 요청할 때 그 벡터를 읽습니다.
임베딩 호출과 캐시 조회 순서
embed_documents()는 문자열 목록을 받아 같은 순서의 벡터 목록을 반환합니다. CacheBackedEmbeddings.from_bytes_store()는 원래 임베딩 앞에 캐시 조회를 붙인 새 객체를 반환합니다.
첫 요청은 캐시에 값이 없으면 임베딩한 뒤 저장하고 같은 키의 다음 요청은 저장값을 읽습니다. 파일 수만으로 API 호출 횟수를 단정할 수 없으며, 모델이나 차원이 바뀌면 네임스페이스를 분리해야 합니다.
1단계: 문장 하나를 벡터로 바꾸기
벡터 전체를 출력하면 숫자가 너무 많습니다. 앞의 다섯 값과 전체 길이만 확인합니다.
2단계: 여러 문장을 한 번에 변환하기
입력 문장 수와 반환된 벡터 수가 같은지 확인합니다. 모든 벡터는 같은 임베딩 설정을 사용하므로 길이도 같습니다.
3단계: 차원 하나 바꾸어 벡터 길이 비교
문장과 모델은 유지하고 dimensions만 256에서 128로 바꿉니다. 반환 벡터의 길이를 비교합니다.
4단계: LangChain 캐시 사용하기
이번 커널에서만 사용하는 빈 임시 폴더를 만듭니다. 같은 문서 목록을 두 번 요청합니다. 첫 요청 뒤 생긴 벡터 파일 수가 두 번째 요청 뒤에도 그대로인지 확인합니다.
실패 확인
Before 원인 128차원 모델에 256차원 캐시에 사용한 것과 같은 namespace를 지정하면, 같은 문장의 오래된 256차원 벡터를 잘못 읽을 수 있습니다.
After 수정 차원을 포함한 새 namespace를 사용합니다. 캐시에 값이 없으므로 128차원 모델이 새 벡터를 계산하고 별도 이름으로 저장합니다.

labs/part3/ch10-document-processing/notebooks/08-인덱싱-비교-실험.ipynb

3가지 청킹 × 2가지 임베딩 실험
같은 교육용 원문과 질문을 유지하고 재귀·토큰·구조 기반 청킹과 두 임베딩 모델의 여섯 조합을 실제로 실행합니다. 이 작은 실험은 전체 검색 품질 순위를 정하지 않습니다.
여섯 조합을 공정하게 비교하기
독립 변수는 청킹 방법 세 가지와 임베딩 모델 두 가지이며 원문·질문·정답·검색 개수는 고정합니다. 각 조합이 반환한 순위와 정답 포함 여부를 같은 열에 기록합니다.
청크 수나 실행 시간만으로 검색 품질을 판정할 수 없습니다. 짧은 원문 한 건의 결과는 방법 전체의 우열이 아니라 Ch 11에서 더 많은 질문으로 검증할 가설입니다.
1. 원문과 질문 고정하기
제목 구조가 있는 배송·환불·회원 규정과 질문 하나를 모든 조합에서 그대로 사용합니다.
2. 세 가지 청킹 실행하기
재귀 청킹은 문자 경계를, 토큰 청킹은 토큰 수를, 구조 기반 청킹은 마크다운 제목을 우선 사용합니다.
3. 여섯 조합에서 실제 임베딩 검색하기
두 모델을 각각 세 개의 청크 집합에 적용합니다. 저장 공간 차이를 제외하고 검색 내용을 비교하기 위해 두 모델 모두 256차원으로 맞춥니다.
4. 같은 형식으로 여섯 결과 읽기
각 행에서 청킹 방법, 모델, 청크 수, 첫 검색 결과의 ID·점수·본문을 함께 확인합니다.
5. 첫 검색 결과의 근거 범위 확인하기
첫 청크에 질문의 대상인 제주와 답인 이틀이 함께 있는지 확인합니다. 이 검사는 질문 하나의 관찰이며 검색 품질 지표가 아닙니다.
6. 제공 자료와 선택 실습 범위 확인하기
배포 묶음의 manifest.json과 실제 PDF 파일을 대조합니다. 디지털 PDF 18건과 기존 문서의 스캔 변형 3건을 구분합니다. 집필용 전체 질의셋 149개는 정답 정보를 포함하므로 학생 배포에서 제외합니다. 이 자료를 수강생의 실제 업무 문서 100건이라고 세지 않습니다.
7. Ch 11과 같은 자료·질문으로 연결 검색하기
앞의 짧은 원문 실험은 청킹 경계를 눈으로 비교하기 위한 학습용 범위입니다. 다음 셀은 Ch 11과 같은 18개 디지털 PDF와 Q001을 사용해 3가지 청킹×2가지 임베딩의 6개 설정을 실행합니다. 질문이 하나이므로 이 결과만으로 설정의 우열을 결정하지 않습니다.
8. 실행별 로그와 Ch 11 입력 포인터 저장하기
실행 ID별 JSONL은 새 파일로 보존합니다. continuity-ch10-indexing.jsonl은 Ch 11이 읽는 최신 포인터이며 기존 Ch 10 로그를 덮어쓰지 않습니다.
선택 실습
수강생이 외부 전송이 허용된 실제 업무 문서 100건과 정답 질문을 준비한 뒤 같은 6개 조합으로 확장합니다. 파일 내용을 해시해 중복을 제외하고 100건인지 먼저 확인합니다. Upstage 또는 LlamaParse 비교는 각 서비스의 자격증명, 비용 확인, 문서 반출 승인이 모두 갖춰졌을 때 별도로 실행합니다. 이 기본 노트북은 상용 파서를 호출하지 않으며, 제공 PDF 21건이나 질문 149개를 업무 문서 100건으로 대체하지 않습니다.
