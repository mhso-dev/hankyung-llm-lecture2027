textbook/part6/ch22-middleware/_src/01-미들웨어와-6개-훅.html

1학습 목표
여섯 훅을 에이전트 전체·모델·도구 범위로 구분할 수 있습니다.
노드형 훅과 감싸기형 훅의 반환 방식 차이를 설명할 수 있습니다.
실제 도구 호출 trace에서 각 훅의 실행 위치를 확인할 수 있습니다.
2이 내용을 배우는 이유
Ch20에서는 모델 노드와 ToolNode를 직접 연결했고 Ch21에서는 create_agent가 같은 반복을 컴파일된 그래프로 만든다는 사실을 확인했습니다. 운영 요구가 추가될 때마다 모델 노드와 도구 함수 본문을 수정하면 핵심 업무 코드와 횡단 기능이 섞입니다. 미들웨어는 반복 구조의 정해진 지점에 검증, 기록, 재시도를 연결합니다. 이 절에서는 먼저 훅의 정확한 이름과 실행 범위를 확인합니다.
이 절의 질문 — 미들웨어의 여섯 훅은 에이전트 실행의 어느 지점에서 어떤 순서로 호출될까요?
3앞에서 배운 내용
Ch16의 guardrails.py는 모델 호출 전후에 validate_query, mask_pii, CallBudget, retry_with_fallback을 직접 호출했습니다. Ch20에서는 도구 요청과 ToolMessage 사이를 ToolNode가 맡았습니다. 이번 절은 그 사이 지점을 create_agent의 middleware 인자로 노출합니다.
4핵심 개념
비유로 시작하기
공항 보안 절차를 떠올려 봅니다. 탑승 수속 전체의 시작과 끝, 탑승구 진입 전후, 수하물 검사 전후는 서로 다른 검사 지점입니다. 미들웨어도 에이전트 전체에는 before_agent와 after_agent, 각 모델 호출에는 before_model·wrap_model_call·after_model, 각 도구 호출에는 wrap_tool_call을 제공합니다. 노드형 훅은 정해진 지점에서 한 번 실행되고 상태 갱신 딕셔너리를 반환할 수 있습니다. 감싸기형 훅은 handler를 호출하기 전후를 모두 제어하며 재시도하거나 요청을 바꾸거나 호출을 생략할 수도 있습니다.
코드를 읽는 순서
미들웨어는 create_agent가 만든 루프의 약속된 시점에 실행되는 로직입니다. 개발자가 훅 함수를 직접 호출하지 않아도 런타임이 before_agent, before_model, after_model, after_agent를 노드처럼 실행합니다. wrap_model_call과 wrap_tool_call은 대상 호출과 handler를 함께 받아 호출 전후를 감쌉니다. 랩 훅에서 handler를 호출하지 않으면 실제 모델 또는 도구도 실행되지 않으므로 단순한 전후 알림과 제어 로직을 구분해야 합니다.
SixHookTrace는 상태를 바꾸지 않고 TRACE에 이름만 남기는 관찰용 클래스입니다. 첫 모델 응답이 도구 호출을 만들기 때문에 before_model과 모델 랩은 두 번 실행되고, 도구 랩은 한 번 실행됩니다. 반면 before_agent와 after_agent는 한 번의 invoke 경계에서 각각 한 번 나타납니다. 훅의 횟수는 등록 개수가 아니라 실제 루프 반복과 도구 선택에 따라 달라집니다.
도식 읽기
왼쪽의 파란 입력 상태에서 실행을 시작해 파란 before_agent를 한 번 통과합니다. 보라색 모델 호출 상자의 앞뒤에는 before_model·wrap_model_call·after_model이 놓입니다. 모델이 도구를 요청하면 초록색 lookup_hours 앞뒤를 wrap_tool_call이 감싸고 다시 모델 상자로 돌아갑니다. 마지막 파란 after_agent 뒤에서 실행이 끝납니다.
5실행 예제
첫 셀은 LangChain·LangGraph 버전을 확인하고 실제 모델에 한 번 요청해 사용량을 출력합니다. 뒤의 훅 순서 실험은 응답을 정해 둔 모델로 도구 호출을 한 번 재현합니다. 이 분리는 훅의 호출 경계와 실제 모델 품질·지연을 구분하기 위한 것입니다.
확인할 점 — before_agent와 after_agent는 한 번씩, 모델 관련 훅은 두 번씩, wrap_tool_call은 한 번 기록됐는지 확인합니다.
다른 상황과 적용 경계
모델 입력에 사용자 등급을 추가하는 일은 before_model, 일시 오류를 재시도하는 일은 wrap_model_call, 도구 인자를 검사하는 일은 wrap_tool_call이 자연스럽습니다. 같은 검사를 모든 노드에 복사하면 변경 위치가 늘어나므로 반복되는 횡단 관심사를 미들웨어로 모읍니다.
모든 로직을 미들웨어로 옮길 필요는 없습니다. 주문 금액 계산처럼 업무 자체를 나타내는 단계는 그래프 노드나 도구에 두는 편이 흐름을 읽기 쉽습니다. 이 실습의 TRACE 순서는 한 번의 도구 호출 경로에서 관찰한 값이며, 도구가 없거나 병렬 호출이 있으면 횟수와 순서가 달라질 수 있습니다.
6실험 결과 해석
학습용 모델은 첫 응답에서 lookup_hours 도구를 한 번 요청하고 두 번째 응답에서 종료합니다. 출력 trace에는 before_agent가 한 번, 모델 관련 세 훅이 두 번, wrap_tool_call이 한 번, after_agent가 한 번 나타납니다. 여섯 훅이라는 말은 여섯 개의 독립 오류 이벤트를 뜻하지 않습니다. 오류는 wrap_model_call 또는 wrap_tool_call에서 예외로 관찰하고 종료는 after_agent에서 관찰합니다.
7주의할 점과 실무 메모
공식 LangChain 1.4.0의 여섯 훅은 before_agent, before_model, wrap_model_call, wrap_tool_call, after_model, after_agent입니다.
노드형 훅에서 상태를 바꾸려면 딕셔너리를 반환합니다. 감싸기형 훅은 handler의 반환값을 보존하거나 문서가 허용한 형식으로 바꿉니다.
첫 기능 셀에서 실제 OpenAI API 연결을 확인한 뒤, 훅의 정확한 순서는 정해 둔 응답을 쓰는 검사 모델로 재현합니다. 키 값은 출력하지 않습니다.
실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.
8정리와 다음 절
훅은 에이전트 전체·모델·도구의 실행 경계에 미들웨어 로직을 연결합니다.
도구를 한 번 쓴 실행에서 모델 훅은 두 번, 도구 훅은 한 번 실행되는 trace를 확인했습니다.
결정적 검사 모델은 훅 경계를 확인하며 실제 모델 품질을 측정하지 않습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 Ch16의 정규식 기반 mask_pii를 LangChain의 PIIMiddleware로 옮기고 입력과 출력 적용 범위를 비교합니다.
9복습 문제
문제와 해설
1. 에이전트 실행당 한 번 호출되는 훅 두 개는 무엇인가요?
해설 — before_agent와 after_agent입니다.
2. handler를 여러 번 호출해 재시도를 구현할 수 있는 모델 훅은 무엇인가요?
해설 — wrap_model_call입니다.
3. 도구 오류를 관찰하기에 알맞은 훅은 무엇인가요?
해설 — wrap_tool_call에서 handler 호출 예외를 처리합니다.
4. after_model은 왜 한 실행에서 여러 번 호출될 수 있나요?
해설 — 도구를 사용한 에이전트는 모델을 여러 차례 호출하기 때문입니다.

textbook/part6/ch22-middleware/_src/02-PII-마스킹-이식.html

1학습 목표
PII와 마스킹 전략을 설명할 수 있습니다.
apply_to_input과 apply_to_output의 적용 범위를 구분할 수 있습니다.
Ch16 정규식 함수와 내장 미들웨어의 책임 차이를 비교할 수 있습니다.
2이 내용을 배우는 이유
개인 식별 정보(PII)는 질문, 모델 답변, 도구 결과 어디에서든 나타날 수 있습니다. Ch16에서는 guarded_generate 안에서 입력과 문서를 직접 mask_pii에 전달했습니다. 에이전트에서는 모델과 도구가 반복되므로 같은 호출을 여러 위치에 빠뜨리지 않고 적용해야 합니다. PIIMiddleware는 이 반복 지점을 설정으로 모읍니다.
이 절의 질문 — Ch16의 PII 마스킹을 PIIMiddleware로 옮기면 적용 지점과 코드가 어떻게 달라질까요?
3앞에서 배운 내용
Ch16 guardrails.py의 mask_pii는 email, phone, rrn, card 정규식을 순서대로 적용하고 종류별 개수를 반환했습니다. 테스트는 가상 이메일과 전화번호가 가려지고 출처 태그는 유지되는지 확인했습니다. 여기서는 같은 가상 이메일을 사용해 직접 함수와 미들웨어 결과를 비교합니다.
4핵심 개념
비유로 시작하기
문서 발송 전에 담당자가 특정 칸을 검게 가리는 절차를 생각해 봅니다. 어떤 문서를 가릴지와 어떤 정보 유형을 찾을지를 따로 정해야 합니다. PIIMiddleware의 pii_type은 찾을 유형, strategy는 block·redact·mask·hash 중 처리 방법입니다. apply_to_input은 사용자가 보낸 메시지, apply_to_output은 모델 답변, apply_to_tool_results는 도구 결과에 적용합니다. 한 인스턴스는 한 유형을 맡으므로 이메일과 신용카드를 함께 다루려면 각각 추가합니다.
코드를 읽는 순서
개인 식별 정보(PII)는 이메일, 전화번호처럼 개인을 알아볼 수 있게 하는 데이터입니다. mask_pii(text)는 문자열 하나를 받아 정규식과 일치한 부분을 표식으로 바꾸고, 유형별 발견 개수를 함께 반환합니다. 이 함수만 정의해 두면 아무 요청에도 자동 적용되지 않습니다. 호출 지점을 빠뜨린 Before가 그대로 노출되는 이유입니다.
PIIMiddleware는 같은 검사를 에이전트 경계에 등록합니다. 입력 검사는 모델에 전달하기 전에 사용자 메시지를 바꾸고, 출력 검사는 모델 응답을 호출자에게 반환하기 전에 바꿉니다. strategy="mask"는 일부를 가리는 처리 방식이며, 감지기가 찾지 못한 형식이나 이미지 속 정보까지 보호한다는 뜻은 아닙니다. 입력과 출력 두 방향은 서로 대신할 수 없습니다.
도식 읽기
파란 원문 입력에는 네 종류의 가상 PII가 있습니다. 파란 Ch16 mask_pii 상자는 네 유형을 완전 치환하고 개수를 반환합니다. 다른 경로의 파란 PIIMiddleware(email) 상자는 이메일 한 유형만 모델 호출 전후에 부분 마스킹합니다. 두 화살표가 같은 보라색 모델 경계에 닿지만 보존하는 정책은 같지 않습니다.
5실행 예제
가상 이메일을 같은 입력에 넣고, Before에서는 Ch16의 함수를 호출하지 않습니다. After에서는 입력·출력 적용 범위를 지정한 PIIMiddleware를 붙인 뒤 모델이 받은 내용과 최종 답변을 비교합니다.
확인할 점 — Before의 모델 입력에는 원문 이메일이, After의 입력과 답변에는 부분 마스킹된 이메일이 남는지 확인합니다.
다른 상황과 적용 경계
고객 상담에서는 사용자가 보낸 주민등록번호가 모델로 들어가기 전 마스킹되어야 하고, 모델이 도구 결과에서 읽은 이메일도 최종 응답에서 다시 검사해야 합니다. 로그 저장 경로가 미들웨어 바깥에 있다면 로그에는 원문이 먼저 남을 수 있으므로 데이터가 지나가는 모든 경계를 따로 검토합니다.
마스킹은 값을 숨기면서 요청을 계속 처리하고, 차단은 요청을 중단합니다. 계좌 이체처럼 민감값 없이 업무를 수행할 수 없는 경우에는 무조건 마스킹보다 승인된 별도 경로가 필요할 수 있습니다. 이번 결과는 네 가지 예시 문자열과 지정한 감지 범위에서만 확인한 것입니다.
6일부러 실패해 보기
Before의 Ch16 축소 함수는 호출자가 mask_pii를 호출하지 않으면 원문 이메일이 그대로 모델에 전달됩니다. After의 PIIMiddleware는 create_agent의 실행 흐름 안에서 사용자 이메일과 모델이 만든 이메일을 모두 부분 마스킹합니다. 기본 내장 email 검출기의 mask 결과는 도메인을 일부 남길 수 있으므로 완전 삭제가 필요한 정책이라면 redact 또는 block을 선택해야 합니다.
7주의할 점과 실무 메모
PIIMiddleware는 비밀 관리 시스템이 아닙니다. 이미 외부 로그에 기록된 값은 되돌려 지우지 못하므로 가장 이른 입력 경계에 둡니다.
정규식 검출에는 오탐과 누락이 있습니다. 주민등록번호처럼 한국 고유 유형은 detector 함수를 직접 제공하고 별도 테스트를 작성합니다.
출력 마스킹은 안전한 응답을 보장하지 않습니다. 허용되지 않은 정보 조회 자체는 권한 검사로 차단해야 합니다.
실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.
8정리와 다음 절
PIIMiddleware는 설정한 메시지 경계에서 정한 개인 식별 정보 유형을 탐지하고 처리합니다.
입력과 출력에 email 마스킹을 적용해 호출자가 직접 함수를 부르지 않아도 경계가 유지됨을 확인했습니다.
마스킹은 접근 권한을 대신하지 않으며 한국 고유 식별자에는 별도 탐지기와 테스트가 필요합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 길어진 메시지를 줄이는 Ch16의 summarize_history와 SummarizationMiddleware를 비교해 Compress의 보존 범위를 확인합니다.
9복습 문제
문제와 해설
1. apply_to_tool_results는 무엇을 제어하나요?
해설 — 도구가 반환한 ToolMessage 내용에도 PII 처리를 적용할지 정합니다.
2. email과 credit_card를 함께 처리하려면 어떻게 하나요?
해설 — 유형별 PIIMiddleware 인스턴스를 middleware 목록에 추가합니다.

4핵심 개념
비유로 시작하기
회의록을 다음 회의용 한 장 요약으로 바꾸는 상황을 생각해 봅니다. trigger는 언제 요약을 시작할지, keep은 최근 기록을 얼마나 원문으로 남길지 정합니다. SummarizationMiddleware는 before_model 훅에서 메시지 수나 토큰 수를 검사합니다. 요약 모델은 압축문을 만들고 주 모델은 압축된 문맥으로 답합니다. 압축은 원문을 완전히 보존하지 않으므로 결정, 예외, 날짜, 출처처럼 반드시 남겨야 할 필드를 프롬프트와 검증에 넣어야 합니다.
코드를 읽는 순서
요약 압축은 오래된 메시지의 핵심을 짧은 메시지로 바꾸어 다음 모델 입력을 줄이는 처리입니다. SummarizationMiddleware는 트리거 조건을 넘으면 요약 모델을 호출하고, 최근 메시지 일부와 생성한 요약을 다음 요청에 전달합니다. 체크포인터의 과거 기록 전체를 삭제하는 기능과는 다릅니다. 무엇을 저장했는지와 이번 모델에 무엇을 보냈는지를 구분합니다.
실습의 CaptureAll과 CaptureCompressed는 모델이 실제로 받은 메시지를 seen_before, seen_after에 복사하는 관찰 장치입니다. 요약문의 길이만 줄었다고 성공으로 판단하지 않고, 대출 권수·기간·연장 조건·출처가 남았는지 문자열을 읽습니다. 압축은 손실을 허용하는 변환이므로 업무에 필요한 사실을 먼저 정해야 합니다.
도식 읽기
파란 원본 여섯 메시지가 노란 trigger 검사로 들어갑니다. 임계값 미만이면 그대로 보라색 주 모델로 이동합니다. 임계값 이상이면 오래된 메시지가 보라색 요약 모델을 거쳐 파란 요약문과 최근 두 메시지로 바뀐 뒤 주 모델에 전달됩니다. E01 p.3은 압축 뒤에도 확인할 보존 항목입니다.
5실행 예제
여섯 메시지를 Before 에이전트에 그대로 전달한 뒤, trigger=4·keep=2 조건의 SummarizationMiddleware를 붙입니다. 결정적 요약문으로 메시지 구성 변화를 재현하고, 별도 실제 모델 호출로 권수·기간·연장 조건·출처를 보존한 요약문과 사용량을 확인합니다.

다른 상황과 적용 경계
친근한 말투나 반복된 인사는 요약해도 영향이 작지만, 승인 여부·계약 숫자·출처 식별자는 빠지면 후속 답이 달라질 수 있습니다. 이런 값은 상태의 별도 필드에 구조화해 보존하고 대화 요약에는 맥락만 맡기는 설계가 안전합니다.
메시지 수 감소와 토큰 수 감소는 관련되지만 같은 값은 아닙니다. 긴 한 메시지가 짧은 여러 메시지보다 토큰이 많을 수 있습니다. 이번 실습은 전달 메시지와 보존 문자열을 확인하며, 실제 모델별 토큰 절감률이나 요약 정확도 전체를 보장하지 않습니다.

여섯 메시지가 요약문과 최근 두 메시지로 바뀌며 날짜·예외·출처가 남았는지 확인했습니다.
결정적 요약문의 검사 통과는 실제 생성 모델의 정확성을 보장하지 않습니다.

1학습 목표
run_limit와 thread_limit을 구분할 수 있습니다.
재시도 대상 예외와 지수 백오프를 설정할 수 있습니다.
폴백 모델이 실행되는 조건과 비용 경계를 설명할 수 있습니다.
2이 내용을 배우는 이유
Ch16의 CallBudget과 retry_with_fallback은 호출자가 매번 reserve와 재시도 함수를 직접 사용했습니다. create_agent 반복에서는 모델이 도구를 여러 번 요청할 수 있으므로 실행 전체에서 호출 수를 세어야 합니다. 일시적 오류에는 재시도가 도움이 되지만 잘못된 입력이나 권한 오류를 반복하면 비용만 늘어납니다. 한도·재시도·폴백을 서로 다른 정책으로 분리해야 합니다.
이 절의 질문 — 호출 한도, 재시도, 폴백은 서로 다른 실패 조건을 어떻게 나누어 처리할까요?
3앞에서 배운 내용
Ch16 CallBudget.reserve는 호출 직전에 예상 비용과 호출 수를 검사했습니다. retry_with_fallback은 TimeoutError만 정해진 횟수만 재시도하고 마지막에 폴백 함수를 호출했습니다. 이 절에서는 같은 역할을 ModelCallLimitMiddleware, ModelRetryMiddleware, ModelFallbackMiddleware의 설정과 실행 trace로 확인합니다.
4핵심 개념
비유로 시작하기
고객센터 전화를 생각해 봅니다. 한도는 한 통화에서 상담원 연결을 몇 번까지 시도할지 막습니다. 재시도는 연결이 일시적으로 끊겼을 때 같은 상담원에게 다시 거는 규칙입니다. 폴백은 주 상담망이 계속 실패할 때 보조 상담망으로 바꾸는 규칙입니다. ModelCallLimitMiddleware의 run_limit는 현재 invoke, thread_limit는 같은 스레드에 누적된 호출을 제한합니다. ModelRetryMiddleware는 retry_on, 지연, 최대 횟수를 정합니다. create_agent의 첫 인자가 최초 모델을 정하고 ModelFallbackMiddleware에는 실패 뒤 시도할 보조 모델만 전달합니다.
코드를 읽는 순서
재시도, 폴백, 호출 한도는 모두 실패에 대응하지만 해결하는 문제가 다릅니다. ModelRetryMiddleware는 같은 요청을 같은 모델에 다시 보내 일시 오류가 사라지는지 확인합니다. max_retries=2는 최초 시도 외에 허용할 재시도 수이며, retry_on=(TimeoutError,)는 어떤 오류만 반복할지 제한합니다. 코드 버그나 잘못된 입력까지 반복하면 같은 실패만 늘어납니다.
ModelFallbackMiddleware는 주 모델 호출이 실패했을 때 다른 모델로 넘깁니다. ModelCallLimitMiddleware(run_limit=1, exit_behavior="end")는 한 invoke 안에서 허용할 모델 호출을 제한하고, 루프가 두 번째 호출을 요구해도 종료 응답을 만듭니다. 재시도 횟수, 모델 교체 횟수, 루프 호출 한도는 서로 다른 카운터입니다.
도식 읽기
파란 모델 요청은 먼저 노란 호출 한도를 확인합니다. 일시적 TimeoutError는 빨간 실패 상자에서 파란 재시도 경로로 돌아가고, 정한 횟수 뒤에도 실패하면 보라색 보조 모델로 이동합니다. 성공 화살표와 차단 화살표를 구분하면 한도·재시도·폴백이 서로 다른 조건을 처리한다는 점을 읽을 수 있습니다.
5실행 예제
한 번 TimeoutError를 내는 모델로 재시도 횟수를 확인하고, 계속 실패하는 주 모델과 보조 모델로 폴백을 확인합니다. 마지막에는 도구 호출 뒤 두 번째 모델 호출이 필요한 흐름에 run_limit=1을 적용해 한도가 종료 메시지를 반환하는지 봅니다.
확인할 점 — 재시도 모델은 두 번 호출되고, 최초 모델과 보조 모델은 각각 한 번 호출되고 폴백은 보조 모델 응답을 반환하며, 한도 에이전트는 모델을 한 번만 호출했는지 확인합니다.
다른 상황과 적용 경계
검색 API의 순간적인 타임아웃에는 재시도가 맞고, 특정 제공자 장애에는 폴백이 맞습니다. 모델이 도구를 계속 호출하는 논리적 루프에는 호출 한도가 필요합니다. 세 정책을 함께 쓸 때는 안쪽 재시도가 모두 끝난 뒤 폴백할지, 전체 한도가 재시도까지 셀지 실행 순서를 명시해야 합니다.
이번 결정적 모델은 오류와 응답 순서를 미리 정해 정책 분기를 재현합니다. 실제 네트워크의 지연 분포나 제공자 장애 복구를 측정한 결과는 아닙니다. calls==2, 보조 모델 응답, 한도 메시지는 각각 별도의 정책이 작동했다는 증거로 읽습니다.
6실험 결과 해석
결정적 오류 모델로 세 정책을 따로 실행합니다. 재시도 실험에서는 첫 TimeoutError 뒤 두 번째 호출이 성공해 호출 수 2가 됩니다. 폴백 실험에서는 최초 모델이 한 번 실패하고 보조 모델이 한 번 응답합니다. 호출 한도 실험에서는 도구를 요청한 뒤 두 번째 모델 호출 전에 제한이 적용됩니다. 이 결과는 정책 경로를 확인하며 실제 공급자 장애율이나 지연 분포를 측정한 값은 아닙니다.
7주의할 점과 실무 메모
retry_on에는 일시적 오류만 포함합니다. 인증 실패, 잘못된 스키마, 정책 차단은 반복해도 해결되지 않습니다.
재시도는 모델 호출 횟수와 비용을 늘립니다. 호출 한도는 재시도 횟수까지 포함해 설계합니다.
폴백 모델은 기능, 도구 호출 형식, 개인정보 처리 지역, 가격을 따로 검토해야 합니다.
실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.
8정리와 다음 절
재시도는 같은 모델의 일시 오류를, 폴백은 다른 모델로의 전환을, 호출 한도는 반복 횟수를 다룹니다.
최초 모델은 한 번 실패하고 보조 모델이 응답하며, 도구 루프는 두 번째 모델 호출 전에 종료됨을 확인했습니다.
재시도 대상 오류와 미들웨어 순서를 정하지 않으면 영구 오류를 반복하거나 호출 한도를 예상과 다르게 소비할 수 있습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 내장 호출 수 제한이 다루지 않는 예상비용 상한을 커스텀 미들웨어로 작성합니다.
9복습 문제
문제와 해설
1. run_limit와 thread_limit의 차이는 무엇인가요?
해설 — run_limit는 한 invoke 안의 호출 수, thread_limit는 같은 스레드에 누적된 호출 수를 제한합니다.
2. 모든 예외를 재시도하면 안 되는 이유는 무엇인가요?
해설 — 영구 오류는 반복해도 해결되지 않고 비용과 지연만 늘어납니다.
3. 폴백 전에 확인할 호환성은 무엇인가요?
해설 — 도구 호출·구조화 출력 지원, 정책, 데이터 처리, 가격을 확인합니다.
4. 재시도와 호출 한도를 함께 설계해야 하는 이유는 무엇인가요?
해설 — 재시도도 모델 호출 수와 비용에 포함되기 때문입니다.

1학습 목표
커스텀 AgentMiddleware 클래스를 작성할 수 있습니다.
wrap_model_call에서 handler 호출 전 예산을 예약할 수 있습니다.
Ch16 CallBudget과 미들웨어 구현의 코드 위치 차이를 비교할 수 있습니다.
2이 내용을 배우는 이유
내장 ModelCallLimitMiddleware는 호출 횟수를 제한하지만 프로젝트가 사용하는 가격표와 예상 토큰으로 비용 상한을 계산하지는 않습니다. Ch16의 CallBudget은 이 정책을 직접 구현했습니다. 에이전트마다 같은 reserve 호출을 넣는 대신 커스텀 미들웨어 하나로 모델 호출 경계를 감싸면 정책 코드를 재사용하고 독립적으로 검사할 수 있습니다.
이 절의 질문 — 모델 호출 수뿐 아니라 예상비용 상한을 호출 직전에 어떻게 검사할까요?
3앞에서 배운 내용
Ch16 CallBudget은 max_calls, max_cost_usd, calls, cost_usd를 보관하고 reserve에서 다음 호출이 한도를 넘는지 검사했습니다. 이번 구현은 그 계산을 wrap_model_call 앞에 옮깁니다. 가격과 토큰 예상치는 수업용 고정값이며 실제 청구액과 구분합니다.
4핵심 개념
비유로 시작하기
교통카드 선불 한도를 생각해 봅니다. 버스를 탄 뒤 잔액을 검사하면 이미 비용이 발생했습니다. 호출 전 예약은 다음 호출의 예상비용을 먼저 더해 상한을 넘으면 handler를 호출하지 않습니다. BudgetMiddleware는 estimated_cost_per_call과 max_cost_usd를 받아 같은 인스턴스가 처리한 요청의 예약 비용을 누적합니다. 이 예제는 한 인스턴스에 두 번의 invoke를 순차적으로 전달하며, 운영의 동시 요청에서는 상태나 외부 저장소에 실행별 카운터를 분리해야 합니다.
코드를 읽는 순서
예산 미들웨어는 모델 호출 직전에 예상 사용량을 예약하고 상한을 넘는 호출을 시작하지 않게 하는 제어 장치입니다. BudgetMiddleware(max_cost_usd, estimated_cost_per_call)은 누적 예약값 reserved를 보관합니다. wrap_model_call은 다음 예약값을 계산한 뒤 허용되면 handler(request)를 한 번 호출하고, 넘으면 BudgetExceeded를 발생시킵니다. 반환값은 모델 응답이며 예산 숫자가 아닙니다.
여기서 estimated_cost_per_call은 실제 사용량에서 계산한 청구 금액이 아니라 실습용 예약 단위입니다. 호출 전에 정확한 출력 길이를 알 수 없기 때문에 보수적인 예상치나 토큰 상한으로 입장을 결정할 수 있습니다. 호출 뒤 실제 사용량을 정산하는 방식과 호출 전 차단은 목적과 오차가 다릅니다.
도식 읽기
파란 요청이 노란 예상비용 예약 상자에 들어갑니다. 예약 합계가 0.006달러 이하이면 보라색 handler와 모델 호출로 이어집니다. 두 번째 요청처럼 0.008달러가 되면 빨간 BudgetExceeded로 이동하고 모델 호출 화살표는 생기지 않습니다. 차단 전후의 guarded.index가 호출 시점을 확인하는 값입니다.
5실행 예제
Before는 두 모델 호출을 제한 없이 실행합니다. After는 같은 미들웨어 인스턴스에 두 번의 invoke를 전달하고, 누적 예산을 넘는 두 번째 요청을 중단하는 커스텀 미들웨어를 사용합니다.
확인할 점 — 첫 요청의 예약·사용 기록과 두 번째 요청의 차단 기록을 구분해 확인합니다.
다른 상황과 적용 경계
사용자별 일일 한도라면 reserved를 미들웨어 객체의 메모리에만 두지 않고 사용자 ID와 날짜를 키로 하는 공유 저장소에 기록해야 합니다. 여러 프로세스가 동시에 요청을 받으면 읽기와 예약을 하나의 원자적 연산으로 처리해야 두 요청이 같은 남은 예산을 함께 사용하는 일을 막을 수 있습니다.
호출 한도는 횟수를 제한하고 예산 한도는 서로 다른 모델·입력 길이를 공통 단위로 비교하려는 정책입니다. 이번 셀의 두 번째 차단은 0.004+0.004가 0.006을 넘는 계산을 검증할 뿐, 실제 모델 비용을 측정하거나 제공자의 청구를 대체하지 않습니다.
6일부러 실패해 보기
Before에서는 두 번의 모델 호출이 모두 실행됩니다. After에서는 첫 invoke가 0.004달러를 예약하고 성공하지만 같은 인스턴스에 전달한 두 번째 invoke는 0.008달러가 0.006달러 상한을 넘으므로 handler 실행 전에 BudgetExceeded가 발생합니다. 모델의 calls 값이 1인 것으로 차단 시점이 호출 전임을 확인합니다.
7주의할 점과 실무 메모
예상비용은 실제 토큰 사용량과 다를 수 있습니다. 응답 후 usage_metadata를 기록해 예상값과 차이를 측정합니다.
미들웨어 인스턴스 필드에 사용자별 값을 두면 동시 요청이 섞일 수 있습니다. 실제 서비스에서는 state, runtime context 또는 원자적 저장소를 사용합니다.
비용 상한 오류 메시지에 계정 잔액이나 내부 가격표 전체를 노출하지 않습니다.
실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.
8정리와 다음 절
BudgetMiddleware는 handler 호출 전에 예상비용을 예약하고 인스턴스의 누적 상한을 넘는 요청을 차단합니다.
같은 인스턴스에 두 invoke를 전달해 첫 요청만 모델에 도달하고 두 번째 요청은 호출 전에 차단됨을 확인했습니다.
운영에서는 예산 범위와 동시성에 맞게 누적값을 state, runtime context 또는 원자적 저장소에 분리합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 입력과 도구 호출을 비밀값 없이 추적하는 두 번째 커스텀 미들웨어를 만듭니다.

문제와 해설

해설 — 상한을 넘는 호출 자체를 실행하지 않기 위해서입니다.
2. 호출당 예상비용의 한계는 무엇인가요?
해설 — 실제 입력·출력 토큰과 캐시 조건에 따라 청구액이 달라질 수 있습니다.
3. 공유 인스턴스 필드가 운영에서 위험한 이유는 무엇인가요?
해설 — 여러 요청의 카운터가 섞여 사용자별 한도가 잘못 적용될 수 있습니다.
4. 내장 호출 한도와 커스텀 예산 미들웨어를 함께 쓸 수 있나요?
해설 — 가능하며 호출 수와 프로젝트별 비용 정책을 각각 검사할 수 있습니다.

1학습 목표
감사 로그와 디버그 로그의 목적을 구분할 수 있습니다.
에이전트 시작·도구 감싸기·종료 훅으로 이벤트를 기록할 수 있습니다.
원문 대신 해시와 유형만 남기는 최소 기록 원칙을 적용할 수 있습니다.
2이 내용을 배우는 이유
Ch16의 AuditLogger는 질문을 마스킹하고 소금값을 더한 해시, 이벤트 이름, 안전한 상세 정보만 JSONL에 기록했습니다. 에이전트에서는 한 요청 안에 여러 모델·도구 호출이 있으므로 시작, 도구, 종료를 같은 실행 식별자로 연결해야 합니다. 감사 미들웨어는 업무 함수에서 기록 코드를 분리합니다.
이 절의 질문 — 에이전트 전체와 도구 호출을 개인정보 없이 어떤 이벤트로 기록할까요?
3앞에서 배운 내용
Ch16 AuditLogger.record는 query_masked와 query_hash를 만들고 중첩된 문자열에도 mask_pii를 적용했습니다. 이번 절에서는 원문 질문 자체를 저장하지 않고 메시지 유형과 길이, 도구 이름, 성공 여부만 메모리 이벤트로 남깁니다. 실제 파일 저장은 운영 저장 정책과 접근 권한이 필요하므로 실습 범위에서 제외합니다.
4핵심 개념
비유로 시작하기
건물 출입 기록은 사람이 들고 있던 문서 내용을 복사하지 않고 출입 시각, 출입구, 승인 여부를 남깁니다. 감사 로그도 목적에 필요한 최소 정보만 기록해야 합니다. AuditMiddleware의 before_agent는 실행 시작, wrap_tool_call은 도구 이름과 성공·오류, after_agent는 종료를 기록합니다. 입력 지문은 고정 소금값과 실제 메시지 텍스트를 함께 해시한 학습용 예시이며 실제 운영에서는 키 관리와 보존 기간 정책이 필요합니다.
코드를 읽는 순서
감사 기록은 나중에 누가 어떤 실행을 했고 어느 단계가 호출됐는지 재구성하기 위한 이 예제의 가변 메모리 사건 목록입니다. AuditMiddleware는 에이전트·모델·도구 경계에서 이벤트를 EVENTS에 추가합니다. 각 항목의 event는 시점을, 해시는 원문을 저장하지 않고 같은 값인지 비교할 식별값을 나타냅니다. 해시만으로 원문을 복원하지는 못하지만 짧거나 예측 가능한 비밀은 대입 공격에 취약하므로 비밀 저장 수단으로 사용하면 안 됩니다.
직렬화 셀은 이벤트를 JSON으로 바꿔 필드와 순서를 검사합니다. sort_keys=True는 같은 딕셔너리를 일정한 문자열로 만드는 데 도움을 주며 시간 순서를 자동 보장하지 않습니다. 모델 호출과 도구 호출의 시작·완료를 구분해야 실패가 어느 경계에서 발생했는지 알 수 있습니다.
도식 읽기
파란 사용자 입력에서 노란 agent_start 이벤트를 만들되 원문 대신 길이와 지문만 남깁니다. 초록색 lookup_hours 전후에는 tool_start와 tool_success가 놓이고, 마지막 노란 agent_end는 메시지 수만 기록합니다. 도구 결과 본문과 이메일 원문은 어느 이벤트 상자에도 들어가지 않습니다.
5실행 예제
에이전트 시작·종료와 도구 호출 전후를 감사 이벤트로 남기는 미들웨어를 정의합니다. 도구를 한 번 호출한 뒤 이벤트 이름·순서·키를 출력하고, 입력 원문과 도구 반환 전문이 감사 기록에 없는지, 길이가 같은 다른 텍스트의 지문이 다른지 검사합니다.
확인할 점 — 이벤트가 실행 경계를 따라 기록되고 민감한 원문·도구 결과가 감사 레코드에 포함되지 않는지 확인합니다.
다른 상황과 적용 경계
운영 환경에서는 메모리 리스트 대신 접근 제어된 로그 저장소에 요청 ID, 실행 ID, 도구 이름, 성공 여부를 기록합니다. 입력 전문을 그대로 남기면 PII나 비밀값이 감사 로그에 복제될 수 있으므로 허용 필드 목록과 보존 기간을 먼저 정합니다.
관측성 로그는 성능과 오류를 분석하는 자료이고 감사 로그는 책임 있는 변경 이력을 증명하는 자료입니다. 같은 시스템에 저장할 수 있어도 접근 권한과 보존 규칙이 다릅니다. 이번 assert는 예상 이벤트 종류와 비밀 문자열 부재를 확인하지만 로그의 위변조 방지나 장기 보존을 검증하지 않습니다.
6실험 결과 해석
운영 시간 질문 한 건을 실행하면 agent_start, tool_start, tool_success, agent_end 순서의 네 이벤트가 남습니다. 이벤트에는 learner@example.com 원문이 없고 입력 길이와 짧은 지문만 있습니다. 길이가 같은 AA와 BB도 서로 다른 지문을 만듭니다. 도구 결과 본문도 기록하지 않습니다. 이 실험은 누락 없는 전체 감사 체계를 증명하지 않으며 선택한 훅에서 정한 네 이벤트만 확인합니다.
7주의할 점과 실무 메모
감사 로그에 전체 프롬프트와 도구 결과를 기본 저장하면 개인정보와 영업 정보가 복제될 수 있습니다.
해시는 익명화와 같지 않습니다. 입력 후보가 좁으면 대입 공격으로 원문을 추정할 수 있으므로 접근 통제와 소금 관리가 필요합니다.
after_agent는 정상 종료 경로입니다. 처리되지 않은 예외를 별도로 기록하려면 wrap 훅에서 오류 이벤트를 남기고 다시 raise합니다.
실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.
8정리와 다음 절
AuditMiddleware는 에이전트 시작·도구 성공 또는 오류·정상 종료를 선택한 훅에서 사건으로 기록합니다.
서로 길이가 같은 두 입력도 서로 다른 지문을 만들고, 예제 이벤트에 이메일 원문과 도구 결과가 없음을 확인했습니다.
짧은 해시와 메모리 목록은 익명화·위변조 방지·영구 보존을 제공하지 않으며 운영에서 키 관리와 접근 통제가 필요합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 여러 미들웨어를 한 목록에 넣었을 때 before, after, wrap의 순서를 실제 trace로 확인합니다.

다른 상황과 적용 경계
하나의 고객이 주문과 환불을 동시에 문의하면 업무별 분리가 오히려 연결 정보를 끊을 수 있습니다. 이런 경우 공통 고객 정보는 별도 컨텍스트로 제공하고, 업무별 대화만 선택하는 두 층 구조가 필요합니다. 단순 키워드 필터보다 생성 시점에 명시적 task_id를 붙이는 편이 경계를 확인하기 쉽습니다.
격리는 접근 통제와 같지 않습니다. 모델 입력에서 급여 문장을 뺐더라도 원본 상태나 로그를 읽을 권한이 그대로라면 보안 경계가 완성되지 않습니다. 이번 출력은 모델이 받은 다섯 문장이 세 문장으로 줄고 급여 문자열이 사라진 사실만 보여 줍니다.
