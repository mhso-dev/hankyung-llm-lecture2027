1학습 목표
한 모델 출력이 다음 모델 입력이 되는 체인을 직접 구현할 수 있습니다.
중간 결과의 필수 항목과 개수를 코드로 검사할 수 있습니다.
검사에 실패한 체인을 다음 호출 전에 중단할 수 있습니다.
2이 내용을 배우는 이유
한 번의 긴 프롬프트에 기획과 집필을 모두 맡기면 어느 단계에서 조건이 빠졌는지 찾기 어렵습니다. 프롬프트 체이닝(prompt chaining)은 일을 작은 단계로 나누고 앞 단계의 출력을 다음 단계의 입력으로 사용합니다. 단계가 늘면 호출 비용과 지연도 늘기 때문에 중간 결과를 후속 작업에 사용할 수 없다면 다음 호출을 막아야 합니다. 이 절의 질문은 ‘기획 결과에 독자와 단계가 빠졌을 때 비용을 쓰기 전에 어떻게 멈추는가?’입니다.
3앞에서 배운 내용
Ch 4에서 함수의 반환값을 다음 함수의 인자로 전달했고, Ch 16에서 호출 전에 입력과 비용을 검사했습니다. 여기서는 같은 파이썬 흐름 안에 실제 Responses API 호출을 두 번 연결합니다. LangChain이나 LangGraph는 사용하지 않습니다. OpenAI 클라이언트, responses.create(), response.output_text를 직접 확인합니다.
4핵심 개념
쉬운 예
기사 초고를 쓰기 전에 취재 메모를 확인하는 상황을 떠올려 봅니다. 메모에 제목만 있고 독자와 설명 순서가 없다면 초고를 쓰기 시작하지 않습니다. 빠진 항목을 채운 뒤에야 다음 작업에 전달합니다. 게이트는 이 확인표를 코드로 옮긴 것입니다.
정의
프롬프트 체이닝은 고정된 순서의 여러 모델 호출을 연결하는 패턴입니다. 중간 출력(intermediate output)은 다음 호출에 전달할 데이터이고, 게이트(gate)는 그 데이터가 정해 둔 조건을 만족하는지 검사하는 코드입니다. 이 실습의 outline_gate()는 title, audience, steps가 있으며 단계가 3개 이상인지 확인합니다. 모델이 판단한 품질 점수 대신 파이썬이 확인할 수 있는 형식을 기준으로 삼습니다.
도식 읽기
요청에서 기획 모델과 게이트로 내려갑니다. 게이트를 통과한 기획만 집필 모델에 전달하고, 조건에 맞지 않으면 추가 모델 호출 전에 중단합니다.
코드를 읽기 전에
이 장은 프레임워크가 패턴을 대신 구현하기 전의 흐름을 보기 위해 OpenAI Python SDK를 직접 사용합니다. OpenAI(...)는 동기 클라이언트를 만들고, client.responses.create(...)를 호출하는 순간 실제 네트워크 요청이 발생합니다. 반환된 응답 객체의 output_text는 모델이 만든 텍스트이고, usage는 성공 응답에 기록된 입력·출력 토큰입니다. call_json()은 JSON 텍스트를 파이썬 사전으로 바꾸며, JSON 객체라는 형식이 업무 필드의 완전성까지 보장하지는 않습니다.
outline_gate(data)는 사전을 입력받아 통과 여부와 누락 이유 목록을 반환합니다. Before에서는 첫 호출 뒤 게이트가 실패하므로 두 번째 모델 호출이 일어나지 않습니다. After에서는 검사한 기획만 문자열로 직렬화해 다음 호출에 전달합니다.
다른 상황과 개념 경계
번역 뒤 법률 용어 검사를 거쳐 요약하는 흐름에서도 중간 게이트를 둘 수 있습니다. 필수 용어 누락처럼 코드로 확인할 조건은 프로그램이 검사하고, 문체 자연스러움처럼 판단 기준이 필요한 조건은 별도 평가가 필요합니다. 게이트는 앞 단계의 오류가 다음 단계로 전파되는 것을 줄이지만, 통과한 내용의 사실 정확성을 자동으로 보장하지는 않습니다.

기본 실행은 완전한 예시 사전이 (True, [])를 반환하는지 먼저 확인합니다. Before에서는 실제 모델에 제목만 요청했습니다. 출력은 {'title': '비밀번호 재설정 안내'}였고, 게이트는 audience와 3개 이상의 steps가 부족하다고 판정했습니다. 다음 호출 수는 0이었습니다. After에서는 세 필드를 요청해 게이트를 통과했고, 검사된 기획으로 4문장 안내문을 생성했습니다. 성공한 SDK 응답은 3개였으며 반환 사용량과 2026-09-10 가격으로 계산한 추정 비용은 0.001007달러였습니다.
확인할 점 — Before의 누락 목록과 다음 호출 수: 0을 확인한 뒤, After에서 게이트 통과와 최종 answer가 함께 기록됐는지 확인합니다.
6일부러 실패해 보기
Before의 실패는 테스트 함수가 임의로 예외를 만든 결과가 아닙니다. 실제 첫 호출의 출력이 후속 단계에 필요한 정보를 담지 못한 상태입니다. 잘못된 방식은 사전에 빠진 키가 있어도 문자열로 바꾸어 다음 프롬프트에 넣는 것입니다. 수정한 방식은 누락 목록을 출력하고 두 번째 호출을 실행하지 않습니다. After에서는 같은 게이트를 유지하고 첫 프롬프트의 산출 형식만 명확히 했습니다.
7주의할 점과 실무 메모
게이트가 확인하는 것은 필드와 개수입니다. 단계 내용의 사실성이나 문장 품질까지 보장하지 않습니다.
max_retries=0으로 두어 표의 호출 수가 성공 응답 수와 일치하게 했습니다. 운영 환경에서 재시도를 켜면 HTTP 시도 횟수를 별도로 기록합니다.
추정 비용은 SDK가 반환한 사용량과 확인한 단가의 곱입니다. 제공자 청구서의 실제 결제 금액으로 표시하지 않습니다.

1학습 목표
모델 분류 결과를 전문 프롬프트에 연결할 수 있습니다.
허용되지 않은 분류와 낮은 신뢰도를 구분할 수 있습니다.
혼합 질문을 임의의 전문 경로로 보내지 않고 추가 구분을 요청할 수 있습니다.
2이 내용을 배우는 이유
결제 질문과 로그인 질문은 확인할 자료와 답변 순서가 다릅니다. 하나의 거대한 지원 프롬프트에 모든 규칙을 넣으면 서로 관계없는 규칙이 함께 작동할 수 있습니다. 라우팅(routing)은 먼저 질문의 범주를 고른 뒤 해당 범주의 지시만 사용합니다. 그러나 분류 모델도 unknown을 반환하거나 높은 신뢰도를 붙인 잘못된 분류를 반환할 수 있습니다. 이 절의 질문은 ‘전문 경로에 없는 분류값을 받았을 때 무엇을 반환해야 하는가?’입니다.
3앞에서 배운 내용
Ch 2에서 사전의 키로 값을 찾았고, Ch 16에서 허용 목록 밖의 출처를 거부했습니다. 같은 원리를 모델이 만든 분류값에 적용합니다. 분류 결과를 믿고 바로 prompts[category]로 접근하지 않고 허용 범주와 신뢰도 하한을 먼저 검사합니다.
4핵심 개념
쉬운 예
종합병원 접수 창구는 증상을 듣고 진료과를 안내합니다. 흉통과 다리 골절처럼 분명한 경우도 있지만 두 증상이 섞이거나 설명이 부족한 경우도 있습니다. 접수표에 없는 진료과 이름을 임의로 만들어 보내는 대신 필요한 정보를 다시 묻습니다.
정의
라우팅은 입력을 분류하고 정해 둔 후속 처리 가운데 하나를 선택하는 패턴입니다. 분류기(classifier)는 category와 confidence를 반환합니다. 허용 목록(allowlist)은 실제로 준비된 경로인 billing, account, technical만 담습니다. 폴백(fallback)은 분류 실패 시 사용하는 별도 처리이며, 이 실습에서는 로그인과 결제 중 먼저 확인할 문제를 선택해 달라고 요청합니다.
도식 읽기
분류 모델의 범주와 신뢰도를 코드에서 검사합니다. 허용 범주이고 신뢰도가 0.75 이상인 경우에만 전문 답변 모델을 호출합니다. 그 밖의 경우에는 추가 구분을 요청합니다.
코드를 읽기 전에
분류 호출은 category와 confidence를 담은 사전을 반환하도록 요청합니다. route(decision)은 범주가 허용 목록에 있는지 먼저 보고, 허용된 범주라면 float(confidence)로 값을 숫자로 변환해 0.75 이상인지 확인합니다. None이나 숫자로 바꿀 수 없는 문자열은 이 함수 안에서 별도 처리하지 않아 TypeError 또는 ValueError가 발생합니다. 반환값의 첫 항목이 None이면 범주 또는 신뢰도가 기준에 맞지 않아 전문 경로를 실행할 수 없다는 뜻입니다.
Before의 사전 조회는 모델 문자열을 곧바로 프로그램의 키로 사용해 KeyError를 만듭니다. After의 answer_ticket()은 실패를 숨기거나 임의 범주로 바꾸지 않고 추가 구분 질문을 반환합니다. 실제 모델 호출은 유효한 범주에서만 발생합니다.
다른 상황과 개념 경계
의료 예약 문의를 진료과로 보낼 때 ‘기타’를 내과로 자동 치환하면 처리 자체는 계속되지만 잘못된 경로가 조용히 실행됩니다. 이 경우 폴백은 기본 진료과가 아니라 증상·긴급도를 더 묻는 절차가 될 수 있습니다. 라우팅의 핵심은 분기 수가 많다는 데 있지 않고, 분류 실패가 어떤 상태로 보존되는지에 있습니다.
5실행 예제
실제 단일 의도 질문 ‘카드에서 같은 요금이 두 번 결제됐어요’는 billing, 신뢰도 0.98로 분류되어 결제 지원 경로로 이어졌습니다. 로그인 문제와 카드 청구를 함께 말한 질문은 unknown, 신뢰도 0.93이었습니다. 높은 신뢰도여도 허용 목록에 없는 범주이므로 라우터는 전문 경로를 선택하지 않았습니다. 지원 답변 호출까지 포함한 성공 응답은 3개였고 사용량 기준 추정 비용은 0.000603달러였습니다.
확인할 점 — unknown의 신뢰도가 높아도 허용 목록 검사에서 멈추고 needs_clarification이 반환되는지 확인합니다.
6일부러 실패해 보기
Before는 unknown을 그대로 prompts 사전의 키로 사용합니다. 이 키는 준비되지 않았으므로 실제 프로그램에서는 KeyError가 날 수 있습니다. After의 answer_ticket()은 범주와 신뢰도를 먼저 확인합니다. 분류가 유효하면 전문 모델을 호출하고, 그렇지 않으면 needs_clarification 상태와 한 문장의 구분 질문을 반환합니다. 혼합 질문을 결제나 계정 중 하나로 임의로 보내지 않았습니다.
7주의할 점과 실무 메모
신뢰도 수치는 모델의 자기 보고이며 실제 정답 확률과 같지 않습니다. 운영 전에는 라벨이 있는 자료로 임계값을 측정합니다.
두 문제가 함께 들어온 경우에는 둘 중 하나를 누락하지 않습니다. 요청을 둘로 나눌지, 먼저 처리할 대상을 물을지 서비스 정책으로 정합니다.
전문 경로는 분류값을 문자열로 이어 붙여 만들지 말고 코드에 등록한 이름으로만 선택합니다.

정의
병렬화(parallelization)는 서로 의존하지 않는 모델 호출을 겹치는 시간 동안 실행하는 패턴입니다. 섹셔닝(sectioning)은 한 과제를 독립 부분으로 나누고 각 부분에 다른 요청을 보냅니다. 투표(voting)는 같은 후보를 여러 평가자에게 보내 다양한 판정을 모읍니다. asyncio.gather()는 여러 awaitable을 함께 실행하고 입력한 순서대로 결과 목록을 반환합니다. 완료 순서와 반환 목록 순서는 구분해야 합니다.

코드를 읽기 전에
AsyncOpenAI는 비동기 클라이언트이며 await client.responses.create(...)에서 각 네트워크 응답을 기다립니다. asyncio.gather(*jobs)는 여러 코루틴을 함께 예약하고 모든 결과가 끝난 뒤 입력 순서의 목록을 반환합니다. 요청을 동시에 시작할 수 있다는 뜻이지 제공자 내부 처리 시간이나 완료 순서가 같다는 뜻은 아닙니다.
섹셔닝은 서로 의존하지 않는 목적·절차·지원 문단을 나눕니다. 투표는 같은 두 후보를 여러 평가 기준에 보냅니다. 전자는 결과를 합쳐 한 문서를 만들고, 후자는 판정 분포를 남긴다는 점에서 출력의 합치는 방식이 다릅니다.

4핵심 개념
쉬운 예
편집장은 들어온 기사의 성격을 보고 취재, 사실 확인, 도표 제작 중 필요한 담당을 정합니다. 모든 기사에 같은 세 담당자를 배정하지 않습니다. 편집장이 업무를 나눈 뒤 각 담당자가 동시에 일하고, 마지막에 편집장이 결과를 하나의 기사로 묶습니다.
정의
오케스트레이터(orchestrator)는 전체 과제를 읽고 하위 작업을 계획하며 결과를 종합하는 모델 역할입니다. 워커(worker)는 할당받은 범위만 처리합니다. 동적 분해(dynamic decomposition)는 하위 작업의 개수와 지시가 입력마다 달라지는 성질입니다. 이 실습은 오케스트레이터가 2~4개의 id와 instruction을 만들게 하고, 유효한 항목만 최대 4개까지 실행합니다. 2개보다 적으면 고정된 기본 목록으로 바꾸지 않고 오류를 숨기지 않은 채 중단합니다.
도식 읽기
오케스트레이터가 작업 목록을 만들면 코드가 유효한 작업 수를 검사합니다. 유효 작업이 두 개보다 적으면 중단하고, 통과하면 최대 네 개의 워커를 실행합니다. 워커 결과를 종합 모델에 전달합니다.
코드를 읽기 전에
오케스트레이터 호출은 전체 과제에서 id와 instruction 목록을 만듭니다. 프로그램은 tasks가 목록이라고 가정하고, 그 안에서 사전이며 id와 instruction 값이 모두 참인 항목을 골라 앞의 네 개만 사용합니다. ID 중복, 문자열 자료형, 40자 길이는 다시 검사하지 않습니다. 남은 항목이 두 개 미만일 때만 중단합니다. 선택된 항목마다 run_worker() 코루틴을 만들고 gather로 실행한 뒤 작업 ID와 결과를 종합 호출에 전달합니다.
동적이라는 말은 워커 함수가 실행 중 새 작업을 계속 만든다는 뜻이 아닙니다. 이 예제에서는 첫 모델 호출이 작업의 개수와 내용을 입력별로 정하고, 이후 코드는 그 유효한 목록만 실행합니다. 계획 검증 실패는 고정 목록으로 조용히 바꾸지 않고 중단합니다.

저장소 수정 요청은 변경할 파일 수가 입력마다 달라 오케스트레이터-워커에 맞을 수 있습니다. 월간 보고서처럼 항상 매출·고객·운영 세 절을 작성한다면 고정 병렬 섹셔닝이 더 직접적입니다. 두 패턴은 모두 병렬 실행할 수 있지만, 하위 작업 목록을 코드가 미리 정하는지 모델이 입력을 보고 정하는지가 경계입니다.

패턴 선택표를 다른 과제에 재사용하려면 입력, 출력 제한, 평가 기준을 새 과제에 맞춰 다시 고정해야 합니다. 분류가 분명한 문의에서는 라우팅이 유리할 수 있고, 하위 작업 수가 매번 달라지는 조사에서는 오케스트레이터가 필요할 수 있습니다. 이 절의 숫자를 그대로 옮기는 대신 반복 실행과 실패율을 추가해 구조가 주는 차이를 다시 측정합니다.

7주의할 점과 실무 메모
품질 기준이 다르면 순위도 바뀔 수 있습니다. 문장 미감, 사실 정확성, 사용자의 이해도는 이번 5점 기준에 포함되지 않습니다.

## 실행 환경과 비용 상한

## 코드를 읽기 전에
이 장은 프레임워크가 패턴을 대신 구현하기 전의 흐름을 보기 위해 OpenAI Python SDK를 직접 사용합니다. `OpenAI(...)`는 동기 클라이언트를 만들고, `client.responses.create(...)`를 호출하는 순간 실제 네트워크 요청이 발생합니다. 반환된 응답 객체의 `output_text`는 모델이 만든 텍스트이고, `usage`는 성공 응답에 기록된 입력·출력 토큰입니다. `call_json()`은 JSON 텍스트를 파이썬 사전으로 바꾸며, JSON 객체라는 형식이 업무 필드의 완전성까지 보장하지는 않습니다.
`outline_gate(data)`는 사전을 입력받아 통과 여부와 누락 이유 목록을 반환합니다. Before에서는 첫 호출 뒤 게이트가 실패하므로 두 번째 모델 호출이 일어나지 않습니다. After에서는 검사한 기획만 문자열로 직렬화해 다음 호출에 전달합니다.
### 다음 셀을 읽는 방법
`load_dotenv(find_dotenv(usecwd=True))`는 현재 폴더에서 위로 올라가며 `.env`를 찾아 환경 변수에 넣습니다. `OpenAI(timeout=45.0, max_retries=0)`는 동기 클라이언트를 만들며 아직 모델을 호출하지 않습니다. `calls`는 이후 성공 응답의 지연과 토큰 수를 모을 빈 목록입니다.

### 다음 셀을 읽는 방법

`cost_usd(records)`는 앞에서 모은 성공 응답의 입력·출력 토큰을 합산해 이 실습에 고정한 단가를 적용합니다. `score_of(data)`는 평가 점수가 불리언이 아닌 숫자이며 0~100 범위인지 확인한 뒤 정수로 반환합니다. 두 함수 모두 모델을 호출하지 않습니다.

# 병렬 섹셔닝과 투표

## 실행 환경과 비용 상한
