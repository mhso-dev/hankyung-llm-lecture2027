최종 응답, 한 단계, 전체 궤적 평가가 찾는 실패를 구분할 수 있습니다.

2이 내용을 배우는 이유
Final Response·Single step·Trajectory는 각각 어떤 실패를 발견하는가?
최종 답이 14일로 맞아도 search_rules를 세 번 반복하면 운영 비용과 장애 가능성이 커집니다. 답과 내부 행동을 서로 다른 평가 단위로 보아야 이런 실패를 찾을 수 있습니다.

4핵심 개념
정의와 구체 예
Final Response는 전체 실행을 블랙박스로 보고 마지막 답을 채점합니다. Single step은 특정 시점의 도구 선택이나 인자를 검사합니다. Trajectory는 시작부터 끝까지의 AIMessage와 ToolMessage 순서를 평가합니다. 세 전략은 서로 대체하지 않으며 발견하려는 실패에 따라 함께 사용합니다.
코드 읽기와 비교 경계
평가 단위는 평가 함수가 입력에서 어느 부분을 읽는지 정합니다. 최종 응답 평가는 마지막 AIMessage.text만 읽고, 한 단계 평가는 지정한 tool_calls의 이름이나 인자를 읽으며, 궤적 평가는 사용자 메시지부터 모든 AI·도구 메시지의 순서를 읽습니다. trace()는 실제 에이전트를 실행하는 함수가 아니라 비교용 메시지 목록을 만드는 보조 함수입니다. 따라서 이 절의 결과는 평가 전략의 차이를 재현하는 고정 예시입니다.
같은 실패도 평가 단위에 따라 보이거나 숨습니다. 도구를 네 번 호출해도 마지막 답이 맞으면 최종 응답 평가는 통과할 수 있습니다. 첫 도구가 맞아도 두 번째 단계에서 권한 없는 도구를 사용하면 한 단계 평가만으로는 놓칩니다. 반대로 궤적이 기준과 같아도 규정 원문이 오래되었다면 사실 오류는 남습니다. 운영 평가에서는 답의 사실성, 필수 단계, 금지 행동, 호출 효율을 각각 측정하고 어느 하나를 전체 품질 점수로 대신하지 않습니다.
도식 읽기
하나의 에이전트 실행에서 세 측정 상자가 나옵니다. Final Response는 마지막 문장, Single step은 첫 tool_calls, Trajectory는 모든 호출 순서를 읽습니다.

2이 내용을 배우는 이유
정답 경로가 여러 개일 때 strict·unordered·subset·superset 중 무엇을 선택해야 하는가?
올바른 경로가 여러 개인 문제에 strict를 적용하면 순서만 다른 정상 실행을 탈락시킵니다. 반대로 필수 순서가 있는 승인 절차에 unordered를 쓰면 위험한 순서도 통과합니다.

4핵심 개념
정의와 구체 예
strict는 메시지 구조와 도구 호출 순서가 기준과 같아야 합니다. unordered는 같은 호출을 순서와 무관하게 요구합니다. subset은 실제 호출이 기준 호출 범위 안에 있는지 보고 누락을 허용합니다. superset은 기준의 필수 호출을 실제 호출이 모두 포함하는지 보고 추가 호출을 허용합니다.
코드 읽기와 비교 경계
create_trajectory_match_evaluator(trajectory_match_mode=...)는 실제 궤적과 기준 궤적을 비교하는 함수를 만듭니다. 이 함수에 outputs와 reference_outputs를 넘기는 순간 평가가 실행되고 score를 포함한 사전이 반환됩니다. strict와 unordered는 두 궤적의 동등성을 서로 다른 순서 규칙으로 보고, subset과 superset은 실제 호출 집합을 기준 호출 집합과 어느 방향으로 포함하는지 봅니다.
포함 방향은 문장으로 확인하면 혼동이 줄어듭니다. subset은 실제 호출이 기준에 나온 도구 안에서만 이루어졌는지 묻기 때문에 필수 도구가 빠진 짧은 경로도 통과할 수 있습니다. superset은 실제 호출이 기준의 필수 도구를 모두 포함했는지 묻기 때문에 관련 없는 추가 호출도 통과할 수 있습니다. 승인 뒤 결제처럼 순서가 안전 조건이면 strict, 순서와 무관한 두 조회라면 unordered, 금지 도구 제한과 필수 도구 확인은 별도 규칙을 조합합니다.
도식 읽기
기준 궤적이 네 검사 상자로 들어갑니다. strict와 unordered는 동등성의 두 방식이고 subset과 superset은 포함 방향이 서로 반대입니다.

1학습 목표

2이 내용을 배우는 이유
정확 일치로 잡기 어려운 합리적 경로를 LLM judge가 어떻게 평가하는가?
도구 이름이 정확히 같아도 질문과 도구 인자의 의미가 어긋날 수 있습니다. 의미와 효율을 함께 읽으려면 루브릭을 받은 judge가 전체 메시지를 평가하는 방법이 필요합니다.
3앞에서 배운 내용
결정적 궤적 매칭을 사용합니다. 필요한 자료와 객체는 노트북에서 다시 선언하므로 앞 노트북의 메모리 상태는 필요하지 않습니다.
4핵심 개념
정의와 구체 예
LLM-as-judge는 다른 언어 모델이 평가 루브릭과 궤적을 읽고 점수와 설명을 반환하는 방식입니다. 이 노트북의 TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE는 단계의 논리, 진행, 상대적 효율, 기준 궤적과의 의미 동등성을 묻습니다. 결정적 매칭과 함께 쓰면 구조 차이와 의미 차이를 구분할 수 있습니다.
코드 읽기와 비교 경계
create_trajectory_llm_as_judge(...)는 평가용 모델과 루브릭 프롬프트를 묶은 평가 함수를 만듭니다. outputs=actual과 reference_outputs=reference를 전달하면 두 메시지 궤적을 텍스트로 구성해 실제 모델을 호출하고, 점수와 설명을 사전으로 반환합니다. 여기서 judge는 피평가 에이전트와 별개의 모델 호출입니다. 고정된 actual을 평가하더라도 judge의 문장이나 점수는 모델과 프롬프트에 따라 달라질 수 있습니다.
결정적 매칭과 judge는 역할이 다릅니다. 필수 도구 이름과 순서처럼 코드로 정확히 표현할 수 있는 규칙은 결정적 검사로 빠르고 재현 가능하게 확인합니다. 여러 합리적 경로의 의미나 불필요한 단계의 정도는 judge가 읽을 수 있지만, 루브릭에 없는 보안 규칙을 자동으로 발견한다고 기대해서는 안 됩니다. 이 예제는 실제와 기준을 동일하게 만들었으므로 두 평가가 모두 통과하는 기본 동작만 확인합니다. 다른 경로의 의미 차이를 비교하려면 별도의 대조 궤적이 필요합니다.
도식 읽기
코드로 만든 실제·기준 메시지 궤적과 평가 루브릭이 LLM judge에 함께 들어가고 trajectory_accuracy 점수와 comment가 나옵니다.

`strict`는 순서까지 같아야 하고 `unordered`는 같은 호출이 있으면 순서를 무시합니다. 두 결과를 같이 보면 요구 사항이 순서에 의존하는지 판단할 수 있습니다.

nearest-rank p95는 값을 정렬한 뒤 `ceil(0.95*n)`번째 값을 고릅니다. 표본이 세 개면 순위가 3이므로 p95는 항상 최댓값과 같습니다. 이는 계산 오류가 아니지만 꼬리 지연의 안정적인 분포를 추정하기에는 자료가 너무 적습니다. 평균과 p95를 함께 볼 때도 과제, 입력 길이, 실행 횟수, 모델 버전이 다른 집단을 직접 우열 비교하지 않습니다. 같은 서비스의 반복 실행을 일정 기간 모은 뒤 실패율과 사용자 수정 횟수도 함께 해석해야 합니다.
