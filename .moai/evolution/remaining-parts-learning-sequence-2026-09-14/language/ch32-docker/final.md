1학습 목표
이미지, 컨테이너, 레이어의 관계를 설명할 수 있습니다.
docker history와 docker diff로 읽기 전용 층과 쓰기 가능 층을 구분할 수 있습니다.
새 컨테이너가 이전 컨테이너의 임시 변경을 이어받지 않는 이유를 설명할 수 있습니다.
2이 내용을 배우는 이유
개발 컴퓨터에서 실행되던 서비스가 배포 환경에서 달라지는 이유는 코드만 옮겼기 때문입니다. 애플리케이션은 Python 버전, 설치한 패키지, 운영체제 파일과 함께 실행됩니다. Docker 이미지는 이 실행 조건을 순서가 있는 파일 시스템 층으로 기록합니다. 첫 절에서 이미지가 무엇을 저장하고 컨테이너가 무엇을 덧붙이는지 알아야 다음 절의 Dockerfile을 읽을 수 있습니다.
3앞에서 배운 내용
Ch 1에서 Docker 클라이언트가 데몬에 요청을 보내는 구조를 확인했습니다. 여기서는 설치 여부 확인을 넘어 실제 이미지를 빌드하고 임시 컨테이너를 만듭니다. Ch30의 서비스 구현이 아직 없어도 실습할 수 있도록 이 챕터 폴더의 app.py를 사용합니다. 이 서비스는 /health에 고정된 JSON을 반환하는 최소 FastAPI 애플리케이션입니다.
4핵심 개념
쉬운 예
택배 상자를 포장하는 과정을 떠올려 봅니다. 바닥 상자 위에 Python 실행 환경을 놓고, 그 위에 패키지와 소스 파일을 차례로 놓습니다. 아래 물건을 바꾸면 그 위의 포장도 다시 확인해야 합니다. Docker의 이미지 레이어(image layer)는 Dockerfile 명령이 만든 파일 시스템 변경분입니다. 이미지는 여러 읽기 전용 레이어와 실행 설정을 가리키는 식별 가능한 결과물입니다. 컨테이너(container)는 이미지를 실행하면서 맨 위에 쓰기 가능 레이어를 추가한 프로세스 환경입니다. 따라서 같은 이미지에서 시작한 두 컨테이너는 같은 바닥을 사용하지만 각자의 변경은 분리됩니다. docker history는 이미지가 어떤 명령과 크기 기록으로 구성됐는지 보여 주고, docker diff는 실행 뒤 컨테이너 파일 시스템에 생긴 추가·변경·삭제를 보여 줍니다. 이 둘을 함께 읽으면 빌드 시점의 변경과 실행 시점의 변경을 구분할 수 있습니다.
코드 읽기와 개념 경계
Dockerfile의 명령은 모두 이미지 기록에 남지만 역할은 다릅니다. RUN, COPY, ADD처럼 파일을 바꾸는 명령은 파일 시스템 레이어를 만들고, CMD와 HEALTHCHECK는 실행 기본값과 상태 검사 같은 이미지 메타데이터를 기록해 0B로 보일 수 있습니다. 이미지는 읽기 전용 레이어와 실행 설정을 담은 템플릿이고, 컨테이너는 그 위에 쓰기 가능한 층을 더한 실행 인스턴스입니다. docker build는 이미지를 만들고 docker run은 그 이미지에서 프로세스를 시작합니다.
컨테이너 안에서 파일을 바꿔도 원본 이미지는 변하지 않습니다. 반대로 Dockerfile을 고쳐 다시 빌드하면 새 이미지 식별자가 생깁니다. 영속 데이터는 컨테이너의 쓰기 층에만 두지 않고 볼륨이나 외부 저장소로 분리해야 컨테이너 교체 뒤에도 남습니다.
도식 읽기초록 상자는 이미지와 파일 데이터를 나타냅니다. 앞의 세 상자는 이미지에 포함되는 층이며, 마지막 상자는 컨테이너마다 따로 생기는 쓰기 가능한 층입니다. 화살표 순서로 각 층이 앞의 내용을 바탕으로 추가되는 관계를 읽습니다.
5실행 예제
노트북은 최적화 이미지를 만든 뒤 docker history로 상위 기록을 읽습니다. 이어서 임시 컨테이너 안의 /tmp/lesson.txt를 만들고 docker diff에서 해당 경로를 확인합니다. 마지막으로 같은 이미지에서 새 컨테이너를 만들면 그 파일이 없다는 사실을 검사합니다. 관찰 대상은 호스트 폴더가 아니라 컨테이너의 쓰기 가능 층입니다.
확인할 점 — 명령의 종료 코드와 실제 출력이 본문의 설명과 같은지 확인합니다. 실습 전용 이름을 사용했으므로 다른 Docker 자원을 변경하지 않습니다.
6실험 결과 해석
실행 결과에는 이미지 기록이 다섯 줄 이상 나타났고, 첫 임시 컨테이너의 변경 목록에는 /tmp/lesson.txt가 포함됐습니다. 새 컨테이너에서 같은 경로를 검사한 값은 False였습니다. 이 결과는 실행 중 만든 파일이 원본 이미지로 역전파되지 않음을 보여 줍니다. 레이어 행의 크기를 모두 더한 값은 이미지의 저장 공간과 정확히 같지 않을 수 있습니다. 여러 이미지가 같은 레이어를 공유할 수 있고, 표시 방식도 명령에 따라 다르기 때문입니다. 이 실험은 현재 로컬 Docker 저장소에서 보이는 기록을 설명하며 레지스트리 전송량을 측정하지 않습니다.
7주의할 점과 실무 메모
컨테이너 안에 수동으로 설치한 패키지는 Dockerfile에 기록되지 않습니다. 컨테이너를 삭제하면 재현 근거도 사라지므로 필요한 변경은 Dockerfile에 적습니다.
데이터베이스 데이터처럼 실행 뒤에도 남겨야 하는 값은 이미지 레이어에 저장하지 않습니다. 4절에서 이름 있는 볼륨을 사용합니다.
이미지 태그는 사람이 읽는 별칭입니다. 같은 태그가 다른 digest를 가리킬 수 있으므로 배포 재현성이 중요한 곳에서는 digest 고정을 검토합니다.
8정리와 다음 절
이미지는 빌드 결과를 읽기 전용 레이어로 보관합니다.
컨테이너는 이미지 위에 분리된 쓰기 가능 층을 추가합니다.
history와 diff는 빌드 기록과 실행 변경을 서로 다른 관점에서 보여 줍니다.
다음 학습과 이어지는 지점 — 2절에서는 어떤 레이어를 최종 이미지에 남길지 uv 멀티스테이지 빌드로 선택합니다.
9복습 문제
문제 1
이미지와 컨테이너의 차이를 한 문장으로 설명해 보세요.
정답과 해설 — 이미지는 실행 조건을 담은 읽기 전용 결과물이고, 컨테이너는 그 이미지에 쓰기 가능 층과 실행 중인 프로세스를 더한 인스턴스입니다.
문제 2
임시 컨테이너의 파일이 새 컨테이너에 보이지 않은 이유는 무엇인가요?
정답과 해설 — 각 컨테이너의 쓰기 가능 층이 분리되어 있고 원본 이미지 레이어는 바뀌지 않았기 때문입니다.
문제 3
docker history와 docker diff는 각각 무엇을 관찰하나요?
정답과 해설 — history는 이미지 빌드 기록을, diff는 특정 컨테이너가 실행 중 파일 시스템에 만든 변경을 관찰합니다.
문제 4
DB 데이터를 컨테이너 쓰기 층에만 두면 어떤 문제가 생기나요?
정답과 해설 — 컨테이너를 교체하거나 삭제할 때 데이터가 함께 사라질 수 있습니다. 영속 데이터는 볼륨에 둡니다.

textbook/part7/ch32-docker/_src/02-uv-멀티스테이지-빌드.html

1학습 목표
멀티스테이지 빌드에서 builder와 runtime의 역할을 구분할 수 있습니다.
uv 잠금 파일로 재현 가능한 의존성 환경을 만들 수 있습니다.
최종 이미지에서 빌드 도구를 제외했는지 실행으로 확인할 수 있습니다.
2이 내용을 배우는 이유
Python 서비스는 실행에 필요한 패키지와 패키지를 설치하는 도구가 다릅니다. 설치기, 컴파일러, 캐시를 모두 최종 이미지에 남기면 배포 파일이 커지고 점검할 대상도 늘어납니다. Docker의 멀티스테이지 빌드는 의존성을 준비하는 환경과 서비스를 실행하는 환경을 한 Dockerfile 안에서 나눕니다. uv 잠금 파일을 함께 사용하면 어떤 버전을 설치했는지도 고정할 수 있습니다.
3앞에서 배운 내용
1절에서 아래 레이어가 바뀌면 위 레이어도 영향을 받는 구조를 확인했습니다. 이제 pyproject.toml과 uv.lock을 앱 코드보다 먼저 복사합니다. Ch30에서 만든 서비스가 있다면 같은 패턴에 프로젝트 파일을 연결할 수 있습니다. 이 절의 app.py는 독립된 최소 서비스이므로 아직 작성 중인 Ch30 파일을 요구하지 않습니다.
4핵심 개념
쉬운 예
공방과 매장을 나누어 생각해 봅니다. 공방에는 절단기와 포장 장비가 필요하지만 손님에게 전달하는 상품 상자에는 완성품만 들어갑니다. 멀티스테이지 빌드(multi-stage build)는 Dockerfile 안에 FROM을 여러 번 사용해 각 작업 환경을 구분합니다. builder 단계는 uv와 Python으로 .venv를 만들고, runtime 단계는 작은 Python 기반 이미지에 .venv와 app.py만 복사합니다. COPY --from=builder가 두 단계 사이의 명시적인 통로입니다. uv는 uv sync --locked로 잠금 파일과 일치하는 환경을 만들며, --no-dev는 개발 전용 의존성을 제외합니다. BuildKit의 cache mount는 다운로드 캐시를 레이어 파일로 굳히지 않으면서 다음 빌드에 재사용하게 합니다. 최종 단계는 비관리자 course 사용자로 실행해 애플리케이션 프로세스의 권한 범위를 줄입니다.
코드 읽기와 개념 경계
멀티스테이지 Dockerfile은 여러 FROM으로 빌드 단계와 실행 단계를 나눕니다. AS builder는 앞 단계를 이름 붙이고, COPY --from=builder는 그 단계에서 필요한 가상환경이나 산출물만 최종 단계로 복사합니다. uv와 컴파일 도구는 빌드에 필요하지만 서비스 실행에는 필요하지 않을 수 있으므로 최종 이미지에서 제외합니다.
단계를 나누는 목적은 줄 수를 늘리는 것이 아니라 최종 런타임의 책임을 줄이는 데 있습니다. 디버깅 도구까지 제거하면 운영 이미지는 작아지지만 장애 조사 방식도 달라집니다. 빌드 단계와 실행 단계의 Python 버전·플랫폼이 다르면 복사한 바이너리 패키지가 동작하지 않을 수 있으므로 같은 호환 조건을 사용합니다.
도식 읽기왼쪽 두 상자는 빌드에만 필요한 단계입니다. 마지막 runtime 상자에는 실행에 필요한 가상환경과 앱 파일만 이어집니다.
5실행 예제
기본 실행은 Dockerfile로 ch32-optimized:local을 빌드합니다. 컨테이너 안의 Python 3.12는 정상 실행되지만 command -v uv는 실패해야 합니다. 실패 확인에서는 존재하지 않는 buidler stage를 지정해 Docker가 대상 이름을 찾지 못하는 실제 오류를 관찰합니다. 수정 셀은 정확한 builder를 대상으로 빌드하고 /app/.venv/bin/uvicorn이 있는지 검사합니다.
확인할 점 — 명령의 종료 코드와 실제 출력이 본문의 설명과 같은지 확인합니다. 실습 전용 이름을 사용했으므로 다른 Docker 자원을 변경하지 않습니다.
6일부러 실패해 보기
오타가 든 stage 이름은 0이 아닌 종료 코드를 반환했습니다. 같은 Dockerfile에서 builder로 고치자 가상환경 실행 파일 검사가 성공했습니다. 이는 stage 이름이 단순한 설명이 아니라 --target과 COPY --from이 참조하는 식별자임을 보여 줍니다. 최종 runtime 이미지에서 uv 명령이 없다는 사실은 이 예제의 분리 결과를 증명합니다. 빌드 도구가 없다고 해서 이미지가 자동으로 안전해지는 것은 아닙니다. 기반 이미지와 설치 패키지의 취약점, 실행 사용자, 업데이트 정책은 별도로 관리해야 합니다.
7주의할 점과 실무 메모
공식 uv 문서는 .venv를 .dockerignore에 넣고 컨테이너 안에서 새로 만들 것을 권합니다. 호스트 가상환경은 운영체제와 CPU에 의존할 수 있습니다.
태그만 고정하면 태그가 이동할 가능성은 남습니다. 높은 재현성이 필요한 배포에서는 기반 이미지와 uv 이미지의 digest 고정을 검토합니다.
Alpine은 항상 가장 좋은 선택이 아닙니다. Python 바이너리 휠 호환성과 운영 도구를 확인한 뒤 Debian slim 같은 기반 이미지와 비교합니다.
8정리와 다음 절
builder는 의존성을 준비하고 runtime은 서비스를 실행합니다.
잠금 파일을 먼저 복사하면 의존성 레이어를 앱 코드 변경과 분리할 수 있습니다.
최종 이미지에 uv가 없는지 실제 컨테이너에서 확인했습니다.
다음 학습과 이어지는 지점 — 3절에서는 같은 앱을 한 단계 기준 이미지와 멀티스테이지 이미지로 빌드해 크기와 캐시 기록을 측정합니다.
9복습 문제
문제 1
COPY --from=builder의 역할은 무엇인가요?
정답과 해설 — builder 단계에서 만든 선택된 파일을 현재 stage로 복사합니다.
문제 2
uv.lock을 pyproject.toml과 함께 먼저 복사하는 이유는 무엇인가요?
정답과 해설 — 앱 코드만 바뀌었을 때 의존성 설치 레이어의 캐시를 유지하기 위해서입니다.
문제 3
최종 이미지에서 uv가 없음을 왜 검사하나요?
정답과 해설 — 빌드 전용 도구가 runtime에 포함되지 않았다는 설계 결과를 확인하기 위해서입니다.
문제 4
비관리자 사용자로 실행하는 이유는 무엇인가요?
정답과 해설 — 프로세스가 침해되었을 때 컨테이너 안에서 행사할 수 있는 권한을 줄이기 위해서입니다.

1학습 목표
캐시 무효화가 뒤따르는 레이어에 미치는 영향을 설명할 수 있습니다.
docker image inspect로 두 이미지 크기를 같은 단위에서 비교할 수 있습니다.
이미지 크기 감소와 서비스 동작 유지를 함께 검증할 수 있습니다.
2이 내용을 배우는 이유
이미지가 실행된다는 사실만으로 배포 준비가 끝나지 않습니다. 큰 이미지는 네트워크 전송과 저장에 더 많은 자원을 사용하고, 불필요한 도구는 점검 범위를 넓힙니다. 그러나 크기 숫자만 줄이다가 실행 파일이나 인증서까지 빼면 서비스가 실패할 수 있습니다. 이 절에서는 같은 앱을 두 방식으로 빌드하고 크기, 캐시, 동작을 한 묶음으로 확인합니다.
3앞에서 배운 내용
2절의 최적화 Dockerfile은 잠금 파일과 앱 코드를 다른 COPY 명령으로 나눴습니다. 비교 대상인 Dockerfile.baseline은 전체 폴더를 먼저 복사하고 한 단계 안에서 빌드 도구와 uv 환경을 모두 남깁니다. 두 파일은 같은 app.py, pyproject.toml, uv.lock을 사용하므로 애플리케이션 기능은 고정됩니다.
4핵심 개념
쉬운 예
주방에서 자주 쓰는 재료를 먼저 준비해 두면 주문마다 처음부터 손질하지 않아도 됩니다. Docker 빌드 캐시(build cache)는 이전 명령의 입력이 같을 때 결과 레이어를 재사용합니다. COPY 대상 파일이 바뀌거나 RUN 명령이 바뀌면 해당 단계의 캐시가 무효화되고 뒤 단계도 다시 계산됩니다. 그래서 변경 빈도가 낮은 잠금 파일을 먼저 복사하고, 자주 바뀌는 앱 코드를 뒤에 복사합니다. 이미지 크기는 docker image inspect의 .Size 값을 바이트로 읽어 같은 Docker 데몬에서 비교합니다. 이 값은 현재 플랫폼의 로컬 이미지 크기이며 레지스트리 압축 전송량과 같지 않습니다. .dockerignore는 빌드 문맥에서 .venv, 노트북, 비밀 파일을 제외해 전송량과 우발적 포함 위험을 줄입니다.
코드 읽기와 개념 경계
Docker 빌드 캐시는 명령과 그 명령이 의존하는 파일이 같을 때 이전 레이어를 재사용합니다. 어느 COPY가 바뀌면 그 단계뿐 아니라 뒤의 단계도 다시 실행됩니다. 그래서 자주 바뀌지 않는 의존성 잠금 파일을 먼저 복사해 설치하고, 자주 바뀌는 애플리케이션 소스는 뒤에서 복사합니다. 출력의 CACHED는 해당 빌드에서 재사용된 단계의 관찰값입니다.
캐시 적중 수와 이미지 크기는 서로 다른 지표입니다. 캐시가 많아도 최종 이미지가 클 수 있고, 멀티스테이지로 작은 이미지를 만들어도 첫 빌드는 오래 걸릴 수 있습니다. 비교할 때는 같은 빌드 컨텍스트와 플랫폼을 사용하고, --no-cache와 --pull이 각각 단계 재실행과 새 베이스 확인이라는 다른 역할임을 구분합니다.
도식 읽기앞쪽 잠금 파일 레이어가 유지되면 앱 코드 변경은 뒤쪽 COPY부터 영향을 줍니다. 마지막 상자는 이번 arm64 환경에서 측정한 실제 크기입니다.
5실행 예제
노트북은 기준 이미지와 최적화 이미지를 차례로 빌드합니다. 측정값은 기준 418,111,662바이트, 최적화 57,560,686바이트였고 감소율은 약 86.2%였습니다. 이어서 최적화 이미지를 같은 입력으로 다시 빌드해 CACHED 표시를 세 번 이상 확인합니다. 마지막으로 두 이미지 모두에서 health() 함수를 호출해 같은 JSON을 반환하는지 검사합니다.
확인할 점 — 명령의 종료 코드와 실제 출력이 본문의 설명과 같은지 확인합니다. 실습 전용 이름을 사용했으므로 다른 Docker 자원을 변경하지 않습니다.
6실험 결과 해석
최적화 이미지는 기준 이미지의 절반보다 작다는 과제 기준을 충족했습니다. 이번 차이는 큰 Debian 기반 이미지와 빌드 환경을 남긴 기준 방식, slim runtime과 선택 복사를 사용한 최적화 방식이 함께 만든 결과입니다. 따라서 멀티스테이지만의 순수 효과로 해석할 수는 없습니다. 또한 한 차례의 반복 빌드에서 CACHED 표시가 나온 것은 입력이 같을 때 재사용됐음을 보여 주지만 여러 빌드 서버의 공유 캐시 성능을 나타내지 않습니다. 기능 검사는 /health의 Python 함수 수준이며 4절에서 실제 HTTP와 DB 연결까지 확인합니다.
7주의할 점과 실무 메모
이미지 크기 목표는 서비스에 따라 정합니다. 절대 크기보다 이전 기준과 감소 이유, 기능 회귀 여부를 함께 기록합니다.
--no-cache는 깨끗한 재검증에 유용하지만 매 빌드의 기본값으로 사용하면 캐시 이점을 잃습니다. 기반 이미지를 새로 받을 때는 --pull의 의미도 구분합니다.
비밀값은 이전 레이어에서 삭제해도 이미지 기록에 남을 수 있습니다. 빌드 시크릿 mount나 Compose 시크릿을 사용하고 COPY 대상에서 제외합니다.
8정리와 다음 절
캐시는 명령과 파일 입력이 같을 때 이전 결과를 재사용합니다.
현재 arm64 환경에서 최적화 이미지는 418.1MB에서 57.6MB로 감소했습니다.
크기 감소와 함께 두 이미지의 기본 서비스 동작도 확인했습니다.
다음 학습과 이어지는 지점 — 4절에서는 최적화 이미지를 PostgreSQL과 연결해 여러 컨테이너를 하나의 Compose 스택으로 관리합니다.

1학습 목표
Compose 서비스, 네트워크, 볼륨의 역할을 설명할 수 있습니다.
app과 PostgreSQL 사이의 준비 순서를 healthcheck로 제어할 수 있습니다.
pgvector 확장과 HNSW 인덱스 생성을 SQL로 확인할 수 있습니다.
2이 내용을 배우는 이유
웹 API 하나만 실행해도 실제 서비스는 데이터베이스, 네트워크, 영속 저장소를 함께 사용합니다. 명령을 각각 기억하면 이름과 포트가 서로 어긋날 수 있습니다. Docker Compose는 여러 컨테이너의 구성을 YAML 파일 하나에 적고 하나의 프로젝트로 관리합니다. Ch31의 데이터베이스 운영 개념을 실제 서비스 구성에 연결하는 단계입니다.
3앞에서 배운 내용
Ch31에서는 PostgreSQL, 트랜잭션, 인덱스와 pgvector를 배웁니다. 이 챕터는 Ch31 파일을 복사하지 않고 init.sql에 필요한 최소 스키마를 독립적으로 제공합니다. Ch12에서 사용한 벡터 검색 개념은 vector(3) 열과 HNSW 인덱스로 다시 나타납니다. 3절의 최적화 이미지는 Compose의 app 서비스 빌드 입력이 됩니다.
4핵심 개념
쉬운 예
공연 무대에는 배우뿐 아니라 조명, 음향, 출입 순서가 필요합니다. Compose 서비스(service)는 함께 관리할 컨테이너 하나의 설정입니다. 이 실습에는 app과 db 두 서비스가 있습니다. Compose는 프로젝트 전용 기본 네트워크를 만들고 서비스 이름 db를 내부 호스트 이름으로 제공합니다. app은 호스트의 localhost가 아니라 db:5432로 PostgreSQL에 연결합니다. 이름 있는 볼륨(named volume) pgdata는 DB 컨테이너를 다시 만들어도 데이터를 별도로 보관합니다. depends_on.condition: service_healthy는 DB 프로세스가 생성되었다는 사실을 넘어 pg_isready 검사가 성공할 때까지 app 시작을 기다립니다. 초기 SQL은 vector 확장, 3차원 벡터 열, HNSW 인덱스와 한 행의 예제 데이터를 만듭니다.
코드 읽기와 개념 경계
Compose는 여러 컨테이너의 이미지, 네트워크, 볼륨, 환경 값을 하나의 YAML에 선언합니다. 서비스 이름 db는 Compose 네트워크 안에서 호스트 이름으로 사용되므로 애플리케이션은 로컬호스트가 아니라 db로 PostgreSQL에 연결합니다. depends_on과 healthcheck 조건은 시작 순서를 돕지만 데이터베이스가 모든 업무 요청을 받을 준비가 됐는지는 애플리케이션 재시도와 readiness로 다시 확인합니다.
docker compose down은 컨테이너를 내리지만 기본적으로 이름 있는 볼륨의 데이터는 남깁니다. --volumes를 붙이면 실습 데이터도 제거됩니다. 개발 환경의 편리한 초기화와 운영 데이터 보존은 요구가 반대이므로 같은 종료 명령을 그대로 사용하지 않습니다.
도식 읽기호스트 요청은 공개한 18332 포트로 app에 들어갑니다. app과 db는 Compose 내부 네트워크에서 서비스 이름으로 통신하고 DB 파일은 pgdata 볼륨에 저장됩니다.
5실행 예제
먼저 docker compose config --format json으로 실제 컨테이너를 만들기 전에 서비스 이름을 검사합니다. 실패 셀은 스택이 없는 상태에서 /ready 연결이 거부되는지 확인합니다. 수정 셀은 up --build --wait로 두 서비스를 만들고 /ready와 /vector-count를 호출합니다. DB 안에서는 pgvector 0.8.6과 course_vectors_embedding_hnsw 인덱스를 직접 조회합니다. 실습 끝에는 down --volumes로 이 챕터 전용 데이터만 제거합니다.
확인할 점 — 명령의 종료 코드와 실제 출력이 본문의 설명과 같은지 확인합니다. 실습 전용 이름을 사용했으므로 다른 Docker 자원을 변경하지 않습니다.
6일부러 실패해 보기
실제 실행에서 db가 먼저 healthy가 되었고 app도 이어서 healthy가 되었습니다. /ready는 status=ready, /vector-count는 1을 반환했습니다. SQL 조회에서는 pgvector 0.8.6과 기본 키, HNSW 인덱스가 확인됐습니다. 이 구성은 시작 순서를 안정화하지만 실행 중 DB 연결이 끊겼을 때 app이 자동으로 모든 요청을 복구한다는 뜻은 아닙니다. 연결 재시도, 트랜잭션 경계, 마이그레이션 동시 실행은 Ch31의 운영 설계와 함께 결정해야 합니다.
7주의할 점과 실무 메모
호스트 포트는 127.0.0.1:18332로 제한했습니다. DB 포트는 호스트에 공개하지 않아 app을 통해서만 접근합니다.
초기화 SQL은 새 볼륨을 처음 만들 때 실행됩니다. 이미 데이터가 있는 볼륨의 스키마 변경은 Alembic 같은 마이그레이션 도구로 관리합니다.
down --volumes는 이 실습 데이터까지 삭제합니다. 운영 데이터가 있는 프로젝트에서는 실행 전에 프로젝트명과 볼륨 대상을 반드시 확인합니다.
8정리와 다음 절
Compose는 app, db, 네트워크와 볼륨을 한 프로젝트로 관리합니다.
service_healthy 조건은 DB 준비 검사가 성공한 뒤 app을 시작하게 합니다.
실제 스택에서 pgvector 0.8.6, HNSW 인덱스와 한 개의 벡터 행을 확인했습니다.
다음 학습과 이어지는 지점 — 5절에서는 같은 스택의 환경변수, 시크릿, 상태 검사와 로그를 운영자가 읽을 수 있는 신호로 정리합니다.

일반 설정과 비밀값에 서로 다른 전달 방식을 적용할 수 있습니다.
liveness와 readiness 상태 검사의 목적을 구분할 수 있습니다.
Compose 로그에서 요청과 오류 유형을 확인하고 비밀값 노출 여부를 검사할 수 있습니다.
2이 내용을 배우는 이유
컨테이너가 시작되었다는 사실과 사용자 요청을 처리할 준비가 됐다는 사실은 다릅니다. 또한 DB 주소 같은 설정과 비밀번호 같은 비밀값을 같은 방식으로 다루면 디버깅 출력에 비밀이 나타날 수 있습니다. 배포 자동화로 넘어가기 전에 설정, 상태, 로그가 운영자에게 어떤 신호를 주는지 명확히 정해야 합니다.
3앞에서 배운 내용
4절에서 app과 db를 연결했고 Compose가 두 서비스의 상태를 기다리는 것을 확인했습니다. app.py의 read_secret()은 DB_PASSWORD_FILE이 있으면 파일 내용을 읽고, 로컬 학습에서만 환경변수 값을 대체 경로로 사용합니다. /health는 프로세스의 HTTP 응답을, /ready는 DB 쿼리 가능 여부를 검사합니다.
4핵심 개념
쉬운 예
건물 안내판에는 공개해도 되는 층 정보가 적히고, 출입 키는 잠긴 보관함에서 필요한 사람에게만 전달됩니다. 환경변수(environment variable)는 DB 호스트나 로그 수준처럼 실행 환경에 따라 바뀌는 일반 설정을 전달하기 좋습니다. 시크릿(secret)은 비밀번호와 API 키처럼 노출되면 안 되는 값입니다. Compose 시크릿은 허용한 서비스의 /run/secrets/<name> 파일로 제공됩니다. 설정 화면과 프로세스 목록에 값이 직접 나타날 가능성을 줄이지만, 개발용 Compose의 파일 원본 보안은 운영자가 별도로 관리해야 합니다. liveness 검사는 프로세스가 응답하는지 확인하고, readiness 검사는 의존 서비스까지 포함해 요청을 받을 준비가 됐는지 확인합니다. 로그는 표준 출력과 표준 오류에 구조가 드러나는 사건을 기록합니다. 비밀값, 전체 인증 헤더, 사용자 원문은 기록하지 않습니다.
코드 읽기와 개념 경계
환경변수는 일반 설정을 전달하기 편하지만 프로세스 정보와 디버그 출력에 노출될 수 있습니다. Compose secret은 허용된 서비스에 파일로 마운트되며, 예제의 DB_PASSWORD_FILE은 /run/secrets/db_password 경로를 가리킵니다. 애플리케이션은 경로 문자열이 아니라 그 파일의 내용을 읽어 인증에 사용합니다.
liveness는 프로세스가 응답할 수 있는지, readiness는 현재 실제 트래픽을 받을 준비가 됐는지 확인합니다. 데이터베이스 주소를 틀린 컨테이너가 /health 200과 /ready 503을 함께 반환하는 이유입니다. 이번 실습은 두 HTTP 상태와 Compose가 표시한 health 상태까지만 확인합니다. 자동 재시작과 트래픽 제외는 배포 오케스트레이터가 이 신호에 별도 정책을 연결할 때 동작하며, healthcheck 자체가 두 행동을 보장하지 않습니다. 로그에는 요청 식별자를 남기되 비밀값을 출력하지 않습니다.
도식 읽기초록 상자의 환경변수와 시크릿을 파란 상자의 앱 실행에 전달합니다. 앱에서 갈라지는 두 화살표는 노란 상자의 상태 코드와 로그를 각각 확인하는 경로입니다. 상태 코드를 먼저 만들어야 로그가 생긴다는 뜻은 아닙니다.
5실행 예제
노트북은 정규화한 Compose 설정에서 DB_PASSWORD_FILE에 /run/secrets/db_password 경로가 있는지 확인합니다. 실패 셀은 DB 호스트를 missing으로 지정한 단독 app을 실행해 /health의 200과 /ready의 503을 함께 확인합니다. 수정 셀은 정상 Compose 스택을 실행하고 app과 db의 Compose 상태와 /ready의 200을 따로 검사합니다. Dockerfile의 app healthcheck는 /health만 호출하므로 Compose의 app healthy 표시는 DB 준비 상태를 포함하지 않습니다. 마지막으로 /vector-count 요청 로그가 있고 공개 예제 비밀번호 문자열은 로그에 없음을 확인합니다.
확인할 점 — 명령의 종료 코드와 실제 출력이 본문의 설명과 같은지 확인합니다. 실습 전용 이름을 사용했으므로 다른 Docker 자원을 변경하지 않습니다.
6일부러 실패해 보기
잘못된 DB 호스트를 사용한 app은 liveness 200과 readiness 503을 동시에 반환했습니다. 이는 프로세스 자체는 응답하지만 DB를 사용하는 요청을 처리할 준비가 안 됐음을 호출자에게 알립니다. 정상 스택에서는 app과 db가 모두 healthy였고 /ready도 200을 반환했습니다. 요청 로그에는 경로와 상태가 남았습니다. replace-this 문자열은 최근 로그에 나타나지 않았습니다. 이 검사는 해당 로그 범위의 비노출만 보여 줍니다. 애플리케이션 예외 처리, 프록시, 외부 관측 도구까지 포함한 전체 시스템의 비밀 보호를 보장하지 않습니다.
7주의할 점과 실무 메모
저장소의 secrets/db_password.txt.example은 공개 실습용 값입니다. 운영 비밀번호로 사용하지 않고 실제 파일은 버전 관리 밖에서 권한을 제한합니다.
상태 검사는 빠르고 부작용이 없어야 합니다. readiness에서 무거운 벡터 검색을 수행하면 검사 자체가 DB 부하를 만들 수 있습니다.
docker compose logs --tail과 --since로 관찰 범위를 제한합니다. 장애 분석에는 시간, 서비스명, 요청 식별자와 오류 유형을 남기되 비밀값과 개인정보는 제외합니다.
8정리와 다음 절
일반 설정은 환경변수로, 비밀값은 서비스별 시크릿 파일로 전달했습니다.
liveness는 HTTP 프로세스, readiness는 DB 연결까지 확인합니다.
로그에서 요청을 확인하고 예제 비밀번호 문자열이 출력되지 않았음을 검사했습니다.

# 이미지와 레이어
Docker Desktop의 실습 전용 이미지와 스택만 사용해 결과를 확인합니다.
## 실행 환경 준비
Docker 데몬의 버전을 확인하고 공통 명령 함수를 준비합니다.
### 이 준비 셀이 하는 일
이 준비 셀은 현재 폴더와 부모 폴더에서 `Dockerfile.baseline`이 있는 Ch32 실습 폴더를 찾습니다. `run(*args, check=True)`은 모든 Docker 명령을 그 폴더에서 실행하고 표준 출력·오류와 종료 코드를 `CompletedProcess`로 반환합니다. 실패 자체를 관찰하는 셀만 `check=False`를 전달하며, 마지막에는 Docker Engine이 응답하는지 확인합니다.
## 이미지의 읽기 전용 레이어 관찰
최적화 이미지의 기록을 크기와 명령으로 읽습니다.
### 바로 다음 코드를 읽는 방법
Dockerfile의 명령은 모두 이미지 기록에 남지만 역할은 다릅니다. `RUN`, `COPY`, `ADD`처럼 파일을 바꾸는 명령은 파일 시스템 레이어를 만들고, `CMD`와 `HEALTHCHECK`는 실행 기본값과 상태 검사 같은 메타데이터를 기록해 0B로 보일 수 있습니다. 이미지는 읽기 전용 레이어와 실행 설정을 담은 템플릿이고, 컨테이너는 그 위에 쓰기 가능한 층을 더한 실행 인스턴스입니다.
## 컨테이너의 쓰기 가능 층 확인
같은 이미지에서 만든 두 컨테이너의 변경은 서로 공유되지 않습니다.
## 실험 결과 해석
이미지 기록과 컨테이너 변경 기록은 서로 다른 범위를 보여 줍니다.
### 이 단계에서 구분할 범위
컨테이너 안에서 파일을 바꿔도 원본 이미지는 변하지 않습니다. 반대로 Dockerfile을 고쳐 다시 빌드하면 새 이미지 식별자가 생깁니다. 영속 데이터는 컨테이너의 쓰기 층에만 두지 않고 볼륨이나 외부 저장소로 분리해야 컨테이너 교체 뒤에도 남습니다.

# uv 멀티스테이지 빌드
Docker Desktop의 실습 전용 이미지와 스택만 사용해 결과를 확인합니다.
## 실행 환경 준비
Docker 명령과 실습 경로를 준비합니다.
### 이 준비 셀이 하는 일
이 준비 셀은 현재 폴더와 부모 폴더에서 `Dockerfile.baseline`이 있는 Ch32 실습 폴더를 찾습니다. `run(*args, check=True)`은 모든 Docker 명령을 그 폴더에서 실행하고 표준 출력·오류와 종료 코드를 `CompletedProcess`로 반환합니다. 실패 자체를 관찰하는 셀만 `check=False`를 전달하며, 마지막에는 Docker Engine이 응답하는지 확인합니다.
## 기본 실행
최적화 Dockerfile을 빌드하고 uv가 최종 이미지에 없는지 확인합니다.
### 바로 다음 코드를 읽는 방법
멀티스테이지 Dockerfile은 여러 `FROM`으로 빌드 단계와 실행 단계를 나눕니다. `AS builder`는 앞 단계를 이름 붙이고, `COPY --from=builder`는 그 단계에서 필요한 가상환경이나 산출물만 최종 단계로 복사합니다. uv와 컴파일 도구는 빌드에 필요하지만 서비스 실행에는 필요하지 않을 수 있으므로 최종 이미지에서 제외합니다.
## 실패 재현
존재하지 않는 stage를 지정하면 빌드가 시작되기 전에 실패합니다.
## 수정
정확한 builder stage를 지정하면 의존성 환경까지 빌드됩니다.
### 이 단계에서 구분할 범위
단계를 나누는 목적은 줄 수를 늘리는 것이 아니라 최종 런타임의 책임을 줄이는 데 있습니다. 디버깅 도구까지 제거하면 운영 이미지는 작아지지만 장애 조사 방식도 달라집니다. 빌드 단계와 실행 단계의 Python 버전·플랫폼이 다르면 복사한 바이너리 패키지가 동작하지 않을 수 있으므로 같은 호환 조건을 사용합니다.

# 빌드 캐시와 이미지 크기
Docker Desktop의 실습 전용 이미지와 스택만 사용해 결과를 확인합니다.
## 실행 환경 준비
두 Dockerfile의 빌드와 측정에 같은 명령 함수를 사용합니다.
### 이 준비 셀이 하는 일
이 준비 셀은 현재 폴더와 부모 폴더에서 `Dockerfile.baseline`이 있는 Ch32 실습 폴더를 찾습니다. `run(*args, check=True)`은 모든 Docker 명령을 그 폴더에서 실행하고 표준 출력·오류와 종료 코드를 `CompletedProcess`로 반환합니다. 실패 자체를 관찰하는 셀만 `check=False`를 전달하며, 마지막에는 Docker Engine이 응답하는지 확인합니다.
## 두 이미지 빌드
기준 이미지와 최적화 이미지를 같은 애플리케이션 코드로 만듭니다.
### 바로 다음 코드를 읽는 방법
Docker 빌드 캐시는 명령과 그 명령이 의존하는 파일이 같을 때 이전 레이어를 재사용합니다. 어느 `COPY`가 바뀌면 그 단계뿐 아니라 뒤의 단계도 다시 실행됩니다. 그래서 자주 바뀌지 않는 의존성 잠금 파일을 먼저 복사해 설치하고, 자주 바뀌는 애플리케이션 소스는 뒤에서 복사합니다. 출력의 `CACHED`는 해당 빌드에서 재사용된 단계의 관찰값입니다.
## 크기 비교
Docker가 보고한 압축 전 이미지 크기를 바이트 단위로 읽습니다.
## 반복 빌드와 캐시
소스가 바뀌지 않은 상태로 다시 빌드해 CACHED 기록을 셉니다.
## 실험 결과 해석
이번 수치는 arm64와 고정된 태그에서 얻었으며 다른 시점에는 달라질 수 있습니다.
### 이 단계에서 구분할 범위
캐시 적중 수와 이미지 크기는 서로 다른 지표입니다. 캐시가 많아도 최종 이미지가 클 수 있고, 멀티스테이지로 작은 이미지를 만들어도 첫 빌드는 오래 걸릴 수 있습니다. 비교할 때는 같은 빌드 컨텍스트와 플랫폼을 사용하고, `--no-cache`와 `--pull`이 각각 단계 재실행과 새 베이스 확인이라는 다른 역할임을 구분합니다.
