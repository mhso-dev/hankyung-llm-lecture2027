4핵심 개념
비유로 먼저 이해하기
도구 설명서는 주문서와 비슷합니다. 모델은 함수 내부를 보지 않고 이름, 설명, 선택 항목을 보고 요청합니다.
정의
Ch 4의 fetch_orders()는 CSV를 읽고 조건에 맞는 사전 목록을 반환합니다. 이번 절에서는 함수 본문을 바꾸지 않고 @tool 데코레이터로 모델이 읽을 이름·설명·입력 형식을 더합니다.
도구로 감싼 뒤에도 CSV 경로는 프로그램이 넘깁니다. 모델에게 파일 경로까지 선택하게 하면 학습 목표와 관계없는 경로 오류가 늘어납니다. 이 절의 도구는 status만 공개하고 data_path는 함수 안에서 사용합니다. 직접 호출과 invoke 호출에 cancelled를 넣었을 때 모두 O104를 반환하므로 필터 조건과 행의 네 필드가 보존됐음을 읽을 수 있습니다. 반면 StructuredTool을 위치 인자로 호출한 TypeError는 주문 데이터의 실패가 아니라 인터페이스 사용 오류입니다. 실패의 층을 구분해야 수정 위치도 정확해집니다.
도구 호출(tool call)은 구조화된 실행 요청이며 도구 메시지(ToolMessage)는 실행 결과와 호출 ID를 돌려주는 메시지입니다.
도식 읽기
Ch 4 함수에 도구 정보를 더한 뒤 invoke로 호출합니다. CSV 경로는 프로그램이 정하고 모델에 공개하는 인자는 status로 제한합니다.
코드를 읽기 전에
@tool은 바로 아래 파이썬 함수를 LangChain의 도구 객체로 감쌉니다. 함수 이름과 문서 문자열, 타입 힌트에서 모델이 볼 이름·설명·입력 스키마를 만들지만 함수 본문을 모델에게 보여 주지는 않습니다. 일반 함수처럼 위치 인자를 넘기는 대신 도구 객체의 invoke({"status": ...})에 입력 사전을 전달하면 검증 뒤 함수가 실행되고 결과가 반환됩니다.
이 절은 Ch 4의 fetch_orders()를 다시 작성하지 않습니다. 모델이 선택할 status만 공개하고 CSV 경로는 애플리케이션 코드가 고정합니다. Before의 TypeError는 주문 자료의 문제가 아니라 도구 객체의 호출 형식을 지키지 않은 인터페이스 오류입니다.
다른 상황과 개념 경계
재고 조회 함수를 도구로 만들 때 창고 ID는 모델이 골라야 할 업무 인자일 수 있지만, 데이터베이스 연결 문자열은 프로그램 설정으로 남겨야 합니다. 모델에게 공개할 입력을 줄이면 선택 오류와 권한 범위가 함께 줄어듭니다. 기존 함수를 재사용한다는 말은 기존 검증과 테스트를 그대로 활용한다는 뜻이며, 도구 장식만으로 원래 함수의 데이터 품질이 좋아지지는 않습니다.
5실행 예제
cancelled 상태를 직접 함수와 도구에 각각 넣습니다. O104 한 행이 양쪽에 나타나므로 빈 목록의 우연한 일치가 아닙니다.
빈 Python 3.12 커널에서 준비 셀부터 실행합니다. 모델 호출이 있는 절은 gpt-5.4-mini, temperature=0을 사용하며 키 값은 출력하지 않습니다.
확인할 점 — 직접 호출과 도구의 invoke() 결과를 비교하면 포장 전후의 업무 로직이 같음을 확인할 수 있습니다.
6일부러 실패해 보기
cancelled를 입력했을 때 직접 호출과 도구의 invoke()가 모두 O104를 반환하는지 확인합니다. same=True와 실제 주문 행을 함께 비교해야 빈 목록끼리 우연히 같아지는 경우를 제외할 수 있습니다.
출력 읽기
출력을 읽을 때 먼저 same이 True인지 확인하고, 이어서 rows 안의 order_id가 O104인지 봅니다. True만 확인하면 두 결과가 모두 빈 목록인 경우를 놓칠 수 있습니다. 실제 행의 ID·고객 ID·상태·금액까지 같아야 기존 함수의 의미가 유지됐다고 말할 수 있습니다. 다음으로 도구 객체의 name과 description, args를 확인합니다. 이 세 값은 모델에게 전달되는 설명서이고 CSV 경로는 포함되지 않습니다. 학생이 상태를 paid로 바꾸면 두 행이 반환되며, 이 변화는 도구로 감쌌기 때문이 아니라 입력 상태가 달라졌기 때문입니다.
7주의할 점과 실무 메모
데코레이터를 붙인 뒤 변수는 일반 함수가 아니라 StructuredTool입니다. 일반 위치 인자로 부르지 않고 invoke()에 필드 이름이 있는 사전을 전달합니다.
직접 함수는 Python 코드가 이름을 정해 호출합니다. 도구 객체는 같은 함수를 모델 선택 후보로 표현합니다. 이 변화 때문에 함수의 책임까지 넓히면 안 됩니다. CSV 읽기와 상태 필터는 Ch 4 함수가 맡고, 도구는 모델이 채울 status 한 칸만 공개합니다. 새로운 상태가 데이터에 추가되면 함수 테스트와 도구 설명을 함께 갱신합니다. 원본 해시는 출처 추적용이며 해시가 같다는 사실만으로 실행 결과까지 보장하지 않으므로 새 커널 비교도 수행합니다.
복사 동등성은 소스 출처를 투명하게 남기기 위한 선택입니다. 실무에서는 검증된 함수를 패키지로 배포해 import하는 편이 중복을 줄입니다. 이 기본 노트북은 프로젝트 전용 import 없이도 실행되어야 하므로 짧은 원문을 포함했습니다. 원본이 바뀌면 해시와 AST 비교가 실패하도록 검증해야 두 사본이 조용히 달라지는 일을 막을 수 있습니다.
도구 설명과 인자 스키마도 모델 컨텍스트를 사용합니다.
API 가격과 모델 동작은 달라질 수 있으므로 실행 시점의 공식 정보를 확인합니다.

4핵심 개념
비유로 먼저 이해하기
도구 설명서는 주문서와 비슷합니다. 모델은 함수 내부를 보지 않고 이름, 설명, 선택 항목을 보고 요청합니다.
정의
인자 스키마는 모델이 채워야 할 입력 칸과 각 칸의 조건을 정의합니다. Field의 설명과 최솟값·최댓값은 JSON Schema로 변환되어 모델과 실행기 사이의 공통 형식이 됩니다.
Literal은 선택 가능한 문자열을 JSON Schema의 enum으로 나타냅니다. 모델은 paid, pending, cancelled라는 후보를 설명서에서 볼 수 있고, 실행기는 후보 밖의 shipped를 거부합니다. limit의 ge와 le는 각각 최솟값과 최댓값입니다. 반환값은 OrderRecord와 TypeAdapter로 검사해 주문 ID·고객 ID·상태·금액의 자료형과 금액의 최솟값을 확인합니다. 입력과 반환 형식을 검사해도 데이터에 주문이 실제로 존재하는지까지 보장하지는 않습니다.
도구 호출(tool call)은 구조화된 실행 요청이며 도구 메시지(ToolMessage)는 실행 결과와 호출 ID를 돌려주는 메시지입니다.
도식 읽기
입력 형식이 맞는지 확인한 뒤 함수를 실행하고 반환값을 검사합니다. 검사에 실패하면 해당 단계에서 오류가 발생하며 다음 단계로 진행하지 않습니다.
코드를 읽기 전에
Pydantic 모델은 실행 전에 입력 값을 확인하는 클래스입니다. Literal은 허용 문자열을 제한하고, Field(ge=1, le=10)은 limit의 최소·최대 범위를 정합니다. args_schema=OrderQuery를 @tool에 넘기면 이 규칙이 도구의 JSON Schema가 되고, invoke()는 함수 본문을 실행하기 전에 값을 검증합니다.
반환 쪽의 TypeAdapter(list[OrderRecord])는 함수가 만든 목록의 각 사전을 다시 검사합니다. 입력 검증은 호출 모양을, 반환 검증은 결과 모양을 확인합니다. 주문이 실제 고객의 것인지 같은 업무 사실은 별도의 데이터 조회와 권한 검사가 필요합니다.
다른 상황과 개념 경계
호텔 검색 도구에서 인원은 1 이상, 객실 등급은 허용 목록으로 제한할 수 있습니다. 하지만 체크인 날짜가 체크아웃 날짜보다 앞서는지는 두 필드의 관계를 검사하는 별도 규칙이 필요합니다. 스키마는 자료형 설명서이면서 실행 경계이지만, 모든 업무 규칙을 자동으로 추론하는 장치는 아닙니다.

빈 Python 3.12 커널에서 준비 셀부터 실행합니다. 모델 호출이 있는 절은 gpt-5.4-mini, temperature=0을 사용하며 키 값은 출력하지 않습니다.
확인할 점 — 잘못된 입력은 조회 전에 거부되고, 정상 반환값은 TypeAdapter를 통과한 뒤 필드별 값으로 출력됩니다.
6일부러 실패해 보기
shipped는 허용 상태 목록에 없고 limit=0은 최솟값보다 작으므로 조회 함수가 실행되기 전에 ValidationError가 발생합니다. 오류의 loc와 type을 읽으면 수정할 입력 필드를 구분할 수 있습니다.
출력 읽기
오류 출력의 loc는 문제가 생긴 필드를 가리킵니다. shipped 입력에서는 status가, limit=0에서는 limit가 표시됩니다. type은 각각 허용 목록 위반과 최솟값 위반을 구분합니다. 프로그램은 이 정보를 운영 로그에 남기거나 사용자에게 고칠 항목을 안내할 수 있습니다. 수정 셀에서 pending을 넣으면 O102가 반환됩니다. 이 행은 공개 CSV에 실제로 있으므로 스키마 통과와 데이터 조회 성공을 함께 확인합니다. 단, Literal 후보를 바꾸면 모델 설명서와 테스트, 데이터 문서도 함께 갱신해야 합니다.
7주의할 점과 실무 메모
설명 문장에 허용 값을 적는 것만으로는 검증되지 않습니다. 자료형 또는 검증 규칙에도 같은 제약이 있어야 실행기가 거부할 수 있습니다.
JSON Schema를 출력하면 enum, minimum, maximum에 해당하는 제약을 찾을 수 있습니다. 모델 제공자는 이 설명을 도구 호출 형식으로 변환하지만 최종 검증 책임은 애플리케이션에 있습니다. 오류를 잡아 무조건 빈 목록으로 바꾸면 잘못된 상태와 검색 결과 없음이 구분되지 않습니다. 입력 오류는 입력 오류로 남기고, 허용된 입력에서 행이 없을 때만 빈 결과로 해석합니다. 반환 목록의 필드 이름도 안정적으로 유지해야 후속 모델이 금액과 상태를 혼동하지 않습니다.
반환 타입 주석만으로 실행 시점의 반환값이 자동 검증되지는 않습니다. 이 절은 OrderRecord에 필드별 자료형과 금액의 최솟값을 정의하고, TypeAdapter(list[OrderRecord])로 실제 목록을 검사합니다. 검증을 마친 객체를 다시 사전으로 출력해 다음 모델 호출에 전달할 필드가 유지되는지도 확인합니다.
도구 설명과 인자 스키마도 모델 컨텍스트를 사용합니다.
API 가격과 모델 동작은 달라질 수 있으므로 실행 시점의 공식 정보를 확인합니다.
8정리와 다음 절
상태 목록과 개수 범위를 JSON Schema와 실제 검증에 함께 반영했습니다.
shipped와 limit=0은 함수 본문이 실행되기 전에 거부됩니다.
유효한 pending 입력은 공개 자료의 O102를 반환합니다.

4핵심 개념
비유로 먼저 이해하기
도구 설명서는 주문서와 비슷합니다. 모델은 함수 내부를 보지 않고 이름, 설명, 선택 항목을 보고 요청합니다.
정의
도구 이름은 동작과 대상을 함께 드러내야 합니다. 설명은 언제 이 도구를 골라야 하는지와 반환값을 짧게 밝힙니다. 세 도구가 목록 조회, ID 조회, 집계로 나뉘면 질문의 의도와 대응시키기 쉽습니다.
목록 조회는 여러 행을 반환하고, ID 조회는 한 행을 반환하며, 집계는 count와 total을 새로 계산합니다. 세 도구의 입력 이름도 status, order_id, status로 나뉩니다. 이름만 길게 만든다고 좋은 설명이 되지는 않습니다. 언제 선택하는지와 무엇을 반환하는지가 서로 겹치지 않아야 합니다. 노트북이 출력하는 문자 수는 description과 args가 공짜가 아니라는 점을 눈으로 확인하기 위한 값입니다. 실제 토큰 수는 모델의 토크나이저와 직렬화 형식에 따라 달라지므로 문자 수를 비용으로 환산하지 않습니다.
도구 호출(tool call)은 구조화된 실행 요청이며 도구 메시지(ToolMessage)는 실행 결과와 호출 ID를 돌려주는 메시지입니다.
도식 읽기
함수의 실제 역할을 기준으로 이름과 설명을 작성합니다. 모델은 이 정보를 읽고 도구 사용 여부를 판단합니다.
코드를 읽기 전에
세 도구는 목록 조회, 단일 ID 조회, 상태별 집계라는 서로 다른 결과를 만듭니다. name은 모델이 호출 요청에 쓸 식별자이고, 함수의 문서 문자열은 description이 됩니다. 이 노트북에서는 타입 힌트가 args의 필드 이름과 자료형으로 변환됩니다. Field(description=...) 같은 명시적 필드 설명은 사용하지 않았으므로 출력에도 필드 설명이 없습니다. 노트북은 이름·설명·입력 스키마를 출력해 모델에게 실제로 전달되는 설명서를 확인합니다.
설명 길이의 문자 수는 스키마가 입력 문맥의 일부라는 사실을 비교하기 위한 보조값입니다. 문자 수와 토큰 수는 같지 않으므로 이 값을 모델 사용량이나 비용으로 바꾸지 않습니다. 좋은 설명은 길이보다 선택 조건과 반환 범위가 겹치지 않는지가 중요합니다.
다른 상황과 개념 경계
search, find, lookup처럼 비슷한 이름의 도구가 모두 ‘정보를 찾습니다’라고만 쓰면 모델은 경계를 알기 어렵습니다. search_articles_by_keyword는 여러 기사 요약을, get_article_by_id는 한 기사의 원문을 반환한다고 구분할 수 있습니다. 설명에 구현 세부를 길게 적기보다 언제 선택하고 무엇을 돌려받는지 명시합니다.
5실행 예제
각 도구의 name, description, args를 그대로 출력하고 설명과 스키마의 문자 수도 측정합니다. 이 수치는 토큰 수가 아니며 설명서 크기를 비교하는 보조 관찰입니다.
빈 Python 3.12 커널에서 준비 셀부터 실행합니다. 모델 호출이 있는 절은 gpt-5.4-mini, temperature=0을 사용하며 키 값은 출력하지 않습니다.
확인할 점 — 설명과 스키마도 매 요청의 모델 컨텍스트에 들어가므로 길이를 측정하고 필요한 정보만 남깁니다.
6실험 결과 해석
세 도구의 name, description, args를 나란히 놓으면 목록·단건·집계의 경계를 확인할 수 있습니다. 문자 수는 설명서의 상대적 크기를 보여 주지만 모델이 청구하는 토큰 수를 뜻하지는 않습니다.
출력 읽기
세 설명서를 표처럼 읽어 봅니다. list_orders_by_status는 상태로 여러 주문을 찾는 질문에 대응합니다. get_order_by_id는 O103처럼 식별자가 들어간 질문에 대응합니다. summarize_order_amounts는 개별 행 대신 건수와 합계를 요구하는 질문에 대응합니다. 설명에 이 차이가 나타나지 않으면 모델은 인자 이름만으로 추측해야 합니다. args 출력은 status와 order_id의 차이를 보여 주지만 반환 목적은 알려 주지 않으므로 docstring이 필요합니다. 다음 절에서는 바로 이 설명 문장을 실험 변수로 삼습니다.
7주의할 점과 실무 메모
도구 이름에는 동작과 대상을 함께 씁니다. get_data처럼 범위가 넓은 이름이나 같은 설명을 반복하면 질문과 도구를 대응할 근거가 줄어듭니다.
도구 설명을 작성한 뒤에는 실제 질문을 세 부류로 적어 봅니다. ‘paid 주문을 보여 줘’는 목록, ‘O103을 찾아 줘’는 단건, ‘paid 총액은 얼마야’는 집계입니다. 어느 질문이 두 도구 설명에 동시에 맞으면 경계가 겹친 것입니다. 이때 설명에 예문을 계속 붙이기보다 함수 책임을 나누거나 이름을 고치는 편이 낫습니다. 반환 필드 설명은 모델이 다음 답을 만들 때 필요한 정도로 적고, 내부 파일명이나 구현 라이브러리는 노출하지 않습니다.
도구 수가 늘어날 때는 새 도구를 추가하기 전에 기존 도구의 인자 하나로 표현할 수 있는지 검토합니다. 그러나 목록과 집계처럼 반환 의미가 크게 다르면 억지로 합치지 않습니다. 이름 충돌 검사와 대표 질문 표를 변경 검토에 넣으면 설명이 비슷해지는 시점을 일찍 찾을 수 있습니다.
도구 설명과 인자 스키마도 모델 컨텍스트를 사용합니다.
API 가격과 모델 동작은 달라질 수 있으므로 실행 시점의 공식 정보를 확인합니다.

목록·단건·집계 도구가 이름과 반환 목적에서 서로 구분됩니다.
인자 스키마는 입력 형식을, 설명은 선택 시점과 반환 목적을 알려 줍니다.
문자 수는 설명서 크기를 비교하는 값이며 토큰 비용으로 환산할 수 없습니다.

도구 설명서는 주문서와 비슷합니다. 모델은 함수 내부를 보지 않고 이름, 설명, 선택 항목을 보고 요청합니다.
정의
모델은 함수 본문을 읽지 않습니다. 바인딩할 때 전달한 이름·설명·스키마만 보고 호출할 도구와 인자를 정합니다. 따라서 구현이 같아도 설명이 모호하면 선택 근거가 부족합니다.
모호 조건과 구체 조건의 Python 함수 이름은 다르지만 모델에게 공개되는 tool name은 동일합니다. 노트북은 same_name과 same_args가 모두 True인지 먼저 확인합니다. 함수 본문도 같은 CSV 조회와 집계를 수행합니다. 따라서 모델에게 달라지는 정보는 description입니다. 채점은 목록 질문에는 list_orders_by_status, 정확한 주문 번호 질문에는 get_order_by_id, 건수와 총액 질문에는 summarize_order_amounts를 기대합니다. 두 조건이 모두 맞았다면 이 표본에서는 차이를 관찰하지 못했다고 기록해야 하며, 모호 조건이 틀렸을 때만 관찰된 차이를 설명합니다.
도구 호출(tool call)은 구조화된 실행 요청이며 도구 메시지(ToolMessage)는 실행 결과와 호출 ID를 돌려주는 메시지입니다.
도식 읽기
설명문을 바꾼 두 조건을 각각 실행하고 도구 선택을 비교합니다. 이번 실행에서는 두 조건 모두 세 질문을 세 번씩 실행한 아홉 응답에서 올바른 도구를 선택했습니다.
코드를 읽기 전에
두 실험 조건은 파이썬 함수 이름이 달라도 모델에게 공개하는 도구 이름과 입력 스키마를 같게 맞춥니다. 바꾸는 값은 description뿐입니다. bind_tools()는 도구 설명을 모델 요청에 포함한 새 모델 객체를 반환하고, invoke()에서 실제 모델 호출이 발생합니다. 응답의 tool_calls에는 모델이 고른 이름과 인자가 들어 있으며 도구 결과는 아직 없습니다.
채점 함수는 질문마다 기대 이름을 미리 정해 실제 선택과 비교합니다. 두 조건이 모두 정답이면 ‘구체 설명의 효과가 없다’가 아니라 이 작은 표본에서는 차이가 관찰되지 않았다고 기록합니다.
다른 상황과 개념 경계
설명 품질을 평가할 때는 비슷한 도구가 경쟁하는 질문, 정보가 부족해 도구를 부르지 않아야 하는 질문, 여러 도구가 필요한 질문을 나눠야 합니다. 세 질문의 성공만으로 모든 표현에 일반화할 수 없습니다. 설명을 바꾼 뒤에는 같은 질문 집합과 반복 횟수로 선택 정확도와 잘못된 인자를 함께 비교합니다.
5실행 예제
질문 3개를 조건마다 3회씩 호출합니다. 전체 tool_calls와 사용량을 보존하고, 호출이 정확히 하나일 때 이름을 기대값과 사람이 비교합니다.
빈 Python 3.12 커널에서 준비 셀부터 실행합니다. 모델 호출이 있는 절은 gpt-5.4-mini, temperature=0을 사용하며 키 값은 출력하지 않습니다.
확인할 점 — 질문 3개, 반복 3회, 같은 모델과 temperature를 유지하고 설명만 바꿉니다. 전체 tool_calls와 사용량을 로그로 남긴 뒤 사람이 질문별 기대 도구와 비교합니다.
6실험 결과 해석
모호 조건과 구체 조건은 공개 이름·인자 스키마·함수 동작·질문·모델·temperature·도구 순서를 모두 같게 유지하고 description만 바꿉니다. 질문 3개를 조건마다 3회 실행한 실제 결과는 두 조건 모두 9/9였습니다. 두 조건을 합친 사용량은 입력 3,483토큰, 출력 366토큰이며 추정 비용은 미화 0.00425925달러입니다.
출력 읽기
두 조건이 모두 9/9이므로 이 실행에서는 선택 차이를 관찰하지 못했습니다. 이것은 설명이 필요 없다는 결론이 아닙니다. 질문에 주문 목록, 주문 번호, 건수와 총액이라는 강한 단서가 있고 인자 스키마도 서로 달라 모델이 구분했을 수 있습니다. 다른 질문이나 도구 수에서 결과가 달라질 수 있습니다. 차이를 더 조사하려면 질문 수를 늘리고 독립 실행을 반복하되, 결과를 얻기 위해 질문 문구를 조건마다 바꾸면 안 됩니다. 원시 tool_calls를 남겨야 수동 채점 오류도 다시 확인할 수 있습니다.
7주의할 점과 실무 메모
temperature 0이어도 서비스 실행이 언제나 동일하다고 가정하지 않습니다. 9회라는 작은 표본과 사용한 질문에 한정해 결과를 보고합니다.
실험은 실행 전에 채점 기준과 반복 횟수를 정합니다. 결과를 본 뒤 기대 도구를 바꾸면 선택률을 믿을 수 없습니다. 한 응답에 호출이 없거나 둘 이상이면 이 실험에서는 오답으로 처리합니다. 전체 로그에는 질문, 기대 이름, 반복 번호, 원시 호출, 토큰 사용량이 있으므로 다른 검토자가 같은 규칙으로 다시 채점할 수 있습니다. 이번 실제 실행에서 두 조건이 모두 9/9이면 ‘혼동을 재현했다’고 쓰지 않고 차이를 관찰하지 못했다고 본문과 검증 기록에 남깁니다.
설명 품질 평가는 선택률 하나로 끝나지 않습니다. 올바른 도구를 골라도 status나 order_id를 잘못 채울 수 있으므로 인자 정확도도 별도로 봅니다. 이번 채점은 도구 이름만 평가하며 인자 값은 원시 로그에서 사람이 확인합니다. 평가 항목의 범위를 명시하면 9/9를 전체 성공률로 오해하지 않습니다.
도구 설명과 인자 스키마도 모델 컨텍스트를 사용합니다.
API 가격과 모델 동작은 달라질 수 있으므로 실행 시점의 공식 정보를 확인합니다.

4핵심 개념
비유로 먼저 이해하기
도구 설명서는 주문서와 비슷합니다. 모델은 함수 내부를 보지 않고 이름, 설명, 선택 항목을 보고 요청합니다.
정의
bind_tools()는 모델에게 도구 설명서를 제공합니다. 모델의 tool_calls에는 이름·인자·고유 ID가 들어 있지만 조회 결과는 아직 없습니다. 프로그램이 호출을 실행하고 같은 ID를 가진 ToolMessage를 대화에 추가해야 결과를 바탕으로 답할 수 있습니다.
AIMessage의 content가 비어 있어도 tool_calls가 있으면 모델은 답 대신 실행 요청을 보낸 것입니다. 각 항목의 name은 실행할 도구를, args는 전달할 주문 ID를, id는 결과 연결표를 나타냅니다. StructuredTool.invoke에 호출 사전 전체를 넘기면 LangChain은 실행 결과를 ToolMessage로 만들고 원래 id를 넣습니다. 마지막 호출에서는 사용자 질문, AIMessage, 두 ToolMessage를 순서대로 전달합니다. 이 메시지 순서가 어긋나거나 ID가 빠지면 제공자 API가 잘못된 대화 형식으로 판단할 수 있습니다.
도구 호출(tool call)은 구조화된 실행 요청이며 도구 메시지(ToolMessage)는 실행 결과와 호출 ID를 돌려주는 메시지입니다.
도식 읽기
모델이 한 응답에 두 호출 요청을 작성해도 Python 실행 방식은 별도로 정합니다. 이 예제는 요청을 순회하며 순차 실행하고 호출 ID에 맞춰 결과를 반환합니다.
코드를 읽기 전에
bind_tools()는 모델이 사용할 수 있는 도구 설명을 붙일 뿐, 파이썬 함수를 실행하지 않습니다. 첫 invoke()의 AIMessage.tool_calls는 실행 요청 목록이며 각 항목의 name, args, id를 읽어야 합니다. 프로그램이 해당 도구의 invoke(tool_call)를 호출하면 실행 결과를 담은 ToolMessage가 만들어지고 원래 호출 ID가 연결됩니다.
마지막 모델 호출에는 사용자 메시지, 도구를 요청한 AIMessage, 각 ToolMessage를 순서대로 전달합니다. 모델이 한 응답에서 호출 두 개를 요청했다는 사실과 프로그램이 두 함수를 동시에 실행했다는 사실은 다릅니다. 이 노트북의 반복문은 순차 실행입니다.
다른 상황과 개념 경계
서울과 부산의 날씨를 한 번에 물으면 모델이 두 호출을 만들 수 있습니다. 두 조회가 독립적이면 애플리케이션이 비동기로 실행할 수 있지만, 두 번째 도구가 첫 결과를 필요로 한다면 순차 실행해야 합니다. 병렬 호출 가능성은 모델 요청 형식의 기능이고, 실제 동시성·재시도·순서 보장은 실행 코드가 결정합니다.
5실행 예제
모델 응답에서 호출 두 개와 각 ID를 먼저 출력합니다. 프로그램이 각 호출을 실행한 뒤 ToolMessage ID를 나란히 비교하고, 마지막 모델 호출에 결과를 전달합니다.
빈 Python 3.12 커널에서 준비 셀부터 실행합니다. 모델 호출이 있는 절은 gpt-5.4-mini, temperature=0을 사용하며 키 값은 출력하지 않습니다.
확인할 점 — 한 질문이 독립된 두 주문을 요구하면 모델은 한 응답에 여러 호출을 낼 수 있습니다. 실제 출력의 호출 개수와 ID 대응을 확인합니다.
6실험 결과 해석
실제 응답에는 O101과 O103을 조회하는 호출 두 개가 들어 있으며, 프로그램은 각 호출을 실행해 성공한 ToolMessage 두 개를 만듭니다. 요청 ID와 결과 ID를 비교하면 어느 결과가 어느 호출에 대응하는지 확인할 수 있습니다. 마지막 모델 호출의 사용량은 입력 290토큰, 출력 36토큰입니다. 추정 비용 미화 0.00074925달러는 첫 호출과 마지막 호출을 합한 값입니다.
출력 읽기
첫 출력에서 content가 빈 문자열이고 tool_calls가 두 개인지 확인합니다. 이것은 모델이 최종 문장보다 두 조회를 먼저 요청했다는 뜻입니다. 두 번째 출력의 content에는 O101의 paid·32000과 O103의 paid·27000이 직렬화되어 있습니다. 세 번째 출력에서 requested와 returned 배열이 같은 순서와 값인지 확인합니다. 마지막 자연어 답은 두 도구 결과를 읽은 모델의 새 응답입니다. 중간 ToolMessage를 생략하고 마지막 호출을 보내면 모델은 주문 상태와 금액을 알 수 없습니다.
7주의할 점과 실무 메모
parallel_tool_calls는 한 응답에 여러 호출을 허용하는 설정입니다. 이 노트북은 실제 함수 실행 시간을 측정하지 않으므로 동시에 실행됐다고 주장하지 않습니다.
두 주문 조회는 서로 의존하지 않으므로 모델이 호출 두 개를 한 응답에 담을 수 있는 사례입니다. 두 번째 주문이 첫 번째 결과를 필요로 한다면 같은 방식으로 병렬 요청하면 안 됩니다. 또한 호출 두 개가 생성됐다는 사실과 Python 함수가 동시에 실행됐다는 사실은 다릅니다. 이 노트북의 리스트 컴프리헨션은 순서대로 invoke를 호출합니다. 실제 동시 실행을 가르치려면 비동기 실행 시간과 시작·종료 기록을 별도 측정해야 하며, 그 내용은 이 절의 범위를 넘습니다.
도구 결과를 모델에게 다시 보낼 때 원본 AIMessage도 함께 넣습니다. ToolMessage만 보내면 어떤 요청에 대한 결과인지 대화 기록이 완전하지 않습니다. 운영 로그에서는 호출 ID로 모델 요청, 함수 시작, 함수 종료, 최종 답을 연결하면 지연과 오류가 생긴 위치를 찾기 쉽습니다.
도구 설명과 인자 스키마도 모델 컨텍스트를 사용합니다.
API 가격과 모델 동작은 달라질 수 있으므로 실행 시점의 공식 정보를 확인합니다.

bind_tools는 호출 요청을 만들며 실제 실행은 애플리케이션이 담당합니다.
호출 ID를 보존해야 여러 요청과 결과를 정확히 연결할 수 있습니다.

NOT_FOUND 오류에서 재시도보다 입력 확인이 필요한 이유를 설명할 수 있습니다.

주문 조회 실패와 주문 취소 요청은 위험이 다릅니다. 예상 가능한 조회 실패는 모델이 다음 판단에 사용할 오류 코드로 반환하고, 상태를 바꾸는 동작은 확인 경로를 별도로 둡니다.
Ch 20에서 ToolNode로 실행 흐름을 조립하기 전에 도구 한 개가 어떤 정보와 결과를 주고받는지 확인합니다.
3앞에서 배운 내용
공개 주문 목록을 메모리에서 읽고 존재하지 않는 O999를 조회합니다. 쓰기 예제는 실제 주문을 변경하지 않고 취소 요청 상태만 구조화해 반환합니다.
실행 파일은 labs/part5/ch19-model-tools/data/orders.csv를 사용하며 Part 1 모듈을 런타임에 import하지 않습니다.
4핵심 개념
비유로 먼저 이해하기
도구 설명서는 주문서와 비슷합니다. 모델은 함수 내부를 보지 않고 이름, 설명, 선택 항목을 보고 요청합니다.
정의
예상 가능한 업무 오류는 NOT_FOUND처럼 짧고 일정한 코드와 관련 인자를 반환합니다. 쓰기 권한은 모델 인자가 아니라 애플리케이션이 기록한 사용자 확인 상태로 제어합니다.
O999가 없다는 사실은 예상 가능한 업무 결과입니다. read_order는 예외 대신 ok=False, error=NOT_FOUND, order_id=O999를 반환합니다. 취소 도구에는 confirmed 필드가 없습니다. 확인 전 available_tools에는 읽기 도구만 있습니다. 애플리케이션은 사용자가 확인한 주문 ID를 confirmed_order_ids에 기록하고, 취소 함수는 요청한 ID가 이 집합에 있는지 다시 검사합니다. 이 예제의 True는 흐름을 보여 주는 로컬 실습값이며 실제 외부 동의가 아닙니다.
도구 호출(tool call)은 구조화된 실행 요청이며 도구 메시지(ToolMessage)는 실행 결과와 호출 ID를 돌려주는 메시지입니다.
도식 읽기
읽기·쓰기 도구의 공개와 실행 권한은 앱 상태로 결정합니다. 모델이 작성한 인자가 앱의 허용 여부를 대신하지 않습니다.
코드를 읽기 전에
read_order()는 예상 가능한 ‘주문 없음’을 예외 대신 ok=False와 오류 코드가 든 사전으로 반환합니다. 호출자는 성공 결과와 업무상 미발견을 같은 반환 형식에서 구분할 수 있습니다. 반면 코드 결함이나 연결 실패까지 모두 같은 오류 코드로 바꾸면 원인을 잃으므로 예상 범위를 정해야 합니다.
쓰기 도구의 인자에는 confirmed가 없습니다. 사용자의 확인된 주문 ID는 애플리케이션 상태인 confirmed_order_ids에 저장되고, 도구 실행 시 요청 ID가 그 집합에 있는지 다시 검사합니다. 모델이 만든 문자열은 사용자 승인 증거가 될 수 없습니다.
다른 상황과 개념 경계
메일 검색과 메일 발송을 한 도구 목록에 함께 제공하면 모델의 선택 오류가 곧 외부 부작용으로 이어질 수 있습니다. 검색 단계에는 읽기 도구만 제공하고, 수신자·본문을 사람이 확인한 뒤 해당 초안 ID에 한해 발송 도구를 열 수 있습니다. 도구 공개 여부와 함수 내부의 권한 재검사를 함께 두어 한 경계가 빠져도 다른 경계가 남게 합니다.
5실행 예제
읽기 도구는 NOT_FOUND와 order_id를 반환합니다. 쓰기 도구는 모델이 정하는 confirmed 인자를 받지 않으며, 애플리케이션 확인 상태에 따라 제공 목록에 추가됩니다.
빈 Python 3.12 커널에서 준비 셀부터 실행합니다. 모델 호출이 있는 절은 gpt-5.4-mini, temperature=0을 사용하며 키 값은 출력하지 않습니다.
확인할 점 — 확인 전 O101 직접 호출과 O101 확인 뒤 O103 호출은 모두 PermissionError로 거부됩니다. 확인한 O101에 대해서만 모의 취소 요청이 반환됩니다.
6일부러 실패해 보기
존재하지 않는 O999를 조회하면 ok=False와 error=NOT_FOUND가 반환됩니다. 확인 전 도구 목록에는 읽기 도구만 있으며, O101 취소를 직접 호출해도 PermissionError가 발생합니다. O101 확인 뒤에는 O101 요청만 통과하고 확인하지 않은 O103은 계속 거부됩니다.
출력 읽기
NOT_FOUND는 재시도하면 항상 해결되는 시스템 장애가 아닙니다. 먼저 주문 ID를 확인하거나 사용자에게 올바른 대상을 요청해야 합니다. 쓰기 도구 제공 여부는 모델 출력과 분리된 애플리케이션 상태가 결정합니다. 확인 전 목록에 취소 도구가 없다는 assert는 구성 실수를 찾는 작은 검사입니다. 실제 취소 API를 연결할 때는 인증된 사용자와 대상 주문의 소유 관계도 검사해야 합니다.
7주의할 점과 실무 메모
예상 가능한 업무 실패와 시스템 예외를 구분합니다. 내부 스택 추적은 운영 로그에 남기고 모델에는 다음 행동에 필요한 코드와 대상만 제공합니다.
확인 상태는 대화 문장만 보고 추측하지 않습니다. 애플리케이션의 확인 화면이나 승인 API가 남긴 신뢰 가능한 상태를 서버가 읽어야 합니다. 실습의 confirmed_order_ids={"O101"}는 이 경계를 보여 주는 고정 예시이며 실제 사용자의 승인을 대신하지 않습니다. 확인 상태는 참·거짓 하나로 저장하지 않고 확인한 주문 ID와 함께 기록해야 다른 주문에 재사용되지 않습니다. 참인 상태에서 반환하는 값도 실제 데이터베이스를 바꾸지 않는 모의 취소 요청입니다.
읽기와 쓰기를 분리해도 쓰기 함수 자체의 검증은 필요합니다. 도구 목록은 선택 가능성을 제한하고, 함수 내부 권한 검사는 최종 방어선을 제공합니다. 모델이 도구를 호출하지 않는 별도 경로에서도 같은 쓰기 API가 사용될 수 있으므로 권한 검사를 도구 설명에만 의존하면 안 됩니다.

API 가격과 모델 동작은 달라질 수 있으므로 실행 시점의 공식 정보를 확인합니다.

# @tool과 Ch 4 함수 재사용
검증한 조회 함수에 도구 인터페이스를 더합니다.
## 준비
공개 CSV와 Ch 4 함수 원문을 사용합니다.
## 코드를 읽기 전에
`@tool`은 바로 아래 파이썬 함수를 LangChain의 도구 객체로 감쌉니다. 함수 이름과 문서 문자열, 타입 힌트에서 모델이 볼 이름·설명·입력 스키마를 만들지만 함수 본문을 모델에게 보여 주지는 않습니다. 일반 함수처럼 위치 인자를 넘기는 대신 도구 객체의 `invoke({"status": ...})`에 입력 사전을 전달하면 검증 뒤 함수가 실행되고 결과가 반환됩니다.
이 절은 Ch 4의 `fetch_orders()`를 다시 작성하지 않습니다. 모델이 선택할 `status`만 공개하고 CSV 경로는 애플리케이션 코드가 고정합니다. Before의 `TypeError`는 주문 자료의 문제가 아니라 도구 객체의 호출 형식을 지키지 않은 인터페이스 오류입니다.
### 다음 셀을 읽는 방법
다음 셀은 Ch 4에서 검증한 `fetch_orders(csv_path, status=...)`의 본문을 같은 입력·반환 형식으로 다시 선언합니다. CSV 경로와 선택 상태를 받아 각 행을 사전으로 담은 목록을 반환하며, 아직 LangChain 도구를 만들거나 모델을 호출하지 않습니다.
