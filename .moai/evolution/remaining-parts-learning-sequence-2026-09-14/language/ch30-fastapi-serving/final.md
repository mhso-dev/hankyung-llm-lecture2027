1학습 목표
비동기 경로 연산을 선언하고 요청 처리 순서를 설명할 수 있습니다.
Pydantic 제약으로 잘못된 요청을 Agent 호출 전에 거부할 수 있습니다.
정상 입력과 422 검증 오류를 직접 비교할 수 있습니다.
2이 내용을 배우는 이유
노트북의 Agent는 파이썬 함수 호출로 시작했습니다. 웹 서비스에서는 다른 프로그램이 HTTP 요청을 보내므로 문자열 하나도 경로, 메서드, 본문 형식이라는 경계를 통과해야 합니다. 이 경계를 먼저 고정해야 Agent 오류와 웹 입력 오류를 구분할 수 있습니다.
3앞에서 배운 내용
Ch2에서 `async def`와 `await`를 배웠고 Ch21에서 Agent 실행 객체를 만들었습니다. Ch25에서는 결과가 조각으로 이어질 수 있음을 확인했습니다. 이 절은 그 실행을 HTTP에 놓기 전에 요청과 응답의 모양부터 고정합니다.
4핵심 개념
식당의 주문표에는 메뉴, 수량, 알레르기 표시를 적는 칸이 있습니다. 비어 있거나 잘못 적힌 주문은 주방에 들어가기 전에 되돌아갑니다. 웹 API의 스키마도 같은 역할을 합니다. 라우트(route)는 HTTP 메서드와 URL 경로를 파이썬 함수에 연결한 규칙입니다. FastAPI에서는 `@app.post('/v1/chat')` 아래의 함수를 경로 연산(path operation)이라고 합니다. 요청 스키마는 클라이언트가 보낼 필드와 제약을, 응답 스키마는 서버가 반환할 필드와 타입을 선언합니다.
Pydantic의 `Field(min_length=1, max_length=500)`는 질문이 비었거나 지나치게 긴 요청을 함수 실행 전에 거부합니다. 따라서 잘못된 입력은 모델 비용을 발생시키지 않습니다. 422 상태는 서버 장애가 아니라 요청 본문이 선언과 맞지 않는다는 뜻입니다. 클라이언트는 오류 위치와 종류를 읽어 사용자가 고칠 수 있는 메시지로 바꿉니다.
`async def`는 함수를 여러 CPU에서 자동으로 실행한다는 뜻이 아닙니다. 네트워크나 저장소를 기다리는 지점에서 `await`로 실행권을 이벤트 루프에 넘길 수 있다는 뜻입니다. Agent의 모델 호출은 대기 시간이 길 수 있어 이 방식과 잘 맞습니다. 반대로 긴 CPU 계산을 비동기 함수 안에서 직접 수행하면 다른 요청도 기다릴 수 있습니다.
응답 모델은 문서 장식이 아닙니다. 내부 상태에서 공개할 필드만 골라 직렬화하고 OpenAPI에 타입을 기록합니다. Agent 상태 전체를 반환하면 시스템 메시지, 도구 출력, 디버그 정보가 외부에 노출될 수 있습니다. 이 장은 `answer`와 `thread_id`만 새 응답 객체로 만듭니다.
코드 읽기와 개념 경계
코드는 Question(BaseModel)로 요청 본문의 모양을 먼저 선언합니다. text: str = Field(...)에서 콜론 뒤의 str은 받을 값의 타입이고, Field의 길이 조건은 라우트 함수가 실행되기 전에 적용됩니다. @mini.post('/ask')는 아래 ask 함수를 POST 요청과 연결하며, body: Question에는 검증이 끝난 객체가 전달됩니다. TestClient.post(..., json=...)가 파이썬 사전을 JSON 본문으로 보내고, 반환된 응답에서 상태 코드와 JSON을 따로 읽습니다.
같은 빈 문자열이라도 쿼리 매개변수, 헤더, JSON 본문 가운데 어디에 놓였는지에 따라 오류 위치가 달라집니다. 또한 422는 입력 형식이 선언과 맞지 않는 경우이고, 라우트 안의 코드가 실패해 생기는 500과 구분해야 합니다. 이 경계를 이해하면 모델 호출 전에 막힌 요청과 모델 실행 중 실패한 요청을 같은 장애로 집계하지 않게 됩니다.
도식 읽기
위쪽의 요청에서 아래쪽의 관찰 결과까지 화살표를 따라 읽습니다. 파란 상자는 데이터, 보라색 상자는 Agent 실행, 초록 상자는 확인할 결과를 나타냅니다.
서비스 설계 판단
서비스 스키마를 정할 때는 성공 예시만 보지 않고 경계값을 표로 적습니다. 질문 길이가 1, 500, 501일 때의 상태 코드와 오류 본문을 확인하고, 필드가 없을 때와 null일 때가 같은지도 구분합니다. 프런트엔드가 보내지 않는 필드에 기본값을 둘지, 누락을 오류로 볼지도 제품 요구에 따라 결정합니다. 응답 모델에서는 클라이언트가 실제로 읽는 필드와 서버 내부 추적 필드를 나눕니다. 이 표가 있으면 모델 호출 결과가 달라져도 HTTP 입력 검증은 결정적으로 회귀 검사할 수 있습니다. 비동기 라우트의 처리량을 확인할 때는 한 요청의 속도만 재지 않고 여러 요청이 기다리는 상황에서 다른 요청이 진행되는지 봅니다. 로컬 TestClient는 기본 계약을 빠르게 확인하는 도구이며, 실제 서버의 동시성은 uvicorn 프로세스와 외부 모델 연결을 포함한 부하 실험에서 측정합니다.
5실행 예제
작은 FastAPI 앱에 `async def` 라우트와 Pydantic 모델을 연결합니다. 정상 문자열은 200과 길이를 반환하고 빈 문자열은 422로 거부됩니다. 같은 경로와 모델에서 입력 값 하나만 바꾸므로 스키마 제약의 효과를 분리해 관찰할 수 있습니다.
확인할 점 — 정상 요청의 200과 `length`, 빈 문자열 요청의 422와 `string_too_short`를 실제 출력에서 확인합니다.
6일부러 실패해 보기
Before에서는 빈 문자열의 422와 최소 길이 오류를 확인합니다. After에서는 같은 JSON 필드에 한 글자 이상의 값을 넣어 200을 받습니다. 오류를 임의의 검사 함수로 만들지 않고 FastAPI가 실제로 반환한 응답을 읽습니다.
7주의할 점과 실무 메모
비동기 함수 안에서 동기 HTTP 클라이언트나 긴 파일 처리를 호출하면 이벤트 루프가 멈출 수 있습니다.
질문 길이 500자는 교육용 값입니다. 실제 서비스에서는 토큰 한도와 비용을 측정해 정합니다.
오류 세부 정보를 화면에 그대로 노출하지 말고 사용자가 수정할 항목만 안내합니다.

해설 — 경로 연산 함수가 호출되기 전에 실행됩니다.

해설 — 외부에 공개할 필드를 제한하고 안정적인 타입을 기록하기 위해서입니다.
4. 빈 질문의 상태 코드는 무엇인가요?
해설 — 422입니다.

1학습 목표
`Depends`로 Agent 제공 함수를 라우트에 연결할 수 있습니다.
테스트에서 Agent만 대체해 라우트 동작을 확인할 수 있습니다.
요청마다 만들 객체와 애플리케이션에서 공유할 객체를 구분할 수 있습니다.
2이 내용을 배우는 이유
라우트 안에서 모델과 저장소를 직접 만들면 함수 하나가 너무 많은 책임을 갖습니다. 테스트할 때도 실제 모델을 호출해야 하므로 느리고 결과가 달라집니다. 의존성 주입은 라우트가 필요한 객체를 선언하고 생성과 교체를 다른 함수에 맡깁니다.
3앞에서 배운 내용
01절에서 요청 검증과 비동기 라우트를 만들었습니다. Ch21의 Agent와 Ch23의 체크포인터처럼 생성 비용과 수명주기가 다른 객체가 있다는 점도 배웠습니다.
4핵심 개념
공구 대여 창구에서 작업자는 드릴이 필요하다고 말하고 창구는 사용할 객체를 건넵니다. 작업자가 매번 창고에서 새 드릴을 조립하지 않습니다. 테스트할 때는 같은 인터페이스의 모형을 건네 순서만 확인할 수도 있습니다.
의존성 주입(dependency injection)은 함수가 필요한 값을 직접 만들지 않고 외부에서 제공받는 방식입니다. `Depends(get_agent)`는 요청이 오면 FastAPI가 제공자 함수를 해결하고 반환값을 라우트 매개변수에 넣게 합니다. 제공자도 헤더나 다른 의존성을 받을 수 있어 인증과 권한 검사를 계층으로 구성할 수 있습니다.
교육용 서비스는 모듈 로드 때 실제 LangGraph를 한 번 컴파일합니다. 그래프 구조는 요청마다 달라지지 않으므로 다시 만들 이유가 없습니다. 사용자별 데이터베이스 세션처럼 요청 뒤 닫아야 하는 자원은 `yield` 의존성으로 열고 정리합니다. 객체를 공유할지는 생성 비용뿐 아니라 동시에 사용해도 상태가 섞이지 않는지 확인해 결정합니다.
`app.dependency_overrides`는 테스트에서 제공자만 바꿉니다. 대체 Agent를 넣어도 경로, 스키마, 인증, 응답 변환은 실제 코드 그대로 실행됩니다. 대체 객체는 `ainvoke`처럼 라우트가 쓰는 메서드를 구현해야 합니다. 테스트 뒤 재정의를 비우지 않으면 다음 테스트에 상태가 남습니다.
공유 Agent가 요청별 변경 상태를 내부 속성에 보관하면 동시에 들어온 사용자의 데이터가 섞일 수 있습니다. 요청 상태는 `ainvoke` 입력이나 체크포인터의 thread 식별자로 나눕니다. 실무에서는 `Protocol`로 필요한 메서드를 선언하면 구현체를 고정하지 않으면서 타입 검사를 받을 수 있습니다.
코드 읽기와 개념 경계
Depends(get_agent)는 get_agent를 지금 직접 호출한 결과가 아니라, 요청 시 FastAPI가 해결할 제공자 함수로 등록합니다. 라우트는 제공자가 반환한 Agent의 ainvoke만 사용합니다. 테스트의 app.dependency_overrides[get_agent] = ...는 원래 제공자를 같은 역할의 StubAgent로 바꾸고, HTTP 경로와 요청 검증은 그대로 통과시킵니다. 따라서 출력의 대체 응답은 라우트 전체를 가짜로 만든 결과가 아니라 Agent 경계만 교체한 결과입니다.
설정처럼 읽기 전용인 값은 여러 요청이 공유해도 되지만, 데이터베이스 세션처럼 닫아야 하는 자원은 요청마다 만들고 정리해야 합니다. 대체 객체가 성공했다는 사실도 실제 모델 품질을 보장하지 않습니다. 의존성 테스트는 연결 방식과 응답 변환을 확인하고, 실제 Agent 통합 테스트는 도구 선택과 생성 결과를 별도로 확인합니다.
도식 읽기
위쪽의 요청에서 아래쪽의 관찰 결과까지 화살표를 따라 읽습니다. 파란 상자는 데이터, 보라색 상자는 Agent 실행, 초록 상자는 확인할 결과를 나타냅니다.
서비스 설계 판단
의존성 트리를 설계할 때는 값이 언제 만들어지고 언제 폐기되는지를 옆에 적습니다. 설정과 컴파일된 그래프는 애플리케이션 수명 동안 공유할 수 있지만 데이터베이스 세션과 요청 추적 문맥은 요청마다 분리해야 합니다. 인증 제공자 아래에 사용자 조회와 권한 검사를 두면 어느 단계에서 401과 403을 반환할지도 분명해집니다. 테스트 대체는 인터페이스만 흉내 내는 수준과 실제 외부 시스템을 포함하는 수준을 나눕니다. 대체 Agent는 오류, 지연, 빈 답 같은 경계 조건을 빠르게 재현하고, 실제 Agent 통합은 도구 선택과 모델 메시지를 확인합니다. 두 검사를 같은 이름으로 부르면 대체 객체의 성공을 운영 준비 완료로 오해할 수 있으므로 검증 기록에 실행 대상을 명시합니다.

확인할 점 — 재정의 중의 `대체 응답`과 재정의 해제 뒤 LangGraph가 만든 답을 실제 출력에서 확인합니다.

4핵심 개념
택배 창구는 주소와 연락처를 내부 운송 형식으로 바꾸고 결과 중 송장 번호와 상태만 고객에게 줍니다. 내부 분류 코드까지 모두 공개하지 않습니다. FastAPI 라우트도 요청과 Agent 상태 사이에서 같은 경계 변환을 맡습니다.
`ainvoke`는 비동기 단일 실행 메서드입니다. 호출자는 `await`로 최종 상태를 기다리지만 그동안 이벤트 루프는 다른 요청을 처리할 수 있습니다. 이 교재의 객체는 `StateGraph`를 컴파일한 실제 LangGraph입니다. 입력은 `{'messages': [question]}`이고 출력에는 입력 메시지와 `answer`가 있습니다.
라우트는 결과의 `answer`만 `ChatResponse`로 옮기고 요청의 `thread_id`를 함께 반환합니다. 이 변환을 명시하면 Agent 내부 키가 추가되어도 외부 계약을 유지할 수 있습니다. 반대로 외부 필드를 바꾸려면 Pydantic 모델과 변환 코드, OpenAPI 변경을 함께 검토합니다.
외부 모델 호출에는 완료 시간이 보장되지 않습니다. DNS, 공급자 대기열, 네트워크, 도구가 모두 지연 원인입니다. `asyncio.wait_for`로 전체 Agent 실행 시간을 제한하고 단일 응답에서는 504로 바꿉니다. 모델 클라이언트 timeout만 두면 여러 도구를 포함한 전체 실행 시간이 상한을 넘을 수 있습니다.
예외 원문에는 내부 경로나 공급자 정보가 포함될 수 있습니다. 로그에는 요청 식별자와 원인 예외를 남기고 공개 응답에는 안정적인 오류 코드와 사용자가 취할 행동을 담습니다. 시간 초과만 기록하지 말고 모델과 도구별 소요 시간도 측정해야 느린 단계를 찾을 수 있습니다.

단일 응답과 스트리밍은 같은 Agent를 소비하는 두 방식입니다. 최종 결과가 한 번에 필요한 저장·평가 작업에는 ainvoke가 맞고, 중간 조각을 사용자에게 보여 주려면 다음 절의 astream을 사용합니다. 예외가 발생했을 때 내부 예외 문자열을 그대로 HTTP 응답으로 내보내지 않고, 로그의 원인 정보와 공개 오류 코드를 분리합니다.

1학습 목표

질문 길이와 조각 수 실험의 해석 범위를 설명할 수 있습니다.
2이 내용을 배우는 이유
모델 답이 완성될 때까지 빈 화면을 보여 주면 사용자는 서비스가 멈췄다고 느낄 수 있습니다. 스트리밍은 중간 결과를 먼저 전달해 첫 응답 지연을 줄이지만 오류, 취소, 완료를 소비자가 관리해야 합니다.
3앞에서 배운 내용
Ch25에서 스트림 모드와 진행 이벤트를 비교했고 03절에서는 같은 Agent의 `ainvoke`가 최종 상태 하나를 반환하는 것을 확인했습니다.
4핵심 개념
완성된 보고서를 한 번에 받으면 첫 내용을 보기까지 기다려야 합니다. 작성 중인 문장을 조각으로 받으면 빨리 볼 수 있지만 순서와 완료 여부를 관리해야 합니다.
`astream`은 비동기 스트림 실행 메서드입니다. 한 번 `await`하는 값이 아니라 `async for`로 여러 번 꺼내는 비동기 반복자를 반환합니다. `stream_mode='custom'`은 노드가 스트림 작성기에 기록한 사용자 정의 데이터를 전달합니다. 교육용 노드는 답을 공백 단위로 나누어 `{'token': piece}`를 기록합니다.
청크 하나가 한 글자나 실제 모델 토큰 하나와 항상 일치하지는 않습니다. 제공자, 네트워크 버퍼, 프레임워크 설정에 따라 여러 토큰이 묶일 수 있습니다. 클라이언트는 청크 수를 언어 단위로 해석하지 않고 순서대로 내용을 이어 붙입니다. 완료는 마지막 문자열을 추측하지 않고 별도 신호로 전달합니다.
스트리밍 성능은 전체 완료 시간만으로 설명할 수 없습니다. 요청 후 첫 조각까지의 시간, 조각 사이 간격, 완료 시간, 취소 반영 시간을 함께 봅니다. 이 노트북은 로컬 결정적 그래프이므로 네트워크 속도를 측정하지 않습니다. 공백 수가 늘면 교육용 조각 수가 늘어나는 현상만 확인합니다.
비동기 생성기는 취소 요청을 처리할 기회를 가져야 합니다. 긴 반복에 `await`가 없으면 연결이 끊겨도 작업이 계속될 수 있습니다. 교육용 노드는 `await asyncio.sleep(0)`으로 실행권을 넘깁니다. 실제 모델 스트림도 하위 도구가 동기 작업으로 이벤트 루프를 막는지 따로 확인합니다.
코드 읽기와 개념 경계
agent.astream(input, stream_mode='custom')은 최종 사전 하나가 아니라 비동기 반복 가능한 스트림을 반환합니다. async for는 새 조각이 도착할 때마다 반복 본문을 실행하며, 이 예제는 각 조각의 token을 목록에 추가합니다. ''.join(chunks).strip()은 조각을 연결해 최종 문장을 만들지만, 연결 전 목록도 출력하여 경계가 어디였는지 확인합니다. 스트림 조각 수는 답의 의미 단위나 모델 토큰 수와 같다고 가정하지 않습니다.
파일 다운로드처럼 이미 만들어진 큰 바이트를 나누는 스트림과 Agent가 생성하면서 내보내는 스트림은 지연 원인이 다릅니다. 첫 조각까지의 시간, 조각 사이의 시간, 전체 완료 시간을 따로 측정해야 합니다. 또한 소비자가 연결을 끊었을 때 생산 작업을 취소하지 않으면 화면은 닫혔는데 모델 호출은 계속될 수 있습니다.

스트림 소비 코드는 세 상태를 구분하면 읽기 쉬워집니다. 시작 전에는 요청 검증과 인증이 실패할 수 있고, 진행 중에는 여러 token 또는 progress 조각이 도착하며, 종료에는 done, error, cancel이 있습니다. 각 상태에서 화면에 무엇을 표시하고 서버 작업을 어떻게 정리할지 정합니다. 받은 문자열을 매번 전체 DOM에 다시 넣으면 답이 길어질수록 렌더링 비용이 커질 수 있습니다. 일정한 간격으로 묶어 반영하되 사용자가 첫 내용을 늦게 보지 않도록 갱신 주기를 측정합니다. 모델 청크에는 텍스트뿐 아니라 도구 호출 조각이나 메타데이터가 들어올 수 있습니다. 사용자 문장으로 표시할 블록만 고르고 나머지는 별도의 진행 표시나 관측 기록으로 보냅니다. 이 구분이 없으면 도구 인자 JSON이 채팅 답에 노출될 수 있습니다.

token과 done 이벤트를 클라이언트가 판별하도록 설계할 수 있습니다.
2이 내용을 배우는 이유
Agent의 비동기 청크는 파이썬 프로세스 안의 값입니다. 브라우저가 받으려면 이벤트 종류와 순서를 보존하는 HTTP 전송 형식이 필요합니다.
3앞에서 배운 내용
04절에서 `astream` 청크를 읽었고 Ch25에서 진행 이벤트와 토큰 이벤트를 분리했습니다. 이제 같은 구분을 HTTP 필드로 옮깁니다.
4핵심 개념
택배 상자에는 종류, 번호, 내용이 적힌 운송장이 있습니다. SSE도 `event`, `id`, `data`로 각 조각의 의미와 순서를 전달합니다.
Server-Sent Events(SSE)는 하나의 HTTP 응답 연결에서 여러 텍스트 이벤트를 순서대로 보내는 표준 형식입니다. 각 이벤트는 필드 행과 빈 줄로 구성됩니다. FastAPI 0.135의 `EventSourceResponse`와 `ServerSentEvent`를 사용하면 비동기 생성기에서 이벤트를 `yield`할 수 있습니다.
`event`는 token, done, error 같은 종류입니다. `data`는 JSON으로 직렬화되는 본문이며 문자열도 JSON 문자열로 인코딩됩니다. `id`는 클라이언트가 마지막 처리 위치를 기억하는 값입니다. 교육용 서비스는 `thread_id:index`를 사용합니다. 식별자에 사용자 입력이나 비밀값을 넣으면 로그와 브라우저 저장소에 남을 수 있습니다.
SSE는 GET에만 제한되지 않습니다. 공식 문서는 POST 본문을 받고 SSE를 반환하는 예를 제공합니다. 채팅 질문과 옵션을 JSON으로 보낼 때 POST가 자연스럽습니다. 하지만 브라우저 `EventSource`는 임의의 POST 본문과 Authorization 헤더를 설정하지 못하므로 `fetch`로 응답 본문을 직접 읽어야 합니다.
네이티브 응답은 캐시 방지, 프록시 버퍼링 방지, 연결 유지 ping을 처리합니다. 그래도 실제 로드 밸런서와 CDN이 스트림을 버퍼링하거나 유휴 연결을 끊지 않는지는 배포 환경에서 확인해야 합니다. 로컬 TestClient 성공은 운영 프록시를 검증하지 않습니다.
코드 읽기와 개념 경계
SSE(Server-Sent Events)는 한 HTTP 응답 안에서 event, id, data 줄을 묶어 사건을 순서대로 보내는 텍스트 형식입니다. 이 실습은 POST 본문으로 질문을 받은 뒤 token 사건을 여러 번 보내고 마지막에 done 사건을 한 번 보냅니다. 빈 줄은 사건과 사건의 경계입니다. 정규식으로 응답을 나눈 다음 첫 사건의 종류와 식별자, 마지막 사건의 종류를 각각 검사합니다.
token과 done을 나누면 클라이언트는 문자열 조각과 실행 완료를 혼동하지 않습니다. 진행률, 출처, 도구 호출을 추가할 때도 별도 사건 이름을 사용하면 데이터 형식을 독립적으로 발전시킬 수 있습니다. 다만 SSE의 id는 업무 결과의 영구 식별자와 목적이 다르므로, 재연결 위치와 대화 식별자를 한 필드에 무리하게 합치지 않습니다.
도식 읽기
위쪽의 요청에서 아래쪽의 관찰 결과까지 화살표를 따라 읽습니다. 파란 상자는 데이터, 보라색 상자는 Agent 실행, 초록 상자는 확인할 결과를 나타냅니다.
서비스 설계 판단
이벤트 종류는 클라이언트 상태 전이와 함께 설계합니다. token은 답 본문에 추가하고 progress는 단계 표시를 갱신하며 done은 입력창을 다시 활성화합니다. error는 코드에 따라 재시도 버튼이나 입력 수정 안내를 보여 줍니다. 이벤트 이름과 data 스키마를 OpenAPI 보충 문서나 별도 JSON Schema로 기록하면 프런트 팀이 문자열 조건을 임의로 만들지 않아도 됩니다. SSE 식별자는 실행 안에서 단조롭게 증가해야 하지만 데이터베이스 기본 키와 같을 필요는 없습니다. 여러 서버 인스턴스에서 재개하려면 어느 인스턴스가 받아도 실행 기록과 다음 순번을 찾을 수 있어야 합니다. 완료 이벤트에도 최종 사용량, 모델, 처리 시간을 넣을 수 있으나 공개 범위와 비용을 검토합니다. 긴 연결을 통해 너무 많은 메타데이터를 보내면 사용자 데이터 노출 면도 넓어집니다.

2이 내용을 배우는 이유
POST SSE에서는 브라우저가 자동 재연결을 대신하지 않습니다. 어떤 질문과 마지막 위치를 다시 보낼지, 중복 도구 실행을 어떻게 막을지 클라이언트와 서버가 함께 정해야 합니다.
3앞에서 배운 내용
05절에서 token 이벤트의 id와 done을 확인했습니다. Ch23의 thread 분리와 Ch24의 중복 실행 방지 원칙을 브라우저 경계에 적용합니다.
4핵심 개념
책을 읽다 연결이 끊겼을 때 마지막 쪽을 기록하면 다음부터 이어갈 수 있습니다. 다만 판본이 바뀌면 같은 쪽이 같은 내용을 뜻하지 않습니다. 이벤트 ID와 실행 ID도 함께 관리해야 합니다.
`fetch()`는 POST, JSON 본문, Authorization 헤더를 설정합니다. 응답 `body`를 문자열로 바꾸고 버퍼에 누적합니다. 네트워크 청크와 SSE 이벤트 경계는 일치하지 않으므로 `\r?\n\r?\n` 패턴으로 완성 블록만 분리하고 남은 문자열은 다음 읽기와 합칩니다. EOF에 남은 완전한 블록도 한 번 더 해석합니다.
클라이언트는 처리에 성공한 id를 저장하고 연결이 끊기면 같은 본문과 `Last-Event-ID`를 보냅니다. 서버는 thread 접두사를 확인하고 다음 인덱스부터 전송합니다. 다른 대화의 ID를 받아들이면 데이터가 섞일 수 있습니다. 잘못된 ID 형식도 400으로 거부해야 하며 교육용 코드는 핵심 흐름만 구현합니다.
안정적인 재연결은 이미 만든 이벤트를 저장하고 이어 보내야 합니다. 이 예제는 결정적 Agent를 다시 실행해 앞부분을 건너뜁니다. 외부 모델은 재실행 결과가 달라질 수 있으므로 운영 복구 방식이 아닙니다. Ch31에서 실행과 이벤트를 저장하면 동일 이벤트를 재생할 수 있습니다.
스트림은 첫 데이터가 전송되면 HTTP 200이 확정됩니다. 이후 모델이 실패해도 500으로 바꿀 수 없습니다. 서버는 예외를 `event: error`와 안정적인 코드로 보냅니다. 클라이언트는 `response.ok`뿐 아니라 각 이벤트 타입을 확인합니다. 결제나 메일 같은 쓰기 도구가 있다면 재연결 중 다시 실행되지 않도록 작업 ID와 완료 기록으로 멱등성을 확보해야 합니다.
코드 읽기와 개념 경계
클라이언트는 마지막으로 처리한 SSE 식별자를 Last-Event-ID 헤더에 넣어 이어받을 위치를 알립니다. 예제의 첫 응답에서 resume-1:0을 읽고 다시 요청하면 서버는 다음 식별자인 resume-1:1부터 보냅니다. 이 결과는 서버가 이번 교육용 실행의 조각을 다시 계산해 건너뛴 동작을 보여 주며, 모든 운영 서버가 과거 조각을 영구 보관한다는 뜻은 아닙니다.
HTTP 헤더를 이미 보낸 뒤 스트림 내부에서 실패하면 상태 코드를 500으로 바꾸기 어렵습니다. 그래서 예제는 HTTP 200 연결 안에 event: error와 안정적인 오류 코드를 보냅니다. 클라이언트는 네트워크 단절, 오류 사건, 정상 done을 서로 다른 종료 상태로 기록해야 하며, 같은 id를 다시 처리해도 부작용이 중복되지 않도록 설계해야 합니다.

재연결 정책에는 재시도 가능한 오류, 최대 횟수, 대기 간격, 사용자 취소를 적습니다. 네트워크 단절은 재시도할 수 있지만 인증 만료는 새 토큰을 받은 뒤 다시 요청해야 하고 입력 검증 오류는 같은 본문으로 반복해도 해결되지 않습니다. 지수 백오프에 작은 무작위 지연을 더하면 많은 브라우저가 동시에 재연결하는 상황을 줄일 수 있습니다. 클라이언트는 id를 화면에 반영한 뒤 저장해야 합니다. 저장을 먼저 하고 렌더링에 실패하면 재연결 때 표시하지 못한 이벤트를 건너뛸 수 있습니다. 반대로 표시 뒤 저장에 실패하면 같은 이벤트를 다시 받을 수 있으므로 token 결합이 중복에 견디는지도 확인합니다. 쓰기 도구가 포함된 실행은 HTTP 재시도와 도구 작업 재시도를 분리하고, 작업 식별자로 이미 완료된 효과를 조회합니다.

단일 응답과 스트림 timeout 결과 차이를 설명할 수 있습니다.
2이 내용을 배우는 이유
브라우저와 연결하면 출처 제한과 인증이 동시에 나타납니다. 모든 출처를 열거나 timeout 없이 모델을 기다리면 보안과 가용성 문제가 생깁니다.
3앞에서 배운 내용
Ch16에서 입력 검증과 비용 상한을, Ch22에서 호출 전후 처리를 배웠습니다. 06절의 클라이언트는 Authorization과 Last-Event-ID를 보냅니다.
4핵심 개념
건물 출입구는 방문 장소, 출입증, 대기 시간을 각각 확인합니다. CORS, 인증, timeout도 서로 다른 질문에 답합니다.
인증은 요청 주체를 확인합니다. 교육용 서비스는 Bearer 헤더를 의존성에서 검사합니다. 실제 서비스는 토큰 발급, 만료, 회전, 폐기를 인증 제공자와 설계해야 합니다. 기본 문자열 비교는 흐름을 보여 줄 뿐 운영 인증 수단이 아닙니다.
CORS는 브라우저가 다른 출처 응답을 스크립트에 공개할지 정하는 규칙입니다. 출처는 프로토콜, 호스트, 포트의 조합입니다. 브라우저는 Authorization과 JSON 본문을 보내기 전에 OPTIONS 사전 요청으로 메서드와 헤더 허용 여부를 확인합니다.
credentials가 True이면 origins, methods, headers를 와일드카드로 두지 않고 명시합니다. 교육용 앱은 `http://localhost:5173`, GET·POST, Authorization·Content-Type·Last-Event-ID를 허용합니다. CORS는 브라우저 정책이며 서버 간 호출 인증을 대신하지 않습니다.
timeout은 서버가 한 요청에 자원을 붙잡을 최대 시간입니다. 단일 `ainvoke`는 아직 헤더를 보내지 않아 504로 바꿀 수 있습니다. 스트림은 200과 일부 이벤트가 전송되었을 수 있으므로 error 이벤트로 끝냅니다. 모델, Agent 전체, 프록시 유휴 timeout 중 가장 짧은 값이 실제 결과를 정할 수 있어 계층별 설정을 기록합니다.
인증 실패는 Agent 호출 전에 끝나야 비용이 없습니다. 사전 요청이 인증 의존성에 막히지 않는지도 확인합니다. 로그에는 토큰 원문 대신 요청 ID와 실패 분류를 남깁니다.
코드 읽기와 개념 경계
인증은 요청한 주체를 확인하고, CORS는 브라우저가 다른 출처의 응답을 읽어도 되는지 결정하며, timeout은 기다릴 최대 시간을 제한합니다. 세 기능은 모두 요청 경계에 있지만 서로 대신하지 않습니다. 먼저 CORSMiddleware가 OPTIONS 사전 요청의 출처와 요청 헤더를 검사해 허용된 경우 200을 반환합니다. 이어지는 실제 POST에서 애플리케이션의 인증 의존성이 Authorization 헤더를 검사하며, 헤더가 없으면 401을 반환합니다. get_timeout을 0.01초로 대체한 테스트는 느린 Agent가 단일 응답에서는 504, 스트림에서는 오류 사건으로 바뀌는 차이를 보여 줍니다.
CORS 허용은 인증 우회가 아니며, 서버 간 요청에는 브라우저의 CORS 검사가 적용되지 않습니다. timeout도 실행 취소가 하위 모델·도구까지 전달되는지 따로 확인해야 합니다. 운영에서는 연결 timeout, 전체 Agent timeout, 프록시의 유휴 timeout을 같은 숫자로 가정하지 말고 어느 계층이 먼저 끊는지 기록합니다.
도식 읽기
위쪽의 요청에서 아래쪽의 관찰 결과까지 화살표를 따라 읽습니다. 파란 상자는 데이터, 보라색 상자는 Agent 실행, 초록 상자는 확인할 결과를 나타냅니다.
서비스 설계 판단
401은 인증 정보가 없거나 유효하지 않을 때, 403은 신원은 확인했지만 해당 작업 권한이 없을 때 사용합니다. 두 상태를 모두 500으로 바꾸면 클라이언트가 로그인 갱신과 운영 장애를 구분할 수 없습니다. 브라우저에서 보이는 CORS 오류도 서버의 실제 응답 상태와 다를 수 있으므로 네트워크 패널에서 OPTIONS와 POST를 각각 읽습니다. 시간 상한 뒤에는 자원이 실제로 정리되었는지 확인합니다. 파이썬 작업이 취소되어도 외부 공급자가 요청을 계속 처리하면 비용이 발생할 수 있습니다. 요청 ID를 공급자 메타데이터와 연결하고 timeout 이후 사용량을 점검합니다. 스트림 연결 수에는 사용자별·프로세스별 상한을 두어 느린 클라이언트가 연결을 무한히 점유하지 않게 합니다. 인증 토큰 만료가 긴 스트림 중간에 발생할 때의 정책도 별도로 정합니다.

4핵심 개념
건축 도면은 부품의 치수와 연결 위치를 합의합니다. OpenAPI도 경로, 입력, 출력, 오류, 인증을 기계가 읽을 수 있게 기록합니다.
FastAPI의 `.openapi()`는 라우트와 Pydantic 모델에서 OpenAPI 3.1 문서를 만들고 캐시합니다. `/openapi.json`도 같은 문서를 제공합니다. `info.version`은 API 제품 버전이며 FastAPI 패키지 버전과 다릅니다.
요청의 길이와 정규식 제약, 응답 타입은 JSON Schema 참조로 기록됩니다. TypeScript 타입이 빌드 오류를 줄이지만 런타임 검증을 없애지는 못합니다. 서버와 클라이언트 배포 버전이 어긋날 수 있고 SSE 이벤트는 생성기가 완전히 모델링하지 못할 수 있습니다.
SDK 생성기는 OpenAPI를 읽어 타입과 HTTP 호출 코드를 만듭니다. `typescript-fetch` 생성물을 직접 수정하지 말고 스키마를 고쳐 다시 생성합니다. 생성기와 Node 버전을 고정하지 않으면 같은 스키마에서도 파일 구조가 달라질 수 있습니다.
SSE는 일반 JSON보다 생성 지원이 제한적입니다. 생성된 SDK가 POST와 인증 헤더를 만들더라도 ReadableStream 분리와 Last-Event-ID 관리는 실제 출력으로 확인해야 합니다. 이 장은 `client/stream.ts`에 그 처리를 둡니다.
필수 요청 필드 추가, 타입 변경, enum 제거, 경로 삭제는 호환성을 깨울 수 있습니다. 이전 스키마와 새 스키마 차이를 CI에서 검사하고 생성된 SDK로 프런트 테스트를 실행합니다. 공개 함수 이름을 안정화하려면 operationId를 명시적으로 관리합니다.

app.openapi()는 현재 라우트와 Pydantic 모델에서 OpenAPI 문서를 파이썬 사전으로 만듭니다. paths에는 URL별 연산이, $ref에는 공통 스키마를 가리키는 참조가 들어갑니다. 예제는 요청이 ChatRequest, 200 응답이 ChatResponse를 참조하는지 검사하고 JSON 파일로 저장합니다. SDK 생성기는 실행 중인 서버를 추측하는 대신 이 문서를 입력으로 사용합니다.
스키마가 같은 문자열로 두 번 생성된다는 검사는 현재 프로세스에서 결정적인 출력을 확인할 뿐, 이전 배포와의 호환성을 증명하지 않습니다. 필수 필드 추가, 타입 축소, 상태 코드 삭제는 기존 클라이언트를 깨뜨릴 수 있습니다. 반대로 선택 필드 추가도 생성된 SDK를 다시 배포해야 소비자가 타입으로 사용할 수 있습니다.

01절부터 08절까지 사용한 결정적 LangGraph는 입력마다 같은 문자열을 만들기 때문에 라우팅, 재연결, 오류 이벤트를 반복 검사하기 좋습니다. 그러나 공백으로 나눈 문자열은 실제 모델의 토큰 스트림이 아니며 도구 선택도 수행하지 않습니다. 서비스가 Ch21에서 만든 Agent와 Ch25의 모델 스트림을 실제로 전달하는지는 별도의 통합 실행으로 확인해야 합니다.
3앞에서 배운 내용
Ch21에서는 init_chat_model과 create_agent로 도구 호출 Agent를 만들었습니다. Ch25에서는 stream_mode="messages"에서 모델 메시지 청크와 실행 메타데이터를 읽었습니다. 03절의 JSON 라우트와 05절의 네이티브 SSE 라우트에 이 실제 Agent를 연결합니다.
4핵심 개념
무대 장치 점검에서는 배우 없이 조명과 문이 같은 순서로 작동하는지 반복합니다. 최종 공연 전에는 배우가 실제 대사를 말하고 소품을 사용하는지 확인합니다. 결정적 그래프가 전송 장치 점검이라면 실제 모델과 도구의 통합 호출은 최종 공연 점검에 해당합니다.
build_live_agent()는 init_chat_model("openai:gpt-5.4-mini")로 모델을 초기화하고, 요일별 운영 시간을 반환하는 도구와 함께 create_agent를 호출합니다. 시스템 메시지는 운영 시간 질문에 반드시 도구를 사용하도록 요구합니다. 노트북은 월요일 질문의 답에 도구가 반환한 18:00이 포함되는지 검사합니다.
단일 응답 라우트는 runtime.ainvoke()의 마지막 AI 메시지에서 text를 골라 ChatResponse로 반환합니다. 스트림 라우트는 runtime.astream(..., stream_mode="messages")를 반복합니다. 실행 메타데이터의 노드가 model인 메시지에서 텍스트 블록만 골라 token 이벤트로 보냅니다. 도구 호출 인자와 도구 결과를 사용자 문장으로 잘못 표시하지 않도록 스트림 종류를 구분합니다.
실제 모델의 청크 경계는 글자, 단어, 언어 토큰 경계와 일치하지 않을 수 있습니다. 노트북 출력에서도 한글 한 글자와 숫자 일부가 별도 이벤트로 나타날 수 있습니다. 클라이언트는 모든 token 데이터의 문자열을 순서대로 이어 붙이고 done 이벤트를 받은 뒤 완성된 답으로 취급합니다.
API 키는 프로젝트의 .env에서 읽고 존재 여부만 출력합니다. 키 값, 전체 환경 변수, Authorization 헤더 원문은 교재 출력에 남기지 않습니다. 실제 모델 호출은 재실행할 때 표현과 token 이벤트 수가 달라질 수 있으므로 답의 정확한 문장 대신 도구 근거인 18:00과 이벤트 종류를 검증합니다.
코드 읽기와 개념 경계
이 절은 로컬 대체 객체 대신 실제 모델과 도구가 연결된 Agent를 HTTP 경계에서 호출합니다. TestClient.post('/v1/chat/live', ...)가 요청 스키마와 인증을 통과시키고, 내부 Agent는 운영 시간 조회 도구를 선택합니다. 이어서 ToolMessage와 tool_calls를 읽어 모델의 최종 문장만 확인하지 않고, 어떤 도구와 인수가 사용됐는지 검사합니다. 마지막 스트림에서는 SSE의 data JSON에서 token을 꺼내 연결합니다.
답에 18:00이 포함됐다는 한 조건만으로 올바른 도구 실행을 증명할 수 없습니다. 모델이 우연히 같은 숫자를 생성했을 수도 있기 때문입니다. 그래서 HTTP 응답, 도구 호출 인수, 도구 결과, 스트림 완료를 서로 다른 관찰로 남깁니다. 이 검사는 현재 질문 한 건의 통합 경로를 확인하며 다른 요일과 오류 입력의 품질까지 일반화하지 않습니다.
도식 읽기
HTTP 질문이 실제 create_agent에 들어가고, Agent가 운영 시간 도구 결과를 읽은 뒤 최종 문장 또는 모델 token SSE를 반환하는 순서로 읽습니다. 보라색은 실제 모델 실행, 파란색은 입력과 도구 데이터, 초록색은 HTTP에서 관찰한 결과입니다.
서비스 운영 인계
실제 Agent 엔드포인트를 운영으로 넘길 때는 모델 이름, 시스템 메시지 버전, 도구 목록, timeout, 평가셋 버전을 한 실행 기록에 묶습니다. 답이 달라졌을 때 모델 변경인지 도구 데이터 변경인지 찾으려면 이 정보가 필요합니다. 요청 식별자는 HTTP 로그, Agent 실행, 공급자 호출에 같은 값으로 연결하되 질문 원문과 인증 토큰은 공개 로그에 남기지 않습니다.
결정적 그래프 엔드포인트와 실제 모델 엔드포인트를 모두 공개할 필요는 없습니다. 전자는 로컬 교육과 회귀 검사에 사용하고, 운영 라우트는 실제 Agent 제공자만 주입하도록 애플리케이션 구성을 분리합니다. 배포 전에 OpenAPI에서 교육용 경로가 빠졌는지 확인하고, 실제 Agent의 오류율과 첫 token 지연을 별도 계기판에서 측정합니다. 이 장의 한 질문 성공은 배포 승인 기준이 아니라 통합 경로가 연결되었다는 최소 증거입니다.
5실행 예제
첫 셀은 상위 폴더의 .env를 찾고 OpenAI 키가 설정되었는지만 확인합니다. 다음 셀은 TestClient로 POST /v1/chat/live를 호출합니다. 마지막 실행은 POST /v1/chat/live/stream에서 이벤트 블록을 분리하고 각 data JSON의 token을 이어 붙입니다.
확인할 점 — 단일 응답과 스트림을 이어 붙인 답에 모두 월요일 운영 종료 시각 18:00이 있는지 확인합니다. 스트림에는 한 개 이상의 token 이벤트와 마지막 done 이벤트가 있는지도 확인합니다.
6실험 결과 해석
새 커널 실행에서 실제 OpenAI 모델이 운영 시간 도구를 사용했고 JSON 응답에 18:00을 포함했습니다. 같은 Agent의 messages 스트림을 SSE로 전달했을 때 token 이벤트가 여러 번 나타났고 이어 붙인 문장에도 18:00이 포함되었습니다. 이는 실제 모델·도구·Agent·FastAPI의 로컬 통합 경로가 실행되었음을 보여 줍니다.
한 질문의 성공은 모든 질문의 도구 선택 정확도나 운영 안정성을 뜻하지 않습니다. 모델 표현과 청크 수는 달라질 수 있습니다. Ch29 평가셋으로 도구 선택과 최종 답을 반복 평가하고, 배포 뒤에는 지연·오류율·비용을 함께 측정해야 합니다.
7주의할 점과 실무 메모
실제 API 호출 횟수와 사용량 메타데이터를 실행 기록에 남기며 키 값은 출력하지 않습니다. 이 절은 응답과 도구 궤적 확인이 목적이므로 비용을 임의로 추정하지 않습니다.
도구 결과를 사용했다는 사실은 Agent 메시지 궤적과 도구 호출 기록으로 확인합니다. 최종 문장에 숫자가 있다는 사실만으로 도구 호출을 단정하지 않습니다.
실제 모델 라우트의 오류 이벤트는 공급자 예외 원문을 숨기고 안정적인 코드와 고정 문구만 보냅니다.

## 실행 환경 준비

### 바로 다음 코드를 읽는 방법
`Depends(get_agent)`는 `get_agent`를 지금 직접 호출한 결과가 아니라, 요청 시 FastAPI가 해결할 제공자 함수로 등록합니다. 라우트는 제공자가 반환한 Agent의 `ainvoke`만 사용합니다. 테스트의 `app.dependency_overrides[get_agent] = ...`는 원래 제공자를 같은 역할의 `StubAgent`로 바꾸고, HTTP 경로와 요청 검증은 그대로 통과시킵니다. 따라서 출력의 `대체 응답`은 라우트 전체를 가짜로 만든 결과가 아니라 Agent 경계만 교체한 결과입니다.
완성된 `agent_service/app.py`에는 `AgentDep = Annotated[object, Depends(get_agent)]`가 있고, 라우트는 `async def chat(body: ChatRequest, runtime: AgentDep, ...)`처럼 이 타입을 매개변수에 선언합니다. 아래 셀은 이 선언을 새로 만드는 코드가 아니라 그 선언이 가리키는 `get_agent` 제공자만 테스트 객체로 바꿉니다.

설정처럼 읽기 전용인 값은 여러 요청이 공유해도 되지만, 데이터베이스 세션처럼 닫아야 하는 자원은 요청마다 만들고 정리해야 합니다. 대체 객체가 성공했다는 사실도 실제 모델 품질을 보장하지 않습니다. 의존성 테스트는 연결 방식과 응답 변환을 확인하고, 실제 Agent 통합 테스트는 도구 선택과 생성 결과를 별도로 확인합니다.

### 바로 다음 코드를 읽는 방법
`await agent.ainvoke(state)`는 상태 하나를 입력해 그래프가 끝날 때까지 기다린 뒤 최종 상태 사전을 반환합니다. `await`는 현재 요청의 결과가 필요하다는 뜻이면서, 기다리는 동안 이벤트 루프가 다른 작업을 처리할 수 있게 하는 지점입니다. 이 예제의 `state`에는 `messages`가 있고, 반환값의 `answer`와 `messages`는 각각 공개할 답과 실행에 사용된 상태를 나타냅니다. 화면에 `print`한 값은 반환 사전 전체가 아니라 학습을 위해 선택한 일부입니다.

## 수정
HTTP 스트림 계층에서는 이 예외를 `error` 이벤트로 바꿉니다. 여기서는 정상 질문으로 호출을 마칩니다.
### 이 단계에서 구분할 범위
단일 응답과 스트리밍은 같은 Agent를 소비하는 두 방식입니다. 최종 결과가 한 번에 필요한 저장·평가 작업에는 `ainvoke`가 맞고, 중간 조각을 사용자에게 보여 주려면 다음 절의 `astream`을 사용합니다. 예외가 발생했을 때 내부 예외 문자열을 그대로 HTTP 응답으로 내보내지 않고, 로그의 원인 정보와 공개 오류 코드를 분리합니다.

### 바로 다음 코드를 읽는 방법
SSE(Server-Sent Events)는 한 HTTP 응답 안에서 `event`, `id`, `data` 줄을 묶어 사건을 순서대로 보내는 텍스트 형식입니다. 이 실습은 POST 본문으로 질문을 받은 뒤 `token` 사건을 여러 번 보내고 마지막에 `done` 사건을 한 번 보냅니다. 빈 줄은 사건과 사건의 경계입니다. 정규식으로 응답을 나눈 다음 첫 사건의 종류와 식별자, 마지막 사건의 종류를 각각 검사합니다.

## 반복 실험과 결과 해석
문장 길이만 바꾸면 토큰 이벤트 수는 달라지지만 완료 이벤트는 한 번입니다.
### 이 단계에서 구분할 범위
`token`과 `done`을 나누면 클라이언트는 문자열 조각과 실행 완료를 혼동하지 않습니다. 진행률, 출처, 도구 호출을 추가할 때도 별도 사건 이름을 사용하면 데이터 형식을 독립적으로 발전시킬 수 있습니다. 다만 SSE의 `id`는 업무 결과의 영구 식별자와 목적이 다르므로, 재연결 위치와 대화 식별자를 한 필드에 무리하게 합치지 않습니다.

### 바로 다음 코드를 읽는 방법
인증은 요청한 주체를 확인하고, CORS는 브라우저가 다른 출처의 응답을 읽어도 되는지 결정하며, timeout은 기다릴 최대 시간을 제한합니다. 먼저 CORSMiddleware가 OPTIONS 사전 요청을 처리해 허용된 출처이면 200을 반환합니다. 그다음 실제 POST에서 인증 의존성이 Authorization 헤더를 검사하고, 헤더가 없으면 401을 반환합니다. `get_timeout`을 0.01초로 대체한 테스트는 느린 Agent가 단일 응답에서는 504, 스트림에서는 오류 사건으로 바뀌는 차이를 보여 줍니다.
## 인증 실패 관찰

### 이 단계에서 구분할 범위
CORS 허용은 인증 우회가 아니며, 서버 간 요청에는 브라우저의 CORS 검사가 적용되지 않습니다. timeout도 실행 취소가 하위 모델·도구까지 전달되는지 따로 확인해야 합니다. 운영에서는 연결 timeout, 전체 Agent timeout, 프록시의 유휴 timeout을 같은 숫자로 가정하지 말고 어느 계층이 먼저 끊는지 기록합니다.

# 실제 Agent HTTP 통합
OpenAI 모델과 조회 도구가 있는 LangChain `create_agent`를 FastAPI에서 실제 호출합니다.
## 실행 환경 준비
현재 폴더나 상위 폴더에서 `labs/part7/ch30-fastapi-serving`을 찾아 작업 폴더로 사용합니다. 비밀 키를 출력하지 않습니다.
### 이 준비 셀이 하는 일
이 준비 셀은 `Path.cwd().resolve()`로 현재 폴더를 절대 경로로 읽고, 현재 폴더와 부모 폴더에서 `agent_service`가 있는 첫 위치를 `next(..., None)`로 찾습니다. 찾지 못하면 `assert`가 실행을 중단합니다. 찾은 뒤 `os.chdir(lab)`이 이후 import와 파일 접근의 기준 폴더를 바꾸고, 마지막 출력은 실제 선택된 폴더 이름을 확인합니다.
## 키 존재 확인
상위 폴더의 `.env`를 읽고 키 값은 출력하지 않습니다.
### API 연결에 필요한 환경 변수 확인
`find_dotenv(usecwd=True)`는 현재 폴더부터 상위 폴더에서 `.env`를 찾고, `load_dotenv()`는 환경 변수를 읽습니다. `os.getenv()`로 키 설정 여부를 읽고 `bool()`로 참·거짓만 출력합니다. `assert has_key`는 키가 없으면 중단합니다. 이 셀은 모델이나 HTTP 경로를 호출하지 않습니다.
## 실제 ainvoke HTTP 요청
Agent는 운영 시간을 도구로 확인한 뒤 한 문장으로 답합니다.
`TestClient(app)`는 같은 프로세스 안에서 FastAPI 요청 처리를 시험하는 클라이언트입니다. `post()`에 경로, 인증 헤더, JSON 본문을 넘기면 해당 경로가 실행됩니다. `/v1/chat/live`의 내부 Agent는 실제 모델을 호출하므로 외부 모델 API 연결이 필요합니다. 반환된 HTTP 상태 코드와 답 문자열을 함께 확인합니다.
## 도구 호출 궤적 확인
같은 실제 Agent의 메시지에서 도구 이름, 입력, 도구 출력을 확인합니다.
`build_live_agent()`는 호출 객체를 준비하고 `await live_agent.ainvoke(...)`가 별도의 실제 실행을 시작합니다. `tool_calls`에는 모델이 요청한 도구 이름과 인수가 있고, `ToolMessage`에는 실행한 도구의 결과가 있습니다. 앞 HTTP 호출의 저장 궤적을 읽는 셀이 아니라 같은 질문으로 별도 실행한 궤적을 확인하는 셀입니다.
## 실제 astream HTTP 요청
같은 Agent의 모델 메시지 청크를 SSE token 이벤트로 받습니다.
SSE는 이벤트 이름과 데이터를 텍스트 블록으로 보내는 형식입니다. 아래에서는 `event: token` 블록을 고르고 `data:` 뒤의 JSON을 읽어 `token` 문자열을 연결합니다. TestClient에서 완성된 응답을 받아 해석하므로 화면에 조각이 실시간으로 보이는 지연을 측정하지 않습니다.
## 실험 결과 해석
결정적 그래프와 실제 모델 Agent의 출력 성질을 구분합니다.
### 이 단계에서 구분할 범위
답에 `18:00`이 포함됐다는 한 조건만으로 올바른 도구 실행을 증명할 수 없습니다. 모델이 우연히 같은 숫자를 생성했을 수도 있기 때문입니다. 그래서 HTTP 응답, 도구 호출 인수, 도구 결과, 스트림 완료를 서로 다른 관찰로 남깁니다. 이 검사는 현재 질문 한 건의 통합 경로를 확인하며 다른 요일과 오류 입력의 품질까지 일반화하지 않습니다.
