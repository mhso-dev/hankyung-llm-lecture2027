2이 내용을 배우는 이유

먼저 용어를 구분하면 오류를 찾을 때도 도움이 됩니다. 질문을 잘못 적은 경우, 모델에 필요한 자료를 빠뜨린 경우, 프로그램이 같은 요청을 계속 반복한 경우는 확인할 코드가 다릅니다. 이 절에서는 전체 위치를 파악한 뒤 입력 준비 → 호출 → 응답 확인을 직접 실행합니다.

4핵심 개념
질문 한 장과 질문을 처리하는 프로그램
도서관에서 상담을 받는 상황을 생각해 봅니다. 신청서의 질문은 “책을 몇 권 빌릴 수 있나요?”입니다. 상담원이 질문과 함께 회원 유형과 대출 규정을 읽으면 답을 정하는 데 필요한 자료가 늘어납니다. 상담 전에 회원 정보를 준비하고 상담 후 답을 기록하는 절차도 있습니다. 답에 필요한 정보가 빠졌다면 보충 자료를 요청하는 단계가 이어질 수 있습니다.
이 비유에서 직접 적은 질문과 지시에 해당하는 것이 프롬프트(prompt)입니다. 모델에 “한국어 한 문장으로 답하세요”라고 적는 문장도 프롬프트의 일부입니다. 컨텍스트(context)는 이번 호출에서 모델이 참고하도록 전달한 전체 정보입니다. 프롬프트와 함께 보낸 규정, 이전 대화, 예시가 여기에 포함됩니다. 로컬 폴더에 규정 파일이 있다는 이유만으로 모델이 그 파일을 읽는 것은 아닙니다. 프로그램이 내용을 요청에 포함해야 합니다.
하네스(harness)는 모델이 작업을 수행하도록 입력 준비·호출·결과 검사·기록 등을 갖춘 실행 틀을 말합니다. 루프(loop)는 결과나 상태를 확인하며 다음 단계를 반복하는 흐름입니다. 반복 조건을 Python 코드로 정할 수도 있고, 뒤에서 배울 에이전트에서는 모델이 다음 행동 선택에 참여할 수도 있습니다. 반복문이 있다는 사실만으로 에이전트가 되는 것은 아닙니다.
프롬프트에서 실행 흐름까지 설명 범위를 넓힌 학습용 지도와 세 제품의 역할입니다. 포함 관계는 어떤 범위를 설명하는지를 나타내며, 같은 자료형의 객체가 차례로 들어 있다는 뜻은 아닙니다.
도식의 안쪽 프롬프트에서 시작해 바깥쪽으로 읽습니다. 질문의 표현을 바꾸면 프롬프트를 바꾼 것입니다. 대출 규정을 추가하면 컨텍스트를 바꾼 것입니다. 답을 저장하거나 검증하는 코드를 추가하면 하네스의 기능을 늘린 것입니다. 결과를 보고 다시 요청하는 조건까지 정하면 루프를 설계한 것입니다. 색은 도식에 표시된 역할을 구분하는 표지이며, 글자와 경계선을 함께 읽습니다.
세 제품의 이름을 지도에 놓기
LangChain은 모델과 메시지를 공통 방식으로 다루는 프레임워크입니다. LangGraph는 상태를 유지하며 여러 단계를 실행하는 런타임을 제공합니다. DeepAgents는 긴 작업에 필요한 기능을 갖춘 하네스를 제공합니다. 이 세 제품은 서로 다른 역할을 맡으며 함께 사용될 수 있습니다. 제품의 전체 기능을 이번 절에서 외우거나 실행할 필요는 없습니다.
개인 노트에 위 네 범위와 세 제품 이름을 적고, 오늘 실행한 init_chat_model과 invoke를 LangChain 옆에 표시합니다. 이후 새 용어를 만나면 이 지도의 해당 위치에 추가합니다. Ch 13에서 프로그램이 정한 흐름을, Ch 20에서 모델이 도구를 선택하는 흐름을 배우면 두 경우를 서로 다른 표시로 구분할 수 있습니다.
입력 목록에서 응답 객체까지 한 줄씩 읽기
이 실습에서 먼저 연결할 이름은 model, messages, response 세 개입니다. model은 요청을 보낼 방법과 설정을 가진 객체이고, messages는 이번에 전달할 역할과 내용의 목록이며, response는 호출이 끝난 뒤 받은 응답 객체입니다. 모델 객체를 만든 뒤 질문 문자열을 바꾸는 것만으로 서버가 실행되지는 않습니다. response = model.invoke(messages)의 오른쪽 호출이 끝나야 왼쪽 이름에 결과가 대입됩니다.
("system", "두 문장 이내의 한국어로 답하세요.")에서 첫 값은 메시지 역할이고 둘째 값은 실제 문장입니다. system은 이 예제의 공통 지시, user는 현재 질문을 나타냅니다. 목록 순서가 전달 순서이며, messages[0]은 첫 메시지를 다시 사용합니다. 출력용 [role for role, _ in messages]는 각 튜플을 두 값으로 나누고 역할만 새 목록에 모읍니다. 밑줄 이름은 둘째 값을 이 계산에서 사용하지 않겠다는 관례입니다.
가령 같은 모델 객체로 도서관 규정을 요약한 뒤 상품 후기를 분류한다고 생각해 봅니다. 바뀌는 것은 매번 넘기는 메시지 목록입니다. 앞 요청의 응답을 다음 목록에 넣지 않으면 이 호출 코드는 두 요청을 하나의 대화로 연결하지 않습니다. 여러 질문을 보냈다는 사실과 대화 이력을 전달했다는 사실을 구분하면 다음 절의 메시지 역할을 이해할 수 있습니다.
같은 모델도 호출 방법에 따라 프로그램의 모양이 달라집니다
모델 객체는 한 가지 요청 방식에만 묶여 있지 않습니다. 고정 환경의 BaseChatModel에는 한 입력의 완성된 답을 받는 invoke(), 조각을 받는 stream(), 여러 독립 입력을 처리하는 batch(), 모델 응답을 기다리는 동안 다른 비동기 작업을 진행할 수 있는 ainvoke()가 있습니다. 네 메서드는 모두 모델에 질문을 보낼 수 있지만, 해결하려는 프로그램 문제가 다릅니다.
상황적합한 호출선택 이유확인할 결과
회원 한 명의 대출 규정 질문invoke()입력 하나와 완성된 답 하나의 관계가 분명합니다.AIMessage와 .text
긴 안내문을 채팅 화면에 표시stream()완료 전에 도착한 텍스트를 보여 줄 수 있습니다.조각 순서와 최종 결합 여부
서로 관계없는 설문 의견 100건 분류batch()독립 입력 목록을 같은 처리 규칙에 적용합니다.입력·출력 순서, 필요하면 return_exceptions=True로 입력별 오류 수집
웹 서버가 여러 사용자의 요청을 함께 처리ainvoke()한 호출을 기다리는 동안 다른 비동기 작업을 진행할 수 있습니다.await 경계와 예외 전달
batch()는 여러 질문을 하나의 대화로 합친다는 뜻이 아닙니다. LangChain의 기본 배치 처리는 독립 호출을 클라이언트 쪽에서 병렬로 실행하며, 제공자가 운영하는 별도의 배치 API와도 구분됩니다. 설문 의견 사이에 앞뒤 맥락이 필요하다면 독립 입력으로 나누기 전에 대화 단위부터 다시 정해야 합니다. ainvoke()도 모델 자체의 생성 시간을 줄이는 설정은 아닙니다. 기다리는 동안 Python 프로그램이 다른 일을 처리할 수 있게 하는 호출 방식입니다.
이번 절의 첫 실습에는 invoke()가 가장 적합합니다. 입력 검증, 네트워크 호출, 응답 객체라는 세 경계를 한 번에 확인할 수 있기 때문입니다. 04절에서는 같은 모델 객체에 stream()을 적용해 반환 단위가 어떻게 달라지는지 비교합니다. 메서드를 먼저 고르는 기준은 “어느 것이 더 고급인가”가 아니라 “완성된 답 하나, 중간 조각, 독립 입력 목록 중 무엇이 필요한가”입니다.
5실행 예제
init_chat_model은 모델과 통신할 객체를 준비합니다. openai:gpt-5.4-mini에서 콜론 앞은 제공자, 뒤는 모델 이름입니다. 객체를 준비하는 것과 질문을 전송하는 것은 다른 단계입니다. model.invoke(messages)를 실행할 때 실제 요청이 발생하며, 완료될 때까지 해당 셀이 실행 중으로 표시됩니다.
준비 셀의 출력 상한과 시간 제한도 읽습니다. 출력 토큰 상한은 모델이 반환할 수 있는 길이를 제한합니다. 시간 제한은 응답을 무한히 기다리지 않도록 설정한 값입니다. 토큰 수와 비용의 관계는 06절에서 계산합니다. 첫 실행에서는 이 값을 바꾸지 않고 메시지와 응답의 모양에 집중합니다.
확인할 점 생성된 문장과 type(response).__name__의 출력을 구분합니다. 전자는 모델이 작성한 내용이고, 후자는 Python이 확인한 실제 객체 타입입니다. 응답 타입은 AIMessage이며, response.text는 그 객체에서 텍스트를 읽는 속성입니다.
메시지 목록에서 사용자 질문만 바꾸면 같은 모델 객체로 다른 질문을 보낼 수 있습니다. 두 응답의 문장이 다르더라도 invoke를 호출하고 .text를 읽는 순서는 같습니다. 반환 객체에는 텍스트 외에 사용량 같은 항목도 들어 있습니다. 모델에게 객체 이름을 말하게 하는 방법으로 실제 Python 타입을 검증하지 않습니다.
아래 실패는 수업에서 직접 작성한 문자열 검사로 확인합니다. all()과 isinstance()의 결과에 따라 코드가 직접 TypeError를 발생시키며, LangChain 내부 검증이나 실제 API 오류를 재현한 결과가 아닙니다. 이 절의 텍스트 입력을 확인하는 제한된 검사입니다.
6일부러 실패해 보기
Before에서는 문자열이 있어야 할 메시지 내용에 None을 넣습니다. 이는 메시지 작성 오류를 다루는 실습입니다. 잘못된 내용이 입력 검증에서 거부되면 모델의 지식이나 답변 품질을 평가한 것이 아닙니다. 출력에 표시된 예외 유형과 값을 만든 코드를 함께 확인합니다.
After는 메시지 내용을 문자열로 고치고 같은 호출 방법으로 응답을 받습니다. 오류 처리 셀은 예상한 입력 검증 예외만 잡습니다. 키 오류나 네트워크 오류가 발생했다면 입력 오류를 확인한 것으로 대신 기록하지 않고 실제 오류 원인을 확인해야 합니다. 커널이 중단됐다면 메시지 값을 수정한 뒤 준비 셀부터 다시 실행합니다.
7주의할 점과 실무 메모
HTML은 설명을 읽고 코드를 복사하는 화면입니다. 복사한 코드는 Jupyter의 코드 셀에서 실행합니다. 출력 문장을 코드 셀에 붙여 넣지 않습니다. 실행 순서를 건너뛰면 아직 만들지 않은 변수 때문에 NameError가 발생할 수 있습니다.
모델의 답은 실행마다 달라질 수 있습니다. 같은 질문에서 문구가 달라졌다는 이유만으로 설치가 잘못됐다고 판단하지 않습니다. 먼저 응답 객체가 반환됐는지와 텍스트가 있는지 확인합니다. 키 값·인증 헤더·환경 변수 전체를 출력해서 문제를 진단하지 않습니다.
temperature, 출력 토큰 상한, timeout처럼 자주 보이는 초기화 인자도 모든 제공자와 모델에서 같은 범위로 지원된다고 가정하지 않습니다. init_chat_model()은 추가 인자를 선택한 통합 객체에 전달합니다. 따라서 공통 인터페이스가 있다는 사실과 제공자별 생성 옵션이 같다는 주장은 구분해야 합니다. 기본 실습은 모델·입력·호출 방법을 고정하고 한 항목씩 바꾸어 결과의 원인을 읽습니다.

반환된 AIMessage의 .text에서 생성 문장을 읽습니다.
다음 절에서는 메시지의 역할을 살펴보고 같은 요청을 다른 제공자 설정으로 보내는 코드를 만듭니다. 여기서 확인한 객체 준비와 호출의 구분은 제공자가 달라져도 계속 사용합니다.
9복습 문제
문제 1 · 입력 자료의 범위
질문은 그대로 두고 대출 규정 본문을 함께 보냈습니다. 지도에서 어느 범위를 바꾼 것인가요?
해설 컨텍스트에 정보를 추가한 것입니다. 질문 외에 모델이 참고할 자료가 늘었습니다. 파일을 저장만 하고 요청에는 넣지 않았다면 모델이 참고할 정보는 늘지 않습니다.
문제 2 · 실제 호출 위치
모델 객체를 만드는 셀과 invoke 셀 중 어느 셀을 다시 실행하면 새 질문 요청이 발생하나요?
해설 invoke 셀입니다. 호출을 반복하면 추가 사용량이 발생합니다. 객체 초기화만으로 질문의 답이 생성되는 것은 아닙니다.
문제 3 · 응답의 타입
모델이 답에 “문자열을 반환합니다”라고 썼습니다. 실제 객체 타입은 무엇으로 확인해야 하나요?
해설 Python의 type(response).__name__으로 확인합니다. 생성 문장은 타입 검사 결과가 아닙니다. response와 response.text도 서로 다른 값입니다.
문제 4 · 오류의 위치
None 메시지가 거부된 것을 모델의 환각 사례로 기록해도 되나요?
해설 안 됩니다. 이 실습은 입력 메시지의 형식 검증을 확인합니다. 모델이 근거 없는 내용을 생성한 상황과 구분해야 수정할 코드도 찾을 수 있습니다.

2이 내용을 배우는 이유
첫 호출이 성공한 뒤 다른 모델도 시험하고 싶어질 수 있습니다. 이때 질문까지 바꾸면 결과가 달라진 이유를 구분하기 어렵습니다. 이번에는 메시지 목록을 그대로 두고 제공자와 모델 설정을 바꿉니다. 응답을 같은 항목에 기록하는 연습을 한 뒤 06절에서 토큰·비용·지연을 함께 측정합니다.
LangChain은 여러 제공자의 모델을 비슷한 방법으로 호출하게 해 줍니다. 다만 같은 메서드 이름을 사용한다고 인증 키나 모델 옵션까지 같아지는 것은 아닙니다. 어떤 부분을 재사용하고 어떤 부분을 제공자별로 확인해야 하는지 실제 코드에서 살펴봅니다.
3앞에서 배운 내용
앞 절에서 만든 model 객체와 invoke, 응답의 .text를 다시 사용합니다. 딕셔너리는 제공자 이름과 설정을 연결하고, 반복문은 설정 하나씩 읽습니다. continue는 현재 제공자의 처리를 마치고 다음 제공자로 이동하는 Python 문법입니다.
이 절도 새 커널에서 시작합니다. 설치 셀은 세 제공자의 통합 패키지를 준비합니다. 기본 OpenAI 실습에는 OPENAI_API_KEY가 필요하고, 다른 두 제공자를 호출하려면 ANTHROPIC_API_KEY와 GOOGLE_API_KEY를 .env에 추가합니다. 키가 없는 상태에서도 해당 행을 미실행으로 기록하는 방법을 확인할 수 있습니다.
4핵심 개념
같은 문장도 메시지의 역할과 함께 전달합니다
상담원에게 전달하는 업무 지침과 고객이 적은 문의를 서로 다른 칸에 보관한다고 생각해 봅니다. 두 칸을 구분하면 문의가 바뀌어도 공통 지침을 유지할 수 있습니다. 채팅 요청에서도 메시지(message)는 역할과 내용을 함께 담습니다. 역할은 문장이 요청에서 어떤 위치에 있는지 표시하고, 내용은 실제 지시나 질문입니다.
시스템 메시지(system message)에는 응답에 적용할 공통 규칙을 둡니다. 이 실습의 “한 문장의 한국어로 답하세요”가 해당합니다. 사용자 메시지(user message)에는 이번 질문을 둡니다. 모델이 답할 때는 메시지 목록을 함께 참고합니다. 역할 표시는 유용한 구분이지만, 모든 입력에서 규칙을 반드시 지킨다는 보장은 아닙니다. 실제 답을 읽어 조건 준수 여부를 확인해야 합니다.
("system", "...")처럼 역할 이름과 문자열을 묶은 튜플은 짧은 표현입니다. SystemMessage와 HumanMessage 객체로 같은 역할을 명시할 수도 있습니다. LangChain의 HumanMessage.type은 human입니다. 튜플에서 user를 썼다고 해서 반드시 .type도 같은 문자열일 것으로 예상하지 말고 출력으로 확인합니다.
제공자를 바꾸는 설정
제공자(provider)는 모델 API를 운영하는 서비스입니다. openai:gpt-5.4-mini, anthropic:claude-haiku-4-5, google_genai:gemini-2.5-flash-lite에서 콜론 앞은 LangChain이 사용할 제공자 통합을, 뒤는 모델 식별자를 나타냅니다. 통합 패키지(integration package)는 공통 호출을 해당 서비스의 요청 형식으로 바꾸는 코드를 제공합니다.
같은 메시지를 제공자별 통합으로 전달하고 응답을 공통 메시지 객체에서 읽습니다. 세 갈래는 비교할 후보이며, 키가 준비되지 않은 갈래에서는 실제 요청이 발생하지 않습니다.
도식에서 초록색 입력 자료인 메시지 목록을 먼저 읽습니다. 제공자 선택과 호출 순서는 학생이 작성한 파란색 코드가 정합니다. 모델이 답을 생성하는 단계는 보라색입니다. 세 모델이 서로 대화하거나 다음 모델을 선택하는 에이전트 흐름은 없습니다. Python 반복문이 등록된 설정을 하나씩 처리합니다.
응답의 텍스트는 공통으로 .text에서 읽습니다. content_blocks는 응답 내용을 종류가 있는 표준 블록으로 볼 때 사용합니다. 이 절에서는 텍스트 블록을 관찰하고 04절에서 조각 응답과 함께 자세히 읽습니다. 한 제공자의 전용 블록이나 옵션을 다른 제공자도 지원한다고 가정하지 않습니다.
메시지 역할은 접근 권한이 아닙니다
시스템 메시지를 회사 정책처럼, 사용자 메시지를 고객 질문처럼 구성하면 지시의 출처를 읽기 쉬워집니다. 그러나 시스템 역할이 데이터베이스 권한처럼 강제되는 것은 아닙니다. 사용자가 “앞의 규칙을 무시하세요”라고 적었을 때 실제 응답이 정책을 따르는지 별도로 확인해야 합니다. 중요한 규칙은 메시지에 적는 것에 더해 출력 검사와 허용 범위 제한으로 보완합니다.
상황에 따라 같은 문장도 역할이 달라집니다. “반품 기한은 14일입니다”가 시스템 메시지에 있으면 답변 규칙이나 참고 정책으로 작동합니다. 이전 상담의 모델 답으로 넣으면 대화 기록이 됩니다. 사용자가 새로 제공한 주장으로 넣으면 검증되지 않은 입력입니다. 문자열만 비교하면 같지만, 프로그램이 그 문장을 신뢰하고 사용하는 방식은 달라야 합니다.
역할 이름과 메시지 객체의 관계
SystemMessage("한 문장으로 답하세요.")는 역할을 클래스로 명시한 메시지 객체를 만듭니다. 여기서 괄호 안 문장은 content에 해당합니다. 같은 내용을 튜플 ("system", "한 문장으로 답하세요.")로 적으면 모델 통합이 메시지 형식으로 읽습니다. 객체 생성과 모델 호출은 별개이므로 SystemMessage나 HumanMessage를 생성하기만 해서는 답이 나오지 않습니다.
사용자 입력을 뜻하는 튜플의 user와 HumanMessage의 type에 나타나는 human은 이 실습에서 같은 역할을 표현하는 서로 다른 표기입니다. 클래스 이름, 객체의 타입 표시, 제공자에게 전달되는 역할 필드가 항상 같은 문자열인 것은 아닙니다. 아래 출력에서 system, human을 본 뒤 메시지 내용을 읽으면 두 표현을 대응시킬 수 있습니다.
예를 들어 번역 서비스에서는 공통 번역 규칙을 system에, 번역할 문장을 user에 둡니다. 여러 사람의 문의를 처리할 때도 공통 규칙과 매번 바뀌는 내용을 따로 만들 수 있습니다. 이전 답을 assistant 메시지로 포함하는 것은 대화 흐름을 제공하는 방법입니다. 그 답이 정확한 근거인지는 별도로 판단해야 하며, 이전 답에 있던 오류를 사실로 확정하지 않습니다.
5실행 예제
코드는 제공자별로 키 이름과 모델 식별자를 보관합니다. 키가 있으면 모델 객체를 만들고 invoke(messages)를 실행합니다. 키가 없으면 요청을 보내지 않고 이유를 기록합니다. 실제 요청에서 발생한 인증·네트워크 오류를 이 준비 상태와 같은 것으로 처리하지 않습니다.
확인할 점 records의 각 행에서 먼저 status를 읽습니다. executed 행에는 실제 응답과 사용량이 있습니다. skipped 행에는 실행하지 않은 이유가 있습니다. 사용량이 없는 항목을 0으로 추정해서 비교하지 않습니다.
저장된 실행에서는 OpenAI 키만 준비되어 OpenAI 응답을 받았습니다. Anthropic과 Google 행은 각각 필요한 키 이름을 표시합니다. 이어지는 메시지 객체 셀의 ['system', 'human'] 출력은 LangChain 객체의 역할을 확인한 결과입니다. 이 객체 생성 자체는 새 API 호출이 아닙니다.
직접 비교할 때는 질문과 공통 응답 길이 지시를 유지합니다. 키를 추가한 뒤 제공자별 호출 셀과 기록 확인 셀을 다시 실행하면 됩니다. 같은 출력 상한을 설정해도 실제 길이나 지연이 같아지는 것은 아닙니다. 제공자마다 토큰을 나누는 방식과 모델의 동작이 다를 수 있습니다.
6실험 결과 해석
이번 저장 결과로 확인할 수 있는 것은 OpenAI의 실제 응답과 두 제공자의 미준비 상태입니다. 세 서비스의 답변 품질이나 속도 순위는 정할 수 없습니다. 미실행 행은 답이 없다는 측정 결과도, 모델 성능이 나쁘다는 결과도 아닙니다.
키가 모두 있는 환경에서는 각 응답을 읽고 한 문장의 한국어라는 조건과 질문에 맞는 설명인지를 먼저 확인합니다. 이 절은 한 질문으로 공통 호출을 익히는 예제입니다. 한 번 빠른 응답을 받았다는 이유만으로 그 모델이 항상 빠르다고 결론 내리지 않습니다. 06절에서 시간과 사용량을 같은 행에 기록하고 비교 범위를 더 명확히 정합니다.
7주의할 점과 실무 메모
.env 파일의 변수 이름은 정확히 일치해야 합니다. 제공자 계정이 서로 다르므로 한 서비스의 키를 다른 서비스의 변수에 복사하지 않습니다. 셀에는 키 문자열 대신 변수 이름만 적습니다. 키가 준비됐다는 출력은 인증 성공을 의미하지 않으며, 실제 요청이 성공해야 해당 키와 모델의 접근 권한을 확인한 것입니다.
검증 환경에서는 세 통합 패키지를 설치했지만 Anthropic·Google의 실제 API 호출은 키가 없어 확인하지 못했습니다. 두 모델의 계정별 접근 권한·옵션 지원·응답 사용량은 각 키를 준비한 환경에서 확인해야 합니다. 온라인 문서가 바뀌면 잠금 파일의 버전과 설치 셀의 버전을 함께 점검합니다.
8정리와 다음 절
메시지는 역할과 내용을 묶으며, 튜플과 메시지 객체로 표현할 수 있습니다.
제공자 전환에서는 질문을 고정하고 모델 식별자·통합 패키지·키를 확인합니다.
실제 응답과 미실행 이유를 서로 다른 상태로 기록합니다.
다음 절에서는 응답을 자유로운 문장 대신 이름 있는 필드로 받습니다. 이 절의 AIMessage를 읽는 경험을 바탕으로 구조화된 객체와 원본 응답의 차이를 확인합니다.
9복습 문제
문제 1 · 공통 지침의 위치
질문이 바뀌어도 “한 문장의 한국어”라는 규칙을 유지하려면 어느 메시지에 두는 것이 적절한가요?
해설 이 실습에서는 시스템 메시지에 둡니다. 이번 질문은 사용자 메시지에 두어 공통 규칙과 입력을 구분합니다. 실제 응답이 규칙을 따랐는지도 읽어 확인합니다.
문제 2 · 객체의 역할 이름
튜플의 user와 HumanMessage의 human은 서로 다른 제공자를 뜻하나요?
해설 아닙니다. 둘 다 사용자 쪽 메시지를 표현하는 LangChain의 표기입니다. 제공자는 모델 식별자의 접두어에서 정합니다.
문제 3 · 미실행 기록
키가 없는 Google 행의 비용과 시간을 0으로 적으면 어떤 오해가 생기나요?
해설 무료이며 즉시 응답한 측정값처럼 보일 수 있습니다. 실제 요청이 없었으므로 준비되지 않은 키 이름과 미실행 상태를 기록합니다.
문제 4 · 비교 조건
OpenAI에는 한 문장 답을, 다른 모델에는 긴 보고서를 요청했습니다. 지연 차이를 모델 차이로만 설명할 수 있나요?

2이 내용을 배우는 이유
모델이 “AIMessage는 모델의 답변입니다. 난이도는 초급입니다”라고 답했다고 생각해 봅니다. 사람은 읽을 수 있지만, 프로그램이 개념 이름·설명·난이도를 각각 저장하려면 어디서 문장을 나눌지 결정해야 합니다. 응답 표현이 바뀔 때마다 문자열을 나누는 규칙을 추가하면 유지하기 어렵습니다.
이번 절에서는 받을 항목을 먼저 정의합니다. 모델의 응답을 개념 이름, 설명, 1~3의 난이도로 받고 Python 객체에서 각 값을 읽습니다. 데이터의 모양이 어긋났을 때 어느 값이 문제인지 확인하는 과정까지 실행합니다.

4핵심 개념
빈칸이 정해진 학습 카드
양식이 없는 메모와 이름·설명·난이도 칸이 인쇄된 카드를 비교해 봅니다. 양식이 있는 카드에서는 무엇을 적을지 미리 알 수 있고, 비어 있는 칸도 찾을 수 있습니다. 구조화 출력(structured output)은 이처럼 프로그램이 받을 항목과 형식을 정해 응답을 받는 방법입니다.
스키마(schema)는 필요한 항목과 값의 형식을 정의한 것입니다. 각 항목을 필드(field)라고 합니다. 실습의 concept와 explanation은 문자열이고, difficulty는 정수입니다. 이 이름을 그대로 사용해야 프로그램이 어느 값을 읽을지 알 수 있습니다.
Pydantic은 선언한 타입과 제약에 맞게 데이터를 읽고 검사하는 Python 라이브러리입니다. BaseModel을 상속한 StudyCard에 세 필드를 선언합니다. Field의 description은 항목의 뜻을 설명합니다. ge=1은 1 이상, le=3은 3 이하라는 조건입니다. 설명 문장에 “1~3”을 적는 것과 실제 범위 제약을 선언하는 것을 구분합니다.
응답 형식과 허용 범위를 먼저 선언하고, 생성된 값을 그 기준으로 검사합니다. 스키마는 요청과 검증에 사용되는 기준이며 모델이 작성한 사실의 근거는 아닙니다.
도식에서 학생이 정한 필드와 제약을 먼저 확인합니다. 모델이 응답을 만드는 보라색 단계 이후에 노란색 검증 결과를 읽습니다. 실습에서는 difficulty=7인 자료가 범위를 벗어나고 difficulty=2인 자료는 범위에 들어갑니다. 검증을 통과해도 설명 문장이 사실인지까지 확인된 것은 아닙니다.
문자열을 객체로 읽는 것과 오류를 읽는 것
파싱(parsing)은 응답 내용을 프로그램이 다룰 구조로 읽는 처리입니다. model.with_structured_output(StudyCard)는 모델에 이 형식을 적용한 호출 객체를 만듭니다. 성공 결과는 일반 호출의 AIMessage 대신 StudyCard 객체로 읽습니다. model_dump()를 호출하면 세 필드를 딕셔너리로 확인할 수 있습니다.
검증 오류(ValidationError)는 값이 선언한 조건을 만족하지 못할 때 발생합니다. 오류를 숨기고 빈 카드로 바꾸면, 다음 코드가 정상 데이터로 오해할 수 있습니다. 어느 필드가 어떤 제약에 걸렸는지 확인한 뒤 입력이나 정의를 고쳐야 합니다.
include_raw=True를 사용하면 결과에 raw, parsed, parsing_error가 들어갑니다. raw는 원본 응답, parsed는 읽고 검증한 결과, parsing_error는 파싱이나 검증에서 발생한 오류입니다. 오류가 없으면 마지막 값은 None입니다. API 자체가 인증 오류나 통신 오류로 실패한 경우까지 이 옵션이 정상 결과로 바꾸는 것은 아닙니다.
with_structured_output의 준비와 실행 구분
이 메서드는 이 절에서 처음 배웁니다. model.with_structured_output(StudyCard)에서 점 앞의 model은 준비한 채팅 모델이고, 괄호 안의 StudyCard는 만들어 달라는 카드의 형식입니다. StudyCard()처럼 빈 카드 객체를 만드는 호출이 아니라 클래스 자체를 전달합니다. LangChain이 필드 설명과 제약을 읽어 모델 호출에 적용할 수 있도록 하기 위한 것입니다.
반환된 structured_model은 나중에 실행할 수 있는 호출 객체입니다. 이 줄만으로 학습 카드가 생성되지 않습니다. 다음 structured_model.invoke("AIMessage를 설명하세요")가 요청을 실행하고, 성공하면 읽고 검증한 StudyCard 인스턴스를 반환합니다. 따라서 card.difficulty로 필드 값을 읽고 card.model_dump()로 딕셔너리 표현을 얻습니다. invoke()의 입력은 카드에 넣을 내용을 요청하는 문장이고, 스키마 자체와 역할이 다릅니다.
학습 카드와 주문 입력을 비교하면 같은 원리가 더 분명해집니다. 카드에서는 난이도 범위가 중요하고 주문에서는 품명이 비어 있지 않은지와 수량이 양수인지가 중요합니다. 아래 주문 예시는 개발자가 직접 만든 JSON을 읽어 검증합니다. 주문을 모델이 추출했다고 가정하지 않으며, 필드 규칙을 바꿔도 실제 재고나 주문의 존재 여부까지 확인되는 것은 아닙니다.
스키마 표현은 다음 코드가 무엇을 요구하는지에 맞춥니다
같은 세 필드라도 Pydantic 모델, TypedDict, JSON Schema로 표현할 수 있습니다. 선택 기준은 문법의 길이보다 결과를 어디에서 검증하고 누구와 공유하는가입니다. Python 프로그램 안에서 범위 검증과 오류 위치가 필요하면 Pydantic이 알맞습니다. 타입 힌트와 고정된 키만 필요하면 TypedDict가 가볍습니다. Python 밖의 서비스와 같은 정의를 교환해야 하면 언어에 덜 종속적인 JSON Schema가 유리합니다.
상황스키마 선택얻는 것추가로 확인할 것

생성 방식의 엄격함과 Pydantic의 엄격함은 다른 층입니다
with_structured_output()의 method는 모델이 구조를 생성하도록 요청하는 방법을 고릅니다. json_schema는 제공자의 전용 구조화 출력 기능을 사용하고, function_calling은 스키마에서 도구 호출 형식을 만들어 결과를 받으며, json_mode는 유효한 JSON 생성을 요청하되 필요한 스키마 설명을 프롬프트에도 제공해야 합니다. 어느 방법을 지원하는지는 제공자·모델·통합 버전에 따라 다릅니다.
고정 환경에서 ChatOpenAI.with_structured_output()은 세 방법과 strict 인자를 제공하고 기본 방법은 json_schema입니다. 같은 환경의 Anthropic 통합은 function_calling과 json_schema를, Google 통합은 세 방법을 시그니처에 표시합니다. 시그니처에 이름이 있다는 사실만으로 선택한 모델과 계정에서 항상 성공한다고 단정하지 않습니다. 수업의 OpenAI 기본 경로처럼 한 조합을 실제로 실행해 확인해야 합니다.
여기서 구조화 출력의 strict와 Pydantic의 엄격 모드(strict mode)를 섞지 않습니다. 앞의 설정은 제공자 API가 스키마를 얼마나 엄격히 따르게 할지에 관한 옵션입니다. 뒤의 설정은 Python이 이미 받은 값을 다른 타입으로 변환해 받아들일지에 관한 검증 규칙입니다. 예를 들어 기본 Pydantic 검증은 정수 필드에 문자열 "2"가 들어오면 정수 2로 변환할 수 있지만, strict=True는 Python 입력의 타입이 맞지 않으면 거부합니다. ConfigDict(extra="forbid")는 선언하지 않은 필드가 추가됐을 때 오류를 냅니다. 타입 변환, 추가 필드, 값의 범위는 서로 다른 검사이므로 필요한 규칙을 각각 정합니다.
설문 분석을 예로 들면, 응답 번호 "2"를 정수로 받아도 되는 CSV 가져오기 단계에서는 변환이 편리합니다. 이미 정수만 전달하기로 정한 내부 API 경계에서는 문자열이 들어온 사실을 조기에 찾기 위해 엄격 검증이 더 적합합니다. 반대로 모델이 설명용 confidence_reason 필드를 새로 반환했을 때 이를 버려도 되는지, 입력 형식 변화로 보고 거부해야 하는지는 데이터 사용 목적에 따라 결정합니다.
5실행 예제
먼저 AIMessage에 관한 카드를 만들고 각 필드와 객체 타입을 확인합니다. 다음에는 주제만 SystemMessage로 바꾸고 같은 스키마를 사용합니다. 설명 문구는 달라질 수 있지만, 프로그램은 같은 필드 이름으로 값을 읽을 수 있습니다.
이어지는 로컬 셀은 문자열 "2"가 기본 검증에서는 정수로 변환되지만 strict=True에서는 int_type 오류로 거부되는 차이와, extra="forbid"가 선언하지 않은 source 필드를 extra_forbidden 오류로 거부하는 결과를 확인합니다. 주문 예시에서는 잘못된 JSON의 JSONDecodeError와 수량 0의 greater_than_equal 오류를 구분합니다. JSON 파싱과 Pydantic 검증을 모두 통과해도 실제 상품명·수량·주문 여부가 사실인지는 원자료와 별도로 대조해야 합니다.
확인할 점 일반 호출과 구조화 호출의 반환 타입을 구분합니다. card.model_dump()의 세 필드가 스키마와 대응하는지 읽고 난이도가 허용 범위에 있는지 확인합니다. 자연스러운 설명 문장만 보고 형식 검증이 성공했다고 추측하지 않습니다.
이후 실제 모델에 “difficulty는 반드시 9로 쓰세요”라는 요구를 보냅니다. 1~3이라는 스키마 제약과 맞지 않는 입력입니다. 결과의 parsed와 parsing_error를 함께 읽습니다. 저장된 실행에서는 모델이 허용 범위의 값을 반환해 parsing_error가 None이었습니다. 따라서 이 호출에서 구조화 출력의 검증 실패를 관찰했다고 말할 수 없습니다. 충돌하는 입력을 보내도 어떤 응답이 나오는지는 모델과 형식 지원에 따라 달라집니다.
6일부러 실패해 보기
모델 호출에서 오류가 나지 않았더라도 프로그램의 오류 처리 경로를 확인할 수 있습니다. 아래 비교는 직접 만든 딕셔너리에 Pydantic 검증을 적용하는 로컬 실습입니다. 이 자료를 모델이 생성한 것으로 표시하지 않습니다.
Before는 난이도 7을 넣어 less_than_equal 오류를 확인합니다. 이 이름은 값이 설정된 상한 이하여야 한다는 조건을 뜻합니다. After는 개념 이름과 설명을 유지하고 난이도만 2로 바꿉니다. 같은 스키마로 객체가 만들어졌다면 바꾼 값이 범위 검증에 영향을 주었다고 확인할 수 있습니다.
오류 처리 코드는 예상한 ValidationError만 잡습니다. 모든 예외를 같은 검증 오류로 처리하면 인터넷 연결 문제와 데이터 문제를 구분하기 어렵습니다. 실제 프로그램에서는 잘못된 값의 원본과 제약을 확인하고 수정 가능한 입력인지 판단합니다.
7주의할 점과 실무 메모
Pydantic은 기본 설정에서 일부 입력을 선언된 타입으로 변환합니다. 타입 이름을 적었다는 이유만으로 원래 입력의 타입까지 엄격하게 제한했다고 생각하지 않습니다. 엄격 모드를 기존 프로그램에 적용하면 이전에 변환되어 통과하던 값이 실패할 수 있으므로 입력 출처별로 먼저 관찰합니다.
형식이 맞는 답에도 잘못된 정보가 들어갈 수 있습니다. 필드의 존재·타입·범위 검증과 내용의 사실 확인은 다른 작업입니다. 이 장에서 만든 형식 검증 경험은 Ch 7의 출력 프롬프트 설계와 Ch 11의 평가 기준을 구분하는 데 사용합니다. 에이전트의 자동 출력 전략은 아직 구현하지 않습니다.
8정리와 다음 절
스키마에 필드·타입·값의 범위를 선언하고 구조화된 객체를 받습니다.
원본 응답, 파싱한 값, 오류를 나누어 읽으면 실패한 위치를 찾을 수 있습니다.
직접 만든 자료의 범위 검증과 실제 모델 응답의 형식 검증은 다른 실험입니다.
다음 절에서는 응답을 다 받을 때까지 기다리는 대신 도착하는 조각을 읽습니다. 조각이 아직 완성되지 않았을 때와 최종 결과를 검사할 때를 구분하는 데 이번 절의 파싱·검증 개념을 사용합니다.

description="난이도는 1~3"만 적는 것과 ge=1, le=3도 선언하는 것은 어떻게 다른가요?

해설 형식과 내용은 별도로 확인해야 합니다. 필드와 값 범위는 맞아도 설명은 틀릴 수 있습니다. 공식 자료나 정해 둔 정답 기준과 설명을 대조합니다.

2이 내용을 배우는 이유
모델이 긴 답변을 모두 만든 뒤 화면에 표시하면 사용자는 첫 문장을 보기까지 기다려야 합니다. 스트리밍(streaming)은 모델이 준비한 응답 조각을 차례로 전달하여 화면을 먼저 갱신하게 합니다. 채팅 화면에서 글자가 이어서 나타나는 동작은 대개 이 방식을 사용합니다. 사용자는 답변 생성을 시작했다는 사실을 일찍 알 수 있고, 프로그램은 도착한 부분부터 화면에 표시할 수 있습니다.
다만 화면에 글자가 나타났다는 사실과 응답 처리가 끝났다는 사실은 서로 다릅니다. 중간 조각은 문장의 한 부분일 수 있고, 구조화된 JSON이라면 여는 중괄호만 도착한 상태일 수도 있습니다. 중간 조각을 완성된 답으로 저장하거나 검증하면 정상적인 응답도 실패로 처리할 수 있습니다. 따라서 화면 표시와 최종 저장의 시점을 분리해야 합니다.
제공자마다 원본 응답의 모양도 다를 수 있습니다. LangChain은 읽기 쉬운 텍스트와 표준 콘텐츠 블록을 함께 제공하여 이러한 차이를 다룰 수 있게 합니다. 이번 절에서는 블록 개수만 세지 않습니다. 실제 블록의 type과 텍스트 일부를 확인하고, 어떤 값을 사용자 화면과 후속 처리에 사용할지 판단합니다.
3앞에서 배운 내용
첫 절에서는 init_chat_model()로 모델 객체를 만들고 invoke()를 호출했습니다. invoke()는 호출이 끝난 뒤 하나의 AIMessage를 반환했습니다. 02절에서는 AIMessage.text로 텍스트를 읽고 content_blocks로 표준화된 내용 블록을 확인했습니다. 이번 절에서는 원본 내용인 content와 스트리밍 조각까지 범위를 넓힙니다.
이번 노트북도 새 Python 3.12 커널에서 독립적으로 시작합니다. 앞 절의 model 변수를 이어서 사용하지 않습니다. 같은 초기화 코드를 다시 실행하고, 실제 네트워크 요청이 시작되는 stream(messages) 경계를 직접 확인합니다.
4핵심 개념
봉투 한 개와 이어지는 쪽지
invoke()의 반환값을 완성된 답이 든 봉투 한 개라고 생각해 봅니다. stream()의 반환값은 작성되는 순서대로 도착하는 여러 장의 쪽지에 가깝습니다. 각 쪽지가 AIMessageChunk입니다. 첫 조각에는 텍스트가 없을 수 있고, 뒤의 여러 조각에 단어나 문장 부호가 나뉘어 들어올 수 있습니다. 마지막 조각에는 텍스트 대신 응답 종료 이유나 사용량 정보가 담길 수도 있습니다.
스트림은 한 번에 전체 목록을 반환하지 않습니다. for 반복문이 다음 조각을 요청할 때마다 도착한 값을 하나씩 받습니다. 프로그램은 그 자리에서 chunk.text를 화면에 표시하고, 같은 조각을 목록에도 보관할 수 있습니다. 화면에 표시만 하고 조각을 버리면 연결이 끝난 뒤 완성된 메시지를 다시 만들 수 없습니다.
content, text, content_blocks
content는 제공자 응답과 가까운 원본 표현입니다. 단순한 모델 응답에서는 문자열일 수 있지만, 텍스트와 다른 종류의 정보가 섞이면 목록처럼 보일 수도 있습니다. 제공자별 문제를 조사하거나 원본 구조를 보존해야 할 때 확인합니다.
text는 메시지에서 사람이 읽을 텍스트 부분을 꺼낸 문자열입니다. 채팅 화면에 문장을 이어 붙이거나 최종 답을 표시할 때 사용하기 좋습니다. 이번 실행에서 텍스트 청크의 표준 블록은 type이 text인 사전 형태로 나타나며, text 항목에 해당 조각의 글자가 담깁니다. 텍스트가 없는 시작·종료 청크는 빈 블록 목록으로 나타날 수 있습니다. 이 차이를 확인해야 빈 청크를 오류로 잘못 판정하지 않습니다.
content_blocks는 텍스트, 추론 정보, 이미지처럼 서로 다른 내용을 LangChain의 표준 블록으로 읽는 속성입니다. 예를 들어 {"type": "text", "text": "스트리밍"}과 같은 텍스트 블록은 종류와 값을 분리해서 보여 줍니다. 실제 출력의 텍스트는 실행마다 달라질 수 있으므로, 교재에서는 특정 단어의 위치보다 type과 필드의 역할을 읽습니다. 블록의 개수만으로는 어떤 내용이 도착했는지 알 수 없습니다.
조각 결합과 완료 시점
AIMessageChunk는 + 연산으로 결합할 수 있습니다. 첫 조각을 combined에 넣고 다음 조각을 차례로 더하면 순서를 보존한 하나의 결합 메시지가 됩니다. 모든 반복이 정상적으로 끝난 뒤 combined.text를 읽으면 화면에 표시한 조각과 같은 흐름의 최종 텍스트를 얻습니다. 저장, 구조 검증, 후속 함수 호출은 이 완료 지점에서 수행합니다.
사용량 메타데이터는 모든 청크에 항상 들어오는 값이 아닙니다. OpenAI 통합에서는 현재 고정 버전에서 stream_usage=True를 지정하여 스트리밍 사용량 수집을 요청할 수 있습니다. 그래도 코드는 실제로 제공된 usage_metadata만 합산해야 합니다. 정보가 없다는 것은 토큰을 사용하지 않았다는 뜻이 아닙니다. 따라서 누락 상태는 None이나 unknown으로 남기고 0으로 바꾸지 않습니다.
스트리밍은 전달 방식이며 완료 규칙은 프로그램이 정합니다
스트리밍을 사용한다고 모든 처리를 조각 단위로 수행할 수 있는 것은 아닙니다. 화면에 글자를 추가하는 일은 조각마다 할 수 있지만, 전체 문장의 금칙어 검사나 JSON 검증은 마지막 조각까지 받은 뒤에 해야 합니다. 번역 자막처럼 문장 경계를 기다려야 자연스러운 처리도 있습니다. 어느 작업이 중간 결과를 받아들일 수 있는지 먼저 나누면 화면 표시와 최종 확정 시점을 혼동하지 않습니다.
상황조각 도착 중에 할 일완료 뒤에 할 일완료 전에 중단되면
긴 개념 설명 채팅도착한 텍스트를 순서대로 표시전체 답을 대화 기록에 저장부분 표시와 미완료 상태를 함께 남깁니다.
구조화된 설문 결과 JSON진행 상태만 표시결합 후 파싱과 스키마 검증미완성 JSON을 유효한 결과로 저장하지 않습니다.
실시간 자막 초안임시 문구로 표시문장 단위 정리와 확정확정 전 자막임을 화면에서 구분합니다.
텍스트와 이미지 설명이 섞인 응답블록의 type별로 렌더링블록 순서와 원본 참조를 보존지원하지 않는 블록을 임의의 문자열로 바꾸지 않습니다.
사용량 기록메타데이터가 있는 청크를 보관결합 메시지의 최종 값을 확인누락을 0으로 기록하지 않습니다.
완료는 “마지막 글자가 화면에 보였다”라는 추측이 아니라 반복문이 정상 종료되고 최종 메시지를 구성했다는 프로그램 상태로 표현합니다. 연결 오류가 발생하면 이미 표시한 문자열을 지울지 유지할지는 화면 정책의 문제입니다. 어느 쪽을 고르더라도 저장 레코드에는 completed와 partial을 구분할 정보가 필요합니다.
조각 수와 토큰 수를 같은 단위로 읽지 않습니다
한 청크에는 글자 하나가 들어올 수도 있고 여러 토큰이 들어올 수도 있습니다. 시작·종료 메타데이터만 담은 빈 텍스트 청크도 있습니다. 따라서 청크 20개는 출력 토큰 20개, 네트워크 요청 20회, 화면 갱신 20회 중 어느 것과도 자동으로 같아지지 않습니다. 이번 실제 출력의 청크 수와 콘텐츠 블록 수가 다른 것도 서로 세는 대상이 다르기 때문입니다.
AIMessageChunk의 덧셈은 텍스트만 이어 붙이는 문자열 연산보다 넓은 의미가 있습니다. 텍스트, 도구 호출 조각, 사용량 같은 메시지 필드를 결합 규칙에 따라 모읍니다. 최종 결과가 텍스트뿐이라면 combined.text가 편리하지만, 여러 종류의 콘텐츠가 있는 응답은 combined.content_blocks를 함께 확인해야 정보 손실을 찾을 수 있습니다.
도식 읽기
질문이 stream()으로 전달되고 여러 AIMessageChunk가 도착한 뒤 최종 메시지로 결합되는 흐름입니다. 화살표 위의 작은 단위는 네트워크에서 받은 조각이고, 마지막 상자는 모든 조각을 순서대로 더한 결과입니다.세 번째 상자의 텍스트 조각이 화면에 먼저 표시되고, 마지막 상자에서 저장 가능한 답이 완성되는 순서를 확인합니다.
청크 하나와 최종 응답을 구분해 읽기
청크(chunk)는 스트림에서 한 번 전달받는 응답 조각입니다. model.stream(messages)는 조각을 차례로 읽을 수 있는 반복자를 제공하며, for chunk in ...가 이를 순서대로 읽습니다. 각 chunk는 AIMessageChunk이고 .text는 그 조각의 텍스트입니다. 청크 경계가 단어·문장·토큰 하나의 경계와 항상 같다고 가정하지 않습니다.
예를 들어 화면에 “대출은”과 “ 3권까지입니다.”가 순서대로 도착한다면, 첫 조각만으로 최대 권수를 정할 수 없습니다. 이 문장은 원리를 설명하기 위한 가정입니다. 실제 예제에서는 저장된 chunks 목록을 읽고 각 조각을 +로 결합합니다. 이는 단순 문자열 덧붙이기와 달리 메시지 조각의 자료를 병합하는 연산이며, 최종 변수도 AIMessageChunk입니다.
print(..., end="", flush=True)의 end는 매 출력 뒤의 줄바꿈을 없애고 flush는 출력 버퍼에 남기지 않고 표시하도록 요청합니다. 두 인자는 모델의 생성 설정이 아니라 Python 화면 출력 설정입니다. 채팅 화면은 조각이 올 때마다 표시할 수 있지만, 결과를 파일에 저장하거나 구조를 검사하는 단계는 완료된 내용을 대상으로 해야 하는 경우가 많습니다.
5실행 예제
노트북은 OpenAI 모델에 짧은 설명을 요청하고 stream()에서 받은 청크를 목록에 저장합니다. 반복문 안에서는 chunk.text를 줄바꿈 없이 출력하여 응답이 이어지는 모습을 확인합니다. 반복이 끝나면 청크 수를 출력하지만, 이 수는 속도 점수가 아닙니다. 제공자와 실행 시점에 따라 한 조각에 담는 글자 수가 달라질 수 있기 때문입니다.
다음 셀은 첫 청크부터 마지막 청크까지 +로 결합합니다. 이어서 텍스트가 있는 대표 청크의 실제 content_blocks를 출력합니다. 출력에서 type: text와 해당 조각의 text를 함께 읽으면, 블록 수가 아니라 블록의 내용까지 확인할 수 있습니다. 마지막으로 사용량 정보가 제공된 청크가 있는지 찾고, 없으면 미확인 상태로 표시합니다.
확인할 점 — stream()의 원소는 AIMessageChunk이고, 결합한 객체도 같은 타입입니다. 대표 블록에서 type과 text를 함께 확인합니다. 사용량 정보가 출력되지 않았다면 0토큰으로 읽지 말고 이번 스트림에서 확인되지 않은 값으로 읽습니다.
6실험 결과 해석
2026-09-09 최종 새 커널 실행에서는 모두 20개의 청크가 도착했고, 표준 콘텐츠 블록은 16개였습니다. 대표 블록은 {"type": "text", "text": "실"}이었습니다. 첫 청크와 마지막 세 청크의 블록 목록은 비어 있었지만, 사이의 텍스트 청크가 정상적으로 이어졌고 반복도 완료되었습니다. 빈 청크 하나만으로 실패라고 판단할 수 없는 이유입니다. 결합 메시지에는 사용량 정보도 있었습니다. 이 수치는 해당 실행의 관찰값이며 다시 실행하면 달라질 수 있습니다.
결합한 text에는 실제 문장이 남았고, 일반 호출의 AIMessage.text에도 텍스트가 있었습니다. 스트림 원소의 타입은 AIMessageChunk, invoke() 결과의 타입은 AIMessage였습니다. 이 결과는 두 호출 방식이 모두 텍스트를 반환하면서 중간 반환 단위는 다르다는 점을 보여 줍니다.
이번 실험은 조각의 순서와 결합 방법을 확인합니다. 20이라는 청크 수만으로 첫 토큰 지연, 전체 지연, 제공자 처리 속도를 비교할 수 없습니다. 청크 수와 생성 문장은 다시 실행하면 달라질 수 있습니다. 속도를 비교하려면 같은 조건의 반복 측정과 별도의 시간이 필요합니다.
7주의할 점과 실무 메모
중간 조각을 완성된 JSON으로 검증하지 않습니다. 닫는 괄호가 아직 도착하지 않은 정상 상태를 구문 오류로 잘못 처리할 수 있습니다.
화면 표시와 저장 상태를 분리합니다. 연결이 끊기면 사용자가 본 일부 텍스트와 서버에 저장한 최종 답이 달라질 수 있으므로 완료 여부를 함께 기록합니다.
빈 텍스트 청크를 곧바로 오류로 판정하지 않습니다. 종료 정보나 사용량처럼 텍스트 이외의 메타데이터를 담은 청크일 수 있습니다.
사용량 누락은 0이 아닙니다. 해당 통합과 모델이 스트리밍 사용량을 제공하는지 확인하고, 제공되지 않은 값은 미확인으로 보존합니다.
화면 갱신 횟수를 제한할 수 있습니다. 청크마다 화면 전체를 다시 그리면 브라우저 작업이 늘어나므로 짧은 간격으로 묶어 표시할 수 있습니다. 원래 순서는 바꾸지 않습니다.
8정리와 다음 절
stream()은 여러 AIMessageChunk를 도착 순서대로 반환합니다.
text는 화면에 표시할 문자열이고, content_blocks는 종류와 값을 가진 표준 블록을 확인할 때 사용합니다.
모든 청크를 결합한 뒤 저장과 검증을 수행하며, 제공되지 않은 사용량은 미확인 값으로 남깁니다.
다음 학습과 이어지는 지점 — 스트리밍도 외부 네트워크 요청이므로 응답이 늦거나 연결이 끝까지 이어지지 않을 수 있습니다. 다음 절에서는 기다리는 시간과 다시 시도하는 횟수를 제한하고, 실패할 때 선택할 대체 경로를 구성합니다.
9복습 문제
문제 1
왜 중간 AIMessageChunk마다 구조화된 JSON 검증을 실행하면 안 되나요?
해설 — 중간 청크에는 JSON의 일부만 들어 있을 수 있습니다. 모든 조각을 결합해 응답이 완성된 뒤 검증해야 정상적인 미완성 상태를 오류로 판단하지 않습니다.
문제 2
text와 content_blocks는 각각 언제 사용하나요?
해설 — 사용자에게 읽을 문자열을 표시할 때는 text가 편리합니다. 텍스트·추론·이미지처럼 콘텐츠 종류와 필드를 구분해 처리할 때는 content_blocks를 사용합니다.
문제 3
스트림에 usage_metadata가 없으면 토큰 수를 0으로 기록해도 되나요?
해설 — 기록하면 안 됩니다. 메타데이터가 없다는 것은 사용량을 확인하지 못했다는 뜻입니다. None이나 unknown으로 남기고 지원 옵션과 제공자 응답을 확인합니다.
문제 4
한 번의 호출에서 청크가 많이 나온 모델이 더 느리다고 판단할 수 있나요?
해설 — 판단할 수 없습니다. 청크를 나누는 방식과 네트워크 전달 방식이 다를 수 있습니다. 속도 비교에는 같은 과제를 여러 번 실행하여 첫 토큰 지연과 전체 지연을 따로 측정해야 합니다.

1학습 목표
타임아웃, 재시도, 폴백이 각각 해결하는 문제를 구분할 수 있습니다.
with_retry()에서 처리할 예외와 전체 시도 횟수를 명시할 수 있습니다.

로컬 실패 시뮬레이션과 실제 제공자 장애를 구분해 기록할 수 있습니다.
2이 내용을 배우는 이유
외부 모델 API는 네트워크 상태, 사용량 제한, 서버 상태의 영향을 받습니다. 평소에는 몇 초 안에 끝나는 호출도 늦어질 수 있고, 일시적인 오류로 응답을 받지 못할 수도 있습니다. 아무 제한 없이 기다리면 사용자는 화면이 멈춘 것으로 생각합니다. 같은 요청을 계속 보내면 대기 시간과 비용이 늘어납니다.
오류가 생겼다고 모두 다시 시도해서도 안 됩니다. 잠깐의 연결 문제는 두 번째 요청에서 해결될 수 있지만, 잘못된 API 키나 존재하지 않는 모델 이름은 같은 요청을 반복해도 해결되지 않습니다. 입력 데이터의 형식 오류도 코드를 고치기 전에는 그대로 발생합니다. 어떤 오류를 몇 번까지 다시 시도할지 정해야 합니다.
기본 모델을 사용할 수 없을 때 다른 모델이나 정해진 안내문으로 응답하는 폴백(fallback)도 필요할 수 있습니다. 그러나 대체 경로가 성공했다는 사실이 기본 경로의 오류를 없애지는 않습니다. 실제로 어느 경로가 응답했는지 기록해야 비용, 품질, 장애 원인을 나중에 확인할 수 있습니다.
3앞에서 배운 내용
앞 절에서 stream()이 네트워크에서 조각을 차례로 받는 호출이라는 점을 확인했습니다. 조각이 일부 도착한 뒤 연결이 끊길 수도 있으므로 완료 상태를 따로 기록해야 했습니다. 첫 절의 모델 초기화에서는 timeout=30과 max_retries=1을 코드에 직접 적었습니다.
이번 절에서는 실제 OpenAI 호출이 정상적으로 끝나는 경로와 실패 처리 규칙을 시험하는 로컬 경로를 분리합니다. 수업 시간에 실제 네트워크 장애가 생기기를 기다리지 않습니다. RunnableLambda가 의도적으로 TimeoutError를 발생시키게 하여 같은 입력에서 재시도와 폴백의 제어 흐름을 반복해서 확인합니다.
4핵심 개념
Python 함수를 Runnable로 감싸는 이유
Runnable은 LangChain에서 같은 호출 방식으로 실행할 수 있는 구성 요소를 가리킵니다. 앞 절의 모델에는 이미 invoke()가 있습니다. 우리가 작성한 일반 함수 fail_primary에는 그 메서드가 없으므로 RunnableLambda(fail_primary)로 감싸서 primary.invoke("질문")으로 실행할 수 있게 합니다. 함수 이름을 전달하는 순간에 함수가 실행되지는 않습니다.
여기서 lambda value: f"대체 경로: {value}"는 입력 하나를 받아 문자열 하나를 만드는 짧은 함수 표현식입니다. 콜론 앞은 매개변수, 뒤는 반환할 값입니다. 이를 감싼 fallback도 호출 객체이므로 with_fallbacks([fallback])의 목록에 넣을 수 있습니다. 이 목록은 대체 응답 문자열 목록이 아니라 오류가 날 때 실행할 객체 목록입니다.
예를 들어 규정 조회가 일시적으로 실패했을 때 같은 조회를 한 번 더 실행하면 재시도입니다. 사전에 확인한 점검 안내문을 반환하면 폴백입니다. 후자는 사용자가 읽을 응답을 제공하지만 규정 조회를 성공시킨 것은 아닙니다. 예제의 시도 횟수는 함수 실행 횟수이며, 실제 네트워크 장애율이나 서비스 복구율을 뜻하지 않습니다.
서로 다른 세 개의 제한
타임아웃(timeout)은 클라이언트가 응답을 기다리는 시간을 제한합니다. 이번 모델 객체에는 timeout=30을 명시합니다. 이 값은 현재 OpenAI 통합의 요청 설정으로 전달됩니다. 프로그램 전체가 반드시 30초 안에 끝난다는 뜻은 아닙니다. 재시도가 있으면 요청이 다시 실행될 수 있고, 연결과 응답의 어느 단계에 제한이 적용되는지는 통합과 하위 HTTP 클라이언트 설정에 따라 달라질 수 있습니다.
재시도(retry)는 같은 작업을 다시 실행합니다. 이번 실제 모델 객체의 max_retries=1은 재시도 가능한 제공자 오류에 대해 첫 요청 뒤 한 번을 더 허용하도록 명시한 값입니다. 따라서 해당 계층에서는 최초 요청을 포함해 최대 두 번의 요청이 생길 수 있습니다. 로컬 Runnable 실험에서는 stop_after_attempt=2를 사용합니다. 이 인자는 재시도 횟수가 아니라 최초 실행을 포함한 전체 시도 횟수입니다.
폴백은 같은 작업을 반복하는 대신 다른 Runnable로 넘깁니다. 기본 모델 대신 다른 모델을 호출할 수도 있고, 외부 호출 없이 정해진 안내문을 반환할 수도 있습니다. with_fallbacks()는 원본 Runnable을 먼저 실행하고, 지정한 예외가 발생하면 목록의 대체 Runnable을 순서대로 시도합니다.
어느 계층이 재시도를 맡는가
모델 통합의 max_retries와 Runnable의 with_retry()를 한 호출 경로에 함께 적용하면 시도 횟수가 겹칠 수 있습니다. 예를 들어 내부 모델 호출이 최대 두 번 시도되고, 바깥 Runnable도 전체 두 번을 시도하도록 구성하면 네트워크 요청은 조건에 따라 최대 네 번 발생할 수 있습니다. 각 계층이 실제로 어디까지 다시 실행하는지 계산하지 않으면 예상보다 대기와 과금이 늘어납니다.
이번 절은 이 차이를 보여 주기 위해 두 경로를 분리합니다. 실제 건강 확인 호출은 모델 통합에 명시한 제한만 사용합니다. 로컬 실험은 네트워크를 호출하지 않는 RunnableLambda에 with_retry()를 적용하여 정확히 두 번의 함수 실행을 확인합니다. 두 결과를 섞어 실제 API가 두 번째 시도에 복구되었다고 설명하지 않습니다.
다시 시도할 오류를 좁히기
with_retry()는 retry_if_exception_type으로 처리할 예외 유형을 받습니다. 이번 실험은 TimeoutError만 지정합니다. 인증 실패, 잘못된 모델 이름, Pydantic 검증 실패까지 넓게 잡지 않습니다. 오류 유형을 좁히면 코드를 고쳐야 하는 문제를 반복 호출로 가리지 않을 수 있습니다.
폴백도 exceptions_to_handle=(TimeoutError,)로 범위를 제한합니다. 이 조건에서는 기본 경로가 TimeoutError를 낼 때만 대체 경로가 실행됩니다. 다른 예외는 호출자에게 전달되므로 로그와 화면에서 원인을 확인할 수 있습니다.
타임아웃과 비용은 별도 문제입니다
클라이언트가 기다림을 멈췄다고 제공자 서버의 처리가 반드시 취소되는 것은 아닙니다. 서버가 이미 요청을 받아 토큰을 생성했다면 응답을 받지 못해도 과금될 수 있습니다. 재시도는 새로운 요청이므로 성공 여부와 관계없이 각 시도가 과금 대상이 될 가능성이 있습니다. 따라서 타임아웃은 사용자 대기 제한이고, 최대 시도 횟수는 요청 수 제한이며, 예산 상한은 별도로 계산해야 합니다.
오류 이름보다 다시 실행했을 때 달라질 조건을 봅니다
재시도 여부는 “오류가 발생했는가”만으로 정하지 않습니다. 같은 입력을 잠시 뒤 다시 보냈을 때 성공 가능성이 달라지는지 판단합니다. 서버가 일시적으로 혼잡하거나 요청 제한이 해제될 수 있다면 다시 시도할 근거가 있습니다. API 키가 틀렸거나 필수 필드가 빠졌다면 시간이 지나도 요청 내용이 같으므로 먼저 설정이나 입력을 고쳐야 합니다.
문제 상황첫 대응재시도 판단대체 경로의 예
짧은 네트워크 단절오류 유형과 시각 기록제한된 횟수로 대기 후 재시도정해진 점검 안내 표시
요청 제한 응답제공자의 대기 지시 확인허용 시점 이후 재시도처리 대기 상태로 보존
잘못된 API 키자격 증명 설정 수정같은 키로 반복하지 않음관리자에게 설정 오류 전달
로컬·고정 입력의 Pydantic 검증 실패필드와 거부된 값 확인입력이나 스키마를 고친 뒤 새 호출수정 가능한 필드를 사용자에게 표시
기본 모델 일시 장애상태와 모델 ID 기록짧은 재시도 뒤 중단요구 조건을 만족하는 대체 모델
존재하지 않는 모델 이름모델 식별자와 접근 권한 확인동일 식별자로 반복하지 않음검증된 모델 설정 사용
폴백도 언제나 다른 모델을 뜻하지 않습니다. 도서관 운영 시간 질문이라면 확인된 정적 안내문을 반환할 수 있고, 요약 작업이라면 더 작은 모델로 전환할 수 있습니다. 정적 안내문 폴백은 사용자가 계속 기다리지 않게 하지만 원래 요약 과제를 완료한 것은 아닙니다. 대체 경로가 반환한 결과와 원래 요청의 완료 상태를 구분해야 합니다.
대기 간격은 여러 호출이 동시에 몰리는 현상을 줄입니다
실패 직후 모든 사용자가 같은 간격으로 다시 요청하면 제공자가 회복하는 순간에 요청이 다시 집중될 수 있습니다. with_retry()의 고정 환경 시그니처에는 wait_exponential_jitter와 exponential_jitter_params가 있습니다. 지수 대기는 시도할수록 간격을 늘리고, 지터(jitter)는 각 요청의 대기 시간에 작은 차이를 더해 재요청 시점을 분산합니다.
대기 설정은 성공을 보장하는 장치가 아닙니다. 서비스가 허용하는 대기 시간에 맞춰 최대 시도 횟수와 간격을 함께 정합니다.
도식 읽기
기본 요청에서 타임아웃이 발생했을 때 제한된 재시도와 폴백으로 이어지는 흐름입니다. 재시도 화살표는 같은 경로를 다시 실행하고, 폴백 화살표는 다른 Runnable로 이동합니다.각 화살표 옆의 조건과 횟수를 확인하여 전체 실행 횟수를 계산합니다.
5실행 예제
첫 부분은 timeout=30, max_retries=1을 명시한 모델로 건강 확인 질문을 한 번 보냅니다. 실제 실행에서는 재시도 횟수 제한이 자원 낭비와 장애 확대를 막는다는 내용의 한 문장 응답을 받았습니다. 이 출력은 정상 경로가 완료되었다는 사실만 보여 줍니다. 오류가 발생하지 않았으므로 내부 재시도가 실행되었는지, 실제 장애가 얼마나 자주 복구되는지는 알 수 없습니다.
다음 부분은 외부 API를 사용하지 않습니다. 첫 실행에서만 TimeoutError("수업용 일시 오류")를 발생시키고 두 번째 실행에서 문자열을 반환하는 함수를 만듭니다. with_retry(retry_if_exception_type=(TimeoutError,), stop_after_attempt=2)를 적용한 결과, 두 번째 실행에서 성공했고 전체 시도 횟수는 2회였습니다. 이 셀은 정해진 제어 흐름을 확인합니다.
확인할 점 — 정상 API 응답과 로컬 재시도 출력을 구분합니다. 로컬 출력의 전체 시도 횟수는 stop_after_attempt와 같습니다. 이 숫자는 OpenAI 네트워크 요청 횟수를 측정한 값이 아닙니다.
6일부러 실패해 보기
Before에서는 입력을 받은 기본 RunnableLambda가 매번 TimeoutError("수업용 로컬 타임아웃")를 발생시킵니다. 실제 출력에는 TimeoutError와 시도 횟수 1회가 남았습니다. 이 오류 문구는 수업 코드가 직접 만든 것이며 OpenAI가 반환한 오류가 아닙니다.
After에서는 같은 기본 Runnable에 폴백을 연결합니다. 기본 경로가 한 번 실패하면 TimeoutError를 처리하도록 지정된 대체 Runnable이 같은 입력을 받아 문자열을 반환했습니다. 누적 기본 경로 시도 횟수는 2회였습니다. Before와 After에서 기본 경로를 각각 한 번 호출했기 때문입니다. 대체 경로 성공은 네트워크 서비스가 복구됐다는 증거가 아니라 로컬 분기 규칙이 예상대로 실행됐다는 증거입니다.
7주의할 점과 실무 메모
기본값에 의존하지 않습니다. 고정한 LangChain·통합 버전에서도 기본값의 위치와 의미가 다를 수 있으므로 timeout, max_retries, 전체 시도 횟수, 예외 유형을 코드에 적습니다.
재시도 범위를 모델 호출에 한정합니다. 모델 호출 뒤의 저장이나 결제까지 같은 Runnable에 넣고 전체를 재시도하면 쓰기 작업이 중복될 수 있습니다.
멱등성(idempotency)을 확인합니다. 같은 요청을 여러 번 실행해도 최종 상태가 달라지지 않는 작업인지 확인하고, 중복 실행 위험이 있는 작업에는 요청 식별자와 별도 복구 절차를 둡니다.
실제 응답 경로를 기록합니다. 폴백 모델이 답했다면 기본 모델 이름으로 비용과 품질을 기록하지 않습니다. 제공자, 모델, 시도 횟수, 최종 상태를 함께 남깁니다.
오류 원문에서 비밀 값을 제거합니다. API 키나 전체 요청 헤더를 노트북 출력과 로그에 남기지 않습니다.
8정리와 다음 절
타임아웃은 기다리는 시간을 제한하고, 재시도는 같은 작업을 다시 실행하며, 폴백은 다른 경로를 선택합니다.
stop_after_attempt는 최초 실행을 포함한 전체 시도 횟수이므로 내부 재시도와 겹치지 않게 계산합니다.
이번 TimeoutError는 제어 흐름을 검증하는 로컬 시뮬레이션이며 실제 제공자 장애나 복구를 관찰한 결과가 아닙니다.
다음 학습과 이어지는 지점 — 제한된 재시도와 폴백도 호출 횟수와 비용을 늘릴 수 있습니다. 다음 절에서는 같은 과제의 응답, 토큰 사용량, 전체 지연, 실행일 단가를 한 레코드에 모아 비교합니다.
9복습 문제
문제 1
stop_after_attempt=2는 첫 실패 뒤 두 번을 더 재시도한다는 뜻인가요?
해설 — 아닙니다. 최초 실행을 포함한 전체 시도 횟수가 최대 두 번이라는 뜻입니다. 첫 실행이 실패하면 한 번을 더 시도할 수 있습니다.
문제 2
모델 통합의 재시도와 Runnable 재시도를 겹치면 무엇을 먼저 계산해야 하나요?
해설 — 한 번의 바깥 실행에서 내부 네트워크 요청이 몇 번까지 생기는지 계산해야 합니다. 두 계층의 최대 시도 횟수가 곱해져 대기와 비용이 예상보다 커질 수 있습니다.
문제 3
이번 After 출력이 OpenAI 서비스의 장애 복구를 보여 주나요?
해설 — 보여 주지 않습니다. 수업 코드가 만든 TimeoutError를 로컬 대체 Runnable이 처리한 결과입니다. 실제 네트워크 실패나 제공자 복구는 측정하지 않았습니다.
문제 4
타임아웃을 설정하면 해당 호출의 과금이 없다고 보장할 수 있나요?
해설 — 보장할 수 없습니다. 클라이언트가 기다림을 멈추기 전에 서버가 요청을 받아 처리했을 수 있습니다. 시도별 사용량과 제공자 청구 기록을 별도로 확인해야 합니다.

1학습 목표
usage_metadata에서 제공자가 보고한 입력·출력 토큰을 읽을 수 있습니다.
perf_counter()로 한 번의 전체 호출 지연을 측정할 수 있습니다.
실행일의 공식 요금과 캐시 입력을 구분하여 예상 비용을 계산할 수 있습니다.
실행되지 않았거나 사용량이 누락된 행을 제외하고 비교 범위를 판정할 수 있습니다.
2이 내용을 배우는 이유
모델이 원하는 답을 만들더라도 호출당 비용과 대기 시간이 서비스 요구 조건을 넘으면 실제 기능에 적용하기 어렵습니다. 반대로 한 번 빠르게 답한 모델을 선택해도 다른 시간과 질문에서는 결과가 달라질 수 있습니다. 모델을 비교하려면 답의 내용과 함께 호출 조건과 원자료를 남겨야 합니다.
토큰 수만 나란히 적는 것으로는 충분하지 않습니다. 제공자마다 같은 문장을 토큰으로 나누는 방식이 다를 수 있고, 입력과 출력의 단가도 다릅니다. 이미 처리한 입력을 다시 사용하는 캐시 입력에는 별도 요금이 적용되기도 합니다. 입력 토큰 전체를 일반 입력 단가로 계산하면 캐시 할인을 반영하지 못합니다.
키가 없는 제공자나 사용량 정보를 보내지 않은 호출을 0으로 채우면 비교표가 사실과 달라집니다. 0초, 0토큰, 0달러는 측정 결과처럼 보이기 때문입니다. 이번 절에서는 실행 상태와 값의 확인 상태를 숫자와 분리해 기록합니다.
3앞에서 배운 내용
첫 절에서 AIMessage와 usage_metadata를 확인했고, 두 번째 절에서 제공자별 원본 메타데이터와 표준 필드를 구분했습니다. 앞 절에서는 timeout과 최대 시도 횟수를 명시하여 한 호출이 끝없이 이어지지 않게 했습니다.
이번 절은 OpenAI, Anthropic, Google의 모델 객체를 같은 init_chat_model() 형태로 준비합니다. 세 제공자 모두 같은 사용자 메시지와 출력 상한을 사용합니다. 각 API 키가 있을 때만 실제 호출하며, 키가 없으면 환경 변수 이름과 건너뜀 상태만 기록합니다. 키의 실제 값은 읽어서 출력하거나 결과 파일에 저장하지 않습니다.
4핵심 개념
비교표의 한 행이 담아야 할 값
비교표의 한 행은 한 제공자에 대한 결론이 아니라 한 번의 실행 기록입니다. 최소한 provider, model_id, 실행 상태, 응답 텍스트, 전체 지연, 입력 토큰, 출력 토큰, 예상 비용을 함께 둡니다. 모델 이름을 기록하지 않으면 같은 제공자의 다른 모델 결과와 섞일 수 있습니다. 응답 원문이 없으면 토큰과 지연이 어떤 품질의 답에 대응하는지도 알 수 없습니다.
비교 조건에는 사용자 메시지, 반복 횟수, 출력 토큰 상한을 기록합니다. 가능하다면 모델의 고정 스냅샷과 실행 지역도 함께 남깁니다. 이번 실습은 호출 형태를 배우기 위한 한 번의 작은 표본이므로 제공자 전체의 성능 순위를 만들지 않습니다.
제공자가 보고한 토큰 읽기
AIMessage.usage_metadata는 제공자가 사용량을 보냈을 때 입력 토큰, 출력 토큰, 전체 토큰을 LangChain의 공통 필드로 제공합니다. 이 값은 로컬에서 문자열 길이를 세어 추정한 수치가 아닙니다. 제공자가 보고한 값이므로 모델과 제공자에 따라 같은 문장에서도 달라질 수 있습니다.
usage_metadata가 None이거나 필요한 필드가 없으면 비용도 확인할 수 없습니다. 이때 dict.get(..., 0)으로 바꾸면 안 됩니다. 토큰이 없었던 실행과 사용량을 받지 못한 실행을 구분할 수 없기 때문입니다. 레코드에는 usage_status="unknown"과 estimated_cost_usd=None처럼 상태를 분명히 남깁니다.
전체 호출 지연 측정
time.perf_counter()는 시스템 시각 변경의 영향을 받지 않는 단조 시계입니다. 모델 호출 직전에 시작 값을 읽고, invoke()가 반환된 직후 종료 값을 읽습니다. 두 값의 차이는 요청을 보내기 시작한 때부터 완성된 응답을 받은 때까지의 전체 지연입니다.
이 측정값에는 네트워크 왕복, 제공자 대기, 모델 생성 시간이 함께 들어 있습니다. 어느 구간이 느렸는지는 이 값 하나로 알 수 없습니다. 사용자에게 표시할 첫 비어 있지 않은 텍스트 청크가 도착할 때까지의 지연과도 다릅니다. 이번 절에서는 모든 제공자에 같은 측정 경계를 적용하여 한 번의 전체 지연 원자료만 남깁니다.
문자 수·토큰 수·응답 시간은 서로 다른 관찰입니다
한국어 한 문장이 30글자라고 해서 입력 토큰도 30개인 것은 아닙니다. 토큰은 모델이 텍스트를 처리하기 위해 나눈 단위이며, 공백·문장 부호·한글 음절·영문 조각을 나누는 방식은 토크나이저와 모델에 따라 달라질 수 있습니다. 같은 질문을 세 제공자에 보내도 입력 토큰 수가 같아야 한다는 조건을 두지 않습니다. 비교할 때는 제공자가 보고한 값을 각 모델의 관찰값으로 보존합니다.
관찰값답하는 질문답하지 못하는 질문예시 해석
문자 수화면에 표시된 답이 얼마나 긴가?모델이 몇 토큰을 처리했는가?짧은 문장 형식을 지켰는지 확인합니다.
입력 토큰해당 모델이 입력을 몇 단위로 처리했는가?답이 정확한가?같은 문장도 모델별 값이 다를 수 있습니다.
출력 토큰생성에 사용된 출력 단위는 얼마인가?사용자가 읽은 글자 수와 같은가?추론 토큰 세부 정보가 별도로 있을 수 있습니다.
첫 텍스트 지연첫 비어 있지 않은 텍스트 청크를 언제 받았는가?전체 답이 언제 끝났는가?채팅 화면이 처음 반응한 시점과 관련됩니다.
전체 지연완성 응답을 받는 데 얼마나 걸렸는가?네트워크와 생성 중 무엇이 느렸는가?이번 invoke() 실습이 측정한 값입니다.
성공 상태정한 조건에서 응답을 받았는가?응답 내용이 유용한가?성공률에는 반복 실행과 판정 기준이 필요합니다.
설명용 가정으로, 두 모델이 모두 2초 만에 끝났더라도 사용 경험은 다를 수 있습니다. 모델 A가 0.3초에 첫 글자를 보여 주고 나머지를 이어서 생성했다면 채팅 화면은 일찍 반응합니다. 모델 B가 2초 뒤 완성 문장을 한 번에 반환했다면 전체 지연은 같지만 첫 표시 시점은 늦습니다. 반대로 화면이 빨리 시작해도 마지막 문장이 오래 걸리면 후속 저장이나 검증은 늦어집니다.
이번 노트북은 invoke()의 시작과 반환 시점만 측정했으므로 첫 텍스트 지연을 관찰하지 않았습니다. 04절의 스트림에 시작 시각과 첫 비어 있지 않은 텍스트 청크 시각을 추가해야 그 값을 측정할 수 있습니다. 실제로 수집하지 않은 지표를 전체 지연에서 추정하지 않습니다.
성공 여부와 답의 품질을 분리합니다
API 호출이 성공했다는 것은 응답 객체를 받았다는 뜻입니다. “한 문장의 한국어로 설명하라”는 과제를 잘 수행했는지는 응답 원문을 읽어 별도로 판단해야 합니다. 내용이 사실인지, 초보자가 이해할 수 있는지, 요구한 형식을 지켰는지는 서로 다른 평가 항목입니다. 토큰과 지연이 더 작은 행이 자동으로 더 좋은 답은 아닙니다.
비교를 확장할 때는 고객 문의, 개념 설명, 정보 추출처럼 성격이 다른 질문을 섞어 평균 하나로 만들기 전에 과제별 결과를 봅니다. 정보 추출에는 필드 누락률이 중요하고, 개념 설명에는 정확성과 설명 가능성이 중요하며, 채팅 화면에는 첫 텍스트 지연이 중요할 수 있습니다. 모델 선택 기준은 측정 가능한 숫자와 실제 과제의 성공 조건을 연결해 정합니다.
실행일 단가와 캐시 입력
예상 비용은 (일반 입력 토큰 × 일반 입력 단가 + 캐시 입력 토큰 × 캐시 입력 단가 + 출력 토큰 × 출력 단가) ÷ 1,000,000으로 계산합니다. 단가는 100만 토큰 기준이고 비용의 통화는 미국 달러입니다. 캐시 입력 토큰이 입력 토큰 합계에 포함되어 있다면 일반 입력 토큰은 전체 입력에서 캐시 입력을 뺀 값입니다.
2026-09-09에 확인한 GPT-5.4 mini 공식 요금은 일반 입력 100만 토큰당 0.75달러, 캐시 입력 0.075달러, 출력 4.50달러입니다. 캐시 사용량 세부 정보가 제공된 OpenAI 행은 두 입력 단가를 나누어 적용합니다. Anthropic Claude Haiku 4.5의 표준 입력·출력 요금은 각각 1달러와 5달러이며, Google Gemini 2.5 Flash-Lite의 표준 입력·출력 요금은 각각 0.10달러와 0.40달러입니다. 이 두 제공자의 캐시 쓰기·읽기 조건은 표준 입출력과 별도일 수 있으므로 이번 기본 계산에 캐시 사용량을 임의로 추정하지 않습니다.
가격은 모델, 사용 방식, 날짜에 따라 바뀔 수 있습니다. 소스 코드의 숫자가 영구적인 사실은 아닙니다. 레코드 필드에 가격 기준일을 포함하고, 수업 배포와 실제 서비스 적용 전에 공식 가격 페이지를 다시 확인합니다.
도식 읽기
같은 질문이 세 제공자 분기로 전달되고, 각 응답에서 텍스트·사용량·전체 지연·예상 비용을 한 행으로 모으는 흐름입니다. 키가 없는 분기는 숫자 행으로 합쳐지지 않고 건너뜀 상태로 남습니다.가운데의 모델 호출보다 오른쪽 레코드에서 상태와 숫자가 분리되어 있는지 먼저 확인합니다.
측정 기록의 값과 상태를 함께 읽기
usage_metadata는 응답 객체에 붙은 사용량 자료입니다. 사용자 질문 문자열의 길이를 센 값과 구분합니다. usage.get("input_tokens")는 딕셔너리에서 해당 키의 값을 읽고 키가 없으면 None을 반환합니다. 사용량 전체가 없을 때 answer.usage_metadata or {}는 계산이 중단되지 않도록 빈 딕셔너리를 준비하지만, 토큰을 0개 사용했다는 측정값을 새로 만드는 것은 아닙니다.
time.perf_counter()는 두 시점 사이에 지난 시간을 재기 위한 시계입니다. 날짜를 뜻하지 않습니다. 시작값을 저장하고 호출 반환 뒤 값에서 빼면 경과 초를 얻습니다. 예를 들어 차이가 1.5초라면 1000을 곱해 1500밀리초로 나타냅니다. 이 계산 예와 아래 실행에 저장된 실제 지연값은 구분합니다.
개념 설명 요청과 상품명 추출 요청을 각각 측정한다고 생각해 봅니다. 둘 다 입력·출력 토큰과 지연을 기록할 수 있지만 성공 기준은 다릅니다. 전자는 설명의 사실성과 이해 가능성을, 후자는 필요한 필드의 정확성을 확인해야 합니다. 공통 숫자를 같은 열에 모으는 것은 기록 형식을 통일하는 일이며 서로 다른 과제를 같은 난이도로 만드는 일은 아닙니다.
5실행 예제
노트북은 OpenAI, Anthropic, Google의 환경 변수 이름과 모델 ID를 표로 준비합니다. 같은 사용자 메시지, 반복 횟수 1회, 같은 출력 상한을 모든 실행에 적용합니다. 각 반복에서 키의 존재만 확인하고, 키가 있는 제공자만 init_chat_model()과 invoke()를 실행합니다. 키가 없는 제공자는 skipped 상태를 남깁니다.
실행된 행은 응답의 text 원문, usage_metadata, perf_counter()로 측정한 전체 지연을 저장합니다. 사용량이 있으면 실행일 단가로 예상 비용을 계산합니다. OpenAI 행에서 input_token_details.cache_read가 제공되면 캐시 입력과 일반 입력을 나누어 계산합니다. 필요한 사용량 필드가 없으면 비용을 0으로 만들지 않고 None으로 남깁니다.
마지막 셀은 공통 조건과 제공자별 원자료를 runs/provider-comparison-continuity.json에 저장하고, 같은 내용을 runs/continuity/<실행 시각>/에도 보존합니다. Ch 7은 정본의 run_id와 파일 지문을 읽어 이전 실행의 출처를 확인합니다.
확인할 점 — 먼저 각 행의 status와 model_id를 확인합니다. 실행된 행에서 응답 원문, 사용량, 전체 지연, 가격 기준일을 차례로 읽습니다. 건너뛴 행과 사용량 미확인 행에는 측정값처럼 보이는 0이 없어야 합니다.
6실험 결과 해석
2026-09-09 최종 새 커널 실행에서는 OpenAI의 openai:gpt-5.4-mini 행만 완료되었습니다. 제공자가 보고한 사용량은 입력 18토큰, 출력 25토큰, 전체 43토큰이었습니다. 전체 호출 지연은 1,507.8밀리초였고, 해당 실행의 캐시 입력은 없었습니다. 기준일의 일반 입출력 단가로 계산한 예상 비용은 0.000126달러였습니다. 생성 문장과 토큰, 지연은 다시 실행하면 달라질 수 있습니다.
Anthropic과 Google 행은 각각 필요한 API 키가 없어 skipped로 기록되었습니다. 0토큰이나 0밀리초로 기록하지 않았습니다. 실제 측정값이 있는 제공자는 한 개뿐이므로 여러 제공자의 수치를 비교할 수 없다는 판정이 출력되었습니다. 이 결과는 두 통합의 코드 분기가 준비되었다는 사실만 보여 주며, 두 모델의 품질·속도·비용을 관찰한 결과는 아닙니다.
OpenAI 한 행도 모델 전체의 성능을 나타내지 않습니다. 이 실험은 한 질문을 한 번 실행한 예시입니다. 생성된 문장의 길이와 내용, 네트워크 상태가 달라지면 출력 토큰과 지연도 달라집니다. 공정한 평가를 이어가려면 실제 업무를 대표하는 질문 집합을 만들고, 같은 날짜와 실행 지역에서 각 조건을 여러 번 반복해야 합니다.
7주의할 점과 실무 메모
누락된 값은 0으로 바꾸지 않습니다. 0은 측정값이고, None은 확인하지 못한 값입니다. 상태 열과 숫자 열을 분리합니다.
캐시 입력을 일반 입력과 구분합니다. 제공자가 캐시 사용량 세부 정보를 보냈을 때만 할인 단가를 적용합니다. 제공되지 않은 캐시 토큰을 추정하지 않습니다.
비용은 예상값으로 표시합니다. 공식 청구서에는 반올림, 요청 종류, 장기 컨텍스트, 배치 처리 같은 별도 조건이 반영될 수 있습니다.
한 번의 지연값을 평균처럼 사용하지 않습니다. 예열, 네트워크 혼잡, 출력 길이의 영향을 줄이려면 반복 횟수와 중앙값 또는 백분위수를 미리 정합니다.
API 키와 개인정보를 기록하지 않습니다. 키는 존재 여부만 확인하고, 프롬프트 원문을 저장할 때도 공개 가능한 입력인지 확인합니다.
확인 필요 항목Anthropic과 Google 호출은 API 키가 없어 실행되지 않았습니다. 두 제공자의 실제 사용량·지연·비용은 키가 준비된 환경에서 같은 조건으로 다시 실행해야 합니다. 가격과 모델 접근 권한은 배포 직전에 공식 문서와 계정 화면에서 다시 확인합니다.
8정리와 다음 절
한 실행 행에는 제공자·모델·상태·응답 원문·사용량·전체 지연·예상 비용·가격 기준일을 함께 기록합니다.
사용량과 캐시 세부 정보가 제공된 범위에서만 비용을 계산하고, 누락된 값은 미확인으로 남깁니다.
한 질문의 1회 실행은 호출 기록의 예시이며 제공자 전체의 순위를 정하는 근거가 아닙니다.
다음 학습과 이어지는 지점 — Ch 7의 08절은 이 파일을 읽어 실행 출처를 확인한 뒤, 별도의 고객 문의와 세 프롬프트 버전을 같은 측정 필드로 기록합니다. 질문과 실험 단위가 다르므로 두 챕터의 수치를 직접 비교하지 않습니다.
9복습 문제
문제 1
usage_metadata가 없을 때 입력·출력 토큰을 0으로 기록하면 왜 안 되나요?
해설 — 0은 토큰을 사용하지 않았다는 측정값처럼 보입니다. 메타데이터가 없으면 사용량을 확인하지 못한 것이므로 None이나 unknown으로 기록해야 합니다.

## 결정적인 로컬 시뮬레이션
네트워크 장애를 꾸며 내지 않고, 실패하는 Runnable로 제어 흐름만 검증합니다.
`Runnable`은 `invoke()`처럼 공통 방식으로 실행할 수 있는 LangChain 구성 요소입니다. `RunnableLambda(fail_primary)`는 Python 함수 자체를 받아 그 호출 방식을 연결합니다. 괄호 안에 `fail_primary()`처럼 실행 결과를 넣지 않습니다. 실제 함수 실행은 `primary.invoke(...)`에서 시작됩니다.
`lambda value: f"대체 경로: {value}"`는 입력 `value`로 문자열을 만들어 반환하는 짧은 함수입니다. `with_fallbacks([fallback])`는 기본 호출에 실패했을 때 실행할 객체 목록을 받습니다. `with_retry()`와 `with_fallbacks()`로 호출 객체를 구성한 다음 `invoke()`해야 설정한 제어 흐름이 실행됩니다.
