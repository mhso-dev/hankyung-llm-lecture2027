2이 내용을 배우는 이유
RAG가 관련 문서를 찾았더라도 모델이 검색하지 않은 문서 ID를 답에 적으면 사용자는 잘못된 근거를 믿게 됩니다. 입력 형식과 출력의 출처를 파이썬 코드로 검사하면 잘못된 요청과 검색 결과에 없는 출처를 모델 바깥에서 멈출 수 있습니다.

4핵심 개념
쉬운 예
도서관 대출대에서 회원증 형식을 먼저 확인하고, 반납 확인서의 책 번호를 실제 대출 목록과 대조하는 상황과 같습니다. 앞 검사는 입력 형식, 뒤 검사는 출력의 허용 목록을 맡습니다.
정의
검증(validation)은 값이 정한 형식과 범위에 맞는지 확인하는 처리입니다. 입력 검증은 빈 질문과 길이 상한을 확인합니다. 출력 검증은 출처 태그가 있고 그 태그가 이번 검색 결과에 포함되는지 확인합니다. 정규 표현식은 형식을 찾지만 사실의 참·거짓까지 판단하지는 못합니다.
호출 표기와 실행 시점
입력 검증은 모델 호출 전에 질문의 빈값·길이·허용 문자를 확인합니다. 출력 검증은 모델 답에서 출처 태그를 추출해 이번 검색 결과의 doc_id와 page 조합에 포함되는지 대조합니다. 함수가 반환한 검증 결과와 print로 보이는 화면 문자열은 구분해 읽습니다.
다른 상황에 적용
의료 안내에서는 질문 길이와 금지 입력을 먼저 검사하고, 답변의 약품 코드가 검색된 공식 문서 목록에 있는지 후처리할 수 있습니다. 도메인이 달라져도 호출 전 입력 경계와 호출 후 허용 목록 경계는 분리됩니다.
비교와 경계
형식이 맞는 출처가 실제 주장을 뒷받침한다는 뜻은 아닙니다. 이 검사는 존재하지 않는 ID를 막지만 인용 문장과 근거 본문의 의미 일치까지 판단하지 않습니다. 근거성 평가는 Ch15의 평가와 함께 사용합니다.
도식 읽기
질문이 비어 있거나 길이 제한을 넘었는지 확인한 뒤 모델을 호출합니다. 답변의 출처 ID와 쪽 번호를 허용 목록과 대조하며, 목록에 없는 출처는 오류로 처리합니다. 이 검사는 답변 내용 전체의 진위를 판정하지 않습니다.
5실행 예제
노트북은 프로젝트 helper 없이 Python 3.12 새 커널에서 실행합니다. 패키지 버전과 API 키 존재 여부를 확인하되 키 값은 출력하지 않습니다. 모델은 init_chat_model()로 만들고 invoke()가 반환한 AIMessage.text를 읽습니다.
확인할 점 — 질문 정규화, 허용된 E01 출처 통과, 허용되지 않은 E02 출처 거부를 확인합니다.
6일부러 실패해 보기
실제 모델 답에서 [E01 p.1]을 추출해 허용 목록과 일치함을 확인했습니다. 합성 답 [E02 p.1]은 검색 결과에 없는 출처라는 오류로 거부했습니다. 이 검사는 답 내용의 정확성을 증명하지 않으므로 Ch 15의 Groundedness 평가와 함께 사용해야 합니다.
7주의할 점과 실무 메모
질문 길이 상한은 서비스 화면과 모델 입력 예산을 함께 보고 정합니다.
출처 검증은 태그 형식과 검색 포함 여부를 확인합니다. 문서 내용이 답을 실제로 뒷받침하는지는 별도 평가가 필요합니다.

1학습 목표
합성 이메일과 전화번호를 모델 호출 전에 마스킹할 수 있습니다.
감사 로그에 원문 개인정보를 남기지 않는 구조를 만들 수 있습니다.
정규 표현식 마스킹의 누락과 오탐 가능성을 설명할 수 있습니다.
2이 내용을 배우는 이유
모델 호출과 관찰 로그는 모두 데이터가 이동하거나 남는 지점입니다. 사용자의 질문을 그대로 보내고 기록하면 답변 생성에 필요하지 않은 개인 식별 정보까지 처리할 수 있습니다. 먼저 필요한 정보인지 판단하고, 필요하지 않으면 값의 종류만 남겨야 합니다.
3앞에서 배운 내용
Ch 2의 문자열 처리와 정규 표현식 기초를 사용합니다. Ch 6에서 invoke()에 메시지를 전달했고 Ch 15에서 트레이스에 남길 필드를 정했습니다. 이 절은 호출과 기록보다 앞에 마스킹 단계를 둡니다.
4핵심 개념
쉬운 예
택배 상자를 분류하는 작업에 전체 전화번호가 필요하지 않다면 ‘연락처 있음’ 표지만 남길 수 있습니다. 모델도 실제 값 대신 정보 종류만 받아 작업할 수 있는지 먼저 판단합니다.
정의
개인 식별 정보(PII)는 한 사람을 직접 또는 다른 정보와 결합해 알아볼 수 있게 하는 정보입니다. 마스킹(masking)은 실제 값을 <EMAIL_MASKED>처럼 의미를 보존한 표지로 바꿉니다. 최소 수집은 작업에 꼭 필요한 정보만 처리하는 원칙입니다.
호출 표기와 실행 시점
탐지 함수는 합성 이메일과 전화번호 패턴의 시작·끝 위치를 찾고, 마스킹 함수는 실제 문자열을 [EMAIL]·[PHONE] 같은 종류 표지로 바꿉니다. 모델 호출과 로그 저장에는 마스킹된 문자열만 전달하고 원문은 출력하지 않습니다.
다른 상황에 적용
주민등록번호가 필요 없는 문의 분류에서는 [ID_NUMBER] 표지만 남겨도 업무 유형을 판단할 수 있습니다. 반대로 배송 연락처럼 실제 번호가 필요한 후속 시스템에는 모델을 거치지 않는 별도 권한 경로를 설계해야 합니다.
비교와 경계
정규식은 알려진 모양을 찾을 뿐 사람 이름·주소·우회 표기를 모두 탐지하지 못합니다. 마스킹은 암호화나 접근 통제를 대신하지 않으며, 이미 외부로 전송한 뒤 적용하면 보호 효과가 없습니다.
도식 읽기
합성 문장에서 정해 둔 전화번호·이메일 등의 형식을 찾아 마스킹합니다. 변경된 문장과 탐지 수를 확인한 뒤, 규칙이 찾지 못하는 형식도 살펴봅니다. 모든 개인정보를 탐지한 결과로 확대하지 않습니다.
5실행 예제
노트북은 프로젝트 helper 없이 Python 3.12 새 커널에서 실행합니다. 패키지 버전과 API 키 존재 여부를 확인하되 키 값은 출력하지 않습니다. 모델은 init_chat_model()로 만들고 invoke()가 반환한 AIMessage.text를 읽습니다.

6일부러 실패해 보기
합성 이메일과 전화번호가 각각 한 건씩 탐지되어 모델 입력과 감사 로그에서 사라졌습니다. 모델 답에도 원문 이메일이 다시 나타나지 않았습니다. 이 결과는 준비한 패턴에서만 관찰한 것이며 띄어쓰기, 국제 전화번호, 오타, 이미지 속 정보까지 탐지한다고 일반화할 수 없습니다.
7주의할 점과 실무 메모
실제 사람의 개인정보로 테스트하지 않습니다. 문서와 시험 데이터에는 명시적으로 만든 합성값만 둡니다.
마스킹 뒤에도 업무상 필요한 식별자가 사라져 답 품질이 낮아질 수 있습니다. 필드별로 보존 여부를 정합니다.

히스토리(history)는 현재 호출에 함께 전달하는 이전 메시지 목록입니다. 트리밍(trimming)은 정한 개수나 예산 밖의 메시지를 제거합니다. 요약 처리는 오래된 대화를 새 요약 메시지로 바꿉니다. 요약도 모델 출력이므로 원문보다 길어지거나 사실을 빠뜨리고 잘못 합칠 수 있습니다.
호출 표기와 실행 시점
트리밍은 시스템 메시지를 보존한 채 최근 메시지 수만 남깁니다. 요약 방식은 오래된 발화를 모델에 입력해 요약 문자열을 만들고 최근 발화와 결합합니다. 두 방식 모두 최종 프롬프트에 어떤 정보가 남았는지 실제 문자열로 확인해야 합니다.

비교와 경계
트리밍은 정보를 삭제하고 요약은 정보를 압축하면서 왜곡 가능성을 만듭니다. 문자 수가 줄어도 토큰 수가 같은 비율로 줄지는 않으며, 이 실험에서 요약 결합 문자가 늘어난 결과를 비용 절감으로 해석할 수 없습니다.
도식 읽기
시스템 정책을 별도로 유지하면서 오래된 대화를 자르거나 모델로 요약합니다. 요약은 최근 대화와 함께 참고 자료로 전달하며, 정리 전후에 조건이 보존됐는지와 글자 수가 어떻게 달라졌는지를 확인합니다.

1학습 목표

4핵심 개념
쉬운 예
전화 연결이 잠시 끊기면 정한 횟수만 다시 걸고, 계속 실패하면 문자 안내로 전환합니다. 언제 어느 경로로 바뀌었는지를 남겨야 반복 장애의 원인을 찾을 수 있습니다.
정의
재시도(retry)는 같은 작업을 제한된 조건에서 다시 요청하는 처리입니다. 지수 백오프(exponential backoff)는 대기 시간을 차례로 늘립니다. 폴백(fallback)은 기본 경로가 실패했을 때 사용하는 대체 모델이나 안전한 고정 답입니다. 멱등성(idempotency)은 같은 요청이 반복되어도 결과 상태가 한 번 처리한 것과 같도록 만드는 성질입니다. 감사 로그(audit log)는 정책 판단과 실행 경로를 나중에 확인하는 기록입니다.
호출 표기와 실행 시점
재시도 함수는 허용한 일시 오류인지 확인하고 시도 횟수가 남았을 때만 같은 작업을 다시 호출합니다. 횟수를 모두 쓰면 고정 답이나 대체 모델의 폴백 함수를 실행합니다. 감사 사건에는 오류 종류, 시도 수, 선택 경로, 마스킹된 요청 식별 정보만 남깁니다.
다른 상황에 적용
검색 서버의 503 오류는 짧게 재시도한 뒤 캐시된 안내로 전환할 수 있지만, 결제 승인 같은 쓰기 작업은 멱등성 키 없이 반복하면 중복 처리될 수 있습니다. 작업의 부작용 여부가 재시도 정책을 바꿉니다.
비교와 경계
폴백은 성공을 보장하는 두 번째 시도가 아닙니다. 대체 모델도 실패할 수 있으므로 마지막에는 검증된 고정 안내와 재시도 가능 시점을 반환해야 합니다. 401·403처럼 설정을 바꾸어야 하는 오류는 대기 시간을 늘려도 해결되지 않습니다.
도식 읽기
주 처리의 응답을 반환하거나, 허용한 오류일 때 정한 횟수 안에서 재시도합니다. 재시도를 소진하면 폴백을 실행하고 결정과 오류를 감사 기록에 남깁니다. 각 실험에서 실제로 실행한 경로를 출력으로 확인합니다.
5실행 예제

6실험 결과 해석
첫 실험은 합성 시간 초과가 두 번 발생한 뒤 고정 문자열 ‘폴백 답’으로 전환했으며 경로는 fallback, 총 시도 표시는 3이었습니다. 둘째 실험은 합성 영구 오류 한 번 뒤 실제 모델 폴백이 서비스 지연 안내를 반환했으며 경로는 fallback, 총 시도 표시는 2였습니다. 감사 로그 한 건에는 이메일 원문 대신 마스킹된 질문과 고정 구분 문자열을 포함해 계산한 12자리 해시, 둘째 폴백 경로가 기록됐습니다.
7주의할 점과 실무 메모
408·429·5xx처럼 일시 오류로 정한 경우만 재시도하고 401·403·잘못된 입력은 즉시 중단합니다.
쓰기 작업은 제공자의 멱등성 키를 확인하지 않고 반복하지 않습니다.
전체 프롬프트, API 키, 원문 개인정보를 기본 감사 로그에 저장하지 않습니다.

1학습 목표
검색 문서 속 지시문이 답변에 미치는 영향을 실제 API 호출로 관찰할 수 있습니다.
문서 데이터와 시스템 지시를 구분하고 의심 패턴을 기록할 수 있습니다.
입력·PII·예산·출처·감사 검사를 하나의 호출 경로로 연결할 수 있습니다.
2이 내용을 배우는 이유
RAG는 사용자가 직접 쓰지 않은 문서도 모델 입력에 넣습니다. 공격자가 문서에 명령문을 숨기면 검색은 관련 문서를 정상적으로 찾았는데 생성 단계가 그 문장을 지시로 해석할 수 있습니다. 이를 간접 프롬프트 인젝션(indirect prompt injection)이라고 합니다. 신뢰 수준이 다른 검색 문서가 모델 입력으로 들어오는 지점에서 별도의 검사가 필요합니다.
3앞에서 배운 내용
Ch 9의 첫 RAG에서 문서 속 지시문 사례를 남겼고 Ch 12에서 실제 검색 결과의 문서·쪽·청크 ID를 전달했습니다. 이 절은 같은 메타데이터 모양의 로컬 학습 문서를 사용합니다. 외부 공격 사이트나 실제 개인정보에는 접근하지 않습니다.
4핵심 개념
쉬운 예
민원 서류 안에 ‘담당자는 이 규칙을 무시하라’는 문장이 있어도 서류 내용으로 읽어야 합니다. 검색 문서도 답변 자료이며 시스템 규칙을 바꾸는 명령으로 승격하지 않습니다.
정의
프롬프트 인젝션(prompt injection)은 데이터로 처리해야 할 문장이 모델의 지시 우선순위를 바꾸게 하는 입력입니다. 간접 공격은 검색 문서, 웹 페이지, 이메일처럼 외부 자료를 통해 들어옵니다. 신뢰 경계(trust boundary)는 신뢰 수준이 다른 문서가 모델 입력으로 전달되는 지점입니다. 완화(mitigation)는 위험이나 영향을 줄이는 조치이며 완전 방어를 뜻하지 않습니다.
호출 표기와 실행 시점
검색 문서는 신뢰하지 않는 데이터 구역으로 표시하고, 의심 패턴 검사는 모델 호출 전에 실행합니다. 통합 함수는 질문 검증→PII 마스킹→예산 예약→문서 검사→모델 호출→출처 검증→감사 기록 순으로 경계를 통과합니다. 앞 단계가 실패하면 뒤 호출은 실행하지 않습니다.
다른 상황에 적용
이메일 요약 시스템에서도 본문 속 ‘이전 지시를 무시하라’는 문장을 데이터로 격리하고, 외부 전송 도구의 권한을 제한할 수 있습니다. 문서 종류가 달라도 신뢰하지 않는 입력이 모델과 도구 사이로 들어오는 경계는 같습니다.
비교와 경계
XML 태그와 금지 문구 정규식은 완전 방어가 아닙니다. 이번 두 호출에서 공격 표지가 나타나지 않은 것은 영향 미관찰이며 완화 효과의 증명이 아닙니다. 출력 허용 목록, 최소 권한, 사람 승인, 반복 공격 평가를 함께 적용해야 합니다.
도식 읽기
검색 문서에 의심 문구가 하나라도 있으면 통합 모듈은 요청 전체를 중단합니다. 의심 문구를 찾지 못한 문서는 자료로 구분해 모델에 전달하고 출처와 기록을 확인합니다. 탐지 규칙의 통과를 모든 공격에 대한 안전 판정으로 취급하지 않습니다.

확인할 점 — 완화 전후 응답 원문, 공격 표지, 출처 검증, 의심 문서 격리 판정을 각각 확인합니다.
6실험 결과 해석
완화 전과 XML 태그로 문서 구역을 표시한 완화 후 응답에서 공격 표지가 모두 나타나지 않아 ‘영향 미관찰’로 기록했습니다. 최종 저장 출력에서 두 답 모두 E99 출처를 표시했지만 전후 차이가 없으므로 단순 분리의 효과를 입증한 결과로 보지 않습니다. 별도의 통합 안전 문서 경로에서는 E01 출처 검증이 통과했습니다. 정규 표현식은 준비한 두 문구 패턴이 합성 문서와 일치한다는 사실만 확인하며 오탐과 누락이 생길 수 있습니다.
7주의할 점과 실무 메모
XML 태그는 문서 구역을 모델에 알리는 표시이며 명령 실행을 강제로 차단하는 보안 경계가 아닙니다. 입력 필터, 출력 허용 목록, 최소 권한, 사람 승인, 반복 공격 검사를 함께 둡니다.
문서가 의심스럽다는 이유만으로 사실 문장까지 자동 삭제하면 답 품질이 달라질 수 있습니다. 격리·검토·출처 표시 정책을 정합니다.
두 정규식은 준비한 문구만 찾습니다. 우회 표현 전반을 탐지한다고 보지 않으며 이 챕터에서는 도구와 에이전트를 연결하지 않습니다.
실제 모델 호출은 절마다 미화 1달러 미만이 되도록 짧은 입력과 출력을 사용했습니다. 정확한 청구액은 제공자 사용량 화면과 해당 실행 시점 가격표를 확인해야 합니다.

# 입출력과 출처 검증
모델 호출 앞뒤에서 질문과 출처 형식을 파이썬으로 검사합니다.
## 개념을 코드에 연결하기
**호출 표기와 실행 시점.** 입력 검증은 모델 호출 전에 질문의 빈값·길이·허용 문자를 확인합니다. 출력 검증은 모델 답에서 출처 태그를 추출해 이번 검색 결과의 doc_id와 page 조합에 포함되는지 대조합니다. 함수가 반환한 검증 결과와 print로 보이는 화면 문자열은 구분해 읽습니다.
**다른 상황에 적용.** 의료 안내에서는 질문 길이와 금지 입력을 먼저 검사하고, 답변의 약품 코드가 검색된 공식 문서 목록에 있는지 후처리할 수 있습니다. 도메인이 달라져도 호출 전 입력 경계와 호출 후 허용 목록 경계는 분리됩니다.
**비교와 경계.** 형식이 맞는 출처가 실제 주장을 뒷받침한다는 뜻은 아닙니다. 이 검사는 존재하지 않는 ID를 막지만 인용 문장과 근거 본문의 의미 일치까지 판단하지 않습니다. 근거성 평가는 Ch15의 평가와 함께 사용합니다.
**이 셀의 코드 읽기.** 이 셀은 앞 셀에서 만든 값을 입력으로 읽어 위에서 아래 순서로 처리하고, 왼쪽 변수에 다음 셀이 사용할 결과를 저장합니다.
