textbook/part7/ch34-cost-rate-limits/_src/01-프롬프트-캐시-계측.html

1학습 목표
프롬프트 캐시가 재사용하는 공통 접두어를 구성할 수 있습니다.
실제 API 사용량에서 캐시 읽기 토큰과 일반 입력 토큰을 분리할 수 있습니다.
API가 제공하지 않는 캐시 생성 값은 0이 아니라 None으로 기록할 수 있습니다.
2이 내용을 배우는 이유
서비스가 같은 정책 문서와 도구 설명을 요청마다 다시 보내면 입력 토큰이 반복됩니다. 프롬프트 캐싱(prompt caching)은 같은 접두어의 내부 계산을 재사용해 지연과 비용을 줄입니다. 그러나 설정만 보고 절감 효과를 확인할 수는 없습니다. 실제 응답의 사용량에서 몇 토큰을 캐시로 읽었는지 확인해야 합니다.
3앞에서 배운 내용
Ch 6에서는 모델 응답의 입력·출력 토큰을 기록했고, Ch 15에서는 추적 항목에서 캐시 읽기와 생성을 구분했습니다. 이번 절은 그 기록을 LangChain AIMessage의 실제 usage_metadata와 연결합니다. API 키는 프로젝트 루트의 .env에서 읽으며 값은 출력하지 않습니다.
4핵심 개념
반복되는 문서의 앞부분
매일 같은 신청서를 처리한다고 생각해 봅니다. 양식과 규칙은 그대로이고 마지막 문의만 바뀝니다. 캐시는 양식과 규칙에 해당하는 앞부분을 재사용합니다. 따라서 변하지 않는 지시문과 예시는 앞에 두고, 요청마다 바뀌는 질문은 뒤에 둡니다.접두어(prefix)입력의 처음부터 이어지는 같은 토큰 구간입니다.캐시 읽기(cache read)이전에 계산한 접두어를 다시 사용한 입력 토큰 수입니다.캐시 생성(cache creation)다음 요청에서 읽을 수 있도록 새로 저장한 구간의 양입니다.적중(cache hit)요청 접두어가 저장된 접두어와 일치해 재사용된 상태입니다.초록 상자의 같은 접두어를 두 번의 모델 호출에 사용합니다. 보라 상자는 모델 호출이며, 노란 상자에서 일반 입력 토큰과 캐시 읽기 토큰을 구분해 확인합니다.
OpenAI 공식 문서는 자동 캐싱이 1,024토큰 이상의 프롬프트에서 적용되며, 캐시 사용량은 cached_tokens에서 확인한다고 설명합니다. 이 실습은 충분히 긴 공통 접두어를 두 번 보내고 이 값을 직접 읽습니다.
코드 읽기와 개념 경계
프롬프트 캐시는 입력의 처음부터 같은 토큰 구간을 다시 사용할 때 적용됩니다. 예제는 고정 정책을 긴 stable_prefix로 만들고 마지막 질문만 바꿔 두 번 호출합니다. usage_metadata의 전체 입력 토큰과 input_token_details의 캐시 읽기 값을 따로 기록하므로, 두 번째 호출이 빨랐다는 느낌 대신 제공자가 반환한 사용량으로 적중을 판단합니다.
문장 내용이 비슷해도 앞부분의 토큰 배열이 달라지면 같은 접두어가 아닙니다. 날짜나 사용자 식별자를 맨 앞에 넣으면 뒤의 긴 정책까지 재사용되지 않을 수 있습니다. 반대로 캐시 적중은 답의 품질이나 최신성을 높이지 않으므로, 반복 지시문 안정성과 질문별 근거 갱신을 별도로 관리합니다.
5실행 예제
먼저 실행마다 달라지는 실험 ID와 긴 정책 접두어를 결합하고 같은 모델에 두 번 전송합니다. 고유한 실험 ID는 이전 실행의 캐시와 구분하며, 두 요청 안에서는 같은 값을 유지합니다. 노트북은 두 응답의 본문이 비어 있지 않고 두 번째 요청에서 1,024토큰 이상이 실제로 읽혔는지 검사합니다.
확인할 점 — 실행 결과에서 첫 호출의 cache_read는 0이고 두 번째 호출은 11,520토큰이었습니다. 캐시 생성 필드는 응답 메타데이터에 없어 None으로 기록되었습니다.
6실험 결과 해석
2026년 9월 11일 실행에서 첫 호출은 입력 11,805토큰, 캐시 읽기 0토큰이었고 두 번째 호출은 입력 11,804토큰 가운데 11,520토큰을 캐시에서 읽었습니다. 두 번째 호출의 비캐시 입력은 284토큰이었습니다. 두 호출 모두 실제 텍스트와 출력 토큰을 반환했습니다. 이 결과는 해당 실행의 두 요청에서 냉·온 조건을 관찰했다는 뜻이며 모든 요청에서 같은 적중률을 보장하지 않습니다.
cache_creation=None은 생성량이 0이라는 뜻이 아닙니다. 현재 사용한 LangChain usage_metadata에서 별도 생성 값을 얻지 못했다는 뜻입니다. 제공되지 않은 값과 실제 0을 구분해야 비용 대시보드가 잘못된 확신을 주지 않습니다.
7주의할 점과 실무 메모
공통 지시문 가운데 한 토큰이 바뀌어도 그 뒤의 접두어 재사용 범위가 줄 수 있습니다.
캐시 적중은 출력 품질 평가가 아닙니다. 같은 질문의 정답률과 지연을 별도로 측정합니다.
단가는 모델과 처리 방식에 따라 바뀝니다. 사용량 원자료와 단가 기준일을 함께 저장합니다.
긴 접두어를 만들기 위해 불필요한 문장을 추가하면 전체 입력과 관리 비용이 늘 수 있습니다.
8정리와 다음 절
변하지 않는 내용을 앞에 배치하면 같은 접두어를 재사용하기 쉽습니다.
캐시 절감은 cached_tokens로 확인합니다.
제공되지 않은 캐시 생성 값은 0으로 바꾸지 않습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 즉시 응답이 필요 없는 요청을 Batch API 입력으로 묶어 처리 비용을 줄입니다.
9복습 문제
문제와 해설
1. 요청마다 바뀌는 고객 질문을 긴 정책보다 앞에 두면 캐시 재사용에 어떤 영향이 있나요?
접두어가 일찍 달라져 뒤쪽의 같은 정책도 재사용하기 어려워집니다.
2. cache_creation=None을 0으로 저장하면 왜 문제가 되나요?
계측 미지원과 실제 생성량 0을 구분할 수 없기 때문입니다.
3. 캐시 읽기 토큰이 많으면 답의 품질도 높다고 볼 수 있나요?
볼 수 없습니다. 캐시 사용량은 계산 재사용을 나타내며 품질은 별도 평가가 필요합니다.

1학습 목표
Batch API용 JSONL 입력을 만들 수 있습니다.
각 요청의 식별자와 구조를 제출 전에 검사할 수 있습니다.
즉시 처리와 비동기 배치 처리의 선택 기준을 설명할 수 있습니다.
2이 내용을 배우는 이유
야간 평가, 대량 분류, 임베딩 생성처럼 완료 시각에 여유가 있는 작업은 비동기 배치로 모을 수 있습니다. OpenAI Batch API는 별도 처리 한도와 24시간 완료 창을 제공하며 표준 동기 API 대비 50% 할인된 가격을 안내합니다. 비용을 줄이는 대신 즉시 결과를 받을 수 없다는 조건을 받아들여야 합니다.
3앞에서 배운 내용
Ch 15의 runs/batch-eval-input.jsonl에서는 평가 입력 형식을 준비했습니다. 이번 절은 같은 JSON Lines(JSONL) 원리를 Responses API의 실제 배치 요청 구조에 적용합니다. JSONL은 한 줄마다 하나의 JSON 객체를 저장하는 파일 형식입니다.
4핵심 개념
접수함에 모아 처리하기
창구 직원이 손님 한 명마다 즉시 서류를 처리하는 방식과, 마감 시각까지 접수한 서류를 한꺼번에 처리하는 방식은 기다림과 운영 비용이 다릅니다. Batch API는 두 번째 방식에 해당합니다. 요청자는 custom_id로 각 결과를 원래 업무와 연결합니다.비동기 처리(asynchronous processing)요청 제출과 결과 수신이 같은 연결에서 즉시 끝나지 않는 처리 방식입니다.JSONL각 줄이 독립된 JSON 객체인 텍스트 형식입니다.custom_id배치 결과를 원래 요청과 연결하기 위해 사용자가 정하는 고유 값입니다.완료 창(completion window)배치 처리가 완료되어야 하는 시간 범위이며 현재 공식 문서는 24h를 안내합니다.초록 상자의 요청 세 건을 JSONL 형식으로 저장하고 파란 상자의 검증을 실행합니다. 마지막 상자는 이번 실습이 외부 제출 전에 중단하는 범위를 표시합니다.
코드 읽기와 개념 경계
JSONL은 파일 전체가 하나의 JSON 배열인 형식이 아니라 각 줄이 독립된 JSON 객체인 형식입니다. 각 Batch 요청에는 결과를 원래 업무와 연결할 custom_id, HTTP 메서드, 엔드포인트, 요청 본문이 들어갑니다. 예제는 세 객체를 줄 단위로 직렬화하고 다시 읽어 필수 키와 식별자 중복을 검사합니다. 여기까지는 로컬 입력 검증이며 업로드나 배치 생성은 실행하지 않습니다.
Batch는 즉시 응답이 필요한 대화보다 야간 분류·대량 평가처럼 완료를 기다릴 수 있는 작업에 맞습니다. 제출 순서와 결과 순서가 같다고 가정하지 말고 custom_id로 결합해야 합니다. 일부 요청만 실패할 수 있으므로 배치 전체 상태와 각 줄의 오류를 나누어 재처리합니다.
5실행 예제
고객 문의 세 건을 /v1/responses 요청으로 직렬화합니다. 각 줄에는 custom_id, method, url, body가 있습니다. 파일을 다시 읽어 필수 키와 식별자 중복 여부를 검사합니다.
확인할 점 — 실행 결과는 요청 수 3과 JSONL 구조 유효 True를 출력합니다. 실제 업로드나 배치 생성은 수행하지 않습니다.
6일부러 실패해 보기
세 개의 JSON 객체를 하나의 배열로 저장하면 일반 JSON으로는 유효하지만 JSONL 배치 입력은 아닙니다. 실패 셀은 첫 줄을 읽었을 때 목록이 나온다는 사실을 확인합니다. 수정 셀은 객체마다 줄바꿈을 넣고 각 줄이 사전인지 다시 검사합니다.
7주의할 점과 실무 메모
custom_id는 배치 안에서 고유해야 하며 결과 순서가 입력 순서와 같다고 가정하지 않습니다.
입력 파일 업로드와 배치 생성은 외부 작업을 시작합니다. 이 교재는 구조를 완성하고 로컬 검증한 뒤 실제 제출은 수행하지 않았습니다.
24시간 완료 창은 즉시 응답이 필요한 사용자 요청에 맞지 않습니다.
할인율과 지원 엔드포인트는 바뀔 수 있으므로 배포 전에 공식 문서를 다시 확인합니다.
8정리와 다음 절
Batch API는 완료 시각에 여유가 있는 대량 작업에 사용합니다.
각 요청은 JSONL 한 줄과 고유한 custom_id를 가져야 합니다.
파일 구조 검증과 실제 제출을 별도 단계로 둡니다.
다음 학습과 이어지는 지점 — 다음 절에서는 요청 난이도에 따라 모델을 선택해 온라인 호출의 단가를 조정합니다.
9복습 문제
문제와 해설
1. Batch API가 고객 채팅의 첫 응답에 맞지 않는 이유는 무엇인가요?
결과가 비동기로 처리되며 현재 완료 창이 24시간이기 때문입니다.
2. 결과를 원래 문의와 연결하는 필드는 무엇인가요?
custom_id입니다.
3. JSON 배열 파일과 JSONL의 차이는 무엇인가요?
JSON 배열은 전체가 하나의 값이고, JSONL은 각 줄이 독립된 JSON 객체입니다.

1학습 목표
요청 특성에 따라 두 모델 가운데 하나를 고르는 규칙을 작성할 수 있습니다.
같은 평가 사례에서 품질과 실제 토큰 비용을 함께 비교할 수 있습니다.
작은 표본의 결과를 서비스 전체 성능으로 일반화할 수 없는 이유를 설명할 수 있습니다.
2이 내용을 배우는 이유
상태 확인과 단일 의도 분류에는 긴 추론이 필요하지 않을 수 있습니다. 반면 여러 규정을 비교하고 근거를 작성하는 요청은 더 높은 성능의 모델이 필요할 수 있습니다. 모델 라우팅(model routing)은 정해 둔 조건에 따라 모델을 선택하는 방법입니다. 비용 절감은 품질 기준을 만족할 때만 의미가 있습니다.
3앞에서 배운 내용
Ch 6에서는 같은 작업을 여러 제공자에 실행해 응답·비용·지연을 비교했습니다. Ch 18에서는 코드가 분기를 고르는 라우팅 패턴을 구현했습니다. 이번 절은 서비스 운영 관점에서 짧은 분류는 gpt-5.4-nano, 복잡한 설명은 gpt-5.4-mini로 보내는 규칙을 만듭니다.
4핵심 개념
업무 난이도에 맞는 담당자 배정
모든 문의를 가장 숙련된 담당자에게 배정하면 쉬운 문의도 비싼 자원을 사용합니다. 반대로 모든 문의를 초급 담당자에게 주면 복잡한 사례의 품질이 낮아질 수 있습니다. 라우터는 요청 길이, 필요한 도구, 위험 수준, 평가 점수처럼 관찰 가능한 조건으로 모델을 고릅니다.모델 라우팅요청 조건을 확인한 뒤 사용할 모델을 선택하는 처리입니다.품질 기준선배포 가능한 최소 정확도나 평가 점수입니다.오분류 비용라우터가 요청 난이도를 잘못 판단했을 때 생기는 재처리와 품질 손실입니다.폴백(fallback)작은 모델 결과가 기준을 만족하지 못할 때 상위 모델로 다시 처리하는 경로입니다.초록 상자는 고객 요청, 파란 상자는 코드로 정한 난이도 규칙, 보라 상자는 두 모델을 나타냅니다. 노란 상자는 품질과 비용을 비교하는 항목입니다. 실습에서는 같은 세 질문을 두 모델에 각각 보내 비교하고, 뒤에서 별도 요청 두 건에 선택 규칙을 적용합니다.
2026년 9월 11일 공식 모델 페이지 기준으로 GPT-5.4 nano 표준 입력은 백만 토큰당 0.20달러, 출력은 1.25달러입니다. GPT-5.4 mini는 입력 0.75달러, 출력 4.50달러입니다. 단가는 변경될 수 있으므로 코드와 함께 기준일을 저장합니다.
코드 읽기와 개념 경계
모델 라우터는 요청을 관찰해 사용할 모델을 선택하는 함수입니다. 이 예제는 먼저 같은 세 분류 사례를 두 모델에 모두 실행하여 정확도와 실제 토큰 사용량을 기록합니다. 그 뒤 route 함수가 문자열 길이와 비교, 근거 포함 여부로 nano와 mini를 고릅니다. 라우팅 규칙의 출력은 모델 이름이며, 실제 모델 답은 선택 뒤 별도 호출에서 얻습니다.
길이가 짧다고 항상 쉬운 요청은 아니고 긴 요청이 항상 어려운 것도 아닙니다. 위험한 업무, 도구 필요 여부, 작은 모델의 확신 부족 같은 신호를 함께 평가하고 폴백 경로를 둡니다. 세 사례에서 두 모델이 모두 맞았더라도 전체 문의 분포의 품질 차이를 증명하지 않으므로 더 큰 고정 평가 세트로 라우터 자체를 검사합니다.
5실행 예제
배송·환불·상품 세 범주를 가진 문의 세 건을 두 모델에 똑같이 실행합니다. 답은 범주 하나로 제한하고 정확 일치로 채점합니다. 실제 입력·출력 토큰에 공식 단가를 적용해 표본 전체 비용을 계산하고, 응답 원문을 정답과 나란히 저장합니다.
확인할 점 — nano는 3문항 중 2문항, mini는 3문항을 맞혔습니다. nano는 상품 문의를 배송으로 잘못 분류했습니다.
6실험 결과 해석
실행된 여섯 번의 API 호출에서 gpt-5.4-nano 정확도는 0.6667, 추정 비용은 0.00003325달러였습니다. gpt-5.4-mini 정확도는 1.0, 추정 비용은 0.00012225달러였습니다. 이 세 사례에서는 nano가 더 저렴했지만 모든 사례를 맞히는 품질 기준을 충족하지 못했습니다. 따라서 “짧은 요청은 모두 nano”라는 규칙을 바로 배포할 수 없습니다. 프롬프트와 구조화 출력 조건을 개선하거나, 실패 검증 뒤 mini로 보내는 폴백을 측정해야 합니다.
비용 계산은 GPT-5.4 nano 입력 0.20달러·출력 1.25달러, GPT-5.4 mini 입력 0.75달러·출력 4.50달러라는 2026년 9월 11일 표준 처리 단가를 반영했습니다. 캐시, Batch, 장문 컨텍스트, 도구 호출 비용은 포함하지 않았습니다. 첫 호출과 재처리 비용을 모두 포함해야 실제 라우팅 비용을 알 수 있습니다.
7주의할 점과 실무 메모
요청 길이만으로 난이도를 완전히 알 수 없습니다. 짧지만 위험이 큰 요청은 상위 경로로 보냅니다.
라우팅 임계값은 실제 서비스 평가셋으로 정하고 정기적으로 다시 측정합니다.
모델 별칭의 동작과 가격이 바뀔 수 있습니다. 재현이 필요하면 지원되는 스냅샷을 검토합니다.
작은 모델의 실패 후 재호출이 많으면 예상한 절감액이 줄어듭니다.
8정리와 다음 절
쉬운 요청에 작은 모델을 사용하되 품질 기준선을 먼저 정합니다.
비용은 실제 토큰과 기준일이 있는 단가로 계산합니다.
라우터의 오분류와 폴백 비용도 전체 비용에 포함합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 선택한 모델이 429를 반환할 때 재시도와 동시성 제한으로 처리량을 안정화합니다.

1학습 목표
HTTP 429 응답을 통제된 로컬 서버에서 재현할 수 있습니다.
지수 백오프와 지터를 적용해 재시도 간격을 분산할 수 있습니다.
큐와 세마포어로 동시 실행 수를 제한할 수 있습니다.
2이 내용을 배우는 이유
모델 API에는 분당 요청 수와 분당 토큰 수 같은 제한이 있습니다. 요청이 한꺼번에 몰리면 서버는 HTTP 429로 현재 요청을 받을 수 없다고 알릴 수 있습니다. 즉시 같은 요청을 반복하면 다시 제한에 걸리고 전체 서비스의 부하도 커집니다. 재시도 시점과 동시에 처리할 작업 수를 조절해야 합니다.
3앞에서 배운 내용
Ch 16에서는 호출 한도와 재시도 함수를 직접 만들었습니다. Ch 30에서는 FastAPI 비동기 요청 처리를 배웠습니다. 이번 절은 그 두 내용을 운영 흐름으로 연결합니다. 실제 제공자에게 의도적으로 429를 만들지 않고, 로컬 HTTP 서버가 처음 두 요청에만 429를 반환하도록 구성합니다.
4핵심 개념
문이 닫혔을 때 줄을 정리하기
입장 제한이 걸린 장소 앞에서 모든 사람이 동시에 문을 두드리면 혼잡이 커집니다. 대기열은 도착한 순서를 보관하고, 동시성 제한은 안에 들어가는 사람 수를 정합니다. 백오프는 거절된 요청이 다시 시도하기 전 기다리는 시간을 늘립니다.Rate limit일정 시간 동안 허용되는 요청이나 토큰의 최대량입니다.HTTP 429요청이 너무 많아 현재 처리할 수 없음을 나타내는 상태 코드입니다.지수 백오프(exponential backoff)재시도 횟수가 늘수록 대기 시간을 배수로 늘리는 방법입니다.지터(jitter)여러 클라이언트의 재시도 시점이 겹치지 않도록 더하는 작은 무작위 지연입니다.세마포어(semaphore)동시에 실행할 수 있는 작업 수를 제한하는 동기화 도구입니다.빨간 상자의 로컬 429 응답을 받으면 파란 상자에서 재시도 대기 시간을 계산하고, 재시도 뒤 초록 상자의 200 응답을 확인합니다. 같은 절의 큐 실험은 별도로 여섯 개의 작업을 처리하며 최대 동시 실행 수를 측정합니다.
코드 읽기와 개념 경계
asyncio.Queue는 기다리는 작업을 보관하고, Semaphore(2)는 동시에 처리 구역에 들어갈 작업을 두 개로 제한합니다. queue.get()으로 항목을 꺼내고 처리가 끝난 뒤 task_done()을 호출합니다. 별도의 로컬 HTTP 서버는 처음 두 요청에 429를 반환해, 재시도 없는 호출과 백오프 호출을 같은 조건에서 비교하게 합니다.
지수 백오프는 시도 횟수에 따라 기본 대기 시간을 늘리고 지터는 여러 클라이언트가 같은 순간 다시 요청하는 현상을 줄입니다. 모든 오류를 재시도하면 안 됩니다. 인증 실패나 잘못된 입력은 기다려도 해결되지 않으며, 429와 일시적 5xx도 최대 횟수와 전체 시간 한도 안에서만 재시도합니다.
5실행 예제
표준 라이브러리의 HTTPServer를 로컬 주소에서 실행합니다. 서버는 첫 두 요청에 429, 세 번째부터 200을 반환합니다. 외부 API의 Rate limit을 소모하지 않으면서 실제 HTTP 오류 처리 코드를 실행할 수 있습니다.
확인할 점 — 첫 요청은 429를 반환합니다. 백오프 함수는 대기 기록을 남기고 최종 200을 받습니다. 실험에서는 작업 여섯 개를 처리했고, 최대 동시 실행 수는 2였습니다.
6일부러 실패해 보기
재시도 없는 코드는 첫 429를 그대로 호출자에게 전달합니다. 수정 코드에서는 429만 재시도하며, 다른 HTTP 오류는 숨기지 않습니다. 대기 시간은 0.05 × 2^attempt에 작은 지터를 더해 계산합니다. 실제 운영에서는 응답 헤더의 재시도 안내와 SDK의 내장 재시도 정책도 함께 확인합니다.
7주의할 점과 실무 메모
실패한 요청도 Rate limit 계산에 포함될 수 있으므로 무제한 재시도를 두지 않습니다.
응답을 이미 일부 처리한 비멱등 작업은 같은 요청을 다시 실행하기 전에 중복 효과를 확인합니다.
큐가 계속 길어지면 대기 시간 상한, 취소, 우선순위 정책이 필요합니다.
세마포어의 적정 값은 계정 등급, 모델, 평균 입력 토큰에 따라 달라집니다.
8정리와 다음 절
429는 즉시 반복하지 않고 제한된 횟수로 백오프합니다.
지터는 여러 요청이 같은 시점에 다시 몰리는 현상을 줄입니다.
큐와 세마포어는 유입량과 동시 실행량을 분리합니다.
다음 학습과 이어지는 지점 — 마지막 절에서는 처리량뿐 아니라 대화당 누적 비용을 p95로 관리하고 요청 전 예산 가드를 적용합니다.

4핵심 개념
평균 뒤에 숨은 비싼 대화
열 명 가운데 아홉 명의 비용이 낮고 한 명의 비용만 매우 높으면 평균만으로는 꼬리 구간을 설명하기 어렵습니다. 백분위수(percentile)는 값을 작은 순서로 정렬했을 때 일정 비율이 그 값 이하에 놓이는 경계를 나타냅니다. p95는 관찰값의 약 95%가 그 값 이하라는 뜻입니다.대화당 비용같은 대화 식별자에 속한 모든 모델·도구 호출 비용의 합입니다.p50비용 분포의 가운데에 해당하는 값입니다.p95비용이 큰 쪽 5%에 들어가기 직전의 경계를 나타내는 값입니다.예산 가드(budget guard)현재 사용액과 다음 호출의 예상 최대 비용이 상한을 넘는지 요청 전에 검사하는 코드입니다.하드 리밋(hard limit)넘으면 호출을 시작하지 않는 절대 상한입니다.초록 상자의 호출 기록을 대화별로 합산하고 노란 상자에서 p95를 계산합니다. 실습에서는 p50도 함께 계산합니다. 파란 상자의 예산 가드는 현재 비용과 다음 호출의 예상 비용을 상한과 비교해 실행 여부를 정합니다.
이 실습은 최근접 순위(nearest rank) 방식을 사용합니다. 정렬한 값이 n개일 때 ceil(0.95 × n)번째 값을 p95로 고릅니다. 도구마다 보간 방식이 다를 수 있으므로 지표 이름과 함께 계산 방식을 기록합니다.
코드 읽기와 개념 경계
대화당 비용은 개별 호출 행을 conversation 식별자로 묶어 합한 값입니다. nearest_rank는 값을 정렬하고 ceil(percentile × n)번째 값을 고릅니다. 표본이 열 개이면 p95가 사실상 가장 큰 관찰값이 되므로 출력의 p95는 한 대화에 민감합니다. 계산 도구마다 보간 방식이 다를 수 있어 지표 이름과 방식을 함께 기록합니다.
allow_call(spent, estimated_max, hard_limit)은 이미 쓴 값과 다음 호출의 예상 최대값을 더해 요청 전에 실행 여부를 반환합니다. 실제 사용량을 사후 집계하는 p95와 호출 전 차단하는 예산 가드는 시점이 다릅니다. 예상치를 너무 낮게 두면 상한을 넘을 수 있고 너무 높게 두면 정상 요청을 막으므로 모델·도구 경로별 상한을 관찰 자료로 갱신합니다.
5실행 예제
열 개의 대화에서 발생한 호출별 비용을 대화 식별자로 합칩니다. 한 대화에 두 개의 호출이 있으면 두 값을 더합니다. 정렬된 합계에서 p50과 p95를 구한 뒤, 현재 사용액과 다음 호출의 예상 최대 비용이 0.005달러 상한을 넘는지 검사합니다.
확인할 점 — 관찰된 p50은 0.0020달러, p95는 0.0062달러입니다. 0.0045달러를 이미 쓴 대화가 최대 0.001달러인 호출을 시작하려 하면 가드가 차단합니다.
6실험 결과 해석
목표를 0.005달러로 두었을 때 관찰 p95 0.0062달러는 목표를 초과했습니다. 열 개의 표본에서 최근접 순위 p95는 최댓값과 같으므로 한 대화의 변화에 매우 민감합니다. 표본을 늘리고 시간 구간을 고정한 뒤 추세를 함께 봐야 합니다. 이 값은 실제 운영 청구서가 아니라 비용 집계 방법을 확인하기 위한 고정 실습 데이터입니다.
비용을 절반으로 줄이는 과제에서는 어떤 품질과 지연을 포기했는지도 기록합니다. 캐시를 늘리면 접두어 변경 자유도가 줄 수 있고, Batch를 쓰면 완료가 늦어집니다. 작은 모델을 쓰면 어려운 요청의 실패율이 오를 수 있으며, 동시성을 낮추면 대기열이 길어질 수 있습니다. 하나의 비용 숫자만으로 최적화를 완료했다고 판단하지 않습니다.
7주의할 점과 실무 메모
예상 최대 비용은 입력 상한과 출력 상한을 포함해 보수적으로 계산합니다.
요청 후 실제 사용량을 다시 기록해 예약한 예산과 차이를 정산합니다.
예산 초과 시 사용자에게 재시도만 요구하면 요청 폭주가 생길 수 있으므로 대체 모델이나 작업 축소 정책을 둡니다.
p95 계산 방식과 표본 기간을 바꾸면 이전 지표와 직접 비교하기 어렵습니다.
8정리와 다음 절
호출 비용은 대화 식별자로 합쳐야 전체 경로의 비용을 볼 수 있습니다.
p95는 평균이 숨기는 비싼 꼬리 대화를 보여 줍니다.
예산 가드는 호출 전에 예상 최대 비용을 검사하고 실제 사용량으로 다시 정산합니다.

# 프롬프트 캐시 계측

프롬프트 캐시는 입력의 처음부터 같은 토큰 구간을 다시 사용할 때 적용됩니다. 예제는 고정 정책을 긴 `stable_prefix`로 만들고 마지막 질문만 바꿔 두 번 호출합니다. `usage_metadata`의 전체 입력 토큰과 `input_token_details`의 캐시 읽기 값을 따로 기록하므로, 두 번째 호출이 빨랐다는 느낌 대신 제공자가 반환한 사용량으로 적중을 판단합니다.

## 실험 결과 해석
캐시 적중 여부는 시간 추정이나 파일 수가 아니라 API가 반환한 사용량으로 판정합니다. 생성 토큰이 제공되지 않았다는 사실과 0을 구분합니다.

## 코드 읽기와 개념 경계
JSONL은 파일 전체가 하나의 JSON 배열인 형식이 아니라 각 줄이 독립된 JSON 객체인 형식입니다. 각 Batch 요청에는 결과를 원래 업무와 연결할 `custom_id`, HTTP 메서드, 엔드포인트, 요청 본문이 들어갑니다. 예제는 세 객체를 줄 단위로 직렬화하고 다시 읽어 필수 키와 식별자 중복을 검사합니다. 여기까지는 로컬 입력 검증이며 업로드나 배치 생성은 실행하지 않습니다.

## 실패 재현
한 줄을 일반 JSON 배열로 감싸면 JSONL의 ‘한 줄에 한 객체’ 규칙을 어깁니다.

# 백오프·큐·동시성 제한
통제된 로컬 HTTP 서버에서 429를 재현하고 재시도 대기와 동시성 제한을 확인합니다.
## 실행 환경 준비
## 코드 읽기와 개념 경계
`asyncio.Queue`는 기다리는 작업을 보관하고, `Semaphore(2)`는 동시에 처리 구역에 들어갈 작업을 두 개로 제한합니다. `queue.get()`으로 항목을 꺼내고 처리가 끝난 뒤 `task_done()`을 호출합니다. 별도의 로컬 HTTP 서버는 처음 두 요청에 429를 반환해, 재시도 없는 호출과 백오프 호출을 같은 조건에서 비교하게 합니다.
지수 백오프는 시도 횟수에 따라 기본 대기 시간을 늘리고 지터는 여러 클라이언트가 같은 순간 다시 요청하는 현상을 줄입니다. 모든 오류를 재시도하면 안 됩니다. 인증 실패나 잘못된 입력은 기다려도 해결되지 않으며, 429와 일시적 5xx도 최대 횟수와 전체 시간 한도 안에서만 재시도합니다.
## 로컬 429 서버
처음 두 요청에는 429를 반환하고 세 번째 요청부터 200을 반환합니다. 외부 제공자에는 요청하지 않습니다.
## 큐와 동시성 제한
세마포어가 동시에 처리하는 작업 수를 2개로 제한합니다.
## 실패 재현
재시도 없이 한 번만 요청하면 429가 그대로 호출자에게 전달됩니다.
## 지수 백오프와 지터 적용
시도 횟수가 늘수록 대기 시간을 늘리고 작은 무작위 지연을 더합니다.

## 실행 환경 준비
## 코드 읽기와 개념 경계
대화당 비용은 개별 호출 행을 `conversation` 식별자로 묶어 합한 값입니다. `nearest_rank`는 값을 정렬하고 `ceil(percentile × n)`번째 값을 고릅니다. 표본이 열 개이면 p95가 사실상 가장 큰 관찰값이 되므로 출력의 p95는 한 대화에 민감합니다. 계산 도구마다 보간 방식이 다를 수 있어 지표 이름과 방식을 함께 기록합니다.
`allow_call(spent, estimated_max, hard_limit)`은 이미 쓴 값과 다음 호출의 예상 최대값을 더해 요청 전에 실행 여부를 반환합니다. 실제 사용량을 사후 집계하는 p95와 호출 전 차단하는 예산 가드는 시점이 다릅니다. 예상치를 너무 낮게 두면 상한을 넘을 수 있고 너무 높게 두면 정상 요청을 막으므로 모델·도구 경로별 상한을 관찰 자료로 갱신합니다.
## 대화별 호출 기록
각 대화는 한 번 이상의 모델 호출을 포함합니다. 아래 값은 비용 계산을 학습하기 위한 고정 기록입니다.
## 최근접 순위 방식 p95
값을 정렬한 뒤 `ceil(0.95 × n)`번째 값을 고릅니다. 계산 방식을 대시보드 문서에 함께 기록해야 합니다.
## 예산 가드 판정
요청 전에 예상 최대 비용을 더해 상한을 넘으면 호출을 시작하지 않습니다.
## 목표치와 비교
목표를 0.005달러로 두고 p95를 판정합니다. 표본이 10개라서 한 개의 큰 값에 민감합니다.
