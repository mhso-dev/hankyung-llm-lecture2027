2이 내용을 배우는 이유
Ch 8에서 모델이 참고할 내용인 컨텍스트를 다루는 네 가지 방법을 배웠습니다. 그중 Select는 "지금 필요한 것만 골라 넣는다"였고, 실습에서는 사람이 손으로 골랐습니다. 문서가 10쪽이면 손으로 고를 수 있습니다. 문서가 100건, 1,000쪽이 되면 손으로 고를 수 없습니다. 질문이 들어올 때마다 그 질문에 맞는 쪽을 자동으로 골라 프롬프트에 넣어야 합니다. 그 자동화 장치가 검색이고, 검색을 붙인 생성이 RAG입니다.
이 챕터에서는 제공된 PDF로 답을 생성하는 RAG를 완성합니다. Ch 10에서 문서 처리 방법을 비교하고, Ch 11에서 품질을 측정한 뒤 Ch 12에서 높입니다. 이 순서에는 이유가 있습니다. 동작하는 결과물이 있어야 "어디가 나쁜가"를 확인할 수 있고, 문제 지점을 알아야 Ch 11에서 무엇을 측정할지 정할 수 있으며, 측정할 수 있어야 Ch 12에서 5일 동안 튜닝할 수 있습니다. 완주가 먼저, 측정이 다음, 튜닝이 마지막입니다.
커리큘럼의 두 규칙을 여기서 다시 확인합니다. 첫째, 이 챕터에는 에이전트가 없습니다. 검색을 몇 번 할지, 몇 개를 가져올지, 답을 어떻게 만들지는 전부 학생이 코드에 적습니다. 모델은 마지막 한 단계, 문장을 만드는 일만 합니다. 둘째, 이 챕터는 측정 도구(Ch 11)보다 앞에 있으므로 "어느 설정이 더 좋은가"를 아직 판정하지 않습니다. 대신 설정과 결과를 같은 형식으로 남기는 반복 실험 틀을 06절에서 만듭니다. 이런 실행 틀을 실험 하네스라고 부릅니다.

4핵심 개념
비유 — 오픈북 시험
RAG는 오픈북 시험과 비슷합니다. 검색으로 고른 몇 쪽을 프롬프트에 넣고, 모델에 그 문서를 근거로 답하라고 요청합니다. 그러나 모델이 학습한 지식을 섞거나 문서에 없는 내용을 만들 수도 있습니다. 따라서 맞는 쪽을 검색했는지 먼저 보고, 답의 내용과 출처가 실제 문서와 일치하는지도 확인해야 합니다.
{{img:01-오픈북-비유|같은 학생이 왼쪽에서는 빈 책상에서 고민하고, 오른쪽에서는 책갈피가 꽂힌 세 쪽을 보며 답을 씁니다.}}
왼쪽은 기억만으로 답하는 학생(순수 LLM), 오른쪽은 책상에 올라온 세 쪽을 보며 답하는 학생(RAG)입니다. 책갈피가 출처 표기에 해당합니다.보는 순서 — ① 왼쪽 학생의 물음표 → ② 오른쪽 책상의 세 쪽 → ③ 쪽에서 답안지로 가는 화살표.
정의
RAG (Retrieval-Augmented Generation, 검색 증강 생성)
질문이 들어오면 먼저 문서 저장소에서 관련 조각을 검색하고, 그 조각을 프롬프트에 넣어 답을 생성하는 방식입니다. "증강"은 프롬프트에 검색 결과를 더한다는 뜻입니다.
색인 (indexing)
문서를 미리 잘게 나누고 벡터로 바꿔 저장해 두는 준비 작업입니다. 문서, 청크 설정, 임베딩 모델 중 하나가 바뀌면 다시 실행합니다.
청크 (chunk)
문서를 검색 단위로 자른 조각입니다. 청크 크기는 각 절의 설정에 따라 달라지며, 값을 바꾼 뒤 실제 길이와 본문을 확인합니다. 검색 결과는 쪽이 아니라 청크 단위로 반환됩니다.
벡터스토어 (vector store)
청크와 그 벡터를 함께 담아 두고, 질문 벡터와 가까운 것을 찾아 주는 저장소입니다. 이 챕터에서는 메모리에 두는 InMemoryVectorStore를 씁니다.
top-k 검색
질문과 가장 가까운 청크 k개를 가져오는 것입니다. k는 학생이 정합니다. 이 절의 기본 실행은 k=2이고, 이어서 k=1과 비교합니다.
출처 인용 (citation)
답의 근거로 사용한 문서와 쪽을 표기하는 형식입니다. 표기가 실제 근거와 일치하는지는 별도로 확인해야 합니다. 출처 표기는 RAG의 실용적인 장점 중 하나입니다.
도식 — 두 흐름
RAG에는 시점이 다른 두 흐름이 있습니다. 위쪽 색인은 문서·청크 설정·임베딩 모델이 바뀔 때 다시 실행되고, 아래쪽 질문 처리 과정은 질문이 들어올 때마다 실행됩니다. 두 흐름이 만나는 곳이 벡터스토어입니다. 색인 단계가 벡터스토어를 채우고, 질문 처리 단계가 관련 문서를 벡터스토어에서 꺼냅니다.
색인은 문서·청크 설정·임베딩 모델이 바뀔 때 다시 만들고, 질문 처리는 질문할 때마다 실행합니다. 파란 상자는 학생 코드가 고정한 흐름입니다. LLM 생성도 그 흐름 안에서 호출됩니다. 초록은 문서와 저장소이며, 모델이 실행 흐름을 판단하는 경우에 사용하는 보라색은 이 도식에 없습니다.
노트북은 각 상자의 입력과 반환값을 별도 셀에서 보여 줍니다. 다음 절부터 이 상자들을 왼쪽에서 오른쪽으로 하나씩 자세히 확인합니다.
상자노트북에서 실행할 동작입력 → 출력절
로더PdfReader로 쪽 반복PDF 경로 → 쪽 단위 Document 목록02
스플리터split_documents()쪽 → 청크 목록02
임베딩 + 벡터스토어add_documents()문서 → 벡터스토어에 저장03
top-k 검색similarity_search_with_score()질문 → (청크, 점수) k개03
프롬프트 조립 + 생성문맥 조립 후 invoke()청크 k개 + 질문 → 답 + 출처04
왜 셀을 단계별로 나눕니까?
처음에는 한 셀에서 한 단계의 결과를 확인합니다. PDF를 읽은 뒤 본문을 보고, 분할한 뒤 청크를 보고, 검색한 뒤 선택된 문서를 봅니다. 마지막 답이 예상과 다르면 이미 출력한 검색 결과부터 살펴볼 수 있습니다. 필요한 근거가 검색되었는지와 모델이 그 근거를 사용했는지를 차례로 확인하는 연습입니다.
각 셀은 앞에서 만든 변수와 LangChain의 메서드를 직접 사용합니다. 기본 실습에서는 별도 함수나 모듈을 먼저 만들 필요가 없습니다. 이후 Ch 13에서 흐름을 그래프로 표현할 때, 지금 확인한 각 단계의 입력과 출력을 바탕으로 노드의 역할을 정합니다.

검색을 실행할 순서와 횟수, k를 몇으로 할지
프롬프트에 무엇을 넣을지, 출처를 어떤 형식으로 붙일지, 답이 없을 때 무엇이라고 할지

첫 실행 코드를 읽는 순서
이 노트북은 색인과 질문 처리를 한 번에 실행하지만, 두 과정은 실행 시점이 다릅니다. PdfReader가 PDF를 쪽별 문자열로 읽고 Document(page_content=..., metadata=...)가 본문과 출처를 한 객체에 묶습니다. 이어서 스플리터가 여러 청크를 만들고, InMemoryVectorStore.from_documents(청크, 임베딩)가 청크를 벡터로 바꾸어 검색 가능한 저장소를 반환합니다. 여기까지는 문서가 바뀔 때 다시 수행하는 색인 단계입니다.
질문이 들어오면 similarity_search_with_score(질문, k=...)가 질문과 가까운 청크와 거리를 반환합니다. 검색 결과의 본문을 프롬프트에 넣은 뒤에야 model.invoke(프롬프트)가 실행되고, 반환된 AIMessage의 text를 화면에 출력합니다. 같은 PDF라도 질문이 바뀌면 질문 처리만 다시 실행할 수 있고, PDF 본문이나 임베딩 모델이 바뀌면 색인부터 다시 만들어야 합니다.
5실행 예제
아래 노트북을 첫 셀부터 순서대로 실행합니다. E01.pdf는 수업용 합성 문서이며, 코드가 labs/data/rag-corpus/pdf/easy/의 원본 경로를 찾으므로 파일을 복사할 필요가 없습니다. PDF 5쪽을 읽은 뒤 API 비용을 줄이기 위해 질문과 관련된 2~3쪽만 분할·임베딩합니다.
확인할 점 — PDF 경로, Document 수와 타입, 청크 수와 출처 정보(metadata), k=2와 k=1의 출처, 모델에 보낸 문맥이 셀별로 출력됩니다. 마지막 답에 PDF의 휴관일과 [E01 p.쪽] 출처가 함께 들어가는지 확인합니다.

7주의할 점과 실무 메모
"RAG를 붙이면 환각이 사라진다"는 말은 틀립니다. 검색된 문서에 답이 없으면 모델이 답하지 못하거나 근거 없는 내용을 생성할 수 있습니다. 05절에서는 검색 누락과 답변 불가에 따른 거부를 구분합니다.
버전을 고정합니다. 이 챕터는 LangChain 1.4, langchain-openai 1.6, Python 3.12 기준입니다. 검색으로 찾은 예제 코드는 0.x 시절 것이 많고, 그 API는 langchain-classic으로 옮겨졌습니다. from langchain.chains import RetrievalQA 같은 줄이 보이면 옛 코드입니다.
PDF 로더 패키지 관련 참고. 공식 문서의 PyPDFLoader는 langchain-community에 있는데, 이 패키지는 2026년 현재 유지보수 종료(sunset)가 예고되어 있습니다. 그래서 02절은 pypdf를 직접 호출해 쪽별 텍스트를 읽고 Document에 담습니다. 결과 형식(Document)은 같습니다.
한국어 문서는 글자 수와 토큰 수가 다릅니다. 문자 길이만으로 모델이 사용하는 토큰 수를 확정할 수 없습니다. 청크 크기를 정할 때 "토큰 기준인지 글자 기준인지"를 항상 확인합니다.
비용. 기본 노트북은 선택한 PDF 두 쪽과 짧은 질문을 사용합니다. 임베딩 셀이나 생성 셀을 다시 실행하면 API 비용이 추가될 수 있습니다. 이 절의 출력은 실제 청구액을 측정한 기록이 아닙니다.
8정리와 다음 절
제공된 합성 PDF를 쪽별 Document로 읽고, 질문과 관련된 두 쪽을 청크로 나누어 실제로 임베딩했습니다.
k=2와 k=1의 검색 출처를 먼저 비교한 뒤 청크 본문을 프롬프트에 넣었습니다.
init_chat_model().invoke()로 휴관일과 출처가 있는 답을 받았으며, 검색 문맥을 빼면 출처 검사가 실패했습니다.

커리큘럼이 정한 범위도 확인합니다. 로더·청킹은 통합 패키지를 그대로 쓰는 영역입니다(직접 구현 대상은 Ch 12의 키워드 검색과 의미 검색 결과 합치기·후보 순서 다시 매기기·질문 다시 쓰기입니다). 노트북은 pypdf.PdfReader로 PDF 한 쪽을 읽고, langchain-text-splitters로 나눕니다.

4핵심 개념
비유 — 책을 색인 카드로 옮기기
도서관 사서가 책 한 권을 색인 카드로 옮긴다고 생각해 보세요. 카드 한 장에는 글이 500자 정도 들어갑니다. 사서는 책을 앞에서부터 500자씩 베껴 쓰되, 문장이 카드 끝에서 잘리지 않도록 문단 경계에서 끊으려 합니다. 그리고 카드마다 구석에 "어느 책, 몇 쪽"을 적어 둡니다. 나중에 카드 한 장만 꺼내 봐도 원래 위치를 확인할 수 있어야 하기 때문입니다. 로더는 책을 쪽 단위로 펼치는 일, 스플리터는 카드에 옮겨 적는 일, metadata는 문서 ID와 쪽 번호 같은 출처 정보를 적은 카드 구석의 메모입니다.
정의
Document
LangChain이 텍스트 조각을 다루는 기본 단위입니다. 본문 page_content(문자열)와 부가 정보 metadata(딕셔너리) 두 칸으로 이루어집니다. 로더의 출력, 스플리터의 입력·출력, 벡터스토어의 저장 단위로 사용됩니다.
로더 (loader)
파일을 읽어 Document 목록으로 바꾸는 함수입니다. PDF는 쪽마다 하나, HTML은 파일당 하나처럼 "무엇을 한 단위로 볼지"를 로더가 정합니다.
스플리터 (text splitter)
Document를 정해진 크기의 청크로 나누는 도구입니다. metadata는 나뉜 청크마다 복사됩니다.
청크 크기 (chunk_size) · 겹침 (chunk_overlap)
청크 하나의 최대 길이와, 이웃 청크가 서로 공유하는 길이입니다. 이 절의 스플리터는 둘 다 글자 수로 셉니다.
구분자 (separators)
어디서 끊을지의 우선순위 목록입니다. ["\n\n", "\n", ". ", " ", ""]이면 문단 경계 → 줄 경계 → 문장 경계 → 단어 경계 → 글자 순으로 시도합니다. "재귀적(Recursive)"이라는 이름은 큰 구분자로 잘라도 크기를 넘으면 다음 구분자로 다시 자른다는 뜻입니다.
도식 — 청크 경계와 겹침
E01 2쪽이 청크 #0과 #1로 나뉩니다. 노란 띠가 겹침 50자입니다. 문장이 청크 경계에 걸리면 겹친 글자가 앞 청크의 끝과 뒤 청크의 앞에 모두 남습니다.
겹침이 왜 필요한지는 이 그림 하나로 충분합니다. 겹침이 0이면 "3일 늦게 반납하면 반납일부터 3일"에서 끊기고, "동안 새로 대출할 수 없습니다"는 다음 청크로 넘어갑니다. 검색이 앞 청크만 가져오면 모델은 "3일 뒤에 무엇이 되는지"를 모른 채 답해야 합니다. 겹침은 이러한 절단을 줄입니다. 다만 겹친 만큼 청크 수가 늘고 임베딩 비용이 늘어납니다.
기본 노트북의 Document
기본 노트북은 제공된 합성 PDF E01.pdf의 2쪽을 읽고 Document로 만듭니다. 본문과 doc_id·page·source가 한 객체에 함께 저장되는지 타입과 내용을 출력해 확인합니다.
기본 노트북의 스플리터
split_documents()는 Document 목록을 받아 Document 목록을 반환합니다. 입력 쪽의 metadata가 출력 청크마다 그대로 복사되므로, 청크 하나만 보고도 "E01의 2쪽"임을 압니다. 여기에 chunk_id를 덧붙여 두면 03절에서 검색 결과를 읽을 때 "#0이 검색되었다"처럼 지칭할 수 있습니다.
호출 표기와 반환값 읽기
reader.pages[1]에서 대괄호는 목록에서 한 항목을 고르는 표기이며, Python의 인덱스가 0부터 시작하므로 두 번째 쪽을 뜻합니다. extract_text()는 그 쪽 객체를 문자열로 바꾸어 반환합니다. 반환 문자열과 문서 ID·쪽 번호를 Document에 넣으면 검색 단계가 본문과 출처를 함께 전달할 수 있습니다.
split_documents([document])는 Document 목록을 입력받아 더 짧은 Document 목록을 반환하며, 이 호출만으로 임베딩이나 검색이 실행되지는 않습니다. split_text(text)가 문자열만 나누는 것과 비교하면, split_documents()는 기존 metadata를 청크에 복사한다는 차이가 있습니다. 계약서처럼 조항 번호가 중요한 문서에서는 쪽 번호 외에 조항 ID도 먼저 메타데이터에 넣어야 분할 뒤 추적할 수 있습니다.
5실행 예제
제공된 합성 PDF E01.pdf의 2쪽을 직접 읽습니다. Document 타입·출처 정보(metadata)·본문을 확인한 뒤 500/50으로 나누고, 겹침 50은 유지한 채 청크 크기만 300으로 바꿉니다. 끝으로 text-embedding-3-small에 대응하는 cl100k_base 토크나이저로 실제 첫 청크의 토큰 수를 출력합니다.
확인할 점 — 분할 결과도 Document 리스트이며 모든 청크에 doc_id=E01과 page=2가 남습니다. 청크 크기를 줄이면 반환 개수와 각 청크의 길이가 바뀌어야 합니다.
6일부러 실패해 보기
Before에서 겹침을 0으로 두어 “월요일”이 청크 경계에서 두 조각으로 갈라지는 결과를 확인합니다. After에서 다른 값은 유지하고 chunk_overlap만 5로 늘려, 겹친 청크 안에 “월요일” 전체가 남는지 검사합니다.
7주의할 점과 실무 메모
글자 수 vs 토큰 수. RecursiveCharacterTextSplitter는 글자를 셉니다. 노트북은 tiktoken.encoding_for_model("text-embedding-3-small")로 첫 청크의 토큰 수를 별도로 확인합니다. Ch 5에서 관찰한 GPT-2·KLUE 토크나이저와 이번 cl100k_base 토크나이저는 계산 단위가 다르므로 두 결과를 직접 비교하지 않습니다. 토큰 수를 분할 기준으로 쓰려면 RecursiveCharacterTextSplitter.from_tiktoken_encoder(...)나 TokenTextSplitter를 사용합니다(Ch 10).
전체 PDF 확장의 로더 선택. 기본 노트북은 pypdf를 직접 사용해 제공된 PDF 한 쪽을 읽습니다. 공식 문서 예제의 langchain-community PyPDFLoader는 유지보수 종료가 예고되어 2026-09-07 기준으로 import 경고가 발생했습니다. Ch 10에서는 Docling·Upstage 같은 독립 파서를 비교합니다.
표의 행과 열 관계가 사라질 수 있습니다. extract_text()는 PDF의 글자를 추출하지만, 어떤 값이 같은 행이나 열에 있었는지 항상 보존하지는 않습니다. 이 절은 E01의 일반 문단만 관찰합니다. 표가 든 문서는 Ch 10에서 여러 PDF 읽기 도구로 비교합니다.
HWP·HWPX. 한국 실무에는 HWP·HWPX 문서도 있으며 pypdf로는 열 수 없습니다. Ch 10의 별도 절입니다.
표지·머리글. 표지 한 쪽이 45자짜리 Document가 됩니다. 검색에서 제목 단어와 겹치면 높은 점수를 받아 자리를 차지합니다(03절). 실무에서는 표지·목차 쪽을 로더 단계에서 거르거나, 청크 최소 길이를 두는 처리를 흔히 합니다. 이 챕터에서는 일부러 두어 그 현상을 보게 합니다.

4핵심 개념
비유 — 지도 위의 핀
기본 노트북의 문서 세 건을 지도 위 핀 세 개라고 생각하세요. 비슷한 내용은 가까운 자리에 놓입니다. 질문이 들어오면 질문도 같은 지도에 핀 하나로 표시하고, 그 핀에서 가장 가까운 핀 k개를 고릅니다. 이것이 top-k 검색의 전부입니다. 지도의 좌표가 벡터이고, 지도가 벡터스토어이며, "가깝다"의 잣대가 코사인 유사도입니다.
정의
임베딩 (embedding)
텍스트를 고정 길이의 숫자 벡터로 바꾸는 것, 또는 그 벡터입니다. 이 절의 모델 text-embedding-3-small은 입력 한도 안의 텍스트를 소수를 포함할 수 있는 숫자 1,536개로 이루어진 벡터로 바꿉니다. dimensions를 지정하면 벡터 길이를 줄일 수 있습니다. 의미가 비슷한 텍스트는 비슷한 벡터가 됩니다.
코사인 유사도 (cosine similarity, 벡터 방향의 가까움을 나타내는 값)
두 벡터가 이루는 각도로 가까운 정도를 측정하는 값입니다. 1이면 같은 방향이고 0이면 두 벡터가 서로 90도를 이룹니다. 0이나 음수라는 값만으로 문장 의미가 무관하거나 반대라고 단정할 수는 없습니다. InMemoryVectorStore의 점수가 이것입니다.
벡터스토어 (vector store)
청크 텍스트·벡터·메타데이터를 함께 저장하고, 질문 벡터와 가까운 것을 찾아 주는 저장소입니다. 기본 노트북의 InMemoryVectorStore는 문서 세 건을 메모리에 둡니다. 문서가 많아졌을 때 사용하며 프로그램을 종료해도 데이터가 남는 저장소와 빠른 검색 구조는 Ch 12에서 다룹니다.
top-k
점수 상위 k개만 반환하는 것입니다. k는 학생이 정하는 값입니다. 이 절은 k=1과 k=2의 반환 개수를 비교하고, 04절은 k=1 Document를 프롬프트에 넣습니다.
질문 임베딩 (query embedding)
질문 문장을 청크와 같은 모델로 벡터화한 것입니다. 같은 모델이어야 같은 지도에 놓입니다. 청크는 A 모델, 질문은 B 모델로 임베딩하면 점수가 무의미해집니다.
저장 ID
add_documents()가 반환하는 각 벡터의 식별자입니다. 기본 노트북은 반환된 ID 리스트의 길이가 입력 Document 수와 같은지 확인합니다.
도식 — 질문 핀과 가까운 청크 핀
질문 벡터와 가까운 문서 벡터를 순서대로 고르는 개념도입니다. 기본 노트북에서는 문서 세 건을 저장하고 k=1과 k=2의 반환 Document·점수를 직접 비교합니다.
노트북에서 확인할 색인과 검색
세 줄이 핵심입니다. OpenAIEmbeddings가 텍스트를 벡터로 바꾸는 담당, InMemoryVectorStore가 벡터를 담는 담당, add_documents()가 청크 목록을 받아 하나씩 임베딩해 넣는 동작입니다. 기본 비교에서는 similarity_search_with_score()를 호출합니다. 이 메서드는 (Document, 점수) 튜플의 리스트를 반환하므로 문서 내용과 순서를 함께 관찰할 수 있습니다. 실패 수정 셀에서는 두 문서의 정보를 함께 묻는 질문에서 k만 1에서 2로 바꾸고 검색된 Document ID를 비교합니다.
직접 호출하는 이유이 절에서는 벡터스토어 메서드를 셀에서 직접 호출합니다. hits_k1과 hits_k2를 바로 출력하면 k 변경 전후의 Document·점수·개수를 한 단계씩 확인할 수 있습니다.
벡터스토어 호출을 단계별로 읽기
OpenAIEmbeddings(model=...)는 임베딩 설정을 가진 객체를 만들 뿐, 이 줄에서 문서 벡터를 요청하지는 않습니다. 실제 호출은 add_documents(documents)가 문서 목록을 받아 각 본문을 임베딩할 때 일어납니다. 반환된 벡터 ID 목록은 저장 성공을 확인하는 값이고, store에는 원문 Document와 검색용 벡터가 연결되어 있습니다.
similarity_search_with_score(question, k=2)는 질문을 같은 모델로 임베딩하고 가까운 문서 두 건을 (Document, 거리) 쌍으로 반환합니다. 거리는 관련성 확률이 아니므로 0.2를 “20% 관련”으로 읽으면 안 됩니다. 제품 코드명처럼 정확한 철자가 핵심인 질문은 의미 벡터만으로 부족할 수 있으며 Ch 12의 키워드 검색과 비교합니다.
5실행 예제
문서 ID와 본문을 튜플에서 하나씩 꺼내 Document로 만듭니다. 실제 임베딩 후 반환된 벡터 ID 수, store 타입, k=1의 Document·점수·본문을 확인하고 k만 2로 바꿉니다.
확인할 점 — add_documents()는 저장된 벡터 ID 리스트를 반환합니다. similarity_search_with_score()는 Document와 점수의 튜플 리스트를 반환하며, k를 1에서 2로 늘리면 결과 개수가 늘어납니다.
6일부러 실패해 보기
Before에서 도서관 휴관일과 회사 급여일을 함께 묻지만 k=1로는 근거 문서 두 건을 모두 가져오지 못하는 결과를 확인합니다. After에서 질문과 문서는 유지하고 k만 2로 늘려 D01과 D03이 함께 검색되는지 검사합니다.
7주의할 점과 실무 메모
점수에 절대 기준은 없습니다. 0.65가 좋고 0.35가 나쁘다고 말할 수 없습니다. 모델·언어·질문 길이에 따라 점수가 퍼지는 범위와 모양이 다릅니다. "이 점수보다 낮으면 버린다"고 정하는 기준값은 Ch 11의 테스트 질문 모음으로 측정한 뒤 정합니다. Ch 14에서는 점수가 기준보다 낮을 때 다른 검색 방법을 시도합니다. 이런 대체 동작을 폴백이라고 부릅니다.
한국어 임베딩 품질. 영어 벤치마크 상위 모델이 한국어 조사·어미 변화에도 같은 성능을 낸다고 단정할 수 없습니다. 이 챕터의 모델은 [[미정: 임베딩 모델]]이 확정될 때까지의 임시값입니다. Ch 10에서 다른 임베딩 모델과 결과를 비교합니다.
짧은 문서도 검색 후보입니다. 기본 노트북의 세 문서는 길이가 비슷하지만 실제 PDF에는 표지와 목차처럼 짧은 문서도 있습니다. 실무에서는 로더 단계에서 제외하거나 최소 청크 길이를 정한 뒤 결과를 비교합니다.
InMemoryVectorStore의 한계. 기본 노트북처럼 문서 세 건을 관찰하기에는 충분하지만, 프로세스가 종료되면 메모리의 값도 사라집니다. 문서가 많아졌을 때 사용할, 프로그램을 종료해도 데이터가 남는 저장소와 빠른 검색 구조는 Ch 12에서 다룹니다.
비용과 재임베딩. 청크 크기나 임베딩 모델을 바꾸면 문서 벡터를 다시 만들어야 합니다. 기본 노트북은 짧은 문서 세 건만 실제 임베딩합니다. Ch 10에서 설정 변경과 재임베딩의 관계를 더 살펴봅니다.

k만 2로 바꾸어 추가 후보가 반환되는 것을 확인했습니다.

9복습 문제
문제 4개 · 해설 포함
1. add_documents()가 입력받고 반환하는 것은 무엇입니까?
Document 리스트를 입력받아 임베딩해 저장하고, 저장된 벡터 ID 리스트를 반환합니다.
2. similarity_search_with_score()의 결과 하나는 어떤 형태입니까?
Document와 점수를 묶은 튜플입니다. 반복문에서 for document, score in ...로 두 값을 나눌 수 있습니다.
3. k=1에서 k=2로 바꾸면 무엇이 달라지고 무엇이 그대로입니까?
반환할 상위 문서 개수만 달라지고 질문, Document, 임베딩 모델, store는 그대로입니다.
4. 두 문서의 정보가 필요한 질문에서 k=1이 부족한 이유는 무엇입니까?
검색 결과를 한 건만 반환하므로 D01과 D03 가운데 하나가 빠집니다. 이 실습에서는 k를 2로 늘려 두 근거를 함께 검색했습니다.

4핵심 개념
비유 — 답안지 규칙
오픈북 시험에서 감독관이 규칙을 정합니다. "책상 위 자료만 보고 답하라. 답의 근거가 된 쪽 번호를 답 옆에 적어라." 규칙이 없으면 학생은 기억으로 답하거나 근거 없이 씁니다. 이 규칙과 검색 문맥, 질문을 합친 단일 프롬프트 문자열을 모델에 전달합니다. [D01 p.1]은 문맥 앞과 답에 사용하는 출처 태그입니다.
정의
문맥 조립 (context assembly)
검색된 Document의 본문과 출처 태그를 모델이 읽을 문자열로 조립하는 것입니다. 기본 노트북은 k=1 Document의 page_content 앞에 [D01 p.1] 태그를 붙여 context를 만듭니다.
프롬프트 (prompt)
모델에 전달하는 입력 문자열입니다. 이 절에서는 “다음 문서만 근거로 답하라”와 “출처를 [doc_id p.페이지]로 붙여라”는 지시, 검색 문맥, 질문을 하나의 삼중따옴표 문자열에 넣습니다.
출처 인용 (citation)
답의 근거가 된 청크의 doc_id·page를 답에 표기하는 것입니다. 모델이 표기한 출처는 검색된 k개 중 하나여야 합니다. 그렇지 않으면 지어낸 출처입니다.
AIMessage
model.invoke(prompt)가 반환하는 LangChain 메시지 객체입니다. 기본 노트북은 객체 타입을 출력하고 .text 속성에서 답 문자열을 읽습니다.
기본 노트북의 조립과 생성
첫째, 검색한 문서의 doc_id와 page로 출처 태그를 만듭니다. 둘째, 태그와 본문을 질문 앞에 놓습니다. 셋째, 모델에 전달한 뒤 답과 출처가 함께 있는지 검사합니다. 기본 노트북은 이 과정을 doc_id·page·source_tag·context 변수로 직접 보여 줍니다.
모델 선택gpt-5.4-mini를 사용하고 temperature=0을 명시합니다. 출력 표현은 실행 시점에 따라 다를 수 있으므로 문장 전체가 같은지보다 휴관일 내용과 [D01 p.1] 태그가 포함되었는지 확인합니다.
검색 결과가 답과 출처가 되는 과정
검색기는 Document를 반환하지만 모델은 그 객체를 자동으로 알지 못합니다. 코드가 각 문서의 page_content와 metadata를 사람이 읽을 수 있는 문맥 문자열로 조합한 뒤 프롬프트에 넣습니다. model.invoke(prompt)를 호출하는 순간에만 생성 요청이 실행되고, 반환된 AIMessage.text가 답 문자열입니다.
출처를 프롬프트에 적는 것, 모델이 답에 출처를 표시하는 것, 표시한 출처가 실제 근거를 포함하는지는 서로 다른 검사입니다. 이 절은 표시된 ID가 검색 결과에 있었는지 확인합니다. 문장 단위 근거가 필요하면 답의 각 주장과 원문 구절을 별도로 대조해야 하며, 단순한 ID 포함 검사만으로 내용의 정확성을 보장할 수 없습니다.
5실행 예제
Document 두 건을 숫자 벡터로 바꿔 검색할 수 있게 저장하고 k=1의 반환 Document를 출력합니다. 문서 ID와 쪽 번호(metadata)로 출처 태그를 만들고 본문과 함께 삼중따옴표 프롬프트에 넣은 뒤 AIMessage를 받습니다. 마지막에 k만 2로 바꿔 문맥 후보 수를 비교합니다.
확인할 점 — Document 타입·출처 정보(metadata)·본문, source_tag, context, 모델에 전달한 전체 프롬프트, AIMessage 타입·본문을 순서대로 확인합니다.
6일부러 실패해 보기
Before에서 실제 검색 결과를 새 Document로 옮기면서 page를 빠뜨려 KeyError가 나는지 확인합니다. After에서는 쪽 번호를 지어내지 않고 원래 검색 결과의 page를 함께 옮겨 같은 출처 태그를 복구합니다. 복구한 태그와 본문으로 같은 질문을 실제 호출해 답의 출처까지 확인합니다.
7주의할 점과 실무 메모
검색 후보와 답의 출처 태그는 다릅니다. hits는 검색이 반환한 Document 리스트이고, 답에 붙은 [D01 p.1]는 모델이 생성한 문자열입니다. 기본 노트북은 k=1 Document의 metadata로 만든 source_tag가 실제 답에 포함되는지 검사합니다.
metadata가 먼저 필요합니다. doc_id나 page가 없으면 출처 태그를 만들 수 없습니다. Before는 실제 검색 결과에서 page를 빠뜨렸을 때 발생한 KeyError를 확인하고, After는 원래 검색 결과의 page를 복사해 태그를 완성합니다.
비용. 기본 노트북은 짧은 Document 두 건을 임베딩하고 k=1 문맥으로 생성 모델을 한 번 호출합니다. k=2 셀은 후보 수와 본문 길이만 비교하며 생성 모델을 다시 호출하지 않습니다. 모델 요금은 바뀔 수 있으므로 실행 시점의 공식 요금표를 확인합니다.
출력 언어. 기본 프롬프트에는 별도의 언어 지시를 넣지 않았고 문서와 질문을 한국어로 작성했습니다. 여러 언어의 문서를 함께 사용할 때는 원하는 출력 언어를 프롬프트에 명시하고 실제 응답을 확인합니다.
응답에서 텍스트 읽기. model.invoke()는 AIMessage를 반환합니다. 기본 노트북은 answer.text로 텍스트를 읽습니다. content는 문자열이나 콘텐츠 블록 목록일 수 있으므로 멀티모달 응답을 다루는 Ch 26에서 별도로 확인합니다.
8정리와 다음 절
검색 Document의 문서 ID와 쪽 번호(metadata)가 출처 태그가 되었고, 본문(page_content)은 모델이 참고할 문맥이 되었습니다.
삼중따옴표 프롬프트에 문맥과 질문을 넣고 AIMessage의 .text로 답을 읽었습니다.
k만 1에서 2로 바꾸어 모델에 전달할 후보 문서 수가 늘어나는 것을 확인했습니다.
다음 학습과 이어지는 지점 — 05절에서 생성 답만 읽지 않고 검색한 Document ID를 함께 보며 실패 원인을 구분합니다.

1학습 목표
이 절을 마치면 k=1의 Document ID·본문·생성 답을 순서대로 확인해 검색 누락을 진단할 수 있습니다.
이 절을 마치면 다른 값은 유지하고 k만 1에서 2로 바꾸어 정답 Document가 문맥에 포함되는지 비교할 수 있습니다.
이 절을 마치면 문서 집합에 답이 없는 경우와 검색이 정답 문서를 놓친 경우를 검색 ID로 구분할 수 있습니다.
2이 내용을 배우는 이유
RAG가 답을 생성해도 그 답만으로 실패 원인을 알 수는 없습니다. 모델이 “찾을 수 없습니다”라고 답했을 때, 문서 집합에 답이 없는 경우와 정답 문서가 검색 결과에서 빠진 경우를 구분해야 합니다.
이번 기본 실습은 처음부터 근거에 없는 내용은 답하지 말라는 지시를 유지합니다. 검색 결과의 개수만 바꾼 뒤 문서 ID와 본문, 생성 답을 차례로 확인합니다. 환각을 반드시 발생시키는 실험은 수행하지 않습니다. 근거 없는 생성은 가능한 실패 유형으로 설명하고, 실제로 관찰한 검색 누락과 거부 응답을 구분해 기록합니다.

4핵심 개념
비유 — 자료 없이 답하는 안내원
고객이 안내 창구에서 "A/S 접수하면 답변이 얼마나 걸리나요?"라고 묻습니다. 안내원은 뒤에서 건네받은 종이 두 장을 봅니다. 한 장은 FAQ 책자의 표지이고, 다른 한 장은 다른 회사의 신입사원 안내문입니다. 어느 장에도 답변 소요 시간은 없습니다. 이때 안내원이 할 수 있는 일은 두 가지입니다. "자료에 없습니다"라고 말하거나, 경험상 그럴듯한 "보통 하루 안에 옵니다"라고 답하는 것입니다. 후자가 환각입니다. 구체적인 답을 요구하는 지시가 있어도 안내원이 어느 쪽을 선택하는지는 실제 답을 읽고 확인해야 합니다.
{{img:05-지어낸-숫자|시계 질문을 받은 안내원이 시계가 없는 두 문서만 들고도 시계가 든 답을 내놓고, 그 위에 빨간 경고 표시가 떠 있습니다.}}
고객이 시계(기한)를 묻고, 안내원은 답이 없는 문서만 들고도 기한을 만들어 낼 수 있습니다. 기본 노트북은 검색 문맥에 답이 없을 때 실제 응답이 어떻게 나타나는지 확인합니다.보는 순서 — ① 왼쪽 고객의 시계 말풍선 → ② 가운데 안내원이 든 두 장(시계가 없다) → ③ 오른쪽 답 말풍선의 시계와 빨간 경고.
정의
환각 (hallucination)
근거 없이 만들어진, 그러나 형식은 그럴듯한 출력입니다. RAG에서는 "검색된 문서에 없는 내용을 문서에 있는 것처럼 답하는 것"으로 좁혀서 씁니다. 숫자·날짜·고유명사처럼 확인 가능한 내용을 문서와 대조해 판정할 수 있습니다.
답변 거부 (refusal)
모델이 답 대신 "문서에서 찾을 수 없습니다"처럼 답할 수 없음을 말하는 것입니다. 답이 문서에 없을 때는 정답이고, 있을 때는 오답입니다.
답을 찾을 수 없는 질문 (unanswerable query)
문서 세트 어디에도 답이 없는 질문입니다. 이런 질문의 정답은 “근거가 없어 답할 수 없다”이며, 답이 있는 질문의 검색 누락과 구분해야 합니다.
실행할 때마다 나타날 수도 있고 나타나지 않을 수도 있는 실패 (stochastic failure)
같은 입력으로도 어떤 실행에서는 일어나고 다른 실행에서는 일어나지 않는 실패입니다. 한 번 실행해서 나타나지 않았다고 실패가 없다고 판단할 수는 없습니다. 기본 노트북은 검색 ID와 실제 응답을 함께 기록해 원인을 구분합니다.
도식 — 같은 출력, 다른 원인
검색 결과에 정답 청크가 있는가, 없는가(검색 실패), 문서에 애초에 없는가에 따라 세 경로로 갈립니다. 가운데와 아래 경로의 출력이 같은 문자열이라는 것이 이 절의 핵심입니다.
위 경로는 근거가 검색된 경우이고, 가운데 경로는 정답 문서가 검색에서 빠진 경우입니다. 정답이 문서에 있는데 검색이 못 가져왔고, 모델은 규칙에 따라 "찾을 수 없습니다"라고 답하거나 규칙을 어기고 숫자를 지어냅니다(환각). 아래 경로는 정답이 문서에 없는 경우이고, "찾을 수 없습니다"가 정답입니다. 가운데와 아래의 출력은 같은 거부 문장으로 나타날 수 있습니다. 출력만 보아서는 검색을 고쳐야 하는지, 아무 문제가 없는지 알 수 없습니다. 구분하려면 "이 질문의 정답이 어느 문서에 있는가"를 미리 적어 둔 표가 필요합니다. Ch 11에서는 질문과 정답 문서 ID를 모은 테스트 질문 모음을 만들어 두 원인을 측정으로 구분합니다.
엄격한 프롬프트와 검색 중간값
기본 노트북은 문서에 답이 없으면 “찾을 수 없습니다”라고 답하도록 지시합니다. 먼저 k=1 검색이 DISTRACTOR를 골랐음을 ID와 본문으로 확인한 뒤 모델 응답을 봅니다. 다음에는 질문·프롬프트·문서를 유지하고 k만 2로 바꿉니다. ANSWER가 문맥에 추가되었을 때 같은 모델이 실제 연체 규정을 답하는지 확인합니다.
마지막 셀은 문서 집합 자체에 A/S 처리 기간이 없는 질문을 별도로 실행합니다. 이 경우에는 k를 늘려도 근거가 생기지 않습니다. 검색 ID를 먼저 확인해야 “정답 문서가 검색에서 빠진 경우”와 “전체 문서에 답이 없는 경우”를 구분할 수 있습니다.
실패를 검색과 생성으로 나누어 읽기
검색 실패는 정답 근거가 후보에 들어오지 않은 상태이고, 생성 실패는 근거가 후보에 있는데도 답이 잘못된 상태입니다. similarity_search_with_score()가 반환한 문서 ID를 먼저 읽으면 두 실패를 구분할 수 있습니다. 이 절의 Before에서는 k=1 때문에 단어가 비슷한 DISTRACTOR만 선택되고, 모델은 정답 규정을 전달받지 못합니다.
After의 k=2는 검색 범위를 넓혀 ANSWER를 포함시킵니다. 이것은 언제나 k를 늘리라는 결론이 아니라 후보 누락이 원인일 때 바꿀 수 있는 한 조건입니다. 정답 문서가 검색되었는데 답이 틀리면 청킹·검색보다 프롬프트와 생성 결과를 조사해야 합니다.
5실행 예제
질문 단어는 많지만 답이 없는 DISTRACTOR와 실제 연체 규정이 있는 ANSWER를 색인합니다. k=1의 ID·본문·엄격한 답을 확인한 뒤 k만 2로 바꾸어 검색 문맥과 생성 답을 비교합니다. 마지막에는 문서 집합 자체에 답이 없는 질문을 별도로 실행합니다.
확인할 점 — k=1의 검색 ID에 ANSWER가 없으면 생성 모델은 연체 규정을 받지 못합니다. k=2에서 ANSWER가 포함되면 같은 엄격한 지시가 문서의 대출 정지 규정을 답합니다. 문서 집합에 A/S 기간이 없는 예제는 k와 관계없이 근거를 제공할 수 없습니다.
6일부러 실패해 보기
Before에서 앞에서 실행한 k=1의 DISTRACTOR ID와 거부 답을 나란히 다시 보여 줍니다. After에서는 앞에서 k를 2로 바꿔 실행한 ANSWER ID와 대출 정지 답을 다시 보여 주고 검사합니다. Before/After 셀에서 모델을 추가로 호출하지는 않습니다.
7주의할 점과 실무 메모
"찾을 수 없습니다" 비율만 보면 안 됩니다. 거부율이 낮다고 좋은 것도, 높다고 안전한 것도 아닙니다. 전체 문서에 답이 없는 질문에서 “찾을 수 없습니다”라고 답한 비율(높아야 함)과 문서에 답이 있는 질문에서 “찾을 수 없습니다”라고 잘못 답한 비율(낮아야 함)을 나눠서 봐야 하고, 나누려면 정답 문서 ID가 필요합니다. Ch 11 테스트 질문 표의 answerable 칸에는 문서에서 답을 찾을 수 있는 질문인지 표시합니다.
관찰한 실패만 기록합니다. 이 노트북은 엄격한 지시를 유지한 채 검색 문맥을 바꿉니다. 환각을 관찰하지 않았는데 발생했다고 적거나, 한 번의 거부를 모든 입력에서의 안전성으로 일반화하지 않습니다.
출처와 내용도 대조합니다. 출처 태그가 있어도 실제 해당 문서가 답을 뒷받침하는지 확인해야 합니다. 예를 들어 같은 규정의 예전 문서와 새 문서가 함께 있으면, 출처 문장은 실제로 있어도 질문이 요구한 시행일과 맞지 않을 수 있습니다.
프롬프트 규칙의 한계 세 가지. ① 검색 실패를 고치지 못한다(재료 문제) ② 같은 지시도 실행에 따라 준수 여부가 달라질 수 있다 ③ 검색 문서 안의 지시문을 모델이 사용자 지시로 잘못 받아들일 수 있다(프롬프트 인젝션). 각각 Ch 12, Ch 11·15, Ch 16의 주제입니다.
한국어 문서의 부칙·단서. 규정 문서는 본문 뒤의 부칙에 "종전 규정에 따른다" 같은 결정적 한 줄이 있습니다. 청크로 나누면 본문과 부칙이 떨어지고, 검색이 "연차"라는 단어가 많은 본문만 선택할 수 있습니다. Ch 12 Parent-document 검색이 이 문제를 완화합니다.
8정리와 다음 절
생성 답을 읽기 전에 검색 ID와 본문을 보면 정답 문서 누락을 직접 확인할 수 있습니다.
k만 1에서 2로 바꾸어 ANSWER가 문맥에 포함되자 같은 엄격한 지시가 연체 규정을 답했습니다.
문서 집합에 답이 없는 경우와 top-k가 정답 문서를 놓친 경우는 거부 답만으로 구분할 수 없습니다.
다음 학습과 이어지는 지점 — 06절은 바꾼 설정과 검색 ID를 JSONL 한 행에 남겨 비교 근거를 보존합니다.
9복습 문제
문제 4개 · 해설 포함
1. k=1 결과에서 생성 전에 확인한 두 중간값은 무엇입니까?
검색된 Document의 doc_id와 page_content입니다. 이 두 값으로 정답 문서가 누락되었는지 알 수 있습니다.
2. k=1에서 k=2로 바꾸었을 때 새로 포함된 문서는 무엇입니까?
연체 일수만큼 대출이 정지된다는 규정을 담은 ANSWER 문서입니다.
3. 문서 집합에 A/S 처리 기간이 없는 경우 k를 늘려도 답할 수 없는 이유는 무엇입니까?
검색 개수를 늘려도 문서 집합에 없는 정보가 새로 생기지 않으므로 근거를 제공할 수 없습니다.
4. 거부 답이 같을 때 두 실패 원인을 구분하는 값은 무엇입니까?
검색한 Document ID입니다. 정답 ID가 전체 문서 집합에는 있지만 top-k에 없다면 검색 누락입니다.

정의
실험 하네스 (experiment harness)
설정을 바꾸고 검색과 생성을 실행한 뒤 결과를 같은 형식으로 기록하게 만든 반복 실험 틀입니다. 기본 노트북은 YAML 읽기, 조건 변경, 설정 식별 문자열 만들기, 검색, 생성, JSONL 한 행 기록을 차례대로 보여 줍니다.
YAML 설정 (YAML configuration)
들여쓰기로 계층을 나타내는 설정 파일입니다. 이 절에서는 분할·임베딩·검색·생성 설정과 질문을 한 파일에 둡니다. yaml.safe_load()로 읽은 뒤 환경 변수의 검색 개수만 실행 설정에 반영합니다.
실행 기록 (run record)
한 설정에서 실행한 결과를 담은 기록입니다. 이 절은 이름이 k2인 설정, 검색 문서 ID, 모델 답을 딕셔너리 한 개로 저장합니다.
설정 해시 (config hash) · 캐시 (cache)
설정 해시는 색인 설정마다 붙이는 짧은 식별 문자열입니다. 캐시는 이미 만든 결과를 잠시 보관하는 공간입니다. 캐시는 설정 해시를 이름표처럼 사용해 기존 벡터스토어 객체를 찾습니다. 이번 예제는 같은 문서를 사용하며 split과 embedding 설정을 해시 입력으로 삼습니다.
JSON Lines (JSONL)
한 줄에 JSON 객체 하나를 두는 파일 형식입니다. 줄을 덧붙일 수 있고, 각 줄을 독립적으로 읽을 수 있습니다. 잘못된 줄의 처리는 별도 오류 대응이 필요합니다. 기본 노트북은 실행 ID별 파일을 runs/continuity/에 보존하고, Ch 11이 읽을 최신 결과를 runs/continuity-ch09-search.jsonl에 기록합니다.
도식 — 루프
설정을 바꾸고 실행한 뒤 결과를 한 줄로 기록합니다. 기록을 읽어 다음 설정을 정합니다. 점선 metrics 칸은 Ch 11이 별도 평가 결과에 계산할 품질 점수입니다.
기본 실습의 실행 범위
임시 폴더에 YAML 설정을 만들고 다시 읽습니다. 검색 개수는 기본값 1에서 환경 변수의 값 2로 바꿉니다. 제공된 18개 디지털 PDF를 실제로 읽고 쪽별 Document를 청크로 나눈 뒤 Ch 11의 Q001과 같은 질문으로 검색합니다. 검색 본문과 문서 ID·쪽을 채팅 모델에 전달해 답을 생성합니다. 설정·검색·생성이 모두 끝나야 기록 한 행을 만듭니다.
설정 하나를 바꾸고 식별 문자열 만들기
기본 노트북은 yaml.safe_load()로 설정을 읽고 deepcopy()로 복사한 뒤 retrieval.k만 1에서 2로 바꿉니다. 이어서 색인에 영향을 주는 split과 embedding만 별도 딕셔너리에 담습니다.
json.dumps(..., sort_keys=True)는 키 순서를 고정한 JSON 문자열을 만들고, SHA-256은 이 문자열을 고정 길이의 해시로 바꿉니다. 해시는 설정에 붙이는 지문과 같습니다. 내용이 같으면 같은 해시가 나오고, 내용 하나가 바뀌면 다른 해시가 나옵니다. 노트북은 전체 해시를 출력하고 앞의 10자만 학습용 키로 사용합니다. 색인 설정을 구분하는 해시를 만들 때 retrieval.k는 뺍니다. k는 이미 만든 색인에서 문서를 몇 건 가져올지만 바꾸기 때문입니다. 따라서 k만 바꾼 설정은 같은 해시를 사용하고 기존 색인을 다시 씁니다.
기록 한 행
한 행에는 qid, question, gold_doc_ids, 전체 config, 순위가 있는 retrieved, answer가 들어갑니다. 검색 결과에는 doc_id·chunk_id·page·rank·score를 남깁니다. Ch 11은 이 중 질문과 정답 문서 ID, 검색 결과만 사용해 검색 지표를 계산하며 answer는 평가하지 않습니다.
설정·실행·기록의 역할 구분
실험 하네스는 설정을 읽고, 같은 절차를 실행하고, 결과를 같은 형식으로 저장하는 코드입니다. YAML의 split.chunk_size 같은 값은 실험 입력이며, run_experiment(config)를 호출할 때 실제 청킹·임베딩·검색·생성이 실행됩니다. 반환 사전에는 설정과 관찰값이 함께 들어가므로 다음 실행과 항목별로 비교할 수 있습니다.
한 번에 조건 하나만 바꾸면 결과 차이를 그 조건과 연결해 해석할 수 있습니다. 모델과 청크 크기를 동시에 바꾸면 어느 변경이 원인이었는지 알 수 없습니다. JSONL은 실행 한 건을 한 줄에 추가하므로 이전 결과를 지우지 않고 실험 이력을 남기며, 로그 저장 성공이 검색 품질을 뜻하지는 않습니다.
5실행 예제
YAML 파일 작성·읽기, k 하나 변경, 설정 해시, 제공 PDF 18개의 실제 임베딩 색인과 Q001 검색, 검색 근거를 사용한 답변 생성, 실행별 JSONL과 Ch 11 입력 포인터 저장을 서로 다른 셀에서 실행합니다. 마지막 셀은 배포 ZIP에도 들어 있는 Jupyter nbconvert로 노트북 전체를 새 커널에서 실행하는 명령을 출력합니다.
확인할 점 — YAML의 기본 k는 1이고 이번 실행 설정의 k는 2입니다. 18개 PDF의 93쪽을 176개 청크로 나눴고, Q001 검색의 상위 두 결과는 모두 E01입니다. 생성 답은 “미르시립도서관의 정기 휴관일은 매주 월요일입니다. [E01 p.2]”처럼 문서 ID와 쪽을 함께 표시합니다. JSONL을 다시 읽은 딕셔너리에는 이 설정·검색 결과·답이 함께 남습니다.
6일부러 실패해 보기

3. 관련 문서 한 건 검색
k=1로 가장 가까운 Document 한 건을 가져옵니다. 문서 ID와 쪽 번호를 담은 출처 정보(metadata), 본문을 따로 출력합니다.
4. 출처 태그와 문맥 만들기
검색한 Document의 문서 ID와 쪽 번호로 [D01 p.1] 모양의 출처 태그를 만들고 본문 앞에 붙입니다.
5. 삼중따옴표로 프롬프트 조립
여러 줄 문자열에 문맥과 질문을 삽입하고 모델에 전달되는 전체 프롬프트를 먼저 출력합니다.
6. 생성 모델 호출
init_chat_model로 모델을 만들고 invoke()로 프롬프트를 전달합니다.
7. k만 2로 바꾸어 문맥 비교
질문과 모델은 유지하고 검색 개수만 늘려 프롬프트에 들어갈 후보가 어떻게 늘어나는지 확인합니다.
정리
Document의 문서 ID와 쪽 번호로 출처 태그를 만들었습니다. 태그와 본문을 프롬프트에 넣었고, invoke()가 반환한 AIMessage에서 답과 출처를 읽었습니다.
원인 — 검색 결과를 새 Document로 옮기면서 page를 빠뜨리면 쪽 번호가 있는 출처 태그를 만들 수 없습니다.
수정 — 같은 검색 결과에서 실제 page 값도 함께 옮깁니다. 복구한 출처 태그와 본문으로 같은 질문의 프롬프트를 만들고 실제 답까지 확인합니다.

실습 안내
두 경우를 구분합니다. 첫째, 전체 문서에 답이 없습니다. 둘째, 정답 문서는 있지만 검색 결과에서 빠졌습니다. 모델의 답만 보지 않고 검색된 문서 ID도 함께 확인합니다.
실패를 검색과 생성으로 나누어 읽기
검색 실패는 정답 근거가 후보에 없는 상태이고, 생성 실패는 근거가 후보에 있는데도 답이 잘못된 상태입니다. Before의 k=1은 DISTRACTOR만 선택하므로 모델은 정답 규정을 받지 못합니다.
After의 k=2는 후보 누락 원인을 확인하기 위한 한 조건입니다. 정답 문서가 이미 검색되었다면 k보다 프롬프트와 생성 결과를 조사합니다.
1. API 키 준비
.env를 로드하고 외부 API를 사용할 수 있는지 확인합니다.
2. 검색 실패를 보이는 문서 준비
첫 문서 DISTRACTOR는 질문과 같은 단어가 많지만 답은 없습니다. 두 번째 문서 ANSWER에는 실제 연체 규정이 있습니다.
3. k=1 검색 중간값 관찰
생성 모델을 호출하기 전에 어느 문서가 선택되었는지 확인합니다.
4. k=1 문맥으로 엄격한 답 생성
검색 문서에 답이 없으면 “찾을 수 없습니다”라고만 답하도록 모델에 지시합니다.
5. k만 2로 바꾸어 검색 비교
다른 값은 그대로 두고 k만 늘려 정답 문서가 포함되는지 확인합니다.
6. 수정된 문맥으로 다시 답하기
같은 엄격한 지시와 질문을 유지하고 문맥만 context_k2로 바꿉니다.
7. 문서 집합에 답이 없는 경우 비교
RAG 문서 자체에 정보가 없으면 k를 늘려도 답을 만들 근거가 생기지 않습니다.
정리
모델이 동일하게 “찾을 수 없습니다”라고 답해도 원인은 다를 수 있습니다. 검색된 문서 ID를 보면 정답 문서가 검색에서 빠졌는지, 전체 문서에 답이 없는지 구분할 수 있습니다.
원인 — k=1이 DISTRACTOR만 가져와 정답 규정이 프롬프트에 들어가지 않았습니다.
수정 — 앞에서 k를 2로 바꾸어 실행한 검색 ID와 생성된 답변을 다시 나란히 보여 줍니다. ANSWER가 포함되고 대출 정지 규정이 답에 있는지 검사하며, 이 셀에서는 모델을 추가로 호출하지 않습니다.
