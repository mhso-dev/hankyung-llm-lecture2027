1학습 목표

  • Subagent 도구 위임의 핵심 구성 요소를 실제 출력에서 구분할 수 있습니다.
  • 같은 입력을 실행하고 호출 경계와 관찰 지표를 설명할 수 있습니다.
  • 결과가 보여 주는 범위와 추가 측정이 필요한 범위를 나눌 수 있습니다.

2이 내용을 배우는 이유

도구가 많아질수록 한 에이전트의 프롬프트와 대화 기록은 길어집니다. Subagent 패턴은 전문 작업을 별도의 문맥에서 수행하고 중앙 에이전트에는 필요한 결과만 반환합니다. 이번 절에서는 전문 에이전트를 도구 함수로 감싸고 호출 경계를 직접 기록합니다.

3앞에서 배운 내용

Ch20에서 ToolNode와 명시적 END 조건을, Ch23에서 thread_id와 체크포인터를 배웠습니다. Ch25에서는 실행 사건을 스트리밍했습니다. 이번 챕터에서는 여러 에이전트 사이의 제어권과 맥락을 어디에 둘지 결정합니다.

4핵심 개념

구체적인 상황

환불 전문가는 내부 기록 전체가 아니라 환불 판단에 필요한 고객 질문만 받아도 됩니다. 중앙 상담자는 전문 결과를 받아 고객 문장으로 다시 작성합니다. 이 경계가 문맥 격리의 최소 단위입니다.

정의

서브에이전트(Subagent)는 중앙 에이전트가 도구처럼 호출하는 전문 에이전트입니다. 중앙 에이전트가 사용자 대화의 문맥을 소유하고, 전문 에이전트는 호출마다 필요한 질문을 받아 결과를 반환합니다. 공식 문서는 이를 중앙 집중 제어와 문맥 격리로 설명합니다. 단일 에이전트의 도구 몇 개로 충분하면 위임 계층을 추가할 이유가 없습니다.

코드 읽기와 비교 경계

@tool은 Python 함수를 모델이 선택할 수 있는 도구 객체로 바꿉니다. 함수 이름과 docstring은 모델이 도구를 고를 때 읽는 설명이 되고, question: str은 입력 스키마가 됩니다. 중앙 supervisor.invoke(...)가 실행되면 모델이 먼저 policy_specialist 호출을 요청하고, LangChain이 함수를 실행한 뒤 반환 문자열을 ToolMessage로 대화에 넣습니다. 전문 에이전트의 invoke는 그 함수 안에서 별도의 모델 실행을 시작하므로 한 번의 위임에는 중앙 판단, 전문 처리, 중앙 종합이라는 호출 경계가 생길 수 있습니다.

서브에이전트와 일반 도구의 경계는 반환값을 누가 만드는지에 있습니다. 세율 조회처럼 입력과 출력이 결정적인 작업은 함수 도구가 더 분명합니다. 여러 자료를 읽고 판단 근거를 요약해야 하는 작업은 전문 프롬프트와 별도 문맥을 가진 서브에이전트가 도움이 됩니다. 이 예제의 문자 수 비교는 전달 범위를 줄였다는 사실만 보여 줍니다. 전문 에이전트가 더 정확해졌는지, 전체 토큰이 줄었는지, 고객 답변이 좋아졌는지는 별도의 질문 묶음과 평가 기준으로 측정해야 합니다.

5실행 예제

policy_specialist를 @tool로 정의하고 내부에서 모델을 호출합니다. supervisor는 이 도구를 선택하고 반환값을 다음 모델 호출의 근거로 사용합니다. calls와 메시지의 tool_calls에는 policy_specialist가 남으며, 전체 639자와 전문 에이전트에 전달한 질문 38자를 비교합니다.

설치 셀은 Python 3.12 환경에 LangChain 1.4.0, langchain-openai 1.6.0, LangGraph 1.2.11을 고정합니다. 예상 API 비용은 1달러 미만이며 키 값은 출력하지 않습니다.

6실험 결과 해석

create_agent supervisor의 실제 메시지 기록에는 policy_specialist 도구 호출이 한 번 있었고 도구 함수 실행 기록도 같은 이름을 남겼습니다. 전체 문맥은 639자였지만 전문 에이전트에는 질문 38자만 전달했습니다. 문자 수 비교는 문맥 격리의 크기만 보여 주며 토큰 절감이나 품질 향상을 직접 증명하지는 않습니다.

이 실험은 한 질문과 한 실행 환경의 결과입니다. 모델 응답 내용과 지연 시간은 실행할 때마다 달라질 수 있습니다. 구조의 품질을 비교하려면 여러 질문, 반복 실행, 오류율, 사용자 수정 횟수를 추가로 측정해야 합니다.

7주의할 점과 실무 메모

  • 전문 에이전트에 사용자 대화 전체를 무조건 전달하지 않습니다. 업무에 필요한 질문과 제약만 전달하고 반환값의 형식과 길이를 정합니다. 병렬 위임은 작업 사이에 선후 관계가 없을 때 사용합니다.
  • 비밀 키는 .env에서 읽고 존재 여부만 확인합니다. 노트북 출력, 예외 메시지, 배포 묶음에 키가 포함되지 않았는지 발행 전에 검사합니다.
  • 외부 모델 호출의 응답과 지연은 공급자 상태에 따라 달라집니다. 운영 기준은 반복 측정의 중앙값과 상위 백분위수로 정합니다.

8정리와 다음 절

  • Subagent는 중앙 에이전트가 호출하는 전문 도구입니다. calls와 전달 문자 수로 호출 경계와 문맥 경계를 따로 확인합니다.
  • 출력값과 상태를 근거로 관찰한 범위를 설명합니다.
  • 반복 측정이 없는 수치를 일반적인 성능으로 확대하지 않습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 사용자가 직접 대화하는 담당자가 바뀌는 Handoff를 active_agent 상태와 thread_id로 구현합니다.

9복습 문제

1. 전문 에이전트에 전체 문맥을 전달하지 않은 이유는 무엇인가요?

해설 — 전문 작업에 필요한 질문만 전달해 불필요한 기록이 전문 문맥을 차지하지 않게 하기 위해서입니다.

2. supervisor가 policy_specialist를 실제로 호출했다는 두 근거는 무엇인가요?

해설 — 결과 메시지의 tool_calls와 도구 함수의 calls가 모두 policy_specialist 한 번을 기록합니다.

3. 전체 639자와 전달 38자의 비교로 직접 확인할 수 없는 것은 무엇인가요?

해설 — 이 비교는 전달 문자 수만 보여 줍니다. 토큰 절감량이나 답변 품질 향상은 별도 측정이 필요합니다.

4. 전문 도구의 반환값 형식과 길이를 정해야 하는 이유는 무엇인가요?

해설 — 중앙 에이전트가 전문 결과를 다음 판단에 사용하므로, 필요한 근거와 불필요한 문맥을 구분할 수 있어야 합니다.
