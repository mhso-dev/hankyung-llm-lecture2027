1학습 목표

  • 롤백과 복구 검증의 핵심 단계와 종료 조건을 설명할 수 있습니다.
  • 제공된 로컬 실습을 실행하고 성공과 실패를 종료 코드로 구분할 수 있습니다.
  • 실행 기록을 근거로 다음 배포 단계를 진행하거나 중단할 수 있습니다.

2이 내용을 배우는 이유

경보를 확인한 뒤에도 이전 버전을 정확히 선택하고 서비스 회복을 검증해야 합니다. 최신 배포 기록을 삭제하면 장애 원인과 대응 시점을 추적할 근거도 사라집니다. 이 절에서는 v2 실패 기록을 보존한 채 v1을 가리키는 롤백 사건을 새 리비전으로 추가합니다.

상태 파일만 바꾸고 끝내지 않습니다. 실제 HTTP 프로세스를 v1, v2, v1 순서로 시작해 /health 응답이 200, 503, 200으로 변하는지 확인합니다.

3앞에서 배운 내용

Ch15의 evaluation-cases.json과 회귀 비교는 이전에 성공했던 답변 품질을 기준선으로 남기는 방법을 보여 주었습니다. Ch29의 에이전트 평가는 최종 답변뿐 아니라 도구 호출 수와 궤적도 확인해야 한다는 점을 다루었습니다. Ch32의 Docker 이미지는 실행 환경을 파일로 고정했습니다. 이 절에서는 그 결과를 자동 검사의 입력으로 사용하며, 원본 평가 자료를 다시 계산했다고 주장하지 않습니다. 공개 실습용 요약 자료의 출처 장과 필드 의미를 README에 기록합니다.

4핵심 개념

변경을 통과시키는 검사대

공항의 수하물은 접수, 보안 검사, 목적지 분류를 차례로 통과합니다. 한 단계가 실패하면 다음 운송 단계로 보내지 않습니다. CI/CD도 변경 하나를 테스트, 정적 검사, 빌드, 평가, 배포 검증의 순서로 처리합니다. 비유에서 검사대는 작업 단계에, 통과 표시는 종료 코드 0에 대응합니다.

정의

롤백(rollback)은 문제가 있는 새 배포를 이전에 확인된 리비전으로 되돌리는 운영 절차입니다. 리비전(revision)은 배포 상태의 순서가 있는 버전 기록입니다. 롤백은 코드만 이전으로 바꾸는 작업으로 끝나지 않습니다. 데이터베이스 스키마, 메시지 형식, 캐시, 외부 API가 이전 버전과 호환되는지 확인해야 합니다. 복구 검증은 이전 다이제스트가 활성화되었는지, readiness가 정상인지, 오류와 지연이 회복되는지 확인합니다. 이 실습은 두 다이제스트의 로컬 이력과 경보 종료 코드를 연결합니다.

앞 절에서 가장 긴 위반 구간이 2로 계산되어 FIRING이 되었습니다. 이 절은 그 신호를 복구 판단에 사용합니다. 롤백 사건에는 출발 리비전, 목표 리비전, 이유, 활성 다이제스트를 함께 기록합니다.

코드 읽기와 개념 경계

롤백은 이전 다이제스트를 다시 활성화하는 변경이고, 복구 검증은 그 뒤 서비스가 기대 상태로 돌아왔는지 확인하는 별도 단계입니다. 예제는 v1과 v2 배포 사건을 기록하고 경보 프로세스의 실패를 확인한 뒤 rollback.py로 새 사건을 추가합니다. 마지막에는 활성 다이제스트와 HTTP 검사를 모두 확인합니다.

이전 이미지로 돌아갔다고 데이터베이스와 외부 작업까지 되돌아가는 것은 아닙니다. 스키마가 비호환이거나 이미 발송된 메시지가 있다면 코드 롤백만으로 복구되지 않습니다. 배포 전에는 이전 버전이 현재 데이터 구조를 읽을 수 있는지, 롤백 후 어떤 대표 요청으로 기능을 확인할지 정합니다.

도식 읽기

도식의 화살표를 따라가며 현재 단계가 무엇을 입력으로 받고 무엇을 남기는지 확인합니다. 검사 결과가 실패이면 다음 단계 화살표를 따라가지 않습니다. 운영 환경에서는 승인, 비밀 정보, 네트워크 상태 같은 조건이 더해질 수 있습니다.

6일부러 실패해 보기

Before에서는 v2 HTTP 프로세스의 /health가 503과 regressed를 반환하고 운영 검사도 FIRING, 종료 코드 1입니다. After에서는 기존 배포 이력을 삭제하지 않고 롤백 사건을 새 리비전으로 추가합니다. 이어 v1 HTTP 프로세스를 다시 시작해 /health가 200과 ok를 반환하는지 확인합니다. 이 실습은 로컬 실제 요청 복구를 확인하지만 클라우드 트래픽 전환과 데이터베이스 호환성은 검증하지 않습니다.

7주의할 점과 실무 메모

  • 되돌릴 이미지가 레지스트리에서 삭제되지 않도록 보존 정책을 정합니다.
  • 하위 호환되지 않는 데이터 마이그레이션은 애플리케이션 롤백만으로 복구되지 않을 수 있습니다. 확장 후 축소 방식이나 별도 데이터 복구 절차를 준비합니다.
  • 자동 롤백은 잘못된 경보에도 반응할 수 있으므로 영향 범위와 승인 정책, 최대 반복 횟수를 정합니다.

HTTP 200은 이 예제의 health 경로가 응답했다는 사실만 보여 줍니다. 데이터베이스 쓰기, 외부 API, 사용자 핵심 흐름은 별도 확인이 필요합니다. 데이터 형식이 이전 버전과 호환되지 않으면 애플리케이션 이미지만 되돌려도 복구되지 않습니다.

8정리와 다음 절

  • 롤백은 이전에 검증한 리비전과 다이제스트를 다시 선택합니다.
  • 롤백 뒤에는 배포 상태와 서비스 지표를 다시 검증합니다.
  • 코드와 데이터의 호환성을 함께 설계해야 복구 절차가 작동합니다.

9복습 문제

롤백과 재배포의 공통점은 무엇인가요?

둘 다 선택한 이미지 다이제스트를 배포 환경의 활성 버전으로 지정합니다.

롤백 뒤 무엇을 확인해야 하나요?

활성 다이제스트, readiness, 핵심 요청, 오류율과 지연의 회복을 확인해야 합니다.

애플리케이션만 되돌려도 복구되지 않는 사례는 무엇인가요?

이전 버전과 호환되지 않는 데이터베이스 스키마 변경이 이미 적용된 사례입니다.

자동 롤백에 필요한 제한은 무엇인가요?

경보 조건, 영향 범위, 승인 정책, 최대 반복 횟수와 중단 조건이 필요합니다.
