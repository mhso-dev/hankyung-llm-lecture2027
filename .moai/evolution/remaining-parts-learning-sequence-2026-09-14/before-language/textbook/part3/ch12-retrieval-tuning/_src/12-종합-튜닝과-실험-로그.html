1학습 목표

  • 가설·설정·지표·날짜를 한 행에 기록해 검색 변경의 효과를 비교하는 절차의 입력과 출력을 설명할 수 있습니다.
  • 제공된 30문항을 개발·시험으로 나누어 설정을 선택하고 평가할 수 있습니다.
  • 관찰한 수치가 설명하는 범위와 설명하지 못하는 범위를 구분할 수 있습니다.

2이 내용을 배우는 이유

검색 설정을 여러 개 바꾸면 좋은 결과가 어느 조건에서 나왔는지 기억만으로 재현하기 어렵습니다. 가설, 입력 해시, 설정, 지표, 시간을 한 행에 남기고 개발 문항으로 설정을 선택해야 합니다. 시험 문항은 선택이 끝난 뒤 한 번만 사용해 결과에 맞춘 설정 선택을 피합니다.

Ch11에서 만든 질문과 정답 문서 ID를 유지한 채 한 조건씩 바꿉니다. 30문항을 개발 15개와 시험 15개로 나누어 설정 선택과 최종 평가를 분리합니다.

3앞에서 배운 내용

Ch10에서 PDF를 문서와 청크로 나누고 메타데이터에 출처를 보존했습니다. Ch11의 evaluation-queries.jsonl은 질문마다 gold_doc_ids와 dev/test 분할을 제공합니다. 노트북은 이 Ch11 원본을 직접 읽고, 독립 실행용 Ch12 복제본과 같은지 확인합니다. advanced-documents.json의 부모 doc_id는 정답 ID와 비교하고, 자식 parent_id는 그 문서를 가리킵니다. page와 chunk_id는 출처 위치를 보존합니다. 앞 절의 변수나 실행 상태는 필요하지 않습니다.

4핵심 개념

쉬운 예

도서관에서 책을 찾을 때 먼저 검색대가 관련 서가를 좁히고, 그 안에서 제목과 목차를 자세히 읽어 우선순위를 정한다고 생각해 봅니다. 첫 단계가 서가를 빠뜨리면 다음 단계는 그 책을 검토할 수 없습니다. 반대로 후보를 지나치게 많이 가져오면 자세히 읽는 시간이 늘어납니다.

정의

가설·설정·지표·날짜를 한 행에 기록해 검색 변경의 효과를 비교하는 절차입니다. 각 개발 행은 가설, 설정, 문서·질문 SHA, 지표, 날짜, 시간을 함께 기록합니다. 개발 행으로 설정을 고른 뒤 시험 결과는 별도 run_id로 한 번 기록합니다.

도식은 위에서 아래로 가설, 개발 설정 36개, 선택 설정의 시험 평가 1회, JSONL 로그 순서로 읽습니다. 초록은 입력·문서·후보, 파랑은 직접 구현한 선택·설정, 보라는 모델 점수·질문 재작성, 노랑은 측정 결과·로그를 뜻합니다. 화살표는 데이터 전달 방향입니다.

통합 실행 흐름

{{svg:12-통합-RAG}}

앞 도식은 TF-IDF와 MMR의 36개 개발 설정과 선택 설정의 시험 평가를 보여 줍니다. 다음 도식은 제공 PDF 로딩, dense와 Kiwi BM25 검색, RRF, CrossEncoder, 쪽 본문과 출처 선택, 답변 생성을 연결한 별도의 개발 질문 1건 스모크 실행입니다. 두 실행은 검색 구성·질문 수·평가 단위가 달라 수치를 직접 비교하지 않습니다. 통합 실행은 단계가 연결되는지만 확인하며, 답변 품질은 Ch15에서 평가합니다.

통합 실행의 임베딩은 Ch10·Ch12 앞 실습과 같은 text-embedding-3-small의 256차원으로 고정합니다. 답변 생성에는 Ch6·Ch9와 같은 gpt-5.4-mini를 사용합니다. 통합 로그의 settings.dimensions는 실제 임베딩 배열에서 읽은 차원이고 settings.chat은 답변 모델입니다. 모델을 맞추더라도 문서·청킹·질문이 다른 앞 예제와 답변 품질을 직접 비교하지 않습니다.

설정 선택과 최종 확인을 분리하기

36개 행은 문자 분석기·n-gram·보고 순위·MMR λ의 조합입니다. 평가 함수는 설정 한 개와 개발 질문을 입력받아 질문별 순위와 평균 지표를 반환하고, 로그는 설정과 결과를 한 행에 저장합니다. 개발 nDCG@5로 설정을 선택한 뒤 시험 질문은 한 번만 실행해야 시험 결과가 선택 과정에 섞이지 않습니다.

마지막 통합 RAG 스모크 실행은 PDF 읽기부터 dense·BM25·RRF·리랭킹·생성까지 연결되는지 확인합니다. 이는 앞의 36개 TF-IDF 설정과 검색기·질문 수·평가 단위가 다르므로 같은 표에서 우열을 비교하지 않습니다. 연결 성공, 검색 지표, 생성 답의 사실성은 서로 다른 검증 결과로 기록합니다.

5실행 예제

노트북은 Python 3.12 새 커널에서 실행합니다. 먼저 부모 문서 수, 자식 청크 수, 질문 수를 출력해 입력 범위를 확인합니다. 다음 셀은 가장 작은 문항 하나에서 중간 결과를 보여 줍니다. 마지막 셀은 조건을 바꾸거나 평가 범위를 넓힙니다. 출력의 문서 ID, 점수, 실행 시간 또는 로그 수를 본문 설명과 대조합니다.

확인할 점 — 코드가 실제 검색 또는 모델 추론을 수행하는지, 정답 문서 ID를 결과 뒤에 새로 붙이지 않는지, 비교할 때 질문과 원문이 유지되는지 확인합니다.

6실험 결과 해석

문자 분석기 2종, n-gram 범위 3종, 보고 순위 2종, λ 3종을 조합해 36개 개발 설정을 실행했습니다. 각 질문에서 상위 50개 청크를 후보로 만든 뒤 parent_id 중복을 제거하고 문서 순위를 평가했습니다. 따라서 이 절의 chunk-candidate-unique-parent-macro-v1은 Ch11의 고유 문서 후보 정책과 단위가 다르며 두 수치를 직접 비교하지 않습니다. 개발 nDCG@5는 0.9754, 선택 설정의 시험 nDCG@5는 0.9508이었습니다. 별도 통합 실행은 개발 문항 Q002를 사용해 PDF 6건 35쪽을 읽고 dense·Kiwi BM25·RRF·CrossEncoder를 거친 뒤 검색된 쪽 본문으로 답변과 출처를 생성했습니다. 이 실행은 처리 단계의 입력과 반환 형식만 확인한 것으로, 검색 지표나 생성 답변 품질은 평가하지 않았습니다.

한 번의 출력은 이 데이터와 실행 환경에서 관찰한 결과입니다. 다른 도메인, 더 긴 문서, 다른 언어 비율에서는 순서와 시간이 달라질 수 있습니다. 설정을 채택하기 전에는 실제 서비스 질문을 같은 형식으로 추가해 다시 계산해야 합니다.

7주의할 점과 실무 메모

  • 이번 절의 중간 결과를 확인한 뒤 다음 단계로 전달합니다. 검색 후보, 선택 결과, 부모 원문, 재작성 질문, 로그 행은 서로 다른 데이터입니다.
  • 실행 시간은 CPU, GPU, 배치 크기, 입력 길이, 모델 캐시에 따라 달라집니다. 장치와 패키지 버전을 로그에 함께 남깁니다.
  • OpenAI 임베딩 175개와 답변 생성 1회의 예상 API 비용은 미화 1달러 미만입니다. 실제 청구액은 사용량 기록으로 확인합니다.
  • 공개 PDF 6건과 30문항은 학습용 기준선입니다. 실제 서비스의 문서 분포와 질문 유형을 대신하지 않습니다.

8정리와 다음 절

  • TF-IDF+MMR 개발 로그 36개에서 설정을 고르고 시험 문항은 한 번 평가했습니다.
  • 별도의 dense·BM25·RRF·CrossEncoder 스모크 실행으로 PDF 로딩부터 답변 생성까지의 입력과 반환 형식을 확인했습니다.
  • 두 실행의 수치는 직접 비교하지 않으며, 생성 답변 품질은 아직 평가하지 않았습니다.

다음 학습과 이어지는 지점 — Ch13에는 스모크 실행의 질문·검색 결과·출처 객체 형식과 단계 순서를 넘깁니다. Ch15에는 generation_evaluation.status=not_evaluated인 통합 로그를 넘겨 답변 정확성·근거성·출처 표기를 별도로 평가합니다.

9복습 문제

1. 이해 — 이번 절에서 고정한 조건은 무엇인가요?

설정 비교에서 바꾸지 않은 입력을 두 가지 적어 보세요.

30개의 질문과 각 질문의 정답 문서 ID, 공개 PDF에서 추출한 본문을 유지했습니다. 입력을 고정해야 설정 변화와 결과 변화의 관계를 설명할 수 있습니다. 오답 시 다시 볼 곳: 3절 ‘앞에서 배운 내용’

2. 이해 — 개발과 시험 문항을 왜 분리하나요?

36개 설정을 시험 문항으로 고를 때 생기는 문제를 설명해 보세요.

시험 결과에 맞춘 설정이 되어 새 질문에서의 품질을 과대평가할 수 있습니다. 개발 문항으로 설정을 고른 뒤 시험 문항은 한 번만 평가합니다. 오답 시 다시 볼 곳: 6절 ‘실험 결과 해석’

3. 적용 — 실험 한 행에 무엇을 기록하나요?

재현 가능한 로그 필드를 네 가지 이상 적어 보세요.

run_id, 날짜, 문서와 질문 SHA, 설정, 지표, 실행 시간, 분할, 문항 수, 지표 정책을 기록합니다. 오답 시 다시 볼 곳: 5절 ‘36개 개발 설정 실행’

4. 분석 — Recall@50=1이면 튜닝이 끝났나요?

개발·시험 nDCG@5와 함께 해석해 보세요.

아닙니다. 이 말뭉치에서는 Recall@50이 포화됐지만 상위 순서는 달라질 수 있습니다. nDCG@5와 실제 통합 답변, 다른 질문 분포를 추가로 확인합니다. 오답 시 다시 볼 곳: 6절 ‘실험 결과 해석’
