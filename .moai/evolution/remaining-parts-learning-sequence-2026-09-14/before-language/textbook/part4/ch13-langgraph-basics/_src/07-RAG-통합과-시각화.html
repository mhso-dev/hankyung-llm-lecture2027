1학습 목표

  • Ch12 통합 로그의 질문과 출처를 입력으로 이어받을 수 있습니다.
  • 실제 문서 검색, 두 순위의 RRF 병합, 후보 재정렬, 모델 생성을 노드로 연결할 수 있습니다.
  • get_graph().draw_mermaid() 출력과 실행 trace를 대조할 수 있습니다.

2이 내용을 배우는 이유

앞 여섯 절에서는 작은 데이터로 그래프 구성 요소를 하나씩 확인했습니다. 이제 Part 3에서 만든 RAG 흐름을 그대로 가져와 각 함수를 노드에 대응시킵니다. 저장된 Ch12 답변을 출력하는 방식으로는 그래프가 실제 생성을 수행했는지 확인할 수 없습니다. 따라서 통합 로그에서는 질문과 이전 출처만 읽고, 이번 그래프가 문서 검색부터 답변 생성까지 다시 실행합니다.

이번 절의 질문은 “Ch12의 실제 문서와 통합 로그를 읽어 검색, 병합, 재정렬, 생성을 하나의 그래프로 연결할 수 있을까요?”입니다. 노트북 출력과 그래프 그림을 함께 읽어 답합니다.

3앞에서 배운 내용

Ch12의 runs/advanced-continuity-integrated-result.json에는 Q002 질문, 검색된 E01·E02 쪽, 실제 모델 응답, 고정 설정이 있습니다. data/advanced-documents.json에는 제공 PDF에서 추출한 부모 문서와 청크가 있습니다. 배포 묶음에 포함된 이 두 Ch12 파일을 상대 경로로 읽으므로 개인 경로가 필요하지 않습니다.

각 노트북은 Python 3.12 새 커널에서 독립 실행되며 이전 절의 메모리나 개인 경로를 사용하지 않습니다.

4핵심 개념

쉬운 예

공장 공정표에서 원료가 어느 기계를 거치고 어떤 검사 결과가 다음 단계로 전달되는지 표시하는 것과 같습니다.

정의

load_pages는 Ch12 문서 목록으로 제공 PDF를 읽습니다. dense_search는 OpenAI 임베딩, sparse_search는 Kiwi BM25 점수를 실제로 계산합니다. fuse는 두 순위를 reciprocal rank fusion(RRF)으로 합칩니다. rerank는 CrossEncoder로 상위 후보를 다시 정렬합니다. generate는 선택한 본문과 출처를 메시지에 넣고 init_chat_model().invoke()를 실제 호출한 뒤 AIMessage.text를 상태에 저장합니다. 각 노드는 하나의 처리 단계만 맡고 필요한 상태 값만 갱신합니다.

코드에서 읽는 순서

그래프 입력에는 Ch12 Q002와 여섯 PDF의 파일 정보가 들어갑니다. load_pages는 PDF 35쪽을 텍스트 청크로 만들고, dense_search는 256차원 OpenAI 임베딩의 코사인 유사도를 계산합니다. sparse_search는 Kiwi 형태소로 나눈 토큰을 BM25에 넣습니다. fuse는 두 점수의 크기를 섞지 않고 각 순위의 역순위 점수를 더합니다. rerank는 상위 열 개만 CrossEncoder로 비교하고 부모 문서가 겹치지 않게 두 건을 고릅니다. generate는 이 본문과 출처를 실제 모델에 전달합니다.

호출 표기와 실행 시점

통합 그래프의 초기 상태에는 질문과 PDF 위치가 들어가고 각 노드는 자신이 만든 필드만 반환합니다. load_pages가 documents를 만들면 검색 노드가 그 값을 읽고, fuse와 rerank가 candidates를 좁힌 뒤 generate가 선택 문서로 answer를 만듭니다. trace는 데이터 자체가 아니라 실행 순서를 확인하려고 누적하는 관찰 필드입니다.

다른 상황에 적용

사내 규정 RAG에서는 PDF 대신 위키 문서를 읽고, sparse_search 대신 제목 키워드 검색을 사용할 수 있습니다. 그래도 로드→복수 검색→병합→재정렬→생성이라는 단계 경계와 각 노드의 입출력 이름을 유지하면 한 단계씩 교체하고 평가할 수 있습니다.

비교와 경계

그래프가 완성됐다는 사실은 답변 품질을 보장하지 않습니다. Mermaid는 선언된 연결을 보여 주고 trace는 이번 실행 경로를 보여 줄 뿐입니다. 검색 정확도와 답변 근거성은 Ch15의 평가 데이터와 지표로 따로 확인해야 합니다.

5실행 예제

Ch12의 Q002와 여섯 PDF 정보를 읽고 PDF 로딩, 임베딩 검색, BM25 검색, RRF 병합, 재정렬, 생성을 차례로 실행합니다. 선택된 E01·E02 문서와 새 답변의 출처, 여섯 노드 trace를 확인합니다. 마지막 셀은 실행 정보와 사용량을 graph-integrated-result.json에 저장합니다.

6실험 결과 해석

출력에서 입력 질문이 Ch12 Q002와 같은지, 두 검색 순위와 RRF 점수가 실제로 계산됐는지, 재정렬된 E01 본문에 7권과 14일이 포함되는지 확인합니다. 모델 출력은 실행 시점에 달라질 수 있으므로 저장된 Ch12 response와 글자가 같은지를 성공 조건으로 삼지 않습니다. 대신 생성 노드가 선택한 실제 본문과 [E01 p.3] 출처를 전달하고 새 AIMessage.text를 반환했는지 확인합니다. trace와 Mermaid에는 load_pages, dense_search, sparse_search, fuse, rerank, generate 순서가 모두 나타납니다.

실제 통합 실행은 E01 3쪽과 E02 3쪽을 선택하고 E01의 7권·14일을 답했습니다. 출력에는 1,230개의 총 토큰 사용량과 여섯 노드의 실행 순서도 함께 기록됐습니다.

Q002 한 건으로 실제 검색부터 생성까지 이어지는지만 확인한 스모크 실행입니다. 전체 질문에서 검색 품질과 답변 품질이 유지되는지는 별도 평가셋과 지표로 측정해야 합니다.

7주의할 점과 실무 메모

  • 모델 출력은 실행할 때마다 문장 표현이 달라질 수 있습니다. 선택 문서에 E01 3쪽이 있고 답변에 [E01 p.3]이 있는지 별도로 검사합니다.
  • OpenAI 임베딩 점수와 Kiwi BM25 점수의 크기는 직접 비교하지 않고 각각의 순위만 RRF 입력으로 사용합니다.
  • RRF와 재정렬 후보가 적은 한 질문의 스모크 실행입니다. 검색 품질과 생성 품질의 전체 평가는 Ch11·Ch15 지표로 따로 수행합니다.
  • OPENAI_API_KEY는 상위 .env에서 읽고 존재 여부만 확인하며 값은 출력하지 않습니다.

8정리와 다음 절

  • 여섯 노드가 PDF 로딩부터 실제 답변 생성까지 차례로 실행됐습니다.
  • 재정렬 결과 E01 3쪽과 E02 3쪽을 선택하고 7권·14일 답변을 생성했습니다.
  • 1,230토큰을 사용한 Q002 한 건의 스모크 실행이므로 전체 품질은 별도로 평가해야 합니다.
