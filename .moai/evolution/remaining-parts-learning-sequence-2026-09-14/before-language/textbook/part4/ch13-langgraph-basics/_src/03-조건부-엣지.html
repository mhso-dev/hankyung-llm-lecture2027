1학습 목표

  • 조건 함수와 작업 노드의 역할을 구분할 수 있습니다.
  • add_conditional_edges로 코드가 정한 분기를 구성할 수 있습니다.
  • 같은 그래프에 두 입력을 넣어 서로 다른 경로를 확인할 수 있습니다.

2이 내용을 배우는 이유

RAG에서는 검색 결과가 충분할 때 답을 만들고 부족할 때 추가 자료를 요청해야 합니다. if문을 호출 코드 여러 곳에 두면 경로를 한눈에 보기 어렵습니다. 조건부 엣지는 상태를 읽는 조건 함수를 그래프의 연결 규칙으로 등록합니다.

이번 절의 질문은 “검색 점수가 기준을 넘는지에 따라 답변 생성과 추가 자료 요청 중 어느 노드로 이동하게 할까요?”입니다. 노트북 출력과 그래프 그림을 함께 읽어 답합니다.

3앞에서 배운 내용

Ch11에서 검색 품질을 점수로 측정했고 Ch12에서 후보를 재정렬했습니다. 이번 절은 검색을 다시 구현하지 않고 0과 1 사이의 rerank_score가 이미 상태에 있다고 가정합니다. 경로 판단은 모델이 아니라 코드의 임계값 비교가 담당합니다.

각 노트북은 Python 3.12 새 커널에서 독립 실행되며 이전 절의 메모리나 개인 경로를 사용하지 않습니다.

4핵심 개념

쉬운 예

택배 분류대는 송장 값을 읽고 상자를 서로 다른 컨베이어로 보냅니다.

정의

조건부 엣지(conditional edge)는 한 노드가 끝난 뒤 상태를 읽어 다음 노드 이름을 반환하는 연결입니다. add_conditional_edges(source, path, path_map)는 source 뒤에서 path 함수를 호출하고 그 반환값을 실제 노드 이름으로 대응시킵니다. Literal 반환형이나 path_map을 적으면 시각화할 때도 가능한 목적지가 분명하게 표시됩니다.

코드에서 읽는 순서

inspect_score는 route에 checked를 기록하고 실행을 마칩니다. 그 다음 choose 함수가 같은 상태의 rerank_score를 읽습니다. 점수가 0.7 이상이면 generate라는 노드 이름을, 미만이면 request_more를 반환합니다. add_conditional_edges는 이 반환값을 실제 목적지와 연결합니다. 두 목적지 노드는 모두 END로 이어지므로 한 입력에서 두 노드가 함께 실행되지 않습니다. 점수 하나만 바꾼 두 출력을 비교하면 분기 기준과 선택 결과를 분리해 읽을 수 있습니다.

호출 표기와 실행 시점

add_conditional_edges('inspect_score', choose)는 inspect_score가 끝난 직후 choose를 호출합니다. choose는 작업 결과를 만드는 노드가 아니라 다음 경로의 이름을 반환하는 함수입니다. 반환값과 실제 노드 이름이 다르면 path_map으로 대응 관계를 적고, 같으면 반환형 Literal이 가능한 경로를 문서화합니다.

다른 상황에 적용

문서 검색 외에도 결제 금액이 승인 한도 이하면 approve, 초과하면 manual_review로 보내는 흐름에 같은 구조를 적용할 수 있습니다. 입력 필드와 임계값은 달라져도 조건 함수와 실제 작업 노드를 분리하는 원칙은 유지됩니다.

비교와 경계

조건부 엣지는 경로만 고릅니다. 판단 결과를 상태에 남기면서 이동까지 한 번에 표현하려면 뒤에서 배우는 Command가 더 직접적입니다. 또한 0.7이라는 숫자는 LangGraph의 기본값이 아니라 이 실습에서 정한 정책이므로 평가 데이터 없이 일반 기준으로 사용할 수 없습니다.

확인할 점 — 검색 점수가 기준을 넘는지에 따라 답변 생성과 추가 자료 요청 중 어느 노드로 이동하게 할까요? 출력에 나타난 상태 필드와 경로를 근거로 답해 봅니다.

6실험 결과 해석

점수 0.82는 generate 경로를 지나 '근거로 답변 생성'을 반환합니다. 점수 0.41은 request_more 경로를 지나 '추가 자료 요청'을 반환합니다. 같은 그래프와 같은 임계값을 사용하고 점수 하나만 바꾸었으므로 경로 차이는 조건 함수의 비교 결과에서 생겼습니다.

두 최종 상태의 route와 answer가 함께 달라졌습니다. 조건 함수의 반환값이 실제 목적지 노드 실행으로 이어졌음을 두 필드로 확인했습니다.

점수 0.82와 0.41은 분기를 관찰하려고 코드에 넣은 값이며 0.7도 이 실습에서 정한 기준입니다. 실제 서비스에서는 평가 데이터로 점수 계산법과 임계값을 별도로 검증해야 합니다.

7주의할 점과 실무 메모

  • 조건 함수는 상태를 갱신하지 않고 다음 경로를 고르는 데 집중합니다.
  • 가능한 목적지를 path_map이나 Literal로 제한하면 구조 검사와 그림 해석이 쉬워집니다.
  • 이 절의 분기는 사람이 작성한 score >= 0.7 조건입니다. 모델 자율 판단이나 도구 호출은 포함하지 않습니다.

8정리와 다음 절

  • 0.82는 generate, 0.41은 request_more 경로를 선택했습니다.
  • 분기 기준은 코드에 작성한 0.7 임계값이었습니다.
  • 한 입력에서는 선택된 목적지 노드 하나만 실행됐습니다.
