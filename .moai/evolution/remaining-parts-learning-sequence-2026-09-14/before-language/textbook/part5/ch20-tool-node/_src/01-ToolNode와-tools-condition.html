1학습 목표

  • MessagesState에 모델 노드와 ToolNode를 등록할 수 있습니다.
  • tools_condition이 도구 실행과 종료를 고르는 기준을 설명할 수 있습니다.
  • 실제 모델 호출의 AIMessage, ToolMessage, 최종 AIMessage를 순서대로 읽을 수 있습니다.

2이 내용을 배우는 이유

Ch18에서는 OpenAI SDK를 직접 호출하고 코드로 단계·분기·병렬 실행과 종료를 연결했습니다. Ch19에서는 @tool과 bind_tools로 모델이 읽을 도구 설명과 인자 형식을 만들고, 모델 응답의 tool_calls를 해석해 도구 함수를 호출했습니다. 이제 그 요소를 Ch13의 StateGraph에 넣습니다. 모델이 도구를 요청하면 ToolNode가 실행하고, 요청하지 않으면 종료하는 연결이 처음 완성됩니다. 이 구조를 직접 조립해야 다음 Ch21의 create_agent가 감추는 반복 구조를 읽을 수 있습니다.

3앞에서 배운 내용

Ch13에서 StateGraph, MessagesState와 add_messages 리듀서, 조건부 엣지를 배웠습니다. Ch17에서는 모델·도구·반복·정지 조건이 에이전트의 구성 요소라는 사실과 자율성의 비용을 확인했습니다. Ch19에서는 주문 조회 함수에 @tool을 붙이고 model.bind_tools(tools)가 도구 스키마를 모델 요청에 포함시키는 과정을 배웠습니다. 이번 노트북은 앞 노트북의 변수에 의존하지 않고 작은 읽기 전용 규정 자료를 다시 선언합니다.

4핵심 개념

구체적인 상황

도서관 상담 직원이 질문에 바로 답할지, 규정 담당자에게 조회를 요청할지 정하는 상황을 떠올려 봅니다.

정의와 메시지 흐름

모델 노드는 질문을 읽고 바로 답하거나 도구 호출 요청을 작성합니다. tools_condition은 마지막 AIMessage에 tool_calls가 있는지만 확인하는 분기 함수입니다. 요청이 있으면 tools 노드로 이동하고, 없으면 END로 이동합니다. ToolNode는 요청 이름과 인자를 확인해 실제 도구를 실행하고 그 결과를 ToolMessage로 추가합니다. 도구 결과를 읽은 모델이 최종 답을 만들면 tool_calls가 사라지고 그래프가 끝납니다. 이때 직접 정의한 AgentState의 messages 필드에 붙인 add_messages 리듀서가 HumanMessage, AIMessage, ToolMessage를 실행 순서대로 보존합니다. trace 필드는 실행한 노드 이름을 별도로 누적합니다.

도식 읽기

{{svg:01-흐름}}

model이 작성한 호출 요청의 유무로 분기합니다. ToolNode 실행 결과는 model에 전달되고, 호출 요청이 없는 응답은 END로 이동합니다.

코드를 읽기 전에

이 절은 MessagesState를 직접 사용하지 않고 AgentState를 정의합니다. AgentState.messages에 add_messages 리듀서를 붙여 새 메시지를 기존 목록에 합치고, 별도의 trace 목록에는 실행한 노드 이름을 기록합니다. StateGraph(AgentState)에 모델 노드와 ToolNode를 등록하고 tools_condition을 조건부 엣지로 연결합니다. 그래프를 compile()한 뒤 invoke()해야 노드 실행이 시작됩니다. 그래프를 그리는 코드만으로 모델이나 도구가 실행되지는 않습니다.

모델 노드는 마지막 메시지를 읽어 답 또는 tool_calls가 든 AIMessage를 반환합니다. 조건 함수는 마지막 AIMessage의 호출 요청 유무만 보고 tools 또는 종료로 보냅니다. ToolNode가 결과 ToolMessage를 추가하면 다시 모델 노드로 돌아갑니다.

다른 상황과 개념 경계

배송 규정 질문은 모델이 바로 답할 수도 있고 최신 규정을 조회할 수도 있습니다. 한 번의 조회 뒤에도 정보가 부족하면 모델이 다른 도구를 요청해 루프가 이어질 수 있습니다. tools_condition은 답이 사실인지 판정하지 않고 호출 요청의 존재만 확인하므로, 품질 검사와 실행 상한은 별도로 설계해야 합니다.

5실행 예제

먼저 gpt-5.4-mini에 lookup_policy를 bind_tools로 연결합니다. call_model은 모델 응답을 messages에 추가하고 모델 호출만 trace에 기록합니다. 그 다음 StateGraph에 model과 ToolNode를 등록하고 tools_condition을 조건부 엣지로 연결합니다. 대출 기간 질문과 인사 질문을 각각 실행해 ToolMessage 생성 여부를 비교합니다.

{{notebook:01-ToolNode와-tools-condition}}

확인할 점 — 대출 기간 질문의 trace에는 모델 호출 두 번이 나타나고, 그 사이의 ToolNode 실행은 메시지 목록의 ToolMessage로 확인합니다. 메시지 종류는 HumanMessage, AIMessage, ToolMessage, AIMessage 순서입니다. 첫 AIMessage의 tool_calls에는 lookup_policy와 topic 인자가 있고, ToolMessage에는 로컬 규정 문자열이 있습니다. 반면 인사 질문은 도구를 호출할 이유가 없으므로 model 노드를 한 번 실행한 뒤 끝날 수 있습니다. 모델 출력은 실행 시점에 달라질 수 있으므로 정확한 문장보다 메시지 종류, 호출 이름, 도구 결과 포함 여부를 확인합니다.

6실험 결과 해석

대출 질문은 HumanMessage, 도구 호출이 있는 AIMessage, '일반 도서는 1인 5권까지 14일'이라는 ToolMessage, 최종 AIMessage 순서로 끝났습니다. 모델 trace는 두 번 기록됐고 ToolNode 실행은 가운데 ToolMessage로 확인했습니다. 두 모델 호출은 입력 370토큰, 출력 50토큰이었고 추정 비용은 0.000503달러, 전체 지연은 1.963초였습니다. 인사 질문에는 ToolMessage가 없었습니다.

두 질문을 한 번씩 실행한 구조 확인입니다. 다른 질문에서도 같은 도구 선택이 일어나는지, 응답 품질이 유지되는지는 더 많은 고정 질문으로 따로 측정해야 합니다.

7주의할 점과 실무 메모

  • tools_condition은 질문의 키워드를 직접 검사하지 않습니다. 마지막 AIMessage의 tool_calls 유무만 봅니다.
  • ToolNode는 모델이 아닙니다. 이미 만들어진 도구 호출 요청을 실행하는 그래프 노드입니다.
  • 이번 자료의 도구는 로컬 딕셔너리를 읽기만 합니다. 쓰기 도구에는 별도의 권한 확인과 중복 실행 방지가 필요합니다.
  • 가격 계산은 2026-09-10 공개 단가인 입력 100만 토큰당 0.75달러, 출력 100만 토큰당 4.50달러를 사용합니다. 실제 청구액은 계정의 캐시·배치 조건에 따라 달라질 수 있습니다.

8정리와 다음 절

  • tools_condition은 마지막 AIMessage의 tool_calls 유무로 ToolNode 또는 END를 선택합니다.
  • ToolNode의 실행 여부는 요청 AIMessage와 결과 ToolMessage의 연결로 확인합니다.
  • 도구가 필요 없는 질문은 model 한 번 뒤에 종료될 수 있습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 ToolNode가 실행한 도구에서 오류가 발생했을 때 예외를 숨기지 않고 ToolMessage로 어떻게 전달할지 확인합니다.

9복습 문제

1. tools_condition이 확인하는 값은 무엇인가요?

해설 — 마지막 AIMessage의 tool_calls 유무를 확인합니다.

2. ToolNode가 메시지 상태에 추가하는 대표 메시지는 무엇인가요?

해설 — 도구 실행 결과와 tool_call_id를 담은 ToolMessage입니다.

3. tools 노드 뒤에 model 노드로 돌아가는 엣지가 필요한 이유는 무엇인가요?

해설 — 모델이 도구 결과를 읽고 최종 답을 만들거나 다음 도구 호출을 정해야 하기 때문입니다.

4. 이번 실행의 성공을 최종 답 문장 일치로 판정하지 않는 이유는 무엇인가요?

해설 — 모델 표현은 실행할 때마다 달라질 수 있고, 이번 학습 목표는 메시지 흐름과 도구 실행이기 때문입니다.
