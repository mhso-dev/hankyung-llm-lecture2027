1학습 목표

  • 오케스트레이터가 만든 하위 작업 목록을 검사할 수 있습니다.
  • 작업 수만큼 워커 코루틴을 동적으로 생성할 수 있습니다.
  • 고정 병렬화와 동적 작업 분해의 차이를 실제 출력으로 설명할 수 있습니다.

2이 내용을 배우는 이유

고정된 안내문이라면 목적·절차·지원 세 부분을 코드에 미리 적을 수 있습니다. 그러나 코드 변경 요청이나 조사 과제는 입력마다 필요한 파일과 자료가 달라집니다. 이때 모든 가능성을 코드 분기로 나열하면 새 유형이 들어올 때마다 프로그램을 고쳐야 합니다. 오케스트레이터-워커에서는 고정된 작업 목록을 넘어 필요한 작업 수와 내용을 중앙 모델이 정합니다.

3앞에서 배운 내용

앞 절의 병렬화는 sections 목록 세 개를 사람이 미리 적었습니다. Ch 17에서는 모델이 흐름을 얼마나 결정하는지 자율성의 기준으로 살펴봤습니다. 이 절은 그 경계를 코드에서 확인합니다. 워커 실행과 결과 집계 방식은 파이썬이 정하지만, 워커의 개수와 담당 내용은 오케스트레이터 출력에 따라 달라집니다.

4핵심 개념

쉬운 예

편집장은 들어온 기사의 성격을 보고 취재, 사실 확인, 도표 제작 중 필요한 담당을 정합니다. 모든 기사에 같은 세 담당자를 배정하지 않습니다. 편집장이 업무를 나눈 뒤 각 담당자가 동시에 일하고, 마지막에 편집장이 결과를 하나의 기사로 묶습니다.

정의

오케스트레이터(orchestrator)는 전체 과제를 읽고 하위 작업을 계획하며 결과를 종합하는 모델 역할입니다. 워커(worker)는 할당받은 범위만 처리합니다. 동적 분해(dynamic decomposition)는 하위 작업의 개수와 지시가 입력마다 달라지는 성질입니다. 이 실습은 오케스트레이터가 2~4개의 id와 instruction을 만들게 하고, 유효한 항목만 최대 4개까지 실행합니다. 2개보다 적으면 고정된 기본 목록으로 바꾸지 않고 오류를 숨기지 않은 채 중단합니다.

도식 읽기

{{svg:04-흐름}}

오케스트레이터가 작업 목록을 만들면 코드가 유효한 작업 수를 검사합니다. 유효 작업이 두 개보다 적으면 중단하고, 통과하면 최대 네 개의 워커를 실행합니다. 워커 결과를 종합 모델에 전달합니다.

코드를 읽기 전에

오케스트레이터 호출은 전체 과제에서 id와 instruction 목록을 만듭니다. 프로그램은 tasks가 목록이라고 가정하고, 그 안에서 사전이며 id와 instruction 값이 모두 참인 항목을 골라 앞의 네 개만 사용합니다. ID 중복, 문자열 자료형, 40자 길이는 다시 검사하지 않습니다. 남은 항목이 두 개 미만일 때만 중단합니다. 선택된 항목마다 run_worker() 코루틴을 만들고 gather로 실행한 뒤 작업 ID와 결과를 종합 호출에 전달합니다.

동적이라는 말은 워커 함수가 실행 중 새 작업을 계속 만든다는 뜻이 아닙니다. 이 예제에서는 첫 모델 호출이 작업의 개수와 내용을 입력별로 정하고, 이후 코드는 그 유효한 목록만 실행합니다. 계획 검증 실패는 고정 목록으로 조용히 바꾸지 않고 중단합니다.

다른 상황과 개념 경계

저장소 수정 요청은 변경할 파일 수가 입력마다 달라 오케스트레이터-워커에 맞을 수 있습니다. 월간 보고서처럼 항상 매출·고객·운영 세 절을 작성한다면 고정 병렬 섹셔닝이 더 직접적입니다. 두 패턴은 모두 병렬 실행할 수 있지만, 하위 작업 목록을 코드가 미리 정하는지 모델이 입력을 보고 정하는지가 경계입니다.

5실행 예제

실제 오케스트레이터는 세 작업을 만들었습니다. 내용은 도입 목적, 등록 절차, 지원 및 문의 방법이었습니다. 코드는 이 세 결과를 읽은 뒤 워커 세 개를 생성했습니다. 출력에는 고정 목록 사용: False가 기록됐습니다. 호출 구성은 계획 1회, 워커 3회, 종합 1회로 모두 5개의 성공 응답이었습니다. 엄격한 answer 형식의 종합 출력이 반환됐고 사용량 기준 추정 비용은 0.002071달러였습니다.

확인할 점 — 오케스트레이터가 만든 작업 수와 실제 워커 수가 같고, 호출 수가 계획 1회와 워커·종합 호출의 합인지 확인합니다.

6실험 결과 해석

이번 입력에서 세 작업이 나온 사실은 다음 실행에서도 세 작업이 나온다는 보장이 아닙니다. 작업 수가 달라지면 호출 수와 비용도 달라집니다. 모델이 만든 지시가 중복되거나 빠질 수 있으므로 배열 자료형, 필수 키, 개수 상한을 코드로 검사해야 합니다. 종합 결과에 실습에서 지정하지 않은 문의처가 들어갈 수 있다는 점도 확인해야 합니다. 동적 분해는 계획을 자동으로 만들지만 사실 검증을 자동으로 해결하지 않습니다.

7주의할 점과 실무 메모

  • 오케스트레이터 출력은 신뢰하지 않는 입력처럼 검사합니다. ID 중복과 빈 지시도 운영 코드에서는 추가로 확인합니다.
  • 워커 수가 입력에 따라 늘 수 있으므로 호출 수·토큰·지연 상한을 계획 단계 뒤에 적용합니다.
  • 워커나 종합 응답의 answer가 비면 명시적으로 실패합니다. 다른 필드의 문자열을 최종 답으로 대신 사용하지 않습니다.

8정리와 다음 절

  • 중앙 모델이 현재 입력을 세 하위 작업으로 동적으로 나눴습니다.
  • 코드는 계획에 나온 수만큼 워커를 실행하고 결과를 종합했습니다.
  • 동적 분해에는 작업 수 상한과 출력 검사가 필요합니다.
