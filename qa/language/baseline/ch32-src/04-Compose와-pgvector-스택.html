1학습 목표

  • Compose 서비스, 네트워크, 볼륨의 역할을 설명할 수 있습니다.
  • app과 PostgreSQL 사이의 준비 순서를 healthcheck로 제어할 수 있습니다.
  • pgvector 확장과 HNSW 인덱스 생성을 SQL로 확인할 수 있습니다.

2이 내용을 배우는 이유

웹 API 하나만 실행해도 실제 서비스는 데이터베이스, 네트워크, 영속 저장소를 함께 사용합니다. 명령을 각각 기억하면 이름과 포트가 쉽게 어긋납니다. Docker Compose는 여러 컨테이너의 구성을 YAML 파일 하나에 적고 하나의 프로젝트로 관리합니다. Ch31의 데이터베이스 운영 개념을 실제 서비스 구성에 연결하는 단계입니다.

3앞에서 배운 내용

Ch31에서는 PostgreSQL, 트랜잭션, 인덱스와 pgvector를 배웁니다. 이 챕터는 Ch31 파일을 복사하지 않고 `init.sql`에 필요한 최소 스키마를 독립적으로 제공합니다. Ch12에서 사용한 벡터 검색 개념은 `vector(3)` 열과 HNSW 인덱스로 다시 나타납니다. 3절의 최적화 이미지는 Compose의 app 서비스 빌드 입력이 됩니다.

4핵심 개념

쉬운 예

공연 무대에는 배우뿐 아니라 조명, 음향, 출입 순서가 필요합니다. Compose 서비스(service)는 함께 관리할 컨테이너 하나의 설정입니다. 이 실습에는 `app`과 `db` 두 서비스가 있습니다. Compose는 프로젝트 전용 기본 네트워크를 만들고 서비스 이름 `db`를 내부 호스트 이름으로 제공합니다. app은 호스트의 `localhost`가 아니라 `db:5432`로 PostgreSQL에 연결합니다. 이름 있는 볼륨(named volume) `pgdata`는 DB 컨테이너를 다시 만들어도 데이터를 별도로 보관합니다. `depends_on.condition: service_healthy`는 DB 프로세스가 생성되었다는 사실을 넘어 `pg_isready` 검사가 성공할 때까지 app 시작을 기다립니다. 초기 SQL은 vector 확장, 3차원 벡터 열, HNSW 인덱스와 한 행의 예제 데이터를 만듭니다.

5실행 예제

먼저 `docker compose config --format json`으로 실제 컨테이너를 만들기 전에 서비스 이름을 검사합니다. 실패 셀은 스택이 없는 상태에서 `/ready` 연결이 거부되는지 확인합니다. 수정 셀은 `up --build --wait`로 두 서비스를 만들고 `/ready`와 `/vector-count`를 호출합니다. DB 안에서는 pgvector 0.8.6과 `course_vectors_embedding_hnsw` 인덱스를 직접 조회합니다. 실습 끝에는 `down --volumes`로 이 챕터 전용 데이터만 제거합니다.

6일부러 실패해 보기

실제 실행에서 db가 먼저 healthy가 되었고 app도 이어서 healthy가 되었습니다. `/ready`는 `status=ready`, `/vector-count`는 1을 반환했습니다. SQL 조회에서는 pgvector 0.8.6과 기본 키, HNSW 인덱스가 확인됐습니다. 이 구성은 시작 순서를 안정화하지만 실행 중 DB 연결이 끊겼을 때 app이 자동으로 모든 요청을 복구한다는 뜻은 아닙니다. 연결 재시도, 트랜잭션 경계, 마이그레이션 동시 실행은 Ch31의 운영 설계와 함께 결정해야 합니다.

7주의할 점과 실무 메모

  • 호스트 포트는 `127.0.0.1:18332`로 제한했습니다. DB 포트는 호스트에 공개하지 않아 app을 통해서만 접근합니다.
  • 초기화 SQL은 새 볼륨을 처음 만들 때 실행됩니다. 이미 데이터가 있는 볼륨의 스키마 변경은 Alembic 같은 마이그레이션 도구로 관리합니다.
  • `down --volumes`는 이 실습 데이터까지 삭제합니다. 운영 데이터가 있는 프로젝트에서는 실행 전에 프로젝트명과 볼륨 대상을 반드시 확인합니다.

8정리와 다음 절

  • Compose는 app, db, 네트워크와 볼륨을 한 프로젝트로 관리합니다.
  • service_healthy 조건은 DB 준비 검사가 성공한 뒤 app을 시작하게 합니다.
  • 실제 스택에서 pgvector 0.8.6, HNSW 인덱스와 한 개의 벡터 행을 확인했습니다.

다음 학습과 이어지는 지점 — 5절에서는 같은 스택의 환경변수, 시크릿, 상태 검사와 로그를 운영자가 읽을 수 있는 신호로 정리합니다.

9복습 문제

문제 1

app의 DB_HOST가 localhost가 아니라 db인 이유는 무엇인가요?

정답과 해설 — Compose 내부 네트워크에서 서비스 이름이 다른 컨테이너의 호스트 이름으로 해석되기 때문입니다.

문제 2

service_started와 service_healthy의 차이는 무엇인가요?

정답과 해설 — started는 컨테이너 시작만 확인하고, healthy는 정의한 상태 검사가 성공할 때까지 기다립니다.

문제 3

pgdata 볼륨은 무엇을 분리하나요?

정답과 해설 — DB 컨테이너의 수명과 PostgreSQL 데이터 파일의 수명을 분리합니다.

문제 4

기존 볼륨에서 init.sql을 변경하면 자동 적용된다고 볼 수 있나요?

정답과 해설 — 그렇지 않습니다. 초기화 스크립트는 새 데이터 디렉터리에서 실행되므로 기존 스키마는 마이그레이션으로 변경합니다.
