1학습 목표

  • HTTP 429 응답을 통제된 로컬 서버에서 재현할 수 있습니다.
  • 지수 백오프와 지터를 적용해 재시도 간격을 분산할 수 있습니다.
  • 큐와 세마포어로 동시 실행 수를 제한할 수 있습니다.

2이 내용을 배우는 이유

모델 API에는 분당 요청 수와 분당 토큰 수 같은 제한이 있습니다. 요청이 한꺼번에 몰리면 서버는 HTTP 429로 현재 요청을 받을 수 없다고 알릴 수 있습니다. 즉시 같은 요청을 반복하면 다시 제한에 걸리고 전체 서비스의 부하도 커집니다. 재시도 시점과 동시에 처리할 작업 수를 조절해야 합니다.

3앞에서 배운 내용

Ch 16에서는 호출 한도와 재시도 함수를 직접 만들었습니다. Ch 30에서는 FastAPI 비동기 요청 처리를 배웠습니다. 이번 절은 그 두 내용을 운영 흐름으로 연결합니다. 실제 제공자에게 의도적으로 429를 만들지 않고, 로컬 HTTP 서버가 처음 두 요청에만 429를 반환하도록 구성합니다.

4핵심 개념

문이 닫혔을 때 줄을 정리하기

입장 제한이 걸린 장소 앞에서 모든 사람이 동시에 문을 두드리면 혼잡이 커집니다. 대기열은 도착한 순서를 보관하고, 동시성 제한은 안에 들어가는 사람 수를 정합니다. 백오프는 거절된 요청이 다시 시도하기 전 기다리는 시간을 늘립니다.

Rate limit
일정 시간 동안 허용되는 요청이나 토큰의 최대량입니다.
HTTP 429
요청이 너무 많아 현재 처리할 수 없음을 나타내는 상태 코드입니다.
지수 백오프(exponential backoff)
재시도 횟수가 늘수록 대기 시간을 배수로 늘리는 방법입니다.
지터(jitter)
여러 클라이언트의 재시도 시점이 겹치지 않도록 더하는 작은 무작위 지연입니다.
세마포어(semaphore)
동시에 실행할 수 있는 작업 수를 제한하는 동기화 도구입니다.

5실행 예제

표준 라이브러리의 HTTPServer를 로컬 주소에서 실행합니다. 서버는 첫 두 요청에 429, 세 번째부터 200을 반환합니다. 외부 API의 Rate limit을 소모하지 않으면서 실제 HTTP 오류 처리 코드를 실행할 수 있습니다.

6일부러 실패해 보기

재시도 없는 코드는 첫 429를 그대로 호출자에게 전달합니다. 수정 코드에서는 429만 재시도하며, 다른 HTTP 오류는 숨기지 않습니다. 대기 시간은 0.05 × 2^attempt에 작은 지터를 더해 계산합니다. 실제 운영에서는 응답 헤더의 재시도 안내와 SDK의 내장 재시도 정책도 함께 확인합니다.

7주의할 점과 실무 메모

  • 실패한 요청도 Rate limit 계산에 포함될 수 있으므로 무제한 재시도를 두지 않습니다.
  • 응답을 이미 일부 처리한 비멱등 작업은 같은 요청을 다시 실행하기 전에 중복 효과를 확인합니다.
  • 큐가 계속 길어지면 대기 시간 상한, 취소, 우선순위 정책이 필요합니다.
  • 세마포어의 적정 값은 계정 등급, 모델, 평균 입력 토큰에 따라 달라집니다.

8정리와 다음 절

  • 429는 즉시 반복하지 않고 제한된 횟수로 백오프합니다.
  • 지터는 여러 요청이 같은 시점에 다시 몰리는 현상을 줄입니다.
  • 큐와 세마포어는 유입량과 동시 실행량을 분리합니다.

다음 학습과 이어지는 지점 — 마지막 절에서는 처리량뿐 아니라 대화당 누적 비용을 p95로 관리하고 요청 전 예산 가드를 적용합니다.

9복습 문제

문제와 해설

1. 429 직후 같은 간격으로 모든 클라이언트가 재시도하면 어떤 문제가 생기나요?

재시도 시점이 다시 겹쳐 제한과 부하가 반복될 수 있습니다.

2. 지터의 역할은 무엇인가요?

재시도 시점을 조금씩 다르게 만들어 요청 집중을 줄입니다.

3. 이번 실습이 실제 제공자의 과부하를 재현했다고 말할 수 있나요?

말할 수 없습니다. 통제된 로컬 서버에서 HTTP 429 처리만 재현했습니다.
