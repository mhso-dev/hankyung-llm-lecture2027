1학습 목표
이 절을 마치면 과정의 개발 기반 학습이 뒤의 프로젝트에 어떻게 이어지는지 설명할 수 있습니다.
실행 전에 결과를 예상하고 실제 출력과 비교한 기록을 남길 수 있습니다.
입력 하나를 바꾼 결과로 확인한 사실과 아직 확인하지 않은 사실을 구분할 수 있습니다.
2이 내용을 배우는 이유
처음 프로그램을 실행하면 화면에 숫자나 문장이 나타납니다. 그 결과가 의도한 것인지 판단하려면 실행 전에 무엇을 만들려 했는지 알아야 합니다. 예를 들어 3,000원짜리 상품 두 개의 합계는 6,000원입니다. 프로그램이 오류 없이 3,002원을 출력했더라도 가격을 올바르게 계산한 것은 아닙니다. 실행되었다는 사실과 원하는 일을 했다는 사실을 각각 확인하는 습관을 첫 장부터 연습합니다.
프로그램에 적힌 명령을 코드(code)라고 합니다. 초반에는 코드를 직접 읽고 입력하며, 바꾼 줄이 결과에 미치는 영향을 설명합니다. 다른 사람이 작성한 코드를 사용하는 경우에도 입력·처리·결과를 스스로 확인할 수 있어야 합니다. 답을 빠르게 얻는 데만 집중하면 예상하지 못한 결과를 어디서부터 살펴볼지 알기 어렵습니다. 지금 쌓는 실행 기록은 이후 더 긴 프로그램을 읽고 수정할 때 원인을 찾는 근거가 됩니다.
3앞에서 배운 내용
이 절은 첫 학습이므로 프로그래밍 경험을 요구하지 않습니다. 파일을 내려받고 폴더에서 찾는 방법을 알고 있으면 시작할 수 있습니다. 아직 실행 도구가 없다면 지금은 설명과 저장된 출력을 읽습니다. 다음 절의 설치 안내와 3절의 실행 환경 준비를 마친 뒤 이 절의 노트북으로 돌아와 직접 실행합니다. HTML은 내용을 읽고 코드를 복사하는 데 사용하는 교재이며, 화면의 복사 버튼이 코드를 실행하지는 않습니다.
준비된 환경이 있다면 이 절 상단의 노트북 내려받기로 파일을 저장합니다. 파일 이름 끝의 .ipynb는 설명과 실행 코드를 함께 담은 노트북 파일임을 나타냅니다. 파일을 열었을 때 글과 코드가 여러 칸으로 나뉘어 보이면 맞는 화면입니다. 파일 내용이 중괄호와 따옴표로만 보이면 텍스트 편집기로 열린 상태이므로 2절의 Jupyter 확장 준비를 확인합니다.
4핵심 개념
예상한 금액과 영수증을 비교합니다
가게에서 상품 두 개를 살 때 머릿속으로 계산한 금액과 영수증을 비교할 수 있습니다. 프로그램에서도 실행 전에 예상값을 적고 실행 후 표시된 값과 비교합니다. 영수증의 합계만 보는 대신 상품 수량과 단가도 확인하는 것처럼, 프로그램이 받은 값과 계산한 값을 함께 살펴봅니다. 이 비유에서는 예상 금액이 확인 기준이며 실제 영수증이 실행 결과에 해당합니다.
이번 절에서 사용하는 다섯 가지 말
프로그램(program)은 컴퓨터가 수행할 작업을 적은 것입니다. 입력(input)은 작업에 사용하는 값이며, 여기서는 단가 3,000과 수량 2입니다. 출력(output)은 실행 결과로 밖에 보여 주는 값입니다. 계산한 합계 6,000을 화면에 표시하면 출력이 됩니다. 셀(cell)은 노트북에서 설명이나 코드를 담는 한 칸입니다. 검증(verification)은 결과가 미리 정한 조건에 맞는지 확인하는 일입니다. 이번 조건은 ‘단가에 수량을 곱한 값이 합계와 같다’입니다.
계산한 값을 기억하는 것과 화면에 표시하는 것은 별개의 동작입니다. 코드에서 이름에 값을 저장해도 화면에 아무것도 나타나지 않을 수 있습니다. 이 교재는 확인할 값을 print로 표시합니다. 처음에는 괄호 안의 값을 화면에 보여 주는 명령으로 읽으면 충분합니다. 코드에서 *는 곱셈을 뜻하고, =는 오른쪽 값을 왼쪽 이름에 저장할 때 사용합니다. 이름과 값의 관계는 Ch 2에서 자세히 배웁니다.
과정에서 이 연습이 이어지는 순서
학습 구간직접 확인할 일다음 학습에 필요한 이유
Ch 1~5 개발 기반파일과 실행 환경을 준비하고, 코드를 읽고 수정하며 데이터를 다룹니다.결과가 달라졌을 때 코드와 입력을 찾아 확인할 수 있어야 합니다.
Ch 6~8 생성 모델 활용 준비첫 외부 API 호출과 입력 구성 방법을 배웁니다.이 장에서는 호출하지 않습니다. 먼저 개발 도구를 사용할 준비를 합니다.
Ch 9~17 검색과 평가문서를 검색하고 결과를 측정한 뒤 개선합니다.Ch 11의 측정을 Ch 12의 조정보다 먼저 배웁니다.
Ch 18~29 도구와 에이전트실행 조건을 살펴보고 도구를 연결합니다.흐름을 모델이 정하는 학습은 Ch 20부터 시작합니다.
Ch 30~41 서비스와 종합 구현프로그램을 서비스로 만들고 함께 검토하며 완성합니다.앞에서 만든 실행·수정·검증 습관을 프로젝트 전체에 적용합니다.
표는 앞으로 무엇을 배우는지 확인하는 과정 지도입니다. 지금 새 도구 이름을 암기할 필요는 없습니다. 첫 두 주에는 파이썬과 협업의 기반을 먼저 익히며, 이 장의 실행 예제는 숫자·파일·개발 도구만 사용합니다. 뒤의 내용을 미리 구현하는 대신 현재 단계에서 만든 파일을 다시 실행할 수 있는지 확인합니다.
확인할 점 — 파란 단계는 학생이 정한 실행 순서, 노란 단계는 결과를 확인하는 행동을 나타냅니다. 3,000×2를 예상한 뒤 6,000이라는 출력과 비교하고, 수량만 3으로 바꿔 9,000인지 다시 확인하는 순서로 읽습니다.
5실행 예제
첫 실행에서는 코드를 바꾸지 않습니다. 6,000이라는 예상값을 먼저 적고 셀을 위에서 아래로 실행합니다. 앞 셀이 만든 값을 다음 셀이 사용하므로 중간 셀만 실행하면 필요한 값이 없을 수 있습니다. 셀 왼쪽의 입력 번호는 실행된 순서를 나타내며, 교재의 번호를 외우거나 코드에 복사할 필요는 없습니다.
첫 셀의 import sys는 Python에 포함된 sys 기능을 현재 노트북에서 사용하겠다는 뜻입니다. sys.version_info는 실행 중인 Python의 버전 정보를 반환합니다. 뒤의 [:2]는 그 정보에서 앞의 두 값인 주 버전과 부 버전만 고릅니다. == (3, 12)는 고른 두 값이 3과 12인지 비교하며, 비교 결과는 참을 뜻하는 True 또는 거짓을 뜻하는 False가 됩니다. 이 문법은 Ch 2에서 차례로 배우므로, 지금은 “현재 실행기가 Python 3.12인가?”라는 질문을 코드로 적은 것으로 읽습니다.
price = 3000에서 price는 값을 다시 사용할 수 있도록 붙인 이름이고, =는 오른쪽 값 3000을 왼쪽 이름에 저장합니다. print(...)는 괄호 안에서 만든 문장을 화면에 출력합니다. 문자열 앞의 f와 중괄호는 저장한 값을 문장 안에 넣는 표기입니다. 예를 들어 f"{price}원"은 3000원이라는 문장을 만듭니다. 함수, 문자열, 이름에 관한 규칙은 Ch 2에서 배우지만, 이 절에서는 각 줄의 역할을 구분할 수 있어야 합니다.
assert total == prediction은 total과 prediction이 같은지 검사합니다. 두 값이 같으면 별도 문장을 출력하지 않고 다음 줄로 넘어가며, 다르면 실행을 멈추고 AssertionError를 표시합니다. 따라서 출력이 없다는 사실만 보지 말고, 그 앞의 print 결과와 셀이 오류 없이 끝났는지를 함께 확인합니다.
확인할 점 — 기본 수량 2의 합계와 변경한 수량 3의 합계를 비교합니다. 단가는 그대로 두었습니다. assert 뒤 조건이 참이면 오류가 발생하지 않습니다. 출력 문장과 확인 조건을 함께 읽고 어느 계산을 확인했는지 설명합니다.
6실험 결과 해석
이번 실행에서는 같은 단가에 수량만 바꿨습니다. 3,000에 2를 곱하면 6,000이고, 3을 곱하면 9,000입니다. 두 조건의 차이는 수량 하나이므로 합계가 3,000만큼 증가한 이유를 설명할 수 있습니다. 입력을 여러 개 동시에 바꾸면 어떤 값이 결과 차이를 만들었는지 따로 확인해야 합니다. 처음에는 비교 조건을 하나씩 정하는 편이 원인을 추적하기 좋습니다.
이 결과로 모든 계산 프로그램이 올바르다고 판단할 수는 없습니다. 할인·환불·배송비가 포함된 계산은 실행하지 않았습니다. 이번 실습에서 확인한 것은 정수 단가와 두 수량의 곱셈입니다. 오류를 재현하지 않은 절이므로 실패를 고쳤다고 기록하지 않습니다. 4절에서는 잘못된 연산으로 계산한 실제 결과를 관찰하고 같은 입력에서 수정합니다.
7주의할 점과 실무 메모
실습 기록에는 예상한 값, 실제 출력, 바꾼 입력, 다음에 확인할 것을 남깁니다. ‘잘 됨’만 적으면 무엇이 맞았는지 나중에 확인하기 어렵습니다. ‘단가 3,000과 수량 2에서 출력 6,000을 확인했다’처럼 입력과 결과를 함께 적습니다. 오류가 발생하면 마지막 메시지와 실행한 셀을 기록하고, 이미 확인한 정상 셀을 무작정 여러 군데 바꾸지 않습니다.
저장된 출력은 교재를 만들 때 실행한 기록입니다. 파일을 열어 출력이 보인다는 사실만으로 자신의 컴퓨터에서도 실행된 것은 아닙니다. 직접 셀을 실행하고 새 입력 번호와 출력을 확인해야 합니다. 실습 중 값이 예상과 다르게 남았다면 실행 프로그램을 다시 시작한 후 처음부터 순서대로 실행합니다. 이 초기화 방법은 3절에서 배웁니다.
8정리와 다음 절
실행 전에 입력과 예상 결과를 정합니다.실행 후 실제 출력이 조건에 맞는지 확인합니다.값 하나를 바꾸고 같은 확인 과정을 반복합니다.
다음 학습과 이어지는 지점 — 다음 절은 이 과정을 자신의 컴퓨터에서 수행하도록 편집기와 터미널을 준비합니다. 이번 절에서 남긴 예상값과 실제값 기록은 4절의 계산 오류를 설명하는 데 다시 사용합니다.
9복습 문제
1. 입력과 출력은 각각 무엇인가요? · 기초
단가 3,000과 수량 2는 입력이며, 화면에 표시한 합계 6,000은 출력입니다. 어떤 값을 사용했는지와 무엇을 보여 주었는지를 구분합니다.
2. 수량을 3으로 바꾸면 어떤 값을 예상하나요? · 적용
단가를 3,000으로 유지하면 9,000을 예상합니다. 실행 전에 예상값을 적고, 실행 후 출력과 비교합니다.
3. 오류 없이 3,002가 출력되면 올바른 합계인가요? · 적용
아닙니다. 두 상품의 총금액은 6,000이어야 합니다. 실행 가능 여부와 계산 결과의 정확성은 별도로 확인해야 합니다.
4. 두 번 확인한 결과로 할인 계산도 맞다고 말할 수 있나요? · 분석
말할 수 없습니다. 할인 조건은 입력하거나 실행하지 않았습니다. 할인 규칙과 예상값을 정한 별도 사례가 필요합니다. 해석 범위를 다시 읽고 실행한 조건만 기록합니다.

VS Code에서 실습 폴더와 터미널을 열고 현재 위치를 확인할 수 있습니다.
같은 파일 이름이 현재 위치에 따라 다른 대상을 가리키는 이유를 설명하고 경로 오류를 수정할 수 있습니다.
2이 내용을 배우는 이유
파일을 만들었는데 프로그램이 찾지 못하는 경우가 있습니다. 파일 이름이 맞아도 명령을 실행한 위치가 다르면 다른 폴더에서 파일을 찾을 수 있습니다. 개발 도구 설치를 마쳤다는 것은 앱 아이콘이 생겼다는 사실만으로 판단하기 어렵습니다. 편집기에 연 폴더, 명령을 입력하는 창, 실제로 읽는 파일이 서로 어떻게 연결되는지 확인해야 첫 스크립트를 실행할 수 있습니다.
이 절은 도구의 역할을 나눠 이해하고, 파일을 찾는 기준을 확인하는 데 집중합니다. 설치할 앱은 공식 안내에서 내려받고, 설치 뒤 새 터미널을 열어 명령이 인식되는지 확인합니다. 운영체제마다 설치 화면과 기본 명령이 다르므로 자신의 환경에 해당하는 안내만 따라갑니다. Windows 안내를 macOS 창에 그대로 입력하는 방식으로 섞지 않습니다.
3앞에서 배운 내용
1절에서는 예상 결과와 실제 출력을 비교하는 학습 규칙을 정했습니다. 이번에는 ‘내가 어느 폴더에서 어떤 파일을 열려 하는가’를 예상한 뒤 실제 결과를 확인합니다. 기존 코드 파일은 필요하지 않습니다. 실습 노트북은 임시 폴더에 예제 파일을 직접 만들며, 개인 문서나 기존 프로젝트를 변경하지 않습니다.
아직 노트북을 실행할 수 없다면 아래 설치와 터미널 설명을 먼저 읽고 3절의 준비 순서를 마칩니다. 이후 이 절의 실행 예제로 돌아옵니다. 설치 안내는 도구를 준비하는 절차이며, 노트북 출력은 준비된 환경에서 실제로 실행한 경로 실습의 기록입니다. 다른 운영체제의 설치 화면까지 실행 검증한 기록으로 읽지 않습니다.
4핵심 개념
주소의 출발점을 먼저 확인합니다
‘옆방의 책’이라는 설명은 지금 있는 방에 따라 다른 책을 가리킵니다. 파일에도 이름을 찾는 출발점이 필요합니다. 이 비유에서 현재 있는 방은 현재 작업 폴더이며, ‘옆방의 책’은 상대적인 위치를 적은 경로입니다. 프로그램은 화면에 보이는 폴더를 사람처럼 추측하지 않고, 정해진 기준 위치에서 파일을 찾습니다.
편집기(editor)는 파일 내용을 읽고 수정하는 앱이며, 이 과정은 VS Code를 사용합니다. 터미널(terminal)은 글자로 명령을 입력하고 결과를 읽는 창입니다. 셸(shell)은 그 명령을 해석해 실행하는 프로그램입니다. Windows에서는 PowerShell, macOS에서는 zsh를 기준으로 설명합니다. 현재 작업 폴더(current working directory)는 명령이 파일을 찾기 시작하는 위치입니다.
경로(path)는 폴더와 파일의 위치를 글자로 적은 값입니다. 절대 경로(absolute path)는 파일 시스템의 기준 위치부터 적고, 상대 경로(relative path)는 현재 위치 같은 지정된 기준에서 적습니다. hello.py라고만 쓰면 이름은 짧지만 기준 위치를 알아야 실제 파일을 찾을 수 있습니다. 다른 컴퓨터에서는 사용자 이름과 폴더 위치가 달라질 수 있으므로 수업 파일은 제공된 폴더 구조와 상대 경로로 사용합니다.

VS Code 설치 페이지에서 자신의 운영체제와 CPU에 맞는 설치본을 고릅니다. macOS는 Apple silicon과 Intel 구분을 확인하고, Windows는 내려받은 설치 파일의 안내를 따릅니다. 설치 후 VS Code를 열어 왼쪽 Extensions 화면에서 Microsoft가 제공하는 Python과 Jupyter 확장을 설치합니다. Python Debugger도 설치되어 있는지 확인합니다. 확장은 편집기에 기능을 추가하는 구성 요소이며, Python을 실행하는 프로그램 자체는 다음 절에서 준비합니다.
uv는 공식 설치 페이지의 Standalone installer에서 자신의 운영체제 탭을 선택합니다. 해당 페이지의 명령을 Windows에서는 PowerShell, macOS와 Linux에서는 터미널에 입력해 설치합니다. 설치가 끝나면 열려 있던 터미널을 닫고 새 창을 엽니다. 새로 설치한 명령의 위치가 기존 창에는 반영되지 않을 수 있기 때문입니다. uv --version으로 버전 문자열이 출력되는지 확인합니다. 명령을 찾지 못한다는 메시지가 나오면 Python 코드 오류로 해석하지 말고 uv 설치 경로와 새 터미널 여부를 확인합니다.
Git과 Docker Desktop의 설치 파일도 표의 공식 페이지에서 받습니다. Docker Desktop은 운영체제 버전과 가상화 지원 등 추가 조건이 있으므로 5절의 운영체제별 설명을 함께 읽습니다. Docker 준비가 지연되더라도 이 절의 파일 경로 실습에는 Docker를 사용하지 않으므로 진행할 수 있습니다. 설치를 마친 도구와 아직 준비 중인 도구를 따로 기록합니다.
폴더를 열고 명령을 입력합니다
파일 탐색기 또는 Finder에서 연습용 폴더 course-ch01을 만듭니다. 이미 같은 폴더가 있다면 내용을 먼저 확인하고 새 빈 폴더를 사용합니다.
VS Code에서 File → Open Folder로 이 폴더를 엽니다. 왼쪽 파일 목록의 맨 위에 폴더 이름이 표시되는지 확인합니다.
Terminal → New Terminal을 선택합니다. Windows에서는 PowerShell인지, macOS에서는 zsh인지 터미널의 프로필 이름을 확인합니다.
PowerShell에서는 Get-Location, macOS·Linux에서는 pwd로 현재 위치를 확인합니다. 마지막 폴더 이름이 course-ch01인지 읽습니다.
PowerShell에서는 Get-ChildItem, macOS·Linux에서는 ls로 폴더 안의 파일을 확인합니다. 빈 폴더라면 사용자 파일 목록이 없는 것이 정상입니다.
다른 위치라면 cd 뒤에 이동할 폴더 경로를 적습니다. 공백이 포함된 경로는 따옴표로 감쌉니다. 경로를 추측해서 입력하기보다 파일 탐색기에서 정확한 위치를 확인합니다. 터미널 맨 앞의 사용자 이름이나 $, > 같은 안내 표시는 입력하는 명령에 포함하지 않습니다. VS Code에서 폴더를 바꾼 뒤 기존 터미널을 계속 사용하는 경우에는 현재 위치도 다시 확인합니다.
확인할 점 — 초록색은 폴더와 파일을, 파란색은 파일을 찾는 동작을 나타냅니다. 파일 이름이 같아도 기준 폴더가 달라지면 빨간 실패 경로에 도달할 수 있습니다. 그림의 폴더 이름과 실제 실습에서 만든 파일의 위치를 비교합니다.
5실행 예제
노트북에서 사용하는 Path는 경로를 다루는 Python의 기본 기능입니다. TemporaryDirectory는 연습용 임시 폴더를 만드는 기능입니다. 지금은 내부 구현을 암기하지 않고, 셀 앞 설명을 따라 어느 폴더와 파일을 만드는지 확인합니다. 임시 폴더의 실제 이름은 컴퓨터마다 달라질 수 있으므로 출력에서는 학습에 필요한 파일 이름과 결과를 중심으로 확인합니다.
from pathlib import Path는 Python 기본 기능인 pathlib에서 Path라는 도구만 가져옵니다. Path(temporary_folder.name)처럼 이름 뒤에 괄호를 붙이면 도구를 호출합니다. 괄호 안의 값은 호출에 전달하는 인자(argument)이며, 호출이 반환하는 결과를 workspace라는 이름에 저장합니다. 여기서 반환된 결과는 경로 문자열을 다루기 편하게 감싼 Path 객체입니다.
workspace / "practice"의 /는 이 코드에서 나눗셈이 아닙니다. Path 객체 뒤에 폴더나 파일 이름을 연결해 새 경로를 만듭니다. 이 줄만으로 실제 폴더가 생기지는 않습니다. 다음 줄의 project.mkdir()가 경로에 해당하는 폴더를 만들고, project.is_dir()는 그 위치가 폴더인지 확인해 True 또는 False를 반환합니다. 경로를 표현하는 일, 폴더를 만드는 일, 존재를 확인하는 일을 서로 구분합니다.
write_text는 첫 번째 인자의 글을 파일에 저장하며 encoding="utf-8"은 글자를 바이트로 바꾸는 규칙을 지정합니다. read_text는 같은 규칙으로 파일을 읽어 문자열을 반환합니다. 메서드(method)는 message_file.write_text(...)처럼 어떤 값 뒤에 점을 붙여 호출하는 기능입니다. 점 앞의 경로가 작업 대상이고 괄호 안의 값이 작업에 필요한 인자입니다.
객체는 관련된 값과 기능을 함께 담은 결과입니다. 점 뒤에 괄호 없이 적은 temporary_folder.name은 그 객체가 가진 폴더 이름이라는 값을 읽습니다. 이런 값을 속성(attribute)이라고 합니다. project.mkdir()는 경로 객체의 폴더 생성 기능을 실행합니다. 객체에 속한 호출 가능한 기능을 메서드(method)라고 하며, 여기서는 이름 뒤 괄호가 실행을 나타냅니다.
확인할 점 — 예제 파일을 만든 위치와 읽기에 사용한 경로를 비교합니다. 텍스트를 읽는 read_text와 파일이 존재하는지 확인하는 is_file는 서로 다른 작업입니다. 파일이 있다는 사실을 확인한 뒤 본문도 읽어 어떤 파일인지 확인합니다.
6일부러 실패해 보기
같은 파일 이름을 유지한 채 기준 폴더를 잘못 지정하면 파일을 찾지 못합니다. 실습에서는 실제 읽기 동작에서 발생한 FileNotFoundError만 포착해 기록합니다. 뒤의 수정 셀에서는 파일을 새로 만드는 대신 파일이 있는 기준 폴더로 경로를 고쳐 읽습니다. 오류 메시지는 ‘파일이 컴퓨터 어디에도 없다’는 뜻이 아니라 ‘요청한 위치에서 찾지 못했다’는 뜻으로 해석해야 합니다.
try 아래에는 실패할 수 있는 읽기 동작을 둡니다. 그 읽기에서 FileNotFoundError가 발생하면 except FileNotFoundError as error 아래로 이동하며, 발생한 오류를 error라는 이름으로 확인할 수 있습니다. else는 예상한 오류가 발생하지 않았을 때 실행됩니다. 이 구조는 Ch 2에서 자세히 배우며, 여기서는 잘못된 경로의 실제 오류만 구분해 기록하기 위한 준비 코드입니다.
7주의할 점과 실무 메모
파일 이름의 대소문자와 확장자도 확인합니다. 운영체제와 파일 시스템 설정에 따라 대소문자 처리 방식이 다를 수 있습니다. 자신의 컴퓨터에서 우연히 열렸다는 이유로 대문자와 소문자를 섞지 않습니다. Windows에서 확장자를 숨긴 상태라면 hello.py.txt를 hello.py로 착각할 수 있으므로 파일 탐색기의 확장자 표시를 확인합니다.
노트북은 작업 위치가 편집기에 연 폴더와 같다고 가정하지 않습니다. 이번 예제는 임시 폴더 변수를 명시적으로 사용해 경로 관계를 확인합니다. 실제 프로젝트에서는 터미널의 현재 위치와 파일 목록을 함께 확인합니다. 삭제 명령으로 문제를 해결하려 하기 전에 요청한 경로를 읽고, 맞는 폴더로 이동하는 것만으로 해결되는지 확인합니다.

2이 내용을 배우는 이유
같은 코드를 실행했는데 한 컴퓨터에서는 되고 다른 컴퓨터에서는 필요한 기능을 찾지 못할 수 있습니다. 코드 파일만 같아도 실행하는 Python 버전과 설치한 패키지가 다르면 결과가 달라질 수 있기 때문입니다. 먼저 어떤 Python으로 실행하는지와 어디에 패키지를 설치하는지를 정합니다. 이후 문제가 생겼을 때 코드와 환경 중 무엇이 다른지 나눠 확인할 수 있습니다.
이 과정은 Python 3.12를 사용합니다. 버전 번호를 단순히 외우는 대신, 터미널과 노트북에서 실제 실행한 버전을 확인합니다. 컴퓨터에 Python이 여러 개 있어도 실습마다 필요한 환경을 선택할 수 있습니다. 프로그램 전체를 삭제하고 재설치하기 전에 현재 프로젝트가 어느 환경을 사용하고 있는지 살펴보는 것이 첫 확인 순서입니다.

처음 실습 묶음을 받았다면 압축을 푼 뒤 위 폴더를 VS Code의 Open Folder로 엽니다. Python 확장과 Jupyter 확장은 설치되어 있어야 합니다. 이 장에는 외부 모델 서비스 계정이나 API 키가 필요하지 않습니다. 준비 단계에서는 Python과 실습 도구를 내려받으므로 인터넷 연결이 필요할 수 있습니다.
4핵심 개념
작업별 준비물을 따로 둡니다
서로 다른 실습의 준비물을 각각의 보관함에 넣으면 어느 실습에서 쓰는지 구분할 수 있습니다. 프로그램의 실행 환경도 프로젝트마다 분리합니다. 다만 실제 보관함처럼 컴퓨터 전체를 나누는 것은 아닙니다. 가상환경은 주로 Python 실행 위치와 패키지 설치 위치를 구분하며, 같은 컴퓨터의 파일과 운영체제를 사용합니다. 어떤 코드든 안전하게 실행해 주는 격리 장치라고 생각하지 않습니다.
인터프리터(interpreter)는 Python 코드를 읽고 실행하는 프로그램입니다. 프로젝트(project)는 하나의 작업에 필요한 코드와 설정을 모은 단위입니다. 패키지(package)는 설치해서 사용하는 Python 기능의 묶음입니다. 가상환경(virtual environment)은 프로젝트별로 Python 패키지 설치 위치를 구분하는 실행 환경입니다. 이 과정은 프로젝트 폴더 안의 .venv를 사용합니다.
의존성(dependency)은 프로그램을 실행하는 데 필요한 다른 패키지입니다. 잠금 파일(lockfile)은 설치할 패키지와 선택된 버전을 기록해 다시 준비할 때 참고하는 파일입니다. uv에서는 uv.lock을 사용합니다. 커널(kernel)은 노트북 코드를 실행하고 변수를 기억하는 프로그램입니다. VS Code에서 파일 실행에 사용할 Python을 골랐더라도 노트북의 커널은 별도로 확인합니다.
프로젝트 안의 세 파일을 읽습니다
파일 또는 폴더담고 있는 내용학생이 확인할 점
pyproject.toml프로젝트 정보와 필요한 Python·패키지 조건입니다.Python 3.12와 노트북 실행 도구 조건을 확인합니다. 처음 실습에서는 수정하지 않습니다.
uv.lock의존성을 계산한 뒤 선택한 패키지 버전입니다.직접 편집하지 않고 제공된 파일로 환경을 준비합니다.
.venv현재 컴퓨터에서 실제 사용할 실행 환경입니다.준비 명령을 실행한 뒤 생성되는지 확인합니다. 다른 컴퓨터에 그대로 복사하지 않습니다.
프로젝트 설정과 잠금 파일이 같으면 설치할 버전을 맞추는 데 도움이 됩니다. 그래도 운영체제와 CPU, 외부 파일까지 모두 같아지는 것은 아닙니다. 설치 오류가 있다면 운영체제와 Python 버전, 실패한 패키지 이름을 함께 확인합니다. 설치된 가상환경 전체 대신 설정과 잠금 파일을 공유하고, 각 컴퓨터에서 환경을 다시 만드는 이유입니다.
확인할 점 — 초록색 환경 A와 B는 각각의 실행 위치를 갖습니다. 노란 확인 단계는 두 환경 폴더의 위치가 서로 다른지와 각 실행이 가상환경 안에서 이루어지는지를 비교합니다. 그림은 패키지 설치 위치를 나누는 원리를 설명하며 운영체제 전체가 두 개 생겼다는 뜻이 아닙니다.
5실행 예제
노트북을 열기 전에 한 번 준비합니다
VS Code에서 제공된 labs/part1/ch01-development-environment 폴더를 엽니다. Terminal → New Terminal로 새 창을 열고 현재 폴더와 파일 목록을 확인합니다.
터미널에서 uv sync --locked를 실행합니다. 잠금 파일의 버전을 사용해 프로젝트에 필요한 도구를 준비합니다. 설치가 끝날 때까지 기다린 뒤 오류 없이 명령 입력 상태로 돌아왔는지 확인합니다.
uv run python --version을 실행해 Python 3.12로 시작하는 출력인지 확인합니다. 마지막 패치 번호는 설치된 환경에 따라 다를 수 있습니다.
VS Code 명령 팔레트를 열고 Python: Select Interpreter를 선택합니다. Windows·Linux는 Ctrl+Shift+P, macOS는 Cmd+Shift+P로 명령 팔레트를 엽니다. 현재 프로젝트의 .venv를 고릅니다.
notebooks에서 원하는 절의 .ipynb를 열고, 오른쪽 위 Select Kernel → Python Environments에서 같은 프로젝트의 .venv를 선택합니다. 표시되지 않으면 VS Code의 환경 목록을 새로 고친 뒤 다시 선택합니다.
첫 코드 셀을 선택하고 Shift+Enter를 누릅니다. 실행 중 표시가 사라진 뒤 출력을 읽고 다음 셀로 이동합니다. 1절과 2절의 노트북도 같은 준비 환경에서 실행할 수 있습니다.
uv sync는 프로젝트의 실행 환경을 준비하는 명령이고, --locked는 제공된 잠금 파일을 변경하지 않고 사용할 수 있는지 확인하는 옵션입니다. 설정과 잠금 파일이 서로 맞지 않아 실패하면 옵션을 지우기 전에 pyproject.toml과 uv.lock이 실습 폴더에 함께 있는지 확인합니다. uv run은 프로젝트 환경에서 뒤에 적은 명령을 실행합니다. 이 방식에서는 매번 별도의 활성화 명령을 입력할 필요가 없습니다.
터미널의 python 명령과 uv run python이 같은 실행 파일을 사용한다고 가정하지 않습니다. 현재 셸 설정에 따라 앞의 명령은 다른 Python을 실행할 수 있습니다. 이 교재의 터미널 예제는 uv run으로 실행 환경을 명확히 지정합니다. 노트북에서는 선택한 커널이 실제로 Python 3.12인지 첫 셀의 결과로 확인합니다.
서로 다른 두 환경을 실제로 확인합니다
다음 노트북은 uv venv로 연습용 환경 두 개를 만듭니다. 2절에서 설치한 uv가 노트북에서도 인식되어야 합니다. 프로젝트의 .venv와 구분되는 임시 폴더에 환경을 준비합니다. sys는 실행 중인 Python 정보를 읽고, subprocess는 별도의 프로그램을 실행하는 기능입니다. 보조 문법은 주석을 따라 읽고, 어떤 위치를 비교하는지와 결과의 뜻에 집중합니다.
import는 이미 준비된 기능을 현재 코드에서 사용할 수 있게 가져옵니다. sys, os, shutil, subprocess, pathlib, tempfile은 Python과 함께 제공되는 표준 라이브러리이므로 이 노트북에서 별도 설치하지 않습니다. 반면 프로젝트의 pyproject.toml에 적힌 제삼자 패키지는 uv가 내려받아 가상환경에 설치합니다. 가져오는 동작인 import와 컴퓨터에 패키지를 추가하는 설치를 구분합니다.
shutil.which("uv")는 셸이 실행할 수 있는 uv 명령의 위치를 찾습니다. 찾으면 경로 문자열을, 찾지 못하면 값이 없음을 뜻하는 None을 반환합니다. assert uv is not None은 위치를 찾았는지 확인하고, 찾지 못했다면 안내 문장과 함께 실행을 멈춥니다. 이 확인을 먼저 하는 이유는 뒤의 가상환경 생성 실패를 코드 오류로 오해하지 않기 위해서입니다.
subprocess.run([...], check=True)에서 대괄호 안의 목록은 터미널에 입력할 명령과 옵션을 순서대로 적은 것입니다. 첫 값은 실행할 프로그램이며 뒤의 값은 그 프로그램에 전달할 인자입니다. check=True는 명령이 실패 상태를 반환하면 Python 실행도 오류로 멈추게 합니다. capture_output=True는 별도 프로그램의 출력을 화면에 바로 표시하지 않고 반환 결과의 stdout에 저장하며, text=True는 그 출력을 글자로 읽습니다.
운영체제에 따라 가상환경 안의 Python 파일 위치가 다르므로 os.name == "nt"일 때 Windows 경로를, 그렇지 않을 때 macOS·Linux 경로를 선택합니다. sys.prefix는 현재 실행 환경의 위치이고 sys.base_prefix는 기반 Python의 위치입니다. 둘이 다르다는 비교 결과가 True이면 해당 실행이 가상환경 안에서 이루어졌다고 해석합니다. 이 비교는 환경의 위치를 확인할 뿐, 설치된 모든 패키지가 원하는 버전이라는 뜻은 아닙니다.
is not None은 값이 없는 상태인 None이 아닌지 확인합니다. assert 조건, "안내 문장"에서 쉼표 뒤 문자열은 조건이 거짓일 때 오류와 함께 보여 줄 설명입니다. 마지막 검사에 쓰는 and는 양쪽 조건이 모두 참일 때 참이 됩니다. 따라서 환경 위치가 서로 다르면서 두 실행 모두 가상환경 내부인지 함께 확인합니다.
확인할 점 — True는 비교 조건이 참이라는 뜻입니다. 어떤 비교에 대한 결과인지 출력 문구를 함께 읽습니다. 실제 사용자 폴더 경로를 외우지 않고, 환경 A와 B가 서로 다른 위치인지와 각 환경이 기반 Python의 위치와 다른지를 확인합니다.
6실험 결과 해석
두 환경은 같은 기반 Python을 사용할 수 있지만 환경의 위치는 서로 다릅니다. 이 실험은 환경을 새로 만들고 각각의 Python을 실행해 환경 폴더의 위치 정보를 확인합니다. 폴더 이름만 두 개 만들어 놓고 가상환경이 분리되었다고 설명하는 것과는 확인 범위가 다릅니다. 출력에서 환경 A와 B가 각각 가상환경인지 확인하고, 두 환경 폴더가 서로 다른지 비교합니다.
이번 예제는 제삼자 패키지의 서로 다른 버전을 설치하지 않았습니다. 그러므로 실제 패키지 충돌을 재현하거나 해결했다고 기록하지 않습니다. 패키지 설치 위치가 분리되는 원리를 확인했으며, 특정 패키지의 호환성은 그 패키지를 설치하고 사용하는 별도 실행이 필요합니다. 연습용 임시 환경과 현재 노트북을 실행하는 프로젝트의 .venv도 구분합니다.
7주의할 점과 실무 메모
환경을 선택한 뒤에도 이미 실행 중인 커널이 이전 상태를 기억할 수 있습니다. VS Code에서 Restart Kernel을 선택하면 노트북의 기존 변수가 사라집니다. 다시 첫 셀부터 실행합니다. 저장된 코드와 출력 파일은 커널 재시작만으로 삭제되지 않습니다. 실행 중인 변수, 저장한 코드, 저장된 출력이 각각 무엇인지 구분하면 이전 실행의 숫자를 새 결과로 오해하는 일을 줄일 수 있습니다.
패키지를 설치했는데 찾지 못한다면 설치한 환경과 실행 중인 커널을 확인합니다. 다른 Python에 다시 설치하는 일을 반복하기 전에 인터프리터와 커널이 같은 프로젝트를 가리키는지 살펴봅니다. .venv를 이동하거나 이름을 바꾼 경우에는 기존 경로를 기억한 설정이 맞지 않을 수 있으므로 제공된 설정으로 새 위치에서 환경을 준비하고 다시 선택합니다.

프로젝트의 Python 버전과 패키지 조건을 확인합니다.uv로 환경을 준비하고 VS Code의 인터프리터와 커널을 각각 선택합니다.환경 위치를 비교한 결과와 패키지 호환성 검증을 구분합니다.

9복습 문제
1. 가상환경은 무엇을 구분하나요? · 기초
프로젝트가 사용하는 Python 실행 위치와 패키지 설치 위치를 구분합니다. 운영체제 전체를 복제하거나 임의 코드 실행을 안전하게 만드는 장치로 해석하지 않습니다.
2. 설치 후 노트북에서 패키지를 찾지 못하면 무엇을 확인하나요? · 적용
패키지를 설치한 환경과 선택한 노트북 커널이 같은지 확인합니다. 편집기의 인터프리터를 고른 것만으로 커널도 같아졌다고 판단하지 않습니다.
3. 새 컴퓨터에 .venv만 복사하면 충분한가요? · 적용
충분하지 않습니다. 경로와 운영체제 조건이 다를 수 있으므로 프로젝트 설정과 잠금 파일을 사용해 새 컴퓨터에서 환경을 준비합니다.
4. 이번 결과로 패키지 버전 충돌을 해결했다고 말할 수 있나요? · 분석
말할 수 없습니다. 두 환경의 Python을 실행해 위치 관계를 확인했지만, 제삼자 패키지의 충돌은 실행하지 않았습니다. 실험 결과 해석의 범위를 다시 확인합니다.

이 절을 마치면 VS Code의 화면 디버깅과 노트북에서 실행하는 pdb 시연의 역할 차이를 설명할 수 있습니다.
2이 내용을 배우는 이유
터미널에 한 줄씩 입력한 코드는 창을 닫으면 다시 찾기 어렵습니다. 여러 줄을 실행하다가 결과가 잘못되어도 어떤 줄에서 값이 달라졌는지 확인하기 어렵습니다. 이제 코드를 파일로 저장하여 다시 실행하고, 디버거로 실행을 잠시 멈춘 뒤 중간 값을 살펴볼 차례입니다.
이 절의 예제는 상품 가격과 개수로 합계를 계산합니다. 프로그램은 오류 메시지 없이 끝나지만 합계가 틀립니다. 요구와 다르게 동작하는 코드의 원인을 논리 오류(logic error)라고 합니다. 논리 오류는 Python이 작성된 식 자체는 정상적으로 계산했기 때문에 문법 오류보다 발견하기 어려울 수 있습니다. 중단점에서 멈추고 변수를 확인하면 코드가 실제로 어떤 값을 사용했는지 차례대로 좁혀 갈 수 있습니다.

편집기는 글자를 입력하고 파일을 저장하는 도구이며, 터미널은 명령을 전달하고 결과를 표시하는 도구입니다. 편집기에서 저장한 hello.py를 터미널에서 uv run python hello.py로 실행하면 두 도구가 하나의 작업 흐름으로 이어집니다.
4핵심 개념
비유 — 계산표를 한 줄씩 확인합니다
영수증의 합계가 예상과 다르면 마지막 숫자만 반복해서 보지 않습니다. 가격, 수량, 계산식 순서로 살펴보며 처음 잘못된 지점을 찾습니다. 디버거도 이와 비슷합니다. 프로그램을 특정 줄에서 잠시 멈추고, 그 시점까지 만들어진 값을 확인한 뒤 다음 줄을 실행합니다.
파일 이름과 확장자를 함께 저장합니다
Python 스크립트(script)는 Python 명령을 순서대로 적어 둔 텍스트 파일입니다. 파일 이름 뒤의 .py는 이 파일이 Python 소스 코드임을 나타내는 확장자입니다. 제공 파일 hello.py 다운로드에는 price = 3000, count = 2, total = price * count, 합계 출력문이 들어 있습니다. 파일을 VS Code에서 열어 같은 내용을 저장합니다. 저장하지 않은 변경은 터미널에서 실행한 파일에 포함되지 않으므로, 실행 전에 탭의 점 표시가 사라졌는지 확인합니다.
uv run python hello.py에서 hello.py는 터미널의 현재 작업 폴더를 기준으로 찾습니다. 터미널의 현재 폴더와 파일을 저장한 폴더가 다르면 파일을 찾을 수 없다는 메시지가 나타납니다. VS Code 탐색기에서 프로젝트 폴더를 열고 그 폴더에서 새 터미널을 만들면 경로를 맞추기 수월합니다.
세 가지 확장과 인터프리터를 준비합니다
VS Code의 확장은 편집기에 기능을 추가합니다. 이 과정에서는 Microsoft가 제공하는 Python, Python Debugger, Jupyter 확장을 설치합니다. Python 확장은 Python 환경 탐색과 코드 편집 기능을 제공하고, Python Debugger 확장은 실행을 멈추고 값을 살펴보는 기능을 제공하며, Jupyter 확장은 .ipynb 노트북 셀을 실행합니다.
인터프리터(interpreter)는 Python 코드를 읽어 실행하는 프로그램입니다. 명령 팔레트에서 Python: Select Interpreter를 실행하거나 상태 표시줄의 Python 버전을 선택한 뒤, 프로젝트 안의 .venv를 고릅니다. 선택한 환경은 일반 Python 파일의 실행, 디버깅, 코드 분석에 사용됩니다. 목록에 보이지 않으면 Python Environments: Refresh All Environment Managers를 실행해 다시 탐색합니다.
노트북 커널(kernel)은 노트북 셀의 코드를 실행하고 변수 상태를 유지하는 프로세스입니다. 노트북 오른쪽 위의 Select Kernel에서도 같은 .venv를 골라야 합니다. Python 파일용 인터프리터를 선택했더라도 노트북 커널이 자동으로 같아진다고 가정하지 않습니다. 첫 노트북을 열 때 두 위치를 각각 확인합니다.
중단점에서 실행 전 상태를 읽습니다
디버거(debugger)는 실행을 잠시 멈추고 현재 줄과 변수 값을 확인하는 도구입니다. 중단점(breakpoint)은 디버거가 실행을 멈출 줄을 표시한 지점입니다. 줄 번호 왼쪽 여백을 누르면 빨간 점이 나타납니다. 실패 비교에서는 total = price + count 줄에 중단점을 둡니다. F5를 눌렀을 때 실행 구성을 묻는 메뉴가 나타나면 Python Debugger: Python File을 선택합니다. 활성 편집기의 .py 파일이 선택한 인터프리터에서 시작되고, 디버거는 중단점 줄을 실행하기 직전에 멈춥니다. 현재 줄은 노란색으로 표시되고, Variables 패널(변수 창)에는 이미 실행된 줄에서 만들어진 price와 count가 보입니다. 아직 실행하지 않은 대입문의 새 total은 그 줄의 결과로 만들어지지 않은 상태입니다.
F10은 다음 줄로 한 단계 진행하는 Step Over입니다. 현재 줄을 실행한 뒤 다음 줄 앞에서 다시 멈춥니다. 이때 Variables 패널에서 total을 확인하면 덧셈으로 만든 값이 나타납니다. +나 *처럼 계산 방법을 나타내는 기호를 연산자(operator)라고 합니다. 계산식의 연산자를 곱셈으로 바꾸고 다시 실행하면 같은 입력에서 합계가 달라집니다. launch.json은 실행 인자나 다른 인터프리터 같은 별도 설정이 필요할 때 사용하므로, 이번 첫 파일에는 만들지 않습니다.
도식 — 멈춘 줄과 만들어진 값을 구분합니다
파란색은 학생이 파일을 저장하고 F5·F10을 누르는 행동, 초록색은 선택한 .venv와 디버거, 노란색은 현재 줄과 Variables 패널에서 확인하는 값, 빨간색은 덧셈 때문에 생긴 잘못된 합계를 뜻합니다. 화살표는 저장한 파일이 선택한 인터프리터에서 실행되고, 중단점에서 멈춘 뒤 한 줄씩 진행되는 순서를 보여 줍니다.
도식에서 노란색 현재 줄은 이미 실행한 줄이 아니라 다음에 실행할 줄입니다. 따라서 빨간색 잘못된 합계는 그 줄에서 F10으로 진행한 뒤 확인합니다. 이 순서를 알면 “중단점에 멈췄는데 왜 새 값이 아직 보이지 않는가?”라는 혼동을 줄일 수 있습니다.
5실행 예제
먼저 제공된 hello.py와 같은 정상 계산을 노트북에서 실행합니다. 가격 3000원과 개수 2를 변수에 저장하고 곱셈으로 합계를 계산한 뒤 출력합니다. 파일을 실행할 때도 uv run python hello.py를 입력하여 같은 계산 결과를 확인합니다.
노트북의 첫 셀은 개인 파일을 건드리지 않도록 임시 폴더와 두 파일 경로를 준비합니다. bug_file = workspace / "price_bug.py"는 파일의 위치만 정하며 아직 파일을 만들지 않습니다. 실제 파일은 뒤 셀의 bug_file.write_text(...)가 만듭니다. 삼중 큰따옴표 """는 여러 줄의 Python 코드를 하나의 문자열로 담기 위해 사용합니다. 그 문자열을 파일에 저장하면 별도로 실행할 수 있는 스크립트가 됩니다.
subprocess.run([sys.executable, bug_file], ...)은 현재 노트북을 실행하는 Python의 위치인 sys.executable로 방금 만든 파일을 실행합니다. 반환된 결과의 stdout에는 스크립트가 출력한 글이 담깁니다. strip()은 출력 끝의 줄바꿈을 제거하고, int(...)는 숫자 모양의 문자열을 계산 가능한 정수로 바꿉니다. 따라서 bug_total은 화면 문장이 아니라 숫자 3002이며, 다음 assert로 예상한 잘못된 결과와 비교할 수 있습니다.
확인할 점 — 2026년 9월 9일 새 커널 실행에서 정상 예제는 총액: 6000원을 출력했습니다. 가격 3000과 개수 2의 곱셈 결과와 같은지 확인합니다. 이 단계는 저장한 파일과 노트북의 기본 계산이 같은지 확인하는 실행입니다.
6일부러 실패해 보기
pdb는 Python에 포함된 줄 단위 디버거입니다. 준비 문자열에서 b 4는 4번 줄에 중단점을 설정하고, c는 그 위치까지 계속 실행합니다. p price, p count, p total은 각 이름의 현재 값을 출력하며, q는 디버거를 종료합니다. 이 명령들을 input=debug_commands로 전달해 사람이 터미널에서 입력하는 순서를 노트북이 같은 조건으로 재현합니다.
출력 정리 부분의 대괄호 코드는 여러 출력 줄 중 숫자인 줄만 고르는 준비 코드입니다. observed[-3:]는 고른 결과의 마지막 세 값을 뜻합니다. 이 문법은 Ch 2에서 목록과 반복을 배운 뒤 직접 작성합니다. 지금은 경로와 디버거 안내 문장을 제외하고 가격, 개수, 합계만 학습 출력으로 남기기 위해 사용했다는 역할을 확인합니다.
Before에서는 가격과 개수를 더한 price + count를 사용합니다. 두 값 모두 숫자이므로 Python은 오류 메시지를 내지 않고 계산을 마칩니다. 그러나 “단가에 수량을 곱한다”는 요구와 계산식이 맞지 않아 잘못된 총액: 3002원이 출력되었습니다. 노트북의 실제 pdb 시연에서도 price = 3000, count = 2, total = 3002가 관찰되었습니다.
After에서는 입력값을 그대로 유지하고 연산자만 price * count로 바꿉니다. 같은 가격과 개수를 사용하므로 결과 차이는 연산자 수정에서 생깁니다. 새 커널 실행에서 수정한 총액: 6000원이 출력되었고, 예상 합계와 실제 합계가 같은지도 검사했습니다. 오류 메시지가 없다는 사실과 프로그램의 답이 옳다는 판단은 서로 다른 확인 절차가 필요합니다.
확인할 점 — 노트북의 pdb 출력은 Python 디버거가 줄 단위로 상태를 관찰하는 과정을 보여 줍니다. VS Code의 빨간 중단점, 노란 현재 줄, Variables 패널은 노트북 출력에 포함되지 않으므로 같은 실패 코드를 VS Code에서 직접 열어 화면으로 확인합니다.
7주의할 점과 실무 메모
저장한 파일을 실행합니다. 편집기 탭에 저장되지 않은 변경 표시가 있으면 터미널과 디버거가 이전 내용을 실행할 수 있습니다.
현재 폴더를 확인합니다. 파일을 찾지 못하면 코드보다 먼저 터미널의 현재 폴더와 파일 위치가 같은지 확인합니다.
인터프리터와 커널을 각각 확인합니다. Python 파일은 선택한 인터프리터를 사용하고, 노트북은 선택한 커널을 사용합니다. 두 위치에서 모두 프로젝트의 .venv를 고릅니다.
중단점의 줄은 실행 전입니다. Variables 패널의 값이 예상보다 하나 이전 단계라면 F10으로 현재 줄을 실행한 뒤 다시 확인합니다.
단축키가 운영체제와 키보드 설정에 따라 다를 수 있습니다. F5나 F10이 동작하지 않으면 Run and Debug 화면의 버튼이나 명령 팔레트를 사용합니다.
노트북의 pdb와 VS Code 화면을 같은 검증으로 취급하지 않습니다. 전자는 Python 디버거의 상태 관찰을 코드로 보여 주며, 후자는 편집기에서 직접 확인해야 합니다.

9복습 문제
1번 문제와 해설
[하] 1. Python 파일을 hello가 아니라 hello.py로 저장하는 이유는 무엇입니까?
정답과 해설 — .py 확장자는 파일이 Python 소스 코드임을 도구와 사용자에게 알려 줍니다. 실행 전에는 저장 여부와 파일이 있는 폴더도 함께 확인합니다.
2번 문제와 해설
[중] 2. VS Code에서 프로젝트의 .venv를 인터프리터로 선택했는데 노트북이 다른 Python을 사용합니다. 무엇을 확인해야 합니까?
정답과 해설 — 노트북 오른쪽 위의 Select Kernel에서 .venv를 별도로 선택합니다. Python 파일용 인터프리터와 노트북 커널은 서로 다를 수 있습니다.
3번 문제와 해설
[중] 3. total = price + count 줄의 중단점에서 멈췄을 때 새 total이 아직 보이지 않는 이유는 무엇입니까?

이 절을 마치면 Docker의 클라이언트와 데몬을 구분하고, docker version에서 어느 쪽이 준비되지 않았는지 확인할 수 있습니다.
이 절을 마치면 자신의 운영체제에 맞는 Docker Desktop 공식 설치 문서를 찾아 필수 조건을 확인할 수 있습니다.

2이 내용을 배우는 이유
4절까지 만든 hello.py는 한 파일이지만, 이후에는 여러 파일을 수정하고 이전 상태와 비교해야 합니다. Git은 어떤 파일이 달라졌는지 기록하는 도구입니다. 한편 뒤의 과정에서는 다른 컴퓨터에서도 같은 실행 조건을 준비해야 합니다. Docker는 필요한 프로그램과 설정을 묶은 실행 환경을 만드는 데 사용합니다.
이번 절의 목표는 두 도구를 깊이 사용하는 것이 아닙니다. Git은 현재 폴더를 저장소로 준비하고 상태를 읽는 데까지 다룹니다. Docker는 설치 파일을 임의로 내려받지 않고 운영체제별 공식 안내를 확인하며, 명령을 입력할 수 있는 상태와 실제 실행 서비스가 준비된 상태를 구분합니다. Git의 브랜치와 협업은 뒤의 실습에서, 컨테이너 설계와 배포는 Ch 32에서 자세히 배웁니다.
3앞에서 배운 내용
2절에서 명령이 발견되는지와 실행이 성공했는지를 구분했습니다. 3절에서는 프로젝트마다 Python 버전과 패키지를 분리했습니다. 4절에서는 hello.py를 저장하고 실행했습니다. 이 절은 같은 원리를 개발 도구의 준비 상태에 적용합니다. 명령 이름이 존재하는지, 현재 폴더가 저장소인지, Docker의 실행 서비스가 응답하는지를 각각 확인합니다.
진단 노트북은 실제 프로젝트를 바꾸지 않도록 임시 폴더에서 Git 저장소를 만듭니다. 노트북이 끝나면 임시 폴더는 정리됩니다. Docker Desktop 설치는 운영체제 설정과 이용 조건을 확인해야 하므로 노트북이 대신 설치하지 않습니다.
4핵심 개념
비유 — 변경 기록과 준비된 작업대
문서를 여러 차례 수정할 때 파일 이름을 최종, 진짜최종처럼 늘리는 대신, 변경 이력을 한곳에 기록하면 어느 부분이 달라졌는지 찾기 쉽습니다. Git이 이 기록을 맡습니다. Docker는 필요한 도구가 놓인 작업대의 설계와 실행을 담당합니다. 작업대 설계도가 있어도 실제 작업대를 펼치지 않았다면 사용할 수 없습니다. Docker 명령줄 도구가 설치되어 있어도 실행 서비스가 시작되지 않은 상태가 이와 비슷합니다.
Git과 GitHub를 구분합니다
Git
컴퓨터의 폴더에서 파일 변경 이력을 기록하고 비교하는 버전 관리 프로그램입니다. 인터넷 연결 없이도 새 저장소를 만들고 상태를 확인할 수 있습니다.
저장소(repository)
Git이 변경 이력을 관리하는 프로젝트 폴더입니다. git init을 실행하면 현재 폴더에 Git 관리 정보가 생기며, 일반 작업 파일과 함께 상태를 추적할 수 있습니다.
GitHub
Git 저장소를 인터넷에 보관하고 다른 사람과 검토·협업할 수 있게 하는 서비스입니다. Git을 설치했다고 GitHub 계정이 자동으로 생기지 않으며, git init만으로 파일이 GitHub에 전송되지도 않습니다.
git status는 현재 저장소에서 무엇이 달라졌는지 보여 줍니다. 아직 기록 대상으로 추가하지 않은 파일은 추적하지 않은 파일(untracked files)로 표시됩니다. 이 상태는 오류가 아니라 Git이 새 파일을 발견했다는 뜻입니다. 이번 절에서는 임시 폴더에 파일 하나를 만들고 상태 표시가 바뀌는 과정을 관찰합니다. 커밋과 원격 저장소 전송은 다음 학습에서 다룹니다.
Docker의 설치와 실행 상태를 구분합니다
클라이언트(client)
사용자가 입력한 docker 명령을 받아 Docker의 실행 서비스에 요청하는 명령줄 프로그램입니다.
데몬(daemon)
백그라운드에서 요청을 받고 이미지와 컨테이너를 관리하는 Docker의 실행 서비스입니다. docker version의 Server 정보가 이 서비스와 통신한 결과입니다.
이미지(image)
프로그램과 실행에 필요한 파일을 묶어 둔 읽기 전용 실행 설계입니다.
컨테이너(container)
이미지를 바탕으로 실제 실행한 격리된 프로세스입니다. 이 절에서는 뜻과 준비 상태만 확인하며, 제작과 배포는 Ch 32에서 다룹니다.
docker --version이 출력되면 클라이언트 명령을 찾았다는 뜻입니다. 이것만으로 데몬이 실행 중이라고 판단할 수 없습니다. Docker Desktop을 시작한 뒤 docker version을 실행하여 클라이언트에 해당하는 Client 구역과 데몬에 해당하는 Server 구역이 모두 나타나는지 확인합니다. 설치본이 Docker Desktop CLI를 지원하면 docker desktop status로 상태를 볼 수 있습니다. 해당 하위 명령이 없으면 Docker Desktop 앱을 연 뒤 docker version으로 확인합니다.
운영체제별 공식 설치 페이지를 사용합니다
Docker Desktop의 지원 운영체제와 필요한 메모리, 가상화 조건은 제품이 갱신되면서 달라질 수 있습니다. Windows는 WSL 2와 하드웨어 가상화, 지원 Windows 빌드를 확인합니다. macOS는 Apple silicon과 Intel 중 자신의 칩에 맞는 설치본 및 지원되는 macOS 범위를 확인합니다. Linux는 지원 배포판, KVM, QEMU, systemd, 데스크톱 환경을 확인합니다. 아래 참고 자료의 공식 운영체제별 페이지에서 현재 조건을 확인한 뒤 설치합니다.
조직과 교육 환경에 적용되는 이용 조건도 최신 공식 안내에서 확인합니다. 이 교재는 특정 조직의 사용 권한이나 비용을 판정하지 않습니다. 설치 전에 자신의 운영체제, 장치 관리 정책, 계정 권한을 확인해야 합니다.
도식 — 명령 발견과 실제 준비를 따로 확인합니다
파란색은 학생이 버전과 상태 명령을 입력하는 행동, 초록색은 Git·Docker 클라이언트와 Docker 데몬, 노란색은 출력에서 확인할 저장소 상태와 Client·Server 구역, 빨간색은 명령을 찾지 못했거나 Server가 응답하지 않는 상태를 뜻합니다. Git 경로는 임시 저장소의 파일 상태로 이어지고, Docker 경로는 클라이언트 확인 뒤 데몬 응답 확인으로 이어집니다.
도식의 Docker 경로가 두 단계인 이유는 설치 확인과 실행 확인이 서로 다른 질문이기 때문입니다. Client만 보이면 명령줄 도구는 준비되었지만 데몬과의 통신은 확인되지 않았습니다. Server까지 보이면 현재 터미널에서 데몬에 요청을 보낼 수 있습니다.
5실행 예제
첫 셀의 shutil.which("git")는 터미널에서 git을 입력했을 때 실행할 프로그램의 위치를 찾습니다. 결과가 None이면 명령을 찾지 못한 상태입니다. git_command is not None은 위치를 찾았는지 비교하여 True 또는 False를 만듭니다. 설치 파일이 있다는 사실만으로 명령 실행까지 성공한다고 단정하지 않기 때문에, 다음 셀에서 git --version의 종료 상태를 다시 확인합니다.
if는 조건이 참일 때 들여쓴 코드만 실행하고, else는 조건이 거짓일 때 다른 코드를 실행합니다. Git이 없는 컴퓨터에서 Git 명령을 무리하게 호출하지 않고 안내를 출력하기 위해 이 구조를 사용합니다. git_version.returncode == 0은 명령이 운영체제에 성공 상태를 반환했는지 확인합니다. 여기서 0은 명령이 정상 종료되었다는 관례이며, Git의 버전 번호를 뜻하지 않습니다.
subprocess.run의 cwd=repository는 그 명령만 임시 저장소 폴더를 현재 작업 폴더로 사용하게 합니다. git init은 그 폴더 안에 Git 관리 정보를 준비하고, git status --short는 파일 상태를 짧은 형식으로 반환합니다. 새 파일 앞의 ??는 Git이 파일을 발견했지만 아직 추적 대상으로 등록하지 않았다는 표시입니다. 파일을 만들었다는 사실, Git이 발견했다는 사실, 변경 이력에 기록했다는 사실은 서로 다른 단계입니다.
Docker 확인도 같은 순서를 따릅니다. docker --version은 명령을 보내는 클라이언트 프로그램이 응답하는지 확인합니다. 이어지는 docker version --format "{{.Server.Version}}"은 요청을 처리하는 서버인 데몬의 버전만 요청합니다. timeout=10은 10초 안에 응답하지 않으면 계속 기다리지 않도록 제한합니다. 이때 발생하는 TimeoutExpired를 따로 처리하므로, 응답 지연을 성공이나 명령 없음으로 잘못 기록하지 않습니다.
노트북은 Python에서 외부 명령을 호출하여 현재 환경을 점검합니다. 먼저 Git과 Docker 명령을 찾을 수 있는지 확인합니다. Git은 임시 폴더를 만들고 git init을 실행한 뒤, 파일 생성 전후의 git status --short 결과를 비교합니다. Docker는 설치를 변경하지 않고 버전과 응답 가능 여부만 확인합니다.
마지막에는 Python, uv, 가상환경, Git, Docker 클라이언트, Docker 데몬의 여섯 항목을 같은 표에 표시합니다. 이 표는 현재 컴퓨터에서 관찰한 준비 상태를 정리하는 자가 점검표입니다. 과정의 공식 평가 점수나 자격 판정이 아닙니다.
server.returncode == 0은 명령이 성공 상태로 마쳤는지 확인합니다. server.stdout.strip()은 받은 출력의 앞뒤 공백과 줄바꿈을 제거합니다. bool(...)은 남은 글자가 있으면 True, 빈 문자열이면 False로 바꿉니다. and로 두 조건을 연결했으므로 명령이 성공하고 버전 글자도 있어야 서버가 응답했다고 판정합니다.
확인할 점 — Git 임시 저장소에서 파일을 만들기 전에는 짧은 상태 출력에 새 파일이 없고, 파일을 만든 뒤에는 아직 추적하지 않은 파일 표시가 나타나는지 확인합니다. Docker는 Client와 Server를 나누어 읽습니다. 설치하지 않은 도구나 시작하지 않은 데몬은 실패를 숨기지 않고 보완 항목으로 표시됩니다.
6실험 결과 해석
여섯 항목은 서로 다른 준비 조건을 확인합니다. Python과 uv 항목은 과정의 명령을 실행할 기반을, 가상환경 항목은 프로젝트별 환경 분리를 확인합니다. Git 항목은 변경 상태를 기록할 도구를, Docker 클라이언트와 데몬 항목은 이후 컨테이너 실습을 시작할 준비를 각각 확인합니다. 한 항목의 통과가 다른 항목의 통과를 대신하지 않습니다.

# 도구 설치와 터미널
현재 작업 폴더와 상대 경로의 관계를 임시 폴더에서 확인합니다. 폴더는 파일과 다른 폴더를 담는 공간이고, 경로는 그 위치를 글자로 나타낸 값입니다. 상대 경로는 기준 폴더가 있어야 하나의 실제 위치를 가리킵니다.
## 실행 환경 준비
개인 파일을 바꾸지 않도록 Python이 제공하는 임시 폴더만 사용합니다. `from pathlib import Path`는 경로를 다루는 `Path`를, `from tempfile import TemporaryDirectory`는 임시 폴더를 만드는 기능을 가져옵니다. `TemporaryDirectory()`가 반환한 결과에는 임시 폴더 이름과 정리 기능이 들어 있습니다. `Path(temporary_folder.name)`은 그 이름을 경로 객체로 바꿉니다. `/`는 `Path` 뒤에 폴더 이름을 연결하고, `mkdir()`가 실제 폴더를 만듭니다.
점 뒤에 괄호 없이 쓰는 `temporary_folder.name`은 객체가 가진 폴더 이름이라는 값(속성)을 읽습니다. `project.mkdir()`는 객체에 속한 기능(메서드)을 호출해 폴더를 만듭니다. 객체는 이렇게 관련된 값과 기능을 함께 담은 결과입니다.
## 기본 실행: 상대 경로로 파일 준비
상대 경로 `data/message.txt`는 어느 폴더를 기준으로 하는지에 따라 다른 파일을 가리킵니다. 먼저 `project / "data"`로 경로를 만들고 `mkdir()`로 `data` 폴더를 만듭니다. 다시 `message.txt`를 연결한 뒤 `write_text`로 글을 저장합니다. `encoding="utf-8"`은 한글을 파일의 바이트로 바꾸고 다시 읽을 때 사용할 문자 규칙입니다. `is_file()`은 해당 위치가 파일이면 `True`를 반환합니다.
## 정상 경로 읽기
의도한 `project`를 기준으로 선택하면 파일을 읽을 수 있습니다. `project / relative_path`는 기준 폴더와 `data/message.txt`를 연결해 실제 파일 경로를 만듭니다. `read_text`는 파일 내용을 문자열로 반환하고, `basic_message`가 그 반환값을 저장합니다. 출력에서 저장한 문장과 읽은 문장이 같은지 확인합니다.
## Before: 기준 폴더가 다른 경우
작업 기준을 `workspace`로 잘못 선택하면 같은 상대 경로에서 파일을 찾지 못합니다. `try` 아래에는 실패할 수 있는 읽기를 둡니다. `FileNotFoundError`가 발생하면 `except` 아래가 실행되고 오류의 종류를 출력합니다. `else`는 예상한 오류가 발생하지 않았을 때 실행됩니다. 이 구조는 Ch 2에서 자세히 배우며, 여기서는 경로 오류만 구분해 관찰하기 위해 사용합니다.
## After: 프로젝트 폴더를 기준으로 선택
같은 상대 경로를 `project`에 연결하면 저장한 파일을 읽을 수 있습니다. 파일 이름과 내용은 바꾸지 않고 기준 폴더만 `workspace`에서 `project`로 수정합니다. `cleanup()`은 실습용 임시 폴더를 정리합니다. 출력이 `안녕, 터미널!`인지 확인한 뒤 정리하므로, 읽기 성공과 정리를 한 단계씩 구분할 수 있습니다.

# Python과 가상환경
현재 Python 버전을 확인하고, 서로 구분되는 두 개의 가상환경을 임시 폴더에 만듭니다. 인터프리터는 Python 코드를 읽어 실행하는 프로그램이고, 가상환경은 프로젝트별 Python 실행 위치와 패키지 설치 위치를 구분합니다. 노트북에서는 선택한 커널이 코드를 실행합니다.
## Python 3.12 확인
가상환경을 만들기 전에 현재 커널이 교재의 기준 버전인지 확인합니다. `import sys`는 실행 중인 Python 정보를 읽는 표준 기능을 가져옵니다. `version_info[:2]`는 버전 정보의 앞 두 값인 주 버전과 부 버전을 고르고, `== (3, 12)`는 두 값이 3과 12인지 비교합니다. 결과가 `False`이면 오른쪽 위에서 Python 3.12 커널을 다시 선택합니다.
## 임시 가상환경 두 개 생성
`uv venv`는 지정한 폴더에 Python 가상환경을 만듭니다. `--python 3.12`는 Python 버전을 고정하고, `--no-project`는 현재 프로젝트 설정을 읽지 않고 지정한 폴더에 환경만 만들게 합니다. `shutil.which("uv")`는 실행 가능한 uv 명령의 위치를 찾아 경로를 반환하며, 찾지 못하면 `None`을 반환합니다. `subprocess.run`의 대괄호 안에는 터미널에서 실행할 프로그램과 인자를 순서대로 적습니다. `check=True`는 명령 실패 시 실행을 멈춥니다. 이 실습에서는 추가 패키지를 설치하지 않습니다.
`uv is not None`은 명령 위치가 없는 상태인지 확인하는 식입니다. `None`이 아니면 참입니다. `assert 조건, "안내 문장"`의 쉼표 뒤 문자열은 조건이 거짓일 때 오류에 표시할 설명입니다.
## 각 환경의 Python 실행
운영체제에 맞는 Python 실행 파일을 고른 뒤, 각 환경 안에서 `prefix`가 기본 Python의 `base_prefix`와 다른지 확인합니다. 조건문의 한 줄 표현은 Windows이면 `Scripts/python.exe`, 그렇지 않으면 `bin/python`을 선택합니다. `subprocess.run`의 `-c`는 뒤의 Python 코드를 파일 없이 실행하는 인자입니다. `capture_output=True`는 별도 실행의 출력을 반환 결과의 `stdout`에 저장하고, `text=True`는 그 출력을 글자로 읽습니다. `splitlines()`는 여러 출력 줄을 줄별 목록으로 나눕니다.
## 서로 구분되는지 확인
각 Python이 보고하는 가상환경 위치(`sys.prefix`)가 다르면 각각 구분된 환경입니다. `lines_a[0]`은 첫 번째 결과인 가상환경 여부이고, `lines_a[1]`은 두 번째 결과인 환경 위치입니다. 환경 A와 B의 위치가 다른지, 두 실행이 모두 가상환경 안인지 차례로 확인합니다. 개인 경로는 출력하지 않고 비교 결과만 표시합니다.
마지막 `and`는 양쪽 조건이 모두 참일 때 참이 됩니다. 환경 위치가 서로 다르고 두 실행이 모두 가상환경 안에서 이루어져야 검사를 통과합니다.
## 실험 결과 해석
두 환경은 같은 Python 3.12를 기반으로 만들었지만 각 환경의 `sys.prefix`는 서로 다릅니다. 이 결과는 환경의 실행 위치가 구분되었음을 보여 줍니다. 제삼자 패키지를 설치하지 않았으므로 패키지 버전 충돌을 재현했다고 해석하지 않습니다. 교재 프로젝트를 준비할 때는 `uv sync --locked`로 잠금 파일에 맞는 환경을 만듭니다.

# Git과 Docker 준비
이번 실습은 도구 설치와 실행 준비 상태를 각각 확인합니다. 3절의 Python 3.12 프로젝트 환경을 준비합니다. Git과 Docker가 아직 없으면 해당 실습을 생략하고 미준비 상태를 기록합니다. `import`는 Python에 포함된 기능을 가져옵니다. `shutil.which`는 터미널에서 실행할 수 있는 명령 위치를 찾아 경로를 반환하고, 찾지 못하면 값이 없다는 뜻의 `None`을 반환합니다. 첫 출력은 설치 완료를 단정하지 않고 명령 위치를 발견했는지만 보여 줍니다.
## 1. Git 명령의 실제 응답
명령 위치를 찾는 것과 실제 실행은 구분합니다. `subprocess.run`의 대괄호 안에는 실행할 프로그램과 인자를 순서대로 적습니다. `capture_output=True`는 결과를 변수에 저장하고, `text=True`는 글자로 읽게 합니다. 반환 결과의 `returncode`가 0이면 명령이 성공 상태로 끝났다는 뜻입니다. `if`는 조건이 참일 때 들여쓴 코드를 실행하고, `else`는 거짓일 때 다른 코드를 실행합니다. 이 문법은 Ch 2에서 배우며, 여기서는 Git이 없는 컴퓨터에서도 다음 점검을 계속하기 위해 사용합니다.
## 2. 비어 있는 임시 저장소
실제 프로젝트 대신 새 임시 폴더에서 `git init`을 실행합니다. 저장소는 Git이 파일의 변경 상태와 이력을 관리하는 폴더입니다. `cwd`는 명령이 사용할 현재 작업 폴더를 지정하므로 노트북 폴더가 아니라 새 임시 폴더에서 Git이 실행됩니다. `git status --short`의 출력이 비어 있으면 표시할 변경 파일이 없다는 뜻입니다. `git init`은 관리 정보를 준비할 뿐 파일을 커밋하거나 GitHub로 전송하지 않습니다.
## 3. 파일 하나를 만든 뒤 비교
같은 저장소에 `hello.py` 파일 하나를 추가합니다. 추적은 Git이 파일을 이후 변경 이력의 대상으로 관리하도록 등록하는 일입니다. `??`는 Git이 새 파일을 발견했지만 아직 추적하지 않는다는 표시입니다. 파일을 만들었다는 사실과 커밋을 만들었다는 사실은 다릅니다. 이 셀은 파일 내용을 실행하지 않고 생성 전후의 Git 상태만 비교한 뒤 임시 저장소를 정리합니다.
## 4. Docker 클라이언트 확인
`docker --version`은 클라이언트 프로그램이 응답하는지 확인합니다. 클라이언트는 사용자가 입력한 Docker 명령을 받아 서버에 요청하는 프로그램입니다. 이 명령은 서버에 컨테이너 실행을 요청하지 않습니다. 명령 위치가 있더라도 실행 결과의 `returncode`를 별도로 확인하며, 버전 문자열은 컴퓨터마다 달라질 수 있습니다.
## 5. Docker 데몬 응답 확인
Docker 서버는 요청을 처리하는 데몬(daemon)을 뜻하며, 출력의 Server 항목에 해당합니다. 클라이언트가 응답한 경우에만 데몬의 버전을 요청합니다. `--format`은 전체 정보에서 서버 버전만 선택합니다. `timeout=10`은 10초가 지나면 계속 기다리지 않게 하며, 이때 발생하는 `TimeoutExpired`만 `except`에서 구분해 기록합니다. 서버가 응답하지 않으면 원인을 숨겨 성공으로 표시하지 않습니다.
`server.returncode == 0`은 명령이 성공 상태로 마쳤는지 확인합니다. `server.stdout.strip()`은 받은 출력의 앞뒤 공백과 줄바꿈을 제거합니다. `bool(...)`은 남은 글자가 있으면 `True`, 빈 문자열이면 `False`로 바꿉니다. `and`로 두 조건을 연결했으므로 명령이 성공하고 버전 글자도 있어야 서버가 응답했다고 판정합니다.
## 6. 여섯 가지 준비 상태
Python 버전, uv 응답, 현재 커널의 가상환경 여부, Git, Docker 클라이언트, Docker 서버를 각각 읽습니다. 각 이름에는 `True` 또는 `False`가 저장됩니다. `sys.prefix != sys.base_prefix`는 현재 커널의 실행 위치와 기반 Python의 위치가 다른지 비교합니다. 이는 어떤 가상환경 안에 있다는 사실만 확인하며, 원하는 프로젝트의 `.venv`인지 여부는 3절의 선택 화면과 함께 확인합니다. 아래 결과는 도구 준비 상태이며 A/B 학습 수준을 채점하는 표가 아닙니다.
## 결과를 해석합니다
Git의 변경 상태는 파일 하나의 생성 전후를 비교한 실제 결과입니다. Docker 서버가 미준비이면 Docker Desktop을 시작한 뒤 다시 확인합니다. 서버가 응답해도 이미지 내려받기와 컨테이너 실행을 검증한 것은 아닙니다. 여섯 출력은 서로 다른 질문의 답이므로 한 항목의 `True`가 다른 항목의 준비를 보장하지 않습니다. Python·Git 실습과 Docker 준비를 나눠 기록합니다.

API 이름을 한 번 언급했거나 실행 코드에 넣었다는 이유로 이미 가르친 개념으로 취급하지 않습니다. 예를 들어 `with_structured_output()`을 처음 사용하는 자리라면, 구조화 출력이 필요한 상황과 메서드의 역할, 스키마로 전달하는 것, 호출 뒤 얻는 객체, 실제 모델 실행 시점을 설명한 뒤 기본 호출과 반환값을 함께 읽습니다. `method`나 `include_raw` 같은 선택지는 그 기본 동작을 이해한 다음에 소개합니다.
절을 쓰기 전에 처음 등장하는 개념·문법·함수와 선수 설명의 위치를 확인합니다. “앞에서 배웠습니다”라고 쓰려면 실제 챕터·절에 그 설명이 있어야 합니다. 선택 학습을 건너뛰는 경로에서도 필요한 설명이 남는지 확인합니다. 이전에 소개하지 않았다면 현재 절에서 필요한 범위를 풀어 쓰거나, 선행 절을 먼저 보완하고 정확한 위치를 연결합니다.
처음 보는 코드에는 무엇을 입력하고 어떤 처리를 거쳐 무엇을 얻는지 설명합니다. 괄호·점·대괄호·콜론·화살표 같은 표기와 객체·메서드·속성의 구분도 해당 코드의 독해에 필요하면 예로 풉니다. 정의와 실행이 다른 경우에는 언제 실행되는지도 짚습니다. 준비 셀의 보조 도구는 실습에서 하는 일을 설명하되, 본문의 핵심 개념을 익히기 전에 관련 없는 내부 구현까지 학습하도록 요구하지 않습니다.
설명이 충분한지는 글자 수나 추가 사례 수로 판정하지 않습니다. 검토자는 각 절에서 처음 사용하는 핵심 개념을 골라 **필요한 이유 → 뜻과 표기 → 기본 코드의 흐름 → 출력 해석**이 실제 어디에 설명되어 있는지 기록합니다. 설명 없는 첫 사용이나 존재하지 않는 선수 지식 연결이 남으면 실행·화면 검사가 통과해도 해당 절의 내용 개정은 완료로 표시하지 않습니다.
먼저 한 가지 예를 끝까지 설명해 개념의 동작을 보여 줍니다. 이어서 다른 상황에도 같은 개념이 적용되는 예와, 조건 하나가 달라져 결과가 바뀌는 예를 고릅니다. 예를 들어 구조화 출력은 학습 카드와 주문 정보에 각각 적용하고, 같은 주문 수량을 정수와 문자열로 전달해 검증 방식의 차이를 확인할 수 있습니다. 이름만 바꾼 예제를 여러 개 만드는 것은 개념 보강으로 보지 않습니다.
예시마다 다음 질문에 답하는 설명을 붙입니다. 어떤 입력을 사용했는지, 이번에 바꾼 조건은 무엇인지, 실행 전에 어떤 결과를 예상할 수 있는지, 실제 출력에서 무엇을 확인했는지, 그 결과가 정의와 어떻게 연결되는지를 씁니다. 실패하지 않은 실행도 그대로 해석합니다. 반례를 만들려고 주제와 관계없는 예외를 추가하지 않습니다.
| 예시의 역할 | 구성 방법 | 개념을 확인하는 질문 |
| --- | --- | --- |
| 기본 동작 이해 | 작은 입력의 처리 과정을 단계별로 풉니다. | 입력이 어떤 과정을 거쳐 이 결과가 되었나요? |
| 다른 상황에 적용 | 목적이나 데이터 구조가 다른 사례에 적용합니다. | 상황이 바뀌어도 유지되는 원리는 무엇인가요? |
| 가까운 개념 비교 | 같은 입력에 두 방법을 적용합니다. | 같은 결과처럼 보여도 처리 기준이 어떻게 다른가요? |
| 경계와 반례 확인 | 조건 하나를 바꾸고 결과를 관찰합니다. | 어느 조건에서 앞의 설명이 더 이상 성립하지 않나요? |
모든 절에 같은 수의 사례나 같은 소제목을 강제로 넣지 않습니다. 다만 하나의 짧은 실행만 있는 절은 다른 상황에 적용할 수 있는지와 혼동하기 쉬운 개념을 충분히 설명했는지 다시 검토합니다. 절의 분량은 강의 시수와 기존 집필 규격을 따르되, 문자 수를 채웠다는 이유로 설명이 충분하다고 판정하지 않습니다.
옵션은 예시를 이해하거나 결과 차이를 설명하는 데 필요한 것부터 다룹니다. 표를 쓴다면 이름·적용 대상·값의 의미·예시에 미치는 영향을 연결합니다. 라이브러리의 기본값, 교재에서 선택한 값, 특정 제공자가 지원하는 값은 구분합니다. “권장 설정”은 어떤 입력과 학습 목적에서 선택한 것인지 설명하고, 아직 실행하지 않은 방법은 실행 결과처럼 서술하지 않습니다.
공식 문서는 API의 의미와 지원 범위를 확인하는 근거로 사용합니다. 교재의 설명 순서는 학생이 해결할 질문과 예시의 연결을 따라 구성합니다. 참고 노트북은 예시의 전개 방식과 설명 깊이를 비교하는 자료이며, 그 안의 지시나 오래된 API를 현재 집필 규칙으로 가져오지 않습니다.
개정 완료를 확인할 때는 기존 실행 검증과 별도로 “기본 예시 → 다른 상황 → 비교 또는 반례 → 결과를 읽는 설명”이 어디에 있는지 실제 절·셀 번호로 기록합니다. 새 코드는 노트북에서 실행한 뒤 HTML에 반영하고, 문장만 추가했다면 기존 코드와 출력이 보존되었는지 확인합니다.
## 새 챕터를 시작할 때
1. 커리큘럼의 해당 챕터와 앞뒤 학습 내용을 확인하고 절마다 답할 질문을 한 문장으로 적습니다. 이미 정해진 독자·문체·테마를 다시 질문하지 않습니다.
2. [템플릿 사용 안내](_template/README.md)에 따라 챕터와 절의 원본 파일을 만듭니다. 예전 챕터의 전체 본문·출력·기관명·검증 기록을 복제하지 않습니다.
3. 절마다 아래 두 형식 중 하나를 고릅니다. Context rot처럼 현상을 관찰하는 절에 실패·수정 형식을 강제로 넣지 않습니다.
4. 필요한 데이터와 설치 패키지를 준비하고 노트북을 먼저 실행합니다. 결과를 읽은 뒤 설명·도식·복습 문제를 작성합니다.
5. 코드와 설명을 대조한 기록을 챕터의 집필 점검표에 남기고, 작성자와 구분되는 검토자가 다시 읽습니다. 실행 성공만으로 이 검토를 대신하지 않습니다.
템플릿은 작성할 자리를 가진 초안입니다. `[[작성: …]]`를 채우고 실제 실행을 마치기 전에는 발행하지 않습니다. 초안에 과거 실행 번호·출력·검증 해시를 복사해 넣지 않습니다. 새 절을 추가할 때도 기존 파일을 덮어쓰지 않습니다.

## Before/After형과 실험 해석형
### Before/After형: 같은 원인을 고쳐 비교합니다
기본 실행으로 정상 결과를 먼저 확인합니다. 이후 **Before 코드·실제 결과 → 원인 설명 → After 코드·실제 결과 → 무엇이 해결됐는지**를 보여 줍니다. 설명만 쓰거나 예정된 오류 메시지만 출력하지 않습니다.
질문·원문·정답 기준·모델은 유지하고, 원인에 해당하는 조건을 바꿉니다. 여러 조건을 바꿔야 한다면 각각의 역할과 비교의 한계를 적습니다. 새 정보가 필요하다면 어디서 확인했는지, 또는 실습을 위해 어떤 가정을 추가했는지 명시합니다. 출처나 시행일을 임의로 만들어 실제 자료를 복구했다고 설명하지 않습니다.
| 피할 예 | 이 주제에서 확인할 결과 |
| --- | --- |
| Select를 설명하며 `require_context([])`의 예외만 관찰 | 같은 질문에서 근거를 메시지에 넣지 않은 실제 답과 선택한 근거를 넣은 실제 답 |
| 규정 충돌을 설명하며 “시행일:” 문자열 유무만 검사 | 서로 맞지 않는 두 규정에 대한 실제 답, 확인한 시행일로 규정을 선택한 뒤의 실제 답 |
| 청킹을 설명하며 잘못된 인자의 타입 오류만 관찰 | 같은 원문에서 청크 경계에 잘린 단어·조건과 설정을 고친 뒤 남은 본문 |
| 출처 누락을 고치며 `page=1`을 새로 대입 | 실제 문서에서 가져온 쪽 번호가 검색·생성 과정에 유지되는지 확인 |
| 캐시 파일 수가 같다는 이유로 API 호출 0회라고 단정 | 파일 수는 파일 수로 설명. 호출 수 주장은 별도 측정이 있을 때만 사용 |
`assert`는 관찰한 결과를 확인하는 보조 수단입니다. 개발자가 직접 만든 검사 함수가 예상대로 예외를 냈다는 사실은 환각·검색 실패·컨텍스트 문제의 증거가 아닙니다. 단, 타입 오류나 예외 처리 자체를 가르치는 절은 해당 오류를 직접 다룰 수 있습니다.
근거가 없어 “모른다”고 답하거나 충돌을 발견해 “확인이 필요하다”고 답하면 그 자체를 모델의 실패로 기록하지 않습니다. 정보가 빠진 프로그램, 아직 답을 정할 수 없는 자료 상태, 모델의 잘못된 답을 구분해서 설명합니다.
노트북의 꼬리 셀에는 설명 셀까지 `metadata.lesson_part="before"` 또는 `"after"`를 지정합니다. HTML 5번에는 ``, 6번에는 ``를 한 번씩 넣습니다. PC에서는 좌우 비교, 모바일에서는 Before 다음 After 순서로 읽습니다.
### 실험 해석형: 관찰한 범위에서 결론을 냅니다
길이별 정답률, 청크 분할 기준, 색인 설정처럼 결과를 측정하는 절에 사용합니다. 노트북에 `metadata.lesson_format="experiment"`를 지정하고 Before/After 태그를 넣지 않습니다. 모든 실행 코드는 5번에 넣고 6번 “실험 결과 해석”에는 실제 관찰과 한계를 설명합니다.
Context rot 실험이라면 질문·정답 근거·모델 등을 유지하고 입력 길이에 따른 정답률을 측정합니다. 입력 토큰이 늘었다는 사실만으로 성능 저하를 확인했다고 쓰지 않습니다. 세 길이에서 모두 정답이었다면 그 조건에서는 저하를 관찰하지 못했다고 적습니다. 실패를 얻으려고 질문·정답·채점 기준을 중간에 바꾸지 않습니다.
청크 수가 적어진 것과 검색 품질이 좋아진 것은 다른 관찰입니다. 한 질문에서 나온 결과로 모델 전체의 우열을 단정하지 않습니다. 반복 횟수와 조건을 먼저 정하고 결과 원문을 읽어 판정합니다.
## 초보자가 복사해서 실행할 수 있는 코드
- 노트북 하나를 새 Python 3.12 커널에서 독립 실행합니다. 첫 셀부터 실행하면 설치·import·데이터·변수가 모두 준비되어야 합니다.
- 셀 하나에는 한 가지 학습 행동을 둡니다. 기본 3~15줄, 최대 25줄을 기준으로 나누고 필요한 설명을 생략해 줄 수만 줄이지 않습니다.
- 주요 변수의 의미, 인자의 단위, 반환값, 낯선 문법과 처리 이유를 한국어 주석으로 설명합니다. 코드 앞에서 실행 목적을, 뒤에서 관찰할 값을 짚습니다.
- 여러 줄 문서와 프롬프트는 삼중 큰따옴표와 실제 줄바꿈으로 작성합니다. `"\n".join(...)`처럼 구분자가 필요한 연산은 그대로 사용합니다.
- 기본 생성 코드는 LangChain의 `init_chat_model` → `invoke` → `AIMessage.text`, 임베딩은 `OpenAIEmbeddings`를 사용합니다. 직접 SDK 실습이 명시된 절은 그 예외를 설명합니다.
- `.env`를 현재 폴더부터 상위 폴더에서 찾고 키의 존재만 확인합니다. 비밀 값이나 전체 환경 변수를 출력하지 않습니다.
- 학생 코드에 프로젝트 전용 모듈, `sys.path` 변경, `__file__`, 개인 절대 경로를 요구하지 않습니다. 파일이 필요하면 제공 자료와 상대 경로를 안내합니다.
- 기본 실습은 완성 코드입니다. 과제용 빈칸·TODO는 요청된 별도 과제본에 둡니다. 공통 클래스·모듈·설정 시스템 구현은 그것이 학습 목표일 때만 기본 경로에 넣습니다.
- 개발 입문자가 이해하기 어려운 추상어는 구체적인 상황으로 풉니다. 필요한 기술 용어는 뜻과 예를 먼저 설명하고, 가능성·예외·적용 범위는 유지합니다.
