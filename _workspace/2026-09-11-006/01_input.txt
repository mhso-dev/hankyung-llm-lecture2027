1학습 목표
DataFrame의 행·열과 자료형을 확인할 수 있습니다.
조건식과 loc로 필요한 주문만 선택할 수 있습니다.
금액 열의 자료형 오류를 발견하고 숫자로 변환할 수 있습니다.
2이 내용을 배우는 이유
에이전트가 주문 상태를 답하려면 먼저 주문 파일에서 필요한 행을 정확히 찾아야 합니다. 파일 전체를 모델에 전달하면 관련 없는 정보까지 입력에 포함되고 금액이 문자열인지 숫자인지 구별하지 못하면 합계도 틀릴 수 있습니다. 이번 절에서는 표를 읽고 조건에 맞는 행만 반환하는 과정을 작은 조회 함수로 구현합니다.
Ch 19에서는 조회 함수를 에이전트 도구로 감쌉니다. 도구 이름과 설명이 좋아도 함수가 잘못된 행을 반환하면 답의 근거가 잘못됩니다. 따라서 모델을 연결하기 전에 입력 열, 선택 조건, 반환 필드를 코드와 테스트로 고정해야 합니다.
3앞에서 배운 내용
Ch 2의 05절에서는 Path로 파일 경로를 만들고 파일을 읽었습니다. 04절에서는 함수의 매개변수와 반환값을 분리했고, 03절에서는 여러 주문을 사전의 목록으로 표현했습니다. 이번 절은 그 사전 목록을 행과 열이 있는 표로 바꾸어 같은 열의 값을 한 번에 비교합니다. 노트북은 이전 커널의 변수나 프로젝트 전용 모듈을 사용하지 않고 교육용 주문 세 건을 직접 준비합니다.
4핵심 개념
표에서 한 열을 먼저 읽습니다
주문 장부 전체가 DataFrame입니다. 한 주문은 행(row), 주문 번호·상태·금액은 열(column)입니다. DataFrame에는 행을 구분하는 인덱스(index)도 있습니다. 이 예제에서 화면 왼쪽에 생략된 0, 1, 2가 인덱스이며 주문 번호인 order_id와 역할이 다릅니다. 인덱스는 pandas가 행을 찾고 맞추는 표식이고, 주문 번호는 업무 데이터에 들어 있는 식별자입니다.
orders["status"]처럼 열 이름 하나를 대괄호 안에 쓰면 표 전체가 아니라 Series 하나를 얻습니다. Series는 같은 열의 값과 각 값의 인덱스를 함께 가진 1차원 자료구조입니다. 이 Series를 "paid"와 비교하면 각 행마다 True 또는 False가 만들어집니다. 이 참·거짓 Series가 불리언 마스크(boolean mask)입니다.
loc는 행 조건과 반환 열을 나눠 받습니다
DataFrame.loc[행 조건, 열 선택]은 레이블을 기준으로 행과 열을 선택합니다. 이 절의 함수는 frame.loc[frame["status"] == status]처럼 행 조건만 전달하므로 조건이 참인 행의 모든 열을 반환합니다. 반환 열까지 제한하려면 frame.loc[mask, ["order_id", "amount"]]처럼 쉼표 뒤에 열 이름 목록을 씁니다. loc라는 이름만 외우기보다 입력이 행 조건이고 반환이 선택된 DataFrame이라는 흐름으로 읽어야 합니다.
자료형이 연산의 뜻을 정합니다
자료형(dtype)은 열의 값이 문자열인지 정수인지 나타냅니다. dtypes는 열마다 자료형을 보여 주는 Series입니다. 화면에는 32000처럼 보여도 문자열이면 덧셈 결과가 320001800027000처럼 이어질 수 있습니다. pd.to_numeric(..., errors="raise")는 Series를 입력으로 받아 숫자로 변환한 Series를 반환하며, 변환할 수 없는 값이 있으면 예외를 발생시킵니다. 따라서 잘못된 값을 누락한 채 합계를 계산하지 않습니다.
도식 읽기
초록 상자는 원본 주문 세 행, 파란 상자는 상태 Series를 비교해 마스크를 만들고 loc에 전달하는 흐름, 노란 상자는 O101과 O103의 합계 59,000을 뜻합니다. 아래쪽 빨간 경로는 금액 열이 문자열일 때 잘못된 합계가 만들어지는 과정을 보여 줍니다.
5실행 예제
첫 셀에서 pandas 3.0.5를 확인합니다. 다음 셀의 pd.DataFrame([...])은 사전 세 개를 입력으로 받아 3행 3열 DataFrame을 만듭니다. to_csv(..., index=False)의 index=False는 0, 1, 2 인덱스를 CSV의 별도 열로 저장하지 않는다는 뜻입니다. pd.read_csv는 파일을 읽어 새 DataFrame을 반환하고, dtype={"order_id": "string"}은 주문 번호를 계산용 숫자가 아닌 문자열로 유지합니다.
fetch_orders의 입력은 CSV 경로와 선택할 상태입니다. 함수 안에서는 frame["status"] Series를 상태 문자열과 비교하고, loc가 참인 행만 남깁니다. 마지막 to_dict(orient="records")는 DataFrame의 각 행을 사전 하나로 바꾸어 사전 목록을 반환합니다. records 방향을 사용하면 인덱스 대신 열 이름이 각 사전의 키가 됩니다. paid 입력은 O101과 O103을, 조건만 pending으로 바꾼 입력은 O102를 반환합니다.
DataFrame은 분석 코드에서 열 연산을 이어 가기 좋고 사전 목록은 JSON으로 변환하거나 도구 결과로 전달하기 좋습니다. 함수의 입력, 처리, 반환을 구분하면 호출자는 pandas의 내부 사용 여부를 몰라도 결과를 사용할 수 있습니다.
확인할 점 — orders["status"]가 Series를 만들고, 비교 결과가 각 행의 선택 여부가 되며, loc가 그 결과로 DataFrame을 줄이는 순서를 확인합니다. 선택 뒤에도 원본 주문 번호와 금액이 유지되는지와 합계 전에 금액 열의 자료형을 확인했는지도 살펴봅니다.
6일부러 실패해 보기
Before는 금액 열을 문자열로 바꾼 뒤 sum()을 호출합니다. 오류가 발생하지 않지만 결과는 77,000이 아니라 세 문자열을 이어 붙인 값입니다. 프로그램이 멈추지 않았다는 사실만으로 결과가 맞다고 판단할 수 없습니다. After는 to_numeric으로 금액을 정수로 변환하고 같은 세 행의 합계를 다시 계산합니다. 출력 77,000과 assert 문이 변환 결과를 확인합니다.
7주의할 점과 실무 메모
CSV의 주문 번호가 숫자로만 보여도 식별자는 문자열로 읽는 편이 안전합니다. 앞의 0은 수량이 아니라 식별 형식의 일부일 수 있습니다.
결측값을 0으로 바꾸기 전에 0이 실제 금액인지 미수집 값을 대신하는지 확인합니다.
행이 많은 파일은 필요한 열과 조건을 일찍 선택해야 메모리 사용을 줄일 수 있습니다. 이 절의 세 행으로 큰 파일 성능을 일반화할 수 없습니다.
반환값은 화면용 표가 아니라 사전 목록처럼 다음 코드가 처리할 수 있는 형식으로 정합니다.
실제 주문 파일을 함수에 연결할 때는 열 이름과 필수 열 목록도 입력 조건으로 확인합니다. 파일이 열리더라도 status 또는 amount 열이 없으면 조회 결과를 만들 수 없습니다. 값의 범주도 함께 확인해야 합니다. 예를 들어 paid, pending, cancelled 외의 상태가 들어오면 새 업무 상태인지 오타인지 원천 시스템에서 확인합니다. 이러한 검사는 잘못된 행을 조용히 제외하는 것보다 문제를 발견하기 쉽습니다.

합계 전에 자료형을 확인하고 변환 실패를 드러냅니다.
다음 학습과 이어지는 지점 — 다음 절에서는 주문 표의 고객 번호를 고객 표의 기본 키와 연결합니다. 현재 만든 fetch_orders 형태는 Ch 19에서 조회 도구의 실행 함수가 됩니다.

1학습 목표
기본 키와 외래 키의 역할을 실제 표에서 구분할 수 있습니다.
고객과 주문을 다대일 관계로 조인할 수 있습니다.
중복 키가 조인 행 수를 늘리는 현상을 발견하고 검사할 수 있습니다.
2이 내용을 배우는 이유
주문에는 고객 이름 대신 고객 번호만 저장되는 경우가 많습니다. 이름과 지역을 매 주문에 반복하면 고객 이름을 고칠 때 여러 행을 수정해야 하고 서로 다른 값이 남을 수 있습니다. 관계형 모델은 정보를 주제별 테이블로 나누고 키로 연결합니다. 조회 도구는 이 연결 규칙을 알아야 주문과 고객 정보를 정확히 함께 반환합니다.
Ch 12에서 벡터 데이터베이스의 스키마를 읽을 때도 어떤 열이 레코드를 구분하고 어떤 열이 다른 테이블을 가리키는지 판단해야 합니다. 이번 절의 목표는 데이터베이스 이론 전체가 아니라 조회 함수를 만들 때 필요한 키, 관계, 최소한의 정규화입니다.
3앞에서 배운 내용
앞 절에서 주문 세 건을 DataFrame으로 표현하고 상태 조건으로 행을 선택했습니다. Ch 2의 사전과 목록으로도 같은 데이터를 나타낼 수 있지만 두 표를 연결하려면 공통 열의 뜻과 값의 유일성을 추가로 확인해야 합니다.
4핵심 개념
키는 행을 찾고 테이블을 연결합니다
도서관 대출표에는 책 제목 전체 대신 도서 번호를 적습니다. 번호 하나가 도서 한 권만 가리키면 번호로 제목과 저자를 찾을 수 있습니다. 고객 표의 기본 키(primary key)인 customer_id도 고객 한 명을 유일하게 구분하며 비어 있지 않아야 합니다. 주문 표의 같은 열은 고객 표의 행을 가리키는 외래 키(foreign key)입니다. 두 열의 이름이 같다는 사실보다 값이 같은 대상을 식별한다는 의미가 중요합니다.
관계의 방향을 왼쪽과 오른쪽에서 읽습니다
관계(relationship)는 두 테이블의 행이 키로 연결되는 방식입니다. 고객 한 명에게 주문 여러 건이 있으므로 고객에서 주문을 보면 일대다(one-to-many)입니다. 조인 코드의 왼쪽에 주문, 오른쪽에 고객을 두면 여러 주문이 고객 한 명을 가리키므로 many_to_one입니다. 같은 데이터를 보더라도 어느 표를 기준으로 읽는지에 따라 표현 순서가 달라집니다.
조인(join)은 키 값이 같은 두 행의 열을 한 결과에 결합합니다. 내부 조인(inner join)은 양쪽에 모두 키가 있는 행만 남깁니다. 왼쪽 조인(left join)은 왼쪽 행을 모두 남기고 오른쪽에서 찾지 못한 열에는 결측값을 둡니다. 데이터베이스에서는 값이 없거나 알려지지 않은 상태를 NULL이라고 하며, pandas에서는 문자열 열의 결측값이 NaN 또는 <NA>처럼 표시될 수 있습니다.
정규화(normalization)는 반복되는 사실을 주제별 테이블로 나누어 한 사실을 한 곳에서 관리하도록 구조를 정리하는 원칙입니다. 고객 이름을 고객 표 한 곳에 저장하면 이름을 바꿀 때 주문 여러 행을 각각 수정하지 않아도 됩니다.
도식 읽기
초록 상자 두 개는 고객 표와 주문 표를 뜻합니다. 파란 화살표는 주문의 외래 키가 고객의 기본 키를 가리키는 흐름이고 노란 상자는 many_to_one 조인 결과 세 행입니다. 빨간 상자는 고객 기본 키가 중복되면 한 주문이 여러 고객 행과 일치해 결과가 다섯 행으로 늘어나는 실패를 나타냅니다.
5실행 예제
orders.merge(customers, on="customer_id", validate="many_to_one")에서 입력은 주문 DataFrame과 고객 DataFrame입니다. on은 양쪽에서 비교할 키 열을 지정하고, 생략된 how="inner"는 양쪽에 일치하는 키가 있는 행만 남깁니다. validate="many_to_one"은 왼쪽 주문 키의 반복은 허용하면서 오른쪽 고객 키는 유일한지 검사합니다. 처리가 끝나면 주문 열 옆에 고객 이름 열이 결합된 새 DataFrame을 반환합니다.
기본 예제에서 C001은 주문 표에 두 번 나타나고 고객 표에는 한 번 나타납니다. 따라서 O101과 O103에는 모두 김하나가 붙고 조인 뒤 행 수는 원래 주문 세 건과 같습니다. 조건을 하나 바꾸어 부모 고객이 없는 O104를 추가한 예제는 how="left"를 사용합니다. indicator=True가 만든 _merge 열의 left_only는 왼쪽 주문은 남았지만 오른쪽 고객을 찾지 못했다는 뜻입니다. 이 행의 고객 이름은 결측값이 됩니다.
정규화된 구조는 고객 이름의 중복을 줄이는 대신 조회할 때 조인이 필요합니다. 이 절에서는 고객과 주문을 두 테이블로 나누는 최소 구조만 사용합니다. 주소 이력이나 주문 당시 수령인처럼 시간에 따라 달라지는 값은 별도 요구사항을 확인한 뒤 어느 테이블에 둘지 정해야 합니다.
확인할 점 — 먼저 조인 키의 의미와 오른쪽 키의 유일성을 확인합니다. 다음으로 내부 조인의 결과 행 수가 주문 수와 같은지 확인합니다. 마지막으로 왼쪽 조인에서 left_only와 고객 이름의 결측값이 같은 O104를 가리키는지 확인합니다.
6일부러 실패해 보기
Before는 고객 C001을 한 행 더 추가합니다. 일반 merge는 이를 허용하므로 C001 주문 두 건이 각각 두 번 결합되고 전체 결과는 다섯 행이 됩니다. 주문 합계를 계산하면 실제 주문보다 크게 집계됩니다. After는 같은 중복 고객 표에 “먼저 들어온 원본 이름을 유지한다”는 교육용 정리 규칙을 적용합니다. 정리한 고객 키의 유일성을 검사하고 many_to_one으로 다시 조인한 결과는 주문과 같은 세 행입니다.
7주의할 점과 실무 메모
중복 행을 무조건 삭제하기 전에 어느 행이 올바른지 결정할 기준을 확인합니다. 최신 수정일이나 원천 시스템 같은 근거가 필요합니다.
외래 키 값이 고객 표에 없으면 내부 조인에서 주문이 사라질 수 있습니다. 누락을 찾아야 할 때는 왼쪽 조인과 조인 상태 표시를 사용합니다.
정규화는 모든 값을 잘게 나누는 작업이 아닙니다. 함께 수정되어야 하는 사실의 중복과 변경 문제를 줄이는 범위에서 적용합니다.
개인정보가 포함된 고객 표는 필요한 열만 조회하고 접근 권한과 보존 기간을 따로 확인합니다.

기본 키는 한 테이블의 행을 유일하게 구분합니다.
외래 키는 다른 테이블의 기본 키를 가리킵니다.
조인 전후 행 수와 관계 검증으로 중복 키 문제를 발견합니다.

2이 내용을 배우는 이유
표 파일은 학습과 작은 업무에 편리하지만 여러 사용자가 같은 구조를 반복 조회할 때는 데이터베이스가 더 적합합니다. SQL은 어떤 열을 반환하고 어떤 테이블을 연결하며 어떤 조건과 순서로 결과를 만들지 선언합니다. 에이전트 도구의 함수는 자연어 질문 전체를 SQL로 바꾸기 전에 검증된 조건 조회부터 제공하는 편이 안전합니다.
이번 절의 find_customer_orders(database, customer_id)는 데이터베이스 경로와 고객 번호를 입력으로 받고 사전 목록을 반환합니다. Ch 19에서 이 함수를 도구로 등록할 때는 실행 환경에서 데이터베이스 경로를 정하고 모델이 고객 번호를 전달하도록 입력 범위를 설계합니다. 데이터 접근과 답변 생성을 나누면 어느 단계에서 잘못된 값이 생겼는지 찾기 쉬워집니다.
3앞에서 배운 내용
앞 절에서 고객 표의 기본 키와 주문 표의 외래 키를 확인하고 pandas의 merge로 두 표를 연결했습니다. Ch 2의 04절에서는 함수의 입력과 반환값을, 05절에서는 예외 처리를 확인했습니다. SQLite는 Python 표준 라이브러리 sqlite3로 사용할 수 있어 별도 데이터베이스 서버 없이 같은 관계를 SQL로 조회할 수 있습니다.
4핵심 개념
요청 문장을 SQL 절로 나눕니다
“고객 C001의 주문 번호, 이름, 금액을 금액이 큰 순서로 주세요”라는 요청에는 네 가지 결정이 들어 있습니다. SELECT는 반환할 열, FROM과 JOIN은 읽고 연결할 테이블, WHERE는 남길 행의 조건, ORDER BY는 반환 순서를 정합니다. SQL은 보통 SELECT → FROM/JOIN → WHERE → ORDER BY → LIMIT 순서로 작성합니다. LIMIT는 최대 몇 행을 반환할지 정하며 이번 함수에는 사용하지 않습니다.
데이터베이스가 개념적으로 처리하는 순서는 작성 순서와 다릅니다. 먼저 FROM/JOIN으로 행의 원천을 만들고, WHERE로 행을 줄인 뒤, SELECT로 반환 열을 정하고, ORDER BY로 정렬하며, 마지막에 LIMIT로 행 수를 제한합니다.
쿼리와 입력값을 분리합니다
SQL(Structured Query Language)은 관계형 데이터베이스의 구조와 데이터를 다루는 언어입니다. 쿼리(query)는 데이터베이스에 보내는 조회 또는 변경 명령입니다. 매개변수 쿼리(parameterized query)는 SQL 문장과 입력값을 분리해 전달합니다. Python sqlite3에서는 물음표 자리표시자와 값 튜플을 사용하므로 입력 전체가 SQL 문법이 아닌 하나의 값으로 처리됩니다.
db.execute(sql, (customer_id,))에서 첫 번째 인자는 SQL 문자열이고 두 번째 인자는 물음표에 대응하는 값의 튜플입니다. 값이 하나뿐이어도 (customer_id,)처럼 쉼표를 써야 한 원소 튜플이 됩니다. 반환되는 커서는 조회 결과를 순회할 수 있는 객체입니다. 행 팩토리(row factory)는 커서가 각 행을 어떤 Python 객체로 만들지 정합니다. sqlite3.Row를 사용하면 열 이름으로 값에 접근할 수 있고 dict(row)로 사전으로 변환할 수 있습니다.
도식 읽기
초록 상자는 데이터베이스 경로·고객 번호 입력과 반환 사전을 나타냅니다. 파란 상자는 테이블 연결, 행 선택, 열 선택, 정렬의 처리 흐름이고 빨간 상자는 입력을 문자열에 직접 붙여 조건식의 구조가 바뀌는 실패를 보여 줍니다.

c.name AS customer_name의 AS는 결과 열에 새 이름을 붙입니다. 처리 결과의 각 sqlite3.Row를 dict로 바꾸므로 함수는 사전 목록을 반환합니다. C001의 결과는 O101, O103 순서이며 두 행의 customer_name은 김하나입니다. 고객 번호만 C002로 바꾸면 같은 처리에서 O102 한 행을 반환합니다. 입력값과 SQL 구조는 분리되어 있으므로 SQL 문법처럼 보이는 고객 번호도 하나의 문자열 값으로 비교됩니다.
확인할 점 — SQL을 작성 순서대로 읽은 뒤 데이터베이스의 개념적 처리 순서로 다시 읽습니다. 물음표 수와 값의 수, 한 원소 튜플의 쉼표, AS로 정한 반환 키, 두 정렬 기준의 적용 순서를 출력과 연결합니다.

값은 매개변수로 전달하지만 테이블명이나 열 이름은 허용 목록에서 고릅니다. 자리표시자는 일반적으로 SQL 식별자를 대신하지 않습니다.

연결은 작업 뒤 닫아야 합니다. 모듈 함수는 with sqlite3.connect(...)로 연결 범위를 제한합니다.
실제 서비스에서는 읽기 전용 계정, 쿼리 시간 제한, 반환 행 수 제한도 함께 적용합니다.

사용자 입력은 SQL 문자열에 붙이지 않고 매개변수로 전달합니다.

기사, 상품, 업무 시스템의 데이터는 파일이나 데이터베이스 대신 HTTP API로 제공되기도 합니다. 한 번의 요청으로 모든 결과를 반환하면 응답이 너무 커질 수 있어 서버는 여러 페이지로 나눕니다. 첫 페이지만 읽는 함수는 정상 응답을 받더라도 뒤쪽 데이터를 빠뜨립니다. 에이전트 도구가 이 함수를 사용하면 모델은 누락 사실을 알기 어렵습니다.

4핵심 개념
요청과 응답을 한 쌍으로 읽습니다
HTTP 요청(request)은 클라이언트가 서버에 보내는 메시지입니다. 요청에는 주소(URL), 작업을 나타내는 메서드, 추가 조건, 필요하면 본문이 들어갑니다. HTTP 응답(response)은 서버가 반환하는 메시지이며 상태 코드, 헤더, 본문으로 구성됩니다. 이 절의 클라이언트는 GET /articles?page=1을 요청하고 서버는 상태 코드 200, JSON이라는 본문 형식을 알리는 헤더, 기사 목록이 든 본문을 반환합니다.
JSON(JavaScript Object Notation)은 문자열·숫자·참과 거짓·null·배열·객체를 텍스트로 표현하는 형식입니다. HTTPX의 response.json()은 JSON 본문을 Python의 사전과 목록으로 변환합니다. JSON의 null은 Python에서 None이 됩니다.
페이지를 하나씩 이어서 요청합니다
페이지네이션(pagination)은 큰 결과를 여러 응답으로 나누는 방식입니다. 첫 응답에는 기사 두 건과 다음 페이지 2가 들어 있습니다. 함수는 현재 페이지를 요청 입력으로 보내고, 응답의 기사 목록을 누적한 뒤, next_page를 다음 요청 입력으로 바꿉니다. 두 번째 응답의 next_page가 None이면 반복을 마치고 누적한 목록을 반환합니다. 구현마다 페이지 번호, 커서, 다음 링크를 사용할 수 있으므로 API 문서를 확인해야 합니다.
REST와 실패 처리를 구분합니다
REST API는 HTTP의 주소, 메서드, 상태 코드와 표현 형식을 사용해 자원을 다루는 인터페이스입니다. 이 절은 GET 요청으로 기사 목록을 읽습니다. 시간 제한(timeout)은 응답을 무한히 기다리지 않도록 대기 한도를 정합니다. raise_for_status()는 4xx·5xx 응답을 성공 데이터처럼 처리하지 않고 예외로 바꿉니다.
도식 읽기
초록 상자는 첫 페이지에서 받은 기사 데이터를 나타냅니다. 파란 상자는 next_page 값을 다음 요청의 입력으로 사용하는 흐름이고 노란 상자는 기사 세 건과 종료 조건을 확인한 결과입니다. 빨간 상자는 첫 페이지만 읽으면 A03이 누락되는 실패를 나타냅니다.
5실행 예제
노트북은 ThreadingHTTPServer를 127.0.0.1의 사용 가능한 포트에서 실행합니다. 이것은 인터넷의 외부 API 대신 같은 HTTP 규칙으로 응답하는 로컬 fixture입니다. 첫 요청의 params={"page": 1}은 주소 뒤에 ?page=1이라는 쿼리 매개변수를 만듭니다. timeout=2.0은 최대 대기 시간을 초 단위로 지정합니다. 반환된 response에서 raise_for_status()로 상태를 검사한 다음 json()으로 본문을 변환합니다.
fetch_articles의 입력은 기본 주소, 선택 범주, 시간 제한, 선택적인 HTTP 클라이언트입니다. 반복문은 페이지 번호를 요청하고, 응답을 검사하고, items를 누적하고, next_page로 상태를 갱신합니다. 반환값은 모든 페이지에서 모은 기사 사전의 목록입니다. 범주를 전달하면 모든 페이지를 수집한 뒤 해당 범주의 기사만 남깁니다. 방문한 페이지를 seen 집합에 저장하므로 서버가 같은 페이지를 계속 안내하는 잘못된 응답도 감지합니다.
확인할 점 — 첫 요청의 입력 page=1, 응답 상태 200, JSON에서 변환된 items와 next_page=2를 순서대로 연결합니다. 다음 요청에서는 next_page가 None으로 바뀌어 종료되고 A01·A02·A03이 한 목록으로 반환되는지 확인합니다.
6일부러 실패해 보기
Before 함수는 page=1을 한 번만 요청해 A01과 A02를 반환합니다. HTTP 요청과 JSON 변환은 성공하지만 A03이 누락됩니다. After 함수는 현재 페이지를 변수로 두고 next_page가 None이 될 때까지 반복합니다. 각 응답에서 상태를 검사하고 기사 목록을 누적하여 A01, A02, A03을 모두 반환합니다. 방문한 페이지 번호를 집합에 기록하므로 서버가 같은 next_page를 반복하면 ValueError로 종료합니다. 마지막에는 서버를 종료해 포트와 스레드를 정리합니다.
7주의할 점과 실무 메모
페이지 종료 규칙은 서비스마다 다릅니다. 빈 목록, 다음 링크 부재, 커서 부재 중 무엇을 사용하는지 공식 문서를 확인합니다.
시간 제한은 연결·읽기 등 단계별로 설정할 수 있습니다. 작업의 응답 시간 요구와 서버 특성에 맞춰 정합니다.
모든 오류를 즉시 재시도하면 서버 장애를 키울 수 있습니다. 재시도할 상태, 횟수, 대기 증가 규칙을 정하고 중복 요청의 영향을 확인합니다.
실제 API의 인증 토큰은 코드나 노트북 출력에 넣지 않고 환경 변수에서 읽습니다.

페이지네이션 함수는 다음 값, 정상 종료 조건, 반복 페이지 오류를 모두 처리합니다.
시간 제한과 자원 정리는 조회 함수의 정상 동작에 포함됩니다.
다음 학습과 이어지는 지점 — 다음 절에서는 JSON API가 없는 HTML 문서에서 구조를 읽고 필요한 필드를 추출합니다. 이 절의 fetch_articles는 Ch 19 도구 함수의 세 번째 재사용 예제입니다.

1학습 목표
HTML 요소와 CSS 선택자로 기사 필드를 추출할 수 있습니다.
선택 결과가 없을 때 반환 형식을 유지할 수 있습니다.
robots.txt와 별도로 이용 조건·저작권·개인정보·호출 간격을 확인해야 하는 이유를 설명할 수 있습니다.
2이 내용을 배우는 이유
모든 웹사이트가 구조화된 API를 제공하지는 않습니다. 공개 HTML에서 제목과 날짜를 읽어야 할 때는 문서의 태그와 속성을 분석해 필요한 값만 추출합니다. 화면에 보이는 문자열을 임의 위치로 자르면 광고나 메뉴가 섞이고 페이지 구조가 조금만 바뀌어도 결과가 달라집니다.
스크래핑은 기술적으로 읽을 수 있다는 사실만으로 사용이 허용되는 작업이 되지 않습니다. 대상 주소의 이용 약관, 저작권과 데이터베이스 권리, 개인정보, 접근 빈도 제한을 확인해야 합니다. robots.txt는 크롤러의 접근 경로를 알리는 규칙이며 접근 허가서나 비공개 보호 장치가 아닙니다.
3앞에서 배운 내용
앞 절에서 HTTP 응답의 JSON 본문을 Python 사전으로 바꾸고 키로 값을 읽었습니다. HTML은 값을 사전의 키 대신 태그의 계층과 속성으로 표현합니다. Ch 2의 04절에서는 None을 값이 없는 상태로 사용했고, 05절에서는 예외를 구분해 처리했습니다. 이 두 방법으로 선택 결과가 없거나 필수 구조가 달라진 경우를 나누어 처리합니다.
4핵심 개념
HTML 문자열을 요소 트리로 바꿉니다
HTML 문서는 여는 태그와 닫는 태그로 내용의 역할과 포함 관계를 표시합니다. <article data-id="A10">은 기사 영역을 여는 태그이고 data-id는 그 요소의 속성입니다. 그 안의 h1, p, time은 자식 요소입니다. 이 부모와 자식 관계를 가지 모양으로 나타낸 것이 요소 트리입니다.
파싱(parsing)은 문자열을 태그와 계층을 가진 구조로 해석하는 과정입니다. Beautiful Soup에 lxml 파서를 명시하면 어떤 파서로 트리를 만들었는지 실행 조건이 분명해집니다. 잘못 구성된 HTML은 파서에 따라 트리가 다를 수 있으므로 프로젝트와 실습의 파서 버전을 고정합니다.
CSS 선택자로 노드를 고릅니다
CSS 선택자는 요소 이름, class, id, 속성 같은 조건으로 트리의 노드를 고르는 표기입니다. article은 이름이 article인 요소, .summary는 class 속성에 summary가 포함된 요소, article time은 article 안에 있는 time 요소를 뜻합니다. select_one()은 첫 번째 일치 노드를 반환하고 일치 항목이 없으면 None을 반환합니다. 반환된 노드의 get_text(strip=True)는 태그를 제외한 텍스트를 읽고 앞뒤 공백을 정리합니다. article["data-id"]와 article.time["datetime"]은 화면 문자열이 아니라 속성값을 읽습니다.
스크래핑(scraping)은 웹 문서에서 필요한 데이터를 자동으로 추출하는 작업입니다. 파싱은 문자열을 구조로 바꾸는 처리이고, 선택과 추출은 그 구조에서 필요한 값을 읽는 처리입니다. robots.txt는 사용자 에이전트별 접근 경로 규칙을 전달하지만 이용 약관이나 법률 검토를 대신하지 않습니다.
도식 읽기
초록 상자는 HTML 원문과 추출한 필드 사전을 나타냅니다. 파란 상자는 lxml 파서가 요소 트리를 만들고 CSS 선택자가 노드를 고르는 흐름입니다. 빨간 상자는 없는 선택자의 결과가 None인 상태에서 메서드를 호출한 실패를 보여 줍니다.
5실행 예제
입력은 data/article.html에서 읽은 하나의 HTML 문자열입니다. BeautifulSoup(html, "lxml")이 이를 요소 트리로 바꾸고, select_one("article")이 기사 컨테이너 하나를 반환합니다. 그 노드를 기준으로 h1, .summary, time을 찾으면 문서의 메뉴나 다른 기사에 있는 같은 태그가 섞이는 범위를 줄일 수 있습니다.
처리 단계에서는 data-id와 datetime 속성, 제목과 요약의 텍스트를 읽습니다. 반환값은 id, title, summary, published, text 키를 가진 사전입니다. 실제 출력에서 A10, 골목상권 매출 회복, 요약 문장, 2026-09-01을 확인합니다. 이 사전에 스키마 버전과 원본 경로를 더해 data/article-text.json에 기록하고, 파일을 다시 읽어 기록 전 값과 같은지도 확인합니다.
다른 조건의 예로 RobotFileParser에 교육용 규칙을 입력합니다. can_fetch는 사용자 에이전트와 주소를 입력으로 받아 경로 규칙상 접근 가능 여부를 불리언으로 반환합니다. /articles/는 True, /private/는 False이지만 이 결과는 이용 허가 전체를 뜻하지 않습니다.
확인할 점 — HTML 문자열, 요소 트리, 선택된 노드, 추출한 문자열, 반환 사전의 순서로 값을 추적합니다. .summary의 점과 article의 점 없는 표기가 무엇을 고르는지 구분하고, 화면 날짜 대신 datetime 속성값이 반환되는지 확인합니다.
6일부러 실패해 보기
Before는 문서에 없는 .subtitle을 선택하고 바로 get_text()를 호출합니다. 선택 결과가 None이므로 AttributeError가 발생합니다. After는 요소가 있는지 확인하고 없는 선택 필드를 None으로 반환합니다. 이렇게 하면 함수 사용자는 키 자체가 빠진 상태와 값이 없는 상태를 구분하지 않고 일정한 사전 구조를 받을 수 있습니다.
7주의할 점과 실무 메모
robots.txt 허용은 법적 이용 허가가 아닙니다. 대상 사이트의 이용 약관, 저작권·데이터베이스 권리, 개인정보 처리 조건을 주소별로 확인합니다.
로그인, 접근 통제, CAPTCHA를 우회하지 않습니다. 접근 제한이 있으면 공식 API나 데이터 제공 경로를 찾습니다.
요청 간격과 동시 요청 수를 제한하고 서비스의 rate limit을 따릅니다. 이 노트북은 외부 사이트에 요청하지 않습니다.
선택자가 바뀌었을 때 빈 값을 계속 저장하지 않도록 필수 필드 누락을 검사하고 원문 URL과 수집 시각을 기록합니다.
기사 전문을 저장하거나 재배포하기 전에 필요한 범위와 권리를 검토합니다.

선택 결과의 존재를 확인해 반환 구조를 일정하게 유지합니다.
robots.txt와 이용 조건·권리·개인정보·호출 제한은 서로 다른 확인 항목입니다.

`DataFrame`은 행과 열로 이루어진 표입니다. 열 이름 하나를 대괄호에 쓰면 인덱스와 값을 함께 가진 1차원 `Series`를 반환합니다. 이 셀에서는 사전 세 개를 3행 3열 표로 바꾸고, CSV에 인덱스를 저장하지 않은 뒤 다시 읽어 열별 자료형을 확인합니다.
## 중간 결과 관찰
`frame["status"]`는 상태 열의 `Series`입니다. 이 Series를 입력 상태와 비교하면 행마다 참·거짓인 불리언 마스크가 만들어집니다. `loc`는 그 마스크가 참인 행을 선택해 새 DataFrame을 반환하고, `to_dict(orient="records")`는 각 행을 사전으로 바꿔 사전 목록을 반환합니다.
## 값 하나를 바꿔 비교

# 관계형 테이블과 키
고객과 주문을 키로 연결하고 조인 행 수가 늘어나는 원인을 확인합니다.
## 실행 환경 준비
## 기본 실행
고객 표의 `customer_id`는 한 고객을 유일하게 구분하는 기본 키입니다. 주문 표의 같은 열은 고객 표를 가리키는 외래 키이며 한 고객에게 여러 주문이 있으므로 반복될 수 있습니다. 두 DataFrame을 입력으로 준비합니다.
## 중간 결과 관찰
`orders.merge(customers, on="customer_id")`는 양쪽 키가 같은 행의 열을 결합합니다. 기본 내부 조인은 양쪽에 모두 있는 키만 남깁니다. `validate="many_to_one"`은 왼쪽 주문 키의 반복은 허용하고 오른쪽 고객 키는 유일한지 검사합니다. 반환된 DataFrame의 행 수와 고객 이름을 확인합니다.
## 값 하나를 바꿔 비교
고객 표에 없는 C999 주문을 추가하고 `how="left"`로 왼쪽 조인을 실행합니다. 왼쪽 주문은 유지되고 찾지 못한 고객 열에는 결측값이 생깁니다. `indicator=True`가 만든 `_merge` 열에서 `left_only`를 선택해 연결되지 않은 외래 키를 찾습니다.
## 실패 재현
고객 키가 중복되면 주문 한 행이 두 행으로 복제됩니다.
## 수정
조인 전에 키의 유일성을 검사하고 many_to_one 규칙을 선언합니다.

## 기본 실행

## 중간 결과 관찰
함수 입력은 데이터베이스 경로와 고객 번호입니다. `JOIN`으로 주문과 고객을 연결하고, `WHERE`로 입력 고객의 행을 남기고, `ORDER BY`로 금액 내림차순을 적용합니다. `db.execute(sql, (customer_id,))`의 두 번째 인자는 물음표에 넣을 값의 튜플이며 값이 하나여도 쉼표가 필요합니다. `sqlite3.Row`를 사전으로 변환한 목록이 반환값입니다.

## 실패 재현
입력 문자열을 SQL에 직접 붙이면 조건의 뜻이 바뀔 수 있습니다.
## 수정

# REST와 페이지네이션

## 실행 환경 준비
## 기본 실행
HTTP 요청은 주소, 메서드, 매개변수로 서버에 작업을 전달합니다. 응답은 상태 코드, 헤더, 본문을 반환합니다. 이 셀은 외부 서비스 대신 같은 HTTP 규칙으로 응답하는 로컬 fixture 서버를 준비합니다. JSON의 객체와 배열은 이후 Python 사전과 목록으로 변환됩니다.
## 중간 결과 관찰
