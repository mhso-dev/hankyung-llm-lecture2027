1학습 목표
문장을 토큰으로 나누는 이유를 설명합니다.
두 토큰화기의 한·영 문장 분할과 토큰 수를 비교합니다.
문자 수와 토큰 수가 같은 개념이 아님을 설명합니다.
2이 내용을 배우는 이유
대규모 언어 모델(Large Language Model, LLM)은 문장을 글자 단위로 바로 처리하지 않습니다. 문장을 토큰이라는 작은 텍스트 단위로 나눈 뒤 각 토큰을 숫자 ID로 바꾸어 처리합니다. 모델 사용량, 입력 길이, 응답 시간을 이해하려면 먼저 토큰을 세어야 합니다. 한국어는 토큰화기의 어휘와 학습 자료에 따라 한 글자가 여러 토큰으로 나뉠 수 있으므로 실측이 필요합니다.
3앞에서 배운 내용
Ch 2에서 문자열을 리스트처럼 순회하고 len()으로 길이를 구했습니다. Ch 4에서는 HTML 기사의 제목과 요약을 추출해 article-text.json으로 보존했습니다. 이 절은 그 파싱 텍스트를 직접 읽고 문자열 길이와 토큰 리스트 길이를 나란히 비교합니다. 가상환경과 Jupyter 커널을 선택하는 방법은 Ch 1에서 배운 절차를 그대로 사용합니다.
4핵심 개념
정의와 관찰
토큰(token)은 모델이 처리하는 텍스트 단위입니다. 토큰은 한 단어일 수도 있고 단어의 조각이나 문장부호일 수도 있습니다. 토큰화(tokenization)는 텍스트를 이러한 단위로 나누고 각 단위를 정수 ID에 연결하는 과정입니다. 모델은 ID 열을 입력받으므로 같은 문장도 토큰화기가 다르면 다른 숫자 열이 됩니다.
어휘(vocabulary)는 토큰화기가 알고 있는 토큰과 ID의 목록입니다. 영어 자료를 중심으로 만든 어휘에는 흔한 영어 단어 조각이 많습니다. 한국어 자료를 반영한 어휘는 '확인', '환불'과 같은 조각을 하나의 토큰으로 가질 수 있습니다. 이 차이는 언어의 우열이 아니라 어휘 설계와 학습 자료의 차이입니다.
토큰화기의 입력은 사람이 읽는 문자열이고, 처리는 문자열을 어휘에 있는 조각과 연결하는 일입니다. tokenize(text)는 조각의 문자열 목록을 반환하고, encode(text)는 조각에 대응하는 정수 ID 목록을 반환합니다. 여기서 반환은 함수가 계산을 마친 뒤 호출한 코드에 결과값을 넘긴다는 뜻입니다. len(...)은 반환된 목록에 들어 있는 항목 수를 셉니다.
예를 들어 입력 "환불!"이 ["환불", "!"]처럼 나뉘었다면 토큰 수는 2입니다. 실제 분할은 토큰화기마다 다르므로 이 모양을 외우지 않습니다. 노트북에서는 같은 입력을 두 토큰화기에 전달하고, 반환된 목록의 길이와 각 조각을 함께 출력해 차이를 읽습니다.
실습의 GPT-2 토큰화기는 '오늘 주문 상태를 확인해 주세요.'를 39개로, KLUE BERT 토큰화기는 9개로 나뉘습니다. 반면 영어 번역문은 각각 7개와 15개였습니다. 이 결과는 특정 문장과 두 토큰화기에서 관찰한 값입니다. '한국어는 항상 비효율적이다'라는 보편적 결론을 내릴 수는 없습니다.
토큰 수는 비용만이 아니라 컨텍스트 윈도에도 영향을 줍니다. 같은 내용을 더 많은 토큰으로 표현하면 모델에 넣을 수 있는 원문의 양이 줄어듭니다. 그러므로 프로덕션에서는 문자 수나 단어 수로 사용량을 추정하지 않고 실제 모델의 토큰화기로 측정합니다.
토큰 수를 비교할 때는 원문의 의미와 형식을 함께 기록합니다. 한국어와 영어 번역문은 비슷한 뜻을 담을 수 있지만 문법 구조와 문자 수가 다릅니다. 그러므로 '뜻이 같다'는 것을 자동으로 통제된 실험으로 보면 안 됩니다. 실습의 두 문장 쌍은 분할 모양을 읽는 예시입니다. 업무용 효율을 비교할 때는 실제 서비스의 대화, 문서, 코드 표본을 같은 비율로 구성하고 모델별 토큰 수의 분포를 측정합니다.
토큰화기는 보이는 문자 외에 특수 토큰(special token)을 추가할 수 있습니다. 문장의 시작과 끝, 발화자 역할, 문장 쌍의 경계를 표시하는 토큰이 예입니다. tokenize()의 결과와 실제 모델 입력의 길이가 다를 수 있는 이유입니다. 특히 채팅 모델은 대화 템플릿이 역할 표시와 생성 시작 표시를 덧붙입니다. 다른 절에서 입력 길이를 측정할 때는 이 템플릿을 적용한 후의 토큰 수를 사용합니다.
출력의 'Ġ'나 '##'와 같은 표시는 사용자 문장에 추가된 글자가 아닙니다. 토큰화기가 공백 앞의 조각인지, 앞 조각에 이어지는 부분인지 표시하는 방식입니다. 입문 단계에서는 표시 자체를 외우기보다 원문이 어떤 조각으로 나뉘었는지 확인합니다. 예상보다 많이 나뉜 단어가 있다면 해당 모델의 어휘에서 흔하지 않은 표현일 가능성을 점검합니다.
파란색은 학습자가 따라갈 입력 흐름, 녹색은 도구와 자료, 보라색은 모델의 처리, 노란색은 측정 결과, 빨간색은 확인할 제한을 뜻합니다. 화살표를 왼쪽에서 오른쪽으로 읽습니다.

6실험 결과 해석
짧은 한국어 문장 하나를 1, 2, 4, 8회 반복했을 때 GPT-2의 토큰 수는 37, 75, 151, 303이었고 KLUE의 토큰 수는 8, 16, 32, 64였습니다. 공백이 추가된 GPT-2 결과는 단순히 정확한 배수가 되지 않았습니다. 이 실험은 문장을 반복한 특수한 조건의 분할 결과만 보여 줍니다. 일반적인 한국어 토큰 효율을 평가하려면 대화, 문서, 코드가 섞인 더 넓은 자료를 사용해야 합니다.

같은 문장도 토큰화기에 따라 분할과 토큰 수가 달라집니다.
사용량은 실제 모델의 토큰화기로 측정합니다.

9복습 문제
문제와 해설
1. 토큰은 항상 한 단어와 같은가요?
해설 — 아닙니다. 단어, 단어 조각, 문장부호 등이 토큰이 될 수 있습니다.
2. 문자 수만으로 모델 사용량을 정확히 계산할 수 있나요?
해설 — 계산할 수 없습니다. 모델의 토큰화기로 인코딩한 토큰 수를 확인합니다.
3. 두 토큰화기의 수치로 언어 자체의 효율을 단정할 수 없는 이유는 무엇인가요?
해설 — 어휘, 학습 자료, 분할 규칙이 다르기 때문입니다. 특정 모델과 자료의 결과로 범위를 한정해야 합니다.

2이 내용을 배우는 이유
검색이나 문장 군집화에서는 단어가 정확히 같지 않아도 뜻이 가까운 문장을 찾아야 합니다. 임베딩은 문장을 고정된 길이의 숫자 목록으로 바꾸어 이런 비교를 가능하게 합니다. Ch 9에서 검색 증강 생성을 배울 때 문서와 질문을 임베딩하므로, 지금 숫자의 의미와 한계를 알아 둡니다.
3앞에서 배운 내용
앞 절에서 문장이 토큰과 토큰 ID의 열로 바뀌는 과정을 확인했습니다. 이 절은 그 결과를 문장 하나를 나타내는 숫자 묶음으로 바꾸는 다음 단계를 다룹니다. NumPy 배열, 벡터, 점곱, 전치, 정규화는 선수 지식으로 가정하지 않고 아래에서 코드에 필요한 만큼 처음부터 설명합니다.
4핵심 개념
정의와 관찰
임베딩(embedding)은 텍스트의 특징을 실수 벡터로 표현한 결과입니다. 검색에서 문장을 숫자로 바꾸는 이유는 표현이 달라도 뜻이 가까운 문장을 계산으로 비교하기 위해서입니다. 실습 모델은 문장 하나를 384개 숫자로 바꿉니다. 각 숫자 하나에 '취소'나 '날씨' 같은 이름을 붙이는 방식이 아니라, 벡터 전체에 특징이 분산되어 표현됩니다.
벡터(vector)는 순서가 있는 숫자 목록입니다. [3, 4]는 숫자 두 개로 이루어진 2차원 벡터이고, 문장 임베딩 모델이 반환한 한 행은 숫자 384개로 이루어진 384차원 벡터입니다. NumPy 배열(array)은 여러 벡터를 계산하기 좋은 표 형태로 보관하는 객체입니다. 네 문장을 한 번에 임베딩하면 네 행과 384개 열을 가진 배열이 반환됩니다.
vectors.shape는 배열의 모양을 (행 수, 열 수)로 반환합니다. 출력 (4, 384)는 문장 네 개가 각각 384개의 숫자로 표현됐다는 뜻입니다. vectors[0, :5]는 0번 행의 처음 다섯 값만 고릅니다. 전체 의미를 다섯 값으로 판단하려는 코드가 아니라 반환 구조를 눈으로 확인하는 코드입니다.
점곱(dot product)은 같은 위치의 숫자를 곱한 뒤 모두 더하는 계산입니다. [3, 4]와 [4, 3]의 점곱은 3×4 + 4×3 = 24입니다. 벡터의 길이는 각 값을 제곱해 더한 뒤 제곱근을 구합니다. 두 예시 벡터의 길이는 각각 5입니다. 정규화(normalization)는 각 값을 이 길이로 나누어 벡터 길이를 1로 만드는 처리입니다.
코사인 유사도(cosine similarity)는 두 벡터의 점곱을 두 벡터 길이의 곱으로 나눈 값입니다. 두 벡터를 먼저 길이 1로 정규화하면 분모가 1이므로 점곱만 계산해도 코사인 유사도가 됩니다. [3, 4]와 [4, 3]을 정규화해 계산한 유사도는 0.96이고, 각 벡터를 자기 자신과 비교한 값은 1입니다.
@는 NumPy의 행렬 곱 연산자입니다. vectors.T의 T는 행과 열을 바꾸는 전치(transpose)입니다. 따라서 vectors @ vectors.T는 모든 문장 쌍의 점곱을 계산해 4행 4열 유사도 표를 반환합니다. 실습은 normalize_embeddings=True로 정규화된 벡터를 받으므로 이 점곱 표가 코사인 유사도 표가 됩니다.
실습에서 '주문한 상품을 취소하고 싶습니다.'와 영어 문장 'I want to cancel my order.'의 유사도는 0.8987이었습니다. 한국어 표현을 바꾼 '구매를 취소하려면 어떻게 하나요?'는 0.8024, 날씨 문장은 0.1044였습니다. 0번 문장을 기준으로 세 값을 읽으면 두 취소 문장이 날씨 문장보다 가까이 놓였음을 확인할 수 있습니다.
유사도는 정답 판정이 아닙니다. '취소'와 '반품'은 관련 있지만 업무 규칙에서 다른 절차일 수 있습니다. 실습의 두 문장 유사도는 0.5931이었습니다. 숫자가 높아도 동일한 정책이나 동일한 사실을 뜻한다고 단정하지 않고, 작업에 맞는 평가 자료를 따로 정합니다.
이 결과는 네 문장과 한 모델에서 관찰한 값입니다. 다국어 번역 능력 전체나 다른 도메인의 검색 품질을 뜻하지 않습니다. 문장 길이, 부정 표현, 전문 용어가 달라져도 같은 순서가 유지되는지는 별도의 대표 질문 집합으로 확인합니다.
파란색은 학습자가 따라갈 입력 흐름, 녹색은 도구와 자료, 보라색은 모델의 처리, 노란색은 측정 결과, 빨간색은 확인할 제한을 뜻합니다. 화살표를 왼쪽에서 오른쪽으로 읽습니다.

먼저 두 개의 2차원 벡터로 shape, 길이, 정규화, 전치와 @의 반환값을 확인합니다. 그다음 문장 네 개를 384차원 벡터로 바꾸고, 0번 취소 문장과 나머지 문장의 유사도를 비교합니다.
노트북을 새 Python 3.12 커널에서 첫 셀부터 순서대로 실행합니다.
확인할 점 — 2차원 예에서 자기 자신과의 유사도가 1이고 두 벡터 사이는 0.96인 이유는 무엇인가요? 실제 문장 표에서 0번과 가장 가까운 문장, 가장 먼 문장은 무엇인가요?
6실험 결과 해석
네 문장 한 번의 결과에서 취소 의도의 한·영 문장이 가장 가까웠고 날씨 문장이 가장 멀었습니다. 이 결과는 다국어 모델이 언어가 다른 문장을 가깝게 배치할 수 있음을 보여 줍니다. 다만 세 예시의 순서가 다른 도메인, 더 긴 문장, 부정문에서도 유지되는지는 알 수 없습니다. 실무 검색은 대표 질문 집합으로 성공률을 측정합니다.
7주의할 점과 실무 메모
코사인 유사도의 절대 기준은 모델과 자료에 따라 달라집니다.
해당 모델은 최대 128토큰을 기준으로 학습된 sentence-transformers 모델입니다. 긴 문서는 분할 전략이 필요합니다.

1학습 목표
어텐션을 입력 토큰 사이의 관련성을 반영하는 처리로 설명합니다.
질문이 바뀌면 관련 있는 입력 부분도 달라질 수 있음을 설명합니다.
교재용 가중치와 실제 모델의 어텐션 측정을 구분합니다.
2이 내용을 배우는 이유
문장에 상품 A와 B의 정보가 함께 있을 때 B의 색을 물으면 B와 색상 표현을 연결해야 합니다. 모델이 모든 입력을 같은 비중으로 섞는다면 관계를 구분하기 어렵습니다. 어텐션은 현재 처리하는 토큰에 따라 입력 토큰의 관련성을 다르게 반영하는 기법입니다. 이 절은 수식과 Transformer 구현을 다루지 않고, 정보가 어떻게 연결되는지 직관으로 범위를 한정합니다.
3앞에서 배운 내용
앞서 토큰이 모델의 입력 단위임을 확인했고, 임베딩이 토큰과 문장을 숫자 벡터로 표현한다는 것을 배웠습니다. 어텐션은 이 표현들 사이의 관계를 반영하여 새로운 표현을 만드는 과정으로 이어집니다. 실습은 Ch 2에서 배운 리스트와 for 반복문을 사용합니다. zip()은 Ch 2의 선수 지식으로 가정하지 않고 이 절에서 처음 설명합니다.
4핵심 개념
정의와 관찰
어텐션(attention)은 현재 토큰의 표현을 만들 때 다른 토큰에서 가져올 정보의 비중을 계산하는 방식입니다. '상품 A는 파란색이고 상품 B는 빨간색입니다'에서 B를 처리할 때 B와 빨간색의 관계가 중요합니다. A를 처리할 때는 A와 파란색의 관계가 중요해집니다. 같은 입력이어도 현재 처리 위치에 따라 비중이 달라질 수 있습니다.
이 절의 입력은 토큰 문자열 목록과 각 토큰에 대응하는 비중 목록입니다. zip(tokens, weights)은 같은 위치의 토큰과 비중을 한 쌍씩 꺼내 반복문에 전달합니다. 반복문은 각 쌍을 한 줄로 출력하고, sum(weights)는 비중의 합 1.0을 반환합니다. 이 작은 계산은 어텐션 구현이 아니라 가중치를 읽는 연습입니다.
가중치(weight)는 여러 입력을 반영할 때 각 입력에 주는 상대적인 비중입니다. 합이 1인 목록에서 0.45는 전체 비중의 45%를 뜻합니다. 이 교재용 표는 질문을 B에서 A로 바꿀 때 큰 값의 위치도 함께 바꾸어, 현재 확인하려는 대상에 따라 관련 정보가 달라질 수 있음을 보여 줍니다.
어텐션 가중치는 보통 여러 계층과 여러 헤드에서 계산됩니다. 헤드(head)는 서로 다른 관계를 병렬로 반영하는 처리 단위로 이해할 수 있습니다. 어느 헤드는 이름과 색상, 다른 헤드는 문장 구조와 위치 관계를 반영할 수 있습니다. 단일 가중치 표만으로 모델 전체의 처리를 설명하면 중요한 맥락을 놓칠 수 있습니다.
어텐션 가중치가 크다고 해서 그 토큰이 모델 답변의 '이유'라고 단정할 수는 없습니다. 가중치는 모델 내부 계산의 한 부분이고, 여러 계층에서 추가 계산이 계속 적용됩니다. 따라서 실무에서는 출력 정확도를 별도의 평가 자료로 확인합니다. 어텐션 시각화는 탐색 도구로 사용하되, 검증 결과로 대체하지 않습니다.
실습의 가중치는 교재 제작자가 개념을 보이려고 직접 정한 값입니다. B 질문에서 'B는'에 0.45, 두 번째 '상품'에 0.30을 놓았고 A 질문에서는 비중을 첫 번째 상품과 A에 옮겼습니다. 이 숫자는 Qwen이나 다른 실제 모델에서 추출한 값이 아닙니다. 노트북도 이 제한을 출력하여 측정과 비유를 명확히 구분합니다.
파란색은 학습자가 따라갈 입력 흐름, 녹색은 도구와 자료, 보라색은 모델의 처리, 노란색은 측정 결과, 빨간색은 확인할 제한을 뜻합니다. 화살표를 왼쪽에서 오른쪽으로 읽습니다.

노트북을 새 Python 3.12 커널에서 첫 셀부터 순서대로 실행합니다.

6실험 결과 해석
질문을 B에서 A로 바꾸면 큰 교재용 비중이 B와 두 번째 '상품'에서 A와 첫 번째 '상품'으로 이동했습니다. 이 조작은 '처리하는 대상에 따라 관련 정보가 달라진다'는 개념을 보여 줍니다. 실제 모델이 이 비중을 갖는지, 빨간색을 예측하는지, 그 예측의 원인이 무엇인지는 이 실습으로 측정하지 않았습니다.

어텐션 가중치와 출력의 정확성은 다른 개념입니다. 정확성은 평가 집합으로 측정합니다.
Transformer의 어텐션을 직접 구현하는 내용은 이 과정의 선수 지식이 아니므로 다루지 않습니다.
8정리와 다음 절
어텐션은 토큰 사이의 관련성을 비중으로 반영합니다.
처리 위치와 질문이 바뀌면 관련 정보도 달라질 수 있습니다.
가중치 표는 답변의 이유나 정확성을 단독으로 증명하지 않습니다.

해설 — 아닙니다. 어텐션 직관을 위한 교재용 숫자입니다.

1학습 목표
컨텍스트 윈도를 한 번의 처리에서 사용할 수 있는 토큰 범위로 설명합니다.
전체 한도에서 출력 예산을 빼 입력 예산을 계산합니다.
시스템 지시, 문서, 질문이 하나의 입력 예산을 공유함을 설명합니다.
2이 내용을 배우는 이유
모델에 긴 문서를 넣을 때는 '몇 자까지'보다 '몇 토큰까지'를 확인해야 합니다. 입력에는 문서 외에도 시스템 지시, 대화 기록, 사용자 질문, 도구 결과가 들어갑니다. 출력을 생성할 공간도 미리 남겨야 하므로 총 한도와 입력 한도를 구분합니다.
3앞에서 배운 내용
01절에서 토큰화기로 문장의 토큰 수를 세었고, 03절에서는 입력 토큰 사이의 관계를 반영하는 어텐션 직관을 살펴봤습니다. 이 절에서는 Qwen2.5 토큰화기로 시스템, 문서, 질문을 각각 인코딩하고 합계를 구합니다. 현실 모델의 공식 한도를 재현하는 대신 계산 구조를 보이기 위해 512토큰의 실습용 한도를 설정합니다.
4핵심 개념
정의와 관찰
컨텍스트(context)는 모델이 현재 응답을 만들 때 함께 참조하도록 한 입력 전체입니다. 사용자 질문만 뜻하지 않으며 시스템 지시, 앞선 대화, 문서, 도구 결과도 포함합니다. 토큰화기는 이 입력을 토큰 ID 목록으로 바꾸고, 채팅 템플릿(chat template)은 역할 표시와 생성 시작 표시를 덧붙인 모델용 입력을 만듭니다.
컨텍스트 윈도(context window)는 모델이 한 번의 처리에서 참조할 수 있는 토큰 범위입니다. 모델별 공식 한도는 서로 다를 수 있고, 같은 모델이어도 제공 환경의 설정에 따라 달라질 수 있습니다. 한도 안에 들어간다는 말은 모델이 모든 정보를 같은 정확도로 사용한다는 뜻이 아닙니다.
노트북의 첫 계산은 각 문자열을 tokenizer.encode(text)에 넣고 토큰 ID 목록의 길이를 반환받습니다. 다음으로 apply_chat_template(..., tokenize=True)가 세 구성 요소를 실제 대화 형식으로 합친 토큰 ID 목록을 반환합니다. 원시 문자열의 토큰 수 합과 템플릿 적용 뒤의 입력 수가 다른 이유를 이 두 반환값으로 확인합니다.
토큰 예산(token budget)은 제한된 한도를 입력과 출력에 나눠 배정하는 계획입니다. 실습용 한도가 512이고 출력 64개를 예약하면 입력에는 448개가 남습니다. 채팅 템플릿을 적용한 실제 입력이 400개이므로 48개의 여유가 있습니다. 출력을 128개로 늘리면 입력 한도는 384개가 되어 현재 입력이 16개 초과합니다.
시스템 지시와 질문도 토큰을 사용합니다. 실습에서 시스템 지시 12개, 문서 360개, 질문 15개의 raw 텍스트 합계는 387개였습니다. 채팅 템플릿이 역할과 생성 시작 표시를 추가한 실제 입력은 400개였습니다. 예산 판정은 400을 기준으로 하고, 387은 구성 요소별 크기를 읽는 참고값으로 사용합니다.
한도를 넘는 입력은 무조건 뒷부분을 잘라 해결하지 않습니다. 뒷부분에 현재 질문이 있을 수 있고, 앞부분에 전체 작업 규칙이 있을 수 있습니다. 대화 요약, 관련 문서 선택, 중복 제거 등을 사용하되 남겨야 할 정보를 평가 자료로 확인합니다. 이 설계는 Ch 8 컨텍스트 엔지니어링에서 더 구체적으로 배웁니다.
토큰 예산은 정적인 문서 하나만 계산하고 끝나지 않습니다. 대화가 이어지거나 도구 결과가 추가되면 매 요청의 입력 크기가 달라집니다. 요청 전에 토큰 수를 기록하고, 한도에 가까운 요청은 문서 선택과 요약 정책을 적용합니다.

6실험 결과 해석
채팅 템플릿을 적용하고 문서 문장을 10, 20, 40, 80회 반복했을 때 전체 입력은 220, 400, 760, 1480토큰이었습니다. 실습용 입력 한도 448을 적용하면 10회와 20회는 한도 이하였고 40회와 80회는 한도를 넘었습니다. 이 결과는 토큰화와 예산 계산만 보여 줍니다. 모델이 정답을 생성할 수 있는지나 어떤 절단 정책을 사용하는지는 측정하지 않았습니다.

4핵심 개념
정의와 관찰
컨텍스트 로트(context rot)는 입력이 모델의 허용 범위 안에 있더라도 길이, 정보 위치, 주변 내용에 따라 필요한 정보를 활용한 결과가 달라질 수 있는 현상을 가리킵니다. 입력 한도를 넘겨 잘린 현상과 구분해야 합니다. 이 노트북은 가장 긴 입력도 모델 설정의 한도 안에 두고 위치와 주변 문장 수만 바꿉니다.
생성 함수의 입력은 프롬프트 문자열이며, 채팅 템플릿 적용과 토큰화를 거쳐 모델에 전달됩니다. 모델은 새 토큰 ID를 반환하고 tokenizer가 이를 다시 문자열로 복원합니다. 실험 코드는 그 문자열에 정답 코드 314159가 들어 있는지만 판정해 조건별 결과를 반환합니다.
실험은 무관한 문장을 2, 20, 60개로 늘리고 핵심 근거를 시작, 중간, 끝에 배치합니다. 질문과 정답 판정 기준은 고정합니다. 정답 문자열 314159가 응답에 포함되면 성공으로 세었습니다. 이 판정은 코드 회상 여부만 확인하며, 응답의 문장 품질은 측정하지 않습니다.
temperature 0의 탐욕 디코딩은 확률 샘플링을 하지 않습니다. 난수 시드를 두 개 제공했지만 두 응답은 독립 확률 표본이 아닙니다. 같은 설정에서 결과가 재현되는지 확인하는 중복 실행입니다. 성공률을 추정하려면 샘플링과 더 많은 반복이 필요합니다.
관찰 결과에서 근거가 시작에 있을 때는 세 길이 모두 2/2였습니다. 중간 위치는 세 길이 모두 0/2였습니다. 끝 위치는 무관한 문장 2개 조건에서 0/2, 20개와 60개 조건에서 2/2였습니다. 위치별 차이는 관찰했지만 길이가 늘어날수록 계속 나빠지는 패턴은 관찰하지 못했습니다.
중간 위치의 실패가 어느 모델에서나 반복된다고 단정하지 않습니다. 모델 크기, 프롬프트, 무관 문장의 내용, 생성 전략을 바꾸면 결과가 달라질 수 있습니다. 핵심은 '길면 나쁘다'라고 단정하는 것이 아니라 현재 작업의 길이와 위치를 분리해 측정하는 실험 설계입니다.
파란색은 학습자가 따라갈 입력 흐름, 녹색은 도구와 자료, 보라색은 모델의 처리, 노란색은 측정 결과, 빨간색은 확인할 제한을 뜻합니다. 화살표를 왼쪽에서 오른쪽으로 읽습니다.

4핵심 개념
후보 단어가 적힌 제비를 뽑습니다
모델은 다음 위치의 각 토큰 후보에 로짓(logit)이라는 변환 전 점수를 계산합니다. 로짓은 확률이 아니므로 합이 1일 필요가 없고 음수일 수도 있습니다. 소프트맥스(softmax)는 로짓을 0과 1 사이의 값으로 바꾸고 합이 1인 확률 분포를 반환합니다. temperature는 소프트맥스를 적용하기 전에 로짓의 상대적인 차이를 조정합니다. 노트북은 실제 Qwen 로짓을 추출하지 않고 [2.0, 1.0, 0.0]이라는 교재용 입력으로 이 변환만 먼저 확인합니다.
문장을 이어 쓸 수 있는 후보가 세 개이고 각 후보가 적힌 제비의 수가 다르다고 생각해 봅니다. 가능성이 높은 후보의 제비가 많으면 자주 선택되지만, 제비가 하나라도 있는 다른 후보도 뽑힐 수 있습니다. 모델의 확률 분포(probability distribution)는 다음 위치에 올 각 토큰의 상대적인 가능성을 나타냅니다. 샘플링(sampling)은 이 분포를 사용해 후보 중 하나를 확률적으로 선택하는 방식입니다. 선택한 토큰을 입력 뒤에 붙인 다음 같은 과정을 반복하므로 앞의 작은 차이가 이후 문장 전체의 차이로 이어질 수 있습니다.
temperature는 샘플링 전에 후보 확률의 상대적인 차이를 조정하는 값입니다. 낮은 값에서는 원래 가능성이 높은 후보에 선택이 더 집중되고, 높은 값에서는 낮은 후보도 선택될 여지가 커집니다. 이것은 정확도 조절 손잡이가 아닙니다. 낮춘다고 사실성이 자동으로 높아지지 않고, 높인다고 유용한 창의성이 자동으로 늘어나지 않습니다. 모델, 프롬프트, 후보 분포, 다른 생성 설정이 함께 결과에 영향을 줍니다.
top-p는 누적 확률이 지정값에 이를 때까지 가능성이 높은 후보 집합을 구성하고 그 안에서 샘플링하는 설정입니다. 실습은 0.9로 고정하므로 temperature 비교 중 후보 집합 제한 방식은 바뀌지 않습니다. 난수 시드(random seed)는 난수 생성의 시작 상태를 정하는 정수입니다. 같은 환경과 연산에서 설정 비교를 재현하는 데 도움이 되지만, 라이브러리·하드웨어·알고리즘이 바뀌어도 동일한 문자열을 보장하는 규격은 아닙니다.
최대 생성 토큰 수(max new tokens)는 모델이 입력 뒤에 추가할 토큰의 상한입니다. 이 값은 글자 수나 어절 수가 아닙니다. 실습은 계산 시간을 줄이려고 24로 제한합니다. 모델이 마침표나 종료 토큰을 선택하기 전에 상한에 도달하면 문장이 중간에서 잘립니다. 출력이 짧다는 사실을 지시 준수로 해석하기 전에 문장이 자연스럽게 끝났는지 확인해야 합니다.
도식 읽기
도식은 왼쪽에서 오른쪽으로 동일 프롬프트, T=0.3 / T=1.0, 각 3회 샘플링, 둘 다 3/3 서로 다름을 차례로 놓습니다. 네 상자는 직선 화살표로 이어집니다. top-p, 난수 시드, 최대 생성 길이처럼 실습에서 함께 고정한 조건과 문장 중간 잘림은 아래 실행 결과에서 확인합니다. 마지막 상자는 높은 temperature의 우위를 뜻하지 않고, 이 실행에서는 두 조건 모두 세 문자열이 서로 달랐다는 관찰만 나타냅니다.
5실행 예제
첫 코드 셀은 모델과 tokenizer를 고정 revision으로 불러오고 파라미터 수 494,032,768개를 출력합니다. 파라미터는 학습 과정에서 조정된 수치이며 모델 파일 크기, 메모리 사용량, 생성 속도와 같은 값이 아닙니다. 다음 셀은 프롬프트·temperature·seed·최대 생성 토큰을 받는 함수를 정의합니다. 이어지는 교재용 최소 예제는 로짓 [2, 1, 0]을 T=0.5와 T=1.0의 확률로 바꾸고 각 합이 1인지 출력합니다. 실제 생성에서는 temperature가 0보다 클 때 샘플링을 켜고 top-p 0.9를 사용합니다.
반복 생성 셀은 “오프라인 서점의 가을 행사 이름을 한국어 5어절 이내로 하나 제안하세요”라는 프롬프트를 고정합니다. temperature 0.3에서 시드 11·22·33을 실행한 다음 temperature 1.0에서 같은 세 시드를 실행합니다. 낮은 조건에서도 세 출력이 모두 달랐고 높은 조건에서도 세 출력이 모두 달랐습니다. 일부 결과는 번호 목록을 만들거나 영어를 섞었고, 봄 행사라고 잘못 쓰거나 요청과 관련 없는 사과 문장을 생성했습니다. 생성 결과가 서로 다르다는 사실과 요청을 잘 수행했다는 평가는 별개입니다.
확인할 점 — 교재용 로짓에서 T=0.5의 첫 후보 확률 0.8668이 T=1.0의 0.6652보다 집중되어 있고 두 합계는 모두 1입니다. 실제 생성의 마지막 출력은 T=0.3 unique=3/3과 T=1.0 unique=3/3입니다. 이 지표에서는 두 조건의 차이가 없습니다. 여러 답이 따옴표나 어절 중간에서 끝나므로 최대 생성 24토큰이 완결된 응답을 보장하기에 부족했음을 함께 확인합니다.
6실험 결과 해석
이번 실행에서 temperature 0.3의 세 답은 모두 서로 달랐습니다. temperature 1.0의 세 답도 모두 서로 달랐습니다. 문자열의 완전 일치 여부만 센 unique 값은 양쪽 모두 3/3입니다. 따라서 이 결과만으로 temperature를 0.3에서 1.0으로 올렸더니 출력 다양성이 증가했다고 말할 수 없습니다. 낮은 조건에서도 이미 세 번 모두 다른 문자열이 나왔기 때문입니다. 더 많은 반복, 다양한 프롬프트, 단어·의미 수준의 거리 지표를 미리 정한 뒤 측정해야 차이를 비교할 수 있습니다.
출력의 품질도 별도로 봐야 합니다. 0.3 조건의 한 답은 가을 질문에 “봄행사”를 포함했고, 1.0 조건의 한 답은 실시간 정보가 없다는 사과로 시작했습니다. 다른 답에는 영어 표현이나 자연스럽지 않은 문자열이 섞였습니다. 문자열이 다르면 unique 수는 늘지만 행사 이름으로 쓸 수 있는지는 알려 주지 않습니다. 실제 작업에서는 어절 수, 계절 관련성, 금지어, 발음 가능성 같은 평가 기준을 만들고 사람이 읽거나 자동 검사로 확인해야 합니다.
여섯 출력 가운데 여러 문장이 인용부호, 단어, 목록의 중간에서 끝났습니다. max_new_tokens=24가 새 토큰 생성을 멈췄기 때문입니다. 이 절단은 temperature 차이라고 해석할 수 없습니다. 두 조건에 동일한 제한이 적용됐고 각 응답이 종료 토큰을 선택하기 전에 한도에 도달할 수 있습니다. 생성 길이를 늘리면 완결성이 나아질 수 있지만 계산 시간과 출력 비용도 늘어납니다. 길이 설정을 바꾼 새 실험은 이번 temperature 비교와 분리해 기록해야 합니다.
7주의할 점과 실무 메모
temperature는 샘플링을 사용할 때 확률 분포에 영향을 줍니다. greedy 방식처럼 가장 높은 후보를 고정 선택하는 생성에서는 같은 의미로 비교할 수 없습니다.
temperature와 top-p를 동시에 바꾸면 어느 설정이 결과 차이를 만들었는지 분리하기 어렵습니다. 한 비교에서는 바꿀 값을 하나로 제한합니다.
난수 시드를 고정해도 모든 기기와 라이브러리 버전에서 같은 문자열이 나온다고 보장할 수 없습니다. 모델 ID, revision, 패키지와 실행 장치를 함께 기록합니다.
서로 다른 문자열 수는 의미 다양성, 사실성, 문법, 업무 적합성을 측정하지 않습니다. 목적에 맞는 별도 평가 항목이 필요합니다.
짧은 최대 생성 길이는 실행 시간을 줄이지만 답을 중간에서 끊을 수 있습니다. 종료 이유와 잘림 여부를 읽고 결과를 평가합니다.
0.49B 파라미터의 작은 로컬 모델 한 개에서 관찰한 결과를 더 큰 모델이나 상용 API 전체의 특성으로 일반화하지 않습니다.
8정리와 다음 절
샘플링은 다음 토큰의 확률 분포에서 후보를 선택하며 temperature는 후보 확률의 상대적인 집중도를 조정합니다.
이번 세 번의 실행에서는 temperature 0.3과 1.0 모두 서로 다른 문자열이 3개여서 다양성 증가를 관찰하지 못했습니다.
최대 생성 24토큰 때문에 여러 답이 중간에서 끝났고, 문자열 종류 수는 결과 품질을 알려 주지 않았습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 출력이 자연스럽게 이어진다는 성질이 사실 확인과 같은 능력이 아님을 확인합니다. 근거가 없는 고유 정보 질문에서 모델이 추측하거나 불확실성을 표현하는 두 결과를 구분합니다.
9복습 문제
문제와 해설
1. 이번 실험에서 temperature 1.0이 0.3보다 출력 다양성을 높였다고 결론 내릴 수 없는 이유는 무엇입니까?
정답: 문자열 완전 일치로 센 서로 다른 답 수가 두 조건 모두 3/3이었기 때문입니다. 반복도 조건당 세 번뿐이어서 더 넓은 효과를 판단할 근거가 부족합니다.
2. 난수 시드 11·22·33을 두 temperature 조건에서 같게 사용한 이유는 무엇입니까?
정답: 난수 시작 조건을 대응시키고 temperature 외의 비교 조건을 가능한 한 같게 유지하기 위해서입니다.
3. 출력이 따옴표나 단어 중간에서 끝난 가장 직접적인 설정 원인은 무엇입니까?
정답: 최대 생성 길이를 24개의 새 토큰으로 제한해 종료 토큰 전에 생성 상한에 도달했기 때문입니다.
4. unique=3/3이 알려 주는 것과 알려 주지 않는 것을 각각 쓰십시오.
정답: 세 문자열이 정확히 서로 달랐다는 점은 알려 줍니다. 의미 다양성, 계절 관련성, 어절 수 준수, 사실성, 행사 이름의 품질은 알려 주지 않습니다.

1학습 목표
언어 모델의 다음 토큰 예측과 사실 확인이 서로 다른 목표임을 설명할 수 있습니다.
근거가 없는 두 질문에 대한 실제 답에서 근거 없는 생성과 불확실성 표현을 구분할 수 있습니다.
답변 제약을 추가한 전후 결과를 비교하고 관찰 범위를 제한할 수 있습니다.
환각을 줄이기 위해 지시, 근거 제공, 검증, 평가 기준을 함께 설계해야 하는 이유를 말할 수 있습니다.
2이 내용을 배우는 이유
언어 모델의 답은 문법이 자연스럽고 설명의 형식도 익숙합니다. 이 때문에 독자는 문장이 자연스러우면 내용도 확인된 사실이라고 받아들이기 쉽습니다. 그러나 모델은 답변을 만들 때 웹이나 사내 데이터베이스를 자동으로 조회하지 않습니다. 입력과 학습 과정에서 얻은 패턴을 바탕으로 다음 토큰을 이어 갑니다. 질문에 필요한 근거가 없는데도 답을 요구받으면 그럴듯한 표현을 선택할 수 있습니다. 제품에 모델을 연결하는 개발자는 자연스러운 문장과 검증된 사실을 분리해야 합니다.
환각을 “모델이 거짓말한다”라고만 설명하면 대응 방법을 잘못 고르게 됩니다. 거짓말은 알고 있는 사실과 다른 내용을 의도적으로 말한다는 뜻을 포함하지만, 언어 모델에는 사람과 같은 의도를 그대로 적용할 수 없습니다. 이 절에서는 환각(hallucination)을 입력이나 확인 가능한 근거가 뒷받침하지 않는 내용을 모델이 답으로 생성한 현상이라고 제한해 사용합니다. 한 출력만 보고 모델 전체의 환각률을 판단하지 않고, 질문에 근거가 있었는지와 답이 어떤 주장을 만들었는지부터 읽습니다.
실습은 실제로 존재하지 않는 기관·제도와 제품을 묻습니다. 첫 질문에 모델은 지원 절차처럼 보이는 내용을 생성했고, 두 번째 질문에는 실제 제품 정보가 없다고 밝혔습니다. 두 답을 모두 같은 실패라고 표시하면 불확실성을 표현한 동작을 놓칩니다. 이후 “근거가 없으면 확인할 수 없다고 답하라”는 지시를 추가해 두 응답이 어떻게 바뀌었는지 관찰합니다. 이 결과는 지시 한 줄이 모든 환각을 막는다는 보증이 아닙니다.
3앞에서 배운 내용
앞 절에서 같은 프롬프트와 모델도 샘플링 설정과 난수 상태에 따라 다른 문자열을 만들 수 있음을 확인했습니다. 출력이 달라지는 현상과 사실이 틀리는 현상은 같은 개념이 아닙니다. 다양한 답이 모두 근거에 맞을 수도 있고, 매번 같은 답이 계속 잘못될 수도 있습니다. 이번 노트북은 temperature를 0으로 설정해 가장 높은 후보를 고르는 방식으로 실행합니다. 샘플링 변화를 줄이고 질문 정보와 지시문 변화에 집중하기 위한 선택입니다.
실행 모델과 함수는 앞 절과 같습니다. Qwen/Qwen2.5-0.5B-Instruct의 같은 고정 revision을 불러오고, 채팅 템플릿과 tokenizer를 거쳐 최대 64개의 새 토큰을 생성합니다. 로컬 모델은 외부 검색 도구, 사내 문서, 실제 상품 데이터에 연결되어 있지 않습니다. 질문 문장에도 정답 근거를 제공하지 않습니다. 따라서 구체적인 지원금 액수나 배터리 용량을 확인해 답할 수 있는 자료가 없습니다.
4핵심 개념
문장을 잘 이어 쓰는 능력과 자료를 확인하는 능력을 구분합니다
이 절은 모델을 새로 학습하거나 내부 구조를 구현하지 않습니다. 입력은 질문 또는 지시문과 질문을 합친 문자열이고, 처리는 다음 토큰 생성이며, 반환은 모델이 만든 답변 문자열입니다.
환각 판정은 답이 마음에 드는지가 아니라 주장과 근거의 관계를 봅니다. 먼저 답에서 외부 확인이 필요한 구체적 주장을 찾고, 다음으로 입력이나 확인 가능한 자료에 그 주장을 뒷받침하는 근거가 있는지 확인합니다. 근거 없이 만들어진 주장이 있으면 이 절의 기준에서 환각으로 분류합니다.
회의록에서 다음 문장을 자연스럽게 이어 쓰는 사람과 회계 시스템에서 실제 금액을 조회하는 사람은 서로 다른 일을 합니다. 문장 작성자는 문맥에 어울리는 표현을 만들 수 있지만, 장부를 보지 않았다면 정확한 금액을 확인할 수 없습니다. 언어 모델의 사전학습(pretraining)은 많은 텍스트에서 다음 토큰을 예측하는 능력을 학습하는 과정입니다. 이 과정은 언어 패턴과 여러 지식을 모델 파라미터에 반영하지만, 각 생성 문장이 현재 시점의 사실인지 자동으로 조회하고 증명하는 절차는 아닙니다.
다음 토큰 예측(next-token prediction)은 앞의 토큰이 주어졌을 때 이어질 토큰의 확률을 높이는 학습 목표입니다. 모델은 “지원금은” 뒤에 금액이나 결정 절차가 이어지는 문장 패턴을 배울 수 있습니다. 그러나 가상 제도의 실제 근거가 없다는 표지가 모든 질문에 명시적으로 붙어 있는 것은 아닙니다. OpenAI의 2025년 연구는 희소하거나 임의적인 사실에서 이러한 학습 목표가 유창한 추측을 만들 수 있고, 정확도만 보상하는 평가가 불확실성 표현보다 추측을 유리하게 만들 수 있다는 한 구조적 설명을 제시합니다. 이것은 환각의 유일한 원인이라는 주장이 아닙니다.
근거(grounding evidence)는 답을 확인하는 데 사용할 수 있는 입력 자료입니다. 정책 원문, 제품 사양표, 데이터베이스 조회 결과, 도구가 반환한 값 등이 될 수 있습니다. 근거가 없을 때 모델이 “확인할 수 없습니다”라고 답하는 행동을 답변 보류(abstention)라고 부릅니다. 보류는 무조건 좋은 답이라는 뜻도 아닙니다. 근거가 충분한데도 계속 답하지 않으면 유용성이 낮아집니다. 시스템은 어떤 질문에서 답하고 어떤 질문에서 보류할지 평가 기준을 정해야 합니다.
지시문(instruction)은 모델이 답을 만드는 방식과 제한을 알려 주는 입력입니다. 실습은 “정답 근거가 없으면 추측하지 말고 정해진 문장으로 답하라”고 명시합니다. 이 지시가 실제 두 질문에서는 답변 보류를 유도했습니다. 하지만 모델이 모든 표현, 언어, 긴 문맥, 공격적인 입력에서도 지시를 따른다는 보증은 아닙니다. 실제 서비스에서는 답에 필요한 근거를 함께 제공하고, 출처를 표시하며, 중요한 수치와 이름을 별도 규칙이나 도구로 검사합니다.
평가 기준(evaluation criterion)은 답을 성공 또는 실패로 판단하는 규칙입니다. 첫 질문은 존재하지 않는 기관의 지원 제도를 실제처럼 설명했으므로 근거 없는 주장을 만들었습니다. 두 번째 질문은 “실제 제품에 대한 정보는 없습니다”라고 밝혔고 구체적인 용량을 만들지 않았습니다. 문장이 끝까지 완성되지 않았지만, 기록된 범위에서 이미 불확실성을 표현했습니다. 두 응답을 모두 환각으로 세면 관찰한 내용과 맞지 않습니다.
도식 읽기
도식은 왼쪽에서 오른쪽으로 근거 없는 질문, 다음 토큰 예측, 추측 또는 불확실성 표현, 근거 확인 필요를 놓습니다. 네 상자는 직선 화살표로 이어집니다. 가운데의 “추측/불확실 표현”은 근거 없는 질문에서 두 종류의 답이 나올 수 있음을 압축해 나타냅니다. 어느 질문에 어떤 답이 기록됐는지와 답변 보류 지시를 추가한 결과는 아래 노트북에서 따로 확인합니다. 마지막 상자는 답을 사실로 받아들이기 전에 근거를 확인해야 한다는 뜻입니다.
5실행 예제
첫 코드 셀은 로컬 생성 모델과 tokenizer를 불러오고 파라미터 수 494,032,768개를 확인합니다. 다음 셀은 temperature 0일 때 샘플링을 끄는 generate() 함수를 정의합니다. 이어지는 셀은 두 질문을 순서대로 모델에 전달합니다. “해바라기 연구소”와 “초록 패스”, “노을 워커 3”은 실습을 위해 만든 이름입니다. 질문에는 제도 지원금이나 제품 배터리 용량의 정답 자료가 없습니다.
첫 답은 지원금 액수를 직접 완성하지 못했지만, 해당 지원금이 2026년에 결정됐고 연구 결과 공개와 연결된다는 절차를 실제 정보처럼 생성했습니다. 질문이나 제공 자료에서 확인할 수 없는 주장입니다. 두 번째 답은 제품이 실제로 존재하지 않는 것으로 보인다고 말하고 구체적인 배터리 용량을 제공하지 않았습니다. 이 응답은 이미 불확실성을 표현했으므로 첫 답과 같은 종류의 근거 없는 사실 생성으로 분류하지 않습니다.
마지막 셀은 질문 앞에 답변 보류 지시를 추가합니다. 같은 두 질문 모두 “제공된 정보로는 확인할 수 없습니다”로 출력됐습니다. 질문 내용과 모델은 유지하고 지시문만 추가했으므로 이 두 사례에서는 지시 변화와 응답 변화의 관계를 볼 수 있습니다. 다만 생성 길이, 다른 표현의 질문, 다른 모델, 대화 이력까지 시험하지 않았습니다.
확인할 점 — 제약 전 첫 답만 확인되지 않은 제도 절차를 만들었습니다. 제약 전 둘째 답은 이미 정보 부재를 밝혔습니다. 제약 후에는 두 답 모두 지정한 보류 문장을 반환했지만, 두 성공 사례를 일반적인 보장으로 확대하지 않습니다.
6실험 결과 해석
첫 질문의 기록된 답에는 “지원금은 2026년에 결정되었습니다”, “연구 결과를 공개하고”와 같은 주장이 나타납니다. 실습 자료에는 이러한 제도 자체가 없으므로 주장을 뒷받침할 근거도 없습니다. 모델은 질문에 포함된 기관·제도 이름과 학술 지원 문장에서 흔한 표현을 연결해 그럴듯한 절차를 만들었습니다. 액수는 생성 길이 안에서 나오지 않았지만, 숫자를 만들지 않았다는 이유로 안전한 답이 되는 것은 아닙니다. 확인되지 않은 절차도 사실 주장입니다.
두 번째 질문의 답은 “실제 제품에 대한 정보는 없습니다”, “실제로 존재하지 않는 것으로 보입니다”라고 말합니다. 문장이 최대 생성 길이에서 끝나 완전한 답은 아니지만, 기록된 범위에서는 배터리 용량을 임의로 만들지 않았습니다. 따라서 이 질문까지 환각이라고 세지 않습니다. 같은 모델과 같은 생성 방식에서도 질문 표현과 학습된 패턴에 따라 추측과 보류가 다르게 나타날 수 있음을 보여 줍니다.
답변 보류 지시를 추가한 뒤 두 질문은 모두 지정 문장과 정확히 같은 답을 반환했습니다. 이 실행에서는 지시가 원하는 행동을 유도했습니다. 그러나 두 질문과 한 번씩의 실행만 관찰했습니다. 모델이 지시를 무시하도록 유도하는 입력, 근거가 일부만 있는 질문, 오래된 사실, 서로 충돌하는 자료, 여러 차례의 대화는 다루지 않았습니다. 중요한 업무에서 지시 한 줄만으로 사실성을 보장했다고 판단하면 안 됩니다.
환각의 원인은 하나로 고정할 수 없습니다. 다음 토큰 예측이라는 학습 목표, 학습 자료의 오류와 빈틈, 질문에 제공된 정보, 모델 크기와 조정 방식, 생성 설정, 평가가 추측에 주는 보상이 함께 영향을 줄 수 있습니다. 이 절은 그중 “근거 없는 고유 사실 질문에도 유창한 답을 이어 갈 수 있다”는 구조를 관찰했습니다. 원인을 정확히 분리하려면 학습 자료와 모델 내부, 반복 평가 자료가 더 필요합니다.
7주의할 점과 실무 메모
자연스러운 문장과 확인된 사실을 같은 것으로 취급하지 않습니다. 특히 금액, 날짜, 법률, 의학, 인물 정보는 원자료나 도구 결과로 다시 확인합니다.
“모르면 모른다고 답하라”는 지시는 유용한 한 층이지만 보안 장치나 사실 검증기의 역할을 대신하지 않습니다.
출처를 요청했다고 해서 출력된 URL이나 문헌이 실제 존재하고 주장을 뒷받침한다고 보장할 수 없습니다. 출처 자체와 연결된 내용을 확인합니다.
보류율만 높이면 환각처럼 보이는 답은 줄 수 있지만 답할 수 있는 질문에도 응답하지 않을 수 있습니다. 정확한 답, 근거 없는 답, 적절한 보류를 함께 측정합니다.
두 번째 답처럼 불확실성을 이미 표현한 사례를 환각으로 세지 않습니다. 평가 전에 어떤 주장이 근거를 요구하는지 판정 규칙을 작성합니다.
실습의 작은 로컬 모델과 두 가상 질문은 현상을 설명하는 사례입니다. 서비스의 실제 환각률이나 다른 모델의 순위를 제공하지 않습니다.
8정리와 다음 절
다음 토큰 예측은 자연스러운 문장 생성을 학습하지만 각 문장의 사실 여부를 자동으로 검증하는 절차는 아닙니다.
근거 없는 첫 질문에서는 확인되지 않은 제도 절차가 생성됐고, 둘째 질문은 이미 정보 부재를 표현했습니다.
답변 보류 지시는 이 두 사례에서 원하는 문장을 만들었지만 사실성을 보장하지 않으므로 근거 제공과 평가를 함께 설계합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 생성·유사도·빈칸 채우기처럼 작업 종류가 다른 모델 후보를 먼저 구분합니다. 라이선스와 실행 가능성으로 후보를 좁힌 뒤 자체 질의셋으로 품질을 측정해야 합니다. Ch 9부터는 외부 문서를 검색해 모델 입력에 근거를 제공하는 RAG 흐름을 만듭니다.
9복습 문제
문제와 해설
1. 첫 번째 질문의 답에서 근거 없이 만들어진 주장은 무엇입니까?
정답: 가상 연구소의 지원금이 2026년에 결정됐고 연구 결과 공개와 연결된다는 제도 절차입니다. 질문과 제공 자료에는 이러한 근거가 없습니다.
2. 두 번째 질문의 제약 전 답을 첫 번째 답과 같은 환각으로 세지 않은 이유는 무엇입니까?
정답: 실제 제품 정보가 없고 존재하지 않는 것으로 보인다고 불확실성을 밝혔으며 구체적인 배터리 용량을 만들지 않았기 때문입니다.
3. 답변 보류 지시를 추가한 뒤 실제로 관찰한 결과와 보장할 수 없는 내용을 구분하십시오.
정답: 두 질문 모두 지정한 확인 불가 문장을 반환한 것은 관찰했습니다. 다른 질문·모델·대화에서도 항상 지시를 따르고 환각이 사라진다고 보장할 수는 없습니다.
4. 환각 대응에서 지시문 외에 필요한 조치를 두 가지 쓰십시오.
정답: 정책 원문이나 검색 결과 같은 근거를 입력에 제공하고, 중요한 주장과 출처를 별도 도구·규칙·질의셋으로 검증해야 합니다. 적절한 보류도 평가 항목에 포함합니다.

1학습 목표
작업 종류와 라이선스를 필수 조건으로 사용해 맞지 않는 모델 후보를 제외할 수 있습니다.
파라미터 수, 로딩 시간, 토큰화 시간을 각각 무엇을 측정한 값인지 구분할 수 있습니다.
후보 필터 결과와 품질 비교 결과가 다름을 설명할 수 있습니다.
실제 서비스 입력과 평가 기준으로 모델 선택 실험을 설계할 수 있습니다.
2이 내용을 배우는 이유
모델을 선택할 때 이름이 널리 알려졌거나 공개 점수가 높다는 이유만으로 결정하면 필요한 작업을 수행하지 못할 수 있습니다. 문장 생성, 문장 유사도 계산, 빈칸 채우기는 입력과 출력 형식이 다릅니다. 라이선스가 프로젝트의 배포 방식과 맞지 않으면 기술적으로 실행할 수 있어도 사용할 수 없습니다. 메모리에 올라가지 않거나 응답 시간이 목표를 넘는 모델도 서비스에 적용하기 어렵습니다. 먼저 반드시 만족해야 하는 조건으로 후보를 거르고, 남은 후보를 같은 평가 자료와 환경에서 측정해야 합니다.
이 절은 세 모델의 작업 종류와 라이선스를 비교합니다. 후보 표는 성능 순위가 아닙니다. 생성 작업과 Apache-2.0을 필수 조건으로 정했을 때 어떤 후보가 남는지 Python 목록 처리로 확인합니다. 이어서 선택된 생성 모델의 파라미터 수, 현재 환경의 캐시된 로딩 시간, 한 문장을 반복한 입력의 토큰화 시간을 측정합니다. 이 수치들은 생성 답변의 품질이나 첫 토큰까지 걸리는 시간을 직접 보여 주지 않습니다.
3앞에서 배운 내용
01절은 tokenizer가 문장을 토큰 ID로 바꾸는 결과를 비교했고, 02절은 문장 임베딩과 코사인 유사도가 특정 모델과 문장 집합에서의 근접도를 나타낸다는 점을 확인했습니다. 06절과 07절은 작은 생성 모델로 샘플링과 근거 없는 답변을 관찰했습니다. 같은 “언어 모델”이라는 넓은 이름 아래에서도 tokenizer, 임베딩 모델, 생성 모델의 역할이 다릅니다. 이번 절에서는 앞에서 사용한 모델을 하나의 순위표에 억지로 놓지 않고, 작업에 맞는 인터페이스부터 확인합니다.
노트북은 이미 사용한 고정 모델 ID와 모델 카드의 라이선스 표기를 후보 목록에 적습니다. Qwen/Qwen2.5-0.5B-Instruct는 텍스트 생성, sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2는 문장 유사도, klue/bert-base는 빈칸 채우기 후보로 기록합니다. 이 목록은 세 모델의 모든 가능한 용도를 설명하지 않으며, 실습에서 사용할 대표 작업을 구분하기 위한 자료입니다.
4핵심 개념
채용 공고의 필수 조건과 실기 평가를 나눕니다
AutoTokenizer.from_pretrained()는 모델 ID와 고정 revision을 입력받아 문자열을 토큰 ID로 바꾸는 tokenizer 객체를 반환합니다. AutoModelForCausalLM.from_pretrained()는 같은 식별자로 다음 토큰 생성용 모델 객체를 반환합니다. num_parameters()는 모델이 가진 파라미터 수를 정수로 반환합니다. 메서드 이름의 Auto는 모델 ID에 맞는 구체 클래스를 라이브러리가 선택한다는 뜻입니다.
운전 업무 지원자를 고를 때 먼저 필요한 면허가 있는지 확인합니다. 면허가 있는 후보끼리는 같은 도로에서 안전성과 업무 수행을 평가합니다. 면허 확인만으로 가장 안전한 운전자를 정할 수 없고, 주행 점수가 높아도 필요한 면허가 없으면 해당 업무를 맡길 수 없습니다. 모델 선택도 필수 조건 필터와 비교 평가를 분리합니다.
작업 종류(task)는 모델이 받는 입력과 만드는 출력의 목적입니다. 텍스트 생성 모델은 입력 뒤의 토큰을 이어 문장을 만들고, 문장 유사도 모델은 문장을 벡터로 바꾸어 거리를 비교하며, 빈칸 채우기 모델은 문장 안의 가려진 위치에 올 후보를 계산합니다. 필요한 작업과 다른 모델은 성능 비교 전에 제외합니다.
라이선스(license)는 모델 코드와 가중치를 사용할 때 지켜야 하는 조건입니다. 같은 Apache-2.0 표기라도 모델 카드, 데이터, 함께 배포하는 코드의 조건을 확인해야 합니다. CC-BY-SA-4.0처럼 표시와 공유 조건이 다른 후보도 있습니다. 이 절은 법률 자문을 제공하지 않습니다. 실제 배포 전에는 모델 카드 원문과 조직 정책을 확인합니다.
파라미터(parameter)는 학습 과정에서 조정되는 모델 내부의 수치입니다. 파라미터 수는 모델 규모를 설명하는 한 값이지만 정확도, 메모리, 파일 용량, 속도와 일대일로 같지 않습니다. 자료형, 양자화, 실행 장치, 구현에 따라 필요한 메모리와 처리 시간이 달라집니다.
로딩 시간(load time)은 모델 파일을 읽고 객체를 준비하는 데 걸린 시간입니다. 노트북의 cached load seconds는 모델 파일이 이미 로컬 캐시에 있는 현재 컴퓨터에서 한 번 측정한 0.376초입니다. 최초 다운로드 시간, 서버 시작 전체 시간, 요청마다 드는 생성 시간이 아닙니다. 토큰화 시간(tokenization time)은 문자열을 토큰 ID로 바꾸는 전처리 시간입니다. 기록된 1.998밀리초는 1,202토큰을 현재 CPU 환경에서 한 번 변환한 값이며, 답을 생성하는 시간이 아닙니다.
생성 지연시간(generation latency)은 입력 처리 후 출력 토큰을 만드는 데 걸리는 시간입니다. 첫 토큰 지연시간(time to first token, TTFT)은 요청을 시작한 뒤 첫 출력 토큰을 받을 때까지의 시간입니다. 이번 노트북은 생성 호출을 수행하지 않으므로 둘 다 측정하지 않았습니다. 서비스 모델을 선택할 때는 워밍업 여부, 입력 길이, 출력 길이, 동시 요청 수를 고정해 별도로 측정해야 합니다.
도식 읽기
도식은 왼쪽에서 오른쪽으로 작업·라이선스, 필수 조건 필터, 후보 모델, 자체 평가 필요를 차례로 놓습니다. 네 상자는 직선 화살표로 이어집니다. 필터를 통과한 후보가 생겨도 마지막 상자처럼 자체 평가가 더 필요합니다. 이 도식은 세 후보의 세부 목록이나 품질 순위를 나타내지 않습니다. 노트북의 Qwen 한 후보 결과도 필터 조건을 만족한 결과일 뿐 품질 우승을 뜻하지 않습니다.
5실행 예제
첫 코드 셀은 세 후보의 모델 ID, 대표 작업, 모델 카드 라이선스를 사전으로 만들고 한 줄씩 출력합니다. 이 표에서 Qwen은 생성, multilingual MiniLM은 문장 유사도, KLUE BERT는 빈칸 채우기로 구분됩니다. 다음 셀은 Qwen의 고정 revision을 로드해 파라미터 494,032,768개를 확인합니다. 이미 캐시된 모델의 로딩 시간은 0.376초였고, 같은 한국어 문장을 100번 반복한 입력은 1,202토큰으로 나뉘며 토큰화에 1.998밀리초가 걸렸습니다.
마지막 셀은 required_task를 text-generation, required_license를 apache-2.0으로 정합니다. 두 값을 모두 만족하는 사전만 목록에 남기면 Qwen 후보 하나가 출력됩니다. 이것은 요구 조건에 맞는 후보를 찾은 결과입니다. 세 모델에 같은 생성 질문을 던져 Qwen의 품질이 더 좋다고 측정한 결과가 아닙니다. 나머지 두 모델은 애초에 대표 작업이 다르므로 이 생성 후보 필터에서 제외됐습니다.
확인할 점 — eligible 목록에는 한 모델만 남지만 출력의 마지막 문장은 선택 전에 자체 질의셋으로 품질과 속도를 측정해야 한다고 명시합니다. 0.376초와 1.998밀리초를 생성 응답 시간이나 TTFT로 부르지 않습니다.
6실험 결과 해석
세 후보 중 필수 작업과 라이선스를 동시에 만족한 항목은 Qwen 하나였습니다. 이는 필터 조건을 코드로 정확히 적용했음을 보여 줍니다. 필수 라이선스를 바꾸거나 임베딩 작업을 선택하면 결과 목록도 달라집니다. 작업 종류와 라이선스 값은 실제 제품 요구에서 먼저 정해야 하며, 원하는 모델이 남도록 사후에 조건을 바꾸면 선택 기준의 의미가 없어집니다.
파라미터 수 494,032,768개는 실행 모델이 약 0.49B 규모라는 모델 카드 정보와 맞습니다. 이 값만으로 품질이나 메모리 사용량을 결정할 수 없습니다. 캐시된 로딩 0.376초도 현재 한 번의 실행 결과입니다. 디스크 캐시, 운영체제 상태, 장치, 패키지 버전에 따라 달라질 수 있습니다. 최초 설치에서는 모델 다운로드 시간이 추가됩니다.
1,202토큰을 1.998밀리초에 토큰화한 측정은 전처리 한 단계만 포함합니다. 모델의 순전파와 새 토큰 생성, 네트워크, 큐 대기, 스트리밍은 포함하지 않습니다. 따라서 “모델 응답이 1밀리초”라고 설명하면 잘못입니다. 실제 후보 비교에서는 같은 입력·출력 길이와 반복 횟수로 전체 지연과 TTFT의 중앙값·상위 백분위수를 측정하고, 품질 평가와 함께 기록합니다.
7주의할 점과 실무 메모
모델 카드의 task 표기는 후보 분류의 시작점입니다. 실제 코드 인터페이스와 입력·출력 형식이 서비스 요구에 맞는지 작은 실행으로 확인합니다.
라이선스 이름만 복사하지 말고 고정 revision의 모델 카드, 가중치, 코드, 데이터 관련 조건을 확인합니다. 조건이 바뀔 수 있으므로 확인 날짜를 남깁니다.
파라미터 수가 큰 모델이 모든 업무에서 더 좋은 것은 아닙니다. 자체 질의셋의 정답 기준과 실패 비용으로 품질을 측정합니다.
캐시된 로딩 시간은 최초 다운로드와 서버 시작 시간을 포함하지 않습니다. 차가운 시작과 준비된 상태를 분리해 측정합니다.
토큰화 시간은 생성 시간이나 TTFT가 아닙니다. 측정 구간의 시작과 끝을 코드로 명시합니다.
후보가 하나 남았다는 사실은 선택이 끝났다는 뜻이 아닙니다. 품질, 지연, 메모리, 비용, 운영 제약을 만족하지 못하면 다른 후보를 추가합니다.
8정리와 다음 절
작업 종류와 라이선스 같은 필수 조건으로 후보를 먼저 거르고 남은 모델만 같은 기준으로 평가합니다.
이번 측정의 로딩 시간과 토큰화 시간은 생성 지연이나 첫 토큰 지연을 나타내지 않습니다.
후보 필터는 품질 비교가 아니므로 실제 입력으로 만든 질의셋과 운영 환경 측정이 필요합니다.
다음 학습과 이어지는 지점 — Ch 6에서는 외부 모델 API를 LangChain의 공통 인터페이스로 호출하고 메시지와 응답 객체를 다룹니다. Ch 5의 로컬 Qwen·MiniLM·KLUE 표를 그대로 사용하지 않고, 생성 API를 제공하는 OpenAI·Anthropic·Google 후보에 작업 적합성과 키 준비 여부를 적용합니다. Ch 6의 1회 호출 기록은 모델 품질 순위가 아닙니다. Ch 11은 검색 결과를 자체 질의셋과 검색 지표로 측정하고, 생성 답변의 정확성과 근거성은 Ch 15에서 별도로 평가합니다.
9복습 문제
문제와 해설
1. 생성 작업과 Apache-2.0을 필수 조건으로 적용했을 때 어떤 후보가 남았습니까?
정답: Qwen/Qwen2.5-0.5B-Instruct 하나가 남았습니다. 다른 두 후보는 대표 작업이나 라이선스 조건이 달랐습니다.
2. 캐시된 로딩 시간 0.376초가 포함하지 않는 시간을 두 가지 쓰십시오.
정답: 최초 모델 다운로드 시간과 실제 출력 토큰 생성 시간을 포함하지 않습니다. 네트워크·큐 대기와 전체 서버 시작도 별도입니다.
3. 1,202토큰을 1.998밀리초에 처리한 값을 생성 지연시간이라고 부를 수 없는 이유는 무엇입니까?
정답: tokenizer가 문자열을 토큰 ID로 바꾸는 전처리만 측정했고 모델 추론과 새 토큰 생성은 실행하지 않았기 때문입니다.
4. 필수 조건 필터 뒤에도 자체 질의셋 평가가 필요한 이유는 무엇입니까?
정답: 필터는 작업·라이선스 적합성만 확인하며 실제 업무 답변의 정확도, 실패 유형, 지연, 비용을 비교하지 않기 때문입니다.

# 임베딩과 의미 유사도
단어가 다르더라도 뜻이 비슷한 문장을 숫자로 비교할 수 있을까요?
Python 3.12와 잠긴 패키지를 사용합니다. 첫 실행에서는 로컬 모델을 다운로드합니다.
## 두 숫자 벡터로 표기 읽기
`[3, 4]`와 `[4, 3]`을 두 행으로 담습니다. `shape`는 행과 열의 수를 반환합니다. `np.linalg.norm(..., axis=1)`은 각 행의 길이를 계산하고, 각 행을 그 길이로 나누면 길이 1인 정규화 벡터가 됩니다. `T`로 행과 열을 바꾼 뒤 `@`를 적용하면 모든 행 쌍의 점곱 표가 반환됩니다.
## 다국어 문장 임베딩
문장 네 개가 **입력**입니다. `model.encode()`는 각 문장을 384개의 실수로 바꾸어 NumPy 배열로 **반환**합니다. `shape`의 `(4, 384)`는 4개 행이 문장 네 개에, 384개 열이 각 문장의 숫자 표현에 대응한다는 뜻입니다. `vectors[0, :5]`는 구조를 확인하려고 첫 문장의 앞 다섯 값만 고릅니다.
## 코사인 유사도 비교
실제 문장 벡터는 길이 1로 정규화되어 있습니다. `vectors.T`는 행과 열을 바꾸고, `@`는 행렬 곱을 수행합니다. 따라서 `vectors @ vectors.T`는 모든 문장 쌍의 점곱, 곧 코사인 유사도를 4×4 배열로 반환합니다. 출력의 `0 vs i`는 항상 0번 취소 문장을 기준으로 읽습니다.
## 단어 하나 바꾸기
'취소'를 '반품'으로 바꿔 유사도가 어떻게 달라지는지 봅니다.

# temperature와 샘플링
같은 프롬프트에서 temperature를 바꾸면 반복 출력의 다양성이 어떻게 달라질까요?
Python 3.12와 잠긴 패키지를 사용합니다. 첫 실행에서는 로컬 모델을 다운로드합니다.
## 로컬 생성 모델 준비
고정 revision의 사전학습 모델을 불러옵니다. `generate()`는 프롬프트와 temperature, 난수 시드, 최대 생성 토큰 수를 입력받습니다. tokenizer가 문자열을 ID로 바꾸고 모델이 새 ID를 생성하며, decode가 새 부분을 문자열로 바꾸어 반환합니다.
## 로짓을 확률로 바꾸기
로짓은 모델이 다음 토큰 후보마다 계산한 변환 전 점수입니다. 아래의 세 값은 설명을 위해 정한 예이며 실제 Qwen에서 추출한 값이 아닙니다. 로짓을 temperature로 나눈 뒤 softmax를 적용하면 합이 1인 확률이 반환됩니다. 두 출력에서 가장 큰 후보는 유지되는지, 후보 사이의 확률 차이는 어떻게 달라지는지 읽습니다.
## temperature별 반복 생성
프롬프트, top-p, 최대 생성 길이와 시드 세 개는 고정하고 temperature만 0.3과 1.0으로 바꿉니다. 각 줄은 `temperature → seed → 반환 문자열` 순서입니다. 같은 시드끼리 두 temperature 결과를 대응해 읽은 뒤, 세 번 전체의 문자열 차이를 확인합니다.
## 서로 다른 출력 수
문자열이 정확히 같은지만 세어, 표현의 다양성을 제한적으로 관찰합니다.

입력은 실습을 위해 만든 기관·제도와 제품에 관한 두 질문입니다. 정답 자료는 제공하지 않습니다. 각 반환 문자열에서 금액·날짜·절차·제품 사양처럼 외부 확인이 필요한 주장을 먼저 표시하고, 입력에 그 근거가 있었는지 확인합니다. 자연스러운 문장인지 여부는 사실 판정 기준이 아닙니다.
## 답변 제약을 추가한 비교
정보가 주어지지 않으면 알 수 없다고 답하도록 제약을 추가합니다. 이 제약이 항상 정확한 답을 보장하지는 않습니다.
