1학습 목표
작업 폴더, 스테이징 영역, 커밋의 차이를 실제 상태 출력으로 설명할 수 있습니다.
한 가지 목적이 드러나는 커밋을 만들고 메시지로 변경 이유를 기록할 수 있습니다.
.gitignore 규칙을 적용하고 이미 추적 중인 파일을 색인에서만 제거할 수 있습니다.
2이 내용을 배우는 이유
프로그램을 수정하다 보면 소스 코드뿐 아니라 실행 로그, 캐시, 개인 설정 파일도 함께 생깁니다. 이 파일을 모두 저장하면 리뷰할 변경이 흐려지고 컴퓨터마다 다른 값이 저장소에 섞입니다. 반대로 필요한 소스까지 빠뜨리면 다른 사람이 같은 결과를 만들 수 없습니다. Git을 사용할 때 첫 판단은 “어떤 변경을 함께 설명할 것인가”와 “어떤 파일을 애초에 추적하지 않을 것인가”입니다. 이 절에서는 파일 상태를 눈으로 확인한 뒤 필요한 변경만 커밋하고, 무시 규칙이 적용되는 시점을 구분합니다.
3앞에서 배운 내용
Ch 1에서 터미널의 현재 폴더를 확인하고 Git 설치 여부를 검사했습니다. Ch 2에서는 Path.write_text()로 파일을 만들고 subprocess.run()으로 외부 명령을 실행했습니다. 이번 노트북은 이 두 기능으로 임시 Git 저장소를 만듭니다. Git 작성자 이름과 전자우편 주소는 임시 저장소의 로컬 설정에만 기록하므로 개인 설정을 바꾸지 않습니다.
4핵심 개념
사진을 찍기 전에 대상을 고릅니다
여행 사진 한 장에는 같은 순간을 설명하는 장면을 담습니다. 점심 식사와 다음 날의 기차표를 한 사진에 억지로 담으면 제목을 붙이기 어렵습니다. Git의 커밋(commit)도 선택한 파일 상태와 설명을 묶은 기록입니다. 편집기에서 저장한 app.py는 작업 폴더(working tree)에 있습니다. git add app.py를 실행하면 그 순간의 파일 상태가 다음 커밋 후보인 색인(index), 즉 스테이징 영역(staging area)에 올라갑니다. 예제 메시지의 feat, fix, chore는 변경 목적을 구분하는 팀 관례이며 Git의 필수 문법이 아닙니다. git commit -m "feat: 주문 요약 추가"를 실행하면 색인에 고른 상태가 새 커밋으로 기록됩니다.
구체적으로 app.py가 주문 2건을 출력하는 상태를 add한 뒤 작업 폴더에서 3건으로 다시 고치면, 색인에는 2건이 남고 작업 폴더에는 3건이 있습니다. 이때 커밋하면 2건 상태가 기록됩니다. git diff는 작업 폴더와 색인의 차이를, git diff --cached는 색인과 현재 커밋의 차이를 보여 줍니다. 어느 두 자리를 비교하는지 먼저 말할 수 있어야 출력의 -와 +를 올바르게 읽을 수 있습니다.
HEAD는 현재 체크아웃한 커밋을 가리킵니다. 보통 HEAD는 main 같은 브랜치 이름을 가리키고, 브랜치는 최신 커밋을 가리킵니다. 새 커밋을 만들면 현재 브랜치가 새 커밋으로 이동합니다. git log가 보여 주는 연속된 기록은 파일 사본의 목록이 아니라 부모 커밋으로 연결된 스냅샷의 이력입니다.
명령과 기호를 왼쪽부터 읽습니다
git status --short --ignored는 git 프로그램의 status 하위 명령을 실행하며, --short는 짧은 형식, --ignored는 무시된 파일도 표시하라는 옵션입니다. git commit -m "메시지"의 -m 뒤 문자열은 커밋 제목입니다. git diff -- app.py의 --는 뒤의 값을 옵션이 아닌 파일 경로로 구분합니다. 옵션을 외우기 전에 명령, 옵션, 대상 경로를 나누어 읽습니다.
.gitignore는 아직 추적하지 않은 파일 중 Git 상태 목록에서 제외할 경로 패턴을 기록합니다. .env 한 줄은 해당 이름의 환경 설정 파일을, __pycache__/는 Python 캐시 폴더를 제외합니다. 이 규칙 자체는 팀이 공유해야 하므로 커밋합니다.
도식 읽기
작업 폴더의 새 app.py와 .env는 먼저 .gitignore 규칙을 확인합니다. 추적할 app.py는 git add를 거쳐 스테이징 영역에서 선택되고 git commit으로 기록됩니다. .env는 규칙과 일치해 스테이징 대상에서 제외됩니다.
5실행 예제
준비 셀은 운영체제의 임시 폴더 아래에 orders 저장소를 만들고 기본 브랜치를 main으로 정합니다. 기본 실행 셀은 .gitignore만 스테이징해 생성 파일을 무시하는 첫 커밋을 만들고, 이어 app.py를 두 번째 커밋에 기록합니다. 함께 만든 .env는 !! .env로 표시되어 무시 규칙이 동작했음을 확인할 수 있습니다. 이 파일의 값은 자격 증명이 아닌 APP_MODE=demo입니다.
다음 셀에서는 주문 숫자만 2에서 3으로 바꿉니다. git diff의 빼기 줄과 더하기 줄을 읽으면 변경 범위가 한 줄임을 알 수 있습니다. 커밋 메시지 fix: 주문 건수 수정은 파일 이름 대신 변경 이유를 설명합니다. 실제 팀에서는 저장소가 정한 메시지 규칙을 따르되, 제목만 읽어도 의도를 파악할 수 있게 씁니다.
확인할 점 — 첫 상태 출력의 !!는 무시된 파일을 뜻합니다. 첫 두 커밋의 짧은 해시는 실행할 때마다 달라질 수 있지만, 최신 메시지 순서는 동일합니다.
6일부러 실패해 보기
debug.log를 먼저 커밋한 다음 *.log를 무시 규칙에 추가합니다. 별표 *는 파일 이름의 임의 문자열과 일치하므로 debug.log, server.log처럼 .log로 끝나는 파일을 뜻합니다. 파일을 다시 수정하면 git status에 변경 파일로 나타납니다. .gitignore는 이미 커밋한 파일의 추적 상태를 자동으로 없애지 않습니다.
수정 셀의 git rm --cached debug.log는 색인에서만 경로를 제거합니다. 작업 폴더의 실제 파일은 남아 있으며 tracked.exists()가 True로 출력됩니다. 제거와 무시 규칙을 함께 커밋한 뒤 로그 내용을 바꾸어도 추적 파일 목록에는 나타나지 않습니다. git check-ignore -v는 어떤 규칙이 해당 파일에 적용됐는지 줄 번호와 함께 보여 줍니다.
7주의할 점과 실무 메모
.gitignore는 보안 도구가 아닙니다. 실수로 커밋한 자격 증명을 이 파일에 추가해도 과거 이력은 남습니다. 이 문제는 05절에서 따로 다룹니다.
git add .를 사용하기 전에 git status --short와 git diff를 읽습니다. 예상하지 않은 생성 파일과 디버그 문장이 포함됐는지 확인합니다.
서식 변경과 기능 변경이 섞이면 리뷰어가 실제 동작 차이를 찾기 어렵습니다. 가능한 경우 목적별 커밋으로 나눕니다.
git rm --cached는 다음 커밋에서 저장소의 파일을 제거합니다. 팀원이 필요한 공용 설정이라면 무시하지 말고 민감한 값만 비운 예시 파일을 제공합니다.
8정리와 다음 절
작업 폴더에서 수정한 내용 중 다음 기록에 포함할 상태를 스테이징 영역에서 고릅니다.
커밋은 한 가지 변경 목적과 그 목적을 설명하는 메시지를 함께 기록합니다.
.gitignore는 새 파일의 추적을 예방하며 이미 추적 중인 파일에는 소급 적용되지 않습니다.
다음 학습과 이어지는 지점 — 다음 절에서는 목적이 분명한 커밋을 기능 브랜치에 쌓고, 원격에 게시한 변경을 PR 단위로 비교하고 검토합니다.
9복습 문제
문제와 해설
1. git add와 git commit은 각각 어느 상태를 바꿉니까?
정답: git add는 현재 파일 내용을 스테이징 영역에 선택하고, git commit은 선택된 상태를 새 이력으로 기록합니다.
2. 노트북에서 .env가 !!로 표시된 이유는 무엇입니까?
정답: .gitignore의 .env 규칙과 일치해 Git이 무시한 파일이기 때문입니다.
3. 이미 커밋한 debug.log가 *.log 추가 뒤에도 변경 파일로 나타나는 이유는 무엇입니까?
정답: 무시 규칙은 아직 추적하지 않은 파일에 적용됩니다. debug.log는 이미 추적 중이므로 상태가 유지됩니다.
4. 작업 폴더의 로그 파일을 보존하면서 추적만 중단한 명령은 무엇입니까?
정답: git rm --cached debug.log입니다. --cached가 색인에서만 제거하도록 지정합니다.

1학습 목표
GitHub Flow에서 main 브랜치와 기능 브랜치의 역할을 구분할 수 있습니다.
기능 브랜치를 원격에 게시하고 기준 브랜치와의 차이를 읽을 수 있습니다.
PR 설명과 코드 리뷰 의견을 근거로 코드를 수정하고 병합할 수 있습니다.
2이 내용을 배우는 이유
여러 사람이 같은 저장소에서 바로 main을 수정하면 아직 검토하지 않은 코드가 다른 작업의 출발점이 됩니다. 기능마다 브랜치를 만들면 완성 전 작업을 기본 흐름과 분리할 수 있습니다. 풀 리퀘스트(Pull Request, PR)는 한 브랜치의 변경을 다른 브랜치에 합치자고 제안하며 변경 이유와 검증 결과를 함께 검토하는 GitHub 협업 단위입니다. 이 절에서는 직접 편집하는 작업 폴더가 없는 로컬 bare 저장소를 원격처럼 사용해 게시와 병합을 실제로 수행하고 PR 화면이 담당하는 절차를 파일과 명령 출력으로 재현합니다.
3앞에서 배운 내용
앞 절에서 한 가지 목적을 가진 커밋을 만들고 git log로 기록을 읽었습니다. 이번 노트북은 새 커널에서 별도의 임시 저장소를 만들고, 같은 커밋 원칙을 feature/order-summary 브랜치에 적용합니다. Ch 2의 함수 절에서 배운 입력과 반환값을 사용해 주문 건수를 문장으로 바꾸는 summarize() 함수를 작성합니다. 실제 GitHub 계정과 네트워크는 사용하지 않습니다. 따라서 PR 번호, 온라인 댓글, 승인 상태는 생성되지 않습니다.
4핵심 개념
검토 가능한 통로를 만듭니다
공용 문서를 고칠 때 사본에서 수정하고 변경 표시를 남기면 검토자는 수정된 문장에 집중할 수 있습니다. GitHub Flow는 배포 가능한 기본 브랜치를 유지하고, 짧게 사용하는 기능 브랜치에서 변경한 뒤 Pull Request로 검토하고 다시 기본 브랜치에 병합하는 작업 방식입니다. 브랜치(branch)는 프로젝트 폴더의 복사본이 아니라 특정 커밋을 가리키는 이름입니다. main에서 git switch -c feature/order-summary를 실행하면 새 이름이 현재 커밋을 함께 가리킵니다. 기능 브랜치에서 summary.py를 커밋하면 기능 브랜치만 새 커밋으로 이동하고 main은 이전 커밋에 남습니다.
원격(remote)은 다른 Git 저장소의 위치에 붙인 이름입니다. origin은 최초 복제한 원격에 관례적으로 붙는 이름일 뿐 특별한 서버 종류가 아닙니다. git push -u origin feature/order-summary에서 push는 로컬 커밋과 브랜치 위치를 보내고, -u는 이후 push와 pull이 참조할 추적 관계를 설정하며, 마지막 인자는 보낼 브랜치입니다. 작업 폴더에서만 고친 미커밋 파일은 push되지 않습니다.
origin/main은 원격 서버를 실시간으로 읽는 이름이 아니라 마지막 fetch에서 로컬이 확인한 원격 main의 위치입니다. git fetch origin을 실행하면 원격의 새 객체와 원격 추적 브랜치가 갱신됩니다. 이 구분 때문에 리뷰어는 fetch 뒤에 새 기능 커밋을 볼 수 있습니다.
merge와 rebase는 이력 모양이 다릅니다
병합(merge)은 두 커밋 흐름을 합치며 필요하면 부모가 둘인 병합 커밋을 만듭니다. fast-forward는 현재 브랜치 이름을 기존 자손 커밋으로 앞으로 옮기기만 하면 되는 관계입니다. git merge --no-ff origin/feature/order-summary의 --no-ff는 이 단순 이동이 가능해도 병합 커밋을 만들라는 옵션입니다. 리베이스(rebase)는 한 브랜치의 커밋을 다른 기준 커밋 위에서 다시 만들어 직선 이력으로 정리하므로 커밋 해시가 달라집니다.
git diff --stat origin/main...HEAD의 점 세 개는 두 참조의 공통 조상부터 현재 HEAD까지 기능 브랜치가 추가한 변경을 비교합니다. --stat은 파일별 줄 수 요약만 보여 주므로 리뷰에서는 이어서 실제 diff와 실행 결과를 확인합니다.
코드 리뷰(code review)는 작성자와 다른 사람이 변경 내용을 읽고 결함, 이해하기 어려운 부분, 테스트 누락을 확인하는 과정입니다. GitHub 리뷰는 댓글과 함께 승인, 변경 요청, 일반 의견 같은 결론을 남길 수 있습니다. 실습에서는 화면 기능 대신 실제 diff를 읽고 리뷰 문장을 출력한 뒤 수정 커밋을 원격에 게시합니다.
도식 읽기
main에서 feature/order-summary 기능 브랜치를 만들고 원격에 게시합니다. 로컬 PR 리뷰 모의 단계에서는 main...feature 차이를 읽습니다. 리뷰 의견을 반영한 수정 커밋을 다시 확인한 뒤 검토된 변경을 main에 병합하고 원격을 갱신합니다.
5실행 예제
준비 셀은 team.git이라는 bare 저장소와 author 작업 폴더를 만듭니다. bare 저장소는 Git 객체와 참조만 보관하고 직접 편집하는 작업 폴더는 두지 않는 저장소입니다. git remote -v의 경로 앞부분은 실행마다 달라지는 임시 폴더이며, 확인할 값은 원격 이름 origin과 가져오기·보내기 경로가 같은 team.git을 가리킨다는 사실입니다.
git diff --stat origin/main...HEAD에서 점 세 개는 두 브랜치의 공통 조상 이후 기능 브랜치가 만든 변경을 비교합니다. 출력에는 summary.py 한 파일의 줄 수가 나타납니다. 기본 브랜치에 미리 둔 템플릿을 읽어 변경 내용과 확인 항목을 채우므로 다음 PR에서도 같은 질문을 빠뜨리지 않게 돕습니다. 이 출력은 PR 화면이 아닙니다. GitHub가 PR에 표시할 핵심 변경 범위를 로컬 Git으로 확인한 결과입니다.
확인할 점 — 작성자 저장소의 기능 브랜치가 origin/feature/order-summary를 추적합니다. PR 템플릿은 origin/main에 미리 있고 기능 코드는 기능 브랜치에만 있습니다.
6일부러 실패해 보기
리뷰어는 별도 폴더에 원격 저장소를 복제하고 기능 브랜치를 읽습니다. 기존 함수는 전달된 값을 그대로 문자열에 넣기 때문에 빈 문자열에도 주문 건을 반환합니다. 명령이 성공했다는 사실과 기능 요구가 충족됐다는 판단은 다릅니다. 리뷰 의견은 “count가 빈 문자열이면 주문 건수가 비어 보입니다”처럼 입력, 관찰 결과, 기대 조건을 함께 적어야 작성자가 문제를 재현할 수 있습니다.
작성자는 매개변수에 int 타입힌트를 붙이고 실행 중에도 isinstance()로 정수 여부를 검사합니다. 수정 커밋을 같은 기능 브랜치에 push하면 PR의 변경 범위도 갱신됩니다. 리뷰어 저장소가 fetch로 새 커밋을 가져온 뒤 main에서 기능 브랜치를 병합합니다. 마지막 그래프에 부모가 둘인 병합 커밋이 나타나고 수정된 파일에서 TypeError를 확인합니다. GitHub에서라면 보호 규칙과 리뷰 상태를 확인한 뒤 병합 버튼을 사용하지만, 이 실습은 Git 명령으로 동일한 브랜치 결합만 확인합니다.
Ch 2의 07절에서 배운 count: int와 -> str은 입력과 반환값의 예상 자료형을 표시하지만 실행 중 값을 검사하지 않습니다. isinstance(count, int)는 현재 count가 정수 유형인지 확인하여 True 또는 False를 반환합니다. 이 결과가 거짓이면 raise TypeError로 잘못된 입력을 알립니다.
7주의할 점과 실무 메모
이 실습은 로컬 원격을 사용한 PR 리뷰 모의 실습입니다. 실제 GitHub PR, 승인, 변경 요청 상태를 생성하지 않습니다.
기능 브랜치는 오래 유지할수록 main과 차이가 커집니다. 검토 가능한 크기로 자주 게시하고 팀이 정한 방식으로 기준 브랜치 변경을 반영합니다.
PR 설명의 확인란은 테스트 실행을 대신하지 않습니다. 어떤 명령을 어떤 환경에서 실행했고 결과가 무엇인지 함께 기록합니다.
리뷰 의견은 작성자를 평가하는 문장보다 코드의 위치, 재현 입력, 관찰 결과, 기대 동작을 구체적으로 적습니다.
병합 방법은 merge commit, squash, rebase 중 저장소 정책을 따릅니다. 이 절은 두 부모를 남기는 --no-ff 병합으로 흐름을 눈에 보이게 합니다.
8정리와 다음 절
GitHub Flow에서는 기능 브랜치에서 변경하고 PR로 차이와 확인 방법을 검토합니다.
리뷰 가능한 PR은 작은 변경 범위, 재현 가능한 설명, 실제 확인 결과를 함께 제공합니다.
리뷰 의견을 반영한 커밋은 같은 기능 브랜치에 추가되고 검토 뒤 기본 브랜치에 병합됩니다.
다음 학습과 이어지는 지점 — 다음 절에서는 기능 브랜치와 main이 같은 줄을 다르게 수정했을 때 Git이 자동 병합을 중단하는 이유와 해결 절차를 확인합니다. W3부터 이어지는 코드 리뷰에서도 충돌 결과의 업무 의미를 함께 검토합니다.

1학습 목표
공통 커밋 이후 두 이력의 변경을 비교해 충돌 원인을 설명할 수 있습니다.
충돌 표시에서 현재 로컬 브랜치와 병합 대상 이력의 내용을 구분할 수 있습니다.
업무 의도를 반영한 결과로 파일을 수정하고 병합 커밋을 완성할 수 있습니다.
2이 내용을 배우는 이유
Git은 서로 다른 파일이나 서로 떨어진 줄의 변경을 대체로 자동으로 합칩니다. 그러나 두 사람이 같은 줄을 다른 내용으로 바꾸면 어느 문장이 맞는지 코드만 보고 판단할 수 없습니다. 최신 커밋을 무조건 고르거나 두 문장을 모두 남기는 선택도 업무 요구와 맞지 않을 수 있습니다. 충돌은 Git이 실패한 상태가 아니라 사람의 판단이 필요한 위치를 표시하고 병합을 멈춘 상태입니다. 개발자는 표시를 제거하는 데서 끝내지 않고, 두 변경의 목적을 확인한 뒤 최종 동작을 선택하고 검사해야 합니다.
3앞에서 배운 내용
앞 절에서 원격에 게시한 커밋과 로컬 작업이 서로 다른 이력이 될 수 있음을 확인했습니다. 이번 노트북은 message.txt의 첫 문장을 공통 시작점으로 커밋합니다. Alice는 원격 main의 같은 줄을 “오늘 출고”로 바꾸고, Bob은 이전 커밋에서 시작한 로컬 main을 “내일 출고”로 바꿉니다. 실제 서비스 코드는 아니지만 동일한 줄의 업무 문구를 두 사람이 수정하는 충돌 조건을 정확히 재현합니다.
4핵심 개념
갈라진 두 편집본을 다시 맞춥니다
공동 문서의 같은 문장을 두 사람이 각자 고치면 최종 문장은 실제 업무 기준을 담아야 합니다. 병합(merge)은 갈라진 두 커밋 흐름의 파일 변화를 한 결과로 합치는 작업입니다. Git은 두 이력이 함께 출발한 공통 조상(merge base), 현재 로컬 브랜치의 변경, 병합 대상의 변경을 비교합니다. Alice와 Bob이 같은 출발 커밋의 같은 줄을 다르게 바꾸면 어느 문장이 맞는지 알 수 없어 병합 충돌(merge conflict)로 멈춥니다.
먼저 Bob의 git push origin main이 non-fast-forward로 거절됩니다. 원격 main에는 Alice의 새 커밋이 있고 Bob의 브랜치에는 그 커밋이 없기 때문입니다. fast-forward는 현재 참조를 기존 자손 커밋으로 앞으로 옮기기만 하면 되는 관계입니다. Bob의 커밋과 Alice의 커밋은 서로 다른 자손이라 단순 이동으로 합칠 수 없습니다.
git pull --no-rebase origin main은 두 단계를 수행합니다. 먼저 원격 객체를 가져오고(fetch), 이어서 현재 Bob 브랜치에 원격 main을 병합합니다. --no-rebase는 Bob의 커밋을 Alice 커밋 위에서 다시 만들지 않고 병합하라는 뜻입니다. 충돌이 나면 명령은 실패로 끝나지만 저장소가 망가진 것은 아닙니다. 색인에 해결되지 않은 경로가 표시되고 작업 파일에 양쪽 후보가 남습니다.
충돌 표시를 파일 변화로 읽습니다
<<<<<<< HEAD 아래는 현재 Bob 브랜치의 내용, ======= 아래부터 >>>>>>>까지는 병합하려는 원격 변경입니다. 표시 세 줄만 삭제하고 한쪽 문장을 무조건 고르면 문법상 병합은 끝나도 업무 규칙은 틀릴 수 있습니다. 이 실습은 policy.txt의 두 출고 조건을 읽고 “14시 이전 결제는 오늘 출고, 14시 이후 결제는 내일 출고”라는 새 문장으로 합칩니다.
해결한 message.txt를 git add하면 Git은 그 경로의 충돌을 해결했다고 색인에 표시합니다. git commit은 Alice 쪽 부모와 Bob 쪽 부모를 함께 가진 병합 커밋을 만듭니다. 출력의 부모 해시가 두 개라는 사실이 두 흐름을 보존한 증거입니다.
도식 읽기
공통 main에서 Alice와 Bob의 변경이 같은 줄을 다르게 수정합니다. Bob의 push 거부와 pull 충돌 뒤에는 policy.txt의 출고 기준을 근거로 새 문장을 작성합니다. 해결 커밋을 원격 main에 게시하면 두 부모를 가진 병합 커밋이 됩니다.
5실행 예제
준비 셀은 공통 안내를 원격에 게시한 직후 Bob의 작업 폴더를 복제합니다. 그 뒤 Alice가 같은 줄을 배송 안내: 14시 이전은 오늘 출고로 바꾸어 push하고, Bob은 자신이 받은 공통 커밋에서 배송 안내: 내일 출고로 바꿉니다. 두 변경이 같은 부모에서 자연스럽게 갈라지므로 브랜치 위치를 따로 옮길 필요가 없습니다.
이 단계에서 두 이력이 갈라졌다는 사실만으로 충돌이 확정되는 것은 아닙니다. 서로 다른 파일을 수정했거나 같은 파일의 서로 떨어진 줄을 수정했다면 자동 병합될 수 있습니다. 이번 실습에서는 같은 한 줄을 서로 다른 문자열로 바꿨다는 조건 때문에 충돌이 발생합니다.
확인할 점 — Alice의 최신 log에는 “당일 출고 안내”와 그 아래 “출고 기준 기록”이 있습니다. Bob의 첫 push 종료 코드는 0이 아니며 아직 원격 변경을 통합하지 않았음을 보여 줍니다.
6일부러 실패해 보기
Bob의 로컬 main에서 git pull --no-rebase origin main을 실행하면 종료 코드가 0이 아닌 값으로 나타납니다. git status --short의 UU는 양쪽에서 수정된 파일이 아직 해결되지 않았음을 뜻합니다. 파일에는 Bob의 “내일 출고”와 원격 main에서 가져온 Alice의 “오늘 출고”가 충돌 표시와 함께 들어 있습니다. 이 출력은 예외 문장을 흉내 낸 것이 아니라 Git이 실제 병합을 중단한 결과입니다.
수정 셀은 운영 규칙을 한 문장에 반영해 배송 안내: 14시 이전 결제는 오늘 출고, 14시 이후 결제는 내일 출고로 바꿉니다. 양쪽 문장을 단순히 이어 붙이는 대신 서로 다른 약속이 적용되는 조건을 명시합니다. 실제 업무에서는 결제 마감 시각과 휴일 규칙까지 제품 담당자에게 확인해야 합니다. 파일을 스테이징하고 병합 커밋을 만든 뒤 상태가 깨끗한지, 충돌 표시가 사라졌는지, 부모 해시가 두 개인지 검사합니다.
7주의할 점과 실무 메모
충돌 표시를 지웠다는 사실만으로 해결이 끝나지 않습니다. 문법 검사와 테스트를 실행하고 최종 문장이 두 변경 목적을 충족하는지 확인합니다.
현재 병합을 취소하고 시작 전 상태로 돌아가려면 해결 커밋 전에 git merge --abort를 사용할 수 있습니다. 작업 폴더의 다른 변경이 있으면 먼저 상태를 확인합니다.
--ours와 --theirs는 파일 전체를 한쪽 버전으로 선택합니다. 여러 변경이 섞인 파일에 무심코 적용하면 필요한 상대편 변경도 사라질 수 있습니다.
생성 파일과 잠금 파일의 충돌 해결 방식은 프로젝트 정책을 따릅니다. 원본 설정을 합친 뒤 도구로 다시 생성해야 하는 파일도 있습니다.
충돌을 줄이려면 기능 브랜치를 짧게 유지하고 큰 파일의 같은 영역을 동시에 수정하는 작업은 먼저 담당 범위를 조율합니다.
8정리와 다음 절
Git은 공통 조상과 두 이력의 변경을 비교하며 자동 선택할 수 없는 부분에서 병합을 멈춥니다.
충돌 표시는 현재 로컬 브랜치와 병합 대상 이력의 내용을 구분하며 최종 파일에는 남기지 않습니다.
해결 결과는 업무 의도를 반영해야 하고 스테이징·테스트·병합 커밋으로 검증합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 병합 뒤 공개된 잘못된 변경을 새 커밋으로 되돌리고, 로컬에서 보이지 않게 된 커밋을 reflog로 찾아 복구합니다.
9복습 문제
문제와 해설
1. 두 이력이 갈라지면 항상 충돌합니까?
정답: 아닙니다. Git이 변경을 자동 결합할 수 있으면 충돌하지 않습니다. 이 실습은 같은 파일의 같은 줄을 다르게 수정해 충돌했습니다.
2. UU message.txt는 무엇을 뜻합니까?
정답: 현재 로컬 main과 원격에서 가져온 이력이 모두 수정한 message.txt가 아직 해결되지 않았음을 뜻합니다.
3. 실습에서 두 문장 중 하나만 선택하지 않은 이유는 무엇입니까?
정답: 오늘과 내일 출고가 결제 시각이라는 조건에 따라 모두 필요하다고 판단해 조건을 포함한 새 문장으로 통합했기 때문입니다.
4. 마지막 셀에서 병합 커밋의 부모 수를 검사하는 이유는 무엇입니까?
정답: 충돌 해결 결과가 두 갈래의 이력을 결합한 병합 커밋으로 기록됐는지 확인하기 위해서입니다.

1학습 목표
공유된 변경과 로컬 변경의 상태에 따라 revert와 이력 이동을 구분할 수 있습니다.
reflog에서 사라진 커밋의 참조 이동 기록을 찾아 새 브랜치로 복구할 수 있습니다.
worktree로 한 저장소의 서로 다른 브랜치를 별도 작업 폴더에서 열 수 있습니다.
2이 내용을 배우는 이유
코드를 되돌린다는 말에는 서로 다른 상황이 섞여 있습니다. 팀이 이미 받은 커밋의 효과를 취소해야 할 수도 있고, 내 컴퓨터에서 실수로 브랜치 이름을 옮겨 커밋이 보이지 않을 수도 있습니다. 작업 중인 긴 기능을 그대로 둔 채 긴급 수정을 별도 폴더에서 처리해야 할 때도 있습니다. 모든 상황에 reset --hard를 사용하면 공유 이력을 다시 쓰거나 아직 저장하지 않은 변경을 잃을 수 있습니다. 이 절에서는 이력을 보존하는 취소, 로컬 참조 기록을 이용한 복구, 여러 작업 폴더의 분리를 각각 실제 커밋으로 확인합니다.
3앞에서 배운 내용
앞 절에서 브랜치가 커밋을 가리키는 이름이고 병합 커밋은 두 부모를 가질 수 있음을 확인했습니다. 여기서는 직선 이력에서 할인율을 잘못 바꾼 커밋을 만들고 그 효과를 되돌립니다. Path와 임시 폴더를 사용하므로 실제 프로젝트 파일은 수정하지 않습니다. reset --hard는 실패 재현용 임시 브랜치에서만 실행합니다.
4핵심 개념
공유 기록은 남기고 반대 변경을 추가합니다
공용 장부의 잘못된 항목을 지우기보다 취소 항목을 다음 줄에 기록하면 무엇이 있었고 왜 취소했는지 모두 확인할 수 있습니다. git revert는 지정한 커밋의 변경을 반대로 적용한 새 커밋을 만듭니다. discount=10을 90으로 바꾼 커밋을 revert하면 작업 파일은 다시 10이 되지만 90 커밋은 사라지지 않습니다. “90으로 변경”, “그 변경을 취소”라는 두 사건이 모두 이력에 남습니다. git revert --no-edit bad에서 bad는 취소할 커밋 해시를 담은 변수이고 --no-edit는 Git의 기본 되돌림 메시지를 그대로 사용합니다.
git reset은 현재 브랜치가 가리키는 위치를 옮깁니다. git reset --hard HEAD~1에서 HEAD~1은 현재 커밋의 첫 번째 부모 한 단계 전이며, --hard는 브랜치뿐 아니라 색인과 작업 폴더까지 그 커밋 상태로 맞춥니다. 따라서 커밋하지 않은 파일 변화도 사라질 수 있습니다. 실습은 임시 저장소의 미공유 커밋에만 사용합니다.
reflog(reference log)는 이 로컬 저장소에서 HEAD와 브랜치 참조가 어디로 이동했는지 기록합니다. reset 뒤 일반 git log는 현재 브랜치에서 도달하는 커밋만 보여 주므로 아이디어 커밋이 보이지 않습니다. reflog에는 reset 전 HEAD 위치가 남아 있어 해당 해시에 recovered-idea라는 브랜치 이름을 붙일 수 있습니다. reflog는 만료될 수 있는 로컬 복구 단서이며 원격 백업을 대신하지 않습니다.
worktree는 브랜치마다 작업 폴더를 분리합니다
worktree는 한 저장소의 객체 이력을 공유하면서 다른 브랜치를 별도 폴더에 체크아웃하는 기능입니다. git worktree add -b fix/urgent urgent-fix에서 add는 새 작업 폴더를 추가하고, -b fix/urgent는 새 브랜치를 만들며, urgent-fix는 폴더 경로입니다. 기본 폴더의 main 작업을 그대로 둔 채 추가 폴더에서 긴급 수정 커밋을 만들 수 있습니다. 별도 복제본과 달리 객체 저장소와 참조 관리 정보는 함께 사용합니다.
세 도구는 순서대로 실행하는 복구 절차가 아닙니다. 공유된 잘못된 커밋의 효과를 취소하려면 revert, 로컬에서 보이지 않게 된 커밋의 위치를 찾으려면 reflog, 두 브랜치를 동시에 편집하려면 worktree를 선택합니다.
도식 읽기
세 행은 순서대로 실행하는 절차가 아니라 서로 다른 상황을 보여 줍니다. 공유한 변경을 취소할 때는 revert로 반대 변경을 새 커밋에 기록합니다. 로컬 커밋을 다시 찾을 때는 reflog에서 참조 이동을 확인합니다. 두 브랜치를 함께 작업할 때는 worktree로 브랜치별 작업 폴더를 만듭니다.
5실행 예제
저장소는 정상 설정 discount=10을 먼저 커밋합니다. 다음 커밋이 값을 90으로 바꾸면 git revert가 반대 패치를 적용해 파일 내용을 다시 10으로 만듭니다. 출력의 최신 세 커밋에는 되돌림, 잘못된 변경, 최초 설정이 모두 남습니다. 잘못된 커밋을 이력에서 지운 것이 아니라 효과를 상쇄한 것입니다.
다음 셀은 urgent-fix 폴더에 fix/urgent 브랜치를 연결합니다. 기본 폴더는 main, 추가 폴더는 fix/urgent를 가리킵니다. 두 폴더는 객체 데이터베이스를 공유하지만 작업 파일은 별도로 가집니다. 긴급 수정이 끝나면 변경을 커밋하고 병합한 뒤 git worktree remove로 추가 폴더를 정리할 수 있습니다.
확인할 점 — revert 뒤 파일 값은 10이지만 잘못된 90 커밋도 log에 남습니다. worktree 출력의 임시 경로는 실행마다 달라집니다. 경로 문자열 대신 기본 폴더의 브랜치가 main, 추가 폴더의 브랜치가 fix/urgent인지 확인합니다.
6일부러 실패해 보기
experiment 브랜치에서 idea.txt를 커밋한 뒤 git reset --hard HEAD~1을 실행합니다. 브랜치가 이전 커밋으로 이동하고 작업 폴더도 그 상태에 맞춰지므로 파일이 사라집니다. 현재 브랜치에서 시작하는 일반 log에는 아이디어 커밋이 나타나지 않습니다. 실습은 복구 결과를 검사하기 위해 원래 커밋 해시를 별도 변수에 보관하지만, 실제 복구 명령은 reflog 출력에서 찾은 후보를 사용해야 합니다.
git reflog --format=%H%x09%gs -5는 최근 5개 행을 전체 해시, 탭 문자, 이동 이유 순서로 출력합니다. reflog.splitlines()는 행 목록을 반환하고, next(...)는 메시지에 commit: experiment: 복구할 아이디어가 포함된 첫 행을 고릅니다. line.split("\t", 1)[0]은 첫 번째 탭에서 최대 한 번 나눈 뒤 탭 앞의 해시를 반환합니다. 그 해시로 recovered-idea 브랜치를 만들고 idea.txt의 recover me를 확인합니다.
7주의할 점과 실무 메모
팀이 이미 받은 커밋에 reset과 강제 push를 적용하면 협업자의 이력이 갈라질 수 있습니다. 공개 변경 취소에는 저장소 정책에 따라 revert를 우선 검토합니다.
revert가 항상 자동 성공하는 것은 아닙니다. 이후 커밋이 같은 줄을 바꿨다면 반대 패치를 적용하는 과정에서도 충돌할 수 있습니다.
reflog는 각 로컬 저장소의 참조 이동 기록입니다. 다른 사람의 reflog나 삭제된 컴퓨터의 기록을 원격에서 조회할 수 없습니다.
reset --hard는 커밋하지 않은 작업 폴더 변경까지 덮어쓸 수 있습니다. 대상 저장소와 현재 상태를 확인한 뒤 사용합니다.
worktree 폴더를 파일 탐색기에서 바로 삭제하면 관리 정보가 남을 수 있습니다. git worktree remove와 git worktree prune을 상황에 맞게 사용합니다.
8정리와 다음 절
revert는 기존 커밋 효과를 취소하는 새 커밋을 만들어 공유 이력을 보존합니다.
reflog는 로컬 참조 이동을 기록하며 보이지 않게 된 커밋을 찾는 단서가 될 수 있습니다.
worktree는 한 저장소의 여러 브랜치를 서로 다른 작업 폴더에 연결합니다.
다음 학습과 이어지는 지점 — 다음 절에서는 일반 코드가 아니라 자격 증명이 이력에 들어간 경우를 다룹니다. 파일을 되돌리는 것만으로 부족한 이유와 이력 재작성 뒤 필요한 키 교체·협업 조치를 확인합니다.

문제와 해설
1. 공개된 잘못된 커밋을 revert하면 기존 커밋은 사라집니까?
정답: 사라지지 않습니다. 기존 변경과 반대되는 새 커밋이 추가되어 파일 효과를 취소합니다.
2. 일반 log에서 아이디어 커밋이 보이지 않았지만 reflog에서 찾을 수 있었던 이유는 무엇입니까?
정답: reset으로 현재 브랜치가 이전 위치로 이동했지만 로컬 reflog에는 이동 전 참조 위치가 남아 있었기 때문입니다.

정답: 로컬 기록이며 만료와 객체 정리 정책에 따라 삭제될 수 있기 때문입니다.
4. worktree를 사용한 두 폴더의 브랜치는 각각 무엇입니까?

1학습 목표
파일 삭제와 Git 이력에서 경로를 제거하는 작업의 차이를 설명할 수 있습니다.
격리된 더미 저장소에서 git-filter-repo로 특정 경로의 이력을 재작성할 수 있습니다.
실제 자격 증명 노출 시 폐기·교체, 협업 조율, 예방 검사가 모두 필요한 이유를 설명할 수 있습니다.
2이 내용을 배우는 이유
API 키나 접근 토큰을 커밋한 뒤 현재 파일에서 삭제하면 작업 폴더에는 보이지 않습니다. 그러나 이전 커밋을 읽을 수 있는 사람은 여전히 값을 찾을 수 있습니다. 공개 저장소의 복제본, 포크, 캐시, 빌드 로그로 값이 복사됐을 가능성도 있습니다. 따라서 실제 자격 증명 사고의 첫 조치는 Git 명령이 아니라 발급 서비스에서 값을 폐기하거나 교체하는 일입니다. 이력 정리는 노출 범위를 줄이고 저장소를 정돈하는 후속 조치입니다. 이 절은 실제로 사용할 수 없는 더미 문자열과 임시 원격만 사용해 파일 삭제가 부족한 이유를 관찰하고, 예방과 대응의 순서를 구분합니다.
3앞에서 배운 내용
01절에서 .gitignore가 아직 추적하지 않는 파일을 제외하며 과거 이력에는 소급 적용되지 않음을 확인했습니다. 02절에서는 원격에 push한 커밋이 다른 저장소로 복제될 수 있음을 확인했습니다. 04절에서는 공개 이력을 보존하는 revert를 배웠습니다. 자격 증명은 이전 커밋에서도 읽을 수 없어야 하므로 일반 revert만으로 해결되지 않습니다. 이번 실습의 문자열 DEMO-ONLY-NOT-A-REAL-SECRET은 어떤 서비스에서도 인증에 사용할 수 없는 교육용 표시입니다.
4핵심 개념
복사된 열쇠는 문에서 무효화합니다
출입 열쇠 사진이 공개됐다면 게시물을 지우기 전에 기존 열쇠가 문을 열지 못하게 해야 합니다. 시크릿(secret)은 API 키, 접근 토큰, 비밀번호처럼 권한을 부여하는 값입니다. 실제 값이 공개되면 먼저 발급 서비스에서 폐기하거나 교체합니다. .env를 작업 폴더에서 삭제하고 다음 커밋에 기록해도 이전 커밋 객체에는 과거 내용이 남습니다. git show <커밋>:.env에서 콜론 앞은 읽을 커밋, 뒤는 그 커밋 안의 파일 경로입니다.
.gitignore는 아직 추적하지 않는 파일이 기본 add 대상에 포함되지 않게 합니다. git check-ignore -v .env의 -v는 적용된 규칙과 규칙 파일을 표시합니다. git ls-files .env가 비어 있으면 색인에 등록되지 않았다는 뜻입니다. 이미 커밋한 파일, 로그에 출력한 값, 채팅이나 빌드 시스템으로 복사된 값에는 이 규칙이 소급 적용되지 않습니다.
실제 값이 공개됐다면 먼저 발급 서비스에서 폐기(revoke)하거나 교체(rotate)합니다. 저장소 이력을 정리하는 동안 누군가 이미 값을 복사했을 수 있기 때문입니다. 값의 권한을 없앤 뒤 저장소 관리자와 이력 재작성 범위를 정하고, 호스팅 서비스의 캐시·포크·열린 PR에 대한 제거 절차를 확인합니다.
이력 재작성 명령의 대상을 읽습니다
이력 재작성(history rewriting)은 조건에 맞는 새 커밋 이력을 만드는 작업입니다. git-filter-repo는 이를 수행하는 도구입니다. git filter-repo --path .env --invert-paths에서 --path .env는 선택할 경로를 지정하고, --invert-paths는 선택을 반대로 바꾸어 그 경로를 제외합니다. 파일이 포함됐던 커밋과 그 뒤 자손의 해시가 달라집니다.
git clone --mirror는 일반 작업 폴더 없이 브랜치와 태그 등 참조를 넓게 복제합니다. 정리 뒤 git push --force --mirror는 원격 참조를 새 이력에 맞춰 강제로 갱신합니다. --force는 협업자의 기존 이력과 충돌할 수 있으므로 실제 저장소에서는 관리자 조율과 백업·검증 없이 실행하지 않습니다. 실습 출력의 경로 없음과 값 커밋 0건은 임시 mirror에서 검사한 참조 범위만 증명합니다.
예방은 여러 층으로 구성합니다. .gitignore로 흔한 환경 파일을 제외하고, 값이 비어 있는 settings.example을 공유하며, 커밋 전에 스테이징한 변경을 직접 읽습니다. 저장소의 시크릿 검사 도구와 호스팅 서비스의 차단 기능도 사용합니다. 한 층이 누락을 발견하면 실제 원격에 게시되기 전에 멈출 수 있습니다.
도식 읽기
실제 유출에서는 제공자에서 자격 증명을 먼저 폐기·교체합니다. 그 뒤 저장소 관리자와 협업자가 재작성 범위를 정하고 이력을 정리·원격 갱신한 뒤 새 이력을 다시 받습니다. 이 노트북은 외부 서비스의 폐기·교체를 실행하지 않으며, 더미 문자열의 경로·값이 격리된 원격의 검사 범위에서 사라졌는지만 확인합니다.
5실행 예제
준비 셀은 임시 bare 원격과 작업 저장소를 만들고 안전한 앱을 main에 게시합니다. 자격 증명 역할을 하는 변수 이름을 사용하지만 값은 명백한 더미입니다. 다음 셀은 .env를 무시하도록 설정하고 git check-ignore -v로 실제 적용 규칙을 확인합니다. git ls-files .env가 빈 문자열이므로 색인에 포함되지 않았습니다.
공유 가능한 settings.example에는 실제 값 대신 replace-me를 적습니다. 커밋 전에 git diff --cached를 읽고 더미 자격 증명 문자열조차 포함되지 않았는지 검사합니다. 실제 조직에서는 알려진 접두사, 문자열의 무작위성 정도, 제공자 규칙을 검사하는 전용 도구를 함께 사용합니다. 문자열 한 개를 검사한 이번 셀이 모든 종류의 시크릿을 찾는다고 해석해서는 안 됩니다.
확인할 점 — .env는 무시되고 설정 예시만 커밋됩니다. 예시 파일은 필요한 변수 이름을 알려 주되 권한을 가진 값을 포함하지 않습니다.
6일부러 실패해 보기
실패 셀은 교육 목적을 분명히 하기 위해 git add -f로 무시 규칙을 우회하고 더미 .env를 커밋합니다. 다음 커밋에서 파일을 삭제하고 원격에 push합니다. 현재 작업 폴더에는 파일이 없지만 git show 커밋:.env는 이전 내용을 반환합니다. 이것이 “현재 파일 삭제”와 “이력에서 제거”가 다른 실제 증거입니다. 실제 시크릿으로 이 과정을 따라 하면 노출이 더 확대되므로 절대 사용하지 않습니다.
수정 셀의 git filter-repo --force에서 --force는 새 복제본인지 확인하는 안전 검사를 완화합니다. 이 실습은 방금 만든 임시 mirror에만 사용합니다. git rev-list --objects --all의 각 행은 객체 해시와 경로를 담습니다. objects.splitlines()가 행 목록을 만들고 line.endswith(" .env")가 경로가 정확히 .env로 끝나는지 검사하며, any(...)는 일치 행이 하나라도 있을 때만 True를 반환합니다. 출력 False와 더미 값 커밋 0건은 검사한 참조 범위에서 경로와 값에 도달하지 못한다는 뜻이며 외부 포크·캐시·로그 삭제를 증명하지 않습니다.
7주의할 점과 실무 메모
실제 시크릿을 실습 파일, 터미널 명령 인자, 채팅, 이슈에 붙여 넣지 않습니다. 노출된 값은 먼저 제공자에서 폐기하거나 교체합니다.
이력 재작성은 커밋 해시를 바꿉니다. 저장소 관리자와 시점, 대상 브랜치와 태그, 강제 push 권한, 협업자의 재복제 절차를 합의합니다.
이력에서 경로가 사라졌다는 검사만으로 다른 경로에 복사된 동일 값이 없다고 결론 내릴 수 없습니다. 경로 검사와 값 검사를 함께 수행합니다.
로컬 reflog와 호스팅 서비스의 캐시·포크·PR 참조는 별도 범위입니다. 서비스 제공자의 공식 지원 절차와 보존 정책을 확인합니다.
.gitignore는 예방의 한 층입니다. 이미 추적한 파일과 명령 출력, 로그, 노트북 출력에는 적용되지 않습니다.
이 챕터는 git-filter-repo 2.47.0을 고정합니다. 다른 버전이나 대규모 저장소에서는 공식 문서와 백업·검증 절차를 먼저 확인합니다.

# 커밋과 .gitignore
모든 저장소는 임시 폴더에 만들며 실제 GitHub 계정이나 원격 저장소를 변경하지 않습니다.
## 명령을 실행하기 전에 알아둘 Git 상태
Git은 파일을 세 자리에서 봅니다. **작업 폴더(working tree)** 는 지금 편집하는 파일이 있는 자리입니다. **색인(index)** 은 다음 커밋에 넣을 파일 상태를 골라 두는 자리이며, 스테이징 영역(staging area)이라고도 합니다. **커밋(commit)** 은 색인에 고른 상태를 저장소 이력에 기록한 결과입니다. 따라서 `git add app.py`는 파일을 영구 저장하는 명령이 아니라 현재 `app.py`를 색인에 올리는 명령입니다. 이어서 `git commit -m "메시지"`를 실행해야 그 상태가 커밋으로 기록됩니다.
**HEAD** 는 현재 체크아웃한 커밋을 가리킵니다. 보통 HEAD는 `main` 같은 **브랜치(branch)** 이름을 가리키고, 브랜치 이름은 다시 최신 커밋을 가리킵니다. 새 커밋을 만들면 현재 브랜치가 새 커밋으로 이동합니다. 이 절에서는 HEAD가 현재 커밋을 가리킨다는 관계까지만 사용합니다.
명령은 왼쪽부터 `git` → 하위 명령 → 옵션 → 대상으로 읽습니다. 예를 들어 `git status --short`에서 `status`는 상태를 보고, `--short`는 짧은 형식으로 표시하라는 옵션입니다. 코드의 `git("status", "--short", cwd=repo)`는 터미널에서 같은 명령을 실행하도록 인자를 나눈 Python 표현입니다.
## 준비
임시 저장소를 만들고 이 노트북에만 적용되는 작성자 정보를 설정합니다. `git init -b main`에서 `init`은 현재 폴더를 Git 저장소로 만들고, `-b main`은 첫 브랜치 이름을 `main`으로 정합니다. 아직 커밋이 없으므로 브랜치 이름만 준비된 상태입니다.
이 절에서는 `app.py`가 작업 폴더, 색인, 커밋을 차례로 이동하는 모습을 확인합니다. `.env`는 작업 폴더에는 있지만 `.gitignore` 규칙 때문에 색인에 올라가지 않습니다. 두 파일이 같은 폴더에 있어도 Git의 추적 상태는 다를 수 있습니다.
## 기본 실행
커밋 메시지 앞의 `feat`, `fix`, `chore`는 이 교재가 변경 목적을 구분하려고 사용한 팀 관례입니다. Git이 요구하는 필수 문법이 아니며 저장소마다 다른 규칙을 사용할 수 있습니다.
무시 규칙을 첫 커밋에, 프로그램을 다음 커밋에 기록합니다. `git add .gitignore`는 그 파일만 색인에 올리고, `git commit -m ...`의 `-m`은 커밋 메시지를 명령줄에서 지정합니다. 다음 `git add app.py`는 새 색인을 구성하므로 두 커밋은 서로 다른 목적을 갖습니다.
실행 뒤 `git status --short --ignored`에서 앞의 `!!`는 무시된 파일, `git log -2 --pretty=%s`의 `-2`는 최근 두 커밋, `%s`는 제목만 출력하라는 뜻입니다. `.env`가 `!!`로 보이고 두 메시지가 역시간순으로 나오면 작업 폴더의 모든 파일이 자동으로 커밋되는 것이 아님을 확인한 것입니다.
## 값 하나를 바꿔 비교
출력 숫자만 2에서 3으로 바꾸고 차이를 확인합니다. 이때 변경은 먼저 작업 폴더에만 존재합니다. `git diff -- app.py`는 작업 폴더와 색인의 차이를 보여 주므로 `-` 줄의 2와 `+` 줄의 3을 읽습니다. `git add` 뒤에는 같은 명령의 출력이 사라지고 변경이 색인으로 이동합니다. 마지막 커밋 뒤에는 작업 폴더·색인·HEAD 커밋이 다시 같은 파일 상태를 가리킵니다.
## 실패 재현
이미 추적 중인 파일은 나중에 무시 규칙을 추가해도 추적 상태가 유지됩니다. `*.log`에서 별표 `*`는 파일 이름의 임의 문자열과 일치하므로 `debug.log`, `server.log`처럼 `.log`로 끝나는 파일을 무시합니다.
## 수정
색인에서만 파일을 제거하면 작업 폴더의 파일은 남고 이후 변경은 무시됩니다.

# GitHub Flow와 PR 리뷰
모든 저장소는 임시 폴더에 만들며 실제 GitHub 계정이나 원격 저장소를 변경하지 않습니다.
## 명령을 실행하기 전에 알아둘 Git 상태
Git은 파일을 세 자리에서 봅니다. **작업 폴더(working tree)** 는 지금 편집하는 파일이 있는 자리입니다. **색인(index)** 은 다음 커밋에 넣을 파일 상태를 골라 두는 자리이며, 스테이징 영역(staging area)이라고도 합니다. **커밋(commit)** 은 색인에 고른 상태를 저장소 이력에 기록한 결과입니다. 따라서 `git add app.py`는 파일을 영구 저장하는 명령이 아니라 현재 `app.py`를 색인에 올리는 명령입니다. 이어서 `git commit -m "메시지"`를 실행해야 그 상태가 커밋으로 기록됩니다.
**HEAD** 는 현재 체크아웃한 커밋을 가리킵니다. 보통 HEAD는 `main` 같은 **브랜치(branch)** 이름을 가리키고, 브랜치 이름은 다시 최신 커밋을 가리킵니다. 새 커밋을 만들면 현재 브랜치가 새 커밋으로 이동합니다. 이 절에서는 HEAD와 브랜치에 더해 `origin/main`을 마지막으로 확인한 원격 `main`의 위치로 읽습니다.
명령은 왼쪽부터 `git` → 하위 명령 → 옵션 → 대상으로 읽습니다. 예를 들어 `git status --short`에서 `status`는 상태를 보고, `--short`는 짧은 형식으로 표시하라는 옵션입니다. 코드의 `git("status", "--short", cwd=repo)`는 터미널에서 같은 명령을 실행하도록 인자를 나눈 Python 표현입니다.
## 준비
로컬 bare 저장소를 원격 저장소처럼 사용합니다. **원격(remote)** 은 네트워크 자체가 아니라 다른 Git 저장소의 위치에 붙인 이름입니다. `git clone 원격경로 author`는 원격의 이력과 브랜치를 받아 `author` 작업 폴더를 만들고, 그 원격을 관례적인 이름인 `origin`으로 등록합니다. **bare 저장소**에는 편집용 작업 폴더가 없어서 중앙 공유 저장소 역할에 알맞습니다.
`git push -u origin main`은 현재 `main` 커밋을 원격 `main`에 보내며, `-u`는 이후 `git push`가 사용할 추적 관계를 기록합니다. push는 작업 폴더의 미커밋 파일을 보내지 않고 커밋과 참조를 전송합니다.
## 기본 실행
기능 브랜치를 만들고 커밋한 뒤 원격에 게시합니다. `git switch -c feature/order-summary`에서 `switch`는 체크아웃할 브랜치를 바꾸고 `-c`는 현재 커밋에서 새 브랜치를 만듭니다. 이 직후 `main`과 기능 브랜치는 같은 커밋을 가리키지만, 기능 커밋을 만들면 기능 브랜치만 앞으로 이동합니다.
`git branch -vv` 출력에서 별표는 현재 브랜치, 대괄호의 `origin/feature/order-summary`는 추적하는 원격 브랜치입니다. `git diff --stat origin/main...HEAD`의 점 세 개는 두 참조의 공통 조상부터 HEAD까지 기능 브랜치가 추가한 변경을 요약합니다. **풀 리퀘스트(Pull Request, PR)** 는 이 차이와 변경 이유를 사람에게 검토해 달라고 요청하는 GitHub의 협업 단위입니다.
## PR 자료와 변경 범위
기본 브랜치에 준비된 템플릿을 읽고 기능 코드 차이만 확인합니다. `--stat`은 실제 코드 대신 바뀐 파일과 줄 수를 요약합니다. 리뷰할 때는 요약으로 범위를 확인한 뒤 실제 diff도 읽어야 합니다.
GitHub Flow의 합치기 단계에는 merge, squash merge, rebase merge 같은 선택이 있을 수 있습니다. **fast-forward**는 현재 브랜치 이름을 기존 자손 커밋으로 앞으로 옮기기만 하면 되는 관계입니다. `--no-ff`는 이 단순 이동이 가능해도 부모가 둘인 병합 커밋을 만들라는 옵션입니다. **rebase**는 한 브랜치의 커밋을 다른 기준 위에서 다시 만든다는 뜻이라 커밋 해시가 바뀝니다.
## 실패 재현
리뷰어가 빈 문자열 입력에 대한 설명과 처리가 없음을 실제 diff에서 발견합니다.
## 수정
작성자가 입력을 정수로 제한하고 리뷰어가 원격 변경을 받아 병합합니다.
Ch 2의 07절에서 배운 `count: int`와 `-> str`은 입력과 반환값의 예상 자료형을 표시하지만 실행 중 값을 검사하지 않습니다. `isinstance(count, int)`는 현재 `count`가 정수 유형인지 확인하여 `True` 또는 `False`를 반환합니다. 이 결과가 거짓이면 `raise TypeError`로 잘못된 입력을 알립니다.

# 병합 충돌 해결
모든 저장소는 임시 폴더에 만들며 실제 GitHub 계정이나 원격 저장소를 변경하지 않습니다.
## 명령을 실행하기 전에 알아둘 Git 상태
Git은 파일을 세 자리에서 봅니다. **작업 폴더(working tree)** 는 지금 편집하는 파일이 있는 자리입니다. **색인(index)** 은 다음 커밋에 넣을 파일 상태를 골라 두는 자리이며, 스테이징 영역(staging area)이라고도 합니다. **커밋(commit)** 은 색인에 고른 상태를 저장소 이력에 기록한 결과입니다. 따라서 `git add app.py`는 파일을 영구 저장하는 명령이 아니라 현재 `app.py`를 색인에 올리는 명령입니다. 이어서 `git commit -m "메시지"`를 실행해야 그 상태가 커밋으로 기록됩니다.
**HEAD** 는 현재 체크아웃한 커밋을 가리킵니다. 보통 HEAD는 `main` 같은 **브랜치(branch)** 이름을 가리키고, 브랜치 이름은 다시 최신 커밋을 가리킵니다. 새 커밋을 만들면 현재 브랜치가 새 커밋으로 이동합니다. 이 절에서는 현재 브랜치의 HEAD와 `origin/main`을 비교해 로컬과 원격의 갈라진 이력을 읽습니다.
명령은 왼쪽부터 `git` → 하위 명령 → 옵션 → 대상으로 읽습니다. 예를 들어 `git status --short`에서 `status`는 상태를 보고, `--short`는 짧은 형식으로 표시하라는 옵션입니다. 코드의 `git("status", "--short", cwd=repo)`는 터미널에서 같은 명령을 실행하도록 인자를 나눈 Python 표현입니다.
## 준비
공용 원격과 두 작업 폴더를 만들고 출고 기준을 기록합니다. **병합(merge)** 은 갈라진 두 커밋 흐름의 변경을 하나의 결과로 합치는 작업입니다. 서로 다른 파일이나 서로 다른 줄을 바꿨다면 Git이 자동으로 합칠 수 있습니다. 같은 파일의 같은 줄을 서로 다르게 바꾸면 어느 내용을 선택할지 알 수 없어 **병합 충돌(merge conflict)** 로 멈춥니다.
이 실습은 `message.txt` 한 줄을 Alice와 Bob이 서로 다르게 수정합니다. `policy.txt`는 정답을 자동 생성하는 파일이 아니라 사람이 최종 문장을 판단할 근거입니다. 충돌 해결은 표시를 지우는 작업만이 아니라 두 변경의 의도를 확인해 올바른 파일 내용을 새로 결정하는 과정입니다.
## 기본 실행
Alice가 정책을 반영한 안내를 먼저 원격에 게시합니다.
## 값 하나를 바꿔 비교
Bob은 Alice가 두 번째 커밋을 push하기 전에 복제한 공통 `main`에서 같은 줄을 다른 문장으로 수정합니다. 따라서 두 사람은 같은 부모 커밋에서 자연스럽게 갈라지며 브랜치 위치를 따로 옮길 필요가 없습니다.
Bob의 push가 `non-fast-forward`로 거절되는 이유는 원격 `main`에 Bob이 갖고 있지 않은 Alice의 커밋이 있기 때문입니다. 강제 push로 덮는 대신 `git pull --no-rebase origin main`으로 원격 커밋을 가져와 병합합니다. `--no-rebase`는 가져온 커밋 위로 Bob의 커밋을 다시 만들지 않고 두 흐름을 병합하라는 뜻입니다.
## 실패 재현
Bob이 원격 변경을 가져와 병합하면 같은 줄의 차이에서 충돌합니다.
## 수정
저장소의 정책 문서를 근거로 안내를 확정하고 원격에 게시합니다.

# revert, reflog, worktree
모든 저장소는 임시 폴더에 만들며 실제 GitHub 계정이나 원격 저장소를 변경하지 않습니다.
## 명령을 실행하기 전에 알아둘 Git 상태
Git은 파일을 세 자리에서 봅니다. **작업 폴더(working tree)** 는 지금 편집하는 파일이 있는 자리입니다. **색인(index)** 은 다음 커밋에 넣을 파일 상태를 골라 두는 자리이며, 스테이징 영역(staging area)이라고도 합니다. **커밋(commit)** 은 색인에 고른 상태를 저장소 이력에 기록한 결과입니다. 따라서 `git add app.py`는 파일을 영구 저장하는 명령이 아니라 현재 `app.py`를 색인에 올리는 명령입니다. 이어서 `git commit -m "메시지"`를 실행해야 그 상태가 커밋으로 기록됩니다.

명령은 왼쪽부터 `git` → 하위 명령 → 옵션 → 대상으로 읽습니다. 예를 들어 `git status --short`에서 `status`는 상태를 보고, `--short`는 짧은 형식으로 표시하라는 옵션입니다. 코드의 `git("status", "--short", cwd=repo)`는 터미널에서 같은 명령을 실행하도록 인자를 나눈 Python 표현입니다.
## 준비
정상 설정 파일과 첫 커밋을 만듭니다. 이 절의 세 도구는 같은 종류의 기능이 아닙니다. **revert**는 이미 공유한 커밋의 효과를 취소하는 새 커밋을 만듭니다. **reflog**는 이 로컬 저장소에서 HEAD나 브랜치가 이동한 기록을 보여 줍니다. **worktree**는 같은 저장소의 다른 브랜치를 별도 작업 폴더에 연결합니다. 문제 상황을 먼저 구분한 뒤 도구를 선택해야 합니다.
## 기본 실행
잘못된 공개 변경은 revert로 반대 변경을 새 커밋에 기록합니다. `git revert --no-edit <커밋>`에서 `<커밋>`은 취소할 대상이고, `--no-edit`는 Git이 만든 기본 되돌림 메시지를 편집기 없이 사용합니다. `discount=90` 커밋은 이력에 남고 새 커밋이 그 패치를 반대로 적용해 파일을 `discount=10`으로 되돌립니다.
반면 reset은 현재 브랜치가 가리키는 위치를 옮깁니다. 파일 결과가 같아 보일 수 있어도 이력의 모양이 다릅니다. 공유한 잘못을 고칠 때는 기존 커밋을 보존하는 revert가 협업자가 이미 받은 이력과 맞추기 쉽습니다.
## worktree로 두 작업 폴더 사용
별도 브랜치를 별도 폴더에 연결합니다. `git worktree add -b fix/urgent <경로>`에서 `add`는 작업 폴더를 추가하고, `-b fix/urgent`는 새 브랜치를 만들며, 마지막 인자는 폴더 위치입니다. 기본 폴더는 `main`의 `config.txt`를 유지하고 추가 폴더는 `fix/urgent`에서 `hotfix.txt`를 커밋합니다. 두 폴더는 커밋 객체를 공유하지만 체크아웃한 브랜치와 작업 파일은 구분됩니다.
## 실패 재현
아직 공유하지 않은 커밋을 hard reset으로 지우면 일반 log에서 보이지 않습니다.
## 수정
reflog에서 이동 전 커밋을 찾아 새 브랜치 이름을 붙입니다. `git reflog --format=%H%x09%gs -5`는 최근 5개 행을 `전체 해시`, 탭 문자, `이동 이유` 순서로 출력합니다.
`reflog.splitlines()`는 출력 문자열을 행 목록으로 반환합니다. `next(...)`는 메시지에 `commit: experiment: 복구할 아이디어`가 포함된 첫 행을 고릅니다. `line.split("\t", 1)[0]`은 첫 번째 탭에서 행을 최대 한 번 나누고 탭 앞의 해시를 반환합니다. 이 해시가 `git branch recovered-idea <해시>`의 복구 대상입니다.

이 실습은 `DEMO-ONLY-NOT-A-REAL-SECRET`만 사용합니다. 원격도 임시 폴더의 bare 저장소이므로 외부에 게시되지 않습니다. 이후 출력의 “0건”은 이 임시 저장소에서 검사한 참조에 더미 값이 없다는 뜻이며 외부 캐시나 다른 복제본까지 삭제했다는 뜻은 아닙니다.
## 기본 실행
추적 전에는 `.gitignore`와 스테이징한 변경 검사를 함께 적용합니다. `git check-ignore -v .env`에서 `-v`는 어떤 규칙이 어느 파일에 적용됐는지 보여 줍니다. `git ls-files .env`는 색인에 등록된 경로를 찾으며, 빈 출력이면 `.env`가 현재 커밋 후보에 포함되지 않았다는 뜻입니다.
`.gitignore`는 아직 추적하지 않는 경로를 기본 `git add` 대상에서 제외할 뿐 파일을 암호화하거나 과거 커밋을 지우지 않습니다. `git diff --cached -- settings.example`은 다음 커밋에 들어갈 실제 내용을 보여 주므로 커밋 직전 시크릿 검사 지점으로 사용합니다.
## 값 하나를 바꿔 검사

## 수정
격리된 예제 저장소의 모든 참조에서 `.env` 경로를 제거한 뒤 원격을 강제로 갱신합니다. `git filter-repo --force`의 `--force`는 새로 복제한 저장소인지 확인하는 안전 검사를 완화합니다. 이 실습은 방금 만든 임시 mirror에만 사용하며 실제 작업 저장소에서 실행할 이유가 되지 않습니다.
`git rev-list --objects --all`의 각 행은 객체 해시와 경로를 담습니다. `objects.splitlines()`가 행 목록을 만들고, `line.endswith(" .env")`는 공백 뒤 경로가 정확히 `.env`로 끝나는 행인지 검사합니다. `any(...)`는 그런 행이 하나라도 있으면 `True`, 하나도 없으면 `False`를 반환합니다. 따라서 출력 `False`는 검사한 모든 참조에서 `.env` 경로를 찾지 못했다는 뜻입니다. 별도의 `git log -S` 결과 0건은 더미 문자열을 추가하거나 제거한 커밋도 찾지 못했다는 뜻입니다.
`len(value_hits.splitlines()) if value_hits else 0`은 결과 문자열이 있으면 행 수를 세고, 빈 문자열이면 0을 사용합니다. 따라서 검색 결과가 없을 때 출력되는 0은 빈 결과를 숫자로 표시한 값입니다.
