1학습 목표

  • 이 절을 마치면 문서 수와 형식을 사전 점검하고, 필수 100건이 준비되지 않은 상태를 실행 로그에 명시할 수 있습니다.
  • 이 절을 마치면 고정된 문서와 질문으로 세 청킹 설정과 두 임베딩 후보의 3×2 실험을 실행할 수 있습니다.
  • 이 절을 마치면 첫 번째·두 번째 캐시 실행, 청크 수, 처리 시간, 상세 검색 결과를 Ch 9 형식의 JSONL로 기록할 수 있습니다.
  • 이 절을 마치면 metrics: {}가 비어 있는 로그에서 품질 승자를 선언하면 안 되는 이유를 설명할 수 있습니다.

2왜 지금 이것인가

Ch 10은 로더, 청킹, 임베딩을 각각 배웠지만 실무 결정은 이 셋의 조합으로 이루어집니다. 좋은 파서가 보존한 구조도 청킹에서 잘리면 검색에 쓰이지 못하고, 같은 청크도 임베딩 모델에 따라 질문과의 순위가 달라집니다. 따라서 마지막 절에서는 앞 절의 함수를 하나의 실험 명령으로 연결합니다.

커리큘럼의 실습 목표는 자기 도메인 문서 100건을 세 청킹과 두 임베딩으로 인덱싱하는 것입니다. 현재 작업 공간에는 중복이 아닌 디지털 PDF 18건과 스캔 변형 3건이 있습니다. 스캔 변형은 같은 원본의 파싱 실패를 보기 위한 자료이며 문서 수를 채우기 위해 복제해 세지 않습니다. 100건 필수 조건이 충족되지 않았으므로 사전 점검 결과는 ready=False여야 합니다. 지금 실행할 수 있는 18건 기준선은 실험 코드와 로그 형식을 검증하는 예행이며, 100건 실험을 완료한 것으로 표현하지 않습니다.

3선수 지식 되짚기

  • Ch 9 실험 하네스 — 설정을 바꾸고 실행한 뒤 JSONL 한 줄로 기록했습니다. 상세 파일에는 질문, 정답 문서 ID, 검색 청크를 남겼고 metrics는 비워 두었습니다.
  • 05·06절 청킹 — 재귀·토큰·구조 방식은 같은 Document 목록을 반환합니다. 이 공통 출력이 3개 행의 입력입니다.
  • 07절 임베딩 캐시 — 같은 텍스트와 모델 조건의 두 번째 실행은 캐시에서 읽고, 모델 후보가 바뀌면 별도 키를 사용합니다.

4핵심 개념

비유 — 여섯 칸의 실험 표

청킹 설정 세 개를 표의 행에, 임베딩 후보 두 개를 열에 놓으면 여섯 칸이 생깁니다. 각 칸은 같은 문서와 같은 질문을 사용합니다. 한 칸만 다른 문서를 사용하거나 질문 수가 달라지면 설정의 효과와 입력 차이를 구분할 수 없습니다. 실험 격자는 바꾼 조건과 고정한 조건을 눈에 보이게 만듭니다.

정의

말뭉치 사전 점검 (corpus preflight)
실험 전에 문서 개수, 중복, 파일 형식, 스캔 여부, 읽기 가능성을 검사하는 단계입니다. 필수 조건을 충족하지 못하면 상태를 로그에 남기고 결과 범위를 제한합니다.
실험 격자 (experiment matrix)
비교할 설정 조합을 행과 열로 배치한 표입니다. 이 절에서는 재귀·토큰·구조 청킹 세 가지와 임베딩 후보 두 가지로 여섯 실행을 만듭니다.
기준선 범위 (baseline scope)
현재 실행에 실제로 포함한 문서와 질문의 범위입니다. 목표 수량과 구분해 기록하면 작은 예행 결과를 전체 실험 결과로 오해하지 않습니다.
상세 실행 로그 (run detail log)
질문별 정답 문서 ID와 검색된 청크·점수를 기록한 JSONL 파일입니다. 요약 한 줄만으로 알 수 없는 실패 원인을 Ch 11에서 계산하고 검토하는 근거입니다.

실험 전에 문서부터 셉니다

사전 점검은 경로 목록에서 중복을 제거하고 required, available, ready를 반환합니다. 현재 디지털 PDF 18건은 색인 기준선으로 사용할 수 있습니다. 스캔 변형 3건은 OCR과 파싱 실패를 확인하는 별도 자료이며 기준선의 문서 수에는 포함하지 않습니다. 자기 도메인 문서 100건이 준비되면 경로와 원문 해시를 매니페스트에 고정하고 같은 6개 조합을 다시 실행합니다.

수량만 채우기 위해 같은 PDF를 복사하면 청크와 검색 결과가 중복되어 실험이 왜곡됩니다. 문서 수는 고유 원문 해시로 확인하는 것이 안전합니다. 암호화 파일, 0쪽 파일, 텍스트층이 없는 스캔은 수량과 처리 가능 상태를 구분해 기록합니다. 사전 점검이 실패해도 코드와 로그 형식을 확인하는 예행은 가능하지만, 결과의 기준선 범위를 반드시 18건으로 표시합니다.

고정 조건과 변경 조건

변경 조건은 청킹 방식과 임베딩 후보입니다. 재귀 방식은 문자 크기 800과 오버랩 100, 토큰 방식은 토큰 크기 400과 오버랩 50, 구조 방식은 최대 문자 800으로 고정합니다. 임베딩 후보는 기능 비교를 위한 text-embedding-3-small과 text-embedding-3-large입니다. 실제 API를 실행할 때는 같은 백엔드와 같은 질문을 사용합니다.

고정 조건은 디지털 PDF 18건, 질문 3개, 검색 k=4, 로더 함수, 로그 형식입니다. 예제는 Ch 9 질의 파일에서 Q001·Q037·Q088을 골라 정답 문서 ID와 함께 사용합니다. 이 세 질문은 전체 품질을 대표하는 평가셋이 아닙니다. 실행 경로와 상세 로그가 작동하는지 확인하는 작은 기준선입니다.

오프라인 백엔드와 실제 API 백엔드를 구분합니다

educational-feature-hash는 네트워크와 API 키 없이 여섯 조합, 캐시, JSONL 기록, top-k 정렬이 실행되는지 확인하는 교육용 특징 벡터입니다. 모델 품질 결과가 아니므로 small과 large 이름을 사용해도 두 벡터가 실제 OpenAI 모델을 뜻하지 않습니다. 실제 모델 비교는 --backend openai로 실행하고, API 키와 비용 사전 점검을 통과한 결과만 사용합니다.

API 실행 전에는 세 청킹 결과의 청크 텍스트와 후보별 질문 임베딩 범위를 합산하고 공식 단가를 곱해 small·large의 예상 비용을 출력합니다. 예상값은 호출 전에 지출 규모를 확인하기 위한 값입니다. 실행 뒤에는 실제 제공자 사용량을 얻을 수 있다면 별도 필드에 기록합니다. 비용이 더 낮은 조합과 품질이 더 높은 조합은 같은 뜻이 아닙니다.

metrics: {}는 미완성 표시가 아니라 학습 경계입니다

여섯 실행에는 정답 문서 ID와 검색 결과가 이미 있으므로 정답 문서가 top-k에 들어왔는지 사람이 볼 수 있습니다. 그러나 이 장에서는 지표 이름과 분모, 문서 단위와 청크 단위의 차이를 아직 정의하지 않았습니다. 따라서 요약과 상세 로그의 metrics는 빈 딕셔너리로 둡니다. 청크 수, 처리 시간, 캐시 적중, 검색 결과 몇 건만 보고 우승 모델이나 우승 청킹을 선언하지 않습니다.

Ch 11은 정답 문서가 k개 안에 들어온 비율과 관련 없는 결과가 얼마나 섞였는지를 분리해 계산합니다. 그때 같은 로그를 다시 읽어 metrics를 채웁니다. 이 순서는 측정이 튜닝보다 먼저라는 커리큘럼의 원칙을 지킵니다.

6일부러 실패해 보기

실패 1 — 스캔 변형을 새 문서로 셉니다. 디지털 원본과 스캔 변형을 함께 21건의 독립 문서로 취급하면 같은 내용이 반복됩니다. 스캔 3건은 파서 실패 실험으로 분리하고, 색인 기준선은 고유 디지털 PDF 18건으로 기록합니다.

실패 2 — 백엔드 이름을 확인하지 않습니다. 오프라인 특징 벡터로 나온 small·large 행을 실제 모델 비교 결과로 보고하면 두 후보의 품질을 측정하지 않은 것입니다. embedding_backend가 openai인지 확인하고, 교육용 백엔드 결과에는 품질 결론을 붙이지 않습니다.

실패 3 — 청크 수가 가장 적은 조합을 우승으로 정합니다. 청크 수가 적으면 저장과 임베딩 호출이 줄 수 있지만 정답 근거가 긴 청크 속에서 희석될 수 있습니다. metrics가 비어 있는 동안은 규모와 비용만 관찰하고 Ch 11 평가까지 결론을 보류합니다.

7주의할 점과 실무 메모

  • 100건 조건 미충족. 현재 기준선 18건과 스캔 변형 3건으로 전체 100건 실습을 완료했다고 말하지 않습니다. 자기 도메인 문서가 준비되면 고유성·파싱 가능 상태를 다시 점검합니다.
  • 세 질문의 한계. Q001·Q037·Q088은 실행 흐름과 로그를 확인하는 작은 표본입니다. 모델 선택에는 Ch 11의 충분한 한국어 평가셋이 필요합니다.
  • 실제 API 비용. --backend openai는 외부 호출과 비용이 발생합니다. 호출 전 출력된 예상 비용, API 키 상태, 모델 접근 가능 여부를 확인하고 실행 기록에 날짜를 남깁니다.
  • 로그 재현성. 움직이는 API 버전, 토크나이저, 파서, 청킹 함수 코드가 바뀌면 같은 설정 이름으로도 결과가 달라질 수 있습니다. 패키지 버전과 코드 리비전을 함께 기록하는 확장은 Ch 12 실험 루프에서 적용합니다.

8정리와 다음 절

  • 말뭉치 사전 점검은 필수 100건과 현재 고유 디지털 PDF 18건을 구분하고, 스캔 변형을 문서 수에 중복해 넣지 않습니다.
  • 재귀·토큰·구조 청킹과 두 임베딩 후보를 같은 문서·질문·k로 실행해 여섯 개 요약과 질문별 상세 로그를 만듭니다.
  • 캐시와 비용·규모는 기록했지만 metrics는 비어 있으므로 Ch 11 전에 품질 승자를 선언하지 않습니다.

다음 학습과 이어지는 지점 — Ch 11은 이 절의 상세 로그에서 gold_doc_id와 retrieved를 읽어 검색 지표를 계산합니다. Ch 12는 충분한 도메인 문서와 질의셋으로 실험을 반복하고, 청킹·임베딩·검색 설정을 바꾼 30건 이상의 로그를 비교합니다.

9복습 문제

문제 4개 · 해설 포함

1. 현재 말뭉치 사전 점검에서 required=100, available=18이면 ready는 무엇입니까?

False입니다. 18건 기준선으로 예행은 할 수 있지만 자기 도메인 문서 100건 실습을 완료한 것은 아닙니다.

2. 3×2 실험에서 고정해야 하는 조건을 세 가지 이상 쓰세요.

같은 고유 문서 목록, 같은 질문과 정답 문서 ID, 같은 검색 k, 같은 로더, 같은 로그 형식을 고정합니다. 변경 조건은 청킹 방식과 임베딩 후보입니다.

3. 출력에 embedding_candidate=text-embedding-3-large가 있지만 embedding_backend=educational-feature-hash입니다. 이 행으로 large의 품질을 판단할 수 있습니까?

판단할 수 없습니다. 교육용 특징 벡터는 실행 구조와 캐시를 오프라인에서 검증하며 실제 OpenAI 모델 벡터를 계산하지 않습니다. 실제 비교에는 API 백엔드 실행과 평가 지표가 필요합니다.

4. 어떤 조합이 청크 수와 시간이 가장 적었습니다. metrics={}인 상태에서 내릴 수 있는 결론과 내릴 수 없는 결론을 구분하세요.

그 실행에서 기록된 청크 수와 처리 시간이 작았다는 관찰은 말할 수 있습니다. 검색 품질이 가장 좋다거나 최종 청킹·임베딩으로 선택해야 한다는 결론은 내릴 수 없습니다. Ch 11에서 같은 로그의 검색 지표와 대표 실패를 확인해야 합니다.

예상 질문 — “18건으로도 비교할 수 있나요?” → 코드와 로그의 작동은 확인할 수 있지만 100건 목표와 최종 모델 결정은 충족하지 못합니다. “스캔 3건을 더하면 21건인가요?” → 원본의 변형이면 독립 도메인 문서 수로 중복 집계하지 않습니다. “지금 정답 문서 ID가 있는데 점수를 계산하면 안 되나요?” → 예행 계산은 가능하지만 지표 정의와 해석은 Ch 11에서 정식으로 다룹니다.

학생이 자주 막히는 지점 — 프로젝트 루트가 달라 PDF 경로가 비는 경우, 이전 캐시가 남아 첫 실행부터 적중이 나오는 경우, 교육용 백엔드를 실제 모델 실행으로 오해하는 경우, runs.jsonl 요약과 질문별 상세 파일을 혼동하는 경우를 확인합니다.
