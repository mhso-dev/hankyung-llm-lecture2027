1학습 목표

  • 이 절을 마치면 노트북 입력의 사전 조건을 단언하고, 작은 기능 검증과 필수 100건 전체 실험을 구분할 수 있습니다.
  • 이 절을 마치면 고정된 문서와 질문으로 세 청킹 설정과 두 임베딩 후보의 3×2 실험을 실행할 수 있습니다.
  • 이 절을 마치면 전략, 모델, 질문, 청크 ID, 최상위 출처를 최소 JSONL 실행 기록으로 저장할 수 있습니다.
  • 이 절을 마치면 metrics: {}가 비어 있는 로그에서 품질 승자를 선언하면 안 되는 이유를 설명할 수 있습니다.

2왜 지금 이것인가

Ch 10은 로더, 청킹, 임베딩을 각각 배웠지만 실무 결정은 이 셋의 조합으로 이루어집니다. 좋은 파서가 보존한 구조도 청킹에서 잘리면 검색에 쓰이지 못하고, 같은 청크도 임베딩 모델에 따라 질문과의 순위가 달라집니다. 따라서 마지막 절에서는 앞 절의 함수를 하나의 실험 명령으로 연결합니다.

커리큘럼의 실습 목표는 자기 도메인 문서 100건을 세 청킹과 두 임베딩으로 인덱싱하는 것입니다. 현재 작업 공간에는 중복이 아닌 디지털 PDF 18건과 스캔 변형 3건이 있으므로 100건 조건은 충족되지 않습니다. 이 절의 노트북은 하나의 짧은 원문과 질문 하나로 청킹 계산, 실제 API 호출, 최소 JSONL 기록을 검증합니다. 18건 전체 처리와 100건 실험은 기존 모듈을 확장하는 후속 과제로 남기며, 작은 노트북 실행을 전체 실험 완료로 표현하지 않습니다.

3선수 지식 되짚기

  • Ch 9 실험 하네스 — 설정을 바꾸고 실행한 뒤 JSONL로 기록했습니다. 이번 노트북은 같은 원칙을 다섯 필드의 최소 로그에 적용합니다.
  • 05·06절 청킹 — 재귀·토큰·구조 방식이 경계를 계산하는 방법을 배웠습니다. 이번 노트북은 같은 원문에서 세 결과를 직접 계산합니다.
  • 07절 임베딩 캐시 — 같은 텍스트와 모델 조건의 벡터를 재사용하는 조건을 확인했습니다. 캐시 통계는 전체 실험 하네스의 확장 항목입니다.

4핵심 개념

비유 — 여섯 칸의 실험 표

청킹 설정 세 개를 표의 행에, 임베딩 후보 두 개를 열에 놓으면 여섯 칸이 생깁니다. 각 칸은 같은 문서와 같은 질문을 사용합니다. 한 칸만 다른 문서를 사용하거나 질문 수가 달라지면 설정의 효과와 입력 차이를 구분할 수 없습니다. 실험 격자는 바꾼 조건과 고정한 조건을 눈에 보이게 만듭니다.

정의

말뭉치 사전 점검 (corpus preflight)
실험 전에 문서 개수, 중복, 파일 형식, 스캔 여부, 읽기 가능성을 검사하는 단계입니다. 필수 조건을 충족하지 못하면 상태를 로그에 남기고 결과 범위를 제한합니다.
실험 격자 (experiment matrix)
비교할 설정 조합을 행과 열로 배치한 표입니다. 이 절에서는 재귀·토큰·구조 청킹 세 가지와 임베딩 후보 두 가지로 여섯 실행을 만듭니다.
기준선 범위 (baseline scope)
현재 실행에 실제로 포함한 문서와 질문의 범위입니다. 목표 수량과 구분해 기록하면 작은 예행 결과를 전체 실험 결과로 오해하지 않습니다.
상세 실행 로그 (run detail log)
질문별 정답 문서 ID와 검색된 청크·점수를 기록한 JSONL 파일입니다. 요약 한 줄만으로 알 수 없는 실패 원인을 Ch 11에서 계산하고 검토하는 근거입니다.

실험 전에 문서부터 셉니다

사전 점검은 경로 목록에서 중복을 제거하고 required, available, ready를 반환합니다. 현재 디지털 PDF 18건은 색인 기준선으로 사용할 수 있습니다. 스캔 변형 3건은 OCR과 파싱 실패를 확인하는 별도 자료이며 기준선의 문서 수에는 포함하지 않습니다. 자기 도메인 문서 100건이 준비되면 경로와 원문 해시를 매니페스트에 고정하고 같은 6개 조합을 다시 실행합니다.

수량만 채우기 위해 같은 PDF를 복사하면 청크와 검색 결과가 중복되어 실험이 왜곡됩니다. 문서 수는 고유 원문 해시로 확인하는 것이 안전합니다. 암호화 파일, 0쪽 파일, 텍스트층이 없는 스캔은 수량과 처리 가능 상태를 구분해 기록합니다. 사전 점검이 실패해도 코드와 로그 형식을 확인하는 예행은 가능하지만, 결과의 기준선 범위를 반드시 18건으로 표시합니다.

고정 조건과 변경 조건

변경 조건은 청킹 방식과 임베딩 후보입니다. 노트북의 재귀 방식은 문자 크기 45와 오버랩 8, 토큰 방식은 토큰 크기 24와 오버랩 4, 구조 방식은 빈 줄로 구분한 제목 블록을 사용합니다. 임베딩 후보는 text-embedding-3-small과 text-embedding-3-large이며 두 모델 모두 256차원으로 호출합니다.

고정 조건은 하나의 인라인 원문, 질문 하나, 코사인 유사도, 최상위 결과 한 건, 로그 필드입니다. 실행 전에는 세 전략 이름과 비어 있지 않은 청크 목록을 단언합니다. 이 입력은 전체 품질을 대표하는 평가셋이 아니라 계산과 기록 경로가 작동하는지 확인하는 기능 검증입니다.

기존 오프라인 기록과 실제 API 결과를 구분합니다

educational-feature-hash로 남긴 기존 로그는 네트워크 없이 여섯 조합, 캐시, JSONL 기록, top-k 정렬의 실행 흐름을 확인한 과거 기록입니다. 실제 OpenAI 모델 품질 결과가 아닙니다. 이 절의 주 실행 경로는 아래 노트북의 실제 API 호출이며, 기존 로그는 대규모 자료 연결 전 구현 회귀를 확인하는 보조 자료로만 사용합니다.

현재 노트북은 각 조합을 실행한 뒤 API가 반환한 실제 토큰 사용량을 JSONL 파일에 기록합니다. 기존 전체 자료용 확장 모듈은 호출 전에 예상 토큰 수와 공식 단가로 비용을 계산하는 예제를 포함합니다. 예상 비용 계산은 현재 노트북의 실행 범위에 포함되지 않습니다. 비용이 더 낮은 조합과 품질이 더 높은 조합은 같은 뜻이 아닙니다.

사전 점검과 3×2 실행

노트북은 같은 원문에서 세 청크 목록을 계산하고 두 모델과 중첩 반복합니다. 각 조합은 전략, 모델, 질문, 전체 청크 ID, 최상위 출처 ID를 한 줄의 JSON으로 기록합니다. 말뭉치 고유성, 파서 상태, 캐시 적중, 처리 시간, 정답 문서와 전체 검색 결과를 담는 run_experiment() 형식은 18건 또는 100건 자료를 연결할 때 적용하는 확장입니다.

metrics: {}는 미완성 표시가 아니라 학습 경계입니다

노트북의 최소 로그에는 정답 문서와 품질 지표가 없습니다. 청크 수, API 토큰 수, 최상위 출처만 보고 우승 모델이나 우승 청킹을 선언하지 않습니다.

Ch 11은 로그 스키마에 정답 문서와 전체 검색 결과를 추가하고, 정답 문서가 k개 안에 들어온 비율과 관련 없는 결과가 얼마나 섞였는지를 계산합니다. 이 순서는 측정이 튜닝보다 먼저라는 커리큘럼의 원칙을 지킵니다.

7주의할 점과 실무 메모

  • 100건 조건 미충족. 현재 기준선 18건과 스캔 변형 3건으로 전체 100건 실습을 완료했다고 말하지 않습니다. 자기 도메인 문서가 준비되면 고유성·파싱 가능 상태를 다시 점검합니다.
  • 질문 하나의 한계. 노트북의 제주 배송 질문은 실행 흐름과 로그를 확인하는 작은 표본입니다. 모델 선택에는 Ch 11의 충분한 한국어 평가셋이 필요합니다.
  • 실제 API 비용. 06~08절의 OpenAI API 셀을 실행하면 비용이 발생합니다. 실행 전에 API 키와 모델 접근 가능 여부를 확인합니다. 08절의 실행 결과에는 실제 토큰 사용량을 기록합니다.
  • 로그 재현성. 움직이는 API 버전, 토크나이저, 파서, 청킹 함수 코드가 바뀌면 같은 설정 이름으로도 결과가 달라질 수 있습니다. 패키지 버전과 코드 리비전을 함께 기록하는 확장은 Ch 12 실험 루프에서 적용합니다.

8정리와 다음 절

  • 말뭉치 사전 점검은 필수 100건과 현재 고유 디지털 PDF 18건을 구분하고, 스캔 변형을 문서 수에 중복해 넣지 않습니다.
  • 재귀·토큰·구조 청킹과 두 임베딩 후보를 같은 원문과 질문으로 실행해 최소 JSONL 여섯 줄을 만듭니다.
  • 전략·모델·질문·청크 ID·최상위 출처를 기록하지만 정답과 지표는 없으므로 Ch 11 전에 품질 승자를 선언하지 않습니다.

다음 학습과 이어지는 지점 — Ch 11은 이 절의 최소 로그에 gold_doc_id와 전체 검색 결과를 추가해 검색 지표를 계산합니다. Ch 12는 충분한 도메인 문서와 질의셋으로 실험을 반복하고, 청킹·임베딩·검색 설정을 바꾼 30건 이상의 로그를 비교합니다.

9복습 문제

문제 4개 · 해설 포함

1. 현재 말뭉치 사전 점검에서 required=100, available=18이면 ready는 무엇입니까?

False입니다. 18건 기준선으로 예행은 할 수 있지만 자기 도메인 문서 100건 실습을 완료한 것은 아닙니다.

2. 3×2 실험에서 고정해야 하는 조건을 세 가지 이상 쓰세요.

같은 고유 문서 목록, 같은 질문과 정답 문서 ID, 같은 검색 k, 같은 로더, 같은 로그 형식을 고정합니다. 변경 조건은 청킹 방식과 임베딩 후보입니다.

3. 출력에 embedding_candidate=text-embedding-3-large가 있지만 embedding_backend=educational-feature-hash입니다. 이 행으로 large의 품질을 판단할 수 있습니까?

판단할 수 없습니다. 교육용 특징 벡터는 실행 구조와 캐시를 오프라인에서 검증하며 실제 OpenAI 모델 벡터를 계산하지 않습니다. 실제 비교에는 API 백엔드 실행과 평가 지표가 필요합니다.

4. 어떤 조합이 청크 수와 시간이 가장 적었습니다. metrics={}인 상태에서 내릴 수 있는 결론과 내릴 수 없는 결론을 구분하세요.

그 실행에서 기록된 청크 수와 처리 시간이 작았다는 관찰은 말할 수 있습니다. 검색 품질이 가장 좋다거나 최종 청킹·임베딩으로 선택해야 한다는 결론은 내릴 수 없습니다. Ch 11에서 같은 로그의 검색 지표와 대표 실패를 확인해야 합니다.

학생이 자주 막히는 지점 — 세 청킹 결과를 직접 계산하지 않고 이름만 붙이는 경우, 최소 JSONL을 전체 실험 로그로 오해하는 경우, 최상위 출처 한 건으로 모델 품질을 선언하는 경우를 확인합니다.

A/B 트랙 — A트랙은 노트북의 인라인 원문으로 실제 여섯 조합을 실행하고 최소 로그를 검사합니다. B트랙은 고유 원문 해시 기반 사전 점검, 패키지·코드 리비전 필드, 변경 청크만 재임베딩하는 매니페스트를 추가합니다. 18건 전체 API 실행은 예상 비용과 자료 외부 전송 조건을 확인한 환경에서 별도 기록합니다.
