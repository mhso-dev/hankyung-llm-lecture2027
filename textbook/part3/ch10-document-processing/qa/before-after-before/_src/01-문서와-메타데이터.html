1학습 목표

  • 이 절을 마치면 파일 형식이 달라도 로더의 출력은 같은 Document 구조여야 하는 이유를 설명할 수 있습니다.
  • 이 절을 마치면 검색·출처 표기·재처리에 필요한 메타데이터 항목을 고르고, 값이 어디에서 만들어졌는지 구분할 수 있습니다.
  • 이 절을 마치면 서로 다른 로더가 만든 메타데이터를 공통 필드로 정규화하고, 원본별 값의 차이를 실행 결과로 확인할 수 있습니다.

2왜 지금 이것인가

Ch 9에서는 PDF 한 쪽을 Document 하나로 바꾸고 바로 청크로 나눴습니다. 그 과정은 RAG의 전체 흐름을 확인하기 위한 최소 구현이었습니다. 실제 조직의 문서 폴더에는 PDF만 있지 않습니다. 같은 규정이 PDF, DOCX, HTML로 배포되고, 표 데이터는 CSV로 내려오며, 결재 문서는 HWP 또는 HWPX로 남습니다. 파일마다 읽는 방법은 달라도 이후의 청킹·임베딩·검색 단계는 한 가지 입력 구조를 기대합니다. 따라서 이번 챕터의 첫 과제는 여러 형식을 일관된 문서 계약으로 맞추는 것입니다.

이 절에서는 파서 성능을 비교하기 전에 입력 문서의 목록과 메타데이터부터 고정합니다. 문서 수, 형식, 원본 경로, 식별자가 기록되지 않으면 파서를 바꾼 뒤 무엇이 빠졌는지 판단할 수 없습니다. Ch 11에서 검색 결과를 정답 문서 ID와 비교하려면 doc_id도 처음부터 안정적이어야 합니다. 측정이 튜닝보다 먼저라는 과정 원칙은 문서 처리에도 그대로 적용됩니다. 먼저 입력과 산출물을 셀 수 있게 만들고, 다음 절부터 형식별 파서를 붙입니다.

현재 기본 실습 자료는 labs/data/rag-corpus/의 합성 PDF 21건입니다. 텍스트를 추출할 수 있는 PDF가 18건이고, 텍스트 레이어가 없는 스캔 PDF가 3건입니다. 커리큘럼의 최종 실습은 자기 도메인 문서 100건을 요구하지만, 이 저장소에는 아직 100건 묶음이 없습니다. 그러므로 이번 챕터의 예제는 21건으로 처리 계약을 검증하고, 100건 비교는 자료가 준비된 뒤 같은 명령에 입력 경로만 바꾸도록 설계합니다.

3선수 지식 되짚기

  • Ch 2 파일과 타입힌트 — pathlib.Path로 경로를 다루고, 함수의 입력과 반환형을 명시했습니다. 이번 절의 파일 조사 함수도 같은 규칙을 따릅니다.
  • Ch 4 문서 파싱 입문 — 파일 확장자와 실제 내용이 다를 수 있으며, 읽기 실패를 예외로 구분해야 한다는 점을 확인했습니다.
  • Ch 9 rag.py — load_pdfs()가 doc_id·page·source를 남기고, split_docs()가 이를 청크마다 복사했습니다. Ch 11의 정답 문서 비교는 이 doc_id를 그대로 사용합니다.

4핵심 개념

비유 — 접수대에서 만드는 표준 봉투

한 기관의 접수대에 종이 신청서, 이메일 인쇄물, 엑셀 목록이 함께 들어온다고 생각해 보세요. 담당자는 원본을 그대로 창고에 보관하고, 처리 부서에는 같은 모양의 봉투로 전달합니다. 봉투 앞면에는 접수 번호, 원본 종류, 접수 시각, 담당 부서를 적습니다. 처리 부서는 봉투 안의 본문을 읽으면 되고, 원본 형식에 따라 접수 방법이 달랐다는 사실까지 알 필요는 없습니다. 로더가 하는 일도 이와 같습니다. 파일별 파서는 다르지만, 청킹 단계에 넘기는 결과는 같은 Document 구조여야 합니다.

정의

문서 객체 (Document)
추출한 본문과 부가 정보를 한 단위로 묶은 객체입니다. LangChain의 Document는 page_content와 metadata를 가집니다. 이후 청킹·임베딩·검색은 원본 파일 대신 이 객체를 받습니다.
파서 (parser)
파일의 내부 구조를 해석하여 텍스트, 표, 이미지 위치 같은 내용을 추출하는 프로그램입니다. 같은 PDF라도 파서에 따라 읽기 순서와 표 표현이 달라질 수 있습니다.
메타데이터 (metadata)
본문을 설명하는 부가 정보입니다. 문서 ID, 원본 파일명, 쪽 번호, 형식, 수정 시각처럼 검색 필터와 출처 표기에 필요한 값을 담습니다.
출처 계보 (provenance)
산출물이 어느 원본에서 어떤 처리 과정을 거쳐 만들어졌는지 추적할 수 있는 기록입니다. source, parser, page를 함께 남기면 검색된 청크를 원본까지 거슬러 확인할 수 있습니다.

도식 — 원본은 여러 가지, 산출물 계약은 한 가지

공통 계약을 만들 때는 본문보다 메타데이터를 먼저 설계하는 편이 안전합니다. 본문은 나중에 파서를 바꾸어 다시 만들 수 있지만, 안정적인 doc_id가 없으면 이전 색인과 새 색인의 결과를 비교하기 어렵습니다. 파일명이 바뀔 수 있는 환경에서는 업무 시스템의 문서 번호를 사용하고, 그런 번호가 없으면 정규화한 상대 경로나 내용 해시를 조합합니다. 이 챕터의 합성 문서는 파일명 앞의 E01, M03, H06을 문서 ID로 사용합니다.

메타데이터는 세 부류로 나누어 생각할 수 있습니다. 첫째, 원본에서 직접 읽은 값입니다. 제목, 작성자, 수정 시각이 여기에 해당합니다. 둘째, 파일 시스템에서 얻은 값입니다. 상대 경로, 확장자, 파일 크기입니다. 셋째, 처리 과정이 만든 값입니다. 사용한 파서 이름, 처리 시각, OCR 적용 여부, 청크 번호입니다. 이 세 부류를 구분해 두면 잘못된 값의 책임 지점을 찾기 쉽습니다. 예를 들어 PDF 안의 제목과 파일명이 다르면 어느 값을 우선할지 정책으로 결정할 수 있습니다.

7주의할 점과 실무 메모

  • 식별자와 제목을 구분합니다. 제목은 사람이 읽기 위한 값이라 수정될 수 있습니다. doc_id는 비교와 갱신을 위한 값이므로 변경에 강해야 합니다.
  • 쪽 번호의 기준을 통일합니다. 일부 라이브러리는 첫 쪽을 0으로 반환합니다. 교재와 최종 출처 표시는 사람이 보는 쪽 번호인 1부터 시작하도록 변환합니다.
  • 원본을 보존합니다. 추출 텍스트만 남기면 파서 오류를 다시 확인할 수 없습니다. 원본 파일과 처리 산출물의 관계를 메타데이터로 유지합니다.
  • 민감한 경로와 문서 속성을 걸러냅니다. 작성자 계정, 내부 서버 경로, 임시 폴더 이름은 검색 품질에 필요하지 않다면 배포용 메타데이터에서 제외합니다.
  • 재처리 조건을 기록합니다. 파일 수정 시각이나 내용 해시를 보관하면 바뀐 문서만 다시 파싱하고 임베딩할 수 있습니다. 캐싱과 재임베딩 비용은 이 챕터 후반 절에서 다룹니다.

8정리와 다음 절

  • 형식별 파서는 달라도 청킹 단계에 전달하는 결과는 Document(page_content, metadata)라는 하나의 계약으로 맞춥니다.
  • doc_id·source·page·file_type·parser를 남기면 누락, 출처, 재처리 경로를 추적할 수 있습니다.
  • 현재 기본 자료는 텍스트 PDF 18건과 스캔 PDF 3건입니다. 100건 도메인 문서 실험은 별도 자료가 준비된 뒤 같은 목록 생성 절차로 시작합니다.

다음 학습과 이어지는 지점 — 이 절의 입력 목록과 공통 메타데이터는 02~04절의 모든 로더가 따라야 하는 계약입니다. Ch 11에서는 doc_id를 정답표와 비교하고, Ch 12에서는 file_type과 parser를 실패 유형별 집계에 사용합니다. 다음 02절에서는 같은 PDF를 서로 다른 방식으로 읽어 표와 스캔본에서 계약이 어떻게 흔들리는지 확인합니다.

9복습 문제

문제 4개 · 해설 포함

1. [하] 여러 파일 형식의 로더가 같은 Document 구조를 반환해야 하는 이유는 무엇입니까?

청킹·임베딩·검색 단계가 원본 형식마다 별도 코드를 가질 필요 없이 하나의 입력 계약만 처리할 수 있기 때문입니다. 형식별 차이는 로더 안에서 흡수하고, 본문과 메타데이터 구조는 통일합니다.

2. [중] doc_id와 문서 제목을 같은 값으로 사용했을 때 생길 수 있는 문제를 설명하세요.

제목은 사람이 수정하거나 여러 문서에서 중복할 수 있습니다. 제목이 바뀌면 같은 문서를 새 문서로 인식하고, 제목이 중복되면 서로 다른 문서의 청크가 하나로 집계됩니다. 안정적인 업무 ID나 상대 경로·내용 해시 조합을 사용해야 합니다.

3. [중] 입력 21건, 성공 17건, 실패 3건으로 보고되었습니다. 어떤 검사를 추가해야 합니까?

성공·실패·건너뜀 건수의 합이 입력 건수와 같은지 검사해야 합니다. 현재 합은 20건이므로 한 건이 기록 없이 누락되었습니다. 누락된 경로를 찾고 모든 입력이 정확히 한 상태를 갖도록 합니다.

4. [상] 파서를 교체한 뒤 검색 품질이 달라졌습니다. 원인을 재현하려면 어떤 메타데이터가 필요합니까?

최소한 원본을 가리키는 doc_id와 source, 쪽 번호, 파일 형식, 파서 이름과 버전, 처리 시각 또는 설정 식별자가 필요합니다. 이 정보로 같은 원본을 같은 조건에서 다시 처리하고 이전 산출물과 비교할 수 있습니다.
