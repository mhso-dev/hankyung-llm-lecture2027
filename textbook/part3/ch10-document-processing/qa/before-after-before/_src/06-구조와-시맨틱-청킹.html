1학습 목표

  • 이 절을 마치면 Markdown 제목과 빈 줄 경계를 사용해 구조 기반 청크를 만들 수 있습니다.
  • 이 절을 마치면 인접 문장 임베딩의 변화량을 사용한 시맨틱 청킹의 경계 결정 과정을 설명할 수 있습니다.
  • 이 절을 마치면 이 장의 구조·시맨틱 청킹 구현이 지원하는 입력과 지원하지 않는 입력을 구분할 수 있습니다.
  • 이 절을 마치면 구조 보존, 경계 수, 임베딩 호출량을 비교하고 어느 방식이 유리한지 조건부로 설명할 수 있습니다.

2왜 지금 이것인가

05절의 세 방식은 길이를 먼저 봅니다. 재귀 청킹이 문단을 우선 보존하더라도 “제3조”, “적용 범위”, 표의 행처럼 업무 문서가 가진 역할을 이해하지는 않습니다. 문서의 제목과 요소 유형이 이미 파싱 결과에 들어 있다면 그 정보를 버리지 않고 경계에 사용할 수 있습니다. 구조 기반 청킹은 파서가 찾아낸 제목·문단·표의 관계를 청크에도 이어 줍니다.

반대로 제목이 없거나 작성 형식이 일정하지 않은 문서도 있습니다. 회의록 한 문단 안에서 예산 이야기에서 일정 이야기로 주제가 바뀔 수 있습니다. 시맨틱 청킹은 인접한 문장들의 임베딩이 크게 달라지는 지점을 의미 경계 후보로 봅니다. 구조와 의미는 서로 다른 증거입니다. 구조는 작성자가 표시한 경계를 사용하고, 의미는 모델이 계산한 변화량을 사용합니다. 어느 한쪽이 항상 우수하다고 가정하지 않고 입력 문서가 제공하는 증거에 맞춰 선택합니다.

3선수 지식 되짚기

  • 02~04절 파서 출력 — HTML 제목과 HWPX 문단·표처럼 파서가 보존한 요소 유형이 구조 기반 청킹의 입력입니다. 평문만 남긴 파서 출력에는 원래 구조를 다시 붙일 수 없습니다.
  • 05절 재귀 청킹 — 길이와 구분자 우선순위로 경계를 정했습니다. 구조 기반 청킹도 너무 긴 절을 다시 나눌 때 이 방식을 보조 단계로 사용할 수 있습니다.
  • Ch 5·Ch 9 임베딩 — 의미가 비슷한 텍스트를 가까운 벡터로 표현했습니다. 시맨틱 청킹은 검색 전에 이 계산을 인접 문장 경계 판단에 사용합니다.

4핵심 개념

비유 — 목차를 따를지, 대화 주제의 변화를 들을지

잘 편집된 보고서는 목차와 소제목이 방의 문패처럼 붙어 있습니다. 문패가 바뀔 때 새 청크를 시작하면 작성자가 의도한 구역을 따를 수 있습니다. 형식이 없는 회의 대화에는 문패가 없습니다. 이때는 인접한 발언의 내용이 얼마나 달라졌는지를 보고 주제가 바뀐 지점을 찾습니다. 구조 기반 청킹은 문패를 읽고, 시맨틱 청킹은 내용의 변화를 비교합니다.

정의

구조 기반 청킹 (structure-aware chunking)
제목 수준, 문단, 목록, 표, 쪽과 같은 문서 구조를 경계와 메타데이터로 사용하는 방식입니다. 구조 정보가 정확할수록 작성자의 논리 단위를 보존하기 쉽습니다.
시맨틱 청킹 (semantic chunking)
문장이나 문장 묶음의 임베딩을 비교해 의미 변화가 큰 지점에서 청크를 나누는 방식입니다. 임베딩 모델과 경계 임계값에 따라 결과가 달라집니다.
의미 경계 (semantic boundary)
앞뒤 텍스트의 주제가 충분히 달라졌다고 판단해 새 청크를 시작하는 위치입니다. 정답으로 주어진 경계가 아니라 계산 기준으로 선택한 후보입니다.
중단점 (breakpoint)
거리나 변화량이 설정 기준을 넘어서 분할이 일어나는 지점입니다. 백분위수나 고정 임계값 같은 규칙으로 정하며, 문서별 분포를 확인해야 합니다.
제목 경계 (header boundary)
Markdown의 #처럼 제목임을 명시한 위치입니다. 제목을 청크 본문 앞에 남기면 뒤따르는 문단이 어느 주제에 속하는지 확인할 수 있습니다.

두 방식이 사용하는 증거

구조 기반 구현의 범위

이 장의 구현은 모든 PDF의 시각적 레이아웃을 분석하는 범용 시스템이 아닙니다. 예제에서 명시한 Markdown 제목과 빈 줄을 블록 경계로 사용합니다. 블록을 max_chars 안에서 결합하고, 한 블록이 너무 길면 재귀 방식으로 다시 나눕니다. 원래 문서 메타데이터와 청킹 방식은 유지하지만 제목 계층을 별도 메타데이터 필드로 해석하지는 않습니다. 병합 셀, 다단 편집, 머리글 반복, 글꼴 크기로만 표시한 제목은 이 함수가 처리하지 못합니다.

실무에서 표 하나를 독립 요소로 유지할지 제목과 함께 묶을지는 질문 유형에 달려 있습니다. “휴가 일수”처럼 한 셀을 찾는 질문과 “등급별 휴가 차이”처럼 여러 행을 비교하는 질문은 필요한 범위가 다릅니다. 이 예제 함수는 표 구조를 직접 해석하지 않으므로, 파서 단계에서 표를 Markdown이나 구조화된 텍스트로 변환한 뒤 결과를 검사해야 합니다.

시맨틱 구현의 범위

시맨틱 방식은 문장을 나눈 뒤 인접한 문장 또는 문장 묶음의 임베딩을 비교합니다. 이 절의 함수는 인접 문장의 코사인 유사도가 임계값보다 낮은 위치를 새 청크의 시작점으로 선택합니다. 따라서 같은 문장들에 더 높은 임계값을 적용하면 분할 조건을 만족하는 위치가 늘 수 있습니다. 너무 짧은 청크를 이웃과 합치는 후처리는 이 예제에 포함하지 않습니다. 이 과정에는 임베딩 호출이 추가됩니다. 청크를 최종 임베딩하기 전에 경계를 찾기 위해 이미 임베딩을 계산하므로 캐시가 없으면 비용과 시간이 늘어납니다.

의미 경계는 사람이 작성한 제목을 복원하지 않습니다. 숫자와 고유명사가 반복되는 규정 문서는 서로 다른 조항도 벡터상 가깝게 보일 수 있고, 짧은 문장은 주변 문맥이 부족해 변화량이 커질 수 있습니다. 따라서 결과에서 경계 전후 문장을 출력하고 사람이 읽을 수 있게 남깁니다.

제목 계층과 임베딩 변화량으로 나누기

구조 함수는 Markdown 제목과 빈 줄로 만든 블록을 결합하고, 시맨틱 함수는 문장을 분리한 뒤 인접 벡터의 코사인 유사도가 임계값보다 낮을 때 새 그룹을 시작합니다. 두 함수가 같은 Document 목록 형태를 반환하므로 08절에서 길이 기반 방식과 같은 기록 형식으로 비교할 수 있습니다.

7주의할 점과 실무 메모

  • 구조 품질은 파서 품질에 의존합니다. PDF에서 제목과 본문을 구분하지 못했다면 구조 기반 청킹도 그 차이를 알 수 없습니다. 02절의 PDF 파서 비교 결과와 함께 판단합니다.
  • 시맨틱 방식은 모델 의존적입니다. 임베딩 모델이 바뀌면 거리 분포와 중단점이 바뀝니다. 모델 이름, 버전, 기준값을 캐시 키와 실험 설정에 포함합니다.
  • 한국어 문장 분리. 마침표만으로 나누면 목록, 조문, 괄호, 표 셀을 잘못 처리할 수 있습니다. 문장 분리기의 이름과 규칙을 기록하고 원문 위치를 유지합니다.
  • 실제 구현 한계 공개. 이 절의 코드는 제목 표시가 있는 텍스트와 작은 예제에서 두 방식을 비교합니다. 범용 레이아웃 분석이나 상용 시맨틱 스플리터 전체 기능을 구현했다고 표현하지 않습니다.

8정리와 다음 절

  • 이 절의 구조 기반 청킹은 Markdown 제목과 빈 줄 경계를 사용하며, 긴 블록만 재귀 방식으로 다시 나눕니다.
  • 시맨틱 청킹은 인접 문장의 임베딩 변화량으로 의미 경계 후보를 정하며 추가 계산과 모델 의존성이 생깁니다.
  • 두 방식 모두 입력 계약과 구현 범위가 있으며, 청크 수만으로 우열을 판단할 수 없습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 청크와 질문을 같은 벡터 공간에 놓을 임베딩 모델을 비교하고, 시맨틱 경계 계산과 색인에 필요한 임베딩 결과를 안전하게 캐시합니다. 08절은 구조·시맨틱 방식의 관찰을 포함하되, 필수 3×2 실험은 재현 가능한 세 청킹 설정으로 고정합니다.

9복습 문제

문제 4개 · 해설 포함

1. 구조 기반 청킹이 사용해야 하는 입력 정보 두 가지를 쓰세요.

이 절의 구현은 Markdown 제목 표시와 빈 줄 경계를 사용합니다. 더 일반적인 구조 청킹에서는 파서가 제공한 제목 수준과 문단·표 같은 요소 유형이 필요합니다.

2. 시맨틱 청킹의 중단점은 무엇을 뜻합니까?

인접한 문장 또는 문장 묶음의 임베딩 변화량이 설정 기준을 넘어 새 청크를 시작하기로 한 위치입니다. 사람이 표시한 정답 경계가 아니라 모델과 규칙으로 선택한 후보입니다.

3. 제목 글꼴만 큰 PDF를 평문으로 파싱한 뒤 구조 기반 청킹을 실행했습니다. 제목 경계를 식별하기 어려운 원인과 개선 순서를 설명하세요.

평문 파서가 글꼴과 제목 유형을 버렸으므로 청킹 함수가 사용할 구조 정보가 없습니다. 먼저 레이아웃이나 제목을 보존하는 파서를 선택하고, 제목을 Markdown 표시나 별도 필드로 변환한 뒤 그 입력 계약에 맞는 청킹을 해야 합니다.

4. 시맨틱 방식이 구조 방식보다 청크 수가 적게 나왔습니다. 이 결과만으로 시맨틱 방식이 우수하다고 할 수 없는 이유는 무엇입니까?

청크 수는 저장 규모의 관찰값일 뿐 검색 품질을 나타내지 않습니다. 제목·표 구조 보존 여부, 정답 근거의 포함 여부, 임베딩 호출 시간과 비용을 함께 기록하고 Ch 11의 검색 지표로 비교해야 합니다.

시간 배분 · 시연 순서 · 예상 질문 · 막히는 지점 · A/B 트랙

시간 배분(3h) — 강의 60분: 구조와 의미의 두 증거(15) · 제목 경계(15) · 시맨틱 중단점 계산(20) · 구현 범위와 비용(10). 실습 120분: 구조 청킹 실행(30) · 청크 본문·출처 메타데이터 검사(25) · 시맨틱 경계 실행(30) · 실패 세 가지 재현(20) · 비교 기록(15).

시연 순서 — ① 제목 계층이 있는 짧은 문서를 구조 함수에 입력 ② 결과 청크의 본문과 chunk_id 출력 ③ 제목 표시를 제거해 입력 계약 확인 ④ 주제가 두 번 바뀌는 문장 묶음의 변화량 출력 ⑤ 기준값을 바꾸며 경계 전후 문장을 나란히 표시.

예상 질문 — “PDF 글꼴 크기로 제목을 자동 판별하나요?” → 이 장의 함수는 파서가 제공한 제목 표시만 사용합니다. “시맨틱이면 의미를 이해한 정답 경계인가요?” → 임베딩 변화량으로 고른 후보이며 모델과 기준값에 따라 달라집니다. “두 방식을 섞어도 되나요?” → 제목으로 먼저 나누고 너무 긴 절 안에서 시맨틱이나 재귀 분할을 적용할 수 있지만 별도 설정으로 기록해야 합니다.

학생이 자주 막히는 지점 — 구조 정보가 없는 평문에 구조 함수를 적용하는 경우, 제목 경로를 청크 본문에만 넣고 메타데이터에는 남기지 않는 경우, 시맨틱 청킹의 임베딩 비용을 최종 색인 비용과 별도로 기록하지 않는 경우를 확인합니다.

A/B 트랙 — A트랙은 제공된 제목·표 예제로 구조 보존과 의미 경계를 비교합니다. B트랙은 제목으로 먼저 나눈 뒤 긴 절에만 시맨틱 분할을 적용하고, 단독 방식과 청크 수·호출량·경계 사례를 비교합니다.
