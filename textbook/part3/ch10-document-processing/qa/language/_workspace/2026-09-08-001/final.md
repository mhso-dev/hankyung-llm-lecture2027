4핵심 개념

비유 — 접수대에서 만드는 표준 봉투

한 기관의 접수대에 종이 신청서, 이메일 인쇄물, 엑셀 목록이 함께 들어온다고 생각해 보세요. 담당자는 원본을 그대로 창고에 보관하고, 처리 부서에는 같은 모양의 봉투로 전달합니다. 봉투 앞면에는 접수 번호, 원본 종류, 접수 시각, 담당 부서를 적습니다. 처리 부서는 봉투 안의 본문을 읽으면 되고, 원본 형식에 따라 접수 방법이 달랐다는 사실까지 알 필요는 없습니다. 로더가 하는 일도 이와 같습니다. 파일별 파서는 다르지만, 청킹 단계에 넘기는 결과는 같은 [PROTECTED_CODE] 구조여야 합니다.

정의

문서 객체 (Document)

추출한 본문과 부가 정보를 한 단위로 묶은 객체입니다. LangChain의 [PROTECTED_CODE]는 [PROTECTED_CODE]와 [PROTECTED_CODE]를 가집니다. 이후 청킹·임베딩·검색은 원본 파일 대신 이 객체를 받습니다.

파서 (parser)

파일의 내부 구조를 해석하여 텍스트, 표, 이미지 위치 같은 내용을 추출하는 프로그램입니다. 같은 PDF라도 파서에 따라 읽기 순서와 표 표현이 달라질 수 있습니다.

메타데이터 (metadata)

본문을 설명하는 부가 정보입니다. 문서 ID, 원본 파일명, 쪽 번호, 형식, 수정 시각처럼 검색 필터와 출처 표기에 필요한 값을 담습니다.

출처 계보 (provenance)

산출물이 어느 원본에서 어떤 처리 과정을 거쳐 만들어졌는지 추적할 수 있는 기록입니다. [PROTECTED_CODE], [PROTECTED_CODE], [PROTECTED_CODE]를 함께 남기면 검색된 청크를 원본까지 거슬러 확인할 수 있습니다.

6일부러 실패해 보기

실패 1 — 파일명만으로 문서 ID를 만든다. [PROTECTED_CODE]라는 파일이 두 부서 폴더에 하나씩 있으면 파일명 줄기만 사용한 ID가 충돌합니다. 두 문서의 청크가 같은 문서로 집계되고, Ch 11의 정답 비교도 잘못됩니다. 상대 경로를 포함하거나 업무 시스템의 고유 번호를 사용하여 충돌을 막아야 합니다.

실패 2 — 절대 경로를 [PROTECTED_CODE]에 저장한다. 개발자의 사용자 이름이 포함된 경로를 색인에 넣으면 다른 컴퓨터에서 출처 링크가 열리지 않고, 실행 로그를 공유할 때 개인 정보가 노출될 수 있습니다. 프로젝트 데이터 루트를 기준으로 한 상대 경로를 저장하고, 실제 파일을 열 때만 로컬 루트와 결합합니다.

실패 3 — 지원하지 않는 확장자를 조용히 건너뛴다. 처리 대상 폴더에 HWP가 있는데 PDF만 읽는 코드가 아무 경고 없이 종료되면 사용자는 모든 문서가 색인되었다고 오해합니다. 지원하지 않는 형식은 별도 목록에 기록하고, 입력 건수와 성공·실패·건너뜀 건수의 합이 일치하는지 검사해야 합니다.

1학습 목표

이 절을 마치면 디지털 PDF와 스캔 PDF의 차이를 설명하고, 텍스트 추출과 OCR 적용 조건을 구분할 수 있습니다.

이 절을 마치면 일반 텍스트 추출 결과에서 표의 행·열 관계와 읽기 순서가 손실되는 사례를 원본 쪽과 대조할 수 있습니다.

이 절을 마치면 같은 PDF를 두 가지 추출 모드로 처리하고, 글자 수·한글 비율·표 보존 여부를 근거로 결과를 기록할 수 있습니다.

2왜 지금 이것인가

Ch 9의 [PROTECTED_CODE]는 [PROTECTED_CODE]의 기본 텍스트 추출로 RAG를 완주하는 데 충분했습니다. 그러나 중간 난이도 문서의 표와 어려운 문서의 두 단 레이아웃에서는 글자가 추출되어도 의미가 보존되지 않을 수 있습니다. 스캔 변형본 세 건은 이미지 안에 글자가 있으므로 추출 결과가 비어 있습니다. 파일을 열 수 있다는 사실과 검색에 사용할 수 있는 본문을 얻었다는 사실을 구분해야 합니다.

PDF는 화면이나 인쇄 결과를 정확히 배치하기 위한 형식입니다. 일부 PDF는 태그나 구조 정보를 가질 수 있지만, 일반적인 텍스트 추출이 문단·표·머리말이라는 의미 구조를 항상 복원할 수 있는 것은 아닙니다. 글자가 쪽의 절대 좌표에 놓여 있으면 추출기는 어느 글자가 같은 행과 열인지 추정해야 합니다. 따라서 파서의 성공 여부를 “문자열이 반환되었다” 하나로 판정해서는 안 됩니다. 원본에서 중요했던 구조가 검색 가능한 표현으로 남았는지 확인해야 합니다.

4핵심 개념

비유 — 좌석 배치도와 참석자 명단

회의장 좌석 배치도에는 사람 이름이 공간에 놓여 있습니다. 글자를 위에서 아래로만 읽으면 왼쪽 열과 오른쪽 열의 이름이 섞일 수 있습니다. 표도 같습니다. 사람은 선과 간격을 보고 같은 행을 알아보지만, 텍스트 추출기는 좌표를 읽기 순서로 바꾸는 규칙이 필요합니다. OCR은 사진 속 이름표를 문자로 바꾸는 일입니다. 문자로 바꾼 뒤에도 어느 좌석에 해당하는지 정리하는 작업은 별도로 남습니다.

정의

텍스트 레이어 (text layer)

PDF 안에서 선택·검색할 수 있는 문자 정보입니다. 스캔 PDF는 페이지 이미지밖에 없어 텍스트 레이어가 없을 수 있습니다.

레이아웃 (layout)

글자·문단·열·표가 쪽 위에 배치된 공간 관계입니다. 문자열 추출 과정에서 이 관계의 일부가 사라질 수 있습니다.

읽기 순서 (reading order)

사람이 문서 내용을 따라가는 순서입니다. 두 단 문서에서는 왼쪽 단을 끝까지 읽은 뒤 오른쪽 단으로 가야 하지만, 좌표 해석에 따라 줄별로 섞일 수 있습니다.

표 추출 (table extraction)

표의 셀 경계와 행·열 관계를 찾아 구조화된 값으로 복원하는 처리입니다. 일반 텍스트 추출과 별도의 검출 전략이 필요할 수 있습니다.

광학 문자 인식 (optical character recognition, OCR)

페이지 이미지의 글자 모양을 문자로 인식하는 처리입니다. OCR은 오탈자를 만들 수 있으며 표 구조를 자동으로 보장하지 않습니다.

OCR 적용 여부는 파일 단위보다 쪽 단위로 결정하는 편이 안전합니다. 디지털 PDF 전체를 이미지로 바꿔 OCR하면 원래 PDF에 있던 글꼴·인코딩 정보가 사라지고, 비슷한 문자를 잘못 인식할 수 있습니다. 처리 시간도 늘어납니다. 먼저 추출 문자열 길이, 한글 비율, 대체 문자 수를 기록하고, 값이 낮은 쪽을 사람 검토 대상으로 표시합니다. OCR을 적용한 쪽에는 [PROTECTED_CODE]와 사용한 엔진·언어 설정을 메타데이터에 남깁니다.

검사확인하는 문제자동 판정의 한계

추출 글자 수빈 스캔 쪽, 지나치게 짧은 결과표지처럼 실제로 짧은 쪽도 있습니다.

한글 비율글꼴 인코딩 오류, OCR 언어 설정 오류영문 사양표에는 낮은 값이 정상일 수 있습니다.

표 머리글과 값의 인접성행·열 관계 손실문자열 규칙만으로 병합 셀을 확정하기 어렵습니다.

원본 쪽 대조누락·순서·표 구조사람 검토가 필요하지만 대표 쪽에 한정할 수 있습니다.

6일부러 실패해 보기

실패 1 — 추출 글자 수만 보고 성공으로 판정합니다. 표의 모든 숫자가 문자열에 있어도 열 머리글과 값의 연결이 끊기면 질의에 답할 수 없습니다. 원본 표의 한 행을 고르고, 머리글·조건·값이 추출 결과에서 함께 읽히는지 확인합니다.

실패 2 — 모든 PDF에 OCR을 강제로 적용합니다. 디지털 PDF의 정확한 문자 정보가 이미지 인식 결과로 대체되어 글자가 바뀌거나 처리 시간이 늘 수 있습니다. 먼저 기존 텍스트를 검사하고 필요한 쪽에만 OCR을 적용합니다.

실패 3 — 두 단 문서의 문자열을 그대로 청킹합니다. 왼쪽 단과 오른쪽 단이 한 줄씩 번갈아 섞이면 한 청크 안에 서로 다른 문장이 연결됩니다. [PROTECTED_CODE]는 주어진 문자열의 순서가 맞다고 가정하므로, 청킹 설정을 바꾸어도 파서 단계의 순서 오류를 고치지 못합니다.

7주의할 점과 실무 메모

PDF는 의미 구조를 항상 보장하지 않습니다. 태그가 있는 PDF도 있지만, 일반 텍스트 추출이 표·문단 구조를 안정적으로 복원한다고 전제하지 않습니다.

OCR 엔진은 별도 의존성입니다. PyMuPDF의 통합 OCR도 Tesseract 설치가 필요합니다. 설치·언어 데이터·버전을 실행 환경에 기록합니다.

메모리를 확인합니다. 압축된 콘텐츠 스트림이 매우 크게 풀리는 PDF가 있으므로 파일 크기만으로 처리 비용을 판단하지 않습니다.

라이선스를 확인합니다. PyMuPDF/MuPDF는 AGPL 또는 상용 라이선스 체계입니다. 교육 실습과 제품 배포의 조건을 별도로 검토합니다.

상용 API 가격은 확인일과 함께 적습니다. Upstage의 Parse only 가격은 2026-09-08 기준 페이지당 미화 0.01달러로 표시되지만 변경될 수 있습니다. LlamaParse는 티어와 파서 버전을 실행 기록에 고정합니다.

8정리와 다음 절

디지털 PDF의 문자 추출, 표 구조 복원, 스캔 이미지 OCR은 서로 다른 문제입니다.

기본 추출과 레이아웃 추출은 [PROTECTED_CODE] 안의 두 모드이며, 표 구조를 보장하는 독립 파서 비교가 아닙니다.

텍스트 품질을 쪽 단위로 검사하고 필요한 쪽만 OCR 후보로 보내며, 표와 읽기 순서는 원본과 대조합니다.

다음 학습과 이어지는 지점 — 현재 로더가 붙인 [PROTECTED_CODE]·[PROTECTED_CODE]와 OCR을 실제로 연결할 때 추가할 [PROTECTED_CODE]는 Ch 11에서 실패 질의를 묶는 기준이 됩니다. 이번 실행은 S01의 5쪽만 판정했으며, S02·S03은 같은 함수로 확인하는 학습자 과제입니다. 다음 03절에서는 DOCX·HTML·CSV의 구조를 공통 계약으로 옮깁니다.

9복습 문제

문제 4개 · 해설 포함

1. [하] 텍스트 추출과 OCR의 차이는 무엇입니까?

텍스트 추출은 PDF에 이미 저장된 문자 정보를 읽습니다. OCR은 페이지 이미지의 글자 모양을 새 문자로 인식합니다.

2. [중] PDF에서 모든 숫자가 추출되었는데도 표 질의에 답하지 못하는 이유는 무엇입니까?

숫자와 행·열 머리글의 관계가 사라질 수 있기 때문입니다. 표 질의에는 값 자체뿐 아니라 그 값이 어떤 조건과 항목에 해당하는지 필요합니다.

3. [중] 디지털 PDF 전체에 OCR을 강제로 적용하지 않는 이유를 두 가지 쓰세요.

원래의 정확한 문자·인코딩 정보를 잃고 OCR 오탈자가 생길 수 있으며, 이미지 렌더링과 인식 때문에 처리 시간과 자원이 늘어납니다.

4. [상] 두 단 PDF의 읽기 순서가 잘못된 상태에서 청크 크기만 조정하면 해결되지 않는 이유는 무엇입니까?

1학습 목표

이 절을 마치면 HWP와 HWPX가 내부 구조와 처리 방법에서 어떻게 다른지 설명할 수 있습니다.

이 절을 마치면 HWPX의 ZIP 컨테이너와 XML 항목을 조사하여 텍스트 단위를 추출하고 출처 메타데이터를 붙일 수 있습니다.

이 절을 마치면 HWP 처리에서 변환·전용 SDK·상용 파서를 선택해야 하는 경계를 정하고, 실행하지 않은 기능을 지원한다고 단정하지 않을 수 있습니다.

2왜 지금 이것인가

한국의 공공기관과 기업 문서 저장소에는 HWP와 HWPX가 함께 있습니다. PDF만 처리하는 RAG는 결재문, 공고문, 회의 자료의 일부를 놓칠 수 있습니다. 그러나 두 확장자를 같은 방식으로 읽을 수 있다고 생각하면 구현 범위를 잘못 잡게 됩니다. HWP는 전용 구조를 해석해야 하는 네이티브 형식이고, HWPX는 XML 파일을 ZIP 컨테이너에 묶은 개방형 형식입니다. 이번 절은 모든 한글 문서를 완벽하게 파싱한다고 약속하는 대신, 형식을 식별하고 검증 가능한 처리 경로를 선택하는 방법을 다룹니다.

현재 [PROTECTED_CODE]의 기본 21건은 PDF입니다. HWP/HWPX 전용 샘플의 성공 여부는 실습 폴더에 실제 파일이 있고 코드가 실행된 경우에만 기록합니다. 샘플이 없다면 HWPX 구조 관찰용 최소 픽스처와 실패 메시지만 검증하고, 실제 업무 문서 호환성을 주장하지 않습니다. 자기 도메인 문서 100건도 아직 저장소에 없으므로 HWP/HWPX 비율이나 성공률을 제시하지 않습니다.

Ch 2 ZIP·XML 처리 — 표준 라이브러리로 압축 항목을 열고 XML 요소를 순회하는 기본 절차를 사용합니다.

01절 공통 계약 — 원본 형식, 파서, 문서 ID, 출처 경로를 모든 결과에 남깁니다.

03절 형식 보존 단위 — DOCX의 표 구분 표식과 HTML 줄 경계는 본문에, CSV 행 번호는 메타데이터에 남겼습니다. 더 세밀한 단위 필드는 확장 과제로 구분했습니다.

4핵심 개념

비유 — 잠긴 서류함과 라벨이 붙은 상자

HWP를 규격에 맞는 열쇠와 해석표가 필요한 서류함이라고 생각해 보세요. HWPX는 여러 XML 문서를 라벨이 붙은 상자에 나누어 담고, 그 상자를 ZIP으로 묶은 형태에 가깝습니다. HWPX는 상자를 열어 항목을 확인하기가 더 수월하지만, 라벨을 읽었다고 문단·표·각주가 저절로 완성되는 것은 아닙니다. 어떤 XML이 본문이고 요소의 순서가 무엇인지 해석해야 합니다.

정의

HWP 네이티브 형식 (HWP native format)

한컴 한글의 전용 문서 형식입니다. 내부 레코드와 구조를 이해하는 전용 도구 또는 변환 경로가 필요하며, 범용 ZIP/XML 처리만으로 읽을 수 없습니다.

HWPX

OWPML에 기반하고 국가표준 KS X 6101에 등록된 XML 기반 개방형 파일 형식입니다. 여러 XML과 자원을 ZIP 컨테이너에 담습니다.

개방형 워드프로세서 마크업 언어 (Open Word-Processor Markup Language, OWPML)

HWPX 문서의 구조와 내용을 XML로 표현하는 규격입니다. 본문, 설정, 메타데이터가 여러 항목으로 나뉠 수 있습니다.

ZIP 컨테이너 (ZIP container)

여러 XML·이미지·설정 파일을 하나의 문서 파일로 묶는 저장 방식입니다. 확장자가 [PROTECTED_CODE]여도 내부 항목과 필수 파일을 검사해야 합니다.

[PROTECTED_TEMPLATE]
HWP는 전용 바이너리 해석기나 변환 도구를 거치고, HWPX는 ZIP 안의 XML을 검사합니다. 두 경로의 결과는 공통 [PROTECTED_CODE]와 출처 메타데이터로 합쳐집니다.

HWPX 처리의 첫 단계는 파일을 열어 항목 목록을 확인하는 것입니다. 그다음 본문 XML을 문서 순서대로 읽고, 텍스트 노드와 문단 경계를 추출합니다. 파일 안의 모든 XML 텍스트를 합치면 스타일 이름, 설정값, 메타데이터가 본문에 섞일 수 있습니다. 본문 항목을 명시적으로 선택하고, 문단 번호나 구역 파일명을 [PROTECTED_CODE]에 남깁니다. 표와 병합 셀은 별도의 구조 해석이 필요하므로 기본 텍스트 로더가 어느 요소를 지원하는지 문서화합니다.

HWP에는 세 가지 현실적인 경로가 있습니다. 첫째, 신뢰할 수 있는 환경에서 HWPX나 PDF로 변환한 뒤 변환 산출물을 처리합니다. 둘째, 한컴이 제공하는 도구나 SDK를 사용합니다. 셋째, 조직의 보안 정책이 허용하면 상용 문서 파서에 전달합니다. 어느 경로든 원본과 변환본의 관계, 변환 도구 버전, 실패 파일을 기록합니다. 변환에 성공했다는 사실이 표·각주·변경 내용까지 보존되었다는 뜻은 아니므로 대표 문서를 원본과 대조합니다.

6일부러 실패해 보기

실패 1 — 확장자만 보고 ZIP으로 엽니다. 이름만 [PROTECTED_CODE]로 바꾼 HWP 파일이나 손상된 파일은 유효한 ZIP이 아닙니다. 압축 열기 실패를 잡아 “본문 없음”으로 처리하지 말고 잘못된 형식 또는 손상으로 기록합니다.

실패 2 — 모든 XML의 텍스트를 합칩니다. 문서 설정과 메타데이터의 값이 본문에 섞이고, 구역 순서가 뒤바뀔 수 있습니다. 본문 항목과 네임스페이스를 명시하여 필요한 요소만 순회합니다.

실패 3 — HWP를 지원한다고 표시하고 실제 호출은 건너뜁니다. 라이브러리가 설치되었다는 사실만으로 샘플 문서 호환성을 보장할 수 없습니다. 입력 파일, 도구 버전, 산출 단위, 원본 대조가 모두 확인된 경우에만 지원 범위에 포함합니다.

7주의할 점과 실무 메모

HWP와 HWPX를 같은 형식으로 취급하지 않습니다. 확장자별 처리 경로와 실패 메시지를 분리합니다.

HWPX도 완전한 평문 형식은 아닙니다. ZIP 안의 여러 XML, 이미지, 표, 각주 관계를 해석해야 합니다.

변환본의 출처를 남깁니다. 원본 HWP의 ID, 변환 파일 경로, 변환 도구와 시각을 기록해야 갱신과 오류 조사가 가능합니다.

외부 전송 정책을 먼저 확인합니다. 계약서·인사 문서·개인정보가 든 HWP를 상용 API에 보내기 전에 조직의 승인과 보관 정책을 확인합니다.

호환성 표는 실제 샘플로 만듭니다. 문단, 표, 병합 셀, 각주, 이미지, 암호화 문서를 각각 검사하고 성공·부분 성공·실패로 구분합니다.

8정리와 다음 절

HWP는 전용 해석 또는 변환 경로가 필요하고, HWPX는 OWPML 기반 XML을 ZIP에 담은 개방형 형식입니다.

HWPX는 본문 XML과 문서 순서를 명시적으로 해석하며, 모든 XML 텍스트를 무분별하게 합치지 않습니다.

실제 샘플과 실행 결과가 없는 HWP/HWPX 지원 범위, 상용 파서 품질, 100건 처리 성공률은 주장하지 않습니다.

다음 학습과 이어지는 지점 — 01~04절에서 만든 [PROTECTED_CODE]가 다음 청킹 절의 입력입니다. 현재 HWPX 로더는 구역 번호를 남기며, 문단·표·각주 단위는 추가 구현이 필요합니다. Ch 11에서는 [PROTECTED_CODE]과 [PROTECTED_CODE]별로 검색 실패를 묶어 어느 형식의 처리부터 개선할지 결정합니다.

9복습 문제

문제 4개 · 해설 포함

1. [하] HWP와 HWPX의 내부 구조 차이를 한 문장으로 설명하세요.

HWP는 전용 구조를 해석해야 하는 네이티브 형식이고, HWPX는 OWPML 기반 XML과 자원을 ZIP 컨테이너에 담은 개방형 형식입니다.

2. [중] HWPX 안의 모든 XML 텍스트를 합치면 어떤 문제가 생깁니까?

설정·메타데이터가 본문에 섞이고 구역 순서가 어긋날 수 있으며, 표·각주 관계도 잃을 수 있습니다. 본문 항목과 필요한 요소를 명시해야 합니다.

3. [중] HWP를 HWPX로 변환한 뒤에도 원본 대조가 필요한 이유는 무엇입니까?

변환 성공은 문단·표·병합 셀·각주·이미지가 모두 보존되었다는 보장이 아닙니다. 검색에 필요한 구조와 값이 남았는지 대표 문서로 확인해야 합니다.

4. [상] 상용 파서 API를 HWP 처리 경로로 채택하기 전에 확인할 항목을 네 가지 쓰세요.

공식 입력 형식 지원, 실제 한국어 샘플 결과, 외부 전송·보관 정책, 자격증명과 비용, 파서 버전 고정 가운데 네 가지 이상을 확인합니다.

긴 컨텍스트 모델을 보고 청크도 크게 만들면 된다고 생각하기 쉽습니다. 그러나 큰 청크는 주변 문맥을 더 보존하는 대신 질문과 무관한 문장도 함께 가져옵니다. 입력 토큰과 임베딩 시간도 늘어날 수 있습니다. 작은 청크는 질문에 맞는 문장을 정밀하게 찾기 쉽지만 설명과 조건이 서로 갈라질 수 있습니다. 이 절의 목표는 한 가지 크기를 정답으로 고르는 것이 아닙니다. 같은 문서를 세 방식으로 나누고, 각 방식이 무엇을 보존하고 무엇을 잃는지 실행 결과로 확인하는 것입니다.

비유 — 원고를 여러 크기의 카드로 나누기

긴 업무 규정을 카드에 나누어 적는다고 생각합니다. 문자 청킹은 카드 한 장에 글자를 일정 수만큼 적고 다음 카드로 넘어갑니다. 재귀 청킹은 먼저 문단을 통째로 넣어 보고, 카드에 들어가지 않으면 문장과 띄어쓰기 순서로 더 잘게 나눕니다. 토큰 청킹은 글자 수 대신 모델이 세는 조각 수를 카드의 한도로 씁니다. 세 방법 모두 카드를 만들지만 경계를 고르는 기준이 다릅니다.

정의

문자 청킹 (character chunking)

문자열의 문자 수를 기준으로 일정한 길이의 조각을 만드는 방식입니다. 구현이 명확하고 빠르지만 제목, 문장, 단어의 경계를 고려하지 않으면 중요한 표현 중간에서 끊길 수 있습니다.

재귀 청킹 (recursive chunking)

문단 구분, 줄바꿈, 문장 부호, 띄어쓰기처럼 큰 경계부터 차례로 시도하고, 조각이 너무 길 때만 더 작은 경계로 내려가는 방식입니다. 경계 후보의 우선순위가 결과를 좌우합니다.

토큰 청킹 (token chunking)

특정 토크나이저가 계산한 토큰 수를 기준으로 청크 한도를 맞추는 방식입니다. 모델 입력 한도와 비용을 직접 관리하기 좋지만, 토크나이저가 바뀌면 같은 텍스트의 경계도 달라질 수 있습니다.

구분자 우선순위 (separator priority)

재귀 청킹에서 어느 경계를 먼저 보존할지 정한 순서입니다. 일반적으로 문단, 줄, 문장, 띄어쓰기, 문자 순으로 내려가지만 한국어 문서의 목록·표·조문 형식에 맞게 조정해야 합니다.

실패 1 — 문장 경계를 무시합니다. 문자 청킹의 크기를 줄여 규정의 날짜, 금액, 예외 조건이 경계에 걸리게 만듭니다. 앞 청크에는 조건만 있고 다음 청크에는 결론만 남으면 어느 쪽도 질문에 완전한 근거를 제공하지 못합니다. 오버랩을 추가한 뒤 두 정보가 함께 들어오는 청크가 생기는지 비교합니다.

실패 3 — 문자 수를 토큰 수로 간주합니다. 같은 문자 수의 한국어 문장, 영문 문장, 이모지와 특수문자가 포함된 문장을 토큰화합니다. 토큰 수가 서로 달라지는 것을 확인하고, 문자 한도를 모델 입력 한도로 바로 환산하면 안 되는 이유를 설명합니다.

메타데이터 유지. 청크를 만들 때 [PROTECTED_CODE], 쪽, 원래 요소 유형을 복사합니다. 문자열 목록만 반환하면 검색 결과가 어느 파일과 위치에서 왔는지 추적할 수 없습니다.

8정리와 다음 절

문자 청킹은 문자 수, 재귀 청킹은 구분자 우선순위, 토큰 청킹은 토크나이저가 계산한 수를 기준으로 경계를 정합니다.

재귀 청킹의 오버랩은 실제 중복을 항상 보장하지 않는 최댓값이므로 결과 청크에서 측정해야 합니다.

큰 청크와 작은 청크의 장단점은 도메인별 품질·비용을 측정하여 비교합니다.

단정할 수 없습니다. 재귀 스플리터는 분할된 단위를 결합하며 이전 단위 가운데 한도 안에 들어오는 부분만 유지합니다. 설정값은 최댓값이고 실제 중복은 경계와 분할 단위에 따라 작아질 수 있으므로 청크를 직접 비교해야 합니다.

3. 한국어 500자와 영어 500자가 같은 토큰 수라고 가정하면 안 되는 이유는 무엇입니까?

토크나이저는 문자를 그대로 하나씩 세지 않고 학습된 어휘 단위로 나눕니다. 언어, 숫자, 특수문자, 이모지 구성에 따라 한 문자에 대응하는 토큰 수가 달라집니다.

4. 긴 컨텍스트 모델을 사용하므로 청크 크기를 두 배로 늘리자는 제안을 검토할 때 함께 기록해야 할 항목을 세 가지 이상 쓰세요.

청크 수와 길이 분포, 질문당 검색되는 총 토큰, 임베딩 시간과 비용, 정답 근거가 검색 범위에 포함되는지, 중복 청크 비율을 기록합니다. Ch 11 전에는 품질 지표가 비어 있으므로 비용이 낮거나 청크 수가 적다는 이유만으로 승자를 정하지 않습니다.

2왜 지금 이것인가

05절의 세 방식은 길이를 먼저 봅니다. 재귀 청킹이 문단을 우선 보존하더라도 “제3조”, “적용 범위”, 표의 행처럼 업무 문서가 가진 역할을 이해하지는 않습니다. 문서의 제목과 요소 유형이 이미 파싱 결과에 들어 있다면 그 정보를 버리지 않고 경계에 사용할 수 있습니다. 구조 기반 청킹은 파서가 찾아낸 제목·문단·표의 관계를 청크에도 이어 줍니다.

반대로 제목이 없거나 작성 형식이 일정하지 않은 문서도 있습니다. 회의록 한 문단 안에서 예산 이야기에서 일정 이야기로 주제가 바뀔 수 있습니다. 시맨틱 청킹은 인접한 문장들의 임베딩이 크게 달라지는 지점을 의미 경계 후보로 봅니다. 구조와 의미는 서로 다른 증거입니다. 구조는 작성자가 표시한 경계를 사용하고, 의미는 모델이 계산한 변화량을 사용합니다. 어느 한쪽이 항상 우수하다고 가정하지 않고 입력 문서가 제공하는 증거에 맞춰 선택합니다.

정의

구조 기반 청킹 (structure-aware chunking)

제목 수준, 문단, 목록, 표, 쪽과 같은 문서 구조를 경계와 메타데이터로 사용하는 방식입니다. 구조 정보가 정확할수록 작성자의 논리 단위를 보존하기 쉽습니다.

시맨틱 청킹 (semantic chunking)

문장이나 문장 묶음의 임베딩을 비교해 의미 변화가 큰 지점에서 청크를 나누는 방식입니다. 임베딩 모델과 경계 임계값에 따라 결과가 달라집니다.

의미 경계 (semantic boundary)

앞뒤 텍스트의 주제가 충분히 달라졌다고 판단해 새 청크를 시작하는 위치입니다. 정답으로 주어진 경계가 아니라 계산 기준으로 선택한 후보입니다.

중단점 (breakpoint)

거리나 변화량이 설정 기준을 넘어서 분할이 일어나는 지점입니다. 백분위수나 고정 임계값 같은 규칙으로 정하며, 문서별 분포를 확인해야 합니다.

제목 경계 (header boundary)

Markdown의 [PROTECTED_CODE]처럼 제목임을 명시한 위치입니다. 제목을 청크 본문 앞에 남기면 뒤따르는 문단이 어느 주제에 속하는지 확인할 수 있습니다.

시맨틱 구현의 범위

시맨틱 방식은 문장을 나눈 뒤 인접한 문장 또는 문장 묶음의 임베딩을 비교합니다. 이 절의 함수는 인접 문장의 코사인 유사도가 임계값보다 낮은 위치를 새 청크의 시작점으로 선택합니다. 따라서 같은 문장들에 더 높은 임계값을 적용하면 분할 조건을 만족하는 위치가 늘 수 있습니다. 너무 짧은 청크를 이웃과 합치는 후처리는 이 예제에 포함하지 않습니다. 이 과정에는 임베딩 호출이 추가됩니다. 청크를 최종 임베딩하기 전에 경계를 찾기 위해 이미 임베딩을 계산하므로 캐시가 없으면 비용과 시간이 늘어납니다.

의미 경계는 사람이 작성한 제목을 복원하지 않습니다. 숫자와 고유명사가 반복되는 규정 문서는 서로 다른 조항도 벡터상 가깝게 보일 수 있고, 짧은 문장은 주변 문맥이 부족해 변화량이 커질 수 있습니다. 따라서 결과에서 경계 전후 문장을 출력하고 사람이 읽을 수 있게 남깁니다.

실제 구현 한계 공개. 이 절의 코드는 제목 표시가 있는 텍스트와 작은 예제에서 두 방식을 비교합니다. 범용 레이아웃 분석이나 상용 시맨틱 스플리터 전체 기능을 구현했다고 표현하지 않습니다.

8정리와 다음 절

이 절의 구조 기반 청킹은 Markdown 제목과 빈 줄 경계를 사용하며, 긴 블록만 재귀 방식으로 다시 나눕니다.

시맨틱 청킹은 인접 문장의 임베딩 변화량으로 의미 경계 후보를 정하며 추가 계산과 모델 의존성이 생깁니다.

두 방식 모두 입력 계약과 구현 범위가 있으며, 청크 수만으로 우열을 판단할 수 없습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 청크와 질문을 같은 벡터 공간에 놓을 임베딩 모델을 비교하고, 시맨틱 경계 계산과 색인에 필요한 임베딩 결과를 안전하게 캐시합니다. 08절은 구조·시맨틱 방식의 관찰을 포함하되, 필수 3×2 실험은 재현 가능한 세 청킹 설정으로 고정합니다.

비유 — 같은 주소 체계와 보관함 표찰

서로 다른 도시의 지도 좌표를 한 표에 섞으면 거리를 비교할 수 없습니다. 청크는 A 모델로, 질문은 B 모델로 변환한 뒤 가까운 것을 찾는 일도 마찬가지입니다. 모델과 차원, 입력 규칙이 같아야 같은 주소 체계입니다. 한 번 계산한 좌표를 보관할 때는 어느 주소 체계로 만들었는지 표찰을 붙여야 합니다. 캐시 키가 그 표찰입니다.

정의

다국어 임베딩 (multilingual embedding)

여러 언어의 텍스트를 검색·분류 같은 작업에 사용할 수 있도록 벡터로 표현하는 모델입니다. 지원 언어 목록은 후보 조건이며 특정 한국어 업무 문서에서 높은 검색 품질을 보장하지 않습니다.

차원 (dimension)

임베딩 벡터에 들어 있는 숫자의 개수입니다. 차원이 커지면 저장 공간과 거리 계산량이 늘어날 수 있으며, 차원 수만으로 품질을 판단할 수 없습니다.

모델 리비전 (model revision)

같은 모델 이름 아래에서 사용한 정확한 코드·가중치 버전입니다. 로컬 오픈 모델은 커밋 SHA를 기록하고, API 모델은 공급자가 제공하는 고정 버전 식별자를 사용할 수 있는지 확인합니다.

입력 접두사 (input prefix)

모델 카드가 문서와 질의를 구분하기 위해 요구하는 앞부분입니다. 예를 들어 문서에는 [PROTECTED_CODE], 질의에는 [PROTECTED_CODE]를 붙이는 모델이 있으며 생략하면 모델 카드가 설명한 검색 방식과 달라집니다.

벡터 캐시 (vector cache)

같은 정규화 텍스트와 같은 임베딩 설정으로 계산한 벡터를 다시 사용하기 위한 저장소입니다. 캐시 키가 입력과 설정을 빠짐없이 구분해야 잘못된 벡터 혼용을 막을 수 있습니다.

인덱스 매니페스트 (index manifest)

원문, 파서, 청킹 설정, 청크 ID와 벡터 캐시 키의 대응을 기록한 목록입니다. 인덱스를 어떻게 구성했는지 재현하고 변경 범위를 판단하는 근거가 됩니다.

모델 후보를 읽는 순서

첫째, 문서와 질문의 언어가 지원 범위에 있는지 봅니다. 둘째, 최대 입력 길이가 현재 청크의 토큰 길이를 수용하는지 확인합니다. 셋째, 문서와 질의에 서로 다른 접두사나 프롬프트가 필요한지 모델 카드를 읽습니다. 넷째, 차원과 실행 위치, 라이선스, API 단가를 기록합니다. 마지막으로 한국어 질의셋에서 검색 결과를 측정합니다. 앞의 네 조건은 실행 가능한 후보를 고르는 기준이고, 마지막 측정은 이 도메인에 맞는 후보를 판단하는 기준입니다.

OpenAI의 [PROTECTED_CODE]과 [PROTECTED_CODE]는 기본 차원이 각각 1,536과 3,072이며 [PROTECTED_CODE] 옵션으로 축소할 수 있습니다. 2026-09-08 확인 단가는 100만 토큰당 각각 미화 0.02달러와 0.13달러입니다. 이 값은 비용 예측에 쓰며 한국어 순위를 뜻하지 않습니다. 공급자가 제공하는 영문 또는 다국어 벤치 결과도 후보 선정 자료일 뿐, 우리 문서의 정답률이 아닙니다.

로컬 오픈 모델 후보로는 [PROTECTED_CODE]와 [PROTECTED_CODE]를 조사했습니다. 두 모델 카드 모두 다국어 지원과 1,024차원을 명시합니다. E5는 검색 입력에 [PROTECTED_CODE]와 [PROTECTED_CODE] 접두사를 요구하고 최대 길이가 512개의 토큰입니다. BGE-M3는 최대 8,192개의 토큰과 dense·sparse·multi-vector 기능을 설명하지만, 이 장의 비교 범위에서는 dense 벡터만 사용합니다. 이 두 모델도 최종 선택이 아니라 공개된 모델 카드와 고정 리비전을 가진 후속 비교 후보입니다.

영어 순위가 한국어 순위가 아닌 이유

MTEB는 모델·과제·언어별 평가를 모으는 평가 모음입니다. 종합 점수 한 줄에는 여러 언어와 분류·검색·군집화 같은 서로 다른 과제가 섞일 수 있습니다. 영어 검색 과제에서 높은 모델이 한국어 사내 규정의 조사·고유명사·표현 변형에서도 같은 순위를 유지한다는 보장은 없습니다. 리더보드를 사용할 때는 Korean retrieval 과제를 별도로 보고, 최종 결정은 이 과정의 한국어 질문과 정답 문서로 측정합니다.

7주의할 점과 실무 메모

최종 모델은 미정입니다. 이 절의 small·large API 후보와 두 오픈 모델은 비교 틀을 보여 줍니다. 한국어 검색 지표와 운영 조건을 확인하기 전에는 하나를 정본으로 선언하지 않습니다.

캐시에 원문을 저장하는 문제. 캐시 파일에 벡터만 저장해도 키 생성 과정에서 원문 해시를 사용합니다. 민감 문서라면 캐시 경로의 접근 권한과 보존 기간을 별도로 정합니다.

8정리와 다음 절

임베딩 후보는 언어·입력 길이·차원·접두사·리비전·비용을 확인한 뒤 한국어 검색 질의셋으로 측정합니다.

영어 또는 종합 벤치마크의 순위는 한국어 도메인 검색 순위를 보장하지 않습니다.

4핵심 개념

비유 — 여섯 칸의 실험 표

청킹 설정 세 개를 표의 행에, 임베딩 후보 두 개를 열에 놓으면 여섯 칸이 생깁니다. 각 칸은 같은 문서와 같은 질문을 사용합니다. 한 칸만 다른 문서를 사용하거나 질문 수가 달라지면 설정의 효과와 입력 차이를 구분할 수 없습니다. 실험 격자는 바꾼 조건과 고정한 조건을 눈에 보이게 만듭니다.

정의

말뭉치 사전 점검 (corpus preflight)

실험 전에 문서 개수, 중복, 파일 형식, 스캔 여부, 읽기 가능성을 검사하는 단계입니다. 필수 조건을 충족하지 못하면 상태를 로그에 남기고 결과 범위를 제한합니다.

문서에서 글자를 추출했다고 해서 검색에 필요한 정보가 모두 보존되는 것은 아닙니다. 표의 열 제목이 사라지면 숫자의 뜻을 알기 어렵고, 예외 조항이 다음 청크로 분리되면 본문 규정만 검색될 수 있습니다. 이 챕터에서는 원문의 내용과 출처를 함께 보존하는 문서 처리 과정을 만듭니다. Ch 9에서 연결한 로더·스플리터·임베딩의 입력과 출력을 하나씩 확인하고, 처리 방법을 바꾸었을 때 무엇이 달라지는지 기록합니다.

학습 범위는 강의 8시간과 실습 16시간입니다. 각 절은 강의 1시간과 실습 2시간으로 구성하며, 설명·실행 예제·실패 사례·복습 문제·강사 노트를 함께 제공합니다. 문서를 처리하는 순서는 파이썬 함수와 조건문으로 정합니다. 검색 품질 지표는 Ch 11에서 계산하고, 최적 설정은 Ch 12에서 선택합니다.

학습 목표

문서 형식에 맞는 로더를 선택하고, 텍스트·표·쪽 번호가 보존되었는지 원문과 대조할 수 있습니다.

문자·재귀·토큰·구조·시맨틱 청킹의 경계 기준과 한계를 설명할 수 있습니다.

임베딩의 한국어 적합성을 확인할 항목을 정하고, 모델·입력·설정이 다른 캐시를 분리할 수 있습니다.

같은 문서에 청킹 3가지와 임베딩 2가지를 적용한 실험 기록을 Ch 11의 평가 입력으로 준비할 수 있습니다.

준비 자료와 학습 순서

선수 교재는 Ch 9 RAG 첫 완주와 실험 하네스입니다. 실습 코드는 [PROTECTED_CODE], 실행 방법과 환경 고정 파일은 같은 폴더의 [PROTECTED_CODE]·[PROTECTED_CODE]·[PROTECTED_CODE]에 있습니다. 문서 세트는 [PROTECTED_CODE]를 사용합니다.

현재 제공된 합성 문서는 텍스트 PDF 18건과 스캔 PDF 3건입니다. 스캔 문서는 추출 실패를 확인하는 실습에 사용합니다. 커리큘럼의 도메인 문서 100건 실습은 별도 문서 수집 후 수행하는 확장 과제입니다. 동일 문서를 복사하여 100건으로 세지 않습니다. 임베딩 최종 선정은 [[미정: 임베딩 모델]]로 남겨 두며, 예제에서 사용하는 모델과 선정 기준을 구분합니다.

다음 학습과 이어지는 지점

이 챕터의 처리 결과에는 문서 ID와 청크 ID가 함께 남습니다. Ch 11에서는 이 식별자를 정답 문서 ID와 비교하여 검색 지표를 계산합니다. Ch 12에서는 그 지표를 근거로 청킹·검색·리랭킹 설정을 변경합니다. 처리 시간과 청크 수만으로 검색 품질이 좋아졌다고 결론 내리지 않습니다.

확인 필요 항목

도메인 문서 100건 확보와 최종 임베딩 모델 선정은 남아 있습니다. HWP 변환, 실제 업무 HWPX 문서 검증, OCR 및 상용 파서 실행 범위는 각 절의 실행 결과와 주의할 점에 표시합니다. 실습용 파일에서 확인한 성공 사례를 모든 업무 문서에 일반화하지 않습니다.

이번 집필 환경에는 [PROTECTED_CODE]가 없어 실제 OpenAI 임베딩 호출은 실행하지 않았습니다. 3×2 실험의 저장 출력은 교육용 특징 벡터로 청킹·캐시·검색 로그의 동작을 검증한 결과입니다. 두 실제 모델의 성능 비교 결과로 사용하지 않습니다. 실제 API 실행 방법과 필요한 키는 실습 README에 안내합니다.
