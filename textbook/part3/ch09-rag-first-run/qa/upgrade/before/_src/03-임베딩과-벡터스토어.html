1학습 목표

  • 이 절을 마치면 ID가 있는 Document 세 건을 만들고 실제 OpenAI 임베딩으로 InMemoryVectorStore에 저장할 수 있습니다.
  • 이 절을 마치면 similarity_search_with_score()가 문서와 점수를 한 쌍으로 묶어 반환한다는 것을 알고, 두 값을 반복문으로 나누어 읽을 수 있습니다.
  • 이 절을 마치면 질문·문서·모델은 유지하고 k만 1에서 2로 바꾸어 검색 결과를 비교할 수 있습니다.

2이 내용을 배우는 이유

02절에서 청크를 만들었습니다. 이제 "질문의 답과 관련 있는 청크"를 골라야 합니다. 단어가 겹치는지로 고를 수도 있지만(Ch 12의 BM25), 이 절은 의미가 가까운지로 고릅니다. 기본 노트북은 원리와 반환값을 분명히 보려고 D01, D02, D03이라는 ID를 붙인 문서 세 건에서 검색합니다.

이 절은 벡터스토어의 similarity_search_with_score()를 직접 호출하고 반환값을 해석하는 능력을 익힙니다. 반환된 Document의 ID·본문과 점수를 함께 읽으면 어떤 문서가 먼저 선택되었는지 확인할 수 있습니다. Ch 12에서는 같은 중간값을 보며 검색 방법을 비교합니다.

4핵심 개념

비유 — 지도 위의 핀

기본 노트북의 문서 세 건을 지도 위 핀 세 개라고 생각하세요. 비슷한 내용은 가까운 자리에 놓입니다. 질문이 들어오면 질문도 같은 지도에 핀 하나로 표시하고, 그 핀에서 가장 가까운 핀 k개를 고릅니다. 이것이 top-k 검색의 전부입니다. 지도의 좌표가 벡터이고, 지도가 벡터스토어이며, "가깝다"의 잣대가 코사인 유사도입니다.

정의

임베딩 (embedding)
텍스트를 고정 길이의 숫자 벡터로 바꾸는 것, 또는 그 벡터입니다. 이 절의 모델 text-embedding-3-small은 입력 한도 안의 텍스트를 소수를 포함할 수 있는 숫자 1,536개로 이루어진 벡터로 바꿉니다. dimensions를 지정하면 벡터 길이를 줄일 수 있습니다. 의미가 비슷한 텍스트는 비슷한 벡터가 됩니다.
코사인 유사도 (cosine similarity, 벡터 방향의 가까움을 나타내는 값)
두 벡터가 이루는 각도로 가까운 정도를 측정하는 값입니다. 1이면 같은 방향이고 0이면 두 벡터가 서로 90도를 이룹니다. 0이나 음수라는 값만으로 문장 의미가 무관하거나 반대라고 단정할 수는 없습니다. InMemoryVectorStore의 점수가 이것입니다.
벡터스토어 (vector store)
청크 텍스트·벡터·메타데이터를 함께 저장하고, 질문 벡터와 가까운 것을 찾아 주는 저장소입니다. 기본 노트북의 InMemoryVectorStore는 문서 세 건을 메모리에 둡니다. 문서가 많아졌을 때 사용하며 프로그램을 종료해도 데이터가 남는 저장소와 빠른 검색 구조는 Ch 12에서 다룹니다.
top-k
점수 상위 k개만 반환하는 것입니다. k는 학생이 정하는 값입니다. 이 절은 k=1과 k=2의 반환 개수를 비교하고, 04절은 k=1 Document를 프롬프트에 넣습니다.
질문 임베딩 (query embedding)
질문 문장을 청크와 같은 모델로 벡터화한 것입니다. 같은 모델이어야 같은 지도에 놓입니다. 청크는 A 모델, 질문은 B 모델로 임베딩하면 점수가 무의미해집니다.
저장 ID
add_documents()가 반환하는 각 벡터의 식별자입니다. 기본 노트북은 반환된 ID 리스트의 길이가 입력 Document 수와 같은지 확인합니다.

도식 — 질문 핀과 가까운 청크 핀

노트북에서 확인할 색인과 검색

세 줄이 핵심입니다. OpenAIEmbeddings가 텍스트를 벡터로 바꾸는 담당, InMemoryVectorStore가 벡터를 담는 담당, add_documents()가 청크 목록을 받아 하나씩 임베딩해 넣는 동작입니다. 기본 비교에서는 similarity_search_with_score()를 호출합니다. 이 메서드는 (Document, 점수) 튜플의 리스트를 반환하므로 문서 내용과 순서를 함께 관찰할 수 있습니다. 실패 수정 셀에서는 두 문서의 정보를 함께 묻는 질문에서 k만 1에서 2로 바꾸고 검색된 Document ID를 비교합니다.

직접 호출하는 이유이 절에서는 벡터스토어 메서드를 셀에서 직접 호출합니다. hits_k1과 hits_k2를 바로 출력하면 k 변경 전후의 Document·점수·개수를 한 단계씩 확인할 수 있습니다.

벡터스토어 호출을 단계별로 읽기

OpenAIEmbeddings(model=...)는 임베딩 설정을 가진 객체를 만들 뿐, 이 줄에서 문서 벡터를 요청하지는 않습니다. 실제 호출은 add_documents(documents)가 문서 목록을 받아 각 본문을 임베딩할 때 일어납니다. 반환된 벡터 ID 목록은 저장 성공을 확인하는 값이고, store에는 원문 Document와 검색용 벡터가 연결되어 있습니다.

similarity_search_with_score(question, k=2)는 질문을 같은 모델로 임베딩하고 가까운 문서 두 건을 (Document, 코사인 유사도) 쌍으로 반환합니다. 이 절의 InMemoryVectorStore 점수는 클수록 질문과 더 가깝습니다. 유사도는 관련성 확률이 아니므로 0.8을 “80% 관련”으로 읽으면 안 됩니다. 제품 코드명처럼 정확한 철자가 핵심인 질문은 의미 벡터만으로 부족할 수 있으며 Ch 12의 키워드 검색과 비교합니다.

7주의할 점과 실무 메모

  • 점수에 절대 기준은 없습니다. 0.65가 좋고 0.35가 나쁘다고 말할 수 없습니다. 모델·언어·질문 길이에 따라 점수가 퍼지는 범위와 모양이 다릅니다. "이 점수보다 낮으면 버린다"고 정하는 기준값은 Ch 11의 테스트 질문 모음으로 측정한 뒤 정합니다. Ch 14에서는 점수가 기준보다 낮을 때 다른 검색 방법을 시도합니다. 이런 대체 동작을 폴백이라고 부릅니다.
  • 한국어 임베딩 품질. 영어 벤치마크 상위 모델이 한국어 조사·어미 변화에도 같은 성능을 낸다고 단정할 수 없습니다. 이 챕터의 모델은 [[미정: 임베딩 모델]]이 확정될 때까지의 임시값입니다. Ch 10에서 다른 임베딩 모델과 결과를 비교합니다.
  • 짧은 문서도 검색 후보입니다. 기본 노트북의 세 문서는 길이가 비슷하지만 실제 PDF에는 표지와 목차처럼 짧은 문서도 있습니다. 실무에서는 로더 단계에서 제외하거나 최소 청크 길이를 정한 뒤 결과를 비교합니다.
  • InMemoryVectorStore의 한계. 기본 노트북처럼 문서 세 건을 관찰하기에는 충분하지만, 프로세스가 종료되면 메모리의 값도 사라집니다. 문서가 많아졌을 때 사용할, 프로그램을 종료해도 데이터가 남는 저장소와 빠른 검색 구조는 Ch 12에서 다룹니다.
  • 비용과 재임베딩. 청크 크기나 임베딩 모델을 바꾸면 문서 벡터를 다시 만들어야 합니다. 기본 노트북은 짧은 문서 세 건만 실제 임베딩합니다. Ch 10에서 설정 변경과 재임베딩의 관계를 더 살펴봅니다.

8정리와 다음 절

  • Document 세 건을 실제로 임베딩해 메모리 벡터스토어에 저장했습니다.
  • k=1 검색의 Document·점수·본문을 분리해 읽었습니다.
  • k만 2로 바꾸어 추가 후보가 반환되는 것을 확인했습니다.

다음 학습과 이어지는 지점 — 04절에서 검색한 Document의 본문과 문서 ID 같은 출처 정보(metadata)를 프롬프트에 넣습니다.

9복습 문제

문제 4개 · 해설 포함

1. add_documents()가 입력받고 반환하는 것은 무엇입니까?

Document 리스트를 입력받아 임베딩해 저장하고, 저장된 벡터 ID 리스트를 반환합니다.

2. similarity_search_with_score()의 결과 하나는 어떤 형태입니까?

Document와 점수를 묶은 튜플입니다. 반복문에서 for document, score in ...로 두 값을 나눌 수 있습니다.

3. k=1에서 k=2로 바꾸면 무엇이 달라지고 무엇이 그대로입니까?

반환할 상위 문서 개수만 달라지고 질문, Document, 임베딩 모델, store는 그대로입니다.

4. 두 문서의 정보가 필요한 질문에서 k=1이 부족한 이유는 무엇입니까?

검색 결과를 한 건만 반환하므로 D01과 D03 가운데 하나가 빠집니다. 이 실습에서는 k를 2로 늘려 두 근거를 함께 검색했습니다.
