2이 내용을 배우는 이유

앞 절에서는 설정을 바꾸고 결과를 화면으로 확인했습니다. 실험이 늘어나면 어떤 설정에서 얻은 결과인지 함께 남겨야 다시 비교할 수 있습니다. 이번 절은 설정을 모으고 검색을 실행한 뒤 기록 한 행을 저장하는 과정을 배웁니다.

설정 변경, 실행, 기록을 같은 순서로 반복하도록 연결한 흐름을 실험 하네스라고 부릅니다. 이번 노트북은 YAML 읽기부터 검색·생성·JSONL 기록까지 한 단계씩 확인하고, 마지막에 같은 흐름을 새 커널에서 실행하는 명령을 만듭니다. Ch 11은 이 파일의 retrieved를 읽어 원본을 덮어쓰지 않는 별도 평가 로그에 검색 지표를 계산합니다.

3앞에서 배운 내용

  • YAML과 딕셔너리 — YAML 파일에 적은 설정을 yaml.safe_load()로 읽으면 중첩 딕셔너리가 됩니다.
  • 문서 분할과 벡터스토어 — 설정에 따라 Document를 나누고 InMemoryVectorStore에 저장합니다.
  • 파일 읽기와 쓰기 — 검색 결과를 JSON 한 행으로 저장한 뒤 다시 읽어 같은 기록인지 확인합니다.
  • assert 문(단언문) — 조건이 거짓이면 실행을 멈추고 AssertionError 예외가 발생합니다. 이번에는 청크 설정이 바뀌었는데 이전 색인을 다시 썼다는 잘못을 조건으로 찾아냅니다.

4핵심 개념

비유 — 실험 노트

화학 실험에서 시약의 양을 바꾸면 조건과 관찰 결과를 함께 적습니다. 검색 실험에서도 설정과 결과를 같은 기록에 남겨야 이전 실행과 비교할 수 있습니다. 이번에는 딕셔너리의 값을 바꾸고 셀을 실행한 뒤 JSONL 파일에 기록 한 행을 저장합니다.

정의

실험 하네스 (experiment harness)
설정을 바꾸고 검색과 생성을 실행한 뒤 결과를 같은 형식으로 기록하게 만든 반복 실험 틀입니다. 기본 노트북은 YAML 읽기, 조건 변경, 설정 식별 문자열 만들기, 검색, 생성, JSONL 한 행 기록을 차례대로 보여 줍니다.
YAML 설정 (YAML configuration)
들여쓰기로 계층을 나타내는 설정 파일입니다. 이 절에서는 분할·임베딩·검색·생성 설정과 질문을 한 파일에 둡니다. yaml.safe_load()로 읽은 뒤 환경 변수의 검색 개수만 실행 설정에 반영합니다.
실행 기록 (run record)
한 설정에서 실행한 결과를 담은 기록입니다. 이 절은 이름이 k2인 설정, 검색 문서 ID, 모델 답을 딕셔너리 한 개로 저장합니다.
설정 해시 (config hash) · 캐시 (cache)
설정 해시는 색인 설정마다 붙이는 짧은 식별 문자열입니다. 캐시는 이미 만든 결과를 잠시 보관하는 공간입니다. 캐시는 설정 해시를 이름표처럼 사용해 기존 벡터스토어 객체를 찾습니다. 이번 예제는 같은 문서를 사용하며 split과 embedding 설정을 해시 입력으로 삼습니다.
JSON Lines (JSONL)
한 줄에 JSON 객체 하나를 두는 파일 형식입니다. 줄을 덧붙일 수 있고, 각 줄을 독립적으로 읽을 수 있습니다. 잘못된 줄의 처리는 별도 오류 대응이 필요합니다. 기본 노트북은 실행 ID별 파일을 runs/continuity/에 보존하고, Ch 11이 읽을 최신 결과를 runs/continuity-ch09-search.jsonl에 기록합니다.

도식 — 루프

기본 실습의 실행 범위

임시 폴더에 YAML 설정을 만들고 다시 읽습니다. 검색 개수는 기본값 1에서 환경 변수의 값 2로 바꿉니다. 제공된 18개 디지털 PDF를 실제로 읽고 쪽별 Document를 청크로 나눈 뒤 Ch 11의 Q001과 같은 질문으로 검색합니다. 검색 본문과 문서 ID·쪽을 채팅 모델에 전달해 답을 생성합니다. 설정·검색·생성이 모두 끝나야 기록 한 행을 만듭니다.

설정 하나를 바꾸고 식별 문자열 만들기

기본 노트북은 yaml.safe_load()로 설정을 읽고 deepcopy()로 복사한 뒤 retrieval.k만 1에서 2로 바꿉니다. 이어서 색인에 영향을 주는 split과 embedding만 별도 딕셔너리에 담습니다.

json.dumps(..., sort_keys=True)는 키 순서를 고정한 JSON 문자열을 만들고, SHA-256은 이 문자열을 고정 길이의 해시로 바꿉니다. 해시는 설정에 붙이는 지문과 같습니다. 내용이 같으면 같은 해시가 나오고, 내용 하나가 바뀌면 다른 해시가 나옵니다. 노트북은 전체 해시를 출력하고 앞의 10자만 학습용 키로 사용합니다. 색인 설정을 구분하는 해시를 만들 때 retrieval.k는 뺍니다. k는 이미 만든 색인에서 문서를 몇 건 가져올지만 바꾸기 때문입니다. 따라서 k만 바꾼 설정은 같은 해시를 사용하고 기존 색인을 다시 씁니다.

기록 한 행

한 행에는 qid, question, gold_doc_ids, 전체 config, 순위가 있는 retrieved, answer가 들어갑니다. 검색 결과에는 doc_id·chunk_id·page·rank·score를 남깁니다. Ch 11은 이 중 질문과 정답 문서 ID, 검색 결과만 사용해 검색 지표를 계산하며 answer는 평가하지 않습니다.

설정·실행·기록의 역할 구분

실험 하네스는 설정을 읽고, 같은 절차를 실행하고, 결과를 같은 형식으로 저장하는 코드입니다. 이 노트북은 하나의 진입 함수를 호출하지 않고 셀을 순서대로 실행합니다. YAML을 읽고 문서를 분할·임베딩한 뒤 검색과 생성을 수행하며, 이어서 record 사전에 설정과 관찰값을 모아 JSONL 한 행으로 씁니다.

한 번에 조건 하나만 바꾸면 결과 차이를 그 조건과 연결해 해석할 수 있습니다. 모델과 청크 크기를 동시에 바꾸면 어느 변경이 원인이었는지 알 수 없습니다. JSONL은 실행 한 건을 한 줄에 추가하므로 이전 결과를 지우지 않고 실험 이력을 남기며, 로그 저장 성공이 검색 품질을 뜻하지는 않습니다.

5. 제공 PDF의 실제 임베딩 색인과 검색 실행

Ch 11이 평가하는 것과 같은 18개 디지털 PDF를 쪽별 Document로 만듭니다. 청크에 문서 ID·쪽·청크 ID를 남기고 Q001을 검색합니다.

In [6]:
from langchain_core.documents import Document
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter
from pypdf import PdfReader

pdf_paths = sorted(path for tier in ("easy", "medium", "hard") for path in (root / "labs/data/rag-corpus/pdf" / tier).glob("*.pdf"))
documents = []
for path in pdf_paths:
    for page, pdf_page in enumerate(PdfReader(path).pages, start=1):
        documents.append(Document(page_content=pdf_page.extract_text(), metadata={"doc_id": path.stem, "page": page, "source": path.name}))
splitter = RecursiveCharacterTextSplitter(**run_config["split"])
chunks = splitter.split_documents(documents)
for number, chunk in enumerate(chunks):
    chunk.metadata["chunk_id"] = f"ch09:{config_sha}:{number:04d}"
embedding = OpenAIEmbeddings(model=run_config["embedding"]["model"])
store = InMemoryVectorStore.from_documents(chunks, embedding)
hits = store.similarity_search_with_score(run_config["question"], k=run_config["retrieval"]["k"])
print("디지털 PDF:", len(pdf_paths), "쪽:", len(documents), "청크:", len(chunks))
print("검색 ID:", [hit.metadata["doc_id"] for hit, _ in hits])
print("첫 근거:", hits[0][0].page_content[:120])

6. 검색 근거로 답변 생성

검색한 본문과 출처 ID를 프롬프트에 넣고 실제 채팅 모델을 호출합니다.

from langchain.chat_models import init_chat_model

context = "\n".join(
    f"[{hit.metadata['doc_id']} p.{hit.metadata['page']}] {hit.page_content}" for hit, _ in hits
)
prompt = f"""다음 근거만 사용해 질문에 답하세요.
근거에 답이 없으면 '확인할 수 없습니다.'라고 답하세요.

근거:
{context}

질문: {run_config['question']}
답에 사용한 출처를 [문서ID p.쪽] 형식으로 표시하세요."""
model = init_chat_model(run_config["generation"]["model"])
response = model.invoke(prompt)
answer = response.text
print(answer)

7주의할 점과 실무 메모

  • 원문을 고정한 실험입니다. 학습용 색인 해시에는 split과 embedding만 들어갑니다. 연속성 로그의 config.inputs에는 18개 PDF 목록과 평가 질문셋의 SHA-256을 따로 남겨 입력 버전을 추적합니다. 실제 색인 캐시를 구현할 때는 이 입력 해시도 캐시 키에 포함해야 문서가 바뀐 뒤 이전 색인을 잘못 재사용하지 않습니다.
  • 키는 학습용으로 줄였습니다. 앞의 10자는 짧게 비교하기 위한 선택입니다. 큰 저장소를 설계할 때는 충분한 길이의 식별자와 실제 설정 대조가 필요합니다.
  • 검색과 생성 호출을 구분합니다. 문서 색인과 질문 검색은 임베딩 API를 호출하고, 답변 생성은 채팅 모델 API를 호출합니다. 이번 노트북은 호출 횟수나 비용을 측정하지 않습니다.
  • 실행별 기록과 최신 포인터를 구분합니다. runs/continuity/의 실행 ID별 파일은 덮어쓰지 않습니다. continuity-ch09-search.jsonl은 다음 챕터가 읽을 최신 실행을 가리키므로 재실행할 때 원자적으로 교체합니다. 기존 runs.jsonl과 과거 상세 로그는 변경하지 않습니다.
  • 동시에 쓰는 상황은 다루지 않습니다. 이번 실습은 한 커널에서 한 파일에 기록합니다. 여러 실행이 같은 파일에 동시에 쓰는 설계는 별도 처리가 필요합니다.

8정리와 다음 절

  • YAML 설정을 읽고 환경 변수로 k 하나만 2로 바꾸었습니다.
  • 제공된 18개 디지털 PDF와 Ch 11의 Q001을 사용해 실제 임베딩 검색과 채팅 모델 생성을 실행했습니다.
  • 질문 ID·정답 문서 ID·청크와 쪽 단위 검색 순위·생성 답을 JSONL에 저장하고, 배포 묶음에서도 실행할 수 있는 명령을 확인했습니다.

다음 학습과 이어지는 지점 — Ch 10은 청크 설정과 임베딩 모델을 바꾼 6개 검색 결과를 같은 필드로 기록합니다. Ch 11은 두 챕터의 최신 포인터를 읽어 질문·정답 문서 ID가 평가셋과 같은지 확인한 뒤 검색 지표만 계산합니다.

9복습 문제

문제 4개 · 해설 포함

1. YAML 설정을 읽은 뒤 deepcopy()를 사용해 k를 바꾼 이유는 무엇입니까?

중첩 딕셔너리의 안쪽 값까지 복사해 원본 설정을 보존한 채 실행 설정을 만들기 위해서입니다.

2. 색인 해시 입력에 retrieval.k를 넣지 않은 이유는 무엇입니까?

k는 기존 벡터스토어에서 몇 건을 반환할지만 바꾸며 문서 벡터 자체를 바꾸지 않기 때문입니다.

3. 생성 프롬프트에 검색 본문과 문서 ID를 함께 넣은 이유는 무엇입니까?

답의 근거를 실제 검색 결과로 제한하고, 생성된 답에 사용한 출처 ID를 표시하기 위해서입니다.

4. JSONL을 다시 읽었을 때 검색과 생성 결과를 보여 주는 두 필드는 무엇입니까?

retrieved에는 검색된 문서 ID가, answer에는 생성된 답이 들어 있습니다.
