1학습 목표

  • 이 절을 마치면 제공된 합성 PDF의 경로를 자동으로 찾고 쪽별 Document로 읽을 수 있습니다.
  • 이 절을 마치면 PDF 본문을 분할하고 실제 OpenAI 임베딩으로 색인한 뒤 질문과 관련된 청크를 검색할 수 있습니다.
  • 이 절을 마치면 검색 문맥과 출처를 삼중따옴표 프롬프트에 넣고 init_chat_model().invoke()로 답을 받을 수 있습니다.

2이 내용을 배우는 이유

Ch 8에서 모델이 참고할 내용인 컨텍스트를 다루는 네 가지 방법을 배웠습니다. 그중 Select는 "지금 필요한 것만 골라 넣는다"였고, 실습에서는 사람이 손으로 골랐습니다. 문서가 10쪽이면 손으로 고를 수 있습니다. 문서가 100건, 1,000쪽이 되면 손으로 고를 수 없습니다. 질문이 들어올 때마다 그 질문에 맞는 쪽을 자동으로 골라 프롬프트에 넣어야 합니다. 그 자동화 장치가 검색이고, 검색을 붙인 생성이 RAG입니다.

이 챕터에서는 제공된 PDF로 답을 생성하는 RAG를 완성합니다. Ch 10에서 문서 처리 방법을 비교하고, Ch 11에서 품질을 측정한 뒤 Ch 12에서 높입니다. 이 순서에는 이유가 있습니다. 동작하는 결과물이 있어야 "어디가 나쁜가"를 확인할 수 있고, 문제 지점을 알아야 Ch 11에서 무엇을 측정할지 정할 수 있으며, 측정할 수 있어야 Ch 12에서 5일 동안 튜닝할 수 있습니다. 완주가 먼저, 측정이 다음, 튜닝이 마지막입니다.

커리큘럼의 두 규칙을 여기서 다시 확인합니다. 첫째, 이 챕터에는 에이전트가 없습니다. 검색을 몇 번 할지, 몇 개를 가져올지, 답을 어떻게 만들지는 전부 학생이 코드에 적습니다. 모델은 마지막 한 단계, 문장을 만드는 일만 합니다. 둘째, 이 챕터는 측정 도구(Ch 11)보다 앞에 있으므로 "어느 설정이 더 좋은가"를 아직 판정하지 않습니다. 대신 설정과 결과를 같은 형식으로 남기는 반복 실험 틀을 06절에서 만듭니다. 이런 실행 틀을 실험 하네스라고 부릅니다.

4핵심 개념

비유 — 오픈북 시험

RAG는 오픈북 시험과 비슷합니다. 검색으로 고른 몇 쪽을 프롬프트에 넣고, 모델에 그 문서를 근거로 답하라고 요청합니다. 그러나 모델이 학습한 지식을 섞거나 문서에 없는 내용을 만들 수도 있습니다. 따라서 맞는 쪽을 검색했는지 먼저 보고, 답의 내용과 출처가 실제 문서와 일치하는지도 확인해야 합니다.

정의

RAG (Retrieval-Augmented Generation, 검색 증강 생성)
질문이 들어오면 먼저 문서 저장소에서 관련 조각을 검색하고, 그 조각을 프롬프트에 넣어 답을 생성하는 방식입니다. "증강"은 프롬프트에 검색 결과를 더한다는 뜻입니다.
색인 (indexing)
문서를 미리 잘게 나누고 벡터로 바꿔 저장해 두는 준비 작업입니다. 문서, 청크 설정, 임베딩 모델 중 하나가 바뀌면 다시 실행합니다.
청크 (chunk)
문서를 검색 단위로 자른 조각입니다. 청크 크기는 각 절의 설정에 따라 달라지며, 값을 바꾼 뒤 실제 길이와 본문을 확인합니다. 검색 결과는 쪽이 아니라 청크 단위로 반환됩니다.
벡터스토어 (vector store)
청크와 그 벡터를 함께 담아 두고, 질문 벡터와 가까운 것을 찾아 주는 저장소입니다. 이 챕터에서는 메모리에 두는 InMemoryVectorStore를 씁니다.
top-k 검색
질문과 가장 가까운 청크 k개를 가져오는 것입니다. k는 학생이 정합니다. 이 절의 기본 실행은 k=2이고, 이어서 k=1과 비교합니다.
출처 인용 (citation)
답의 근거로 사용한 문서와 쪽을 표기하는 형식입니다. 표기가 실제 근거와 일치하는지는 별도로 확인해야 합니다. 출처 표기는 RAG의 실용적인 장점 중 하나입니다.

도식 — 두 흐름

RAG에는 시점이 다른 두 흐름이 있습니다. 위쪽 색인은 문서·청크 설정·임베딩 모델이 바뀔 때 다시 실행되고, 아래쪽 질문 처리 과정은 질문이 들어올 때마다 실행됩니다. 두 흐름이 만나는 곳이 벡터스토어입니다. 색인 단계가 벡터스토어를 채우고, 질문 처리 단계가 관련 문서를 벡터스토어에서 꺼냅니다.

노트북은 각 상자의 입력과 반환값을 별도 셀에서 보여 줍니다. 다음 절부터 이 상자들을 왼쪽에서 오른쪽으로 하나씩 자세히 확인합니다.

상자노트북에서 실행할 동작입력 → 출력절
로더PdfReader로 쪽 반복PDF 경로 → 쪽 단위 Document 목록02
스플리터split_documents()쪽 → 청크 목록02

왜 셀을 단계별로 나눕니까?

처음에는 한 셀에서 한 단계의 결과를 확인합니다. PDF를 읽은 뒤 본문을 보고, 분할한 뒤 청크를 보고, 검색한 뒤 선택된 문서를 봅니다. 마지막 답이 예상과 다르면 이미 출력한 검색 결과부터 살펴볼 수 있습니다. 필요한 근거가 검색되었는지와 모델이 그 근거를 사용했는지를 차례로 확인하는 연습입니다.

각 셀은 앞에서 만든 변수와 LangChain의 메서드를 직접 사용합니다. 기본 실습에서는 별도 함수나 모듈을 먼저 만들 필요가 없습니다. 이후 Ch 13에서 흐름을 그래프로 표현할 때, 지금 확인한 각 단계의 입력과 출력을 바탕으로 노드의 역할을 정합니다.

첫 실행 코드를 읽는 순서

이 노트북은 색인과 질문 처리를 한 번에 실행하지만, 두 과정은 실행 시점이 다릅니다. PdfReader가 PDF를 쪽별 문자열로 읽고 Document(page_content=..., metadata=...)가 본문과 출처를 한 객체에 묶습니다. 이어서 스플리터가 여러 청크를 만들고, InMemoryVectorStore.from_documents(청크, 임베딩)가 청크를 벡터로 바꾸어 검색 가능한 저장소를 반환합니다. 여기까지는 문서가 바뀔 때 다시 수행하는 색인 단계입니다.

질문이 들어오면 similarity_search(질문, k=...)가 질문과 가까운 Document 목록을 반환합니다. 이 노트북은 점수를 요청하지 않으므로 검색 결과에는 거리나 유사도 값이 포함되지 않습니다. 검색 결과의 본문을 프롬프트에 넣은 뒤에야 model.invoke(프롬프트)가 실행되고, 반환된 AIMessage의 text를 화면에 출력합니다. 같은 PDF라도 질문이 바뀌면 질문 처리만 다시 실행할 수 있고, PDF 본문이나 임베딩 모델이 바뀌면 색인부터 다시 만들어야 합니다.

실습 안내

프로젝트에 제공된 E01.pdf는 수업을 위해 내용을 지어 만든 문서입니다. 파일을 복사할 필요는 없습니다. 코드가 현재 폴더에서 시작해 부모 폴더를 하나씩 확인하고 원본 위치를 찾습니다.

첫 실행 코드를 읽는 순서

PdfReader와 Document, 스플리터, 벡터스토어는 문서가 바뀔 때 실행하는 색인 단계입니다. 질문이 들어오면 similarity_search()가 가까운 Document 목록을 반환합니다. 이 호출은 점수를 요청하지 않으므로 거리나 유사도 값은 반환하지 않습니다. 그 본문을 프롬프트에 넣은 뒤 model.invoke()를 호출할 때 생성이 실행됩니다.

같은 PDF에서 질문만 바뀌면 질문 처리를 다시 실행할 수 있지만, PDF 본문이나 임베딩 모델이 바뀌면 색인부터 다시 만들어야 합니다. 마지막 답이 이상하면 검색된 청크와 모델 답을 따로 확인합니다.

2. PDF에서 쪽별 텍스트 읽기

PdfReader가 PDF를 읽으면 pages에 쪽별 데이터가 들어갑니다. 각 쪽을 Document로 바꿉니다. Document는 본문과 출처 정보를 한 묶음으로 담는 LangChain 객체입니다.

In [3]:
# extract_text()는 한 쪽의 텍스트를 문자열로 반환합니다.
# enumerate(..., start=1)로 사람이 읽는 쪽 번호를 metadata에 저장합니다.
from pypdf import PdfReader
from langchain_core.documents import Document

reader = PdfReader(pdf_path)
pages = []
for page_number, page in enumerate(reader.pages, start=1):
    page_text = page.extract_text()
    document = Document(
        page_content=page_text,
        metadata={"doc_id": "E01", "page": page_number, "source": pdf_path.name},
    )
    pages.append(document)
print("Document 수:", len(pages), "타입:", type(pages[0]).__name__)
print(pages[1].page_content[:180])

3. 쪽을 검색 단위로 나누기

RecursiveCharacterTextSplitter는 쪽 본문을 검색하기 좋은 작은 조각인 청크로 나눕니다. 문서 ID와 쪽 번호 같은 출처 정보(metadata)도 각 청크에 복사합니다. API 비용을 낮추기 위해 질문과 관련된 2~3쪽만 숫자 벡터로 바꿉니다.

In [4]:
# chunk_size는 청크 최대 길이, chunk_overlap은 이웃 청크의 공유 길이입니다.
# split_documents()는 Document 리스트를 받고 더 작은 Document 리스트를 반환합니다.
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
practice_pages = pages[1:3]
chunks = splitter.split_documents(practice_pages)
for chunk_number, chunk in enumerate(chunks):
    chunk.metadata["chunk_id"] = chunk_number
print("청크 수:", len(chunks), "첫 길이:", len(chunks[0].page_content))
print("첫 metadata:", chunks[0].metadata)
출력:
청크 수: 4 첫 길이: 498
첫 metadata: {'doc_id': 'E01', 'page': 2, 'source': 'E01.pdf', 'chunk_id': 0}

7. k만 1로 바꾸어 비교

질문·임베딩·문서는 그대로 두고 검색 개수만 2에서 1로 줄입니다. 생성 전에 출처 후보가 어떻게 달라지는지 확인합니다.

In [8]:
# hits_k1은 같은 question에서 k만 1로 바꾼 Document 리스트입니다.
# 두 반복문으로 k=2와 k=1의 출처 태그를 모아 나란히 출력합니다.
ids_k2 = []
for hit in hits:
    ids_k2.append(f"{hit.metadata['doc_id']} p.{hit.metadata['page']}")
hits_k1 = store.similarity_search(question, k=1)
ids_k1 = []
for hit in hits_k1:
    ids_k1.append(f"{hit.metadata['doc_id']} p.{hit.metadata['page']}")
print("k=2:", ids_k2)
print("k=1:", ids_k1)
assert len(hits_k1) == 1

9. LangChain으로 답변 생성하기

삼중따옴표 문자열은 여러 줄 프롬프트를 코드 모양 그대로 적을 때 사용합니다. 문서만 근거로 사용하고 출처를 붙이라고 명시합니다.

In [10]:
# f 삼중 문자열은 context와 question 변수를 여러 줄 템플릿에 삽입합니다.
# invoke()는 AIMessage를 반환하고 .text는 생성된 답변 문자열입니다.
from langchain.chat_models import init_chat_model

prompt = f"""다음 문서만 근거로 질문에 답하세요.
답 끝에 [문서ID p.쪽] 형식의 출처를 붙이세요.

[문서]
{context}

[질문]
{question}
"""
model = init_chat_model(
    "openai:gpt-5.4-mini",
    temperature=0,
    reasoning_effort="none",
    max_tokens=300,
)
answer = model.invoke(prompt)
print(answer.text)
출력:
미르시립도서관의 정기 휴관일은 **매주 월요일**입니다. [E01 p.2]

10. 첫 RAG 완주 확인

출력 문자열에 PDF의 휴관일과 출처 형식이 함께 있는지 검사합니다.

In [11]:
# in은 특정 문자열이 answer.text 안에 포함되었는지 검사합니다.
# 답과 출처를 따로 검사해 어느 조건이 깨졌는지 바로 알 수 있습니다.
assert "월요일" in answer.text
assert "[E01 p." in answer.text
print("검증 통과: PDF → 분할 → 임베딩 → 검색 → 생성을 완주했습니다.")
출력:
검증 통과: PDF → 분할 → 임베딩 → 검색 → 생성을 완주했습니다.

정리

수업용 PDF를 쪽별 Document로 읽고 작은 청크로 나눴습니다. 청크를 벡터스토어에 저장하고 검색한 문맥을 모델에 전달해 출처가 있는 답을 만들었습니다.

확인할 점 — PDF 경로, Document 수와 타입, 청크 수와 출처 정보(metadata), k=2와 k=1의 출처, 모델에 보낸 문맥이 셀별로 출력됩니다. 마지막 답에 PDF의 휴관일과 [E01 p.쪽] 출처가 함께 들어가는지 확인합니다.

6일부러 실패해 보기

Before에서 검색 문맥 없이 PDF의 휴관일을 물어 출처 검사가 실패합니다. After에서 실제 PDF 검색 문맥을 넣은 같은 질문으로 답과 근거를 함께 확인합니다.

앞의 실행 예제를 실행한 같은 노트북에서 Before 다음 After 순서로 실행합니다. 출력은 실제 실행 결과입니다.

Before — 실패 코드

원인 — 질문만 모델에 전달하면 제공 PDF의 본문과 출처를 사용할 수 없습니다.

In [12]:
# before_prompt는 정상 프롬프트와 지시·질문·출처 형식이 같고 문서 내용만 비어 있습니다.
# 출처가 있어야 한다는 assert는 실패하고 except가 그 사실을 출력합니다.
empty_context = ""
before_prompt = f"""다음 문서만 근거로 질문에 답하세요.
답 끝에 [문서ID p.쪽] 형식의 출처를 붙이세요.

[문서]
{empty_context}

[질문]
{question}
"""
plain_answer = model.invoke(before_prompt)
print(plain_answer.text)
try:
    assert "[E01 p." in plain_answer.text
except AssertionError:
    print("예상한 실패: PDF 문맥이 전달되지 않았습니다.")
출력:
제공된 문서에는 미르시립도서관의 정기 휴관일 정보가 없습니다. 따라서 문서만으로는 확인할 수 없습니다.
예상한 실패: PDF 문맥이 전달되지 않았습니다.

After — 수정 코드

수정 — 검색한 PDF 문맥과 출처 형식을 프롬프트에 넣어 같은 질문을 다시 실행합니다.

In [13]:
# fixed_answer는 앞에서 만든 prompt, 즉 PDF 검색 문맥이 포함된 입력의 응답입니다.
# 동일한 휴관일 질문에 답과 E01 출처가 함께 있는지 확인합니다.
fixed_answer = model.invoke(prompt)
print(fixed_answer.text)
assert "월요일" in fixed_answer.text
assert "[E01 p." in fixed_answer.text
출력:
미르시립도서관의 정기 휴관일은 **매주 월요일**입니다. [E01 p.2]

7주의할 점과 실무 메모

  • "RAG를 붙이면 환각이 사라진다"는 말은 틀립니다. 검색된 문서에 답이 없으면 모델이 답하지 못하거나 근거 없는 내용을 생성할 수 있습니다. 05절에서는 검색 누락과 답변 불가에 따른 거부를 구분합니다.
  • 버전을 고정합니다. 이 챕터는 LangChain 1.4, langchain-openai 1.6, Python 3.12 기준입니다. 검색으로 찾은 예제 코드는 0.x 시절 것이 많고, 그 API는 langchain-classic으로 옮겨졌습니다. from langchain.chains import RetrievalQA 같은 줄이 보이면 옛 코드입니다.
  • PDF 로더 패키지 관련 참고. 공식 문서의 PyPDFLoader는 langchain-community에 있는데, 이 패키지는 2026년 현재 유지보수 종료(sunset)가 예고되어 있습니다. 그래서 02절은 pypdf를 직접 호출해 쪽별 텍스트를 읽고 Document에 담습니다. 결과 형식(Document)은 같습니다.
  • 한국어 문서는 글자 수와 토큰 수가 다릅니다. 문자 길이만으로 모델이 사용하는 토큰 수를 확정할 수 없습니다. 청크 크기를 정할 때 "토큰 기준인지 글자 기준인지"를 항상 확인합니다.
  • 비용. 기본 노트북은 선택한 PDF 두 쪽과 짧은 질문을 사용합니다. 임베딩 셀이나 생성 셀을 다시 실행하면 API 비용이 추가될 수 있습니다. 이 절의 출력은 실제 청구액을 측정한 기록이 아닙니다.

8정리와 다음 절

  • 제공된 합성 PDF를 쪽별 Document로 읽고, 질문과 관련된 두 쪽을 청크로 나누어 실제로 임베딩했습니다.
  • k=2와 k=1의 검색 출처를 먼저 비교한 뒤 청크 본문을 프롬프트에 넣었습니다.
  • init_chat_model().invoke()로 휴관일과 출처가 있는 답을 받았으며, 검색 문맥을 빼면 출처 검사가 실패했습니다.

다음 학습과 이어지는 지점 — 02절은 방금 완주한 흐름 중 PDF 읽기와 청크 분할을 더 천천히 살펴봅니다.

9복습 문제

문제 4개 · 해설 포함

1. 노트북이 E01.pdf를 다른 폴더로 복사하지 않고도 찾는 방법은 무엇입니까?

Path.cwd()부터 부모 폴더를 하나씩 확인하며 labs/data/rag-corpus가 있는 프로젝트 루트를 찾습니다. 그 루트에서 PDF의 상대 경로를 조합합니다.

2. PDF 5쪽 전체를 읽은 뒤 2~3쪽만 임베딩한 이유는 무엇입니까?

첫 실습의 입력 비용과 실행 시간을 줄이면서 휴관일 질문에 필요한 본문과 비교 후보를 모두 포함하기 위해서입니다.

3. k=2와 k=1을 비교할 때 바꾼 값과 유지한 값을 구분해 쓰세요.

검색 개수 k만 2에서 1로 바꾸었습니다. 질문, 임베딩 모델, 벡터스토어, 문서는 그대로 유지했습니다.

4. 검색 문맥 없이 모델을 호출한 Before와 PDF 문맥을 넣은 After의 차이는 무엇입니까?

Before는 PDF 본문과 실제 출처 태그를 받지 못했으므로 E01 출처를 확인할 수 없습니다. After는 검색한 문맥과 출처 태그를 프롬프트에 포함합니다.
