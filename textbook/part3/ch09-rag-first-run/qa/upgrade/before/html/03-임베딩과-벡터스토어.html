4핵심 개념

비유 — 지도 위의 핀

기본 노트북의 문서 세 건을 지도 위 핀 세 개라고 생각하세요. 비슷한 내용은 가까운 자리에 놓입니다. 질문이 들어오면 질문도 같은 지도에 핀 하나로 표시하고, 그 핀에서 가장 가까운 핀 k개를 고릅니다. 이것이 top-k 검색의 전부입니다. 지도의 좌표가 벡터이고, 지도가 벡터스토어이며, "가깝다"의 잣대가 코사인 유사도입니다.

정의

임베딩 (embedding)
텍스트를 고정 길이의 숫자 벡터로 바꾸는 것, 또는 그 벡터입니다. 이 절의 모델 text-embedding-3-small은 입력 한도 안의 텍스트를 소수를 포함할 수 있는 숫자 1,536개로 이루어진 벡터로 바꿉니다. dimensions를 지정하면 벡터 길이를 줄일 수 있습니다. 의미가 비슷한 텍스트는 비슷한 벡터가 됩니다.
코사인 유사도 (cosine similarity, 벡터 방향의 가까움을 나타내는 값)
두 벡터가 이루는 각도로 가까운 정도를 측정하는 값입니다. 1이면 같은 방향이고 0이면 두 벡터가 서로 90도를 이룹니다. 0이나 음수라는 값만으로 문장 의미가 무관하거나 반대라고 단정할 수는 없습니다. InMemoryVectorStore의 점수가 이것입니다.
벡터스토어 (vector store)
청크 텍스트·벡터·메타데이터를 함께 저장하고, 질문 벡터와 가까운 것을 찾아 주는 저장소입니다. 기본 노트북의 InMemoryVectorStore는 문서 세 건을 메모리에 둡니다. 문서가 많아졌을 때 사용하며 프로그램을 종료해도 데이터가 남는 저장소와 빠른 검색 구조는 Ch 12에서 다룹니다.
top-k
점수 상위 k개만 반환하는 것입니다. k는 학생이 정하는 값입니다. 이 절은 k=1과 k=2의 반환 개수를 비교하고, 04절은 k=1 Document를 프롬프트에 넣습니다.
질문 임베딩 (query embedding)
질문 문장을 청크와 같은 모델로 벡터화한 것입니다. 같은 모델이어야 같은 지도에 놓입니다. 청크는 A 모델, 질문은 B 모델로 임베딩하면 점수가 무의미해집니다.
저장 ID
add_documents()가 반환하는 각 벡터의 식별자입니다. 기본 노트북은 반환된 ID 리스트의 길이가 입력 Document 수와 같은지 확인합니다.

도식 — 질문 핀과 가까운 청크 핀

노트북에서 확인할 색인과 검색

세 줄이 핵심입니다. OpenAIEmbeddings가 텍스트를 벡터로 바꾸는 담당, InMemoryVectorStore가 벡터를 담는 담당, add_documents()가 청크 목록을 받아 하나씩 임베딩해 넣는 동작입니다. 기본 비교에서는 similarity_search_with_score()를 호출합니다. 이 메서드는 (Document, 점수) 튜플의 리스트를 반환하므로 문서 내용과 순서를 함께 관찰할 수 있습니다. 실패 수정 셀에서는 두 문서의 정보를 함께 묻는 질문에서 k만 1에서 2로 바꾸고 검색된 Document ID를 비교합니다.

직접 호출하는 이유이 절에서는 벡터스토어 메서드를 셀에서 직접 호출합니다. hits_k1과 hits_k2를 바로 출력하면 k 변경 전후의 Document·점수·개수를 한 단계씩 확인할 수 있습니다.

벡터스토어 호출을 단계별로 읽기

OpenAIEmbeddings(model=...)는 임베딩 설정을 가진 객체를 만들 뿐, 이 줄에서 문서 벡터를 요청하지는 않습니다. 실제 호출은 add_documents(documents)가 문서 목록을 받아 각 본문을 임베딩할 때 일어납니다. 반환된 벡터 ID 목록은 저장 성공을 확인하는 값이고, store에는 원문 Document와 검색용 벡터가 연결되어 있습니다.

similarity_search_with_score(question, k=2)는 질문을 같은 모델로 임베딩하고 가까운 문서 두 건을 (Document, 코사인 유사도) 쌍으로 반환합니다. 이 절의 InMemoryVectorStore 점수는 클수록 질문과 더 가깝습니다. 유사도는 관련성 확률이 아니므로 0.8을 “80% 관련”으로 읽으면 안 됩니다. 제품 코드명처럼 정확한 철자가 핵심인 질문은 의미 벡터만으로 부족할 수 있으며 Ch 12의 키워드 검색과 비교합니다.

벡터스토어 호출을 단계별로 읽기

OpenAIEmbeddings()는 설정 객체를 만들고, 실제 문서 임베딩은 add_documents()를 호출할 때 실행됩니다. similarity_search_with_score(question, k=2)는 질문을 같은 모델로 임베딩한 뒤 (Document, 코사인 유사도) 두 건을 반환합니다. 이 InMemoryVectorStore 점수는 클수록 질문과 더 가깝습니다.

유사도는 관련성 확률이 아니므로 0.8을 80% 관련으로 해석하지 않습니다. 정확한 제품 코드가 중요한 질문은 의미 벡터만으로 부족할 수 있으며 Ch 12에서 키워드 검색과 비교합니다.

2. 라벨이 있는 문서 준비

검색된 문서를 이름으로 구분할 수 있게 각 Document에 D01, D02, D03이라는 문서 ID(doc_id)를 넣습니다.

In [3]:
# raw_documents의 각 튜플은 (문서 ID, 본문) 두 값을 묶습니다.
# for로 튜플을 doc_id와 content로 나누어 Document를 하나씩 추가합니다.
from langchain_core.documents import Document

raw_documents = [
    ("D01", "미르시립도서관의 정기 휴관일은 매주 월요일입니다."),
    ("D02", "해솔식당의 점심 영업은 오전 11시에 시작합니다."),
    ("D03", "별빛회사의 급여일은 매월 25일입니다."),
]
documents = []
for doc_id, content in raw_documents:
    document = Document(page_content=content, metadata={"doc_id": doc_id})
    documents.append(document)
print("문서 수:", len(documents), "타입:", type(documents[0]).__name__)
for document in documents:
    print(document.metadata, document.page_content)
출력:
문서 수: 3 타입: Document
{'doc_id': 'D01'} 미르시립도서관의 정기 휴관일은 매주 월요일입니다.
{'doc_id': 'D02'} 해솔식당의 점심 영업은 오전 11시에 시작합니다.
{'doc_id': 'D03'} 별빛회사의 급여일은 매월 25일입니다.

3. 임베딩 모델과 벡터스토어 만들기

각 문서를 뜻을 나타내는 숫자 벡터로 바꾸고, 원문과 벡터를 현재 실행 메모리의 저장소에 함께 넣습니다.

In [4]:
# embedding은 문장을 숫자 벡터로 바꾸는 OpenAI 모델 객체입니다.
# add_documents()는 문서 벡터와 원본 Document를 store에 저장합니다.
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings

embedding = OpenAIEmbeddings(model="text-embedding-3-small")
store = InMemoryVectorStore(embedding=embedding)
stored_ids = store.add_documents(documents)
print("store 타입:", type(store).__name__)
print("저장된 벡터 ID 수:", len(stored_ids))
출력:
store 타입: InMemoryVectorStore
저장된 벡터 ID 수: 3

4. 기본값 k=1로 검색

검색 결과는 Document와 유사도 점수를 한 쌍으로 반환합니다. 두 값을 따로 출력해 어떤 문서가 먼저 선택되었는지 확인합니다.

In [5]:
# similarity_search_with_score()는 (Document, 점수) 튜플의 리스트를 반환합니다.
# k=1은 가장 관련 높은 결과 한 건만 요청합니다.
query = "도서관이 쉬는 요일은?"
hits_k1 = store.similarity_search_with_score(query, k=1)
print("반환 타입:", type(hits_k1).__name__, "개수:", len(hits_k1))
for document, score in hits_k1:
    print("doc_id:", document.metadata["doc_id"])
    print("score:", round(score, 3))
    print("content:", document.page_content)
출력:
반환 타입: list 개수: 1
doc_id: D01
score: 0.526
content: 미르시립도서관의 정기 휴관일은 매주 월요일입니다.

5. k만 2로 바꾸어 비교

질문·문서·임베딩 모델은 그대로 두고 반환 개수만 늘립니다.

In [6]:
# hits_k2는 같은 query에서 k만 2로 변경한 결과입니다.
# 반복문으로 두 결과의 ID와 점수를 모두 보여 줍니다.
hits_k2 = store.similarity_search_with_score(query, k=2)
print("k=1 개수:", len(hits_k1))
print("k=2 개수:", len(hits_k2))
for document, score in hits_k2:
    print(document.metadata["doc_id"], round(score, 3))
assert hits_k1[0][0].metadata["doc_id"] == "D01"
assert len(hits_k2) == 2
출력:
k=1 개수: 1
k=2 개수: 2
D01 0.526
D03 0.325

정리

뜻이 가까운 문서를 찾는 검색에서 D01이 첫 번째로 나왔습니다. k만 1에서 2로 늘리자 D01은 그대로 있고 문서 한 건이 더 보였습니다.

확인할 점 — add_documents()는 저장된 벡터 ID 리스트를 반환합니다. similarity_search_with_score()는 Document와 점수의 튜플 리스트를 반환하며, k를 1에서 2로 늘리면 결과 개수가 늘어납니다.

6일부러 실패해 보기

Before에서 도서관 휴관일과 회사 급여일을 함께 묻지만 k=1로는 근거 문서 두 건을 모두 가져오지 못하는 결과를 확인합니다. After에서 질문과 문서는 유지하고 k만 2로 늘려 D01과 D03이 함께 검색되는지 검사합니다.

앞의 실행 예제를 실행한 같은 노트북에서 Before 다음 After 순서로 실행합니다. 출력은 실제 실행 결과입니다.

Before — 실패 코드

원인 — 도서관 휴관일과 회사 급여일을 함께 묻지만 k=1은 문서 한 건만 반환하므로 두 답의 근거를 모두 가져올 수 없습니다.

In [7]:
# combined_query는 서로 다른 두 문서의 정보가 필요한 질문입니다.
# k=1에서 빠진 근거를 ID와 본문으로 직접 확인합니다.
combined_query = "도서관 휴관일과 회사 급여일은 언제인가요?"
before_hits = store.similarity_search(combined_query, k=1)
before_ids = [document.metadata["doc_id"] for document in before_hits]
print("Before ID:", before_ids)
for document in before_hits:
    print("Before 본문:", document.page_content)
try:
    assert {"D01", "D03"}.issubset(before_ids)
except AssertionError:
    print("예상한 실패: 질문에 필요한 문서 두 건을 모두 가져오지 못했습니다.")
else:
    raise AssertionError("k=1 검색 누락이 재현되어야 합니다.")
출력:
Before ID: ['D01']

7주의할 점과 실무 메모

  • 점수에 절대 기준은 없습니다. 0.65가 좋고 0.35가 나쁘다고 말할 수 없습니다. 모델·언어·질문 길이에 따라 점수가 퍼지는 범위와 모양이 다릅니다. "이 점수보다 낮으면 버린다"고 정하는 기준값은 Ch 11의 테스트 질문 모음으로 측정한 뒤 정합니다. Ch 14에서는 점수가 기준보다 낮을 때 다른 검색 방법을 시도합니다. 이런 대체 동작을 폴백이라고 부릅니다.
  • 한국어 임베딩 품질. 영어 벤치마크 상위 모델이 한국어 조사·어미 변화에도 같은 성능을 낸다고 단정할 수 없습니다. 이 챕터의 모델은 [[미정: 임베딩 모델]]이 확정될 때까지의 임시값입니다. Ch 10에서 다른 임베딩 모델과 결과를 비교합니다.
  • 짧은 문서도 검색 후보입니다. 기본 노트북의 세 문서는 길이가 비슷하지만 실제 PDF에는 표지와 목차처럼 짧은 문서도 있습니다. 실무에서는 로더 단계에서 제외하거나 최소 청크 길이를 정한 뒤 결과를 비교합니다.
  • InMemoryVectorStore의 한계. 기본 노트북처럼 문서 세 건을 관찰하기에는 충분하지만, 프로세스가 종료되면 메모리의 값도 사라집니다. 문서가 많아졌을 때 사용할, 프로그램을 종료해도 데이터가 남는 저장소와 빠른 검색 구조는 Ch 12에서 다룹니다.
  • 비용과 재임베딩. 청크 크기나 임베딩 모델을 바꾸면 문서 벡터를 다시 만들어야 합니다. 기본 노트북은 짧은 문서 세 건만 실제 임베딩합니다. Ch 10에서 설정 변경과 재임베딩의 관계를 더 살펴봅니다.

8정리와 다음 절

  • Document 세 건을 실제로 임베딩해 메모리 벡터스토어에 저장했습니다.
  • k=1 검색의 Document·점수·본문을 분리해 읽었습니다.
  • k만 2로 바꾸어 추가 후보가 반환되는 것을 확인했습니다.

다음 학습과 이어지는 지점 — 04절에서 검색한 Document의 본문과 문서 ID 같은 출처 정보(metadata)를 프롬프트에 넣습니다.

9복습 문제

문제 4개 · 해설 포함

1. add_documents()가 입력받고 반환하는 것은 무엇입니까?

Document 리스트를 입력받아 임베딩해 저장하고, 저장된 벡터 ID 리스트를 반환합니다.

2. similarity_search_with_score()의 결과 하나는 어떤 형태입니까?

Document와 점수를 묶은 튜플입니다. 반복문에서 for document, score in ...로 두 값을 나눌 수 있습니다.

3. k=1에서 k=2로 바꾸면 무엇이 달라지고 무엇이 그대로입니까?

반환할 상위 문서 개수만 달라지고 질문, Document, 임베딩 모델, store는 그대로입니다.

4. 두 문서의 정보가 필요한 질문에서 k=1이 부족한 이유는 무엇입니까?

검색 결과를 한 건만 반환하므로 D01과 D03 가운데 하나가 빠집니다. 이 실습에서는 k를 2로 늘려 두 근거를 함께 검색했습니다.
