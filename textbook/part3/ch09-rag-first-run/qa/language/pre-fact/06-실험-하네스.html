1학습 목표

  • 이 절을 마치면 설정을 YAML 한 곳에 모으고, --set a.b=값으로 값 하나만 바꿔 한 명령으로 실험을 실행할 수 있습니다.
  • 이 절을 마치면 runs/runs.jsonl의 한 줄이 무엇을 담고 무엇을 아직 담지 않는지(metrics: {}) 말할 수 있습니다.
  • 이 절을 마치면 설정 해시로 색인 캐시를 판단하는 이유를 설명하고, 같은 질의셋을 네 가지 설정으로 실행한 답을 나란히 놓고 "눈으로 비교하는 일이 왜 한계에 부딪히는지" 확인할 수 있습니다.

2왜 지금 이것인가

05절까지 여러분은 설정을 바꿀 때마다 스크립트를 고치고, 실행하고, 화면을 읽고, 결과를 기억에 의존해 두었습니다. 다섯 번까지는 됩니다. Ch 12는 5일 동안 "가설 → 설정 변경 → 평가 실행 → 표에 한 줄"을 30번 이상 반복합니다. 커리큘럼은 이 절의 이유를 한 문장으로 적어 두었습니다. "이게 없으면 Chapter 12에서 5일 동안 실험을 세 번밖에 못 돌립니다."(커리큘럼 원문)

하네스가 하는 일은 세 가지뿐입니다. 설정을 한 곳에 모은다. 실행한다. 한 줄 기록한다. 지표는 아직 없습니다. Ch 11이 지표를 만들면 하네스의 빈칸에 들어옵니다. 순서가 중요합니다. 지표 없이 튜닝하면 "느낌으로 좋아졌다"가 되고, 하네스 없이 지표만 있으면 실험을 실행할 때마다 손으로 표를 채우게 됩니다.

4핵심 개념

비유 — 실험 노트

설정을 바꿀 때마다 한 줄이 쌓이는 실험 노트가 없으면, 5일이 지나도 무엇을 해 봤는지 모릅니다. 화학 실험실에서 시약의 양을 바꿔 가며 반응을 볼 때, 연구자는 매번 노트에 한 줄을 씁니다. 날짜, 조건, 결과. 노트가 없으면 "어제 그 조건이 무엇이었더라"를 찾는 데 하루가 걸립니다. 하네스는 그 노트를 자동으로 쓰는 장치입니다. 설정 다이얼을 돌리고(YAML) 실행하면(한 명령) 노트에 한 줄이 생깁니다(JSONL).

정의

실험 하네스 (experiment harness)
설정을 입력받아 파이프라인을 실행하고 결과를 정해진 형식으로 기록하는 실행기입니다. 파이프라인 자체(rag.py)와 분리되어 있어, 파이프라인을 고쳐도 기록 형식은 그대로입니다.
설정 파일 (config.yaml)
바꿀 수 있는 값 전부를 모아 둔 한 파일입니다. 코드 안에 숫자를 적지 않고 이 파일에서 읽습니다. "설정을 바꾼다"는 이 파일을 고치거나 --set으로 덮어쓰는 것입니다.
실행 (run) · run_id
설정 하나로 질의셋을 한 번 돌리는 단위입니다. 시각과 이름을 붙인 run_id로 구분하고, 요약 한 줄과 상세 파일 하나가 남습니다.
설정 해시 (config hash) · 캐시
색인 결과를 좌우하는 설정(문서·청크·임베딩)만 골라 짧은 문자열로 만든 것입니다. 같은 해시면 색인을 다시 만들지 않고 저장된 것을 씁니다. k나 프롬프트를 바꾸는 실험은 색인이 같으므로 임베딩 비용이 0입니다.
JSON Lines (JSONL)
한 줄에 JSON 객체 하나를 두는 파일 형식입니다. 줄을 덧붙이기만 하면 되고, 한 줄이 깨져도 나머지는 읽힙니다. queries.jsonl과 runs.jsonl이 이 형식입니다.

6일부러 실패해 보기

실패 1 — 캐시를 속인다. .cache/index-*.json이 있는 상태에서 rag.py의 split_docs() 안 separators를 바꾸고 하네스를 실행하세요. 해시는 split 설정(chunk_size·chunk_overlap)만 보므로 바뀐 것을 모르고 옛 색인을 씁니다. 코드 변경은 해시에 잡히지 않습니다. 실무에서는 코드 버전(git 커밋 해시)을 해시에 함께 넣거나, 코드가 바뀌면 캐시를 지우는 규칙을 둡니다. Ch 33 CI에서 이 문제를 다시 만납니다.

실패 2 — 타입이 틀린 값을 넣는다. --set retrieval.k=four를 넣으면 similarity_search_with_score(k="four")에서 오류가 납니다. 그런데 오류는 색인을 만들고 질의셋을 읽은 뒤에 납니다. 설정을 읽은 직후에 타입을 검사하는 함수를 하나 두면(assert isinstance(cfg["retrieval"]["k"], int)) 몇 초를 아낍니다. Ch 2 B트랙에서 본 Pydantic으로 설정 스키마를 만드는 것이 정석이며, B트랙 과제입니다.

실패 3 — 이름을 바꾸지 않고 두 번 실행한다. --set name 없이 기준선을 두 번 실행하면 runs.jsonl에 name=baseline 두 줄이 생깁니다. run_id는 시각이 붙어 다르지만, 나중에 표를 만들 때 어느 줄이 어느 가설인지 알 수 없습니다. name은 가설의 이름입니다. "k8"이 아니라 "k8-표지제외전"처럼 실행 이유가 드러나게 짓는 습관을 Ch 12에서 30번 반복하게 됩니다.

7주의할 점과 실무 메모

  • 비용 추정의 정확도. 생성 토큰은 응답 메타데이터에서 정확히 오지만, 임베딩 토큰은 OpenAIEmbeddings가 알려 주지 않아 글자 수 ÷ 1.2로 어림했습니다(02절 실측 498자 = 431토큰). 이 챕터 규모에서는 오차가 0.001달러 미만입니다. 정확한 값이 필요하면 tiktoken으로 세어 넣으면 됩니다.
  • 요금은 바뀝니다. prices 칸의 값은 2026-09-07 확인값이며 확인 날짜를 주석에 적어 두었습니다. 요금표 URL을 함께 적어 두면 나중에 갱신할 때 어디를 볼지 압니다.
  • 지연 시간은 평균만으로 부족합니다. latency_mean_s만 기록했지만 Ch 15는 p50/p95/p99를 요구합니다. 상세 파일에 질문별 지연을 남겨 두면 나중에 계산할 수 있습니다 — 지금 하네스는 남기지 않으니 B트랙 과제입니다.
  • 동시 실행과 로그 경쟁. runs.jsonl에 덧붙이기("a" 모드)는 한 프로세스일 때 안전합니다. Ch 12에서 실험을 병렬로 실행하면 줄이 섞일 수 있습니다. 병렬 실행 시에는 실행마다 파일을 따로 쓰고 나중에 합칩니다.
  • .cache/와 runs/는 git에 넣지 않습니다. 색인 파일은 수 MB이고 실행 로그는 개인 실험 기록입니다. 프로젝트 .gitignore에 .cache/가 들어 있습니다. 다만 Ch 12의 실험 로그 30건은 중간 프로젝트 리포트의 근거이므로 Ch 12에서는 runs.jsonl만 따로 보관합니다.

8정리와 다음 절

  • 하네스는 설정(YAML) → 실행(한 명령) → 기록(JSONL 한 줄)입니다. 하네스는 rag.py의 파이프라인 함수를 직접 호출하고 결과를 기록합니다.
  • 설정 해시로 색인 캐시를 판단하므로 k·프롬프트 실험은 임베딩 비용이 0입니다. 코드 변경은 해시에 잡히지 않습니다.
  • 한 줄에는 설정·규모·비용이 있고 지표는 비어 있습니다. 네 설정의 답을 눈으로 비교해 보면 그 빈칸이 왜 필요한지 보입니다.

다음 학습과 이어지는 지점 — Ch 10 실습 "문서 100건 × 3 청킹 × 2 임베딩"은 이 하네스에 --set 6가지 조합을 적용하는 것입니다. Ch 11은 상세 파일의 gold_doc_id와 retrieved를 비교하는 Recall@k·Precision@k 함수를 만들어 metrics 칸에 넣습니다. Ch 12는 이 루프를 5일 동안 30번 이상 실행하고, 그 runs.jsonl이 중간 프로젝트 평가 리포트의 뼈대가 됩니다. Ch 15는 여기에 judge 점수와 p95 지연을 더합니다. 이 챕터는 여기서 마무리됩니다. 다음은 Ch 10 문서 처리입니다.

9복습 문제

문제 4개 · 해설 포함

1. --set retrieval.k=8로 실행했을 때 색인을 다시 만들지 않는 이유는 무엇입니까?

index_key()가 corpus·split·embedding만 해시하므로 retrieval.k가 바뀌어도 해시가 같고, 같은 해시의 .cache/index-{hash}.json이 있으면 그것을 불러옵니다.

2. 청크 1000과 k=8은 둘 다 "모델에게 더 많이 보여 준다"입니다. 비용 구조가 어떻게 다릅니까?

청크 1000은 색인을 다시 만들어야 하고(임베딩 비용·시간) 청크 하나가 길어져 입력 토큰이 1.6배가 됩니다. k=8은 색인은 그대로이고 입력 토큰만 약 1.8배가 되었습니다. 어느 쪽이 답을 더 잘 맞히는지는 지표가 있어야 알 수 있습니다.

3. Q008에서 기준선은 E02 2쪽을 가져왔는데도 "찾을 수 없습니다"였습니다. 쪽 단위 로그만 보면 생성 실패로 보입니다. 실제 원인은 무엇이고, 어떻게 알 수 있었습니까?

검색 실패입니다. 가져온 것은 2쪽의 첫 청크(#9, 환영 인사)였고 급여일이 있는 청크(#10)는 5위였습니다. 로그에 chunk_id를 함께 적어야 드러납니다. 기록 단위는 검색 단위(청크)와 같아야 하고, 검색 지표(정답 청크가 k개 안에 있었나)와 생성 지표(답이 맞았나)를 나눠 기록해야 합니다.

4. runs.jsonl 한 줄에 아직 없는 것과, 그것을 채우는 챕터를 쓰세요.

품질 지표(metrics: {})와 지연의 분포(p95 등)입니다. 검색·생성 지표는 Ch 11, judge 점수와 p50/p95/p99는 Ch 15가 채웁니다.

시간 배분 · 시연 순서 · 예상 질문 · 막히는 지점 · A/B 트랙

시간 배분(2h) — 강의 60분: 실험 노트 비유(10) · 설정 파일 읽기(15) · 덮어쓰기·해시 코드(15) · 한 줄 기록과 네 실행 결과 표(20). 실습 60분: 네 설정 실행(15) · 상세 파일에서 갈린 문항 찾아 표 만들기(25) · 실패 1~3(20).

시연 순서 — ① config.yaml을 열어 01절 도식의 상자와 키를 짝지어 보여 줌 ② 기준선 실행, 한 줄 출력 ③ --set retrieval.k=8을 실행하며 색인을 다시 만들지 않는 점 확인(index_seconds 동일) ④ runs.jsonl을 cat으로 열어 네 줄 확인 ⑤ 상세 파일 두 개를 나란히 열어 Q003·Q008을 찾게 하고 "900칸이면?"이라고 묻기 ⑥ metrics: {}를 가리키며 Ch 11 예고.

예상 질문 — "지금 정답 문서 ID가 있으니 Recall을 바로 계산하면 안 되나요?" → 계산할 수 있으며 B트랙에서는 시도하되, 지표를 어떻게 나눠 측정할지(Recall@50 vs Precision@5)와 무엇을 맞다고 볼지가 Ch 11의 내용이므로 Ch 11에서 정식으로 다룬다고 답함. "YAML 대신 파이썬 딕셔너리로 하면요?" → 가능하지만 설정과 코드가 섞이면 "무엇을 바꿨나"가 diff에 드러나지 않는다고 답함. "MLflow 같은 도구를 쓰면요?" → 나중에 사용해도 되며, 그 도구의 역할을 이해하려고 30줄짜리 하네스를 먼저 만드는 것이 이 과정의 방식이라고 답함.

학생이 막히는 지점 — --set의 값에 공백이 있으면 셸이 나누는 문제(따옴표 안내). queries.file의 상대 경로가 실행 위치 기준이 아니라 harness.py 위치 기준이라는 점. 캐시를 지우지 않고 rag.py를 고친 뒤 결과가 바뀌지 않는 상황(실패 1로 연결).

A/B 트랙 — A트랙은 네 실행과 비교표까지. B트랙은 ① Pydantic 설정 스키마 ② 질문별 지연을 상세 파일에 남기고 p95 계산 ③ 상세 파일에서 gold_doc_id in retrieved 비율을 세는 함수(Ch 11 예행, 이름은 아직 Recall이라 부르지 않게 함).
