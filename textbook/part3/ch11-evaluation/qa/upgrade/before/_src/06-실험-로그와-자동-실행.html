1학습 목표

  • 설정·지표·날짜를 한 실행 기록으로 저장할 수 있습니다.
  • 지표 정책과 말뭉치 지문을 로그에 포함해야 하는 이유를 설명할 수 있습니다.
  • Ch 9·10의 검색 순위를 Ch 11 질의셋과 대조하고 JSON 평가 결과를 만들 수 있습니다.

2이 내용을 배우는 이유

숫자만 적으면 어떤 설정이 만든 결과인지 며칠 뒤에 알기 어렵습니다. Ch 12에서는 청킹, 검색, 재정렬 설정을 반복해서 바꿉니다. 실행 하나를 한 행으로 남겨야 좋아진 설정과 나빠진 설정을 같은 기준으로 비교할 수 있습니다.

3앞에서 배운 내용

Ch 9의 실험 하네스는 설정·검색 문서 ID·생성 답변을 한 기록에 남겼습니다. Ch 10은 청킹과 임베딩 조합별로 검색 청크와 점수를 확인했습니다. 이번 절은 두 챕터가 Ch 11 질의셋의 Q001에 대해 저장한 continuity 로그를 읽어 검색 지표를 계산합니다. 생성 답변은 이 계산에 사용하지 않으며 Ch 15에서 따로 평가합니다.

4핵심 개념

비유 — 실험실 시료 라벨

측정값이 같아도 시료와 장비 설정이 다르면 같은 실험이 아닙니다. 검색 로그도 숫자 옆에 데이터와 설정의 이름을 붙여야 재현할 수 있습니다.

실행 ID (run ID)
한 번의 평가 실행을 구분하는 이름입니다.
설정 스냅샷 (settings snapshot)
청킹·검색·후보 수처럼 결과에 영향을 주는 값을 한 시점에 기록한 자료입니다.
말뭉치 지문 (corpus fingerprint)
평가에 사용한 문서 집합이 같은지 확인하는 해시입니다.
지표 정책 버전 (metrics policy version)
중복 제거, 빈 정답 제외, 분모 처리 규칙의 버전입니다.
회귀 실행 (regression run)
변경 뒤 같은 평가를 다시 실행해 이전 결과가 유지되는지 확인하는 작업입니다.

최소 로그에는 run_id, run_date, settings, metrics_policy, 입력 파일 식별 정보, query_count, metrics, 조건별 slices, 질문별 results가 필요합니다. 질문별 결과에는 qid, gold_doc_ids, 지표 계산에 사용한 전체 candidate_doc_ids와 candidate_count, 보고서에 보존한 top_results와 returned_count, 검색 지표를 둡니다. top_results에는 문서·쪽·청크 ID와 순위, 점수가 있습니다. Ch 9처럼 후보를 2개만 저장했다면 Recall@5·50과 Precision@5·nDCG@5는 측정하지 않고, recall_at_logged_candidates만 남깁니다. Ch 10의 후보 5개로는 @5 지표를 계산할 수 있지만 Recall@50은 측정하지 않습니다.

질문 목록, 문서 집합, 검색기, 평가 단위, 후보 저장 개수 가운데 하나라도 다르면 지표를 직접 비교하지 않습니다. Q001 한 개로 연결을 확인한 Ch 9·10 결과도 dev 15개를 사용한 독립 기준선과 수치를 직접 비교하지 않습니다. 개발용 질문은 설정 선택에 사용하고, 시험용 질문은 선택을 마친 뒤 한 번 확인합니다.

로그 한 행이 완성되는 시점

노트북은 subprocess.run()으로 evaluate.py를 실행합니다. 저장은 evaluate.py가 평가 결과를 만든 뒤 Path.write_text(json.dumps(...))를 호출할 때 이루어집니다. 노트북은 저장된 파일을 read_text()와 json.loads()로 다시 읽습니다. 파일을 읽었다는 사실, 스키마 검사를 통과했다는 사실, 지표가 좋아졌다는 사실은 서로 다른 상태입니다.

corpus_fingerprint는 문서 집합이 같은지 확인하고 metrics_policy는 중복 제거와 빈 정답 처리 방식이 같은지 확인합니다. 둘 중 하나가 다르면 같은 지표 이름이라도 직접 전후 비교하기 어렵습니다. 자동 실행은 반복을 일정하게 만들지만, 낮은 질문별 결과의 원인을 원문에서 확인하는 판단까지 대신하지 않습니다.

5실행 예제

노트북은 Ch 9·10 continuity JSONL을 읽어 qid·질문·정답 문서 ID·순위 필드를 검사합니다. 그런 뒤 문서 ID 중복을 제거한 검색 지표를 계산하고 Ch 11의 새 결과 파일에 저장합니다. 원래 Ch 9·10 로그는 덮어쓰지 않습니다. evaluate.py의 기본 모드는 개발용 15개 질문과 단어·한글 두 글자 조각 겹침을 사용한 독립 기준선입니다. 전체 30개는 --split all을 명시할 때만 사용합니다. TF-IDF 기준선이 아닙니다.

{{notebook:06-실험-로그와-자동-실행}}
uv run python evaluate.py --top-k 5 --output runs/continuity-baseline.json

확인할 점 — Ch 9·10 실행별 질문 수와 검색 지표가 출력됩니다. Q001 하나의 결과는 연결 형식을 확인하는 용도이며 개발용 15개 기준선의 수치와 우열을 비교하는 근거가 아닙니다.

6실험 결과 해석

dev 15개 독립 기준 로그는 word+bigrams-overlap 검색 설정에서 Recall@50 1.000, Precision@5 0.200, nDCG@5 약 0.893을 기록합니다. Recall과 Precision은 검색 가능한 고유 문서가 17개이고 질문당 정답 문서가 하나인 조건에서 천장에 도달했습니다. Ch 9·10 continuity 결과는 Q001 하나만 사용하므로 수치 상승·하락을 판정하지 않고, 앞 챕터의 산출물을 Ch 11 지표로 읽을 수 있다는 것만 확인합니다.

자동 실행은 판단을 자동으로 대신하지 않습니다. 로그가 같은 스키마로 축적되면 어떤 설정이 달랐는지 찾기 쉬워집니다. 지표가 바뀌면 질문별 결과와 원문을 읽고 수정할 단계를 확인합니다.

7주의할 점과 실무 메모

  • 날짜만으로 실행을 식별하지 말고 고유한 실행 ID를 사용합니다.
  • Ch 11 독립 기준선은 TF-IDF가 아니라 단어와 한글 두 글자 조각의 겹침을 측정합니다. 검색기가 다른 두 실행의 수치는 설정 효과로 단정하지 않습니다.
  • API 모델을 쓰는 Ch 12 실험은 모델명, 버전, 차원, 예상 비용을 설정에 추가합니다. Ch 11 독립 기준선 비용은 0달러입니다.
  • 비밀 키와 전체 환경 변수는 로그에 쓰지 않습니다.
  • 원래 Ch 9·10 로그를 덮어쓰지 말고 Ch 11에 새 평가 파일을 추가합니다.

8정리와 다음 절

  • 실행 결과에는 설정·지표·날짜·정책·데이터 식별 정보를 함께 남깁니다.
  • 질문별 원자료를 보존해야 평균 변화의 원인을 읽을 수 있습니다.
  • 개발용 질문으로 설정을 고른 뒤 시험용 질문으로 한 번 확인합니다.

다음 학습과 이어지는 지점 — Ch 12에서는 질문 하나를 사용하는 청킹·MMR 관찰, 개발용 15문항의 설정 비교와 시험용 15문항의 최종 확인, 개발용 Q002 한 문항의 별도 통합 RAG 실행을 서로 다른 실험으로 기록합니다.

9복습 문제

문제 4개 · 해설과 보충 위치

1. [이해] 지표 정책 버전은 무엇을 기록합니까?

중복 제거, 빈 정답 제외, 분모 처리 규칙을 기록합니다. 4절을 확인합니다.

2. [이해] 말뭉치 지문이 다른 두 로그를 바로 비교할 수 없는 이유는 무엇입니까?

검색 설정뿐 아니라 문서 집합도 달라졌기 때문입니다.

3. [적용] 임베딩 모델만 비교하려면 어떤 설정을 유지해야 합니까?

질문, 말뭉치, 청킹, 후보 수, 지표 정책을 유지합니다. 4절 마지막 단락을 확인합니다.

4. [분석] 평균 지표만 저장한 로그에서 원인 분석이 어려운 이유는 무엇입니까?

어느 질문과 순위가 변했는지 알 수 없기 때문입니다. 질문별 결과 필드를 확인합니다.
