## Ch 11: 검색 지표의 고정 계약

### 먼저 고정할 평가 단위

질의 `q`마다 다음을 로그에 남긴다.

```json
{
  "query_id": "Q001",
  "gold_doc_ids": ["E05"],
  "retrieved": [
    {"rank": 1, "doc_id": "E05", "chunk_id": "E05-003"}
  ],
  "answerable": true
}
```

- `gold_doc_ids`는 **문서 ID 기준**이다. Ch 9·10이 물려준 `chunk_id`는 실패를 읽기 위한 보조 정보다. 같은 문서의 여러 청크가 상위 결과에 있어도 지표에서는 한 문서로 한 번만 세어야 합니다. 그렇지 않으면 청크를 더 잘게 자른 설정이 부당하게 유리해진다.
- 한 질문에 근거 문서가 여러 개면 모두 `gold_doc_ids`에 넣는다. Ch 11의 Recall@50은 다중 정답을 얼마나 포괄했는지, Precision@5와 nDCG@5는 앞 다섯 자리의 품질을 보여 준다.
- 시스템마다 문서/청크의 식별 규칙이 같아야 비교할 수 있다. 청킹을 바꾸는 실험이라도 `doc_id`는 바꾸지 않는다.

### 정의와 빈 결과 처리

`Gq`를 질의 q의 고유 정답 문서 집합, `Lq@k`를 반환 순서를 보존한 뒤 중복 `doc_id`를 제거한 상위 k개 문서로 둔다. `Hq@k = |Gq ∩ Lq@k|`이다. TREC은 precision을 “반환한 문서 가운데 관련 문서 비율”, recall을 “관련 문서 가운데 반환한 문서 비율”로 정의하며, 절단 깊이는 순위 상한이다. [TREC 2021 Overview](https://trec.nist.gov/pubs/trec30/papers/Overview-2021.pdf)

|지표|질의별 계산|빈 반환 목록 (`Lq=[]`), `Gq`가 비어 있지 않을 때|
|---|---|---|
|Recall@50|`Hq@50 / |Gq|`|0|
|Precision@5|`Hq@5 / 5`|0|
|nDCG@5|아래 정의|0|

- **Precision@5의 분모는 5로 고정**한다. 시스템이 2개만 반환해도 `2`로 나누지 않는다. `H/len(returned)`는 빈 목록 또는 너무 짧은 목록을 유리하게 만드는 다른 지표다. `returned_count`도 로그에 함께 남겨, API/필터 때문에 k개를 채우지 못한 경우를 보인다.
- 평균은 질의별 점수의 **macro mean**으로 낸다. 관련 문서가 많은 질문이 전체 평균을 지배하지 않게 하기 위함이다. TREC도 주제별로 동등한 가중치를 두는 방식을 설명한다. [TREC 2021 Overview](https://trec.nist.gov/pubs/trec30/papers/Overview-2021.pdf)
- `gold_doc_ids=[]`는 검색 지표에 넣지 않는다. 분모 또는 이상적 순위(IDCG)가 0이어서, “정답 문서가 없는 질문”과 “정답을 아직 붙이지 않은 질문”을 구별할 수 없기 때문이다. `answerable:false`와 별도 `expected_action:"refuse"` 같은 필드로 기록하고, **검색 recall/precision/nDCG 평균에서는 제외**하며 제외한 질문 수를 보고한다. 이 질문은 Ch 15의 거부·근거성 평가 대상이다.
- 같은 문서 ID의 중복과 정답 없는 질의를 어떤 방식으로 처리했는지 `metrics_policy`에 버전과 함께 기록한다. 정책을 중간에 바꾸면 이전 로그와 직접 비교하지 않는다.

### nDCG@5

순위 i의 등급 관련도를 `rel_i`(이 과정의 기본은 정답이면 1, 아니면 0)라고 하면:

```
DCG@5  = Σ(i=1..5) (2^rel_i - 1) / log2(i + 1)
nDCG@5 = DCG@5 / IDCG@5
```

`IDCG@5`는 같은 정답 등급들을 가장 좋은 순서로 정렬했을 때의 DCG@5이다. 이진 정답에서는 `2^rel_i - 1`이 `rel_i`와 같지만, 식을 그대로 쓰면 나중에 0/1/2의 등급 정답으로 확장할 수 있다. nDCG는 0~1 범위에서 **정답을 위쪽에 배치했는지**를 보므로, 단지 50개 후보 안에 넣었는지를 보는 Recall@50과 역할이 다르다. Haystack의 공식 평가 문서도 nDCG를 정답 문서가 어떤 순위에 나타나는지 확인하는 지표로 설명한다. [Haystack Evaluators](https://docs.haystack.deepset.ai/docs/evaluators)

**오해하지 말 것**: `gold_doc_ids`가 하나뿐인 Ch 11 기본 질의셋에서 nDCG@5는 첫 정답의 순위에 크게 좌우된다. 한 문서도 검색하지 못한 원인은 nDCG가 아니라 Recall@50부터 확인한다. 리랭커가 바뀐 비교는 후보 집합을 고정하고 Precision@5/nDCG@5를 비교해야 리랭커의 영향을 읽을 수 있다.

### Ch 11 최소 검증 경계

1. 20~30개의 `answerable:true` 질의마다 적어도 하나의 `gold_doc_id`가 있고, 모든 ID가 현재 말뭉치에 존재하는지 검사한다.
2. 의도적으로 정답을 6위와 51위에 놓은 작은 순위 목록으로 각 지표를 단위 검증한다. 6위는 Recall@50에는 기여하지만 Precision@5/nDCG@5에는 기여하지 않고, 51위는 셋 모두 0이어야 한다.
3. `[]`, 중복 `doc_id`, `gold_doc_ids=[]`를 각각 넣어 정책대로 0 또는 제외가 되는지 검사한다.
4. 한 실험 행에는 `corpus_fingerprint`, 청킹/임베딩/검색/리랭킹 설정, 질의셋 버전, 실행일, `returned_count`, 정책 버전을 함께 남긴다. 설정만 달라진 두 행만 전후 비교의 근거가 된다.

## Ch 12: 검색 품질 구현 근거

### 1. pgvector HNSW와 필터

공식 pgvector README 기준 최신 안정 태그는 **v0.8.6**이다. PostgreSQL 13+를 지원하고, Docker 태그 `pgvector/pgvector:0.8.6-pg16-bookworm`처럼 pgvector와 PostgreSQL 주 버전을 함께 고정할 수 있다. 데이터베이스마다 `CREATE EXTENSION vector;`가 필요하며 실행 환경에서는 `SELECT extversion FROM pg_extension WHERE extname = 'vector';`로 실제 확장 버전을 기록한다. [pgvector v0.8.6 README](https://github.com/pgvector/pgvector/tree/v0.8.6)

|항목|공식 근거와 Ch 12에서 확인할 점|
|---|---|
|HNSW `vector`|HNSW 인덱스는 `vector`에서 최대 2,000차원을 지원한다. 예: 1,536차원 임베딩은 `vector(1536)`과 `vector_cosine_ops`로 색인할 수 있다.|
|HNSW `halfvec`|HNSW 인덱스는 `halfvec`에서 최대 4,000차원을 지원한다. `halfvec(1536)`의 연산자 클래스는 `halfvec_cosine_ops`처럼 타입에 맞춰야 한다. halfvec는 반정밀도로 저장하므로 메모리/저장량과 Recall@50·nDCG@5의 변화를 같은 질의셋으로 측정한다.|
|HNSW 매개변수|기본 `m=16`, `ef_construction=64`, 검색 시 `hnsw.ef_search=40`이다. `ef_construction`을 높이면 구축 시간·삽입 비용을 내고 recall을 높일 수 있으며, `ef_search`도 속도-재현율 교환이다.|
|거리/차원|임베딩 모델이 낸 차원과 열 정의는 정확히 같아야 한다. 모델을 교체할 때 기존 벡터를 재사용하거나 차원을 임의로 자르면 안 된다. cosine이면 `<=>`와 cosine 연산자 클래스를 한 실험에서 함께 사용한다.|

HNSW는 근사 최근접 이웃 색인이므로 정확 검색보다 빠른 대신 결과가 달라질 수 있다. 공식 문서는 색인 없이 검색하면 완전한 recall을 얻고, 근사 색인은 속도와 recall을 교환한다고 명시한다. [pgvector Indexing](https://github.com/pgvector/pgvector/tree/v0.8.6#hnsw)

#### post-filter와 iterative scan

근사 HNSW는 먼저 후보를 찾고 SQL 필터를 적용한다. 그래서 `WHERE category_id = ...` 같은 필터가 있고 `LIMIT 5`일 때, 초기 후보 중 필터 통과 문서가 적으면 5개보다 적게 반환될 수 있다. 이것은 데이터가 없다는 뜻도, HNSW 오류라는 뜻도 아니다. pgvector는 v0.8.0부터 충분한 결과를 찾거나 상한에 이를 때까지 더 스캔하는 iterative index scan을 제공한다. [pgvector Iterative Index Scans](https://github.com/pgvector/pgvector/tree/v0.8.6#iterative-index-scans)

- 수업의 기본 실험은 트랜잭션 범위에서 `SET LOCAL hnsw.iterative_scan = strict_order`로 둔다. strict는 거리 순서를 보존한다.
- `relaxed_order`는 recall에 유리할 수 있지만 약간 정렬이 어긋날 수 있다. 최종 순위가 필요하면 공식 문서처럼 materialized CTE 뒤에서 거리로 다시 정렬한다. PostgreSQL 17+에서는 `distance + 0` 형태가 필요하다는 주석도 함께 남긴다.
- `hnsw.max_scan_tuples`(기본 20,000)와 `hnsw.scan_mem_multiplier`는 더 많이 찾을 여지를 주지만 비용도 늘린다. `ef_search`만 높였다는 기록으로 끝내지 말고, 필터 선택도·반환 개수·latency·Recall@50을 같은 행에 기록한다.
- 필터가 매우 선택적이면 B-tree 필터 색인, 부분 색인 또는 파티션도 공식 대안이다. Ch 12에서는 원리를 보이고, 어떤 대안이 좋은지는 이 과정의 말뭉치와 조건으로 평가한다.

### 2. 한국어 sparse: Kiwi + BM25

Kiwi의 Python API `Kiwi.tokenize()`는 입력을 형태소 분석해 `Token` 목록으로 반환하며, `Token.form`과 품사 태그를 제공한다. 공백으로만 나누는 방식보다 한국어 조사·어미가 붙은 형태를 관찰할 근거가 된다. [kiwipiepy README](https://github.com/bab2min/kiwipiepy) · [tokenize API](https://bab2min.github.io/kiwipiepy/v0.21.0/kr/)

1. 문서와 질문을 **같은 `kiwi.tokenize()` 정책**으로 처리해 `Token.form` 배열을 만든다.
2. 기호 태그 등 제거 규칙은 코드와 실험 설정에 명시한다. 명사만 남기기 같은 품사 필터는 가능한 선택지일 뿐 기본 사실이 아니므로, 원문+형태소/필터 변형을 같은 질의셋으로 비교한다.
3. BM25는 이 토큰 배열로 점수를 계산해 `(doc_id, rank)`만 반환한다. `rank_bm25` 0.2.2는 설치 가능하지만 최신 배포가 오래되었으므로, 수업에서는 작은 직접 구현 또는 고정 버전 패키지 중 하나를 택하되 환경 파일에 근거를 남긴다. [PyPI rank-bm25](https://pypi.org/project/rank-bm25/) · [upstream source](https://github.com/dorianbrown/rank_bm25)
4. PostgreSQL `ts_rank`는 텍스트 검색의 빈도·근접성·구조 정보를 쓰는 순위 함수이지 BM25라는 이름의 구현이 아니다. 따라서 Ch 12의 “Kiwi+BM25” 실험과 `ts_rank` 결과를 같은 것으로 표시하지 않는다. [PostgreSQL text-search ranking](https://www.postgresql.org/docs/current/textsearch-controls.html)

Kiwi 최신 PyPI 공개판은 **0.23.2**(2026-06-11)이며 라이선스는 LGPL-3.0이다. 이는 패키지의 라이선스이고, 학생 말뭉치의 사용 권리는 별도로 확인한다. [PyPI kiwipiepy](https://pypi.org/project/kiwipiepy/) · [upstream packaging metadata](https://github.com/bab2min/kiwipiepy/blob/main/setup.py)

### 3. 직접 Reciprocal Rank Fusion(RRF)

RRF는 dense와 sparse처럼 점수 척도가 다른 두 순위 목록을 순위만으로 합친다. 문서 d의 점수는 다음과 같다.

```
rrf(d) = Σ_source weight_source / (rank_constant + rank_source(d))
```

- 두 검색기를 독립 실행하고, 각 결과의 `doc_id`와 1부터 시작하는 rank를 보존한 뒤 같은 문서의 항만 더한다.
- 처음에는 양쪽 weight=1, `rank_constant=60`, 양쪽 후보 창을 같은 값(예: 50)으로 고정한다. 이후에는 weight, rank constant, 후보 창 중 한 항목만 바꾸고 Ch 11 로그로 비교한다.
- RRF는 원래 점수값을 섞지 않는다. 따라서 cosine similarity와 BM25 점수를 그대로 더하는 방식보다 실험의 의미가 명확하다.

Elasticsearch 공식 문서는 RRF의 위 식, 1부터 시작하는 rank, 기본 `rank_constant=60`, 개별 후보 창과 최종 `size`의 차이를 설명한다. [Elasticsearch Reciprocal Rank Fusion](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

### 4. Cross-Encoder 재정렬

Cross-Encoder는 질문과 후보 문서를 **쌍으로 함께** 입력해 관련성 점수 하나를 낸다. 후보를 각각 임베딩하는 bi-encoder와 달리 쌍 수만큼 계산해야 하므로, 큰 말뭉치를 전부 점수화하는 1차 검색기가 아니다. Sentence Transformers 공식 안내도 1차 검색이 만든 예컨대 100개의 후보를 Cross-Encoder로 재정렬하는 두 단계 구조를 제시한다. [Sentence Transformers Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

수업의 비교 후보는 다음 두 모델 카드의 명시 정보까지 확인했다. 어느 모델이 이 도메인에서 더 낫다는 결론은 아직 없으며, 같은 후보 집합과 질의셋에서 nDCG@5·latency·메모리를 측정해 정한다.

|후보|확인된 사실|라이선스·운영 경계|
|---|---|---|
|`BAAI/bge-reranker-v2-m3`|공식 모델 카드는 multilingual이며 query+passage를 입력해 직접 유사도 점수를 낸다고 설명한다.|모델 카드 Apache-2.0. 모델 가중치는 최초 내려받을 때의 revision/SHA를 실험 행에 기록한다. [모델 카드](https://huggingface.co/BAAI/bge-reranker-v2-m3)|
|`Dongjin-kr/ko-reranker`|공식 모델 카드는 한국어·영어 태그, XLM-RoBERTa 기반 분류 모델, query+문서의 직접 관련성 점수를 설명한다.|모델 카드 MIT. 저장소 화면의 가중치 크기는 약 2.24 GB이므로 로컬 디스크/다운로드 시간을 실습 전 확인한다. [모델 카드](https://huggingface.co/Dongjin-kr/ko-reranker)|

`sentence-transformers` PyPI 최신판은 **6.0.1**(2026-08-31, Python >=3.10)이며 라이브러리 라이선스는 Apache-2.0이다. 라이브러리 라이선스와 각 모델의 라이선스는 별개로 기록한다. [PyPI sentence-transformers](https://pypi.org/project/sentence-transformers/) · [upstream LICENSE](https://github.com/huggingface/sentence-transformers/blob/main/LICENSE)

**검증 경계**: 1차 후보 k를 고정하지 않으면 리랭커 비교가 아니다. 먼저 dense/sparse/RRF가 만든 동일 후보 목록을 저장하고, 모델별로 그 목록을 재정렬한 뒤 Precision@5와 nDCG@5를 비교한다. Recall@50이 낮다면 reranker 교체만으로 누락 문서를 되살릴 수 없다.

### 5. MMR과 parent-document 전달

MMR(Maximal Marginal Relevance)은 후보 하나의 질문 관련성만 보지 않고, 이미 고른 후보와의 중복도 뺀다. 각 단계에서 다음 값이 가장 큰 후보를 고른다.

```
λ × similarity(query, candidate)
− (1 − λ) × max_similarity(candidate, already_selected)
```

`λ`가 높으면 관련성 중심, 낮으면 다양성 중심이다. MMR은 정확도를 보장하는 필터가 아니라, 겹침 청크가 top-k의 여러 자리를 차지하는 현상을 조절하는 재정렬 규칙이다. Haystack의 공식 API 문서도 query 관련성과 이미 선택한 문서와의 다양성을 함께 계산하고, `lambda_threshold`가 교환을 조절한다고 설명한다. [Haystack Rankers API](https://docs.haystack.deepset.ai/reference/rankers-api)

Parent-document 방식은 **작은 child 청크를 검색 단위로, 더 긴 parent 문서를 생성 컨텍스트 단위로** 쓴다. 구현 계약은 다음처럼 단순하게 유지한다.

1. parent를 만들고 각 child에 `parent_id`와 `doc_id`를 넣는다.
2. child 결과를 rank 순으로 받는다.
3. parent_id별로 중복을 제거하고, parent 본문은 한 번만 전달한다.
4. 평가할 때는 child가 아니라 `doc_id` 기준으로 Recall@50을 계산하고, 생성에 전달한 parent 수·토큰 수도 별도 기록한다.

이 방식은 검색 단위와 전달 단위를 분리한다. parent를 늘리면 정답 근처 문장을 덜 자를 수 있지만, 생성 입력 토큰과 비관련 문맥도 늘 수 있다. Ch 11 검색 지표만으로 생성 품질을 주장하지 않는다.

### 6. Query rewrite

Ch 12에서의 query rewrite는 원 질문을 지우는 기능이 아니라, 검색용 질의를 하나 더 만든 뒤 원문과 함께 비교하는 실험이다.

- 원 질문, 재작성 질문, 사용한 프롬프트/모델/온도, dense·sparse 각 결과를 모두 로그에 남긴다.
- 재작성 실패나 의미 확장은 실제 실패 사례로 남긴다. 특히 한국어 고유명사·약어·날짜·부정 조건은 원문에서 사라지지 않는지 검사한다.
- 첫 실험은 원 질문만, 두 번째 실험은 rewrite만, 세 번째는 둘의 RRF를 비교한다. 한 번에 청킹·임베딩·rewrite·reranker를 함께 바꾸지 않는다.
- PostgreSQL의 `ts_rewrite`는 `tsquery` 일부를 치환하는 텍스트 검색 함수다. LLM이 자연어 질문을 새로 만드는 query rewrite와 같은 기능으로 설명하지 않는다. [PostgreSQL ts_rewrite](https://www.postgresql.org/docs/current/functions-textsearch.html)

## 설치·실행 기준선

다음은 현재 설치 가능한 버전의 **실행 계획**이며, 기존 Ch 9·10 환경을 무단으로 바꾸는 명령이 아니다.

1. Docker가 있는 환경에서 `pgvector/pgvector:0.8.6-pg16-bookworm`을 고정하고, 컨테이너 안에서 `CREATE EXTENSION vector;`와 확장 버전을 확인한다. 공식 pgvector Docker 태그와 지원 PostgreSQL 조합은 README를 따른다. [pgvector Docker installation](https://github.com/pgvector/pgvector/tree/v0.8.6#docker)
2. 별도 uv 환경에 Python 3.12를 유지하며 `kiwipiepy==0.23.2`와 필요 시 `sentence-transformers==6.0.1`을 고정한다. `rank-bm25==0.2.2`는 설치는 가능하지만 최신 릴리스가 오래되었다는 점을 `pyproject.toml`과 교재에 표시한다.
3. 모델은 실습 첫 실행에서 내려받으므로 네트워크·디스크·CPU/GPU 조건을 먼저 기록한다. 모델 이름만으로 재현하지 말고 Hugging Face revision도 로그에 남긴다.
4. API 키가 필요한 OpenAI 임베딩은 기존 `.env`에서만 읽는다. KIWI/BM25/HNSW의 개념 검증은 가능한 한 로컬 입력으로 분리해 API 비용과 네트워크 실패를 분리한다.

- “리랭커는 1차 검색이 가져온 후보만 다시 정렬합니다. 후보에 없는 문서는 리랭커가 되살리지 못합니다.”
- “HNSW에 필터를 함께 걸면 후보를 찾은 뒤 필터를 적용하므로 결과가 k개보다 적을 수 있습니다. iterative scan은 더 찾아볼지 정하는 기능이며, 속도와 recall을 함께 측정해야 합니다.”
