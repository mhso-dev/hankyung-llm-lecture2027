4
핵심 개념
비유 — 오픈북 시험
RAG는 오픈북 시험과 비슷합니다. 검색으로 고른 몇 쪽을 프롬프트에 넣고, 모델에 그 문서를 근거로 답하라고 요청합니다. 그러나 모델이 학습한 지식을 섞거나 문서에 없는 내용을 만들 수도 있습니다. 따라서 맞는 쪽을 검색했는지 먼저 보고, 답의 내용과 출처가 실제 문서와 일치하는지도 확인해야 합니다.
{{img:01-오픈북-비유|같은 학생이 왼쪽에서는 빈 책상에서 고민하고, 오른쪽에서는 책갈피가 꽂힌 세 쪽을 보며 답을 씁니다.}}
왼쪽은 기억만으로 답하는 학생(순수 LLM), 오른쪽은 책상에 올라온 세 쪽을 보며 답하는 학생(RAG)입니다. 책갈피가 출처 표기에 해당합니다.
보는 순서 — ① 왼쪽 학생의 물음표 → ② 오른쪽 책상의 세 쪽 → ③ 쪽에서 답안지로 가는 화살표.
정의
RAG (Retrieval-Augmented Generation, 검색 증강 생성)
질문이 들어오면 먼저 문서 저장소에서 관련 조각을
검색
하고, 그 조각을 프롬프트에 넣어 답을
생성
하는 방식입니다. "증강"은 프롬프트에 검색 결과를 더한다는 뜻입니다.
색인 (indexing)
문서를 미리 잘게 나누고 벡터로 바꿔 저장해 두는 준비 작업입니다. 문서, 청크 설정, 임베딩 모델 중 하나가 바뀌면 다시 실행합니다.
청크 (chunk)
문서를 검색 단위로 자른 조각입니다. 청크 크기는 각 절의 설정에 따라 달라지며, 값을 바꾼 뒤 실제 길이와 본문을 확인합니다. 검색 결과는 쪽이 아니라 청크 단위로 반환됩니다.
벡터스토어 (vector store)
청크와 그 벡터를 함께 담아 두고, 질문 벡터와 가까운 것을 찾아 주는 저장소입니다. 이 챕터에서는 메모리에 두는
를 씁니다.
top-k 검색
질문과 가장 가까운 청크 k개를 가져오는 것입니다. k는 학생이 정합니다. 이 절의 기본 실행은 k=2이고, 이어서 k=1과 비교합니다.
출처 인용 (citation)
답의 근거로 사용한 문서와 쪽을 표기하는 형식입니다. 표기가 실제 근거와 일치하는지는 별도로 확인해야 합니다. RAG가 순수 LLM과 다른 가장 실용적인 장점입니다.
도식 — 두 흐름
RAG에는 시점이 다른 두 흐름이 있습니다. 위쪽
색인

질문 처리
과정은 질문이 들어올 때마다 실행됩니다. 두 흐름이 만나는 곳이 벡터스토어입니다. 색인 단계가 벡터스토어를 채우고, 질문 처리 단계가 관련 문서를 벡터스토어에서 꺼냅니다.

색인은 문서·청크 설정·임베딩 모델이 바뀔 때 다시 만들고, 질문 처리는 질문할 때마다 실행합니다. 파란 상자는 학생 코드가 고정한 흐름입니다. LLM 생성도 그 흐름 안에서 호출됩니다. 초록은 문서와 저장소이며, 모델이 실행 흐름을 판단하는 경우에 사용하는 보라색은 이 도식에 없습니다.

왜 셀을 단계별로 나눕니까?
처음에는 한 셀에서 한 단계의 결과를 확인합니다. PDF를 읽은 뒤 본문을 보고, 분할한 뒤 청크를 보고, 검색한 뒤 선택된 문서를 봅니다. 마지막 답이 예상과 다르면 이미 출력한 검색 결과부터 살펴볼 수 있습니다. 필요한 근거가 검색되었는지와 모델이 그 근거를 사용했는지를 차례로 확인하는 연습입니다.
각 셀은 앞에서 만든 변수와 LangChain의 메서드를 직접 사용합니다. 기본 실습에서는 별도 함수나 모듈을 먼저 만들 필요가 없습니다. 이후 Ch 13에서 흐름을 그래프로 표현할 때, 지금 확인한 각 단계의 입력과 출력을 바탕으로 노드의 역할을 정합니다.

표지

{{img:05-지어낸-숫자|시계 질문을 받은 안내원이 시계가 없는 두 문서만 들고도 시계가 든 답을 내놓고, 그 위에 빨간 경고 표시가 떠 있습니다.}}
고객이 시계(기한)를 묻고, 안내원은 답이 없는 문서만 들고도 기한을 만들어 낼 수 있습니다. 기본 노트북은 검색 문맥에 답이 없을 때 실제 응답이 어떻게 나타나는지 확인합니다.
보는 순서 — ① 왼쪽 고객의 시계 말풍선 → ② 가운데 안내원이 든 두 장(시계가 없다) → ③ 오른쪽 답 말풍선의 시계와 빨간 경고.
정의
환각 (hallucination)
근거 없이 만들어진, 그러나 형식은 그럴듯한 출력입니다. RAG에서는 "검색된 문서에 없는 내용을 문서에 있는 것처럼 답하는 것"으로 좁혀서 씁니다. 숫자·날짜·고유명사처럼 확인 가능한 내용을 문서와 대조해 판정할 수 있습니다.
답변 거부 (refusal)
모델이 답 대신 "문서에서 찾을 수 없습니다"처럼 답할 수 없음을 말하는 것입니다. 답이 문서에 없을 때는 정답이고, 있을 때는 오답입니다.
답을 찾을 수 없는 질문 (unanswerable query)
문서 세트 어디에도 답이 없는 질문입니다. 이런 질문의 정답은 “근거가 없어 답할 수 없다”이며, 답이 있는 질문의 검색 누락과 구분해야 합니다.
실행할 때마다 나타날 수도 있고 나타나지 않을 수도 있는 실패 (stochastic failure)
같은 입력으로도 어떤 실행에서는 일어나고 다른 실행에서는 일어나지 않는 실패입니다. 한 번 실행해서 나타나지 않았다고 실패가 없다고 판단할 수는 없습니다. 기본 노트북은 검색 ID와 실제 응답을 함께 기록해 원인을 구분합니다.

위 경로는 근거가 검색된 경우이고, 가운데 경로는 정답 문서가 검색에서 빠진 경우입니다. 정답이 문서에 있는데 검색이 못 가져왔고, 모델은 규칙에 따라 "찾을 수 없습니다"라고 답하거나 규칙을 어기고 숫자를 지어냅니다(환각). 아래 경로는 정답이 문서에 없는 경우이고, "찾을 수 없습니다"가 정답입니다. 가운데와 아래의 출력은

기본 노트북은 문서에 답이 없으면 “찾을 수 없습니다”라고 답하도록 지시합니다. 먼저 k=1 검색이

마지막 셀은 문서 집합 자체에 A/S 처리 기간이 없는 질문을 별도로 실행합니다. 이 경우에는 k를 늘려도 근거가 생기지 않습니다. 검색 ID를 먼저 확인해야 “정답 문서가 검색에서 빠진 경우”와 “전체 문서에 답이 없는 경우”를 구분할 수 있습니다.
5
실행 예제
질문 단어는 많지만 답이 없는 DISTRACTOR와 실제 연체 규정이 있는 ANSWER를 색인합니다. k=1의 ID·본문·엄격한 답을 확인한 뒤 k만 2로 바꾸어 검색 문맥과 생성 답을 비교합니다. 마지막에는 문서 집합 자체에 답이 없는 질문을 별도로 실행합니다.
확인할 점
— k=1의 검색 ID에 ANSWER가 없으면 생성 모델은 연체 규정을 받지 못합니다. k=2에서 ANSWER가 포함되면 같은 엄격한 지시가 문서의 대출 정지 규정을 답합니다. 문서 집합에 A/S 기간이 없는 예제는 k와 관계없이 근거를 제공할 수 없습니다.
6
일부러 실패해 보기
Before에서 앞에서 실행한 k=1의 DISTRACTOR ID와 거부 답을 나란히 다시 보여 줍니다. After에서는 앞에서 k를 2로 바꿔 실행한 ANSWER ID와 대출 정지 답을 다시 보여 주고 검사합니다. Before/After 셀에서 모델을 추가로 호출하지는 않습니다.
7
주의할 점과 실무 메모
"찾을 수 없습니다" 비율만 보면 안 됩니다.
거부율이 낮다고 좋은 것도, 높다고 안전한 것도 아닙니다. 전체 문서에 답이 없는 질문에서 “찾을 수 없습니다”라고 답한 비율(높아야 함)과 문서에 답이 있는 질문에서 “찾을 수 없습니다”라고 잘못 답한 비율(낮아야 함)을 나눠서 봐야 하고, 나누려면 정답 문서 ID가 필요합니다. Ch 11 테스트 질문 표의
칸에는 문서에서 답을 찾을 수 있는 질문인지 표시합니다.
관찰한 실패만 기록합니다.
이 노트북은 엄격한 지시를 유지한 채 검색 문맥을 바꿉니다. 환각을 관찰하지 않았는데 발생했다고 적거나, 한 번의 거부를 모든 입력에서의 안전성으로 일반화하지 않습니다.
출처와 내용도 대조합니다.
출처 태그가 있어도 실제 해당 문서가 답을 뒷받침하는지 확인해야 합니다. 예를 들어 같은 규정의 예전 문서와 새 문서가 함께 있으면, 출처 문장은 실제로 있어도 질문이 요구한 시행일과 맞지 않을 수 있습니다.
프롬프트 규칙의 한계 세 가지.
① 검색 실패를 고치지 못한다(재료 문제) ② 같은 지시도 실행에 따라 준수 여부가 달라질 수 있다 ③ 검색 문서 안의 지시문을 모델이 사용자 지시로 잘못 받아들일 수 있다(프롬프트 인젝션). 각각 Ch 12, Ch 11·15, Ch 16의 주제입니다.
한국어 문서의 부칙·단서.

회의장 좌석 배치도에는 사람 이름이 공간에 놓여 있습니다. 글자를 위에서 아래로만 읽으면 왼쪽 열과 오른쪽 열의 이름이 섞일 수 있습니다. 표도 같습니다. 사람은 선과 간격을 보고 같은 행을 알아보지만, 텍스트 추출기는 좌표를 읽기 순서로 바꾸는 규칙이 필요합니다. OCR은 사진 속 이름표를 문자로 바꾸는 일입니다. 문자로 바꾼 뒤에도 어느 좌석에 해당하는지 정리하는 작업은 별도로 남습니다.
정의
텍스트 레이어 (text layer)
PDF 안에서 선택·검색할 수 있는 문자 정보입니다. 스캔 PDF는 페이지 이미지밖에 없어 텍스트 레이어가 없을 수 있습니다.
레이아웃 (layout)
글자·문단·열·표가 쪽 위에 배치된 공간 관계입니다. 문자열 추출 과정에서 이 관계의 일부가 사라질 수 있습니다.
읽기 순서 (reading order)
사람이 문서 내용을 따라가는 순서입니다. 두 단 문서에서는 왼쪽 단을 끝까지 읽은 뒤 오른쪽 단으로 가야 하지만, 좌표 해석에 따라 줄별로 섞일 수 있습니다.
표 추출 (table extraction)
표의 셀 경계와 행·열 관계를 찾아 구조화된 값으로 복원하는 처리입니다. 일반 텍스트 추출과 별도의 검출 전략이 필요할 수 있습니다.
광학 문자 인식 (optical character recognition, OCR)
페이지 이미지의 글자 모양을 문자로 인식하는 처리입니다. OCR은 오탈자를 만들 수 있으며 표 구조를 자동으로 보장하지 않습니다.

7
주의할 점과 실무 메모
PDF는 의미 구조를 항상 보장하지 않습니다.
태그가 있는 PDF도 있지만, 일반 텍스트 추출이 표·문단 구조를 안정적으로 복원한다고 전제하지 않습니다.
OCR 엔진은 별도 의존성입니다.
PyMuPDF의 통합 OCR도 Tesseract 설치가 필요합니다. 설치·언어 데이터·버전을 실행 환경에 기록합니다.
메모리를 확인합니다.
압축된 콘텐츠 스트림이 매우 크게 풀리는 PDF가 있으므로 파일 크기만으로 처리 비용을 판단하지 않습니다.
라이선스를 확인합니다.
PyMuPDF/MuPDF는 AGPL 또는 상용 라이선스 체계입니다. 교육 실습과 제품 배포의 조건을 별도로 검토합니다.
상용 API 가격은 확인일과 함께 적습니다.
Upstage의 Parse only 가격은 2026-09-08 기준 페이지당 미화 0.01달러로 표시되지만 변경될 수 있습니다. LlamaParse는 티어와 파서 버전을 실행 기록에 고정합니다.
8
정리와 다음 절
디지털 PDF의 문자 추출, 표 구조 복원, 스캔 이미지 OCR은 서로 다른 문제입니다.
기본 텍스트와
의

텍스트 품질을 쪽 단위로 검사하고 필요한 쪽만 OCR 후보로 보내며, 표와 읽기 순서는 원본과 대조합니다.

복습 문제
문제 4개 · 해설 포함
1. [하] 텍스트 추출과 OCR의 차이는 무엇입니까?
텍스트 추출은 PDF에 이미 저장된 문자 정보를 읽습니다. OCR은 페이지 이미지의 글자 모양을 새 문자로 인식합니다.
2. [중] PDF에서 모든 숫자가 추출되었는데도 표 질의에 답하지 못하는 이유는 무엇입니까?
숫자와 행·열 머리글의 관계가 사라질 수 있기 때문입니다. 표 질의에는 값 자체뿐 아니라 그 값이 어떤 조건과 항목에 해당하는지 필요합니다.
3. [중]
처럼 1을 빼는 이유는 무엇입니까?
사람이 보는 쪽 번호는 1부터 시작하지만 Python 목록 위치는 0부터 시작하기 때문입니다. 2쪽은 목록 위치 1에 있습니다.
4. [상] 두 단 PDF의 읽기 순서가 잘못된 상태에서 청크 크기만 조정하면 해결되지 않는 이유는 무엇입니까?
청킹은 입력 문자열의 순서를 신뢰합니다. 파서가 서로 다른 단의 문장을 이미 섞었다면 청크 크기를 바꾸어도 잘못 연결된 문장 관계가 남으므로 파서나 레이아웃 처리 단계에서 고쳐야 합니다.

학습 목표
이 절을 마치면 HWP와 HWPX가 내부 구조와 처리 방법에서 어떻게 다른지 설명할 수 있습니다.
이 절을 마치면 제공된 HWPX의 ZIP 항목을 확인하고 본문 section XML만 선택해 텍스트를 추출할 수 있습니다.
이 절을 마치면 전체 XML과 본문 XML의 선택 결과를 비교하고, 레거시 HWP를 미지원 경로로 안전하게 분기할 수 있습니다.
2
이 내용을 배우는 이유
한국의 공공기관과 기업 문서 저장소에는 HWP와 HWPX가 함께 있습니다. PDF만 처리하는 RAG는 결재문, 공고문, 회의 자료의 일부를 놓칠 수 있습니다. 그러나 두 확장자를 같은 방식으로 읽을 수 있다고 생각하면 구현 범위를 잘못 잡게 됩니다. HWP는 전용 구조를 해석해야 하는 네이티브 형식이고, HWPX는 본문과 설정을 담은 여러 XML 파일을 ZIP 방식으로 한 파일에 묶은 개방형 형식입니다. 이번 절은 모든 한글 문서를 완벽하게 파싱한다고 약속하는 대신, 파일 내부가 ZIP인지 먼저 확인하고, HWP와 HWPX를 서로 다른 읽기 방법으로 보내는 과정을 다룹니다.
기본 문서 묶음은 PDF이므로 Ch10 실습 폴더에 HWPX 구조 관찰용 최소 표식과 레거시 HWP 형식 분기용 표식을 별도로 제공합니다. 이 파일로 ZIP/XML 읽기와 미지원 분기를 검증할 수 있지만 실제 업무 문서의 표·각주·이미지나 한컴오피스 호환성을 주장하지 않습니다. 수강생이 실제 업무에서 다룰 문서 100건도 아직 저장소에 없으므로 HWP/HWPX 비율이나 처리 성공률을 제시하지 않습니다.

핵심 개념
비유 — 잠긴 서류함과 라벨이 붙은 상자
HWP를 규격에 맞는 열쇠와 해석표가 필요한 서류함이라고 생각해 보세요. HWPX는 여러 XML 문서를 라벨이 붙은 상자에 나누어 담고, 그 상자를 ZIP으로 묶은 형태에 가깝습니다. HWPX는 상자를 열어 항목을 확인하기가 더 수월하지만, 라벨을 읽었다고 문단·표·각주가 저절로 완성되는 것은 아닙니다. 어떤 XML이 본문이고 요소의 순서가 무엇인지 해석해야 합니다.
정의
HWP 네이티브 형식 (HWP native format)
한컴 한글의 전용 문서 형식입니다. 내부 레코드와 구조를 이해하는 전용 도구 또는 변환 경로가 필요하며, 범용 ZIP/XML 처리만으로 읽을 수 없습니다.
HWPX
한글 문서의 XML 파일 구조를 정한 OWPML을 따르며, 국가표준 KS X 6101에 등록된 개방형 파일 형식입니다. 여러 XML과 자원을 ZIP 컨테이너에 담습니다.
개방형 워드프로세서 마크업 언어 (Open Word-Processor Markup Language, OWPML)
HWPX 문서의 구조와 내용을 XML로 표현하는 규격입니다. 본문, 설정, 메타데이터가 여러 항목으로 나뉠 수 있습니다.
ZIP 컨테이너 (ZIP container)
여러 XML·이미지·설정 파일을 ZIP 압축 폴더처럼 하나의 문서 파일 안에 묶는 저장 방식입니다. 확장자가
여도 내부 항목과 필수 파일을 검사해야 합니다.
{{svg:04-hwp-hwpx}}
HWP는 전용 바이너리 해석기나 변환 도구를 거치고, HWPX는 ZIP 안의 XML을 검사합니다. 본문 추출을 마친 결과는 후속 단계에서
와 출처 메타데이터로 옮길 수 있습니다. 이번 실습은 HWP의 미지원 상태와 HWPX에서 읽은 문자열까지만 확인하며,
를 만들지는 않습니다.
HWPX 처리의 첫 단계는 파일을 열어 항목 목록을 확인하는 것입니다. 그다음 본문 XML을 문서 순서대로 읽고, 텍스트 노드와 문단 경계를 추출합니다. 파일 안의 모든 XML 텍스트를 합치면 스타일 이름, 설정값, 메타데이터가 본문에 섞일 수 있습니다. 본문 항목을 명시적으로 선택하고, 문단 번호나 구역 파일명을
에 남깁니다. 표와 병합 셀은 별도의 구조 해석이 필요하므로 기본 텍스트 로더가 어느 요소를 지원하는지 문서화합니다.
HWP에는 세 가지 현실적인 경로가 있습니다. 첫째, 신뢰할 수 있는 환경에서 HWPX나 PDF로 변환한 뒤 변환 산출물을 처리합니다. 둘째, 한컴이 제공하는 도구나 SDK를 사용합니다. 셋째, 회사의 보안 규칙상 외부 전송이 허용되면 상용 문서 파서에 전달합니다. 어느 경로든 원본과 변환본의 관계, 변환 도구 버전, 실패 파일을 기록합니다. 변환에 성공했다는 사실이 표·각주·변경 내용까지 보존되었다는 뜻은 아니므로 대표 문서를 원본과 대조합니다.

주의할 점과 실무 메모
HWP와 HWPX를 같은 형식으로 취급하지 않습니다.
확장자별 처리 경로와 실패 메시지를 분리합니다.
HWPX도 완전한 평문 형식은 아닙니다.
ZIP 안의 여러 XML, 이미지, 표, 각주 관계를 해석해야 합니다.
변환본의 출처를 남깁니다.
원본 HWP의 ID, 변환 파일 경로, 변환 도구와 시각을 기록해야 갱신과 오류 조사가 가능합니다.
외부 서비스에 보내도 되는 문서인지 먼저 확인합니다.
계약서·인사 문서·개인정보가 든 HWP를 상용 API에 보내기 전에 회사 승인을 받고, 외부 서비스가 파일을 얼마나 오래 보관하는지 확인합니다.
호환성 표는 실제 샘플로 만듭니다.
문단, 표, 병합 셀, 각주, 이미지, 암호화 문서를 각각 검사하고 성공·부분 성공·실패로 구분합니다.

이 내용을 배우는 이유
앞 절까지는 PDF·DOCX·HTML·CSV·HWPX에서 텍스트를 꺼내고, 표와 이미지가 손실되는 지점을 확인했습니다. 파싱한 결과는 아직 문서 전체이거나 쪽 단위입니다. 검색 시스템은 이 긴 텍스트를 그대로 다루지 않습니다. 질문과 직접 관련 있는 범위를 찾을 수 있도록 더 작은 단위인 청크로 나눕니다. 같은 파싱 결과라도 어디에서 끊는지에 따라 검색 결과가 달라지므로, 청킹은 파일을 읽은 다음 가장 먼저 비교할 설정입니다.
긴 컨텍스트 모델을 보고 청크도 크게 만들면 된다고 생각하기 쉽습니다. 그러나 큰 청크는 주변 문맥을 더 보존하는 대신 질문과 무관한 문장도 함께 가져옵니다. 입력 토큰과 임베딩 시간도 늘어날 수 있습니다. 작은 청크는 질문에 맞는 문장을 정밀하게 찾기 쉽지만 설명과 조건이 서로 갈라질 수 있습니다. 이 절의 목표는 한 가지 크기를 정답으로 고르는 것이 아닙니다. 같은 문서를 세 방식으로 나누고, 각 방식이 무엇을 보존하고 무엇을 잃는지 실행 결과로 확인하는 것입니다.

비유 — 원고를 여러 크기의 카드로 나누기
긴 업무 규정을 카드에 나누어 적는다고 생각합니다. 문자 청킹은 카드 한 장에 글자를 일정 수만큼 적고 다음 카드로 넘어갑니다. 재귀 청킹은 먼저 문단을 통째로 넣어 보고, 카드에 들어가지 않으면 문장과 띄어쓰기 순서로 더 잘게 나눕니다. 토큰 청킹은 글자 수 대신 모델이 세는 조각 수를 카드의 한도로 씁니다. 세 방법 모두 카드를 만들지만 경계를 고르는 기준이 다릅니다.
정의
문자 청킹 (character chunking)
하나의 구분자로 텍스트를 나누고, 문자 길이를 계산하며 조각을 합치는 방식입니다.
는 목표 크기이며 구분자보다 긴 조각이 있으면 결과가 이 값을 넘을 수 있으므로 실제 길이를 확인해야 합니다.
재귀 청킹 (recursive chunking)
문단 구분, 줄바꿈, 문장 부호, 띄어쓰기처럼 큰 경계부터 차례로 시도하고, 조각이 너무 길 때만 더 작은 경계로 내려가는 방식입니다. 경계 후보의 우선순위가 결과를 좌우합니다.
토큰 청킹 (token chunking)
특정 토크나이저가 계산한 토큰 수를 기준으로 청크 한도를 맞추는 방식입니다. 모델 입력 한도와 비용을 직접 관리하기 좋지만, 토크나이저가 바뀌면 같은 텍스트의 경계도 달라질 수 있습니다.
구분자 우선순위 (separator priority)
재귀 청킹에서 어느 경계를 먼저 보존할지 정한 순서입니다. 일반적으로 문단, 줄, 문장, 띄어쓰기, 문자 순으로 내려가지만 한국어 문서의 목록·표·조문 형식에 맞게 조정해야 합니다.

주의할 점과 실무 메모
유니코드 경계.
파이썬의 문자열 길이, 화면에 보이는 글자 수, 토크나이저의 토큰 수는 서로 다를 수 있습니다. 결합 문자, 이모지, 특수 공백이 섞인 입력은 특히 별도 사례로 검사합니다.
토크나이저 고정.
토큰 청킹에 사용한 토크나이저 이름과 버전을 설정에 남깁니다. 임베딩 모델과 생성 모델이 서로 다른 토크나이저를 쓸 수 있으므로 어느 모델의 한도를 관리하는지도 명시합니다.
큰 청크의 장단점.
청크를 크게 만들면 한 조각에 더 많은 문맥을 담을 수 있습니다. 동시에 관련 없는 내용이 함께 검색되거나 입력 토큰이 늘어날 수 있으므로, 큰 청크가 모든 종류의 문서와 질문에서 더 정확하다고 가정하지 않습니다. 문서 구조, 질문 길이, 검색 k, 비용을 함께 측정해야 합니다.
메타데이터 유지.

, 쪽, 원래 요소 유형을 복사합니다. 문자열 목록만 반환하면 검색 결과가 어느 파일과 위치에서 왔는지 추적할 수 없습니다.
8
정리와 다음 절
문자 청킹은 문자 수, 재귀 청킹은 구분자 우선순위, 토큰 청킹은 토크나이저가 계산한 수를 기준으로 경계를 정합니다.
재귀 청킹의 오버랩은 실제 중복을 항상 보장하지 않는 최댓값이므로 결과 청크에서 측정해야 합니다.
큰 청크와 작은 청크는 실제로 사용할 문서와 질문으로 검색 결과와 비용을 측정해 비교합니다.

복습 문제
문제 4개 · 해설 포함
1. 문자 청킹과 토큰 청킹의 기준 차이를 한 문장으로 설명하세요.
문자 청킹은 파이썬 문자열의 문자 수를 기준으로 하고, 토큰 청킹은 지정한 토크나이저가 만든 토큰 수를 기준으로 합니다.
2. 재귀 청킹에서
인데 실제 중복이 50자보다 작았습니다. 구현 오류라고 단정할 수 있습니까?
단정할 수 없습니다. 재귀 스플리터는 분할된 단위를 결합하며 이전 단위 가운데 한도 안에 들어오는 부분만 유지합니다. 설정값은 최댓값이고 실제 중복은 경계와 분할 단위에 따라 작아질 수 있으므로 청크를 직접 비교해야 합니다.
3. 한국어 500자와 영어 500자가 같은 토큰 수라고 가정하면 안 되는 이유는 무엇입니까?
토크나이저는 문자를 그대로 하나씩 세지 않고 학습된 어휘 단위로 나눕니다. 언어, 숫자, 특수문자, 이모지 구성에 따라 한 문자에 대응하는 토큰 수가 달라집니다.
4. 긴 컨텍스트 모델을 사용하므로 청크 크기를 두 배로 늘리자는 제안을 검토할 때 함께 기록해야 할 항목을 세 가지 이상 쓰세요.
청크 수와 길이별 개수(예: 100자 이하가 몇 개인지), 질문당 검색되는 총 토큰, 임베딩 시간과 비용, 정답 근거가 검색 범위에 포함되는지, 중복 청크 비율을 기록합니다. Ch 11 전에는 품질 지표가 비어 있으므로 비용이 낮거나 청크 수가 적다는 이유만으로 승자를 정하지 않습니다.

4
핵심 개념
비유 — 목차를 따를지, 대화 주제의 변화를 들을지
잘 편집된 보고서는 목차와 소제목이 방의 문패처럼 붙어 있습니다. 문패가 바뀔 때 새 청크를 시작하면 작성자가 의도한 구역을 따를 수 있습니다. 형식이 없는 회의 대화에는 문패가 없습니다. 이때는 인접한 발언의 내용이 얼마나 달라졌는지를 보고 주제가 바뀐 지점을 찾습니다. 구조 기반 청킹은 문패를 읽고, 시맨틱 청킹은 내용의 변화를 비교합니다.
정의
구조 기반 청킹 (structure-aware chunking)
제목·문단·목록·표·쪽을 보고 문서를 나누고, 각 조각이 어디에 속하는지 함께 남기는 방식입니다. 예를 들어 “배송” 제목 아래의 문단을 함께 묶고 제목도 저장합니다.
시맨틱 청킹 (semantic chunking)
문장이나 문장 묶음의 임베딩을 비교해 의미 변화가 큰 지점에서 청크를 나누는 방식입니다. 어떤 임베딩 모델을 쓰는지, 거리가 얼마나 커야 나눌지에 따라 결과가 달라집니다.
의미 경계 (semantic boundary)
앞뒤 텍스트의 주제가 충분히 달라졌다고 판단해 새 청크를 시작하는 위치입니다. 정답으로 주어진 경계가 아니라 계산 기준으로 선택한 후보입니다.
중단점 (breakpoint)
문장 묶음 사이의 의미 거리가 기준보다 커서 새 청크를 시작하는 위치입니다. 백분위를 쓰면 거리를 작은 값부터 정렬한 뒤, 예를 들어 95%의 값이 그보다 작거나 같은 지점을 기준으로 삼습니다. 문장이 적거나 같은 거리값이 많으면 예상한 청크 수와 다를 수 있으므로 실제 거리와 결과 본문을 함께 봅니다.
제목 경계 (header boundary)
Markdown의
처럼 제목임을 명시한 위치입니다. 제목을 청크 본문 앞에 남기면 뒤따르는 문단이 어느 주제에 속하는지 확인할 수 있습니다.

핵심 개념
비유 — 같은 주소 체계와 보관함 표찰
서로 다른 도시의 지도 좌표를 한 표에 섞으면 거리를 비교할 수 없습니다. 청크는 A 모델로, 질문은 B 모델로 변환한 뒤 가까운 것을 찾는 일도 마찬가지입니다. 모델과 차원, 입력 규칙이 같아야 같은 주소 체계입니다. 한 번 계산한 좌표를 보관할 때는 어느 주소 체계로 만들었는지 표찰을 붙여야 합니다. 캐시 키가 그 표찰입니다.
정의
다국어 임베딩 (multilingual embedding)
여러 언어의 텍스트를 검색·분류 같은 작업에 사용할 수 있도록 벡터로 표현하는 모델입니다. 지원 언어 목록은 후보 조건이며 특정 한국어 업무 문서에서 높은 검색 품질을 보장하지 않습니다.
차원 (dimension)
임베딩 벡터에 들어 있는 숫자의 개수입니다. 차원이 커지면 저장 공간과 거리 계산량이 늘어날 수 있으며, 차원 수만으로 품질을 판단할 수 없습니다.
모델 버전 (model revision)
같은 모델 이름 아래에서 사용한 정확한 코드·가중치 버전입니다. 로컬 오픈 모델은 커밋 SHA를 기록하고, API 모델은 공급자가 제공하는 고정 버전 식별자를 사용할 수 있는지 확인합니다.

모델 카드가 문서와 질의를 구분하기 위해 요구하는 앞부분입니다. 예를 들어 문서에는

벡터 캐시 (vector cache)
같은 입력 문자열과 같은 임베딩 설정으로 계산한 벡터를 다시 사용하기 위한 저장소입니다. 이 노트북은 입력 문자열의 공백이나 줄바꿈을 자동으로 정리하지 않습니다. 전처리 방법을 추가한다면 그 이름과 버전도 캐시 키에 반영해야 다른 입력의 벡터가 섞이지 않습니다.
인덱스 구성 기록표 (index manifest)
원문, 파서, 청킹 설정, 청크 ID와 벡터 캐시 키의 대응을 기록한 목록입니다. 인덱스를 어떻게 구성했는지 재현하고 변경 범위를 판단하는 근거가 됩니다.
원리 더 알아보기 — 모델 후보와 평가 기준
모델 후보를 읽는 순서
첫째, 문서와 질문의 언어가 지원 범위에 있는지 봅니다. 둘째, 최대 입력 길이가 현재 청크의 토큰 길이를 수용하는지 확인합니다. 셋째, 문서와 질의에 서로 다른 접두사나 프롬프트가 필요한지 모델 카드를 읽습니다. 넷째, 차원과 실행 위치, 라이선스, API 단가를 기록합니다. 마지막으로 한국어 질의셋에서 검색 결과를 측정합니다. 앞의 네 조건은 실행 가능한 후보를 고르는 기준이고, 마지막 측정은 실제로 사용할 한국어 문서와 질문에 맞는 후보를 판단하는 기준입니다.

영어 시험 점수가 한국어 업무 문서의 검색 결과를 보장하지 않는 이유
MTEB는 모델·과제·언어별 평가를 모으는 평가 모음입니다. 종합 점수 한 줄에는 여러 언어와 분류·검색·군집화 같은 서로 다른 과제가 섞일 수 있습니다. 영어 검색 과제에서 높은 모델이 한국어 사내 규정의 조사·고유명사·표현 변형에서도 같은 순위를 유지한다는 보장은 없습니다. 리더보드를 사용할 때는 Korean retrieval 과제를 별도로 보고, 최종 결정은 이 과정의 한국어 질문과 정답 문서로 측정합니다.

인덱스 구성 기록표에는 원문 해시, 사용한 파서와 공백·줄바꿈·문자 표기를 정리한 방법의 버전, 청킹 방식과 크기·오버랩, 청크 ID, 각 청크가 참조하는 벡터 캐시 키를 적습니다. 청킹 설정이 바뀌면 청크의 순서와 ID 대응이 달라지므로 인덱스는 다시 구성합니다. 그러나 새 인덱스를 구성한다는 말이 모든 벡터 API를 다시 호출한다는 뜻은 아닙니다. 새로 생기거나 텍스트가 바뀐 청크만 캐시 미스로 계산합니다.
같은 문서를 두 번 요청하기
처음에는 비어 있는 임시 폴더를 사용합니다. 문장 목록을 첫 번째로 요청하면 문서 벡터가 저장됩니다. 두 번째로 같은 목록을 요청한 뒤 파일 수와 벡터를 비교합니다. 파일 수가 유지되고 벡터가 같다는 출력만으로 외부 호출 횟수를 직접 측정했다고 표현하지 않습니다. 아래 차원 실습에서는 같은 캐시 이름이 실제로 오래된 벡터를 반환하는 현상을 따로 확인합니다.

실행 예제
먼저 문장 하나를 임베딩하고 앞의 다섯 값과 벡터 길이를 확인합니다. 다음에는 문장 목록의 개수와 반환된 벡터 개수를 비교합니다. 같은 문장과 모델에서 차원만 256에서 128로 바꾸어 반환 벡터의 길이도 확인합니다. 마지막으로 같은 문서를 두 번 요청해 캐시 파일 수와 반환값을 관찰합니다. 임시 폴더는 이번 실행을 위한 것이므로 다시 시작하면 새 캐시로 비교합니다.
확인할 점
— 문장 목록을 기본 설정으로 변환하면 문장 수와 벡터 수는 같고 각 벡터의 길이는 256입니다. 같은 입력을 두 번 요청하면 반환 벡터는 같고 캐시 파일 수는 유지됩니다. 이 두 출력은 외부 호출 횟수의 직접 측정값이 아닙니다.

주의할 점과 실무 메모
최종 모델은 미정입니다.
이 절의 small·large API 후보와 두 오픈 모델은 비교 틀을 보여 줍니다. 한국어 검색 지표와 운영 조건을 확인하기 전에는 하나를 정본으로 선언하지 않습니다.
입력 규칙을 모델 카드에서 확인합니다.
문서와 질의 접두사, 최대 길이, 공백·줄바꿈·문자 표기를 정리하는 방법이 모델마다 다릅니다. 예를 들어 모델마다 요구하는

표시가 다르면, 각 모델 설명서에 맞게 입력을 준비한 뒤 비교해야 합니다.
가격에는 확인일을 붙입니다.
API 단가는 바뀔 수 있습니다. 로그에는 실제 입력 토큰 합계와 단가, 통화, 확인일을 함께 남깁니다.
캐시에 원문을 저장하는 문제.
캐시 파일에 벡터만 저장해도 키 생성 과정에서 원문 해시를 사용합니다. 민감 문서라면 캐시 경로의 접근 권한과 보존 기간을 별도로 정합니다.
8
정리와 다음 절
임베딩 후보는 언어·입력 길이·차원·접두사·정확한 모델 버전·비용을 확인한 뒤 정답 문서가 표시된 한국어 질문 모음으로 측정합니다.
영어 또는 종합 벤치마크의 순위는 한국어 업무 문서 검색 순위를 보장하지 않습니다.
벡터 캐시 키와 인덱스 구성 기록표를 분리하면 인덱스를 다시 구성하면서도 정확히 같은 청크의 벡터를 재사용할 수 있습니다.
다음 학습과 이어지는 지점
— 다음 절은 한 설정으로 검색을 끝까지 실행한 뒤 청크 크기만, 그다음 임베딩 모델만 바꿉니다. 검색 결과를 관찰하는 연습을 마친 뒤 Ch 11에서 정답 질의셋과 품질 지표를 배웁니다.
9
복습 문제
문제 4개 · 해설 포함
1. 문장 세 개를 256차원으로 임베딩하면 벡터 개수와 각 벡터의 길이는 얼마입니까?
벡터는 세 개이고 각각 256개의 숫자를 담습니다. 입력 문장 수와 벡터 길이는 서로 다른 값입니다.
2. 캐시를 비교할 때 빈 임시 폴더부터 사용하는 이유는 무엇입니까?
이전 실습의 저장 파일이 남아 있으면 첫 요청부터 기존 벡터를 사용할 수 있습니다. 비어 있는 상태로 시작해야 저장 전후의 변화를 관찰할 수 있습니다.
3. 모델 이름은 같지만 차원을 바꿨습니다. namespace도 바꾸어야 하는 이유는 무엇입니까?
서로 다른 차원으로 만든 벡터를 구분하기 위해서입니다. 같은 입력이어도 차원 설정이 다르면 이전 벡터를 그대로 사용하면 안 됩니다.
4. 영어 벤치마크 순위가 높은 모델을 한국어 업무 문서에도 바로 선택할 수 있습니까?
언어와 문서, 질문의 표현과 길이, 자주 묻는 내용이 다르므로 바로 선택할 수 없습니다. 해당 한국어 질문과 정답 문서로 검색 품질을 측정해야 합니다.
