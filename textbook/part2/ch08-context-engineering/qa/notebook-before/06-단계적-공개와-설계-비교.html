2왜 지금 이것인가

05절에서 긴 입력이 허용 범위 안에 있더라도 필요한 근거를 항상 같은 품질로 활용한다고 가정할 수 없음을 확인했습니다. 대응 방법은 창을 더 크게 만드는 데만 있지 않습니다. 처음에는 문서의 식별자와 짧은 설명만 보고, 현재 요청에 필요한 문서의 본문을 그때 읽을 수 있습니다. 이러한 정보 제시 방식을 단계적 공개라고 합니다.

단계적 공개는 화면 설계에서 오랫동안 사용한 개념이지만, 컨텍스트 엔지니어링에서는 모델이 처음부터 모든 세부 내용을 받지 않도록 하는 입력 설계로 적용할 수 있습니다. Anthropic의 Agent Skills 설명은 스킬 이름과 설명, 본문, 연결 파일을 단계별로 여는 사례를 제시합니다. 컨텍스트 엔지니어링 글도 파일 경로와 링크 같은 가벼운 식별자를 유지하고 필요한 자료를 실행 시점에 불러오는 방식을 권합니다.

이 절에서는 에이전트를 만들지 않습니다. 모델이 어떤 문서를 읽을지 판단하거나 도구를 호출하지도 않습니다. 학생이 질문과 문서 ID의 대응을 코드에 적고, 고정된 파이썬 함수가 목록을 보여 준 뒤 지정된 본문 하나를 읽습니다. Ch 9에서는 사람이 정한 대응을 검색이 자동화합니다. 두 단계의 경계를 분명히 알아야 “선택”과 “에이전트 판단”을 같은 것으로 오해하지 않습니다.

3선수 지식 되짚기

  • Write — 자세한 본문을 창 밖의 파일이나 변수에 보관합니다. 단계적 공개는 기록을 삭제하지 않고 처음 입력에서 제외합니다.
  • Select — 현재 질문과 관련된 기록만 컨텍스트 안으로 가져옵니다. 이 절에서는 학생이 지정한 문서 ID를 함수가 읽습니다.
  • Compress — 원문 전체 대신 짧은 요약을 사용할 수 있습니다. 다만 조건, 예외, 출처가 사라질 수 있으므로 원문 보존 여부를 따로 평가합니다.
  • Context rot 실험 — 입력 길이, 근거 위치, 반복 조건을 기록했습니다. 같은 기록 형식을 사용해 세 입력 설계를 비교합니다.

4핵심 개념

비유 — 도서관의 목록과 서가

도서관에서 질문 하나에 답하려고 모든 책을 책상에 쌓지 않습니다. 먼저 목록에서 제목, 주제, 청구기호를 확인합니다. 필요한 책을 정한 다음 서가에서 그 책을 가져와 관련 쪽을 읽습니다. 목록은 얕고 넓은 정보이며, 본문은 깊고 좁은 정보입니다. 단계적 공개는 이 두 수준을 분리합니다.

목록만으로 최종 답을 만들 수는 없습니다. 목록은 어느 본문을 읽을지 결정하는 데 필요한 최소 정보입니다. 본문을 읽은 뒤에는 답의 근거가 되는 문장이 입력에 있어야 합니다. 따라서 단계적 공개의 성공 기준은 토큰 감소 하나가 아닙니다. 필요한 근거를 보존하면서 불필요한 내용을 줄였는가를 함께 봐야 합니다.

정의

단계적 공개 (progressive disclosure)
처음에는 식별자와 짧은 설명 같은 얕은 정보를 제공하고, 요청에 필요할 때 해당 본문처럼 더 자세한 정보를 여는 방식입니다.
요약 목록 (summary catalog)
문서 ID, 제목, 한 줄 설명을 모은 목록입니다. 본문 선택을 돕지만 최종 답의 근거를 대신하지 않습니다.
전체 입력 (full context)
후보 문서의 본문을 모두 한 번에 프롬프트에 포함하는 설계입니다. 선택 과정은 없지만 무관한 정보와 입력 토큰이 늘 수 있습니다.
선택 입력 (selected context)
현재 질문에 필요하다고 지정한 원문 본문만 프롬프트에 포함하는 설계입니다. 이 절에서는 사람이 정한 ID와 고정 함수로 만듭니다.
압축 입력 (compressed context)
원문 대신 짧게 줄인 내용을 프롬프트에 포함하는 설계입니다. 토큰을 줄일 수 있지만 예외 조건과 출처가 손실될 수 있고, 모델로 압축하면 별도 호출 비용이 생깁니다.

고정 함수로 구현하는 세 단계

이 절의 실행 흐름은 세 단계로 고정합니다. 첫째, progressive_disclosure()가 쪽별 문서 ID와 출처로 이루어진 목록을 구성합니다. 둘째, 학생 코드가 필요한 ID E01-p3을 명시합니다. 셋째, select_documents()가 전체 레코드에서 지정된 ID의 원문을 반환합니다. 모델은 마지막에 완성된 컨텍스트와 질문을 받아 답만 만듭니다. 문서 ID를 고르는 코드가 모델 출력에 의존하지 않으므로 에이전트가 아닙니다.

이 구조는 Ch 9의 Select와 직접 이어집니다. Ch 9에서는 문서가 많아져 사람이 ID를 지정하기 어려워지므로 질문과 가까운 문서 조각을 검색합니다. 검색이 선택을 자동화하지만, 어떤 문서를 몇 개 가져오고 어떤 순서로 프롬프트에 넣을지는 여전히 학생이 코드로 정합니다. 모델이 검색 도구를 선택하고 호출하는 단계는 Ch 20 이후입니다.

세 응답의 원문 비교

full

회원 한 사람이 한 번에 일반 도서 7권까지 빌릴 수 있고, 대출 기간은 14일입니다. 대출 기간은 다른 이용자의 예약이 없는 경우에 한해 1회 7일 연장할 수 있으며, 반납 예정일 전에 앱, 홈페이지, 전화로 신청해야 합니다. [E01 p.3]

selected

일반 도서는 한 번에 **7권까지** 빌릴 수 있고, 대출 기간은 **14일**입니다.  
연장은 **다른 이용자의 예약이 없는 경우에 한해 1회, 7일 연장**할 수 있으며, **반납 예정일 전에 앱·홈페이지·전화(032-000-1998)로 신청**해야 합니다. [E01 p.3]

compressed

도서는 1인 기준 최대 7권까지 14일 동안 대출할 수 있습니다. 다른 이용자의 예약이 없고 반납 예정일 전에 신청하면 1회에 한해 7일 연장할 수 있습니다. [E01 p.3]

이번 full 호출에는 1,792개의 캐시 입력 토큰이 적용되어, 입력이 더 짧은 selected보다 비용 추정치가 낮았습니다. 입력 토큰 감소와 실제 적용 단가를 분리하여 읽어야 합니다. 캐시가 없는 첫 호출끼리 비교하거나 캐시 여부를 별도 열에 기록해야 설계의 비용 차이를 해석할 수 있습니다.

목록에는 쪽별 식별자와 출처만 들어 있습니다. 이번 예제는 학생이 원문을 읽고 p.3을 지정하는 선택 연습이며, 제목에서 답을 자동으로 찾는 검색기는 구현하지 않습니다. progressive_disclosure()는 PDF 전체를 로컬에서 읽은 뒤 목록과 선택 결과를 분리하므로 파일 읽기 비용을 줄이는 지연 로딩까지 구현한 것은 아닙니다. 줄어드는 것은 모델에 전달하는 자료의 범위입니다. 실제 지연 로딩은 목록을 미리 저장하고 선택한 파일의 본문을 나중에 읽도록 확장할 수 있습니다.

확인할 점 — selected의 토큰이 적다는 사실만으로 설계가 더 좋다고 결론 내리지 않습니다. 정답에 필요한 조건과 출처가 원문 그대로 포함되었는지 확인합니다. 현재 compressed는 고정 함수가 조립하므로 추가 API 비용이 없습니다. 모델로 압축문을 만드는 다른 설계에서는 전체 비용에 압축 호출을 합쳐야 하며, 검증하여 저장한 압축문을 여러 번 재사용하는 경우와 질문마다 새로 압축하는 경우도 구분합니다.

6일부러 실패해 보기

실패 실습 1 — 목록만으로 답합니다. 제목과 한 줄 설명에 답과 비슷한 단어가 있다는 이유로 본문을 읽지 않고 최종 답을 만듭니다. 목록은 선택을 위한 정보이므로 세부 조건과 예외를 담지 않습니다. 목록에서 ID를 정한 뒤 원문을 읽는 두 번째 단계를 복원합니다.

실패 실습 2 — selected에서 정답 문서를 제외합니다. 질문과 문서 ID의 대응표를 의도적으로 잘못 지정합니다. 입력 토큰은 줄지만 필요한 근거가 없어집니다. 이 결과는 단계적 공개 자체의 실패라기보다 선택 규칙의 실패입니다. Ch 9에서는 검색 결과에 정답 문서가 포함되었는지 측정해야 같은 문제를 진단할 수 있습니다.

실패 실습 3 — 압축문에서 예외를 삭제합니다. “매주 월요일 휴관, 공휴일이 월요일이면 다음 날도 휴관”이라는 원문을 “월요일 휴관”으로만 줄입니다. 일반 질문에는 맞을 수 있지만 공휴일 다음 날을 묻는 질문에는 근거가 부족합니다. 토큰 감소와 근거 보존을 별도 열에 기록해야 하는 이유입니다.

실패 실습 4 — 압축 비용을 제외합니다. compressed 조건의 답변 호출만 비용표에 넣어 가장 저렴하다고 보고합니다. 질문마다 모델로 압축문을 새로 만들었다면 압축 호출도 설계 비용입니다. 답변 비용, 압축 비용, 합계를 구분하여 표를 수정합니다.

7주의할 점과 실무 메모

  • 단계적 공개가 언제나 빠르거나 저렴한 것은 아닙니다. 목록 확인, 본문 읽기, 압축 생성이 추가 단계가 되며 잘못된 선택은 재호출을 유발합니다. 사용 패턴과 재사용 횟수를 함께 봅니다.
  • 요약은 원문을 완전히 보존하지 않습니다. 수치, 부정 표현, 적용 기간, 예외, 출처를 우선 확인합니다. 중요한 결정에는 원문 링크나 문서 ID를 남깁니다.
  • 모델과 프롬프트를 고정합니다. 세 설계를 비교하면서 답변 모델이나 지시를 바꾸면 입력 설계의 영향을 구분할 수 없습니다.
  • 선택 규칙을 숨기지 않습니다. 이 절에서는 질문과 문서 ID의 대응을 코드에 명시합니다. Ch 9의 검색과 비교할 수 있도록 어떤 ID를 왜 선택했는지 기록합니다.
  • 에이전트라는 표현을 사용하지 않습니다. 함수 호출 순서와 문서 ID가 코드에 고정되어 있고 모델이 흐름을 바꾸지 않습니다. 에이전트는 Ch 20 ToolNode부터 다룹니다.
  • 한국어 문서의 조건 표현을 보존합니다. “이상”, “미만”, “다만”, “부칙”, “시행일”을 압축 과정에서 삭제하면 적용 범위가 달라질 수 있습니다.

8정리와 다음 절

  • 단계적 공개는 요약 목록에서 시작해 현재 요청에 필요한 본문만 읽는 입력 설계입니다.
  • full, selected, compressed는 입력 토큰뿐 아니라 정답 근거와 예외 조건의 보존 여부를 함께 비교해야 합니다.
  • 이 절의 선택은 학생이 지정한 문서 ID와 고정 함수가 수행하며, 모델이 도구나 흐름을 결정하지 않습니다.

다음 학습과 이어지는 지점 — Ch 9에서는 Select를 검색으로 자동화하여 문서가 많을 때 필요한 조각을 가져옵니다. Ch 11에서는 정답 문서 ID와 품질 지표로 선택 및 답변 결과를 평가합니다. Ch 19에서는 비슷한 도구 설명이 선택에 주는 Confusion을 다시 확인합니다. Ch 22에서는 Compress와 Isolate를 장기 실행 흐름에 적용하며, 요약의 근거 보존과 작업별 컨텍스트 분리를 다룹니다.

9복습 문제

문제 4개 · 해설 포함

[하] 1. 단계적 공개의 세 단계를 도서관 목록 비유에 맞추어 쓰세요.

정답·해설 — 문서 ID·제목·한 줄 설명의 목록을 확인하고, 질문에 맞는 ID를 정한 뒤, 해당 문서의 원문 본문을 읽습니다. 오답 학습 연결 — 목록만 보고 답한다고 썼다면 요약 목록이 선택을 돕고 본문을 대신하지 않는다는 정의를 다시 확인합니다.

[중] 2. selected가 full보다 입력 토큰이 적었습니다. selected가 더 좋은 설계라고 결론 내리기 전에 확인할 항목 두 가지는 무엇입니까?

정답·해설 — 정답에 필요한 문서와 근거 문장이 선택 입력에 포함되었는지, 답이 핵심 조건과 출처를 보존했는지 확인해야 합니다. 오답 학습 연결 — 비용만 언급했다면 토큰 절약과 근거 보존을 함께 보는 비교표를 다시 확인합니다.

[중] 3. compressed 조건의 총비용을 계산할 때 답변 호출 외에 확인할 비용은 무엇입니까?

정답·해설 — 모델을 사용해 압축문을 만들었다면 압축 호출의 입력·출력 토큰 비용을 별도로 더해야 합니다. 저장된 압축문을 재사용했는지, 질문마다 새로 만들었는지도 구분합니다. 오답 학습 연결 — 답변 호출만 계산했다면 실행 예제의 비용 구분 원칙을 다시 적용합니다.

[상] 4. 질문이 두 문서의 규정 차이를 비교하도록 요구합니다. full, selected, compressed를 어떻게 구성하고 어떤 기준으로 평가할지 설계하세요.

정답·해설 — full에는 후보 전체, selected에는 비교 대상 두 문서의 관련 원문, compressed에는 두 문서의 수치·시점·예외·출처를 보존한 요약을 넣습니다. 같은 모델과 프롬프트로 실행하고 입력 토큰, 두 문서의 핵심 사실 포함 여부, 차이 설명의 정확성, 근거 밖 주장, 압축 비용을 비교합니다. 오답 학습 연결 — selected에 한 문서만 넣었다면 복수 근거 질문에서 선택 범위를 정하는 방법을 다시 검토합니다.

10강사 노트

시간 배분 · 시연 순서 · 예상 질문 · 막히는 지점 · A/B 트랙

시간 배분(강의 60분 · 실습 60분) — 강의: 도서관 목록 비유와 정의(15분) · 요약 목록→본문 흐름 도식(15분) · full·selected·compressed 비교 기준(20분) · Ch 9와 에이전트 경계(10분). 실습: 세 입력 구성(20분) · 같은 질문으로 실행(15분) · 토큰·근거 보존·비용 표 작성(15분) · 실패 실습과 결론 작성(10분).

시연 순서 — ① progressive_disclosure()로 쪽별 문서 ID와 출처 목록을 출력합니다. ② 학생 코드에 명시된 E01-p3을 확인하고 select_documents()가 반환한 원문을 표시합니다. ③ 전체 원문, 선택 원문, 압축문을 나란히 표시합니다. ④ 모델과 프롬프트를 고정한 채 세 조건을 실행합니다. ⑤ 압축문에서 예외 한 줄을 삭제한 결과를 보여 줍니다. ⑥ Ch 9의 검색이 ID 선택을 자동화하는 지점을 도식에 표시합니다.

예상 질문 — “목록에서 모델이 ID를 고르면 에이전트인가요?” → 이 절에서는 모델이 고르지 않으며, 모델 선택을 흐름 제어에 사용하는 구조는 Ch 20 이후라고 답합니다. “selected가 항상 가장 좋은가요?” → 선택 규칙이 틀리거나 여러 문서를 함께 봐야 하는 질문에서는 필요한 근거를 제외할 수 있다고 답합니다. “압축문은 한 번만 만들면 되나요?” → 문서가 안정적이고 검증된 압축문을 재사용할 수 있지만 원문 버전이 바뀌면 함께 갱신해야 한다고 답합니다.

학생이 자주 막히는 지점 — summary catalog의 한 줄 설명에 답을 모두 넣어 본문 읽기 단계가 무의미해집니다. 목록은 선택에 충분한 최소 정보로 제한합니다. selected를 만들 때 관련 문단이 아니라 단어 하나만 잘라 조건이 사라지는 경우에는 문단 경계를 유지하게 합니다.

A/B 트랙 — A트랙은 제공된 문서 ID 대응표로 세 설계를 비교합니다. B트랙은 복수 문서 질문을 추가하고, 압축문을 한 번 생성해 재사용하는 경우와 질문마다 생성하는 경우의 누적 비용이 어떻게 달라지는지 계산합니다.
