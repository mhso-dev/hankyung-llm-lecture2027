  • 이 절을 마치면 잘못된 정보, 무관한 정보, 비슷한 대상, 서로 맞지 않는 규정이 답에 어떤 오류를 만들 수 있는지 설명할 수 있습니다.
  • 이 절을 마치면 하나의 오답에 두 가지 이상의 문제가 함께 나타날 수 있음을 사례에서 확인할 수 있습니다.

2이 내용을 배우는 이유

앞 절에서는 컨텍스트를 구성하는 원칙을 배웠습니다. 필요한 정보를 외부 파일에 기록하고(Write), 현재 질문에 맞는 정보를 고르고(Select), 긴 내용을 줄이고(Compress), 서로 다른 작업을 분리합니다(Isolate). 이제 반대 방향에서 살펴볼 차례입니다. 어떤 정보를 넣었을 때 답이 틀리는지 살펴보면, 앞에서 배운 네 방법을 언제 쓸지 판단할 수 있습니다.

Poisoning, Distraction, Confusion, Clash는 업계가 공통으로 정한 공식 오류 이름이 아닙니다. LangChain 팀이 Drew Breunig의 글을 인용하여 여러 실패 사례를 설명할 때 소개한 이름입니다. 네 이름 중 하나만 골라야 하는 것도 아닙니다. 예를 들어 긴 회의록 때문에 중요한 문장을 놓치면서, 이름이 비슷한 다른 기관의 규정까지 답에 섞일 수 있습니다. 이때는 Distraction과 Confusion을 함께 기록합니다. 다만 이름을 붙였다고 해서 모델이 왜 그런 답을 했는지까지 알 수 있는 것은 아닙니다. 입력과 실제 답을 함께 살펴봐야 합니다.

이 구분은 다음 학습의 준비이기도 합니다. Ch 9에서는 Select를 검색으로 자동화합니다. 검색이 관련 없는 문서를 가져오면 Distraction이나 Confusion이 나타날 수 있습니다. Ch 19에서는 모델이 읽는 도구 설명이 서로 비슷할 때 Confusion을 다시 다룹니다. 지금은 에이전트와 검색을 사용하지 않고, 고정된 파이썬 코드로 기준 입력과 네 실패 조건을 구성하여 결과를 비교합니다.

3앞에서 배운 내용

  • Write — 다음 호출에 쓸 결정과 사실을 외부 파일에 기록합니다. 잘못된 정보까지 기록하면 이후 호출에서 반복 사용될 수 있습니다.
  • Select — 현재 질문과 관련된 문서 조각만 고릅니다. 관련 없는 조각이나 다른 기관의 문서를 고르면 답의 근거가 흐려집니다.
  • Compress — 긴 내용을 줄이면서 결정, 수치, 출처를 남깁니다. 요약 과정에서 조건이 빠지면 원문과 다른 주장처럼 사용될 수 있습니다.
  • Isolate — 목적이 다른 자료 묶음을 분리합니다. 고객 문의 자료와 내부 코드 검토 자료를 한 입력에 섞지 않는 것이 이 장의 범위입니다.

앞 절에서 사용한 컨텍스트 조립 방식도 다시 사용합니다. 시스템 지시, 질문, 선택한 문서 조각을 일정한 순서로 문자열에 배치합니다. 달라지는 것은 문서 조각의 구성뿐입니다. 모델, 질문, 시스템 지시는 고정해야 어느 입력 차이가 결과에 영향을 주었는지 비교할 수 있습니다.

4핵심 개념

비유 — 여러 사람이 함께 쓰는 인수인계 노트

고객지원팀이 한 권의 인수인계 노트를 사용한다고 가정합니다. 첫 담당자가 휴관일을 잘못 적으면 다음 담당자도 그 기록을 사실로 사용합니다. 이것이 Poisoning과 닮았습니다. 질문과 무관한 회의 기록이 수십 쪽 붙어 있으면 필요한 한 줄을 찾기 어려워집니다. 이것은 Distraction에 해당합니다. 이름이 비슷한 두 기관의 안내문이 섞이면 다른 기관의 규정을 현재 기관의 규정으로 잘못 적용할 수 있습니다. 이것은 Confusion입니다. 같은 기관의 구 규정과 신 규정이 날짜 표시 없이 함께 있으면 어느 문장을 따라야 할지 판단하기 어렵습니다. 이것은 Clash입니다.

인수인계 노트의 사례처럼 한 사례에 여러 문제가 겹칠 수 있습니다. 잘못 저장된 정보가 다른 기관의 문서에서 왔다면 Poisoning과 Confusion을 함께 확인합니다. 오래된 규정을 잘못 요약해 다음 호출에서 다시 썼다면 Poisoning과 Clash를 함께 확인합니다. 아래 표에서는 이름 하나를 고르지 말고, 해당하는 질문을 모두 확인합니다.

정의

컨텍스트 오염 (context poisoning)
이전 답이나 저장한 메모에 틀린 내용이 들어 있고, 그 내용을 다음 질문에 다시 넣어 사실처럼 사용하는 문제입니다. 공격자가 정보를 바꾼 경우에만 쓰는 말이 아닙니다. 모델이 지어낸 내용, 사람이 잘못 입력한 값, 오래된 요약도 원인이 될 수 있습니다.
컨텍스트 산만화 (context distraction)
현재 질문과 관계없는 내용이 많이 들어가서 모델이 중요한 지시나 근거를 놓치는 문제입니다. 문장 자체가 모두 사실이어도 이번 질문에 필요하지 않으면 답을 방해할 수 있습니다.
컨텍스트 혼동 (context confusion)
이름이나 설명이 비슷한 두 대상이 함께 들어가서, 모델이 다른 대상을 고르거나 두 대상의 내용을 섞는 문제입니다. 예를 들어 미르시립도서관 질문에 미르시립자료관 규정이 섞일 수 있습니다.
컨텍스트 충돌 (context clash)
입력 안에 서로 맞지 않는 지시나 사실이 있는데, 어느 출처가 최신인지 또는 무엇을 먼저 따라야 하는지 표시되지 않은 문제입니다. 예를 들어 같은 휴관일이 월요일과 화요일로 함께 적혀 있는 경우입니다.
출력에서 확인한 증거 (observational evidence)
모델의 실제 답에서 잘못된 요일, 다른 기관명, 서로 맞지 않는 문장처럼 직접 확인한 내용입니다. 실패가 나도록 입력을 만들었다는 사실만으로는 모델이 실제로 실패했다고 말할 수 없습니다.

문제 이름입력에서 확인할 것출력에서 확인할 것먼저 할 일
Poisoning이전 출력이나 메모의 잘못된 주장이 다시 들어갔는가같은 잘못이 후속 답에서 사실처럼 반복되는가어디에서 가져왔는지와 사실을 확인했는지 따로 적습니다.
Distraction질문과 무관한 긴 내용이 추가되었는가핵심 근거를 놓치거나 무관한 내용을 길게 답하는가현재 과제에 필요한 조각만 선택합니다.
Confusion이름이나 설명이 비슷한 다른 대상이 함께 있는가기관명, 제품명, 규정을 다른 대상과 섞는가기관 ID와 출처를 적고 서로 다른 기관의 자료를 나눕니다.
Clash서로 다른 지시나 사실이 함께 있는가한쪽을 임의로 고르거나 모순된 내용을 동시에 답하는가시점, 출처, 우선순위 규칙을 추가합니다.

Distraction과 Confusion의 차이는 정보량만으로 결정되지 않습니다. 무관한 회의록이 길어서 핵심 문장을 찾기 어려워졌다면 Distraction을 의심합니다. 다른 기관의 규정이 짧더라도 현재 기관의 규정처럼 답에 사용되었다면 Confusion을 확인합니다. Clash도 단순히 숫자가 두 개 있다는 뜻이 아닙니다. 서로 다른 조건에 적용되는 두 값이라면 충돌이 아닐 수 있습니다. 적용 조건이 같은데 값이 다르거나, 우선순위가 필요한데 표시가 없을 때 충돌로 진단합니다.

비교 조건 이름과 실제 실패를 구분하기

conditions의 키인 poisoning이나 clash는 개발자가 입력에 붙인 이름입니다. conditions.items()로 이름과 내용을 하나씩 읽어 같은 질문에 넣고, 반환된 AIMessage를 results[name]에 저장합니다. 딕셔너리의 키가 오류 진단 결과를 자동으로 만드는 것은 아닙니다. 실제 답이 잘못된 문장을 사용했는지 별도로 읽어야 합니다.

예를 들어 배송 안내에 “일반 배송은 3일, 도서 지역은 5일”이 있으면 숫자가 달라도 적용 지역이 달라 충돌하지 않습니다. 같은 지역·같은 배송 조건에 3일과 5일이 동시에 적혀 있고 시행일도 없다면 충돌 여부를 확인해야 합니다. 값의 차이를 발견한 뒤 대상과 조건이 같은지 확인하는 순서가 중요합니다.

뒤의 날짜 선택은 모든 규정에 통용되는 해결책이 아닙니다. 같은 업무의 새 규정이 이전 규정을 대체한다는 실습 가정 아래, 기준일 전에 시행된 후보에서 가장 늦은 날짜를 고릅니다. max(eligible, key=effective_date)에서 key는 비교할 값을 꺼내는 함수입니다. 후보가 비어 있으면 max()가 값을 고를 수 없으므로 실제 서비스에서는 후보 없음도 별도로 처리해야 합니다.

각 조건은 정상 입력인 clean을 그대로 두고, 잘못된 메모·무관한 문장·비슷한 기관·상충 규정 중 하나만 더합니다. 조건 이름과 실제로 추가한 문장을 함께 읽습니다.

3. 같은 질문으로 다섯 조건을 실행합니다

어떤 실패가 나타날지 미리 정하지 않습니다. 조건 이름, 실제 입력 토큰, 응답 원문을 나란히 기록합니다.

conditions.items()는 조건 이름과 입력 내용을 쌍으로 제공합니다. results[name] = response는 해당 이름에 실제 응답 객체를 저장합니다. 이름은 개발자가 붙인 실험 조건이며 모델 오류를 자동 진단한 값이 아닙니다.

일반 배송 3일과 도서 지역 배송 5일은 적용 조건이 다릅니다. 같은 조건에 서로 다른 값이 있을 때 충돌을 검토합니다. 이처럼 입력에서 의심할 문제와 실제 출력에서 확인한 오류를 나누어 기록합니다.

In [6]:
# items()는 조건 이름과 근거를 한 쌍씩 반환하며 모든 조건에 같은 질문을 적용합니다.
# results에는 조건별 AIMessage를 저장하고, usage에서 실제 입력 토큰 수를 읽습니다.
results = {}
for name, context in conditions.items():
    messages = [
        ("system", "근거만 사용하고, 충돌하면 확인이 필요하다고 답하세요."),
        ("user", f"""근거:
{context}

질문: 미르시립도서관의 정기 휴관일은 언제인가요?"""),
    ]
    response = model.invoke(messages)
    usage = response.usage_metadata
    if usage is None:
        raise RuntimeError("모델 사용량 메타데이터가 없습니다.")
    results[name] = response
    print(f"\n[{name}] input_tokens={usage['input_tokens']}")
    print(response.text)

출력:
[distraction] input_tokens=285

출력:

for name, response in results.items():

6일부러 실패해 보기

Before에서는 월요일 하루만 휴관한다는 규정과 화요일 하루만 휴관한다는 규정을 같은 질문과 함께 모델에 전달합니다. 시행일이 없어 확인이 필요하다는 답이 나오면, 모델이 잘못 선택한 것은 아니지만 현재 자료로 답을 확정할 수는 없습니다. After에서는 시행일을 확인했다는 실습 상황을 추가합니다. 같은 업무의 새 규정이 이전 규정을 대체한다고 가정하고 최신 규정을 선택한 뒤, 같은 질문으로 다시 호출합니다. 날짜를 임의로 추측하여 충돌을 해결하는 방법으로 이해하지 않도록 주의합니다.

앞의 실행 예제를 실행한 같은 노트북에서 Before 다음 After 순서로 실행합니다. 출력은 실제 실행 결과입니다.

Before — 실패 코드

실패 재현: 상충 규정의 시행일을 기록하지 않습니다

월요일 하루만 휴관한다는 규정과 화요일 하루만 휴관한다는 규정을 함께 전달합니다. 질문 날짜는 같지만 규정의 시행일이 없어 어느 쪽을 적용할지 알 수 없습니다.

In [9]:
# 비교할 날짜와 질문을 먼저 고정합니다.
as_of = "2026-09-08"
question = f"{as_of} 기준 미르시립도서관의 정기 휴관일은 언제인가요?"
# 두 호출 모두 같은 규칙을 사용합니다. 모르는 날짜를 추측하지 않게 합니다.
answer_rule = "근거만 사용하고 출처를 표시하세요. 규정이 충돌하고 시행일을 알 수 없으면 확인이 필요하다고 답하세요."
before_context = conditions["clash"]
print(before_context)
출력:
[E01 p.2] 미르시립도서관의 정기 휴관일은 오직 매주 월요일 하루뿐입니다.
[합성 부록] 미르시립도서관의 정기 휴관일은 오직 매주 화요일 하루뿐입니다.

같은 질문으로 실제 답을 읽습니다

임의의 오류를 내는 검사 대신 모델이 두 규정을 어떻게 설명하는지 확인합니다. 확인이 필요하다고 답했다면 잘못된 규정을 고른 실패는 관찰되지 않은 것입니다. 다만 현재 자료만으로 질문에 확정 답변을 할 수는 없습니다.

In [10]:
# 두 규정의 본문과 질문을 그대로 전달합니다.
before_prompt = f"""근거:
{before_context}

질문: {question}"""
before_response = model.invoke([
    ("system", answer_rule),
    ("user", before_prompt),
])
print(before_response.text)
출력:
근거가 서로 충돌합니다.

- [E01 p.2]에는 **정기 휴관일이 매주 월요일**이라고 되어 있습니다.
- [합성 부록]에는 **정기 휴관일이 매주 화요일**이라고 되어 있습니다.

따라서 **2026-09-08 기준 미르시립도서관의 정기 휴관일이 언제인지 확정할 수 없으며, 확인이 필요합니다.**

After — 수정 코드

수정: 확인한 시행일로 적용할 규정을 고릅니다

이 연습에서는 기관에 확인한 결과 기존 규정의 시행일은 2025-01-01, 대체 규정의 시행일은 2026-01-01이라고 가정합니다. 날짜는 실습용으로 정한 값이며 실제 기관의 규정이 아닙니다. 두 규정의 본문은 그대로 두고, 같은 업무의 새 규정이 이전 규정을 대체한다는 조건에서 기준일까지 시행된 가장 최근 규정을 선택합니다.

eligible은 기준일 전에 시행된 후보 목록입니다. max(eligible, key=effective_date)는 각 후보를 effective_date()에 넘겨 얻은 날짜 문자열을 비교합니다. 함수 이름을 넘기므로 비교할 때마다 필요한 후보의 날짜를 읽습니다. 후보가 비어 있거나 서로 다른 날짜 형식이 섞인 경우는 이 예제의 입력에 없으며 실제 처리에서는 별도 분기가 필요합니다.

In [11]:
# versioned는 같은 두 규정에 시행일만 추가한 목록이고 as_of는 질문한 날짜입니다.
# eligible에서 기준일까지 시행된 규정만 남긴 뒤 max의 key로 가장 최근 시행일을 고릅니다.
# YYYY-MM-DD처럼 자릿수가 고정된 날짜는 문자열 순서와 날짜 순서가 같습니다. 다른 형식은 날짜 객체로 바꿉니다.
versioned = [
    {"effective_date": "2025-01-01", "rule": clean, "source": "E01 p.2"},
    {"effective_date": "2026-01-01", "rule": conditions["clash"].splitlines()[-1],
     "source": "합성 부록"},
]
eligible = []
for record in versioned:
    if record["effective_date"] <= as_of:
        eligible.append(record)

def effective_date(record: dict[str, str]) -> str:
    return record["effective_date"]

selected_rule = max(eligible, key=effective_date)
assert "오직 매주 화요일 하루뿐" in selected_rule["rule"]
assert selected_rule["source"] == "합성 부록"
print("수정 후 적용 규정:", selected_rule)
출력:
수정 후 적용 규정: {'effective_date': '2026-01-01', 'rule': '[합성 부록] 미르시립도서관의 정기 휴관일은 오직 매주 화요일 하루뿐입니다.', 'source': '합성 부록'}

선택한 규정으로 같은 질문에 다시 답합니다

새 규정을 고른 결과를 근거로 넣습니다. 질문·모델·답변 규칙은 Before와 같습니다. 실제 답이 화요일과 선택한 출처를 사용하는지 확인합니다. 이는 시행일을 확인하고 선택한 효과이며, 모델 자체의 성능이 높아졌다는 뜻은 아닙니다.

In [12]:

{selected_rule['rule']}
시행일: {selected_rule['effective_date']}

    ("user", after_prompt),

print(after_response.text)

근거: “[합성 부록] 미르시립도서관의 정기 휴관일은 오직 매주 화요일 하루뿐입니다.” (시행일: 2026-01-01)

7주의할 점과 실무 메모

  • 네 이름만으로 모든 오답을 설명하지 않습니다. 이 이름들은 팀에서 문제를 확인할 때 쓰는 질문에 가깝습니다. 검색이 잘못된 문서를 가져왔는지, 지시가 부족했는지, 모델이 해당 내용을 학습하지 않았는지, 최신 자료가 빠졌는지도 따로 확인합니다.
  • Poisoning은 공격만을 뜻하지 않습니다. 사람이 잘못 입력한 수치, 오래된 회의 요약, 모델이 만든 환각을 검증 없이 저장한 경우도 포함합니다. 보안 공격은 Ch 16에서 별도로 다룹니다.
  • 한 번 정확히 답했다고 같은 문제가 다시 생기지 않는다고 결론 내리지 않습니다. 모델이 이번 한 번은 문제 문장의 영향을 받지 않았을 수 있습니다. 같은 조건을 반복하거나 입력 순서와 질문을 바꾸어 다시 확인하고, 실제로 확인한 범위까지만 기록합니다.
  • Confusion과 Clash는 출처 메타데이터로 줄일 수 있습니다. 기관 ID, 문서 버전, 시행일, 적용 대상을 입력에 표시하면 구분에 도움이 됩니다. 표시했다고 해서 모델이 언제나 올바르게 따른다는 보장은 없습니다.
  • 프롬프트에는 개인정보나 비공개 기록을 넣지 않습니다. 수업에서는 수업을 위해 만든 가상 기관 자료만 사용합니다. 실제 고객 문의나 내부 회의록을 복사하지 않습니다.

8정리와 다음 절

  • Poisoning은 잘못된 정보의 재사용, Distraction은 무관한 정보의 집중 방해, Confusion은 비슷한 대상의 구분 실패, Clash는 서로 맞지 않는 지시나 사실의 처리 문제를 살펴보는 이름입니다.
  • 네 이름은 공식 오류 코드가 아니며, 한 답에 여러 문제가 함께 나타날 수 있습니다.
  • 실패가 나도록 문제 문장을 넣은 사실과 모델 답에서 실제 오류를 확인한 사실을 따로 기록해야 합니다.

다음 학습과 이어지는 지점 — 다음 05절에서는 입력이 길어질 때 성능이 달라지는 context rot를 같은 질문과 모델을 유지한 채 입력 길이만 바꾸어 살펴봅니다. Ch 9에서는 Select가 검색으로 자동화되면서 Distraction과 Confusion이 검색 결과의 품질 문제로 다시 나타납니다. Ch 19에서는 서로 비슷한 도구 설명이 Confusion을 일으킬 수 있는 조건을 다루고, 이 절의 진단표를 도구 선택 기록에 적용합니다.

9복습 문제

문제 4개 · 해설 포함

[하] 1. 이전 호출에서 만들어진 잘못된 휴관일을 메모에 저장하고 다음 답변에 다시 사용했습니다. 우선 확인할 실패 양상과 그 이유를 쓰세요.

정답·해설 — Context Poisoning을 우선 확인합니다. 잘못된 정보가 다음 호출의 입력에 남아 사실처럼 다시 쓰였기 때문입니다. 공격자가 개입하지 않아도 이 문제가 생길 수 있습니다. Confusion이라고 답했다면 서로 비슷한 두 대상을 잘못 구분한 일도 있었는지 따로 확인합니다.

[중] 2. 질문과 무관한 긴 회의록과 이름이 비슷한 다른 기관의 안내문을 함께 넣었더니 다른 기관의 규정이 답에 포함되었습니다. 가능한 진단 두 가지를 설명하세요.

정답·해설 — 질문과 관계없는 긴 회의록 때문에 핵심 근거를 놓쳤다면 Distraction입니다. 다른 기관의 규정을 현재 기관의 규정으로 사용했다면 Confusion입니다. 두 일이 함께 나타났으므로 두 이름을 모두 기록할 수 있습니다.

[중] 3. 구 규정과 신 규정을 함께 넣었지만 모델이 시행일 확인을 요청했습니다. “Clash 실패가 발생했다”고 기록하면 왜 부정확합니까?

정답·해설 — 서로 맞지 않는 두 규정을 입력에 넣었지만, 모델은 하나를 임의로 고르지 않고 시행일을 물었습니다. 따라서 “서로 맞지 않는 규정을 입력했지만, 모델 답에서는 잘못된 선택을 확인하지 못함”이라고 기록해야 합니다. 문제를 일으키려 넣은 문장과 실제 답에서 확인한 오류를 구분합니다.

[상] 4. 한 답변이 다른 기관의 오래된 규정을 현재 기관의 최신 규정으로 인용했습니다. Poisoning, Confusion, Clash를 각각 적용할 수 있는 조건을 구분하여 쓰고, 추가로 확인할 로그를 제안하세요.

정답·해설 — 오래된 규정을 이전 메모에서 다시 가져왔다면 Poisoning입니다. 이름이 비슷한 다른 기관을 잘못 골랐다면 Confusion입니다. 최신 규정과 오래된 규정이 함께 있는데 적용 순서를 잘못 정했다면 Clash입니다. 어떤 경우인지 확인하려면 입력에 들어간 문서 ID·버전·시행일, 메모를 만든 시점, 답이 인용한 문장을 남겨야 합니다.
