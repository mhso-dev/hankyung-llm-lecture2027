1학습 목표

  • 입력이 길어졌다는 사실과 정답을 활용하는 성능이 낮아졌다는 사실을 구분할 수 있습니다.
  • 같은 질문과 근거에서 주변 문장 수만 늘려 세 길이의 입력을 만들 수 있습니다.
  • 각 길이를 세 번 호출하고 입력 토큰·실제 답·정답 확인 결과를 비교할 수 있습니다.
  • 성능 저하가 관찰되었는지 실행 결과에 근거해 설명하고, 이 작은 실험의 한계를 말할 수 있습니다.

2이 내용을 배우는 이유

04절에서는 입력에 포함된 정보가 답을 어떻게 바꾸는지 살펴보았습니다. 이번 절의 질문은 하나입니다. 같은 정답 근거를 넣었을 때, 입력이 길어지면 모델이 그 근거를 덜 정확하게 활용할까요? 이를 확인하려면 입력 토큰 수와 답의 정확성을 함께 비교해야 합니다. 토큰 수만 출력해서는 성능이 낮아졌는지 알 수 없습니다.

입력이 길어지면 모델이 그 안에서 필요한 문장을 찾고 답에 적용하는 능력이 낮아질 수 있습니다. 이 현상을 컨텍스트 로트(context rot)라고 부릅니다. 입력을 조금 늘리기만 하면 모든 질문에서 오답이 생긴다는 뜻은 아닙니다. 이 실습은 성능 저하가 일어났다고 미리 가정하지 않습니다. 길이에 따라 정답 확인 결과가 달라지는지 실제 답으로 확인합니다.

아래 코드는 하나의 휴관일 질문을 세 길이에서 반복합니다. 결과가 낮아지면 답 원문에서 어떤 오류가 생겼는지 확인합니다. 결과가 같으면 이번 조건에서는 저하를 관찰하지 못했다고 설명합니다. 두 경우 모두 실험의 결과이며, 관찰하지 않은 현상을 재현했다고 쓰지 않습니다.

3앞에서 배운 내용

  • 컨텍스트와 토큰 — 모델은 지시문과 자료, 질문을 입력으로 받습니다. 글자 수와 토큰 수는 다르며, 실제 입력 토큰은 호출 결과의 usage_metadata에서 확인합니다.
  • LangChain 모델 호출 — 앞 절에서 준비한 방식과 같은 init_chat_model()과 invoke()를 사용합니다. 응답 본문은 AIMessage.text에서 읽습니다.
  • 반복문과 딕셔너리 — 조건별 입력을 딕셔너리에 담고 반복문으로 호출합니다. 각 실행의 답과 토큰 수를 목록에 보관합니다.

4핵심 개념

입력의 양과 정답을 활용하는 성능

긴 회의록 가운데 “정기 휴관일은 월요일”이라는 문장이 있다고 생각해 봅니다. 회의록이 길어져도 그 문장은 그대로입니다. 모델이 계속 월요일이라고 답한다면, 자료가 늘었어도 이 문제의 정답은 유지한 것입니다. 긴 조건에서 화요일이라고 답하거나 필요한 정보를 찾지 못한다면, 그 실행에서는 정답 활용에 실패한 것입니다.

이 예에서는 입력 길이만 바꾸고, 모델이 정답을 맞혔는지 확인합니다. 입력이 길어서 비용이 늘어난 일, 질문을 잘못 입력한 일, 파이썬 코드가 오류로 멈춘 일은 정답 성능 저하와 다른 문제입니다. 이번 실습은 입력 길이와 정답 확인 결과만 비교합니다.

컨텍스트 로트 (context rot)
입력이 길어질 때 모델이 필요한 정보를 찾아 적용하는 성능이 낮아지는 현상입니다. 모델·과제·자료 구성에 따라 관찰 여부와 정도가 달라질 수 있습니다.
통제 조건 (controlled condition)
입력 길이의 영향만 비교하려고 바꾸지 않고 그대로 두는 항목입니다. 질문, 근거 문장, 모델, 지시문, 출력 상한, 근거를 자료 가운데에 두는 규칙을 같게 유지합니다.
반복 실행 (repeated run)
같은 입력을 다시 호출하는 것입니다. 한 번의 우연한 응답을 전체 경향으로 해석하지 않도록 각 길이를 세 번 실행합니다. 세 번은 통계적 결론을 내리기에 충분한 표본을 뜻하지 않습니다.
정답 확인 기준
코드는 답에 ‘월요일’과 출처 ‘E01 p.2’가 모두 들어 있는지 확인합니다. 이 검사는 두 문자열의 포함 여부만 판단하므로 답의 뜻까지 이해하지는 못합니다. 예를 들어 ‘월요일이 아닙니다’에도 ‘월요일’이 들어 있습니다. 따라서 자동 검사 결과와 답 원문을 함께 읽습니다.

도식 — 같은 문제에서 입력 길이만 늘려 비교하기

아래 세 상자는 모델에 보낼 입력 세 개입니다. 각 입력의 가운데에는 동일한 휴관일 근거가 있습니다. 짧은 입력에는 주변 문장을 넣지 않고, 중간 입력에는 근거 앞뒤로 같은 문장을 각각 120번, 긴 입력에는 각각 1,200번 넣습니다. 여기서 숫자는 문장 반복 수이며 토큰 수가 아닙니다.

‘가운데’는 정답 문장을 입력 자료의 앞뒤 주변 문장 사이에 둔다는 뜻입니다. 원본 PDF의 페이지 번호를 뜻하지 않습니다. 입력이 늘어나면 근거 앞의 문자 수는 늘지만, 자료 가운데에 둔다는 배치 규칙은 같습니다. 이번 실습에서 근거를 앞·가운데·뒤로 이동하는 별도 위치 실험은 하지 않습니다.

실행 전에 무엇을 고정하고 바꾸는지 확인합니다

역할이번 실습의 값
고정할 질문미르시립도서관의 정기 휴관일과 출처
고정할 근거[E01 p.2] 정기 휴관일은 매주 월요일입니다.
고정할 호출 조건같은 모델·지시문·출력 상한, 자료 가운데의 근거
바꿀 값근거 앞뒤에 붙이는 무관한 문장의 반복 수: 각 0·120·1,200회
관찰할 결과각 호출의 입력 토큰, 실제 답, 핵심어·출처 포함 여부와 답의 의미

반복 관찰을 다른 과제에 적용하기

각 길이의 호출을 세 번 실행하므로 records에는 아홉 개의 딕셔너리가 쌓입니다. rows는 그중 길이 이름이 같은 행만 골라 만든 목록입니다. sum(record["keyword_pass"] for record in rows)는 Python에서 참을 1, 거짓을 0으로 더하는 성질을 이용해 문자열 기준을 통과한 행 수를 셉니다. 답 전체의 의미를 채점한 점수와 구분합니다.

같은 방법을 회의록에서 담당자를 찾는 과제에 적용하려면 담당자 이름이 적힌 근거와 질문을 고정하고 주변 기록의 양을 바꿀 수 있습니다. 반면 두 부서의 일정 차이를 계산하는 과제는 여러 근거를 연결해야 합니다. 지금의 한 문장 찾기 결과만으로 그 과제도 같은 성능을 보인다고 예상할 수는 없습니다.

추가 실험에서는 먼저 주변 문장의 종류만 바꾸거나, 길이를 유지한 채 근거 위치만 바꾸는 식으로 비교합니다. 길이·위치·질문 난이도를 동시에 변경하면 어느 차이가 결과에 영향을 주었는지 구분하기 어렵습니다. 아래 저장 출력은 동일 문장의 반복과 가운데 근거만 시험한 결과이며, 이 추가 설계를 실제 실행한 결과는 아닙니다.

05. 입력 길이에 따라 정답을 활용하는 성능이 달라질까요?

같은 질문·정답 근거·모델을 사용하고, 근거 앞뒤의 무관한 문장 수만 늘립니다. 세 길이를 각각 세 번 호출하여 답과 입력 토큰, 정답 확인 결과를 기록합니다. 성능 저하가 나오는지는 실행 후 판단합니다. 토큰 수가 늘었다는 사실만으로 context rot가 나타났다고 결론 내리지 않습니다.

1. 실행 환경 준비

Python 3.12 커널에서 아래 셀을 순서대로 실행합니다. 프로젝트 폴더 또는 상위 폴더의 .env에 OPENAI_API_KEY를 둡니다. 이 실습은 생성 API를 총 아홉 번 호출합니다.

# %pip은 현재 노트북 커널에 패키지를 설치하는 Jupyter 전용 명령입니다.

2. 모든 조건에서 같은 문제를 사용합니다

답에 필요한 정보는 아래 근거 문장 하나에 있습니다. 모델은 휴관일과 출처를 답해야 합니다. 근거 문장과 질문을 바꾸면 문제 자체가 달라지므로 두 값을 고정합니다.

In [4]:
# evidence는 정답을 포함한 자료이며 question은 모든 실행에 사용하는 질문입니다.
evidence = "[E01 p.2] 정기 휴관일은 매주 월요일입니다."
question = "미르시립도서관의 정기 휴관일과 출처를 알려 주세요."
# note는 휴관일 답변에 필요하지 않은 주변 문장입니다.
note = "회의 준비 항목을 확인했습니다. "
print("질문:", question)
print("정답 근거:", evidence)
출력:
질문: 미르시립도서관의 정기 휴관일과 출처를 알려 주세요.
정답 근거: [E01 p.2] 정기 휴관일은 매주 월요일입니다.

3. 근거를 가운데에 두고 주변 문장 수만 바꿉니다

0·120·1,200은 근거의 각 앞뒤에 붙일 문장의 반복 수입니다. 토큰 수가 아닙니다. 실제 입력 토큰 수는 모델 호출 후 확인합니다. 근거를 입력 자료 가운데에 두는 배치 규칙은 세 조건에서 같습니다.

In [5]:
# 조건 이름과 근거 한쪽에 붙일 반복 수를 딕셔너리로 정합니다.
repeat_counts = {"short": 0, "medium": 120, "long": 1200}
prompts = {}
for name, count in repeat_counts.items():
    # 같은 문장을 근거 앞뒤에 같은 양으로 넣어 중앙 배치를 유지합니다.
    padding = note * count
    prompts[name] = f"""자료:
{padding}
{evidence}
{padding}

질문: {question}"""
    # 문자 수는 입력이 길어졌는지 미리 확인하는 값입니다.
    print(name, "문자 수:", len(prompts[name]))
출력:
short 문자 수: 68
medium 문자 수: 4388
long 문자 수: 43268

4. 비교 전에 입력 조건을 확인합니다

모든 입력에 질문과 정답 근거가 한 번씩 들어 있어야 합니다. 주변 문장에 정답을 추가하거나 근거 문장을 삭제하지 않았는지 확인합니다. 이 검사는 성능 점수가 아니라 실험에 사용할 입력의 확인입니다.

In [6]:
# 입력이 길어져도 동일한 질문과 근거가 보존되었는지 확인합니다.
for name, prompt in prompts.items():
    print(name, "근거 수:", prompt.count(evidence), "질문 수:", prompt.count(question))
    assert prompt.count(evidence) == 1
    assert prompt.count(question) == 1
# short → medium → long 순으로 실제 문자열 길이가 증가합니다.
assert len(prompts["short"]) < len(prompts["medium"]) < len(prompts["long"])
출력:
short 근거 수: 1 질문 수: 1
medium 근거 수: 1 질문 수: 1
long 근거 수: 1 질문 수: 1

5. 각 길이를 세 번 실행하고 실제 답을 읽습니다

짧음·중간·김 순서의 비교를 세 차례 반복합니다. record는 한 번 실행한 길이, 반복 번호, 답, 토큰 수를 담는 딕셔너리입니다. records는 아홉 개의 record를 차례로 모은 목록입니다. 응답의 input_tokens는 모델 제공자가 센 입력 토큰 수입니다. 아홉 번의 호출이 끝날 때까지 출력되는 답을 확인합니다.

In [7]:
# records는 나중에 같은 길이의 결과를 모으기 위한 기록 목록입니다.
records = []
for trial in range(1, 4):
    for name, prompt in prompts.items():
        # 모든 호출에 같은 모델·지시문을 사용합니다.
        result = model.invoke([
            ("system", "근거만 사용하고 출처를 표시하세요."),
            ("user", prompt),
        ])
        record = {

            "trial": trial,
            "input_tokens": result.usage_metadata["input_tokens"],
            "answer": result.text,
        }
        records.append(record)
        print(name, "반복:", trial, "입력 토큰:", record["input_tokens"])
        print(record["answer"])

7. 입력 토큰과 정답 확인 결과를 나란히 비교합니다

각 길이에서 조건을 충족한 응답 수를 셉니다. 점수가 낮아졌다면 먼저 실제 답을 다시 읽습니다. 점수가 같다면 이번 과제와 입력 범위에서는 이 기준으로 성능 저하를 관찰하지 못한 것입니다.

rows는 현재 길이 조건과 이름이 같은 기록만 고르는 목록 표현식입니다. sum()은 참을 1, 거짓을 0으로 더하여 문자열 기준 충족 횟수를 셉니다. 이번에는 길이마다 기록이 세 개이므로 분모가 3입니다. 이 값은 답 전체의 사실성을 자동 채점한 점수가 아닙니다.

회의록 담당자 찾기에도 같은 비교 방법을 적용할 수 있습니다. 여러 문서의 일정을 연결하는 과제는 필요한 추론이 달라 별도 실험이 필요합니다. 추가 실험에서 근거 위치와 길이를 동시에 바꾸면 원인을 구분하기 어려우므로 하나씩 변경합니다. 여기의 저장 출력에는 그런 추가 실험이 포함되어 있지 않습니다.

In [9]:
# rows는 같은 입력 길이 조건의 실행 기록만 모은 목록입니다.
for name in prompts:
    rows = [record for record in records if record["length"] == name]
    passed = sum(record["keyword_pass"] for record in rows)
    # 토큰 수는 세 호출의 값을 모두 보여 주어 실행 기록을 보존합니다.
    tokens = [record["input_tokens"] for record in rows]
    print(name, "입력 토큰:", tokens, "기준 충족:", passed, "/", len(rows))
출력:

medium 입력 토큰: [2224, 2224, 2224] 기준 충족: 3 / 3
long 입력 토큰: [21664, 21664, 21664] 기준 충족: 3 / 3

결과 해석

입력 토큰 증가와 정답 확인 결과를 함께 읽습니다. 모든 길이에서 정답을 유지할 수도 있습니다. 그런 결과를 성능 저하가 발생한 것처럼 표현하지 않습니다. 짧은 근거 한 문장과 반복된 주변 문장만 사용하는 작은 실험이므로, 긴 실제 문서의 모든 과제로 결론을 확대하지 않습니다. 더 복잡한 과제와 여러 질문을 사용하는 평가는 Ch 11·15에서 다룹니다.

확인할 점 — 마지막 출력의 각 행에서 입력 토큰과 기준 충족 횟수를 함께 봅니다. 토큰 수가 증가했는지 확인한 다음, 기준 충족 횟수도 달라졌는지 확인합니다. 기준 충족 횟수만 보지 말고 앞에 출력된 아홉 개의 답도 읽습니다.

긴 입력에서 기준 충족 횟수가 줄었다면 해당 답을 먼저 읽습니다. 요일을 틀렸는지, 근거를 찾지 못했는지, 출처 형식만 달라졌는지를 구분합니다. 출처 표기 한 번이 빠진 것을 곧바로 모든 정보 활용 능력의 저하로 해석하지 않습니다. 같은 문제가 더 많은 반복과 다른 질문에서도 나타나는지 추가 측정해야 합니다.

세 길이의 결과가 같다면 “이번 모델, 질문, 자료 구성, 입력 길이 범위에서는 이 기준으로 저하를 관찰하지 못했다”고 정리합니다. “입력 토큰이 늘었으므로 context rot가 발생했다”거나 “이번에 모두 맞았으므로 context rot는 없다”는 결론은 모두 실행 결과를 넘어섭니다.

7주의할 점과 실무 메모

  • 작은 실험의 범위를 지킵니다. 정답 문장이 하나이고 주변 문장은 같은 문장의 반복입니다. 실제 긴 문서에서 여러 근거를 연결하는 과제의 난이도를 대표하지 않습니다.
  • 자동 검사와 의미 판단을 구분합니다. ‘월요일이 아닙니다’에도 ‘월요일’이 들어 있습니다. 자동 확인을 통과한 답도 원문을 읽어야 합니다. 이 문자열 검사를 완전한 정확도 지표로 사용하지 않습니다.
  • 반복 세 번으로 성능 순위를 만들지 않습니다. 응답은 실행마다 달라질 수 있습니다. 여러 질문과 충분한 반복을 사용한 평가는 Ch 11·15에서 다룹니다.
  • 입력이 길어지면 호출량도 늘어납니다. 전체 실습을 다시 실행하면 아홉 번의 API 호출이 추가됩니다. 길이를 더 늘리기 전에 입력 토큰과 모델의 한도를 확인합니다.
  • 같은 위치 규칙을 유지합니다. 이번 결과는 자료 가운데에 근거를 둔 조건의 결과입니다. 다른 위치에서도 같을 것이라고 가정하지 않습니다.

8정리와 다음 절

  • context rot를 살펴보려면 입력 토큰 증가와 정답 활용 성능의 변화를 함께 확인해야 합니다.
  • 같은 질문과 근거에서 주변 문장의 양만 바꾸고, 세 길이를 각각 세 번 호출했습니다.
  • 관찰된 답과 확인 기준으로 결론을 제한합니다. 저하가 나오지 않았다면 미관찰 결과로 기록합니다.

다음 학습과 이어지는 지점 — 06절에서는 필요한 자료만 전달하는 설계를 비교합니다. 이번 결과에서 성능 저하가 나왔는지와 별개로, 각 설계가 필요한 근거를 보존하면서 입력량을 어떻게 바꾸는지 살펴봅니다. 여러 질문을 사용하는 평가와 더 정교한 채점은 Ch 11·15에서 이어집니다.

9복습 문제

문제 4개 · 해설 포함

1. 입력 토큰 수가 늘었다는 출력만으로 context rot를 관찰했다고 말할 수 없는 이유는 무엇입니까?

입력의 양만 확인했기 때문입니다. 같은 과제에서 필요한 정보를 활용하는 성능이 낮아졌는지 답도 확인해야 합니다.

2. 이번 실습에서 바꾼 값 하나와 고정한 조건 세 가지를 쓰세요.

근거 앞뒤에 넣는 주변 문장의 반복 수를 바꿨습니다. 질문·정답 근거·모델을 고정했고, 지시문·출력 상한·근거를 가운데에 두는 규칙도 유지했습니다.

3. 긴 입력의 답이 ‘월요일이 아닙니다. [E01 p.2]’라면 자동 검사는 어떻게 판단하며, 사람은 무엇을 확인해야 합니까?

이번 모델·질문·자료 구성·길이 범위에서는 저하를 관찰하지 못했다고 쓸 수 있습니다. 모든 긴 문서에서 성능이 유지된다는 결론은 내릴 수 없습니다.
