1학습 목표

  • 이 절을 마치면 문서 목록을 먼저 보고, 질문에 필요한 문서의 본문만 읽는 절차를 설명할 수 있습니다.
  • 이 절을 마치면 전체 입력, 선택 입력, 압축 입력을 같은 과제로 비교하고 토큰 절약과 근거 보존을 함께 평가할 수 있습니다.
  • 이 절을 마치면 모델과 프롬프트를 고정하고, 압축을 위한 추가 호출 비용을 본 답변 비용과 구분해 기록할 수 있습니다.
  • 이 절을 마치면 학생이 문서 ID를 직접 고르는 이 절의 코드와 Ch 9에서 검색 코드가 문서를 고르는 방식의 차이를 설명할 수 있습니다.

2이 내용을 배우는 이유

05절에서는 길이를 달리한 세 조건의 답을 관찰했고, 이번 실행에서는 성능 저하를 확인하지 못했습니다. 이 결과를 모든 긴 문서의 과제로 확대할 수는 없습니다. 처음부터 모든 문서 본문을 보낼 필요도 없습니다. 먼저 문서 ID와 한 줄 설명만 보여 주고, 질문에 필요한 문서를 고른 뒤 그 본문을 읽을 수 있습니다. 이처럼 정보를 한꺼번에 주지 않고 필요한 단계에서 자세히 보여 주는 방식을 단계적 공개라고 합니다.

단계적 공개는 화면 설계에서 오랫동안 사용한 개념이지만, 컨텍스트 엔지니어링에서는 모델이 처음부터 모든 세부 내용을 받지 않도록 하는 입력 설계로 적용할 수 있습니다. Anthropic의 Agent Skills 설명은 스킬 이름과 설명, 본문, 연결 파일을 단계별로 여는 사례를 제시합니다. 컨텍스트 엔지니어링 글도 파일 경로와 링크 같은 가벼운 식별자를 유지하고 필요한 자료를 실행 시점에 불러오는 방식을 권합니다.

이 절에서는 에이전트를 만들지 않습니다. 모델이 어떤 문서를 읽을지 판단하거나 도구를 호출하지도 않습니다. 학생이 질문과 문서 ID의 대응을 코드에 적고, 고정된 파이썬 반복문이 목록을 보여 준 뒤 지정된 본문 하나를 읽습니다. Ch 9에서는 사람이 정한 대응을 검색이 자동화합니다. 두 단계의 경계를 분명히 알아야 “선택”과 “에이전트 판단”을 같은 것으로 오해하지 않습니다.

3앞에서 배운 내용

Ch 7의 마지막 노트북은 프롬프트 원문, 변경 이유, 응답, 토큰·캐시·지연·예상 비용을 prompt-ab-continuity.json에 저장했습니다. 이 절은 그 파일과 SHA-256 지문을 직접 읽어 실행 기록의 출처를 확인한 뒤 같은 측정 필드와 가격 기준일·100만 토큰당 단가를 컨텍스트 설계 비교에 사용합니다. Ch 7은 고객 지원 질문이고 이 절은 도서관 질문이므로 두 실행의 수치를 직접 비교하지 않습니다.

  • Write — 현재 호출에 넣지 않은 자세한 본문을 파일이나 변수에 보관합니다. 단계적 공개는 기록을 삭제하지 않고 처음 입력에서 제외합니다.
  • Select — 현재 질문과 관련된 기록만 컨텍스트 안으로 가져옵니다. 이 절에서는 학생이 지정한 문서 ID를 반복문에서 비교합니다.
  • Compress — 원문 전체 대신 짧은 요약을 사용할 수 있습니다. 다만 조건, 예외, 출처가 사라질 수 있으므로 원문 보존 여부를 따로 평가합니다.
  • Context rot 실험 — 입력 길이만 바꾸고, 같은 질문·모델을 사용했으며 근거는 항상 자료 가운데에 두었습니다. 각 길이를 세 번씩 실행했습니다. 이 절도 무엇을 고정하고 바꿨는지 같은 방식으로 기록합니다.

4핵심 개념

비유 — 도서관의 목록과 서가

도서관에서 질문 하나에 답하려고 모든 책을 책상에 쌓지 않습니다. 먼저 목록에서 여러 책의 제목, 주제, 청구기호를 짧게 확인합니다. 필요한 책을 정한 다음 서가에서 그 책을 가져와 자세한 본문을 읽습니다. 단계적 공개는 여러 문서의 짧은 목록과 선택한 한 문서의 자세한 본문을 나눕니다.

목록만으로 최종 답을 만들 수는 없습니다. 목록은 어느 본문을 읽을지 결정하는 데 필요한 최소 정보입니다. 본문을 읽은 뒤에는 답의 근거가 되는 문장이 입력에 있어야 합니다. 따라서 단계적 공개의 성공 기준은 토큰 감소 하나가 아닙니다. 필요한 근거를 보존하면서 불필요한 내용을 줄였는가를 함께 봐야 합니다.

정의

단계적 공개 (progressive disclosure)
처음에는 문서 ID와 한 줄 설명만 보여 주고, 질문에 필요한 문서를 고른 뒤 그 문서의 자세한 본문을 보여 주는 방식입니다.
요약 목록 (summary catalog)
문서 ID, 제목, 한 줄 설명을 모은 목록입니다. 본문 선택을 돕지만 최종 답의 근거를 대신하지 않습니다.
전체 입력 (full context)
후보 문서의 본문을 모두 한 번에 프롬프트에 포함하는 설계입니다. 선택 과정은 없지만 무관한 정보와 입력 토큰이 늘 수 있습니다.
선택 입력 (selected context)
현재 질문에 필요하다고 지정한 원문 본문만 프롬프트에 포함하는 설계입니다. 이 절에서는 사람이 정한 ID와 고정 코드로 만듭니다.
압축 입력 (compressed context)
원문 대신 짧게 줄인 내용을 프롬프트에 포함하는 설계입니다. 토큰을 줄일 수 있지만 예외 조건과 출처가 손실될 수 있고, 모델로 압축하면 별도 호출 비용이 생깁니다.

도식 — 목록에서 필요한 본문으로

세 입력 설계 비교

설계프롬프트에 들어가는 내용기대되는 이점확인할 위험
full후보 문서 전체 본문선택 과정에서 정답 문서를 제외할 위험이 적습니다.무관한 정보, Confusion, 입력 토큰 증가가 생길 수 있습니다.
selected질문에 대응하는 원문 본문원문 근거를 유지하면서 입력을 줄일 수 있습니다.선택 규칙이 틀리면 필요한 문서를 처음부터 제외합니다.
compressed원문을 줄인 요약더 적은 토큰으로 핵심 사실을 제공할 수 있습니다.조건, 예외, 출처, 수치의 관계가 손실될 수 있습니다.

세 설계의 우열은 미리 정하지 않습니다. 질문이 여러 문서의 관계를 물으면 full이 필요한 근거를 더 잘 보존할 수 있습니다. 질문별 선택 규칙이 정확하면 selected가 적은 입력으로 같은 답을 만들 수 있습니다. 압축문이 질문에 필요한 예외까지 보존하면 compressed도 유효할 수 있습니다. 반대로 압축이 핵심 조건을 삭제하면 가장 짧지만 가장 부정확한 입력이 됩니다.

고정 코드로 구현하는 세 단계

실행 순서는 세 단계입니다. 첫째, 문서 ID와 제목만 있는 짧은 목록을 만듭니다. 둘째, 학생이 필요한 ID E01-p3을 코드에 적습니다. 셋째, 같은 ID를 가진 원문 하나를 가져옵니다. 모델은 마지막에 완성된 자료와 질문을 받아 답만 만듭니다. 어떤 문서를 고를지 학생 코드에 이미 정해져 있으므로 모델이 다음 행동을 결정하는 에이전트가 아닙니다.

E01-p3은 Ch 9의 doc_id=E01, page=3과 같은 출처 위치를 가리킵니다. 이 구조는 Ch 9의 Select와 직접 이어집니다. Ch 9에서는 문서가 많아져 사람이 ID를 지정하기 어려워지므로 질문과 가까운 문서 조각을 검색합니다. 검색이 선택을 자동화하지만, 어떤 문서를 몇 개 가져오고 어떤 순서로 프롬프트에 넣을지는 여전히 학생이 코드로 정합니다. 질문이 휴관일이면 Ch 9가 같은 E01에서 2쪽을 선택할 수 있으므로 3쪽과 다른 결과는 출처 불일치가 아닙니다. 모델이 검색 도구를 선택하고 호출하는 단계는 Ch 20 이후입니다.

문서 목록을 읽는 사람과 답을 만드는 모델

이 코드의 catalog는 문서별 ID와 제목만 복사한 목록입니다. selected_id는 사람이 대출 규정의 ID로 지정하고, 반복문이 일치하는 첫 문서를 찾아 selected에 보관합니다. break는 찾은 뒤 반복을 중단합니다. 이 선택 과정에는 모델 호출이 없으며, 모델은 나중에 완성된 입력을 받아 답을 생성합니다.

온라인 상품의 호환성을 묻는 상황에서는 상품 목록으로 후보를 고른 뒤 상세 규격을 읽을 수 있습니다. 그러나 “이 상품과 이전 모델의 차이”를 묻는다면 두 모델의 상세 규격이 필요합니다. 선택 입력이 항상 문서 하나여야 하는 것은 아닙니다. 질문이 요구하는 근거 수에 맞춰 선택 범위를 정합니다.

문자 수 비교의 selected["text"]에는 본문만 있지만 실제 호출용 selected_context에는 출처 ID도 붙습니다. 따라서 본문 길이 출력과 API가 보고한 입력 토큰을 같은 대상으로 해석하지 않습니다. 출력 검사의 “연장 예외” 항목도 실제로는 “연장”이라는 문자열의 포함 여부만 봅니다. 예약이 없는 경우라는 조건과 1회·7일 제한은 답 원문에서 별도로 확인해야 합니다.

5실행 예제

먼저 짧은 문서 목록을 확인하고 대출 규정의 식별자를 선택합니다. 전체·선택·압축 입력을 같은 질문과 지시로 각각 실제 API에 전달하여 입력·출력·캐시 토큰, 지연, 예상 비용, 답변 원문, 대출 조건·연장 예외·출처의 보존 여부를 비교합니다. 압축문은 사람이 미리 작성했으므로 별도의 압축 모델 호출 비용은 포함되지 않습니다. 결과는 context-design-continuity.json과 실행 시각별 사본에 저장합니다.

7주의할 점과 실무 메모

  • 단계적 공개가 언제나 빠르거나 저렴한 것은 아닙니다. 목록 확인, 본문 읽기, 압축 생성이 추가 단계가 되며 잘못된 선택은 재호출을 유발합니다. 사용 패턴과 재사용 횟수를 함께 봅니다.
  • 요약은 원문을 완전히 보존하지 않습니다. 수치, 부정 표현, 적용 기간, 예외, 출처를 우선 확인합니다. 중요한 결정에는 원문 링크나 문서 ID를 남깁니다.
  • 모델과 프롬프트를 고정합니다. 세 설계를 비교하면서 답변 모델이나 지시를 바꾸면 입력 설계의 영향을 구분할 수 없습니다.
  • 선택 규칙을 숨기지 않습니다. 이 절에서는 질문과 문서 ID의 대응을 코드에 명시합니다. Ch 9의 검색과 비교할 수 있도록 어떤 ID를 왜 선택했는지 기록합니다.
  • 에이전트라는 표현을 사용하지 않습니다. 함수 호출 순서와 문서 ID가 코드에 고정되어 있고 모델이 흐름을 바꾸지 않습니다. 에이전트는 Ch 20 ToolNode부터 다룹니다.
  • 한국어 문서의 조건 표현을 보존합니다. “이상”, “미만”, “다만”, “부칙”, “시행일”을 압축 과정에서 삭제하면 적용 범위가 달라질 수 있습니다.

8정리와 다음 절

  • 단계적 공개는 요약 목록에서 시작해 현재 요청에 필요한 본문만 읽는 입력 설계입니다.
  • full, selected, compressed는 입력 토큰뿐 아니라 정답 근거와 예외 조건의 보존 여부를 함께 비교해야 합니다.
  • 이 절의 선택은 학생이 지정한 문서 ID와 고정 코드가 수행하며, 모델이 도구나 흐름을 결정하지 않습니다.

다음 학습과 이어지는 지점 — Ch 9에서는 Select를 검색으로 자동화하여 문서가 많을 때 필요한 조각을 가져옵니다. Ch 11에서는 정답 문서 ID와 검색 지표로 선택 결과를 평가합니다. 생성된 답의 내용·근거·출처 형식을 자동 평가하는 방법은 Ch 15에서 다룹니다. Ch 19에서는 비슷한 도구 설명이 선택에 주는 Confusion을 다시 확인합니다. Ch 22에서는 Compress와 Isolate를 장기 실행 흐름에 적용하며, 요약의 근거 보존과 작업별 컨텍스트 분리를 다룹니다.

문제 4개 · 해설 포함

[하] 1. 단계적 공개의 세 단계를 도서관 목록 비유에 맞추어 쓰세요.

정답·해설 — 문서 ID·제목·한 줄 설명의 목록을 확인하고, 질문에 맞는 ID를 정한 뒤, 해당 문서의 원문 본문을 읽습니다. 오답 학습 연결 — 목록만 보고 답한다고 썼다면 요약 목록이 선택을 돕고 본문을 대신하지 않는다는 정의를 다시 확인합니다.

[중] 2. selected가 full보다 입력 토큰이 적었습니다. selected가 더 좋은 설계라고 결론 내리기 전에 확인할 항목 두 가지는 무엇입니까?

정답·해설 — 정답에 필요한 문서와 근거 문장이 선택 입력에 포함되었는지, 답이 핵심 조건과 출처를 보존했는지 확인해야 합니다. 오답 학습 연결 — 비용만 언급했다면 토큰 절약과 근거 보존을 함께 보는 비교표를 다시 확인합니다.

[중] 3. compressed 조건의 총비용을 계산할 때 답변 호출 외에 확인할 비용은 무엇입니까?

정답·해설 — 모델을 사용해 압축문을 만들었다면 압축 호출의 입력·출력 토큰 비용을 별도로 더해야 합니다. 저장된 압축문을 재사용했는지, 질문마다 새로 만들었는지도 구분합니다. 오답 학습 연결 — 답변 호출만 계산했다면 실행 예제의 비용 구분 원칙을 다시 적용합니다.

[상] 4. 질문이 두 문서의 규정 차이를 비교하도록 요구합니다. full, selected, compressed를 어떻게 구성하고 어떤 기준으로 평가할지 설계하세요.

정답·해설 — full에는 후보 전체, selected에는 비교 대상 두 문서의 관련 원문, compressed에는 두 문서의 수치·시점·예외·출처를 보존한 요약을 넣습니다. 같은 모델과 프롬프트로 실행하고 입력 토큰, 두 문서의 핵심 사실 포함 여부, 차이 설명의 정확성, 근거 밖 주장, 압축 비용을 비교합니다. 오답 학습 연결 — selected에 한 문서만 넣었다면 복수 근거 질문에서 선택 범위를 정하는 방법을 다시 검토합니다.
