1학습 목표

  • stream()이 반환하는 AIMessageChunk를 도착 순서대로 읽을 수 있습니다.
  • 메시지 조각을 결합해 완성된 AIMessageChunk의 text를 얻을 수 있습니다.

  • 스트리밍 사용량 정보가 없을 때 이를 0이 아닌 미확인 값으로 기록할 수 있습니다.

2이 내용을 배우는 이유

모델이 긴 답변을 모두 만든 뒤 화면에 표시하면 사용자는 첫 문장을 보기까지 기다려야 합니다. 스트리밍(streaming)은 모델이 준비한 응답 조각을 차례로 전달하여 화면을 먼저 갱신하게 합니다. 채팅 화면에서 글자가 이어서 나타나는 동작은 대개 이 방식을 사용합니다. 사용자는 답변 생성을 시작했다는 사실을 일찍 알 수 있고, 프로그램은 도착한 부분부터 화면에 표시할 수 있습니다.

다만 화면에 글자가 나타났다는 사실과 응답 처리가 끝났다는 사실은 서로 다릅니다. 중간 조각은 문장의 한 부분일 수 있고, 구조화된 JSON이라면 여는 중괄호만 도착한 상태일 수도 있습니다. 중간 조각을 완성된 답으로 저장하거나 검증하면 정상적인 응답도 실패로 처리할 수 있습니다. 따라서 화면 표시와 최종 저장의 시점을 분리해야 합니다.

제공자마다 원본 응답의 모양도 다를 수 있습니다. LangChain은 읽기 쉬운 텍스트와 표준 콘텐츠 블록을 함께 제공하여 이러한 차이를 다룰 수 있게 합니다. 이번 절에서는 블록 개수만 세지 않습니다. 실제 블록의 type과 텍스트 일부를 확인하고, 어떤 값을 사용자 화면과 후속 처리에 사용할지 판단합니다.

3앞에서 배운 내용

첫 절에서는 init_chat_model()로 모델 객체를 만들고 invoke()를 호출했습니다. invoke()는 호출이 끝난 뒤 하나의 AIMessage를 반환했습니다. 02절에서는 AIMessage.text로 텍스트를 읽고 content_blocks로 표준화된 내용 블록을 확인했습니다. 이번 절에서는 원본 내용인 content와 스트리밍 조각까지 범위를 넓힙니다.

이번 노트북도 새 Python 3.12 커널에서 독립적으로 시작합니다. 앞 절의 model 변수를 이어서 사용하지 않습니다. 같은 초기화 코드를 다시 실행하고, 실제 네트워크 요청이 시작되는 stream(messages) 경계를 직접 확인합니다.

4핵심 개념

봉투 한 개와 이어지는 쪽지

invoke()의 반환값을 완성된 답이 든 봉투 한 개라고 생각해 봅니다. stream()의 반환값은 작성되는 순서대로 도착하는 여러 장의 쪽지에 가깝습니다. 각 쪽지가 AIMessageChunk입니다. 첫 조각에는 텍스트가 없을 수 있고, 뒤의 여러 조각에 단어나 문장 부호가 나뉘어 들어올 수 있습니다. 마지막 조각에는 텍스트 대신 응답 종료 이유나 사용량 정보가 담길 수도 있습니다.

스트림은 한 번에 전체 목록을 반환하지 않습니다. for 반복문이 다음 조각을 요청할 때마다 도착한 값을 하나씩 받습니다. 프로그램은 그 자리에서 chunk.text를 화면에 표시하고, 같은 조각을 목록에도 보관할 수 있습니다. 화면에 표시만 하고 조각을 버리면 연결이 끝난 뒤 완성된 메시지를 다시 만들 수 없습니다.

content, text, content_blocks

content는 제공자 응답과 가까운 원본 표현입니다. 단순한 모델 응답에서는 문자열일 수 있지만, 텍스트와 다른 종류의 정보가 섞이면 목록처럼 보일 수도 있습니다. 제공자별 문제를 조사하거나 원본 구조를 보존해야 할 때 확인합니다.

text는 메시지에서 사람이 읽을 텍스트 부분을 꺼낸 문자열입니다. 채팅 화면에 문장을 이어 붙이거나 최종 답을 표시할 때 사용하기 좋습니다. 이번 실행에서 텍스트 청크의 표준 블록은 type이 text인 사전 형태로 나타나며, text 항목에 해당 조각의 글자가 담깁니다. 텍스트가 없는 시작·종료 청크는 빈 블록 목록으로 나타날 수 있습니다. 이 차이를 확인해야 빈 청크를 오류로 잘못 판정하지 않습니다.

content_blocks는 텍스트, 추론 정보, 이미지처럼 서로 다른 내용을 LangChain의 표준 블록으로 읽는 속성입니다. 예를 들어 {"type": "text", "text": "스트리밍"}과 같은 텍스트 블록은 종류와 값을 분리해서 보여 줍니다. 실제 출력의 텍스트는 실행마다 달라질 수 있으므로, 교재에서는 특정 단어의 위치보다 type과 필드의 역할을 읽습니다. 블록의 개수만으로는 어떤 내용이 도착했는지 알 수 없습니다.

조각 결합과 완료 시점

AIMessageChunk는 + 연산으로 결합할 수 있습니다. 첫 조각을 combined에 넣고 다음 조각을 차례로 더하면 순서를 보존한 하나의 결합 메시지가 됩니다. 모든 반복이 정상적으로 끝난 뒤 combined.text를 읽으면 화면에 표시한 조각과 같은 흐름의 최종 텍스트를 얻습니다. 저장, 구조 검증, 후속 함수 호출은 이 완료 지점에서 수행합니다.

사용량 메타데이터는 모든 청크에 항상 들어오는 값이 아닙니다. OpenAI 통합에서는 현재 고정 버전에서 stream_usage=True를 지정하여 스트리밍 사용량 수집을 요청할 수 있습니다. 그래도 코드는 실제로 제공된 usage_metadata만 합산해야 합니다. 정보가 없다는 것은 토큰을 사용하지 않았다는 뜻이 아닙니다. 따라서 누락 상태는 None이나 unknown으로 남기고 0으로 바꾸지 않습니다.

스트리밍은 전달 방식이며 완료 규칙은 프로그램이 정합니다

스트리밍을 사용한다고 모든 처리를 조각 단위로 수행할 수 있는 것은 아닙니다. 화면에 글자를 추가하는 일은 조각마다 할 수 있지만, 전체 문장의 금칙어 검사나 JSON 검증은 마지막 조각까지 받은 뒤에 해야 합니다. 번역 자막처럼 문장 경계를 기다려야 자연스러운 처리도 있습니다. 어느 작업이 중간 결과를 받아들일 수 있는지 먼저 나누면 화면 표시와 최종 확정 시점을 혼동하지 않습니다.

상황조각 도착 중에 할 일완료 뒤에 할 일완료 전에 중단되면
긴 개념 설명 채팅도착한 텍스트를 순서대로 표시전체 답을 대화 기록에 저장부분 표시와 미완료 상태를 함께 남깁니다.
구조화된 설문 결과 JSON진행 상태만 표시결합 후 파싱과 스키마 검증미완성 JSON을 유효한 결과로 저장하지 않습니다.
실시간 자막 초안임시 문구로 표시문장 단위 정리와 확정확정 전 자막임을 화면에서 구분합니다.
텍스트와 이미지 설명이 섞인 응답블록의 type별로 렌더링블록 순서와 원본 참조를 보존지원하지 않는 블록을 임의의 문자열로 바꾸지 않습니다.
사용량 기록메타데이터가 있는 청크를 보관결합 메시지의 최종 값을 확인누락을 0으로 기록하지 않습니다.

완료는 “마지막 글자가 화면에 보였다”라는 추측이 아니라 반복문이 정상 종료되고 최종 메시지를 구성했다는 프로그램 상태로 표현합니다. 연결 오류가 발생하면 이미 표시한 문자열을 지울지 유지할지는 화면 정책의 문제입니다. 어느 쪽을 고르더라도 저장 레코드에는 completed와 partial을 구분할 정보가 필요합니다.

조각 수와 토큰 수를 같은 단위로 읽지 않습니다

한 청크에는 글자 하나가 들어올 수도 있고 여러 토큰이 들어올 수도 있습니다. 시작·종료 메타데이터만 담은 빈 텍스트 청크도 있습니다. 따라서 청크 20개는 출력 토큰 20개, 네트워크 요청 20회, 화면 갱신 20회 중 어느 것과도 자동으로 같아지지 않습니다. 이번 실제 출력의 청크 수와 콘텐츠 블록 수가 다른 것도 서로 세는 대상이 다르기 때문입니다.

AIMessageChunk의 덧셈은 텍스트만 이어 붙이는 문자열 연산보다 넓은 의미가 있습니다. 텍스트, 도구 호출 조각, 사용량 같은 메시지 필드를 결합 규칙에 따라 모읍니다. 최종 결과가 텍스트뿐이라면 combined.text가 편리하지만, 여러 종류의 콘텐츠가 있는 응답은 combined.content_blocks를 함께 확인해야 정보 손실을 찾을 수 있습니다.

도식 읽기

청크 하나와 최종 응답을 구분해 읽기

청크(chunk)는 스트림에서 한 번 전달받는 응답 조각입니다. model.stream(messages)는 조각을 차례로 읽을 수 있는 반복자를 제공하며, for chunk in ...가 이를 순서대로 읽습니다. 각 chunk는 AIMessageChunk이고 .text는 그 조각의 텍스트입니다. 청크 경계가 단어·문장·토큰 하나의 경계와 항상 같다고 가정하지 않습니다.

예를 들어 화면에 “대출은”과 “ 3권까지입니다.”가 순서대로 도착한다면, 첫 조각만으로 최대 권수를 정할 수 없습니다. 이 문장은 원리를 설명하기 위한 가정입니다. 실제 예제에서는 저장된 chunks 목록을 읽고 각 조각을 +로 결합합니다. 이는 단순 문자열 덧붙이기와 달리 메시지 조각의 자료를 병합하는 연산이며, 최종 변수도 AIMessageChunk입니다.

print(..., end="", flush=True)의 end는 매 출력 뒤의 줄바꿈을 없애고 flush는 출력 버퍼에 남기지 않고 표시하도록 요청합니다. 두 인자는 모델의 생성 설정이 아니라 Python 화면 출력 설정입니다. 채팅 화면은 조각이 올 때마다 표시할 수 있지만, 결과를 파일에 저장하거나 구조를 검사하는 단계는 완료된 내용을 대상으로 해야 하는 경우가 많습니다.

5실행 예제

노트북은 OpenAI 모델에 짧은 설명을 요청하고 stream()에서 받은 청크를 목록에 저장합니다. 반복문 안에서는 chunk.text를 줄바꿈 없이 출력하여 응답이 이어지는 모습을 확인합니다. 반복이 끝나면 청크 수를 출력하지만, 이 수는 속도 점수가 아닙니다. 제공자와 실행 시점에 따라 한 조각에 담는 글자 수가 달라질 수 있기 때문입니다.

다음 셀은 첫 청크부터 마지막 청크까지 +로 결합합니다. 이어서 텍스트가 있는 대표 청크의 실제 content_blocks를 출력합니다. 출력에서 type: text와 해당 조각의 text를 함께 읽으면, 블록 수가 아니라 블록의 내용까지 확인할 수 있습니다. 마지막으로 사용량 정보가 제공된 청크가 있는지 찾고, 없으면 미확인 상태로 표시합니다.

스트리밍 호출

stream()이 반환하는 AIMessageChunk를 도착 순서대로 저장합니다.

청크는 한 번 전달된 응답 조각입니다. stream()에서 읽는 각 값은 AIMessageChunk이며 for 반복문이 순서대로 소비합니다. .text가 비어 있는 조각도 있으므로 청크 수가 곧 글자 수나 토큰 수는 아닙니다.

end=""는 조각 사이의 자동 줄바꿈을 없애고 flush=True는 Python 출력이 바로 표시되도록 요청합니다. 생성 모델의 설정이 아닙니다. chunks.append(chunk)는 나중에 결합할 원본 조각을 순서대로 남깁니다.

안내문에서 권수나 예외 조건이 마지막에 나올 수 있으므로 앞 조각만 보고 최종 답을 확정하지 않습니다. 아래에서는 같은 스트림의 조각을 결합한 뒤, 별도의 invoke() 호출에서 받은 응답과 타입을 비교합니다. 두 호출의 문구가 같을 필요는 없습니다.

In [4]:
# stream이 내보내는 AIMessageChunk를 도착 순서대로 chunks 목록에 저장합니다.
messages = [("user", "LangChain 스트리밍을 열두 단어 이내로 설명하세요.")]
chunks = []
for chunk in model.stream(messages):
    chunks.append(chunk)
    print(chunk.text, end="", flush=True)
print()
print("조각 수:", len(chunks))

조각 결합

+ 연산으로 메시지 조각을 결합하고 최종 텍스트를 확인합니다.

In [5]:
# 청크의 + 연산으로 메타데이터를 보존한 최종 AIMessageChunk를 만듭니다.
combined = chunks[0]
for chunk in chunks[1:]:
    combined = combined + chunk
print("결합 텍스트:", combined.text)
print("결합 성공:", bool(combined.text.strip()))

결합 성공: True

content blocks 관찰

각 조각의 표준 콘텐츠 블록 수를 세되 제공자별 블록 모양을 단정하지 않습니다.

In [6]:
# 각 청크의 표준 content_blocks 개수와 합계를 관찰값으로 남깁니다.
block_counts = [len(chunk.content_blocks) for chunk in chunks]
print("조각별 블록 수:", block_counts)
print("전체 블록 수:", sum(block_counts))
representative = next((c.content_blocks[0] for c in chunks if c.content_blocks), None)
print("대표 content block:", representative)
print("결합 메시지 usage 있음:", combined.usage_metadata is not None)

invoke와 결과 비교

같은 질문을 일반 호출로 한 번 더 실행해 반환 타입을 비교합니다.

In [7]:
# 같은 질문의 invoke 반환 타입과 결합 청크 타입을 비교합니다.
single = model.invoke(messages)
print("stream 반환 타입:", type(chunks[0]).__name__)
print("invoke 반환 타입:", type(single).__name__)
print("두 결과 모두 텍스트 있음:", bool(combined.text and single.text))
출력:
stream 반환 타입: AIMessageChunk
invoke 반환 타입: AIMessage
두 결과 모두 텍스트 있음: True

확인할 점 — stream()의 원소는 AIMessageChunk이고, 결합한 객체도 같은 타입입니다. 대표 블록에서 type과 text를 함께 확인합니다. 사용량 정보가 출력되지 않았다면 0토큰으로 읽지 말고 이번 스트림에서 확인되지 않은 값으로 읽습니다.

6실험 결과 해석

2026-09-09 최종 새 커널 실행에서는 모두 20개의 청크가 도착했고, 표준 콘텐츠 블록은 16개였습니다. 대표 블록은 {"type": "text", "text": "실"}이었습니다. 첫 청크와 마지막 세 청크의 블록 목록은 비어 있었지만, 사이의 텍스트 청크가 정상적으로 이어졌고 반복도 완료되었습니다. 빈 청크 하나만으로 실패라고 판단할 수 없는 이유입니다. 결합 메시지에는 사용량 정보도 있었습니다. 이 수치는 해당 실행의 관찰값이며 다시 실행하면 달라질 수 있습니다.

결합한 text에는 실제 문장이 남았고, 일반 호출의 AIMessage.text에도 텍스트가 있었습니다. 스트림 원소의 타입은 AIMessageChunk, invoke() 결과의 타입은 AIMessage였습니다. 이 결과는 두 호출 방식이 모두 텍스트를 반환하면서 중간 반환 단위는 다르다는 점을 보여 줍니다.

이번 실험은 조각의 순서와 결합 방법을 확인합니다. 20이라는 청크 수만으로 첫 토큰 지연, 전체 지연, 제공자 처리 속도를 비교할 수 없습니다. 청크 수와 생성 문장은 다시 실행하면 달라질 수 있습니다. 속도를 비교하려면 같은 조건의 반복 측정과 별도의 시간이 필요합니다.

7주의할 점과 실무 메모

  • 중간 조각을 완성된 JSON으로 검증하지 않습니다. 닫는 괄호가 아직 도착하지 않은 정상 상태를 구문 오류로 잘못 처리할 수 있습니다.
  • 화면 표시와 저장 상태를 분리합니다. 연결이 끊기면 사용자가 본 일부 텍스트와 서버에 저장한 최종 답이 달라질 수 있으므로 완료 여부를 함께 기록합니다.
  • 빈 텍스트 청크를 곧바로 오류로 판정하지 않습니다. 종료 정보나 사용량처럼 텍스트 이외의 메타데이터를 담은 청크일 수 있습니다.
  • 사용량 누락은 0이 아닙니다. 해당 통합과 모델이 스트리밍 사용량을 제공하는지 확인하고, 제공되지 않은 값은 미확인으로 보존합니다.
  • 화면 갱신 횟수를 제한할 수 있습니다. 청크마다 화면 전체를 다시 그리면 브라우저 작업이 늘어나므로 짧은 간격으로 묶어 표시할 수 있습니다. 원래 순서는 바꾸지 않습니다.

8정리와 다음 절

  • stream()은 여러 AIMessageChunk를 도착 순서대로 반환합니다.
  • text는 화면에 표시할 문자열이고, content_blocks는 종류와 값을 가진 표준 블록을 확인할 때 사용합니다.
  • 모든 청크를 결합한 뒤 저장과 검증을 수행하며, 제공되지 않은 사용량은 미확인 값으로 남깁니다.

다음 학습과 이어지는 지점 — 스트리밍도 외부 네트워크 요청이므로 응답이 늦거나 연결이 끝까지 이어지지 않을 수 있습니다. 다음 절에서는 기다리는 시간과 다시 시도하는 횟수를 제한하고, 실패할 때 선택할 대체 경로를 구성합니다.

9복습 문제

문제 1

왜 중간 AIMessageChunk마다 구조화된 JSON 검증을 실행하면 안 되나요?

해설 — 중간 청크에는 JSON의 일부만 들어 있을 수 있습니다. 모든 조각을 결합해 응답이 완성된 뒤 검증해야 정상적인 미완성 상태를 오류로 판단하지 않습니다.

문제 2

text와 content_blocks는 각각 언제 사용하나요?

해설 — 사용자에게 읽을 문자열을 표시할 때는 text가 편리합니다. 텍스트·추론·이미지처럼 콘텐츠 종류와 필드를 구분해 처리할 때는 content_blocks를 사용합니다.

문제 3

스트림에 usage_metadata가 없으면 토큰 수를 0으로 기록해도 되나요?

해설 — 기록하면 안 됩니다. 메타데이터가 없다는 것은 사용량을 확인하지 못했다는 뜻입니다. None이나 unknown으로 남기고 지원 옵션과 제공자 응답을 확인합니다.

문제 4

한 번의 호출에서 청크가 많이 나온 모델이 더 느리다고 판단할 수 있나요?

해설 — 판단할 수 없습니다. 청크를 나누는 방식과 네트워크 전달 방식이 다를 수 있습니다. 속도 비교에는 같은 과제를 여러 번 실행하여 첫 토큰 지연과 전체 지연을 따로 측정해야 합니다.
