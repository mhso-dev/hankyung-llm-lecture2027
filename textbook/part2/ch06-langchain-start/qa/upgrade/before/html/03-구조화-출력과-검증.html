1학습 목표

이 절을 마치면 다음을 할 수 있습니다.

  • Pydantic으로 응답의 필드·타입·허용 범위를 선언할 수 있습니다.
  • 구조화 출력의 파싱 결과와 원본 메시지를 구분할 수 있습니다.
  • 검증 오류를 처리하고 형식 검증과 내용의 사실 확인을 구분할 수 있습니다.

2이 내용을 배우는 이유

모델이 “AIMessage는 모델의 답변입니다. 난이도는 초급입니다”라고 답했다고 생각해 봅니다. 사람은 읽을 수 있지만, 프로그램이 개념 이름·설명·난이도를 각각 저장하려면 어디서 문장을 나눌지 결정해야 합니다. 응답 표현이 바뀔 때마다 문자열을 나누는 규칙을 추가하면 유지하기 어렵습니다.

이번 절에서는 받을 항목을 먼저 정의합니다. 모델의 응답을 개념 이름, 설명, 1~3의 난이도로 받고 Python 객체에서 각 값을 읽습니다. 데이터의 모양이 어긋났을 때 어느 값이 문제인지 확인하는 과정까지 실행합니다.

3앞에서 배운 내용

앞 절의 init_chat_model과 invoke를 그대로 사용하되 이번에는 OpenAI 한 모델에 집중합니다. Ch 2의 딕셔너리와 class 이름: 문법을 사용하며, 10절 B 경로에서 다룬 BaseModel·Field·엄격 검증을 모델 응답에 연결합니다. B 경로를 건너뛴 학생도 여기서는 같은 항목을 가진 학습 카드의 형식을 한 번 정의하는 코드로 읽으면 됩니다. 클래스의 내부 동작을 새로 구현하지 않습니다.

새 Python 3.12 커널에서 설치·키 확인·모델 준비 셀을 실행합니다. 이 절에 필요한 Pydantic도 실습 환경에 설치됩니다. StudyCard와 모델 객체는 이 노트북 안에서 준비하므로 앞 절의 변수에 의존하지 않습니다.

4핵심 개념

빈칸이 정해진 학습 카드

양식이 없는 메모와 이름·설명·난이도 칸이 인쇄된 카드를 비교해 봅니다. 양식이 있는 카드에서는 무엇을 적을지 미리 알 수 있고, 비어 있는 칸도 찾을 수 있습니다. 구조화 출력(structured output)은 이처럼 프로그램이 받을 항목과 형식을 정해 응답을 받는 방법입니다.

스키마(schema)는 필요한 항목과 값의 형식을 정의한 것입니다. 각 항목을 필드(field)라고 합니다. 실습의 concept와 explanation은 문자열이고, difficulty는 정수입니다. 이 이름을 그대로 사용해야 프로그램이 어느 값을 읽을지 알 수 있습니다.

Pydantic은 선언한 타입과 제약에 맞게 데이터를 읽고 검사하는 Python 라이브러리입니다. BaseModel을 상속한 StudyCard에 세 필드를 선언합니다. Field의 description은 항목의 뜻을 설명합니다. ge=1은 1 이상, le=3은 3 이하라는 조건입니다. 설명 문장에 “1~3”을 적는 것과 실제 범위 제약을 선언하는 것을 구분합니다.

도식에서 학생이 정한 필드와 제약을 먼저 확인합니다. 모델이 응답을 만드는 보라색 단계 이후에 노란색 검증 결과를 읽습니다. 실습에서는 difficulty=7인 자료가 범위를 벗어나고 difficulty=2인 자료는 범위에 들어갑니다. 검증을 통과해도 설명 문장이 사실인지까지 확인된 것은 아닙니다.

문자열을 객체로 읽는 것과 오류를 읽는 것

파싱(parsing)은 응답 내용을 프로그램이 다룰 구조로 읽는 처리입니다. model.with_structured_output(StudyCard)는 모델에 이 형식을 적용한 호출 객체를 만듭니다. 성공 결과는 일반 호출의 AIMessage 대신 StudyCard 객체로 읽습니다. model_dump()를 호출하면 세 필드를 딕셔너리로 확인할 수 있습니다.

검증 오류(ValidationError)는 값이 선언한 조건을 만족하지 못할 때 발생합니다. 오류를 숨기고 빈 카드로 바꾸면, 다음 코드가 정상 데이터로 오해할 수 있습니다. 어느 필드가 어떤 제약에 걸렸는지 확인한 뒤 입력이나 정의를 고쳐야 합니다.

include_raw=True를 사용하면 결과에 raw, parsed, parsing_error가 들어갑니다. raw는 원본 응답, parsed는 읽고 검증한 결과, parsing_error는 파싱이나 검증에서 발생한 오류입니다. 오류가 없으면 마지막 값은 None입니다. API 자체가 인증 오류나 통신 오류로 실패한 경우까지 이 옵션이 정상 결과로 바꾸는 것은 아닙니다.

with_structured_output의 준비와 실행 구분

이 메서드는 이 절에서 처음 배웁니다. model.with_structured_output(StudyCard)에서 점 앞의 model은 준비한 채팅 모델이고, 괄호 안의 StudyCard는 만들어 달라는 카드의 형식입니다. StudyCard()처럼 빈 카드 객체를 만드는 호출이 아니라 클래스 자체를 전달합니다. LangChain이 필드 설명과 제약을 읽어 모델 호출에 적용할 수 있도록 하기 위한 것입니다.

반환된 structured_model은 나중에 실행할 수 있는 호출 객체입니다. 이 줄만으로 학습 카드가 생성되지 않습니다. 다음 structured_model.invoke("AIMessage를 설명하세요")가 요청을 실행하고, 성공하면 읽고 검증한 StudyCard 인스턴스를 반환합니다. 따라서 card.difficulty로 필드 값을 읽고 card.model_dump()로 딕셔너리 표현을 얻습니다. invoke()의 입력은 카드에 넣을 내용을 요청하는 문장이고, 스키마 자체와 역할이 다릅니다.

학습 카드와 주문 입력을 비교하면 같은 원리가 더 분명해집니다. 카드에서는 난이도 범위가 중요하고 주문에서는 품명이 비어 있지 않은지와 수량이 양수인지가 중요합니다. 아래 주문 예시는 개발자가 직접 만든 JSON을 읽어 검증합니다. 주문을 모델이 추출했다고 가정하지 않으며, 필드 규칙을 바꿔도 실제 재고나 주문의 존재 여부까지 확인되는 것은 아닙니다.

스키마 표현은 다음 코드가 무엇을 요구하는지에 맞춥니다

같은 세 필드라도 Pydantic 모델, TypedDict, JSON Schema로 표현할 수 있습니다. 선택 기준은 문법의 길이보다 결과를 어디에서 검증하고 누구와 공유하는가입니다. Python 프로그램 안에서 범위 검증과 오류 위치가 필요하면 Pydantic이 알맞습니다. 타입 힌트와 고정된 키만 필요하면 TypedDict가 가볍습니다. Python 밖의 서비스와 같은 정의를 교환해야 하면 언어에 덜 종속적인 JSON Schema가 유리합니다.

학습 카드의 난이도를 1~3으로 제한Pydantic타입·범위의 실행 시점 검증타입 변환 허용 여부
뉴스 제목과 URL 키만 Python 코드에 표시TypedDict간결한 타입 힌트반환값의 별도 실행 시점 검증

생성 방식의 엄격함과 Pydantic의 엄격함은 다른 층입니다

with_structured_output()의 method는 모델이 구조를 생성하도록 요청하는 방법을 고릅니다. json_schema는 제공자의 전용 구조화 출력 기능을 사용하고, function_calling은 스키마에서 도구 호출 형식을 만들어 결과를 받으며, json_mode는 유효한 JSON 생성을 요청하되 필요한 스키마 설명을 프롬프트에도 제공해야 합니다. 어느 방법을 지원하는지는 제공자·모델·통합 버전에 따라 다릅니다.

고정 환경에서 ChatOpenAI.with_structured_output()은 세 방법과 strict 인자를 제공하고 기본 방법은 json_schema입니다. 같은 환경의 Anthropic 통합은 function_calling과 json_schema를, Google 통합은 세 방법을 시그니처에 표시합니다. 시그니처에 이름이 있다는 사실만으로 선택한 모델과 계정에서 항상 성공한다고 단정하지 않습니다. 수업의 OpenAI 기본 경로처럼 한 조합을 실제로 실행해 확인해야 합니다.

여기서 구조화 출력의 strict와 Pydantic의 엄격 모드(strict mode)를 섞지 않습니다. 앞의 설정은 제공자 API가 스키마를 얼마나 엄격히 따르게 할지에 관한 옵션입니다. 뒤의 설정은 Python이 이미 받은 값을 다른 타입으로 변환해 받아들일지에 관한 검증 규칙입니다. 예를 들어 기본 Pydantic 검증은 정수 필드에 문자열 "2"가 들어오면 정수 2로 변환할 수 있지만, strict=True는 Python 입력의 타입이 맞지 않으면 거부합니다. ConfigDict(extra="forbid")는 선언하지 않은 필드가 추가됐을 때 오류를 냅니다. 타입 변환, 추가 필드, 값의 범위는 서로 다른 검사이므로 필요한 규칙을 각각 정합니다.

설문 분석을 예로 들면, 응답 번호 "2"를 정수로 받아도 되는 CSV 가져오기 단계에서는 변환이 편리합니다. 이미 정수만 전달하기로 정한 내부 API 경계에서는 문자열이 들어온 사실을 조기에 찾기 위해 엄격 검증이 더 적합합니다. 반대로 모델이 설명용 confidence_reason 필드를 새로 반환했을 때 이를 버려도 되는지, 입력 형식 변화로 보고 거부해야 하는지는 데이터 사용 목적에 따라 결정합니다.

Pydantic 스키마

Ch 2의 클래스 문법을 사용하며, 10절 B 경로에서 다룬 BaseModel·Field·엄격한 검증을 모델 응답에 연결합니다. B 경로를 건너뛴 학생도 따라오도록 필요한 규칙을 다시 확인합니다.

스키마는 받을 항목과 형식의 정의입니다. class StudyCard(BaseModel):는 Pydantic의 검증 기능을 물려받은 클래스입니다. concept: str은 문자열 필드, difficulty: int는 정수 필드이며 Field(ge=1, le=3)는 1 이상 3 이하라는 범위를 선언합니다. description은 필드 의미를 설명하는 문자열입니다. Ch 2의 선택 B 경로를 읽지 않았더라도 이 선언을 카드의 각 칸과 허용값으로 읽을 수 있습니다.

model.with_structured_output(StudyCard)는 이 절에서 처음 사용하는 메서드입니다. 카드 인스턴스가 아닌 클래스 StudyCard를 넘겨 출력 형식을 설정한 호출 객체를 만듭니다. 실제 생성은 다음 셀의 structured_model.invoke(...)에서 이루어집니다. 성공하면 AIMessage 대신 StudyCard를 받으며, model_dump()로 그 필드들을 딕셔너리로 읽습니다.

같은 셀의 diagnostic_model은 뒤의 오류 관찰에 사용할 두 번째 호출 객체입니다. include_raw=True를 주면 이후 호출 결과가 raw·parsed·parsing_error 키를 가진 딕셔너리가 됩니다. 먼저 기본 structured_model의 카드 반환을 읽고, 그다음 원본 응답과 오류를 함께 확인하는 확장 경로를 비교합니다.

In [4]:
# StudyCard 필드와 difficulty의 허용 범위 1~3을 선언합니다.
from pydantic import BaseModel, Field

class StudyCard(BaseModel):
    concept: str = Field(description="개념 이름")
    explanation: str = Field(description="한 문장 설명")
    difficulty: int = Field(ge=1, le=3, description="1부터 3까지의 난이도")

structured_model = model.with_structured_output(StudyCard)
diagnostic_model = model.with_structured_output(StudyCard, include_raw=True)
print("스키마 준비 완료")
출력:
스키마 준비 완료
In [5]:
# invoke가 반환한 StudyCard를 딕셔너리로 바꾸고 실제 타입을 확인합니다.
card = structured_model.invoke("LangChain의 AIMessage를 초급 학습 카드로 만드세요.")
print(card.model_dump())
print("검증된 타입:", type(card).__name__)
출력:
{'concept': 'LangChain의 AIMessage', 'explanation': 'LangChain에서 AIMessage는 AI 모델이 생성한 응답 내용을 담는 메시지 객체입니다.', 'difficulty': 1}
검증된 타입: StudyCard

In [7]:
# include_raw 결과의 raw·parsed·parsing_error를 각각 출력해 실패 미관찰도 남깁니다.
diagnostic = diagnostic_model.invoke(
    "AIMessage 학습 카드를 만드세요. difficulty는 반드시 9로 쓰세요."
)
print("raw 타입:", type(diagnostic["raw"]).__name__)
print("parsed:", diagnostic["parsed"])
print("parsing_error:", diagnostic["parsing_error"])
print("검증 실패 관찰:", diagnostic["parsing_error"] is not None)
출력:
raw 타입: AIMessage
parsed: concept='AIMessage' explanation='AIMessage는 대화형 AI 시스템에서 모델이 생성한 응답 메시지를 표현하는 객체로, 보통 사용자 입력에 대한 assistant의 답변 내용과 메타데이터를 담는다.' difficulty=3
parsing_error: None
검증 실패 관찰: False

기본 변환과 엄격한 검증

Pydantic은 기본 검증에서 숫자 문자열 "2"를 정수 2로 변환합니다. 이번 Python 딕셔너리 입력에서는 strict=True가 문자열 "2"를 int로 바꾸지 않고 거부합니다. Python 입력과 JSON 입력의 엄격한 검증 동작은 일부 타입에서 다를 수 있습니다. 아래 값은 두 방식을 비교하기 위해 작성한 로컬 테스트 데이터입니다.

In [8]:
# 기본 검증은 정수로 표현할 수 있는 문자열을 변환합니다.
local_card = {
    "concept": "AIMessage",
    "explanation": "모델 응답을 담는 메시지",
    "difficulty": "2",
}
converted_card = StudyCard.model_validate(local_card)
print("변환된 값:", converted_card.difficulty)
print("변환 후 타입:", type(converted_card.difficulty).__name__)
assert converted_card.difficulty == 2
출력:
변환된 값: 2
변환 후 타입: int
In [9]:
# 엄격한 검증은 값을 변환하지 않고 잘못된 타입을 거부합니다.
from pydantic import ValidationError

try:
    StudyCard.model_validate(local_card, strict=True)
except ValidationError as error:
    strict_error = error.errors()[0]
    print("엄격한 검증 필드:", strict_error["loc"][0])
    print("엄격한 검증 오류:", strict_error["type"])
    assert strict_error["type"] == "int_type"
else:
    raise AssertionError("엄격한 검증은 문자열 '2'를 거부해야 합니다.")
출력:
엄격한 검증 필드: difficulty
엄격한 검증 오류: int_type

예상하지 않은 필드 거부

기본 설정은 스키마에 없는 필드를 제외할 수 있습니다. 입력에 허용한 필드만 받아야 한다면 extra='forbid'를 설정합니다.

In [10]:
# 허용하지 않은 source 필드가 포함되면 검증이 실패합니다.
from pydantic import ConfigDict

class ClosedStudyCard(StudyCard):
    model_config = ConfigDict(extra="forbid")

extra_data = {
    "concept": "AIMessage", "explanation": "모델 응답",
    "difficulty": 2, "source": "로컬 메모",
}
try:
    ClosedStudyCard.model_validate(extra_data)
except ValidationError as error:
    extra_error = error.errors()[0]
    print("거부된 필드:", extra_error["loc"][0])
    print("검증 오류:", extra_error["type"])
    assert extra_error["type"] == "extra_forbidden"
else:
    raise AssertionError("추가 필드는 거부되어야 합니다.")
출력:
거부된 필드: source
검증 오류: extra_forbidden

JSON 문법과 스키마 값 제약

json.loads는 JSON 문법을, Pydantic은 파싱된 객체의 필드·타입·범위를 검사합니다. 둘을 통과해도 주문이 실제로 존재하는지나 품명이 사실인지는 별도로 확인합니다.

In [11]:
# 정상 JSON을 파싱한 뒤 주문 내용 규칙을 검증합니다.
import json

class OrderItem(BaseModel):
    product_name: str = Field(min_length=1, description="품명")
    quantity: int = Field(ge=1, description="1 이상의 수량")

valid_text = '{"product_name": "노트", "quantity": 2}'
parsed_order = json.loads(valid_text)
valid_order = OrderItem.model_validate(parsed_order)
print("JSON 형식: 통과")
print("주문 내용:", valid_order.model_dump())
출력:
JSON 형식: 통과
주문 내용: {'product_name': '노트', 'quantity': 2}
In [12]:
# JSON 형식 오류와 주문 내용 오류를 각각 확인합니다.
broken_text = '{"product_name": "노트", "quantity": 2'
try:
    json.loads(broken_text)
except json.JSONDecodeError as error:
    print("JSON 형식 오류:", type(error).__name__)

wrong_content = '{"product_name": "노트", "quantity": 0}'
parsed_wrong = json.loads(wrong_content)
try:
    OrderItem.model_validate(parsed_wrong)
except ValidationError as error:
    content_error = error.errors()[0]
    print("주문 내용 오류:", content_error["type"])
    assert content_error["type"] == "greater_than_equal"
else:
    raise AssertionError("수량 0은 거부되어야 합니다.")
출력:
JSON 형식 오류: JSONDecodeError
주문 내용 오류: greater_than_equal

확인할 점 일반 호출과 구조화 호출의 반환 타입을 구분합니다. card.model_dump()의 세 필드가 스키마와 대응하는지 읽고 난이도가 허용 범위에 있는지 확인합니다. 자연스러운 설명 문장만 보고 형식 검증이 성공했다고 추측하지 않습니다.

이후 실제 모델에 “difficulty는 반드시 9로 쓰세요”라는 요구를 보냅니다. 1~3이라는 스키마 제약과 맞지 않는 입력입니다. 결과의 parsed와 parsing_error를 함께 읽습니다. 저장된 실행에서는 모델이 허용 범위의 값을 반환해 parsing_error가 None이었습니다. 따라서 이 호출에서 구조화 출력의 검증 실패를 관찰했다고 말할 수 없습니다. 충돌하는 입력을 보내도 어떤 응답이 나오는지는 모델과 형식 지원에 따라 달라집니다.

6일부러 실패해 보기

모델 호출에서 오류가 나지 않았더라도 프로그램의 오류 처리 경로를 확인할 수 있습니다. 아래 비교는 직접 만든 딕셔너리에 Pydantic 검증을 적용하는 로컬 실습입니다. 이 자료를 모델이 생성한 것으로 표시하지 않습니다.

앞의 실행 예제를 실행한 같은 노트북에서 Before 다음 After 순서로 실행합니다. 출력은 실제 실행 결과입니다.

Before — 실패 코드

실패 재현

In [13]:
# 범위 밖 7을 직접 넣어 예상한 Pydantic ValidationError 유형만 처리합니다.
from pydantic import ValidationError

bad_data = {"concept": "AIMessage", "explanation": "모델 응답", "difficulty": 7}
try:
    StudyCard.model_validate(bad_data)
except ValidationError as error:
    print("관찰한 검증 오류:", error.errors()[0]["type"])
else:
    raise AssertionError("범위를 벗어난 값은 거부되어야 합니다.")
출력:
관찰한 검증 오류: less_than_equal

After — 수정 코드

수정

In [14]:
# 다른 필드는 유지하고 difficulty만 2로 고쳐 검증된 객체를 만듭니다.
fixed_data = {"concept": "AIMessage", "explanation": "모델 응답", "difficulty": 2}
fixed_card = StudyCard.model_validate(fixed_data)
print(fixed_card.model_dump())
assert fixed_card.difficulty == 2
출력:
{'concept': 'AIMessage', 'explanation': '모델 응답', 'difficulty': 2}

Before는 난이도 7을 넣어 less_than_equal 오류를 확인합니다. 이 이름은 값이 설정된 상한 이하여야 한다는 조건을 뜻합니다. After는 개념 이름과 설명을 유지하고 난이도만 2로 바꿉니다. 같은 스키마로 객체가 만들어졌다면 바꾼 값이 범위 검증에 영향을 주었다고 확인할 수 있습니다.

오류 처리 코드는 예상한 ValidationError만 잡습니다. 모든 예외를 같은 검증 오류로 처리하면 인터넷 연결 문제와 데이터 문제를 구분하기 어렵습니다. 실제 프로그램에서는 잘못된 값의 원본과 제약을 확인하고 수정 가능한 입력인지 판단합니다.

7주의할 점과 실무 메모

Pydantic은 기본 설정에서 일부 입력을 선언된 타입으로 변환합니다. 타입 이름을 적었다는 이유만으로 원래 입력의 타입까지 엄격하게 제한했다고 생각하지 않습니다. 엄격 모드를 기존 프로그램에 적용하면 이전에 변환되어 통과하던 값이 실패할 수 있으므로 입력 출처별로 먼저 관찰합니다.

형식이 맞는 답에도 잘못된 정보가 들어갈 수 있습니다. 필드의 존재·타입·범위 검증과 내용의 사실 확인은 다른 작업입니다. 이 장에서 만든 형식 검증 경험은 Ch 7의 출력 프롬프트 설계와 Ch 11의 평가 기준을 구분하는 데 사용합니다. 에이전트의 자동 출력 전략은 아직 구현하지 않습니다.

8정리와 다음 절

  • 스키마에 필드·타입·값의 범위를 선언하고 구조화된 객체를 받습니다.
  • 원본 응답, 파싱한 값, 오류를 나누어 읽으면 실패한 위치를 찾을 수 있습니다.
  • 직접 만든 자료의 범위 검증과 실제 모델 응답의 형식 검증은 다른 실험입니다.

다음 절에서는 응답을 다 받을 때까지 기다리는 대신 도착하는 조각을 읽습니다. 조각이 아직 완성되지 않았을 때와 최종 결과를 검사할 때를 구분하는 데 이번 절의 파싱·검증 개념을 사용합니다.

9복습 문제

문제 1 · 설명과 제약

description="난이도는 1~3"만 적는 것과 ge=1, le=3도 선언하는 것은 어떻게 다른가요?

해설 전자는 필드 뜻에 관한 설명이고 후자는 검증할 수치 범위입니다. 프로그램이 값의 상한·하한을 검사하도록 하려면 해당 제약을 선언합니다.

문제 2 · 미관찰 결과

난이도 9를 요구했는데 유효한 카드가 반환됐습니다. 검증 실패가 재현됐다고 적어도 되나요?

해설 안 됩니다. 실제 파싱 오류가 없었다면 그 실행에서 검증 실패를 관찰하지 못한 것입니다. 충돌 입력과 실제 응답을 함께 기록합니다.

문제 3 · 로컬 오류 처리

Before와 After에서 고정한 것과 바꾼 것은 무엇인가요?

해설 스키마·개념 이름·설명은 고정하고 난이도만 7에서 2로 바꿨습니다. 이 비교는 Pydantic의 범위 검증을 보여 주며 모델의 오류 발생률을 측정하지 않습니다.

문제 4 · 내용 확인

스키마를 통과한 카드에 잘못된 개념 설명이 있습니다. 검증 라이브러리가 고장 난 것인가요?

해설 형식과 내용은 별도로 확인해야 합니다. 필드와 값 범위는 맞아도 설명은 틀릴 수 있습니다. 공식 자료나 정해 둔 정답 기준과 설명을 대조합니다.
