1학습 목표

  • ChatPromptTemplate으로 메시지 틀을 만들 수 있습니다.
  • MessagesPlaceholder에 선택적 대화 기록을 삽입할 수 있습니다.
  • 템플릿 변수와 완성된 메시지를 구분하여 검사할 수 있습니다.

2이 내용을 배우는 이유

문자열을 더하여 프롬프트를 만들면 변수의 경계와 메시지 역할을 놓치기 쉽습니다. 질문이 바뀔 때마다 system 문구까지 복사하면 수정본이 여러 곳에 생깁니다. ChatPromptTemplate은 변하지 않는 메시지 구조와 실행할 때 채울 값을 구분합니다. 같은 형식을 여러 문의에 재사용하면서도 실제 모델에 전달된 메시지 목록을 확인할 수 있습니다.

대화형 서비스에는 과거 메시지가 있을 때도 있고 첫 요청처럼 없을 때도 있습니다. MessagesPlaceholder는 이미 만들어진 메시지 목록을 지정한 위치에 삽입합니다. 다만 기록을 많이 넣으면 비용과 혼동이 늘 수 있습니다. 이 절에서는 작은 기록 한 턴만 사용하여 구조를 확인하고, 길이 예산과 선택은 Ch 8에서 다룹니다.

3앞에서 배운 내용

01절에서 system과 user 메시지의 책임을 구분했고, 03절에서는 예시 입출력 쌍을 메시지에 추가했습니다. 이제 그 구조를 재사용 가능한 틀로 표현합니다. 모델 호출, AIMessage.text, 사용량 기록은 같습니다. 노트북은 기록 없음과 한 턴 있음의 두 조건을 실행합니다.

4핵심 개념

양식과 작성값을 나눕니다

신청서 양식에는 “이름”, “연락처”, “요청 내용”이라는 칸이 있고 사람마다 다른 값을 채웁니다. 프롬프트 템플릿도 고정 문장 속 {format_rule}과 {question} 자리에 실행값을 넣습니다. 양식 자체를 수정하지 않아도 여러 질문을 같은 구조로 처리할 수 있습니다.

정의

프롬프트 템플릿 (prompt template)
고정 메시지와 나중에 채울 변수를 함께 정의한 재사용 가능한 틀입니다.
ChatPromptTemplate
여러 역할의 채팅 메시지를 순서대로 구성하고 변수 값을 받아 완성된 프롬프트 값을 만드는 LangChain 클래스입니다.
템플릿 변수
{question}처럼 실행할 때 실제 값으로 바뀌는 자리입니다.
MessagesPlaceholder
문자열 한 개가 아니라 메시지 객체 목록을 템플릿의 지정 위치에 삽입합니다.
optional=True
해당 메시지 목록이 없어도 템플릿을 완성할 수 있게 하는 설정입니다.
n_messages
목록 뒤쪽에서 포함할 최근 메시지 수를 제한하는 선택 인자입니다.

도식 — 틀에 값을 넣고 메시지 목록을 확인합니다

문자열 변수와 메시지 목록은 다릅니다

{question}에는 텍스트가 들어갑니다. 반면 history에는 ("human", "..."), ("ai", "...")처럼 역할을 가진 메시지 목록이 들어갑니다. 과거 대화를 하나의 긴 문자열로 합치면 누가 어떤 말을 했는지 경계가 사라질 수 있습니다. MessagesPlaceholder는 역할과 순서를 유지한 채 목록을 삽입합니다.

템플릿의 invoke와 모델의 invoke는 다른 단계입니다

ChatPromptTemplate.from_messages(...)는 메시지의 틀을 만드는 클래스 메서드입니다. ("human", "{question}")에는 현재 질문 대신 변수 자리만 들어 있습니다. 일반 문자열의 {question}을 템플릿이 읽고, 이후 base_values["question"]의 값으로 채웁니다. Python f 문자열처럼 정의 즉시 치환되는 코드와 구분합니다.

prompt.invoke(base_values)는 빈칸을 채워 ChatPromptValue를 만듭니다. 여기서 invoke를 호출해도 모델 서버에 질문하지 않습니다. 이어 붙인 .to_messages()가 이를 역할 있는 메시지 객체 목록으로 바꿉니다. 실제 모델 요청은 그 목록을 run(first_messages)에 넘겼을 때 함수 안의 model.invoke()에서 발생합니다. 같은 메서드 이름이라도 점 앞의 객체가 무엇인지 확인해야 합니다.

예를 들어 번역 템플릿의 언어와 원문은 문자열 변수이고, 이전 번역 요청과 답의 쌍은 메시지 목록입니다. MessagesPlaceholder("history", optional=True)는 그 목록이 들어갈 위치를 정합니다. 이 객체가 과거 대화를 저장하거나 찾아 주는 것은 아닙니다. 현재 코드가 history 값을 넘긴 경우에만 해당 메시지가 목록에 삽입됩니다. n_messages는 메시지 개수 기준이므로 대화 한 턴과 메시지 하나를 같게 세지 않습니다.

선택적 기록과 필수 기록을 구분합니다

기본 MessagesPlaceholder("history")는 값을 요구합니다. 첫 요청에는 기록이 없으므로 변수를 넘기지 않으면 템플릿 완성 단계에서 오류가 날 수 있습니다. optional=True를 사용하면 기록이 없는 경우 빈 목록처럼 처리할 수 있습니다. 이 설정은 과거 대화를 임의로 무시한다는 뜻이 아니라, 기록이 없어도 정상인 입력 형태를 명시한 것입니다.

완성된 메시지를 먼저 봅니다

템플릿 코드가 의도대로 보여도 변수 값에 중괄호가 남거나 메시지 순서가 바뀔 수 있습니다. 모델을 호출하기 전에 prompt.invoke(values).to_messages()를 출력하면 각 메시지의 역할과 내용을 확인할 수 있습니다. 디버깅에서는 템플릿 원문, 입력값, 완성 메시지, 모델 응답을 서로 다른 단계로 보존합니다.

최근 메시지만 자를 때 잃는 정보가 있습니다

n_messages로 최근 몇 개만 남길 수 있지만 오래된 정책이나 고객의 중요한 요구도 함께 사라질 수 있습니다. 단순히 메시지 수가 줄었다는 사실은 품질 개선을 뜻하지 않습니다. 무엇을 보존할지 정하고 원문과 대조해야 합니다. 이 문제는 Ch 8의 Select와 Compress에서 더 자세히 다룹니다.

5실행 예제

템플릿은 system 지시, 선택적 history, 현재 human 질문 순서입니다. 첫 실행은 history를 넘기지 않아 메시지 두 개를 만듭니다. 둘째 실행은 고객의 “세 줄 이내” 요청과 이전 답을 추가하여 메시지 네 개를 만듭니다. 현재 고객 문의와 평가 기준은 같습니다.

MENTIONS = ["교환", "A-1042", "사진"]

측정 함수

단어 포함 표시는 원문 정독을 돕는 표시이며 품질 점수가 아닙니다.

run(messages)는 이 노트북에서 작성하는 보조 함수입니다. 역할·내용 목록을 받아 model.invoke()를 한 번 실행하고, 답 문자열·사용량·경과 초를 담은 딕셔너리를 반환합니다. def 셀은 함수를 정의할 뿐이며 뒤에서 run(...)을 호출할 때 모델 요청이 시작됩니다. mention_flags(text)는 지정 단어가 문자열에 있는지 표시한 딕셔너리를 반환합니다. 답의 뜻을 판단하는 모델 호출은 포함하지 않습니다.

In [4]:
# 모델 응답의 원문, 사용량, 경과 시간을 한 레코드로 보존합니다.
def run(messages):
    started = time.perf_counter()
    answer = model.invoke(messages)
    return {"text": answer.text, "usage": answer.usage_metadata,
            "latency_s": round(time.perf_counter() - started, 3)}

def mention_flags(text):
    return {word: word in text for word in MENTIONS}

메시지 템플릿 만들기

MessagesPlaceholder(optional=True)는 기록이 없는 첫 요청도 같은 틀로 처리합니다.

from_messages()는 고정 메시지와 빈칸으로 템플릿을 만드는 클래스 메서드입니다. {format_rule}와 {question}은 실행 때 값으로 채울 변수 자리입니다. base_values가 같은 이름의 키로 값을 제공합니다. 여기서는 문자열 앞에 f가 없으므로 Python이 미리 값을 채우는 방식이 아닙니다.

prompt.invoke(base_values)는 완성한 ChatPromptValue를 만들고 .to_messages()가 역할 있는 메시지 객체 목록으로 바꿉니다. 이 단계는 모델을 호출하지 않습니다. 다음 run(first_messages)의 내부에서 model.invoke()를 실행할 때 요청이 발생합니다.

MessagesPlaceholder("history", optional=True)는 과거 메시지 목록을 삽입할 자리입니다. 기억을 저장하는 기능이 아니며 값이 없으면 빈 목록으로 처리합니다. 다음 셀은 human 질문과 ai 답이라는 메시지 두 개로 한 턴을 추가합니다. {**base_values, "history": ...}는 기존 딕셔너리 항목을 펼친 새 딕셔너리에 history를 추가하는 Python 표기입니다.

In [5]:
# optional placeholder는 기록이 없는 첫 요청에서도 메시지 틀을 완성합니다.
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "고객 지원 답변을 {format_rule} 형식으로 작성하세요."),
    MessagesPlaceholder("history", optional=True),
    ("human", "{question}"),
])
base_values = {"format_rule": "분류/다음 행동/고객 문장", "question": TASK}
first_messages = prompt.invoke(base_values).to_messages()
print([(m.type, m.text[:80]) for m in first_messages])
출력:
[('system', '고객 지원 답변을 분류/다음 행동/고객 문장 형식으로 작성하세요.'), ('human', '고객 문의: 어제 받은 텀블러 뚜껑이 깨졌습니다. 주문번호는 A-1042입니다.\n새 상품으로 바꾸고 싶습니다. 회사 규정상 교환 접수에는 파손 ')]

기록 없음과 한 건 있음 비교

과거 고객 요청 한 건만 추가하고 현재 질문과 평가 기준은 유지합니다.

In [6]:
# 기록 없음과 한 턴 기록의 완성 메시지를 각각 호출합니다.
first = run(first_messages)
with_history = prompt.invoke({**base_values, "history": [
    ("human", "답변을 세 줄 이내로 써 주세요."),
    ("ai", "알겠습니다. 이후 답변을 세 줄 이내로 작성하겠습니다."),
]}).to_messages()
second = run(with_history)
print("메시지 수:", len(first_messages), len(with_history))

기록을 추가한 조건은 입력 토큰이 38 늘고 출력 토큰도 4 늘어 전체 토큰은 42 증가했습니다. 과거 요청이 짧은 형식을 요구했기 때문으로 해석할 수 있으나, 한 번의 출력만으로 인과를 확정할 수는 없습니다. 중요한 관찰은 선택적 placeholder가 기록이 없을 때와 있을 때 모두 같은 템플릿을 완성했고, 메시지 역할과 순서를 유지했다는 점입니다.

두 조건 모두 과업을 충족했으므로 기록 없음 조건을 실패로 부르지 않습니다. 기록을 추가하면 언제나 더 좋은 답이 나온다는 결과도 아닙니다. 실제 서비스에서는 기록이 현재 질문과 관련 있는지, 이전의 민감 정보가 포함되는지, 오래된 제약이 현재 정책과 맞는지 추가로 확인해야 합니다.

7주의할 점과 실무 메모

  • optional=True는 기록이 없어도 정상인 경우에만 사용합니다.
  • placeholder에는 문자열이 아니라 역할이 있는 메시지 목록을 전달합니다.
  • 변수 이름이 템플릿과 입력 딕셔너리에서 일치하는지 확인합니다.
  • 모델 호출 전에 to_messages()로 역할과 순서를 검사합니다.
  • 대화 기록을 무제한으로 넣지 말고 개인정보와 오래된 지시를 검토합니다.

8정리와 다음 절

  • ChatPromptTemplate은 고정 구조와 실행값을 분리합니다.
  • MessagesPlaceholder는 메시지의 역할과 순서를 유지합니다.
  • 기록 제한은 토큰 수뿐 아니라 잃는 정보까지 평가해야 합니다.
