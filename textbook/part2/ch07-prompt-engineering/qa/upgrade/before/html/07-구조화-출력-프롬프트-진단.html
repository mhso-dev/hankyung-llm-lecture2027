1학습 목표

  • JSON 파싱 성공과 필요한 필드 충족을 서로 다른 검사로 설명할 수 있습니다.
  • 같은 과제에서 출력 지시의 구체성만 바꾼 세 프롬프트를 비교할 수 있습니다.
  • 응답 원문을 보존하면서 json.loads()와 필드 존재 검사를 수행할 수 있습니다.

2이 내용을 배우는 이유

모델이 “JSON으로 답하라”는 요청을 따르면 프로그램이 바로 사용할 수 있을 것처럼 보입니다. 그러나 올바른 JSON 문법으로 작성되었다는 사실과 프로그램이 기대한 필드 이름·자료형·허용값을 지켰다는 사실은 다릅니다. 예를 들어 {"분류": "교환"}은 문법상 올바른 JSON이지만 프로그램이 category를 읽으면 키를 찾지 못합니다. 다음 행동이 문자열이어야 하는데 목록으로 생성되어도 파싱 자체는 성공할 수 있습니다.

이번 절은 프롬프트 문장만으로 구조를 요청했을 때 무엇을 진단해야 하는지 보여 줍니다. Ch 6에서 배운 Pydantic 기반 구조화 출력은 스키마와 모델 호출을 직접 연결하는 방법입니다. 여기서는 그 기능을 대체하려 하지 않고, 프롬프트 지시와 문자열 파싱만 사용한 경로의 한계를 관찰합니다.

3앞에서 배운 내용

Ch 6의 ‘구조화 출력과 검증’ 절에서는 Pydantic 모델로 필드 이름, 타입, 허용 범위를 선언하고 with_structured_output(..., include_raw=True)의 raw, parsed, parsing_error를 확인했습니다. 이번 챕터에서는 역할별 메시지, 과업 제약, 관련 예시가 출력에 미치는 영향을 비교했습니다. 이번 실습은 모델과 고객 문의를 고정하고 JSON을 요구하는 user 메시지의 구체성만 세 단계로 바꿉니다.

4핵심 개념

파싱, 필드, 자료형

파싱(parsing)은 문자열을 프로그램이 다룰 수 있는 자료 구조로 읽는 과정입니다. Python의 json.loads()는 JSON 문자열을 사전이나 목록 같은 객체로 변환합니다. JSON 문법이 깨져 있으면 JSONDecodeError가 발생합니다. 파싱 성공은 중괄호, 따옴표, 쉼표 같은 문법을 읽을 수 있었다는 뜻입니다.

필드(field)는 객체 안에서 값을 찾는 이름입니다. 이번 프로그램은 category, next_action, customer_message 세 필드를 요구합니다. 필드 존재 검사(field presence check)는 각 이름이 파싱된 객체에 있는지 확인합니다. 스키마(schema)는 필요한 필드, 자료형, 허용값 같은 구조 규칙을 모아 둔 정의입니다. 실습의 schema 프롬프트는 세 필드와 category의 허용값, 모든 필드가 문자열이라는 조건을 자연어로 적습니다. 자연어 스키마는 설명일 뿐이므로 Python 검증 코드가 자동으로 생기지는 않습니다.

세 단계 진단

brief는 JSON이라는 형식만 요구합니다. fields는 세 필드 이름을 추가합니다. schema는 코드 울타리나 부가 설명을 금지하고 필드 이름, 허용 분류, 문자열 자료형을 지정합니다. 비교할 때는 첫째로 원문이 JSON 문법인지, 둘째로 세 필드가 있는지, 셋째로 각 값의 자료형과 내용이 요구 조건에 맞는지 확인합니다. 이번 코드가 자동 검사하는 범위는 첫째와 둘째입니다. 셋째는 원문 정독으로 확인하며, 운영 코드에서는 Pydantic 같은 검증기를 사용해야 합니다.

구문 오류(syntax error)는 JSON 문법을 읽지 못한 상태입니다. 구조 오류는 파싱되었지만 필요한 필드나 자료형이 맞지 않는 상태입니다. 내용 오류는 구조가 맞아도 분류나 고객 안내가 업무 규정과 맞지 않는 상태입니다. 오류 층을 나누면 프롬프트를 고칠지, 스키마 검증을 추가할지, 업무 자료를 보완할지 결정할 수 있습니다.

도식 읽기

JSON을 읽는 것과 필요한 필드를 검증하는 것

json.loads(result["text"])는 모델 응답인 문자열을 Python 값으로 읽습니다. JSON에는 객체뿐 아니라 목록, 문자열, 숫자도 있으므로 파싱이 성공했다고 딕셔너리가 만들어졌다고 가정하면 안 됩니다. 아래 저장 원문은 객체였지만 실제 프로그램에서는 먼저 기대한 자료형인지 검사해야 합니다. 자연어로 JSON을 요청하는 방식과 Ch 6의 구조화 출력 호출도 같은 기능으로 취급하지 않습니다.

진단 코드의 f in parsed는 현재 객체에 필요한 키가 있는지를 확인합니다. 예를 들어 category 키의 값이 빈 문자열이어도 키는 존재합니다. 값이 “알 수 없음”이어도 허용 라벨 검사 없이 키 존재 결과만 참이 됩니다. 따라서 파싱 성공, 객체 여부, 필드 존재, 값의 타입, 허용 범위, 업무 사실은 차례로 다른 질문입니다.

일정 추출에 적용하면 “일시”와 “장소”가 담긴 JSON이 문법상 유효해도 프로그램이 요구한 starts_at과 location 키는 없을 수 있습니다. 키를 맞춰도 날짜 형식이나 장소의 실제 존재는 아직 확인하지 않았습니다. 이런 사례를 층별로 나누어 보면 프롬프트를 더 구체화할 부분과 코드로 검증할 부분을 구별할 수 있습니다.

5실행 예제

측정 함수

단어 포함 표시는 원문 정독을 돕는 표시이며 품질 점수가 아닙니다.

run(messages)는 이 노트북에서 작성하는 보조 함수입니다. 역할·내용 목록을 받아 model.invoke()를 한 번 실행하고, 답 문자열·사용량·경과 초를 담은 딕셔너리를 반환합니다. def 셀은 함수를 정의할 뿐이며 뒤에서 run(...)을 호출할 때 모델 요청이 시작됩니다. mention_flags(text)는 지정 단어가 문자열에 있는지 표시한 딕셔너리를 반환합니다. 답의 뜻을 판단하는 모델 호출은 포함하지 않습니다.

In [4]:
# 모델 응답의 원문, 사용량, 경과 시간을 한 레코드로 보존합니다.
def run(messages):
    started = time.perf_counter()
    answer = model.invoke(messages)
    return {"text": answer.text, "usage": answer.usage_metadata,
            "latency_s": round(time.perf_counter() - started, 3)}

def mention_flags(text):
    return {word: word in text for word in MENTIONS}

질문과 필요한 필드는 같고 JSON 지시의 구체성만 다릅니다.

In [5]:
# 질문은 고정하고 JSON 지시의 구체성만 세 단계로 바꿉니다.
prompts = {
    "brief": "JSON으로 답하세요. " + TASK,
    "fields": "JSON 객체로 답하세요. 필드는 category, next_action, customer_message입니다. " + TASK,

실제 파싱과 필드 검사

파싱 실패를 가정하지 않고 각 원문에 json.loads를 실제 적용합니다.

json.loads()의 입력은 응답 문자열이고 반환값은 JSON 내용에 대응하는 Python 값입니다. JSON 객체는 딕셔너리, 배열은 목록이 됩니다. 파싱 성공만으로 원하는 객체나 필드를 받았다고 볼 수 없습니다. 이번에 저장된 세 응답은 객체이지만 일반 입력에 대한 자료형 검증까지 이 코드가 수행하는 것은 아닙니다.

{f: f in parsed for f in fields}는 필요한 필드별로 키가 있는지 표시하는 사전 표현식입니다. 키 값의 타입·허용값·빈 문자열·업무 사실은 검사하지 않습니다. 예를 들어 빈 category도 키 자체가 있으면 이 검사에서는 참입니다.

일정 자료의 “일시”를 프로그램이 기대하는 starts_at으로 바꾸는 문제와 날짜가 실제로 맞는지 확인하는 문제도 다릅니다. 아래 결과에서는 파싱 성공과 영문 필드 충족부터 따로 읽고, 전체 검증이 끝났다고 해석하지 않습니다.

In [6]:
# json.loads 파싱 성공과 필요한 영문 필드 존재를 별도로 기록합니다.
diagnostics = {}
for name, result in results.items():
    try:
        parsed = json.loads(result["text"])
        fields = ["category", "next_action", "customer_message"]
        diagnostics[name] = {"parsed": True, "fields": {f: f in parsed for f in fields}}
    except (json.JSONDecodeError, TypeError) as error:
        diagnostics[name] = {"parsed": False, "error": type(error).__name__}
print(json.dumps(diagnostics, ensure_ascii=False, indent=2))

6실험 결과 해석

이번 실행에서는 brief, fields, schema 세 응답 모두 json.loads()로 파싱되었습니다. 따라서 이 세 표본에서는 JSON 구문 오류를 관찰하지 못했습니다. 그러나 brief 응답은 ‘분류’, ‘필요한 다음 행동’, ‘고객에게 보낼 한 문장’이라는 한국어 키를 사용했습니다. 프로그램이 요구한 category, next_action, customer_message는 모두 없었습니다. 또한 ‘필요한 다음 행동’ 값은 문자열이 아니라 두 항목의 목록이었습니다.

fields와 schema 응답은 요구한 세 영문 필드를 모두 포함했습니다. schema 응답의 category는 허용값 중 하나인 ‘교환’이었고 세 값도 문자열로 보였습니다. 입력 토큰은 지시가 구체해지면서 98, 110, 137토큰으로 늘었습니다. 전체 토큰은 각각 244, 199, 243토큰이어서 입력이 길어진 순서와 같지 않았습니다. 출력 길이도 함께 달라졌기 때문입니다.

세 번의 성공은 자연어 스키마가 항상 지켜진다는 증거가 아닙니다. 호출은 조건마다 한 번뿐이며 자동 진단 코드도 필드의 존재까지만 검사합니다. 허용값, 자료형, 추가 필드, 빈 문자열, 업무 내용의 정확성을 강제하려면 명시적인 스키마 검증이 필요합니다. 구조가 맞아도 파손 사진이 필요한 규정을 잘못 설명할 수 있으므로 내용 평가는 별도로 수행합니다.

7주의할 점과 실무 메모

  • 응답을 정규식으로 잘라 JSON처럼 보이는 부분만 파싱하면 앞뒤의 오류나 지시 위반이 사라질 수 있습니다. 진단 단계에서는 원문 전체를 보존합니다.
  • 필드가 있다는 사실만 검사하면 값의 자료형과 허용 범위를 놓칩니다. 운영 경로에서는 Pydantic 스키마로 필드 설명과 제약을 선언합니다.
  • 파싱 실패 원문에 고객 개인정보가 포함될 수 있습니다. 로그 저장 범위와 마스킹 규칙을 먼저 정합니다.
  • 모델별 구조화 출력 지원 방식이 다를 수 있습니다. LangChain 공통 인터페이스를 사용해도 제공자 문서와 고정 환경에서 실제 지원 범위를 확인합니다.
  • 재시도로 우연히 성공한 결과만 남기지 않습니다. 첫 실패 원문과 재시도 횟수, 추가 비용을 함께 기록해야 원인을 진단할 수 있습니다.

8정리와 다음 절

  • JSON 파싱 성공은 문법을 읽었다는 뜻이며 필요한 필드와 자료형을 보장하지 않습니다.
  • 출력 지시에 필드와 허용값을 적으면 이번 표본에서는 구조가 더 구체적으로 나타났습니다.
  • 프로그램에서 사용할 값은 명시적인 스키마와 내용 평가로 다시 확인해야 합니다.

다음 학습과 이어지는 지점 — 다음 절에서는 프롬프트 문구와 변경 이유를 버전별 아티팩트로 저장하고, 동일한 평가 조건으로 세 버전을 비교합니다.

9복습 문제

문제 1

brief 응답은 파싱에 성공했는데 왜 프로그램의 요구를 충족하지 못했나요?

해설 — JSON 문법은 맞았지만 프로그램이 찾는 세 영문 필드가 없었고 다음 행동의 자료형도 목록이었습니다.

문제 2

필드 존재 검사만으로 category가 허용값인지 확인할 수 있나요?

해설 — 확인할 수 없습니다. 필드가 존재하는지와 값이 ‘배송’, ‘교환’, ‘환불’ 중 하나인지는 별도의 검사입니다.

문제 3

세 응답이 모두 파싱된 결과를 다른 질문에도 일반화하면 안 되는 이유는 무엇인가요?

해설 — 각 조건을 한 번만 호출했고 입력과 생성 결과가 바뀌면 코드 울타리, 부가 설명, 잘못된 자료형이 나타날 수 있기 때문입니다.

문제 4

구조 검증을 통과한 응답에도 내용 평가가 필요한 이유는 무엇인가요?

해설 — 필드와 자료형이 맞아도 분류가 틀리거나 업무 규정에 없는 안내를 생성할 수 있기 때문입니다.
