2이 내용을 배우는 이유

“친절한 상담원처럼 답하세요”는 답변의 말투와 관점을 알려 줍니다. 그러나 무엇을 분류하고 어떤 정보를 포함하며 무엇을 약속하지 말아야 하는지는 알려 주지 않습니다. 실제 업무에서는 친절한 문장보다 주문번호, 다음 행동, 회사 규정이 빠지지 않는 것이 먼저입니다. 페르소나는 도움이 될 수 있지만 과업 명세를 대신하지 못합니다.

이 절에서는 같은 상담원 페르소나를 유지한 채 과업·금지 조건·출력 형식을 추가합니다. 첫 응답이 이미 충분할 수도 있습니다. 실패를 만들려고 질문이나 규정을 바꾸지 않고, 두 원문이 고정된 요구를 어떻게 표현했는지 정직하게 비교합니다.

3앞에서 배운 내용

01절에서 공통 역할을 system, 개별 고객 문의를 user에 두었습니다. 이 절도 같은 텀블러 파손 문의와 gpt-5.4-mini를 사용합니다. 교환, 주문번호 A-1042, 파손 사진이라는 세 단어 포함 여부는 정독 보조 표시로만 사용합니다. 실제 품질은 부정 표현과 문장 뜻을 포함하여 원문을 읽고 판단합니다.

4핵심 개념

직함과 업무 요청서를 구분합니다

새 상담원에게 “당신은 친절한 상담원입니다”라고만 말하면 태도는 알 수 있지만 처리 절차는 알 수 없습니다. 업무 요청서에는 파손 상품을 교환으로 분류하고, 주문번호와 사진을 확인하며, 규정 밖 보상을 약속하지 말라는 내용이 필요합니다. 프롬프트도 같은 방식으로 성격 설명과 수행 조건을 나누어 작성합니다.

정의

페르소나 (persona)
모델이 답할 때 취할 역할, 관점, 말투를 설명한 것입니다. 전문성의 범위를 좁히는 데 도움을 주지만 사실 정확성이나 절차 준수를 보장하지 않습니다.
과업 (task)
입력을 받아 어떤 결과를 만들어야 하는지 구체적으로 적은 일입니다.
성공 기준 (success criteria)
결과가 목적을 충족했다고 판단할 수 있는 관찰 가능한 조건입니다.
부정 제약 (negative constraint)
규정에 없는 보상 약속처럼 결과에 포함하면 안 되는 행동을 적은 조건입니다.
출력 형식 (output format)
세 줄, 필드 이름, JSON처럼 결과를 배열하는 모양입니다.

도식 — 페르소나를 과업 명세로 둘러쌉니다

좋은 제약은 확인할 수 있습니다

“좋게 답하세요”는 사람마다 판단이 달라집니다. “분류, 다음 행동, 고객 문장을 세 줄로 작성하세요”는 결과에서 바로 확인할 수 있습니다. “절대로 실수하지 마세요”도 실행 가능한 행동을 알려 주지 않습니다. 대신 “규정에 없는 환불이나 보상을 약속하지 마세요”처럼 금지 대상을 적습니다. 제약이 많아질수록 좋아지는 것도 아닙니다. 서로 겹치거나 충돌하는 문장이 늘면 어떤 규칙을 적용해야 하는지 불분명해집니다.

목표와 형식의 역할이 다릅니다

출력 형식은 결과를 읽고 파싱할 때 사용할 규칙을 정하지만 답에 필요한 정보를 채워 주지는 않습니다. 세 줄을 요구해도 어떤 정보를 넣을지 말하지 않으면 중요한 주문번호가 빠질 수 있습니다. 반대로 필수 정보를 모두 적어도 형식이 없으면 긴 상담 문장이 나올 수 있습니다. 목표, 필수 정보, 금지 사항, 형식은 서로 다른 질문에 답합니다. 프롬프트 검토 때 네 항목을 따로 읽어야 합니다.

페르소나를 행동으로 바꾸어 읽는 연습

“친절한 상담원”이라는 페르소나는 말투나 관점을 정하는 단서입니다. “교환 접수에 필요한 사진을 요청하세요”는 입력에서 수행할 행동입니다. “분류·다음 행동·고객 문장의 세 줄”은 출력 배치입니다. 같은 프롬프트에 함께 쓸 수 있지만 각각 무엇을 바꾸는지 나누어 읽으면 결과를 고칠 때 수정 지점을 찾을 수 있습니다.

다른 상황으로 회의록 작성을 생각해 봅니다. “숙련된 비서”만 지정하면 어떤 회의를 어떻게 정리할지는 남아 있습니다. 결정 사항, 담당자, 기한을 추출하되 언급되지 않은 기한은 미정으로 표시하도록 지시하면 확인할 항목과 누락 처리 방식이 정해집니다. 비서라는 역할과 달리 이 조건들은 원문 회의록에서 항목별로 대조할 수 있습니다. 이는 적용 원리를 설명하는 사례이며 아래 모델 실행은 고객 문의로 진행합니다.

금지 조건에도 수행 가능한 다음 행동이 필요합니다. “주문번호를 추측하지 마세요”와 함께 “없으면 주문번호 확인을 요청하세요”를 적으면 정보가 부족할 때의 응답이 구체화됩니다. 모든 상황에 답을 만들어 내도록 요구하면 부족한 정보와 완료된 처리를 구분하기 어렵습니다. 현재 과제에는 주문번호가 있으므로 실제 결과에서 그 값을 정확히 유지했는지 확인합니다.

측정 함수

단어 포함 표시는 원문 정독을 돕는 표시이며 품질 점수가 아닙니다.

run(messages)는 이 노트북에서 작성하는 보조 함수입니다. 역할·내용 목록을 받아 model.invoke()를 한 번 실행하고, 답 문자열·사용량·경과 초를 담은 딕셔너리를 반환합니다. def 셀은 함수를 정의할 뿐이며 뒤에서 run(...)을 호출할 때 모델 요청이 시작됩니다. mention_flags(text)는 지정 단어가 문자열에 있는지 표시한 딕셔너리를 반환합니다. 답의 뜻을 판단하는 모델 호출은 포함하지 않습니다.

In [4]:
# 모델 응답의 원문, 사용량, 경과 시간을 한 레코드로 보존합니다.
def run(messages):
    started = time.perf_counter()
    answer = model.invoke(messages)
    return {"text": answer.text, "usage": answer.usage_metadata,
            "latency_s": round(time.perf_counter() - started, 3)}

def mention_flags(text):
    return {word: word in text for word in MENTIONS}

페르소나만 지정

친절한 상담원이라는 성격만 지정합니다.

페르소나는 답하는 사람의 역할·말투·관점을 지정한 설명입니다. 아래 첫 조건의 “친절한 고객 상담원”은 태도에 관한 문장이고, 다음 조건의 세 줄 형식과 규정 밖 약속 금지는 수행 조건입니다. 두 번째 조건이 더 길다는 사실 자체를 품질 개선으로 해석하지 않습니다.

회의록 정리에서는 “숙련된 비서”라는 역할에 결정 사항·담당자·기한을 추출하라는 과업과 미정 기한을 추측하지 말라는 조건을 따로 붙일 수 있습니다. 같은 구분을 고객 문의에 적용해 말투, 필수 정보, 금지 사항, 출력 배열을 각각 읽습니다.

persona와 bounded는 함수가 아니라 run()이 반환한 결과 딕셔너리입니다. result["text"]는 모델이 생성한 원문이고 len(...)은 그 문자열의 글자 수입니다. 요청에 쓴 글자 수나 토큰 수와 구분합니다.

결과 비교

같은 세 평가 항목과 응답 길이를 함께 확인합니다.

In [7]:
# 페르소나 조건과 구체 제약 조건의 글자 수·토큰·지연을 원문 이름과 연결합니다.
for name, result in {"persona": persona, "task_constraints": bounded}.items():
    print(name, mention_flags(result["text"]), "글자 수", len(result["text"]),
          "토큰", result["usage"], "지연", result["latency_s"])
출력:
persona {'교환': True, 'A-1042': True, '사진': True} 글자 수 220 토큰 {'input_tokens': 96, 'output_tokens': 125, 'total_tokens': 221, 'input_token_details': {'audio': 0, 'cache_read': 0}, 'output_token_details': {'audio': 0, 'reasoning': 0}} 지연 1.287
task_constraints {'교환': True, 'A-1042': True, '사진': True} 글자 수 176 토큰 {'input_tokens': 134, 'output_tokens': 109, 'total_tokens': 243, 'input_token_details': {'audio': 0, 'cache_read': 0}, 'output_token_details': {'audio': 0, 'reasoning': 0}} 지연 1.235

확인할 점 — 최종 실행에서 첫 응답은 220자, 제약을 추가한 응답은 176자였습니다. 두 원문 모두 교환, A-1042, 사진을 올바른 뜻으로 포함했습니다. 제약 조건은 실패를 고친 것이 아니라 이미 충족한 내용을 더 일정한 세 줄 구조로 표현하게 했습니다.

6실험 결과 해석

입력 지시가 길어져 전체 토큰은 늘었지만 출력 글자 수는 줄었습니다. 전체 토큰은 입력과 출력의 합이므로 짧은 답이 항상 더 적은 전체 토큰을 뜻하지 않습니다. 두 조건 모두 과업을 충족했으므로 페르소나 조건의 실패를 재현했다고 표시하지 않습니다. 이번 과업·제약 조건의 응답에서는 요청한 세 줄 배열을 확인했습니다. 앞으로의 모든 응답이 같은 형식을 따르는지는 이 한 번의 출력으로 알 수 없습니다.

지연 시간은 약 0.05초 달랐지만 한 번의 실행으로 속도 차이를 일반화할 수 없습니다. 반복 측정에서는 프롬프트 외에 모델, 생성 상한, 입력을 고정하고 중앙값이나 분포를 봅니다. 또한 고객에게 실제로 보낼 문장이라면 회사 정책 담당자가 문구를 검토해야 합니다.

7주의할 점과 실무 메모

  • 전문가 페르소나는 실제 자격이나 사실 검증을 만들지 않습니다.
  • 금지 제약만 나열하지 말고 원하는 행동도 함께 적습니다.
  • “항상”, “절대” 같은 표현은 실제 예외가 없는지 확인합니다.
  • 길이 제한이 필수 정보와 충돌하면 필수 정보를 우선하도록 기준을 적습니다.
  • 개인정보가 든 고객 원문을 프롬프트 실험 로그에 그대로 남기지 않습니다. 수업은 합성 문의를 사용합니다.

8정리와 다음 절

  • 페르소나는 역할과 말투를 정하며 과업 명세를 대신하지 않습니다.
  • 확인 가능한 목표·필수 정보·금지 사항·출력 형식을 구분합니다.
  • 프롬프트 효과는 원문과 사용량을 함께 읽어 판단합니다.

9복습 문제

문제 4개 · 해설 포함

[하] 1. 페르소나는 무엇을 정합니까?

정답과 해설 — 모델이 취할 역할, 관점, 말투를 정합니다. 절차 준수나 사실 정확성을 자동으로 보장하지 않습니다.

[중] 2. “잘 답하세요”보다 확인하기 쉬운 제약을 하나 쓰세요.

정답과 해설 — “분류, 다음 행동, 고객 문장을 세 줄로 작성하세요”처럼 결과에서 확인 가능한 조건을 씁니다.

[중] 3. 출력 글자 수가 줄었는데 전체 토큰이 늘 수 있는 이유는 무엇입니까?

정답과 해설 — 전체 토큰에는 입력과 출력이 모두 포함되며, 구체적인 제약 문구가 입력 토큰을 늘릴 수 있기 때문입니다.

[상] 4. 둘째 조건이 첫째 조건의 실패를 해결했다고 말할 수 없는 이유는 무엇입니까?

정답과 해설 — 첫 응답도 세 필수 내용을 올바르게 포함했기 때문입니다. 관찰하지 않은 실패를 만들었다고 기록하면 안 됩니다.
