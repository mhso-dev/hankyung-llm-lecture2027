1학습 목표

  • Zero-shot과 Few-shot 프롬프트의 차이를 설명할 수 있습니다.
  • 현재 과제를 대표하는 입출력 예시를 고를 수 있습니다.

2이 내용을 배우는 이유

출력 형식을 문장으로 길게 설명해도 모델이 작성자의 의도를 다르게 해석할 수 있습니다. 이때 완성된 입출력 한 쌍은 규칙을 구체적인 모양으로 보여 줍니다. 고객 문의와 기대 답안을 함께 주면 필드 순서, 문장 길이, 필요한 정보가 결과에 어떻게 나타나야 하는지 확인할 수 있습니다.

예시는 많다고 좋은 것이 아닙니다. 현재 문의와 관련 없는 예시는 입력 토큰을 사용하고 잘못된 분류 경계를 암시할 수 있습니다. 또한 예시에 있던 주문번호나 표현을 새 사례에 그대로 복사할 위험도 있습니다. 예시 선택은 장식이 아니라 실패 사례와 평가 기준을 근거로 하는 설계 결정입니다.

3앞에서 배운 내용

02절에서 과업과 출력 형식을 말로 지정했습니다. 이 절에서는 같은 세 필드 형식을 유지하고 예시의 존재와 관련성만 비교합니다. 모델, 텀블러 문의, 교환 규정, 확인 기준은 바꾸지 않습니다. 실행 결과는 매번 달라질 수 있으므로 노트북에 저장된 원문을 기준으로 해석합니다.

4핵심 개념

완성본 한 장을 함께 보여 줍니다

처음 작성하는 신청서에서 설명문만 읽는 것보다 올바르게 작성된 견본 한 장을 보면 칸의 의미를 빨리 이해할 수 있습니다. Few-shot 예시는 모델에게도 입력과 기대 출력의 대응을 보여 줍니다. 다만 견본이 다른 업무의 양식이면 오히려 혼동을 줄 수 있습니다.

정의

Zero-shot 프롬프트
현재 과업의 입출력 예시 없이 지시와 질문만 주는 방식입니다.
Few-shot 프롬프트
소수의 예시 입력과 예시 출력을 함께 제공하여 원하는 행동을 보여 주는 방식입니다.
예시 선택 (example selection)
평가하려는 입력의 형식, 주제, 경계 사례를 대표하는 예시를 고르는 과정입니다.
관련성 (relevance)
예시가 현재 과제의 판단 기준과 출력 형태를 얼마나 직접 보여 주는지 나타냅니다.
경계 사례 (edge case)
두 분류가 헷갈리거나 일부 정보가 빠져 일반 규칙만으로 처리하기 어려운 입력입니다.
데이터 누출 (data leakage)
평가 답안이나 평가 대상 자체가 예시에 섞여 결과가 실제 능력보다 좋아 보이는 문제입니다.

도식 — 예시는 선택을 거쳐 프롬프트에 들어갑니다

형식과 판단 근거를 함께 대표해야 합니다

뉴스레터 글꼴 설정 예시는 “분류/다음 행동/고객 문장”이라는 표면 형식은 보여 줍니다. 그러나 파손 상품의 사진과 주문번호 확인이라는 판단 근거는 보여 주지 못합니다. 셔츠 단추 파손 예시는 상품 하자, 교환, 사진 확인이라는 현재 과제의 구조를 공유합니다. 좋은 예시는 단어가 비슷한 문장이 아니라 어떤 근거로 어떤 출력을 내야 하는지 보여 주는 사례입니다.

예시를 평가 답안으로 만들지 않습니다

현재 평가 문의의 주문번호 A-1042와 정답 문장을 예시에 그대로 넣으면 모델은 과업을 해결하지 않고 복사할 수 있습니다. 실습의 관련 예시는 다른 상품과 다른 주문번호 B-203을 사용합니다. 공통 판단은 유지하되 개별 값은 다르게 둡니다. 예시 집합을 변경하면 버전 또는 식별자를 남겨 어떤 결과가 어떤 예시에서 나왔는지 추적합니다.

동적 선택은 뒤 단계입니다

LangChain은 많은 예시 중 관련 항목을 선택하는 구성도 제공합니다. 그러나 처음부터 선택기를 숨기면 왜 그 예시가 들어왔는지 알기 어렵습니다. 이 절에서는 작은 고정 예시를 직접 읽고 비교합니다. Ch 9에서 검색을 배우면 관련 자료를 고르는 과정과 연결할 수 있습니다.

예시의 입력과 답에서 각각 무엇을 배우는가

Few-shot의 한 예시는 요청 문장 하나가 아니라 입력과 원하는 출력의 대응입니다. 파손된 셔츠 문의는 어떤 사실을 확인할지 보여 주고, 예시 답은 그 사실을 교환 분류와 사진 요청으로 어떻게 연결할지 보여 줍니다. relevant_example + " " + TASK는 예시와 현재 문의 사이에 빈 줄을 넣어 하나의 문자열을 만들며, 모델의 가중치를 다시 학습하는 코드는 아닙니다.

감정 분류로 옮기면 “배송은 빨랐지만 제품이 깨졌습니다”처럼 판단이 갈리는 문장이 경계 사례가 됩니다. 긍정 단어가 포함되어도 전체 평가를 부정으로 볼지, 혼합으로 둘지를 예시와 기준에서 일치시켜야 합니다. 쉬운 긍정 예시만 여러 개 넣는 것보다 실제로 혼동하는 판단을 드러내는 예시가 학습 목적에 맞습니다. 단, 효과는 별도 입력에서 확인해야 합니다.

예시는 그대로 복사할 부분과 바꿔야 할 부분을 함께 가집니다. 출력 필드 순서는 재사용할 수 있지만 B-203이라는 주문번호는 현재 A-1042로 바뀌어야 합니다. 관련 예시를 선택했다는 사실만으로 이 구분이 보장되지는 않습니다. 아래 원문에서 예시 주문번호가 섞였는지, 현재 주문번호가 누락됐는지, 필요한 행동이 유지됐는지를 각각 읽습니다.

측정 함수

단어 포함 표시는 원문 정독을 돕는 표시이며 품질 점수가 아닙니다.

run(messages)는 이 노트북에서 작성하는 보조 함수입니다. 역할·내용 목록을 받아 model.invoke()를 한 번 실행하고, 답 문자열·사용량·경과 초를 담은 딕셔너리를 반환합니다. def 셀은 함수를 정의할 뿐이며 뒤에서 run(...)을 호출할 때 모델 요청이 시작됩니다. mention_flags(text)는 지정 단어가 문자열에 있는지 표시한 딕셔너리를 반환합니다. 답의 뜻을 판단하는 모델 호출은 포함하지 않습니다.

In [4]:
# 모델 응답의 원문, 사용량, 경과 시간을 한 레코드로 보존합니다.
def run(messages):
    started = time.perf_counter()
    answer = model.invoke(messages)
    return {"text": answer.text, "usage": answer.usage_metadata,
            "latency_s": round(time.perf_counter() - started, 3)}

def mention_flags(text):
    return {word: word in text for word in MENTIONS}

관련 예시와 관련 없는 예시 비교

두 조건 모두 예시는 하나이며, 현재 질문과의 관련성만 다릅니다.

Few-shot은 예시 입력과 예시 답의 대응을 현재 요청에 함께 넣는 방식입니다. relevant_example과 irrelevant_example은 준비된 문자열이며 현재 질문 TASK 앞에 연결됩니다. 별도의 모델 훈련은 수행하지 않습니다. 고정된 작은 예시를 직접 고르는 방식이며 자동 예시 선택기는 사용하지 않습니다.

감정 분류에서는 칭찬과 불만이 함께 있는 문장이 경계 예시가 될 수 있습니다. 상담에서는 상품명보다 파손 사실과 사진 확인이라는 판단 구조가 관련성을 결정합니다. 예시 수뿐 아니라 어떤 구분을 보여 주는지를 확인합니다.

예시의 B-203은 현재 문의의 주문번호가 아닙니다. 현재 A-1042를 그대로 유지하면서 예시의 분류 방식만 적용했는지 원문을 읽습니다. 아래 단어 포함 표시는 형식·사실·규정 준수 전체의 점수가 아닙니다.

In [6]:
# 관련 예시와 관련 없는 예시는 한 개씩 두고 현재 질문은 고정합니다.
relevant_example = """예시 문의: 셔츠 단추가 떨어졌습니다. 주문번호 B-203입니다.
예시 답: 분류=교환 / 다음 행동=하자 사진과 주문번호 확인 / 고객 문장=사진을 첨부해 주세요."""
irrelevant_example = """예시 문의: 뉴스레터 글꼴을 바꾸고 싶습니다.
예시 답: 분류=설정 / 다음 행동=설정 메뉴 확인 / 고객 문장=글꼴 메뉴를 선택해 주세요."""
few = run([("system", "분류/다음 행동/고객 문장 형식으로 답하세요."),
           ("user", relevant_example + "\n\n" + TASK)])
off = run([("system", "분류/다음 행동/고객 문장 형식으로 답하세요."),
           ("user", irrelevant_example + "\n\n" + TASK)])

세 조건의 원문과 확인 표시

예시가 정답을 보장하는지, 입력 토큰이 얼마나 늘었는지도 확인합니다.

In [7]:
# 예시 없음·관련 예시·관련 없는 예시의 raw 응답을 모두 출력합니다.
for name, result in {"zero_shot": zero, "relevant": few, "unrelated": off}.items():
    print("\n", name, json.dumps(mention_flags(result["text"]), ensure_ascii=False),
          result["usage"], result["latency_s"])
    print(result["text"])

관련 예시가 항상 더 좋은 답을 만든다는 결과는 나오지 않았습니다. 관련 예시는 짧은 슬래시 형식을 강하게 보여 주었고, 모델은 그 모양을 따르면서 현재 주문번호를 생략했습니다. 관련 없는 예시도 슬래시 형식에 영향을 주어 분류를 “교환/파손 접수”로 표현했습니다. 이 차이는 예시 한 개와 실행 한 번에서 관찰한 결과이므로 Few-shot 전체의 우열로 일반화할 수 없습니다.

입력 토큰은 예시가 없는 조건보다 약 48~54토큰 늘었습니다. 예시가 늘면 비용뿐 아니라 모델이 읽어야 할 경쟁 정보도 늘어납니다. 예시는 평가 실패를 해결하는 데 필요한 최소 수부터 추가하고, 기존에 맞던 항목이 빠지지 않는지 회귀 검사를 합니다.

7주의할 점과 실무 메모

  • 예시의 정답이 실제 업무 규정과 맞는지 먼저 검토합니다.
  • 현재 평가 입력이나 정답을 예시 집합에 넣지 않습니다.
  • 예시 속 이름·주문번호가 새 답에 복사되는지 확인합니다.
  • 긍정 사례만으로 부족하면 실제로 혼동한 경계 사례를 추가합니다.
  • 예시를 바꿀 때 예시 집합 ID와 프롬프트 버전을 함께 기록합니다.

8정리와 다음 절

  • Few-shot은 입출력 쌍으로 원하는 행동을 구체적으로 보여 줍니다.
  • 관련 예시도 현재 입력의 필수 값을 생략하게 만들 수 있으므로 원문을 읽습니다.
  • 예시 추가에는 토큰 비용과 데이터 누출 위험이 따릅니다.
