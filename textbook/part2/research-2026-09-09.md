## Ch 6 — 첫 호출, 교체 가능한 provider, 계측

### 확정 사실과 권장 실습 형태

1. `init_chat_model("provider:model")`은 provider 접두어로 통합 패키지를 해석합니다. OpenAI, Anthropic, Google 모델을 같은 호출 모양으로 초기화할 수 있습니다. 실습에서는 접두어를 생략하지 말고 `openai:...`, `anthropic:...`, `google_genai:...`처럼 적어 어떤 키와 패키지를 쓰는지 보이게 합니다. 각 provider에는 별도 integration 패키지와 API 키가 필요합니다.
   - [LangChain Providers and models](https://docs.langchain.com/oss/python/concepts/providers-and-models)
   - [LangChain Models](https://docs.langchain.com/oss/python/langchain/models)

2. 응답은 `AIMessage`입니다. `content`는 provider 원본 표현을 보존하고, `content_blocks`는 텍스트·추론·이미지 등 provider 차이를 표준 블록으로 지연 변환합니다. 교차-provider 비교표에는 `response.content_blocks`와 `response.usage_metadata`를 읽고, 원본 API 디버깅 때만 `content`와 `response_metadata`를 함께 기록합니다. 표준 블록을 `content`에도 직렬화해야 하는 클라이언트만 `output_version="v1"` 또는 `LC_OUTPUT_VERSION=v1`을 사용합니다.
   - [LangChain Messages](https://docs.langchain.com/oss/python/langchain/messages)
   - [LangChain v1 migration — standard content](https://docs.langchain.com/oss/python/migrate/langchain-v1)

3. Pydantic은 필드 설명·범위·중첩 구조의 런타임 검증까지 제공하므로 Ch 6의 기본 스키마로 적합합니다. 에이전트의 `response_format`은 Ch 20 이후 주제입니다. 이 장에서는 직접 모델 호출에 `model.with_structured_output(Schema, include_raw=True)`를 붙이고, `raw`, `parsed`, `parsing_error`를 모두 출력해 깨진 입력을 관찰합니다. `include_raw=False`인 기본 경로는 파싱·검증 예외가 호출자에게 전파될 수 있으므로, 실패 처리 수업에는 맞지 않습니다.
   - [LangChain Models — structured output](https://docs.langchain.com/oss/python/langchain/models)
   - [LangChain Structured output](https://docs.langchain.com/oss/python/langchain/structured-output) — agent API도 설명하지만, 이 장에서는 개념·Pydantic 검증 설명에만 참고합니다.

4. `stream()`은 여러 `AIMessageChunk`를 내보냅니다. 청크는 `+`로 합쳐 완전한 메시지를 만들 수 있으므로, 화면에는 `chunk.text`를 누적 출력하고 검증·저장은 합쳐진 최종 메시지에 한 번만 수행합니다. 구조화 JSON은 중간 청크에 대해 검증하지 않습니다. 사용량을 스트리밍에서도 받으려면 OpenAI `ChatOpenAI`에 `stream_usage=True`를 줍니다.
   - [LangChain Models — streaming](https://docs.langchain.com/oss/python/langchain/models)
   - [LangChain ChatOpenAI — streaming usage metadata](https://docs.langchain.com/oss/python/integrations/chat/openai)

5. `timeout`과 provider SDK의 재시도는 초기화 인자로 줄 수 있습니다. 현재 Models 문서는 `timeout` 초 단위와 `max_retries` 기본 6회(지수 backoff+jitter)를 설명하며, 네트워크 오류·429·5xx만 자동 재시도하고 401·404는 재시도하지 않는다고 명시합니다. 실습은 긴 기본값을 그대로 숨기지 말고, 타임아웃·시도 횟수·실패 유형을 출력합니다.
   - [LangChain Models — initialization parameters](https://docs.langchain.com/oss/python/langchain/models)

6. Runnable의 `.with_retry()`는 기본적으로 모든 예외를 세 번까지 재시도하므로, API 호출에는 일시 오류의 예외형만 지정합니다. 재시도 범위는 파싱·표 렌더링까지 넓히지 말고 모델 호출에만 둡니다. `.with_fallbacks()`는 원본과 fallback을 순서대로 시도합니다. fallback이 성공한 경우에도 비교표에 실제 사용 provider/model을 기록해야 비용·품질 비교가 정직해집니다. 인증 오류·Pydantic 검증 오류를 다른 provider 호출로 감추지 않습니다.
   - [Runnable.with_retry reference](https://reference.langchain.com/python/langchain-core/runnables/base/Runnable/with_retry)
   - [Runnable.with_fallbacks reference](https://reference.langchain.com/python/langchain-core/runnables/base/Runnable/with_fallbacks)

7. `AIMessage.usage_metadata`는 입력·출력·전체 토큰을 provider가 보낸 경우 표준 형태로 제공합니다. 비용은 **기록된 실제 토큰 수 × 그 실행일의 provider 요금**으로 계산하며, 세 provider의 토큰화 방식과 캐시 과금이 다를 수 있음을 표에 적습니다. 모델 가격을 소스 코드 상수로 고정하지 않습니다.
   - [LangChain ChatOpenAI — usage metadata](https://docs.langchain.com/oss/python/integrations/chat/openai)

### Ch 6 실습 안전선

- API 키는 `.env`에만 두고 `python-dotenv`로 읽습니다. 출력·노트북·JSONL에 키, 전체 Authorization 헤더, 원문 개인정보를 남기지 않습니다.
- `max_retries`가 provider SDK 재시도와 `.with_retry()` 재시도를 동시에 만들 수 있습니다. 한 실험 경로의 소유자를 하나로 정하고, 시도 수를 제한합니다.
- `timeout`은 전체 비용 상한이 아닙니다. timeout 뒤 provider가 이미 처리했을 가능성이 있으므로, 쓰기 작업·결제 작업처럼 비멱등인 요청은 이 장에서 재시도 예제로 쓰지 않습니다.

## Ch 7 — 프롬프트와 메시지 경계

### 메시지 역할과 템플릿

1. OpenAI Chat Completions 레퍼런스는 `developer` 메시지를 사용자 입력과 무관하게 따라야 하는 개발자 지시로 정의하고, o1 이후 모델에서는 기존 `system` 역할 대신 `developer`를 사용한다고 밝힙니다. 이것은 **OpenAI API의 역할 규칙**입니다.
   - [OpenAI Chat Completions message reference](https://developers.openai.com/api/reference/cli/resources/chat)

2. LangChain의 cross-provider `ChatPromptTemplate` 기본 예제·참조는 `system`, `human`/`user`, `ai`, `tool` 등 메시지 표현을 중심으로 합니다. 따라서 세 provider를 같은 코드로 비교하는 기본 실습은 변하지 않는 정책을 `system`, 과제 데이터를 `human`, 예시는 `human`/`ai` 쌍으로 둡니다. OpenAI 전용 developer 역할은 provider의 현재 integration에서 직접 시험하는 별도 예제로 다루며, `("developer", ...)` 튜플의 cross-provider 이식성을 전제하지 않습니다.
   - [ChatPromptTemplate reference](https://reference.langchain.com/python/langchain-core/prompts/chat/ChatPromptTemplate)
   - [LangSmith prompt quickstart](https://docs.langchain.com/langsmith/prompt-engineering-quickstart)

3. `MessagesPlaceholder("history")`는 이미 메시지 목록인 변수를 지정한 위치에 삽입합니다. 기본값은 필수이므로 history가 없을 수도 있는 첫 턴에는 `optional=True`을 명시합니다. `n_messages`는 최근 메시지 수를 제한할 수 있지만, 단순히 오래된 메시지를 자르면 이전 제약이나 근거도 사라질 수 있습니다. Ch 7은 작은 history로 모양을 확인하고, Ch 8에서 예산·압축을 본격적으로 다룹니다.
   - [MessagesPlaceholder reference](https://reference.langchain.com/python/langchain-core/prompts/chat/MessagesPlaceholder)

4. Few-shot은 예시 입·출력 쌍으로 원하는 행동을 보여 주는 기법입니다. 예시는 형식·경계 사례·부정 사례를 대표해야 하고, 예시 선택은 고정 문장 장식이 아니라 평가 집합의 실패를 고친 결과여야 합니다. LangChain 문서는 관련 예시를 동적으로 선택할 수 있는 selector를 제공하지만, Ch 7 기본 실습은 선정 규칙을 숨기지 않는 작은 고정 예시부터 시작합니다.
   - [LangChain memory overview — few-shot](https://docs.langchain.com/oss/python/concepts/memory)

### CoT, ReAct, Self-Consistency의 범위

| 기법 | Ch 7에서 다룰 수 있는 최소 범위 | 넘지 말아야 할 경계 |
| --- | --- | --- |
| CoT | 같은 문제에 짧은 단계적 풀이 지시를 넣고, 정답·출력 토큰·지연을 no-CoT와 비교합니다. | 모델의 내부 reasoning을 요구·저장·채점 가능한 사실로 취급하지 않습니다. GPT-5 계열 reasoning 모델에는 세세한 풀이 절차를 늘어놓기보다 목표·제약·출력 형식을 먼저 평가합니다. |
| Self-Consistency | 서로 독립인 N회 호출의 **최종 답**만 집계하고, seed·모델 snapshot·N·집계 규칙·총 토큰을 기록합니다. | 다수결을 정답 보장으로 표시하지 않습니다. 외부 사실 확인·유효성 검증을 대체하지 않습니다. |
| ReAct | "관찰 → 다음 단계의 텍스트 계획 → 최종 답"을 한 번의 정해진 호출에서 읽는 개념 실험으로 한정합니다. | 모델이 도구를 선택하고 결과를 받아 반복하는 실행 loop, `create_agent`, ToolNode는 Ch 20 전에는 만들지 않습니다. 조건 분기는 Ch 13 그래프로 옮깁니다. |

- 공개된 OpenAI 모델 지침은 GPT-5 계열에서는 필요한 경우를 제외하고 상세 step-by-step process 지시를 줄이고, 목표·성공 기준·구조화 출력으로 튜닝하라고 권합니다. 반면 GPT-4.1 지침은 비추론 모델의 명시적 CoT가 비용·지연 증가와 맞바꾸어 품질을 높일 수 있다고 설명합니다. 따라서 CoT가 항상 좋은 기법이라는 문장은 쓰지 말고, 모델·과제·평가표에 따라 확인한다는 실험으로 씁니다.
  - [OpenAI model guidance — GPT-5.5, GPT-5 계열 지침](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.5)
  - [OpenAI model guidance — GPT-4.1 CoT 및 장문 컨텍스트](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-4.1)

### 프롬프트 A/B 실습의 기록 단위

각 실행 행에 `prompt_version`, `model`(가능하면 snapshot), provider, temperature/reasoning 설정, 예시 집합 ID, 입력 ID, 출력, 평가 기준별 점수, `usage_metadata`, 시작·종료 시간을 남깁니다. 텍스트를 바꾼 동시에 모델·온도·예시를 바꾸면 원인을 분리할 수 없습니다. LangSmith의 prompt push는 같은 이름으로 새 commit을 만들어 과거 버전을 보존하지만, 외부 서비스 사용이 없는 수업 기본 경로에는 저장소의 프롬프트 파일과 실행 로그만으로도 같은 원칙을 적용할 수 있습니다.

## Ch 8 — Context Engineering 기초

### 교재의 네 전략을 구현에 연결하는 법

| 전략 | 이 장에서 관찰할 수 있는 결정론적 구현 | 관찰값 |
| --- | --- | --- |
| Write | 원문 대화·문서에서 재사용할 사실을 짧은 레코드로 저장합니다. | 저장 전후 토큰, 빠진 사실, 잘못 저장된 사실 |
| Select | 현재 질문에 필요한 레코드·문서만 선택해 넣습니다. 다음 RAG 장에서는 이 선택을 검색으로 자동화합니다. | 선택 수, 관련 문서 누락/잡음, 입력 토큰 |
| Compress | 오래된 대화나 긴 문서를 요약하되 원문 ID·근거 위치를 보존합니다. | 압축률, 필수 제약 보존 여부, 답 품질 |
| Isolate | 큰 보조 작업의 원문 출력과 최종 요약을 분리해 주 호출에는 요약만 넣습니다. 이 장에서는 일반 Python 함수의 분리로 보이고, subagent는 아직 사용하지 않습니다. | 주 호출에 전달된 토큰, 요약의 근거 보존 여부 |

- LangChain의 공식 정의는 context engineering을 "올바른 정보와 도구를 올바른 형식으로 제공하는 동적 시스템"으로 설명합니다. model context(지시·message history·response format)는 호출마다 일시적이며, state/store/lifecycle 맥락은 지속될 수 있습니다. 이 차이는 이 장의 Write와 Compress가 원본을 영구히 바꿀 수 있다는 주의점의 근거가 됩니다.
  - [LangChain context overview](https://docs.langchain.com/oss/python/concepts/context)
  - [LangChain context engineering](https://docs.langchain.com/oss/python/langchain/context-engineering)

### 네 실패 모드와 검증 문장

- Poisoning: 선택한 맥락에 잘못된 지시·사실을 넣어 답을 오염시키는 사례입니다. 원문과 선택본을 나란히 저장하고, 신뢰 출처·권한·문서 ID를 확인합니다.
- Distraction: 관련 없는 정보가 많아 필요한 근거의 주의가 분산되는 사례입니다. 입력 토큰만 줄었다고 성공으로 판정하지 않고, 목표 사실을 실제로 인용·추출했는지 측정합니다.
- Confusion: 같은 대상의 이름·버전·시간 범위가 모호해 모델이 서로 다른 대상을 섞는 사례입니다. 각 레코드에 출처·날짜·범위·식별자를 붙입니다.
- Clash: 서로 맞지 않는 정책·사실을 함께 준 사례입니다. 우선순위 규칙을 명시하고, 답이 충돌을 숨기지 않고 보고하는지 확인합니다.

위 네 이름은 이 커리큘럼의 교육용 분류입니다. LangChain 공식 문서가 이 네 명칭을 표준 분류로 보증하지는 않습니다. 본문에서는 "모델이 긴 context에서 언제나 같은 품질을 낸다"고 단정하지 않습니다. OpenAI의 장문 context 지침도 관련·무관 문서가 많고 전체 상태에 대한 복잡한 추론이 필요해지면 성능이 저하될 수 있다고 적습니다.

- [OpenAI GPT-4.1 model guidance — optimal context size](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-4.1)
- [LangChain context engineering — best practices](https://docs.langchain.com/oss/python/langchain/context-engineering)

### Context rot 실험의 최소 설계

1. 같은 질문·정답 기준·모델 snapshot을 고정하고 context 길이만 단계적으로 늘립니다.
2. 길이마다 target fact의 위치를 앞·가운데·뒤로 바꾸고, 관련 없는 filler와 충돌하는 filler를 구분합니다.
3. 정확도/근거 인용 여부, 입력·출력 토큰, 지연, 비용을 함께 기록하고 각 조건을 반복합니다.
4. 관찰하지 못한 저하는 "저하를 재현했다"고 쓰지 않고, 그 모델·입력·반복 수에서는 미관찰이라고 기록합니다.

- Ch 6의 Anthropic·Google 분기는 키가 없어도 코드와 설치 목록까지 완결해야 합니다. 2026-09-09 확인 기준으로 Anthropic API alias는 `claude-haiku-4-5`(고정 ID `claude-haiku-4-5-20251001`도 active), Google 안정 ID는 `gemini-2.5-flash-lite`입니다. 표준 1M token 가격은 각각 입력/출력 $1/$5, 입력/출력 $0.10/$0.40입니다. `langchain==1.4.0`은 lockfile에서 `langchain-core==1.6.2`와 함께 해석되며, 최신 `langchain-anthropic==1.7.1`·`langchain-google-genai==4.4.0`의 `langchain-core>=1.6.1,<2.0.0` 요구도 충족합니다. 격리 환경에서 이 최신 세 package와 두 `init_chat_model` 객체 생성을 확인했습니다. 따라서 이 조합을 고정하고, 키가 없으면 해당 호출 결과만 `skipped: <환경 변수> 필요`로 기록합니다.
  - [Anthropic Haiku 4.5 model ID·가격](https://www.anthropic.com/claude/haiku)
  - [Anthropic model lifecycle](https://platform.claude.com/docs/en/about-claude/model-deprecations)
  - [Gemini 2.5 Flash-Lite model ID](https://ai.google.dev/gemini-api/docs/models)
  - [Gemini Developer API 가격](https://ai.google.dev/gemini-api/docs/pricing)
- 온라인 LangChain 문서에 나타나는 모델 또는 재시도 기본값은 provider 공통 계약으로 쓰지 않습니다. 이 프로젝트의 로컬 고정 조합(`langchain-openai==1.6.0`)에서 `ChatOpenAI.model_fields['max_retries'].default`와 `request_timeout` 기본값은 모두 `None`이고, `Runnable.with_retry()`의 기본 `stop_after_attempt`는 3이며 모든 `Exception`을 대상으로 합니다. 이 관찰은 OpenAI integration 한정이므로 Anthropic·Google에 일반화하지 않습니다. 따라서 본문·노트북에서는 `timeout`, `max_retries`, 재시도 대상 예외를 명시하고, 기본값을 설명하거나 비교 근거로 사용하지 않습니다.
- `gpt-5.4-mini`의 alias는 업데이트될 수 있습니다. 재현성 우선 실험에서만 `gpt-5.4-mini-2026-03-17` snapshot을 사용하고, 수업 준비 시 API 계정에서 접근 가능 여부를 확인합니다.
- LangChain 온라인 문서는 지속 갱신됩니다. 집필 기준 lockfile의 `langchain==1.4.0`과 `langchain-core==1.6.2`에서 `.with_structured_output(..., include_raw=True)`, `MessagesPlaceholder`, `stream_usage=True`를 빈 커널로 검증한 출력만 본문에 넣습니다.
