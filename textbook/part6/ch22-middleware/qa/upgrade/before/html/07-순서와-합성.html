1학습 목표

  • before 훅의 순방향 실행을 확인할 수 있습니다.
  • after 훅의 역방향 실행을 확인할 수 있습니다.
  • wrap 훅의 중첩 순서를 함수 호출 구조로 설명할 수 있습니다.

2이 내용을 배우는 이유

PII 처리, 예산, 재시도, 감사를 한 에이전트에 함께 넣으면 목록 순서가 실제 동작을 바꿉니다. 예산을 예약한 뒤 재시도하면 각 시도를 비용으로 셀지, 재시도 전체를 한 호출로 셀지에 따라 결과가 다릅니다. 출력 감사가 마스킹보다 바깥에 있으면 마스킹 전 값을 기록할 수도 있습니다. 따라서 합성 순서를 trace로 확인해야 합니다.

이 절의 질문 — 여러 미들웨어의 before·after·wrap 훅은 어떤 순서로 합성될까요?

3앞에서 배운 내용

앞 절까지 PIIMiddleware, 내장 안정화 미들웨어, 두 커스텀 미들웨어를 각각 실행했습니다. 이번에는 기능을 추가하지 않고 A, B, C 세 미들웨어가 같은 훅에서 남기는 문자열만 관찰합니다. 모델은 한 번만 답하는 결정적 모델로 고정합니다.

4핵심 개념

비유로 시작하기

겹쳐 입은 옷을 생각해 봅니다. 안으로 들어갈 때는 겉옷 A, 중간 옷 B, 안쪽 옷 C 순서로 통과합니다. 밖으로 나올 때는 C, B, A 순서입니다. LangChain의 before 훅은 목록의 앞에서 뒤로 실행됩니다. after 훅은 뒤에서 앞으로 실행됩니다. wrap 훅은 첫 항목이 가장 바깥쪽이 되어 A before, B before, C before, 모델, C after, B after, A after 순서가 됩니다.

코드를 읽는 순서

여러 미들웨어를 등록하면 목록 순서가 실행 경계를 만듭니다. before_agent와 before_model 같은 진입 훅은 A→B→C 순서로 실행됩니다. 랩 훅은 A가 B를 감싸고 B가 C를 감싸는 중첩 구조이므로 호출 전에는 A→B→C, 반환 후에는 C→B→A가 됩니다. after_model과 after_agent도 바깥으로 나오며 역순으로 실행됩니다.

Tagged(name)은 각 훅에서 태그와 시점을 ORDER에 남깁니다. handler(request) 앞뒤에 서로 다른 문자열을 기록하면 한 랩의 진입과 이탈을 구분할 수 있습니다. 예상 목록과 실제 목록의 완전 일치 검사는 훅이 모두 한 번 실행됐다는 사실뿐 아니라 중첩 순서까지 확인합니다.

도식 읽기

파란 middleware 목록 A·B·C가 파란 before 구간에서는 왼쪽부터 A→B→C로 실행됩니다. 보라색 모델을 감싸는 wrap 구간은 A(B(C(model))) 형태입니다. 반환과 after 구간은 C→B→A로 반대 방향입니다. 노트북의 ORDER 18개 항목이 각 화살표의 순서를 검증합니다.

5실행 예제

A·B·C 미들웨어에 before, wrap 전후, after 태그를 남기게 한 뒤 등록 순서를 고정해 실행합니다. 각 구간의 태그 배열을 출력해 before는 정방향, wrap과 after는 역방향으로 중첩되는지를 확인합니다.

결정적 모델 준비

이 모델은 정해 둔 응답으로 훅 경계를 관찰하는 결정적 검사 장치입니다. BaseChatModel 상속 구현 자체는 이 절의 학습 대상이 아닙니다.

In [2]:
# 이 셀은 결정적 모델 준비 작업을 수행하고 확인할 값을 출력합니다.
# 정해 둔 응답으로 미들웨어 실행 순서를 재현합니다.
from typing import Any
from langchain.agents import create_agent
from langchain.agents.middleware import AgentMiddleware
from langchain.tools import tool
from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.messages import AIMessage
from langchain_core.outputs import ChatGeneration, ChatResult
class ScriptedModel(BaseChatModel):
    replies: list[AIMessage]
    index: int = 0
    @property
    def _llm_type(self) -> str: return "scripted-model"
    def _generate(self, messages: Any, stop: Any = None, run_manager: Any = None, **kwargs: Any) -> ChatResult:
        reply = self.replies[min(self.index, len(self.replies) - 1)]
        self.index += 1
        return ChatResult(generations=[ChatGeneration(message=reply)])
    def bind_tools(self, tools: Any, *, tool_choice: Any = None, **kwargs: Any) -> "ScriptedModel":
        return self
@tool
def lookup_hours(day: str) -> str:
    """자료실 운영 시간을 요일로 조회합니다."""
    return "평일 09:00~20:00" if day == "평일" else "토요일 10:00~17:00"

태그 미들웨어 정의

여러 미들웨어를 등록하면 목록 순서가 실행 경계를 만듭니다. before_agent와 before_model 같은 진입 훅은 A→B→C 순서로 실행됩니다. 랩 훅은 A가 B를 감싸고 B가 C를 감싸는 중첩 구조이므로 호출 전에는 A→B→C, 반환 후에는 C→B→A가 됩니다. after_model과 after_agent도 바깥으로 나오며 역순으로 실행됩니다.

Tagged(name)은 각 훅에서 태그와 시점을 ORDER에 남깁니다. handler(request) 앞뒤에 서로 다른 문자열을 기록하면 한 랩의 진입과 이탈을 구분할 수 있습니다. 예상 목록과 실제 목록의 완전 일치 검사는 훅이 모두 한 번 실행됐다는 사실뿐 아니라 중첩 순서까지 확인합니다.

In [3]:
# 이 셀은 태그 미들웨어 정의 작업을 수행하고 확인할 값을 출력합니다.
ORDER=[]
class Tagged(AgentMiddleware):
    def __init__(self, tag: str) -> None: self.tag=tag
    @property
    def name(self) -> str: return f"Tagged-{self.tag}"
    def before_agent(self, state: Any, runtime: Any) -> None: ORDER.append(f"before_agent:{self.tag}")
    def before_model(self, state: Any, runtime: Any) -> None: ORDER.append(f"before_model:{self.tag}")
    def wrap_model_call(self, request: Any, handler: Any) -> Any:
        ORDER.append(f"wrap_in:{self.tag}"); result=handler(request); ORDER.append(f"wrap_out:{self.tag}"); return result
    def after_model(self, state: Any, runtime: Any) -> None: ORDER.append(f"after_model:{self.tag}")
    def after_agent(self, state: Any, runtime: Any) -> None: ORDER.append(f"after_agent:{self.tag}")

합성 표 출력

입력 마스킹 뒤 감사 해시를 만들면 감사 기록에는 마스킹된 값이 남습니다. 반대로 감사 뒤 마스킹하면 원문 해시가 남을 수 있습니다. 재시도 랩과 사용량 기록 랩의 순서도 재시도마다 사용량을 셀지 전체 요청 한 번으로 셀지를 바꿉니다. 목록 순서는 코드 스타일이 아니라 정책 의미입니다.

서로 독립적인 읽기 전용 기록은 순서 영향이 작지만, 요청이나 상태를 수정하는 미들웨어는 교환해도 같은 결과가 나오는지 확인해야 합니다. 이 실습은 모델 호출 한 번인 경로를 사용하므로 도구 루프와 재시도가 섞인 전체 순서를 자동으로 증명하지 않습니다.

6실험 결과 해석

middleware=[A,B,C]로 한 번 실행한 trace를 세 구간으로 나눕니다. before_agent와 before_model은 A·B·C, wrap_model_call 진입은 A·B·C이고 반환은 C·B·A, after_model과 after_agent는 C·B·A입니다. 이 순서는 공식 문서의 실행 순서와 일치합니다. 도구 훅도 같은 중첩 원칙을 따르지만 이 셀은 모델 한 번의 최소 예제로 제한합니다.

7주의할 점과 실무 메모

  • 목록 순서를 문서화하고 trace 회귀 테스트로 고정합니다. 라이브러리 업그레이드 뒤에도 다시 실행합니다.
  • 마스킹 전후의 어느 값이 감사 로그에 들어가는지 실제 요청과 반환 위치로 확인합니다.
  • 재시도 미들웨어의 안쪽과 바깥쪽에 예산 미들웨어를 둘 때 시도 횟수 계산이 달라질 수 있습니다.

실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.

8정리와 다음 절

  • 여러 미들웨어의 before 훅은 등록 순서로, after 훅과 wrap 반환 구간은 역순으로 실행됩니다.
  • A·B·C의 18개 trace를 예상 목록과 비교해 진입과 반환의 중첩 순서를 확인했습니다.
  • 요청이나 상태를 바꾸는 미들웨어는 순서가 정책 결과를 바꾸므로 trace 회귀 검사로 고정합니다.

9복습 문제

문제와 해설

1. before 훅의 실행 순서는 무엇인가요?

해설 — middleware 목록의 첫 항목에서 마지막 항목 순서입니다.

2. after 훅이 역순인 이유를 함수 중첩으로 설명해 보세요.

해설 — 안쪽 처리가 먼저 반환되고 바깥쪽 처리가 나중에 반환되기 때문입니다.

3. 첫 미들웨어의 wrap 훅은 어느 위치인가요?

해설 — 다른 wrap 훅과 실제 호출을 감싸는 가장 바깥쪽입니다.

4. 순서 테스트가 필요한 실무 사례는 무엇인가요?

해설 — PII 마스킹 전 원문이 감사 로그에 남지 않는지 확인하는 사례입니다.
