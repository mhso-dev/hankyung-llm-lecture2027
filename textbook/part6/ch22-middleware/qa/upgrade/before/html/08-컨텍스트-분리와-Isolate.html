1학습 목표

  • Ch8의 Isolate를 업무별 모델 입력 분리로 설명할 수 있습니다.
  • wrap_model_call에서 request.override(messages=...)를 사용할 수 있습니다.
  • 텍스트 태그와 실제 별도 모델 요청의 차이를 검증할 수 있습니다.

2이 내용을 배우는 이유

Ch8에서는 대출 문의와 휴관 문의의 자료를 별도 메시지 목록으로 구성했습니다. create_agent 상태에는 여러 업무의 대화가 누적될 수 있고, 전체 상태를 그대로 모델에 전달하면 관련 없는 자료가 입력을 차지합니다. 미들웨어는 영구 상태를 삭제하지 않고 이번 모델 호출에 보낼 메시지만 선택할 수 있습니다. 이것이 Ch8의 Isolate를 실행 구조로 연결하는 방법입니다.

이 절의 질문 — 같은 상태에 섞인 여러 업무 메시지에서 현재 업무에 필요한 내용만 모델 요청으로 분리하려면 어떻게 할까요?

3앞에서 배운 내용

Ch8 context_lab.py의 assemble_isolated_messages는 업무별 자료를 별도 필드로 조립했고 텍스트 태그는 보안 격리가 아니라고 설명했습니다. 이번 절도 같은 경계를 지킵니다. request.override로 메시지를 줄이는 것은 모델 입력 분리이며 저장소 권한이나 프로세스 격리를 제공하지 않습니다.

4핵심 개념

비유로 시작하기

두 사건의 서류를 한 책상에 올려놓되 담당자에게는 현재 사건 서류철만 건네는 상황을 생각해 봅니다. 상태에는 감사와 추적을 위해 전체 메시지가 남아 있을 수 있습니다. IsolateMiddleware는 각 메시지의 additional_kwargs에 있는 topic을 읽어 현재 topic과 같은 메시지만 새 요청에 넣습니다. request.override는 원래 요청 객체를 바꾸지 않고 선택된 messages를 가진 새 요청을 만듭니다. handler는 그 새 요청만 모델에 전달합니다.

코드를 읽는 순서

컨텍스트 분리는 한 대화 기록에서 현재 작업에 필요한 메시지만 모델 입력으로 선택하는 처리입니다. mixed에는 대출과 급여 두 업무의 메시지가 함께 있고, CapturingModel.seen은 모델이 실제로 받은 텍스트를 보관합니다. Before는 다섯 메시지를 모두 전달하므로 현재 질문과 무관한 급여 정보도 모델 입력에 포함됩니다.

IsolateMiddleware("loan")은 모델 호출 직전 요청의 메시지를 업무 표식으로 걸러 새 요청을 전달합니다. 원래 그래프 상태를 영구 삭제하는 것과는 다르며, 이번 모델 호출의 가시 범위를 줄입니다. 필터가 필요한 근거까지 제거하면 답변 품질이 낮아질 수 있으므로 업무 ID를 붙이는 시점과 기본 포함 규칙을 명확히 해야 합니다.

도식 읽기

파란 상태에는 loan 세 메시지와 hr 두 메시지가 함께 있습니다. 파란 IsolateMiddleware가 topic=loan인 세 메시지만 선택해 새 파란 요청을 만들고 보라색 모델에 전달합니다. hr 메시지로 향하는 빨간 차단 표시는 모델 입력에서 제외됐다는 뜻이며 원래 상태나 저장소에서 삭제됐다는 뜻은 아닙니다.

class CapturingModel(BaseChatModel):

    def _generate(self, messages: Any, stop: Any = None, run_manager: Any = None, **kwargs: Any) -> ChatResult:

다른 상황과 적용 경계

하나의 고객이 주문과 환불을 동시에 문의하면 업무별 분리가 오히려 연결 정보를 끊을 수 있습니다. 이런 경우 공통 고객 정보는 별도 컨텍스트로 제공하고, 업무별 대화만 선택하는 두 층 구조가 필요합니다. 단순 키워드 필터보다 생성 시점에 명시적 task_id를 붙이는 편이 경계를 확인하기 쉽습니다.

격리는 접근 통제와 같지 않습니다. 모델 입력에서 급여 문장을 뺐더라도 원본 상태나 로그를 읽을 권한이 그대로라면 보안 경계가 완성되지 않습니다. 이번 출력은 모델이 받은 다섯 문장이 세 문장으로 줄고 급여 문자열이 사라진 사실만 보여 줍니다.

6일부러 실패해 보기

# 이 셀은 After: 업무별 요청 분리 작업을 수행하고 확인할 값을 출력합니다.
class IsolateMiddleware(AgentMiddleware):
    def __init__(self, topic: str) -> None: self.topic=topic
    def wrap_model_call(self, request: Any, handler: Any) -> Any:
        selected=[m for m in request.messages if m.additional_kwargs.get("topic")==self.topic]
        return handler(request.override(messages=selected))
after_model=CapturingModel()
create_agent(after_model,tools=[],middleware=[IsolateMiddleware("loan")]).invoke({"messages":mixed})
print("model_messages:",after_model.seen)
assert len(after_model.seen)==3 and all("급여" not in text for text in after_model.seen)
출력:
model_messages: ['대출은 5권', '기간은 14일', '대출 연장은?']

7주의할 점과 실무 메모

  • 메시지 메타데이터는 신뢰할 수 있는 애플리케이션 코드가 붙여야 합니다. 사용자가 topic 값을 임의로 바꿀 수 있으면 접근 통제가 되지 않습니다.
  • 민감한 자료는 선택 전에도 권한이 없는 프로세스나 상태에 넣지 않습니다. 저장소·도구·런타임 권한을 별도로 검사합니다.
  • Isolate와 Compress를 함께 쓰면 먼저 업무 범위를 선택한 뒤 그 범위 안에서 압축하는 순서를 검토합니다.

실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.

8정리와 다음 절

  • IsolateMiddleware는 저장 상태를 지우지 않고 현재 모델 호출에 전달할 메시지만 request.override로 선택합니다.
  • loan 메시지 세 개만 모델에 도달하고 hr 급여 문자열은 제외됨을 수집 모델의 입력으로 확인했습니다.
  • topic 태그는 모델 입력 범위를 줄이지만 저장소·도구·런타임의 접근 권한을 대신하지 않습니다.

다음 학습과 이어지는 지점 — Ch23에서는 체크포인터와 스레드에 상태를 저장하고 프로세스 중단 뒤 이어서 실행합니다. 이 절의 업무별 상태 범위가 지속성 설계의 입력이 됩니다.

9복습 문제

문제와 해설

1. request.override의 역할은 무엇인가요?

해설 — 원본 요청을 직접 바꾸지 않고 일부 필드를 바꾼 새 요청을 만듭니다.

2. 메시지 태그만으로 보안 격리가 되지 않는 이유는 무엇인가요?

해설 — 같은 호출이나 상태에 들어간 자료는 모델이나 프로세스가 접근할 수 있기 때문입니다.

3. Compress와 Isolate를 함께 적용할 때 한 가지 합리적인 순서는 무엇인가요?

해설 — 현재 업무의 자료를 먼저 선택하고 그 범위 안에서 오래된 내용을 압축합니다.

4. topic 메타데이터를 누가 붙여야 하나요?

해설 — 권한과 업무 범위를 확인한 애플리케이션 코드가 붙여야 합니다.
