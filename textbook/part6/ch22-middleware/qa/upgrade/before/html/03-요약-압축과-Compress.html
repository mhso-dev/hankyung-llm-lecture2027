2이 내용을 배우는 이유

대화가 길어지면 모든 메시지를 모델에 전달하는 비용이 커지고 모델이 현재 질문에 필요한 사실을 찾기 어려워집니다. Ch8의 Compress는 필요한 정보를 남기고 반복을 줄이는 전략이었습니다. Ch16에서는 summarize_history를 직접 호출했습니다. 미들웨어는 모델 호출 직전에 임계값을 검사하고 오래된 메시지를 요약해 이 전략을 반복 루프에 연결합니다.

이 절의 질문 — 자동 요약 압축은 언제 실행되며 최근 메시지와 중요 조건을 어떻게 보존해야 할까요?

3앞에서 배운 내용

Ch8에서는 압축할 때 결정·조건·예외·출처를 보존해야 한다고 배웠습니다. Ch16 summarize_history는 system 메시지와 최근 대화를 남기고, 오래된 대화를 summarizer 함수에 넘긴 뒤 참고용 요약 메시지로 바꿨습니다. 이번 절은 같은 메시지 수 조건을 미들웨어 설정으로 표현합니다.

4핵심 개념

비유로 시작하기

회의록을 다음 회의용 한 장 요약으로 바꾸는 상황을 생각해 봅니다. trigger는 언제 요약을 시작할지, keep은 최근 기록을 얼마나 원문으로 남길지 정합니다. SummarizationMiddleware는 before_model 훅에서 메시지 수나 토큰 수를 검사합니다. 요약 모델은 압축문을 만들고 주 모델은 압축된 문맥으로 답합니다. 압축은 원문을 완전히 보존하지 않으므로 결정, 예외, 날짜, 출처처럼 반드시 남겨야 할 필드를 프롬프트와 검증에 넣어야 합니다.

코드를 읽는 순서

요약 압축은 오래된 메시지의 핵심을 짧은 메시지로 바꾸어 다음 모델 입력을 줄이는 처리입니다. SummarizationMiddleware는 트리거 조건을 넘으면 요약 모델을 호출하고, 최근 메시지 일부와 생성한 요약을 다음 요청에 전달합니다. 체크포인터의 과거 기록 전체를 삭제하는 기능과는 다릅니다. 무엇을 저장했는지와 이번 모델에 무엇을 보냈는지를 구분합니다.

실습의 CaptureAll과 CaptureCompressed는 모델이 실제로 받은 메시지를 seen_before, seen_after에 복사하는 관찰 장치입니다. 요약문의 길이만 줄었다고 성공으로 판단하지 않고, 대출 권수·기간·연장 조건·출처가 남았는지 문자열을 읽습니다. 압축은 손실을 허용하는 변환이므로 업무에 필요한 사실을 먼저 정해야 합니다.

도식 읽기

파란 원본 여섯 메시지가 노란 trigger 검사로 들어갑니다. 임계값 미만이면 그대로 보라색 주 모델로 이동합니다. 임계값 이상이면 오래된 메시지가 보라색 요약 모델을 거쳐 파란 요약문과 최근 두 메시지로 바뀐 뒤 주 모델에 전달됩니다. E01 p.3은 압축 뒤에도 확인할 보존 항목입니다.

5실행 예제

여섯 메시지를 Before 에이전트에 그대로 전달한 뒤, trigger=4·keep=2 조건의 SummarizationMiddleware를 붙입니다. 결정적 요약문으로 메시지 구성 변화를 재현하고, 별도 실제 모델 호출로 권수·기간·연장 조건·출처를 보존한 요약문과 사용량을 확인합니다.

# 정해 둔 응답으로 미들웨어 실행 순서를 재현합니다.
from typing import Any
from langchain.agents import create_agent
from langchain.agents.middleware import AgentMiddleware
from langchain.tools import tool
from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.messages import AIMessage
from langchain_core.outputs import ChatGeneration, ChatResult
class ScriptedModel(BaseChatModel):
    replies: list[AIMessage]
    index: int = 0
    @property
    def _llm_type(self) -> str: return "scripted-model"
    def _generate(self, messages: Any, stop: Any = None, run_manager: Any = None, **kwargs: Any) -> ChatResult:
        reply = self.replies[min(self.index, len(self.replies) - 1)]
        self.index += 1
        return ChatResult(generations=[ChatGeneration(message=reply)])
    def bind_tools(self, tools: Any, *, tool_choice: Any = None, **kwargs: Any) -> "ScriptedModel":
        return self
@tool
def lookup_hours(day: str) -> str:
    """자료실 운영 시간을 요일로 조회합니다."""
    return "평일 09:00~20:00" if day == "평일" else "토요일 10:00~17:00"

다른 상황과 적용 경계

친근한 말투나 반복된 인사는 요약해도 영향이 작지만, 승인 여부·계약 숫자·출처 식별자는 빠지면 후속 답이 달라질 수 있습니다. 이런 값은 상태의 별도 필드에 구조화해 보존하고 대화 요약에는 맥락만 맡기는 설계가 안전합니다.

메시지 수 감소와 토큰 수 감소는 관련되지만 같은 값은 아닙니다. 긴 한 메시지가 짧은 여러 메시지보다 토큰이 많을 수 있습니다. 이번 실습은 전달 메시지와 보존 문자열을 확인하며, 실제 모델별 토큰 절감률이나 요약 정확도 전체를 보장하지 않습니다.

6일부러 실패해 보기

Before에서는 여섯 메시지가 그대로 주 모델에 전달됩니다. After에서는 trigger=(messages,4), keep=(messages,2)를 적용해 오래된 대화를 요약 메시지로 바꾸고 최근 두 메시지를 유지합니다. 학습용 요약 모델이 만든 문자열에서 14일, 예약 없음, E01 p.3을 검사합니다. 이 검사는 설정이 실행됐음을 보여 주지만 실제 생성 모델의 모든 요약이 정확하다는 뜻은 아닙니다.

앞의 실행 예제를 실행한 같은 노트북에서 Before 다음 After 순서로 실행합니다. 출력은 실제 실행 결과입니다.

Before: 원문 전체 전달

seen_before=[]
class CaptureAll(AgentMiddleware):
    def wrap_model_call(self, request: Any, handler: Any) -> Any:
        seen_before.extend(message.text for message in request.messages)
        return handler(request)
before_agent=create_agent(ScriptedModel(replies=[AIMessage("답")]),tools=[],middleware=[CaptureAll()])
before_agent.invoke({"messages":history})

 ScriptedModel(replies=[AIMessage("압축된 조건을 확인했습니다.")]), tools=[],

7주의할 점과 실무 메모

  • 메시지 개수 임계값은 문자 수나 실제 토큰 수와 다릅니다. 운영에서는 모델 프로필이 확인되면 토큰 또는 fraction 조건을 검토합니다.
  • 요약 호출도 비용과 지연을 추가합니다. 너무 낮은 임계값은 매번 요약을 실행할 수 있습니다.
  • 압축본에는 원문 식별자를 남겨 중요한 판단 전에 원문을 다시 확인할 수 있게 합니다.

실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.

8정리와 다음 절

  • SummarizationMiddleware는 trigger에 도달하면 오래된 메시지를 요약하고 keep 범위는 원문으로 남깁니다.
  • 여섯 메시지가 요약문과 최근 두 메시지로 바뀌며 날짜·예외·출처가 남았는지 확인했습니다.
  • 결정적 요약문의 검사 통과는 실제 생성 모델의 정확성을 보장하지 않습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 모델 호출 횟수 제한과 재시도·폴백을 내장 미들웨어로 조합합니다.

9복습 문제

문제와 해설

1. trigger와 keep의 역할은 각각 무엇인가요?

해설 — trigger는 압축 시작 조건, keep은 압축하지 않고 남길 최근 범위를 정합니다.

2. 메시지 수 임계값의 한계는 무엇인가요?

해설 — 메시지마다 길이가 달라 실제 토큰 사용량을 정확히 나타내지 못합니다.

3. 압축 결과에서 출처 식별자를 보존하는 이유는 무엇인가요?

해설 — 중요한 판단 때 압축 주장과 원문을 다시 대조하기 위해서입니다.

4. 요약 미들웨어가 비용을 항상 줄인다고 단정할 수 없는 이유는 무엇인가요?

해설 — 별도 요약 모델 호출 비용이 들고 임계값과 대화 길이에 따라 절감량이 달라집니다.
