## S1 · 반드시 수정

### 1. 2절의 저장 출력과 본문·검증 기록이 다릅니다

- 노트북 `02-토큰과-중간-진행-스트리밍.ipynb`의 실제 출력: `토큰 조각 수: 71`
- `_src/02-토큰과-중간-진행-스트리밍.html`: `messages는 73개 조각`
- `qa/authoring-checklist.md`와 `qa/verification.md`: `messages 73개 조각`

실행 출력이 정본이므로 본문·체크리스트·검증 기록을 71로 맞추거나 새 커널에서 다시 실행한 뒤 모든 수치를 함께 갱신해야 합니다.

### 2. 3절 복습 문제의 수치가 저장 출력과 다릅니다

- 노트북 실제 출력: `custom first_event_s: 0.001`
- 본문 실험 해석: 0.001초
- 복습 문제 1: `custom의 first_event 0.002초`

복습 문제도 같은 실행 결과인 0.001초를 사용해야 합니다. 현재 문항은 학생이 노트북과 본문 중 어느 값을 근거로 답해야 하는지 혼동하게 합니다.

### 3. 2절의 `seen["messages"]`는 토큰 수가 아닙니다

코드는 `messages` 사건이 발생할 때마다 1을 더합니다. 내용이 비어 있는 마지막 조각도 셀 수 있고 한 `AIMessageChunk.text`에 여러 토큰이 들어갈 수 있습니다. 그런데 출력 이름은 `토큰 조각 수`이고 본문은 `답변 토큰`과 `messages 73개 조각`을 이어 설명합니다.

사건 수는 `메시지 조각 수`로 표시하고, 모델 토큰은 마지막 사용량 메타데이터의 `output_tokens`로 별도 기록해야 합니다. 내용이 있는 첫 조각, 빈 조각, 실제 출력 토큰 수를 구분해야 합니다.

### 4. 3절은 모드별 사용량을 기록하지 않아 비교 조건을 검증할 수 없습니다

3절은 동일한 질문·모델로 `updates`, `messages`, `custom`을 순서대로 세 번 호출하지만 `usage_metadata`를 수집하지 않습니다. 따라서 각 실행의 입력·출력 토큰이 같았는지, 응답 길이 차이가 전체 시간에 영향을 주었는지 확인할 수 없습니다. 본문도 비용이 실제 토큰과 호출 수에 좌우된다고 설명하지만 이를 실행하지 않습니다.

각 실행에서 최종 모델 메시지의 입력·출력 토큰을 기록해야 합니다. 비교표에는 질문, 모델, reasoning 설정, 실행 순서, first event, TTFT, total, 입력 토큰, 출력 토큰을 함께 넣어야 합니다. 현재 결과는 네트워크 조건뿐 아니라 생성 응답 길이도 통제되지 않았습니다.

## S2 · 중요한 보완

### 5. 세 모드 시간 비교는 세 번의 독립 API 호출이라 동일 실행 비교가 아닙니다

질문·모델·그래프는 같지만 각 모드에서 모델을 새로 호출합니다. 저장 결과도 updates 0.991초, messages 1.008초, custom 1.003초로 서로 다른 요청에서 나왔습니다. 본문은 이 한계를 밝히고 있어 허위 단정은 피했지만, 도식 제목과 학습 목표의 “같은 에이전트를 세 모드로 실행”만 보면 같은 실행에서 얻은 지표처럼 읽힐 수 있습니다.

한 실행에서 `stream_mode=["messages", "updates", "custom"]`을 구독해 first custom event, first message event, first content chunk, updates event, total을 같은 호출에서 측정하는 실험을 기본 비교로 두는 편이 적절합니다. 세 번의 독립 호출 비교를 유지한다면 이를 부가 실험으로 분리하고 사용량과 반복 횟수를 추가해야 합니다.

### 6. 2절 도식에 실제로 실행하지 않은 도구가 표시됩니다

`02-흐름.svg`의 첫 상자는 `모델·도구 실행`이지만 노트북의 `answer` 노드는 모델만 호출하고 LangChain 도구를 정의하거나 실행하지 않습니다. 본문은 “도구 호출 진행 상황은 도구 내부에서 custom 사건을 보내야 한다”고 설명하지만 해당 동작은 후속 권고이며 실제 관찰이 아닙니다.

도식을 `모델 실행`으로 한정하거나 실제 도구와 custom writer를 추가해야 합니다. 실행하지 않은 후속 기능은 도식에서 구분해 표시해야 합니다.

### 7. 3절 도식이 first event와 TTFT의 핵심 차이를 표현하지 못합니다

도식은 세 모드 다음에 `first_event · TTFT · total`을 한 상자에 넣어 모든 모드가 세 지표를 제공하는 것처럼 보입니다. 실제 출력에서 TTFT는 `messages`에만 있고 updates/custom의 `ttft_s`는 `None`입니다. `custom first_event → 즉시`, `messages first content chunk → TTFT`, `stream 종료 → total`의 세 측정 지점을 별도 화살표로 표시해야 본문 정의와 일치합니다.

### 8. 1절의 로컬 실습이 불필요하게 OpenAI 키에 의존합니다

1절은 모델을 호출하지 않는 합성 로컬 StateGraph이며 `messages=0`을 의도적으로 관찰합니다. 그런데 공통 설치 셀이 `OPENAI_API_KEY`가 없으면 중단합니다. 이 때문에 키가 없는 학생은 비용 0인 일곱 모드 구조 실습도 실행할 수 없습니다.

1절에서는 키 검사를 제거하고 API 비용을 0달러로 명시해야 합니다. 2·3절에서만 키를 요구하면 로컬 실습과 실제 API 실습의 경계가 더 분명해집니다.

### 9. 2절은 조각을 합친 결과와 최종 상태를 대조하지 않습니다

코드는 내용이 있는 조각을 `preview`에 모으지만 앞부분 80자만 출력하고, `updates`의 최종 `answer`와 전체 결합 문자열이 같은지 확인하지 않습니다. 따라서 “토큰 조각이 순서대로 도착했다”는 본문 설명을 실제 완성 결과로 검증하지 못합니다.

내용 조각 전체를 합친 문자열과 updates가 반환한 최종 answer를 대조하고 `assert`해야 순서·누락 여부를 확인할 수 있습니다.

## 확인된 적합 사항

- LangGraph 1.2.11의 `StreamMode` 일곱 값은 `values`, `updates`, `messages`, `custom`, `checkpoints`, `tasks`, `debug`로 조사 기록과 일치합니다.
- 1절은 `InMemorySaver`와 서로 다른 `thread_id`를 사용해 checkpoints/tasks 사건이 생성되는 조건을 충족합니다.
- 1절이 모델 없는 로컬 그래프라 `messages=0`이라고 설명한 것은 실제 코드와 일치합니다.
- 2절과 3절은 `gpt-5.4-mini`를 호출한 실제 API 실습이며 1절은 합성 로컬 실습입니다. 본문은 1절을 로컬 그래프로 명시합니다.
- 3절은 첫 `messages` 사건과 내용이 있는 첫 조각을 분리해 각각 `first_event`와 `first_token`으로 기록합니다. 저장 출력의 0.525초와 0.529초가 이 차이를 보여 줍니다.
- 3절의 total은 스트림 반복이 끝난 뒤 측정하므로 해당 실행의 전체 소비 시간을 포함합니다.
- 세 노트북은 각각 설치·환경·그래프·입력을 정의하며 앞 노트북 변수나 개인 절대 경로에 의존하지 않습니다.
- 주요 함수에 반환 타입 힌트가 있고 한국어 목적 주석이 있으며 코드 셀은 25줄 이하입니다.
