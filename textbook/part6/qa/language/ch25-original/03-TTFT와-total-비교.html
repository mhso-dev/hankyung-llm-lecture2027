1학습 목표

  • TTFT와 total 비교의 핵심 구성 요소를 실제 출력에서 구분할 수 있습니다.
  • 같은 입력을 실행하고 호출 경계와 관찰 지표를 설명할 수 있습니다.
  • 결과가 보여 주는 범위와 추가 측정이 필요한 범위를 나눌 수 있습니다.

2이 내용을 배우는 이유

스트리밍을 켰다는 사실만으로 응답 전체가 빨라지지는 않습니다. 사용자가 첫 변화를 본 시간, 실제 답변의 첫 토큰을 본 시간, 최종 결과가 끝난 시간을 따로 측정해야 합니다. 이 구분은 Ch30의 FastAPI 서버 전송 이벤트(SSE) 응답 설계에 그대로 이어집니다.

3앞에서 배운 내용

Ch23에서 체크포인터와 thread_id가 상태를 저장하는 방법을 배웠고, Ch24에서 interrupt와 재개 사건을 확인했습니다. 이번 챕터는 같은 실행을 사용자 화면과 운영 로그에 어떤 단위로 노출할지 다룹니다.

4핵심 개념

구체적인 상황

사용자는 화면에 첫 변화가 나타나면 시스템이 동작한다고 느끼지만, 그 변화가 실제 답변 토큰인지 ‘시작됨’ 표시인지는 구분하기 어렵습니다. 세 시각을 같은 이름으로 기록하면 성능 보고서가 잘못됩니다.

정의

첫 토큰까지의 시간(Time To First Token, TTFT)은 요청을 시작한 뒤 내용이 있는 첫 모델 메시지 조각을 받을 때까지 걸린 시간입니다. first_event는 모드와 관계없이 첫 사건을 받은 시간이고 total은 마지막 사건까지 소비한 전체 시간입니다. custom의 시작 사건을 TTFT라고 부르면 모델이 아직 답을 만들기 전의 값을 첫 토큰으로 오해하게 됩니다.

5실행 예제

perf_counter()를 요청 직전에 시작하고 세 모드를 각각 새로 실행합니다. 첫 yield를 first_event로, messages의 내용이 있는 첫 chunk를 first_token으로, 반복 종료를 total로 기록합니다. rows의 ttft_s는 messages에서만 숫자가 됩니다.

설치 셀은 Python 3.12 환경에 LangChain 1.4.0, langchain-openai 1.6.0, LangGraph 1.2.11을 고정합니다. 예상 API 비용은 1달러 미만이며 키 값은 출력하지 않습니다.

확인할 점 — 출력과 trace에서 위 설명의 변수와 단계가 실제로 이어지는지 확인합니다. assert는 관찰 결과가 기대한 구조를 만족하는지 확인하는 보조 수단입니다.

6실험 결과 해석

이번 실행에서 updates의 first_event와 total은 모두 0.991초였습니다. messages는 first_event 0.525초, 내용이 있는 첫 토큰까지 0.529초, total 1.008초였습니다. custom은 시작 사건이 0.001초에 왔고 total은 1.003초였습니다. 세 실행은 API를 각각 새로 호출했으므로 네트워크 조건이 완전히 같지는 않습니다. updates와 custom에는 TTFT가 없습니다.

이 실험은 한 질문과 한 실행 환경의 결과입니다. 모델 응답 내용과 지연 시간은 실행할 때마다 달라질 수 있습니다. 구조의 품질을 비교하려면 여러 질문, 반복 실행, 오류율, 사용자 수정 횟수를 추가로 측정해야 합니다.

7주의할 점과 실무 메모

  • 한 번의 측정으로 모델이나 모드의 우열을 단정하지 않습니다. 운영 비교에서는 워밍업, 반복 횟수, 입력 길이, 네트워크 구간, 백분위수를 함께 기록합니다. 비용은 스트리밍 여부보다 실제 입력·출력 토큰과 호출 수에 좌우됩니다.
  • 비밀 키는 .env에서 읽고 존재 여부만 확인합니다. 노트북 출력, 예외 메시지, 배포 묶음에 키가 포함되지 않았는지 발행 전에 검사합니다.
  • 외부 모델 호출의 응답과 지연은 공급자 상태에 따라 달라집니다. 운영 기준은 반복 측정의 중앙값과 상위 백분위수로 정합니다.

8정리와 다음 절

  • first_event와 TTFT와 total은 측정 지점이 다릅니다. 세 번의 별도 API 호출이라는 한계를 포함해 수치를 읽습니다.
  • 출력값과 상태를 근거로 관찰한 범위를 설명합니다.
  • 반복 측정이 없는 수치를 일반적인 성능으로 확대하지 않습니다.

다음 학습과 이어지는 지점 — Ch30에서는 messages와 custom 사건을 FastAPI SSE로 브라우저에 전송하고 연결 종료와 재접속을 처리합니다.

9복습 문제

1. custom의 first_event 0.002초를 TTFT라고 부를 수 있나요?

해설 — 아닙니다. 그 사건은 노드가 보낸 시작 알림이며 모델 답변의 첫 토큰이 아닙니다.

2. 이 절의 assert가 확인하는 것은 무엇인가요?

해설 — 노트북에서 출력한 사건, trace, 상태, 완료 조건이 의도한 구조와 일치하는지 확인합니다.

3. 한 번의 실행 결과로 평균 성능을 단정할 수 없는 이유는 무엇인가요?

해설 — 네트워크와 모델 출력이 실행할 때마다 달라질 수 있고 입력 종류도 하나뿐이기 때문입니다.

4. API 키를 실습 출력에 표시하면 안 되는 이유는 무엇인가요?

해설 — 노트북과 HTML이 공유될 때 비밀 값도 함께 공개될 수 있기 때문입니다.
