1학습 목표

  • Ch8의 Isolate를 업무별 모델 입력 분리로 설명할 수 있습니다.
  • wrap_model_call에서 request.override(messages=...)를 사용할 수 있습니다.
  • 텍스트 태그와 실제 별도 모델 요청의 차이를 검증할 수 있습니다.

2이 내용을 배우는 이유

Ch8에서는 대출 문의와 휴관 문의의 자료를 별도 메시지 목록으로 구성했습니다. create_agent 상태에는 여러 업무의 대화가 누적될 수 있고, 전체 상태를 그대로 모델에 전달하면 관련 없는 자료가 입력을 차지합니다. 미들웨어는 영구 상태를 삭제하지 않고 이번 모델 호출에 보낼 메시지만 선택할 수 있습니다. 이것이 Ch8의 Isolate를 실행 구조로 연결하는 방법입니다.

이 절의 질문 — 같은 상태에 섞인 여러 업무 메시지에서 현재 업무에 필요한 내용만 모델 요청으로 분리하려면 어떻게 할까요?

3앞에서 배운 내용

Ch8 context_lab.py의 assemble_isolated_messages는 업무별 자료를 별도 필드로 조립했고 텍스트 태그는 보안 격리가 아니라고 설명했습니다. 이번 절도 같은 경계를 지킵니다. request.override로 메시지를 줄이는 것은 모델 입력 분리이며 저장소 권한이나 프로세스 격리를 제공하지 않습니다.

4핵심 개념

비유로 시작하기

두 사건의 서류를 한 책상에 올려놓되 담당자에게는 현재 사건 서류철만 건네는 상황을 생각해 봅니다. 상태에는 감사와 추적을 위해 전체 메시지가 남아 있을 수 있습니다. IsolateMiddleware는 각 메시지의 additional_kwargs에 있는 topic을 읽어 현재 topic과 같은 메시지만 새 요청에 넣습니다. request.override는 원래 요청 객체를 바꾸지 않고 선택된 messages를 가진 새 요청을 만듭니다. handler는 그 새 요청만 모델에 전달합니다.

도식 읽기

파란 상태에는 loan 세 메시지와 hr 두 메시지가 함께 있습니다. 노란 IsolateMiddleware가 topic=loan인 세 메시지만 선택해 새 파란 요청을 만들고 보라색 모델에 전달합니다. hr 메시지로 향하는 빨간 차단 표시는 모델 입력에서 제외됐다는 뜻이며 원래 상태나 저장소에서 삭제됐다는 뜻은 아닙니다.

7주의할 점과 실무 메모

  • 메시지 메타데이터는 신뢰할 수 있는 애플리케이션 코드가 붙여야 합니다. 사용자가 topic 값을 임의로 바꿀 수 있으면 접근 통제가 되지 않습니다.
  • 민감한 자료는 선택 전에도 권한이 없는 프로세스나 상태에 넣지 않습니다. 저장소·도구·런타임 권한을 별도로 검사합니다.
  • Isolate와 Compress를 함께 쓰면 먼저 업무 범위를 선택한 뒤 그 범위 안에서 압축하는 순서를 검토합니다.

실습의 결정적 모델은 미들웨어 실행 경계를 재현하기 위한 검사 도구입니다. 실제 모델 품질, 공급자 장애율, 운영 비용을 대신 측정하지 않습니다. 적용 전에는 사용 중인 모델과 계정의 실제 사용량을 다시 확인합니다.

9복습 문제

문제와 해설

1. request.override의 역할은 무엇인가요?

해설 — 원본 요청을 직접 바꾸지 않고 일부 필드를 바꾼 새 요청을 만듭니다.

2. 메시지 태그만으로 보안 격리가 되지 않는 이유는 무엇인가요?

해설 — 같은 호출이나 상태에 들어간 자료는 모델이나 프로세스가 접근할 수 있기 때문입니다.

3. Compress와 Isolate를 함께 적용할 때 한 가지 합리적인 순서는 무엇인가요?

해설 — 현재 업무의 자료를 먼저 선택하고 그 범위 안에서 오래된 내용을 압축합니다.

4. topic 메타데이터를 누가 붙여야 하나요?

해설 — 권한과 업무 범위를 확인한 애플리케이션 코드가 붙여야 합니다.
