1학습 목표

  • 직접 도구와 MCP 도구를 같은 질문과 모델 조건에서 비교할 수 있습니다.
  • 도구 정의 개수·직렬화 크기·모델 입력 토큰을 서로 다른 측정값으로 기록할 수 있습니다.
  • 첫 호출 usage_metadata로 비용을 계산하고 결과의 적용 범위를 설명할 수 있습니다.

2이 내용을 배우는 이유

MCP는 기능을 연결하는 비용을 없애지 않습니다. 모델이 어떤 도구를 고를지 판단하려면 이름·설명·입력 스키마를 첫 호출에 받아야 합니다. Ch19에서 도구 개수가 늘면 선택 정보가 커진다는 사실을 배웠습니다. 이제 직접 도구와 MCP 어댑터 도구를 같은 모델에 연결해 프로토콜 도입 자체와 도구 정의 수 증가를 분리합니다.

3앞에서 배운 내용

Ch19에서 bind_tools가 도구 설명을 모델 요청에 포함시키고 usage_metadata가 입력·출력 토큰을 제공한다는 사실을 확인했습니다. 앞 절에서 MCPAdapter가 MCP 도구를 BaseTool로 변환했습니다. 이번 실험은 도구 실행 뒤의 두 번째 호출이 아니라, 도구를 고르는 첫 모델 호출만 측정합니다.

4핵심 개념

쉬운 예

메뉴판의 음식 수와 종이 무게는 관련이 있지만 같은 값은 아닙니다. 도구 정의 수는 항목 개수입니다. JSON Schema 직렬화 문자의 수는 클라이언트가 가진 정의의 대략적인 크기입니다. input_tokens는 모델 제공자가 실제 요청을 토큰화하고 보고한 값입니다. MCP JSON-RPC 전송 바이트는 클라이언트와 서버 사이 통신량이며 usage_metadata에 포함되지 않습니다. 따라서 MCP 연결 전후 토큰을 말할 때는 모델에 전달한 도구 정의가 무엇인지 함께 기록해야 합니다. 직접 도구 한 개와 MCP 도구 한 개 비교는 어댑터 변환 차이를, MCP 도구 한 개와 다섯 개 비교는 목록 규모 차이를 보여 줍니다.

정의와 경계

첫 호출 입력 토큰은 사용자 메시지와 시스템 지침, 모델에 전달된 도구 정의 등 첫 모델 요청에 포함된 입력을 제공자가 토큰화한 수치입니다. 이번 실험에서는 대화 이력과 도구 결과가 아직 없으므로 도구 정의 규모의 차이를 읽기 좋습니다. schema_chars는 동일한 Python JSON 직렬화 방식으로 이름·설명·스키마를 문자열로 바꾼 문자 수입니다. 이 값은 토큰 수의 대체물이 아니며 설명 길이를 대조하는 보조 측정입니다. 직접 도구와 MCP 도구가 같은 158 입력 토큰을 기록하면 MCP라는 이유만으로 모델 입력이 늘었다고 말할 수 없습니다. MCP 도구 다섯 개가 316 토큰을 기록한 결과는 이 실행에서 정의 수와 내용이 늘어 입력이 커졌다는 증거입니다.

코드 읽기와 비교 경계

bind_tools(tools, tool_choice='required')는 선택 가능한 도구 정의를 첫 모델 요청에 포함하고 모델이 반드시 하나의 도구 호출을 만들도록 합니다. 이때 도구가 실행되는 것은 아닙니다. 반환한 첫 AIMessage의 tool_calls에는 선택한 이름과 인자가 있고, usage_metadata['input_tokens']에는 공급자가 보고한 전체 입력 토큰이 있습니다. schema_chars는 도구 이름·설명·스키마를 같은 JSON 방식으로 직렬화한 문자 수라서 정의 규모를 읽는 보조값입니다.

도구 수와 입력 토큰의 관계를 분리해서 읽어야 합니다. 직접 도구 한 개와 MCP 도구 한 개는 연결 방식이 다르지만 모델에 보이는 변환 결과가 비슷할 수 있습니다. MCP 한 개와 다섯 개 비교에서는 개수뿐 아니라 각 이름과 설명의 내용도 함께 바뀝니다. 따라서 이번 결과는 ‘이 정의 묶음에서 다섯 개 조건의 입력이 더 컸다’는 관찰입니다. 자주 쓰지 않는 도구를 상황에 따라 필터링하면 선택 오류와 입력 규모를 함께 줄일 수 있지만, 권한이 없는 도구를 숨기는 일은 서버의 인가 검사를 대신하지 않습니다.

A는 직접 @tool 한 개, B는 같은 역할의 MCP 도구 한 개, C는 읽기 전용 MCP 도구 다섯 개입니다. 각 호출에서 input_tokens, output_tokens와 첫 AIMessage의 tool_calls를 출력합니다. 실행된 수치는 노트북 출력과 verification.md에 기록합니다. 한 번의 작은 질문이므로 토큰 증가 방향을 관찰할 수 있지만 모든 모델과 제공자의 직렬화 방식에 일반화할 수는 없습니다.

6실험 결과 해석

같은 gpt-5.4-mini 모델에서 직접 도구 한 개와 MCP 도구 한 개는 같은 input_tokens를 기록했습니다. MCP 도구 다섯 개 조건에서는 입력 토큰이 늘었습니다. 따라서 이 작은 조건에서는 MCP 연결 자체보다 다섯 도구의 이름·설명·스키마가 함께 늘어난 쪽에서 입력 토큰 차이가 나타났습니다. 첫 도구 선택 결과도 조건마다 같지 않을 수 있습니다. 이 값은 한 번의 실행 결과이며, 다른 모델·도구 정의·제공자 직렬화 방식에는 그대로 적용할 수 없습니다.

7주의할 점과 실무 메모

  • MCP 연결 초기화·목록 조회의 JSON-RPC 바이트를 모델 입력 토큰으로 부르지 않습니다. 이 실습은 OpenAI가 보고한 모델 호출 usage_metadata를 측정합니다.
  • 직접 도구 한 개와 MCP 도구 한 개는 이름과 변환된 스키마 표현이 완전히 같지 않으므로 결과 차이를 MCP 하나의 원인으로 단정하지 않습니다. MCP 한 개와 다섯 개 조건도 도구 수와 각 정의 내용이 함께 바뀝니다.
  • 도구가 많다고 항상 선형으로 같은 토큰 수가 늘지는 않습니다. 이름·설명·스키마 길이와 제공자 직렬화가 함께 영향을 줍니다.
  • 비용은 2026-09-11에 이 교재가 사용하는 기존 gpt-5.4-mini 단가 가정으로 추정하며 모든 조건 합계가 1달러 미만인지 확인합니다. 실제 청구는 계정 조건에 따라 달라질 수 있습니다.
  • 권한이 없는 도구는 모델에게 보이지 않게 서버나 클라이언트에서 필터링하면 보안 범위와 도구 정의 입력을 함께 줄일 수 있습니다. 단, 토큰 절감을 권한 검사의 대체 수단으로 사용해서는 안 됩니다.

8정리와 다음 절

  • MCP의 발견·전송·모델 호출은 서로 다른 층이므로 각 층의 값을 따로 측정합니다.
  • 서버 기능은 클라이언트가 발견할 수 있어도 인증과 인가를 통과한 범위에서만 실행합니다.
  • 실습 결과는 고정 버전과 로컬 읽기 전용 서버의 범위에서 해석합니다.

다음 학습과 이어지는 지점 — Ch29에서는 최종 답만 보지 않고 도구 선택과 호출 순서를 포함한 실행 궤적을 평가합니다. Ch37에서는 MCP 도구 정의가 계기판의 컨텍스트 지표를 어떻게 악화시키는지 다시 측정합니다.

9복습 문제

문제 1

usage_metadata의 input_tokens가 포함하지 않는 것은 무엇인가요?

해설 — MCP 클라이언트와 서버 사이에서 오간 JSON-RPC 전송 바이트입니다.

문제 2

직접 도구 한 개와 MCP 도구 한 개를 비교하는 이유는 무엇인가요?

해설 — 도구 수 증가와 어댑터 변환의 영향을 분리해서 보기 위해서입니다.

문제 3

MCP 도구 한 개와 다섯 개 조건에서 고정한 값은 무엇인가요?

해설 — 모델, 질문, 첫 호출, tool_choice와 추론 설정을 고정합니다.

문제 4

권한별 도구 필터링의 두 효과는 무엇인가요?

해설 — 사용자가 호출할 수 있는 범위를 제한하고 모델에 전달할 불필요한 도구 정의를 줄입니다.

문제 5

한 번의 측정으로 모든 MCP 서버의 비용을 단정할 수 없는 이유는 무엇인가요?

해설 — 도구 설명 길이, 스키마, 모델, 제공자 직렬화와 실행 시점이 다르기 때문입니다.
