1학습 목표

  • 클라이언트가 course_server.py를 stdio 하위 프로세스로 실행할 수 있습니다.
  • stdio와 Streamable HTTP의 프로세스·네트워크 경계를 비교할 수 있습니다.
  • 하위 프로세스 환경 변수와 원격 인증 정보를 최소 범위로 구성할 수 있습니다.

2이 내용을 배우는 이유

같은 도구 목록을 제공해도 서버가 어디에서 실행되는지에 따라 위험이 달라집니다. stdio에서는 클라이언트가 로컬 하위 프로세스를 만들고 표준 입력과 출력으로 통신합니다. 원격 서버에서는 이미 실행 중인 HTTP 서비스에 연결합니다. 코드를 그대로 옮기기 전에 누가 서버를 시작하고 어떤 비밀과 파일에 접근할 수 있는지 선을 그어야 합니다.

3앞에서 배운 내용

앞 절에서 course_server.py의 main 블록이 stdio 전송을 시작하도록 작성했습니다. Ch16에서 허용 목록과 최소 권한을 다뤘고, Ch24에서 사람이 승인해야 하는 작업 경계를 확인했습니다. 여기서는 인증(authentication: 누구인지 확인)과 인가(authorization: 무엇을 할 수 있는지 결정)를 구분합니다.

4핵심 개념

쉬운 예

stdio는 같은 컴퓨터 안의 전용 통로입니다. 클라이언트가 서버 프로세스의 시작과 종료를 관리하며 네트워크 포트를 열지 않습니다. 그러나 하위 프로세스는 전달받은 환경 변수와 운영체제 권한으로 로컬 파일에 접근할 수 있습니다. Streamable HTTP는 네트워크 주소의 서비스에 연결하며 여러 클라이언트가 사용할 수 있습니다. 서버는 요청의 Origin을 검증해야 합니다. 로컬 실행은 127.0.0.1에 바인딩하고, 공개 서비스에는 통신 보호와 인증·사용자별 인가를 설계합니다. MCP 공식 스펙은 HTTP 전송의 OAuth 절차를 stdio에 그대로 적용하지 않으며, stdio 구현은 필요한 자격 정보를 환경에서 읽을 수 있습니다. HTTP에서는 Authorization 헤더나 OAuth 흐름을 쓸 수 있지만, 헤더가 있다는 사실만으로 모든 도구를 허용해서는 안 됩니다.

정의와 경계

전송(transport)은 JSON-RPC 메시지를 어느 통로로 옮길지 정합니다. stdio 전송은 줄바꿈으로 구분한 메시지를 하위 프로세스의 표준 입력과 출력에서 교환합니다. Streamable HTTP 전송은 하나의 MCP 엔드포인트에 HTTP POST와 선택적인 GET을 사용합니다. 전송 선택은 도구의 업무 의미를 바꾸지 않지만 연결 수명, 자격 정보 위치, 접근 가능한 사용자의 범위를 바꿉니다. 인증은 요청 주체를 확인하는 과정이고 인가는 확인된 주체가 특정 도구를 호출할 수 있는지 판정하는 과정입니다. 최소 권한은 서버 프로세스와 사용자에게 필요한 자원과 동작만 허용하는 원칙입니다.

코드 읽기와 비교 경계

stdio 연결에서는 클라이언트가 서버 명령을 하위 프로세스로 시작하고 표준 입력·출력으로 JSON-RPC 메시지를 교환합니다. env에 넘긴 사전은 그 프로세스가 볼 수 있는 환경 변수를 정합니다. 부모 프로세스의 전체 환경을 복사하면 API 키처럼 서버에 필요하지 않은 값도 함께 전달될 수 있습니다. 필요한 변수만 새 사전에 넣는 After 코드는 서버 기능은 유지하면서 노출 범위를 줄입니다.

Streamable HTTP에서는 서버가 별도 주소에서 실행되므로 프로세스 환경 대신 네트워크 요청의 인증 정보와 서버 측 인가가 중요합니다. TLS는 전송 중 내용을 보호하고 인증은 요청 주체를 확인하지만, 어떤 사용자가 어떤 도구를 실행할 수 있는지는 인가 규칙이 정합니다. stdio가 로컬이라는 이유로 안전하다고 단정할 수도 없습니다. 하위 프로세스는 전달받은 운영체제 권한으로 파일과 네트워크에 접근할 수 있으므로 실행 파일, 환경, 작업 폴더를 함께 제한해야 합니다.

7주의할 점과 실무 메모

  • stdio라는 이름만으로 서버가 안전해지는 것은 아닙니다. 실행 파일 경로를 고정하고 설치 출처를 확인하며 전달 환경을 제한합니다.
  • Streamable HTTP 서버는 127.0.0.1 실험과 공개 네트워크 배포를 구분합니다. 이 챕터는 외부에 포트를 공개하지 않습니다.
  • 원격 토큰은 코드나 노트북 출력에 적지 않습니다. .env에서 읽고 헤더를 구성하더라도 존재 여부만 확인합니다.
  • 인증은 사용자 신원을 확인하고 인가는 도구·리소스별 허용 범위를 정합니다. 읽기 권한이 있는 사용자가 관리 도구까지 호출할 수 있어서는 안 됩니다.

8정리와 다음 절

  • MCP의 발견·전송·모델 호출은 서로 다른 층이므로 각 층의 값을 따로 측정합니다.
  • 서버 기능은 클라이언트가 발견할 수 있어도 인증과 인가를 통과한 범위에서만 실행합니다.
  • 실습 결과는 고정 버전과 로컬 읽기 전용 서버의 범위에서 해석합니다.

다음 학습과 이어지는 지점 — 다음 절에서는 stdio 서버의 도구를 LangChain BaseTool로 변환하고 기존 bind_tools 흐름에 연결합니다.

9복습 문제

문제 1

stdio 서버를 누가 시작하나요?

해설 — 일반적으로 MCP 클라이언트가 로컬 하위 프로세스로 시작하고 종료합니다.

문제 2

부모 환경 전체를 하위 프로세스에 전달할 때의 문제는 무엇인가요?

해설 — 서버에 필요하지 않은 비밀 값과 설정까지 접근 가능해질 수 있습니다.

문제 3

인증과 인가는 어떻게 다른가요?

해설 — 인증은 사용자가 누구인지 확인하고, 인가는 확인된 사용자가 어떤 기능을 사용할 수 있는지 결정합니다.

문제 4

이 실습에서 원격 서버를 공개하지 않는 이유는 무엇인가요?

해설 — TLS·OAuth·호스팅 운영까지 검증하지 않은 상태에서 외부 접근 경계를 만들지 않기 위해서입니다.
