### 2-2. 바꾼 값 — 인계 후보 (가) 도구 수 1 → 3, 05와 겹치지 않는 설계

- 인계 후보 (가) 도구 수·(나) 설명을 늘린 판 모두 **05가 첫 요청으로 이미 보인 비교**(05 5절 MCP 하나 187 ↔ 셋 252 · 설명을 늘린 판 218)라, 그대로 쓰면 05를 되풀이합니다(Ch 26 B-7). 그래서 **05가 재지 않았다고 적은 것**을 새로 볼 것으로 잡았습니다 — 05 b7 「도구를 알린 에이전트는 요청마다 도구 명세를 다시 싣습니다 … 이 절은 첫 요청만 셌고, 여러 요청의 합은 재지 않았습니다」. 06은 에이전트를 실제로 실행해 **둘째 요청(도구를 부른 뒤의 요청)**과 **실행 합**을 요청 번호마다 견줍니다.
- 값 하나는 `tool_count`(서버가 알린 도구 셋에서 앞의 몇 개를 붙이나 — 05 4절 `wide_tools[:count]` 슬라이싱과 같은 모양). 서버·질문·시스템 메시지 글·호출 한도·조립 함수는 같고, 서버 객체도 하나(도구 셋을 알림)라 연결 방법이 바뀌지 않습니다.
- (가)를 (나)보다 고른 까닭: 02 기능(서버에 도구 붙이기)이 흐름에서 쓰이고(붙인 두 도구가 실행 2에 실림), 「서버가 알린 도구를 모두 붙일지」는 MCP를 쓸 때 실제로 정할 일입니다(b2·b7 실무 메모). 단점(도구가 셋이면 모델이 다른 도구를 고를 수 있음)은 §0 규칙으로 막았고, 흔들림 확인 열 번·두 커널 모두 `lookup_policy` 하나.
- b2 「새로 볼 것」은 실행이 보인 만큼만: 「두 조건의 첫 요청은 05절 5절에서 이미 셌습니다. 새로 볼 것은 … 둘째 요청과, 실행 전체의 입력 토큰 합」. 첫 요청 187·252는 본문에서 「05절 5절에서 본 값과 같음」으로만 적었습니다.
