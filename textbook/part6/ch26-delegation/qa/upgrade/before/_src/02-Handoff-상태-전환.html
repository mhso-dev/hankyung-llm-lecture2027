1학습 목표

  • Handoff 상태 전환의 핵심 구성 요소를 실제 출력에서 구분할 수 있습니다.
  • 같은 입력을 실행하고 호출 경계와 관찰 지표를 설명할 수 있습니다.
  • 결과가 보여 주는 범위와 추가 측정이 필요한 범위를 나눌 수 있습니다.

2이 내용을 배우는 이유

사용자가 여러 턴에 걸쳐 같은 담당자와 대화해야 하면 매번 새로 분류하는 것만으로 부족합니다. Handoff는 active_agent 같은 상태를 바꾸고 다음 턴의 동작을 그 상태에 맞춰 선택합니다. 담당 전환과 완료 조건을 상태로 남겨야 대화가 예상한 위치에서 이어집니다.

3앞에서 배운 내용

Ch20에서 ToolNode와 명시적 END 조건을, Ch23에서 thread_id와 체크포인터를 배웠습니다. Ch25에서는 실행 사건을 스트리밍했습니다. 이번 챕터에서는 여러 에이전트 사이의 제어권과 맥락을 어디에 둘지 결정합니다.

4핵심 개념

구체적인 상황

첫 턴에서 고객이 환불 담당자를 요청하고 두 번째 턴에서 주문 번호만 말합니다. 두 번째 문장에는 ‘환불’이 없으므로 이전 담당자를 저장하지 않으면 일반 상담으로 되돌아갑니다.

정의

핸드오프(Handoff)는 도구 호출이나 그래프 노드가 active_agent 또는 current_step 상태를 바꾸어 제어권을 다른 담당 동작으로 전환하는 패턴입니다. 전환된 담당자는 사용자와 직접 대화할 수 있고, 체크포인터가 active_agent를 저장하면 다음 턴도 그 상태에서 이어집니다. 전환 도구가 메시지와 상태 중 무엇을 넘기는지 명시해야 합니다.

코드 읽기와 비교 경계

active_agent는 현재 대화를 담당하는 이름을 상태에 저장하는 필드입니다. 첫 호출은 message, 빈 active_agent, 빈 reply를 넣지만 두 번째 호출은 새 message만 전달합니다. 같은 thread_id와 체크포인터를 사용하므로 런타임이 직전 상태를 읽고 누락된 active_agent를 이어 줍니다. dispatch()는 새 메시지에 명시적인 전환 신호가 있으면 담당자를 바꾸고, 그렇지 않으면 저장된 담당자를 유지합니다. respond()는 갱신된 상태를 받아 답변을 만듭니다.

핸드오프는 함수를 한 번 호출하고 결과를 반환받는 서브에이전트 위임과 다릅니다. 위임 뒤에는 중앙 에이전트가 계속 사용자와 대화하지만, 핸드오프 뒤에는 선택된 담당자가 다음 턴의 제어권을 가집니다. 배송 문의가 해결된 뒤 일반 상담으로 복귀하려면 active_agent를 언제 초기화할지 별도 전환 규칙이 필요합니다. 이 예제의 종료 판정은 주문 번호 문자열과 담당자 이름만 확인하므로 실제 주문이 존재하거나 환불이 가능한지는 검증하지 않습니다.

5실행 예제

dispatch는 새 메시지와 저장된 active_agent를 함께 읽습니다. InMemorySaver와 thread_id='handoff-demo'를 사용해 두 턴을 실행합니다. 두 번째 결과가 refund_agent를 유지하고 주문 번호 A-102가 있으면 완료 조건을 참으로 만듭니다.

설치 셀은 Python 3.12 환경에 LangGraph 1.2.11만 고정합니다. 모든 노드는 로컬 Python 함수이며 모델 API 키를 사용하지 않습니다.

확인할 점 — 같은 thread_id에서 첫 턴과 둘째 턴의 active_agent가 모두 refund_agent인지 확인합니다. A-102 문자열 확인은 실습의 종료 조건일 뿐 실제 주문 조회가 아닙니다.

6실험 결과 해석

첫 턴의 ‘환불’ 표현이 active_agent를 refund_agent로 바꿨고 같은 thread_id의 두 번째 호출도 refund_agent를 유지했습니다. 주문 번호 A-102가 모이자 실습의 완료 조건이 참이 되어 다음 상태를 END로 표시했습니다. 실제 서비스에서는 전환 권한과 사용자 확인도 함께 설계해야 합니다.

이 결과는 같은 thread_id의 메모리에서 담당자 상태가 유지된 것을 보여 줍니다. 프로세스를 다시 시작했을 때의 영속성이나 실제 주문 존재 여부는 검증하지 않습니다.

7주의할 점과 실무 메모

  • Handoff는 다음 사용자 턴의 담당자를 바꾸는 상태 전환입니다. 언제 일반 담당자로 복귀할지 규칙을 함께 정합니다.
  • InMemorySaver는 프로세스 내 실습에 적합합니다. 재시작 후에도 상태를 유지하려면 영속 저장소와 보존·삭제 규칙을 구성합니다.

8정리와 다음 절

  • Handoff는 다음 턴의 동작을 바꾸는 상태 전환입니다. active_agent 유지와 A-102 수집을 각각 대화 지속과 완료 판정의 근거로 사용합니다.
  • thread_id가 연결한 두 호출에서 active_agent가 유지되는지 상태 출력으로 확인합니다.
  • 메모리 체크포인터는 현재 프로세스 내에서만 유지되므로 서버 재시작 영속성은 별도 저장소로 검증합니다.

다음 학습과 이어지는 지점 — 다음 절에서는 한 번의 구조화 분류가 여러 독립 전문가를 선택하고 병렬 실행하는 Router를 구현합니다.

9복습 문제

1. 두 번째 턴이 refund_agent에서 이어진 근거는 무엇인가요?

해설 — 같은 thread_id의 체크포인트에 첫 턴의 active_agent가 저장되었기 때문입니다.

2. 두 번째 호출에 새 thread_id를 사용하면 어떤 상태가 달라지나요?

해설 — 첫 턴의 active_agent가 저장된 체크포인트를 읽지 못하므로, 이 실습의 dispatch는 general_agent를 선택합니다.

3. A-102가 있어도 완료 조건이 거짓이 되는 경우는 언제인가요?

해설 — active_agent가 refund_agent가 아니면 주문 번호만으로는 완료가 아닙니다. 이 실습은 필수 정보와 담당자 상태를 함께 확인합니다.

4. 운영 체크포인터의 개인정보 보존 기간을 정해야 하는 이유는 무엇인가요?

해설 — 다음 턴에 담당자를 유지하려면 상태를 저장해야 하지만, 주문 정보와 대화 기록은 보관 기간과 삭제 방법도 함께 정해야 합니다.
