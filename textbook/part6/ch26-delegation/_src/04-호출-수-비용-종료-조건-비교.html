1학습 목표

  • 같은 문의를 서브에이전트·핸드오프·라우터에 보내고, 구조마다 모델 요청 수를 셈으로 설명할 수 있습니다.
  • 실행 한도와 호출 한도로 멈춘 실행을 만들고, 멈춘 까닭을 출력에서 읽을 수 있습니다.
  • 필요한 결과가 다 모였는지 보는 완료 조건을 구조마다 문장과 코드로 적을 수 있습니다.

2이 내용을 배우는 이유

01절부터 03절까지 위임 구조 셋을 차례로 만들었습니다. 구조를 고를 때는 요청이 몇 번 나가는지와 언제 끝나는지를 함께 따져야 합니다. 그런데 구조마다 다른 문의로 실행했기 때문에, 같은 일을 시켰을 때 무엇이 다른지는 아직 보지 못했습니다. 이 절은 같은 문의와 같은 전문 에이전트로 세 구조를 한 번씩 실행해 견줍니다.

절 제목의 종료 조건은 두 가지로 나눠 봅니다. 하나는 Ch 17 03절의 정지 조건으로, 실행이 멈추는 까닭입니다. 다른 하나는 이 절이 새로 적는 완료 조건으로, 일이 끝났는지 보는 기준입니다. 한도에 닿아 멈춘 실행은 멈추기는 했어도 일을 끝내지 못했을 수 있습니다.

3앞에서 배운 내용

01절에서는 중앙 에이전트가 도구로 전문 에이전트에게 일을 맡겼습니다. 요청 수는 중앙 = 도구를 요청한 응답 수 + 1, 전문 = 부른 횟수로 셌습니다. 02절의 핸드오프는 넘긴 차례에 첫 담당 1번과 받은 담당 1번 요청했습니다. 02절 5절에서는 도구 메시지가 빠진 넘기기 기록을 모델 없이 보았습니다. 03절의 라우터는 분류 1 + 고른 분야 수만큼 요청했고, 걸리는 분야가 없으면 조용히 끝났습니다.

Ch 17 03절에서는 반복을 멈추는 정지 조건 넷을 보았습니다. 모델의 끝 선택, 사람 확인, 같은 도구를 다시 고름, 바퀴 한도입니다. Ch 20 03절의 실행 한도는 그래프가 진행한 단계 수의 한도였고, 넘으면 GraphRecursionError가 났습니다. Ch 22 04절에서는 ModelCallLimitMiddleware로 모델 요청을 1번으로 묶는 호출 한도를 붙였습니다. 호출 한도라는 말은 Ch 16 04절에서 처음 썼습니다.

Ch 6 06절의 예상 비용은 요금표로 어림한 값이고, 청구 금액이 아닙니다. Ch 23 01절에서는 체크포인터에 저장된 상태를 get_state로 읽었습니다. 앞 절에서 처음 가르친 함수 넷은 이 절부터 도구 파일 delegation_tools.py에서 가져옵니다.

4핵심 개념

비유로 시작하기

나란한 물길 두 줄에 같은 모양 짐배가 한 척씩 떠 있습니다. 두 배의 갑판에는 짐을 실을 칸이 똑같이 그려져 있습니다. 위 배는 칸이 모두 찼고, 앞쪽 물길도 열려 있습니다. 아래 배는 칸이 반만 찼는데, 뱃머리 앞을 닫힌 문이 막아 멈춰 있습니다.

갑판의 칸이 필요한 결과이고, 칸이 다 찼는지 보는 것이 완료 조건입니다. 닫힌 문은 실행 한도나 호출 한도처럼 실행을 멈추게 하는 한도입니다. 아래 배는 멈췄지만 짐은 덜 찼습니다. 한도로 멈춘 것과 일이 끝난 것은 다릅니다.

비유와 다른 점이 있습니다. 짐배는 문이 열릴 때까지 기다릴 수 있지만, 한도에 닿은 실행은 그 자리에서 끝납니다. 또 이 절의 완료 조건은 짐의 수가 아니라, 필요한 분야 이름이 담당 답으로 모였는지를 봅니다.

도식 읽기 — 위에서 아래로 읽습니다. 파란 상자 셋은 우리가 적은 세 구조이고, 상자 아래쪽 줄이 01~03절에서 정한 요청 수 셈입니다. 왼쪽 상자가 노트북 3절, 가운데가 4절, 오른쪽이 5절의 구조입니다. 맨 아래 회색 상자는 세 구조가 함께 쓴 전문 에이전트 셋입니다. 이 그림에는 이번 실행의 요청 수를 넣지 않았습니다.

세 구조의 요청 수는 구조가 정하는 셈을 따릅니다

서브에이전트는 중앙 에이전트가 도구로 맡기고 답을 받아, 최종 답을 한 번 더 씁니다. 그래서 중앙 쪽은 도구를 요청한 응답 수 + 1이고, 담당 쪽은 부른 횟수입니다. 핸드오프는 넘긴 담당 1번과 받은 담당 1번이고, 라우터는 분류 1번에 고른 분야 수를 더합니다. 셈은 구조가 정하고, 맡기는 수와 고르는 분야는 모델이 정합니다.

같은 전문 에이전트, 다른 첫 에이전트

세 구조는 03절의 도구 없는 전문 에이전트 셋을 함께 씁니다. 다른 것은 문의를 처음 받는 쪽입니다. 서브에이전트는 중앙 에이전트, 핸드오프는 넘기기만 하는 안내 담당, 라우터는 분류 모델이 처음 받습니다. 세 쪽 모두 같은 담당 설명 글을 받아, 같은 설명을 보고 담당을 고릅니다.

01절은 담당마다 도구 하나를 두었습니다. 이 절의 중앙 에이전트는 담당 이름을 인자로 받는 도구 하나로 셋 가운데 누구에게든 맡깁니다. 공식 Subagents 문서도 담당마다 도구를 두는 모양과, 이름을 받는 도구 하나로 보내는 모양을 함께 적습니다.

서브에이전트의 완료 조건

서브에이전트의 완료 조건은 두 가지입니다. 맡긴 분야마다 전문 에이전트의 답 글이 도구 메시지로 돌아와야 합니다. 그 뒤 중앙 에이전트가 도구 요청 없는 최종 답을 모델 응답으로 써야 합니다. 도구 메시지가 모두 돌아와도 최종 답이 없으면, 중앙 에이전트는 일을 끝내지 못한 것입니다.

핸드오프는 넘겨받은 담당이 이번 차례의 마지막 응답을 쓰고, 필요한 분야가 모두 그 답에 들어야 끝입니다. 라우터는 필요한 분야의 답이 답 칸에 모이고, 종합 칸이 빈 글이 아니어야 끝입니다. 이 절은 이 문장들을 함수 is_complete 하나로 적고, 모인 분야와 마지막 답은 구조마다 따로 셉니다.

5실행 예제

노트북 2절은 03절과 같은 문의 글과 전문 에이전트 셋을 준비합니다. 3~5절은 그 문의를 서브에이전트·핸드오프·라우터에 한 번씩 보내고, 6절은 요청 수와 토큰을 한 표로 모읍니다. 7절은 모델 없는 핑퐁 그래프를 실행 한도 4로, 3절 중앙 에이전트를 호출 한도 1로 실행합니다. 8절은 완료 조건 함수를 네 실행에 대어 봅니다.

실제 OpenAI 모델 gpt-5.4-mini를 temperature 0으로 부르고, 모든 에이전트가 모델 객체 하나를 함께 씁니다. 모델 요청은 노트북 한 번에 11번이고, 4절에서 서비스가 거절한 요청 하나는 이 수에 넣지 않았습니다. 요금표로 어림한 예상 비용은 0.005달러 아래이고, 청구 금액이 아닙니다. 읽거나 쓰는 파일은 없고, 걸린 시간은 재지 않았습니다.

도식 읽기 — 왼쪽 칸이 서브에이전트, 오른쪽 칸이 라우터이고, 칸 안은 위에서 아래로 요청 차례입니다. 보라 상자는 실제로 모델 요청을 보낸 자리이고, 파란 상자는 요청이 없는 종합 노드입니다. 담당 둘의 요청은 한 상자로 묶어 그렸습니다. 노란 상자는 노트북 3절과 5절에서 출력한 모델 요청 수입니다. 두 칸의 맡긴 모양과 고른 분야는 흔들림 확인 다섯 번과 두 커널에서 모두 같았습니다.

6실험 결과 해석

서브에이전트는 이번 실행에서 한 응답에 두 담당을 맡겨, 요청이 중앙 2번과 담당 2번이었습니다. 라우터는 두 분야를 골라 분류 1번과 담당 2번이었습니다. 두 실행 모두 요청 수가 구조의 셈과 맞았고, 필요한 두 분야의 답이 모였습니다. 맡긴 모양과 고른 분야는 흔들림 확인 다섯 번과 두 커널에서 모두 같았습니다.

7주의할 점과 실무 메모

  • 맡기는 모양, 넘기는 수, 고르는 분야는 모델이 정합니다. 노트북 밖에서 세 구조를 다섯 번씩 실행하자 다섯 번 모두 같은 모양이었습니다. 그래도 같은 요청이 실행한 때에 따라 달라질 수 있습니다. 중앙 에이전트가 응답 둘에 나눠 맡기면 요청은 5번, 라우터가 한 분야만 고르면 2번이 됩니다.
  • 핸드오프는 노트북 밖에서 열 번 실행해 열 번 모두 같은 오류로 거절되었습니다. 기록을 읽은 다섯 번은 모두 넘기기 요청이 둘이었습니다. 바깥 그래프에 적용된 넘기기는 대출 규정 담당 셋, 시설 담당 둘로 갈렸고, 그래서 4절의 담당 칸은 결론에 쓰지 않았습니다.
  • 설치판 langchain 1.4.0 agents/factory.py 1964행은 한 응답의 도구 요청마다 도구 실행 노드를 따로 부릅니다. 그래서 넘기기 도구 둘은 저마다 바깥 그래프로 가는 Command를 올려 보냈습니다. langgraph 1.2.11 graph/state.py 1762행이 그 Command를 올려 보내는 자리입니다. 두 작업이 끝나면 같은 판 pregel/_runner.py 650~690행이 그 가운데 하나만 골라 바깥으로 넘깁니다. 어느 쪽이 남는지는 실행마다 달라, 도구 요청 차례가 같아도 담당 칸이 대출 셋·시설 둘로 갈렸습니다.
  • 넘기기 요청을 한 응답에 하나로 묶는 설정이나, 두 분야를 차례로 넘기는 방법은 이 절에서 실행하지 않았습니다. 안내 담당의 시스템 메시지 글에 담당 한 명을 적었지만, 이번 실행에서는 그 글만으로 한 번에 하나를 넘기게 되지 않았습니다.
  • 설치판 langchain 1.4.0 agents/middleware/model_call_limit.py 168~208행은 모델 요청 전에 요청 수를 봅니다. 한도에 닿았으면 한도 글을 담은 응답을 넣고 끝으로 건너뜁니다. 236~250행은 모델 요청 뒤에 수를 늘립니다. 그래서 첫 요청의 도구는 실행되고, 둘째 요청 전에 끝났습니다.
  • 호출 한도는 한도를 붙인 에이전트의 요청만 셉니다. 이번 실행에서 한도는 (1/1)이었지만, 도구 안에서 부른 담당의 요청 2번이 더 나갔습니다. 요금을 묶으려면 담당 에이전트에도 한도를 따로 붙여야 하고, 이 절에서는 실행하지 않았습니다.
  • 분야 이름을 받는 도구에 없는 이름이 오면 KeyError가 납니다. 도구 실행 노드는 이 오류를 받지 않고 올려 보내 실행이 멈춥니다. 이번 실행과 흔들림 확인에서는 모델이 늘 셋 가운데 이름을 골라, 이 경우는 실행하지 않았습니다.
  • 필요한 분야 둘은 문의 글을 보고 실행 전에 정했습니다. 모델이 고른 값이 아니라, 흐름을 보여 주려고 정한 기준입니다. 규정 글은 모두 교재용이고, 실제 도서관 규정이 아닙니다.
  • 토큰 수와 예상 비용은 2026-09-17 과정 요금표로 어림했고, 청구 금액이 아닙니다. 걸린 시간은 재지 않았습니다. 교재 출력은 Linux의 Python 3.12.13으로 만들었고, 다른 판과 Windows·macOS에서는 실행하지 않았습니다.

8정리와 다음 절

  • 서브에이전트의 요청은 중앙(도구를 요청한 응답 수 + 1)과 전문(부른 횟수)의 합이었습니다. 라우터의 요청은 분류 1 + 고른 분야 수였습니다.
  • 핸드오프에서는 흔들림 확인 다섯 번과 두 커널 모두, 안내 담당이 한 응답에 넘기기 요청 둘을 냈습니다. 넘기기 하나만 적용되어 기록이 어긋났고, 받은 담당의 요청이 거절되었습니다. 넘기기가 한 담당에게 오류 없이 갔더라도, 모인 분야가 하나라 완료 조건은 False였을 것입니다.
  • 실행 한도와 호출 한도로 멈춘 실행은 완료 조건을 채우지 못했고, 한도로 끝남과 일이 끝남은 다릅니다.

중앙 에이전트는 도구를 요청한 응답 하나에 최종 답 하나를 더해 2번입니다. 한 응답에서 두 담당에게 맡겨, 담당 쪽은 부른 횟수인 2번입니다. 틀렸다면 노트북 3절을 다시 읽습니다.

2. 핸드오프 실행에서 받은 담당의 모델 요청이 거절된 까닭은 무엇인가요?

안내 담당이 한 응답에 넘기기 요청 둘을 냈지만, 바깥 그래프에는 넘기기 하나와 도구 메시지 하나만 남았습니다. 짝 없는 넘기기 요청이 받은 담당의 요청에 실려, 서비스가 잘못된 요청으로 거절했습니다. 틀렸다면 노트북 4절을 다시 읽습니다.

3. 호출 한도 1을 붙인 실행은 두 담당의 답이 모였는데도 완료 조건이 False였습니다. 왜 그런가요?

마지막 응답이 중앙 에이전트가 쓴 최종 답이 아니라, 호출 한도가 적어 넣은 글이기 때문입니다. 그 응답은 모델 요청으로 받은 것이 아니라 사용량이 None입니다. 틀렸다면 노트북 7절과 8절을 다시 읽습니다.

4. 동료가 「실행이 오류 없이 멈췄으니 일도 끝난 것」이라고 말합니다. 이 절의 결과로는 어떻게 답하나요?

멈춘 까닭과 일이 끝났는지는 따로 봐야 합니다. 호출 한도로 멈춘 실행은 오류 없이 끝났지만 완료 조건은 False였습니다. 필요한 결과가 모였는지를 완료 조건으로 따로 봅니다. 틀렸다면 노트북 8절을 다시 읽습니다.
