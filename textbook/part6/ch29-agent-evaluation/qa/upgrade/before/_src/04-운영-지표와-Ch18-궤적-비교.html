1학습 목표

  • 저장된 Ch18·Ch21 실행 기록을 공통 운영 열로 바꿀 수 있습니다.
  • 모델 호출, 도구 호출, 토큰, 지연을 함께 읽을 수 있습니다.
  • 작은 표본의 nearest-rank p95를 운영 기준으로 확정하지 않을 수 있습니다.

2이 내용을 배우는 이유

개발 평가를 운영의 스텝·도구 호출·비용 p95와 어떻게 연결하는가?

개발 단계의 통과율만 보면 호출 증가와 꼬리 지연을 놓칩니다. Ch18 워크플로우와 Ch21 에이전트의 실제 기록을 같은 열로 바꾸면 최종 품질과 실행 비용을 함께 볼 수 있습니다.

3앞에서 배운 내용

Ch18의 실제 워크플로우 비교 출력을 사용합니다. 필요한 자료와 객체는 노트북에서 다시 선언하므로 앞 노트북의 메모리 상태는 필요하지 않습니다.

4핵심 개념

정의와 구체 예

운영 지표는 실제 대화에서 계속 모으는 측정값입니다. 이 절의 공통 열은 final_score, model_calls, tool_calls, tokens, latency_s입니다. p95는 측정값을 작은 값부터 정렬했을 때 95% 지점의 nearest-rank 값으로, 평균에 숨는 느린 실행을 보는 데 사용합니다.

코드 읽기와 비교 경계

공통 열로 변환한다는 것은 서로 다른 기록에서 이름과 단위를 맞춰 한 표로 읽게 한다는 뜻입니다. Ch18의 quality/5는 0~1로 나누고, Ch21의 agent_supported는 불리언을 0 또는 1로 바꿉니다. 두 값이 모두 final_score 열에 들어가도 원래 평가 기준이 같아지는 것은 아닙니다. trace_source를 함께 남기는 이유는 숫자가 어느 실행과 판정식에서 왔는지 다시 확인하기 위해서입니다.

nearest-rank p95는 값을 정렬한 뒤 ceil(0.95*n)번째 값을 고릅니다. 표본이 세 개면 순위가 3이므로 p95는 항상 최댓값과 같습니다. 이는 계산 오류가 아니지만 꼬리 지연의 안정적인 분포를 추정하기에는 자료가 너무 적습니다. 평균과 p95를 함께 볼 때도 과제, 입력 길이, 실행 횟수, 모델 버전이 다른 집단을 직접 우열 비교하지 않습니다. 같은 서비스의 반복 실행을 일정 기간 모은 뒤 실패율과 사용자 수정 횟수도 함께 해석해야 합니다.

6실험 결과 해석

Ch18 다섯 패턴은 평균 final_score 0.88, 모델 2.8회, 610.2토큰, 4.145초였습니다. Ch21 세 Agentic RAG 행은 평균 final_score 1.0, 모델 2회, 도구 1회, 519.7토큰, 1.880초였습니다. Agent 세 건의 p95는 지연 2.094초, 토큰 541이었습니다. 서로 다른 과제와 표본 수이므로 이 숫자로 시스템 우열을 정하지 않습니다.

Ch18 quality/5와 Ch21 supported는 판정 척도가 다릅니다. 공통 열 변환은 운영 화면을 맞추는 작업이며 직접 성능 대결이 아닙니다. p95도 세 건으로 안정적인 운영 기준을 만들 수 없습니다.

7주의할 점과 실무 메모

  • 이 절은 Ch18과 Ch21의 저장 파일을 읽으며 모델을 다시 호출하지 않습니다. 원본 파일의 기록 시점과 필드 단위를 함께 확인합니다.
  • 표본 세 건의 p95는 nearest-rank 방법에서 최댓값이 됩니다. 이 수치만으로 운영 기준을 정하지 않습니다.

9복습 문제

1. p95를 보는 이유는 무엇인가요?

해설 — 평균에 가려지는 느린 실행과 높은 비용을 보기 위해서입니다.

2. Ch18과 Ch21의 final_score를 바로 비교할 수 없는 이유는 무엇인가요?

해설 — 평가 과제와 척도가 다르기 때문입니다.

3. 이번 Agent 기록의 지연 p95는 얼마였나요?

해설 — 2.094초였습니다.
