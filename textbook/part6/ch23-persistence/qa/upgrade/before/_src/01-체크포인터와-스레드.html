1학습 목표

  • 체크포인터와 thread_id가 각각 맡는 역할을 설명할 수 있습니다.
  • 같은 thread_id의 누적 결과와 다른 thread_id의 격리 결과를 읽을 수 있습니다.
  • 메모리 체크포인터를 운영 재개 저장소로 쓰기 어려운 이유를 설명할 수 있습니다.

2이 내용을 배우는 이유

에이전트가 여러 차례 호출되는 동안 같은 사용자의 상태를 이어 가고 다른 사용자의 상태는 섞지 않아야 합니다.

이 절에서는 customer-a가 3 뒤에 4를 더해 7이 되는지, customer-b의 4가 독립적으로 시작하는지를 같은 그래프에서 확인합니다. 저장 시점과 외부 부작용의 중복 문제는 뒤 절에서 다룹니다.

3앞에서 배운 내용

Ch13의 StateGraph는 한 번의 invoke 안에서 State를 노드 사이에 전달했습니다. Ch20의 도구 반복도 같은 실행 안에서 메시지를 누적했습니다. 이번 절에서는 실행이 끝난 뒤에도 값을 찾을 수 있도록 compile(checkpointer=memory)를 사용하고, config의 configurable.thread_id가 어느 기록을 읽을지 지정합니다.

4핵심 개념

구체적인 상황

상담 시스템에서 customer-a가 앞서 입력한 3에 이어 4를 보내면 합계는 7이어야 합니다. 같은 시각 customer-b가 4를 보내도 customer-a의 3이 섞이면 안 됩니다. 체크포인트는 계산 결과를 남기고 스레드는 두 고객의 기록 경계를 만듭니다.

정의

체크포인터(checkpointer)는 그래프 단계가 끝날 때 상태 스냅샷을 저장합니다. 스레드(thread)는 관련 체크포인트를 묶는 논리적 실행 단위이며 thread_id가 그 묶음을 찾는 키가 됩니다.

StateSnapshot의 values는 그 시점의 채널 값이고 next는 다음에 실행할 노드 이름입니다. 실행을 마친 스냅샷에서 next가 빈 튜플이면 이어서 실행할 노드가 없다는 뜻입니다. get_state_history()는 입력, 노드 실행, 종료 뒤에 만들어진 스냅샷을 최신순으로 반환합니다.

코드를 읽는 순서

체크포인터(checkpointer)는 그래프의 단계별 상태 스냅샷을 저장하고, 스레드(thread)는 관련 체크포인트를 묶는 식별자입니다. builder.compile(checkpointer=memory)에서 저장 기능을 그래프에 연결하지만 이때 상태가 생기지는 않습니다. invoke(..., {"configurable": {"thread_id": ...}})가 실행될 때 해당 스레드에 체크포인트가 기록됩니다.

InMemorySaver는 현재 Python 프로세스의 메모리에만 저장합니다. get_state(config)는 선택한 스레드의 최신 StateSnapshot을, get_state_history(config)는 단계별 기록을 최신순으로 반환합니다. 상태의 events가 누적되는 방식은 상태 스키마와 노드가 반환하는 값에 달려 있으며, 체크포인터가 모든 리스트를 자동으로 합치는 것은 아닙니다.

5실행 예제

첫 셀은 total과 events를 가진 State와 add 노드를 정의하고 InMemorySaver를 붙입니다. customer-a 설정으로 3을 실행한 뒤 같은 설정에 4를 입력합니다. 마지막 셀은 입력 4를 유지한 채 thread_id만 customer-b로 바꾸어 누적값과 기록 수를 비교합니다.

확인할 점 — 같은 thread_id의 두 실행은 total 7로 이어졌고 다른 thread_id는 total 4에서 독립적으로 시작했습니다.

다른 상황과 적용 경계

같은 고객의 이어지는 대화에는 같은 thread_id를 사용하고, 독립된 상담이나 테스트에는 새 ID를 사용합니다. 사용자 ID를 그대로 스레드 ID로 쓰면 동시에 열린 두 상담이 섞일 수 있으므로 대화 단위를 구분하는 식별자가 필요합니다.

체크포인터는 그래프 상태를 저장하고 Store는 여러 스레드가 공유할 사용자 선호 같은 데이터를 저장합니다. 이번 customer-a와 customer-b 비교는 스레드 격리를 보여 주며, 프로세스 종료 뒤 복구는 증명하지 않습니다. 그 경계는 파일 또는 데이터베이스 기반 저장기를 사용하는 다음 절에서 다룹니다.

6실험 결과 해석

customer-a의 첫 결과는 3, 두 번째 결과는 7이며 저장된 최신 values의 total도 7입니다. customer-b는 4에서 시작합니다. 기록 수가 각각 6과 3인 것은 customer-a가 두 번, customer-b가 한 번 실행됐기 때문입니다. 기록 수 자체를 대화 턴 수로 해석하지 않습니다.

같은 thread_id의 두 실행은 total 7로 이어졌고 다른 thread_id는 total 4에서 독립적으로 시작했습니다.

7주의할 점과 실무 메모

  • InMemorySaver의 내용은 Python 프로세스가 끝나면 사라집니다.
  • thread_id를 사용자 입력에서 그대로 받기보다 인증된 사용자와 대화 식별자에서 서버가 생성합니다.
  • 체크포인트 상태에는 비밀 키와 불필요한 개인정보를 넣지 않습니다.

8정리와 다음 절

  • 같은 thread_id는 최신 체크포인트의 total을 이어 받아 7을 만들었습니다.
  • 다른 thread_id는 customer-a의 값을 읽지 않아 total 4에서 시작했습니다.
  • InMemorySaver는 프로세스 종료 뒤 상태가 남지 않으므로 다음 절의 PostgreSQL 저장소와 용도가 다릅니다.

다음 학습과 이어지는 지점 — 다음 절에서는 메모리 대신 PostgreSQL에 체크포인트 표를 만듭니다.

9복습 문제

1. customer-a의 두 번째 total이 7인 이유는 무엇인가요?

해설 — 같은 thread_id의 최신 체크포인트 total 3을 읽고 새 입력 4를 더했기 때문입니다.

2. customer-b의 total이 4인 결과가 보여 주는 것은 무엇인가요?

해설 — 다른 thread_id는 customer-a의 저장 상태를 읽지 않는다는 것을 보여 줍니다.

3. StateSnapshot.next가 빈 튜플이라는 뜻은 무엇인가요?

해설 — 현재 실행에서 이어서 실행할 노드가 없다는 뜻입니다.

4. InMemorySaver를 운영 재개 저장소로 쓰기 어려운 이유는 무엇인가요?

해설 — 프로세스가 종료되면 메모리의 체크포인트도 사라지기 때문입니다.
