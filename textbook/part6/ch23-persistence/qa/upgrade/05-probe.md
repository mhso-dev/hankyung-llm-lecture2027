# Ch 23 05절 흔들림 확인 기록 — 남은 쓰기와 이어 가기

- 작업 2026-09-25 · 규격 `QUALITY-UPGRADE.md` §2-7 9번 끝·10번 끝, 인계 `handoff.md` 「§04 → §05」 2항에 따른 **노트북 밖 확인 실행**(모델 요청 0).
- 까닭: 05절의 핵심 관찰(「같은 단계의 두 노드 가운데 `flaky`만 실패하면, 성공한 `good`의 쓰기가 체크포인트에 남고, 원인을 없앤 뒤 `invoke(None, config)`로 이어 가면 `good`은 다시 실행되지 않는다」)은 두 노드가 함께 실행되는 차례에 기댈 수 있습니다. 설치판 소스 `langgraph/pregel/_runner.py`(`tick` — 한 작업이 실패하면 `_should_stop_others`로 기다림을 멈추고 `_panic_or_proceed`로 오류를 올림)를 보면, 실패를 본 뒤 아직 끝나지 않은 노드의 쓰기는 기다리지 않습니다. 그래서 두 노드가 끝나는 차례에 따라 `good`의 쓰기가 남지 않을 틈이 있는지 **노트북을 쓰기 전에** 확인합니다.

## 1. 규칙 (실행 전에 적음)

1. **무엇을 보나** — 노트북과 같은 모양의 그래프(상태 형식 칸 `results` 하나에 `operator.add`, 가상 시작점에서 엣지 둘로 `good`·`flaky`, 두 노드에서 가상 끝점으로)를 회마다 새 SQLite 파일·새 `SqliteSaver`로 컴파일합니다. 노드 `good`은 부른 횟수를 세고 `['good-result']`를 냅니다. 노드 `flaky`는 부른 횟수를 세고, 실패 스위치가 켜져 있으면 `TimeoutError`를 냅니다. 회마다 ① 받은 오류 종류 ② 실패 뒤 부른 횟수 ③ `get_state`의 칸 값·`next` ④ `tasks`의 차례·이름·오류 종류·`result` ⑤ 마지막 체크포인트에 딸린 표 `writes` 줄의 칸 `channel`(이름 차례) ⑥ 체크포인트 수를 적고, 스위치를 끈 뒤 `invoke(None, config)`로 이어 가 ⑦ 결과 목록(정렬 전·정렬 뒤) ⑧ 부른 횟수 ⑨ `next` ⑩ 체크포인트 수를 적습니다. 흔들림을 보려고 두 노드가 **시작한 차례**도 적습니다(결론에는 쓰지 않음).
2. **판** — A1: `flaky`가 바로 실패 · A2: `flaky`가 0.1초 쉰 뒤 실패(시간 초과 흉내) · B: `good`이 0.3초 쉬고 `flaky`는 바로 실패(경계 확인용, 노트북에 넣지 않음). 저장 시점은 기본값(인자 없음 = `async`)·`exit`·`sync` 셋.
3. **몇 번** — A1·A2는 저장 시점마다 100번(판마다 따로 Python 프로세스 하나), B는 저장 시점마다 10번. 수는 결과를 보기 전에 정한 이 값 그대로이고, 더 돌려 고르지 않습니다.
4. **노트북 장면은 실행 전에 A2로 정합니다.** 소스상 실패를 본 뒤 끝나지 않은 노드를 기다리지 않으므로, 실패 흉내가 `good`보다 늦게 나게 해 두면 학생 컴퓨터에서도 같은 관찰이 나올 가능성이 큽니다. 0.1초 쉬는 것은 시간 초과 흉내로 설명합니다. A1은 참고입니다.
5. **판정** — ②·③·④(차례 뺌)·⑤·⑥·⑦(정렬 뒤)·⑧·⑨·⑩이 A2의 한 저장 시점 100번에서 모두 같으면 그 값을 결론·그림 라벨·정리·복습에 씁니다. 한 번이라도 다르면 그 값은 결론에 쓰지 않고 장면을 다시 설계합니다. 시작 차례·`tasks` 차례·정렬 전 결과 목록은 몇 번이 나오든 적기만 하고, 다르면 노트북에 출력하지 않거나 결과 읽기 둘째 단락·b7에만 둡니다. A1에서 `good`의 쓰기가 빠진 회가 있으면 그 수를 b7(「노트북 밖 확인에서는」)과 진단에 적습니다. B는 소스로 읽은 경계가 실제로 보이는지 확인하는 용도이고, 결과가 섞이면 섞인 대로 적습니다.
6. **환경** — 가상환경 `.cache/vm/venv-ch23-persistence`, `env -u OPENAI_API_KEY`, 파일은 기기 `/tmp/ch23-05/probe-*`에만. 걸린 시간은 결론에 쓰지 않습니다.

### 1-2. 더한 규칙 (B 결과를 본 뒤, C를 실행하기 전에 적음)

- B(`good` 0.3초 · `flaky` 바로 실패)에서도 `good`의 쓰기가 30/30 남았습니다. 까닭을 찾으려고 한 번 계측한 결과(기기 `/tmp/ch23-05/why2.py` — 실패 뒤 0.15초에 주 실행 흐름의 호출 차례를 찍음), 그래프는 `langgraph/pregel/_runner.py` 337행 `futures.event.wait`에서 `good`이 끝나기를 기다렸습니다. 같은 파일 104~114행에서 작업을 새로 등록하면 기다림 표시(`event`)를 지우므로, `flaky`가 `good`의 등록보다 먼저 실패하면 기다림이 다시 걸리는 것으로 읽힙니다(소스 읽기 — 차례에 기대는 동작).
- **C 판을 더합니다**: `good`이 0.3초 쉬고, `flaky`는 0.1초 쉰 뒤 실패(두 노드가 모두 등록된 뒤 `flaky`가 먼저 실패). 저장 시점마다 10번. 소스 읽기대로라면 실패를 본 그래프는 `good`을 기다리지 않고 나가므로 `good`의 쓰기가 남지 않아, 이어 갈 때 `good`을 다시 실행할 것(`good` 2)이라고 예상합니다. 결과는 나온 그대로 적고, 노트북에는 넣지 않으며 b7 한 줄(「노트북 밖 확인에서는」)과 진단에만 씁니다.

### 1-3. 더한 규칙 (노트북 설계를 정한 뒤, D를 실행하기 전에 적음)

- 노트북은 원인을 없앤 뒤 한 번만 이어 갑니다. 본문 b7에 「원인을 없애지 않고 이어 가면 같은 실패로 다시 멈춘다」를 쓰려고, **D 판**을 노트북 밖에서 실행합니다: A2 모양으로 실패시킨 뒤, 실패 스위치를 켠 채 `invoke(None, config)` → 받은 오류·부른 횟수·`next`를 적고, 스위치를 끈 뒤 다시 `invoke(None, config)` → 부른 횟수·정렬한 결과. 저장 시점마다 20번. 결과는 b7 한 줄(「노트북 밖 확인에서는」)과 진단에만 씁니다.
