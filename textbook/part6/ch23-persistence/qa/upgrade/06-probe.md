- 까닭: 06절의 핵심 관찰(「결제 기록을 적는 둘째 노드 `charge` 안에서 자식 프로세스를 강제로 끝낸 뒤 새 프로세스로 다시 실행하면, `charge`가 처음부터 다시 실행되어 검사 없이 적는 쓰기 방식 `naive`는 같은 키를 두 줄, 이미 적힌 키를 건너뛰는 `idempotent`는 한 줄 남긴다」)은 자식 프로세스와 강제 종료 시점에 기댑니다. 준비 조사(옛 worker 20번, 준비 노트 §7-4)에서는 두 방식이 10/10씩 같았습니다. 06절은 worker를 04절 인자 모양으로 새로 쓰고(인자 다섯·`first-run`/`resume`·노드 둘·저장 시점 `sync`) 04절 함수를 도구 파일에서 가져와 쓰므로, **고친 worker와 도구 파일 사본으로 노트북을 쓰기 전에 다시 확인합니다.**

## 1. 규칙 (실행 전에 적음)

1. **판 A — 무엇을 보나(노트북과 같은 장면)**: 고친 worker(`author_06.py`의 `WORKER` 글과 같은 사본)와 도구 파일 사본(`author_06.py`의 `TOOLS` 글 — 04절 함수 여섯은 `author_04.DEF_*`와 글자가 같음)을 기기 `/tmp/ch23-06/probe/`에 두고, 쓰기 방식(`naive`·`idempotent`)마다 회마다 새 임시 폴더에서 ① `kill_at_second(worker, builder, 앞머리, 방식)`로 띄워 둘째 노드에서 끊은 뒤 남은 칸 값·다음 노드·체크포인트 수 ② 끊긴 직후 결제 기록 파일의 키 목록 ③ `start_worker(…, "resume")`의 종료 코드(`wait(timeout=30)`) ④ 다시 실행한 뒤 칸 값·체크포인트 수 ⑤ 결제 기록 파일의 키 목록을 적습니다. 설계 객체는 노트북과 같은 상태 형식·노드 이름·엣지(읽기용).
2. **판 B — 참고(노트북에 넣지 않음, b7 한 줄)**: 같은 모양의 그래프를 한 프로세스 안에서 SQLite 체크포인터·저장 시점 `sync`로 실행하고, 노드 `charge`가 결제 기록을 적은 뒤 실패 흉내(`TimeoutError("이 절에서 만든 실패 흉내입니다.")`)를 내게 합니다. 실패 뒤 다음 노드·체크포인트 수·키 목록을 적고, 실패 흉내를 끈 뒤 `invoke(None, config)`로 이어 가 칸 값·키 목록을 적습니다(05절 모양).
3. **몇 번** — 판 A 쓰기 방식마다 **20번**(합 40번, 자식 프로세스 80번) · 판 B 쓰기 방식마다 **10번**. 수는 결과를 보기 전에 정한 이 값 그대로이고, 더 돌려 고르지 않습니다.
4. **판정** — 판 A의 ①~⑤가 한 쓰기 방식 안에서 한 번이라도 다르면 그 값은 결론에 쓰지 않고 장면을 다시 설계합니다. 모두 같으면 결론·그림 라벨·정리·복습에 씁니다. 판 B는 결과가 섞이면 섞인 대로 적고, 본문에는 b7 「노트북 밖 확인에서는」 한 줄로만 둡니다.
5. **노트북 되풀이 수** — 노트북 6절 되풀이는 쓰기 방식마다 **다섯 번**으로 이 확인 전에 정했습니다(04절 6절과 같은 수). 이 확인 결과를 보고 바꾸지 않습니다.
6. **환경** — 가상환경 `.cache/vm/venv-ch23-persistence`, `env -u OPENAI_API_KEY`, 파일은 기기 `/tmp/ch23-06/probe-*`에만(판 A는 회마다 새 폴더). 묶음마다 끝에 `ps -eo pid,args | awk '$2 ~ /python/ && /idempotency_worker/'`로 남은 자식 프로세스가 없는지 봅니다(`pgrep -f`는 셸 명령 자체가 걸려 거짓 양성 — 04절). 걸린 시간은 결론에 쓰지 않습니다.
