# Ch 23 04절 흔들림 확인 기록 — 저장 시점(durability)과 강제 종료

- 작업 2026-09-25 · 규격 `QUALITY-UPGRADE.md` §2-7 9번 끝·10번 끝, 인계 `handoff.md` 「챕터 공통」 결정 4·`§03 → §04` 4·5항에 따른 **노트북 밖 확인 실행**(모델 요청 0).
- 까닭: 04절의 핵심 관찰(「둘째 노드에서 강제로 끝내면 `exit`는 아무것도 남기지 않고 `sync`는 첫째 노드 결과를 남긴다」)은 자식 프로세스와 강제 종료 시점에 기댑니다. 준비 조사(옛 worker 60번, 준비 노트 §7-1)에서 `exit`·`sync`는 20/20씩 같았고 `async`만 60번 중 4번 첫째 노드 결과를 잃었습니다. 04절은 worker 스크립트를 새로 고쳐 쓰므로(인자·다시 실행 단계·기록 파일), **고친 worker로 같은 확인을 노트북을 쓰기 전에 다시 합니다.**

## 1. 규칙 (실행 전에 적음)

1. **무엇을 보나** — 고친 worker(`labs/part6/ch23-persistence/durability_worker.py`에 넣을 판과 글자가 같은 사본)를 모드마다 `first-run` 단계로 띄우고, 신호 파일이 생기면 `kill()` → `wait(timeout=5)`. 새 연결로 SQLite 파일을 읽어 ① 종료 코드 ② 남은 칸 값 ③ 다음 노드 ④ 체크포인트 수를 적고, 같은 파일로 `resume` 단계를 끝까지 실행한 뒤 ⑤ 체크포인트 수 ⑥ 기록 파일의 노드 이름 차례를 적습니다. 따로, 한 프로세스 안에서 두 노드 그래프를 모드마다 끝까지 실행했을 때의 체크포인트 수(노트북 2절 장면)도 셉니다.
2. **몇 번** — 강제 종료 장면 `exit` 20 · `sync` 20 · `async` 40(준비 조사 60번과 합쳐 볼 수 있게). 끝까지 실행하는 장면은 모드마다 20. 되풀이 수는 결과를 보기 전에 정한 이 값 그대로이고, 더 돌려 고르지 않습니다.
3. **판정** — `exit`·`sync`가 한 번이라도 다른 값을 내면 그 값은 결론에 쓰지 않고 장면을 다시 설계합니다. 모두 같으면 결론·그림 라벨·정리·복습에 씁니다. `async`는 몇 번이 나오든 그대로 적고, 노트북 결과 읽기 둘째 단락·본문 b6 둘째 단락·b7에만 「이번 실행에서는」·「준비 확인에서는」으로 둡니다.
4. **노트북 되풀이 수** — 노트북의 되풀이 장면은 모드마다 **다섯 번**으로 이 확인 전에 정했습니다(모드마다 약 0.6초 × 5, 셀 하나가 약 10초 — 준비 조사의 모드당 약 1.1초에서 다시 실행을 뺀 값으로 어림). 이 확인 결과를 보고 바꾸지 않습니다.
5. **환경** — 가상환경 `.cache/vm/venv-ch23-persistence`, `env -u OPENAI_API_KEY`, 파일은 기기 `/tmp/ch23-04/probe-*`에만. 묶음마다 끝에 `pgrep -f durability_worker`로 남은 자식 프로세스가 없는지 봅니다. 걸린 시간은 결론에 쓰지 않습니다(참고로만 적음).
