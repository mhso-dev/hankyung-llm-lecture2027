## 0. 실행 전에 적은 입력과 판단 규칙 (2026-09-25T05:36Z, 첫 요청 전에 적음)

### 0-1. 모델 없이 먼저 본 것 (요청 0, 가짜 키 글자 — 기기 `/tmp/ch21-07/nomodel_check.py`)

- 조립한 그래프 종류 `CompiledStateGraph` · 노드 `['model', 'tools']` · 조건 함수 `tools | tools_to_model | ['model', '__end__']` · `model | model_to_tools | ['tools', '__end__', 'model']`(02절 도구 전략 그래프와 같음) · 상태 칸 `['messages', 'jump_to', 'structured_response']`(실행 정보 형식은 상태 칸이 아님 — 03절과 같음).
- 도구 명세의 인자: `lookup_policy` `['topic']` · `check_my_loan` `[]`(03절과 같음).
- 양식 클래스 `LoanAnswer`의 꼭 채울 칸 `['can_borrow', 'answer']` · `can_borrow` 고를 수 있는 값 `['가능', '불가']`.
- 설치판 소스(`langchain/agents/factory.py`): 도구 전략이면 요청마다 `tool_choice="any"`(1423행) · 양식 도구 요청은 모델 노드가 검사해 `structured_response`와 도구 메시지를 만듦(1224~1290행) · 양식 도구 요청과 다른 도구 요청이 한 응답에 함께 오면 다른 도구만 도구 실행 노드로 가고, 도구 실행 뒤 `tools_to_model`이 끝으로 감(1953~1966·2027~2029행) → 이때는 양식 값이 **도구 결과를 보기 전에** 채워짐. 이 경우가 나오는지를 아래에서 봄.

### 0-2. 흔들림 확인 입력 (노트북과 같은 코드, 결과를 보고 바꾸지 않음)

- 모델 `init_chat_model("openai:gpt-5.4-mini", temperature=0, reasoning_effort="none")` 객체(01~06과 같음).
- 자료 `POLICIES`·도구 `lookup_policy` — **01절 셀 그대로**. 실행 정보 형식 `MemberContext`·도구 `check_my_loan(runtime: ToolRuntime[MemberContext])` — **03절 셀 그대로**.
- 양식 클래스(02절 `PolicyAnswer`와 같은 모양, 칸만 바꿈 — 02절 판은 주제어 칸뿐이라 이번 문의의 결과인 새 대출 가능 여부를 담을 칸이 없음):
  ```python
  class LoanAnswer(BaseModel):
      can_borrow: Literal["가능", "불가"] = Field(description="check_my_loan 도구 결과로 본, 지금 새 책을 빌릴 수 있는지")
      answer: str = Field(description="두 도구 결과에 근거한 한두 문장 답")
  ```
- 시스템 메시지 글(**01절 글 + 03절 글의 둘째 문장**): 「교육센터 자료실 안내 도우미입니다. 자료실 규정을 묻는 질문에는 lookup_policy 도구로 찾은 규정 글에 근거해 답하세요. 이용자가 지금 새 책을 빌릴 수 있는지 물으면 check_my_loan 도구로 확인한 결과에 근거해 답하세요.」
- 에이전트: `create_agent(model, tools=[lookup_policy, check_my_loan], system_prompt=system_text, response_format=ToolStrategy(LoanAnswer), context_schema=MemberContext)`.
- 문의(이 절에서 새로 정한 글, 두 도구가 모두 있어야 답할 수 있게): 「제가 지금 새 책을 빌릴 수 있는지 확인해 주세요. 일반 도서 대출 규정도 함께 알려 주세요.」 · 입력 상태 `{"messages": [HumanMessage(content=문의)]}`.
- 설정 둘(바꾼 값은 실행 정보의 `overdue_days` 하나 — **03절 7·8절 값 그대로**):
  - **R0** `context={"member_id": "M-0317", "overdue_days": 0}`(노트북 실행 1)
  - **R3** `context={"member_id": "M-0317", "overdue_days": 3}`(노트북 실행 2)

회차마다 기록: 결과 딕셔너리 키 · 메시지 종류 차례 · 응답마다 도구 호출 요청 이름과 인자 · 도구 메시지 이름·결과 상태·내용 · 요청 id 목록 == 호출 ID 목록 · 응답 수 · `structured_response` 종류와 칸 값 · 응답마다 사용량(입력·출력·캐시 입력) · 모델 이름 · 오류.

### 0-3. 판단 규칙

- **후보 A**(위 입력)가 아래 넷을 **두 설정 다섯 번씩 모두** 채우면 A를 노트북 입력으로 씀.
  1. 오류 없이 `structured_response`가 있고 종류가 `LoanAnswer`.
  2. `check_my_loan`과 `lookup_policy`를 **둘 다** 부름(01절 도구와 03절 실행 정보가 흐름 안에서 쓰임).
  3. 양식 도구 `LoanAnswer` 요청이 두 도구 요청과 **같은 응답에 오지 않음**(양식 값이 도구 결과 뒤에 채워짐 — 02절 구조화 출력이 흐름 안에서 쓰임).
  4. 모델 요청 수가 두 설정의 최댓값을 더해 **5 이하**(실습 절 3~5번).
- A가 하나라도 못 채우면 **후보 B** — 입력은 A와 같고 시스템 메시지 글 끝에 한 문장 「두 도구가 모두 필요하면 한 번에 함께 부르고, 도구 결과를 받은 뒤에 LoanAnswer로 답을 정리하세요.」만 더함. 같은 규칙으로 다섯 번씩 봄. B도 못 채우면 A 입력으로 노트북을 쓰되, 못 채운 항목과 요청 수를 준비물 범위·b7·진단·강사 확인 대상에 올림(더 고르지 않음).
- 규칙을 채운 후보 안에서: 메시지 종류와 수·응답마다 요청 이름·응답 수·도구 메시지 수·호출 ID 짝이 **5번 모두 같으면** 결론·그림에 씀. 다른 회차가 있으면 그 값은 결과 읽기 둘째 단락·b7에 회차 수와 함께만.
- `can_borrow`(모델이 채우는 칸)가 R0 「가능」·R3 「불가」로 **5번 모두 같으면** 결론 가까이에 「모델이 채운 칸이지만 다섯 번·새 커널 두 번 같았다」는 조건과 함께 둘 수 있음. 아니면 둘째 단락에만. `answer` 칸 글·마지막 응답 글·출력 토큰·예상 비용은 결론에 쓰지 않음(둘째 단락·b7).
- 입력 토큰(응답마다)이 5번 모두 같으면 첫 단락 가까이에 둘 수 있음.
- 결과를 보고 문의 글·시스템 메시지 글(후보 B의 한 문장 밖)·도구 글·양식 칸·실행 정보 값을 바꾸지 않음.
