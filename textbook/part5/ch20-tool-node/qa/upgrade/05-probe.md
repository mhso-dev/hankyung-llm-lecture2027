# 05절(실습) 흔들림 확인 (노트북 밖, 2026-09-24)

규격 §7-2 6항·§2-7 10번 끝 · 챕터 리드 결정 6 · 인계 「§04 → 실습(05)」 5·6항. 이 절은 모델이 도구를 몇 번, 어떤 주제어로 부르는지가 실행 흔적·노드 실행 수·모델 요청 수를 정하고, 실행 2의 실행 한도도 실행 1에서 센 노드 실행 수로 정합니다. 그래서 노트북을 실행하기 **전에** 같은 흐름을 노트북 밖에서 **5번** 보냅니다. 키는 루트 `.env`에서만 읽고 출력하지 않습니다. 걸린 시간은 재지 않습니다.

## 0. 실행 전에 적은 입력과 판단 규칙 (2026-09-24, 첫 요청 전)

공통(노트북과 같은 코드):

- 모델 `init_chat_model("openai:gpt-5.4-mini", temperature=0, reasoning_effort="none")`(과정 표준) · 시스템 메시지 없음 · `bound_model = model.bind_tools([lookup_policy], parallel_tool_calls=False)`(01절 셀과 같은 값) · 첫 상태 `{"messages": [HumanMessage(content=문의)], "trace": []}`.
- 자료 `POLICIES` 셋과 도구 `@tool lookup_policy(topic: str)`은 01·03절 셀과 같은 코드(독스트링 「교육센터 자료실 규정 하나를 주제어로 찾습니다. topic에는 대출, 운영, 연체 가운데 하나를 넣습니다.」, 없는 주제면 `raise ValueError("지원하지 않는 주제: " + topic)`).
- 오류 처리 함수는 02절 셀 그대로: `def handle_policy_error(error: ValueError):` → `"규정을 찾지 못했습니다(" + str(error) + "). 이 도구로 찾을 수 있는 주제어는 대출, 운영, 연체입니다."`
- 그래프는 01절 모양 그대로(상태 형식 `AgentState` · 모델 노드 `call_model` · `START → "model"` · `add_conditional_edges("model", tools_condition, {"tools": "tools", END: END})` · 되돌아가는 엣지 `tools → model`)이고, 도구 실행 노드만 02절 After처럼 `ToolNode(tools, handle_tool_errors=handle_policy_error)`.
- **실행 1**: `graph.invoke(첫 상태, {"recursion_limit": 10})`(03절 `limit_config`와 같은 값).
- **노드 실행 수** = 실행 흔적 칸의 `model` 수 + 도구 메시지 수(01절에서 본 것처럼 도구 실행 노드는 흔적 칸을 쓰지 않고, 요청을 하나씩만 받게 해 도구 실행 노드 한 번 = 도구 메시지 하나).
- **실행 2**: 같은 첫 상태로 `graph.invoke(첫 상태, {"recursion_limit": 실행 1의 노드 실행 수})` — 바꾸는 값은 실행 한도 하나. 03절 규칙(노드 K번 실행 흐름은 한도 K+1부터 통과)대로면 `GraphRecursionError`가 날 것. 받은 오류 이름·오류 글을 기록.
- 노트북 밖 확인에서만: 모델 노드 함수 안에 부른 횟수와 응답(도구 호출 요청·사용량)을 적는 목록을 두어, **실행 2처럼 결과를 받지 못한 실행에서도 모델 요청 수를 셉니다**(노트북 셀에는 이 목록이 없음).

입력 후보(문의 글, 차례대로 — 앞 후보가 아래 조건을 모두 채우면 뒤 후보는 보내지 않음):

- **A** 「자료실 주차 규정을 알려 주세요.」 — 02절 5절의 주차 질문 그대로. 02절은 이 질문에 손으로 만든 요청을 붙였고, 이번에는 모델이 스스로 요청을 적는지 봅니다.
- **B** 「주제어 주차로 자료실 규정을 찾아 주세요.」 — A에서 모델이 도구를 부르지 않거나 회차마다 달라질 때만 보냄(주제어를 글에 적은 문의, 이 절이 정함).
- **C(마지막 대안)** 「자료실에서 일반 도서를 며칠 빌릴 수 있나요?」 — 01절 대출 질문 그대로. A·B 모두 조건을 채우지 못하면 이 문의로 바꾸고, 오류 처리 함수는 켜 두기만 한 설계가 된다는 사실을 본문 b3·b7과 진단에 적습니다. C의 조건은 아래에서 「주차」를 「대출」로, 결과 상태 `error`를 `success`로 읽습니다.

회차마다 기록하는 표지: 후보 · 실행 1의 실행 흔적 칸 · 메시지 종류 차례 · 응답마다 도구 호출 요청의 이름과 인자 · 도구 메시지마다 결과 상태와 내용 · 요청 `id` 목록 == 도구 메시지 호출 ID 목록 · 마지막 응답의 도구 호출 요청 수 · 노드 실행 수 · 모델 응답마다 입력·출력 토큰(캐시 입력 포함) · 응답 모델 이름 · 답 글(기록만) · 실행 2의 한도·받은 오류 이름·오류 글 첫 줄·모델 노드를 지난 수(부른 횟수 목록) · 오류.

판단 규칙(후보를 채택하는 조건 — 다섯 번 **모두**):

1. 실행 1 흔적 `['model', 'model']` · 메시지 종류 Human·AI·Tool·AI · 첫 응답의 도구 호출 요청 하나 `lookup_policy {'topic': '주차'}` · 도구 메시지 결과 상태 `error`이고 내용이 오류 처리 함수의 글 · 호출 ID 짝 `True` · 마지막 응답의 도구 호출 요청 0건 · 노드 실행 수 3.
2. 실행 2(한도 3) `GraphRecursionError`, 모델 노드를 지난 수 2.
3. 오류 없음(서비스 오류가 나면 그 회차를 다시 보내지 않고 기록한 뒤 조건을 채우지 못한 것으로 봄).

- 조건을 채운 후보를 노트북 문의로 그대로 쓰고, 새 커널 두 번에서도 같을 때만 1·2의 값을 결론·그림·정리에 씁니다. 실행 2의 모델 요청 수는 노트북에서 셀 수 없으므로 「노트북 밖 다섯 번에서 센 값」으로만 적습니다.
- 입력 토큰(요청마다)이 다섯 번 모두 같으면 그 값을 결론에 쓸 수 있습니다. 출력 토큰·답 글·출력 몫이 든 예상 비용은 결론에 쓰지 않고 결과 읽기 둘째 단락·「확인할 점」·b7에만 「이번 실행에서는」으로 둡니다.
- 후보는 위 셋뿐입니다. 결과를 보고 다른 글·다른 한도·다른 오류 처리 함수로 바꾸지 않습니다. 한 후보를 다섯 번보다 많이 보내지 않습니다.
- 모델 답·모델이 고른 값에는 노트북에서 `assert`를 걸지 않습니다.
