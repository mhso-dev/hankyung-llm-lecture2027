## 3. 설계 — experiment

**학습 질문**: 서로 기다릴 필요가 없는 모델 요청 여러 개를 함께 보내면 결과는 어떤 차례로 모이고, 걸린 시간은 어떻게 달라질까요? 같은 글을 기준이 다른 평가자 여럿에게 보내면 표를 어떻게 세어 결과를 정할까요?

- **함께 보내는 수단(챕터 리드 결정 2)**: 01 `ask_json`을 고치지 않고 `asyncio.to_thread(ask_json, client, records, 단계, 지시 글, 요청 글)`로 감쌈. 5절은 Ch 2 12 After처럼 **코루틴 변수 셋을 `gather()` 괄호에 직접**(3절 「코루틴 만들기만 — `coroutine`·`쌓인 기록 줄 수: 0`」을 먼저 보임), 6절 함수 `ask_all_together`에서 처음 `gather(*waitings)` + 별표 두 문장. `AsyncOpenAI` 0.
- **걸린 시간(이 절의 주제)**: 4절 하나씩 세 번(01·02처럼 `ask_json` 차례로) ↔ 5절 함께 세 번을 **같은 요청 글**로 각각 `time.perf_counter()` 앞뒤(Ch 2 12 5·6절 모양 — 차례로 기다리기 vs gather). 옛 「개별 지연 합」은 쓰지 않음. 결과 읽기 첫 단락은 `요청 수(기록 줄 수): 3 3`·`함께 기다린 쪽이 짧은가: True`(두 번 + 밖 다섯 번 같음)만, 초 값은 둘째 단락 「교재 출력에서는」·「확인할 점」에만. 결론·그림·정리에는 「두 번 모두 함께 기다린 쪽이 짧았다」만(몇 배인지 없음).
- **기록 줄 차례(인계 결정 2의 주의)**: 5절에서 기록 목록 **하나를 세 스레드가 함께** 쓰게 두고, `받은 답의 칸 「부분」 차례`(gather 목록 = 넣은 차례)와 `print_records`(도착 차례)를 한 셀에 나란히. 첫 단락은 「기록 줄은 응답을 받은 때에 더해져 도착 차례로 쌓인다」(코드 구조), 실제 차례는 둘째 단락(A 절차·문의·목적). 요청 수는 기록 줄 수로 세므로 차례와 상관없다는 것과 칸 「단계」로 찾는다는 것을 b4에 적음. 도구 파일 `ask_all_together`도 같은 성질을 주석에 적음. 기록 칸은 01 그대로(새 칸 없음).
- **나눠 쓰기와 투표를 한 함수로**: 요청 딕셔너리 `{"단계", "지시 글", "요청 글"}` 목록 → `ask_all_together`. `write_sections` = 지시 글 하나 + 요청 글을 부분마다(`build_part_request`), 받은 글을 `join_parts`로 이어 `{"상태": "완료", "부분", "안내문"}`. `run_vote` = 요청 글 하나 + 지시 글을 평가자마다, `count_votes` → `decide_vote(counts, needed_votes)` → `{"상태": "완료", "답", "셈", "결과"}`. **「무엇이 요청마다 달라지는가」**가 두 모양의 차이(b4 첫 도식·복습 1 — 옛 학습 목표 「섹셔닝과 투표의 입력 차이」를 이음).
- **투표 입력**: 후보 글 A·B를 **손으로 씀**(옛 판은 모델이 후보를 만들어 원표가 흔들림). 평가자 셋(인사 담당·보안 담당·신입 직원)은 가운데 기준 문장만 다른 지시 글. 칸 「표」 하나. 다수결 규칙은 코드가 결정적으로 정하는 것이라 **손으로 적은 답 목록 둘**(A·A·B / A·B·고르지 않음)과 셈 둘에 `assert` 넷. 모델 표에는 `assert` 없음. `Counter`·`most_common` 대신 딕셔너리 + `for`(인계 4번).
- **값 바꿔 보기(9절, 모델 요청 0)**: 필요한 표 수 2 → 3(과반 → 만장일치). 8절 셈 그대로 → `A` → `정하지 못함`. 예상 두 문장을 먼저 적음. Anthropic 글의 「다른 투표 기준」과 이음(b4·b10).
- 칸 이름: 부분 답 `부분`·`글`, 표 답 `표`, 셈 `A`·`B`·`그 밖`, 흐름 결과 `상태`(두 흐름 모두 「완료」)·`부분`·`안내문` / `답`·`셈`·`결과`. 단계 이름 = 부분 이름(`목적`·`절차`·`문의`) / 평가자 이름(`인사 담당`·`보안 담당`·`신입 직원`).
- **처음 쓴 모양**(한 문장씩 풂): 이 챕터 첫 `async def`·셀 맨 위 `await`·`asyncio.to_thread`·`asyncio.gather`(모두 Ch 2 12에서 배운 모양이라 되짚기) · `type(…).__name__`로 `coroutine` 확인 · `gather(*목록)` 별표 풀기(과정 처음) · 함수 안에서 `await` 쓰려면 `async def` · 목록 안 딕셔너리 `judges[i]["이름"]` · `!=`와 `and`로 「A도 B도 아니면」 · `>=` 「이상」. **안 쓴 것**은 생성기 머리말.
- 공통 사실에 날짜·까닭·등록 방법·문의처를 모두 넣어 부분 글이 사실을 지어낼 까닭을 줄임(04 옛 판의 지어낸 연락처 문제를 미리 피함). 문의처 `help@company.test`(옛 06 과제와 같은 연습용 주소).

## 4. 스레드 안전 확인 (챕터 리드 결정 2 — `03-probe.md` §1)

- **문서·소스**: httpx 0.28.1 설치판 `Client` 설명 「It can be shared between threads.」(웹 문서 https://www.python-httpx.org/api/ 같음, 확인 2026-09-23) · httpx 관리자 답(Discussion #1633, 2021-05-10) 「HTTPX is intended to be thread-safe … a single client-instance across all threads will do better」 · httpcore 1.0.9 연결 풀 `threading.Lock` · openai 2.29.0 `SyncAPIClient._client`는 `httpx.Client` 하위 클래스 하나 · openai README는 스레드를 적지 않음(Discussion #1901도 명시 없음) · Python 3.12 FAQ `L.append(x)` 원자적.
- **실행**: 클라이언트 하나로 요청 열 개를 `to_thread` + `gather` 두 번 → 20/20 `completed`, 답의 번호 = 보낸 번호 20/20, 응답 id 모두 다름, 스레드 8개(CPU 4). 이어서 밖 확인 45번·새 커널 24번도 같은 모양으로 오류 0.
- **결론**: 동기 `OpenAI()` 하나를 여러 스레드가 함께 쓰는 모양 그대로(스레드마다 클라이언트를 만들지 않음). 본문 b7·노트북 2절 결과 읽기에 근거 한 문장씩.
