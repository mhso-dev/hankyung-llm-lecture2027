1학습 목표

  • AsyncOpenAI와 asyncio.gather()로 독립 호출을 함께 기다릴 수 있습니다.
  • 섹셔닝과 투표의 입력 차이를 설명할 수 있습니다.
  • 동점·거절·형식 오류를 제외하거나 미결정으로 기록할 수 있습니다.

2이 내용을 배우는 이유

안내문의 목적, 등록 절차, 지원 방법은 같은 사실을 쓰지만 서로의 완성 결과를 기다릴 필요가 없습니다. 세 작업을 차례로 호출하면 네트워크 대기 시간이 누적됩니다. 반대로 앞 단계 결과가 필요한 작업까지 함께 시작하면 입력이 준비되지 않습니다. 이 절은 독립성을 먼저 판단한 뒤 asyncio.gather()로 섹션 작성과 평가 투표를 실행합니다.

3앞에서 배운 내용

Ch 2에서 코루틴과 await를 배웠습니다. Ch 18의 앞 두 절은 호출 순서와 분기를 코드로 고정했습니다. 이제 AsyncOpenAI를 사용하되 API 메서드와 응답 형식은 동기 클라이언트와 같은 Responses API를 유지합니다.

4핵심 개념

쉬운 예

신문 지면에서 경제 기사와 스포츠 기사는 서로 다른 기자가 동시에 쓸 수 있습니다. 한편 제목은 두 기사의 본문을 읽은 뒤 정해야 하므로 먼저 시작할 수 없습니다. 섹셔닝은 독립 기사 작성에 해당하고, 투표는 같은 후보를 여러 편집자가 각자의 기준으로 검토하는 일에 해당합니다.

정의

병렬화(parallelization)는 서로 의존하지 않는 모델 호출을 겹치는 시간 동안 실행하는 패턴입니다. 섹셔닝(sectioning)은 한 과제를 독립 부분으로 나누고 각 부분에 다른 요청을 보냅니다. 투표(voting)는 같은 후보를 여러 평가자에게 보내 다양한 판정을 모읍니다. asyncio.gather()는 여러 awaitable을 함께 실행하고 입력한 순서대로 결과 목록을 반환합니다. 완료 순서와 반환 목록 순서는 구분해야 합니다.

도식 읽기

{{svg:03-흐름}}

왼쪽은 공통 사실을 목적·절차·지원으로 나누어 동시에 작성한 뒤 결과를 모으는 섹셔닝입니다. 오른쪽은 같은 후보 A·B를 여러 평가자가 검토하는 별도 투표 실험입니다. A·B 득표수와 tie·refuse 원자료를 구분합니다.

코드를 읽기 전에

AsyncOpenAI는 비동기 클라이언트이며 await client.responses.create(...)에서 각 네트워크 응답을 기다립니다. asyncio.gather(*jobs)는 여러 코루틴을 함께 예약하고 모든 결과가 끝난 뒤 입력 순서의 목록을 반환합니다. 요청을 동시에 시작할 수 있다는 뜻이지 제공자 내부 처리 시간이나 완료 순서가 같다는 뜻은 아닙니다.

섹셔닝은 서로 의존하지 않는 목적·절차·지원 문단을 나눕니다. 투표는 같은 두 후보를 여러 평가 기준에 보냅니다. 전자는 결과를 합쳐 한 문서를 만들고, 후자는 판정 분포를 남긴다는 점에서 출력의 합치는 방식이 다릅니다.

다른 상황과 개념 경계

한 보고서의 매출 표와 고객 인터뷰 요약은 동시에 만들 수 있지만, 두 결과를 인용하는 결론은 먼저 실행할 수 없습니다. 보안 검토에서는 같은 코드에 서로 다른 취약점 관점을 병렬 적용할 수 있습니다. 병렬화는 의존성이 없는 구간의 대기 시간을 겹치게 할 뿐이며, 호출 수와 오류 처리 책임을 줄여 주지는 않습니다.

5실행 예제

섹셔닝 세 호출의 반환 목록은 목적, 절차, 지원이라는 입력 순서로 나타났습니다. 병렬 벽시계 시간은 2.283초였고 개별 호출 지연의 합은 5.644초였습니다. 이 한 번의 실행에서는 함께 기다린 시간이 개별 지연 합보다 짧았습니다. 투표 원자료는 A, B, A였으며 유효표 집계는 A 2표, B 1표였고 제외한 표는 없었습니다. 전체 성공 응답은 8개, 입력 1,251토큰, 출력 546토큰, 사용량 기준 추정 비용은 0.003395달러였습니다.

{{notebook:03-병렬-섹셔닝과-투표}}

확인할 점 — 반환 목록이 요청 순서를 보존하는지, 벽시계 시간이 개별 지연 합보다 짧은지, 원표와 유효표가 모두 남는지 확인합니다.

6실험 결과 해석

이 결과는 gather가 호출을 겹쳐 기다렸다는 한 번의 관찰입니다. 이번에 5.644초의 개별 지연 합과 2.283초의 벽시계 시간 사이에서 나타난 차이가 반복된다고 일반화할 수 없습니다. 서비스 부하와 네트워크가 바뀌면 지연도 달라집니다. 투표 결과 A는 이 세 평가 프롬프트의 결과이며 정답이나 보편적 선호를 뜻하지 않습니다. 이번에는 세 표 모두 A/B 집계에 포함되었습니다. tie나 refuse가 반환되는 경우에는 원표에 남기고 A/B 승자 집계에서 제외하도록 작성했습니다. A와 B가 같은 수를 받으면 tie, 유효표가 하나도 없으면 undecided로 반환합니다.

7주의할 점과 실무 메모

  • 앞 호출의 출력이 필요한 작업에는 gather를 사용하지 않습니다.
  • 동시에 보내는 요청 수는 계정의 속도 제한과 서비스 부하를 고려해 상한을 둡니다.
  • 다수결은 같은 오류를 반복하는 평가자 집단에서 신뢰를 보장하지 않습니다. 평가 기준과 사람이 판정한 라벨을 별도로 확인합니다.

8정리와 다음 절

  • 독립 섹션 세 개를 동시에 시작해 벽시계 시간을 측정했습니다.
  • 동점·거절 처리 규칙을 두고 원자료와 A/B 집계를 구분했습니다.
  • 병렬화의 지연 이점과 품질 효과는 서로 다른 측정입니다.

다음 학습과 이어지는 지점 — 다음 절에서는 하위 작업 목록 자체를 미리 정하지 않고 중앙 모델이 입력에 따라 작업 수와 지시를 결정합니다.
