1학습 목표

  • 01~05절의 흐름 함수를 도구 파일에서 가져와, 같은 과제 글로 다섯 흐름을 실행할 수 있습니다.
  • 흐름마다 요청 수·토큰 수·걸린 초·코드 검사 점수·상태를 표 한 줄로 만들어 견줄 수 있습니다.
  • 흐름의 모양이 정한 값과 실행마다 달라진 값을 가려 비교 표를 읽을 수 있습니다.

2이 내용을 배우는 이유

01~05절은 흐름마다 과제와 설정이 조금씩 달랐습니다. 그래서 절마다 본 요청 수를 나란히 놓아도 차이가 어디서 왔는지 가를 수 없습니다. 흐름에서 왔을 수도, 과제에서 왔을 수도 있습니다. 같은 과제 글과 같은 모델, 같은 코드 검사 값을 두고 흐름만 바꿔야 흐름끼리 견줄 수 있습니다.

이 절은 다섯 흐름에 같은 과제를 넣고, 결과를 같은 칸의 표 한 장으로 모읍니다. 다만 한 번 실행한 표로 어느 흐름이 늘 낫다고 정하지는 않습니다. 모델 답은 실행마다 달라질 수 있기 때문입니다. 그래서 흐름의 모양이 정한 값과 실행마다 달라진 값을 가려 읽습니다.

3앞에서 배운 내용

01~05절에서 만든 흐름 함수 다섯은 모두 도구 파일 workflow_tools.py에 있습니다. 다섯 함수는 설정 딕셔너리 한 벌과 기록 목록을 받고, 칸 「상태」가 있는 흐름 결과를 내놓습니다. 아래 표는 이 절이 가져다 쓰는 모양입니다.

절흐름 함수모델 요청 수상태가 「완료」가 아닐 때
01 단계 잇기run_gated_chain게이트를 지나면 2번게이트에 걸리면 「멈춤」
02 라우팅route_question검사를 지나면 2번검사에 걸리면 「되묻기」

05 쓰고 평가하기 반복run_write_judge_loop바퀴 수 × 2바퀴 한도로 멈추면 「멈춤」

01절에서 기록 한 줄은 요청 한 번이라고 정했으므로, 요청 수는 기록 줄 수입니다. 03절에서는 time.perf_counter()로 걸린 초를 쟀습니다. 05절에서는 함수 check_draft로 글자 수와 꼭 담을 말을 코드로 검사했습니다. 이 절은 세 가지를 모두 다시 씁니다.

Ch 17 01절 규칙으로 가르면 다섯 흐름은 모두 워크플로우였습니다. 04절 작업 수와 05절 바퀴 수처럼 모델 답이 정하는 값이 있어도, 다음 단계를 고른 것은 코드였습니다.

4핵심 개념

비유로 시작하기

도자기 공방에서 그릇을 빚는 방법 다섯을 견준다고 해 봅니다. 같은 흙을 같은 크기로 다섯 덩이 떼어, 덩이마다 다른 방법으로 빚습니다. 다 빚은 그릇은 한 선반에 나란히 놓고, 모두 같은 자로 잽니다. 흙이나 자가 서로 다르면, 그릇의 차이가 빚는 방법에서 왔는지 알 수 없습니다.

한 번 빚은 그릇만 보고 어느 방법이 늘 낫다고 정하지도 않습니다. 같은 방법으로 다시 빚어도 그릇은 조금씩 다를 수 있습니다. 그래도 방법마다 손이 몇 번 가는지는 빚기 전에 정해진 것도 있습니다.

그림 읽기 — 두 칸짜리 나무 선반의 위 칸에 같은 크기의 회색 흙덩이 다섯이 한 줄로 놓여 있습니다. 아래 칸에는 흙덩이마다 바로 아래에 그릇이 하나씩, 왼쪽부터 컵·사발·세운 접시·꽃병·주전자가 있습니다. 위 칸의 같은 덩이 다섯은 다섯 흐름에 똑같이 준 과제 글입니다. 아래 칸의 서로 다른 그릇 다섯은 흐름마다 다른 방법으로 만든 안내문입니다. 같은 선반에 나란히 놓아야 같은 자로 견줄 수 있습니다.

말뜻
같은 조건 비교(fair comparison)과제 글과 모델, 설정, 검사 값을 같게 두고 흐름만 바꿔 견주는 일입니다. 같은 흙과 같은 자를 두고 빚는 방법만 바꾸는 것과 같습니다.
비교 표 한 줄흐름 하나를 실행한 결과를 패턴 이름·요청 수·토큰 수·걸린 초·품질·상태 여섯 칸에 적은 것입니다. 선반 위 그릇 하나에 붙인 기록표와 같습니다.
품질 칸(quality)안내문을 코드 검사 항목으로 보고 문제가 없는 항목 수를 센 값입니다. 이 절에서는 0~5이고, 평가 모델의 점수가 아닙니다. 모든 그릇을 같은 자로 잰 눈금과 같습니다.

새 말을 이 절 코드에서 보면 이렇습니다. 같은 조건 비교는 다섯 흐름이 함께 쓰는 과제 글 task_text와 코드 검사 값 grade_setup입니다. 비교 표 한 줄은 함수 make_row가 만드는 딕셔너리입니다. 품질 칸은 함수 grade_notice가 셉니다.

도식 읽기 — 왼쪽에서 오른쪽으로 읽습니다. 왼쪽 초록 상자의 과제 글과 코드 검사 값을 가운데 파란 흐름 다섯이 똑같이 받습니다. 흐름마다 만든 표 한 줄이 오른쪽 노란 비교 표로 모입니다. 두 번 실행 모두 다섯 줄의 칸 「상태」가 ok였습니다.

요청 수는 누가 정하는가

단계 잇기와 라우팅은 검사를 지나면 요청이 두 번입니다. 나눠 쓰기는 코드에 적은 부분 수만큼 요청을 보냅니다. 이 셋은 실행하기 전에 요청 수를 셀 수 있습니다. 작업 나눠 맡기기는 계획 모델이 정한 작업 수에 따라 요청 수가 달라집니다. 쓰고 평가하기 반복은 멈추기까지 돈 바퀴 수에 따라 달라집니다.

그래도 다섯 흐름 모두 다음 단계를 고른 것은 코드입니다. 04절 최대 작업 수와 05절 바퀴 한도처럼, 모델 답에 기대는 요청 수에도 코드가 정한 상한이 있습니다. 그래서 이 절 노트북의 요청은 한 번 실행에 많아야 19번입니다.

품질 칸은 무엇을 재는가

품질 칸은 글자 수 범위와 꼭 담을 말 넷만 봅니다. 문장이 자연스러운지, 공통 사실에 없는 내용을 지어냈는지는 보지 않습니다. 셀 수 있는 조건만 코드로 세었으므로, 같은 안내문에는 늘 같은 값이 나옵니다.

쓰고 평가하기 반복은 같은 코드 검사를 정지 조건에 넣었습니다. 그래서 상태가 「완료」이면 품질은 늘 5입니다. 다른 넷은 흐름이 끝난 뒤에야 이 검사를 받습니다. 이 차이는 흐름이 더 잘 써서가 아니라, 검사를 어디에 두었는지에서 옵니다.

다른 상황에 적용

번역문이나 요약문을 쓰는 흐름을 견줄 때도 같은 차례를 따릅니다. 먼저 과제 글과 모델, 검사 값을 적고, 흐름만 바꿔 실행합니다. 검사 값은 결과를 보기 전에 정해 둡니다. 결과를 본 뒤 검사 값을 바꾸면, 표의 차이가 흐름에서 왔는지 검사 값에서 왔는지 가를 수 없습니다.

비교와 경계

이 절의 표는 한 과제를 한 번 실행한 기록입니다. 걸린 초는 네트워크와 서비스 상태에 따라 실행마다 달라집니다. 토큰 수는 입력 토큰과 출력 토큰을 더한 값입니다. 요금표로 셈하면 같은 토큰 수라도 예상 비용이 다를 수 있고, 이 절 노트북은 예상 비용을 셈하지 않았습니다.

6실험 결과 해석

새 커널 두 번 모두 다섯 흐름이 「완료」로 끝났고, 표의 칸 「상태」는 다섯 줄 모두 ok였습니다. 요청 수도 두 번 모두 단계 잇기 2, 라우팅 2, 나눠 쓰기 3, 작업 나눠 맡기기 5, 쓰고 평가하기 반복 2였습니다. 노트북 밖에서 다섯 번 보냈을 때도 같았습니다.

앞의 셋은 게이트와 검사를 지나면 요청 수가 코드로 정해집니다. 단계 잇기와 라우팅은 두 번, 나눠 쓰기는 부분 셋이라 세 번입니다. 게이트와 검사를 지날지는 모델 답에 달려 있습니다.

작업 나눠 맡기기의 5는 계획 모델이 작업 셋을 써서 나온 수입니다. 쓰고 평가하기 반복의 2는 첫 바퀴에서 기준을 통과해서 나온 수입니다. 이 두 수는 모델 답이 달라지면 바뀔 수 있습니다.

품질 칸에서 두 번 모두 같았던 것은 둘입니다. 나눠 쓰기는 두 번 모두 104자로 120자보다 짧아 품질 4였습니다. 부분마다 한 문장씩 쓰게 했고, 이은 글의 글자 수를 보는 요청이 없었기 때문입니다. 쓰고 평가하기 반복은 두 번 모두 품질 5였고, 이것은 코드 검사를 정지 조건에 넣은 구조에서 옵니다.

걸린 초는 다섯 흐름 모두 두 번이 달랐습니다. 토큰 수는 작업 나눠 맡기기와 쓰고 평가하기 반복이, 품질은 라우팅이 두 번 달랐습니다. 단계 잇기의 품질은 두 번 같았지만, 노트북 밖 다섯 번 가운데 한 번은 4였습니다. 아래 표는 두 번의 출력입니다.

도식 읽기 — 왼쪽 칸의 파란 상자는 코드에 적은 규칙만으로 요청 수가 정해지는 흐름입니다. 오른쪽 칸의 보라 상자는 계획 모델이 쓴 작업 수나 멈추기까지 돈 바퀴 수에 따라 요청 수가 달라지는 흐름입니다. 노란 상자는 두 번 실행 모두 같았던 요청 수입니다. 맨 아래 회색 상자는 오른쪽 칸의 요청 수에도 코드가 정한 상한이 있다는 뜻입니다.

값 바꿔 보기에서는 코드 검사의 최소 글자 수만 120에서 100으로 낮췄습니다. 흐름을 다시 실행하지 않았으므로 요청 수와 토큰 수, 걸린 초는 그대로입니다. 두 번 모두 새 검사 값으로는 다섯 흐름의 품질이 모두 5였습니다. 같은 안내문이라도 검사 값에 따라 품질 칸이 달라진다는 뜻입니다.

그래서 검사 값은 결과를 보기 전에 정해 둡니다. 결과를 본 뒤 검사 값을 바꾸면, 나눠 쓰기도 다른 흐름과 같은 품질로 보이게 할 수 있습니다. 이 절은 2절에서 정한 120~180자를 9절 표까지 바꾸지 않았습니다.

7주의할 점과 실무 메모

  • 노트북을 쓰기 전에 같은 과제 글로 다섯 흐름을 노트북 밖에서 다섯 번씩 보냈습니다. 다섯 흐름 모두 다섯 번 다 「완료」였고, 요청 수도 다섯 번 모두 2·2·3·5·2였습니다. 과제 글과 코드 검사 값은 그 전에 정했고, 결과를 보고 바꾸지 않았습니다.
  • 과제 글은 다섯 흐름이 모두 끝까지 가는 예로 정했습니다. 05절처럼 글자 수를 150~170자로 좁히면 쓰고 평가하기 반복은 바퀴가 늘어납니다. 「바퀴 한도」로 멈추면 칸 「상태」가 ok가 아니게 됩니다. 흐름을 보여 주려고 정한 예이고, 같은 요청도 실행한 때에 따라 결과가 달라질 수 있습니다.
  • 이 절의 표는 Ch 29 04절이 저장된 출력에서 읽습니다. 그래서 표의 칸 이름과 패턴 이름은 영어로 두고, 표 뒤에는 칸을 나눈 줄을 더 출력하지 않았습니다. 흐름이 「완료」가 아니면 칸 「상태」가 ok가 아니게 되고, 그 절의 확인 줄이 멈춥니다.
  • 나눠 쓰기 흐름에는 과제 글을 넣지 않았습니다. 03절 함수가 과제 글을 받지 않는 모양이기 때문입니다. 과제가 담으라는 내용은 부분 셋으로, 글자 수 요구는 「부분마다 한 문장」으로 옮겨 적었습니다. 안내문 전체의 글자 수를 보는 요청은 이 흐름에 없습니다.
  • 작업 나눠 맡기기 흐름은 종합 머리글에만 과제 글을 넣었습니다. 작업 모델의 요청 글은 04절처럼 공통 사실과 맡을 작업만 받습니다.
  • 품질 칸은 글자 수와 꼭 담을 말만 봅니다. 문장이 좋은지, 공통 사실에 없는 날짜나 절차를 지어냈는지는 가리지 않습니다. 평가 모델의 점수도 아닙니다.
  • 걸린 초는 흐름마다 한 번씩만 쟀습니다. 첫 흐름에는 서비스와 연결을 여는 시간이 들어 있을 수 있지만 따로 재지 않았습니다. 걸린 초로 흐름의 빠르기 순위를 정하지 않습니다.
  • 토큰 수는 입력 토큰과 출력 토큰을 더한 값입니다. 출력 토큰이 더 비싸므로, 예상 비용을 견주려면 두 토큰을 나눠 요금표를 곱해야 합니다. 이 절은 예상 비용을 노트북에서 셈하지 않았습니다.
  • 분류 답에 칸 「종류」나 「신뢰도」가 없으면 KeyError로 셀이 멈춥니다. 다른 흐름도 약속한 칸이 없거나 답이 JSON 글이 아니면 멈춥니다. 이번 실행과 노트북 밖 확인에서는 그런 답을 받지 않았습니다.
  • 모델이 쓴 안내문과 잰 값에는 assert를 쓰지 않았습니다. 손으로 적은 기록과 글에 건 함수 동작만 assert로 확인했습니다.
  • temperature 값을 0으로 두어도 답 문장이 매번 같다고 보장하지는 않습니다. 안내문 글과 글자 수, 출력 토큰은 실행마다 달라질 수 있습니다.
  • 교재 출력을 만든 실행의 요청 수는 14번입니다. 노트북 밖 확인에서 다섯 흐름 한 번은 입력 약 3,300토큰, 출력 약 900토큰이었습니다. 요금표로 어림하면 0.01달러 아래이고, 요금표는 100만 토큰당 입력 0.75달러, 출력 4.50달러로 셈했습니다. 실제 청구 금액과는 다를 수 있습니다.
  • 이 절은 자료 파일을 읽거나 새 파일을 쓰지 않습니다. 이 절에서 만든 함수 셋도 실습 폴더 notebooks/workflow_tools.py에 옮겨 두었습니다.
  • 교재 출력은 Linux의 Python 3.12.13과 openai 2.29.0으로 만들었습니다. 다른 판과 Windows·macOS에서는 이번에 실행하지 않았습니다.

9복습 문제

문제 4개 · 해설 포함

1. 이 절의 나눠 쓰기 설정에서 부분을 넷으로 늘리면, 모델 요청은 몇 번 나가나요?

네 번입니다. 나눠 쓰기 흐름은 코드에 적은 부분마다 요청을 하나씩 보냅니다. 부분 수는 모델이 아니라 설정이 정합니다. 틀렸다면 「핵심 개념」의 「요청 수는 누가 정하는가」를 다시 읽습니다.

2. 작업 나눠 맡기기 흐름에서 계획 모델이 작업 넷을 쓰면 요청 수는 몇 번인가요? 최대 작업 수는 4입니다.

여섯 번입니다. 계획 요청 한 번, 작업마다 한 번씩 네 번, 종합 요청 한 번입니다. 틀렸다면 노트북 7절의 요청 수 설명을 다시 봅니다.

3. 비교 표에서 쓰고 평가하기 반복 줄의 상태가 ok이면, 품질이 늘 5인 까닭은 무엇인가요?

이 흐름은 같은 코드 검사를 정지 조건에 넣었기 때문입니다. 「기준 통과」로 끝나려면 코드 검사 문제가 없어야 합니다. 흐름이 더 잘 써서가 아니라 검사를 둔 자리 때문입니다. 틀렸다면 「핵심 개념」의 「품질 칸은 무엇을 재는가」를 다시 읽습니다.

4. 결과를 본 뒤 코드 검사 값을 바꾸면 무엇이 문제인가요?

표의 차이가 흐름에서 왔는지 검사 값에서 왔는지 가를 수 없습니다. 노트북 10절처럼 요청 수와 토큰 수가 그대로여도 품질 칸은 검사 값에 따라 달라질 수 있습니다. 틀렸다면 「핵심 개념」의 「다른 상황에 적용」을 다시 읽습니다.
