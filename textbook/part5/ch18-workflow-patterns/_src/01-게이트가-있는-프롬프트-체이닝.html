1학습 목표

  • 앞 단계 모델이 쓴 기획을 다음 단계 요청 글에 넣어 두 요청을 이을 수 있습니다.
  • 중간 결과의 칸과 개수를 코드 게이트로 검사할 수 있습니다.
  • 게이트가 문제를 찾으면 다음 요청을 보내지 않고 멈출 수 있습니다.

2이 내용을 배우는 이유

안내문 기획을 먼저 받고, 그 기획으로 안내문을 쓰게 하는 흐름을 생각해 봅니다. 첫 단계 답이 약속한 모양이 아니어도 둘째 단계는 그대로 실행됩니다. 그러면 쓸 수 없는 기획이 요청 한 번을 더 쓰고 안내문까지 흘러갑니다.

제목의 프롬프트 체이닝(prompt chaining)은 모델 요청 여러 개를 정해 둔 차례로 잇는 모양입니다. 이 챕터는 이 모양을 「단계 잇기」라고 부릅니다. 이 절은 두 단계 사이에 코드 게이트를 둡니다. 게이트는 기획이 약속한 모양인지 보고, 아니면 둘째 요청을 보내지 않습니다.

이 챕터는 Ch 17에서 본 워크플로우의 다섯 모양을 LangChain 없이 코드로 직접 만듭니다. 이 절은 그 첫째입니다.

3앞에서 배운 내용

Ch 17 01절은 워크플로우를 모델과 도구가 코드에 미리 적어 둔 차례대로 실행되는 구조로 정했습니다. 이 절의 두 단계도 차례를 코드가 정합니다. 모델은 기획과 안내문 글만 쓰고 다음 단계를 고르지 않습니다. 그래서 Ch 17 01절 규칙으로 가르면 워크플로우입니다.

Ch 15 02절과 Ch 17 03절에서는 모델이 쓴 JSON 글을 json.loads로 딕셔너리로 읽었습니다. 이 절도 두 단계의 답을 모두 JSON 글로 받아 같은 방법으로 읽습니다. 「머리글」과 「요청 글」도 Ch 15·Ch 17 뜻 그대로 씁니다.

Ch 16 01절은 모델을 부르기 전에 질문을 보는 입력 검사를 붙였습니다. 이 절의 게이트는 두 요청 사이에서 앞 요청의 답을 봅니다. 검사할 값이 사람이 쓴 질문이 아니라 모델이 쓴 중간 결과라는 점이 다릅니다.

Ch 6부터 Ch 17까지는 LangChain의 init_chat_model로 모델을 불렀습니다. 이 챕터는 OpenAI가 낸 파이썬 패키지(SDK)를 직접 씁니다. 다섯 모양의 흐름을 프레임워크 없이 코드로 적어 보려는 까닭입니다. 이 챕터 실습 폴더도 openai와 python-dotenv 두 패키지만 설치합니다.

4핵심 개념

비유로 시작하기

도자기 공방의 차례를 떠올려 봅니다. 물레에서 그릇을 빚고, 말린 뒤 가마에 넣어 굽습니다. 빚은 그릇에 금이 가 있으면 가마에서 구워 나와도 쓸 수 없습니다. 그래서 가마에 넣기 전에 그릇을 하나씩 살펴 금 간 그릇을 옆으로 골라냅니다.

빚은 그릇이 이 절의 중간 결과이고, 가마가 다음 단계입니다. 가마 앞에서 살피는 자리가 게이트입니다. 살피지 않으면 금 간 그릇도 가마 자리와 땔감을 쓰고 끝까지 갑니다.

그림 읽기 — 왼쪽 나무 물레 위에 회색 점토 덩이가 있습니다. 가운데 긴 나무 판 위에는 매끈한 그릇 둘이 나란히 서 있습니다. 판 끝은 오른쪽 벽돌 가마의 열린 문으로 이어지고, 문 안은 주황빛입니다. 판 아래 따로 놓인 둥근 접시 위에는 옆면에 금이 간 그릇 하나가 있습니다. 판 위 그릇 둘은 게이트를 지난 중간 결과이고, 접시 위 그릇은 게이트가 멈춘 중간 결과입니다.

말뜻
단계 잇기(prompt chaining)앞 단계 모델이 쓴 결과를 다음 단계 요청 글에 넣어, 모델 요청 여러 개를 정해 둔 차례로 잇는 모양입니다. 빚기와 말리기, 굽기처럼 차례가 정해진 일과 같습니다.
중간 결과(intermediate output)앞 단계가 내놓아 다음 단계 요청 글에 들어갈 값입니다. 가마에 들어가기 전의 빚은 그릇과 같습니다.
게이트(gate)중간 결과가 다음 단계에 쓸 모양인지 코드로 검사해, 통과한 것만 넘기는 자리입니다. 가마 앞에서 금 간 그릇을 골라내는 일과 같습니다.
지시 글(instructions)요청 글보다 먼저 모델에게 주는 역할과 규칙 글입니다. 공방 벽에 붙여 둔 작업 규칙과 같습니다.
클라이언트(client)서비스에 요청을 보내고 응답을 받는 파이썬 객체입니다. 주문을 받아 전해 주는 접수 창구와 같습니다.

새 말을 이 절 코드에서 보면 이렇습니다. 단계 잇기는 함수 run_gated_chain 안의 두 요청입니다. 중간 결과는 첫 요청이 내놓은 기획 딕셔너리이고, 게이트는 함수 check_plan입니다. 지시 글은 인자 instructions에, 요청 글은 인자 input에 넣습니다. 클라이언트는 client = OpenAI()로 만든 객체입니다.

도식 읽기 — 위에서 아래로 읽습니다. 맨 위 초록 상자가 칸 셋을 약속한 기획 요청 글이고, 그 아래 보라 상자가 첫 단계 모델 요청입니다. 노란 상자는 노트북 4절이 출력한 중간 결과로, 칸 셋이 있는 기획 딕셔너리입니다. 파란 게이트에서 점선이 둘로 나뉩니다. 문제가 없으면 보라 둘째 단계 모델을 지나 안내문으로 가고, 문제가 있으면 작성 요청 없이 멈춥니다.

요청 한 번의 모양

요청은 메서드 client.responses.create로 보냅니다. 인자 model에는 모델 이름 gpt-5.4-mini를 적습니다. 인자 temperature=0과 reasoning={"effort": "none"}은 Ch 6부터 쓴 설정과 같은 뜻입니다. 인자 text의 형식 json_object는 답을 JSON 글 하나로만 쓰게 합니다.

응답 객체의 속성 output_text는 모델이 쓴 글입니다. 속성 usage에는 입력 토큰 수와 출력 토큰 수가 들어 있습니다. 이 절은 요청마다 이 두 수와 단계 이름을 기록 한 줄로 남깁니다. 요청 수는 기록 목록의 줄 수로 셉니다.

게이트는 코드로 검사합니다

이 절의 게이트는 두 가지를 봅니다. 먼저 약속한 칸 「제목」·「독자」·「절차」가 모두 있는지 봅니다. 그다음 칸 「절차」가 목록이고 셋 이상인지 봅니다. 문제를 찾으면 문제 글을 목록에 담고, 흐름 함수는 둘째 요청을 보내지 않습니다.

칸 「절차」가 없는 기획에서는 둘째 검사를 건너뜁니다. 없는 칸을 읽으려다 멈추지 않게, 칸이 있는지를 조건 맨 앞에 두었습니다.

검사를 모델에게 맡기지 않고 코드로 하는 까닭이 있습니다. 코드 검사는 요청을 더 쓰지 않고, 같은 기획에는 늘 같은 결과를 냅니다. 무엇을 막는지도 코드에 그대로 보입니다.

다른 상황에 적용

기사 초안을 번역하는 흐름이라면 번역 전에 초안에 제목 칸과 본문 칸이 있는지 볼 수 있습니다. 회의록에서 할 일 목록을 뽑은 뒤 알림을 쓰는 흐름이라면 할 일마다 담당자 칸이 있는지 봅니다. 자리는 같습니다. 앞 단계 결과를 다음 요청 글에 넣기 전에 봅니다.

비교와 경계

게이트는 기획의 모양만 봅니다. 칸이 모두 있어도 기획 내용이 사실인지, 안내문 문장이 좋은지는 보지 않습니다. 내용 판정은 Ch 15에서 본 평가 모델이 맡는 자리이고, 이 절은 그 판정을 하지 않았습니다.

SDK 설명은 형식 json_object를 옛 방법으로 적고, 칸 모양을 정해 주는 형식 json_schema를 권합니다. 이 절은 칸이 빠진 기획을 게이트로 잡는 연습이라 json_object를 썼습니다. 형식 json_schema는 이번에 실행하지 않았습니다.

5실행 예제

노트북은 먼저 기획 요청을 SDK로 한 번 직접 보내고 응답 객체를 봅니다. 그다음 기록 한 줄을 남기는 함수와 요청 도움 함수, 게이트 함수를 차례로 만듭니다. 게이트는 손으로 적은 기획 둘과 모델이 쓴 기획 하나에 걸어 봅니다.

이 부분에서 모델 요청은 한 번 나갑니다. 노트북 전체로는 여섯 번이고, 파일을 읽거나 쓰지 않습니다.

도식 읽기 — 왼쪽 칸이 Before이고 오른쪽 칸이 After입니다. 두 칸은 같은 요청 글로 기획을 받습니다. 왼쪽 빨간 상자 둘은 칸 셋이 없는 기획이 작성 요청으로 넘어가고 흐름이 문제 없이 완료를 알린 결함입니다. 오른쪽은 파란 게이트가 문제 셋을 찾아 노란 멈춤 상자로 끝납니다. 맨 아래 회색 상자는 두 칸에 공통인 사실입니다.

게이트 없는 흐름은 약속한 칸 셋이 하나도 없는 기획으로 작성 요청까지 보냈습니다. 흐름이 알린 상태는 완료였고 문제 목록은 비어 있었습니다. 문제는 흐름이 끝난 뒤 같은 게이트 규칙으로 따로 검사해서야 보였습니다.

게이트가 있는 흐름은 같은 요청 글에서 기획 단계에 멈췄습니다. 출력 줄 요청 수(기록 줄 수): 1로 작성 요청을 한 번 덜 보냈습니다. 게이트가 알려 준 문제 셋은 모두 약속한 칸이 없다는 것이었습니다.

칸 셋을 약속한 요청 글로 다시 실행하자 기획이 게이트를 지나 작성까지 갔습니다. 새 커널로 두 번 실행했을 때 상태와 요청 수, 문제 목록은 두 번 모두 같았습니다. 기획과 안내문 문장, 출력 토큰 수는 실행마다 달라 본문에 적지 않았습니다.

값 바꿔 보기는 게이트의 필수 칸 목록 하나만 바꿉니다. 칸 「문의처」를 더하자 노트북 10절에서 통과한 같은 기획이 ['문의처 칸 없음']으로 막혔습니다. 게이트 규칙을 바꾸면 요청 글의 약속도 함께 고쳐야 합니다.

도식 읽기 — 위에서 아래로 읽습니다. 초록 요청 글로 받은 보라 기획이 왼쪽의 원래 규칙과 오른쪽의 바꾼 규칙으로 각각 들어갑니다. 왼쪽은 점선 갈래 「문제 없음」을 지나 노란 완료 상자로 갑니다. 오른쪽은 초록 바꾼 값을 더한 규칙이라 노란 상자 「문의처 칸 없음」으로 끝납니다. 오른쪽 검사는 모델을 다시 부르지 않았습니다.

7주의할 점과 실무 메모

  • 노트북을 쓰기 전에 같은 요청을 노트북 밖에서 따로 다섯 번씩 보냈습니다. 칸 이름을 적지 않은 기획 요청은 다섯 번 모두 칸 「제목」·「독자」·「절차」가 없었습니다. 칸을 약속한 요청은 다섯 번 모두 칸 셋이 있었고 게이트를 지났습니다.
  • 같은 요청도 실행한 때에 따라 기획 모양이 달라질 수 있습니다. 칸 이름을 적지 않은 요청이 칸 셋을 모두 채우면, 노트북 10절 게이트도 멈추지 않고 작성 요청까지 보냅니다.
  • 게이트는 칸과 개수만 봅니다. 기획 내용이 사실인지, 안내문이 좋은지는 이번에 판정하지 않았습니다.
  • 모델이 쓴 글에는 assert를 쓰지 않았습니다. 손으로 적은 기획 둘에 건 게이트 동작만 assert로 확인했습니다.
  • 설치한 SDK 소스에서 확인한 기본값으로, 클라이언트는 연결 오류나 일부 서비스 오류에서 요청을 두 번까지 다시 보냅니다. 기록 줄 수는 받은 응답 수이고, 다시 보낸 요청은 세지 않습니다.
  • 요청 수는 노트북 한 번에 여섯 번입니다. 토큰 수를 출력하는 요청은 그 가운데 네 번입니다. 나머지 요청도 같은 크기로 보고 요금표를 곱해 어림하면 0.01달러 아래입니다. 요금표는 100만 토큰당 입력 0.75달러, 출력 4.50달러로 셈했고 실제 청구 금액과는 다를 수 있습니다.
  • 걸린 시간은 재지 않았습니다.
  • 이 챕터 실습 폴더는 openai 2.29.0을 씁니다. 다른 챕터 실습 폴더에는 다른 판이 설치될 수 있고, 이 절은 2.29.0으로만 실행했습니다.
  • temperature 값을 0으로 두어도 답 문장이 매번 같다고 보장하지는 않습니다.
  • 이 절은 파일을 읽거나 쓰지 않습니다.
  • 교재 출력은 Linux의 Python 3.12.13으로 만들었습니다. 다른 판과 Windows·macOS에서는 이번에 실행하지 않았습니다.

8정리와 다음 절

  • 첫 단계 기획을 JSON 글로 받아 딕셔너리로 읽고, 요청마다 기록 한 줄을 남겼습니다.
  • 게이트 없는 흐름은 약속한 칸 셋이 없는 기획으로도 작성 요청까지 보내고 완료를 알렸습니다.
  • 게이트가 있는 흐름은 같은 요청 글에서 기획 단계에 멈춰 요청을 한 번 덜 보냈습니다.

9복습 문제

문제 4개 · 해설 포함

1. 이 절의 게이트는 두 단계 흐름의 어디에 두나요?

첫 단계가 기획을 내놓은 뒤, 그 기획으로 둘째 요청 글을 만들기 전에 둡니다. 틀렸다면 「핵심 개념」의 첫 도식을 다시 봅니다.

2. 게이트 없는 흐름이 알린 상태는 무엇이었고, 그 상태를 믿을 수 없는 까닭은 무엇인가요?

상태는 완료였습니다. 흐름 안에 검사가 없어 약속한 칸 셋이 없는 기획으로 작성까지 가도 완료를 알립니다. 틀렸다면 노트북 9절을 다시 읽습니다.

3. 같은 요청 글에서 게이트가 있는 흐름은 요청을 몇 번 보냈고, 게이트가 찾은 문제는 무엇이었나요?

요청을 한 번 보냈습니다. 게이트는 칸 「제목」·「독자」·「절차」가 없다는 문제 셋을 찾고 작성 요청 전에 멈췄습니다. 틀렸다면 노트북 10절을 다시 읽습니다.

4. 게이트의 필수 칸에 「문의처」를 더하면 칸 셋을 약속한 요청 글의 기획은 어떻게 되나요?

칸 「문의처」가 없어 막힙니다. 게이트 규칙을 바꾸면 요청 글의 약속도 함께 고쳐야 합니다. 틀렸다면 노트북 11절을 다시 읽습니다.
