2이 내용을 배우는 이유

02절에서는 단계를 미리 적기 어려운 일이면 모델이 고르는 단계를 검토하라는 추천을 냈습니다. 모델에게 다음 단계를 고르게 두면, 모델이 끝을 고를 때까지 반복이 이어집니다. 모델이 언제 끝을 고를지 코드는 미리 알 수 없습니다. 그래서 반복을 멈추는 조건을 코드에 먼저 적어 두어야 합니다.

멈추는 조건이 없으면 모델이 끝을 고를 때까지 요청이 계속 나갑니다. 부작용이 있는 도구도 그대로 불릴 수 있습니다. 이 절은 실제 모델로 짧은 루프를 실행하고, 코드가 정한 조건에서 멈추는 모습을 기록으로 봅니다.

4핵심 개념

비유로 시작하기

01절의 눈 덮인 마당을 다시 떠올려 봅니다. 걸으며 다음 걸음을 고르는 사람은 언제 멈출지도 스스로 정할 수 있습니다. 가려던 자리에 꽂힌 말뚝에 닿으면 거기서 걸음을 멈춥니다.

그런데 말뚝을 찾지 못하면 눈밭 끝까지 걸어갈 수도 있습니다. 그래서 눈밭 주인은 미리 낮은 울타리를 둘러 둡니다. 걷는 사람이 멈추지 않아도 울타리 앞에서는 발자국이 끝납니다. 이 절의 루프에서 말뚝은 모델이 고르는 끝이고, 울타리는 코드가 세운 정지 조건입니다.

그림 읽기 — 눈밭 위쪽을 낮은 나무 울타리가 왼쪽 끝에서 오른쪽 끝까지 가로지릅니다. 왼쪽 발자국 한 줄은 아래 끝에서 올라와, 울타리 조금 아래에 홀로 선 짧은 말뚝 곁에서 끝납니다. 오른쪽 발자국 한 줄은 회색 바위 두 개 사이를 지나 울타리 바로 앞에서 끝납니다. 울타리 너머 눈밭에는 발자국이 없고, 먼 곳에 흐릿한 말뚝과 울타리가 보일 뿐입니다. 왼쪽은 걷는 사람이 고른 멈춤, 오른쪽은 울타리가 정한 멈춤입니다.

말뜻
루프(loop)모델에게 다음 행동을 묻고, 고른 도구를 부르고, 그 결과를 들고 다시 묻기를 되풀이하는 구조입니다. 눈밭에서 한 걸음 딛고 주위를 본 뒤 다음 걸음을 고르는 것과 같습니다. 이 절 코드에서는 함수 run_loop 안의 for가 루프입니다.
바퀴루프를 한 번 도는 차례입니다. 모델에게 한 번 묻고, 고른 도구를 한 번 부릅니다. 운동장 트랙을 한 바퀴 도는 것과 같습니다. 이 절에서는 바퀴마다 기록 줄이 둘 늘고 모델 요청이 한 번 나갑니다.
정지 조건(stopping condition)반복을 멈추는 조건입니다. 산책을 목적지에 닿거나 해가 지면 멈추는 것과 같습니다. 이 절에서는 모델의 끝 선택, 사람 확인, 같은 도구 다시 고름, 바퀴 한도 넷입니다.
바퀴 한도루프가 돌 수 있는 바퀴 수의 상한입니다. 놀이기구를 세 바퀴만 타기로 미리 정해 두는 것과 같습니다. 이 절 코드에서는 인자 turn_limit이고, 4와 2를 넣어 봅니다.
사람 확인부작용이 있는 도구를 모델이 고르면, 부르기 전에 반복을 멈추고 사람에게 넘기는 정지 조건입니다. 02절의 승인 지점에 닿으면 멈추는 것입니다. 이 절 코드에서는 목록 confirm_tools에 적은 환불 요청 등록이 그 도구입니다.

새 말을 이 절 코드에서 보면 이렇습니다. 함수 run_loop는 바퀴마다 ask_next로 모델에게 다음 행동을 묻고, stop_reason으로 멈출 까닭을 찾습니다. 멈출 까닭이 없으면 turn_lines 안에서 도구 흉내 run_tool이 불립니다. 바퀴를 다 쓰면 바퀴 한도로 멈춥니다.

도식 읽기 — 위에서 아래로 읽습니다. 맨 위 초록 기록에서 오른쪽 파란 상자 ask_next로 가고, 보라 모델이 다음 행동을 고릅니다. 파란 상자 stop_reason이 멈출 까닭이 없다고 보면 왼쪽 아래 도구 흉내로 갑니다. 도구 결과는 실선을 따라 맨 위 기록으로 되돌아가고, 그 자리에서 다음 바퀴가 시작됩니다. 오른쪽 아래 노란 상자와 맨 위 상자 바로 아래 노란 상자가 멈추는 자리입니다.

루프를 이루는 네 가지

이 절의 루프는 모델·도구·반복·정지 조건 네 가지로 이루어집니다. 모델은 다음 행동을 고르고, 도구는 정해진 일 하나를 합니다. 반복은 도구 결과를 다음 요청에 넣어 잇습니다. 정지 조건은 그 반복을 끝냅니다. 정지 조건이 빠지면 모델이 끝을 고를 때까지 루프가 멈추지 않습니다.

모델이 고르고 코드가 부릅니다

이 절에서 모델은 도구를 직접 부르지 않습니다. 모델은 도구 이름을 JSON 글로 적을 뿐입니다. 코드가 그 글을 읽고, 정지 조건을 본 뒤, 이름에 맞는 함수를 부릅니다. 그래서 멈추는 조건을 적어 두는 쪽은 코드입니다.

누가 멈추기로 정했는가

멈춤 줄의 칸 「고른 쪽」에는 누가 멈추기로 정했는지 적습니다. 모델이 끝을 고르면 모델이고, 사람 확인·같은 도구 다시 고름·바퀴 한도는 코드입니다. 모델의 끝 선택은 모델이 내놓은 멈춤입니다. 나머지 셋은 모델 뜻과 관계없이 코드가 세운 울타리입니다.

다른 상황에 적용

문서를 찾아 답하는 루프라면 근거 문서를 셋 찾았을 때 끝을 고르게 할 수 있습니다. 검색 다섯 바퀴를 바퀴 한도로 둘 수도 있습니다. 유료 자료를 부르거나 메일을 보내는 도구 앞에는 사람 확인을 둡니다. 조건마다 막는 것이 다릅니다. 바퀴 한도는 끝없는 반복을 막지만, 답이 충분한지는 알려 주지 않습니다.

비교와 경계

Ch 16 04절의 호출 한도는 예산 딕셔너리에 적은 모델 요청 수의 상한이었습니다. 부르기 전에 예약하고, 한도를 넘으면 요청을 보내지 않았습니다. 이 절의 바퀴 한도는 루프가 도는 바퀴 수의 상한입니다. 이 절은 바퀴마다 요청이 한 번이라, 바퀴 한도 4는 요청 네 번까지라는 뜻도 됩니다. 한 바퀴에 요청이 여러 번 나가는 루프라면 두 한도를 따로 두어야 합니다.

이 절의 모델은 도구 이름을 글로 적고, 코드가 그 글을 읽습니다. 모델 요청에 도구를 함께 싣는 방법(bind_tools)은 Ch 19 04절부터 다룹니다. 그래프로 도구 루프를 만드는 ToolNode는 Ch 20 01절에서 다룹니다.

3. 도구 흉내 셋

01절에서 도구는 모델 밖에서 정해진 일 하나를 하는 함수나 서비스라고 했습니다. 이 절의 도구는 이 절에서 만든 도구 흉내입니다. 바깥 서비스를 부르지 않고, 정해 둔 결과 글을 내놓는 파이썬 함수입니다. 그래서 같은 도구를 부르면 결과 글이 매번 같습니다.

# 머리글 뒤에 문의와 지금까지 부른 도구의 결과를 이어 붙여 요청 글 하나를 만듭니다
def build_request(head, question, steps):
    text = head + "\n\n문의: " + question + "\n지금까지 부른 도구와 결과:"
    if count_steps(steps, "한 쪽", "도구") == 0:
        text = text + " 없음"
    for step in steps:
        if step["한 쪽"] == "도구":
            text = text + "\n- " + step["단계"] + ": " + step["결과"]
    return text

결과 읽기 — 정의 셀이라 출력이 없습니다. 함수 build_request는 머리글과 문의, 기록을 받아 요청 글 하나를 내놓습니다. 기록에서 도구가 한 줄만 요청 글에 들어갑니다.

6. 정지 조건

5절에서는 모델에게 다음 행동을 한 번 물었습니다. 7절에서는 묻고, 고른 도구를 부르고, 그 결과를 들고 다시 묻기를 되풀이합니다. 이 되풀이를 루프(loop)라고 부르고, 한 번 도는 차례를 바퀴라고 부릅니다.

모델이 끝을 고르지 않으면 루프는 계속 돕니다. 그래서 모델이 고른 이름을 코드가 먼저 보고 멈출지 정합니다. 정지 조건(stopping condition)은 반복을 멈추는 조건입니다. 눈밭을 걷다가 울타리 앞에서 발자국이 끝나는 것과 같습니다.

다음 셀은 모델이 고른 이름을 보고 멈출 까닭을 찾는 함수입니다. 모델이 끝을 고르면 모델이 끝을 고름, 사람 확인이 필요한 도구이면 사람 확인을 내놓습니다. 이미 부른 도구를 다시 고르면 같은 도구를 다시 고름을 내놓습니다. 이 절 도구는 인자가 없어 같은 도구를 다시 부르면 같은 결과만 받기 때문입니다. 멈출 까닭이 없으면 빈 글 ""을 내놓습니다.

In [14]:
# 모델이 고른 이름을 보고 멈출 까닭을 찾습니다(멈추지 않으면 빈 글)
def stop_reason(name, steps, confirm_tools):
    if name == "끝":
        return "모델이 끝을 고름"
    if name in confirm_tools:
        return "사람 확인"
    if count_steps(steps, "단계", name) > 0:
        return "같은 도구를 다시 고름"
    return ""

결과 읽기 — 정의 셀이라 출력이 없습니다. 함수 stop_reason은 끝, 사람 확인, 다시 고름 차례로 봅니다. 이름 뒤에 in과 목록을 두면 그 이름이 목록에 있는지 봅니다. 01절 함수 count_steps로 칸 「단계」에 그 이름이 있는 줄을 세어, 0보다 크면 이미 부른 도구입니다.

다음 셀은 손으로 적은 기록 한 줄로 이 함수를 확인합니다. 기록에는 주문 조회를 이미 부른 줄 하나만 있습니다. 조건이 참이 아니면 셀을 멈추는 assert 줄로 네 경우를 확인합니다.

# 손으로 적은 기록 한 줄로 멈추는 경우 셋과 멈추지 않는 경우 하나를 확인합니다

assert stop_reason("끝", checked_steps, confirm_tools) == "모델이 끝을 고름"
assert stop_reason("환불 요청 등록", checked_steps, confirm_tools) == "사람 확인"
assert stop_reason("주문 조회", checked_steps, confirm_tools) == "같은 도구를 다시 고름"
assert stop_reason("환불 규정 확인", checked_steps, confirm_tools) == ""
print("손 확인 통과:", stop_reason("주문 조회", checked_steps, confirm_tools))
출력:

정지 조건이 없는 루프는 모델이 끝을 고를 때까지 돕니다. 모델이 무엇을 고를지는 요청을 보내 봐야 알고, 같은 요청 글에도 다른 행동을 고를 수 있습니다. 바퀴마다 요청도 하나씩 늡니다. 그래서 정지 조건 없이 자율성을 주면 드는 비용과 예측하기 어려운 정도가 함께 커질 수 있습니다. 이 절에서 센 비용은 모델 요청 수이고, 걸린 시간과 요금은 재지 않았습니다.

7주의할 점과 실무 메모

  • 도구 셋은 이 절에서 만든 도구 흉내입니다. 정해 둔 결과 글을 내놓을 뿐, 실제 주문을 조회하거나 환불을 등록하지 않습니다.
  • 두 문의와 도구 결과 글, 바퀴 한도 4와 2는 흐름을 보여 주려고 이 절에서 정한 값입니다.
  • 노트북을 실행하기 전에 노트북 밖에서 같은 요청을 다섯 번씩 보내 흔들림을 확인했습니다. 요청 여섯 가지 모두 고른 이름이 다섯 번 같았습니다. 같은 요청도 실행한 때에 따라 모델이 고르는 행동이 달라질 수 있습니다. 04절에서 환불 문의 루프를 노트북 밖에서 다섯 번 돌렸을 때는, 한 번 첫 바퀴에 환불 요청 등록을 골랐습니다.
  • 모델이 쓴 까닭 문장은 실행마다 달라 결론에 쓰지 않았습니다. 모델이 쓴 글에는 assert를 걸지 않았습니다.
  • 받은 글이 JSON 모양이 아니면 json.loads에서 셀이 멈춥니다. 이번 실행에서는 그런 글을 받지 않았습니다.
  • 같은 도구를 다시 고르면 멈추는 규칙은 이 절 도구에 인자가 없어서 정한 규칙입니다. 이번 실행에서 이 조건으로 멈춘 기록은 없었고, 손으로 적은 기록으로만 확인했습니다.
  • 노트북 9절 손 확인 셀은 모델 대신 정해 둔 선택을 씁니다. 바퀴 한도로 멈추는 코드 자리를 보이려는 셀이고, 모델이 고른 기록이 아닙니다.
  • 기록 한 번으로 가르는 01절 규칙에는 한계가 있습니다. 이 절 기록은 모델이 고른 도구를 부른 줄과 끝을 고른 멈춤 줄에만 칸 「고른 쪽」을 모델로 적습니다. 코드가 부르기 전에 멈추면, 모델이 한 번 골랐어도 워크플로우로 가려질 수 있습니다.
  • 사람 확인은 멈추기까지만 다뤘습니다. 사람이 확인한 뒤 루프를 이어 가는 장면은 실행하지 않았습니다.
  • 모델 요청은 노트북 전체에서 15번을 넘지 않고, 요금표로 어림한 예상 비용은 0.01달러 아래입니다. 예상 비용은 청구 금액이 아니며, 걸린 시간과 요금은 재지 않았습니다. 자율성에 드는 대가는 04절에서 다룹니다.
  • 교재 출력은 Linux의 Python 3.12.13으로 만들었습니다. 다른 판과 Windows·macOS에서는 이번에 실행하지 않았습니다.

8정리와 다음 절

  • 모델이 JSON 글로 다음 행동을 고르고 코드가 그 도구를 부르는 루프를 만들었습니다.
  • 도착 문의는 모델이 끝을 골라 멈췄고, 환불 문의는 코드가 사람 확인에서 멈췄습니다.
  • 바퀴 한도 2에서는 모델 요청이 두 번을 넘지 않았고, 사람 확인을 빼면 등록 도구가 불렸습니다.

9복습 문제

문제 4개 · 해설 포함

1. 이 절의 루프는 어떤 네 가지로 이루어지나요?

모델·도구·반복·정지 조건입니다. 모델은 다음 행동을 JSON 글로 고르고, 코드가 그 이름의 도구를 부릅니다. 도구 결과를 다음 요청에 넣어 되풀이하고, 정지 조건이 반복을 끝냅니다. 틀렸다면 「핵심 개념」의 「루프를 이루는 네 가지」를 다시 읽습니다.

2. 도착 문의와 환불 문의는 각각 무엇 때문에 멈췄고, 멈추기로 정한 쪽은 누구인가요?

도착 문의는 모델이 끝을 골라 멈췄고, 정한 쪽은 모델입니다. 환불 문의는 사람 확인에서 멈췄고, 정한 쪽은 코드입니다. 틀렸다면 노트북 7·8절을 다시 읽습니다.

3. 바퀴 한도를 2로 두면, 모델이 첫 바퀴에 무엇을 고르든 지켜지는 것은 무엇인가요?

모델 요청이 두 번을 넘지 않는다는 것입니다. 누가 멈추는지는 첫 두 바퀴의 선택에 달려 있습니다. 등록을 고르면 사람 확인으로, 조회와 규정 확인을 고르면 바퀴 한도로 코드가 멈춥니다. 끝을 고르면 모델이 멈춥니다. 틀렸다면 노트북 9절을 다시 읽습니다.

4. 사람 확인이 필요한 도구 목록을 비우면 무엇이 달라졌고, 이 결과로 말할 수 없는 것은 무엇인가요?

환불 요청 등록이 불렸고 모델 요청이 3에서 4로 늘었습니다. 이번 문의에서 모델이 고른 차례가 02절 코드 차례와 같았다고 해서 다른 문의에서도 같다고 말할 수는 없습니다. 틀렸다면 노트북 10절과 「주의할 점」을 다시 읽습니다.
