1학습 목표

  • 같은 조건에서 도구 설명이 선택에 미치는 영향을 측정할 수 있습니다.
  • 노트북의 실제 출력에서 도구 이름, 인자, 결과를 확인할 수 있습니다.
  • 관찰한 범위를 넘지 않고 결과를 해석할 수 있습니다.

2이 내용을 배우는 이유

좋은 설명이 선택을 돕는다는 주장을 확인하려면 설명 외의 조건을 고정해야 합니다. 공개 도구 이름과 인자 스키마, 함수 동작, 질문, 모델, temperature, 도구 순서를 같게 둡니다.

Ch20에서 ToolNode로 실행 흐름을 조립하기 전에 도구 한 개가 어떤 정보와 결과를 주고받는지 확인합니다.

3앞에서 배운 내용

03절의 세 도구를 두 묶음으로 다시 정의합니다. 모호 조건은 모두 ‘주문 정보를 찾습니다’라고 설명하고 구체 조건은 목록·단건·집계 목적을 각각 밝힙니다.

실행 파일은 labs/part5/ch19-model-tools/data/orders.csv를 사용하며 Part1 모듈을 런타임에 import하지 않습니다.

4핵심 개념

비유로 먼저 이해하기

도구 설명서는 주문서와 비슷합니다. 모델은 함수 내부를 보지 않고 이름, 설명, 선택 항목을 보고 요청합니다.

정의

모델은 함수 본문을 읽지 않습니다. 바인딩할 때 전달한 이름·설명·스키마만 보고 호출할 도구와 인자를 정합니다. 따라서 구현이 같아도 설명이 모호하면 선택 근거가 부족합니다.

모호 조건과 구체 조건의 Python 함수 이름은 다르지만 모델에게 공개되는 tool name은 동일합니다. 노트북은 same_name과 same_args가 모두 True인지 먼저 확인합니다. 함수 본문도 같은 CSV 조회와 집계를 수행합니다. 따라서 모델에게 달라지는 정보는 description입니다. 채점은 목록 질문에는 list_orders_by_status, 정확한 주문 번호 질문에는 get_order_by_id, 건수와 총액 질문에는 summarize_order_amounts를 기대합니다. 두 조건이 모두 맞았다면 이 표본에서는 차이를 관찰하지 못했다고 기록해야 하며, 모호 조건이 틀렸을 때만 관찰된 차이를 설명합니다.

도구 호출(tool call)은 구조화된 실행 요청이며 도구 메시지(ToolMessage)는 실행 결과와 호출 ID를 돌려주는 메시지입니다.

도식 읽기

모델 요청과 함수 실행 사이의 경계를 따라 읽습니다. 자율 반복은 Ch20 이후에 다룹니다.

5실행 예제

질문 3개를 조건마다 3회씩 호출합니다. 전체 tool_calls와 사용량을 보존하고, 호출이 정확히 하나일 때 이름을 기대값과 사람이 비교합니다.

빈 Python 3.12 커널에서 준비 셀부터 실행합니다. 모델 호출이 있는 절은 gpt-5.4-mini, temperature=0을 사용하며 키 값은 출력하지 않습니다.

6실험 결과 해석

질문 3개, 반복 3회, 같은 모델과 temperature를 유지하고 설명만 바꿉니다. 전체 tool_calls와 사용량을 로그로 남긴 뒤 사람이 질문별 기대 도구와 비교합니다. 같은 질문과 입력을 유지한 채 비교 대상 한 가지를 바꿉니다. 출력에 나타난 값만 근거로 삼으며, 작은 표본으로 모든 모델과 질문에 같은 결과가 난다고 단정하지 않습니다.

출력 읽기

실험 결과가 모호 9/9, 구체 9/9라면 이 실행에서는 선택 차이를 관찰하지 못한 것입니다. 이것은 설명이 필요 없다는 결론이 아닙니다. 질문에 주문 목록, 주문 번호, 건수와 총액이라는 강한 단서가 있고 인자 스키마도 서로 달라 모델이 구분했을 수 있습니다. 다른 질문이나 도구 수에서 결과가 달라질 수 있습니다. 차이를 더 조사하려면 질문 수를 늘리고 독립 실행을 반복하되, 결과를 얻기 위해 질문 문구를 조건마다 바꾸면 안 됩니다. 원시 tool_calls를 남겨야 수동 채점 오류도 다시 확인할 수 있습니다.

7주의할 점과 실무 메모

temperature 0이어도 서비스 실행이 언제나 동일하다고 가정하지 않습니다. 9회라는 작은 표본과 사용한 질문에 한정해 결과를 보고합니다.

실험은 실행 전에 채점 기준과 반복 횟수를 정합니다. 결과를 본 뒤 기대 도구를 바꾸면 선택률을 믿을 수 없습니다. 한 응답에 호출이 없거나 둘 이상이면 이 실험에서는 오답으로 처리합니다. 전체 로그에는 질문, 기대 이름, 반복 번호, 원시 호출, 토큰 사용량이 있으므로 다른 검토자가 같은 규칙으로 다시 채점할 수 있습니다. 이번 실제 실행에서 두 조건이 모두 9/9이면 ‘혼동을 재현했다’고 쓰지 않고 차이를 관찰하지 못했다고 본문과 검증 기록에 남깁니다.

설명 품질 평가는 선택률 하나로 끝나지 않습니다. 올바른 도구를 골라도 status나 order_id를 잘못 채울 수 있으므로 인자 정확도도 별도로 봅니다. 이번 채점은 도구 이름만 평가하며 인자 값은 원시 로그에서 사람이 확인합니다. 평가 항목의 범위를 명시하면 9/9를 전체 성공률로 오해하지 않습니다.

  • 도구 설명과 인자 스키마도 모델 컨텍스트를 사용합니다.
  • API 가격과 모델 동작은 달라질 수 있으므로 실행 시점의 공식 정보를 확인합니다.

8정리와 다음 절

  • description만 다른 두 조건의 실제 선택 기록을 같은 채점 기준으로 비교했습니다.
  • 관찰한 요청과 실행 결과를 구분해 기록했습니다.
  • 작은 표본의 결과를 다른 모델과 질문에 일반화하지 않습니다.

9복습 문제

문제 1. 모델은 무엇을 보고 도구를 고르나요?

바인딩된 이름·설명·인자 스키마를 봅니다.

문제 2. tool_calls가 있으면 실행도 끝났나요?

아닙니다. 프로그램이 검사하고 실행해야 합니다.

문제 3. 이 절에서 확인한 실제 출력은 무엇인가요?

질문 3개, 반복 3회, 같은 모델과 temperature를 유지하고 설명만 바꿉니다. 전체 tool_calls와 사용량을 로그로 남긴 뒤 사람이 질문별 기대 도구와 비교합니다.

문제 5. 이 실험에서 도구 순서를 고정하는 이유는 무엇인가요?

설명 외의 조건이 선택에 미치는 영향을 줄이기 위해서입니다.
