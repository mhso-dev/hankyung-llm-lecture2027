1학습 목표

  • 오류 결과를 모델이 읽을 수 있게 만들고 읽기와 쓰기 도구를 분리할 수 있습니다.
  • NOT_FOUND 오류에서 재시도보다 입력 확인이 필요한 이유를 설명할 수 있습니다.
  • 사용자 확인을 애플리케이션 상태에 기록한 뒤에만 취소 도구를 제공할 수 있습니다.

2이 내용을 배우는 이유

주문 조회 실패와 주문 취소 요청은 위험이 다릅니다. 예상 가능한 조회 실패는 모델이 다음 판단에 사용할 오류 코드로 반환하고, 상태를 바꾸는 동작은 확인 경로를 별도로 둡니다.

Ch 20에서 ToolNode로 실행 흐름을 조립하기 전에 도구 한 개가 어떤 정보와 결과를 주고받는지 확인합니다.

3앞에서 배운 내용

공개 주문 목록을 메모리에서 읽고 존재하지 않는 O999를 조회합니다. 쓰기 예제는 실제 주문을 변경하지 않고 취소 요청 상태만 구조화해 반환합니다.

실행 파일은 labs/part5/ch19-model-tools/data/orders.csv를 사용하며 Part 1 모듈을 런타임에 import하지 않습니다.

4핵심 개념

비유로 먼저 이해하기

도구 설명서는 주문서와 비슷합니다. 모델은 함수 내부를 보지 않고 이름, 설명, 선택 항목을 보고 요청합니다.

정의

예상 가능한 업무 오류는 NOT_FOUND처럼 짧고 일정한 코드와 관련 인자를 반환합니다. 쓰기 권한은 모델 인자가 아니라 애플리케이션이 기록한 사용자 확인 상태로 제어합니다.

O999가 없다는 사실은 예상 가능한 업무 결과입니다. read_order는 예외 대신 ok=False, error=NOT_FOUND, order_id=O999를 반환합니다. 취소 도구에는 confirmed 필드가 없습니다. 확인 전 available_tools에는 읽기 도구만 있습니다. 애플리케이션은 사용자가 확인한 주문 ID를 confirmed_order_ids에 기록하고, 취소 함수는 요청한 ID가 이 집합에 있는지 다시 검사합니다. 이 예제의 True는 흐름을 보여 주는 로컬 실습값이며 실제 외부 동의가 아닙니다.

도구 호출(tool call)은 구조화된 실행 요청이며 도구 메시지(ToolMessage)는 실행 결과와 호출 ID를 돌려주는 메시지입니다.

도식 읽기

{{svg:06-오류와-읽기-쓰기-분리-flow}}

읽기·쓰기 도구의 공개와 실행 권한은 앱 상태로 결정합니다. 모델이 작성한 인자가 앱의 허용 여부를 대신하지 않습니다.

코드를 읽기 전에

read_order()는 예상 가능한 ‘주문 없음’을 예외 대신 ok=False와 오류 코드가 든 사전으로 반환합니다. 호출자는 성공 결과와 업무상 미발견을 같은 반환 형식에서 구분할 수 있습니다. 반면 코드 결함이나 연결 실패까지 모두 같은 오류 코드로 바꾸면 원인을 잃으므로 예상 범위를 정해야 합니다.

쓰기 도구의 인자에는 confirmed가 없습니다. 사용자의 확인된 주문 ID는 애플리케이션 상태인 confirmed_order_ids에 저장되고, 도구 실행 시 요청 ID가 그 집합에 있는지 다시 검사합니다. 모델이 만든 문자열은 사용자 승인 증거가 될 수 없습니다.

다른 상황과 개념 경계

메일 검색과 메일 발송을 한 도구 목록에 함께 제공하면 모델의 선택 오류가 곧 외부 부작용으로 이어질 수 있습니다. 검색 단계에는 읽기 도구만 제공하고, 수신자·본문을 사람이 확인한 뒤 해당 초안 ID에 한해 발송 도구를 열 수 있습니다. 도구 공개 여부와 함수 내부의 권한 재검사를 함께 두어 한 경계가 빠져도 다른 경계가 남게 합니다.

5실행 예제

읽기 도구는 NOT_FOUND와 order_id를 반환합니다. 쓰기 도구는 모델이 정하는 confirmed 인자를 받지 않으며, 애플리케이션 확인 상태에 따라 제공 목록에 추가됩니다.

빈 Python 3.12 커널에서 준비 셀부터 실행합니다. 모델 호출이 있는 절은 gpt-5.4-mini, temperature=0을 사용하며 키 값은 출력하지 않습니다.

6일부러 실패해 보기

존재하지 않는 O999를 조회하면 ok=False와 error=NOT_FOUND가 반환됩니다. 확인 전 도구 목록에는 읽기 도구만 있으며, O101 취소를 직접 호출해도 PermissionError가 발생합니다. O101 확인 뒤에는 O101 요청만 통과하고 확인하지 않은 O103은 계속 거부됩니다.

출력 읽기

NOT_FOUND는 재시도하면 항상 해결되는 시스템 장애가 아닙니다. 먼저 주문 ID를 확인하거나 사용자에게 올바른 대상을 요청해야 합니다. 쓰기 도구 제공 여부는 모델 출력과 분리된 애플리케이션 상태가 결정합니다. 확인 전 목록에 취소 도구가 없다는 assert는 구성 실수를 찾는 작은 검사입니다. 실제 취소 API를 연결할 때는 인증된 사용자와 대상 주문의 소유 관계도 검사해야 합니다.

7주의할 점과 실무 메모

예상 가능한 업무 실패와 시스템 예외를 구분합니다. 내부 스택 추적은 운영 로그에 남기고 모델에는 다음 행동에 필요한 코드와 대상만 제공합니다.

확인 상태는 대화 문장만 보고 추측하지 않습니다. 애플리케이션의 확인 화면이나 승인 API가 남긴 신뢰 가능한 상태를 서버가 읽어야 합니다. 실습의 confirmed_order_ids={"O101"}는 이 경계를 보여 주는 고정 예시이며 실제 사용자의 승인을 대신하지 않습니다. 확인 상태는 참·거짓 하나로 저장하지 않고 확인한 주문 ID와 함께 기록해야 다른 주문에 재사용되지 않습니다. 참인 상태에서 반환하는 값도 실제 데이터베이스를 바꾸지 않는 모의 취소 요청입니다.

읽기와 쓰기를 분리해도 쓰기 함수 자체의 검증은 필요합니다. 도구 목록은 선택 가능성을 제한하고, 함수 내부 권한 검사는 최종 방어선을 제공합니다. 모델이 도구를 호출하지 않는 별도 경로에서도 같은 쓰기 API가 사용될 수 있으므로 권한 검사를 도구 설명에만 의존하면 안 됩니다.

  • 도구 설명과 인자 스키마도 모델 컨텍스트를 사용합니다.
  • API 가격과 모델 동작은 달라질 수 있으므로 실행 시점의 공식 정보를 확인합니다.

8정리와 다음 절

  • O999 조회 실패를 NOT_FOUND 오류 결과로 구조화했습니다.
  • 확인 전에는 읽기 도구만 제공하고, 애플리케이션이 O101 확인을 기록한 뒤에는 취소 도구를 제공합니다.
  • 취소 함수는 요청한 주문 ID가 애플리케이션의 확인 목록에 있는지 다시 검사합니다.

9복습 문제

문제 1. NOT_FOUND가 발생했을 때 먼저 확인할 것은 무엇인가요?

재시도 전에 주문 ID가 올바른지 확인해야 합니다.

문제 2. 취소 도구 제공 여부는 누가 결정하나요?

모델과 분리된 애플리케이션 상태가 사용자가 확인한 주문 ID를 바탕으로 결정합니다.

문제 3. 확인 전 도구 목록에는 무엇이 들어 있나요?

상태를 바꾸지 않는 읽기 도구만 들어 있습니다.

문제 4. confirmed를 모델 인자로 받지 않는 이유는 무엇인가요?

모델이 True를 생성한 사실은 사용자가 확인했다는 증거가 아니기 때문입니다.
