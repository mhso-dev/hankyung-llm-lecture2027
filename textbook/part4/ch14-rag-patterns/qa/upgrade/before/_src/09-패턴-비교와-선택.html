1학습 목표

  • 이 절을 마치면 패턴 비교와 선택의 입력과 출력을 설명할 수 있습니다.
  • 이 절을 마치면 Recall@3, 지연 시간, 토큰 사용량, 통제 비교의 역할을 코드의 입력·처리·출력으로 구분할 수 있습니다.
  • 이 절을 마치면 세 패턴의 Recall@3, 토큰, 지연 시간, 추정 비용을 함께 비교해 선택 근거를 설명할 수 있습니다.

2이 내용을 배우는 이유

패턴 이름만 보고 선택하면 호출 비용과 지연을 놓치기 쉽습니다. 같은 질문, 문서, 정답 ID, 생성 모델을 유지하고 한 번에 패턴 하나만 바꿔야 품질과 비용의 차이를 읽을 수 있습니다.

Ch9의 기본 RAG는 검색 한 번과 생성 한 번으로 구성되었습니다. Ch14에서는 질문을 바꾸거나 결과를 검사하는 단계를 추가합니다. 모든 선택은 if 문, 수치 임계값, 반복 상한에 적힌 규칙으로 실행합니다. 모델이 다음 행동을 자율적으로 결정하는 에이전트는 아직 사용하지 않습니다.

3앞에서 배운 내용

Ch11에서 정답 문서 ID와 Recall을 분리해 기록했습니다. Ch12에서는 core-documents.json의 문서 12건과 core-queries.json의 질문 8건으로 검색 설정을 비교했습니다. 이 절은 두 파일의 내용을 챕터 폴더에 복제해 같은 문서와 정답을 사용합니다. 전체 제공 PDF와 30문항을 쓰지 않는 축소 표본입니다. 02절의 Multi-Query와 05절의 HyDE를 같은 질문·문서 조건으로 다시 실행해 기준선과 비교합니다.

4핵심 개념

Recall@3

Recall@3
통제 비교는 비교하려는 조건 외의 입력을 같게 유지하는 실험입니다. 이 절은 Ch12 문서 12건 중 Ch11 형식의 질문 세 건을 고정합니다. 기준선, Multi-Query, HyDE를 각각 실행하고 Recall@3, 전체 생성 토큰, 벽시계 시간을 기록합니다. 각 패턴은 최종 답 생성까지 포함합니다.
흐름을 정하는 규칙
같은 세 질문·문서·정답·모델을 유지하고 패턴만 바꿉니다. 모든 패턴은 상위 세 문서와 최종 답까지 측정하며 Multi-Query 후보는 RRF로 정렬합니다.

호출 표기와 실행 시점

패턴 비교는 질문·문서·정답 ID·모델·상위 k를 고정하고 바꾸려는 검색 패턴만 달리합니다. 각 행에는 검색 후보, 정답 순위, 생성 사용량, 지연을 같은 열로 기록해 질문별 차이와 전체 요약을 함께 읽습니다.

다른 상황에 적용

새로운 고객지원 데이터에서도 기준선, Multi-Query, HyDE를 같은 실패 질문 묶음에 적용할 수 있습니다. 평균만 보지 말고 어떤 질문 유형에서 순위가 올랐고 다른 질문에서 내려갔는지 사례별로 확인합니다.

비교와 경계

패턴 선택은 기능 목록을 고르는 일이 아니라 실패 원인에 맞는 개입을 고르는 일입니다. 표현 불일치에는 Multi-Query, 복합 요구에는 분해, 배경 규칙 부족에는 Step-back이 후보입니다. 이 실험의 세 질문 결과를 전체 서비스 성능으로 일반화할 수 없습니다.

도식의 상자를 위에서 아래로 읽습니다. 나란한 상자는 분기하거나 따로 실행한 뒤 다시 합치는 처리입니다. 생성한 질문, 가상 문서, 평가 점수는 검색을 돕는 중간 값이며 출처로 인용하지 않습니다.

6실험 결과 해석

축소 표본 세 건에서 기준선 Recall@3은 0.667, 평균 129토큰, 약 905.4ms, 추정 0.000206달러였습니다. RRF로 후보를 합친 Multi-Query는 Recall@3 0.667, 평균 188토큰, 약 1863.2ms, 추정 0.000379달러였습니다. HyDE는 Recall@3 1.0, 평균 197.7토큰, 약 1945.0ms, 추정 0.000414달러였습니다. Multi-Query는 비용이 늘었지만 Recall이 개선되지 않았습니다.

질문 세 건, 한 번 실행한 결과라 분산이나 통계적 유의성을 알 수 없습니다. API 응답 시간은 네트워크 상태에 영향을 받습니다. 이 표는 수업용 선택 연습이며 운영 환경의 패턴 우열을 확정하지 않습니다.

코사인 유사도는 질문과 문서 벡터가 같은 방향을 가리키는 정도입니다. 이 값은 정답 확률이 아니며 데이터와 임베딩 모델이 바뀌면 임계값도 다시 정해야 합니다.

7주의할 점과 실무 메모

  • 운영 전에 확인합니다. 질문 세 건의 단일 실행으로 패턴의 우열을 정하지 말고, 운영 데이터에서 반복 실행해 분산과 답변 품질을 추가로 측정해야 합니다.
  • 기록할 항목을 정합니다. 검색 품질, 답변 품질, 토큰, 지연 시간, 비용을 분리해 기록해야 한 지표의 개선을 전체 품질로 오해하지 않습니다.

8정리와 다음 절

  • 이 축소 표본에서는 HyDE의 Recall이 높았지만 토큰·지연·추정 비용도 가장 컸습니다.
  • 세 질문을 한 번 실행한 값이므로 운영 환경의 패턴 우열로 일반화할 수 없습니다.

9복습 문제

문제 4개 · 해설 포함

1. 패턴 비교와 선택의 입력과 출력은 무엇입니까?

같은 질문·정답·문서와 패턴 이름을 입력하면 검색 후보, 답, 순위, 토큰, 지연 시간, 추정 비용이 담긴 실행 행을 출력합니다.

2. 이 절의 실제 출력은 패턴 선택에 어떤 근거를 줍니까?

Multi-Query는 기준선과 Recall이 같으면서 토큰·시간·비용이 늘어 이 표본에서는 이득이 없었습니다.

3. 코드에서 호출 수나 후보 수를 제한하는 규칙은 무엇입니까?

모든 패턴은 상위 세 문서를 사용하고 Multi-Query 후보는 RRF로 정렬합니다.

4. 생성한 중간 문장을 최종 답의 출처로 쓰면 안 되는 이유를 설명하세요.

모델이 만든 문장은 원문 자료에서 확인한 사실이 아닙니다. 실제 검색된 문서의 ID와 본문만 근거로 인용합니다.
