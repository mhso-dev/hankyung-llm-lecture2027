
===== textbook/part4/ch13-langgraph-basics/_src/01-StateGraph와-노드-엣지.html =====
1
학습 목표
StateGraph의 상태, 노드, 엣지를 코드에서 구분할 수 있습니다.
START와 END를 포함한 순차 그래프를 컴파일하고 실행할 수 있습니다.
실행 흔적과 Mermaid 문자열을 읽어 실제 실행 순서를 확인할 수 있습니다.
2
이 내용을 배우는 이유
Part 3에서 만든 RAG는 문서 읽기, 검색, 병합, 재정렬, 생성 함수를 차례로 호출했습니다. 단계가 두세 개일 때는 함수 나열도 읽을 수 있습니다. 조건에 따라 건너뛰거나 되돌아가는 단계가 생기면 호출 순서가 여러 곳에 흩어집니다. LangGraph는 상태와 실행 순서를 하나의 그래프로 선언해 이 문제를 다룹니다.
이번 절의 질문은 “파이썬 함수 나열을 상태 그래프로 옮기면 실행 순서를 어떻게 읽을 수 있을까요?”입니다. 노트북 출력과 그래프 그림을 함께 읽어 답합니다.
3
앞에서 배운 내용
Ch12의 통합 실습은 질문을 받고 검색 결과와 출처를 만든 뒤 답변을 생성했습니다. 이번 절은 그 처리 단계에서 모델 호출을 제외하고, 질문 정리와 검색어 작성이라는 두 함수를 그래프에 배치합니다. 앞 노트북의 변수에는 의존하지 않습니다.
각 노트북은 Python 3.12 새 커널에서 독립 실행되며 이전 절의 메모리나 개인 경로를 사용하지 않습니다.
4
핵심 개념
쉬운 예
지하철 노선도에서 역은 작업이고 선은 이동 순서입니다.
정의
LangGraph의 상태(State)는 그래프 실행 동안 노드들이 함께 읽고 갱신하는 데이터입니다. 노드(node)는 상태를 읽어 일부 값을 반환하는 함수이고, 엣지(edge)는 다음 노드를 정하는 연결입니다. StateGraph는 이 세 요소를 모아 실행 가능한 그래프를 만드는 빌더입니다. START는 입력이 들어오는 가상 시작점이고 END는 더 실행할 노드가 없음을 나타내는 가상 끝점입니다. compile()은 선언한 노드 이름과 연결을 확인하고 invoke()할 수 있는 실행 객체를 반환합니다.
코드에서 읽는 순서
코드는 상태 형식을 먼저 선언한 뒤 노드 함수를 정의합니다. 각 함수의 state 매개변수는 현재 상태를 읽고, 반환 딕셔너리는 다음 상태에 반영할 값만 담습니다. 이어서 add_node로 이름과 함수를 연결하고 add_edge로 START부터 END까지의 순서를 적습니다. compile() 뒤 invoke()에 입력 상태를 전달하면 엣지를 따라 노드가 실행됩니다. trace 값과 Mermaid의 화살표를 함께 보면 파이썬 함수 이름, 그래프 노드 이름, 실제 실행 순서를 하나씩 대응할 수 있습니다.
도식 읽기
{{svg:01-흐름}}
도식은 위에서 아래로 읽습니다. 입력 상태에서 normalize와 make_query를 차례로 지나 최종 상태로 이동합니다. 두 화살표는 add_edge로 선언한 고정 순서입니다. 초록은 자료, 파랑은 코드로 정한 처리, 보라는 모델 계산, 노랑은 측정·평가, 빨강은 오류·격리를 나타냅니다. 노트북의 Mermaid 출력에서도 같은 노드 이름을 찾아 선언한 구조를 대조합니다.
5
실행 예제
첫 셀에서 LangGraph 1.2.11을 준비한 뒤 상태 형식과 두 노드를 정의합니다. 두 질문으로 그래프를 실행해 trace가 normalize와 make_query 순서로 유지되는지 비교합니다. 마지막 Mermaid 출력에서는 START부터 END까지 이어지는 고정 엣지를 확인합니다.
확인할 점
— 파이썬 함수 나열을 상태 그래프로 옮기면 실행 순서를 어떻게 읽을 수 있을까요? 출력에 나타난 상태 필드와 경로를 근거로 답해 봅니다.
6
실험 결과 해석
실행 결과의 trace에는 normalize와 make_query가 차례로 남습니다. Mermaid 출력에서도 START에서 normalize, make_query, END로 이어지는 화살표가 나타납니다. 노드를 등록한 순서가 실행 순서를 정하는 것이 아니라 add_edge로 선언한 연결이 실행 순서를 정합니다.
질문을 바꾼 두 실행에서 검색어는 달라졌지만 trace는 같은 두 노드를 기록했습니다. 고정 엣지가 입력 내용과 무관하게 같은 실행 순서를 만든 결과입니다.
이번 실행은 엣지로 고정한 두 노드의 순서만 확인했습니다. 노드가 늘어나거나 분기가 생긴 그래프의 실행 특성은 뒤 절에서 따로 확인합니다.
7
주의할 점과 실무 메모
노드는 전체 상태를 복사해 반환하지 않고 바꿀 키만 반환할 수 있습니다.
compile() 전의 객체는 설계도이며 compile() 결과가 실행 객체입니다.
이 절의 그래프는 모델이 경로를 정하지 않습니다. 코드로 적은 고정 엣지가 경로를 정합니다.
8
정리와 다음 절
두 질문 모두 normalize와 make_query를 같은 순서로 실행했습니다.
노드는 상태 갱신을 반환하고 엣지는 실행 순서를 정했습니다.
Mermaid에서 START부터 END까지의 고정 연결을 확인했습니다.
다음 학습과 이어지는 지점
— 다음 절에서는 각 노드가 반환한 일부 값이 기존 상태에 어떻게 반영되는지 확인합니다.

===== textbook/part4/ch13-langgraph-basics/_src/02-State-갱신.html =====
1
학습 목표
상태 스키마가 노드 입력과 출력의 키·값 형식을 정의하는 방식을 설명할 수 있습니다.
기본 덮어쓰기와 리듀서 누적의 차이를 실행 결과로 비교할 수 있습니다.
노드가 일부 키만 반환하는 갱신 방식을 적용할 수 있습니다.
2
이 내용을 배우는 이유
검색 단계는 documents를 만들고 생성 단계는 answer를 만듭니다. 모든 함수가 전체 딕셔너리를 다시 만들면 빠진 키나 오래된 값을 섞기 쉽습니다. LangGraph의 노드는 자신이 맡은 키의 갱신값만 반환합니다. 같은 키에 여러 갱신이 모일 때는 리듀서가 합치는 규칙을 담당합니다.
이번 절의 질문은 “노드가 같은 상태 키를 여러 번 반환하면 값은 덮어쓸까요, 누적할까요?”입니다. 노트북 출력과 그래프 그림을 함께 읽어 답합니다.
3
앞에서 배운 내용
앞 절에서 StateGraph, 노드, 엣지, compile(), invoke()를 사용했습니다. 이번 절도 같은 순차 그래프를 사용하지만 상태 키별 갱신 규칙에 초점을 맞춥니다.
각 노트북은 Python 3.12 새 커널에서 독립 실행되며 이전 절의 메모리나 개인 경로를 사용하지 않습니다.
4
핵심 개념
쉬운 예
공용 화이트보드의 칸마다 쓰기 규칙이 다르다고 생각해 봅니다.
정의
query 키는 새 값으로 교체하고 log 키는 새 항목을 뒤에 붙이도록 선언합니다. TypedDict는 상태에 어떤 키와 값 형식이 있는지 표현합니다. 리듀서(reducer)는 한 상태 키의 기존 값과 새 갱신값을 받아 최종 값을 만드는 함수입니다. Annotated[list[str], operator.add]는 두 목록을 이어 붙이도록 지정하므로 각 노드가 반환한 목록이 누적됩니다. 리듀서가 없는 키는 기본적으로 새 값이 기존 값을 덮어씁니다.
코드에서 읽는 순서
UpdateState에서 query에는 리듀서가 없고 log에는 operator.add가 붙어 있습니다. normalize와 expand는 모두 두 키를 갱신하지만 처리 방식은 키 선언에 따라 달라집니다. query는 두 번째 노드가 반환한 값으로 교체되고 log는 입력의 ['input']과 두 노드의 새 목록이 이어집니다. 이 구조에서는 각 노드가 이전 log 전체를 복사할 필요가 없습니다. 새 기록만 목록으로 반환해야 중복 없이 누적됩니다.
도식 읽기
{{svg:02-흐름}}
도식은 위에서 아래로 읽습니다. normalize와 expand가 같은 query 키를 차례로 갱신하고 log 키에는 두 기록이 누적됩니다. query와 log의 결과가 서로 다른 갱신 규칙을 보여 줍니다. 초록은 자료, 파랑은 코드로 정한 처리, 보라는 모델 계산, 노랑은 측정·평가, 빨강은 오류·격리를 나타냅니다. 노트북의 Mermaid 출력에서도 같은 노드 이름을 찾아 선언한 구조를 대조합니다.
5
실행 예제
UpdateState의 query와 log 키를 선언하고 두 갱신 노드를 연결합니다. 실행 결과에서 query가 마지막 문자열로 교체되고 log는 세 기록을 이어 붙였는지 확인합니다. 입력 log를 바꾼 비교 실행으로 리듀서가 기존 목록을 보존하는지도 살펴봅니다.
확인할 점
— 노드가 같은 상태 키를 여러 번 반환하면 값은 덮어쓸까요, 누적할까요? 출력에 나타난 상태 필드와 경로를 근거로 답해 봅니다.
6
실험 결과 해석
첫 노드는 query를 '도서 대출 기간'으로 바꾸고 log에 normalize를 보냅니다. 둘째 노드는 query를 '도서 대출 기간 정책'으로 다시 바꾸고 log에 expand를 보냅니다. 최종 query에는 마지막 값만 남지만 log에는 두 항목이 모두 남습니다. 키마다 규칙이 독립적으로 적용된다는 증거입니다.
두 번째 입력에 넣은 input 기록까지 유지되어 최종 log에는 세 항목이 남았습니다. 반면 query에는 expand가 만든 마지막 문자열 하나만 남았습니다.
이번 실행은 두 노드가 순서대로 한 상태를 갱신하는 경우만 확인했습니다. 여러 노드가 동시에 같은 키를 갱신하는 경우에는 해당 키의 리듀서 규칙을 추가로 검토해야 합니다.
7
주의할 점과 실무 메모
리듀서는 상태 전체가 아니라 Annotated로 표시한 키 하나에 적용됩니다.
목록을 누적할 때 노드가 기존 목록을 다시 포함하면 항목이 중복될 수 있습니다.
동시에 실행되는 노드가 같은 비리듀서 키를 갱신하면 충돌이 발생할 수 있으므로 병렬 구조에서는 합치는 규칙을 먼저 정합니다.
8
정리와 다음 절
query 키는 마지막 값으로 교체됐습니다.
log 키는 operator.add 리듀서로 세 기록을 누적했습니다.
노드는 자신이 바꿀 키와 새 값만 반환했습니다.
다음 학습과 이어지는 지점

1
학습 목표
조건 함수와 작업 노드의 역할을 구분할 수 있습니다.

이 내용을 배우는 이유
RAG에서는 검색 결과가 충분할 때 답을 만들고 부족할 때 추가 자료를 요청해야 합니다. if문을 호출 코드 여러 곳에 두면 경로를 한눈에 보기 어렵습니다. 조건부 엣지는 상태를 읽는 조건 함수를 그래프의 연결 규칙으로 등록합니다.
이번 절의 질문은 “검색 점수가 기준을 넘는지에 따라 답변 생성과 추가 자료 요청 중 어느 노드로 이동하게 할까요?”입니다. 노트북 출력과 그래프 그림을 함께 읽어 답합니다.
3
앞에서 배운 내용

각 노트북은 Python 3.12 새 커널에서 독립 실행되며 이전 절의 메모리나 개인 경로를 사용하지 않습니다.
4
핵심 개념
쉬운 예
택배 분류대는 송장 값을 읽고 상자를 서로 다른 컨베이어로 보냅니다.
정의
조건부 엣지(conditional edge)는 한 노드가 끝난 뒤 상태를 읽어 다음 노드 이름을 반환하는 연결입니다. add_conditional_edges(source, path, path_map)는 source 뒤에서 path 함수를 호출하고 그 반환값을 실제 노드 이름으로 대응시킵니다. Literal 반환형이나 path_map을 적으면 시각화할 때도 가능한 목적지가 분명하게 표시됩니다.
코드에서 읽는 순서
inspect_score는 route에 checked를 기록하고 실행을 마칩니다. 그 다음 choose 함수가 같은 상태의 rerank_score를 읽습니다. 점수가 0.7 이상이면 generate라는 노드 이름을, 미만이면 request_more를 반환합니다. add_conditional_edges는 이 반환값을 실제 목적지와 연결합니다. 두 목적지 노드는 모두 END로 이어지므로 한 입력에서 두 노드가 함께 실행되지 않습니다. 점수 하나만 바꾼 두 출력을 비교하면 분기 기준과 선택 결과를 분리해 읽을 수 있습니다.
도식 읽기
{{svg:03-흐름}}
도식은 위에서 아래로 읽습니다. inspect_score 뒤의 화살표가 generate와 request_more로 갈라집니다. 0.7이라는 코드 기준에 따라 두 목적지 중 하나만 실행됩니다. 초록은 자료, 파랑은 코드로 정한 처리, 보라는 모델 계산, 노랑은 측정·평가, 빨강은 오류·격리를 나타냅니다. 노트북의 Mermaid 출력에서도 같은 노드 이름을 찾아 선언한 구조를 대조합니다.
5
실행 예제
점수를 기록하는 노드와 목적지를 고르는 조건 함수를 정의합니다. 0.82와 0.41을 각각 입력해 generate와 request_more 중 하나만 실행되는지 확인합니다. Mermaid 출력에서는 inspect_score 뒤에 두 경로가 선언됐는지 대조합니다.
확인할 점
— 검색 점수가 기준을 넘는지에 따라 답변 생성과 추가 자료 요청 중 어느 노드로 이동하게 할까요? 출력에 나타난 상태 필드와 경로를 근거로 답해 봅니다.
6

점수 0.82는 generate 경로를 지나 '근거로 답변 생성'을 반환합니다. 점수 0.41은 request_more 경로를 지나 '추가 자료 요청'을 반환합니다. 같은 그래프와 같은 임계값을 사용하고 점수 하나만 바꾸었으므로 경로 차이는 조건 함수의 비교 결과에서 생겼습니다.
두 최종 상태의 route와 answer가 함께 달라졌습니다. 조건 함수의 반환값이 실제 목적지 노드 실행으로 이어졌음을 두 필드로 확인했습니다.

정의
팬아웃(fan out)은 한 흐름을 여러 작업으로 나누는 구조입니다. Send(node, arg)는 실행할 노드 이름과 그 실행에만 전달할 상태를 담습니다. 조건 함수가 Send 목록을 반환하면 항목 수만큼 노드 실행이 만들어집니다. 여러 실행이 같은 results 키를 갱신하므로 operator.add 리듀서가 결과 목록을 합칩니다.

정의
Command(update=..., goto=...)는 상태에 적용할 갱신과 다음에 실행할 노드를 함께 담습니다. Command[Literal['generate', 'request_more']] 반환형은 그래프 시각화 도구가 가능한 목적지를 표시하게 합니다. update는 일반 노드 반환 딕셔너리와 같은 방식으로 리듀서의 적용을 받습니다.
코드에서 읽는 순서
route 함수는 score를 한 번 비교해 enough 값을 만듭니다. 그 값으로 decision 갱신값과 goto 목적지를 동시에 선택합니다. 반환형의 Literal은 generate와 request_more 두 목적지만 가능하다는 정보를 제공합니다. 각 목적지 노드는 answer만 갱신하고 END로 이어집니다. 최종 상태에서 decision과 answer를 함께 보면 판단 기록과 실제 이동이 일치했는지 확인할 수 있습니다. 이동만 필요할 때는 조건부 엣지, 갱신도 함께 남길 때는 Command라는 기준으로 구분합니다.

6
실험 결과 해석
점수 0.82에서는 decision이 sufficient로 갱신되고 generate로 이동합니다. 점수 0.41에서는 decision이 insufficient로 갱신되고 request_more로 이동합니다. 최종 상태에는 경로뿐 아니라 판단 결과가 함께 남습니다.
두 점수에서 decision과 answer의 조합이 각각 sufficient·생성, insufficient·추가 확인으로 맞았습니다. update와 goto가 같은 판단에서 만들어진 결과입니다.
