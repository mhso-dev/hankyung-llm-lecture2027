===== textbook/part4/ch15-evaluation-advanced/_src/02-4대-RAG-평가자.html =====
1
학습 목표
정답 일치도(Correctness)·답변 관련성(Relevance)·근거 충실도(Groundedness)·검색 관련성(Retrieval relevance)의 비교 대상을 설명할 수 있습니다.
정답 답변이 필요한 평가자와 필요하지 않은 평가자를 구분할 수 있습니다.
코드 규칙과 평가 모델(LLM judge)의 역할을 함께 설계할 수 있습니다.
2
이 내용을 배우는 이유
RAG 답변이 좋다는 한 문장에는 서로 다른 네 질문이 들어 있습니다. 답이 정답과 맞는지, 사용자의 질문에 직접 답하는지, 검색 문서가 답을 뒷받침하는지, 검색 문서 자체가 질문과 관련 있는지를 각각 확인해야 원인을 찾을 수 있습니다. 네 점수를 하나로 합치기 전에 각 점수가 비교하는 두 대상을 확인해야 합니다.
3
앞에서 배운 내용
앞 절의 세 레코드에는 질문, 검색된 문서 본문, 실제 응답이 있습니다. Ch11의
는 검색 정답 문서 ID입니다. 이것은 정답 답변 문장과 다르므로 Correctness의 reference answer로 그대로 사용할 수 없습니다.
4
핵심 개념
쉬운 예
한 답변을 네 방향에서 비추는 손전등을 떠올려 봅니다. 정답과 같은지, 질문을 직접 다루는지, 문서가 주장을 뒷받침하는지, 가져온 문서가 질문에 필요한지를 각각 비추면 어두운 지점이 달라집니다.
정의
정답 일치도(Correctness)는 응답과 정답 답변을 비교하므로 정답 답변이 필요합니다. 답변 관련성(Relevance)은 응답이 질문을 직접 다루는지 비교합니다. 근거 충실도(Groundedness 또는 faithfulness)는 응답의 주장이 검색 문서로 뒷받침되는지 봅니다. 검색 관련성(Retrieval relevance)은 검색 문서가 질문에 필요한 내용을 담는지 봅니다. 뒤의 세 평가는 정답 답변 없이 수행할 수 있습니다. 코드 평가자는 출처 표기·JSON 형식처럼 명확한 조건에 적합하고, 평가 모델(LLM judge)은 의미가 같은 표현이나 응답의 일부 주장만 문서로 확인되는 경우를 판정할 때 사용합니다.
도식 읽기
{{svg:02-평가-흐름}}
네 상자는 평가 이름과 비교 대상을 짝지어 보여 줍니다. Correctness만 정답 답변이 필요하며, 나머지는 질문·응답·전달 문서 가운데 표시된 두 대상을 비교합니다.
5
실행 예제
노트북은 평가자별 입력 필요 여부를 표로 만들고, Q002 응답에 네 평가자를 적용합니다. 제공된 정답 답변은 학습용 작성자 기준이며 사람 검토 라벨이 아닙니다. 코드 평가자는 출처 ID가 응답에 있는지 확인하고, 단어 집합 겹침은 평가 구조를 보여 주는 교육용 근사값으로만 사용합니다. 실제 평가 모델 원문은 준비 단계에서 고정한
결과를 읽습니다.
확인할 점
— 네 평가자의 비교 대상, Q002의 교육용 근사값 세 개와 실제 근거 충실도 평가 모델 값 하나를 구분합니다.
6
실험 결과 해석
Q002에서 실제 근거 충실도 평가 모델은 1을 반환했습니다. 작성자 기준 답변과 응답의 단어 겹침은 0.667, 질문과 응답은 0.5, 질문과 검색 문서는 0.5였습니다. 세 겹침 값은 계산 절차를 보여 주는 교육용 근사값이며 LangSmith 평가 결과로 해석하지 않습니다. 실제 의미 평가로 실행한 값은 근거 충실도 평가 모델 하나입니다.
7
주의할 점과 실무 메모
Correctness의 reference answer와 검색용 gold document ID를 혼동하지 않습니다.
단어 겹침 점수는 문장의 의미가 같은지 판정하지 못하므로 운영 품질 점수로 사용하지 않습니다.
네 평가자 중 하나의 점수만 높아도 전체 답변이 좋다고 결론 내릴 수 없습니다.
8
정리와 다음 절
네 평가자는 서로 다른 두 대상을 비교합니다.
Correctness만 정답 답변이 필요하고 gold 문서 ID로 대신할 수 없습니다.
코드 근사값과 실제 LLM judge 결과를 구분해 기록했습니다.
다음 학습과 이어지는 지점
— 다음 절에서는 같은 응답도 평가 모델 프롬프트와 후보 순서에 따라 판정이 달라질 수 있는지 확인합니다.

1
학습 목표
평가 모델(LLM judge)·프롬프트·온도·버전을 한 평가 실행에 고정할 수 있습니다.
위치·장황함·자기 선호 편향을 구분할 수 있습니다.
후보 순서를 바꾼 쌍대 비교로 위치 편향 신호를 확인할 수 있습니다.
2
이 내용을 배우는 이유
평가 모델(LLM judge)도 언어 모델이므로 같은 품질을 항상 같은 점수로 판정하지 않습니다. 앞에 놓인 후보, 더 긴 답, 평가 모델과 비슷한 말투를 선호할 수 있습니다. 평가 대상 모델을 고정했더라도 평가 모델 조건이 바뀌면 점수 변화가 애플리케이션 변화인지 평가자 변화인지 구분할 수 없습니다.
3
앞에서 배운 내용
앞 절은 네 평가자의 입력을 나누었습니다. 이 절은 의미 판단이 필요한 근거 충실도(Groundedness)를 골라 평가자 자체를 실험합니다. 실행용 모델은
로 기록하지만 과정의 운영 평가 모델 선택은
로 유지합니다.
4
핵심 개념
쉬운 예
두 음식을 비교할 때 접시 위치를 바꾸었는데 선택도 함께 바뀐다면 맛 이외의 조건이 판정에 영향을 준 것입니다. 평가 모델도 후보 순서와 답변 길이에 영향을 받을 수 있어 순서 교환 검사가 필요합니다.
정의
평가 모델(LLM judge) 사양에는 모델 이름, 제공자(provider), 온도, 프롬프트 전문 또는 해시, 프롬프트 버전, 출력 스키마, 평가 데이터 지문을 포함합니다. 위치 편향은 먼저 제시된 답을 선호하는 경향이고, 장황함 편향은 더 긴 답을 더 좋게 평가하는 경향입니다. 자기 선호는 평가 모델 계열과 비슷한 표현이나 출력 스타일에 유리한 판정을 내릴 가능성입니다. 후보 A와 B의 순서를 바꾸어 두 번 평가하고 승자가 뒤집히는지 기록하면 위치 민감도를 확인할 수 있습니다.

같은 후보 A와 B를 A→B, B→A 순서로 각각 평가 모델에 전달합니다. 평가 모델이 고른 위치를 원래 후보 ID로 변환한 뒤 두 실행이 같은 후보를 골랐는지 비교합니다.

===== textbook/part4/ch15-evaluation-advanced/_src/05-로컬-트레이싱과-지연.html =====
1
학습 목표
질문 재작성·검색·리랭킹·생성을 하위 실행(child run)으로 기록할 수 있습니다.
첫 토큰 도착 시간(TTFT)과 전체 지연(total latency)을 분리해 계산할 수 있습니다.
캐시 읽기(cache read)와 캐시 생성(cache creation) 토큰을 별도 필드로 보존할 수 있습니다.
2
이 내용을 배우는 이유
최종 답과 전체 시간만 남기면 어느 단계가 느렸는지, 비용이 어디서 생겼는지 알 수 없습니다. 검색이 늦었는지 생성 첫 토큰이 늦었는지 구분하려면 단계별 시작·종료 시각과 생성의 첫 토큰 시각을 기록해야 합니다. 캐시 사용량도 읽은 토큰과 새로 만든 토큰을 합치면 비용 변화를 설명하기 어렵습니다.
3
앞에서 배운 내용
앞 절에서 평가 대상과 평가 모델 결과를 레코드로 묶었습니다. 이제 같은 레코드에 실행 경로를 추가합니다. LangSmith 클라우드 키가 없으므로 기본 실습은 표준 JSON 로컬 실행 추적이며, 클라우드 업로드는 선택 확장으로만 안내합니다.
4
핵심 개념
쉬운 예
택배가 늦었을 때 전체 배송 시간만 보면 창고, 간선 운송, 지역 배송 중 어디가 늦었는지 알 수 없습니다. 실행 추적도 재작성·검색·리랭킹·생성 구간을 따로 기록해 지연의 위치를 찾습니다.
정의
실행 추적(trace)은 한 요청의 전체 실행 기록이고 하위 실행(child run)은 그 안의 단계별 기록입니다. 첫 토큰 도착 시간(TTFT, time to first token)은 생성 시작부터 첫 토큰 도착까지의 시간입니다. 전체 지연(total latency)은 요청 시작부터 최종 응답 종료까지의 시간입니다. 스트리밍하지 않은 호출에는 첫 토큰 이벤트가 없으므로 TTFT를 추정해 넣지 않고
로 남깁니다. 사용량은 input·output·cache_read·cache_creation 토큰을 구분합니다.
도식 읽기
{{svg:05-평가-흐름}}
호출 시작, 첫 텍스트 도착, 마지막 응답 완료 시각으로 TTFT와 total을 각각 계산합니다. 입력·출력·캐시 사용량은 시간선 아래에서 서로 다른 필드로 기록합니다.
5
실행 예제
노트북은 재작성 12ms, 검색 31ms, 리랭킹 18ms, 생성 240ms인 로컬 실행 추적을 만듭니다. 생성 시작 후 85ms에 첫 토큰이 도착하도록 기록하고 첫 토큰 도착 시간 85ms, 전체 지연 301ms를 계산합니다. 캐시 읽기 420개의 토큰과 캐시 생성 80개의 토큰도 분리합니다. 이 숫자는 계측 구조를 학습하기 위한 고정 실습값이며 실제 API 실행 추적으로 가장하지 않습니다.
확인할 점
— 하위 실행 네 구간, 첫 토큰 도착 시간 85ms, 전체 지연 301ms와 캐시 읽기·생성 토큰을 확인합니다.
6
실험 결과 해석
고정 로컬 실행 추적에서 생성은 61ms에 시작했고 첫 텍스트는 146ms에 도착하여 첫 토큰 도착 시간은 85ms였습니다. 전체 요청은 0ms부터 301ms까지여서 전체 지연은 301ms였습니다. 캐시 읽기 420개의 토큰과 캐시 생성 80개의 토큰을 분리해 저장했습니다. 실제 LangSmith 클라우드 실행 추적 업로드는 수행하지 않았습니다.
7
주의할 점과 실무 메모
TTFT는 스트리밍의 첫 토큰 이벤트가 있을 때만 계산합니다.
서버 처리 시간과 네트워크 왕복 시간이 함께 포함될 수 있으므로 측정 위치를 기록합니다.
LangSmith 클라우드에서는 비밀 키나 개인정보를 trace 입력에 넣지 않도록 전송 전 마스킹 정책을 적용합니다.
8
정리와 다음 절
실행 추적은 RAG 단계를 하위 실행으로 나눕니다.
첫 토큰 도착 시간 85ms와 전체 지연 301ms는 시작점과 끝점이 다릅니다.
캐시 읽기와 생성 토큰을 별도 필드로 보존했습니다.
