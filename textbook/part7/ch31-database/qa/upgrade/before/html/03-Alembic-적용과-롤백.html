1학습 목표

  • Alembic 리비전 파일이 스키마 변경 순서를 기록하는 방법을 설명할 수 있습니다.
  • `upgrade head`와 `downgrade base`로 표의 생성과 제거를 실행할 수 있습니다.
  • 카탈로그 조회로 적용·제거·재적용 상태를 확인할 수 있습니다.

2이 내용을 배우는 이유

코드 배포에서 모델 필드를 추가해도 이미 운영 중인 데이터베이스 표는 자동으로 바뀌지 않습니다. 코드와 스키마 버전이 어긋나면 요청이 시작된 뒤에야 없는 열이나 표 오류가 나타납니다. 이 절에서는 변경 파일을 버전 기록으로 남기고 적용과 롤백을 실제 카탈로그 조회로 확인합니다.

3앞에서 배운 내용

Ch4에서 `CREATE TABLE`을 실행했고 앞 절에서는 트랜잭션 경계를 정했습니다. Alembic은 이 DDL 변경의 순서와 현재 적용 위치를 파일과 버전 표로 관리합니다.

4핵심 개념

구체적인 상황

건물 도면을 지우고 매번 새로 그리면 어느 공사에서 문제가 생겼는지 알기 어렵습니다.

정의

변경 도면에 번호를 붙이고 순서대로 적용하면 현재 상태와 되돌릴 지점을 확인할 수 있습니다. 마이그레이션(migration)은 데이터베이스 구조 변경을 순서가 있는 코드로 기록하는 작업입니다. 리비전(revision)은 한 변경의 식별자이며 `down_revision`은 바로 앞 변경을 가리킵니다. `upgrade()`는 앞으로 적용할 DDL을, `downgrade()`는 되돌릴 DDL을 작성합니다. 자동 생성은 모델과 데이터베이스의 차이를 초안으로 만들 뿐이므로, 데이터 손실 가능성과 제약 조건을 사람이 읽어야 합니다.

이 절의 새 용어 — 마이그레이션, revision, upgrade, downgrade

운영에서 경계를 정하는 방법

배포 순서는 새 코드와 이전 코드가 잠시 함께 실행될 수 있다는 전제에서 정합니다. 새 열을 바로 필수로 만들기보다 먼저 NULL을 허용해 추가하고, 새 코드가 값을 쓰게 한 뒤 기존 행을 채우고, 마지막 배포에서 제약을 강화하는 방식이 안전할 수 있습니다. 이를 확장과 축소 패턴이라고 부릅니다. 롤백 파일도 작성 가능하다는 사실과 운영에서 안전하게 실행 가능하다는 사실은 다릅니다. 열을 삭제한 뒤 downgrade로 같은 이름의 열을 다시 만들더라도 원래 행 값은 돌아오지 않습니다. 큰 표의 인덱스 생성은 오랜 잠금이나 많은 I/O를 만들 수 있으므로 PostgreSQL 버전과 `CREATE INDEX CONCURRENTLY` 사용 조건을 따로 검토합니다. CI에서는 빈 데이터베이스에 처음부터 head까지 적용하는 경로와, 현재 운영 리비전에서 다음 리비전으로 이동하는 경로를 모두 시험합니다. 배포 기록에는 적용한 리비전 ID와 실행 시간을 남겨 장애 시 코드 버전과 스키마 버전을 함께 찾을 수 있게 합니다.

코드 읽기와 개념 경계

Alembic 리비전은 데이터베이스 구조 변경을 순서가 있는 파일로 기록합니다. upgrade head는 현재 데이터베이스를 최신 리비전까지 올리고, downgrade base는 정의된 역방향 작업을 적용합니다. 노트북의 subprocess.run(..., check=True)는 명령이 실패하면 즉시 예외를 내며, 이어지는 to_regclass 조회가 실제 표의 생성과 제거를 확인합니다.

코드 롤백과 스키마 다운그레이드는 같은 일이 아닙니다. 애플리케이션만 이전 버전으로 돌려도 이미 삭제하거나 변환한 열은 돌아오지 않습니다. 데이터가 손실되는 변경은 역방향 SQL보다 먼저 확장-이행-축소 순서를 검토하고 백업 복구 시간을 측정해야 합니다. 이 실습은 교육용 표 하나의 가역성만 확인합니다.

도식 읽기

푸른 리비전 파일을 붉은 upgrade 명령이 적용하면 초록색 버전 표와 tickets 표가 생깁니다. 보라색 downgrade는 반대 방향 변경을 실행합니다.

두 번째 준비 셀은 CH31_DATABASE_URL을 읽고 없으면 로컬 실습용 주소를 사용합니다. 같은 데이터베이스를 비동기 SQLAlchemy, psycopg, PostgreSQL 명령에서 사용할 수 있도록 드라이버 표기만 바꾼 세 URL을 만듭니다. 화면에는 데이터베이스 이름과 비밀값을 숨겼다는 사실만 출력합니다.

바로 다음 코드를 읽는 방법

Alembic 리비전은 데이터베이스 구조 변경을 순서가 있는 파일로 기록합니다. upgrade head는 현재 데이터베이스를 최신 리비전까지 올리고, downgrade base는 정의된 역방향 작업을 적용합니다. 노트북의 subprocess.run(..., check=True)는 명령이 실패하면 즉시 예외를 내며, 이어지는 to_regclass 조회가 실제 표의 생성과 제거를 확인합니다.

In [3]:
import os, subprocess
from pathlib import Path
# 현재 폴더와 상위 폴더에서 제공된 마이그레이션 설정을 찾습니다.
candidates = [parent / "labs/part7/ch31-database" for parent in (Path.cwd(), *Path.cwd().parents)]
candidates += [Path.cwd(), Path.cwd().parent]
LAB_ROOT = next(path for path in candidates if (path / "alembic.ini").is_file())
env = os.environ | {"CH31_SYNC_URL": SYNC_URL}
def alembic(*args: str) -> str:
    result = subprocess.run(
        ["alembic", "-c", str(LAB_ROOT / "alembic.ini"), *args],
        cwd=LAB_ROOT, env=env, text=True, capture_output=True, check=True,
    )
    return (result.stdout + result.stderr).strip()
print("migration directory:", LAB_ROOT.name)
출력:
migration directory: ch31-database

마이그레이션 적용

upgrade head가 표와 버전 기록을 함께 만드는지 확인합니다.

In [4]:
import psycopg
with psycopg.connect(NATIVE_URL, autocommit=True) as conn:
    conn.execute("DROP SCHEMA IF EXISTS ch31_migration CASCADE")
print(alembic("upgrade", "head").splitlines()[-1])
with psycopg.connect(NATIVE_URL) as conn:
    applied = conn.execute("SELECT to_regclass('ch31_migration.tickets')::text").fetchone()[0]
print("applied table:", applied)
assert applied == "ch31_migration.tickets"
출력:
INFO  [alembic.runtime.migration] Running upgrade  -> 20260911_01, 상담 티켓 표 구조를 변경합니다.
applied table: ch31_migration.tickets

확인할 점 — 마이그레이션 폴더 이름, 적용 뒤 표 이름, 다운그레이드 뒤 `None`, 재적용 뒤 복구된 표 이름을 순서대로 확인합니다. 이 절은 실행 시간을 출력하지 않습니다.

6일부러 실패해 보기

`upgrade head` 뒤에는 `ch31_migration.tickets`와 Alembic 버전 기록이 생성되었습니다. `downgrade base` 뒤 `to_regclass`는 NULL을 반환해 표가 제거됐음을 확인했습니다. 다시 `upgrade head`를 실행하자 같은 표가 복구되었습니다. 표를 되돌렸다는 사실만 확인했으며 운영 데이터가 안전하게 복원된다는 뜻은 아닙니다.

앞의 실행 예제를 실행한 같은 노트북에서 Before 다음 After 순서로 실행합니다. 출력은 실제 실행 결과입니다.

Before — 실패 코드

실패 확인

After — 수정 코드

수정

배포 코드와 맞는 리비전을 다시 적용해 표를 복구합니다.

이 단계에서 구분할 범위

코드 롤백과 스키마 다운그레이드는 같은 일이 아닙니다. 애플리케이션만 이전 버전으로 돌려도 이미 삭제하거나 변환한 열은 돌아오지 않습니다. 데이터가 손실되는 변경은 역방향 SQL보다 먼저 확장-이행-축소 순서를 검토하고 백업 복구 시간을 측정해야 합니다. 이 실습은 교육용 표 하나의 가역성만 확인합니다.

In [6]:
print(alembic("upgrade", "head").splitlines()[-1])
with psycopg.connect(NATIVE_URL) as conn:
    restored = conn.execute("SELECT to_regclass('ch31_migration.tickets')::text").fetchone()[0]
print("restored:", restored)
assert restored == "ch31_migration.tickets"
출력:
INFO  [alembic.runtime.migration] Running upgrade  -> 20260911_01, 상담 티켓 표 구조를 변경합니다.
출력:
restored: ch31_migration.tickets

이 결과는 Docker의 독립 PostgreSQL 17.8 컨테이너와 작은 데이터에서 측정했습니다. 행 수, 네트워크, 디스크, 동시 요청 수가 달라지면 시간과 실행 계획도 달라집니다.

롤백 시간을 측정할 때는 DDL 실행 시간과 데이터 되채우기 시간을 나눕니다. 배포 제한 시간을 넘는 변경은 한 리비전에 모두 넣지 않고 호환 가능한 여러 단계로 나누어 각 단계의 중단 가능 지점을 기록합니다.

7주의할 점과 실무 메모

  • 삭제 열이나 타입 축소는 롤백만으로 데이터를 복구하지 못할 수 있으므로 먼저 백업과 복원 연습이 필요합니다.
  • 여러 애플리케이션 인스턴스가 시작할 때 동시에 마이그레이션을 실행하지 않도록 배포 단계에서 한 번 실행합니다.
  • 자동 생성 결과에는 이름 없는 제약 조건과 데이터 변환 절차가 빠질 수 있어 파일을 검토해야 합니다.

운영 전 확인 순서

마이그레이션 검증에서는 빈 데이터베이스 적용, 현재 리비전에서 다음 리비전 적용, 한 단계 롤백을 구분합니다. 각 경로에서 Alembic 버전과 실제 열·제약·인덱스를 조회합니다. 시간 측정이 필요한 DDL은 운영과 비슷한 행 수의 복제 환경에서 실행합니다.

8정리와 다음 절

  • Alembic 리비전은 스키마 변경의 앞뒤 순서를 코드로 기록합니다.
  • upgrade, downgrade, 재적용을 `to_regclass`의 표 존재 여부로 확인했습니다.
  • 되돌리는 DDL이 있어도 삭제한 운영 데이터가 자동으로 복원되지는 않습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 요청이 늘 때 마이그레이션된 데이터베이스 연결을 풀에서 어떻게 빌리고 반환하는지 확인합니다.

9복습 문제

1. 리비전의 `down_revision`은 무엇을 가리키나요?

해설 — 현재 변경 바로 앞에 적용되어야 하는 리비전을 가리킵니다.

2. `upgrade head`의 `head`는 무엇인가요?

해설 — 현재 마이그레이션 계보에서 가장 최신 리비전을 뜻합니다.

3. 자동 생성 파일을 그대로 적용하면 안 되는 이유는 무엇인가요?

해설 — Alembic이 의도와 데이터 변환 안전성을 모두 알 수 없으므로 생성된 DDL과 손실 가능성을 사람이 확인해야 합니다.

4. 이 실습의 롤백 검사가 보장하지 않는 것은 무엇인가요?

해설 — 운영 데이터가 백업 없이 복원된다는 점은 보장하지 않습니다.
