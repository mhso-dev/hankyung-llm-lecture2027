1학습 목표

  • 벡터 표와 체크포인터 표가 같은 PostgreSQL에 있을 때 역할과 소유권을 구분할 수 있습니다.
  • HNSW 인덱스 존재와 실제 EXPLAIN 계획의 사용 여부를 구분할 수 있습니다.
  • 논리 덤프를 복원한 데이터베이스에서 문서·체크포인트 행과 인덱스를 확인할 수 있습니다.

2이 내용을 배우는 이유

에이전트 서비스는 검색 문서와 실행 상태를 같은 PostgreSQL에 저장할 수 있습니다. 벡터 표만 백업하면 대화 재개 정보가 사라지고, 체크포인터 표만 백업하면 검색 결과를 다시 만들 시간과 원본이 필요합니다. 마지막 절에서는 두 표 집합이 함께 존재하는 구조와 HNSW 인덱스, 논리 백업의 포함 범위를 확인합니다.

3앞에서 배운 내용

Ch12에서 pgvector의 거리 연산과 HNSW를 사용했고 Ch23에서는 PostgresSaver의 `setup()`이 체크포인터 표를 만든다는 점을 확인했습니다. 이번 절은 두 결과를 한 운영 스키마에서 함께 관리합니다.

4핵심 개념

구체적인 상황

한 창고에 상품과 배송 장부를 함께 보관하면 창고 주소는 하나지만 재고와 장부의 수명과 복구 우선순위는 다릅니다.

정의

PostgreSQL 스키마는 관련 표의 이름 공간을 나누며, 인덱스는 특정 표의 조회 경로를 추가합니다. HNSW(Hierarchical Navigable Small World)는 여러 층의 근접 그래프를 탐색하는 근사 최근접 이웃 인덱스입니다. 코사인 거리 쿼리에는 `vector_cosine_ops` 연산자 클래스를 맞춰야 합니다. 체크포인터는 그래프 실행 단계의 상태와 중간 쓰기를 저장합니다. 논리 백업(logical backup)은 `pg_dump`가 스키마와 행을 SQL 또는 아카이브 형식으로 추출하는 방식입니다. 백업 파일의 존재만으로 복구가 보장되지 않으므로 별도 데이터베이스에 복원하고 애플리케이션 조회까지 확인해야 합니다.

이 절의 새 용어 — HNSW, 연산자 클래스, 체크포인터, 논리 백업, 복원 연습

운영에서 경계를 정하는 방법

공존 설계에서는 같은 서버를 쓴다는 사실보다 소유권과 복구 순서를 문서로 남기는 일이 중요합니다. 애플리케이션 마이그레이션이 체크포인터 패키지가 만든 표를 변경하지 않게 스키마와 권한을 나눌 수 있습니다. 백업 범위에는 표뿐 아니라 확장, 함수, 인덱스, 시퀀스와 필요한 역할을 검토합니다. HNSW 인덱스는 원본 벡터 행에서 다시 만들 수 있으므로 복구 시간을 줄이기 위해 백업할지, 백업 크기를 줄이고 복원 뒤 재생성할지 선택할 수 있습니다. 선택은 데이터량과 허용 복구 시간에 달려 있습니다. 체크포인터는 오래된 스레드를 계속 보관하면 빠르게 늘 수 있으므로 제품의 보존 기간과 삭제 작업을 정합니다. `pg_dump`는 실행 시점의 서로 맞는 스냅샷을 만들지만, 지속 복제나 시점 복구 전체를 대신하지 않습니다. 정기 복원 훈련에서는 새 데이터베이스에 확장을 설치하고 덤프를 복원한 뒤 최근 스레드 재개, 문서 검색, 인덱스 존재와 권한을 애플리케이션 경로로 확인합니다.

코드 읽기와 개념 경계

pgvector 표의 임베딩은 의미 검색용 애플리케이션 데이터이고, LangGraph 체크포인터 표는 실행 상태를 이어가기 위한 운영 데이터입니다. 같은 PostgreSQL 스키마에 놓을 수 있어도 생성 주체와 복구 기준이 다릅니다. HNSW 인덱스는 근사 최근접 이웃 검색을 돕지만, 행이 세 개인 실습에서는 최적화기가 순차 스캔을 선택할 수 있습니다. 인덱스가 존재한다는 사실과 실제 계획에서 사용됐다는 사실을 구분합니다.

논리 백업에 두 종류의 표 정의가 들어갔다는 검사는 백업 범위를 확인합니다. 이것만으로 벡터 값, 체크포인트 행, 확장 설치, 복구 후 검색 결과까지 보장되지는 않습니다. 운영 검증은 새 데이터베이스에 복원한 뒤 행 수와 대표 벡터 검색, 스레드 재개를 실행해야 합니다.

도식 읽기

푸른 문서·HNSW와 붉은 체크포인터 표가 초록색 ch31_shared 스키마에 공존합니다. 보라색 pg_dump 상자는 이 스키마를 선택한 논리 백업입니다.

연결 준비와 실습 스키마 생성

이 셀은 psycopg와 PostgresSaver를 가져오고, 앞에서 준비한 NATIVE_URL로 PostgreSQL에 연결합니다. autocommit=True는 각 SQL 문장을 별도 명시적 커밋 없이 반영하는 설정입니다. vector 확장을 준비하고 기존 실습용 ch31_shared 스키마를 제거한 뒤 다시 만듭니다. 따라서 이 이름의 스키마에는 실습 자료만 두어야 합니다. shared_url은 다음 연결에서 사용할 스키마 검색 순서를 포함한 주소입니다.

In [3]:
import os, subprocess
import psycopg
from langgraph.checkpoint.postgres import PostgresSaver

BASE_URL = NATIVE_URL
with psycopg.connect(BASE_URL, autocommit=True) as conn:
    conn.execute("CREATE EXTENSION IF NOT EXISTS vector")
    conn.execute("DROP SCHEMA IF EXISTS ch31_shared CASCADE")
    conn.execute("CREATE SCHEMA ch31_shared")
shared_url = BASE_URL + "?options=-csearch_path%3Dch31_shared%2Cpublic"
print("schema: ch31_shared")

벡터 표와 HNSW 인덱스

세 문서를 저장하고 코사인 거리용 HNSW 인덱스를 만듭니다.

바로 다음 코드를 읽는 방법

pgvector 표의 임베딩은 의미 검색용 애플리케이션 데이터이고, LangGraph 체크포인터 표는 실행 상태를 이어가기 위한 운영 데이터입니다. 같은 PostgreSQL 스키마에 놓을 수 있어도 생성 주체와 복구 기준이 다릅니다. HNSW 인덱스는 근사 최근접 이웃 검색을 돕지만, 행이 세 개인 실습에서는 최적화기가 순차 스캔을 선택할 수 있습니다. 인덱스가 존재한다는 사실과 실제 계획에서 사용됐다는 사실을 구분합니다.

In [4]:
with psycopg.connect(shared_url, autocommit=True) as conn:
    conn.execute("CREATE TABLE documents(id int primary key, content text, embedding vector(3))")
    rows = "(1,'배송','[1,0,0]'),(2,'환불','[0,1,0]'),(3,'결제','[0,0,1]')"
    conn.execute("INSERT INTO documents VALUES " + rows)
    index_ddl = (
        "CREATE INDEX documents_embedding_hnsw ON documents "
        "USING hnsw (embedding vector_cosine_ops)"
    )
    conn.execute(index_ddl)
with psycopg.connect(shared_url) as conn:
    nearest = conn.execute(
        "SELECT content FROM documents "
        "ORDER BY embedding <=> '[0.9,0.1,0]' LIMIT 2"
    ).fetchall()
print("nearest:", [row[0] for row in nearest])
assert nearest[0][0] == "배송"

체크포인터 표 공존

공식 체크포인터 구현의 setup()으로 같은 스키마에 운영 표를 추가합니다.

In [6]:
with PostgresSaver.from_conn_string(shared_url) as saver:
    saver.setup()
    from typing_extensions import TypedDict
    from langgraph.graph import END, START, StateGraph
    class State(TypedDict):
        value: int
    graph_builder = StateGraph(State)
    graph_builder.add_node("double", lambda state: {"value": state["value"] * 2})
    graph_builder.add_edge(START, "double")
    graph_builder.add_edge("double", END)
    graph = graph_builder.compile(checkpointer=saver)
    saved = graph.invoke({"value": 6}, {"configurable": {"thread_id": "backup-demo"}})
with psycopg.connect(BASE_URL) as conn:
    tables = [row[0] for row in conn.execute(
        "SELECT table_name FROM information_schema.tables "
        "WHERE table_schema='ch31_shared' ORDER BY table_name"
    )]
    checkpoint_count = conn.execute(
        "SELECT count(*) FROM ch31_shared.checkpoints"
    ).fetchone()[0]
print("saved:", saved, "checkpoint rows:", checkpoint_count)
assert saved["value"] == 12 and checkpoint_count > 0
출력:
saved: {'value': 12} checkpoint rows: 3

논리 백업 확인

전용 스키마를 SQL 형식으로 덤프하고 두 종류의 표 정의가 모두 포함되는지 검사합니다.

백업을 새 데이터베이스에 복원하여 확인

이 셀은 Docker 컨테이너 안에서 pg_dump를 실행해 ch31_shared의 논리 백업을 문자열로 받습니다. subprocess.run(..., check=True)는 외부 명령이 실패하면 예외로 중단하며, text=True와 capture_output=True는 출력을 문자열로 수집하도록 지정합니다. 별도의 실습용 ch31_restore 데이터베이스를 다시 만든 뒤 백업을 복원하고 문서·체크포인트 행 수와 HNSW 인덱스 존재를 확인합니다. 이 검사는 모든 벡터 값의 일치나 스레드 재개까지 확인하지는 않습니다. 두 항목은 추가 복구 검사로 구분합니다.

In [7]:
container = os.getenv("CH31_POSTGRES_CONTAINER", "kdt-ch31-postgres")
dump = subprocess.run(
    ["docker", "exec", container, "pg_dump", "-U", "postgres", "-d", "ch31_lab",
     "--schema=ch31_shared", "--no-owner", "--no-privileges"],
    text=True, capture_output=True, check=True,
).stdout
for command in (["dropdb", "-U", "postgres", "--if-exists", "ch31_restore"],
                ["createdb", "-U", "postgres", "ch31_restore"]):
    subprocess.run(["docker", "exec", container, *command], check=True)
subprocess.run(
    ["docker", "exec", container, "psql", "-U", "postgres", "-d", "ch31_restore",
     "-c", "CREATE EXTENSION vector"], check=True, capture_output=True,
)
subprocess.run(
    ["docker", "exec", "-i", container, "psql", "-U", "postgres", "-d", "ch31_restore"],
    input=dump, text=True, check=True, capture_output=True,
)
restore_url = BASE_URL.replace("/ch31_lab", "/ch31_restore")
with psycopg.connect(restore_url) as conn:
    restored = conn.execute("SELECT (SELECT count(*) FROM ch31_shared.documents), "
                            "(SELECT count(*) FROM ch31_shared.checkpoints)").fetchone()
    index_ok = conn.execute("SELECT to_regclass('ch31_shared.documents_embedding_hnsw') IS NOT NULL").fetchone()[0]
print("restored rows:", restored, "hnsw:", index_ok)
assert "CREATE TABLE ch31_shared.documents" in dump
assert restored[0] == 3 and restored[1] > 0 and index_ok
출력:
restored rows: (3, 3) hnsw: True

확인할 점 — 가장 가까운 문서, Seq Scan 실행 계획, 체크포인트 결과값, 복원 뒤 문서·체크포인트 행 수와 HNSW 인덱스 이름을 확인합니다. 그래프 스레드 재개 자체는 이 노트북의 실행 범위가 아닙니다.

6실험 결과 해석

전용 `ch31_shared` 스키마에 문서 세 건과 코사인 HNSW 인덱스를 만들었습니다. `[0.9,0.1,0]`에 가장 가까운 문서는 ‘배송’이었습니다. 데이터가 세 행뿐이어서 실제 `EXPLAIN (ANALYZE, BUFFERS)`에서는 최적화기가 순차 스캔을 선택했습니다. 인덱스를 만들었다는 사실만으로 모든 쿼리가 그 인덱스를 사용하지 않음을 확인했습니다. PostgresSaver로 value 6을 12로 계산한 체크포인트를 실제 저장했습니다. 논리 덤프를 별도 `ch31_restore` 데이터베이스에 복원한 뒤 문서 3행, 1개 이상의 체크포인트 행, HNSW 인덱스를 다시 조회했습니다.

이 결과는 Docker의 독립 PostgreSQL 17.8 컨테이너와 작은 데이터에서 측정했습니다. 행 수, 네트워크, 디스크, 동시 요청 수가 달라지면 시간과 실행 계획도 달라집니다.

실행 계획의 Seq Scan은 HNSW 생성 실패가 아닙니다. 세 행에서는 전체를 읽고 정렬하는 비용이 작아 최적화기가 순차 스캔을 선택했습니다. 행 수와 통계를 운영 규모에 맞춘 뒤 같은 EXPLAIN을 반복해야 인덱스 선택과 버퍼 사용을 판단할 수 있습니다.

7주의할 점과 실무 메모

  • 근사 인덱스는 정확 검색과 속도·재현율 특성이 다르므로 Ch11 평가셋으로 변경 전후를 측정합니다.
  • WAL과 정기 논리 백업은 목적이 다릅니다. 필요한 복구 시점과 허용 손실 시간을 먼저 정합니다.
  • 백업에는 확장 설치 명령과 역할·권한이 환경에 따라 다르게 포함될 수 있으므로 깨끗한 복원 대상에서 연습합니다.
  • 벡터를 원문에서 다시 만들 수 있더라도 사용한 임베딩 모델 버전과 전처리 설정을 함께 보관해야 같은 결과를 재현할 수 있습니다.

운영 전 확인 순서

복원 검증은 빈 대상에 확장을 준비하고 덤프를 적용하는 순간부터 시작합니다. 문서 수와 체크포인트 수를 원본과 대조하고, 인덱스 정의와 실제 검색·스레드 재개를 확인합니다. 이번 실습은 행 수와 인덱스 존재까지 실행했으며 그래프 스레드 재개는 추가 검증 항목으로 남깁니다.

8정리와 다음 절

  • HNSW 인덱스는 거리 연산자 클래스와 쿼리가 맞아야 하며 작은 표에서는 선택되지 않을 수 있습니다.
  • 문서 표와 실제 체크포인트 행을 같은 스키마에 저장했습니다.
  • 논리 덤프를 별도 데이터베이스에 복원해 문서 행, 체크포인트 행, HNSW 인덱스를 확인했습니다.

다음 학습과 이어지는 지점 — Ch32에서는 이 애플리케이션과 PostgreSQL·pgvector를 Compose 서비스로 묶고 헬스체크와 시크릿을 설정합니다.

9복습 문제

1. 코사인 거리용 HNSW 인덱스에 사용한 연산자 클래스는 무엇인가요?

해설 — `vector_cosine_ops`입니다.

2. 검색 표와 체크포인터 표를 함께 확인한 이유는 무엇인가요?

해설 — 한 에이전트 서비스의 검색 데이터와 실행 재개 상태가 같은 백업 범위에 포함되는지 확인하기 위해서입니다.

3. 백업 파일이 만들어지면 복구 준비가 끝났다고 볼 수 있나요?

해설 — 볼 수 없습니다. 별도 데이터베이스에 복원하고 표, 행, 인덱스, 애플리케이션 조회를 확인해야 합니다.

4. 벡터를 다시 생성할 때 함께 보관해야 할 정보는 무엇인가요?

해설 — 원문뿐 아니라 임베딩 모델 버전과 전처리 설정을 함께 보관해야 합니다.

5. HNSW를 추가하면 정확 검색과 결과가 항상 같나요?

해설 — 항상 같지 않습니다. 근사 검색이므로 평가셋에서 재현율과 지연을 함께 측정해야 합니다.
