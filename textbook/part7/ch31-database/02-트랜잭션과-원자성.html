1학습 목표

  • 잔액 칸에 CHECK 제약을 건 표에서, 제약을 어기는 빼기가 받은 오류와 오류 코드를 출력으로 확인할 수 있습니다.
  • 이체의 두 변경을 블록 둘로 따로 확정하면, 둘째 변경이 막힌 뒤 첫째 변경만 남는 것을 재현할 수 있습니다.
  • 두 변경을 블록 engine.begin() 하나로 묶어, 오류가 나면 모두 취소되는 것을 잔액과 합계로 확인할 수 있습니다.

2이 내용을 배우는 이유

에이전트 서비스의 요청 하나가 데이터베이스의 줄 여럿을 함께 바꿀 때가 있습니다. 예를 들어 대화 기록 한 줄을 저장하면서, 사용자가 쓸 수 있는 남은 횟수를 하나 줄이는 일입니다. 둘 가운데 하나만 남으면, 다음 요청은 사실과 다른 상태를 읽습니다. 이 절은 두 계좌 사이의 이체로, 함께 바꿔야 하는 두 줄을 다룹니다.

절 제목의 트랜잭션(transaction)은 데이터베이스가 한 묶음으로 다루는 작업입니다. 이 교재 본문에서는 「한 묶음 작업」이라고 부릅니다. 제목의 원자성은 그 작업 안의 변경이 모두 확정되거나 모두 없던 일이 되는 성질입니다. 01절에서는 오류 없이 끝난 블록 engine.begin()이 변경을 확정하는 것만 봤고, 이 절은 블록 안에서 오류가 날 때를 봅니다.

3앞에서 배운 내용

01절에서는 비동기 엔진을 만들고, 연결 풀에서 빌린 연결로 SQL 글을 보냈습니다. 블록 engine.begin()으로 이름 공간과 표를 만들고, 블록이 오류 없이 끝나면 확정되는 것을 봤습니다. SQL 글 속 :id 같은 자리에 값을 따로 넘기는 방법도 이 절에서 그대로 씁니다.

Ch 4 03절에서는 표에 기본 키·외래 키 제약을 걸고, 어기는 행을 넣다가 오류 sqlite3.IntegrityError를 받았습니다. 넣은 행은 commit()으로 확정했습니다. Ch 2 05절에서는 try와 except로 이름이 맞는 오류만 받아, 셀을 끝까지 실행했습니다. 이 절은 세 가지를 PostgreSQL 서버의 CHECK 제약과 블록 engine.begin()에 씁니다.

Ch 23 04절부터 06절까지는 멈춘 그래프를 체크포인트에서 이어 실행했습니다. 06절에서는 다시 실행된 단계가 바깥 파일에 같은 쓰기를 두 번 하지 않게, 멱등 키로 이미 한 일인지 확인했습니다. 이 절은 그보다 앞의 물음을 봅니다. 이어 실행할 때 읽을 데이터베이스의 줄들이 반쯤 바뀐 채 남지 않게 하는 방법입니다.

4핵심 개념

비유로 시작하기

옛 전화 교환대의 넓은 판 하나를 떠올려 봅니다. 판에는 꽂는 자리가 두 개씩 짝을 지어 놓여 있고, 자리마다 위에 작은 불이 달려 있습니다. 통화 하나를 이으려면 선 한 가닥의 양 끝을 짝이 되는 두 자리에 모두 꽂아야 합니다. 끝이 꽂힌 자리에는 불이 켜집니다.

판에 짝 셋이 왼쪽부터 나란히 있습니다. 첫째 짝은 선의 양 끝이 두 자리에 모두 꽂혀, 불 둘이 켜져 있습니다. 둘째 짝은 한 끝만 꽂히고 다른 끝은 아래로 늘어져, 불 하나만 켜져 있습니다. 셋째 짝은 두 자리가 모두 비어 불이 꺼져 있고, 선은 판 아래쪽 나무 선반에 감겨 놓여 있습니다.

짝이 된 두 자리가 이체의 두 변경이고, 선 한 가닥이 한 묶음 작업입니다. 첫째 짝은 이체 100처럼 두 변경이 모두 확정된 모습입니다. 둘째 짝은 Before 판처럼 한쪽만 남은 모습이고, 셋째 짝은 After 판처럼 두 변경이 모두 취소된 모습입니다. 교환대에서 쓸모 있는 모습은 첫째와 셋째뿐입니다.

비유와 다른 점이 있습니다. 실제 블록은 안의 변경을 하나씩 먼저 적용해 둡니다. 그리고 블록이 끝날 때 한꺼번에 확정하거나, 한꺼번에 취소합니다.

그림 읽기 — 초록 금속 판 하나에 꽂는 자리 여섯이 두 개씩 짝 셋으로 놓여 있습니다. 왼쪽 짝은 선의 양 끝이 모두 꽂혀 불 둘이 켜져 있습니다. 가운데 짝은 한 끝만 꽂히고 다른 끝은 아래로 늘어져, 불 하나만 켜져 있습니다. 오른쪽 짝은 두 자리가 모두 비어 불이 꺼져 있고, 선은 선반 위에 감겨 있습니다. 짝 하나가 이체의 두 변경이고, 왼쪽이 이체 100, 가운데가 Before 판, 오른쪽이 After 판이 남긴 모습입니다.

한 묶음 작업과 원자성

블록 engine.begin() 하나가 한 묶음 작업 하나입니다. 블록 안의 SQL 글은 차례로 서버에 가서 적용되지만, 아직 확정된 것은 아닙니다. 블록이 오류 없이 끝나면 라이브러리가 확정(커밋)을 보내고, 블록 안에서 오류가 나면 취소(롤백)를 보냅니다. SQLAlchemy 문서도 블록이 정상으로 끝나면 확정하고, 오류가 나면 취소한 뒤 그 오류를 블록 밖으로 내보낸다고 적습니다.

PostgreSQL 문서는 한 묶음 작업이 여러 단계를, 모두 되거나 모두 안 되는 하나의 일로 묶는다고 적습니다. 문서의 예도 한 계좌에서 빼고 다른 계좌에 더하는 이체입니다. 둘 가운데 한쪽만 남으면 안 되는 일을 한 블록에 넣는 것이 이 절의 방법입니다.

말뜻
한 묶음 작업(트랜잭션, transaction)여러 SQL 글을 한 묶음으로 실행하고, 끝에서 한꺼번에 확정하는 작업입니다. 장바구니의 물건을 한 번에 계산해, 결제가 되면 모두 사고 안 되면 아무것도 사지 않는 것과 같습니다. 이 절에서는 블록 async with engine.begin() as conn: 하나가 한 묶음 작업 하나입니다.
원자성(atomicity)한 묶음 작업 안의 변경이 모두 확정되거나, 모두 없던 일이 되는 성질입니다. 두 사람이 모두 서명해야 효력이 생기는 계약서와 같습니다. 이 절에서는 빼기가 막히자 같은 블록의 더하기도 남지 않았습니다.
취소(롤백, rollback)블록 안에서 오류가 나면, 확정하지 않고 블록 안의 변경을 모두 없던 일로 하는 것입니다. 연필로 적어 둔 것을 볼펜으로 옮겨 적기 전에 지우개로 모두 지우는 것과 같습니다. 이 절에서는 블록 안에서 읽은 2번 잔액 1100이 블록 밖에서 500이었습니다.

새 말을 이 절 코드에서 보면 이렇습니다. 이체 함수 transfer_one_block의 블록 하나가 한 묶음 작업이고, 100을 보내자 잔액: [(1, 400), (2, 600)]으로 두 줄이 함께 확정되었습니다. 600을 보내자 빼기가 막혀 더하기도 남지 않았고, 잔액은 [(1, 500), (2, 500)]이었습니다.

도식 읽기 — 위에서 아래로 읽습니다. 파란 상자는 우리가 적은 블록과 그 안의 두 줄입니다. 회색 상자 둘은 블록이 끝날 때 라이브러리가 보내는 확정과 취소이고, 점선은 둘 가운데 한쪽으로 가는 갈래입니다. 노란 상자는 노트북 4절과 6절 출력으로 확인한 잔액입니다.

CHECK 제약과 오류 코드

CHECK 제약은 칸 값이 적어 둔 식을 만족해야 한다는 조건입니다. 이 절의 표는 잔액 칸에 CHECK (balance >= 0)을 걸었습니다. 잔액을 0보다 작게 만드는 변경은 서버가 저장하지 않고 오류를 냅니다. 제약 이름을 적지 않으면 서버가 이름을 붙이고, 이 표에서는 accounts_balance_check였습니다.

오류 코드 SQLSTATE는 PostgreSQL 서버가 오류마다 붙이는 다섯 글자 코드입니다. 앞 두 글자가 오류의 갈래이고, 23은 제약을 어긴 오류의 갈래입니다. 이 절의 23514는 CHECK 제약 위반입니다. PostgreSQL 문서는 오류를 가릴 때 오류 글보다 이 코드를 보라고 적습니다.

라이브러리 SQLAlchemy는 서버의 오류를 IntegrityError로 감쌉니다. 속성 orig에는 SQLAlchemy가 드라이버 오류를 파이썬 데이터베이스 약속(DB-API)의 모양으로 바꾼 오류가 있습니다. 그 오류의 글 첫머리에 드라이버 오류 이름 CheckViolationError가 붙습니다.

이 절의 취소와 03절 제목의 롤백

이 절에서 취소는 블록 engine.begin()이 오류로 끝날 때, 블록 안의 변경을 확정하지 않는 일입니다. 03절 제목의 롤백은 Alembic으로 표 구조의 판을 내리는 일이라, 뜻이 다릅니다. 둘 다 영어로 rollback이라 부르지만, 이 교재에서는 말을 나눠 씁니다.

3. 계좌 표와 CHECK 제약

이 절의 표 accounts는 계좌 번호 칸 id와 잔액 칸 balance를 가집니다. 표는 이름 공간 ch31_tx에 두고, 01절처럼 처음에 지우고 다시 만듭니다.

잔액 칸에는 제약을 겁니다. Ch 4 03절에서 제약(constraint)은 표에 적어 두고, 어기는 행을 막는 조건이었습니다. CHECK 제약은 칸 값이 적어 둔 식을 만족해야 한다는 조건입니다. 이 표의 CHECK (balance >= 0)은 잔액이 0 이상이어야 한다는 뜻입니다. 잔액이 0보다 작아지는 줄은 PostgreSQL 서버가 저장하지 않고 오류를 냅니다.

In [5]:
# 이름 공간 ch31_tx를 지우고 다시 만든 뒤, 표 accounts에 계좌 두 줄을 넣습니다
# CHECK (balance >= 0)은 잔액 칸이 0 이상이어야 한다는 조건이고, 어기는 줄은 서버가 막습니다
table_sql = "CREATE TABLE ch31_tx.accounts (id int PRIMARY KEY, balance int CHECK (balance >= 0))"
insert_sql = "INSERT INTO ch31_tx.accounts VALUES (1, 500), (2, 500)"
async with engine.begin() as conn:
    await conn.execute(text("DROP SCHEMA IF EXISTS ch31_tx CASCADE"))
    await conn.execute(text("CREATE SCHEMA ch31_tx"))
    await conn.execute(text(table_sql))
    inserted = await conn.execute(text(insert_sql))
print("넣은 줄 수:", inserted.rowcount)
출력:
넣은 줄 수: 2

결과 읽기 — 출력 줄 넣은 줄 수: 2가 보입니다. 계좌 두 줄이 잔액 500씩으로 표에 들어갔습니다. 블록이 오류 없이 끝나, 이름 공간·표·두 줄을 한꺼번에 확정했습니다.

다음 두 셀은 잔액을 읽는 함수와 잔액을 더하는 함수를 정의합니다. 함수 read_balances는 연결을 하나 빌려, 두 계좌의 번호와 잔액을 번호 차례로 읽습니다. 메서드 fetchall은 01절처럼 결과의 줄을 모두 목록으로 꺼냅니다.

In [6]:
# 두 계좌의 번호와 잔액을 번호 차례로 읽어, 줄 목록을 내놓습니다(연결 하나를 빌렸다가 풀에 다시 넣습니다)
async def read_balances():
    async with engine.connect() as conn:
        result = await conn.execute(text("SELECT id, balance FROM ch31_tx.accounts ORDER BY id"))
        rows = result.fetchall()
    return rows

결과 읽기 — 정의 셀이라 출력이 없습니다. 함수는 불릴 때마다 연결을 빌렸다가, 블록이 끝나면 풀에 다시 넣습니다.

다음 셀의 함수 add_balances는 줄 목록을 받아 잔액을 모두 더한 합계를 내놓습니다. 줄의 칸 값은 row.balance처럼 점 뒤에 칸 이름을 적어 꺼냅니다. 두 계좌 사이에서 돈을 보내기만 하면, 합계는 처음과 같아야 합니다.

In [7]:
# 줄 목록을 받아 잔액을 모두 더한 합계를 내놓습니다(줄의 칸 값은 row.balance처럼 칸 이름으로 꺼냅니다)
def add_balances(rows):
    total = 0
    for row in rows:
        total = total + row.balance
    return total

결과 읽기 — 정의 셀이라 출력이 없습니다. 합계를 세는 모양은 Ch 2 02절의 for 반복문과 같습니다.

다음 셀은 두 함수로 처음 잔액과 합계를 봅니다. 합계는 변수 start_total에 남겨, 뒤에서 견줄 기준으로 씁니다.

In [8]:
# 처음 잔액과 합계를 봅니다(합계는 뒤에서 견줄 기준으로 남겨 둡니다)
rows = await read_balances()
start_total = add_balances(rows)
print("잔액:", rows)
print("합계:", start_total)
출력:
잔액: [(1, 500), (2, 500)]
합계: 1000

결과 읽기 — 출력 줄 잔액: [(1, 500), (2, 500)]과 합계: 1000이 보입니다. 줄 하나는 계좌 번호와 잔액의 튜플 모양으로 찍힙니다. 두 계좌의 잔액을 더한 1000이 이 절의 기준 합계입니다.

4. 한 묶음 작업으로 이체하기

이체는 받는 계좌의 잔액에 더하고, 보내는 계좌의 잔액에서 빼는 일입니다. 두 줄 가운데 하나만 바뀌면 합계가 달라집니다. 그래서 두 줄은 모두 바뀌거나, 모두 그대로여야 합니다.

한 묶음 작업(트랜잭션)은 여러 SQL 글을 한 묶음으로 실행하고, 끝에서 한꺼번에 확정하는 작업입니다. 장바구니에 담은 물건을 한 번에 계산해, 결제가 되면 모두 사고 안 되면 아무것도 사지 않는 것과 비슷합니다. 이 절의 코드에서는 블록 async with engine.begin() as conn: 하나가 한 묶음 작업 하나입니다. 블록이 오류 없이 끝나면 블록 안의 변경을 한꺼번에 확정(커밋)합니다. 확정은 Ch 4 03절의 커밋과 같은 일입니다.

제목의 원자성(atomicity)은 한 묶음 작업 안의 변경이 모두 확정되거나, 모두 없던 일이 되는 성질입니다. 두 사람이 모두 서명해야 효력이 생기는 계약서와 비슷합니다. 한 사람만 서명한 계약서는 없는 계약입니다. 이 절에서는 6절 After 판의 잔액으로 이 성질을 확인합니다.

다음 셀은 잔액을 바꾸는 SQL 글 둘을 객체로 만듭니다. SQL 문장 UPDATE는 WHERE 조건에 맞는 줄에서, SET 뒤에 적은 칸 값을 바꿉니다. 글 balance = balance + :amount는 지금 잔액에 금액을 더한 값으로 바꾸라는 뜻입니다. 자리 :amount와 :id에는 01절처럼 실행할 때 따로 넘긴 값이 들어갑니다.

In [9]:
# 잔액을 바꾸는 SQL 글 둘을 객체로 만듭니다(계좌 번호와 금액이 들어갈 자리를 둡니다)
# UPDATE는 WHERE 조건에 맞는 줄에서, SET 뒤에 적은 칸 값을 바꿉니다
deposit_sql = text("UPDATE ch31_tx.accounts SET balance = balance + :amount WHERE id = :id")
withdraw_sql = text("UPDATE ch31_tx.accounts SET balance = balance - :amount WHERE id = :id")
print("더하는 SQL 글:", deposit_sql)
print("빼는 SQL 글:", withdraw_sql)
출력:
더하는 SQL 글: UPDATE ch31_tx.accounts SET balance = balance + :amount WHERE id = :id
빼는 SQL 글: UPDATE ch31_tx.accounts SET balance = balance - :amount WHERE id = :id

결과 읽기 — 라벨 더하는 SQL 글:과 빼는 SQL 글: 뒤에 두 SQL 글이 그대로 찍혔습니다. 두 글은 +와 -만 다릅니다. 이 셀은 객체를 만들기만 했고, 서버에는 아직 아무것도 보내지 않았습니다.

다음 셀의 함수 transfer_one_block은 보내는 계좌·받는 계좌·금액을 받아 이체합니다. 블록 하나 안에서 받는 계좌에 먼저 더하고, 그다음 보내는 계좌에서 뺍니다. 이 차례는 5절의 결과가 잘 보이도록 정한 것이고, 까닭은 5절 끝에서 봅니다.

In [10]:
# 받는 계좌에 더하기와 보내는 계좌에서 빼기를 begin 블록 하나에 함께 넣은 이체 함수를 정의합니다
async def transfer_one_block(from_id, to_id, amount):
    async with engine.begin() as conn:
        await conn.execute(deposit_sql, {"id": to_id, "amount": amount})
        await conn.execute(withdraw_sql, {"id": from_id, "amount": amount})

결과 읽기 — 정의 셀이라 출력이 없습니다. 두 await 줄이 같은 블록 안에 있어, 두 변경이 한 묶음 작업이 됩니다.

다음 셀은 1번 계좌에서 2번 계좌로 100을 보내고, 잔액과 합계를 봅니다.

In [11]:
# 1번 계좌에서 2번 계좌로 100을 한 블록으로 보내고, 잔액과 합계를 봅니다
await transfer_one_block(1, 2, 100)
rows = await read_balances()
print("잔액:", rows)
print("합계:", add_balances(rows))
출력:
잔액: [(1, 400), (2, 600)]
합계: 1000

결과 읽기 — 출력 줄 잔액: [(1, 400), (2, 600)]과 합계: 1000이 보입니다. 1번은 100이 줄고 2번은 100이 늘어, 합계는 처음과 같습니다. 블록이 오류 없이 끝나 두 변경을 함께 확정했습니다.

확인할 점 — 노트북 3절 끝에서 잔액: [(1, 500), (2, 500)]과 합계: 1000을 봅니다. 4절 이체 뒤 잔액: [(1, 400), (2, 600)]과 합계 1000을 확인합니다. 2절의 풀에 둘 연결 수: 5는 SQLAlchemy의 기본값입니다.

도식 읽기 — 위에서 아래로 읽습니다. 파란 상자 둘은 노트북 3절의 표 만들기 블록과 4절의 이체 함수입니다. 초록 상자는 표에 넣은 계좌 두 줄이고, 회색 상자는 블록 끝의 확정입니다. 노란 상자 둘은 3절과 4절 출력으로 확인한 잔액과 합계입니다.

Before — 실패 코드

5. 블록 둘로 따로 확정하는 이체 (Before)

이번에는 1번 계좌에서 2번 계좌로 600을 보냅니다. 1번 계좌의 잔액은 500이라, 600을 빼면 CHECK 제약에 걸립니다. Before 판의 이체 함수는 더하기와 빼기를 블록 둘에 하나씩 넣습니다. 블록마다 따로 확정하므로, 한 묶음 작업이 둘로 나뉩니다. 다음 셀은 그 함수를 정의합니다.

In [12]:
# Before: 더하기와 빼기를 begin 블록 둘에 하나씩 넣어, 블록마다 따로 확정하는 이체 함수를 정의합니다
async def transfer_two_blocks(from_id, to_id, amount):
    async with engine.begin() as conn:
        await conn.execute(deposit_sql, {"id": to_id, "amount": amount})
    async with engine.begin() as conn:
        await conn.execute(withdraw_sql, {"id": from_id, "amount": amount})

결과 읽기 — 정의 셀이라 출력이 없습니다. 함수 transfer_one_block과 다른 곳은 둘째 async with engine.begin() as conn: 줄 하나입니다.

다음 셀은 4절의 이체로 바뀐 잔액을, 두 계좌 모두 500으로 다시 맞춥니다. 조건 WHERE를 적지 않은 UPDATE는 표의 모든 줄을 바꿉니다.

In [13]:
# 두 계좌의 잔액을 모두 500으로 다시 맞추고, 잔액을 봅니다
async with engine.begin() as conn:
    reset = await conn.execute(text("UPDATE ch31_tx.accounts SET balance = 500"))
print("다시 500으로 맞춘 줄 수:", reset.rowcount)
rows = await read_balances()
print("잔액:", rows)
출력:
다시 500으로 맞춘 줄 수: 2
잔액: [(1, 500), (2, 500)]

결과 읽기 — 출력 줄 다시 500으로 맞춘 줄 수: 2와 잔액: [(1, 500), (2, 500)]이 보입니다. 두 계좌가 처음과 같은 잔액이 되었습니다.

다음 셀은 Before 판 함수로 600을 보내 봅니다. 둘째 블록에서 오류가 날 것이므로, Ch 2 05절처럼 오류 이름 IntegrityError만 받는 try로 감쌉니다. 받은 오류의 이름과 오류 코드, 드라이버가 받은 오류 글을 출력하고 셀은 끝까지 갑니다. 실행 전에 예상해 봅니다. 오류가 난 뒤, 두 계좌의 잔액은 무엇일까요?

In [14]:
# 1번에서 2번으로 600을 블록 둘로 보내 보고, 오류가 나면 받은 오류의 이름·코드·글을 출력합니다
try:
    await transfer_two_blocks(1, 2, 600)
except IntegrityError as error:
    print("받은 오류:", type(error).__name__)
    print("오류 코드(SQLSTATE):", error.orig.sqlstate)
    print("드라이버가 받은 오류 글:")
    print(error.orig)
출력:
받은 오류: IntegrityError
오류 코드(SQLSTATE): 23514
드라이버가 받은 오류 글:
<class 'asyncpg.exceptions.CheckViolationError'>: new row for relation "accounts" violates check constraint "accounts_balance_check"
DETAIL:  Failing row contains (1, -100).

결과 읽기 — 출력 줄 받은 오류: IntegrityError와 오류 코드(SQLSTATE): 23514가 보입니다. 라벨 줄 아래 오류 글에는 violates check constraint "accounts_balance_check"가 있습니다. 그 아래 줄 DETAIL: Failing row contains (1, -100).은 막힌 줄이 1번 계좌라는 뜻입니다. 1번 잔액이 -100이 될 뻔해서, 둘째 블록의 빼기가 CHECK 제약에 막혔습니다.

오류 코드 SQLSTATE는 PostgreSQL 서버가 오류마다 붙이는 다섯 글자 코드입니다. PostgreSQL 문서는 23514를 CHECK 제약 위반(check_violation)이라고 적습니다. 제약 이름 accounts_balance_check는 이름을 적지 않은 제약에 서버가 붙인 이름입니다. 오류 글 맨 앞의 CheckViolationError는 드라이버 asyncpg의 오류 이름입니다.

라벨 드라이버가 받은 오류 글: 아래 글은 속성 orig의 글입니다. 속성 orig에 든 것은 SQLAlchemy가 드라이버 오류를 파이썬 데이터베이스 약속(DB-API)의 모양으로 바꾼 오류입니다. 그래서 그 글 첫머리에 드라이버의 오류 이름이 붙어 찍혔습니다.

다음 셀은 오류가 난 뒤의 잔액과 합계를 봅니다.

In [15]:
# Before 판의 이체가 끝난 뒤, 잔액과 합계를 봅니다

before_total = add_balances(rows)
print("잔액:", rows)
print("합계:", before_total)
출력:
잔액: [(1, 500), (2, 1100)]
합계: 1600

결과 읽기 — 출력 줄 잔액: [(1, 500), (2, 1100)]과 합계: 1600이 보입니다. 1번에서는 빠지지 않았는데, 2번에는 600이 더해져 있습니다. 합계가 처음 1000보다 600 많아졌습니다. 이것이 이 절의 Before 결함입니다.

첫째 블록은 오류 없이 끝나, 더하기를 이미 확정했습니다. 둘째 블록의 오류는 둘째 블록의 빼기만 막았고, 이미 확정한 첫째 블록에는 닿지 않았습니다. 오류는 받았지만, 데이터베이스에는 반쯤 끝난 이체가 남았습니다.

4절에서 받는 계좌에 먼저 더하게 정한 것은 이 결함이 잔액에 보이게 하려는 것입니다. 노트북 밖에서 빼기를 먼저 하는 블록 둘로 600을 보내 보자, 첫째 블록에서 막혀 잔액이 그대로였습니다. 그래도 블록이 둘이면, 둘째 블록이 막힐 때 첫째 블록의 확정은 남습니다.

정리

1. 표의 CHECK 제약은 잔액을 0보다 작게 만드는 빼기를 막았고, 받은 오류의 코드는 23514였습니다. 2. 더하기와 빼기를 블록 둘로 따로 확정하자, 빼기가 막힌 뒤에도 더하기가 남아 합계가 1600이 되었습니다. 3. 두 줄을 블록 하나로 묶자, 같은 오류에서 두 변경이 함께 취소되어 합계가 1000으로 남았습니다.

03절에서는 Alembic으로 표 구조를 판마다 바꾸는 방법을 봅니다.

도식 읽기 — 위에서 아래로 읽습니다. 맨 위 회색 상자는 Before 판을 시작할 때의 잔액과 보낼 돈입니다. 칸 둘은 begin 블록 둘이고, 칸 안 파란 상자가 블록마다 보낸 SQL 글 하나입니다. 노란 상자는 노트북 5절에서 받아 출력한 오류이고, 빨간 상자는 그 뒤에 남은 잔액과 합계입니다.

도식 읽기 — 맨 위 회색 상자는 두 판에서 같았던 처음 잔액·보낼 돈·받은 오류 코드입니다. 왼쪽 Before 칸과 오른쪽 After 칸의 제목이 두 판에서 다른 블록의 수이고, 파란 상자는 그 블록에서 일어난 일입니다. 빨간 상자는 Before 판의 결함 결과이고, 노란 상자는 After 판의 결과입니다. 두 칸의 잔액과 합계는 노트북 5절과 6절 출력입니다.

두 판은 같은 오류를 받았습니다. 받은 오류는 IntegrityError이고, 오류 코드는 23514였습니다. 다른 것은 블록의 수 하나였고, 그 차이가 남은 잔액을 갈랐습니다.

Before 판에서 첫째 블록은 오류 없이 끝나, 더하기를 이미 확정했습니다. 둘째 블록의 오류는 둘째 블록의 빼기만 막았고, 확정이 끝난 첫째 블록에는 닿지 않았습니다. 그래서 2번 잔액만 1100이 되어, 합계가 1600으로 남았습니다. 오류를 받고 셀은 끝까지 갔지만, 데이터베이스에는 반쯤 끝난 이체가 남은 것입니다.

After 판은 더하기와 빼기가 한 블록 안에 있었습니다. 블록 안에서 2번 잔액은 1100이 되었지만, 빼기가 막히자 블록이 두 변경을 함께 취소했습니다. 블록 밖에서 다시 읽은 잔액은 500과 500이었고, 합계는 처음과 같은 1000이었습니다.

노트북 7절에서 보낼 돈만 500으로 바꾸자, 같은 한 블록 함수가 오류 없이 두 변경을 확정했습니다. 1번 잔액 0은 제약 balance >= 0을 만족하기 때문입니다. 한 블록은 막힌 이체는 모두 취소하고, 막히지 않은 이체는 모두 확정했습니다.

새 커널로 두 번 실행해 견주자, 코드 셀 스물셋의 출력이 셀마다 모두 같았습니다. 한 번은 프로젝트 맨 위에서, 한 번은 notebooks/ 폴더에서 연 커널이었습니다. 모델을 부르지 않아, 이 절의 출력은 서버에 남은 잔액과 받은 오류로 정해집니다.

확인할 점 — Before 판에서 오류 코드(SQLSTATE): 23514와 잔액: [(1, 500), (2, 1100)]을 봅니다. After 판에서 같은 오류 코드와 잔액: [(1, 500), (2, 500)]을 확인합니다. 블록 안에서 읽은 2번 잔액 1100과, 7절의 잔액: [(1, 0), (2, 1000)]도 찾습니다.

7주의할 점과 실무 메모

  • 이 절의 이체 함수는 받는 계좌에 먼저 더하고, 보내는 계좌에서 뺍니다. 이 차례는 Before 판의 결함이 잔액에 보이게 하려고 정한 예입니다. 노트북 밖에서 빼기를 먼저 하는 블록 둘로 600을 보내 보자, 첫째 블록에서 막혀 잔액이 500과 500 그대로였습니다. 그래도 블록이 둘이면, 둘째 블록이 막힐 때 첫째 블록의 확정은 남습니다.
  • 한 묶음 작업의 취소는 데이터베이스 안의 변경에만 닿습니다. 블록 안에서 바깥 서비스에 보낸 요청은 취소되지 않습니다. 이미 끝난 바깥 일을 반대 방향의 일로 맞추는 것을 보상 작업이라고 부르고, 결제를 취소하는 요청이 그 예입니다. 이 챕터에서는 보상 작업을 실행하지 않았습니다. 같은 일을 두 번 하지 않게 하는 멱등 키는 Ch 23 06절에서 봤습니다.
  • 노트북 밖에서 받은 오류를 print(error)로 모두 찍어 보니, SQL 글과 넘긴 값, 오류 설명 주소까지 여러 줄이 나왔습니다. 이 절은 매번 같은 오류 이름·오류 코드와, 드라이버가 받은 오류 글만 출력했습니다. 오류를 가릴 때는 PostgreSQL 문서대로 글보다 오류 코드를 봅니다.
  • 이 절은 오류 이름 IntegrityError만 받아 셀을 끝까지 실행했습니다. 받지 않은 오류는 Ch 2 05절에서 본 것처럼 셀 밖으로 나와 실행을 멈춥니다. 실제 서비스에서는 받은 오류를 기록하고, 요청한 쪽에 실패를 알려야 합니다.
  • 잔액이 0보다 작아지지 않게 파이썬 코드에서 먼저 검사할 수도 있습니다. 이 절은 그런 검사를 두지 않고, 서버의 CHECK 제약이 막게 했습니다. 여러 연결이 같은 계좌를 함께 바꾸는 장면은 이 절에서 실행하지 않았습니다.
  • 노트북을 쓰기 전에 노트북 밖에서 같은 장면을 파이썬 파일로 다섯 번 실행했고, 출력이 다섯 번 모두 같았습니다. 잔액·합계·오류 코드·오류 글 모두 실행할 때마다 같은 값입니다.
  • 교재 출력은 Linux의 Python 3.12.13과 PostgreSQL 17.11 서버로 만들었습니다. 그 서버는 Docker 컨테이너가 아니라 같은 접속 글로 켠 서버입니다. Docker 이미지로 켜면 버전 번호의 끝자리가 다를 수 있습니다. 다른 버전과 Windows·macOS에서는 실행하지 않았습니다.

8정리와 다음 절

  • 표의 CHECK 제약은 잔액을 0보다 작게 만드는 빼기를 막았고, 받은 오류는 IntegrityError, 오류 코드는 23514였습니다.
  • 두 변경을 블록 둘로 따로 확정하자, 빼기가 막힌 뒤에도 더하기가 남아 합계가 1600이 되었습니다.
  • 두 변경을 블록 하나로 묶자, 같은 오류에서 두 변경이 함께 취소되어 합계가 1000으로 남았습니다.

9복습 문제

문제 5개 · 해설 포함

1. 표 accounts의 CHECK 제약은 무엇을 막았고, 막을 때 받은 오류 이름과 오류 코드는 무엇이었나요?

잔액을 0보다 작게 만드는 빼기를 막았습니다. 받은 오류는 IntegrityError, 오류 코드는 23514였습니다. 틀렸다면 노트북 3절과 5절을 다시 읽습니다.

2. Before 판에서 합계가 1600이 된 까닭은 무엇인가요?

첫째 블록이 2번 계좌의 더하기를 이미 확정했기 때문입니다. 둘째 블록의 빼기가 막혀도, 확정된 더하기는 남았습니다. 틀렸다면 노트북 5절을 다시 읽습니다.

3. After 판에서 블록 안에서 읽은 2번 잔액과, 블록 밖에서 다시 읽은 2번 잔액은 무엇이었나요?

블록 안에서는 1100, 블록 밖에서는 500이었습니다. 빼기가 막히자 블록이 더하기까지 함께 취소했습니다. 틀렸다면 노트북 6절을 다시 읽습니다.

4. 보낼 돈을 500으로 바꾸자 오류가 나지 않은 까닭은 무엇인가요?

1번 잔액이 0이 되는데, 제약 balance >= 0은 0을 허용하기 때문입니다. 한 블록이 두 변경을 함께 확정해 잔액은 [(1, 0), (2, 1000)]이었습니다. 틀렸다면 노트북 7절을 다시 읽습니다.

5. 동료가 「블록 안에서 결제 서비스에 요청을 보냈어도, 오류가 나면 블록이 결제까지 취소한다」고 말합니다. 맞나요?

맞지 않습니다. 블록의 취소는 데이터베이스 안의 변경에만 닿습니다. 바깥에 보낸 요청은 보상 작업으로 따로 맞춰야 하고, 이 챕터에서는 실행하지 않았습니다. 틀렸다면 본문 7블록을 다시 읽습니다.
