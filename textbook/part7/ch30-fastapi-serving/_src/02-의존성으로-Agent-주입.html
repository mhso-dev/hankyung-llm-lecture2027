1학습 목표

  • 처리 함수의 매개변수에 의존성을 적어, 라이브러리가 요청마다 제공 함수의 값을 넘기게 할 수 있습니다.
  • 재정의 딕셔너리로 제공 함수를 바꿔 끼우고, 원래 함수가 불리지 않는 것을 출력으로 확인할 수 있습니다.
  • 남은 재정의가 다음 테스트를 504로 바꾸는 것을 보고, 재정의 딕셔너리를 비워 고칠 수 있습니다.

2이 내용을 배우는 이유

01절의 처리 함수는 몸통에서 함수 make_result를 바로 불렀습니다. 실습 앱의 처리 함수는 에이전트 그래프·시간 제한 값·접근 토큰 검사처럼 여러 값을 씁니다. 이 값을 몸통에서 직접 만들면, 시험 때 다른 값으로 바꾸기 어렵습니다. 그래서 이 절은 처리 함수가 쓸 값을 라이브러리가 요청마다 넘겨 주게 합니다.

제목의 주입은 FastAPI 문서의 말 injection을 옮긴 말이고, 본문에서는 「넘겨 주기」라고 부릅니다. 제목의 Agent는 실습 앱의 에이전트 그래프입니다. 넘겨 줄 값은 시험 때 다른 함수로 바꿔 낄 수 있습니다. 그런데 바꿔 낀 것을 지우지 않으면, 다음 테스트의 결과까지 바뀝니다. 이 절의 Before가 그 장면입니다.

3앞에서 배운 내용

01절에서는 앱 객체에 요청 방식·요청 주소와 처리 함수를 잇고, 시험용 클라이언트로 요청을 넣었습니다. 처리 함수의 매개변수 힌트에 입력 형식을 적어, 빈 질문을 몸통 전에 422로 멈추게 했습니다. 이 절은 같은 매개변수 힌트 자리에 의존성을 적습니다. 실습 폴더의 앱 파일은 이 절에서 처음 가져옵니다.

Ch 13 02절의 표시 Annotated는 자료형 옆에 함께 쓸 정보를 적어 두는 표시였습니다. 그 절에서는 둘째 자리에 합칠 함수를 적었고, 이 절에서는 값을 줄 함수를 적습니다. Ch 2 12절의 await와, Ch 28 01절에서 쓴 셀 맨 위 await 줄도 씁니다. Ch 16 05절에서 받은 오류 TimeoutError는 이 절 실습 앱의 504 응답 뒤에 있습니다.

Ch 2 11절에서는 목록 하나를 함께 쓴 두 테스트 가운데, 둘째 테스트가 앞 테스트의 노트를 받았습니다. 테스트마다 따로 준비한 값으로 실행하는 테스트 격리가 깨진 장면이었습니다. B 트랙의 절이라, A 트랙은 이 뜻을 여기서 처음 봐도 됩니다. 그 절 끝에서 예고한 대로, 이 절은 한 테스트가 남긴 재정의가 다음 질문까지 이어지는 실패를 다룹니다.

Ch 23 03절에서는 객체의 수명을 배웠습니다. 객체를 만든 때부터, 닫혀서 더 쓸 수 없게 된 때까지입니다. 이 절은 실습 앱이 에이전트 그래프를 언제 만들고, 요청마다 어떤 객체를 넘기는지 봅니다. 접근 토큰은 Ch 28 03절의 말이고, 이 절에서는 요청을 보낼 때 한 번 적습니다.

4핵심 개념

비유로 시작하기

화물역에서는 열차를 떠나보내기 전에 맨 앞에 기관차를 붙입니다. 평소에는 늘 쓰는 파란 기관차를 붙이기로 정해져 있습니다. 시험 운행 날에는 그 약속을 작은 주황 시험용 기관차로 바꿔 둡니다. 시험이 끝나도 바꾼 약속을 되돌리지 않으면, 다음 열차도 주황 기관차를 달고 떠납니다.

짐칸이 처리 함수이고, 앞에 붙는 기관차가 제공 함수가 내놓는 값입니다. 어느 기관차를 붙일지 정한 약속이 재정의 딕셔너리입니다. 파란 기관차는 원래 제공 함수, 주황 기관차는 시험용으로 바꿔 낀 함수입니다. 짐칸은 그대로인데, 약속 하나 때문에 다음 열차까지 달라집니다.

비유와 다른 점이 있습니다. 실제 앱에서는 기관차 한 대가 열차 둘을 끄는 것이 아닙니다. 요청마다 바꿔 낀 함수가 새로 불려 값을 내놓습니다.

그림 읽기 — 흰 바탕에 선로 세 줄이 위아래로 있습니다. 가운데와 아래 선로의 두 열차는 똑같이 초록 짐칸 둘을 달았고, 맨 앞에 작은 주황 기관차가 하나씩 붙어 있습니다. 맨 위 짧은 선로에는 큰 파란 기관차 하나가 짐칸 없이 홀로 서 있습니다. 두 열차가 첫 테스트와 다음 테스트, 짐칸이 처리 함수, 주황 기관차가 바꿔 낀 함수가 요청마다 내놓은 값입니다. 파란 기관차는 쓰이지 않은 원래 제공 함수이고, 기관차의 크기는 어떤 값과도 짝짓지 않습니다.

의존성과 제공 함수

처리 함수가 쓸 값을 몸통에서 만들지 않고, 라이브러리가 요청마다 넘겨 주게 할 수 있습니다. 패키지 fastapi는 이 약속을 의존성이라고 부릅니다. 의존성은 표시 Annotated의 둘째 자리에 함수 Depends로 적습니다. 함수 Depends에는 값을 줄 함수를 부르지 않고 넘깁니다.

요청이 오면 라이브러리가 그 함수를 불러, 내놓은 값을 매개변수에 넣고 처리 함수를 부릅니다. 설치판 fastapi 0.135.0 dependencies/utils.py 675~676행이 비동기 제공 함수를 await로 부르는 자리입니다. FastAPI 문서는 표시를 이름에 담아, 여러 처리 함수에서 함께 쓰는 모양을 보여 줍니다. 실습 앱 파일의 TimeoutDep도 같은 모양입니다.

말뜻
의존성(dependency)처리 함수가 쓸 값을 라이브러리가 요청마다 만들어 넘겨 주도록 적어 둔 약속입니다. 도서관에 책을 신청해 두면, 자리에 앉을 때마다 사서가 그 책을 책상에 놓아 주는 것과 같습니다. 이 절에서는 LimitDep = Annotated[float, Depends(get_limit)]로 적고, 매개변수 힌트 limit: LimitDep에 씁니다.
제공 함수의존성에 적어, 처리 함수에 넘길 값을 만들어 내놓는 함수입니다. 신청한 책을 서고에서 꺼내 오는 사서의 일과 같습니다. 이 절에서는 연습 앱의 get_limit과 실습 앱의 get_agent·get_timeout·require_token입니다.
재정의(override) · 재정의 딕셔너리제공 함수를 다른 함수로 바꿔 끼우는 일입니다. 앱 객체의 딕셔너리 dependency_overrides에 원래 함수를 키로, 바꿔 낄 함수를 값으로 적습니다. 시험 날에만 다른 책을 놓아 달라고 신청서를 고쳐 두는 것과 같습니다. 이 절에서는 get_timeout 대신 zero_timeout을 적어 시간 제한을 0초로 바꿉니다.
상태 코드 504기다리던 쪽이 정한 시간 안에 답을 받지 못했다는 뜻의 상태 코드입니다. 택시가 약속 시간까지 오지 않아 예약이 취소된 것과 같습니다. 이 절에서는 실습 앱의 처리 함수가 시간 제한을 넘기면 이 값으로 답합니다.

새 말을 이 절 코드에서 보면 이렇습니다. 요청 두 번에 제공 함수의 기록이 ['get_limit', 'get_limit']이 되었습니다. 재정의를 적자 응답이 {'limit': 0.5}로 바뀌었고, 기록은 []였습니다. 시간 제한 0초를 재정의한 실습 앱은 상태 코드: 504로 답했습니다.

재정의 딕셔너리

앱 객체의 속성 dependency_overrides는 평범한 딕셔너리입니다. 원래 제공 함수를 키로, 바꿔 낄 함수를 값으로 적습니다. 라이브러리는 요청이 올 때마다 이 딕셔너리에서 제공 함수를 찾고, 있으면 값 쪽 함수를 부릅니다. 설치판 dependencies/utils.py 629~643행이 그 자리입니다.

이 딕셔너리는 앱 객체의 속성이라, 적은 셀이 끝나도 지우기 전까지 남습니다. 새 시험용 클라이언트를 만들어도, 같은 앱 객체에 요청하면 재정의가 그대로 쓰입니다. FastAPI 문서는 테스트 함수 처음에 재정의를 적고, 끝에서 비우라고 적습니다.

실습 앱의 의존성과 객체의 수명

실습 앱의 처리 함수 chat은 의존성 셋을 받습니다. 제공 함수 get_agent는 에이전트 그래프를, get_timeout은 시간 제한 2.0초를 내놓습니다. 제공 함수 require_token은 요청 머리의 접근 토큰을 검사하고, 맞지 않으면 401로 답합니다. 설치판 routing.py 452~462행은 의존성을 먼저 풀고, 그 뒤에 처리 함수 쪽으로 갑니다. 그래서 의존성이 401로 멈추면 처리 함수 몸통은 실행되지 않습니다.

제공 함수 get_agent는 요청마다 불리지만, 내놓는 그래프는 늘 같은 객체였습니다. 그래프 파일 agent.py 46행이 파일을 가져올 때 그래프를 한 번 만들기 때문입니다. 이 그래프를 닫는 줄은 없어서, 앱을 가져온 프로그램이 끝날 때까지 같은 객체가 쓰입니다. Ch 23 03절의 말로 하면, 이 그래프의 수명은 프로그램과 같습니다.

모델을 부르는 에이전트를 만드는 live_agent.py는 줄 @lru_cache(maxsize=1)로 처음 만든 에이전트를 기억해 둡니다. 첫 요청 때 한 번 만들고, 다음 요청부터는 같은 객체를 씁니다. 이 줄은 설치판 소스로만 보았고, 노트북에서는 실행하지 않았습니다. 이 앱에는 앱의 시작과 끝에 할 일을 적는 lifespan 설정이 없습니다. 그래프를 만드는 데 걸린 시간은 재지 않았습니다.

시간 제한과 상태 코드 504

처리 함수 chat의 몸통은 함수 asyncio.wait_for로 에이전트 그래프 실행에 시간 제한을 겁니다. 이 함수는 코루틴을 기다리다가, 정한 초 안에 끝나지 않으면 멈추고 오류 TimeoutError를 일으킵니다. 몸통은 이 오류를 받아 상태 코드 504로 답합니다. 앱 파일 76~83행이 이 자리입니다.

시간 제한이 0초이면 그래프는 끝날 틈이 없어, 처리 함수는 504로 답합니다. 설치판 Python 3.12.13 asyncio/tasks.py 507~517행은 시간 제한이 0 이하이면 작업을 기다리지 않고 취소합니다. 그래서 이 절의 504는 다시 실행해도 같게 나옵니다. 노트북 밖에서도 같은 장면을 다섯 번 실행해 모두 같았습니다.

5실행 예제

노트북 2절은 연습 앱에 의존성을 적고, 요청 두 번에 제공 함수가 몇 번 불리는지 봅니다. 이어서 재정의를 적고 같은 요청을 넣어, 받는 값과 불린 기록을 견줍니다. 3절은 실습 앱을 가져와, 의존성을 적은 줄과 처리 함수 chat의 정의 줄을 읽습니다. 제공 함수 둘을 직접 부르고, 접근 토큰 없이 한 번과 적어서 한 번 질문을 보냅니다.

모델 요청은 0번이고, API 키 없이 실행합니다. 서버 프로그램을 띄우지 않아 네트워크·포트·자식 프로세스를 쓰지 않습니다. 실습 폴더의 앱 파일을 가져오고 읽기만 하며, 쓰는 파일은 없습니다. 걸린 시간은 재지 않았습니다.

7주의할 점과 실무 메모

  • FastAPI 문서의 예는 재정의를 비울 때 딕셔너리를 {}로 새로 적습니다. 이 절은 딕셔너리의 메서드 clear로 비웠고, 문서의 방법은 실행하지 않았습니다. 재정의 하나만 지우는 메서드 pop도 이 절에서는 쓰지 않았습니다.
  • 테스트를 pytest로 쓴다면, 비우는 줄을 테스트 함수 끝이나 Ch 2 11절의 픽스처에 둡니다. 테스트가 중간에 실패하면 함수 끝의 줄까지 가지 못합니다. 이 절에서는 pytest를 실행하지 않았습니다.
  • 폴더 agent_service의 첫 파일 __init__.py는 앱 객체를 이름 app으로 내보냅니다. 그래서 가져올 때는 from agent_service.app import … 모양을 씁니다. 줄 import agent_service.app 뒤의 이름 agent_service.app은 파일이 아니라 앱 객체를 가리킵니다. 이 사실은 노트북 밖에서 확인했습니다.
  • 시험용 클라이언트는 with 없이 만들었습니다. FastAPI 문서는 lifespan이 있는 앱이면 with TestClient(app)일 때만 시작과 끝의 할 일이 돈다고 적습니다. 이 앱에는 lifespan이 없고, 이 절에서 실행하지도 않았습니다.
  • 접근 토큰 local-demo-token은 교재용 값입니다. 앱 파일 57행은 환경 변수 DEMO_API_TOKEN이 있으면 그 값을 씁니다. 인증은 07절에서 자세히 봅니다.
  • 앱 파일에는 이 절이 풀지 않은 줄도 있습니다. 나머지 처리 함수 넷과 그 의존성은 뒤 절에서 봅니다.
  • 걸린 시간은 재지 않았습니다. 교재 출력은 Linux의 Python 3.12.13으로 만들었고, 다른 판과 Windows·macOS에서는 실행하지 않았습니다.

8정리와 다음 절

  • 매개변수 힌트에 의존성을 적자, 라이브러리가 요청마다 제공 함수를 불러 값을 넘겼습니다.
  • 재정의 딕셔너리에 바꿔 낄 함수를 적자, 처리 함수는 그대로인 채 받는 값이 바뀌었습니다.
  • 첫 테스트가 남긴 재정의로 다음 테스트도 504를 받았고, 딕셔너리를 비우자 200이 왔습니다.

다음 학습과 이어지는 지점 — 03절에서는 처리 함수 몸통이 에이전트 그래프를 부르는 줄을 봅니다. 비동기 그래프를 await로 기다려 부르는 방법입니다.

9복습 문제

문제 5개 · 해설 포함

1. 연습 앱에 같은 요청을 두 번 넣었을 때, 제공 함수가 불린 기록은 무엇이었나요?

기록은 ['get_limit', 'get_limit']이었습니다. 라이브러리가 요청 한 번에 제공 함수를 한 번씩 불렀습니다. 틀렸다면 노트북 2절을 다시 읽습니다.

2. 연습 앱에 재정의를 적은 뒤 받은 응답과 기록은 무엇이었나요? 처리 함수를 고쳤나요?

응답은 {'limit': 0.5}, 기록은 빈 목록이었습니다. 처리 함수는 고치지 않았고, 원래 제공 함수는 한 번도 불리지 않았습니다. 틀렸다면 노트북 2절을 다시 읽습니다.

3. Before에서 다음 테스트는 새 시험용 클라이언트를 만들었는데도 504를 받았습니다. 까닭은 무엇인가요?

재정의는 클라이언트가 아니라 앱 객체의 딕셔너리에 남아 있었기 때문입니다. 그때 재정의 딕셔너리의 키 수는 1이었습니다. 틀렸다면 노트북 4절을 다시 읽습니다.

4. 동료가 「다음 테스트가 200을 받았으니 재정의는 남아 있지 않다」고 말합니다. 맞나요?

맞지 않습니다. 6절에서 2초를 내놓는 재정의를 남기자, 상태 코드는 200인데 키 수는 1이었습니다. 남은 재정의는 키 수로 확인합니다. 틀렸다면 노트북 6절을 다시 읽습니다.

5. 제공 함수 get_agent를 두 번 불러 받은 그래프가 같은 객체였던 까닭은 무엇인가요?

그래프 파일이 가져올 때 그래프를 한 번 만들고, 제공 함수는 늘 그 객체를 내놓기 때문입니다. 그래프를 닫는 줄이 없어, 프로그램이 끝날 때까지 같은 객체가 쓰입니다. 틀렸다면 노트북 3절과 본문 4블록을 다시 읽습니다.
