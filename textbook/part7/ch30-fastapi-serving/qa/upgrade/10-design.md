## 1. 상황과 한 요청 흐름

도서관 웹 화면(허용 출처 `http://localhost:5173` — 앱 21행, 07절)이 질문 「반납 기한을 알려 주세요」(03~07절과 같은 질문)를 요청 주소 `/v1/chat/stream`에 보냅니다. SSE 사건 둘을 받은 뒤 연결이 끊겼다고 보고(06절과 같은 자리), 마지막 사건 번호로 이어 받습니다. 흐름은 한 차례로 이어집니다.

1. **사전 요청**(07절) — `OPTIONS /v1/chat/stream`, 요청 머리 `Origin`·`Access-Control-Request-Method: POST`·`Access-Control-Request-Headers: Authorization, Content-Type`(07절과 같은 글) → 상태 코드와 허용 출처 응답 머리(`header_or_none` — 07절 함수).
2. **첫 요청**(05절 SSE + 07절 접근 토큰) — `POST /v1/chat/stream`, 요청 머리 `Origin`·`Authorization` → 200이면 `read_events`(06)로 칸 딕셔너리 목록, 아니면 빈 목록.
3. **끊김** — 앞 사건 둘만 받은 것으로 봄(`[0:2]`, 06절 4절과 같은 자리).
4. **사전 요청(이어 받기)**(07절) — 이어 받기 요청은 요청 머리 `Last-Event-ID`를 더 싣기 때문에, 흐름이 그 머리 이름까지 적은 사전 요청을 한 번 더 보냄(앱 24행 `allow_headers`에 `Last-Event-ID`가 있음 — 07절 출력 「허용 요청 머리」). 브라우저가 언제 사전 요청을 다시 보내는지는 실행하지 않음(b7).
5. **이어 받기**(06절) — 받은 마지막 사건 번호(`last_event_id` — 06절 함수)를 요청 머리 `Last-Event-ID`에 실어 다시 요청 → 이은 목록. 번호가 없으면(받은 사건 0) 4·5단계를 보내지 않음.
6. **판정**(06절·04절) — 이은 목록의 마지막 사건이 `done`인가(`ended_with_done`) · 이어 붙인 글(`token_values` → `join_tokens`)이 끊기지 않은 기준 응답의 글과 같은가.

기록 장치: 단계마다 `[단계 이름, 상태 코드, 허용 출처]` 한 줄을 목록에 더하고(`record_step`), 표로 출력(`print_log`).

## 2. 실행 1과 실행 2 — 값 하나만

| | 실행 1 | 실행 2 |
|---|---|---|
| 접근 토큰(요청 머리 `Authorization`) | `Bearer local-demo-token`(앱 57행 기본값 — 02·07절 교재용 접근 토큰) | **`Bearer wrong-token`**(07절 2절에서 쓴 틀린 값) |
| 그 밖 | 출처·질문·스레드 이름 `web-1`·끊기는 자리 둘·사전 요청 머리 이름 모두 같음 | 같음 |

- 손으로 적은 값은 모두 실행 전에 정함: 질문(03~07절) · 출처(앱 21행) · 두 접근 토큰(앱 57행·07절) · 스레드 이름 `web-1`(이 절에서 정함 — 이름 규칙 `^[a-zA-Z0-9_-]{1,64}$` 안) · 끊기는 자리 2(06절) · 사전 요청 머리 이름 글(07절 + `Last-Event-ID`). 노트북 출력 라벨과 b7에 출처를 적음.
- **바꾼 값을 접근 토큰으로 고른 까닭**: 07절도 틀린 접근 토큰에 401을 받았으므로(요청 주소 `/v1/chat`, 요청 머리 `Origin` 없음) 401 자체는 새것이 아님 → b2 「새로 볼 것」은 실행이 보인 만큼만(Ch 26 05 검토 B-7): ① 사전 요청은 접근 토큰을 싣지 않아 두 실행 모두 200 ② 401 응답에도 허용 출처 응답 머리가 붙음 ③ 흐름이 첫 요청에서 멈춰 이어 받기 단계를 보내지 않고, 판정은 빈 목록이라 `False`. 다른 후보와 견줌:
  - 허용 출처 하나(`http://localhost:3000`) — 사전 요청 400·SSE 사건은 같고 허용 출처만 `None`. 07절 값 바꿔 보기(모르는 출처 POST → 200·허용 출처 `None`)의 결론을 요청 주소만 바꿔 되풀이 · 흐름 코드가 사전 요청 결과로 멈추게 하려면 브라우저 규칙을 흐름에 흉내 내야 함 → 뺌.
  - `Last-Event-ID` 하나 — 06절이 `sse-1:1`·`sse-1:5`·`other:0`·`sse-1:x`·`sse-1:99`를 모두 보임 → 뺌.
  - 시간 제한 값 하나(0초 재정의) — 06절 Before와 같은 장면 · 재정의가 앱 객체에 남는 위험(02절)을 실습에서 되풀이할 까닭 없음 → 뺌.

## 3. 붙인 앞 절 기능과 뺀 것

- **붙인 것(셋 — 모두 실행 1 흐름 안에서 쓰임)**: **05절** SSE 응답(`/v1/chat/stream`의 SSE 사건 — 칸 `event`·`id`·`data`) · **06절** 이어 받기(요청 머리 `Last-Event-ID`·`last_event_id`·`read_events`·`event_names`·`token_values`·`ended_with_done`) · **07절** CORS 사전 요청과 허용 출처 응답 머리(`header_or_none`)·접근 토큰 검사 401. 받쳐 주는 것: 01절 시험용 클라이언트·입력 형식(질문 본문) · 02절 의존성(처리 함수 머리 99~105행 — `AuthDep`·`TimeoutDep`·`ResumeIndexDep`) · 04절 `join_tokens`.
- **뺀 것과 까닭**: 01절 입력 형식 422(흐름은 올바른 입력만 보냄) · 02·06절 시간 제한 재정의(위) · 03절 `ainvoke`·JSON 요청 주소 `/v1/chat`(스트림 흐름 하나에 모음) · 04절 `astream` 직접 부르기(앱이 안에서 부름) · 07절 `HTTPBearer` 새 앱(실습 앱은 고치지 않음) · 08절 응답 문서(요청 흐름이 아님 — 응답 문서 해시는 노트북 밖에서 그대로인지 확인) · 09절 실제 모델(챕터 결정 M0 · 09 인계 권고 — 모델 요청 0, Ch 23·24 실습 선례).
