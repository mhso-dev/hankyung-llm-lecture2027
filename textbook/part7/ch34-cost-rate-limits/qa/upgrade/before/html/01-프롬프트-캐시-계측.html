1학습 목표

  • 프롬프트 캐시가 재사용하는 공통 접두어를 구성할 수 있습니다.
  • 실제 API 사용량에서 캐시 읽기 토큰과 일반 입력 토큰을 분리할 수 있습니다.
  • API가 제공하지 않는 캐시 생성 값은 0이 아니라 None으로 기록할 수 있습니다.

2이 내용을 배우는 이유

서비스가 같은 정책 문서와 도구 설명을 요청마다 다시 보내면 입력 토큰이 반복됩니다. 프롬프트 캐싱(prompt caching)은 같은 접두어의 내부 계산을 재사용해 지연과 비용을 줄입니다. 그러나 설정만 보고 절감 효과를 확인할 수는 없습니다. 실제 응답의 사용량에서 몇 토큰을 캐시로 읽었는지 확인해야 합니다.

3앞에서 배운 내용

Ch 6에서는 모델 응답의 입력·출력 토큰을 기록했고, Ch 15에서는 추적 항목에서 캐시 읽기와 생성을 구분했습니다. 이번 절은 그 기록을 LangChain AIMessage의 실제 usage_metadata와 연결합니다. API 키는 프로젝트 루트의 .env에서 읽으며 값은 출력하지 않습니다.

4핵심 개념

반복되는 문서의 앞부분

매일 같은 신청서를 처리한다고 생각해 봅니다. 양식과 규칙은 그대로이고 마지막 문의만 바뀝니다. 캐시는 양식과 규칙에 해당하는 앞부분을 재사용합니다. 따라서 변하지 않는 지시문과 예시는 앞에 두고, 요청마다 바뀌는 질문은 뒤에 둡니다.

접두어(prefix)
입력의 처음부터 이어지는 같은 토큰 구간입니다.
캐시 읽기(cache read)
이전에 계산한 접두어를 다시 사용한 입력 토큰 수입니다.
캐시 생성(cache creation)
다음 요청에서 읽을 수 있도록 새로 저장한 구간의 양입니다.
적중(cache hit)
요청 접두어가 저장된 접두어와 일치해 재사용된 상태입니다.

OpenAI 공식 문서는 자동 캐싱이 1,024토큰 이상의 프롬프트에서 적용되며, 캐시 사용량은 cached_tokens에서 확인한다고 설명합니다. 이 실습은 충분히 긴 공통 접두어를 두 번 보내고 이 값을 직접 읽습니다.

코드 읽기와 개념 경계

프롬프트 캐시는 입력의 처음부터 같은 토큰 구간을 다시 사용할 때 적용됩니다. 예제는 고정 정책을 긴 stable_prefix로 만들고 마지막 질문만 바꿔 두 번 호출합니다. usage_metadata의 전체 입력 토큰과 input_token_details의 캐시 읽기 값을 따로 기록하므로, 두 번째 호출이 빨랐다는 느낌 대신 제공자가 반환한 사용량으로 적중을 판단합니다.

문장 내용이 비슷해도 앞부분의 토큰 배열이 달라지면 같은 접두어가 아닙니다. 날짜나 사용자 식별자를 맨 앞에 넣으면 뒤의 긴 정책까지 재사용되지 않을 수 있습니다. 반대로 캐시 적중은 답의 품질이나 최신성을 높이지 않으므로, 반복 지시문 안정성과 질문별 근거 갱신을 별도로 관리합니다.

5실행 예제

먼저 실행마다 달라지는 실험 ID와 긴 정책 접두어를 결합하고 같은 모델에 두 번 전송합니다. 고유한 실험 ID는 이전 실행의 캐시와 구분하며, 두 요청 안에서는 같은 값을 유지합니다. 노트북은 두 응답의 본문이 비어 있지 않고 두 번째 요청에서 1,024토큰 이상이 실제로 읽혔는지 검사합니다.

프롬프트 캐시는 입력의 처음부터 같은 토큰 구간을 다시 사용할 때 적용됩니다. 예제는 고정 정책을 긴 stable_prefix로 만들고 마지막 질문만 바꿔 두 번 호출합니다. usage_metadata의 전체 입력 토큰과 input_token_details의 캐시 읽기 값을 따로 기록하므로, 두 번째 호출이 빨랐다는 느낌 대신 제공자가 반환한 사용량으로 적중을 판단합니다.

In [3]:

records = []
for question in questions:
    answer = model.invoke(stable_prefix + "\n" + question)

실험 결과 해석

캐시 적중 여부는 시간 추정이나 파일 수가 아니라 API가 반환한 사용량으로 판정합니다. 생성 토큰이 제공되지 않았다는 사실과 0을 구분합니다.

In [5]:

print("캐시 생성 계측 지원:", records[0]["cache_creation"] is not None)

6실험 결과 해석

2026년 9월 11일 실행에서 첫 호출은 입력 11,805토큰, 캐시 읽기 0토큰이었고 두 번째 호출은 입력 11,804토큰 가운데 11,520토큰을 캐시에서 읽었습니다. 두 번째 호출의 비캐시 입력은 284토큰이었습니다. 두 호출 모두 실제 텍스트와 출력 토큰을 반환했습니다. 이 결과는 해당 실행의 두 요청에서 냉·온 조건을 관찰했다는 뜻이며 모든 요청에서 같은 적중률을 보장하지 않습니다.

cache_creation=None은 생성량이 0이라는 뜻이 아닙니다. 현재 사용한 LangChain usage_metadata에서 별도 생성 값을 얻지 못했다는 뜻입니다. 제공되지 않은 값과 실제 0을 구분해야 비용 대시보드가 잘못된 확신을 주지 않습니다.

7주의할 점과 실무 메모

  • 공통 지시문 가운데 한 토큰이 바뀌어도 그 뒤의 접두어 재사용 범위가 줄 수 있습니다.
  • 캐시 적중은 출력 품질 평가가 아닙니다. 같은 질문의 정답률과 지연을 별도로 측정합니다.
  • 단가는 모델과 처리 방식에 따라 바뀝니다. 사용량 원자료와 단가 기준일을 함께 저장합니다.
  • 긴 접두어를 만들기 위해 불필요한 문장을 추가하면 전체 입력과 관리 비용이 늘 수 있습니다.

8정리와 다음 절

  • 변하지 않는 내용을 앞에 배치하면 같은 접두어를 재사용하기 쉽습니다.
  • 캐시 절감은 cached_tokens로 확인합니다.
  • 제공되지 않은 캐시 생성 값은 0으로 바꾸지 않습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 즉시 응답이 필요 없는 요청을 Batch API 입력으로 묶어 처리 비용을 줄입니다.

9복습 문제

문제와 해설

1. 요청마다 바뀌는 고객 질문을 긴 정책보다 앞에 두면 캐시 재사용에 어떤 영향이 있나요?

접두어가 일찍 달라져 뒤쪽의 같은 정책도 재사용하기 어려워집니다.

2. cache_creation=None을 0으로 저장하면 왜 문제가 되나요?

계측 미지원과 실제 생성량 0을 구분할 수 없기 때문입니다.

3. 캐시 읽기 토큰이 많으면 답의 품질도 높다고 볼 수 있나요?

볼 수 없습니다. 캐시 사용량은 계산 재사용을 나타내며 품질은 별도 평가가 필요합니다.
