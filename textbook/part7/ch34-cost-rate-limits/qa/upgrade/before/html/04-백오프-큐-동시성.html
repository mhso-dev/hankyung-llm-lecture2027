1학습 목표

  • HTTP 429 응답을 통제된 로컬 서버에서 재현할 수 있습니다.
  • 지수 백오프와 지터를 적용해 재시도 간격을 분산할 수 있습니다.
  • 큐와 세마포어로 동시 실행 수를 제한할 수 있습니다.

2이 내용을 배우는 이유

모델 API에는 분당 요청 수와 분당 토큰 수 같은 제한이 있습니다. 요청이 한꺼번에 몰리면 서버는 HTTP 429로 현재 요청을 받을 수 없다고 알릴 수 있습니다. 즉시 같은 요청을 반복하면 다시 제한에 걸리고 전체 서비스의 부하도 커집니다. 재시도 시점과 동시에 처리할 작업 수를 조절해야 합니다.

3앞에서 배운 내용

Ch 16에서는 호출 한도와 재시도 함수를 직접 만들었습니다. Ch 30에서는 FastAPI 비동기 요청 처리를 배웠습니다. 이번 절은 그 두 내용을 운영 흐름으로 연결합니다. 실제 제공자에게 의도적으로 429를 만들지 않고, 로컬 HTTP 서버가 처음 두 요청에만 429를 반환하도록 구성합니다.

4핵심 개념

문이 닫혔을 때 줄을 정리하기

입장 제한이 걸린 장소 앞에서 모든 사람이 동시에 문을 두드리면 혼잡이 커집니다. 대기열은 도착한 순서를 보관하고, 동시성 제한은 안에 들어가는 사람 수를 정합니다. 백오프는 거절된 요청이 다시 시도하기 전 기다리는 시간을 늘립니다.

Rate limit
일정 시간 동안 허용되는 요청이나 토큰의 최대량입니다.
HTTP 429
요청이 너무 많아 현재 처리할 수 없음을 나타내는 상태 코드입니다.
지수 백오프(exponential backoff)
재시도 횟수가 늘수록 대기 시간을 배수로 늘리는 방법입니다.
지터(jitter)
여러 클라이언트의 재시도 시점이 겹치지 않도록 더하는 작은 무작위 지연입니다.
세마포어(semaphore)
동시에 실행할 수 있는 작업 수를 제한하는 동기화 도구입니다.

코드 읽기와 개념 경계

asyncio.Queue는 기다리는 작업을 보관하고, Semaphore(2)는 동시에 처리 구역에 들어갈 작업을 두 개로 제한합니다. queue.get()으로 항목을 꺼내고 처리가 끝난 뒤 task_done()을 호출합니다. 별도의 로컬 HTTP 서버는 처음 두 요청에 429를 반환해, 재시도 없는 호출과 백오프 호출을 같은 조건에서 비교하게 합니다.

지수 백오프는 시도 횟수에 따라 기본 대기 시간을 늘리고 지터는 여러 클라이언트가 같은 순간 다시 요청하는 현상을 줄입니다. 모든 오류를 재시도하면 안 됩니다. 인증 실패나 잘못된 입력은 기다려도 해결되지 않으며, 429와 일시적 5xx도 최대 횟수와 전체 시간 한도 안에서만 재시도합니다.

백오프·큐·동시성 제한

통제된 로컬 HTTP 서버에서 429를 재현하고 재시도 대기와 동시성 제한을 확인합니다.

실행 환경 준비

이 준비 셀이 하는 일

준비 셀은 비동기 큐, 난수 지터, 로컬 HTTP 서버, 시간 측정에 필요한 표준 라이브러리만 불러옵니다. 외부 제공자 API는 호출하지 않습니다. 다음 셀에서 운영체제가 배정한 로컬 포트에 교육용 429 서버를 시작하며, 절이 끝나면 서버를 종료합니다.

from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.error import HTTPError
from urllib.request import urlopen
print("표준 라이브러리 준비 완료")

표준 라이브러리 준비 완료

로컬 429 서버

처음 두 요청에는 429를 반환하고 세 번째 요청부터 200을 반환합니다. 외부 제공자에는 요청하지 않습니다.

In [2]:
class Handler(BaseHTTPRequestHandler):
    count = 0
    def do_GET(self):
        Handler.count += 1
        status = 429 if Handler.count <= 2 else 200
        self.send_response(status); self.end_headers(); self.wfile.write(str(status).encode())
    def log_message(self, *args): pass

server = HTTPServer(("127.0.0.1", 0), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()
url = f"http://127.0.0.1:{server.server_port}/"
print("로컬 서버 준비")
출력:
로컬 서버 준비

큐와 동시성 제한

세마포어가 동시에 처리하는 작업 수를 2개로 제한합니다.

바로 다음 코드를 읽는 방법

asyncio.Queue는 기다리는 작업을 보관하고, Semaphore(2)는 동시에 처리 구역에 들어갈 작업을 두 개로 제한합니다. queue.get()으로 항목을 꺼내고 처리가 끝난 뒤 task_done()을 호출합니다. 별도의 로컬 HTTP 서버는 처음 두 요청에 429를 반환해, 재시도 없는 호출과 백오프 호출을 같은 조건에서 비교하게 합니다.

In [3]:
active = peak = 0
queue, semaphore, completed, waits = asyncio.Queue(), asyncio.Semaphore(2), [], []
for number in range(6): queue.put_nowait((number, time.perf_counter()))
initial_size = queue.qsize()

async def worker():
    global active, peak
    while not queue.empty():
        number, queued_at = await queue.get()
        async with semaphore:
            waits.append(time.perf_counter() - queued_at)
            active += 1; peak = max(peak, active)
            await asyncio.sleep(0.03); completed.append(number); active -= 1
        queue.task_done()

await asyncio.gather(worker(), worker(), worker())
print("초기 큐:", initial_size, "완료:", len(completed), "최대 동시 실행:", peak)
print("대기 발생 작업:", sum(wait > 0 for wait in waits))
assert queue.empty() and peak <= 2
출력:
초기 큐: 6 완료: 6 최대 동시 실행: 2
대기 발생 작업: 6

확인할 점 — 첫 요청은 429를 반환합니다. 백오프 함수는 대기 기록을 남기고 최종 200을 받습니다. 실험에서는 작업 여섯 개를 처리했고, 최대 동시 실행 수는 2였습니다.

6일부러 실패해 보기

재시도 없는 코드는 첫 429를 그대로 호출자에게 전달합니다. 수정 코드에서는 429만 재시도하며, 다른 HTTP 오류는 숨기지 않습니다. 대기 시간은 0.05 × 2^attempt에 작은 지터를 더해 계산합니다. 실제 운영에서는 응답 헤더의 재시도 안내와 SDK의 내장 재시도 정책도 함께 확인합니다.

지수 백오프와 지터 적용

시도 횟수가 늘수록 대기 시간을 늘리고 작은 무작위 지연을 더합니다.

이 단계에서 구분할 범위

지수 백오프는 시도 횟수에 따라 기본 대기 시간을 늘리고 지터는 여러 클라이언트가 같은 순간 다시 요청하는 현상을 줄입니다. 모든 오류를 재시도하면 안 됩니다. 인증 실패나 잘못된 입력은 기다려도 해결되지 않으며, 429와 일시적 5xx도 최대 횟수와 전체 시간 한도 안에서만 재시도합니다.

In [5]:
def fetch_with_backoff(target, attempts=4):
    waits = []
    for attempt in range(attempts):
        try:
            return urlopen(target).status, waits
        except HTTPError as error:
            if error.code != 429 or attempt == attempts - 1: raise
            delay = 0.05 * (2 ** attempt) + random.uniform(0, 0.01)
            waits.append(round(delay, 3)); time.sleep(delay)

status, waits = fetch_with_backoff(url)
print("최종 상태:", status, "대기:", waits)
server.shutdown(); assert status == 200
출력:
최종 상태: 200 대기: [0.052]

7주의할 점과 실무 메모

  • 실패한 요청도 Rate limit 계산에 포함될 수 있으므로 무제한 재시도를 두지 않습니다.
  • 응답을 이미 일부 처리한 비멱등 작업은 같은 요청을 다시 실행하기 전에 중복 효과를 확인합니다.
  • 큐가 계속 길어지면 대기 시간 상한, 취소, 우선순위 정책이 필요합니다.
  • 세마포어의 적정 값은 계정 등급, 모델, 평균 입력 토큰에 따라 달라집니다.

8정리와 다음 절

  • 429는 즉시 반복하지 않고 제한된 횟수로 백오프합니다.
  • 지터는 여러 요청이 같은 시점에 다시 몰리는 현상을 줄입니다.
  • 큐와 세마포어는 유입량과 동시 실행량을 분리합니다.

9복습 문제

문제와 해설

1. 429 직후 같은 간격으로 모든 클라이언트가 재시도하면 어떤 문제가 생기나요?

재시도 시점이 다시 겹쳐 제한과 부하가 반복될 수 있습니다.

2. 지터의 역할은 무엇인가요?

재시도 시점을 조금씩 다르게 만들어 요청 집중을 줄입니다.

3. 이번 실습이 실제 제공자의 과부하를 재현했다고 말할 수 있나요?

말할 수 없습니다. 통제된 로컬 서버에서 HTTP 429 처리만 재현했습니다.
