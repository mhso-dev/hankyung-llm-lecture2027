1학습 목표

  • 데코레이터가 함수를 받아 새 함수를 반환하는 과정을 설명할 수 있습니다.
  • functools.wraps로 원래 함수의 이름·설명·서명을 유지할 수 있습니다.
  • contextmanager와 try/finally로 예외 발생 여부와 관계없이 자원을 정리할 수 있습니다.

2이 내용을 배우는 이유

여러 함수에서 호출 시각 기록, 권한 확인, 재시도 같은 공통 처리를 반복하면 핵심 기능보다 부가 코드가 많아집니다. 데코레이터는 공통 처리를 한곳에 정의하고 필요한 함수에 적용하게 합니다. 파일·연결·잠금처럼 사용 뒤 정리가 필요한 자원은 정상 처리뿐 아니라 예외 경로에서도 정리되어야 합니다. 컨텍스트 매니저는 시작과 정리 규칙을 묶어 with 문에서 재사용하게 합니다. 이 절은 A 경로 01~08절을 마친 학생이 선택하는 B 경로 확장 학습입니다. Ch 18에서는 API 호출의 기록과 재시도에, Ch 30에서는 서비스 자원의 수명 관리에 같은 구조가 이어집니다.

3앞에서 배운 내용

04절에서 함수를 정의하고 호출하면 인자가 매개변수에 연결되고 return 값이 호출 위치로 반환된다고 배웠습니다. 이번 절에서는 함수 자체도 다른 함수의 입력과 반환으로 사용할 수 있다는 새 내용을 추가합니다. 05절에서는 try와 except로 예외가 발생한 경로를 처리했습니다. finally가 예외 여부와 관계없이 실행되는 규칙과 with가 준비·정리를 묶는 규칙은 이 절에서 처음 정의합니다. 07절의 타입힌트는 B 경로에서 배웠지만, 데코레이터 예제의 보조 타입 표기는 제거하여 함수의 입력과 반환에 집중합니다.

4핵심 개념

쉬운 예

건물 출입구에서 모든 방문자가 같은 절차를 거친다고 생각해 봅니다. 방문 목적은 사람마다 다르지만 입장 기록과 퇴장 기록은 공통입니다. 각 업무 함수 안에 기록 코드를 복사하면 수정할 곳이 늘어납니다. 데코레이터는 업무 함수를 감싸 호출 전후의 공통 절차를 담당합니다. 자원 정리는 대여 물품을 반납하는 절차와 비슷합니다. 업무 중 문제가 생겨도 반납 규칙은 실행되어야 합니다.

정의와 표기 읽기

데코레이터(decorator)는 함수를 입력으로 받아 기능을 덧붙인 새 함수를 반환하는 호출 가능한 객체입니다. @trace를 normalize_title 정의 바로 위에 쓰면 함수 정의 시점에 normalize_title = trace(normalize_title)가 실행된 것과 같습니다. trace의 입력 func에는 원래 함수가 들어가고, 반환된 wrapper가 이후 normalize_title 이름에 연결됩니다. 따라서 나중에 normalize_title(" 월간 보고서 ")를 호출하면 래퍼가 먼저 실행되고 래퍼 내부에서 원래 함수가 호출됩니다.

래퍼(wrapper)는 원래 함수를 감싸는 내부 함수입니다. *args는 이름 없이 위치로 전달된 인자를 튜플로 받고, **kwargs는 이름을 붙여 전달된 인자를 딕셔너리로 받습니다. func(*args, **kwargs)는 받은 인자를 원래 함수에 다시 전달하고, 그 반환값을 래퍼가 호출자에게 반환합니다. 메타데이터(metadata)는 함수 이름, 설명, 서명처럼 함수를 설명하는 정보이며 functools.wraps가 이를 래퍼에 복사합니다.

컨텍스트 매니저(context manager)는 with 블록에 들어갈 때 준비하고 나올 때 정리하는 규칙을 가진 객체입니다. with managed_resource() as managed:는 관리자를 호출해 준비를 시작하고, yield current가 내보낸 자원을 managed에 연결한 뒤 블록을 실행한다고 읽습니다. 블록이 끝나거나 예외로 중단되면 실행은 yield 다음 문장으로 이어집니다. 종료 코드를 finally에 두면 두 경로 모두에서 정리됩니다.

도식 읽기

도식의 위쪽은 장식 시점에 원래 함수가 trace로 들어가 래퍼로 바뀌는 단계와, 호출 시점에 래퍼가 시작 기록·원래 함수 호출·완료 기록·결과 반환을 수행하는 단계를 나누어 보여 줍니다. 아래쪽은 같은 RuntimeError가 발생했을 때 Before에서는 정리 코드에 도달하지 못하고 After에서는 finally가 자원을 정리하는 결과를 비교합니다. 두 경우 모두 오류는 발생하며 정리 위치만 다릅니다.

5실행 예제

먼저 trace(func)를 정의합니다. 입력은 장식할 함수 객체이고 반환은 내부 함수 wrapper입니다. @wraps(func)는 이 래퍼의 정보를 원래 함수와 맞춥니다. 이어서 @trace 아래에 normalize_title()을 정의하면 장식이 즉시 적용됩니다. 이후 제목 문자열을 호출 인자로 주면 래퍼가 호출 시작을 출력하고, 원래 함수에 문자열을 전달해 공백을 제거한 값을 받은 뒤, 완료를 출력하고 그 값을 반환합니다.

실제 출력 호출 시작, 호출 완료, 결과의 순서는 공통 처리와 호출자의 출력 시점을 보여 줍니다. 다음 셀의 inspect.signature()는 장식된 함수가 받는 매개변수 표기를 반환합니다. 마지막 셀은 공백이 없는 제목만 입력으로 바꾸어도 같은 래퍼와 원래 함수가 호출되는지 확인합니다.

데코레이터와 컨텍스트 매니저

함수 호출 전후의 공통 처리와 자원 정리를 어떻게 안전하게 재사용하는지 확인합니다.

실행 환경 준비

이 노트북은 Python 3.12 표준 라이브러리만 사용합니다. A 경로 01~08절을 마친 뒤 선택하는 B 경로 확장 실습입니다. 04절의 함수 호출과 반환, 05절의 예외 처리를 사용합니다. finally와 with의 실행 규칙은 이 절에서 처음 정의합니다.

In [1]:
# 필요한 표준 라이브러리를 가져옵니다.
import inspect
from contextlib import contextmanager
from functools import wraps
print("Python 표준 라이브러리 준비 완료")
출력:
Python 표준 라이브러리 준비 완료

기본 실행: 함수의 앞뒤에 기록을 더하기

@trace는 함수 정의 시점에 바로 아래 원래 함수를 trace()에 입력하고, 반환된 wrapper를 같은 함수 이름에 연결하는 표기입니다. 나중에 장식된 함수를 호출하면 래퍼가 먼저 실행하고 func(*args, **kwargs)로 받은 인자를 원래 함수에 전달합니다. 래퍼는 원래 함수의 결과를 다시 호출자에게 반환합니다. wraps는 원래 함수의 이름과 설명을 새 함수에 복사합니다.

In [2]:
# 원래 함수 정보를 유지하는 호출 기록 데코레이터를 만듭니다.
def trace(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        print(f"호출 시작: {function.__name__}")
        result = function(*args, **kwargs)
        print(f"호출 완료: {function.__name__}")
        return result
    return wrapper

@trace
def normalize_title(title: str) -> str:
    """제목 양쪽의 공백을 제거합니다."""
    return title.strip()

print("결과:", normalize_title("  월간 보고서  "))
출력:
호출 시작: normalize_title
호출 완료: normalize_title
결과: 월간 보고서

중간 결과 관찰: 원래 함수 정보 유지

디버거와 문서 생성기는 __name__, __doc__, 함수 서명을 읽습니다. inspect.signature()는 함수가 받는 매개변수와 예상 반환 타입 표기를 반환합니다. wraps를 썼으므로 장식 뒤에도 (title: str) -> str를 확인할 수 있습니다.

In [3]:
# 장식된 함수의 이름·설명·서명을 확인합니다.
print("함수 이름:", normalize_title.__name__)
print("함수 설명:", normalize_title.__doc__)
print("함수 서명:", inspect.signature(normalize_title))
assert normalize_title.__name__ == "normalize_title"
출력:
함수 이름: normalize_title
함수 설명: 제목 양쪽의 공백을 제거합니다.
함수 서명: (title: str) -> str

값 하나를 바꿔 비교: 공백 없는 입력

같은 함수에 공백이 없는 제목을 전달합니다. 데코레이터가 입력값을 바꾸지 않고 원래 함수에 전달하는지 확인합니다.

In [4]:
# 공백이 없는 입력 한 가지만 바꿔 같은 함수를 실행합니다.
changed_title = normalize_title("월간 보고서")
print("공백 없는 결과:", changed_title)
assert changed_title == "월간 보고서"
출력:
호출 시작: normalize_title
호출 완료: normalize_title
공백 없는 결과: 월간 보고서

확인할 점 — 장식된 함수의 이름은 wrapper가 아니라 normalize_title로 출력됩니다. (title: str) -> str는 문자열 제목을 받아 문자열을 반환한다는 서명입니다. 기록 두 줄 뒤에 반환값이 출력되므로 래퍼가 결과를 잃지 않고 호출자에게 전달했음을 확인할 수 있습니다.

6일부러 실패해 보기

Before 코드는 자원을 만든 뒤 의도적으로 RuntimeError를 발생시킵니다. close()가 정상 처리 문장 뒤에 있으므로 해당 문장까지 실행되지 않습니다. 실제 출력의 닫힘: False는 정리가 누락되었음을 보여 줍니다.

After의 @contextmanager는 yield를 한 번 사용하는 함수에 컨텍스트 매니저 규칙을 부여하여 with에서 호출할 수 있게 합니다. 같은 오류가 with managed_resource() 안에서 발생하면 관리자의 finally가 먼저 정리 실행을 출력하고, 예외 처리 뒤 닫힘 상태는 True입니다. 이 결과는 예외가 없어졌다는 뜻이 아닙니다. 오류는 호출자가 처리하고, 컨텍스트 매니저는 자원 정리를 보장합니다.

앞의 실행 예제를 실행한 같은 노트북에서 Before 다음 After 순서로 실행합니다. 출력은 실제 실행 결과입니다.

Before — 실패 코드

Before: 예외가 발생하면 정리 코드에 도달하지 못함

close()를 정상 경로 끝에만 쓰면 작업 중 예외가 발생했을 때 자원이 열린 상태로 남습니다.

In [5]:
# 예외가 정리 문장보다 먼저 발생하는 상황을 재현합니다.
class DemoResource:
    def __init__(self) -> None:
        self.closed = False
    def close(self) -> None:
        self.closed = True

resource = DemoResource()
try:
    raise RuntimeError("처리 중 오류")
    resource.close()
except RuntimeError as error:
    print(type(error).__name__, "/ 닫힘:", resource.closed)
assert resource.closed is False
출력:
RuntimeError / 닫힘: False

After — 수정 코드

After: try/finally로 항상 정리하기

@contextmanager는 yield를 한 번 사용하는 함수에 컨텍스트 매니저 규칙을 부여하여 with에서 호출할 수 있게 합니다. with managed_resource() as managed:는 관리자를 호출해 준비를 시작하고, yield current가 내보낸 자원을 managed에 연결한 뒤 블록을 실행합니다. 블록이 정상 종료되거나 예외로 중단되면 실행은 yield 다음 문장으로 이어집니다. 정리 코드를 finally에 두었으므로 두 경로 모두에서 close()가 호출됩니다.

In [6]:
# finally에서 자원을 닫는 컨텍스트 관리자를 만듭니다.
@contextmanager
def managed_resource():
    current = DemoResource()
    try:
        yield current
    finally:
        current.close()
        print("정리 실행")

managed = None
try:
    with managed_resource() as managed:
        raise RuntimeError("처리 중 오류")
except RuntimeError as error:
    print(type(error).__name__, "/ 닫힘:", managed.closed)
assert managed is not None and managed.closed is True
출력:
정리 실행
RuntimeError / 닫힘: True

7주의할 점과 실무 메모

  • wraps를 생략해도 작은 예제는 실행될 수 있지만 문서 생성기, 디버거, 의존성 주입 도구가 함수 정보를 잘못 읽을 수 있습니다.
  • 래퍼에서 예외를 무조건 잡아 숨기면 호출자가 실패를 알 수 없습니다. 기록 후 다시 발생시키거나 처리 책임을 명확히 정합니다.
  • contextmanager 함수는 yield를 정확히 한 번 수행해야 합니다. 준비 중 실패했다면 아직 얻지 못한 자원을 정리하려 하지 않도록 단계별 상태를 고려합니다.
  • 이 실습의 DemoResource는 정리 순서를 관찰하기 위한 모의 객체입니다. 데이터베이스 연결이나 네트워크 세션의 실제 종료 방식은 해당 라이브러리 문서를 확인합니다.

8정리와 다음 절

  • 데코레이터는 함수 호출 전후의 공통 처리를 재사용합니다.
  • wraps는 원래 함수의 이름·설명·서명을 유지합니다.
  • 컨텍스트 매니저의 finally는 정상 종료와 예외 종료 모두에서 자원을 정리합니다.

다음 학습과 이어지는 지점 — 10절에서는 함수 호출 경계에 들어온 데이터가 정해진 자료형과 범위를 만족하는지 Pydantic으로 확인합니다. Ch 18의 API 호출과 Ch 30의 서비스 자원 관리에서도 이 절의 호출 전후 처리 구조를 다시 사용합니다.

9복습 문제

1. wraps를 쓰는 주된 이유는 무엇인가요?

정답과 해설: 래퍼가 원래 함수의 이름, 문서 문자열, 서명 같은 정보를 유지하게 하기 위해서입니다. 실행 결과만 같다고 함수 정보까지 자동으로 보존되지는 않습니다.

2. contextmanager 함수에서 yield 앞뒤는 각각 무엇을 담당하나요?

정답과 해설: 앞부분은 자원 준비, 뒷부분은 종료 처리를 담당합니다. 종료 처리는 finally 안에 두어 예외 경로에서도 실행하게 합니다.

3. Before 예제에서 자원이 열린 채 남은 직접 원인은 무엇인가요?

정답과 해설: 예외가 resource.close()보다 먼저 발생하여 실행 흐름이 except로 옮겨졌기 때문입니다.

4. 데코레이터가 예외를 잡은 뒤 아무 일도 하지 않고 반환하면 어떤 문제가 생기나요?

정답과 해설: 호출자는 작업 실패를 알지 못하고 성공으로 오해할 수 있습니다. 예외 처리 책임에 따라 다시 발생시키거나 명시적인 실패 값을 반환해야 합니다.
