1학습 목표

  • pyproject.toml에 빌드 시스템을 선언하고 uv로 휠을 만들 수 있습니다.
  • 만든 휠을 격리된 위치에 설치하고 새 프로세스에서 가져올 수 있습니다.
  • pytest fixture와 monkeypatch로 테스트의 목록·환경 변수를 분리할 수 있습니다.

2이 내용을 배우는 이유

코드가 현재 폴더에서 실행된다는 사실만으로 다른 컴퓨터나 프로젝트에서 사용할 수 있다고 판단할 수 없습니다. 패키징은 소스 파일과 버전 정보를 정해진 배포 형식으로 묶고, 설치 과정을 거쳐 가져올 수 있는지 확인합니다. 테스트도 한 번 통과한 결과보다 같은 조건에서 반복해도 같은 결과가 나오는지가 중요합니다. 공유 목록이나 개인 환경 변수에 기대면 테스트 순서와 컴퓨터 설정에 따라 결과가 달라질 수 있습니다. 이 절은 B 경로 선택 학습입니다. Ch 18에서 API 클라이언트를 모듈로 관리하고 Ch 30에서 서비스를 배포할 때 빌드와 격리 검증을 다시 사용합니다.

3앞에서 배운 내용

07절에서 .py 파일을 모듈로 가져왔고, 08절에서 pytest가 test_ 함수와 assert를 실행하는 방법을 배웠습니다. 09절에서 @이름이 바로 아래 함수를 데코레이터에 전달하는 표기임을 배웠으므로 @pytest.fixture도 같은 방식으로 읽을 수 있습니다. Ch 1에서는 실행 환경을 맞추기 위해 uv 프로젝트와 잠금 파일을 만들었습니다. 여기서는 설치 가능한 배포 파일을 만드는 별도 예제 프로젝트에 [build-system]을 선언합니다. 10절의 Pydantic은 이 절의 필수 선행 지식이 아닙니다.

4핵심 개념

쉬운 예

작성 중인 원고 폴더와 출판된 책은 역할이 다릅니다. 원고 폴더를 다른 사람에게 그대로 전달하면 어떤 파일을 어디에 두어야 하는지 알기 어렵습니다. 패키지는 설치 도구가 읽을 이름, 버전, 소스 위치를 함께 제공합니다. 테스트 격리는 시험지를 풀 때마다 새 답안지를 지급하는 것과 비슷합니다. 이전 테스트가 남긴 표시가 다음 테스트의 정답에 영향을 주지 않아야 합니다.

정의와 표기 읽기

패키지(package)는 함께 배포하고 가져올 Python 모듈의 묶음입니다. 이 실습에서 src/report_tools/__init__.py는 import할 코드이고, pyproject.toml은 프로젝트 이름·버전·빌드 방법을 설명하는 설정 파일입니다. TOML의 [project]와 [build-system]은 설정 구역 이름이며, 아래의 name = "report-tools" 같은 문장은 키와 값을 연결합니다. 배포 이름에는 하이픈을 사용하지만 Python 코드에서는 import report_tools처럼 밑줄 이름으로 가져옵니다.

빌드 백엔드(build backend)는 소스와 설정을 읽어 배포 파일을 만드는 도구입니다. uv build --wheel을 호출하면 uv가 [build-system]에 지정된 uv_build를 사용합니다. 휠(wheel)은 설치할 코드와 메타데이터를 담은 .whl 파일입니다. 빌드는 휠 파일을 만드는 처리이고, 설치는 그 파일을 Python 환경에 배치해 import할 수 있게 하는 별도 처리입니다.

테스트 격리(test isolation)는 각 테스트가 독립된 준비 상태에서 실행되게 하는 원칙입니다. @pytest.fixture 아래의 items()는 준비 함수입니다. 테스트가 def test_add_alpha(items):처럼 같은 이름을 매개변수로 적으면 pytest가 호출 직전에 fixture를 실행하고 반환된 빈 목록을 전달합니다. 기본 함수 범위에서는 각 테스트 호출마다 새 목록이 반환됩니다.

monkeypatch는 테스트 동안 속성이나 환경 변수를 임시로 바꾸는 pytest fixture입니다. monkeypatch.setattr(status_service, "fetch_status", fake_status)는 검사 대상 모듈이 참조하는 함수 이름을 바꾸고, setenv()는 첫 테스트 안에서 환경 변수를 지정합니다. 이 노트북은 첫 테스트 안의 환경 변수 값과 다음 테스트에서 원래 함수가 반환한 대기를 직접 검사합니다. 환경 변수의 테스트 후 복원값은 별도로 출력하거나 단언하지 않습니다.

도식 읽기

도식의 위쪽은 src/report_tools와 pyproject.toml을 입력으로 받아 빌드 백엔드가 휠을 만들고, 그 휠을 새 환경에 설치한 뒤 새 프로세스가 report_tools를 가져오는 흐름입니다. 아래쪽은 공유 목록 하나를 연속으로 수정하는 Before와, 각 테스트 호출 직전에 fixture가 새 목록을 반환하는 After를 비교합니다. 마지막 상자는 첫 테스트에서 함수를 대체하고 다음 테스트에서 원래 함수의 반환값을 확인하는 범위를 나타냅니다.

5실행 예제

준비 셀은 임시 프로젝트의 src/report_tools/__init__.py에 make_title()을 저장합니다. 함수의 입력은 문자열이며 양쪽 공백을 제거하고 각 단어의 첫 글자를 바꾼 문자열을 반환합니다. 같은 셀은 pyproject.toml에 배포 이름 report-tools, 버전 0.1.0, 빌드 백엔드 uv_build를 기록합니다.

다음 셀은 현재 Python에서 uv의 build --wheel 명령을 호출합니다. 입력은 임시 프로젝트 폴더이고 산출물은 dist 폴더의 휠입니다. 이어서 새 가상환경을 만들고 그 휠을 설치합니다. 마지막 하위 프로세스는 설치 환경의 Python으로 import report_tools를 실행하고 make_title(" agent log ")의 반환값을 출력합니다. report_tools-0.1.0-py3-none-any.whl -> Agent Log는 빌드 파일 이름과 설치 뒤 함수 결과를 한 줄에 보여 줍니다.

결과 확인 셀은 휠 파일이 실제로 존재하는지, 첫 입력이 Agent Log인지, 바꾼 입력이 Weekly Note인지 각각 검사합니다. 두 문자열은 같은 설치된 함수에 서로 다른 입력을 전달한 결과입니다.

uv 패키징과 pytest 테스트 격리

로컬 패키지를 실제로 빌드·설치·가져오고, fixture와 monkeypatch로 반복 가능한 테스트를 만드는 과정을 확인합니다.

기본 실행: 가장 작은 패키지 만들기


src/report_tools/__init__.py에는 설치 뒤 import report_tools로 가져올 코드를 씁니다. pyproject.toml의 [project] 구역은 배포 이름과 버전을, [build-system] 구역은 소스를 휠로 바꿀 도구를 지정합니다. 배포 이름 report-tools와 import 이름 report_tools의 하이픈·밑줄 차이도 확인합니다.


In [2]:
# 임시 폴더에 패키지 소스와 빌드 설정을 준비합니다.
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess
import sys

workspace = TemporaryDirectory()
root = Path(workspace.name)
package = root / "src" / "report_tools"
package.mkdir(parents=True)
(package / "__init__.py").write_text("""def make_title(name: str) -> str:
    return name.strip().title()
""")
(root / "pyproject.toml").write_text("""[project]
name = "report-tools"
version = "0.1.0"
[build-system]
requires = ["uv_build==0.12.11"]
build-backend = "uv_build"
""")
print(root.name, "패키지 소스 준비")


출력:
tmpw_hpy_x1 패키지 소스 준비



빌드·설치·가져오기


현재 커널의 Python으로 uv build --wheel을 호출하면 임시 프로젝트의 소스와 설정을 입력으로 받아 .whl 파일을 만듭니다. 이어서 새 가상환경을 만들고 그 휠을 설치합니다. 마지막으로 설치 환경의 새 Python 프로세스가 패키지를 가져와 함수를 호출합니다. 빌드, 설치, import는 서로 다른 단계입니다.


In [3]:
# 휠을 빌드하고 격리된 위치에 설치한 뒤 새 프로세스로 가져옵니다.
built = subprocess.run(
    [sys.executable, "-m", "uv", "build", "--wheel"],
    cwd=root, text=True, capture_output=True, check=True,
)
wheel = next((root / "dist").glob("*.whl"))
venv = root / ".venv"
subprocess.run([sys.executable, "-m", "uv", "venv",
                str(venv), "--python", sys.executable],
               check=True, capture_output=True)
env_python = venv / ("Scripts/python.exe" if os.name == "nt" else "bin/python")
subprocess.run([sys.executable, "-m", "uv", "pip", "install",
                "--python", str(env_python), str(wheel)],
               check=True, capture_output=True)
imported = subprocess.run(
    [str(env_python), "-c",
     "import report_tools; print(report_tools.make_title('  agent log  '))"],
    text=True, capture_output=True, check=True, cwd=root,
)
print(wheel.name, "->", imported.stdout.strip())


출력:
report_tools-0.1.0-py3-none-any.whl -> Agent Log



결과 확인: 배포 산출물과 import


휠 파일이 존재하는지만으로 설치 성공을 알 수 없습니다. 새 Python 프로세스가 설치된 make_title()에 문자열을 입력하고 Agent Log를 반환받았는지 검사합니다. 이어서 입력만 weekly note로 바꾸어 같은 설치된 함수가 Weekly Note를 반환하는지 확인합니다.


In [4]:
# 빌드 파일과 설치 후 함수 결과를 함께 확인합니다.
print("휠 존재:", wheel.exists())
print("첫 입력:", imported.stdout.strip())
changed = subprocess.run(
    [str(env_python), "-c",
     "import report_tools; print(report_tools.make_title('  weekly note  '))"],
    text=True, capture_output=True, check=True, cwd=root,
)
print("바꾼 입력:", changed.stdout.strip())
assert wheel.exists()
assert imported.stdout.strip() == "Agent Log"
assert changed.stdout.strip() == "Weekly Note"


출력:
휠 존재: True
첫 입력: Agent Log
바꾼 입력: Weekly Note



확인할 점 — 소스 폴더를 현재 커널의 검색 경로에 직접 추가하지 않습니다. 빌드, 설치, 새 프로세스 import는 서로 다른 처리 단계입니다. 휠 존재 여부만으로 import 성공을 판단하지 않고 새 프로세스의 실제 반환 문자열까지 확인합니다.


6일부러 실패해 보기
Before 테스트 두 개는 모듈 전역의 같은 items 목록을 수정합니다. 첫 테스트가 alpha를 추가한 뒤 둘째 테스트가 beta를 추가하므로, 둘째 테스트가 기대한 ["beta"]와 실제 목록이 다릅니다. pytest의 실제 출력은 1 failed, 1 passed와 종료 코드 1입니다. After에서는 두 테스트가 이름이 같은 fixture를 요청하며 fixture는 호출될 때마다 빈 목록을 반환합니다. 동일한 두 동작과 검사를 다시 실행하면 출력은 2 passed가 됩니다. 이 두 테스트와 별도로 test_mock.py의 검사 두 개를 실행합니다. 첫 검사는 fetch_status를 완료를 반환하는 함수로 임시 대체하고 환경 변수를 지정합니다. 다음 검사는 원래 함수가 대기를 반환하는지 확인합니다. 이 별도 검사도 2 passed이며, 실제 네트워크를 호출하지 않는 연습용 함수입니다. 실패를 숨긴 것이 아니라 각 테스트의 입력 상태를 분리한 결과입니다.

Before — 실패 코드


Before: 공유 상태 때문에 두 번째 테스트가 실패함


두 테스트가 같은 목록을 수정하면 실행 순서가 결과에 영향을 줍니다. pytest를 실제 실행하고 실패 코드와 요약을 관찰합니다.


In [5]:
# 공유 목록 때문에 두 번째 테스트가 실패하는 파일을 실행합니다.
bad_test = root / "test_shared.py"
bad_test.write_text("""items: list[str] = []
def test_add_alpha() -> None:

def test_add_beta() -> None:
    items.append("beta")
    assert items == ["beta"]
""")

After — 수정 코드


After: fixture와 monkeypatch로 입력을 분리함


@pytest.fixture는 바로 아래 items()를 준비 함수로 등록합니다. 테스트 함수가 같은 이름의 items 매개변수를 적으면 pytest가 호출 직전에 fixture를 실행하고 반환된 빈 목록을 전달합니다. 각 테스트 호출이 새 목록을 받으므로 앞 테스트의 append() 결과가 이어지지 않습니다. monkeypatch는 뒤의 별도 예제에서 다룹니다.


In [6]:
# 같은 두 테스트를 유지하고 fixture로 준비 목록만 분리합니다.
good_test = root / "test_isolated.py"
good_test.write_text("""import pytest
@pytest.fixture
def items() -> list[str]:
    return []
def test_add_alpha(items: list[str]) -> None:
    items.append("alpha")
    assert items == ["alpha"]
def test_add_beta(items: list[str]) -> None:
    items.append("beta")
    assert items == ["beta"]
""")
passed = subprocess.run(
    [sys.executable, "-m", "pytest", "-q", good_test.name],
    cwd=root, text=True, capture_output=True, check=True,
)
print(passed.stdout.strip().splitlines()[-1])
assert "2 passed" in passed.stdout



출력:
2 passed in 0.00s



추가 확인: 함수 대체와 함수 복원


목록 공유 문제를 고친 두 테스트와 별도로 monkeypatch를 확인합니다. setattr()은 status_service.fetch_status를 테스트 동안 fake_status에 연결하고, setenv()는 첫 테스트 안에서 APP_MODE를 test로 지정합니다. 코드는 첫 테스트 안의 환경 변수 값과, 다음 테스트에서 원래 함수가 반환하는 대기를 직접 확인합니다. 환경 변수의 테스트 후 복원값은 이 출력에서 따로 검사하지 않습니다. 아래 서비스 모듈은 네트워크를 호출하지 않습니다.

7주의할 점과 실무 메모
  • dependencies에 uv-build를 넣는 것과 [build-system]에서 백엔드를 선언하는 것은 역할이 다릅니다. 실제 패키지 프로젝트에는 빌드 시스템 선언이 필요합니다.
  • uv_build는 순수 Python 프로젝트를 위한 백엔드입니다. 네이티브 확장 모듈이 필요한 프로젝트는 지원 범위와 다른 백엔드를 확인합니다.
  • 테스트 순서를 바꿔 실패를 피하지 않습니다. 어떤 순서에서도 독립되도록 입력 상태를 fixture로 만듭니다.
  • monkeypatch는 검사 대상 코드가 참조하는 이름에 적용합니다. pytest 자체나 표준 라이브러리 전역을 넓게 바꾸면 테스트 실행기까지 영향을 받을 수 있습니다.
  • 이 실습은 임시 폴더만 사용하며 끝에서 제거합니다. 실제 배포 저장소에 업로드하는 과정은 포함하지 않습니다.


8정리와 다음 절
  • pyproject.toml의 빌드 시스템 선언을 바탕으로 uv가 설치 가능한 휠을 만듭니다.
  • 빌드 결과는 격리된 위치에 설치하고 새 프로세스에서 가져와 확인합니다.
  • fixture와 monkeypatch는 테스트마다 입력 상태와 외부 설정을 분리합니다.
다음 학습과 이어지는 지점 — 12절에서는 여러 대기 작업을 동시에 진행할 때 실행 순서를 관찰합니다. Ch 18의 API 코드와 Ch 30의 서비스 코드를 패키지로 관리하고 외부 의존을 테스트에서 대체할 때 이 절의 방법을 사용합니다.


9복습 문제
1. [build-system]은 무엇을 지정하나요?
정답과 해설: 소스 트리를 휠이나 소스 배포 파일로 바꾸는 데 필요한 패키지와 빌드 백엔드를 지정합니다.
2. 휠을 만들기만 하고 가져오기 검사를 생략하면 무엇을 알 수 없나요?
정답과 해설: 빌드 파일이 실제로 설치되고 새 Python 프로세스에서 원하는 모듈을 가져올 수 있는지 알 수 없습니다.
3. 기본 함수 범위의 fixture가 테스트 격리에 도움이 되는 이유는 무엇인가요?
정답과 해설: 각 테스트가 fixture를 요청할 때 준비 코드가 다시 실행되어 새 값을 받기 때문입니다. 이전 테스트가 수정한 목록을 이어받지 않습니다.
4. monkeypatch로 환경 변수를 바꾼 뒤 직접 복구 코드가 없어도 되는 이유는 무엇인가요?
정답과 해설: pytest의 monkeypatch fixture가 해당 테스트가 끝날 때 변경을 자동으로 되돌리기 때문입니다.
