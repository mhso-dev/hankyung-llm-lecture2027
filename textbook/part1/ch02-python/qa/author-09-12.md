## 09 데코레이터와 컨텍스트 매니저

- 학습 질문: 호출 전후의 공통 처리를 재사용하면서 원래 함수 정보와 예외 경로의 자원 정리를 어떻게 유지하는가?
- 입력과 비교 조건: `normalize_title()`에 공백 포함 문자열과 공백 없는 문자열을 차례로 전달했습니다. 실패 비교에서는 같은 `RuntimeError`를 발생시키고 정리 위치만 일반 문장과 컨텍스트 관리자의 `finally`로 바꿨습니다.
- 실제 연산: 코드 셀 1은 표준 라이브러리를 준비합니다. 셀 2는 `@wraps`가 적용된 데코레이터를 실행합니다. 셀 3은 이름·문서 문자열·서명을 읽습니다. 셀 4는 공백 없는 입력을 비교합니다. Before/After 셀은 `DemoResource.close()` 실행 여부를 비교합니다.
- 관찰 결과: 함수 이름은 `normalize_title`, 서명은 `(title: str) -> str`로 유지됐습니다. Before는 `RuntimeError / 닫힘: False`, After는 `정리 실행` 뒤 `RuntimeError / 닫힘: True`를 출력했습니다.
- 해석 범위: 모의 자원 객체로 `finally` 실행 순서를 확인했습니다. 실제 데이터베이스·네트워크 자원의 종료 API까지 검증한 결과는 아닙니다.
- 본문과 그림: 본문은 데코레이터 호출 흐름과 컨텍스트 관리자의 준비·사용·정리를 설명하며 실제 출력의 이름·서명·닫힘 상태와 일치합니다. 그림 자리표시자는 `{{svg:09-concept}}`입니다.

## 10 Pydantic v2

- 학습 질문: 같은 `retries` 입력이 기본 자동 변환과 엄격한 필드에서 어떻게 다르게 처리되는가?
- 입력과 비교 조건: 기본 모델과 엄격한 모델 모두 `{"retries": "3"}`을 검사합니다. 범위 확인만 정수 8로 바꾸고 0 이상 5 이하 규칙을 유지했습니다.
- 실제 연산: 셀 1은 Pydantic 2.13.5를 설치합니다. 셀 2는 `model_validate()`의 기본 변환을 실행합니다. 셀 3은 변환된 사전을 확인합니다. 셀 4는 범위 오류의 구조화된 정보를 읽습니다. Before/After는 같은 문자열 입력에 필드의 `strict` 설정만 바꿉니다.
- 관찰 결과: 기본 모델은 문자열을 정수 3으로 변환했고 `{'retries': 3}`을 반환했습니다. 정수 8은 `less_than_equal`, 엄격한 필드의 문자열 `"3"`은 `int_type` 오류였습니다. 정수 3은 엄격한 필드를 통과했습니다.
- 해석 범위: Python 사전을 `model_validate()`로 검사한 결과입니다. JSON 입력에서는 일부 자료형의 엄격성 규칙이 다를 수 있습니다.
- 본문과 그림: 본문은 변환 여부와 값 범위를 별도 규칙으로 설명하며 노트북 오류 유형과 일치합니다. 그림 자리표시자는 `{{svg:10-concept}}`입니다.

## 11 uv 패키징과 pytest 테스트 격리

- 학습 질문: 소스 폴더를 설치 가능한 휠로 검증하고 테스트마다 새 상태를 제공하려면 무엇이 필요한가?
- 입력과 비교 조건: `report_tools` 0.1.0을 빌드하여 공백을 포함한 두 제목 입력을 비교했습니다. Before/After의 테스트는 `alpha`와 `beta`를 각각 목록에 추가하는 동일한 동작·검사를 유지하고 목록 제공 방식만 전역 공유에서 fixture로 바꿨습니다.
- 실제 연산: 셀 2는 임시 `src` 패키지와 `[build-system]`을 만듭니다. 셀 3은 `python -m uv build --wheel`, 격리된 venv 생성, 휠 설치, 새 Python 프로세스 import를 실행합니다. 셀 4는 두 입력의 반환값을 확인합니다. Before/After는 pytest를 별도 프로세스로 실제 실행하며 After의 두 테스트는 fixture로 목록만 분리합니다. 추가 셀 7~9는 별도의 테스트 파일에서 monkeypatch로 함수와 환경 변수를 임시 지정하고 원래 함수의 복원을 검사합니다.
- 관찰 결과: `report_tools-0.1.0-py3-none-any.whl`을 만들고 설치된 패키지는 `Agent Log`와 `Weekly Note`를 반환했습니다. 공유 목록 테스트는 종료 코드 1과 `1 failed, 1 passed`, fixture 적용 테스트는 `2 passed`를 출력했습니다.
- 해석 범위: 순수 Python 패키지와 uv-build 범위에서 확인했습니다. 외부 패키지 저장소 업로드, 네이티브 확장 빌드, 실제 네트워크 모킹은 포함하지 않았습니다.
- 본문과 그림: 본문은 소스→휠→격리 설치→새 프로세스 import와 공유 상태→fixture 분리를 설명합니다. 출력에 개인 절대 경로가 남지 않도록 uv 하위 프로세스 출력은 캡처했습니다. 그림 자리표시자는 `{{svg:11-concept}}`입니다.

## 12 async와 await

- 학습 질문: 여러 대기 작업은 어떤 순서로 완료되고 동기 차단 호출을 이벤트 루프 밖으로 옮기면 진행 순서가 어떻게 달라지는가?
- 입력과 비교 조건: 0.03초와 0.01초 모의 I/O의 완료·반환 순서를 비교했습니다. 성능 관찰은 같은 0.04초 모의 I/O 두 건을 순차 실행과 `gather` 실행으로 바꿨습니다. Before/After는 같은 `time.sleep(0.05)`를 이벤트 루프에서 직접 호출하거나 `to_thread`로 옮겼습니다.
- 실제 연산: 셀 2는 Jupyter 최상위 `await`로 코루틴을 실행합니다. 셀 3은 `gather`와 별도 진행 목록을 비교합니다. 셀 4는 `perf_counter()`로 한 번 측정합니다. Before는 `asyncio.Event`로 하트비트 시작을 확인한 뒤 동기 sleep을 호출합니다. After는 sleep만 `to_thread`로 옮기고 사건 세 개가 모두 완료됐는지 검사합니다.
- 관찰 결과: 완료 순서는 `빠른 작업, 느린 작업`, gather 반환 순서는 `느린 작업, 빠른 작업`이었습니다. 이번 실행의 순차/동시 측정은 0.082초/0.042초였습니다. Before 사건은 `block-start, block-end, heartbeat`, After 사건은 `wait-start, heartbeat, wait-end`였고 관찰 불리언은 `True`였습니다.
- 해석 범위: 지연은 실제 네트워크가 아닌 `asyncio.sleep` 모의 I/O입니다. 측정값은 실행 환경에 따라 달라지며 보편적인 속도 향상이나 CPU 계산 가속을 뜻하지 않습니다. After의 합격 검사는 시간 임계값이나 하트비트 순서에 의존하지 않습니다.
- 본문과 그림: 본문은 코루틴·태스크·gather·이벤트 루프·차단 호출을 실제 출력 순서와 연결합니다. Jupyter의 최상위 `await` 실행은 nbclient 새 커널에서 직접 확인했습니다. 그림 자리표시자는 `{{svg:12-concept}}`입니다.

- 네 노트북을 저장된 출력 없이 시작해 임시 작업 폴더의 새 커널에서 순차 실행했습니다. 공통 실행기는 각 노트북의 코드 셀을 모두 PASS로 판정했습니다(09·10·12절 각 6개, 11절 9개).

- 네 본문은 코드 태그를 제외한 텍스트가 각각 2,500자 이상이며 고정 10개 블록, 복습 문제 4개와 정답·해설, example/failure 노트북 삽입을 포함합니다.

- 공식 근거는 `qa/research.md`의 Python 3.12, Pydantic 2.13.5, pytest 9.1.1, uv/uv-build 0.12.11 조사 결과와 각 절의 공식 문서 링크를 사용했습니다.

## 확인 필요 항목

- Windows와 Linux에서 임시 venv의 설치·import 흐름은 실행하지 않았습니다. 경로 선택 코드는 두 운영체제 형식을 모두 처리하도록 작성했습니다.
- 비동기 시간 수치는 현재 macOS 실행 한 번의 결과입니다. 학생 환경에서는 표시값이 달라질 수 있습니다.
- 최종 한국어 검토와 HTML 화면·복사 검증 결과는 `qa/verification.md`와 `qa/language/`에 기록합니다.
