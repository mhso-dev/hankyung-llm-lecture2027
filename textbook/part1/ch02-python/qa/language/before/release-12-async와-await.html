1학습 목표

  • async def가 만드는 코루틴을 await로 실행할 수 있습니다.
  • 태스크의 완료 순서와 gather의 반환 순서를 구분할 수 있습니다.
  • 동기 time.sleep이 이벤트 루프를 막는 현상을 관찰하고 asyncio.to_thread로 수정할 수 있습니다.

2이 내용을 배우는 이유

LLM API, 파일 저장소, 데이터베이스에 요청을 보내면 프로그램은 응답을 기다리는 시간이 생깁니다. 한 요청을 기다리는 동안 다른 요청을 시작할 수 있다면 전체 대기 시간을 줄일 가능성이 있습니다. Python의 asyncio는 여러 대기 작업이 한 이벤트 루프에서 번갈아 진행되도록 합니다. 하지만 비동기 함수 안에서 오래 걸리는 동기 함수를 직접 호출하면 다른 작업도 멈춥니다. 이 절은 A·B 경로 모두의 필수 학습이며 01~04절의 함수 기초만 사용합니다. B 경로 09~11절을 거치지 않아도 됩니다. Ch 18의 여러 API 요청과 Ch 30의 동시 요청 처리에서 다시 사용합니다.

3앞에서 배운 내용

02절에서 문장이 순서대로 실행되고 반복문이 같은 동작을 여러 번 수행하는 과정을 배웠습니다. 04절에서는 함수를 호출하면 반환값을 받는다고 배웠습니다. 비동기 함수는 호출 직후 최종 값을 주지 않고 코루틴 객체를 반환한다는 점이 새롭습니다. 05절의 파일 처리나 08절의 테스트 지식은 이 절의 시작 조건이 아닙니다. 노트북 셀은 Jupyter가 지원하는 최상위 await 문법을 사용하므로 셀 전체를 그대로 복사해 실행합니다.

4핵심 개념

쉬운 예

두 문서의 처리가 끝나기를 기다린다고 생각해 봅니다. 첫 문서의 대기가 끝날 때까지 아무 일도 하지 않은 뒤 둘째 문서를 시작하면 대기 시간이 이어집니다. 두 요청을 먼저 시작하면 첫 요청이 기다리는 동안 둘째 요청도 진행될 수 있습니다. 다만 한 사람이 계산을 계속 점유해 자리를 내주지 않으면 다른 일이 진행되지 않습니다. 비동기 코드도 완료되지 않은 작업을 await하여 실제로 기다릴 때 실행 기회를 넘길 수 있습니다.

정의

코루틴(coroutine)은 실행을 잠시 멈췄다가 이어갈 수 있는 함수 실행 단위입니다. async def로 정의한 함수를 호출하면 코루틴 객체가 생기며, await는 완료되지 않은 작업을 기다리는 동안 현재 코루틴을 멈추고 다른 작업이 진행될 기회를 줍니다. 이미 완료된 작업은 바로 반환될 수 있습니다. 이벤트 루프(event loop)는 실행할 작업과 완료된 대기를 확인하며 코루틴 사이를 전환합니다. 한 시점에는 한 태스크의 Python 코드가 실행됩니다.

태스크(Task)는 코루틴을 이벤트 루프에 예약한 객체입니다. asyncio.create_task()로 만들 수 있습니다. asyncio.gather()는 여러 await 가능 객체의 완료를 함께 기다리고 결과를 입력 순서대로 모읍니다. 작업이 끝난 순서와 결과 목록 순서는 다를 수 있습니다. 차단 호출(blocking call)은 반환될 때까지 현재 스레드의 실행을 점유하는 호출입니다. time.sleep을 이벤트 루프 스레드에서 호출하면 다른 태스크도 진행하지 못합니다. asyncio.to_thread()는 바꿀 수 없는 동기 함수를 별도 스레드에서 실행하고 그 결과를 비동기로 기다리게 합니다.

6일부러 실패해 보기

Before의 blocked_probe는 하트비트 태스크가 시작됐다는 신호를 먼저 받습니다. 이어서 현재 코루틴이 time.sleep(0.05)를 호출합니다. 하트비트는 0.01초 대기를 요청했지만 이벤트 루프가 차단되어 block-end 뒤에 기록됩니다. 검사는 불안정한 시간 임계값 대신 사건 목록의 순서를 확인합니다. After는 같은 time.sleep(0.05)를 asyncio.to_thread로 옮깁니다. 이번 실행에서는 하트비트가 wait-end보다 먼저 나타났으며 출력의 불리언 값도 True입니다. 시간 차이에 기대어 합격 여부를 정하지 않고 세 사건이 모두 완료되었는지만 검사합니다. 이 예제는 동시 진행 여부를 보여 주며 보편적인 속도 향상을 보장하지 않습니다.

7주의할 점과 실무 메모

  • async def 함수를 호출만 하고 await하거나 태스크로 예약하지 않으면 함수 본문이 완료되지 않습니다. 실행기에서 경고가 나타날 수도 있습니다.
  • gather의 결과 순서는 완료 순서가 아니라 입력 순서입니다. 진행 상황이 필요하면 별도 기록이나 완료 순회 도구를 사용합니다.
  • Jupyter는 셀에서 최상위 await를 지원합니다. 일반 .py 파일에서는 보통 asyncio.run(main())으로 최상위 진입점을 만듭니다.
  • to_thread는 주로 차단 I/O 함수를 옮길 때 사용합니다. Python GIL 때문에 일반적인 CPU 집중 계산을 병렬화하는 수단으로 일반화하지 않습니다.
  • 실제 API에는 동시 요청 제한, 재시도, 시간 제한, 비용 정책이 있습니다. 무제한으로 태스크를 만들지 않고 Ch 18에서 제공자 정책과 함께 다룹니다.

8정리와 다음 절

  • 비동기 함수 호출은 코루틴을 만들며 await가 완료 결과를 받습니다.
  • 여러 대기 작업은 함께 진행될 수 있지만 완료 순서와 gather 반환 순서는 다릅니다.
  • 동기 차단 호출은 이벤트 루프를 멈추므로 변경할 수 없는 I/O 함수는 to_thread로 옮길 수 있습니다.

다음 학습과 이어지는 지점 — Ch 3부터는 이 동시 실행 문법을 당장 확대하지 않고 각 라이브러리의 기본 흐름을 먼저 익힙니다. Ch 18의 API 호출과 Ch 30의 FastAPI 서비스에서 여러 대기 작업을 처리할 때 이 절의 실행 순서와 차단 호출 구분을 다시 사용합니다.

9복습 문제

1. async def 함수를 호출하면 즉시 최종 반환값을 받나요?

정답과 해설: 아닙니다. 코루틴 객체를 받으며, await하거나 태스크로 예약해야 본문이 진행되고 최종 결과를 얻습니다.

2. 빠른 작업이 먼저 끝나도 gather 결과가 입력 순서인 이유는 무엇인가요?

정답과 해설: gather는 전달받은 await 가능 객체의 위치에 맞춰 결과 목록을 구성하기 때문입니다. 완료 순서는 별도 기록으로 확인해야 합니다.

3. 비동기 함수 안의 time.sleep이 문제가 되는 이유는 무엇인가요?

정답과 해설: 현재 이벤트 루프 스레드를 점유하여 대기 중인 다른 태스크도 실행하지 못하게 하기 때문입니다.

4. to_thread를 CPU 계산의 보편적 가속 수단이라고 설명하면 안 되는 이유는 무엇인가요?

정답과 해설: 주된 용도는 차단 I/O 함수를 이벤트 루프 밖에서 실행하는 것이며, Python GIL 때문에 일반적인 CPU 집중 계산이 스레드에서 병렬로 빨라진다고 보장할 수 없기 때문입니다.
