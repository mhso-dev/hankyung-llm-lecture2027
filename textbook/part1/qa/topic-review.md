## Ch 3 확인 결과

초기 검토에서는 bare 저장소의 기본 브랜치 환경 의존, 기능 브랜치와 원격 `main` 상태 불일치, 저장된 해시를 그대로 사용한 reflog 복구, 로컬 경로만 검사한 비밀 이력 정리, 실제 팀 원격과 분리된 충돌 예제가 확인되었습니다. 수정본은 다음 조건을 충족합니다.

- bare 저장소 세 곳이 `--initial-branch=main`을 명시합니다.
- PR 템플릿은 기능 브랜치 이전의 `main`에 있고, 리뷰 뒤 병합 결과를 원격 `main`까지 push합니다.
- 빈 문자열 실패는 종료 코드뿐 아니라 `TypeError: count는 정수여야 합니다`라는 실제 stderr 원인을 검사합니다.
- Alice와 Bob이 같은 bare 원격을 사용합니다. Bob의 push 거부와 `git pull --no-rebase origin main` 충돌을 실제로 만들고, `policy.txt`의 `14시 이전=오늘 / 14시 이후=내일` 규칙을 결과 파일에 완전히 보존합니다.
- 충돌 표시 제거는 문자열 상수가 아니라 저장한 파일을 다시 읽어 확인하며, 빈 `git status --porcelain`, 두 부모 해시, 원격 `main` 일치도 검사합니다.
- reflog 출력에서 커밋 메시지에 해당하는 후보 해시를 파싱해 복구 브랜치를 만듭니다.
- 비밀 정리 후 로컬과 원격 재복제본에서 경로와 더미 값이 모두 사라졌는지 검사합니다.

확인 근거는 Python 3.12 새 커널의 5개 노트북·30개 코드 셀 실행 통과, 전역 `init.defaultBranch=master` 강제 환경 통과, Pyright 0 errors입니다. 최종 빌드 뒤 공통 검증은 5개 절·30개 코드 셀·셀 최대 22줄로 통과했습니다. 1280px·390px 화면에서 수행한 12개 시각 검사도 복사·다운로드·대비·잘림 오류 없이 통과했습니다.

낮은 우선순위 정리 항목으로 import 순서, 일부 노트북에서 사용하지 않는 공통 `sys` import, 실패를 의도한 `subprocess.run()`의 명시적 `check=False`가 남아 있습니다. 실제 동작과 학습 목표를 바꾸는 문제는 아닙니다.

## Ch 4 확인 결과

초기 검토에서는 중복 고객을 정리하는 대신 깨끗한 표로 교체한 Before/After, 노트북과 모듈의 서로 다른 함수 인자, 선언되지 않은 외래 키, 같은 페이지를 계속 반환할 때 끝나지 않는 REST 반복이 확인되었습니다. 수정본은 같은 오염 표에 중복 정리 규칙을 적용하고 정리 전 `MergeError`를 실제로 관찰합니다. `fetch_orders`, `find_customer_orders`, `fetch_articles`의 공개 인자와 핵심 연산은 노트북과 모듈에서 일치합니다. SQLite는 `PRAGMA foreign_keys = ON`과 실제 `IntegrityError`를 사용하며 REST 함수는 방문 페이지 집합으로 반복을 중단합니다.

검증 결과는 다음과 같습니다.

- 임시 작업 디렉터리에서 노트북 5개, 각 6개 코드 셀 새 커널 실행 통과
- `uv run python -m pytest -q`: 8 passed
- `ruff check data_tools.py tests notebooks --select I,E701,E702,F,PLW1510`: 통과
- `pyright data_tools.py tests`: 0 errors
- 공통 notebook/HTML 검증: 5개 절, 코드 셀 30개, 셀 최대 24줄 통과

최종 통합본에서 03절 본문과 HTML은 실제 함수 인자 `find_customer_orders(database, customer_id)`와 `TemporaryDirectory/orders.db`의 임시 파일 SQLite 데이터베이스를 설명합니다. 수정된 도식 5쌍도 빌드에 반영됐고, 1280px·390px에서 index와 5개 절의 화면 검사 12건이 모두 통과했습니다. 최종 공통 검증은 5개 절·30개 코드 셀·셀 최대 24줄로 다시 통과했습니다.

## Ch 5 확인 결과

01–04 노트북은 모델·토크나이저를 실제로 로드한 임시 새 커널에서 모두 실행됐습니다. 01의 GPT-2·KLUE 분할 수, 02의 384차원 임베딩과 코사인 유사도, 03의 교재용 가중치, 04의 raw 텍스트 수치는 현재 출력과 본문이 일치합니다. 03은 수동으로 정한 숫자를 실제 어텐션 가중치나 답변 원인으로 주장하지 않으며 수식·Transformer 구현도 다루지 않습니다.

04는 시스템 지시·문서·질문 raw 텍스트의 387토큰과 채팅 역할·생성 시작 표시까지 포함한 실제 입력 400토큰을 구분합니다. 출력 64토큰을 예약한 448토큰 입력 한도에서 실제 여유는 48토큰입니다. 반복 문서 조건의 전체 입력 220·400·760·1,480토큰과 448토큰 연습 한도 판정도 새 커널에서 다시 확인했습니다. 이 절은 토큰 예산만 계산하며 생성 정확도나 절단 정책을 측정했다고 주장하지 않습니다.

05는 직전 절의 512토큰이 계산 연습용 한도임을 밝힙니다. 실제 Qwen 설정의 `max_position_embeddings`는 32,768이며 가장 긴 입력 1,201토큰과 최대 생성 20토큰의 합 1,221은 이 한도보다 작습니다. 따라서 입력 절단과 길이·위치에 따른 응답 차이를 분리했습니다. 탐욕 디코딩에서 시드만 바꾼 두 출력을 독립 확률 표본으로 세지 않고, 시작·중간·끝 위치별 hit 결과와 길이에 따른 단조 저하 미관찰을 실제 출력 범위에서만 설명합니다.

06은 두 temperature 조건이 모두 `unique=3/3`이므로 다양성이 늘었다고 주장하지 않습니다. 07은 근거 없는 제도 절차를 만든 첫 답과 정보 부재를 표현한 둘째 답을 구분하고, 답변 보류 지시의 두 성공 사례를 일반화하지 않습니다. 08은 캐시 로딩과 1,202토큰의 토큰화 시간을 생성 지연시간이나 TTFT로 해석하지 않습니다. 02·06·08의 모델 revision과 Transformers 기준 버전은 실제 실행 파일과 참고 자료에서 일치합니다.

확인 근거는 동결된 8개 노트북의 실행 완료 상태, 코드 셀 33개·셀 최대 21줄, 수정된 04의 독립 새 커널 실행, Pyright 0 errors, `uv lock --check`, Ruff의 F/E701/E702/PLW1510 검사 통과입니다. 각 절은 고정 구조 10개, 노트북 1개, 도식 1개, 복습 문제와 해설 3~4개를 갖춥니다.

05–07의 생성 문자열은 모델·revision·seed를 고정해 게시본을 재현했지만 장비와 라이브러리 실행 조건에 따라 달라질 수 있습니다. 합법적인 변동을 학생 코드 실패로 만들지 않기 위해 생성 문장 자체를 exact assertion으로 고정하지 않았습니다. 게시본은 동결 출력 해시, HTML 출력 대조, 본문 수치·문장 정독으로 검증하며 출력이 바뀌면 본문 해석도 다시 검토해야 합니다.
