2이 내용을 배우는 이유

4절까지 만든 hello.py는 한 파일이지만, 이후에는 여러 파일을 수정하고 이전 상태와 비교해야 합니다. Git은 어떤 파일이 달라졌는지 기록하는 도구입니다. 한편 뒤의 과정에서는 다른 컴퓨터에서도 같은 실행 조건을 준비해야 합니다. Docker는 필요한 프로그램과 설정을 묶은 실행 환경을 만드는 데 사용합니다.

이번 절의 목표는 두 도구를 깊이 사용하는 것이 아닙니다. Git은 현재 폴더를 저장소로 준비하고 상태를 읽는 데까지 다룹니다. Docker는 설치 파일을 임의로 내려받지 않고 운영체제별 공식 안내를 확인하며, 명령을 입력할 수 있는 상태와 실제 실행 서비스가 준비된 상태를 구분합니다. Git의 브랜치와 협업은 뒤의 실습에서, 컨테이너 설계와 배포는 Ch 32에서 자세히 배웁니다.

3앞에서 배운 내용

2절에서 명령이 발견되는지와 실행이 성공했는지를 구분했습니다. 3절에서는 프로젝트마다 Python 버전과 패키지를 분리했습니다. 4절에서는 hello.py를 저장하고 실행했습니다. 이 절은 같은 원리를 개발 도구의 준비 상태에 적용합니다. 명령 이름이 존재하는지, 현재 폴더가 저장소인지, Docker의 실행 서비스가 응답하는지를 각각 확인합니다.

진단 노트북은 실제 프로젝트를 바꾸지 않도록 임시 폴더에서 Git 저장소를 만듭니다. 노트북이 끝나면 임시 폴더는 정리됩니다. Docker Desktop 설치는 운영체제 설정과 이용 조건을 확인해야 하므로 노트북이 대신 설치하지 않습니다.

4핵심 개념

비유 — 변경 기록과 준비된 작업대

문서를 여러 차례 수정할 때 파일 이름을 최종, 진짜최종처럼 늘리는 대신, 변경 이력을 한곳에 기록하면 어느 부분이 달라졌는지 찾기 쉽습니다. Git이 이 기록을 맡습니다. Docker는 필요한 도구가 놓인 작업대의 설계와 실행을 담당합니다. 작업대 설계도가 있어도 실제 작업대를 펼치지 않았다면 사용할 수 없습니다. Docker 명령줄 도구가 설치되어 있어도 실행 서비스가 시작되지 않은 상태가 이와 비슷합니다.

Git과 GitHub를 구분합니다

Git
컴퓨터의 폴더에서 파일 변경 이력을 기록하고 비교하는 버전 관리 프로그램입니다. 인터넷 연결 없이도 새 저장소를 만들고 상태를 확인할 수 있습니다.
저장소(repository)
Git이 변경 이력을 관리하는 프로젝트 폴더입니다. git init을 실행하면 현재 폴더에 Git 관리 정보가 생기며, 일반 작업 파일과 함께 상태를 추적할 수 있습니다.
GitHub
Git 저장소를 인터넷에 보관하고 다른 사람과 검토·협업할 수 있게 하는 서비스입니다. Git을 설치했다고 GitHub 계정이 자동으로 생기지 않으며, git init만으로 파일이 GitHub에 전송되지도 않습니다.

git status는 현재 저장소에서 무엇이 달라졌는지 보여 줍니다. 아직 기록 대상으로 추가하지 않은 파일은 추적하지 않은 파일(untracked files)로 표시됩니다. 이 상태는 오류가 아니라 Git이 새 파일을 발견했다는 뜻입니다. 이번 절에서는 임시 폴더에 파일 하나를 만들고 상태 표시가 바뀌는 과정을 관찰합니다. 커밋과 원격 저장소 전송은 다음 학습에서 다룹니다.

Docker의 설치와 실행 상태를 구분합니다

클라이언트(client)
사용자가 입력한 docker 명령을 받아 Docker의 실행 서비스에 요청하는 명령줄 프로그램입니다.
데몬(daemon)
백그라운드에서 요청을 받고 이미지와 컨테이너를 관리하는 Docker의 실행 서비스입니다. docker version의 Server 정보가 이 서비스와 통신한 결과입니다.
이미지(image)
프로그램과 실행에 필요한 파일을 묶어 둔 읽기 전용 실행 설계입니다.
컨테이너(container)
이미지를 바탕으로 실제 실행한 격리된 프로세스입니다. 이 절에서는 뜻과 준비 상태만 확인하며, 제작과 배포는 Ch 32에서 다룹니다.

docker --version이 출력되면 클라이언트 명령을 찾았다는 뜻입니다. 이것만으로 데몬이 실행 중이라고 판단할 수 없습니다. Docker Desktop을 시작한 뒤 docker version을 실행하여 클라이언트에 해당하는 Client 구역과 데몬에 해당하는 Server 구역이 모두 나타나는지 확인합니다. 설치본이 Docker Desktop CLI를 지원하면 docker desktop status로 상태를 볼 수 있습니다. 해당 하위 명령이 없으면 Docker Desktop 앱을 연 뒤 docker version으로 확인합니다.

운영체제별 공식 설치 페이지를 사용합니다

Docker Desktop의 지원 운영체제와 필요한 메모리, 가상화 조건은 제품이 갱신되면서 달라질 수 있습니다. Windows는 WSL 2와 하드웨어 가상화, 지원 Windows 빌드를 확인합니다. macOS는 Apple silicon과 Intel 중 자신의 칩에 맞는 설치본 및 지원되는 macOS 범위를 확인합니다. Linux는 지원 배포판, KVM, QEMU, systemd, 데스크톱 환경을 확인합니다. 아래 참고 자료의 공식 운영체제별 페이지에서 현재 조건을 확인한 뒤 설치합니다.

조직과 교육 환경에 적용되는 이용 조건도 최신 공식 안내에서 확인합니다. 이 교재는 특정 조직의 사용 권한이나 비용을 판정하지 않습니다. 설치 전에 자신의 운영체제, 장치 관리 정책, 계정 권한을 확인해야 합니다.

도식 — 명령 발견과 실제 준비를 따로 확인합니다

도식의 Docker 경로가 두 단계인 이유는 설치 확인과 실행 확인이 서로 다른 질문이기 때문입니다. Client만 보이면 명령줄 도구는 준비되었지만 데몬과의 통신은 확인되지 않았습니다. Server까지 보이면 현재 터미널에서 데몬에 요청을 보낼 수 있습니다.

5실행 예제

첫 셀의 shutil.which("git")는 터미널에서 git을 입력했을 때 실행할 프로그램의 위치를 찾습니다. 결과가 None이면 명령을 찾지 못한 상태입니다. git_command is not None은 위치를 찾았는지 비교하여 True 또는 False를 만듭니다. 설치 파일이 있다는 사실만으로 명령 실행까지 성공한다고 단정하지 않기 때문에, 다음 셀에서 git --version의 종료 상태를 다시 확인합니다.

if는 조건이 참일 때 들여쓴 코드만 실행하고, else는 조건이 거짓일 때 다른 코드를 실행합니다. Git이 없는 컴퓨터에서 Git 명령을 무리하게 호출하지 않고 안내를 출력하기 위해 이 구조를 사용합니다. git_version.returncode == 0은 명령이 운영체제에 성공 상태를 반환했는지 확인합니다. 여기서 0은 명령이 정상 종료되었다는 관례이며, Git의 버전 번호를 뜻하지 않습니다.

subprocess.run의 cwd=repository는 그 명령만 임시 저장소 폴더를 현재 작업 폴더로 사용하게 합니다. git init은 그 폴더 안에 Git 관리 정보를 준비하고, git status --short는 파일 상태를 짧은 형식으로 반환합니다. 새 파일 앞의 ??는 Git이 파일을 발견했지만 아직 추적 대상으로 등록하지 않았다는 표시입니다. 파일을 만들었다는 사실, Git이 발견했다는 사실, 변경 이력에 기록했다는 사실은 서로 다른 단계입니다.

Docker 확인도 같은 순서를 따릅니다. docker --version은 명령을 보내는 클라이언트 프로그램이 응답하는지 확인합니다. 이어지는 docker version --format "{{.Server.Version}}"은 요청을 처리하는 서버인 데몬의 버전만 요청합니다. timeout=10은 10초 안에 응답하지 않으면 계속 기다리지 않도록 제한합니다. 이때 발생하는 TimeoutExpired를 따로 처리하므로, 응답 지연을 성공이나 명령 없음으로 잘못 기록하지 않습니다.

노트북은 Python에서 외부 명령을 호출하여 현재 환경을 점검합니다. 먼저 Git과 Docker 명령을 찾을 수 있는지 확인합니다. Git은 임시 폴더를 만들고 git init을 실행한 뒤, 파일 생성 전후의 git status --short 결과를 비교합니다. Docker는 설치를 변경하지 않고 버전과 응답 가능 여부만 확인합니다.

마지막에는 Python, uv, 가상환경, Git, Docker 클라이언트, Docker 데몬의 여섯 항목을 같은 표에 표시합니다. 이 표는 현재 컴퓨터에서 관찰한 준비 상태를 정리하는 자가 점검표입니다. 과정의 공식 평가 점수나 자격 판정이 아닙니다.

server.returncode == 0은 명령이 성공 상태로 마쳤는지 확인합니다. server.stdout.strip()은 받은 출력의 앞뒤 공백과 줄바꿈을 제거합니다. bool(...)은 남은 글자가 있으면 True, 빈 문자열이면 False로 바꿉니다. and로 두 조건을 연결했으므로 명령이 성공하고 버전 글자도 있어야 서버가 응답했다고 판정합니다.

준비된 Python 3.12 노트북에서 첫 셀부터 Shift+Enter로 하나씩 실행합니다. 안내한 결과를 먼저 확인하고 지정한 값 하나를 바꿔 비교합니다. 문서를 사용하는 실습은 파일 묶음이 필요합니다. 노트북과 실습 파일 함께 받기 · 처음 실습하는 방법. 전체 코드 복사에는 실험 셀 전체가 포함됩니다. 이 HTML에서는 코드를 실행하지 않습니다.

Git과 Docker 준비

이번 실습은 도구 설치와 실행 준비 상태를 각각 확인합니다. 3절의 Python 3.12 프로젝트 환경을 준비합니다. Git과 Docker가 아직 없으면 해당 실습을 생략하고 미준비 상태를 기록합니다. import는 Python에 포함된 기능을 가져옵니다. shutil.which는 터미널에서 실행할 수 있는 명령 위치를 찾아 경로를 반환하고, 찾지 못하면 값이 없다는 뜻의 None을 반환합니다. 첫 출력은 설치 완료를 단정하지 않고 명령 위치를 발견했는지만 보여 줍니다.

In [1]:
import sys
import shutil
import subprocess
from pathlib import Path
from tempfile import TemporaryDirectory

# which는 명령의 위치를 찾습니다. 개인 경로 대신 발견 여부만 출력합니다.
git_command = shutil.which("git")
uv_command = shutil.which("uv")
docker_command = shutil.which("docker")
print(f"Git 명령 발견: {git_command is not None}")
print(f"uv 명령 발견: {uv_command is not None}")
print(f"Docker 명령 발견: {docker_command is not None}")
출력:
Git 명령 발견: True
uv 명령 발견: True
Docker 명령 발견: True

1. Git 명령의 실제 응답

명령 위치를 찾는 것과 실제 실행은 구분합니다. subprocess.run의 대괄호 안에는 실행할 프로그램과 인자를 순서대로 적습니다. capture_output=True는 결과를 변수에 저장하고, text=True는 글자로 읽게 합니다. 반환 결과의 returncode가 0이면 명령이 성공 상태로 끝났다는 뜻입니다. if는 조건이 참일 때 들여쓴 코드를 실행하고, else는 거짓일 때 다른 코드를 실행합니다. 이 문법은 Ch 2에서 배우며, 여기서는 Git이 없는 컴퓨터에서도 다음 점검을 계속하기 위해 사용합니다.

In [2]:
# 명령이 없으면 Git 미준비를 기록하고 다른 도구 점검을 계속합니다.
git_ready = False
if git_command is None:
    print("Git: 2절의 설치 안내를 확인하세요.")
else:
    git_version = subprocess.run(
        [git_command, "--version"], capture_output=True, text=True,
    )
    git_ready = git_version.returncode == 0
    print(f"Git 응답: {git_ready}")
    if git_ready:
        print(git_version.stdout.strip())
출력:
Git 응답: True
git version 2.50.1 (Apple Git-155)

2. 비어 있는 임시 저장소

실제 프로젝트 대신 새 임시 폴더에서 git init을 실행합니다. 저장소는 Git이 파일의 변경 상태와 이력을 관리하는 폴더입니다. cwd는 명령이 사용할 현재 작업 폴더를 지정하므로 노트북 폴더가 아니라 새 임시 폴더에서 Git이 실행됩니다. git status --short의 출력이 비어 있으면 표시할 변경 파일이 없다는 뜻입니다. git init은 관리 정보를 준비할 뿐 파일을 커밋하거나 GitHub로 전송하지 않습니다.

In [3]:
temporary_folder = TemporaryDirectory()
repository = Path(temporary_folder.name)

if git_ready:
    # -q는 초기화 안내를 줄이고, -c는 이번 명령에만 설정을 적용합니다.
    subprocess.run(
        [git_command, "-c", "init.defaultBranch=main", "init", "-q"],
        cwd=repository, capture_output=True, text=True, check=True,
    )
    before = subprocess.run(
        [git_command, "status", "--short"], cwd=repository,
        capture_output=True, text=True, check=True,
    )
    print(f"파일 생성 전 상태가 비어 있음: {before.stdout == ''}")
    assert before.stdout == ""
else:
    print("저장소 비교: Git 미준비로 실행하지 않음")
출력:
파일 생성 전 상태가 비어 있음: True

3. 파일 하나를 만든 뒤 비교

같은 저장소에 hello.py 파일 하나를 추가합니다. 추적은 Git이 파일을 이후 변경 이력의 대상으로 관리하도록 등록하는 일입니다. ??는 Git이 새 파일을 발견했지만 아직 추적하지 않는다는 표시입니다. 파일을 만들었다는 사실과 커밋을 만들었다는 사실은 다릅니다. 이 셀은 파일 내용을 실행하지 않고 생성 전후의 Git 상태만 비교한 뒤 임시 저장소를 정리합니다.

In [4]:
if git_ready:
    # 작은 파일 하나를 만들고 Git이 발견하는지 확인합니다.
    script_file = repository / "hello.py"
    script_file.write_text("price = 3000", encoding="utf-8")

        [git_command, "status", "--short"], cwd=repository,

4. Docker 클라이언트 확인

docker --version은 클라이언트 프로그램이 응답하는지 확인합니다. 클라이언트는 사용자가 입력한 Docker 명령을 받아 서버에 요청하는 프로그램입니다. 이 명령은 서버에 컨테이너 실행을 요청하지 않습니다. 명령 위치가 있더라도 실행 결과의 returncode를 별도로 확인하며, 버전 문자열은 컴퓨터마다 달라질 수 있습니다.

In [5]:
docker_client_ready = False
if docker_command is None:
    print("Docker 클라이언트: 명령을 찾지 못함")
else:
    # 이 요청은 Docker 서버를 시작하거나 이미지를 내려받지 않습니다.
    client = subprocess.run(
        [docker_command, "--version"], capture_output=True, text=True,
    )
    docker_client_ready = client.returncode == 0
    print(f"Docker 클라이언트 응답: {docker_client_ready}")
    if docker_client_ready:
        print(client.stdout.strip())
출력:
Docker 클라이언트 응답: True
Docker version 29.4.1, build 055a478

5. Docker 데몬 응답 확인

Docker 서버는 요청을 처리하는 데몬(daemon)을 뜻하며, 출력의 Server 항목에 해당합니다. 클라이언트가 응답한 경우에만 데몬의 버전을 요청합니다. --format은 전체 정보에서 서버 버전만 선택합니다. timeout=10은 10초가 지나면 계속 기다리지 않게 하며, 이때 발생하는 TimeoutExpired만 except에서 구분해 기록합니다. 서버가 응답하지 않으면 원인을 숨겨 성공으로 표시하지 않습니다.

server.returncode == 0은 명령이 성공 상태로 마쳤는지 확인합니다. server.stdout.strip()은 받은 출력의 앞뒤 공백과 줄바꿈을 제거합니다. bool(...)은 남은 글자가 있으면 True, 빈 문자열이면 False로 바꿉니다. and로 두 조건을 연결했으므로 명령이 성공하고 버전 글자도 있어야 서버가 응답했다고 판정합니다.

In [6]:
docker_server_ready = False
if docker_client_ready:
    try:
        server = subprocess.run(
            [docker_command, "version", "--format", "{{.Server.Version}}"],
            capture_output=True, text=True, timeout=10,
        )
        docker_server_ready = server.returncode == 0 and bool(server.stdout.strip())
        print(f"Docker 서버 응답: {docker_server_ready}")
        if docker_server_ready:
            print(f"서버 버전: {server.stdout.strip()}")
    except subprocess.TimeoutExpired:
        print("Docker 서버: 10초 안에 응답하지 않음")
else:
    print("Docker 서버: 클라이언트 미준비로 확인하지 않음")
출력:
Docker 서버 응답: True
서버 버전: 29.4.1

6. 여섯 가지 준비 상태

Python 버전, uv 응답, 현재 커널의 가상환경 여부, Git, Docker 클라이언트, Docker 서버를 각각 읽습니다. 각 이름에는 True 또는 False가 저장됩니다. sys.prefix != sys.base_prefix는 현재 커널의 실행 위치와 기반 Python의 위치가 다른지 비교합니다. 이는 어떤 가상환경 안에 있다는 사실만 확인하며, 원하는 프로젝트의 .venv인지 여부는 3절의 선택 화면과 함께 확인합니다. 아래 결과는 도구 준비 상태이며 A/B 학습 수준을 채점하는 표가 아닙니다.

In [7]:
# uv 역시 위치 발견에 그치지 않고 버전 명령의 성공을 확인합니다.
uv_ready = False
if uv_command is not None:
    uv_result = subprocess.run([uv_command, "--version"], capture_output=True, text=True)
    uv_ready = uv_result.returncode == 0
python_ready = sys.version_info[:2] == (3, 12)
virtual_environment = sys.prefix != sys.base_prefix
print(f"Python 3.12: {python_ready}")
print(f"uv 응답: {uv_ready}")
print(f"현재 커널이 가상환경 내부: {virtual_environment}")
print(f"Git 응답: {git_ready}")
print(f"Docker 클라이언트 응답: {docker_client_ready}")
print(f"Docker 서버 응답: {docker_server_ready}")
assert python_ready, "Python 3.12 커널을 선택하세요."
출력:
Python 3.12: True
uv 응답: True
현재 커널이 가상환경 내부: True
Git 응답: True
Docker 클라이언트 응답: True
Docker 서버 응답: True

결과를 해석합니다

Git의 변경 상태는 파일 하나의 생성 전후를 비교한 실제 결과입니다. Docker 서버가 미준비이면 Docker Desktop을 시작한 뒤 다시 확인합니다. 서버가 응답해도 이미지 내려받기와 컨테이너 실행을 검증한 것은 아닙니다. 여섯 출력은 서로 다른 질문의 답이므로 한 항목의 True가 다른 항목의 준비를 보장하지 않습니다. Python·Git 실습과 Docker 준비를 나눠 기록합니다.

확인할 점 — Git 임시 저장소에서 파일을 만들기 전에는 짧은 상태 출력에 새 파일이 없고, 파일을 만든 뒤에는 아직 추적하지 않은 파일 표시가 나타나는지 확인합니다. Docker는 Client와 Server를 나누어 읽습니다. 설치하지 않은 도구나 시작하지 않은 데몬은 실패를 숨기지 않고 보완 항목으로 표시됩니다.

6실험 결과 해석

여섯 항목은 서로 다른 준비 조건을 확인합니다. Python과 uv 항목은 과정의 명령을 실행할 기반을, 가상환경 항목은 프로젝트별 환경 분리를 확인합니다. Git 항목은 변경 상태를 기록할 도구를, Docker 클라이언트와 데몬 항목은 이후 컨테이너 실습을 시작할 준비를 각각 확인합니다. 한 항목의 통과가 다른 항목의 통과를 대신하지 않습니다.

환경 준비 안내는 학습 시작 순서를 정합니다. 여섯 항목이 모두 준비되면 Ch 2의 기본 실습을 시작할 수 있습니다. Python·uv·가상환경·Git 중 하나가 준비되지 않았다면 관련 절을 다시 실행한 뒤 시작합니다. Docker 클라이언트나 데몬만 준비되지 않았다면 Ch 2의 Python 학습은 진행할 수 있지만, Docker를 사용하는 후속 실습 전에 설치와 실행 상태를 보완합니다. 도구의 설치 여부는 프로그래밍 경험이나 학습 트랙을 판정하지 않습니다.

이 실험은 명령의 존재와 제한된 상태 응답을 한 번 확인합니다. Git의 사용자 이름 설정, GitHub 로그인, 네트워크 연결, Docker 이미지 내려받기, 컨테이너 실행 성능은 측정하지 않습니다. 한 번 통과한 결과도 운영체제 갱신이나 설정 변경 뒤에는 달라질 수 있습니다.

2026년 9월 9일 검증 환경에서는 Python 3.12, uv, 현재 커널의 가상환경 여부, Git, Docker 클라이언트, Docker 서버가 모두 True로 출력되었습니다. Git은 파일 생성 전에 상태 출력이 비어 있었고, 파일 생성 뒤 ?? hello.py가 나타났습니다. Docker 클라이언트와 서버 버전은 이 실행 환경의 값일 뿐 학생 컴퓨터의 기준 버전이 아닙니다. 같은 명령을 자신의 컴퓨터에서 실행한 결과로 준비 상태를 판단합니다.

A/B 트랙 자가진단

다음 여섯 과제는 Ch 2를 시작할 학습 경로를 임시로 고르는 비공식 자가진단입니다. 설치된 도구의 수를 점수로 바꾸지 않습니다. 답을 보지 않고 수행한 뒤, 자신이 어떤 근거로 답했는지 한두 문장으로 적습니다.

  1. price = 3000, count = 2, total = price * count를 읽고 출력할 합계를 예측합니다.
  2. count만 4로 바꾸면 어느 값이 달라지는지 설명하고 결과를 확인합니다.
  3. uv run python hello.py에서 상대 경로로 적은 hello.py를 어느 폴더에서 찾는지 설명합니다.
  4. total = price * count 줄의 중단점에서 F5로 멈췄을 때, 그 줄의 실행 전과 F10을 누른 후 Variables 패널이 어떻게 다른지 설명합니다.
  5. 이전에 직접 작성한 함수가 있다면 입력과 반환값을 예로 들어 설명합니다. 경험이 없다면 “아직 경험 없음”이라고 표시합니다.
  6. 이전에 예외 처리나 자동 테스트를 작성한 적이 있다면 한 사례와 확인 목적을 설명합니다. 경험이 없다면 “아직 경험 없음”이라고 표시합니다.

B 트랙 권장 — 1~4번을 독립적으로 수행하고 5~6번에서 실제 작성 경험을 구체적으로 설명할 수 있다면 확장 과제를 함께 수행합니다. A 트랙 권장 — B 트랙의 조건을 모두 충족하지 않으면 기초 경로에서 Ch 2의 변수, 연산자, 조건문, 함수 단계를 순서대로 학습합니다. 1~4번은 수행했지만 함수·예외 처리·테스트 경험이 부족한 학습자도 A 트랙에서 해당 내용을 익힌 뒤 B 트랙 확장 과제를 선택할 수 있습니다. 이 기준은 교육기관의 공식 배치 기준이 아니라 이 절에서 제안한 학습 안내입니다. 첫 주 실습 뒤 결과가 맞지 않으면 트랙을 다시 선택할 수 있으며, 공식 배치 기준은 [[미정: Ch 1 A/B 트랙 공식 배치 기준]]으로 남깁니다.

자가진단 답안과 판단 근거

1번의 합계는 6000원입니다. 2번에서 count = 4로 바꾸면 가격은 유지되고 합계는 12000원이 됩니다. 3번의 hello.py는 터미널의 현재 작업 폴더를 기준으로 찾습니다. 4번은 중단점 줄을 실행하기 전에는 그 줄이 만들 새 total을 아직 확인할 수 없고, F10을 누른 뒤에는 계산된 total을 변수 창에서 확인할 수 있다고 설명해야 합니다. 5~6번은 공통 정답이 없습니다. 직접 만든 사례의 입력·반환값 또는 확인 목적을 구체적으로 설명하면 되며, 경험이 없다면 그대로 기록합니다. 경험이 없다는 답을 실패로 꾸미지 않습니다.

7주의할 점과 실무 메모

  • 현재 프로젝트에서 git init을 시험하지 않습니다. 노트북은 임시 폴더를 사용하여 기존 파일의 관리 상태를 바꾸지 않습니다.
  • Git과 GitHub를 같은 도구로 설명하지 않습니다. 로컬 Git 저장소는 계정이나 인터넷 연결 없이 만들 수 있으며, GitHub 전송에는 별도 원격 저장소와 인증이 필요합니다.
  • Docker 명령의 버전 출력만으로 데몬 실행을 단정하지 않습니다. docker version에서 Server 응답을 별도로 확인합니다.
  • 설치 조건은 운영체제별 공식 페이지에서 다시 확인합니다. Windows 빌드와 WSL 버전, 지원 macOS 범위, Linux 배포판과 가상화 조건은 바뀔 수 있습니다.
  • 관리되는 학교·회사 컴퓨터는 설치 권한을 먼저 확인합니다. 가상화 설정이나 애플리케이션 설치가 관리 정책으로 제한될 수 있습니다.
  • 컨테이너 개념은 준비 수준까지만 다룹니다. 이미지 작성, 포트, 볼륨, 네트워크, 배포 구성은 Ch 32의 학습 범위입니다.

8정리와 다음 절

  • Git은 로컬 변경 이력을 관리하는 프로그램이고, GitHub는 저장소 협업 서비스입니다.
  • Docker 클라이언트가 설치된 상태와 Docker 데몬이 실행 중인 상태는 별도로 확인합니다.
  • 여섯 항목의 자가 점검은 현재 준비 상태와 다음 행동을 정하며, 공식 성적이나 고정된 반 배치가 아닙니다.

다음 학습과 이어지는 지점 — Ch 2에서는 여기서 준비한 Python 3.12와 uv 환경으로 문법과 자료구조를 배우며 여러 스크립트를 작성합니다. Git 상태와 커밋은 Ch 3에서 노트북이 만든 임시 저장소의 변경을 확인할 때 사용합니다. Docker는 후속 프로젝트의 실행 환경을 준비할 때 다시 사용하고, Ch 32에서 이미지와 컨테이너를 직접 다룹니다.

9복습 문제

1번 문제와 해설

[하] 1. git init을 실행하면 파일이 곧바로 GitHub에 전송됩니까?

정답과 해설 — 전송되지 않습니다. git init은 현재 폴더를 로컬 Git 저장소로 준비합니다. GitHub에 전송하려면 원격 저장소 설정, 인증, 전송 명령이 추가로 필요합니다.

2번 문제와 해설

[중] 2. 임시 저장소에서 새 파일을 만든 뒤 git status --short에 아직 추적하지 않은 파일이 표시됩니다. 이것은 무엇을 뜻합니까?

정답과 해설 — Git이 새 파일을 발견했지만 아직 변경 이력에 추가할 대상으로 등록하지 않았다는 뜻입니다. 명령 실패가 아니라 현재 저장소 상태에 대한 정보입니다.

3번 문제와 해설

[중] 3. docker --version은 출력되지만 docker version의 Server 정보가 나타나지 않습니다. 어떤 상태입니까?

정답과 해설 — Docker 클라이언트 명령은 설치되어 있지만 데몬이 실행되지 않았거나 현재 클라이언트가 데몬과 통신하지 못하는 상태입니다. Docker Desktop을 시작하고 다시 확인합니다.

4번 문제와 해설

[상] 4. 자가 점검에서 Python·uv·가상환경·Git은 통과하고 Docker 두 항목만 준비되지 않았습니다. Ch 2 학습과 후속 Docker 실습을 어떻게 진행해야 합니까?

정답과 해설 — Ch 2의 Python 기본 실습은 진행할 수 있습니다. Docker를 사용하는 후속 실습 전에는 운영체제별 공식 안내로 Docker Desktop을 설치하고, 클라이언트와 데몬 상태를 각각 다시 확인합니다. 자가 점검 결과는 보완 순서를 정하는 안내이며 공식 성적이 아닙니다.
