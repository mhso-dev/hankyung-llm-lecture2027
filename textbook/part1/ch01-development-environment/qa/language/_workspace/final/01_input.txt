
1 학습 목표

이 절을 마치면 과정의 개발 기반 학습이 뒤의 프로젝트에 어떻게 이어지는지 설명할 수 있습니다.
실행 전에 결과를 예상하고 실제 출력과 비교한 기록을 남길 수 있습니다.
입력 하나를 바꾼 결과로 확인한 사실과 아직 확인하지 않은 사실을 구분할 수 있습니다.

2 이 내용을 배우는 이유

처음 프로그램을 실행하면 화면에 숫자나 문장이 나타납니다. 그 결과가 의도한 것인지 판단하려면 실행 전에 무엇을 만들려 했는지 알아야 합니다. 예를 들어 3,000원짜리 상품 두 개의 합계는 6,000원입니다. 프로그램이 오류 없이 3,002원을 출력했더라도 가격을 올바르게 계산한 것은 아닙니다. 실행되었다는 사실과 원하는 일을 했다는 사실을 각각 확인 하는 습관을 첫 장부터 연습합니다.

초반에는 코드를 직접 읽고 입력하며, 바꾼 줄이 결과에 미치는 영향을 설명합니다. 다른 사람이 작성한 코드를 사용하는 경우에도 입력·처리·결과를 스스로 확인할 수 있어야 합니다. 답을 빠르게 얻는 데만 집중하면 예상하지 못한 결과를 어디서부터 살펴볼지 알기 어렵습니다. 지금 쌓는 실행 기록은 이후 더 긴 프로그램을 읽고 수정할 때 원인을 찾는 근거가 됩니다.

3 앞에서 배운 내용

이 절은 첫 학습이므로 프로그래밍 경험을 요구하지 않습니다. 파일을 내려받고 폴더에서 찾는 방법을 알고 있으면 시작할 수 있습니다. 아직 실행 도구가 없다면 지금은 설명과 저장된 출력을 읽습니다. 다음 절의 설치 안내와 3절의 실행 환경 준비를 마친 뒤 이 절의 노트북으로 돌아와 직접 실행합니다. HTML은 내용을 읽고 코드를 복사하는 데 사용하는 교재이며, 화면의 복사 버튼이 코드를 실행하지는 않습니다.

준비된 환경이 있다면 이 절 상단의 노트북 내려받기로 파일을 저장합니다. 파일 이름 끝의 는 설명과 실행 코드를 함께 담은 노트북 파일임을 나타냅니다. 파일을 열었을 때 글과 코드가 여러 칸으로 나뉘어 보이면 맞는 화면입니다. 파일 내용이 중괄호와 따옴표로만 보이면 텍스트 편집기로 열린 상태이므로 2절의 Jupyter 확장 준비를 확인합니다.

4 핵심 개념

예상한 금액과 영수증을 비교합니다

가게에서 상품 두 개를 살 때 머릿속으로 계산한 금액과 영수증을 비교할 수 있습니다. 프로그램에서도 실행 전에 예상값을 적고 실행 후 표시된 값과 비교합니다. 영수증의 합계만 보는 대신 상품 수량과 단가도 확인하는 것처럼, 프로그램이 받은 값과 계산한 값을 함께 살펴봅니다. 이 비유에서는 예상 금액이 확인 기준이며 실제 영수증이 실행 결과에 해당합니다.

이번 절에서 사용하는 다섯 가지 말

프로그램(program) 은 컴퓨터가 수행할 작업을 적은 것입니다. 입력(input) 은 작업에 사용하는 값이며, 여기서는 단가 3,000과 수량 2입니다. 출력(output) 은 실행 결과로 밖에 보여 주는 값입니다. 계산한 합계 6,000을 화면에 표시하면 출력이 됩니다. 셀(cell) 은 노트북에서 설명이나 코드를 담는 한 칸입니다. 검증(verification) 은 결과가 미리 정한 조건에 맞는지 확인하는 일입니다. 이번 조건은 ‘단가에 수량을 곱한 값이 합계와 같다’입니다.

계산한 값을 기억하는 것과 화면에 표시하는 것은 별개의 동작입니다. 코드에서 이름에 값을 저장해도 화면에 아무것도 나타나지 않을 수 있습니다. 이 교재는 확인할 값을 로 표시합니다. 처음에는 괄호 안의 값을 화면에 보여 주는 명령으로 읽으면 충분합니다. 코드에서 는 곱셈을 뜻하고, 는 오른쪽 값을 왼쪽 이름에 저장할 때 사용합니다. 이름과 값의 관계는 Ch 2에서 자세히 배웁니다.

5 실행 예제

첫 실행에서는 코드를 바꾸지 않습니다. 6,000이라는 예상값을 먼저 적고 셀을 위에서 아래로 실행합니다. 앞 셀이 만든 값을 다음 셀이 사용하므로 중간 셀만 실행하면 필요한 값이 없을 수 있습니다. 셀 왼쪽의 입력 번호는 실행된 순서를 나타내며, 교재의 번호를 외우거나 코드에 복사할 필요는 없습니다.


확인할 점 — 기본 수량 2의 합계와 변경한 수량 3의 합계를 비교합니다. 단가는 그대로 두었습니다. 뒤 조건이 참이면 오류가 발생하지 않습니다. 출력 문장과 확인 조건을 함께 읽고 어느 계산을 확인했는지 설명합니다.

6 실험 결과 해석

이번 실행에서는 같은 단가에 수량만 바꿨습니다. 3,000에 2를 곱하면 6,000이고, 3을 곱하면 9,000입니다. 두 조건의 차이는 수량 하나이므로 합계가 3,000만큼 증가한 이유를 설명할 수 있습니다. 입력을 여러 개 동시에 바꾸면 어떤 값이 결과 차이를 만들었는지 따로 확인해야 합니다. 처음에는 비교 조건을 하나씩 정하는 편이 원인을 추적하기 좋습니다.

이 결과로 모든 계산 프로그램이 올바르다고 판단할 수는 없습니다. 할인·환불·배송비가 포함된 계산은 실행하지 않았습니다. 이번 실습에서 확인한 것은 정수 단가와 두 수량의 곱셈입니다. 오류를 재현하지 않은 절이므로 실패를 고쳤다고 기록하지 않습니다. 4절에서는 잘못된 연산으로 계산한 실제 결과를 관찰하고 같은 입력에서 수정합니다.

7 주의할 점과 실무 메모

실습 기록에는 예상한 값, 실제 출력, 바꾼 입력, 다음에 확인할 것을 남깁니다. ‘잘 됨’만 적으면 무엇이 맞았는지 나중에 확인하기 어렵습니다. ‘단가 3,000과 수량 2에서 출력 6,000을 확인했다’처럼 입력과 결과를 함께 적습니다. 오류가 발생하면 마지막 메시지와 실행한 셀을 기록하고, 이미 확인한 정상 셀을 무작정 여러 군데 바꾸지 않습니다.

저장된 출력은 교재를 만들 때 실행한 기록입니다. 파일을 열어 출력이 보인다는 사실만으로 자신의 컴퓨터에서도 실행된 것은 아닙니다. 직접 셀을 실행하고 새 입력 번호와 출력을 확인해야 합니다. 실습 중 값이 예상과 다르게 남았다면 실행 프로그램을 다시 시작한 후 처음부터 순서대로 실행합니다. 이 초기화 방법은 3절에서 배웁니다.

9 복습 문제

1. 입력과 출력은 각각 무엇인가요? · 기초
단가 3,000과 수량 2는 입력이며, 화면에 표시한 합계 6,000은 출력입니다. 어떤 값을 사용했는지와 무엇을 보여 주었는지를 구분합니다.

2. 수량을 3으로 바꾸면 어떤 값을 예상하나요? · 적용
단가를 3,000으로 유지하면 9,000을 예상합니다. 실행 전에 예상값을 적고, 실행 후 출력과 비교합니다.

3. 오류 없이 3,002가 출력되면 올바른 합계인가요? · 적용
아닙니다. 두 상품의 총금액은 6,000이어야 합니다. 실행 가능 여부와 계산 결과의 정확성은 별도로 확인해야 합니다.

4. 두 번 확인한 결과로 할인 계산도 맞다고 말할 수 있나요? · 분석
말할 수 없습니다. 할인 조건은 입력하거나 실행하지 않았습니다. 할인 규칙과 예상값을 정한 별도 사례가 필요합니다. 해석 범위를 다시 읽고 실행한 조건만 기록합니다.

4 핵심 개념

주소의 출발점을 먼저 확인합니다

‘옆방의 책’이라는 설명은 지금 있는 방에 따라 다른 책을 가리킵니다. 파일에도 이름을 찾는 출발점이 필요합니다. 이 비유에서 현재 있는 방은 현재 작업 폴더이며, ‘옆방의 책’은 상대적인 위치를 적은 경로입니다. 프로그램은 화면에 보이는 폴더를 사람처럼 추측하지 않고, 정해진 기준 위치에서 파일을 찾습니다.

편집기(editor) 는 파일 내용을 읽고 수정하는 앱이며, 이 과정은 VS Code를 사용합니다. 터미널(terminal) 은 글자로 명령을 입력하고 결과를 읽는 창입니다. 셸(shell) 은 그 명령을 해석해 실행하는 프로그램입니다. Windows에서는 PowerShell, macOS에서는 zsh를 기준으로 설명합니다. 현재 작업 폴더(current working directory) 는 명령이 파일을 찾기 시작하는 위치입니다.

경로(path) 는 폴더와 파일의 위치를 글자로 적은 값입니다. 절대 경로(absolute path) 는 파일 시스템의 기준 위치부터 적고, 상대 경로(relative path) 는 현재 위치 같은 지정된 기준에서 적습니다. 라고만 쓰면 이름은 짧지만 기준 위치를 알아야 실제 파일을 찾을 수 있습니다. 다른 컴퓨터에서는 사용자 이름과 폴더 위치가 달라질 수 있으므로 수업 파일은 제공된 폴더 구조와 상대 경로로 사용합니다.

uv는 공식 설치 페이지의 Standalone installer에서 자신의 운영체제 탭을 선택합니다. 해당 페이지의 명령을 Windows에서는 PowerShell, macOS와 Linux에서는 터미널에 입력해 설치합니다. 설치가 끝나면 열려 있던 터미널을 닫고 새 창을 엽니다. 새로 설치한 명령의 위치가 기존 창에는 반영되지 않을 수 있기 때문입니다. 으로 버전 문자열이 출력되는지 확인합니다. 명령을 찾지 못한다는 메시지가 나오면 Python 코드 오류로 해석하지 말고 uv 설치 경로와 새 터미널 여부를 확인합니다.

Git과 Docker Desktop의 설치 파일도 표의 공식 페이지에서 받습니다. Docker Desktop은 운영체제 버전과 가상화 지원 등 추가 조건이 있으므로 5절의 운영체제별 설명을 함께 읽습니다. Docker 준비가 지연되더라도 이 절의 파일 경로 실습에는 Docker를 사용하지 않으므로 진행할 수 있습니다. 설치를 마친 도구와 아직 준비 중인 도구를 따로 기록합니다.

확인할 점 — 초록색은 폴더와 파일을, 파란색은 파일을 찾는 동작을 나타냅니다. 파일 이름이 같아도 기준 폴더가 달라지면 빨간 실패 경로에 도달할 수 있습니다. 그림의 폴더 이름과 실제 실습에서 만든 파일의 위치를 비교합니다.

노트북은 작업 위치가 편집기에 연 폴더와 같다고 가정하지 않습니다. 이번 예제는 임시 폴더 변수를 명시적으로 사용해 경로 관계를 확인합니다. 실제 프로젝트에서는 터미널의 현재 위치와 파일 목록을 함께 확인합니다. 삭제 명령으로 문제를 해결하려 하기 전에 요청한 경로를 읽고, 맞는 폴더로 이동하는 것만으로 해결되는지 확인합니다.

2 이 내용을 배우는 이유

같은 코드를 실행했는데 한 컴퓨터에서는 되고 다른 컴퓨터에서는 필요한 기능을 찾지 못할 수 있습니다. 코드 파일만 같아도 실행하는 Python 버전과 설치한 패키지가 다르면 결과가 달라질 수 있기 때문입니다. 먼저 어떤 Python으로 실행하는지와 어디에 패키지를 설치하는지 를 정합니다. 이후 문제가 생겼을 때 코드와 환경 중 무엇이 다른지 나눠 확인할 수 있습니다.

이 과정은 Python 3.12를 사용합니다. 버전 번호를 단순히 외우는 대신, 터미널과 노트북에서 실제 실행한 버전을 확인합니다. 컴퓨터에 Python이 여러 개 있어도 실습마다 필요한 환경을 선택할 수 있습니다. 프로그램 전체를 삭제하고 재설치하기 전에 현재 프로젝트가 어느 환경을 사용하고 있는지 살펴보는 것이 첫 확인 순서입니다.

4 핵심 개념

작업별 준비물을 따로 둡니다

서로 다른 실습의 준비물을 각각의 보관함에 넣으면 어느 실습에서 쓰는지 구분할 수 있습니다. 프로그램의 실행 환경도 프로젝트마다 분리합니다. 다만 실제 보관함처럼 컴퓨터 전체를 나누는 것은 아닙니다. 가상환경은 주로 Python 실행 위치와 패키지 설치 위치를 구분하며, 같은 컴퓨터의 파일과 운영체제를 사용합니다. 어떤 코드든 안전하게 실행해 주는 격리 장치라고 생각하지 않습니다.

인터프리터(interpreter) 는 Python 코드를 읽고 실행하는 프로그램입니다. 프로젝트(project) 는 하나의 작업에 필요한 코드와 설정을 모은 단위입니다. 패키지(package) 는 설치해서 사용하는 Python 기능의 묶음입니다. 가상환경(virtual environment) 은 프로젝트별로 Python 패키지 설치 위치를 구분하는 실행 환경입니다. 이 과정은 프로젝트 폴더 안의 를 사용합니다.

의존성(dependency) 은 프로그램을 실행하는 데 필요한 다른 패키지입니다. 잠금 파일(lockfile) 은 설치할 패키지와 선택된 버전을 기록해 다시 준비할 때 참고하는 파일입니다. uv에서는 을 사용합니다. 커널(kernel) 은 노트북 코드를 실행하고 변수를 기억하는 프로그램입니다. VS Code에서 파일 실행에 사용할 Python을 골랐더라도 노트북의 커널은 별도로 확인합니다.

프로젝트 안의 세 파일을 읽습니다

파일 또는 폴더 담고 있는 내용 학생이 확인할 점
프로젝트 정보와 필요한 Python·패키지 조건입니다. Python 3.12와 노트북 실행 도구 조건을 확인합니다. 처음 실습에서는 수정하지 않습니다.
의존성을 계산한 뒤 선택한 패키지 버전입니다. 직접 편집하지 않고 제공된 파일로 환경을 준비합니다.
현재 컴퓨터에서 실제 사용할 실행 환경입니다. 준비 명령을 실행한 뒤 생성되는지 확인합니다. 다른 컴퓨터에 그대로 복사하지 않습니다.

프로젝트 설정과 잠금 파일이 같으면 설치할 버전을 맞추는 데 도움이 됩니다. 그래도 운영체제와 CPU, 외부 파일까지 모두 같아지는 것은 아닙니다. 설치 오류가 있다면 운영체제와 Python 버전, 실패한 패키지 이름을 함께 확인합니다. 설치된 가상환경 전체 대신 설정과 잠금 파일을 공유하고, 각 컴퓨터에서 환경을 다시 만드는 이유입니다.


확인할 점 — 초록색 환경 A와 B는 각각의 실행 위치를 갖습니다. 노란 확인 단계는 두 환경 폴더의 위치가 서로 다른지와 각 실행이 가상환경 안에서 이루어지는지를 비교합니다. 그림은 패키지 설치 위치를 나누는 원리를 설명하며 운영체제 전체가 두 개 생겼다는 뜻이 아닙니다.

6 실험 결과 해석

두 환경은 같은 기반 Python을 사용할 수 있지만 환경의 위치는 서로 다릅니다. 이 실험은 환경을 새로 만들고 각각의 Python을 실행해 환경 폴더의 위치 정보를 확인합니다. 폴더 이름만 두 개 만들어 놓고 가상환경이 분리되었다고 설명하는 것과는 확인 범위가 다릅니다. 출력에서 환경 A와 B가 각각 가상환경인지 확인하고, 두 환경 폴더가 서로 다른지 비교합니다.

이번 예제는 제삼자 패키지의 서로 다른 버전을 설치하지 않았습니다. 그러므로 실제 패키지 충돌을 재현하거나 해결했다고 기록하지 않습니다. 패키지 설치 위치가 분리되는 원리를 확인했으며, 특정 패키지의 호환성은 그 패키지를 설치하고 사용하는 별도 실행이 필요합니다. 연습용 임시 환경과 현재 노트북을 실행하는 프로젝트의 도 구분합니다.

7 주의할 점과 실무 메모

환경을 선택한 뒤에도 이미 실행 중인 커널이 이전 상태를 기억할 수 있습니다. VS Code에서 Restart Kernel을 선택하면 노트북의 기존 변수가 사라집니다. 다시 첫 셀부터 실행합니다. 저장된 코드와 출력 파일은 커널 재시작만으로 삭제되지 않습니다. 실행 중인 변수, 저장한 코드, 저장된 출력이 각각 무엇인지 구분하면 이전 실행의 숫자를 새 결과로 오해하는 일을 줄일 수 있습니다.

패키지를 설치했는데 찾지 못한다면 설치한 환경과 실행 중인 커널을 확인합니다. 다른 Python에 다시 설치하는 일을 반복하기 전에 인터프리터와 커널이 같은 프로젝트를 가리키는지 살펴봅니다. 를 이동하거나 이름을 바꾼 경우에는 기존 경로를 기억한 설정이 맞지 않을 수 있으므로 제공된 설정으로 새 위치에서 환경을 준비하고 다시 선택합니다.

2 이 내용을 배우는 이유

터미널에 한 줄씩 입력한 코드는 창을 닫으면 다시 찾기 어렵습니다. 여러 줄을 실행하다가 결과가 잘못되어도 어떤 줄에서 값이 달라졌는지 확인하기 어렵습니다. 이제 코드를 파일로 저장하여 다시 실행하고, 디버거로 실행을 잠시 멈춘 뒤 중간 값을 살펴볼 차례입니다.

이 절의 예제는 상품 가격과 개수로 합계를 계산합니다. 프로그램은 오류 메시지 없이 끝나지만 합계가 틀립니다. 요구와 다르게 동작하는 코드의 원인을 논리 오류(logic error) 라고 합니다. 논리 오류는 Python이 작성된 식 자체는 정상적으로 계산했기 때문에 문법 오류보다 발견하기 어려울 수 있습니다. 중단점에서 멈추고 변수를 확인하면 코드가 실제로 어떤 값을 사용했는지 차례대로 좁혀 갈 수 있습니다.

4 핵심 개념

비유 — 계산표를 한 줄씩 확인합니다

영수증의 합계가 예상과 다르면 마지막 숫자만 반복해서 보지 않습니다. 가격, 수량, 계산식 순서로 살펴보며 처음 잘못된 지점을 찾습니다. 디버거도 이와 비슷합니다. 프로그램을 특정 줄에서 잠시 멈추고, 그 시점까지 만들어진 값을 확인한 뒤 다음 줄을 실행합니다.


파일 이름과 확장자를 함께 저장합니다

Python 스크립트(script)는 Python 명령을 순서대로 적어 둔 텍스트 파일입니다. 파일 이름 뒤의 는 이 파일이 Python 소스 코드임을 나타내는 확장자입니다. 제공 파일 다운로드 에는 , , , 합계 출력문이 들어 있습니다. 파일을 VS Code에서 열어 같은 내용을 저장합니다. 저장하지 않은 변경은 터미널에서 실행한 파일에 포함되지 않으므로, 실행 전에 탭의 점 표시가 사라졌는지 확인합니다.

에서 는 터미널의 현재 작업 폴더를 기준으로 찾습니다. 터미널의 현재 폴더와 파일을 저장한 폴더가 다르면 파일을 찾을 수 없다는 메시지가 나타납니다. VS Code 탐색기에서 프로젝트 폴더를 열고 그 폴더에서 새 터미널을 만들면 경로를 맞추기 수월합니다.


세 가지 확장과 인터프리터를 준비합니다

VS Code의 확장은 편집기에 기능을 추가합니다. 이 과정에서는 Microsoft가 제공하는 Python , Python Debugger , Jupyter 확장을 설치합니다. Python 확장은 Python 환경 탐색과 코드 편집 기능을 제공하고, Python Debugger 확장은 실행을 멈추고 값을 살펴보는 기능을 제공하며, Jupyter 확장은 노트북 셀을 실행합니다.

인터프리터(interpreter)는 Python 코드를 읽어 실행하는 프로그램입니다. 명령 팔레트에서 를 실행하거나 상태 표시줄의 Python 버전을 선택한 뒤, 프로젝트 안의 를 고릅니다. 선택한 환경은 일반 Python 파일의 실행, 디버깅, 코드 분석에 사용됩니다. 목록에 보이지 않으면 를 실행해 다시 탐색합니다.

노트북 커널(kernel)은 노트북 셀의 코드를 실행하고 변수 상태를 유지하는 프로세스입니다. 노트북 오른쪽 위의 에서도 같은 를 골라야 합니다. Python 파일용 인터프리터를 선택했더라도 노트북 커널이 자동으로 같아진다고 가정하지 않습니다. 첫 노트북을 열 때 두 위치를 각각 확인합니다.


중단점에서 실행 전 상태를 읽습니다

디버거(debugger)는 실행을 잠시 멈추고 현재 줄과 변수 값을 확인하는 도구입니다. 중단점(breakpoint)은 디버거가 실행을 멈출 줄을 표시한 지점입니다. 줄 번호 왼쪽 여백을 누르면 빨간 점이 나타납니다. 실패 비교에서는 줄에 중단점을 둡니다. F5 를 눌렀을 때 실행 구성을 묻는 메뉴가 나타나면 을 선택합니다. 활성 편집기의 파일이 선택한 인터프리터에서 시작되고, 디버거는 중단점 줄을 실행하기 직전 에 멈춥니다. 현재 줄은 노란색으로 표시되고, Variables 패널(변수 창)에는 이미 실행된 줄에서 만들어진 와 가 보입니다. 아직 실행하지 않은 대입문의 새 은 그 줄의 결과로 만들어지지 않은 상태입니다.

F10 은 다음 줄로 한 단계 진행하는 Step Over입니다. 현재 줄을 실행한 뒤 다음 줄 앞에서 다시 멈춥니다. 이때 Variables 패널에서 을 확인하면 덧셈으로 만든 값이 나타납니다. 계산식의 연산자를 곱셈으로 바꾸고 다시 실행하면 같은 입력에서 합계가 달라집니다. 은 실행 인자나 다른 인터프리터 같은 별도 설정이 필요할 때 사용하므로, 이번 첫 파일에는 만들지 않습니다.


도식 — 멈춘 줄과 만들어진 값을 구분합니다



파란색은 학생이 파일을 저장하고 F5·F10을 누르는 행동, 초록색은 선택한 와 디버거, 노란색은 현재 줄과 Variables 패널에서 확인하는 값, 빨간색은 덧셈 때문에 생긴 잘못된 합계를 뜻합니다. 화살표는 저장한 파일이 선택한 인터프리터에서 실행되고, 중단점에서 멈춘 뒤 한 줄씩 진행되는 순서를 보여 줍니다.

도식에서 노란색 현재 줄은 이미 실행한 줄이 아니라 다음에 실행할 줄 입니다. 따라서 빨간색 잘못된 합계는 그 줄에서 F10으로 진행한 뒤 확인합니다. 이 순서를 알면 “중단점에 멈췄는데 왜 새 값이 아직 보이지 않는가?”라는 혼동을 줄일 수 있습니다.

4 핵심 개념

비유 — 변경 기록과 준비된 작업대

문서를 여러 차례 수정할 때 파일 이름을 , 처럼 늘리는 대신, 변경 이력을 한곳에 기록하면 어느 부분이 달라졌는지 찾기 쉽습니다. Git이 이 기록을 맡습니다. Docker는 필요한 도구가 놓인 작업대의 설계와 실행을 담당합니다. 작업대 설계도가 있어도 실제 작업대를 펼치지 않았다면 사용할 수 없습니다. Docker 명령줄 도구가 설치되어 있어도 실행 서비스가 시작되지 않은 상태가 이와 비슷합니다.


Git과 GitHub를 구분합니다


Git
컴퓨터의 폴더에서 파일 변경 이력을 기록하고 비교하는 버전 관리 프로그램입니다. 인터넷 연결 없이도 새 저장소를 만들고 상태를 확인할 수 있습니다.

저장소(repository)
Git이 변경 이력을 관리하는 프로젝트 폴더입니다. 을 실행하면 현재 폴더에 Git 관리 정보가 생기며, 일반 작업 파일과 함께 상태를 추적할 수 있습니다.

GitHub
Git 저장소를 인터넷에 보관하고 다른 사람과 검토·협업할 수 있게 하는 서비스입니다. Git을 설치했다고 GitHub 계정이 자동으로 생기지 않으며, 만으로 파일이 GitHub에 전송되지도 않습니다.


는 현재 저장소에서 무엇이 달라졌는지 보여 줍니다. 아직 기록 대상으로 추가하지 않은 파일은 추적하지 않은 파일(untracked files) 로 표시됩니다. 이 상태는 오류가 아니라 Git이 새 파일을 발견했다는 뜻입니다. 이번 절에서는 임시 폴더에 파일 하나를 만들고 상태 표시가 바뀌는 과정을 관찰합니다. 커밋과 원격 저장소 전송은 다음 학습에서 다룹니다.


Docker의 설치와 실행 상태를 구분합니다


클라이언트(client)
사용자가 입력한 명령을 받아 Docker의 실행 서비스에 요청하는 명령줄 프로그램입니다.

데몬(daemon)
백그라운드에서 요청을 받고 이미지와 컨테이너를 관리하는 Docker의 실행 서비스입니다. 의 Server 정보가 이 서비스와 통신한 결과입니다.

이미지(image)
프로그램과 실행에 필요한 파일을 묶어 둔 읽기 전용 실행 설계입니다.

컨테이너(container)
이미지를 바탕으로 실제 실행한 격리된 프로세스입니다. 이 절에서는 뜻과 준비 상태만 확인하며, 제작과 배포는 Ch 32에서 다룹니다.


이 출력되면 클라이언트 명령을 찾았다는 뜻입니다. 이것만으로 데몬이 실행 중이라고 판단할 수 없습니다. Docker Desktop을 시작한 뒤 을 실행하여 클라이언트에 해당하는 Client 구역과 데몬에 해당하는 Server 구역이 모두 나타나는지 확인합니다. 설치본이 Docker Desktop CLI를 지원하면 로 상태를 볼 수 있습니다. 해당 하위 명령이 없으면 Docker Desktop 앱을 연 뒤 으로 확인합니다.


운영체제별 공식 설치 페이지를 사용합니다

Docker Desktop의 지원 운영체제와 필요한 메모리, 가상화 조건은 제품이 갱신되면서 달라질 수 있습니다. Windows는 WSL 2와 하드웨어 가상화, 지원 Windows 빌드를 확인합니다. macOS는 Apple silicon과 Intel 중 자신의 칩에 맞는 설치본 및 지원되는 macOS 범위를 확인합니다. Linux는 지원 배포판, KVM, QEMU, systemd, 데스크톱 환경을 확인합니다. 아래 참고 자료의 공식 운영체제별 페이지에서 현재 조건을 확인한 뒤 설치합니다.

조직과 교육 환경에 적용되는 이용 조건도 최신 공식 안내에서 확인합니다. 이 교재는 특정 조직의 사용 권한이나 비용을 판정하지 않습니다. 설치 전에 자신의 운영체제, 장치 관리 정책, 계정 권한을 확인해야 합니다.


도식 — 명령 발견과 실제 준비를 따로 확인합니다



파란색은 학생이 버전과 상태 명령을 입력하는 행동, 초록색은 Git·Docker 클라이언트와 Docker 데몬, 노란색은 출력에서 확인할 저장소 상태와 Client·Server 구역, 빨간색은 명령을 찾지 못했거나 Server가 응답하지 않는 상태를 뜻합니다. Git 경로는 임시 저장소의 파일 상태로 이어지고, Docker 경로는 클라이언트 확인 뒤 데몬 응답 확인으로 이어집니다.

도식의 Docker 경로가 두 단계인 이유는 설치 확인과 실행 확인이 서로 다른 질문이기 때문입니다. Client만 보이면 명령줄 도구는 준비되었지만 데몬과의 통신은 확인되지 않았습니다. Server까지 보이면 현재 터미널에서 데몬에 요청을 보낼 수 있습니다.

# Git과 Docker 준비

이번 실습은 도구 설치와 실행 준비 상태를 각각 확인합니다. 3절의 Python 3.12 프로젝트 환경을 준비합니다. Git과 Docker가 아직 없으면 해당 실습을 생략하고 미준비 상태를 기록합니다. Docker가 아직 준비되지 않았으면 해당 상태를 출력하고 다른 확인을 계속합니다. 외부 명령을 호출하는 보조 문법은 주석을 읽으며 따라 합니다.
## 1. Git 명령의 실제 응답

명령 위치를 찾는 것과 실제 실행은 구분합니다. 은 목록에 적은 프로그램을 실행합니다. 는 결과를 변수에 저장하고, 는 글자로 읽게 합니다. Git 명령이 없거나 응답하지 않으면 상태를 기록하고 다음 도구를 확인합니다.
## 2. 비어 있는 임시 저장소

실제 프로젝트 대신 새 임시 폴더에서 을 실행합니다. 는 해당 명령이 사용할 작업 폴더입니다. 의 출력이 비어 있으면 이번 폴더에서 표시할 변경 파일이 없다는 뜻입니다. 커밋을 생성했다는 뜻은 아닙니다.
## 3. 파일 하나를 만든 뒤 비교

같은 저장소에  파일 하나를 추가합니다. 는 Git이 아직 추적하지 않는 파일 표시입니다. 이 셀은 파일의 내용을 실행하는 것이 아니라 파일 생성 전후의 Git 상태를 비교합니다.
## 4. Docker 클라이언트 확인

은 클라이언트 프로그램이 응답하는지 확인합니다. 아직 설치되지 않았다면 준비하지 않은 상태로 기록합니다. 명령이 있더라도 실행 결과를 별도로 확인합니다. 버전 문자열은 컴퓨터마다 달라질 수 있습니다.
## 5. Docker 데몬 응답 확인

Docker 서버는 요청을 처리하는 데몬(daemon)을 뜻하며, 출력의 Server 항목에 해당합니다. 클라이언트가 응답한 경우에만 데몬의 버전을 요청합니다. 은 필요한 버전 항목만 선택합니다. 서버가 응답하지 않으면 원인을 숨겨 성공으로 표시하지 않고 미준비 상태를 기록합니다. 10초 안에 응답하지 않는 경우도 별도로 표시합니다.
## 6. 여섯 가지 준비 상태

Python 버전, uv 응답, 현재 커널의 가상환경 여부, Git, Docker 클라이언트, Docker 서버를 각각 읽습니다. 가상환경 여부는 현재 커널이 어떤 가상환경 안에 있다는 사실만 확인합니다. 원하는 프로젝트의 인지 여부는 3절의 인터프리터·커널 선택 화면과 함께 확인합니다. 아래 결과는 도구 준비 상태이며 A/B 학습 수준을 채점하는 표가 아닙니다.
## 결과를 해석합니다

Git의 변경 상태는 파일 하나의 생성 전후를 비교한 실제 결과입니다. Docker 서버가 미준비이면 Docker Desktop을 시작한 뒤 다시 확인합니다. 서버가 응답해도 이미지 내려받기와 컨테이너 실행을 검증한 것은 아닙니다. Python·Git 실습과 Docker 준비를 나눠 기록합니다.
