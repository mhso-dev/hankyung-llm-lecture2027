2이 내용을 배우는 이유

모델에 긴 문서를 넣을 때는 '몇 자까지'보다 '몇 토큰까지'를 확인해야 합니다. 입력에는 문서 외에도 시스템 지시, 대화 기록, 사용자 질문, 도구 결과가 들어갑니다. 출력을 생성할 공간도 미리 남겨야 하므로 총 한도와 입력 한도를 구분합니다.

3앞에서 배운 내용

01절에서 토큰화기로 문장의 토큰 수를 세었고, 03절에서는 입력 토큰 사이의 관계를 반영하는 어텐션 직관을 살펴봤습니다. 이 절에서는 Qwen2.5 토큰화기로 시스템, 문서, 질문을 각각 인코딩하고 합계를 구합니다. 현실 모델의 공식 한도를 재현하는 대신 계산 구조를 보이기 위해 512토큰의 실습용 한도를 설정합니다.

4핵심 개념

정의와 관찰

컨텍스트(context)는 모델이 현재 응답을 만들 때 함께 참조하도록 한 입력 전체입니다. 사용자 질문만 뜻하지 않으며 시스템 지시, 앞선 대화, 문서, 도구 결과도 포함합니다. 토큰화기는 이 입력을 토큰 ID 목록으로 바꾸고, 채팅 템플릿(chat template)은 역할 표시와 생성 시작 표시를 덧붙인 모델용 입력을 만듭니다.

컨텍스트 윈도(context window)는 모델이 한 번의 처리에서 참조할 수 있는 토큰 범위입니다. 모델별 공식 한도는 서로 다를 수 있고, 같은 모델이어도 제공 환경의 설정에 따라 달라질 수 있습니다. 한도 안에 들어간다는 말은 모델이 모든 정보를 같은 정확도로 사용한다는 뜻이 아닙니다.

노트북의 첫 계산은 각 문자열을 tokenizer.encode(text)에 넣고 토큰 ID 목록의 길이를 반환받습니다. 다음으로 apply_chat_template(..., tokenize=True)가 세 구성 요소를 실제 대화 형식으로 합친 토큰 ID 목록을 반환합니다. 원시 문자열의 토큰 수 합과 템플릿 적용 뒤의 입력 수가 다른 이유를 이 두 반환값으로 확인합니다.

토큰 예산(token budget)은 제한된 한도를 입력과 출력에 나눠 배정하는 계획입니다. 실습용 한도가 512이고 출력 64개를 예약하면 입력에는 448개가 남습니다. 채팅 템플릿을 적용한 실제 입력이 400개이므로 48개의 여유가 있습니다. 출력을 128개로 늘리면 입력 한도는 384개가 되어 현재 입력이 16개 초과합니다.

시스템 지시와 질문도 토큰을 사용합니다. 실습에서 시스템 지시 12개, 문서 360개, 질문 15개의 raw 텍스트 합계는 387개였습니다. 채팅 템플릿이 역할과 생성 시작 표시를 추가한 실제 입력은 400개였습니다. 예산 판정은 400을 기준으로 하고, 387은 구성 요소별 크기를 읽는 참고값으로 사용합니다.

한도를 넘는 입력은 무조건 뒷부분을 잘라 해결하지 않습니다. 뒷부분에 현재 질문이 있을 수 있고, 앞부분에 전체 작업 규칙이 있을 수 있습니다. 대화 요약, 관련 문서 선택, 중복 제거 등을 사용하되 남겨야 할 정보를 평가 자료로 확인합니다. 이 설계는 Ch 8 컨텍스트 엔지니어링에서 더 구체적으로 배웁니다.

토큰 예산은 정적인 문서 하나만 계산하고 끝나지 않습니다. 대화가 이어지거나 도구 결과가 추가되면 매 요청의 입력 크기가 달라집니다. 요청 전에 토큰 수를 기록하고, 한도에 가까운 요청은 문서 선택과 요약 정책을 적용합니다.

5실행 예제

시스템 지시, 문서, 질문을 각각 토큰화한 합과 채팅 템플릿을 적용한 전체 입력을 비교합니다. 이어서 출력 예약량을 32·64·128로 바꾸고 입력 한도를 계산한 뒤, 문서 반복 횟수별 실제 입력이 448 이하인지 판정합니다.

노트북을 새 Python 3.12 커널에서 첫 셀부터 순서대로 실행합니다.

준비된 Python 3.12 노트북에서 첫 셀부터 Shift+Enter로 하나씩 실행합니다. 안내한 결과를 먼저 확인하고 지정한 값 하나를 바꿔 비교합니다. 문서를 사용하는 실습은 파일 묶음이 필요합니다. 노트북과 실습 파일 함께 받기 · 처음 실습하는 방법. 전체 코드 복사에는 실험 셀 전체가 포함됩니다. 이 HTML에서는 코드를 실행하지 않습니다.

컨텍스트 윈도

모델에 넣을 수 있는 토큰 예산은 입력과 출력 사이에서 어떻게 나눌까요?

Python 3.12와 잠긴 패키지를 사용합니다. 첫 실행에서는 로컬 모델을 다운로드합니다.

입력 토큰 세기

시스템 지시, 문서, 질문 문자열이 입력입니다. parts는 이 세 문자열을 이름과 본문으로 묶은 사전입니다. messages는 role과 content를 가진 사전의 목록이며, system 역할에는 지시를, user 역할에는 문서와 질문을 넣습니다. encode()는 각 문자열의 토큰 ID 목록을 반환합니다. apply_chat_template(..., tokenize=True, add_generation_prompt=True)는 역할 표시와 모델이 답을 시작할 표시까지 추가한 토큰 ID 목록을 반환합니다. 출력의 원시 텍스트 합계와 채팅 템플릿 적용 입력을 비교합니다.

In [1]:
# 위 설명의 조건을 실행하고 실제 출력을 확인합니다.
import warnings
warnings.filterwarnings("ignore", message="IProgress not found")
from transformers import AutoTokenizer

MODEL_ID = "Qwen/Qwen2.5-0.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID, revision="7ae557604adf67be50417f59c2c2f167def9a775")
parts = {
    "시스템": "주어진 문서 범위에서만 답하세요.",
    "문서": "환불은 결제일로부터 7일 이내에 신청합니다. " * 20,
    "질문": "환불은 며칠 이내에 신청하나요?",
}


counts = {}
for name, text in parts.items():
    counts[name] = len(tokenizer.encode(text))
print(counts)
print("raw 텍스트 합계:", sum(counts.values()))
messages = [
    {"role": "system", "content": parts["시스템"]},
    {"role": "user", "content": parts["문서"] + "\n\n" + parts["질문"]},
]
actual_input = len(tokenizer.apply_chat_template(messages, tokenize=True, add_generation_prompt=True))
print("채팅 템플릿 적용 입력:", actual_input)
출력:
{'시스템': 12, '문서': 360, '질문': 15}
raw 텍스트 합계: 387
채팅 템플릿 적용 입력: 400

출력 공간 예약

512는 계산 구조를 보기 위한 실습용 전체 한도입니다. 처리식 input_budget = window - output_budget은 출력에 남긴 수를 전체에서 빼고 입력 한도를 반환합니다. 각 출력 줄에서 예약한 출력 수, 계산된 입력 한도, 현재 입력을 넣고 남은 수를 차례로 읽습니다. 음수는 현재 입력이 한도를 초과했다는 뜻입니다.

In [2]:
# 위 설명의 조건을 실행하고 실제 출력을 확인합니다.
window = 512
for output_budget in [32, 64, 128]:
    input_budget = window - output_budget
    remaining = input_budget - actual_input
    print(f"출력 {output_budget:3}개 예약 -> 입력 한도 {input_budget:3}개, 남은 입력 {remaining:3}개")
출력:
출력  32개 예약 -> 입력 한도 480개, 남은 입력  80개
출력  64개 예약 -> 입력 한도 448개, 남은 입력  48개
출력 128개 예약 -> 입력 한도 384개, 남은 입력 -16개

문서 길이 비교

동일한 문장을 늘려 언제 실습용 한도를 넘는지 관찰합니다.

In [3]:
# 위 설명의 조건을 실행하고 실제 출력을 확인합니다.
full_counts = {}
for repeat in [10, 20, 40, 80]:
    document = "환불은 결제일로부터 7일 이내에 신청합니다. " * repeat
    messages = [
        {"role": "system", "content": parts["시스템"]},
        {"role": "user", "content": document + "\n\n" + parts["질문"]},
    ]
    used = len(tokenizer.apply_chat_template(messages, tokenize=True, add_generation_prompt=True))
    full_counts[repeat] = used
    print(repeat, "반복:", used, "토큰 | 448 이하:", used <= 448)
출력:
10 반복: 220 토큰 | 448 이하: True
20 반복: 400 토큰 | 448 이하: True
40 반복: 760 토큰 | 448 이하: False
80 반복: 1480 토큰 | 448 이하: False

구조 검증

예상한 실험 조건과 출력 구조가 유지되었는지 확인합니다.

출력:
검증: 채팅 템플릿 입력과 20/40회 반복의 한도 분류를 확인했습니다.

6실험 결과 해석

채팅 템플릿을 적용하고 문서 문장을 10, 20, 40, 80회 반복했을 때 전체 입력은 220, 400, 760, 1480토큰이었습니다. 실습용 입력 한도 448을 적용하면 10회와 20회는 한도 이하였고 40회와 80회는 한도를 넘었습니다. 이 결과는 토큰화와 예산 계산만 보여 줍니다. 모델이 정답을 생성할 수 있는지나 어떤 절단 정책을 사용하는지는 측정하지 않았습니다.

7주의할 점과 실무 메모

  • 모델 카드의 총 한도와 API의 실제 요청 한도를 함께 확인합니다.
  • 출력 토큰을 예약하지 않으면 응답이 중간에 끊길 수 있습니다.
  • 한도 이내에 있다고 해서 모든 정보가 균등하게 사용되는 것은 아닙니다.

8정리와 다음 절

  • 컨텍스트 윈도는 한 번의 처리에서 참조할 수 있는 토큰 범위입니다.
  • 총 한도에서 출력 예산을 빼면 입력 예산을 구할 수 있습니다.
  • 지시, 문서, 질문, 대화 기록은 같은 입력 예산을 사용합니다.

다음 학습과 이어지는 지점 — 다음 절에서는 한도 안에 있는 정보도 길이와 위치에 따라 활용 결과가 달라질 수 있는지 실제 생성으로 관찰합니다.

9복습 문제

문제와 해설

1. 총 한도가 512이고 출력에 64개를 남겨 두면 입력 한도는 몇 개인가요?

해설 — 448개입니다.

2. 문서만 컨텍스트 예산을 사용하나요?

해설 — 아닙니다. 시스템 지시, 대화, 질문, 도구 결과도 포함됩니다.

3. 한도 이내의 모든 정보는 같은 정확도로 사용되나요?

해설 — 그렇지 않습니다. 한도는 처리 가능 범위이며 정보 활용 품질을 보장하지 않습니다.
