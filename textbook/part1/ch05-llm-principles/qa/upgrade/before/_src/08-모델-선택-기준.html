1학습 목표

  • 작업 종류와 라이선스를 필수 조건으로 사용해 맞지 않는 모델 후보를 제외할 수 있습니다.
  • 파라미터 수, 로딩 시간, 토큰화 시간을 각각 무엇을 측정한 값인지 구분할 수 있습니다.
  • 후보 필터 결과와 품질 비교 결과가 다름을 설명할 수 있습니다.
  • 실제 서비스 입력과 평가 기준으로 모델 선택 실험을 설계할 수 있습니다.

2이 내용을 배우는 이유

모델을 선택할 때 이름이 널리 알려졌거나 공개 점수가 높다는 이유만으로 결정하면 필요한 작업을 수행하지 못할 수 있습니다. 문장 생성, 문장 유사도 계산, 빈칸 채우기는 입력과 출력 형식이 다릅니다. 라이선스가 프로젝트의 배포 방식과 맞지 않으면 기술적으로 실행할 수 있어도 사용할 수 없습니다. 메모리에 올라가지 않거나 응답 시간이 목표를 넘는 모델도 서비스에 적용하기 어렵습니다. 먼저 반드시 만족해야 하는 조건으로 후보를 거르고, 남은 후보를 같은 평가 자료와 환경에서 측정해야 합니다.

이 절은 세 모델의 작업 종류와 라이선스를 비교합니다. 후보 표는 성능 순위가 아닙니다. 생성 작업과 Apache-2.0을 필수 조건으로 정했을 때 어떤 후보가 남는지 Python 목록 처리로 확인합니다. 이어서 선택된 생성 모델의 파라미터 수, 현재 환경의 캐시된 로딩 시간, 한 문장을 반복한 입력의 토큰화 시간을 측정합니다. 이 수치들은 생성 답변의 품질이나 첫 토큰까지 걸리는 시간을 직접 보여 주지 않습니다.

3앞에서 배운 내용

01절은 tokenizer가 문장을 토큰 ID로 바꾸는 결과를 비교했고, 02절은 문장 임베딩과 코사인 유사도가 특정 모델과 문장 집합에서의 근접도를 나타낸다는 점을 확인했습니다. 06절과 07절은 작은 생성 모델로 샘플링과 근거 없는 답변을 관찰했습니다. 같은 “언어 모델”이라는 넓은 이름 아래에서도 tokenizer, 임베딩 모델, 생성 모델의 역할이 다릅니다. 이번 절에서는 앞에서 사용한 모델을 하나의 순위표에 억지로 놓지 않고, 작업에 맞는 인터페이스부터 확인합니다.

노트북은 이미 사용한 고정 모델 ID와 모델 카드의 라이선스 표기를 후보 목록에 적습니다. Qwen/Qwen2.5-0.5B-Instruct는 텍스트 생성, sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2는 문장 유사도, klue/bert-base는 빈칸 채우기 후보로 기록합니다. 이 목록은 세 모델의 모든 가능한 용도를 설명하지 않으며, 실습에서 사용할 대표 작업을 구분하기 위한 자료입니다.

4핵심 개념

채용 공고의 필수 조건과 실기 평가를 나눕니다

AutoTokenizer.from_pretrained()는 모델 ID와 고정 revision을 입력받아 문자열을 토큰 ID로 바꾸는 tokenizer 객체를 반환합니다. AutoModelForCausalLM.from_pretrained()는 같은 식별자로 다음 토큰 생성용 모델 객체를 반환합니다. num_parameters()는 모델이 가진 파라미터 수를 정수로 반환합니다. 메서드 이름의 Auto는 모델 ID에 맞는 구체 클래스를 라이브러리가 선택한다는 뜻입니다.

운전 업무 지원자를 고를 때 먼저 필요한 면허가 있는지 확인합니다. 면허가 있는 후보끼리는 같은 도로에서 안전성과 업무 수행을 평가합니다. 면허 확인만으로 가장 안전한 운전자를 정할 수 없고, 주행 점수가 높아도 필요한 면허가 없으면 해당 업무를 맡길 수 없습니다. 모델 선택도 필수 조건 필터와 비교 평가를 분리합니다.

작업 종류(task)는 모델이 받는 입력과 만드는 출력의 목적입니다. 텍스트 생성 모델은 입력 뒤의 토큰을 이어 문장을 만들고, 문장 유사도 모델은 문장을 벡터로 바꾸어 거리를 비교하며, 빈칸 채우기 모델은 문장 안의 가려진 위치에 올 후보를 계산합니다. 필요한 작업과 다른 모델은 성능 비교 전에 제외합니다.

라이선스(license)는 모델 코드와 가중치를 사용할 때 지켜야 하는 조건입니다. 같은 Apache-2.0 표기라도 모델 카드, 데이터, 함께 배포하는 코드의 조건을 확인해야 합니다. CC-BY-SA-4.0처럼 표시와 공유 조건이 다른 후보도 있습니다. 이 절은 법률 자문을 제공하지 않습니다. 실제 배포 전에는 모델 카드 원문과 조직 정책을 확인합니다.

파라미터(parameter)는 학습 과정에서 조정되는 모델 내부의 수치입니다. 파라미터 수는 모델 규모를 설명하는 한 값이지만 정확도, 메모리, 파일 용량, 속도와 일대일로 같지 않습니다. 각 수치를 저장하는 정밀도, CPU나 GPU 중 어디서 실행하는지, 프로그램 구현에 따라 필요한 메모리와 처리 시간이 달라집니다.

로딩 시간(load time)은 모델 파일을 읽고 객체를 준비하는 데 걸린 시간입니다. 노트북의 cached load seconds는 모델 파일이 이미 로컬 캐시에 있는 현재 컴퓨터에서 한 번 측정한 0.384초입니다. 최초 다운로드 시간, 서버 시작 전체 시간, 요청마다 드는 생성 시간이 아닙니다. 토큰화 시간(tokenization time)은 문자열을 토큰 ID로 바꾸는 전처리 시간입니다. 기록된 3.631밀리초는 1,202토큰을 현재 CPU 환경에서 한 번 변환한 값이며, 답을 생성하는 시간이 아닙니다.

생성 지연시간(generation latency)은 입력 처리 후 출력 토큰을 만드는 데 걸리는 시간입니다. 첫 토큰 지연시간(time to first token, TTFT)은 요청을 시작한 뒤 첫 출력 토큰을 받을 때까지의 시간입니다. 이번 노트북은 생성 호출을 수행하지 않으므로 둘 다 측정하지 않았습니다. 서비스 모델을 선택할 때는 모델을 처음 실행하는 경우와 한 번 실행해 준비된 경우를 구분하고, 입력 길이, 출력 길이, 동시에 처리하는 요청 수를 고정해 별도로 측정해야 합니다.

5실행 예제

첫 코드 셀은 세 후보의 모델 ID, 대표 작업, 모델 카드 라이선스를 사전으로 만들고 한 줄씩 출력합니다. 이 표에서 Qwen은 생성, multilingual MiniLM은 문장 유사도, KLUE BERT는 빈칸 채우기로 구분됩니다. 다음 셀은 Qwen의 고정 revision을 로드해 파라미터 494,032,768개를 확인합니다. 이미 캐시된 모델의 로딩 시간은 0.384초였고, 같은 한국어 문장을 100번 반복한 입력은 1,202토큰으로 나뉘며 토큰화에 3.631밀리초가 걸렸습니다.

마지막 셀은 required_task를 text-generation, required_license를 apache-2.0으로 정합니다. for가 후보를 하나씩 읽고 두 비교 결과를 참 또는 거짓으로 저장합니다. and로 둘 다 참인지 확인한 뒤 eligible.append(item)으로 만족한 후보를 결과 목록에 추가하면 Qwen 후보 하나가 출력됩니다. 이것은 요구 조건에 맞는 후보를 찾은 결과입니다. 세 모델에 같은 생성 질문을 던져 Qwen의 품질이 더 좋다고 측정한 결과가 아닙니다. 나머지 두 모델은 애초에 대표 작업이 다르므로 이 생성 후보 필터에서 제외됐습니다.

확인할 점 — eligible 목록에는 한 모델만 남지만 출력의 마지막 문장은 선택 전에 실제 대표 질문과 정답 기준으로 품질과 속도를 측정해야 한다고 명시합니다. 자체 질의셋은 서비스에서 실제로 들어올 대표 질문과 질문별 정답 기준을 함께 모은 평가 자료입니다. 0.384초와 3.631밀리초를 생성 응답 시간이나 TTFT로 부르지 않습니다.

6실험 결과 해석

세 후보 중 필수 작업과 라이선스를 동시에 만족한 항목은 Qwen 하나였습니다. 이는 필터 조건을 코드로 정확히 적용했음을 보여 줍니다. 필수 라이선스를 바꾸거나 임베딩 작업을 선택하면 결과 목록도 달라집니다. 작업 종류와 라이선스 값은 실제 제품 요구에서 먼저 정해야 하며, 원하는 모델이 남도록 사후에 조건을 바꾸면 선택 기준의 의미가 없어집니다.

파라미터 수 494,032,768개는 실행 모델이 약 0.49B 규모라는 모델 카드 정보와 맞습니다. 이 값만으로 품질이나 메모리 사용량을 결정할 수 없습니다. 캐시된 로딩 0.384초도 현재 한 번의 실행 결과입니다. 디스크 캐시, 운영체제 상태, 장치, 패키지 버전에 따라 달라질 수 있습니다. 최초 설치에서는 모델 다운로드 시간이 추가됩니다.

1,202토큰을 3.631밀리초에 토큰화한 측정은 전처리 한 단계만 포함합니다. 모델이 입력을 계산하고 새 토큰을 만드는 시간, 네트워크 전송, 요청 대기, 생성 중인 답을 조금씩 전송하는 시간은 포함하지 않습니다. 따라서 “모델 응답이 1밀리초”라고 설명하면 잘못입니다. 실제 후보 비교에서는 같은 입력·출력 길이와 반복 횟수로 전체 지연과 TTFT를 여러 번 측정합니다. 측정값을 정렬해 가운데에 있는 값과 느린 실행 사례도 품질 평가와 함께 기록합니다.

7주의할 점과 실무 메모

  • 모델 카드의 task 표기는 후보 분류의 시작점입니다. 실제 코드 인터페이스와 입력·출력 형식이 서비스 요구에 맞는지 작은 실행으로 확인합니다.
  • 라이선스 이름만 복사하지 말고 고정 revision의 모델 카드, 가중치, 코드, 데이터 관련 조건을 확인합니다. 조건이 바뀔 수 있으므로 확인 날짜를 남깁니다.
  • 파라미터 수가 큰 모델이 모든 업무에서 더 좋은 것은 아닙니다. 자체 질의셋의 정답 기준과 실패 비용으로 품질을 측정합니다.
  • 캐시된 로딩 시간은 최초 다운로드와 서버 시작 시간을 포함하지 않습니다. 모델을 처음 불러오는 경우와 이미 불러온 경우를 분리해 측정합니다.
  • 토큰화 시간은 생성 시간이나 TTFT가 아닙니다. 측정 구간의 시작과 끝을 코드로 명시합니다.
  • 후보가 하나 남았다는 사실은 선택이 끝났다는 뜻이 아닙니다. 품질, 지연, 메모리, 비용, 운영 제약을 만족하지 못하면 다른 후보를 추가합니다.

8정리와 다음 절

  • 작업 종류와 라이선스 같은 필수 조건으로 후보를 먼저 거르고 남은 모델만 같은 기준으로 평가합니다.
  • 이번 측정의 로딩 시간과 토큰화 시간은 생성 지연이나 첫 토큰 지연을 나타내지 않습니다.
  • 후보 필터는 품질 비교가 아니므로 서비스의 대표 질문과 정답 기준으로 만든 자체 질의셋과 운영 환경 측정이 필요합니다.

다음 학습과 이어지는 지점 — Ch 6에서는 외부 모델 API를 LangChain의 공통 인터페이스로 호출하고 메시지와 응답 객체를 다룹니다. Ch 5의 로컬 Qwen·MiniLM·KLUE 표를 그대로 사용하지 않고, 생성 API를 제공하는 OpenAI·Anthropic·Google 후보에 작업 적합성과 키 준비 여부를 적용합니다. Ch 6의 1회 호출 기록은 모델 품질 순위가 아닙니다. Ch 11은 검색 결과를 자체 질의셋과 검색 지표로 측정하고, 생성 답변의 정확성과 근거성은 Ch 15에서 별도로 평가합니다.

9복습 문제

문제와 해설

1. 생성 작업과 Apache-2.0을 필수 조건으로 적용했을 때 어떤 후보가 남았습니까?

정답: Qwen/Qwen2.5-0.5B-Instruct 하나가 남았습니다. 다른 두 후보는 대표 작업이나 라이선스 조건이 달랐습니다.

2. 캐시된 로딩 시간 0.384초가 포함하지 않는 시간을 두 가지 쓰십시오.

정답: 최초 모델 다운로드 시간과 실제 출력 토큰 생성 시간을 포함하지 않습니다. 네트워크·큐 대기와 전체 서버 시작도 별도입니다.

3. 1,202토큰을 3.631밀리초에 처리한 값을 생성 지연시간이라고 부를 수 없는 이유는 무엇입니까?

정답: tokenizer가 문자열을 토큰 ID로 바꾸는 전처리만 측정했고 모델 추론과 새 토큰 생성은 실행하지 않았기 때문입니다.

4. 필수 조건 필터 뒤에도 자체 질의셋 평가가 필요한 이유는 무엇입니까?

정답: 필터는 작업·라이선스 적합성만 확인하며 실제 업무 답변의 정확도, 실패 유형, 지연, 비용을 비교하지 않기 때문입니다.
