1학습 목표

  • 파일 삭제와 Git 이력에서 경로를 제거하는 작업의 차이를 설명할 수 있습니다.
  • 격리된 더미 저장소에서 git-filter-repo로 특정 경로의 이력을 재작성할 수 있습니다.
  • 실제 자격 증명 노출 시 폐기·교체, 협업 조율, 예방 검사가 모두 필요한 이유를 설명할 수 있습니다.

2이 내용을 배우는 이유

API 키나 접근 토큰을 커밋한 뒤 현재 파일에서 삭제하면 작업 폴더에는 보이지 않습니다. 그러나 이전 커밋을 읽을 수 있는 사람은 여전히 값을 찾을 수 있습니다. 공개 저장소의 복제본, 포크, 캐시, 빌드 로그로 값이 복사됐을 가능성도 있습니다. 따라서 실제 자격 증명 사고의 첫 조치는 Git 명령이 아니라 발급 서비스에서 값을 폐기하거나 교체하는 일입니다. 이력 정리는 노출 범위를 줄이고 저장소를 정돈하는 후속 조치입니다. 이 절은 실제로 사용할 수 없는 더미 문자열과 임시 원격만 사용해 파일 삭제가 부족한 이유를 관찰하고, 예방과 대응의 순서를 구분합니다.

4핵심 개념

복사된 열쇠는 문에서 무효화합니다

출입 열쇠 사진이 공개됐다면 게시물을 지우기 전에 기존 열쇠가 문을 열지 못하게 해야 합니다. 시크릿(secret)은 API 키, 접근 토큰, 비밀번호처럼 권한을 부여하는 값입니다. 실제 값이 공개되면 먼저 발급 서비스에서 폐기하거나 교체합니다. .env를 작업 폴더에서 삭제하고 다음 커밋에 기록해도 이전 커밋 객체에는 과거 내용이 남습니다. git show <커밋>:.env에서 콜론 앞은 읽을 커밋, 뒤는 그 커밋 안의 파일 경로입니다.

.gitignore는 아직 추적하지 않는 파일이 기본 add 대상에 포함되지 않게 합니다. git check-ignore -v .env의 -v는 적용된 규칙과 규칙 파일을 표시합니다. git ls-files .env가 비어 있으면 색인에 등록되지 않았다는 뜻입니다. 이미 커밋한 파일, 로그에 출력한 값, 채팅이나 빌드 시스템으로 복사된 값에는 이 규칙이 소급 적용되지 않습니다.

실제 값이 공개됐다면 먼저 발급 서비스에서 폐기(revoke)하거나 교체(rotate)합니다. 저장소 이력을 정리하는 동안 누군가 이미 값을 복사했을 수 있기 때문입니다. 값의 권한을 없앤 뒤 저장소 관리자와 이력 재작성 범위를 정하고, 호스팅 서비스의 캐시·포크·열린 PR에 대한 제거 절차를 확인합니다.

이력 재작성 명령의 대상을 읽습니다

이력 재작성(history rewriting)은 조건에 맞는 새 커밋 이력을 만드는 작업입니다. git-filter-repo는 이를 수행하는 도구입니다. git filter-repo --path .env --invert-paths에서 --path .env는 선택할 경로를 지정하고, --invert-paths는 선택을 반대로 바꾸어 그 경로를 제외합니다. 파일이 포함됐던 커밋과 그 뒤 자손의 해시가 달라집니다.

git clone --mirror는 일반 작업 폴더 없이 브랜치와 태그 등 참조를 넓게 복제합니다. 정리 뒤 git push --force --mirror는 원격 참조를 새 이력에 맞춰 강제로 갱신합니다. --force는 협업자의 기존 이력과 충돌할 수 있으므로 실제 저장소에서는 관리자 조율과 백업·검증 없이 실행하지 않습니다. 실습 출력의 경로 없음과 값 커밋 0건은 임시 mirror에서 검사한 참조 범위만 증명합니다.

예방은 여러 층으로 구성합니다. .gitignore로 흔한 환경 파일을 제외하고, 값이 비어 있는 settings.example을 공유하며, 커밋 전에 스테이징한 변경을 직접 읽습니다. 저장소의 시크릿 검사 도구와 호스팅 서비스의 차단 기능도 사용합니다. 한 층이 누락을 발견하면 실제 원격에 게시되기 전에 멈출 수 있습니다.

도식 읽기

실제 유출에서는 제공자에서 자격 증명을 먼저 폐기·교체합니다. 그 뒤 저장소 관리자와 협업자가 재작성 범위를 정하고 이력을 정리·원격 갱신한 뒤 새 이력을 다시 받습니다. 이 노트북은 외부 서비스의 폐기·교체를 실행하지 않으며, 더미 문자열의 경로·값이 격리된 원격의 검사 범위에서 사라졌는지만 확인합니다.

5실행 예제

준비 셀은 임시 bare 원격과 작업 저장소를 만들고 안전한 앱을 main에 게시합니다. 자격 증명 역할을 하는 변수 이름을 사용하지만 값은 명백한 더미입니다. 다음 셀은 .env를 무시하도록 설정하고 git check-ignore -v로 실제 적용 규칙을 확인합니다. git ls-files .env가 빈 문자열이므로 색인에 포함되지 않았습니다.

공유 가능한 settings.example에는 실제 값 대신 replace-me를 적습니다. 커밋 전에 git diff --cached를 읽고 더미 자격 증명 문자열조차 포함되지 않았는지 검사합니다. 실제 조직에서는 알려진 접두사, 문자열의 무작위성 정도, 제공자 규칙을 검사하는 전용 도구를 함께 사용합니다. 문자열 한 개를 검사한 이번 셀이 모든 종류의 시크릿을 찾는다고 해석해서는 안 됩니다.

시크릿 이력 정리와 예방

모든 저장소는 임시 폴더에 만들며 실제 GitHub 계정이나 원격 저장소를 변경하지 않습니다.

명령을 실행하기 전에 알아둘 Git 상태

Git은 파일을 세 자리에서 봅니다. 작업 폴더(working tree) 는 지금 편집하는 파일이 있는 자리입니다. 색인(index) 은 다음 커밋에 넣을 파일 상태를 골라 두는 자리이며, 스테이징 영역(staging area)이라고도 합니다. 커밋(commit) 은 색인에 고른 상태를 저장소 이력에 기록한 결과입니다. 따라서 git add app.py는 파일을 영구 저장하는 명령이 아니라 현재 app.py를 색인에 올리는 명령입니다. 이어서 git commit -m "메시지"를 실행해야 그 상태가 커밋으로 기록됩니다.

HEAD 는 현재 체크아웃한 커밋을 가리킵니다. 보통 HEAD는 main 같은 브랜치(branch) 이름을 가리키고, 브랜치 이름은 다시 최신 커밋을 가리킵니다. 새 커밋을 만들면 현재 브랜치가 새 커밋으로 이동합니다. 이 절에서는 브랜치와 태그처럼 커밋을 가리키는 이름을 묶어 참조(reference)라고 부릅니다.

명령은 왼쪽부터 git → 하위 명령 → 옵션 → 대상으로 읽습니다. 예를 들어 git status --short에서 status는 상태를 보고, --short는 짧은 형식으로 표시하라는 옵션입니다. 코드의 git("status", "--short", cwd=repo)는 터미널에서 같은 명령을 실행하도록 인자를 나눈 Python 표현입니다.

준비

예제 문자열은 실제 서비스에서 사용할 수 없는 더미 자격 증명입니다. 시크릿(secret) 은 API 키, 접근 토큰, 비밀번호처럼 권한을 부여하는 값입니다. 실제 값이 노출되면 Git 이력 정리를 기다리지 말고 발급 서비스에서 먼저 폐기하거나 교체해야 합니다. 이미 복제되거나 로그에 남은 값은 저장소 파일을 지워도 다시 통제할 수 없기 때문입니다.

이 실습은 DEMO-ONLY-NOT-A-REAL-SECRET만 사용합니다. 원격도 임시 폴더의 bare 저장소이므로 외부에 게시되지 않습니다. 이후 출력의 “0건”은 이 임시 저장소에서 검사한 참조에 더미 값이 없다는 뜻이며 외부 캐시나 다른 복제본까지 삭제했다는 뜻은 아닙니다.

In [1]:
# 셀이 만든 저장소만 사용하는 임시 작업 폴더를 준비합니다.
import subprocess
import sys
import tempfile
from pathlib import Path
workspace = tempfile.TemporaryDirectory(prefix="git-lesson-")
root = Path(workspace.name)
# cwd는 명령을 실행할 폴더이며 check=True는 명령 실패를 예외로 알립니다.
def git(*args: str, cwd: Path | None = None, check: bool = True) -> str:
    """지정한 임시 저장소에서 Git 명령을 실행합니다."""
    result = subprocess.run(["git", *args], cwd=cwd or root,
                            text=True, capture_output=True, check=check)
    return result.stdout.strip() or result.stderr.strip()
def configure(repo: Path) -> None:
    """실습 저장소에만 작성자 정보를 설정합니다."""
    git("config", "user.name", "Git Learner", cwd=repo)
    git("config", "user.email", "learner@example.invalid", cwd=repo)

기본 실행

추적 전에는 .gitignore와 스테이징한 변경 검사를 함께 적용합니다. git check-ignore -v .env에서 -v는 어떤 규칙이 어느 파일에 적용됐는지 보여 줍니다. git ls-files .env는 색인에 등록된 경로를 찾으며, 빈 출력이면 .env가 현재 커밋 후보에 포함되지 않았다는 뜻입니다.

.gitignore는 아직 추적하지 않는 경로를 기본 git add 대상에서 제외할 뿐 파일을 암호화하거나 과거 커밋을 지우지 않습니다. git diff --cached -- settings.example은 다음 커밋에 들어갈 실제 내용을 보여 주므로 커밋 직전 시크릿 검사 지점으로 사용합니다.

In [3]:
# .env를 추적하기 전에 무시 규칙이 적용되는지 확인합니다.
(repo / ".gitignore").write_text(".env\n", encoding="utf-8")
(repo / ".env").write_text(f"DEMO_API_KEY={DUMMY}\n", encoding="utf-8")
git("add", ".gitignore", cwd=repo)
git("commit", "-m", "chore: 환경 파일 제외", cwd=repo)
print(git("check-ignore", "-v", ".env", cwd=repo))
print("색인에 없음:", git("ls-files", ".env", cwd=repo) == "")
출력:
.gitignore:1:.env	.env
색인에 없음: True

값 하나를 바꿔 검사

안전한 설정 예시는 커밋할 수 있지만 더미 키 패턴이 있으면 검사를 실패로 판정합니다.

In [4]:
# 스테이징한 변경은 이번 커밋에 실제로 포함될 내용만 보여 줍니다.
(repo / "settings.example").write_text("DEMO_API_KEY=replace-me\n", encoding="utf-8")
git("add", "settings.example", cwd=repo)
staged = git("diff", "--cached", "--", "settings.example", cwd=repo)

print("더미 자격 증명 발견:", contains_dummy)
print(staged)
assert not contains_dummy
git("commit", "-m", "docs: 설정 예시 추가", cwd=repo)
print("안전한 설정 예시 커밋 완료")

6일부러 실패해 보기

실패 셀은 교육 목적을 분명히 하기 위해 git add -f로 무시 규칙을 우회하고 더미 .env를 커밋합니다. 다음 커밋에서 파일을 삭제하고 원격에 push합니다. 현재 작업 폴더에는 파일이 없지만 git show 커밋:.env는 이전 내용을 반환합니다. 이것이 “현재 파일 삭제”와 “이력에서 제거”가 다른 실제 증거입니다. 실제 시크릿으로 이 과정을 따라 하면 노출이 더 확대되므로 절대 사용하지 않습니다.

수정 셀의 git filter-repo --force에서 --force는 새 복제본인지 확인하는 안전 검사를 완화합니다. 이 실습은 방금 만든 임시 mirror에만 사용합니다. git rev-list --objects --all의 각 행은 객체 해시와 경로를 담습니다. objects.splitlines()가 행 목록을 만들고 line.endswith(" .env")가 경로가 정확히 .env로 끝나는지 검사하며, any(...)는 일치 행이 하나라도 있을 때만 True를 반환합니다. 출력 False와 더미 값 커밋 0건은 검사한 참조 범위에서 경로와 값에 도달하지 못한다는 뜻이며 외부 포크·캐시·로그 삭제를 증명하지 않습니다.

파일을 다음 커밋에서 삭제해도 이전 커밋 객체에는 내용이 남습니다.

In [5]:
# 가상 키 파일을 다음 커밋에서 삭제해도 과거 커밋에는 값이 남습니다.
git("check-ignore", "-q", ".env", cwd=repo)
git("add", "-f", ".env", cwd=repo)
git("commit", "-m", "test: 더미 키를 잘못 기록", cwd=repo)
leak_commit = git("rev-parse", "HEAD", cwd=repo)
git("rm", ".env", cwd=repo)
git("commit", "-m", "fix: 환경 파일 삭제", cwd=repo)
git("push", cwd=repo)
historic = git("show", f"{leak_commit}:.env", cwd=repo)
print("현재 파일 존재:", (repo / ".env").exists())
print("이전 커밋 내용:", historic.strip())
assert DUMMY in historic
출력:
현재 파일 존재: False
이전 커밋 내용: DEMO_API_KEY=DEMO-ONLY-NOT-A-REAL-SECRET

After — 수정 코드

수정

격리된 예제 저장소의 모든 참조에서 .env 경로를 제거한 뒤 원격을 강제로 갱신합니다. git filter-repo --force의 --force는 새로 복제한 저장소인지 확인하는 안전 검사를 완화합니다. 이 실습은 방금 만든 임시 mirror에만 사용하며 실제 작업 저장소에서 실행할 이유가 되지 않습니다.

git rev-list --objects --all의 각 행은 객체 해시와 경로를 담습니다. objects.splitlines()가 행 목록을 만들고, line.endswith(" .env")는 공백 뒤 경로가 정확히 .env로 끝나는 행인지 검사합니다. any(...)는 그런 행이 하나라도 있으면 True, 하나도 없으면 False를 반환합니다. 따라서 출력 False는 검사한 모든 참조에서 .env 경로를 찾지 못했다는 뜻입니다. 별도의 git log -S 결과 0건은 더미 문자열을 추가하거나 제거한 커밋도 찾지 못했다는 뜻입니다.

len(value_hits.splitlines()) if value_hits else 0은 결과 문자열이 있으면 행 수를 세고, 빈 문자열이면 0을 사용합니다. 따라서 검색 결과가 없을 때 출력되는 0은 빈 결과를 숫자로 표시한 값입니다.

In [6]:
# 격리된 원격의 모든 참조를 갱신하고 새 복제본에서 경로와 값을 검사합니다.
clean = root / "clean-history"
git("clone", "--mirror", remote.as_posix(), clean.as_posix())
result = subprocess.run(
    ["git", "filter-repo", "--force", "--path", ".env", "--invert-paths"],
    cwd=clean, text=True, capture_output=True, check=True,
)
git("remote", "add", "origin", remote.as_posix(), cwd=clean)
git("push", "--force", "--mirror", cwd=clean)
objects = git("rev-list", "--objects", "--all", cwd=clean)
value_hits = git("log", "-S", DUMMY, "--all", "--format=%H", cwd=clean)
print("정리 후 .env 경로 있음:", any(line.endswith(" .env") for line in objects.splitlines()))
print("정리 후 더미 값 커밋 수:", len(value_hits.splitlines()) if value_hits else 0)
verify = root / "verify-remote"
git("clone", "--mirror", remote.as_posix(), verify.as_posix())
remote_objects = git("rev-list", "--objects", "--all", cwd=verify)
remote_hits = git("log", "-S", DUMMY, "--all", "--format=%H", cwd=verify)
print("원격 재검사 값 커밋 수:", len(remote_hits.splitlines()) if remote_hits else 0)
assert not any(line.endswith(" .env") for line in objects.splitlines())
assert not any(line.endswith(" .env") for line in remote_objects.splitlines())
assert not value_hits and not remote_hits
출력:
정리 후 .env 경로 있음: False
정리 후 더미 값 커밋 수: 0
원격 재검사 값 커밋 수: 0

7주의할 점과 실무 메모

  • 실제 시크릿을 실습 파일, 터미널 명령 인자, 채팅, 이슈에 붙여 넣지 않습니다. 노출된 값은 먼저 제공자에서 폐기하거나 교체합니다.
  • 이력 재작성은 커밋 해시를 바꿉니다. 저장소 관리자와 시점, 대상 브랜치와 태그, 강제 push 권한, 협업자의 재복제 절차를 합의합니다.
  • 이력에서 경로가 사라졌다는 검사만으로 다른 경로에 복사된 동일 값이 없다고 결론 내릴 수 없습니다. 경로 검사와 값 검사를 함께 수행합니다.
  • 로컬 reflog와 호스팅 서비스의 캐시·포크·PR 참조는 별도 범위입니다. 서비스 제공자의 공식 지원 절차와 보존 정책을 확인합니다.
  • .gitignore는 예방의 한 층입니다. 이미 추적한 파일과 명령 출력, 로그, 노트북 출력에는 적용되지 않습니다.
  • 이 챕터는 git-filter-repo 2.47.0을 고정합니다. 다른 버전이나 대규모 저장소에서는 공식 문서와 백업·검증 절차를 먼저 확인합니다.

8정리와 다음 절

  • 현재 파일을 삭제해도 과거 커밋에는 내용이 남을 수 있습니다.
  • 실제 시크릿 사고에서는 권한을 먼저 폐기·교체하고 이력 정리와 협업자 조치를 이어서 수행합니다.
  • .gitignore, 안전한 예시 파일, 스테이징한 변경 확인, 시크릿 검사를 겹쳐 적용합니다.

다음 학습과 이어지는 지점 — Ch 4는 별도의 실습 프로젝트와 제공 데이터로 시작하며, CSV·JSON·API 데이터를 처리하는 함수를 만듭니다. Ch 3의 임시 저장소를 입력으로 사용하지는 않지만, 시크릿을 제외하고 diff를 확인하는 습관은 Ch 4 프로젝트의 변경을 검토할 때도 적용합니다. 후반 AI 페어 개발에서는 Git 커밋이 자동 생성 변경을 되돌릴 수 있는 지점이 되고, Ch 38에서는 커밋 전 시크릿 검사를 게이트로 자동화합니다.

9복습 문제

문제와 해설

1. 실수로 커밋한 실제 API 키를 발견했을 때 가장 먼저 할 일은 무엇입니까?

정답: 키 발급 서비스에서 노출된 키를 폐기하거나 교체해 더 이상 권한을 사용할 수 없게 합니다.

2. 현재 .env를 삭제한 뒤에도 이전 내용을 읽을 수 있었던 명령은 무엇입니까?

정답: git show <이전-커밋>:.env입니다. 특정 커밋에 저장된 파일 내용을 읽습니다.

3. 이력 재작성 뒤 협업자 조율이 필요한 이유는 무엇입니까?

정답: 커밋 해시가 달라지고 원격을 강제로 갱신하므로 협업자가 이전 이력을 다시 push하거나 새 이력과 섞지 않도록 작업을 옮기는 절차가 필요합니다.

4. .gitignore만으로 시크릿 사고를 완전히 막을 수 없는 이유를 두 가지 쓰십시오.

정답: 이미 추적한 파일과 과거 이력에는 소급 적용되지 않으며, 다른 파일·로그·노트북 출력에 적힌 값도 검사하지 못하기 때문입니다.
