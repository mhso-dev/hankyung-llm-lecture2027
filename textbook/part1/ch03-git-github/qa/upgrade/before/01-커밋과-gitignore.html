1학습 목표

  • 작업 폴더, 스테이징 영역, 커밋의 차이를 실제 상태 출력으로 설명할 수 있습니다.
  • 한 가지 목적이 드러나는 커밋을 만들고 메시지로 변경 이유를 기록할 수 있습니다.
  • .gitignore 규칙을 적용하고 이미 추적 중인 파일을 색인에서만 제거할 수 있습니다.

2이 내용을 배우는 이유

프로그램을 수정하다 보면 소스 코드뿐 아니라 실행 로그, 캐시, 개인 설정 파일도 함께 생깁니다. 이 파일을 모두 저장하면 리뷰할 변경이 흐려지고 컴퓨터마다 다른 값이 저장소에 섞입니다. 반대로 필요한 소스까지 빠뜨리면 다른 사람이 같은 결과를 만들 수 없습니다. Git을 사용할 때 첫 판단은 “어떤 변경을 함께 설명할 것인가”와 “어떤 파일을 애초에 추적하지 않을 것인가”입니다. 이 절에서는 파일 상태를 눈으로 확인한 뒤 필요한 변경만 커밋하고, 무시 규칙이 적용되는 시점을 구분합니다.

3앞에서 배운 내용

Ch 1에서 터미널의 현재 폴더를 확인하고 Git 설치 여부를 검사했습니다. Ch 2에서는 Path.write_text()로 파일을 만들고 subprocess.run()으로 외부 명령을 실행했습니다. 이번 노트북은 이 두 기능으로 임시 Git 저장소를 만듭니다. Git 작성자 이름과 전자우편 주소는 임시 저장소의 로컬 설정에만 기록하므로 개인 설정을 바꾸지 않습니다.

4핵심 개념

사진을 찍기 전에 대상을 고릅니다

여행 사진 한 장에는 같은 순간을 설명하는 장면을 담습니다. 점심 식사와 다음 날의 기차표를 한 사진에 억지로 담으면 제목을 붙이기 어렵습니다. Git의 커밋(commit)도 선택한 파일 상태와 설명을 묶은 기록입니다. 편집기에서 저장한 app.py는 작업 폴더(working tree)에 있습니다. git add app.py를 실행하면 그 순간의 파일 상태가 다음 커밋 후보인 색인(index), 즉 스테이징 영역(staging area)에 올라갑니다. 예제 메시지의 feat, fix, chore는 변경 목적을 구분하는 팀 관례이며 Git의 필수 문법이 아닙니다. git commit -m "feat: 주문 요약 추가"를 실행하면 색인에 고른 상태가 새 커밋으로 기록됩니다.

구체적으로 app.py가 주문 2건을 출력하는 상태를 add한 뒤 작업 폴더에서 3건으로 다시 고치면, 색인에는 2건이 남고 작업 폴더에는 3건이 있습니다. 이때 커밋하면 2건 상태가 기록됩니다. git diff는 작업 폴더와 색인의 차이를, git diff --cached는 색인과 현재 커밋의 차이를 보여 줍니다. 어느 두 자리를 비교하는지 먼저 말할 수 있어야 출력의 -와 +를 올바르게 읽을 수 있습니다.

HEAD는 현재 체크아웃한 커밋을 가리킵니다. 보통 HEAD는 main 같은 브랜치 이름을 가리키고, 브랜치는 최신 커밋을 가리킵니다. 새 커밋을 만들면 현재 브랜치가 새 커밋으로 이동합니다. git log가 보여 주는 연속된 기록은 파일 사본의 목록이 아니라 부모 커밋으로 연결된 스냅샷의 이력입니다.

명령과 기호를 왼쪽부터 읽습니다

git status --short --ignored는 git 프로그램의 status 하위 명령을 실행하며, --short는 짧은 형식, --ignored는 무시된 파일도 표시하라는 옵션입니다. git commit -m "메시지"의 -m 뒤 문자열은 커밋 제목입니다. git diff -- app.py의 --는 뒤의 값을 옵션이 아닌 파일 경로로 구분합니다. 옵션을 외우기 전에 명령, 옵션, 대상 경로를 나누어 읽습니다.

.gitignore는 아직 추적하지 않은 파일 중 Git 상태 목록에서 제외할 경로 패턴을 기록합니다. .env 한 줄은 해당 이름의 환경 설정 파일을, __pycache__/는 Python 캐시 폴더를 제외합니다. 이 규칙 자체는 팀이 공유해야 하므로 커밋합니다.

도식 읽기

작업 폴더의 새 app.py와 .env는 먼저 .gitignore 규칙을 확인합니다. 추적할 app.py는 git add를 거쳐 스테이징 영역에서 선택되고 git commit으로 기록됩니다. .env는 규칙과 일치해 스테이징 대상에서 제외됩니다.

5실행 예제

준비 셀은 운영체제의 임시 폴더 아래에 orders 저장소를 만들고 기본 브랜치를 main으로 정합니다. 기본 실행 셀은 .gitignore만 스테이징해 생성 파일을 무시하는 첫 커밋을 만들고, 이어 app.py를 두 번째 커밋에 기록합니다. 함께 만든 .env는 !! .env로 표시되어 무시 규칙이 동작했음을 확인할 수 있습니다. 이 파일의 값은 자격 증명이 아닌 APP_MODE=demo입니다.

다음 셀에서는 주문 숫자만 2에서 3으로 바꿉니다. git diff의 빼기 줄과 더하기 줄을 읽으면 변경 범위가 한 줄임을 알 수 있습니다. 커밋 메시지 fix: 주문 건수 수정은 파일 이름 대신 변경 이유를 설명합니다. 실제 팀에서는 저장소가 정한 메시지 규칙을 따르되, 제목만 읽어도 의도를 파악할 수 있게 씁니다.

커밋과 .gitignore

모든 저장소는 임시 폴더에 만들며 실제 GitHub 계정이나 원격 저장소를 변경하지 않습니다.

명령을 실행하기 전에 알아둘 Git 상태

Git은 파일을 세 자리에서 봅니다. 작업 폴더(working tree) 는 지금 편집하는 파일이 있는 자리입니다. 색인(index) 은 다음 커밋에 넣을 파일 상태를 골라 두는 자리이며, 스테이징 영역(staging area)이라고도 합니다. 커밋(commit) 은 색인에 고른 상태를 저장소 이력에 기록한 결과입니다. 따라서 git add app.py는 파일을 영구 저장하는 명령이 아니라 현재 app.py를 색인에 올리는 명령입니다. 이어서 git commit -m "메시지"를 실행해야 그 상태가 커밋으로 기록됩니다.

HEAD 는 현재 체크아웃한 커밋을 가리킵니다. 보통 HEAD는 main 같은 브랜치(branch) 이름을 가리키고, 브랜치 이름은 다시 최신 커밋을 가리킵니다. 새 커밋을 만들면 현재 브랜치가 새 커밋으로 이동합니다. 이 절에서는 HEAD가 현재 커밋을 가리킨다는 관계까지만 사용합니다.

명령은 왼쪽부터 git → 하위 명령 → 옵션 → 대상으로 읽습니다. 예를 들어 git status --short에서 status는 상태를 보고, --short는 짧은 형식으로 표시하라는 옵션입니다. 코드의 git("status", "--short", cwd=repo)는 터미널에서 같은 명령을 실행하도록 인자를 나눈 Python 표현입니다.

준비

임시 저장소를 만들고 이 노트북에만 적용되는 작성자 정보를 설정합니다. git init -b main에서 init은 현재 폴더를 Git 저장소로 만들고, -b main은 첫 브랜치 이름을 main으로 정합니다. 아직 커밋이 없으므로 브랜치 이름만 준비된 상태입니다.

이 절에서는 app.py가 작업 폴더, 색인, 커밋을 차례로 이동하는 모습을 확인합니다. .env는 작업 폴더에는 있지만 .gitignore 규칙 때문에 색인에 올라가지 않습니다. 두 파일이 같은 폴더에 있어도 Git의 추적 상태는 다를 수 있습니다.

In [1]:
# 셀이 만든 저장소만 사용하는 임시 작업 폴더를 준비합니다.
import subprocess
import sys
import tempfile
from pathlib import Path
workspace = tempfile.TemporaryDirectory(prefix="git-lesson-")
root = Path(workspace.name)
# cwd는 명령을 실행할 폴더이며 check=True는 명령 실패를 예외로 알립니다.
def git(*args: str, cwd: Path | None = None, check: bool = True) -> str:
    """지정한 임시 저장소에서 Git 명령을 실행합니다."""
    result = subprocess.run(["git", *args], cwd=cwd or root,
                            text=True, capture_output=True, check=check)
    return result.stdout.strip() or result.stderr.strip()
def configure(repo: Path) -> None:
    """실습 저장소에만 작성자 정보를 설정합니다."""
    git("config", "user.name", "Git Learner", cwd=repo)
    git("config", "user.email", "learner@example.invalid", cwd=repo)
In [2]:
# 저장소를 main 브랜치로 초기화합니다.
repo = root / "orders"
repo.mkdir()
git("init", "-b", "main", cwd=repo)
configure(repo)
print(repo.name, git("branch", "--show-current", cwd=repo))
출력:
orders main

기본 실행

커밋 메시지 앞의 feat, fix, chore는 이 교재가 변경 목적을 구분하려고 사용한 팀 관례입니다. Git이 요구하는 필수 문법이 아니며 저장소마다 다른 규칙을 사용할 수 있습니다.

무시 규칙을 첫 커밋에, 프로그램을 다음 커밋에 기록합니다. git add .gitignore는 그 파일만 색인에 올리고, git commit -m ...의 -m은 커밋 메시지를 명령줄에서 지정합니다. 다음 git add app.py는 새 색인을 구성하므로 두 커밋은 서로 다른 목적을 갖습니다.

실행 뒤 git status --short --ignored에서 앞의 !!는 무시된 파일, git log -2 --pretty=%s의 -2는 최근 두 커밋, %s는 제목만 출력하라는 뜻입니다. .env가 !!로 보이고 두 메시지가 역시간순으로 나오면 작업 폴더의 모든 파일이 자동으로 커밋되는 것이 아님을 확인한 것입니다.

In [3]:
# 무시 규칙과 기능 코드를 나누어 기록하고 두 커밋의 메시지를 확인합니다.
(repo / "app.py").write_text('print("주문 2건")\n', encoding="utf-8")
(repo / ".gitignore").write_text(".env\n__pycache__/\n", encoding="utf-8")
(repo / ".env").write_text("APP_MODE=demo\n", encoding="utf-8")
git("add", ".gitignore", cwd=repo)
git("commit", "-m", "chore: 생성 파일 추적 제외", cwd=repo)
git("add", "app.py", cwd=repo)
git("commit", "-m", "feat: 주문 요약 추가", cwd=repo)
print(git("status", "--short", "--ignored", cwd=repo))
print(git("log", "-2", "--pretty=%s", cwd=repo))
출력:
!! .env
feat: 주문 요약 추가
chore: 생성 파일 추적 제외

값 하나를 바꿔 비교

출력 숫자만 2에서 3으로 바꾸고 차이를 확인합니다. 이때 변경은 먼저 작업 폴더에만 존재합니다. git diff -- app.py는 작업 폴더와 색인의 차이를 보여 주므로 - 줄의 2와 + 줄의 3을 읽습니다. git add 뒤에는 같은 명령의 출력이 사라지고 변경이 색인으로 이동합니다. 마지막 커밋 뒤에는 작업 폴더·색인·HEAD 커밋이 다시 같은 파일 상태를 가리킵니다.

In [4]:
# 파일의 출력 숫자 하나를 바꾼 뒤 diff로 실제 변경을 읽습니다.
(repo / "app.py").write_text('print("주문 3건")\n', encoding="utf-8")
print(git("diff", "--", "app.py", cwd=repo))
git("add", "app.py", cwd=repo)
git("commit", "-m", "fix: 주문 건수 수정", cwd=repo)
print(git("log", "--oneline", "-2", cwd=repo))
출력:
diff --git a/app.py b/app.py
index 0bde456..4333761 100644
--- a/app.py
+++ b/app.py
@@ -1 +1 @@
-print("주문 2건")
+print("주문 3건")
81b0b9a fix: 주문 건수 수정
b510f0f feat: 주문 요약 추가

확인할 점 — 첫 상태 출력의 !!는 무시된 파일을 뜻합니다. 첫 두 커밋의 짧은 해시는 실행할 때마다 달라질 수 있지만, 최신 메시지 순서는 동일합니다.

6일부러 실패해 보기

debug.log를 먼저 커밋한 다음 *.log를 무시 규칙에 추가합니다. 별표 *는 파일 이름의 임의 문자열과 일치하므로 debug.log, server.log처럼 .log로 끝나는 파일을 뜻합니다. 파일을 다시 수정하면 git status에 변경 파일로 나타납니다. .gitignore는 이미 커밋한 파일의 추적 상태를 자동으로 없애지 않습니다.

수정 셀의 git rm --cached debug.log는 색인에서만 경로를 제거합니다. 작업 폴더의 실제 파일은 남아 있으며 tracked.exists()가 True로 출력됩니다. 제거와 무시 규칙을 함께 커밋한 뒤 로그 내용을 바꾸어도 추적 파일 목록에는 나타나지 않습니다. git check-ignore -v는 어떤 규칙이 해당 파일에 적용됐는지 줄 번호와 함께 보여 줍니다.

앞의 실행 예제를 실행한 같은 노트북에서 Before 다음 After 순서로 실행합니다. 출력은 실제 실행 결과입니다.

Before — 실패 코드

실패 재현

이미 추적 중인 파일은 나중에 무시 규칙을 추가해도 추적 상태가 유지됩니다. *.log에서 별표 *는 파일 이름의 임의 문자열과 일치하므로 debug.log, server.log처럼 .log로 끝나는 파일을 무시합니다.

In [5]:
# 이미 추적하는 debug.log는 무시 규칙을 추가해도 변경 대상으로 남습니다.
tracked = repo / "debug.log"
tracked.write_text("first run\n", encoding="utf-8")
git("add", "debug.log", cwd=repo)
git("commit", "-m", "chore: 디버그 로그 기록", cwd=repo)
with (repo / ".gitignore").open("a", encoding="utf-8") as file:
    file.write("*.log\n")
tracked.write_text("second run\n", encoding="utf-8")
print("추적 여부:", git("ls-files", "debug.log", cwd=repo))
print("변경 상태:", git("status", "--short", cwd=repo))
출력:
추적 여부: debug.log
변경 상태: M .gitignore
 M debug.log

After — 수정 코드

수정

색인에서만 파일을 제거하면 작업 폴더의 파일은 남고 이후 변경은 무시됩니다.

In [6]:
# --cached는 색인에서만 제거하므로 작업 폴더의 로그 파일은 유지됩니다.
git("rm", "--cached", "debug.log", cwd=repo)
git("add", ".gitignore", cwd=repo)
git("commit", "-m", "chore: 로그 파일 추적 제외", cwd=repo)
tracked.write_text("third run\n", encoding="utf-8")
print("파일 존재:", tracked.exists())
print("추적 결과:", git("ls-files", "debug.log", cwd=repo) or "없음")
print("무시 규칙:", git("check-ignore", "-v", "debug.log", cwd=repo))
assert tracked.exists() and not git("ls-files", "debug.log", cwd=repo)
출력:
파일 존재: True
추적 결과: 없음
무시 규칙: .gitignore:3:*.log	debug.log

7주의할 점과 실무 메모

  • .gitignore는 보안 도구가 아닙니다. 실수로 커밋한 자격 증명을 이 파일에 추가해도 과거 이력은 남습니다. 이 문제는 05절에서 따로 다룹니다.
  • git add .를 사용하기 전에 git status --short와 git diff를 읽습니다. 예상하지 않은 생성 파일과 디버그 문장이 포함됐는지 확인합니다.
  • 서식 변경과 기능 변경이 섞이면 리뷰어가 실제 동작 차이를 찾기 어렵습니다. 가능한 경우 목적별 커밋으로 나눕니다.
  • git rm --cached는 다음 커밋에서 저장소의 파일을 제거합니다. 팀원이 필요한 공용 설정이라면 무시하지 말고 민감한 값만 비운 예시 파일을 제공합니다.

8정리와 다음 절

  • 작업 폴더에서 수정한 내용 중 다음 기록에 포함할 상태를 스테이징 영역에서 고릅니다.
  • 커밋은 한 가지 변경 목적과 그 목적을 설명하는 메시지를 함께 기록합니다.
  • .gitignore는 새 파일의 추적을 예방하며 이미 추적 중인 파일에는 소급 적용되지 않습니다.

다음 학습과 이어지는 지점 — 다음 절에서는 목적이 분명한 커밋을 기능 브랜치에 쌓고, 원격에 게시한 변경을 PR 단위로 비교하고 검토합니다.

9복습 문제

문제와 해설

1. git add와 git commit은 각각 어느 상태를 바꿉니까?

정답: git add는 현재 파일 내용을 스테이징 영역에 선택하고, git commit은 선택된 상태를 새 이력으로 기록합니다.

2. 노트북에서 .env가 !!로 표시된 이유는 무엇입니까?

정답: .gitignore의 .env 규칙과 일치해 Git이 무시한 파일이기 때문입니다.

3. 이미 커밋한 debug.log가 *.log 추가 뒤에도 변경 파일로 나타나는 이유는 무엇입니까?

정답: 무시 규칙은 아직 추적하지 않은 파일에 적용됩니다. debug.log는 이미 추적 중이므로 상태가 유지됩니다.

4. 작업 폴더의 로그 파일을 보존하면서 추적만 중단한 명령은 무엇입니까?

정답: git rm --cached debug.log입니다. --cached가 색인에서만 제거하도록 지정합니다.
